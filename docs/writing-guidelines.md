# 文書の書き方

このリポジトリの文書と、コードに書く定型文の書き方を定める。対象は次の2つである。

- リポジトリの文書: README、AGENTS.md、`docs/`、自作のスキル、subagentの定義、各ディレクトリのREADME
- コードに書く定型文: Issueへのコメント、Discordの通知、Consoleのnotice、通知の理由と次の操作

Claudeが生成する文章(要件定義書、監査レポートと改善提案、PR本文、レビューの指摘、修正の返信、Issue化の提案、コミットメッセージ)の書き方は、[factory-writingスキル](../.claude/skills/factory-writing/SKILL.md)が定める。
生成するときにClaudeが読めるのは注入されるスキルだけなので、スキルを正本にし、この文書には重ねて書かない。

ここに書いていないことは、Googleの開発者向けドキュメントのスタイルガイドと、JTF日本語標準スタイルガイドに従う。日本語の推敲には`yomiyasu`スキルを使う。

## 文書の種類

1つのファイルには1種類の内容だけを書く。種類が混ざると、読み手は自分に要らない記述を読み飛ばしながら探すことになる。

| 種類 | 読み手と目的 | 置き場所 |
| --- | --- | --- |
| 入口 | 初めて来た人が、何のリポジトリで、どこから読むかを知る | README |
| 手順 | 運用する人が、何をすればよいか、失敗したらどうするかを知る | `docs/setup.md`、`docs/operations.md` |
| 説明 | 構成と、その構成をとる理由を理解する | `docs/architecture.md`、`docs/security.md` |
| 仕様 | 変更する人が、内部の挙動と設定値を確かめる | `docs/internals/` |
| 規約 | 書く人が、守ることを確かめる | `docs/coding-guidelines.md`、この文書 |
| エージェント向けの指示 | Claudeが、作業の決まりを知る | AGENTS.md、`.claude/skills/`、`.claude/agents/` |

内部の挙動は、まずコードのコメントとテストで表す。`docs/internals/`には、複数のファイルにまたがる挙動の要約だけを書き、詳細はコードを参照させる。

## 書く内容

### 現在の状態だけを書く

文書には、今の構成、今の手順、今の決まりだけを書く。変更の経緯はコミットとPRに残す。

次のものは書かない。

- 決定や変更の日付(「2026-09-27方針変更」など)
- 誰が決めたか(「ユーザー決定」など)
- 以前の形(「旧形式」「旧来の」「以前は」「〜から変更した」など)
- これから実装する予定の機能の説明。未実装であることは、機能の一覧で1行だけ示す

経緯を書くと、読み手は「前に決めたから守る」と受け取る。前提が崩れた後も、その記述が見直しを止める理由として残り続ける。Claudeは文書の記述を今のルールとして読むので、この影響はClaudeに対して特に強い。

例外は、変更そのものを伝える成果物である。PR本文、コミットメッセージ、要件定義書の「変更履歴」章は、何を変えたかを書くのが目的なので、変更を書く。

### 制約には前提を添える

守らせたい制約には、その制約が必要な理由を1文で添える。理由は現在形で書く。

- 良い例: 「PATにWorkflowsの権限は付けない。`.github/workflows/`を含むpushをGitHubに拒否させるため。」
- 悪い例: 「PATにWorkflowsの権限は付けない(2026-09-26決定)。」

理由が書いてあれば、前提が崩れたときに、制約を外してよいかを人とClaudeが判断できる。理由を書けない制約は、残す必要があるか見直す。

### 1つの情報は1か所に書く

同じ情報を複数の文書に書かない。ほかの文書からはリンクで参照する。複数か所に書くと、片方だけが更新されて食い違う。

| 情報 | 書く場所 |
| --- | --- |
| Claudeが生成する文章の書き方 | `factory-writing`スキル |
| 秘密値の投入コマンド | `docs/setup.md` |
| 資格情報の取得手順(PAT、OAuthトークン、Webhook) | `docs/security.md` |
| miseタスクの一覧 | README(`mise.toml`のタスクと過不足が無いかを検査する) |
| スケジュールの一覧 | `docs/architecture.md`(`*.schedule.yaml`から生成) |
| script・flow・appのpathとsummaryの一覧 | `docs/architecture.md`(各`*.yaml`から生成) |
| 作業項目の状態の一覧 | `docs/architecture.md` |
| PRの章立て | `.github/PULL_REQUEST_TEMPLATE.md` |

設定ファイルやコードから取れる事実は手で書かず、`mise run docs:gen`で生成する。生成した範囲は`<!-- generated:名前 -->`と`<!-- /generated:名前 -->`で囲み、手で編集しない。`mise run lint:docs`は、生成し直した結果と文書が違えば失敗する。

### 追記せず書き直す

挙動が変わったら、既存の記述に条件を書き足さず、その節を今の挙動に合わせて書き直す。前提が崩れた制約は、上書きの注記を足さずに消す。

箇条書きの1項目が2〜3文を超えたら、見出しに上げるか表にする。

## 章立て

- 文書の冒頭に、何の文書かを1〜3文で書く。
- `#`の見出しは1つだけにする。見出しの階層は飛ばさない。
- 見出しは内容が分かる短い名詞句か、作業を表す句にする。見出しにコード表記、日付、括弧の注釈は入れない。識別子は見出し直後の本文に書く。
- 1つの段落には1つの話題だけを書く。
- 箇条書きは、短い項目を並べるときだけ使う。手順は番号付きのリストにする。
- 項目と値の対応や、複数の属性を持つものの一覧は表にする。

## 記法

### コード表記

コード表記(バッククォート)を使うのは、読み手がそのまま入力するものと、画面やファイルでそのまま見るものである。

| 使う | 使わない |
| --- | --- |
| コマンド、ファイル名とパス、設定キー、環境変数、関数・テーブル・フローなどの識別子、入力する値、ラベル名 | 製品名(Windmill、GitHub、Claude)、概念、強調、日本語の語句 |

識別子は、初めて出てくるところで言葉と一緒に1回示し、それ以降は言葉で書く。

- 良い例: 「作業項目は人の対応待ち(`needs_human`)になる。人の対応待ちの作業項目は、Consoleから再実行できる。」
- 悪い例: 「`needs_human`の`work_items`は`retry_work_item`で`failed`と同じく再実行できる。」

状態の値のように識別子が多く出てくるときは、識別子と意味の対応を表にまとめ、本文からはその表を参照する。

### 太字

太字は、画面の項目名(ボタン、タブ、メニュー)に使う。強調に使うのは1つの文書で数か所までにする。太字で始まる箇条書きを見出しの代わりにしない。

### リンク

リポジトリ内の文書へのリンクは相対パスで書く。リンクの文字列は、参照先の文書名か見出しにする。「こちら」とは書かない。

### 注意書き

注意書きにはGitHubのアラート記法を使う。

- `> [!NOTE]`: 補足
- `> [!IMPORTANT]`: 読み飛ばすと作業が成り立たない情報
- `> [!WARNING]`: データの消失や、元に戻せない操作

### コードブロック

コードブロックには言語名を書く(`bash`、`ts`、`yaml`など)。シェルのコマンドは、そのまま貼って実行できる形にする。

## 日本語

- リポジトリの文書は常体で書く。
- コードに書く定型文は、人に読ませて行動を求めるので、敬体(です・ます)で書く。
- 英字や数字と日本語の間にスペースを入れない。
- 1文は1行に書き、「。」の後で改行する。差分で文ごとに変更を追え、長い文に気づきやすいためである。
- 1文は短くする。目安は60字で、100字を超えたら分ける。
- 主語と述語、誰が何をするかが分かるように書く。システムの動作と人の操作を書き分ける。
- 「適切に」「必要に応じて」「など」で条件をぼかさない。
- 前置き、言い訳、締めのあいさつを書かない。
- 絵文字を使わない。

## エージェント向けの文書

AGENTS.mdとスキル、subagentの定義はClaudeが読む。Claudeは書かれていることをすべて今のルールとして扱うので、人向けの文書より短く書く。

- AGENTS.mdは毎回読み込まれる。1つのルールを1〜2行で書き、詳しい説明は`docs/`へのリンクにする。
- スキルの`description`には、いつ使うかと、誰が参照するかを書く。
- スキルの本文は、そのスキルを使う作業に要ることだけを書く。長い参考情報は同じディレクトリの別ファイルに分ける。
- Factoryが生成する文章の書き方は`factory-writing`スキルにまとめ、すべての生成フローに注入する。生成する成果物ごとの章立てや出力の形式は、それぞれのスキルに書く。

## 検査

`mise run lint:docs`で次の検査をする。`mise run check`にも含まれる。

| 検査 | 道具 | 見るもの |
| --- | --- | --- |
| Markdownの構造 | markdownlint(`.markdownlint-cli2.jsonc`) | 見出しの階層、太字の見出し代わり、コードブロックの言語名など |
| 日本語の文章 | textlint(`.textlintrc.json`) | 文の長さ、読点の数、文体の混在、表記の揺れなど |
| このリポジトリの規則 | `scripts/lint-docs.ts` | 経緯の語と日付、見出しのコード表記、長すぎる段落と箇条書き |
| 生成した範囲 | `scripts/docs-gen.ts --check` | 生成し直した結果との差 |

`scripts/lint-docs.ts`は、Factoryの出力を検査する`f/factory/lib/prose_check.ts`と同じ規則を使う。規則を変えるときは`prose_check.ts`を直す。

次のファイルは検査の対象外にする。自分で編集しないか、外から取り込んだものだからである。

- `wmill`が生成するファイル: `AGENTS.wmill.md`、管理スキル、raw appの`AGENTS.md`と`DATATABLES.md`
- 管理スキルの置き場所: `.agents/skills/`と、`.claude/skills/`のうち自作でないもの
- 外から取り込んだスキル: `.claude/skills/yomiyasu/`
- テストの入力: `tests/fixtures/`
