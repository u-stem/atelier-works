# Consoleの画面の表示の原則

Consoleの画面に、表示を足すか残すかを決める原則を定める。
画面を作る人、直す人、レビューする人が読む。
画面ごとの仕様は[Consoleの仕様](internals/console.md)にある。

運用者はConsoleを毎日開く。
判断につながらない表示は、毎日読み飛ばす行になり、読むべき行を埋める。
そのため、表示は足す前に要るかを確かめ、要らないものを削る。
レビューと報告の手順は、[レビューの規則](../.claude/skills/review-loop/rules.md)の「画面の表示」にある。

## 表示の要素ごとに問うこと

見出し、数字、時刻、ラベル、注記、ボタンを、画面の要素と呼ぶ。
要素ごとに、次の3つを問う。

1. 誰が、いつ見るか。
2. 見て何を決めるか。
3. 同じ情報が別の場所に無いか。

1か2に答えられない表示は、判断につながらない。
3が「ある」表示は、重複である。
どちらもノイズなので、削る。

## 情報の置き場所

3つ目の問いは、次の表に照らして決める。
表の「情報」を出す要素が「置き場所」以外にあれば、重複である。
表に無い情報を出すときは、表に1行足し、置き場所を1か所に決める。

| 情報 | 置き場所 | 本体に置かないもの |
| --- | --- | --- |
| 要対応の件数 | サイドバーの要対応の入口のバッジ(幅が狭いときは、メニューのボタンの点と読み上げの名前) | 見出しや案内文での、同じ件数の繰り返し |
| 要対応の種類ごとの件数 | 種類の切り替えのチップの横 | 見出しの副題での、同じ件数の繰り返し |
| 最終更新の時刻と更新の操作 | 画面の見出しの右に1組(複数の取得を持つ画面は、取得できた中で最も古い時刻) | 帯や節ごとの取得の時刻 |
| 自動更新の間隔 | 最終更新の脇 | 帯や節ごとの間隔の注記 |
| 画面全体の更新の失敗 | 見出しの最終更新の脇 | 本体での、同じ失敗の言い換え |
| 値の無い取得の失敗 | 失敗した表や節の位置 | 画面全体に重ねる別の失敗の表示 |
| 前の値を出し続ける取得の失敗 | その節の知らせ | 同じ節の別の場所での繰り返し |
| 選んでいないタブに隠れた段と取得の失敗 | タブの名前の印 | 同じ印を本体の別の場所に重ねること |
| 判定の段(正常、注意、要対応) | 要約の帯のチップ(タブの名前の印は、段が上がったチップの目印で、三角や八角の記号と「注意」「要対応」の語で示す) | 同じ判定を別の語や形で言い換えること、チップの文と件数をタブの印に繰り返すこと |
| 失敗の件数(システムの画面) | 要約の帯の失敗のチップ | 失敗と通知のタブの名前の件数 |
| 予定のジョブ(これから始まる定期実行)の次回 | スケジュールのタブの次回の予定。scheduleに由来しない予定は、どのタブにも出ない | 実行中と待ちのタブでの、予定のジョブの行、予定の件数、案内の注記 |
| flowのステップの順序と、flowごとの出口 | flowの図(`/console/jobs/flows/:name`)。作業項目の詳細の進行の節は、同じ図にステップの状態を重ねる | ジョブの詳細での、定義の順序と起動の関係の繰り返し |
| flowをまたぐ起動の関係 | 起動の図(`/console/jobs/origins/:name`)。定期ジョブから前進の辺でたどれるflowを、段に並べる | flowの図での、複数のflowにまたがる連鎖の繰り返し。作業項目の詳細での、別のflowの図への展開 |
| scheduleの1行の説明と、起動するflow | スケジュールのタブの行の説明と、起動するflowの名前、起動の図へのリンク | ジョブの詳細や他のタブでの、説明の繰り返し |
| scheduleの直近の実行と成否、cron | スケジュールのタブの行。起動の図の起点の箱は、直近の実行の成否と、止まっているかの印だけを出す | 起動の図での、cron、時刻帯、実行の履歴の繰り返し |
| 実行中のflowの今のステップ | 実行中と待ちのタブの行の1行(古い2件まで)。全ステップはジョブの詳細のステップの一覧 | 行の中での、全ステップの一覧と、3件目以降の行のステップ |
| 現在のflowのステップの状態 | 作業項目の詳細の概要の進行の節。現在のflowの図に重ねる | 要件定義やラウンドのタブでの、同じ進行の繰り返し。作業項目が通るflowの経路を別の図にすること |
| 一覧の件数 | 件数を持つタブはタブの名前、タブが件数を持たない一覧は一覧の上 | タブの名前と同じ数を、本体の見出しや先頭の文で繰り返すこと |
| 画面の見出し | 画面の見出し(h1)の1つ | タブの名前と重なる見出し |
| 作業項目の種別(詳細の画面) | 見出しの副題 | 概要の行での繰り返し |
| 状態、種別、ジョブへのリンク(一覧の行) | それが起きた行の中 | 行の外の要約での、同じ状態の繰り返し |
| 配信している版と最後に確かめた時刻 | サイドバーの下部 | 本体での、同じ版や時刻の繰り返し |
| 取り込みの状態と原因 | システムの画面の反映の状態のカード(サイドバーの下部は、失敗か固定中のときの注意の一言だけ) | カードの外での、状態の説明の繰り返し |
| ログイン切れ、Windmillに届かない | 画面の上部の帯 | 各節での同じ内容の警告 |
| 設計書の全文(実装に渡る正規化後の文字) | 設計の承認画面の全文のパネル。原文を既定で置き、見えない文字はコードポイントの表記にして、ここだけに出す。承認の判断は、この原文で行う。読みやすい描画は、承認を止める参考表示として、同じパネルの切り替えで置く | 承認画面での、要約、図、未確定事項(実装に渡らないので出さない)。原文とプレビューの同時の表示。設計書の本文の画面のMarkdownの文字は、この全文の代わりではなく、決着した設計書の文字を確かめる入口が他に無いための例外である |
| 設計書の読み返し(読みやすく描いた本文、図、要約、未確定事項) | 設計書の本文の画面。承認の操作は置かない。本文は、プレビューとMarkdownの文字の2つの形式で読める。要件定義書の本文(承認画面を含む)も、同じ切り替えを持つ | 承認画面での、同じ描画の併置。本文の画面での、承認の操作と、承認の状態の表示 |
| 取り込み時点のIssueと提案の本文 | 要件定義の承認画面の取り込み時点のIssueのパネルと、Issue提案の承認画面の本文のパネル。原文を既定で置き、読みやすい描画は、承認を止める参考表示として切り替えで置く | 原文とプレビューの併置。要件定義書の本文の切り替えとの共有(効き目が逆で、要件定義書のプレビューは承認を止めない) |
| 実装が受け取る文字との違い | 設計書の本文の画面の先頭の固定の注記。文言は、表示の形式ごとに事実に合わせる。承認待ちの設計書には、承認画面へのリンクを添える。設計の承認画面は、全文のパネルの先頭に、表示の形式ごとの注記を1つ置く | 本文の画面の中での、同じ注記の繰り返し。設計の承認画面の止める理由の文での、プレビューが描かないものの列挙の繰り返し |
| 設計書ごとの名前、要約、承認の状態 | 作業項目の詳細の設計タブの行 | 設計書の本文の画面での、承認の状態の表示と設計書の切り替え。設計書の有無を示す、一覧の行の外での繰り返し |
| 設計書の有無(一覧) | 要件定義の一覧の行の「設計あり」のバッジ | 設計書の本文へのリンクの入れ子(行は全体が1つのリンク)。設計の一覧のタブ |
| 設計書の長さと終わりの印 | 全文のパネルの先頭に行数とコードポイント数、全文の外の末尾に終わりの印 | 全文の中での、終わりの印。本文が書く同じ文言と紛れるため |
| 設計の承認を止める理由 | 承認バーの承認ボタンの上の1文。設計書をプレビューで表示中の理由も、同じ1文に置く。見えにくい並びの内訳は、全文のパネルの先頭 | 設計書の依頼の状態(`approval_status`)の描画。依頼の状態は見出しのバッジが出す。プレビューのパネルでの、同じ理由の繰り返し |
| 取り込み時点のIssueと提案の本文をプレビューで表示中の、承認を止める理由 | 承認バーの承認ボタンの上の1文 | プレビューのパネルでの、同じ理由の繰り返し |
| 設計工程が実際に効いているか | 設定タブの設計工程の行。書かれた値が無視されているときと、設定が参照で書かれていて判定できないときは、その理由もここに添える | 通知での、効いている値の言い換え。通知は書き忘れだけを知らせる。一覧の値は書かれたままで、効いている値の代わりにしない |
| 承認を省く進め方であること(新規投入) | 進め方の選択欄の、進め方ごとの1行説明。送信ボタンの文言は、押す場所での確認として別に置く | 注記での、同じ旨の繰り返し |
| 入力の誤りの件数(投入の2画面) | 視覚的に隠した読み上げ専用の領域。最初の誤りの入力欄にフォーカスがすでにあるときだけ書き、誤りの無い送信に進むと消す。誤りの文は、各入力欄の下にある | 画面に見える誤りの要約と件数。フォーカスが移る場面での、領域への同じ件数の重複 |
| PRレビューの投入の結果(始まった、断られた、読めない) | 投入の画面の送信ボタンの下の知らせ。始まった後の進捗は、作業項目の詳細 | トーストでの、同じ結果の言い換え |

取得の失敗は、全体の更新、値の無い節、前の値の節、選んでいないタブ、帯のチップで、役割が違う。
役割ごとに別の行に置き、同じ役割の表示を2か所に置かない。

## 重複の判定

1. 要素が出す情報を、表の「情報」から選ぶ。
2. 要素が「置き場所」以外にあれば、重複と判定する。
3. 表に無い情報は、行を足して置き場所を決める。
   決められなければ削る。
4. 次の「削らないもの」は削らない。
   置き場所の役割と違う場所にあるときは、場所を寄せる。

## 削らないもの

次の表示は、3つの問いに答えられるので、削る対象にしない。
置き場所の表より、こちらを優先する。

- 失敗の表示。
  取得の失敗、前の値であることの知らせ、判定の注意と要対応が当たる。
  運用者が異常に気づけなくなるためである。
- 色に頼らない並記。
  三角と「注意」の併記のように、色の違いを文字や記号でも伝える表示が当たる。
  色を見分けられない人にも、段を伝えるためである。
- 置き場所を持たない取得の失敗。
  見出しにしか出ない失敗が当たる。
  ほかに知らせる場所が無いためである。
- 正常、空、取得済みの明示。
  「すべて片付いています」の文と、一覧が空であることを伝える文が当たる。
  何も出ない画面は、空なのか、未取得なのか、壊れているのかを見分けられないためである。
- 安全上の注記。
  伏せ字の限界を伝える文が当たる。
  読み手が、秘密の扱いを誤らないようにするためである。
- 読み上げ専用の語。
  画面に見えず、読み手の邪魔にならないためである。
- 取り消せない操作の確認。
  誤操作を元に戻せないためである。

## 隠れない条件のために表示を足すとき

失敗や古い値を隠さないために、表示を足したくなることがある。
足す前に、次の順で考える。

1. 既存の場所の値や印を変えて満たせないかを考える。
   例えば、古い節が新しく見えないようにするには、見出しの最終更新を最も古い時刻にする。
   タブに隠れた失敗は、タブの名前の印で示す。
2. 満たせないときだけ、異常のときに出る表示を足す。
   正常な間も出続ける表示は、毎日読み飛ばす行になるためである。
3. 足した表示は、置き場所の表に1行足す。

## 毎日見る目での確認

画面を作る、直す変更は、動くかと崩れないかだけでなく、毎日使う人の目で全画面を読む。
確認は、次のいずれかの方法で行う。
上の方法を優先する。

1. ブランチ版を、ローカルのWindmillに繋いで開く。
   読み取りだけを中継するので、確認では承認、却下、再実行、解除などのボタンを押さず、読むだけにする。
   手順は[ブランチ版のConsoleを確かめる](setup.md#ブランチ版のconsoleを確かめる)にある。
2. 1を行えないときは、開発サーバーと`/api`の差し替えで開く。
   行えないのは、ローカルのWindmillを起動できないときである。
   手順は[Consoleの仕様](internals/console.md#描画の確認)にある。
3. どちらも行えなかったときだけ、PR本文に「未実施」と書く。

開いたら、次の順に確かめる。

1. 経路の表(`console/src/app/screens.ts`)の全経路と、すべてのタブを開く。
2. 異常の無い状態で、上から読む。
   読み飛ばした行は、判断につながらない表示の候補とする。
3. 同じ数字、時刻、語が2か所に見えるものを探す。
   置き場所の表と照らし、置き場所以外の側を重複とする。
4. 候補ごとに、3つの問いに答える。
   答えられないものは削る。

## 表示の一覧

画面を作る、直す変更では、追加と変更をした要素ごとに、次の表を報告に載せる。
設計書にも、同じ形で載せる。
理由の欄には、残す理由が要るときに、置き場所の表と矛盾しない理由を書く。
「何を決めるか」の欄が空か「-」の要素は、欄を満たしていないものとして扱う。

| 表示の要素 | 誰が | 何を決めるか | 他の場所にあるか | 理由 |
| --- | --- | --- | --- | --- |
| 要件定義のタブの名前の件数 | 運用者が、画面を開くたびに | 要件定義を確かめに行くか | 無い | - |
| パレットの「画面」グループの5画面 | 運用者が、キーボードだけで画面を移るとき | どの画面へ移るか | サイドバー | 1文字のキーが既定で無効なので、キーボードだけで入口へ届く経路が要るため。件数と時刻は足さない |
| パレットの固定の行き先(新規投入、PRレビューの投入、要件定義、履歴、スケジュール) | 運用者が、キーボードだけでタブや画面へ移るとき | どのタブか、新規投入かPRレビューの投入を開くか | 作業項目の画面とジョブの画面の中のタブとリンク。PRレビューの投入は、作業項目の一覧のボタンと同じ画面 | サイドバーの1回の押下では届かず、パレットがサイドバーの繰り返しにならないため |
| パレットの「ヘルプ」グループ | 運用者が、ショートカットを確かめるとき | ショートカットを有効にするか | サイドバーの「ショートカット」ボタン | 1文字のキーが既定で無効なので、一覧を開く入口をキー以外に置くため |
| パレットの結果の件数(読み上げ専用) | スクリーンリーダーの運用者が、絞り込むたびに | 候補があるか | 無い | 候補の有無を伝える経路が、読み上げしかないため。見た目には出さない |
| ショートカットの一覧と有効にする切り替え | 運用者が、ヘルプを開いたとき | 使えるキーを知るか、1文字のキーを有効にするか | 無い | 1文字のキーを使う人だけが有効にできるようにするため |
| サイドバーの「ショートカット」ボタン | 運用者が、キーを使わずヘルプを開くとき | ヘルプを開くか | パレットのヘルプの項目 | マウスだけの運用者にも、ヘルプへの入口を置くため |
| 新規投入の「投入しました」の知らせ | 運用者が、投入の直後に | 作業項目の一覧で、投入したIssueが増えていることを確かめるか | 作業項目の一覧に最初の投入のIssueがある | 冪等キーで止めた再送も同じ知らせにする。区別しても、運用者が決めることは変わらないため |
| 新規投入の「投入されたか分かりません」の確認の案内と「確かめたので再送する」 | 運用者が、投入されたか分からない結果が出たとき | 再送するか、入力を破棄するか | 作業項目の一覧とWindmillのジョブ一覧 | 冪等キーが止めるのは、同じタブの同じ送信だけである。それ以外の重複は、運用者が確かめて防ぐため |
| 新規投入の進め方の選択 | 運用者が、新規投入で | どの進め方を選ぶか。承認を省くか | 無い | - |
| 新規投入の進め方ごとの1行説明 | 運用者が、進め方を選ぶとき | 進め方の違いを知り、どれを選ぶか | 無い | 承認を省く旨を、選ぶ根拠として説明に出す。注記には繰り返さない |
| 新規投入の承認を省く注記(通常以外のとき1つ) | 運用者が、承認を省く進め方を選んだとき | PRを人がレビューしてからマージするか | 無い | 承認という安全策を外す選択で、その後の人の関門が強制されないことを知らせるため |
| 新規投入の送信ボタンの文言(通常以外のとき「承認なしで投入する」) | 運用者が、投入を押す前に | 承認なしで投入すると決めて押すか | 進め方ごとの1行説明。説明は選ぶ根拠、ボタンは押す場所での確認で、役割が違う | 題名などの欄のEnterで送るときも、承認なしで投入することを押す前に見せるため。確認のダイアログは足さない |

## 機械的な検査

`tests/scripts/console_display_contract.test.ts`が、画面のソースを走査して、次の3つの違反を検出する。
走査はコメントを除き、折り返したJSXを1つの並びとして読む。
対象は、画面、部品(下位のディレクトリを含む)、表示の文を作る`lib/`のファイル、外枠である。

- 件数つきの見出し。
  タブの名前と件数を近くに並べた文字列である。
  タブを持つ画面の下では、その画面のタブの名前を使う。
  それ以外のファイルでは、3字以上のタブの名前を使う。
- 取得の時刻。
  前置きが「取得」「最終取得」「最終更新」の時刻と、「最終取得」の語である。
  見出し(`PageHeader`)だけが出してよい。
  行の出来事の時刻(「失敗」「発生」「更新」「作成」)は対象にしない。
- 要対応の件数。
  要対応と件数を並べた文字列である。
  メニューのボタンの名前(`lib/navigation.ts`)だけが出してよい。

検査はタブを持つ画面の一覧を持ち、一覧に載らないタブの定義が増えると失敗する。
検査が検出できる範囲は、ソースに文字列として書いた表示に限る。
定数や関数を経由して作った前置きや見出しは、見つけられない。
検査が捕まえる例と通す例は、同じファイルのテストが固定する。
