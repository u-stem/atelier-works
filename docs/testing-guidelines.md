# テストの基準

このリポジトリのテストについて、何をどこまで確かめるか、どう書くか、どう計測するかを定める。
テストを書く人と、Claudeが読む。
コードの書き方は[コーディング規約](coding-guidelines.md)にある。

## 用語

- C0は、命令(行)の網羅である。
- C1は、分岐の網羅である。
- C2は、出典によって意味が割れるため、記号を使わない。
  条件の独立した効き目を確かめるときは、MC/DCと書く。
- テストの区分は、Googleのsmall、medium、largeを使う。

件数の比率(80/15/5など)は目標にしない。
比率はsizeではなくscopeの目安で、チームごとに違うためである。

## 層ごとの強度

重要度に応じて、確かめる強さを変える。
安全規格のDO-178Cが、重要度別に網羅の段階を分けるのと同じ形である。

| 層 | 例 | 確かめること |
| --- | --- | --- |
| 判断の層 | 純粋関数。`f/factory/lib`の判断の部分、`console/src/lib` | C1をレビューで確かめる。差分のC0は90%以上にする |
| 権限・保護パス・秘密値の判定 | 保護パスの判定、許可リストの判定 | MC/DC。条件ごとに、結果を反転させるテストを置く |
| 配線の層 | steps、I/Oのアダプタ、Console API | 入出力の契約と、準正常系・異常系の扱いを確かめる。層ごとのC0の目標は置かない |
| 入口 | Windmillの`main`、画面の組み立て | 判断を持たせない。テストは配線の層に任せる |

差分のC0とC1は、機械では検査していない。
レビューで確かめる。
bunのlcovに分岐の記録が無く、差分の行を切り出す検査も持たないためである。

## 観点の区分

テストの観点を、正常系、準正常系、異常系に分ける。
準正常系は定義が人によって揺れるので、ここで固定する。

| 区分 | 定義 | 例 |
| --- | --- | --- |
| 正常系 | 想定した入力で、目的が果たされる経路 | 許可されたリポジトリのPRを修正する |
| 準正常系 | 想定内の拒否や分岐 | 入力不正、権限なし、対象なし、競合 |
| 異常系 | 想定外の障害 | I/Oの失敗、タイムアウト、外部の5xx |

判断の層は、3つの区分すべてを確かめる。
配線の層は、準正常系と異常系の扱い(再試行、通知、終了コード)を確かめる。

## テストの区分

| サイズ | 対象 | 実行 |
| --- | --- | --- |
| small | DB、ネットワーク、コンテナを使わない単体テスト。外部プロセスの起動と`fetch`は、注入したダミーに差し替える | `mise run test` |
| medium | 実ファイル、子プロセス、実git、composeのPostgres、使い捨てのコンテナなど、1台のマシンの中の依存を使うテスト | `mise run test:db`、`mise run test:check-sandbox` |
| large | 実際にIssueを起票して確かめるE2E | `factory-dev`スキルの「E2Eの動作確認」の手順 |

実ファイル、子プロセス、実gitを使うテストは、sizeの定義上mediumに入る。
一時ディレクトリのリポジトリで実際のgitを実行するテストは、`mise run test`の中で動くが、区分はmediumである。
そのため、`mise run test`には、smallでないテストも含まれる。

## 実DBの検査

`mise run test:db`は、使い捨てのDBにmigrationを適用する。
その後、`scripts/test-db-*.ts`が、アプリのコードが組み立てたSQL文を本物のPostgreSQLで流して確かめる。

`scripts/test-db-queries.ts`は、psqlを文ごとに起動せず、データベースごとの1本のセッションを使い回す。
文ごとに起動すると約2,000回になり、起動が検査の時間の大半を占めるためである。
セッションは`scripts/test-db-session.ts`が持つ。
ほかの`scripts/test-db-*.ts`は、`scripts/test-db-sql.ts`の同期の`execPsql`と`createPsqlClient`で、文ごとに起動する。

`scripts/test-db-queries.ts`を書くときは、次を守る。

- 文を流す呼び出しには`await`を付ける。
  対象は、`execPsqlAsync`と、それを呼ぶ補助関数である。
  呼び出しは1件ずつ流れるので、`await`が抜けても文の順は変わらないが、結果を読む前に次の検査へ進む。
  `tests/scripts/test_db_await.test.ts`が、抜けを検出する。
- セッションの状態を変える文は流さない。
  `SET`、一時表、`PREPARE`、`pg_advisory_*`が当たる。
  状態が次の呼び出しに残るためである。
  `set_config`は、トランザクションに限る第3引数を`true`にしたときだけ使える。
  文のあとにトランザクションかadvisory lockが残ると、セッションはその場で終了する。
  `tests/scripts/test_db_await.test.ts`が、`scripts/test-db-queries.ts`の文字列に、状態を変える文が無いことを確かめる。
  この検査は、そのファイルの文字列だけを見る。
  `f/factory/**`の文と、migrationの関数の本体は見ない。
  今は、それらを通して状態を変える文が無いことを確かめてある。
  足すときは、文のあとの状態の判定の対象を広げるか、この前提を見直す。
- 前の文が完了してから、次の文を流すまでに、2ミリ秒以上が空く。
  DBの時刻はマイクロ秒だが、JSの`Date`はミリ秒に切り捨てる。
  連続する2つの文のDBの時刻が2ミリ秒以上離れれば、切り捨てても別の値になる。
  間隔が短いと、「時刻が変わっていない」ことを確かめる検査が退行を見逃すためである。
  それ以上の間隔に頼る検査は、`Bun.sleep`で間隔を足す。
- 文がエラーで終わるとpsqlが終了するので、セッションは自動で起動し直す。
  エラーは、その呼び出しのエラーの出力だけを載せた例外になる。
- 待ちの上限(1文60秒)、印の読み取りの失敗、エラー以外の終了は、例外にしない。
  標準エラーに理由を出して、終了コード1で終わる。
  例外にすると、検査のcatchが失敗を飲み込むためである。
  待ちの上限のときだけ、そのセッションのbackendを止める。
  止めるのは、使い捨てのDBの、控えたpidと開始時刻に一致する接続だけである。

## テストの書き方

- 1つのテストで、1つの振る舞いを確かめる。
  同じ振る舞いを確かめるexpectは、複数あってよい。
- Arrange-Act-Assertの構成にする。
- `test.each`は、静的な表に限る。
- テストに分岐やループを書かない。

## 書かないテスト

次のテストは書かない。
変更のたびに直すだけで、壊れたときに見つけたい不具合を見つけないためである。

- 人が読む文言の固定。
- 実DBで確かめているSQLの文字列の照合。
- 下位のテストで確かめた内容を、上位で繰り返すテスト。
- 自明なコードのテスト。

残すのは、機械が解析する契約(マーカー、表、設定のキー)だけである。

## カバレッジの計測

`mise run test`は、`coverage/lcov.info`を作る。
`mise run check`は、`test`の後に`bun ./scripts/check-coverage.ts`で全体の行カバレッジの下限を確かめる。
CIの`check`ジョブも、`test`の後に同じ検査をステップとして呼ぶので、ローカルとCIは同じ検査を通る。
測った値はOS(macOSとubuntu)で変わりうる。
OSやrootの有無で、動くテストが分かれるためである。

`test:changed`は計測しない。
部分実行の値は、全体の下限と比べられないためである。
`test:all`は、`test:changed`が全件を要する差分で呼ぶ。
全件を実行するが、日常の確認を速くするために計測を省く。

### 下限の対象と計算

対象は、`f/factory/**`と`scripts/**`の`.ts`から、`*.test.ts`と`*.d.ts`を除いたものである。
lcovには`console/`、`infra/`、`tests/`の補助、テストが作る一時ファイルも混ざるが、母数に入れない。

計算では、対象のファイルごとに、lcovの`DA`(行と実行回数)を行ごとの和集合で数える。
どれかの記録で実行回数が0より大きい行を、実行済みの行とする。
全対象の実行済みの行数を合計し、全対象の実行可能な行数の合計で割る。
`--parallel`で同じファイルが複数回出ても、同じ行を2度数えないためである。

失敗の出力は、全体の値、下限、未実行の行が多い対象の上位5件のパスと割合に限る。
行の中身は出さない。

次のときも、検査は失敗する。

- `coverage/lcov.info`が無い、空、通常のファイルでない、読めない。
- `coverage`がsymlinkなど、実在のディレクトリでない。
- `git ls-files -- coverage`が空でない。
  コミットされたlcovで検査を通せないようにするためである。
- 対象のファイルが1件も無い。

### 下限の置き方

下限は、スクリプトの定数で持つ。
ローカル(macOS)の実測より2ポイント低く置く。
ローカルの1回の計測だけでは、CI(ubuntu)の値とのずれが分からないためである。
CIの値を数回見てから、下限を詰める。

全体のC0は、下限を割らないことを条件にする。
差分のC0を、主な基準にする。

下限を割ったとき、下限を上げるときの手順は、[セットアップ](setup.md#カバレッジの下限)にある。

### bunの挙動と限界

- bunのlcovには、分岐(BRDA)が出ない。
  出るのは、`DA`、関数(`FNF`と`FNH`)、行(`LF`と`LH`)である。
  C1は機械で判定できない。
- bunの`coverageThreshold`は、`lines`と`functions`をファイルごとに判定する。
  全体では判定しない。
  bunが出す全ファイルの全体の値が高くても、閾値を下回るファイルが1つあれば、テストが全部通っても終了コードは1になる。
  この全体の値は、下限の母数(上の「下限の対象と計算」の対象のファイルだけ)とは定義が違い、同じ数字にならない。
  そのため、`bunfig.toml`の`coverageThreshold`は全体の下限に使えない。
- bunは、読み込まれなかったファイルをカバレッジに出さない。
  下限は「読み込まれた対象」の値で、未読み込みのファイルは分母に入らない。
  部分的にテストした大きなファイルを、新しいテストが読み込むようになると、値は下がりうる。
- 対象の接頭辞(`f/factory`、`scripts`)を持つ`.ts`でも、名前に許可する文字(英数字と`._/@+-`)以外を含むファイルは、母数に入らない。気づかないうちに外れる。
- 単独で`bun ./scripts/check-coverage.ts`を呼ぶと、最後に書かれた`coverage/lcov.info`を読む。
  古い実行やパスを絞った実行の結果でも、検査は通りうる。
  lcovが古いか部分的かを、スクリプトは見分けないためである。
- `--coverage-reporter=text`は足さない。
  表が失敗の詳細を検査の出力の末尾から押し出し、Claudeに届かなくなるためである。
- lcovは自前で解析する。
  必要なのは`SF`、`DA`、`end_of_record`の数十行で、依存を足す利点が無いためである。

## 残るリスク

下限の定数と対象の定義は、implementフローのClaudeが書き換えられる。
implementフローは、保護パスの変更を記録するだけで、止めない。
下限を下げたり、対象を狭めたりする変更が、検査を通りうる。
人のレビューが、最後の関門になる。

そのため、`scripts/check-coverage.ts`とそのテストは、保護パスに入れている。
保護パスの変更は、人が書くPRでは「保護パスの変更」の節に、Factoryが作るimplementのPRでは「確認して欲しい点」の`保護パスを変更: <path>`の行に書く。
どちらも、レビューする人が見落とさないためである。

保護パスの外にも、検査を緩める経路が2つ残る。

- 下限の母数は、テストが読み込んだファイルで決まる。
  保護していないテストの削除やimportの変更で母数が変わる。
  部分的にしかテストされていない大きなモジュールを読み込むテストを外すと、値が上がる。
- lcovは、検査されるテストのプロセス自身が書く。
  改ざんを防ぐ関門にならないので、検査はテストの質の保証ではなく、うっかりの退行を拾う網である。

テストを消すimplementのPRは、人のレビューで見る。
保護パスの行が無くても、差分でテストの削除を確かめるためである。
