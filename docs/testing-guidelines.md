# テストの基準

このリポジトリのテストについて、何をどこまで確かめるか、どう書くか、どう計測するかを定める。
テストを書く人と、Claudeが読む。
コードの書き方は[コーディング規約](coding-guidelines.md)にある。

## 用語

- C0は、命令(行)の網羅である。
- C1は、分岐の網羅である。
- C2は、出典によって意味が割れるため、記号を使わない。
  条件の独立した効き目を確かめるときは、MC/DCと書く。
- テストの区分は、Googleのsmall、medium、largeを使う。

件数の比率(80/15/5など)は目標にしない。
比率はsizeではなくscopeの目安で、チームごとに違うためである。

## 層ごとの強度

重要度に応じて、確かめる強さを変える。
安全規格のDO-178Cが、重要度別に網羅の段階を分けるのと同じ形である。

| 層 | 例 | 確かめること |
| --- | --- | --- |
| 判断の層 | 純粋関数。`f/factory/lib`の判断の部分、`console/src/lib` | C1をレビューで確かめる。差分のC0は90%以上にする |
| 権限・保護パス・秘密値の判定 | 保護パスの判定、許可リストの判定 | MC/DC。条件ごとに、結果を反転させるテストを置く |
| 配線の層 | steps、I/Oのアダプタ、Console API | 入出力の契約と、準正常系・異常系の扱いを確かめる。層ごとのC0の目標は置かない |
| 入口 | Windmillの`main`、画面の組み立て | 判断を持たせない。テストは配線の層に任せる |

差分のC0とC1は、機械では検査していない。
レビューで確かめる。
bunのlcovに分岐の記録が無く、差分の行を切り出す検査も持たないためである。

## 観点の区分

テストの観点を、正常系、準正常系、異常系に分ける。
準正常系は定義が人によって揺れるので、ここで固定する。

| 区分 | 定義 | 例 |
| --- | --- | --- |
| 正常系 | 想定した入力で、目的が果たされる経路 | 許可されたリポジトリのPRを修正する |
| 準正常系 | 想定内の拒否や分岐 | 入力不正、権限なし、対象なし、競合 |
| 異常系 | 想定外の障害 | I/Oの失敗、タイムアウト、外部の5xx |

判断の層は、3つの区分すべてを確かめる。
配線の層は、準正常系と異常系の扱い(再試行、通知、終了コード)を確かめる。

## テストの区分

| サイズ | 対象 | 実行 |
| --- | --- | --- |
| small | DB、ネットワーク、コンテナを使わない単体テスト。外部プロセスの起動と`fetch`は、注入したダミーに差し替える | `mise run test` |
| medium | 実ファイル、子プロセス、実git、composeのPostgres、使い捨てのコンテナなど、1台のマシンの中の依存を使うテスト | `mise run test:db`、`mise run test:check-sandbox` |
| large | 実際にIssueを起票して確かめるE2E | `factory-dev`スキルの「E2Eの動作確認」の手順 |

実ファイル、子プロセス、実gitを使うテストは、sizeの定義上mediumに入る。
一時ディレクトリのリポジトリで実際のgitを実行するテストは、`mise run test`の中で動く。
区分はmediumである。
実行する場所と区分の合わないテストを含む。

## テストの書き方

- 1つのテストで、1つの振る舞いを確かめる。
  同じ振る舞いを確かめるexpectは、複数あってよい。
- Arrange-Act-Assertの構成にする。
- `test.each`は、静的な表に限る。
- テストに分岐やループを書かない。

## 書かないテスト

次のテストは書かない。
変更のたびに直すだけで、壊れたときに見つけたい不具合を見つけないためである。

- 人が読む文言の固定。
- 実DBで確かめているSQLの文字列の照合。
- 下位のテストで確かめた内容を、上位で繰り返すテスト。
- 自明なコードのテスト。

残すのは、機械が解析する契約(マーカー、表、設定のキー)だけである。

## カバレッジの計測

`mise run test`は、`coverage/lcov.info`を作る。
`mise run check`は、`test`の後に`bun ./scripts/check-coverage.ts`で全体の行カバレッジの下限を確かめる。
CIは`mise run check`を呼ぶので、ローカルとCIは同じ検査を見る。

`test:changed`は計測しない。
部分実行の値は、全体の下限と比べられないためである。

### 下限の対象と計算

対象は、`f/factory/**`と`scripts/**`の`.ts`から、`*.test.ts`と`*.d.ts`を除いたものである。
lcovには`console/`、`infra/`、`tests/`の補助、テストが作る一時ファイルも混ざるが、母数に入れない。

計算では、対象のファイルごとに、lcovの`DA`(行と実行回数)を行ごとの和集合で数える。
どれかの記録で実行回数が0より大きい行を、実行済みの行とする。
全対象の実行済みの行数を合計し、全対象の実行可能な行数の合計で割る。
`--parallel`で同じファイルが複数回出ても、同じ行を2度数えないためである。

失敗の出力は、全体の値、下限、未実行の行が多い対象の上位5件のパスと割合に限る。
行の中身は出さない。

次のときも、検査は失敗する。

- `coverage/lcov.info`が無い、空、通常のファイルでない、読めない。
- `coverage`がsymlinkなど、実在のディレクトリでない。
- `git ls-files -- coverage`が空でない。
  コミットされたlcovで検査を通せないようにするためである。
- 対象のファイルが1件も無い。

### 下限の置き方

下限は、スクリプトの定数で持つ。
実測より2ポイント低く置く。
ローカルの1回の計測だけでは、CIの値のぶれが分からないためである。
CIの値を数回見てから、下限を詰める。

全体のC0は、下限を割らないことを条件にする。
差分のC0を、主な基準にする。

下限を割ったとき、下限を上げるときの手順は、[セットアップ](setup.md#カバレッジの下限)にある。

### bunの挙動と限界

- bunのlcovには、分岐(BRDA)が出ない。
  出るのは、`DA`、関数(`FNF`と`FNH`)、行(`LF`と`LH`)である。
  C1は機械で判定できない。
- bunの`coverageThreshold`は、`lines`と`functions`をファイルごとに判定する。
  全体では判定しない。
  全体が行83%、関数85%でも、80%未満のファイルが97件あり、テストが全部通ったのに終了コードが1になった。
  `bunfig.toml`の閾値は、全体の下限に使えない。
- bunは、読み込まれなかったファイルをカバレッジに出さない。
  下限は「読み込まれた対象」の値で、未読み込みのファイルは分母に入らない。
- `--coverage-reporter=text`は足さない。
  表が失敗の詳細を検査の出力の末尾から押し出し、Claudeに届かなくなるためである。
- lcovは自前で解析する。
  必要なのは`SF`、`DA`、`end_of_record`の数十行で、依存を足す利点が無いためである。

## 残るリスク

下限の定数と対象の定義は、implementフローのClaudeが書き換えられる。
implementフローは、保護パスの変更を記録するだけで、止めない。
下限を下げたり、対象を狭めたりする変更が、検査を通りうる。
人のレビューが、最後の関門になる。

そのため、`scripts/check-coverage.ts`とそのテストは、保護パスに入れている。
PR本文の「保護パスの変更」に載るので、レビューする人が見落とさない。
