# テストの基準

このリポジトリのテストについて、何をどこまで確かめるか、どう書くか、どう計測するかを定める。
テストを書く人と、Claudeが読む。
コードの書き方は[コーディング規約](coding-guidelines.md)にある。

## 用語

- C0は、命令(行)の網羅である。
- C1は、分岐の網羅である。
- C2は、出典によって意味が割れるため、記号を使わない。
  条件の独立した効き目を確かめるときは、MC/DCと書く。
- テストの区分は、Googleのsmall、medium、largeを使う。

件数の比率(80/15/5など)は目標にしない。
比率はsizeではなくscopeの目安で、チームごとに違うためである。

## 層ごとの強度

重要度に応じて、確かめる強さを変える。
安全規格のDO-178Cが、重要度別に網羅の段階を分けるのと同じ形である。

| 層 | 例 | 確かめること |
| --- | --- | --- |
| 判断の層 | 純粋関数。`f/factory/lib`の判断の部分、`console/src/lib` | C1をレビューで確かめる。差分のC0は90%以上にする |
| 権限・保護パス・秘密値の判定 | 保護パスの判定、許可リストの判定 | MC/DC。条件ごとに、結果を反転させるテストを置く |
| 配線の層 | steps、I/Oのアダプタ、Console API | 入出力の契約と、準正常系・異常系の扱いを確かめる。層ごとのC0の目標は置かない |
| 入口 | Windmillの`main`、画面の組み立て | 判断を持たせない。テストは配線の層に任せる |

差分のC0とC1は、機械では検査していない。
レビューで確かめる。
bunのlcovに分岐の記録が無く、差分の行を切り出す検査も持たないためである。

## 観点の区分

テストの観点を、正常系、準正常系、異常系に分ける。
準正常系は定義が人によって揺れるので、ここで固定する。

| 区分 | 定義 | 例 |
| --- | --- | --- |
| 正常系 | 想定した入力で、目的が果たされる経路 | 許可されたリポジトリのPRを修正する |
| 準正常系 | 想定内の拒否や分岐 | 入力不正、権限なし、対象なし、競合 |
| 異常系 | 想定外の障害 | I/Oの失敗、タイムアウト、外部の5xx |

判断の層は、3つの区分すべてを確かめる。
配線の層は、準正常系と異常系の扱い(再試行、通知、終了コード)を確かめる。

## テストの区分

| サイズ | 対象 | 実行 |
| --- | --- | --- |
| small | DB、ネットワーク、コンテナを使わない単体テスト。外部プロセスの起動と`fetch`は、注入したダミーに差し替える | `mise run test` |
| medium | 実ファイル、子プロセス、実git、composeのPostgres、使い捨てのコンテナなど、1台のマシンの中の依存を使うテスト | `mise run test:db`、`mise run test:check-sandbox` |
| large | 実際にIssueを起票して確かめるE2E | `factory-dev`スキルの「E2Eの動作確認」の手順 |

実ファイル、子プロセス、実gitを使うテストは、sizeの定義上mediumに入る。
一時ディレクトリのリポジトリで実際のgitを実行するテストは、`mise run test`の中で動くが、区分はmediumである。
そのため、`mise run test`には、smallでないテストも含まれる。

## 実DBの検査

`mise run test:db`は、使い捨てのDBにmigrationを適用する。
その後、`scripts/test-db-*.ts`が、アプリのコードが組み立てたSQL文を本物のPostgreSQLで流して確かめる。

`scripts/test-db-queries.ts`は、psqlを文ごとに起動せず、データベースごとの1本のセッションを使い回す。
文ごとに起動すると約2,000回になり、起動が検査の時間の大半を占めるためである。
セッションは`scripts/test-db-session.ts`が持つ。
ほかの`scripts/test-db-*.ts`は、`scripts/test-db-sql.ts`の同期の`execPsql`と`createPsqlClient`で、文ごとに起動する。

`scripts/test-db-queries.ts`を書くときは、次を守る。

- 文を流す呼び出しには`await`を付ける。
  対象は、`execPsqlAsync`と、それを呼ぶ補助関数である。
  呼び出しは1件ずつ流れるので、`await`が抜けても文の順は変わらないが、結果を読む前に次の検査へ進む。
  `tests/scripts/test_db_await.test.ts`が、抜けを検出する。
- セッションの状態を変える文は流さない。
  `SET`、一時表、`PREPARE`、`pg_advisory_*`が当たる。
  状態が次の呼び出しに残るためである。
  `set_config`は、トランザクションに限る第3引数を`true`にしたときだけ使える。
  文のあとの判定が見るのは、トランザクションとadvisory lockだけである。
  どちらかが残っていると、セッションはその場で終了する。
  `tests/scripts/test_db_await.test.ts`は、`scripts/test-db-queries.ts`の文字列に、状態を変える文が無いことだけを確かめる。
  `f/factory/**`の文と、migrationの関数の本体は見ない。
  今は、それらを通して状態を変える文が無いことを確かめてある。
  `f/factory/**`とmigrationに、状態を変える文を足すときは、文のあとの判定の対象を広げるか、この前提を見直す。
- 前の文が完了してから、次の文を流すまでに、2ミリ秒以上空ける。
  DBの時刻はマイクロ秒だが、JSの`Date`はミリ秒に切り捨てる。
  連続する2つの文のDBの時刻が1ミリ秒を超えて離れれば、切り捨てても別の値になる。
  空ける間隔は2ミリ秒で、この条件を満たす。
  サーバーとの時計のずれまでは保証しない。
  間隔が短いと、「時刻が変わっていない」ことを確かめる検査が退行を見逃すためである。
  2ミリ秒を超える間隔に頼る検査は、`Bun.sleep`で間隔を足す。
- 文がエラーで終わるとpsqlが終了するので、セッションは自動で起動し直す。
  エラーは、その呼び出しのエラーの出力だけを載せた例外になる。
- 待ちの上限(1文60秒)、印の読み取りの失敗、エラー以外の終了は、例外にしない。
  標準エラーに理由を出して、終了コード1で終わる。
  例外にすると、検査のcatchが失敗を飲み込むためである。
  待ちの上限のときだけ、そのセッションのbackendを止める。
  止めるのは、使い捨てのDBの、控えたpidと開始時刻に一致する接続だけである。

## テストの書き方

- 1つのテストで、1つの振る舞いを確かめる。
  同じ振る舞いを確かめるexpectは、複数あってよい。
- Arrange-Act-Assertの構成にする。
- `test.each`は、静的な表に限る。
- テストに分岐やループを書かない。

## 書かないテスト

次のテストは書かない。
変更のたびに直すだけで、壊れたときに見つけたい不具合を見つけないためである。

- 人が読む文言の固定。
- 実DBで確かめているSQLの文字列の照合。
- 下位のテストで確かめた内容を、上位で繰り返すテスト。
- 自明なコードのテスト。

残すのは、機械が解析する契約(マーカー、表、設定のキー)だけである。

## カバレッジの計測

`mise run test`は、`coverage/lcov.info`を作る。
`mise run check`は、`test`の後に`bun ./scripts/check-coverage.ts`で、全体と層ごとの行カバレッジの下限と、lcovに出ない対象を確かめる。
CIの`check`ジョブも、`test`の後に同じ検査をステップとして呼ぶので、ローカルとCIは同じ検査を通る。
測った値はOS(macOSとubuntu)で変わりうる。
OSやrootの有無で、動くテストが分かれるためである。

`test:changed`は計測しない。
部分実行の値は、全体の下限と比べられないためである。
`test:all`は、`test:changed`が全件を要する差分で呼ぶ。
全件を実行するが、日常の確認を速くするために計測を省く。

### 下限の対象と計算

対象は、`f/factory/**`と`scripts/**`の`.ts`から、`*.test.ts`と`*.d.ts`を除いたものである。
対象の一覧は`git ls-files`で作る。
追跡しているファイルと、追跡していない(gitignoreされていない)ファイルの両方を入れる。
作業ツリーから消しただけでステージしていないファイルは、入れない。
lcovには`console/`、`infra/`、`tests/`の補助、テストが作る一時ファイルも混ざる。
一覧に無いものは集計に含めない。

計算では、対象のファイルごとに、lcovの`DA`(行と実行回数)を行ごとの和集合で数える。
どれかの記録で実行回数が0より大きい行を、実行済みの行とする。
全対象の実行済みの行数を合計し、全対象の実行可能な行数の合計で割る。
`--parallel`で同じファイルが複数回出ても、同じ行を2度数えないためである。

層ごとにも同じ計算で値を求める。
層はパスの接頭辞で決める。
どの対象もどれかの層に入る。

| 層 | 出力に出る名前 | 含むパス |
| --- | --- | --- |
| lib | `f/factory/lib` | `f/factory/lib/`の下 |
| steps | `f/factory/steps` | `f/factory/steps/`の下 |
| `f/factory`のその他 | `f/factory (other)` | 上の2つ以外の`f/factory/`の下。直下と、それ以外の深い階層を含む |
| scripts | `scripts` | `scripts/`の下。`host_apply/`と`claude-hooks/`を含む |

層ごとの下限は全体の値に隠れる低い層を拾うために置く。

失敗の出力は、全体と各層の値と下限、割った層の未実行の行が多い対象の上位5件、未読み込みの総数と上位5件のパスに限る。
層がどれも下限を満たし、全体だけが割ったときは、全体から未実行の行が多い対象の上位5件を出す。
割った層、全体、未読み込みの理由は、出力の最後に置く。
失敗の出力は1800字に収める。
Factoryの修正のプロンプトに載るのは、検査の出力の末尾2000字である。
末尾にはmiseのタスク失敗の行が付くので、その分を引いた字数にして、理由を残す。
行の中身と、gitの標準エラーは出さない。
成功したときも、全体と各層の値と下限を1行ずつ出す。
CIのログで値を見て、下限を詰めるためである。

次のときも、検査は失敗する。

- `coverage/lcov.info`が無い、空、通常のファイルでない、読めない。
- `coverage`がsymlinkなど、実在のディレクトリでない。
- `git ls-files -- coverage`が空でない。
  コミットされたlcovで検査を通せないようにするためである。
- 対象を列挙する`git ls-files`が失敗する。
- 一覧のパスを作業ツリーで調べられない。
  パスが無いとき(途中の要素がファイルに替わっている場合を含む)は、一覧から外すだけで失敗にしない。
  権限やsymlinkの輪など、ほかの理由で調べられないときは、無いものとして外さず失敗にする。
  失敗の文には、エラーのコード名だけを載せ、パスは載せない。
- 対象のファイルが1件も無い。
- 下限の表に載る層のどれかで、対象が1件も無い。
- 名前に許可する文字(英数字と`_./@+-`)以外を含む対象がある。
  数えられないまま、検査から外れるのを防ぐためである。
  出力には件数と、エスケープしたパスの上位5件を出す。
- lcovに出ない対象がある。
  詳しくは次の「未読み込みの対象」にある。

### 未読み込みの対象

bunは、テストが読み込まなかったファイルをlcovに出さない。
そのファイルの実行可能な行数は分からず、推定の行数で0%として数えると検査が甘くなる。
そのため、一覧にあるのにlcovに出ない対象があれば、失敗にする。
テストを書いていない新しいscriptは、その場で止まる。

対象ごとの直し方は次のとおりである。

| 対象 | 直し方 |
| --- | --- |
| `scripts/` | そのファイルをimportするテストを足す |
| `f/factory/` | `tests/lib/coverage_load_all.test.ts`が、追跡している対象をすべて動的importで読み込む。読み込みの失敗を直す。追跡していない新しいファイルなら`git add`する。`git add`できない環境(Factoryの検査の中など)では、そのファイルをimportするテストを足す |
| bunのテストで読み込めないもの | 読み込めない理由があるときだけ、`NOT_LOADABLE_BY_BUN_TEST`に足す |

`NOT_LOADABLE_BY_BUN_TEST`は、`scripts/test-db-*.ts`の4ファイルである。
読み込むと本物のDBに文を流すので、`mise run test:db`が実行する。
一覧のパスは集計に含めない。
一覧には次の条件を満たすパスだけを入れられる。
条件を外れると、検査は失敗する。

- パスが`scripts/test-db-`で始まる形である。
- パスが、作業ツリーにある対象の一覧に入っている。
  古い除外を残さないためである。
- パスがlcovに出ていない。
  読み込めるようになったのに除外が残るのを防ぐためである。

読み込みのテストは、読み込む間だけ次のAPIを差し替える。
差し替えるのは、`fetch`、`Bun.spawn`、`Bun.spawnSync`、`Bun.$`、`Bun.write`、`Bun.connect`、`Bun.serve`である。
差し替えた関数は、呼ばれると呼び出しを記録し、例外を投げる。
読み込みが終わると、`finally`で元に戻す。
1回でも呼ばれたら、テストが失敗する。
記録するのは、APIの名前と、読み込んでいたファイルのパスだけである。
引数、ヘッダー、`env`は記録せず、出力に載せない。

この検出には限りがある。
衛生のための検査で、セキュリティの境界ではない。

- 検出するのは、このテストが最初にそのモジュールを読み込んだときに、差し替えたAPIが同期で呼ばれた場合だけである。
  同じworkerで先に別のテストが読み込んだモジュールは、キャッシュから返るので検出しない。
- `node:child_process`、`import { spawn } from "bun"`の束縛、`rmSync`、`process.exit`、読み込みの後に動くコールバックは検出しない。
- 読み込みの間に後から動くマイクロタスクの呼び出しは、次のモジュールの名前で記録されることがある。
- symlinkの検査は、ファイル自身にしか効かない。
  途中のディレクトリのsymlinkは見ない。
- `f/factory`はWindmillが`main`を呼ぶ形なので、最上位に処理を置かない前提に立つ。
  最上位に処理を持つファイルを足すときは、読み込みのテストが止める。
- 読み込む対象は追跡している(コミット済みかステージ済みの)ファイルまでである。
  追跡していない新しいファイルは、`git add`の後に初めて読み込まれる。
  `git add`の前は、そのファイルが未読み込みとして失敗する。
  `mise run pull`で取り込んだ新しいファイルが、確かめる前に、テストの中で実行されないようにするためである。
  `mise run pull`で書き換わった追跡済みのファイルは、読み込まれる。

読み込むだけで、最上位の宣言の行は実行済みになり、関数の本体は実行されない。
読み込まれただけのファイルは0%にならず、宣言の行の分の値が出る。
効果は層ごとに違う。
`scripts/`は、importするテストの無い新しいファイルが、その場で止まる。
`f/factory`は、読み込みのテストがすべて読み込むので、未読み込みでは止まらない。
新しいファイルは、宣言の行が実行済みになり、その割合に応じて層の平均を上げる場合と下げる場合がある。
ファイルごとの下限は、このカバレッジの検査では扱わない。
宣言の行が多いファイルを足すと、テストが無い場合でも層の値が上がりうる。
ファイルごとの下限が入るまでは、人のレビューで見る。

実行可能な行が0行のファイル(型だけのモジュールなど)も、読み込まれればlcovに出る。
`import type`は実行時に消えるので、読み込みにならない。
そのようなファイルが`scripts/`にあるときは、実行時にimportするテストが要る。

### 下限の置き方

下限は、スクリプトの定数で持つ。
全体の下限と、層ごとの下限の表がある。
ローカル(macOS)とCI(ubuntu)の値の小さいほうから、2ポイント下げて置く。
幅は2ポイントに固定し、層によって変えない。
値は小数第2位で切り捨てる。
たとえば小さいほうの値が84.7599%なら、82.75%に置く。
OSで値が変わりうるので、小さいほうに合わせる。
CIの値が出るまでは、ローカルの値で仮置きし、CIの値が出たら置き直す。
CIは成功したときも各層の値を出すので、ログで確かめる。

全体のC0は、下限を割らないことを条件にする。
差分のC0を、主な基準にする。

下限を割ったとき、下限を上げるときの手順は、[セットアップ](setup.md#カバレッジの下限)にある。

### bunの挙動と限界

- bunのlcovには、分岐(BRDA)が出ない。
  出るのは、`DA`、関数(`FNF`と`FNH`)、行(`LF`と`LH`)である。
  C1は機械で判定できない。
- bunの`coverageThreshold`は、`lines`と`functions`をファイルごとに判定する。
  全体では判定しない。
  bunが出す全ファイルの全体の値が高くても、閾値を下回るファイルが1つあれば、テストが全部通っても終了コードは1になる。
  この全体の値は、下限の母数(上の「下限の対象と計算」の対象のファイルだけ)とは定義が違い、同じ数字にならない。
  そのため、`bunfig.toml`の`coverageThreshold`は全体の下限に使えない。
- bunは、読み込まれなかったファイルをカバレッジに出さない。
  検査は一覧にあるのにlcovに出ない対象を失敗にする(上の「未読み込みの対象」)。
- 対象の接頭辞(`f/factory`、`scripts`)を持つ`.ts`でも、名前に許可する文字(英数字と`_./@+-`)以外を含むファイルは、数えられない。
  検査は、そのファイルがあれば失敗にする。
- 単独で`bun ./scripts/check-coverage.ts`を呼ぶと、最後に書かれた`coverage/lcov.info`を読む。
  古い実行やパスを絞った実行の結果でも、検査は通りうる。
  lcovが古いか部分的かを、スクリプトは見分けないためである。
- `--coverage-reporter=text`は足さない。
  表が失敗の詳細を検査の出力の末尾から押し出し、Claudeに届かなくなるためである。
- lcovは自前で解析する。
  必要なのは`SF`、`DA`、`end_of_record`の数十行で、依存を足す利点が無いためである。

## 残るリスク

下限の定数と対象の定義は、implementフローのClaudeが書き換えられる。
implementフローは、保護パスの変更を記録するだけで、止めない。
下限を下げたり、対象を狭めたりする変更が、検査を通りうる。
人のレビューが、最後の関門になる。
残るリスクは[R-COV-01](security-risks.md#r-cov-01)である。

そのため、`scripts/check-coverage.ts`とそのテストは、保護パスに入れている。
保護パスの変更は、人が書くPRでは「保護パスの変更」の節に、Factoryが作るimplementのPRでは「確認して欲しい点」の`保護パスを変更: <path>`の行に書く。
どちらも、レビューする人が見落とさないためである。

検査を緩める経路が残る。

- [R-COV-02](security-risks.md#r-cov-02)
- [R-COV-03](security-risks.md#r-cov-03)
- [R-COV-04](security-risks.md#r-cov-04)

残るリスクは[R-COV-05](security-risks.md#r-cov-05)である。

テストを消すimplementのPRは、人のレビューで見る。
保護パスの行が無くても、差分でテストの削除を確かめるためである。
