# Consoleのシステムの画面の仕様

Consoleのシステムの画面(反映の状態、保留と凍結、通知の履歴、設定)の仕様を書く。
システムの画面を変更する人が読む。
画面をまたぐ仕様と、ほかの画面の仕様の置き場は、[Consoleの仕様](../console.md)にある。

## システムの画面

この画面は、Software Factory自身の状態を、先頭の要約の帯と、4つのタブに分けた節で出す。
結論は帯で読み、根拠はタブの節で読む。
書き込みは、保留と凍結の設置と解除、反映の承認と却下だけで、ほかの節は読むだけである。
通知の解決は、要対応の画面の詳細で行う。

更新のボタンと最終更新は、画面の見出しに1組だけ置く。
ボタンは、下の4つの取得(`console_holds`、`system_status`、`deployments`、`summary`)を取り直す。
設定のタブを開いた後は、設定の取得(`console_config`)も取り直す。
最終更新は、設定を除く4つの取得のうち、取得できたものの最も古い時刻である。
設定は自動で取り直さないので、最終更新には数えない。
数えると、タブを開いた後は、見出しの時刻が設定を取った時刻で止まるためである。
取得中と失敗には、設定も含める。
保留と凍結と要約は定期に取り直し、`system_status`は取り直さない。
そのため、最も古い時刻は、たいてい`system_status`の取得を指す。
節と帯は、取得の時刻を出さない。
画面の見出しの「最終更新」と重なるためである。
4つの取得は、保留と凍結、状態、要約、更新履歴の順に始める。
workerは1台で直列に処理する。
帯とタブの判定に使う3つを先に済ませ、帯が読まない更新履歴を最後にするためである。
節は、読み込みが続く間は骨組み([画面の切り替え](../console.md#画面の切り替え))、取得に失敗したときは節の中に失敗の表示と「もう一度取得する」を出す。
401のときは、上のバナーが知らせるので、節にはログインを促す文だけを出す。
1つの節が失敗しても、ほかの節は表示する。

反映の状態、workerの負荷、情報の通知、解決済みの通知、作業項目に紐づかない失敗は、`console_query`の`system_status`viewを1回取って揃える。
この5つの節は、取得の結果を分け合う。
画面が取得を1つだけ持ち、見出しの更新で一緒に取り直す。
同じ取得を重ねて取り直すと、互いを打ち切るためである。
定期には取り直さない。
通知の解決が、この取得を読み直すので、要対応の画面で解決した通知を、未解決のまま出さない。
各一覧は200件までで、200件に達した節には、これより古いものは表示していない場合がある旨を添える。
情報の通知、解決済みの通知、更新履歴(すべて表示したとき)、監査の失敗の一覧と、作業項目に紐づかない失敗のflowごとの失敗は、取得した件数を10件ずつのページに分ける([ページ送り](../console.md#ページ送り))。
ページに分けても取得の上限は変わらない。
上限の注記は、全ページを通した一覧にかかる。
型は`src/api/guards/systemStatus.ts`の型ガードで確かめる。
形がずれると、画面は`invalid_response`の失敗を出す。
backendの型との一致は、`tests/scripts/console_system_contract.test.ts`が確かめる。

### 要約の帯

帯は、タブの上に置き、タブと一緒に本文のスクロール枠の先頭に置く。
幅が768px(md)以上で、高さが640px(40rem)以上のときだけ、枠の上端に貼り付ける。
貼り付くと、タブを替えても、本文をスクロールしても、帯とタブが見える。
条件の片方でも満たさない画面では、貼り付けず、本文と一緒にスクロールさせる。
帯とタブが画面の大半を占め、本文が読めなくなるためである。
条件はCSSの媒体条件で書く(`STICKY_HEADER_CLASS`)。
画面の大きさで親を入れ替えない。
入れ替えると、切り替えのたびに本文を描き直し、スクロール位置を失うためである。
貼り付いた部分は、背景を持ち、下をくぐる本文が透けない。
貼り付いた部分の高さと16pxの余白は、節への移動とページ送りのスクロールが差し引く。
見出しや一覧の先頭が、帯とタブの下に止まる。
帯はチップの並びで、折り返す。
チップは、段の記号、短い名前、件数か一言を並べる。
チップは、節が使う既存の判定を段と文に写したもので、新しいしきい値は作らない。
段は正常、注意、要対応の3つで、読めないチップは「判定なし」にする。
段は、色だけに頼らず、記号と文字でも示す。
記号は、正常が丸のチェック、注意が三角の警告、要対応が八角の警告、判定なしが横線である。
段の語は、読み上げにだけ出す。
読み上げは名前、文、段の語の順で、「要対応 3件 注意」のように結論を先に伝える。
チップの文と段は、`src/lib/summaryBand.ts`の純関数が決める。

| チップ | 文と段の決め方 |
| --- | --- |
| 要対応 | 要対応の画面のバッジと同じ件数。1件以上は注意、0件は正常。押すと要対応の画面へ移る |
| 保留と凍結 | 有効な行があれば注意(意図した停止の周知)、無ければ正常。期限切れの行は何も止めないので、有効な件数から外し、段に影響させない。保留か凍結を読めない場合と、取得が丸ごと失敗した場合は要対応。読めないときは、何が止まっているかを判断できないためである |
| 直近の反映 | 反映が失敗なら要対応。ホストの作業が残っているかは、未解決の通知の件数で決める。1件以上なら注意で、押すと要対応の画面のその通知へ移る。無ければ、成功は正常、記録が無ければ判定なし |
| Consoleの取り込み | 版の固定だけが注意(意図した状態)。失敗、更新の停止、状態を読めない場合、知らない状態は要対応。取り込みが止まっている可能性があるためである。取り込み済みは正常 |
| 失敗 | 監査の失敗(後の監査で報告済みでないもの)が1件以上あれば注意。監査が0件で、作業項目に紐づかない失敗が無ければ正常。紐づかない失敗だけが残るときは、正常にせず、判定なしにして件数を添える |

ホストの作業は、反映の記録の印(`needs_host_action`)では判定しない。
作業が済んでも、記録の印は残るためである。
数えるのは、`summary`の未解決の通知のうち、種類が`host_action_required`のものである(`src/lib/hostActionNotices.ts`)。
通知は、ホストでの反映が済むと自動で解決される。
件数は、残っている作業の数と一致するとは限らない。
通知は版を持たず、反映の回数分だけ溜まることがある。
`summary`の一覧は上限までしか取らない。
全件の数が一覧より多いときは、件数を「N件以上」と書く。
一覧にホストの作業の通知が1件も無いときは、残っているかを言い切れないので、反映の記録の印で代え、「通知を確認できません」と添える。
通知の取得に失敗して値が無いときも、記録の印で代え、「通知の取得に失敗」と添える。
通知を取得中のあいだは、記録の印で代えず、取得中にする。
作業が済んでいても、残っているように見えるためである。

作業項目に紐づかない失敗を判定しないのは、直近7日の窓に残る過去の記録で、今対応が要るかを決められないためである。
同じ失敗が繰り返されるflowは、対応が済んだ後も、窓から外れるまで件数に残る。
判定すると、対応しても注意が消えない。
一方、監査の失敗は、後の監査で報告済みのものを件数から外す。
そのため、対応の後は0件になる。

要対応と失敗の件数は、帯に必ず出る。
情報の通知とworkerの負荷は、判定が無く、行動につながらないので、帯に置かない。
内容は各タブの節にある。
取得中のチップは「取得中です」、取得に失敗したチップは「取得できませんでした」と出し、判定しない。
ただし、保留と凍結は、取得が丸ごと失敗したときも要対応にする。
一部を読めないときと同じ扱いである。
待ちの間は、段を決めない。
取得中の文は、待ちが300msを超えるまで出さず、チップの名前だけを出し、記号と文を隠す。
短い取得で文が一瞬だけ出るのを避け、値が届いたときにチップの大きさを動かさないためである。
規則は[画面の切り替え](../console.md#画面の切り替え)のスケルトンと同じである(`useDelayedVisible`)。
取得に失敗したチップは、待たずに出す。
取り直しに失敗しても前の値が残っているときは、前の値で判定して出し、「前の値(取得に失敗)」と添える。
失敗の件数は、片方の取得が読めなくても、もう片方の件数を出す。
読めない側は「取得中」か「取得できません」と書く。

帯は、取得の時刻を出さない。
画面の見出しの「最終更新」が、画面の全取得のうち最も古い時刻を示すためである。
取得の失敗は、時刻を消しても残る。
取得に失敗したチップは「取得できませんでした」、前の値を出すチップは「前の値(取得に失敗)」と書く。
取得に失敗した節は、失敗の表示と「もう一度取得する」を出す。
定期のジョブが動いているかは、この帯では判定しない。
ジョブの画面のスケジュールのタブで、有効かどうかと次回の予定、直近の実行を読める。
workerが動いているかも、この帯では判定しない。
止まったときは通知で知らせる([workerの負荷](#workerの負荷))。

チップは関係する節へのリンクである。
押すと、その節があるタブを開き、節の見出しへ移る。
失敗のチップは、監査の失敗が無く、作業項目に紐づかない失敗だけがあるときは、その節へ移る。
直近の反映のチップは、未解決のホストの作業の通知があるときは、要対応の画面のその通知へ移る。
移動は、本文のスクロール枠だけを動かし、見出しへフォーカスを移す。
URLの`?tab=`は替えるが、履歴は積まない。
チップの行き先にあるたたんだ部分は、作業項目に紐づかない失敗の最新のflowの組だけである。
節へ移るときは、その`<details>`を開く。
移った先で本文が見えるようにするためである。
情報の通知と解決済みの通知は、チップの行き先ではないので、移るときも開かない。
修飾キーを押したクリックと中ボタンは、リンクの既定に任せ、新しいタブで開く。

### タブの構成

タブは状態、失敗と通知、履歴、設定の4つで、開くタブは`?tab=failures`、`?tab=history`、`?tab=config`で選ぶ。
状態は名前を持たない。
共通の規則は[タブ](../console.md#タブ)にある。

| タブ | 節 |
| --- | --- |
| 状態 | 保留と凍結、反映の状態、workerの負荷 |
| 失敗と通知 | 監査の失敗、作業項目に紐づかない失敗、情報の通知(たたむ) |
| 履歴 | 更新履歴、解決済みの通知 |
| 設定 | 設定の全項目 |

タブに分ける理由は、1つの縦並びが長すぎることである。
全部を縦に並べると、実データで約5200px(画面6枚以上)になる。
たたむだけでは、短くならない節が残る。
分けた後の長さは、各タブの本体が1〜2画面に収まる目安である。

選んでいないタブは、初めて開くまで描かない。
開いた後は隠して残し、スクロール位置と、折りたたみの状態を保つ。
更新履歴と解決済みの通知は描くのが重いので、開かないタブの描画を避ける。
取得は画面が持ち、帯が読む値は常に取得する。
節を分けても、取得の数は増えない。
設定の取得だけは、設定のタブを初めて開いた後に始める。
帯とタブは枠の先頭にあり、貼り付くときは本文の上に重なる。
本体は、どのタブも帯とタブの下から始まる。

### 失敗が隠れないための条件

タブで分けても、失敗を見落とさないよう、次を守る。

- 帯の失敗のチップに、失敗の件数を必ず出す。
  監査の失敗の未解決の件数と、作業項目に紐づかない失敗の件数は、開いているタブにかかわらず読める。
  タブの名前には件数を添えない。
  同じ数字を2か所で確かめさせないためである
- どちらかの件数が読めないときは、読めない側を「取得中」か「取得できません」と書く。
  読めた側の件数は出す
- 作業項目に紐づかない失敗が取得の上限(200件)に達したときは、帯の文に「200件以上」と書く。
  上限で切れた件数を、少なく見せないためである
- 失敗と通知のタブに、失敗のチップが注意のとき、三角と「注意」の印を付ける。
  紐づかない失敗だけが残るときは、判定しないので印を付けない。
  選んでいても外さない
- 状態のタブに、そのタブのチップのうち、反映が注意以上のとき(ホストの作業が残っているとき、反映が失敗したとき)、または保留と凍結か取り込みが要対応のとき、最も重い段の印を付ける。
  注意は三角と「注意」、要対応は八角と「要対応」である。
  保留の有効な行や、取り込みの版の固定のように意図した状態(注意)は、印を付けない。
  いつも印が付くと、本物の注意が埋もれるためである
- 印の語と記号は、印を付けるチップの段から決める。
  帯のチップと同じ形で、色だけに頼らない
- 取得が失敗したタブには、八角と「取得に失敗」の印を付ける。
  段の印があるタブは、「注意・取得に失敗」のように並べる。
  段の印があるタブは、選んでいても並べる。
  値が前の取得のものだと伝えるためである
- 要対応の画面は、この画面のタブとは別で、変えない

次の純関数のテストが、これらの条件を固定する。

- 帯の写像: `src/lib/summaryBand.ts`
- タブの印: `src/lib/systemTabs.ts`
- 取得の失敗とタブの結び付け: `src/screens/system/systemScreenView.ts`

### 保留と凍結

この節は、Factoryのマージと反映を止めている保留、スケジュールの凍結、deployの保留を出し、人が確認して置き、解除できる。
システムの画面で書き込みを持つのは、この節だけである。
置く操作は、節の先頭にある「保留や凍結を置く」のボタンが開くダイアログで行う。
置く操作の仕様は、次の「置く」にある。
ホストの端末のCLIでも置ける([保留の内部仕様](../holds.md))。

取得は`console_holds`の1回で、保留の表、凍結の変数、全停止の変数を別々に読む。
どれかが読めなくても、ほかは表示する。
取得の結果は`src/api/holdsQueries.ts`の`useHolds`が持つ。
保留は期限で終わるので、画面が見えている間は`summary`と同じ120秒ごとに取り直す。
見出しの更新も、この取得を取り直す。
型は`src/api/guards/holds.ts`の型ガードで確かめる。
形がずれると、節は`invalid_response`の失敗を出す。
backendの型との一致は、`tests/scripts/console_holds_contract.test.ts`が確かめる。

節の先頭に、全停止の区画を出す。
止まっていないときは、説明の1文と「全停止」のボタンだけを出す。
止まっているときは、置いた時刻、操作者、理由と「解除」のボタンを出す。
全停止の変数が壊れているときは、止まっている扱いにして、解除のボタンを出す。
全停止の状態を読めないときは、止まっているかが分からない旨と理由に加え、ホストの端末で`mise run stop`と`mise run stop:release`が使える旨の固定の1文を出す。
読めない間は、画面から操作できないためである。
古いbackendが状態を返さない間は、区画を描かない。
「全停止」は、理由の入力欄を持つ確認のダイアログを通す。
理由が使えない間は、確認のボタンを押せない。
全停止の確認のダイアログには、止めた`*_enabled`の名前を記録し、解除の後にホストの`mise run stop:restore`で戻すことを並べる。
解除も確認のダイアログを通し、設定の`*_enabled`を戻さないので機能は動き出さないことと、戻すコマンドを並べる。
全停止の結果の知らせは、止めた名前を記録できなかったときと、記録に載らなかった名前があるときに、警告の色で名前を出す。
その名前は戻すコマンドで戻らないので、手で戻すよう伝える。
全停止と解除は、`console_stop_all`と`console_stop_all_release`が記録する。
置く操作と解除は同じキーでロックし、終わると保留と凍結の取得とシステムの状態を取り直す。
急ぐときのホストのコマンドは、断りの知らせに添える。

全停止の区画の次に、保護パスの変更の反映の承認待ちを出す。
行には、版、保護パス(50件まで。超えた分は件数だけ)、止めた時刻、承認と却下のボタンを出す。
承認待ちが無いときは出さない。
読めないときは、承認待ちなしとは書かず、反映が止まったままである旨と理由を出す。
承認と却下は、確認のダイアログを通して、`console_deploy_decide`が記録する。
承認待ちの読み取りは`console_holds`の取得に含め、版とパスは文字としてだけ描く([反映の承認の内部仕様](../deploy-approvals.md))。

保留と凍結の両方が読めて、有効な行が1つも無いときは、2つのカードを1行にたたむ。
「有効な保留と凍結はありません」と、置き方の案内を出す。
どちらかが読めなかったときと、どちらかに行があるときは、次の2つのカードを出す。
カードは成功と失敗を別々に出す。

| カード | 出す行 | 並び |
| --- | --- | --- |
| 保留 | 有効な保留。マージの保留と、読む処理が無い取り込みの保留 | マージ、取り込みの順に、それぞれ期限が近い順 |
| 凍結とdeployの保留 | 有効なスケジュールの凍結とdeployの保留 | deployの保留、スケジュールの凍結の順に、それぞれ期限が近い順 |

行には、種類、対象、理由、置いた主体、期限と残り時間、「解除」のボタンを出す。
deployの保留の対象は、反映全体(`self_update`、push、migration)と書く。
取り込みの保留は、読む処理が無いので何も止めていないと注記する。
期限を過ぎた行と、有効の条件を満たさない未解除の行は返さない。
それらは止める効果が無く、`mise run hold:list`が見せる。
期限は画面の時計で判定する。
取得の間に期限が来た行は、解除のボタンを外し、「期限切れ」と出す。
DBの時計と画面の時計のずれで、境界に数秒の誤差が出る。
解除はidで行い、idは再利用されないので、別の行を解除することはない。

行の理由、対象、置いた主体は、DBや変数に書ける主体が決める信頼できない文字列である。
backendが制御文字と書式文字を空白にして切り詰め(理由は200字、置いた主体は100字、対象は200字)、画面が`displayableIssueText`で同じ検査をやり直す。
文字としてだけ描き、リンク、画像、Markdownにしない。
書字方向は行ごとに隔離する。
通知とログには、理由と置いた主体を載せない。

読めなかったときは、保留なしと取り違えないよう、次の表示にする。

| 状況 | 表示 |
| --- | --- |
| 読めて、行が無い | 「有効な保留はありません」。成功のときだけ出す |
| 保留の表が無い | 警告。migrationが未反映で、dependabotの自動マージとローカルのマージが止まる旨 |
| 保留の表を読めない | 警告と「もう一度取得する」。理由は折りたたむ。止まる旨を添える |
| 保留の表に壊れた行がある | 警告。一覧を出せない旨、止まる旨、理由に含まれる回復の手順をそのまま開いて出す。解除のボタンは出さず、`mise run hold:list`を案内する |
| 凍結の変数を読めない | 警告と「もう一度取得する」。理由に含まれる回復の手順を開いて出す。反映が要る回の`self_update`が止まる旨を添える |
| 取得全体の失敗 | 節の失敗の表示。401はログインを促す文だけ |
| 前回の値があり、取り直しに失敗 | 値を出したまま、古い旨の注意を出す |

失敗の種類と、行の範囲と置いた主体の種類は、文字列で受ける。
知らない値は、決まった文言に落とす。
backendが先に新しい値を反映した間も、一覧の全体が消えないためである。
文言は`src/lib/labels.ts`に集め、表示の判断は`src/lib/holdsView.ts`の純関数が持つ。

#### 置く

「保留や凍結を置く」を押すと、確認のダイアログを開く。
入力は、種類、対象、期限(分)、理由の4つである。
種類は、マージの保留、deployの保留、スケジュールの凍結から選ぶ。
deployの保留は対象を持たないので、対象の欄を出さない。

| 種類 | 対象 | 期限の上限 |
| --- | --- | --- |
| マージの保留 | `owner/repo`の形 | 1440分 |
| deployの保留 | 無し | 120分 |
| スケジュールの凍結 | `f/factory/名前`の形のスケジュール | 1440分 |

期限の欄には、入力できる範囲(「1分から120分まで」のような文)を常に添える。
範囲は、置くscriptの上限と同じ値を`src/lib/holdPlace.ts`が持つ。
一致は、`tests/scripts/console_hold_place.test.ts`が固定する。
期限の問題の文(短すぎる、上限を超えている)は、範囲の数字を繰り返さない。
理由は必須で、200字までである。
制御文字と書式文字は使えない。
入力が正しくない間は、確認のボタンを押せなくし、問題のある欄の下に文を出す。
空の欄は、まだ入力していないだけなので、問題の文を出さない。

ダイアログは、種類ごとに、置いたときの効果と、終わり方(期限と解除)を並べる。
確認のボタンは破壊的な色にしない。
期限が来れば必ず終わり、解除でき、置き直せるためである。
フォーカスは「取り消す」に置く。
画面の検査は案内で、境界は置くscriptが同じ検査で確かめる。

確認すると`console_hold_place`を呼ぶ。
操作者と置く主体は引数に取らない。
scriptが実行文脈から操作者を導き、置く主体は人に固定する。
二重の送信は、種類と対象ごとのロックで止める。
置く操作は再試行しない。

| 結果 | 知らせ |
| --- | --- |
| 置いた | 成功の色。止められるスケジュールの凍結には、止められるようになる時刻を添える。凍結が、止められる前、または残りの下限(5分)を割る前に終わるときは添えない |
| 置いたが、読み直しで確認できなかった | 警告の色。置いた行が見えない、または書く前に有効だった他の行が欠けているとき。一覧を取り直して確かめる旨 |
| 断った | 情報の色。理由は`writeNotices.ts`の対応表にある |
| 失敗 | 失敗の色 |

置いた後は、保留と凍結の取得と、システムの状態を読み直す。
同じ対象に有効な保留か凍結がすでにあれば、重ねずに断る。
ローカルのセッションの保留や凍結があるときも断る。
保留と凍結の件数が上限に達しているときも断る。
断りの文には、内部の用語(行、主体)を使わない。
二重の送信を止めるロックの鍵は、種類と、小文字にそろえた対象である。
スクリプトが対象を小文字にそろえて置くためである。

確認の流れ(ダイアログを開く、入力を整える、確認を通ったときにだけ書き込みを呼ぶ)は、`src/screens/system/usePlacement.ts`の純関数が持つ。
開いただけでは書き込みを呼ばず、整っていない入力では呼ばない。
フックは、この関数に状態と書き込みを渡すだけにする。

#### 解除

「解除」を押すと、確認のダイアログを開く。
ダイアログは、種類、対象、理由、置いた主体、期限と残り時間、id、解除の効果を出す。
フォーカスは「取り消す」に置く。
確認のボタンは破壊的な色にしない。
人以外(セッション、Factory)が置いた行には、置いた理由を確かめてから解除する旨を添える。

| 種類 | 解除の効果 |
| --- | --- |
| マージの保留 | dependabotの自動マージとローカルのセッションのマージが、次の取得から再開する |
| 取り込みの保留 | この範囲を読む処理が無いので、動作は変わらない。表の掃除として解除できる |
| deployの保留 | `self_update`が次の回から反映を再開し、見送っていた変更をまとめて反映する。ほかに有効なdeployの保留が残るときは、その件数を添え、すべて外れるまで再開しない旨を出す |
| スケジュールの凍結 | 次の反映(`self_update`の追従)で、このスケジュールがリポジトリの定義に戻る。有効なdeployの保留があるあいだは、追従も待つので戻らない旨を、その件数とともに添える |

確認の入力(`yes`の打鍵)は求めない。
ログインした管理者が、対象、期限、効果を見て押す操作であり、フォーカスの既定が「取り消す」で、解除は止めが外れる向きだが期限で必ず終わるためである。

確認すると、保留は`hold_release`、凍結とdeployの保留は`freeze_release`を呼ぶ。
操作者は引数に取らない。
scriptが実行文脈から導き、解除する主体は人に固定する。
結果は、トーストで知らせる。

| 結果 | 知らせ |
| --- | --- |
| 解除した | 成功の色 |
| 解除した。通知を残せなかった | 警告の色。誰が解除したかはジョブの記録で確かめる旨 |
| 解除したが、解除の前に有効だったかを確認できなかった(`active_unknown`) | 警告の色。通知を残せなかったときは、その旨の文も続く |
| 期限切れの行を片付けた | 成功の色。通知は残さない |
| すでに解除されていた、すでに終わっていた | 情報の色。複数のタブからの再送も成功として返る |
| 解除を確認できなかった | 警告の色。一覧を取り直して確かめる旨 |
| 失敗 | 失敗の色 |

解除の後は、保留と凍結の取得と、解除の通知が出るシステムの状態を読み直す。
読み直せなければ、一覧が更新されるまで、その行を止めたままにする。
二重の送信は、行ごとのロック(`writeTargetKey`の`hold`と`freeze`)で止める。
ロックは同じタブの中だけである。
解除は再試行しない。

#### ブランチ版の確認

検証用サーバー(`scripts/console-branch-server.ts`)は、ブランチ版のConsoleを、ローカルのWindmillに繋いで開かせる。
操作の手順は、[ブランチ版のConsoleを確かめる](../../setup.md#ブランチ版のconsoleを確かめる)にある。
ブラウザから見るとConsoleとWindmillが同じオリジンになるので、ブランチ版のConsoleが、運用者のCookieのまま本物のWindmillのAPIを呼ぶ。
既定は読み取りだけで、要求を次のように振り分ける。

| 要求 | 扱い |
| --- | --- |
| `/console/*` | `console/dist`を返し、無いパスはSPAの`index.html`に落とし、assets、draw.ioのファイル、`status.json`は無ければ404にし、Caddyと同じCSPなどのヘッダーを付ける |
| `/console` | `/console/`へ308で飛ばす |
| 符号化した区切りと`..`を含む`/console/`のパス | 400にする |
| `/api/`の外のGET、HEAD、OPTIONS | `--upstream`(既定は`http://127.0.0.1:8080`)へ中継する(ログインの画面と静的な資源が当たる) |
| `/api/`の下の読み取りのGET、HEAD、OPTIONS | 許可リストにある経路だけ中継する(`/api/version`、`/api/users/whoami`、ジョブ1件を読む`jobs_u`の経路) |
| 読み取りの5つのscriptを実行するPOST | 中継する |
| ほかの要求 | 403にし、人が`--allow-writes`を付けたときだけ中継する |

Windmillは、GETでもscriptを同期で実行できる(`GET /api/w/{workspace}/jobs/run_wait_result/p/{path}`)。
`windmill-client` 1.817.0のOpenAPIに、この経路がGETとPOSTの両方で載っている。
そのため、GETとHEADも許可リストで絞る。
実行、再開、取り消し、再実行、ストリーム、エンドポイントの経路(`/api/r/`)、webhookを含むパスは、メソッドを問わず403にする。
ConsoleがWindmillを呼ぶのは、読み取りのscriptを実行するPOSTと、`/console/status.json`のGETだけである。
`/api/`のGETは使わない。

読み取りの5つは、`console_query`、`console_holds`、`console_jobs`、`console_schedules`、`console_config`である。
`tests/scripts/console-branch-server-readonly.test.ts`が、次を固定する。

- 5つが相対importで辿るファイルに、SQLの書き込みとWindmillの書き込みや実行のAPIが無い。
- 書き込みと読み取りが同居する共有の部品(`lib/db.ts`、`lib/holds.ts`、`lib/freeze_apply.ts`)から取り込む名前が、読み取りの関数に限られる。
- 呼ぶ関数(`fetchDeploymentRows`、`sumAgentCostSince`、`listActiveHolds`、`readFreezeState`)の本文に、書き込みが無い。
- `console_holds`は、凍結の変数の書き込みの口(`writeVariable`)を組み立てるが、読む経路は`readVariable`だけを呼ぶ。

`console_holds`は、保留、凍結、全停止の状態、反映の承認待ちを読むだけである。
解除、承認、却下、全停止は別のscriptが行う。

要求は、次の検査も通る。

- Hostは、`127.0.0.1:<port>`か`localhost:<port>`だけを通す。
  DNSリバインディングで別の名前から届いた要求を断るためである。
- Originは、このサーバー自身のオリジンのときだけ、中継先のオリジンに置き換えて中継する。
  ほかは403にする。
- 中継の要求の`Sec-Fetch-Site`が`cross-site`か`same-site`なら403にする。
- 転送元を名乗るヘッダー(`Forwarded`、`X-Forwarded-*`、`X-Real-IP`)とhop-by-hopのヘッダー(`Connection`が名指しするものを含む)は、中継先へ渡さない。
- 中継先の`Location`は、このサーバーのパスに直す。
  `//host`のようなプロトコル相対の形にならないよう、先頭の`/`を1つにそろえる。
- Bunのfetchは、渡した`Sec-Fetch-*`を落とさずに中継先へ送る(模擬の中継先で実測した)。
  ブラウザが付けた値のまま、中継先のCaddyの規則に届く。

`--allow-writes`は、端末で人が「yes」と入力したときだけ有効になる。
標準入力が端末でないとき(agentの起動やパイプ)は、起動に失敗する。
有効な間は、起動時に目立つ警告を標準出力に出し、全応答に`x-branch-server-writes: on`を付ける。

反映後の実機と違う点は、`status.json`を配信しないことである。
そのため、サイドバーの版の情報は出ない。
CSPなどのヘッダーは、`infra/Caddyfile`の`console_headers`と`drawio_headers`と同じ値を付け、テストが一致を確かめる。

#### 描画の確認

アクセシビリティの機械で確かめられる範囲は、[ブラウザでのa11y検査](../console.md#ブラウザでのa11y検査)が毎回確かめる。
ここは、その検査が見ない見た目と文言を、目で確かめる手順である。

画面の描画は、Playwrightで確かめる。
Consoleの開発サーバー(`bun run --cwd console dev`、`http://localhost:5173/console/system`)は`/api`を中継しない。
そのため、`/api/w/factory/jobs/run_wait_result/p/**`をすべて`page.route`で差し替える。
`console_holds`だけでなく、システムの画面が呼ぶ`console_query`の`system_status`、`deployments`、`summary`も差し替える。
実際のWindmillには何も届かないので、解除のボタンを押しても、本物の保留は解除されない。

状態ごとに応答を変えて、次を確かめる。

- 保留、取り込みの保留、deployの保留、スケジュールの凍結が並ぶ表示と、何も無い表示
- 保留の表が無い、保留を読めない、保留の表が壊れている、凍結の変数を読めない表示
- `<a href>`を含む理由と、書字方向を変える制御文字を含む置いた主体が、文字のまま出ること
- 長い理由と長い対象の折り返し
- 期限が数十秒後の行が、画面の時計の更新(30秒ごと)で「期限切れ」に変わること
- 401のときの、ログインを促す文
- ライト、ダーク、狭い幅
- 確認のダイアログと、開いた直後のフォーカスが「取り消す」にあること
- 実行中のロックと、解除の結果のトースト

撮影した画像はリポジトリに置かない。

### 区画への移動

要対応の通知の詳細から、システムの画面の区画へ、1回の操作で移れる。
区画は全停止、反映の承認待ち、保留の3つで、`?section=`のidは`stop-all`、`deploy-approvals`、`holds`である。
idと、区画が属するタブの表は`src/lib/systemSections.ts`にある。
3つの区画はどれも状態のタブにある。

#### 通知の移動先

通知の案内(`src/lib/noticeGuide.ts`)は、種類ごとに移動先を持てる。
移動先は区画とボタンの名前である。
タブは区画から決まるので、移動先には持たない。
どの種類が移動先を持つかは、文面を持たない小さな表(`src/lib/systemTargetKinds.ts`)が決める。
バッジの件数は、この表だけを読む。
ボタンの名前は区画ごとに通知の案内が持つ。
次の3つの種類が移動先を持つ。

| 種類 | 区画 | ボタンの名前 |
| --- | --- | --- |
| `deploy_approval_required` | 反映の承認待ち | システムの画面の反映の承認待ちへ |
| `dependabot_merge_held` | 保留 | システムの画面の保留と凍結へ |
| `stop_all_active` | 全停止 | システムの画面の全停止へ |

設定の変更を求める通知(`config_misfit`など)は、移動先を持たない。
操作がConsoleのシステムの画面ではなく、Windmillの設定リソースの編集だからである。
移動先を持たない種類と、表に無い種類は、ボタンを出さない。
作業項目の失敗へ移るボタンは、[通知](attention.md#通知)にある。

通知の詳細は、移動先があり、未解決のときだけ、次の操作の文の下にボタンを出す。
ボタンは`/system?section=<区画>`へのリンクで、新しいタブでは開かない。
状態のタブは既定なので、`?tab=`は付かない。
組む側と読む側は、同じ定数(`SECTION_PARAM`)を使う。

#### 移動の受け取り

システムの画面は`?section=`から区画を読む。
許可するid以外の値は無視する。
区画があるあいだは、URLの`?tab=`と食い違っていても、区画のタブを開く。
移動を待つあいだに、人が別のタブを選んだら、移動を捨てて、選んだタブを開く。
同じタブを選び直したときは、移動を続ける。
帯のチップを押したときは、同じタブへのチップでも、待っている区画を捨てる。
遅れて着地する区画が、人の操作の後で、スクロールとフォーカスを奪わないためである。

移動は、区画の部品が描かれたときに、区画が自分で受ける(`useSectionArrival`)。
取得の決着や、読み込み中の骨組みが残る時間を、画面が見積もらないためである。
受けた区画は本文のスクロール枠だけを動かして自分の要素を見せ、フォーカスを移して、画面へ知らせる。
画面は`?section=`を消し、区画のタブを`?tab=`に書く(履歴は置き換える)。
消したときにタブが戻らないようにするためである。
再読み込みや戻る操作で、再び移ることはない。

移動で見せる要素は`id`(`system-section-`に区画のidを付けた値)と`tabindex="-1"`を持つ。
Tabの順には入らず、見出しと同じく、キーボードのフォーカスのときだけ輪を出す。

| 区画 | 見せる要素 | 区画が描かれる状態 |
| --- | --- | --- |
| 反映の承認待ち | 見出し | 承認待ちがあるとき。読めないときも描く |
| 保留 | 保留のカードの見出し | 保留か凍結に有効な行があるとき。読めない源があるときも描く |
| 全停止 | 状態ごとの根の要素(止まっていないときは説明とボタンの行、止まっているときと壊れているときは名前を持つ枠、読めないときは説明の枠) | 状態を返すbackendのとき |

保留の区画で見せる要素は、保留のカードの見出しだけである。
「凍結とdeployの保留」のカードは対象にしない。

保留と凍結の取得が走っている間は、区画へ移動を渡さない。
取得の途中の値は取り終えると変わるためである。
取得が済んで、値が区画を描かないと言うときは、節の見出し(保留と凍結)へ着地して、`?section=`を消す。
強調はしない。
承認待ちが無いとき、承認待ちか全停止を返さない旧版のbackendのとき、保留と凍結に有効な行が無い(1行にたたむ)ときが当たる。
取得に失敗して値が無いときも、見出しへ着地する。
区画を描くと言う値なら、区画の部品が描かれるまで待つ。
骨組みが残る間も待つ。
取得に失敗しても前の値が残っているときは、前の値の区画が描かれるので、その区画が受ける。

判定は、`src/screens/system/systemScreenView.ts`の純関数が持ち、テストが固定する。

#### 強調

着地した区画は操作を求める状態のときだけ、数秒強調する。
承認待ちが1件以上、全停止が止まっている状態か壊れている状態、保留の行が1件以上のときである。
承認待ちが無いときや、止まっていないとき、保留の行が無いときは、強調しない。
読めない状態でも強調しない。
判定は、取得が済んだ値だけで行う。
古い値で、承認済みの区画を強調しないためである。

強調は区画の枠の`data-highlighted`属性で表し、`src/index.css`が背景と輪郭の静的な色で描く。
アニメーションは使わない。
動きを減らす設定の利用者では、アニメーションが一瞬で終わり、強調が見えなくなるためである。
動くのは背景の色の遷移だけで、長さは動きのトークンを読み、動きを減らす設定は全要素の規則が受ける([動きのトークン](../console.md#動きのトークン))。
部品側では`motion-reduce`と`matchMedia`を使わない。

強調を外す時機は、画面が持つタイマーで、4秒である。
続けて移動したときは、前のタイマーを取り消す。
前の強調の時間切れが後の強調を外さないためである。
画面を離れたときは、タイマーを取り消し、以後は状態を更新しない。
StrictModeで効果が繰り返されても、取り消した制御は通知しない。
タイマーの制御は時間を計る道具を差し替えられる形で切り離してあり、偽のタイマーでテストする。

#### サイドバーのバッジ

システムの入口のバッジは`summary`の未解決の通知のうち、重要度が要対応で、移動先を持つ種類を数える(`src/lib/systemActionCount.ts`)。
今は、`deploy_approval_required`と`stop_all_active`が当たる。
`dependabot_merge_held`は、重要度が情報で、要対応の一覧に出ないので数えない。
保留と凍結の取得(`console_holds`)は、サイドバーでは呼ばない。
取得の数と負荷を増やさず、旧版のbackendでも動くためである。

件数は要対応のバッジと同じ通知から来るので、システムのバッジは要対応のバッジを超えない。
要対応の合計には足さない。
`Screen`の`badge`は要対応の合計に数え、`destinationBadge`は数えない。

#### 限界

- 通知の一覧が上限で切れているときは、一覧にある分だけを数える。
  件数は下限で、`+`は付けない。
  切れていて、システムの通知が一覧に1件も無いときは、バッジを出さない。
  未解決の要対応の通知が200件を超え、最も古い承認待ちの通知が一覧から落ちると、バッジが出ない。
  この状態は、要対応の画面自体が使えない状態で、通知の掃除が先に要るので受け入れる
- 全停止の通知は置いてから最大5分遅れて出て、解除してから最大5分遅れて消える(検出器の間隔)。
  `summary`の取り直しは最大2分遅れる。
  バッジが実際の状態とずれる時間がある
- 反映の承認待ちの依頼の記録と、通知の記録は、別の呼び出しである。
  通知の記録が失敗すると、承認待ちがあっても、バッジと通知のボタンは出ない
- `dependabot_merge_held`は情報の通知で、保留が解けても、最大7日、通知の詳細にボタンが出る。
  移動先の保留の区画に行は無く、見出しへ着地する
- 区画が描かれないまま着地したときは、見出しへ着地するだけで、強調しない。
  別のタブで承認済みになったときが当たる
- 却下しても通知は残るので、バッジは通知が解決されるまで出続ける。
  承認待ちの区画は無く、見出しへ着地する。
  操作はConsoleの外で、mainへ戻すPRを作ることで、通知の詳細の補足が説明する

### 反映の状態

次の3行を、1枚のカードに出す。

- 反映した版。
  `system_status`が読んだ、反映済みの版の記録である。
  読めなければ「不明」にする
- 直近の反映。
  日時、前の版から今の版、結果、ホストの作業の残りを出す。
  ホストの作業は、帯の「直近の反映」と同じく、未解決の通知の件数で出す(`describeHostAction`)
- Consoleの取り込み。
  状態を出す。
  取り込んだ版と最後に確かめた時刻は、サイドバーの下部が示すので、このカードでは繰り返さない

取り込みの状態は、`console_fetcher`が書く`status.json`から、backendが判定する。
状態の語は、取り込み済み、取り込みに失敗、版を固定中のどれかで、知らない値は「不明な状態」にする。
判定が更新の停止のときは、語に「(古い記録)」を添える。
色は、判定が失敗なら失敗の色、更新が30分以上無いか版を固定していれば警告の色(30分は`FETCHER_STALE_MINUTES`と同じ値で、契約テストで一致を確かめる)、それ以外は成功の色にする。
状態を読めないときは、警告の色で「状態を読めません」と理由を出す。
失敗の分類と運用者の次の操作があれば、補足の行に出す。
ホストの作業の表示は、通知があれば「ホストの作業N件が残っています」、通知が全件読めて無ければ「ホストの作業は不要」にする。
通知を取得中のあいだは「確認中」と出す。
通知を読めないときと、一覧が切れて確かめられないときだけ、反映の記録の印で代える。

### 更新履歴

更新履歴は、Software Factoryが自分を更新した反映の一覧である。
`console_query`の`deployments`viewから、直近90日のものを新しい順に100件まで取る。
自動では取り直さず、見出しの更新で取り直す。
最初は新しい3件だけを出し、「すべて表示」を押すと全件を開く。
全件は10件ずつのページに分け、「新しい3件だけ表示」で戻る。
切り替えのボタンは1つで、3件のときも全件のときも、同じ位置の同じ要素である。
ラベルと`aria-expanded`だけが替わる。
押した後も、フォーカスがボタンに残るためである。
ボタンは`aria-controls`で一覧を指す。
ホストの作業が残っているかは、この節では数えない。
記録の印は、作業が済んでも残り、残っている作業の数にならないためである。
残っている作業は、帯の「直近の反映」と、状態のタブの印が示す。
直近の反映は「反映の状態」の節にもあるので、更新履歴は過去の記録を読む場所である。

反映1回を1枚のカードにする。
カードには、次を出す。

- 日時。
  相対時刻で、日本時間の絶対時刻をツールチップに添える
- 版。
  前の版と今の版を、7桁の短い形で「前 → 今」と書く。
  前の版が無い初回は「初回 → 今」にする
- 結果。
  「反映済み」か「失敗」で、知らない値は「不明な状態」にする
- ホストの作業の要否。
  要るときは警告の色にする
- 含まれるPR。
  作り手のバッジ、題名、番号を1行にする
- 失敗の理由。
  失敗した反映だけに、先頭の120字を「理由:」に続けて出す

失敗の理由は、外部のコマンドの出力を含みうる信頼できない文字列なので、文字としてだけ出し、リンクやマークアップにはしない。
理由を記録する前の失敗の反映には、「理由の記録はありません」と出す。

作り手のバッジは、「Software Factory」か「人」である。
backendが確かな情報(マージしたブランチの名前)を読めたときだけ付ける。
読めなければ、バッジを付けない。
読み手が判断に使えない印で、行を埋めるだけだからである。
含まれるPRが無い反映には、「含まれるPRの記録はありません」と出す。
PRを記録する前の反映と、PRを取り出せなかった反映も、同じ表示になる。
区別できないのは、取り出せなかったときも空で記録するためである。
失敗した反映は、PRを取り出す前に止まるので、PRを持たない。
空の配列で記録する。
記録するPRは1回の反映につき100件までなので、100件に達した反映には、これより古いPRは表示していない場合があると添える。
件数がちょうど100のときも同じ注記になる。
題名は、GitHubのUIでマージしたコミットの本文の1行目である。
別の形でマージしたコミットは、題名が空になるか、PRとして記録されない。

題名はコミットメッセージ由来の信頼できない文字列なので、Reactが文字として描く。
マークアップとしては解釈しない。
番号は、GitHubのPRのURLの形で、末尾の番号がPRの番号と一致するときだけリンクにする。
それ以外は文字で出す。
リンクは`rel="noopener noreferrer"`を付けて新しいタブで開く。
backendは、URLを`https://github.com/<owner>/<repo>/pull/<N>`の形に限り、題名の制御文字と書字方向の制御文字を空白にし、200字に切って返す。
画面は、同じ検査を`src/lib/updateHistory.ts`の純関数でやり直す。
表示する語は`src/lib/labels.ts`にある。

### workerの負荷

defaultのworkerの直近24時間の負荷を出す。
先頭に結論の1行を置き、内訳は「内訳を表示」で開く。
結論の1行は、枠が塞がっていた記録の件数、開始が遅れた記録の件数、メモリの最大の割合(`anon`の上限に対する割合。読めなければ「不明」)、記録の数を並べる。
どれも内訳にある値で、判定はしない。
値は`system_status`の`worker_load`で、`worker_samples`を1回のクエリで集計した数と時刻だけである。
外部の文字列は含まない。
内訳の行は次のとおりである。

- 枠の使用。
  最新の記録の実行中のジョブの数と、他のジョブが使える枠の数、窓の中の最大
- 枠が塞がっていた記録。
  他のジョブが枠をすべて使っていた記録の数と、`running_jobs`が読めた記録に対する割合。
  他のジョブの使える枠が無い記録は数えない
- queueの待ち。
  待ちの最大の秒数と、待つジョブの最大の数
- 開始が遅れた記録。
  `lag_seconds`が30秒以上の記録の数と、最大の遅れ
- メモリ。
  最新と最大の`anon`、working set、上限に対する割合
- `memory.current`と`memory.peak`。
  キャッシュを含み、`memory.current`は最新の瞬間値、`memory.peak`はコンテナの起動からの最大値で、どちらも逼迫の判断には使わない

「枠の使用」と「メモリ」の最新の行には、最新の記録の時刻をJSTで添える。
上限に対する割合は、窓の中の最大の行にだけある。
割合は、0%に丸まる正の値を小数1桁で出す。

窓に記録が無いときと、集計を読めなかったときは、`worker_load`が`null`になる。
2つを分けないのは、画面が出す次の操作が同じだからである。
画面は、記録がないか集計を読めなかった旨と、`sample_worker_load`のスケジュールと`console_query`のジョブログの警告を確かめる操作を出す。
集計の失敗は、`console_query`のジョブログに警告`could not read the worker load`として残る。

`worker_load`を返す前のbackendの応答では、項目が欠ける。
Consoleが先に配信されても画面が壊れないよう、欠けた値は記録なしと同じに扱う。
形が違う値は、システムの画面の型ガードでは確かめない。
カードが確かめ、形が違えば、カードだけを「表示できません」にする。
画面の他の節は消えない。

節の説明に、workerの一覧をここでは読めないことと、止まったときは通知で知らせることを添える。
workerの一覧が読めない根拠は、[workerの生死の取得](api.md#workerの生死の取得)にある。

画面は閾値を持たない。
通知を出すのはメモリの割合とOOMの増加だけで、割合は`factory_config`の設定にある。
通知は要対応に出る([閾値の通知](../../operations.md#閾値の通知))。
待ちと枠の塞がりは通知にせず、この画面と日次のまとめで見る。
「枠の使用」と「枠が塞がっていた記録」を塞がりの判断に使える条件は、[枠の占有](../../operations/monitoring.md#枠の占有)にある。
型は`src/api/guards/workerLoad.ts`で確かめる。

### 情報の通知

重要度が情報の通知は、人の行動が要らないので、要対応の一覧に出ない。
この節は、直近7日の未解決の情報の通知を、新しい順に出す。
行動が要らない通知は、失敗と通知のタブを短くするため、「一覧を表示(N件)」の折りたたみに入れる。
件数は、たたんだ行に出す。
通知が無いときは、たたまずに空の旨を出す。
監査の失敗は、失敗の本文を先に見せるため、折りたたまない。
作業項目に紐づかない失敗は、flowごとの組を折りたたむ。
節へ移るときは、この節の折りたたみを開く。
行には、通知の種類の日本語名、発生の時刻、本文の最初の行を120文字まで出す。
本文は`displayableIssueText`を通し、プレーンテキストで描く。

行の「詳細」は、要対応の画面で同じ通知を選んだ経路(`/console/?notice=<id>`)へのリンクである。
詳細には、本文の全文、対象へのリンク、起きたことと次の操作が出る。
Consoleから解決できる種類の行は、「詳細と解決」と書く。
解決は、その詳細で行う。
この節では、解決しない。
同じ操作を2か所に置くと、取得の更新が食い違うためである。

### 解決済みの通知

解決した通知の履歴を出す。
履歴は参照用なので、「一覧を表示(N件)」の折りたたみに入れ、開くまで一覧を見せない。
件数は、たたんだ行に出す。
人が解決したものを先に、DBの掃除が解決したものを後にし、それぞれ解決の新しい順に並べる。
機械が片付けた大量の通知で、人の解決の履歴が押し出されないためである。
並べるのはbackendで、画面は返った順に描く。
行には、通知の種類の日本語名、解決の時刻、解決した主体、本文の最初の行を出す。
行を開くと、本文と発生の時刻を読める。
本文は`system_status`が先頭の500文字で切るので、500文字に達した本文には、先頭だけを表示している旨を添える。
解決した主体は、DBの掃除、自己更新、Issueの取得、PRの取得なら処理の名前に「(自動)」を添える。
それ以外は、記録された名前を文字のまま出す。
記録が無ければ「記録なし」にする。
解決の時刻が記録されていない通知は、「解決の時刻の記録なし」と出す。
解決済みの通知は、解決から既定30日で消えるので、履歴もその間のものである。

### 監査の失敗

失敗した監査の一覧である。
再実行できない失敗なので、要対応の画面では再実行の対象にせず、件数のカードで知らせてこの節へ案内する。
データは、`summary`の失敗のうち、作業項目の種類が監査のものを使う。
要対応の画面と同じ取得とキャッシュを共有する。
`summary`の定期の取り直しがあるので、この節も画面を開いている間に更新される。
`summary`の失敗は新しい順に上限まで取る。
失敗の件数が取得した件数より多いときは、古い監査の失敗は表示していない場合があると添える。

行には、監査の題名(作業項目の詳細へのリンク)、状態、失敗の時刻、ジョブへのリンク、失敗の内容を出す。
内容は、実行の出力でIssueの文字を含みうるので、プレーンテキストで描く。
500文字で切られているときは、切られている旨とジョブのログで全文を読める旨を添える。
再実行のボタンは置かない。
次の監査が、失敗した期間を扱う。
内容は`src/lib/failureView.ts`の`describeFailure`を、要対応の失敗の詳細と共有する。

後の監査で報告済みの失敗は、一覧に残し、「後の監査で報告済み」の印を付ける。
印の文言は、期間の終わりまで確かめたとは言わない。
比べるのは報告の開始だけだからである。
要対応の画面は、この失敗を件数から外す。
履歴として読めるように、この節は全件を出す。
印は文言で示し、色だけに頼らない。
印は`summary`の失敗の`superseded`で決まる。
古いbackendが送らないときは、印を付けない。

取得の上限を超えたときは、要対応のカードの件数とこの節の件数が食い違う。
カードは上限の前の全件から数え、この節は取得した新しい順の行だけを出すためである。
そのため、上限を超えた失敗があるときは、節に2つの注記を添える。
1つめは、古い監査の失敗を表示していない場合があること。
2つめは、要対応のカードの件数は表示していない分も数えるので、この節より多いことがあること。

### 作業項目に紐づかない失敗

定期のジョブなど、作業項目を持たないジョブの失敗を、直近7日の分だけ出す。
作業項目が無いので、要対応の画面にも作業項目の画面にも出ない。
この節だけが知らせる。
同じflowの失敗が繰り返されるので、flowごとにまとめる。
まとめるのはflowのパスで、ステップは分けない。
先頭に失敗の件数とflowの数を出す。
組は、flowのパス、失敗の回数、最新の失敗の時刻を持つ折りたたみで、最新の失敗が新しい順に並べる。
開くと、失敗を新しい順に1件ずつ、ステップ、失敗の時刻、ジョブへのリンク、失敗の内容を出す。
1つの組の失敗は、10件ずつのページに分ける。
ジョブへのリンクは、ジョブのIDがUUIDの形のときだけ張る。
内容の扱いは、監査の失敗と同じである。
再実行の操作は置かない。

表示する内容は、`src/lib/systemView.ts`の純関数が決める。

### 設定

設定のタブは、`factory_config`の全項目を、機能ごとのグループに分け、グループごとの表で出す。
許可した項目だけ、変えられる([設定の変更](#設定の変更))。
真偽は止める向き、数値は下げる向き、一覧の3項目は1要素の追加か削除である。
取得は`console_config`で、設定のタブを初めて開いたときに始める。
自動では取り直さない。
見出しの更新のボタンは、タブを開いた後だけ、この取得も取り直す。
節の見出し「設定」は、タブの名前と重なるので、読み上げにだけ残す。
見出しの下の説明文は、1文と箇条書き3行である。
1文は、全項目を出すことと、参照と伏せた値を「参照(出さない)」と表示することを言う。
箇条書きは3行で、順に次を言う。
Consoleで変えられる変更は、止める向き、下げる向き、3つの一覧の追加と削除である。
それ以外の変更は、端末から行う。
有効にする向き、値の引き上げ、`owners`などで、`wmill resource push`などを使う。
全部を止めるときは、システムの「状態」タブの全停止を使う。
「全停止」は、全停止の区画へのリンクである。
リンク先は`systemSectionPath("stop-all")`で、状態タブへ切り替えて区画へ移る([区画への移動](#区画への移動))。
この案内は、絞り込み中と設定が空のときも要るので、表の外の説明文に置く。
機能のスイッチの表には置かない。
全停止の区画は[保留と凍結](#保留と凍結)にある。
節の最大幅は、他のタブより広い(`SystemSection`の`wide`)。
表が横に広がるためである。
広げるのはグループの表だけである。
説明文、古い値と失敗の知らせ、読み込み中の枠は、他のタブと同じ読みやすい幅にとどめる。
文章が広い画面で長い1行になると、読みにくいためである。

グループの定義は`src/lib/configGroups.ts`にある。
定義は、グループの並び、見出しの文言、見出しの下の説明、グループごとのキーの並びを持つ。
説明は、グループが何を決めるかを言う1文である。
全グループが持ち、「その他」も持つ。
説明は、表の説明(`aria-describedby`)にも結ぶ。
どのグループにも入らない項目は、最後の「その他」に出す。
項目の無いグループは、見出しも出さない。

#### 設定の変更

変更の候補を出すかは、`changeOffersOf`(`src/lib/configChange.ts`)が決める。
一覧の3項目は、要素ごとの削除と、一覧ごとの追加を返す。
それ以外の項目は、`changeOfferOf`が返す1つである。
候補は、止める操作、数値を下げる操作、一覧への追加、一覧からの削除の4つである。

- 真偽の6項目は、値が`true`のときだけ、行に**止める**を出す。
  `false`のときは何も出さない。
  6項目に`design_enabled`を含み、`design_enabled_since`は含まない。
  `design_enabled`を止める書き込みは、他の項目と同じく、その1キーだけを書く。
  `design_enabled`の確認のダイアログは、結論で、止めている間の承認が設計書の承認を挟まず実装へ進むことと、戻すには設定の書き換えが要ることを伝える。
  詳細は、次の4つを伝える。
  進行中の設計と承認待ちが止まらないこと。
  承認は設計書を渡さずに進み、却下はIssueが変わっていれば要件定義へ戻り、そうでなければ人の対応待ちで止まること。
  止めても`design_enabled_since`は残り、有効に戻すには、人が`design_enabled`を`true`にし、`design_enabled_since`に新しい時刻を書くこと。
  `design_enabled`だけを`true`に戻すと、残った時刻が読めるので、設計工程がすぐ開くこと。
  この注意は「注意:」で始める。
  設計工程が無視されているとき(判定の`ignored`)は、結論を「いま設計工程は無視されていて、動いていません。止めても、動きは変わりません。」に替える。
  詳細は、効く時期を言わず、戻す手順(設定を書き換えて`design_enabled`を`true`にし、新しい`design_enabled_since`を書く)の1項目だけにする。
  止める操作は、これまでどおり押せる。
  結論は、区切りの無い長い要素(URLなど)が枠からはみ出さないよう、どこでも折り返す。
- 数値の5項目は、値が範囲に合い、下げる余地があるときだけ、**下げる**を出す。
  予算の2項目は0より大きい小数、ほかの3項目は1以上の整数である。
  整数の項目は、1つ下の整数が範囲に残るときだけである
- 一覧の3項目は、要素ごとに**削除**、一覧の下に**追加**を出す。
  値が文字列だけの配列のときに限る。
  `repo_allowlist`の要素が1件のときは、空にすると`owners`配下の全リポジトリが対象になるので、その要素の**削除**を出さない
- 参照と、伏せた値には出さない。
  値を読めないためである
- 要素に`$var:`か`$res:`を含む一覧と、文字列でない要素を含む配列には出さない
- 表の外の項目には出さない

この表は画面が出す操作の絞り込みで、境界ではない。
`console_config_update`が同じ表で確かめ、画面の表との一致を`tests/scripts/console_config_update.test.ts`が固定する。
一覧の許可表(`EDITABLE_LISTS`)と、要素の長さの上限(`MAX_ELEMENT_LENGTH`)も、同じテストが突き合わせる。

一覧の3項目は、`console_config_update`が1要素の追加と削除を受ける。
3項目は、`repo_allowlist`、`dependabot_other_repos`、`default_reviewers`である。
引数の形は、真偽と数値と同じ3つである。
項目と、読んだ時の値と、新しい値を渡し、一覧では後ろの2つが文字列の配列になる。
scriptは、2つの配列の差分から、追加か削除かと、動いた要素を導く。
末尾への1要素の追加か、ちょうど1要素の削除でなければ、`invalid_value`で断る。
結果は、`op`、`element`、前後の件数を持ち、真偽と数値の結果の`before`と`after`は持たない。
断る理由は、既存の7つに4つを足した11個である。
足した4つは、次のとおりである。

- `already_present`: 追加する要素が、正規化した後で既にある
- `invalid_element`: 要素の形が合わない、または長すぎる
- `would_empty`: `repo_allowlist`を空にする削除
- `owner_not_listed`: `repo_allowlist`への追加で、URLのownerが`owners`に無い

削除する要素は、2つの配列の差分から導くので、一覧に無い要素の削除は起きない。
守りと要素の形は[設定の変更](security.md#設定の変更)にある。

#### 確認のダイアログ

ダイアログ(`ConfigChangeDialog`)は、止める向き、下げる向き、一覧への追加、一覧からの削除の4つを扱う。
上から、結論、入力欄、詳細の順に並べる。
止める向きだけ、結論と入力欄の位置に、項目と値の行を置く。
結論は、強調した1文で、項目ごとの重大な結果を言う(`changeDialogConclusion`)。
詳細は、効く時期と元に戻す方法などを、結論と重ならない文だけで箇条書きにする(`changeDialogDetails`)。
サーバー由来の項目名と要素は、`safeText`を通して文字としてだけ描く。

止める向きの結論は、項目と値を言わない。
そのため、項目の行と、「有効 → 無効」の値の行を置く。
書かれた値(`true`、`false`)は、読み上げにだけ残す。
下げる向きの結論は、項目と単位つきの前後の値(「50 USD から 5 USD に」)を言うので、どちらの行も置かない。
追加と削除の結論は、一覧と要素を言うので、項目の行を置かない。
同じ内容を2か所で繰り返さないためである。

結論は、項目ごとに次のとおりである。

- 止める向きの`design_enabled`は、止めている間の承認が設計書の承認を挟まず実装へ進むことと、戻すには設定の書き換えが要ることを言う。
  設計工程が無視されているときは、止めても動きが変わらないことを言う
- 止める向きの`implement_enabled`は、止めている間に承認した要件定義が承認済みで止まり、要対応に載らないことを言う
- 止める向きのそれ以外は、項目名と、新しく動かなくなることを言う
- 下げる向きは、項目名と前後の値を言う。
  変更後の値が使えないときは、前の値だけを言う。
  `daily_budget_usd`は、今日の使用額を下回ると、今日のClaudeを使うフローがすべて失敗することも言う。
  今日の使用額は調べない
- 一覧への追加は、一覧と要素を言う。
  要素は入力欄が使える値のときだけ入れる。
  空の`repo_allowlist`への追加は、空の一覧への追加であることと、`factory_repo`と追加した要素以外のリポジトリが止まることも言う。
  空のときは`owners`配下のすべてが対象だったためである
- 一覧からの削除は、一覧と要素を言う

詳細は、項目ごとに次を並べる。

- 変更は、次に設定を読む処理から効く
- 動いているフローも、以後の手順が設定を読むときから、新しい値で動く
- 止める向きと下げる向きは、元に戻すには、運用者がWindmillでリソースを編集するか、`wmill resource push`で戻す。
  Consoleからは戻せない。
  下げる向きは、引き上げもできないと添える
- 一覧は、逆の操作で戻せる。
  追加は同じ値の削除、削除は同じ値の追加で戻せると伝える。
  Consoleから戻せないとは書かない
- `implement_enabled`だけ、有効に戻した後に人が再実行で再開することを足す
- `repo_allowlist`への追加だけ、`allowed_check_commands`が空でないとき、検査コマンドの件数と、新しいリポジトリの修正の検証でも隔離なしで実行されることを足す。
  参照か伏せた値で件数を読めないときは、読めないことと、新しいリポジトリでも実行されることを足す
- `repo_allowlist`への追加だけ、`check_commands_by_repo`で検査コマンドを持つリポジトリがあるとき、その数を足す。
  追加したリポジトリが同じ名前なら、その検査コマンドが隔離なしで実行されることを足す。
  参照か伏せた値で数を読めないときは、読めないことを足す

検査コマンドの設定は、設定の項目の一覧から`checkCommandsOf`が読む。
`allowed_check_commands`は件数、`check_commands_by_repo`は検査コマンドを持つリポジトリの数である。
空の配列のエントリは、実行するコマンドが無いので数えない。
設定の取得は、絞り込みの前の全項目で読む。
項目が無いときは、設定を読む処理の既定の空と同じく、0件と見なす。
`check_commands_by_repo`は、追加した要素との一致を画面で判定しない。
キーの正規化は設定を読む処理が持つので、画面に複製しないためである。
数が1以上なら、一致するかを問わず、一般の警告を出す。

数値の項目は、変更後の値を入力欄で受ける。
入力は`parseNewNumber`が読む。
数字だけを受け、符号、指数、16進、全角の数字は受けない。
範囲に合わない値と、現在の値以上の値は、理由を欄の下に出し、確認のボタンを押せなくする。
欄の補足に、入力の前から制約を出す(`lowerHint`)。
制約は、数値の規則(整数か、下限、下限を含むか)から作る。
例は、「いまの値(50 USD)より小さい数。0より大きい」と「整数。1以上、いまの値(3 ラウンド)より小さい」である。

一覧への追加は、足す要素を入力欄で受ける。
入力は`parseNewElement`が読む。
前後の空白は除く。
空と、100字を超える要素は、確認のボタンを押せなくする。
100字を超える理由は欄の下に出す。
形式の検査は画面では持たず、scriptの`invalid_element`の断りの文が伝える。
画面とscriptで同じ規則を二重に持たないためである。
欄の補足に、項目ごとの形の例を出す。

欄が空の間は、理由を出さずに、確認のボタンだけを押せなくする。
この押せなさは、確認のダイアログの`confirmDisabled`で表す。
実行中を表す`busy`とは別の指定である。
確認のボタンは、4つの操作のどれでも、破壊的な色にする。
止めると下げるはConsoleから戻せず、追加は対象を広げ、削除は対象を外すためである。
フォーカスは**取り消す**に置く(`ConfirmDialog`)。
**取り消す**ボタンとEscは、ダイアログを閉じるだけで、書き込みを呼ばない。
URLの値や画面の遷移からは、変更を起こさない。

#### 書き込みと結果

書き込みの入力は`changeInputOf`が作る。
読んだ時の値は、候補を作ったときの値で、scriptが書く直前の値と突き合わせる。
一覧の`expected`は画面が読んだ配列で、`next`は末尾に1要素を足した配列か、選んだ位置の要素を除いた配列である。
呼び出しは、書き込みの共通のフック(`useWriteMutation`)に載せる。
ロックのキーは項目名で、実行中は同じ項目を操作できなくする。
変更の後は、設定の取得を読み直す。

成功は、画面の知らせ(トースト)に出す。
成功でない結果は、操作が要るので、閉じるまで残る知らせに出す([残る知らせ](#残る知らせ))。

| 結果 | 知らせ |
| --- | --- |
| 変えた | 成功。トースト。止めた項目は「止めました」、下げた項目は前後の値を添えて「下げました」、一覧は前後の件数を添えて「追加しました」か「削除しました」 |
| 書いたが、読み直した値が期待と違う | 警告。残る知らせ。書き込みは済んでいることと、Windmillで確かめることを伝える |
| 断られた | 情報。残る知らせ。理由を日本語の固定文で伝え、続けて次の操作を書く。11の理由のそれぞれが、次の操作の文を持つ |
| 記録を残せなかった(`action_audit`が`failed`) | 警告。残る知らせ。変更は済んでいることと、誰が変えたかはジョブのログで確かめることを伝える |
| 書き込みの失敗 | 失敗。残る知らせ。失敗の文をそのまま伝える |

一覧の断りの文は、次のとおりである。
`invalid_element`は、どの項目の要素かを結果が持たないので、3項目の形をまとめて伝える。

- `already_present`: その要素はすでにある
- `invalid_element`: 形式が正しくない。
  3項目の形と、100字までであることを、1文で伝える
  形は、`repo_allowlist`が`https://github.com/owner/repo`である。
  `dependabot_other_repos`は`owner/repo`、`default_reviewers`はGitHubのログイン名である
- `would_empty`: 最後の1件は削除できない。
  空だと`owners`配下の全リポジトリが対象になる
- `owner_not_listed`: `owners`に無いアカウントのリポジトリは追加できない

`audit_unavailable`の文は、次の場合も、この理由で断ることを添える。
削除する既存の要素が100字を超えるときと、記録に使えない文字を含むときである。
その場合にCLIで直すことは、次の操作の文が伝える。
要素ごとの削除ボタンは、形に合わない要素でも出し分けない。
表示が増えるためである。

#### 残る知らせ

成功でない結果は、設定のタブの先頭に、閉じるまで残る知らせとして出す(`ConfigNotice`)。
どの結果が残るかは`staysUntilClosed`(`src/lib/writeNotices.ts`)が決める。
成功以外の結果が残る。
トーストは操作した場所から離れて出て、項目ごとの文脈を持たないためである。
設定のタブの先頭なら、どの項目の変更の結果かを題で言い、断りの次の操作を続けて読める。
一覧を読み直せなかったときの警告は、一覧が更新されると要らなくなるので、閉じるまで残さないトーストにする。

知らせは1件だけ持つ。
次の結果が届くと置き換え、次の変更を始めたときに消す。
置き場(`src/lib/pinnedNotice.ts`)は画面の部品の外にある。
結果が届いたときにシステムの画面を離れていても、戻ると残っている。
結果の振り分けは`routeConfigOutcome`(`useConfigChange.ts`)が行う。

題は、どの項目の変更かと、結果の種類を語で言う。
断りは「<項目>の変更を断られました」、確かめる警告は「…を確かめてください」、失敗は「…に失敗しました」である。
本文は、何が起きたかの1文と、断りのときの「次の操作:」の1文である。
断りの文は何が起きたかだけを言い、次の操作は理由ごとの別の文が持つ(`CONFIG_UPDATE_NEXT_STEPS`)。
次の操作は、画面で直せるものと、端末で直すものを分ける。

- `item_not_allowed`は、端末から変更する
- `has_reference`は、端末から変更し、変更した後に画面を更新して、値が変わったことを確かめる。
  設定のどこかに参照があるときは、書き戻しで秘密の値が設定に入るおそれがあるので、Consoleから変更しない
- `conflict`と`invalid_value`は、画面を更新していまの値を確かめる。
  変えたいなら、もう一度行う
- `not_lowering`は、画面を更新して確かめる。
  値の引き上げと有効にする向きは、端末から変更する
- `actor_unknown`は、ログインし直して、もう一度行う
- `audit_unavailable`は、少し待って、もう一度行う。
  要素が原因のときは、CLIで直す
- `already_present`は、画面の一覧で、その要素があることを確かめる
- `invalid_element`は、要素を正しい形に直して、もう一度行う
- `would_empty`は、置き換えるときは、新しい要素を先に追加してから、古い要素を削除する
- `owner_not_listed`は、`owners`を端末から変更して、もう一度行う

知らせが現れたとき、画面は知らせへスクロールして、フォーカスを移す(`jumpToSection`)。
スクロールした先の操作の結果を、見落とさないためである。
移るかは`src/lib/noticeFocus.ts`が決める。
隠れたタブには移らない。
タブが見えるようになった時点で、残っている知らせへ移る。
設定の節は、タブが選ばれているか(`visible`)を、システムの画面から受け取る。
新しい知らせが届いたときは、フォーカスが体(`body`)にあるか、確認のダイアログを開いたボタンに戻っているときだけ移る。
絞り込み欄などに別のフォーカスがあるときは、フォーカスを奪わず、スクロールもしない。
知らせは`role="alert"`で読み上げられるためである。
知らせは`role="alert"`で、フォーカスを受けられる。
Tabの順には入れない。
閉じるボタンを押したときは、節の見出しへフォーカスを戻す。
ボタンが消えて、フォーカスが失われないためである。
色は警告と失敗だけに付ける。
断りは中立の枠にし、語で種類を言う。
