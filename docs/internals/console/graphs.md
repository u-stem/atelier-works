# Consoleの図の画面の仕様

Consoleのflowの図と起動の図の画面の仕様を書く。
図の画面と、図のデータを作るスクリプトを変更する人が読む。
画面をまたぐ仕様と、ほかの画面の仕様の置き場は、[Consoleの仕様](../console.md)にある。

## flowの図の画面

`/console/jobs/flows/:name`は、flow1つの図を出す。
入口、ステップ、出口を左から右に並べ、どのステップで何が起き、次にどのflowが動くかを読む。
全flowを1枚に描くと線が交差して読めないので、flowごとに分ける。
flowをまたぐ起動は、定期ジョブを起点にした[起動の図](#起動の図の画面)で読む。
名前を省いた`/console/jobs/flows`は、ジョブの一覧へ戻す。
データに無い名前と安全でない名前では、「flowが見つかりません」とだけ出す。
入力された名前は画面に書かない。
データを読み込めないときは、その旨を出す。

見出しにはflowの名前と1行の説明を置き、本文の先頭に`flow.yaml`の説明の全文と、そのflowのジョブの履歴へのリンクを置く。
一覧の行から開いたときは、履歴の`state`で戻り先を受け取り、パンくずの「ジョブ」がその一覧へ戻る。

### データ

`mise run docs:gen`が`console/src/generated/flows.json`を作る。
`scripts/docs-gen.ts --check`が古さを検出するので、CIの`check-docs`が、データを更新し忘れたPRを止める。
元は次の3つである。

| 元 | 取るもの |
| --- | --- |
| `f/factory/*__flow/flow.yaml` | flowの説明、ステップ(モジュールのid、題、script、`skip_if`の有無) |
| `scripts/launch-graph.ts` | flowを起動する辺。承認を作るステップと承認の結果の表、配線されていない辺の表、差し戻しの辺の表、PRを介した関係の表、scriptを呼ぶscriptの表 |
| `f/factory/*.schedule.yaml` | scheduleの題、実行先、有効かどうか |

scheduleが起動するflowには、そのscheduleのscriptが呼ぶscriptの起動も含める。
題とflowの説明は、先頭の接頭辞(`[SF-…]`、`[SYS-…]`、`[OP-…]`、`[LIB]`)を`scripts/flow-graph.ts`の`withoutIdPrefix`で除く。
ステップのidは`modules[].id`と一致するので、実行の状態はidの突き合わせだけで重ねられる。
`skip_if`は式で日本語に直せないので、条件で飛ぶことがある印だけを持つ。
`failure_module`は全flowで共通なので、図に入れない。
並びは入力の順に依らず、同じ元から同じJSONができる。

JSONはViteがそのままバンドルに取り込む。
`src/lib/flowsData.ts`の`parseFlowsData`が形を確かめ、次の条件を外れるとnullを返す。

- flowの名前とscheduleの名前が一意で、英小文字、数字、`_`だけでできている
- ステップのidがflowの中で一意である
- 入口、出口、scheduleの行き先のflowが存在する
- 出口のステップが、出口を持つflowの中にある

### 入口と出口

入口は、そのflowを起動するものを、左の列へ縦に並べる。
出口は、ステップが起動する次のflowを、ステップの下の行に並べる。
出口はクリックで次のflowの図へ移る。
flow自身からの入口(却下の作り直し)は、同じ戻りを出口が示す。
そのため、図と一覧のどちらにも描かない。

| 入口の種類 | 内容 |
| --- | --- |
| スケジュール | flowを起動するscriptを実行する、有効なscheduleの名前 |
| 人の操作 | フォームからの実行と、Consoleの再実行、新規投入、今すぐ監査 |
| script | スケジュールも人の操作も持たない、flowを起動するscript。別のscriptが呼ぶときは、呼ぶscriptを添える(`SCRIPT_CALLERS`) |
| 他のflow | そのflowのステップが起動する。scriptではなく、起動元のflowとして示す。承認、却下、差し戻し、PR経由、CI修正後の戻りを介するときは、そう示す |

承認を作るステップは、`steps/pipeline_request_approval`と`steps/design_request_approval`である。
このステップの出口には、承認を処理するscriptが起動するflowを、承認と却下に分けて出す。
承認の処理は`handlerPathFor`が返すscriptで、`LAUNCH_EDGES`の辺と`scripts/launch-graph.ts`の`APPROVAL_OUTCOMES`を突き合わせて決める。

| flow | 出口 |
| --- | --- |
| `pipeline` | 承認の後に`design`か`implement`、却下の後に`pipeline`(要件定義の作り直し) |
| `design` | 承認の後に`implement`、却下の後に`design`(設計の作り直し)か`pipeline`(要件定義へ戻る) |

`LAUNCH_EDGES`にあって本番では起動しない辺は、`UNWIRED_LAUNCH_EDGES`に載せ、入口と出口のどちらにも描かない。
起動先のflowの図には、「pipelineの承認からは、まだ起動されません」のように添える。
今は、載せる辺が無い。
設計工程の辺は、設定の`design_enabled`で切り替わる辺として`LAUNCH_EDGES`に載せる。
設計工程の辺は、承認の処理から`design`を起動する辺と、設計の不足を`design`へ戻す`implement_finish`と`pr_fix_finish`の辺である。
設定と上限で決まる辺と同じく、図に印は付けない([設定と上限で決まる辺](#設定と上限で決まる辺))。
`startDesign`を結ぶのが`config.design_enabled`の内側だけであることは、`tests/scripts/flows_data_contract.test.ts`が確かめる。

### 差し戻し

`implement`、`pr_fix`、`design`のステップは、前のflowの不足を見つけたときだけ、そのflowへ戻して起動する。
要件定義の不足(`requirements_gap`)は`pipeline`へ、設計の不足(`design_gap`)は`design`へ戻す。
通常の起動と分けて、出口に「差し戻し」、戻された側の入口に「implementの差し戻し」のように示す。
どの辺が差し戻しかは、`scripts/launch-graph.ts`の`REWORK_LAUNCH_EDGES`が持つ。
契約テストが、辺の行き先ごとに、各ステップのソースの`requirements_gap`か`design_gap`と照合する。
設計の不足を`design`へ戻す辺も差し戻しに含める。
通常の起動の辺にすると、`design`から`implement`への承認の辺と合わせて、前進の辺が循環する。
[起動の図](#起動の図の画面)は前進の辺だけで段を決めるので、循環があると最長の経路が決まらない。
契約テストが、前進の辺(起動、承認、PR経由)に循環が無いことと、定期ジョブから見た段の数が起点を含めて6以下であることを確かめる。

### PR経由の関係

flowの終わりのステップがPRにラベルやレビューを残すと、定期ジョブがPRのラベルやCIの結果を見て、次のflowを起動する。
この関係は、flowのコードが次のflowを起動する辺ではない。
そのため`LAUNCH_EDGES`には混ぜず、`scripts/launch-graph.ts`の`PR_RELATION_EDGES`に持つ。
辺の一覧と、辺ごとの証拠(ソースの式)は、この表に任せる。

表の辺は、ステップのscriptから、続くflowへ向かう。
向きは、前進(`forward`)と戻り(`return`)の2つである。
前進の辺は、出口を「PR経由」、続く側の入口を「<flow>からPR経由」と示す。
戻りの辺は、出口を「CI修正後の戻り」、戻された側の入口を「<flow>からCI修正後の戻り」と示す。
戻りに数えるのは、CIの修正の回と、設定で有効にしたときの競合の修正の回である。
この2つは作業項目のheadを進めないので、新しいheadを見つけた定期ジョブが自動の再レビューを起こす。
通常のラベルの回の修正はheadを進めるので、自動の再レビューを起こさず、戻りに数えない。
語は「CI修正後の戻り」の1つにし、競合の修正の回も同じ語で示す。
戻りの辺は`pr_fix_finish`から`pr_review`への1本で、CIの回と競合の回をデータで分けられないためである。
語に「CI」を残すのは、ラベルの回の修正は戻らないことと区別するためである。

契約テストの`tests/scripts/launch-graph.test.ts`が、各辺の証拠を照合する。
照合は、コメントを除いたソースに、証拠の文字列がちょうど1か所あることを確かめる。
関数は`scripts/launch-evidence.ts`の`findMissingEvidence`である。
証拠を読むファイルは、`f/factory`の下のTypeScriptに限る。

### 設定と上限で決まる辺

承認、却下、差し戻しの起動は、設定(`implement_enabled`と`design_enabled`)と試行の上限で決まる。
図は設定の値を読まないため、辺に印は付けない。
この辺を入口か出口に持つflowの図には、図の下に1文を添える。
文は「設定や試行の上限により、起動しない場合があります」である。
PR経由の関係と戻りは、起動しない理由が人のラベルとCIの結果なので、この辺に数えない。

### 配置

座標は`src/lib/flowDiagram.ts`の`layoutFlowDiagram`が決める純関数である。
入口は左の列、ステップは右へ一列、出口はステップの下の行に置く。
線は隣り合う列と行の間だけを引くので、他の箱の上を通らない。
出口は、つくステップの真下に置き、同じ行で重なるときは右へずらす。
出口が右へ広がるpipeline、pr_fix、designは、ジョブの画面の本文の最大の幅(1152px)からカードの分(18px)を引いた幅を超え、横にスクロールする枠で出す。
ほかのflowは、その幅に収まる。

図は自前のSVGで描く(`src/screens/jobs/FlowDiagram.tsx`)。
色はCSSのトークンだけで指定するので、ライトとダークの両方で読める。
線は、入口を破線、ステップの間を実線、出口を点線にして見分ける。
ステップの箱は、1行の説明、id、実行の状態の語の順に書く。
実行の状態を重ねた図には、条件で飛ぶことがあるステップに「条件で飛ぶ」を添える。
重ねない静的な図には出さない。
スキップが異常でないと知る場面は、状態を重ねた図だけにあるためである。
入口と出口の文は、箱の幅で折り返す。
文字の幅は、半角を0.55em、それ以外を1emとする見積もりである。
出口と、子のジョブを持つステップの箱はリンクで、キーボードで届き、焦点は枠の太い線で示す。
読み上げの名前は「<flowの名前>の図」で、リンクはその行き先を名前に含める。

### 実行の状態

図の部品は、ジョブのステップの状態を、ステップのidで重ねられる。
実行中のステップは、面と枠を強調し、三角の記号と「実行中」を添える。
失敗には×、成功にはチェックの記号を添える。
強調は色だけに頼らない。
状態の語は、ジョブの詳細のステップの一覧と同じ`stepStateInfo`で決める。
条件で飛ばしたステップは「スキップ」と示す。
ジョブにそのステップが無いときは、語を出さない。
ジョブが返すステップのうち、定義にidが無いものは、図の後ろに「定義に無いステップ」として一覧で出す。
`flow.yaml`のモジュール名を変えた後に古いジョブを開いても、止まったステップを隠さないためである。

### 幅

図の幅と、図を包む要素の実際の幅(`useElementWidth`が測る)を比べて、見せ方を決める。
決める関数は`src/lib/flowGraphFit.ts`の`graphPresentation`である。

| 幅 | 見せ方 |
| --- | --- |
| 図の幅とカードの分以上 | 図をそのまま出す |
| 640px以上で、上に満たない | 横にスクロールできる枠に入れる。枠は`role="region"`で名前を持ち、キーボードで焦点を受ける |
| 640px未満 | 図の代わりに、入口、ステップ、出口の一覧を出す |

一覧では、他のflowのステップから起動される入口と差し戻しを、起動元のflowとして1行ずつにまとめ、それぞれ図へのリンクにする。
flow自身へ戻る入口は、同じ戻りを出口が示すので出さない。
ステップは番号付きの一覧で、説明、id、状態、子のジョブへのリンクを出す。
出口には、出口がつくステップを添える。
flow自身へ戻る出口は、同じ図なのでリンクにしない。

幅を測る前は、図と一覧のどちらも描かない。
描き直しで見せ方が変わると画面がちらつくため、測り終えてから描く。

### 無害化

flowの名前、説明、ステップのidと説明、入口の名前、出口の文、定義に無いステップは、`safeText`を通して描く。
生成データはリポジトリの定義から作るが、ジョブが返すステップのidと状態は、サーバー由来の文字列と同じく扱うためである。
`src/screens/jobs/safeTextCoverage.test.tsx`が、図と画面のすべての文字列に見えない文字を入れて描き、残らないことを確かめる。

## 起動の図の画面

`/console/jobs/origins/:name`は、定期ジョブ(schedule)1つから起動するflowのつながりを、1枚の図で出す。
運用者が、定期ジョブが何を、どの順に起動するかを読む。
flowの図は1つのflowの中を読む画面で、起動の図はflowをまたぐ起動を読む画面である。
起点を定期ジョブに絞り、起点から届く範囲だけを描く。
全flowを1枚に描くと線が交差して読めないためである。
入口は、スケジュールのタブの行にある「起動の図を開く」のリンクである。
名前を省いた`/console/jobs/origins`は、ジョブの一覧へ戻す。
データに無い名前と安全でない名前では、「定期ジョブが見つかりません」とだけ出す。
入力された名前は画面に書かない。
データを読み込めないときは、その旨を出す。

見出しには定期ジョブの名前と1行の説明を置き、パンくずは「ジョブ › <名前>の起動の図」にする。
一覧の行から開いたときは、履歴の`state`で戻り先を受け取る。
flowの図へ移るリンクは`state`を渡さない。
渡すと、flowの図のパンくずの「ジョブ」が起動の図へ戻り、flowの図を直接開いたときと食い違うためである。
flowの図から起動の図へは、ブラウザの戻るで戻る。

起点は定期ジョブだけである。
人の操作は名前を持つ実体が無く、起点にすると全体図に戻る。
承認は、flow間の辺としてすでに図に出る。
PRを介して続くflowは、[PR経由の関係](#pr経由の関係)の前進の辺として、図に出る。

### 図の組み立て

組み立ては`src/lib/originGraph.ts`の`originGraphModel`が行う純関数である。

- 描くflowは、定期ジョブから前進の辺(起動、承認、PR経由)でたどれるものに限る。
  差し戻しと却下の先でしか届かないflowは描かない。
- 段は、前進の辺だけを使った、起点からの最長の経路で決める。
- 起点の箱が0段、定期ジョブの起動先が1段で、その先が2段、3段になる。
- 前進の辺は線で描く。
  段を飛ぶ辺(`pipeline`から`implement`への承認)も線にする。
- 承認の線には語「承認」、PR経由の線には語「PR経由」を添える。
  起動の線には語を付けない。
- PR経由の線は破線で描く。
  承認と起動の線は実線である。
- 戻りの辺(差し戻し、却下、CI修正後の戻り)は線にせず、flowの箱の下に足の注記として書く。
- 同じ行き先でも、経路が違えば注記は別の行にする。
- 自分へ戻る却下は、「やり直し」と書く。

足の注記の文言は、向きではなく経路で決める。
文言は[入口と出口](#入口と出口)の出口の語と同じで、「差し戻し: design」「却下の後: pipeline」「CI修正後の戻り: pr_review」のように書く。
戻りを線にすると、線が増えて全体図に戻るためである。

前進の辺が循環するデータでも、図の組み立ては止まる。
循環を閉じる辺は、線にせず、注記として書く。
循環しないことと、段が起点を含めて6以下であることは、`tests/scripts/flows_data_contract.test.ts`が確かめる。
段が増えると図が横に広がるので、上限を決めて、際限なく広がらないようにする。
設計の不足を`design`へ戻す辺を差し戻しに含めるのは、この条件を満たすためである([差し戻し](#差し戻し))。

起動先のflowが1つだけの定期ジョブは、そのflowを初めから開く。
1回押さないと中身が見えない遠回りを避けるためである。
数える対象は、定期ジョブが直接起動するflowの数である。
起動先のflowが無い定期ジョブは、図の代わりに「この定期ジョブはflowを起動しません」と出す。

設定や試行の上限で起動しないことがあるので、承認の線か、差し戻しと却下の注記があるときは、図の下に1文を添える。
文は[設定と上限で決まる辺](#設定と上限で決まる辺)と同じである。
PR経由の線とCI修正後の戻りの注記は、この文の条件に数えない。
図の下には、線と注記の読み方を1行の凡例で添える。
PR経由の線を持つ図の凡例は、破線の意味も書く。
破線は、定期ジョブがPRのラベルやCIの結果を見て起動する関係で、人のラベルを含む。
flowの図の破線は入口の線を指すので、この意味は起動の図の中だけで決める。
640px未満の一覧には、凡例を出さない。
PR経由の線を持つ図の一覧には、破線と同じ意味の1文を、一覧の下に添える。
一覧だけでは、PR経由の行に人のラベルを要することが伝わらないためである。
起動の句は、凡例と一覧で同じ定数を使う。
「人のラベルを含む」は、凡例と一覧の文のそれぞれで付ける。

### 起点の箱

起点の箱には、定期ジョブの名前と、直近の実行の成否と、止まっていないかを出す。
cronと時刻帯は、判断に使わず、スケジュールのタブの行と重なるので出さない。

成否は、記号(チェックと×)と文言で示す。
止まっているときは、「無効」「一時停止中」「エラーあり」の印を添える。
止めた定期ジョブに「成功」だけが出て、正常と読まれないためである。
凍結中の印は出さない。
凍結の取得は、起動の図が読まないためである。
止めた定期ジョブは、凍結の有無にかかわらず「無効」が出る。

図は、起点の箱の取得を待たずに描く。
取得の状態を持つのは、実行の欄だけである。

| 取得の状態 | 実行の欄 |
| --- | --- |
| 取得中 | 読み込み中 |
| ログインが必要 | ログインが必要です |
| 取得に失敗 | 取得できませんでした |
| リポジトリにあって、Windmillに無い | Windmillにありません |
| 値があり、実行の記録が無い | 実行の記録がありません |
| 値があり、実行の記録がある | 直近の実行の成否と、止まっているときの印 |

取り直しに失敗しても、前の値があれば値から出す。
取得の方針は[取得の方針](api.md#取得の方針)にある。

### 配置(起動の図の画面)

座標は`layoutOriginGraph`が決める純関数である。
左端に起点の箱を置き、右へ段ごとにflowの箱を縦に積む。
箱の幅は、flowが200px、起点が180pxで、段の間隔は96pxである。
flowの箱の幅は、開閉で変えない。
変えると、図の幅が変わって見せ方が入れ替わり、押したボタンが消えてフォーカスを失うためである。

隣り合う段を結ぶ線は、右辺から左辺へ直線で引く。
出る点と入る点の高さが同じ線は水平に入り、違う線は斜めに入る。
たとえば、行き先の段の先頭へ入る線は、次の箱から出ると斜めになる。
同じ段で先頭でない閉じた箱、起点の箱、開いた箱である。
段を飛ぶ線は、すべての箱の下端より下に引いた通り道を回し、間の段の箱の上を通さない。
段を飛ぶ線の終点は、見出しの中心から28px下へずらす。
矢じりは12px四方なので、中心へ入る線の矢じりと、斜めに入る線とその矢じりに重ならない距離が要るためである。
線の出る位置は、たたんだ箱では見出しの高さ、開いた箱では出口のつくステップの行の高さである。
同じステップから出る承認の線は、同じ点から出る。

flowの箱は、たたむと、名前、説明1行、ステップ数、開閉の印、足の注記を出す。
開くと、箱が縦に伸びて、ステップの行(idと1行の説明)を細い矢印でつないで並べ、「flowの図」のリンクを添える。
ステップの行は、状態や入口の列を持たない。
詳細は「flowの図」のリンクの先にある。
flowの箱に実行の状態は重ねない。
flowの最新のジョブは1件に決まらないためである。

### 開閉

開閉の状態は、画面が`ReadonlySet`で持つ。
URLと履歴のどちらにも残さない。
図と一覧は、同じ集合を読むので、幅が640pxをまたいでも、開閉が保たれる。
図と一覧は別の要素なので、幅が640pxをまたぐと、見出しのフォーカスと横スクロールの位置は失われる。
これは既知の挙動である。
「すべて開く」の操作は置かない。
図に出るflowは、最も多い定期ジョブでも5つで、1つずつ開けるためである。

### 幅(起動の図の画面)

見せ方は、[flowの図の画面の幅](#幅)と同じ`graphPresentation`で決める。

| 幅 | 見せ方 |
| --- | --- |
| 図の幅とカードの分以上 | 図をそのまま出す |
| 640px以上で、上に満たない | 横にスクロールできる枠に入れる |
| 640px未満 | 段ごとの平らな一覧に替える |

最も段の多い`poll_issues`は、起点を含めて6段で、図の幅が約1,700pxになる。
最も広い画面でも収まらないので、横にスクロールして読む。
`self_update`のようにflowが3列(起点を含めて4段)の定期ジョブは、図の幅が1108pxになる。
サイドバーを開いた1280pxの画面では本文の幅が足りず、横にスクロールする。

一覧は、起点の箱、段ごとのflowの順に並べる。
各flowは共通の`Disclosure`で開閉し、出口の行を、開閉の外に並べる。
出口の行は、図の線と注記の代わりである。
起点のカードにも出口の行を並べ、起点からの線ごとに「次に起動: <flow>」と書く。
1段目のflowの並びだけでは、段を飛ぶ起動が落ちるので、段を飛ぶ線だけでなく、起点からの線をすべて並べる。

### キーボードと読み上げ

- ボタンは、flowの見出しだけである。
  見出しは`role="button"`、`tabindex="0"`、`aria-expanded`を持つ。
  名前は「<flow名>のステップ」である。
- ボタンの子は、矩形と、flowの名前の文字と、開閉の印だけにする。
  説明とステップ数は、ボタンの外の兄弟として描く。
- ステップの行、足の注記、「flowの図」のリンクは、ボタンの外の兄弟として描く。
- Enterはkeydownで、Spaceはkeyupで切り替える。
  ネイティブのボタンと同じである。
  Spaceのkeydownは、ページのスクロールを止める。
- Spaceの押し始めが見出しのときだけ、keyupで切り替える。
  押している間に焦点が移ったときに、切り替えないためである。
- 矢印キーは使わない。
  Tabの順は、段の順、上から下の順である。
  見出しの次に、同じflowのリンクが来る。
- `aria-controls`は付けない。
  閉じているときは、指す先を描かないためである。
- 「flowの図」のリンクの名前は、「flowの図: <flow名>」である。

ボタンの子を限るのは、ボタンの子は読み上げの対象にならず、リンクを入れると入れ子の操作になるためである。
ボタンの名前を、見える文字を含む形にするのは、axe-coreの`label-content-name-mismatch`を避けるためである。
フォーカスの輪は、見出しの矩形とリンクの矩形にだけ付く。
輪を子の矩形すべてに付けると、箱全体が太く囲まれる。

色だけに頼らない。
開閉は、三角の向きと`aria-expanded`で示す。
線の種類は、線の形(実線と破線)と、語「承認」「PR経由」で示す。
起点の箱の成否は、記号と文言で示す。

- 起動先が無い定期ジョブ
- 見つからない場合と、読めない場合
