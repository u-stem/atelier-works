# Consoleの要対応の画面の仕様

Consoleの要対応の画面(承認、失敗と再実行、通知)の仕様を書く。
要対応の画面を変更する人が読む。
画面をまたぐ仕様と、ほかの画面の仕様の置き場は、[Consoleの仕様](../console.md)にある。

## 要対応の画面

一覧に出すのは承認、失敗、通知である。
項目は、時刻が新しい順に並べる。
同時刻なら種類の順(承認、失敗、通知)、次にidが大きい順にする。
種類の切り替え(すべて、承認、失敗、通知)は、一覧に2種類以上の項目があるときだけ出す。
切り替えには、項目が1件以上ある種類だけを並べる。
選んだ種類の項目がなくなったら、切り替えの状態も「すべて」に戻す。
承認の下位の種類(要件定義、設計、Issue化提案、改善提案)は、行のラベルで示す。
改善提案は、監査から出たIssue提案である。

`summary`の承認には、承認待ちのほかに、承認済みでIssueをまだ作っていないIssue提案も入る。
承認を記録した後にIssueの作成が失敗した提案を、見えなくしないためである。
その行には「承認済み(Issue作成待ち)」のラベルを付ける。

承認として取るのは、画面が扱える種類(`requirements`、`issue_proposal`、`design`)だけである。
`summary`と`inbox`の両方がこの種類で絞る。
除外する書き方では、種類を足すと、画面の未対応の種類の行が届く。
届いた行のために、一覧全体を表示できなくなる。
設計の承認依頼(`design`)は、承認待ちの間だけ、一覧の行と件数に数える。
`summary`と`inbox`の並びは、依頼の時刻の新しい順に、同時刻ならidの大きい順にする。
承認のうち、一覧の上限(200件)を超えた分は、行に出ず、件数にだけ数える。
設計の行を足したので、押し出される行は今までより増えうる。

設計の行は、作業項目の状態(`work_item_status`)を持つ。
設計の承認を押せるのは、作業項目が設計の承認待ち(`awaiting_design_approval`)のときだけである。
古いbackendの応答は、この項目を持たない。
画面は、項目が無いときも応答を受け入れ、承認を止める側に倒す。
設計書の本文は、行に載せない。
行を選んだときに、`approval_design_doc`で取る。

選んだ項目は、URLの`?approval=<id>`、`?failure=<id>`、`?notice=<id>`のどれか1つに持つ。
2つ以上あるときは、どれも選んでいないものとして扱う。
値が正の整数でなければ、選んでいないものとして扱う。
選択の変更は履歴を積まない。
ただし幅が狭いとき(lg未満)に項目を選ぶ操作は、履歴を積む。
面が一覧から詳細へ切り替わるので、ブラウザやスマートフォンの戻る操作で一覧へ戻れるようにするためである。
積んだ履歴には、一覧から選んだ印を付ける。
広い幅で選び直して履歴を置き換えるときは、置き換わる履歴の印を引き継ぐ。
種類の切り替えが選んだ項目の種類を隠すときは、選択を外す。
一覧と詳細は別々にスクロールする。
幅が狭いとき(lg未満)は、一覧と詳細を1画面ずつ出す。
項目を選んでいなければ一覧、選んでいれば詳細を出す。
詳細の上の「一覧へ戻る」と、種類の切り替えによる選択の解除は、印のある履歴を戻って取り除く。
置き換えると、画面の変わらない履歴が残り、戻る操作を余分に求めるためである。
選択つきのURLを直接開いたときは印が無いので、選択を外して履歴を置き換える。
面が切り替わったら、新しく出た面にフォーカスを移す。
一覧へ戻るときは、離れる前のスクロール位置と、直前に選んでいた行に戻す。
どちらを出すかは`src/lib/inboxPane.ts`が決める。

一覧は`InboxList`、詳細は`InboxDetail`の別の部品が描く。
再実行、解決、承認などの行の操作は、一覧の行ではなく詳細のペインに置く。
一覧の行は1つのbuttonなので、操作のbuttonを入れ子にしないためである。
詳細は、種類ごとの描き分けを`InboxDetail`の1か所に集める。
詳細のペインは左寄せで、本文の幅に上限を置く。
上限は、詳細の部品([`ApprovalOverview.tsx`](../../../console/src/screens/inbox/ApprovalOverview.tsx)、[`FailureOverview.tsx`](../../../console/src/screens/inbox/FailureOverview.tsx)、[`NoticeDetail.tsx`](../../../console/src/screens/inbox/NoticeDetail.tsx))の`article`のclassが定める。
サイドバーを畳んでも位置が動かない。
一覧の行は、1行目に題名と相対時刻、2行目に種類、副題、期限、状態のバッジを並べる。
一覧の項目がすべて通知、またはすべて失敗のときは、全行に同じ語が付いて情報にならないので、「通知」と「失敗」の語を省く。
この判定は、種類の切り替えで絞り込む前の一覧全体で行い、切り替えても行の書式が変わらないようにする。
承認の語(要件定義、Issue化提案、改善提案、承認依頼)は区別を担うので、承認だけの一覧でも省かない。
通知の副題は、同じ題名の通知を見分けるために、本文の最初の対象(`owner/repo#番号`)、最初の版(先頭7桁)、本文の抜粋を「・」でつないで1行にする。
見分ける相手は、種類の切り替えで絞り込む前の一覧全体にある、同じ種類の通知である。
同じ種類の通知が並ぶときは、全員が同じ値の対象と版だけを省く。
一部だけ同じなら、全員に出す。
全員が同じ値なら見分ける役に立たず、幅が狭い一覧では抜粋の食い違いを押し出すためである。
同じ種類の通知が1件だけのときは、本文にあれば出す。
抜粋は、副題に出した対象と最初の版を除いた本文から決まった文字数を取り、省いた側へ省略記号を付ける。
文字数は[`src/lib/inboxView.ts`](../../../console/src/lib/inboxView.ts)の`EXCERPT_LENGTH`が定める。
対象と版は現れた位置で切り出す。
先頭の対象と同じ文字列で始まる別の対象(`o/r#1`を切っても`o/r#12`)や、2番目以降の対象と版は残る。
版の直前が文頭から始まる「ラベル: 」で、直後が「。」か本文の終わりのときは、ラベルとコロンと「。」も一緒に切り出す。
ラベルの長さの上限は、同じファイルの正規表現`LABEL_BEFORE_SHA`の量指定子が定め、[`keeps a label longer than twelve code points`](../../../console/src/lib/inboxView.test.ts)で確かめる。
絵文字などはコードポイントで数える。
区切りは、半角か全角のコロンに空白が0個以上続く形とする。
切り出す範囲が対象の範囲と重なるときは、1つにまとめて切り出す。
版だけを切ると「反映を待つ版: 。」のように値の無い文が残るためである。
同じ種類の通知が並ぶときは、本文の先頭が最も長く重なる通知と食い違う位置の直前の語の区切りから抜粋する。
書き出しがそろう通知を見分けるためである。
副題にマウスを重ねると、本文の全体を表示する。
通知の詳細の先頭には、種類と重要度を1つにしたタグ(「要対応の通知」と「情報の通知」)を出す。
通知の本文に含まれる40桁の版は、先頭7桁で示す。
全体は、マウスを重ねたときの表示と、複製のボタンで取り出せる。
本文が取得の上限で切れているとき、末尾に接する40桁は、別の値の途中である可能性があるので版にしない。
状態のバッジは2行目の末尾で、狭いときは省略記号で縮める。
2行目の高さは[`InboxList.tsx`](../../../console/src/screens/inbox/InboxList.tsx)の`ItemRow`と`GroupHeader`のclassで固定し、バッジの有無によらず、どの行も同じ高さにする。
行の頭に種類の点は付けない。
期限が24時間を切った行(期限を過ぎた行を含む)だけ、期限に警告色の印を付ける。
期限を過ぎた行は、失敗の色にする。
選んだ行は、藍を帯びた面(ライトでは淡く、ダークでは暗い)と左の帯で示す。

同じ種類の未解決の通知が2件以上あるときは、件数つきの1行にまとめる。
まとめる単位は通知の種別だけで、対象や版は見ない。
重要度は種別だけで決まるので、同じグループに要対応と情報の通知は混ざらない。
承認と失敗は、1件ずつ判断して操作するので、まとめない。
解決済みの通知は、対応が済んでいるので、まとめずに1件ずつ出す。
まとめた行は、最初の通知があった位置に置き、時刻には中で最も新しい通知の時刻を出す。
副題には、閉じている間、中の通知の本文が最初に挙げる対象を、重複なしで最大2つ並べ、残りを「ほか対象N件」と数える。
「対象」の語は、通知の件数と紛れないよう添える。
対象を挙げない通知は数えない。
別の対象の通知が紛れ込んだことに、開かなくても気づけるようにするためである。

まとめた行を押すと、個々の通知が字下げされて開く。
開閉のbuttonは`aria-expanded`を持ち、矢印キーで通常の行と同じように移れる。
グループは、閉じた状態で始める。
ただし、選んだ通知を含むグループは開く。
URLで通知を直接開いたときも、選択が別の通知やグループに移ったときも同じである。
選んだ通知を折りたたみの中に隠さないためである。
開いた後に自分でグループを閉じても、選択は外れず、同じ選択のままでは開き直さない。
閉じたグループが選んだ通知を含むときは、行の背景で示し、読み上げにも「選択中の通知を含む」と添える。
取り直しや種類のチップでの絞り込みで、まとめられなくなった(行から消えた)種別は、開閉の状態から外れる。
チップを切り替えて戻すと、そのグループは閉じた状態に戻る。
URLの選択は個々の通知のidなので、グループの開閉に左右されない。
グループが後から成り立つ(同じ種別の通知が増える)と、行の並びが変わる。
そのとき、押していた行はグループの中に移って消えるので、フォーカスを失うことがある。

サイドバーのバッジと種類の切り替えのチップは、まとめる前の個々の項目の数で数える。
見出しの副題は、何も残っていないときの「すべて片付いています」だけで、種類ごとの件数は出さない。
件数はチップの横が示すので、同じ数字を2か所で確かめさせないためである。
一覧では、まとめた行の件数と、まとめない行(1行で1件)の合計が、通知の数と一致する。
開閉の判定とこの対応は`src/lib/inboxGroups.ts`が決め、テストで固定する。

承認の詳細と行には、期限があれば残り時間を出し、過ぎていれば「期限切れ」と出す。
承認の詳細には、題名、種類、作業項目(要件定義なら試行)、Issueへのリンク、期限、依頼した時刻を出す。
要件定義の承認には、要件定義書(`/console/items/<id>/requirements`)へのリンクを添える。
監査から出た提案には、元の監査レポート(`/console/reports/audit/<id>`)へのリンクを添える。
題名は`displayableIssueText`を通してプレーンテキストで描く。
期限と依頼した時刻は、日本時間の絶対時刻と相対時刻を並べる(例: 10/15 18:48まで(残り6日)、10/09 18:48(1時間前))。
IssueのリンクはGitHubのIssueのURLの形のときだけ張る。

### 失敗と再実行

一覧には、`summary`の失敗の行を、作業項目ごとに1行で出す。
対象は、状態が失敗、人の対応待ち、期限切れの作業項目である。
監査の失敗は、再実行できないので行にしない。
件数のカードで知らせる。
同じIssueに新しいサイクルがある古い作業項目は含まない。

詳細のペインには、次を出す。

- 題名、種類、状態
- 作業項目への経路(`/items/<id>`)とリポジトリ
- IssueかPRへのリンク
- 失敗した時刻と、最終更新の時刻。
  一覧は最終更新の新しい順に並ぶので、並びの根拠を示す
- フローとステップ、ジョブへのリンク
- 失敗の内容と、状態が変わったときの注記

失敗の記録が無い作業項目では、その旨を出し、時刻は状態が変わった時刻で代える。
失敗の記録が、今の状態へ遷移した時刻より5分以上前のものは、前の失敗の記録とみなす。
再実行の起動に失敗して人の対応待ちに戻った作業項目で、前の失敗の内容を今の失敗として見せないためである。
この記録の内容、フロー、ジョブは出さず、「この状態になってからの失敗の記録はありません」と出す。
時刻は状態が変わった時刻にする。
失敗の処理は、記録を書いてから状態を更新するので、正常な記録も状態の時刻より数秒前になる。
5分は、その差を許す幅である。
失敗の内容と注記は、実行の出力であり、Issueの文字を含みうる。
そのため`displayableIssueText`を通し、プレーンテキストで描く。
`summary`は失敗の文を500文字で切る。
500文字に達した文には、先頭だけを表示している旨と、ジョブのログへの案内を添える。
IssueかPRへのリンクは、GitHubのURLの形のときだけ張る。
PRのURLは、リポジトリと番号から組み立てて、同じ検査を通す。
ジョブへのリンクは、ジョブIDの形のものだけ張る。

再実行は、詳細のペインのボタンから、確認を経て`retryWorkItem`を呼ぶ。
確認は、ブラウザ標準のdialog要素をモーダルで開く。
最初のフォーカスは「取り消す」に置く。
確定すると、フォーカスを詳細のペインの処理中の行へ移す。
ボタンが無効になっても、フォーカスが文書の先頭へ落ちないためである。
確認には、再実行する作業項目を特定する情報(題名、リポジトリ、対象のIssueかPR、失敗した時刻)と、状態の遷移(今の状態 → 再開先)を出す。
似た題名や古い表示の作業項目を取り違えないためである。
開いた直後のフォーカスは、明示的に「取り消す」へ置く。
確定では取り消しの処理を呼ばない。
確認を開いている間に、その作業項目が一覧から外れたときは、確認を閉じ、その旨をトーストで知らせる。
再開先は、scriptが作業項目の種類で決める。

- PRのレビューは、レビュー中へ戻す
- PRの修正は、修正中へ戻す
- Issueは、要件定義の生成、設計、実装のどれかへ戻す。
  画面はこの3つを並べて示す。
  再開先の決まりは[作業項目の状態とリース](../work-items.md)の「再実行」に書く
- Issueの再開先が要件定義の生成のときは、GitHubの現在のIssueの題名と本文を取り込み直す。
  確認の注記で伝える
- 知らない種類は、再開先を決めつけない。
  ボタンは押せるままにして、断るかどうかはscriptに任せる
- 監査は、scriptが再実行を認めない。
  ボタンの代わりに理由を出す
- dependabotの更新も、scriptが再実行を認めない。
  ボタンの代わりに、PRを確かめて手でマージするか閉じるよう案内する
- 調査も、scriptが再実行を認めない。
  ボタンの代わりに、依頼を新規投入し直すよう案内する

ロックのキーは作業項目ごとである(`retryTargetKey`)。
失敗の行の1つを再実行している間も、ほかの行は押せる。
再実行のボタンは詳細のペインだけにある。
ロックは画面全体で共有するので、同じ作業項目は二重に実行できない。

scriptは、次のときに再実行を断る。
確認の文で、事前に挙げて伝える。

- 記録されたフローが動いている、または動いているか読めないとき
- 同じIssueに、より新しいサイクルがあるとき
- 要件定義が承認済みで、要件定義の改ざんや差し戻しの停止ではなく、設計が無効か承認済みで、実装が無効のとき
- 確認から更新までの間に、作業項目の状態が変わったとき

断りはジョブの失敗として返り、結果が分からない失敗と区別できない。
そのため、断られたときの知らせにも「処理に失敗した可能性があります」と「一覧を読み直して確かめてください」の案内が入る。
括弧の中に、scriptの断りの理由が入る。
断りを区別して返すには、scriptの戻りの契約を変える必要がある。
この課題はConsoleの外で扱う。

成功と、結果が分からない失敗の後は、`summary`を読み直す。
結果は、どの作業項目のものかを添えて、トーストで伝える。
トーンは次のとおりである。

- 成功は、成功として伝える
- 別の実行が先に作業項目を押さえていたときと、結果が分からない失敗は、警告にする
- ジョブが動く前に断られた失敗は、エラーにする

読み直せなかったときは、一覧が更新されるまで、その作業項目を押せないままにする。

### 取り込み時点のIssue

要件定義の承認の詳細には、取り込み時点のIssueの題名と本文を出す。
実装のClaudeが受け取るのはこの内容で、GitHub上の現在のIssueではない。
承認者が現在のIssueだけを読んで承認すると、取り込み後に書き換えられた内容を見落とすためである。

内容は選んだ承認の作業項目ごとに、`console_query`の`intake_snapshot`で取る。
`summary`には載せない。
本文が長く、120秒ごとの取得に含めると応答が膨らむためである。
却下や再実行による作り直しは、同じ作業項目の取り込み内容を書き換える。
そのため、承認依頼ごとに別のキャッシュにし、画面を開くたびに取り直す。
更新前の内容を新しい承認の画面に出さないためである。

題名と本文は起票者が書いた信頼できない入力である。
次のように扱う。

- 題名は、MarkdownやHTMLとして解釈せず、文字列としてReactが描く。
- 本文は、既定の原文では、解釈せずに`<pre>`へ文字列として描く。
  タグやリンクは文字のまま見える。
  承認の対象は原文である。
- 本文のプレビューは、参考の表示として、切り替えで選んだときだけ描く([承認画面の本文のプレビュー](#承認画面の本文のプレビュー))。
- 本文は20,000文字、題名は300文字で`console_query`が切る。
  切ったときは、先頭だけを表示している旨を出す。
- 切った後ろの部分は、承認者がConsoleでも、HTMLのコメントや不可視の文字を描かないGitHubの画面でも確かめられない。
  後ろの部分にあるHTMLのコメントの開始(`<!--`)と不可視の文字の数を`console_query`が数え、あれば警告する。
- 取り込み内容を更新したことがあれば(`refreshed`。更新の履歴から導く)、目立つ警告を出す。
- 見えない文字と、並びの見た目を入れ替える文字は、代替文字(U+FFFD)に置き換え、置き換えたことを警告で示す(`src/lib/intakeText.ts`)。
  対象は、Unicodeの分類がCf(双方向の制御文字、ゼロ幅の文字、tag文字を含む)、Cc(改行とタブを除く)、Zl、Zpの文字と、異体字セレクタである。
- 題名と原文の要素は、`dir="ltr"`と`unicode-bidi: isolate`で、周りの文字の並びに影響しないようにする。

### 承認画面の本文のプレビュー

要件定義の承認画面の取り込み時点のIssueと、Issue提案の本文は、原文を既定にして、プレビューを参考表示で足す。
表を含むMarkdownは原文では読みにくいが、承認の対象は実装や起票に渡る原文だからである。
プレビューは、HTMLのコメント、閉じない`<!--`より後ろの本文、リンク参照定義、画像を描かない。
そのため、プレビューを見たままでは、承認者が見ていない内容を承認しうる。

切り替えと状態は、画面が持つ。
取り込み時点のIssueでは`RequirementsReview`、Issue提案では`ProposalReview`である。
画面は、`mode`と、プレビューを一度でも選んだかの真偽値(`previewed`)を持つ。
どちらの向きの切り替えでも`previewed`を立てる。
選択肢の名前は「プレビュー」と「原文」で、既定は原文である。
読み上げの名前は、取り込み時点のIssueでは「取り込み時点のIssueの表示の形式」、提案では「提案の本文の表示の形式」である。
承認依頼を替えると、画面ごと作り直し、原文に戻る。

パネル(`IntakeSnapshotPanel`と`ProposalBody`)は、`mode`と切り替えの要素を受け取る。
`mode`を省略すると原文になる。
設計の承認画面(`DesignReview.tsx`)は、同じパネルを`mode`なしで使うので、原文のままである。
要件定義書の表示の形式の切り替えは別で、承認の判定に渡さない。

次のとおり、プレビューを参考表示に留める。

- プレビューを表示している間は、承認を止める。
  止める理由は、対象を名指しする。
  画面は、既存の止める理由があればそれを優先し、なければ`previewBlockedReason`の文を`approveBlockedReason`に渡す。
- プレビューを一度でも選んだ承認は、原文を表示している間、承認バーに、原文を確かめたかのチェックを出す。
  プレビューを表示している間は、承認を止めているので、チェックを出さない。
  切り詰めの確認とは別のチェックで、別の状態で持つ。
  両方が要るときは、両方を済ませるまで承認を止める。
  入れたチェックは、プレビューへ切り替えても承認バーに残る。
  判定の順は、止める理由、期限、切り詰めの確認、プレビューの確認である(`approveGateProblem`)。
- 確認ダイアログで「承認する」を押した時点にも、同じ判定をやり直す。
- 却下は止めず、チェックも求めない。
- プレビューの本文は、見えない文字を置き換えた文字(`displayableIssueText`の結果)を`Markdown`に渡す。
  目次、図、タイトルの非表示は使わない。
  `Markdown`は生のHTMLを描かず、リンクを作業項目のリポジトリのIssueとPRに絞る。
  `.drawio`でない画像は、代わりの文字だけを出す。
- プレビューの本文の上に、固定の注記を出す。
  原文には出さない。
- 次の警告は、どちらの形式でも出す。
  更新の履歴、見えない文字の置き換え、切り詰め、切った後ろの内容である。
- 本文が空のときは、どちらの形式でも固定の文を出す。
- 提案のリンク先のリポジトリは、承認依頼の作業項目のリポジトリである。
  提案のIssueは、承認依頼と同じ作業項目のリポジトリに作られる。
  リポジトリが分からない呼び出しには、`null`を渡し、リンクを作らない。

プレビューを表示した状態は、`data-preview`の属性で示す。
`Markdown`の描画は重いので、`memo`で包んだ部品の入力は、同じ参照を渡し続ける。

この方針の根拠と残るリスクは、[Consoleの安全策の内部仕様の「取り込み時点のIssueと提案の描画」](security.md#取り込み時点のissueと提案の描画)に書く。

### 承認バー

承認と却下の操作は、詳細のペインの承認バー(`ApprovalBar`)に置く。
要件定義では、取り込み時点のIssueのパネルと、承認する試行の要件定義書を並べ、その直下に置く。
Issue提案では、提案の本文の直下に置く。
承認者が見た内容の隣で押せるようにするためである。

詳細に出す操作は、依頼の状態で決まる(`decisionSurface`)。

| 依頼の状態 | 出すもの |
| --- | --- |
| 承認待ちで期限内 | 承認と却下 |
| 承認待ちで期限切れ | 操作を出さず、その旨の文を出す |
| 承認済みでIssueを未作成のIssue提案 | 「Issueの作成をやり直す」だけを出す |
| その他の承認済み | 操作を出さず、「起票を待っています」などの文を出す |
| 却下済みなど | 何も出さない |

知らない種類の承認は、操作を出さない。

| 操作 | 決まり |
| --- | --- |
| 承認 | 確認ダイアログを経る。承認は取り消せず、要件定義ではClaudeの実装が始まるためである。ダイアログには件名、承認依頼のid、起こることを出し、開いたら取り消しにフォーカスを置く。ダイアログは新しい依存を足さず、ブラウザ標準の`<dialog>`で作る(`components/ConfirmDialog.tsx`)。再実行の確認も同じ部品を使う |
| 却下 | 理由が必須で、空白だけでは押せない。理由の上限は[`src/api/writes.ts`](../../../console/src/api/writes.ts)の`MAX_REASON_LENGTH`が定め、入力欄の横に「文字数 / 上限」を出す。要件定義の却下だけ、確認ダイアログを経る。却下は要件定義の作り直しになり、その時点の現在のIssueで取り込み内容が更新されるためである |
| 補足 | 承認の記録には、Consoleから決めたことを示す固定の文を添える。画面から補足は入力しない |

確認ダイアログで「承認する」を押した時点で、期限と、承認を止める理由と、確認のチェックをもう一度確かめる。
満たさなければ送らず、ダイアログを閉じて理由を出す。
ダイアログを開いている間に期限を過ぎることがあるためである。

### 承認と却下の呼び出し

承認と却下は`decideApproval`で呼び、`useWriteMutation`のロックと読み直しに載せる。
ロックのキーは依頼のidで、承認と却下は同じキーで止まる。
二重に押しても、呼び出しは1回になる。
成功したら`summary`を読み直し、処理した依頼が一覧から消える。
ただしIssue提案は、承認の後にIssueを作り終えるまで、承認済みの状態で一覧に残る。
結果は`sonner`のトーストで知らせる。
結果が分からない失敗の文は`describeWriteFailure`が作る。
読み直せなかったときは、一覧が更新されるまで、その依頼のボタンを押せないままにする。

送る`options`の形は、依頼の種類で決め、他のキーは送らない。
Issue提案は`{ with_factory_label: boolean }`、それ以外は`{}`である。
作るIssueにfactoryラベルを付けるかは、チェックボックスで選ぶ。
監査から出た提案は初期値をオンにし、PRのレビューから出た提案はオフにする。
ラベルを付けられない監査の提案(`factory_label_available`が偽)は、選択肢を出さず、`false`を送る。

### Issue作成のやり直し

承認を記録した後でIssueの作成が止まった提案は、承認済みのまま残る。
「Issueの作成をやり直す」は、同じ承認を`decideApproval`でもう一度送る。
サーバーは、同じ決定が記録済みなら、記録せずに起票だけをやり直し、記録済みのラベルの選択を使う。
そのため、ラベルの選択肢は出さない。
押しても結果が変わらないためである。
作成済みのIssueは、マーカーで見つけて再利用する。
確認ダイアログに、この2点を書く。

承認の直後は、起票の処理が走っている間でも押せてしまう。
決定の時刻は`summary`と`inbox`のどちらにも無いので、押せる条件に経過時間を入れられない。
代わりに、次の2層で重なりを防ぐ。

- 画面: やり直しに成功したら、このタブでは15分間、同じ依頼のボタンを止めて「起票に数分かかります」と出す(`redoCooldowns`)。
  時刻はタブのメモリにだけ持つ。
  画面とダイアログにも、承認の直後は押さないよう書く
- サーバー: `issue_proposal_apply`が、Issueを作る前に`claimIssueCreation`の条件付きUPDATEで印を取る。
  取れなかった呼び出しは、何もせずに終える。
  印は15分で切れるので、止まった処理のやり直しは塞がれない。
  失敗して提案を保留に戻した後も印は残り、期限が切れるまで、次の承認は何もせずに終わる。
  期限を過ぎて走り続けた呼び出しが失敗して戻すとき、印を取り直した別の呼び出しがIssueを作っている最中のことがあり、その処理と重ならないようにするためである。
  同時の呼び出しは、どちらもマーカーの走査の時点でIssueが無いと見て、Issueを2件作りうる。
  Windmillの同時実行の制限は設定しない。
  有償版でしか効かないので、印だけで直列化する

別のタブや別の端末からは、画面の側では止められない。
サーバーの印が、この重なりを止める。

### 断りの表示

`approval_decide`は、承認の記録の前に、次の理由で断ることがある。
断りはジョブの失敗として返り、文は英語である。
既知の断りの文を含む失敗だけを、日本語の固定文と取れる手にして、承認バーの中に出す(`classifyDecisionRefusal`)。
トーストにも同じ文を出す。
バーは操作した場所で断りと取れる手を示し、トーストは項目が一覧から外れてバーごと消えても残る。
Windmillは失敗の文に「Error:」などを前置きすることがあるので、文頭は見ない。
他のscriptの失敗とは、断りの文に固有の部分で区別する。

| 断りの理由 | 取れる手 |
| --- | --- |
| Issueが取り込みの後に書き換えられた | Issueを取り込み時点の内容に戻して承認し直す。現在のIssueを使うなら却下する |
| 現在のIssueを比べられなかった | 少し待って承認し直す。Issueを移したか削除したなら却下する |
| 別の決定が記録済みか、期限切れ | 一覧を読み直して状態を確かめる |
| 却下の理由が空 | 理由を入力して却下し直す |
| 承認依頼が見つからない | 一覧を読み直して状態を確かめる |

文は、`approval_decide.ts`と`approval_support.ts`が関数で作る。
`tests/scripts/console_approval_refusal_contract.test.ts`が、その関数の出力を画面の分類に通す。
Windmillの失敗の包み方を通した場合も、同じテストが確かめる。
既知でない文言は、結果が分からない失敗の案内に落とす。

### 要件定義の承認の前提

要件定義の承認は、承認者が次の2つを見られるときだけ押せる。
実装のClaudeが受け取る取り込み時点のIssueと、承認の対象である要件定義書である。
どちらかが読み込み中か、取得に失敗しているあいだは、承認を止めて理由を添える。
承認の可否は、取得の状態だけで決まる。
そのため、承認が載る2つの面(要件定義の承認と、Issue提案の承認)は、取得が済んだらすぐ内容を出す。
読み込み中の骨組みは残さない([画面の切り替え](../console.md#画面の切り替え))。
承認を押せるのに内容が見えない時間を作らないためである。
作業項目に取り込み内容が無いときも止める。
確かめる内容が無いまま承認させないためである。
却下は止めない。
内容を見られないことが、却下を妨げる理由にならないためである。
本文が長く切られているとき(`body_truncated`)は、GitHubで全文を確かめた旨のチェックを求め、チェックするまで承認を止める。
取り込み後に書き換えられていた場合の警告(`refreshed`)は、パネルの先頭に加えて、承認バーの中にも出す。
承認を押す位置で、確かめるよう促すためである。

要件定義書は、承認依頼の試行(`draft_attempt`)を指定して取り、要件定義書の画面と同じ部品で描く。
本文の描画、図の拒否、見えない文字の置き換えは、その部品に任せる。
承認の画面では、メタ情報、試行の切り替え、目次を省く。
承認する試行を切り替えさせないためである。
長い本文は、枠の中でスクロールさせ、承認バーを遠ざけない。
「別の画面で開く」のリンクから、要件定義書の画面で読める。
`draft_attempt`が`null`で承認の試行が分からないときは、最新の試行で代えず、「承認する試行が特定できない」として承認を止める。
最新の試行は、承認する試行と違うことがあるためである。
取得した書の試行が承認の試行と違うときも、承認を止める。

承認の前の確認は、承認の操作を受ける側で働く([要件定義](../requirements.md)の「承認の前のIssueの確認」)。

### 設計書の取得

設計の承認依頼が指す設計書は、承認依頼のidを渡して、`console_query`の`approval_design_doc`で取る。
型付きの関数は`fetchApprovalDesignDoc`と`useApprovalDesignDoc`である。
この取得を呼ぶのは、設計の承認画面(`DesignReview`)である。

返す`text`は、承認後の実装が受け取る文字そのものである。
人が見る文字と実装が受け取る文字を一致させるためである。
backendが実装の関門と同じ整形(`normalizeDesignForImplement`)を通すので、Consoleは整形の関数を持たない。
整形は、制御文字と書式文字を除き、秘密値をマスクし、8000コードポイントで切る。
切ったときは末尾に印の行を足し、`truncated`が真になる。
HTMLとリンク参照定義は除かず、文字のまま返す。
承認できる状態(原文)では、描く側はこの文字を要素や定義にしない。
要素にして描くのはプレビューだけで、プレビューを表示している間は承認を止める。
さらに描く側は、整形が除かない不可視文字(異体字セレクタ、ハングルのフィラー、点字の空白、結合文字、U+2028、U+2029、`\r`)を、代替の記号やコードポイントの表記で見える形に描く。
`safeText`は文字を置き換えて`text`と対応しなくなるので通さず、1文字ずつの対応をテストで確かめる。

依頼が指す設計書を、実装の関門(`latestDesignApproval`)と同じ条件で引く。
結ぶのは、依頼と同じ作業項目の設計書だけである。
作業項目の最新の設計書は引かない。
承認の対象とは別の設計書を見せないためである。
依頼の状態は問わず、承認済み、却下、期限切れの依頼の設計書も返す。
状態は`approval_status`で添える。
設計の依頼でない、設計書が無い、下書きが別の作業項目のものであるときは、空の配列を返す。
図、要約、未確定事項と、整える前の本文は返さない。
実装に渡らないためである。
承認依頼のidが無いか、正の整数でなければ、backendは例外を投げる。

型は`ApprovalDesignDocRow`に合わせてある。
`tests/scripts/console_approval_design_doc_contract.test.ts`が、変換結果が型ガードを通ることを確かめる。

### 設計の承認

設計の承認画面(`console/src/screens/inbox/DesignReview.tsx`)は、取り込み時点のIssueと、承認する依頼の設計書の全文を並べ、その直下に承認バーを置く。
要件定義の承認と同じ組み立てで、承認を押せるかどうかは、取得の状態と、設計書の表示の形式で決める。

設計書は、原文を既定で出す。
原文は`<pre>`に、実装に渡る正規化後の文字のまま出す。
HTMLとリンク参照定義は解釈せず、文字として出す。
読みやすい描画(プレビュー)は、承認できる状態では出さない。
描画と全文の食い違う余地ができるためである。
参考の表示として、設計書のパネルの見出しの下の切り替えで置き、プレビューを表示している間は承認を止める。
切り替えの読み上げの名前は「設計書の表示の形式」で、選択肢は「プレビュー」と「原文」である。
切り替えは、設計書の本文を描く部品の中だけに置き、取得中、取得の失敗、設計書が無いときには出さない。
取り込み時点のIssueのパネルは、切り替えの対象にせず、常に原文のままである。
図、要約、未確定事項は実装に渡らないので、画面に出さず、渡らないことを注記する。

プレビューを一度でも選んだ承認は、原文を表示しているとき、原文で確かめたことを申告するチェックを求める。
チェックの文は、設計書のプレビューを表示したことと、原文で確かめたことだけを伝える。
プレビューが描かないものは、注記が1か所で挙げるので、チェックの文では繰り返さない。
チェックは自己申告で、読んだことは保証しない。
切り詰めの確認とは別の状態で、切り詰めの確認を済ませても、プレビューの確認は求める。
プレビューを表示している間は、承認そのものを止めるので、チェックを出さない。
承認バーの判定の順は、止める理由、期限、切り詰めの確認、プレビューの確認である。
チェックを付けた後に、プレビューへ移って原文へ戻しても、付けたチェックは残る。

プレビューを選んだ記録は、設計書の表示の状態(`mode`と`previewed`)の`previewed`が持つ。
`nextDesignView`が、今の形式か次の形式がプレビューのときに立て、一度立てたら下ろさない。
知らない形式への切り替えは、プレビューとして扱う。
この記録は画面の状態にだけあるので、承認画面を離れて戻ると消え、原文のまま確認のチェックを求めない。
承認依頼を替えると、承認画面ごと作り直すので、別の依頼には持ち越さない。

注記は、表示の形式ごとに1つで、設計書の本文を描く部品が持つ。
原文では、全文が実装にそのまま渡ることを伝える。
プレビューでは、承認の対象が原文であること、プレビューが描かないもの、原文で確かめることを伝える。
描かないものは、生のHTML(コメントを含む)、リンク参照定義、画像、閉じない`<!--`より後ろの本文、文字参照で書いた見えない文字と向きの制御文字である。
プレビューの本文は注記を持たず、`DesignTextPreview`が`Markdown`だけで描く。
異常の内訳、行数、終わりの印は、どちらの形式でも出す。

全文は、`visibleText`が返す区切りだけから描く。
見えない文字はコードポイントの表記(`U+2028`)にする。
3行以上続く空行は、件数を書いた印(`[空行 N 行]`)にし、長く続く空白も印(`[空白 N 個]`)にする。
どの印も、元の文字列を属性に持つ。
`<pre>`の中の行は、行ごとに`<bdo dir="ltr">`で包む。
右から左に書く文字が、周りの並びを入れ替えないためである。
印の要素には、向きを付けない。
`tab-size`は4にする。
承認を止める件数がタブを4桁に数えるためである。

行数とコードポイント数、全文の終わりの印は、`<pre>`の外に出す。
本文が同じ文言を書いても、本物の印と紛れないためである。
行番号の欄は置かない。
`<pre>`は長い行を折り返し、空行の連続を1行の印にまとめるので、番号が本文の行とずれるためである。
長さは、行数とコードポイント数で確かめる。
全文を最後までスクロールしたかは、承認の条件にしない。

設計書が長さの上限で切られているときの理由は、承認バーの止める理由だけが出す。
全文のパネルには、同じ注記を重ねない。

承認を止める理由は、`designBlockedReason`と、画面のソースの中の`designPreviewGate`が決める。
`designPreviewGate`は、表示の形式が`text`(原文)以外のときに、理由を返す。
プレビューのほか、知らない値でも止める。
原文で、プレビューを一度でも選んでいるときは、確認のチェックの文を返す。
画面は、`designBlockedReason`の理由があればそれを優先し、なければ`designPreviewGate`の理由を、承認バーに渡す。
確認のチェックの文は、`designPreviewGate`が返したものだけを、承認バーに渡す。
そのため、設計書が長さの上限で切られているときは、プレビューを表示していても、切られている理由が出る。
最初の表示の状態は、省略できる`initialView`で決める。
既定は、原文を表示し、プレビューをまだ選んでいない状態である。
承認の詳細(`ApprovalOverview`)は`initialView`を渡さない。
承認バーは、承認依頼ごとに`key`で作り直す。
却下は、設計書を読めなくても押せる。
全文に見えない文字や見えにくい並びがあるときは、内訳をパネルの先頭に出し、承認を止める。
設計書の`approval_status`は描かない。
依頼の状態は、見出しのバッジが出す。

承認と却下の呼び出しには、設計のときだけ`kind`を渡す。
結果のトーストと、断りの案内を、設計の行き先に合わせるためである。
承認は「実装の開始は作業項目で確かめてください」、却下は「行き先は作業項目で確かめてください」と伝える。
却下の行き先は、設計の再生成、要件定義へ戻る、人の対応待ちの3通りで、反映が済むまで分からない。

次の契約テストが、描き方と配線を固定する。
これらは保護パスにある。

- 描き方: `tests/scripts/console_design_visible_text_contract.test.ts`が確かめる。
  `visibleText`だけから描くこと、`safeText`を通さないこと、`bdo`と`tab-size`を持つことである。
- 配線: `console/src/designApprovalWiring.test.ts`が確かめる。
  承認画面から承認のボタンまでを描き、異常のある設計書で承認が止まることを確かめる。
  画面が描いた`<pre>`の文字と印が持つ元の文字列から全文を組み直すと、固定した入力の`text`と一致することも確かめる。
  全文を切る・隠す代表的なスタイルを使わないことも、ソースで確かめる。
  スタイルの検査は拒否の一覧で、網羅しない。
  プレビューの配線も固定する。
  最初の描画が原文で、確認のチェックが出ないことを確かめる。
  最初の状態が、プレビューで、まだ選んでいないときは、承認が止まることを確かめる。
  このとき、止める理由の文とプレビューの印も出る。
  最初の状態が、原文で、プレビューを選んだ後のときは、確認のチェックが出て承認が止まることを確かめる。
  このとき、理由は確認の理由の文である。
  切り詰めた設計書では、プレビューでも切り詰めの理由が先に出ることも確かめる。
  遷移の関数`nextDesignView`と、判定の関数`designPreviewGate`は、直接呼んで戻り値の全体を照合する。
  ソースでは、次のことを確かめる。
  判定の関数の呼び出しが1つで、止める理由と確認の文だけを、それぞれ1か所で承認バーに渡すこと。
  状態が1つで、`setView`という名前の出現が2つで、切り替えが`nextDesignView`を使う1か所であること。
  `mode`が名指しの3か所だけに渡ること。
  `DesignTextPreview`がプレビューの分岐にだけ現れること。
  `ApprovalOverview`が`initialView`を渡さないこと。
  `ApprovalBar`のソースが、`previewCheckMessage`が非nullのときに確認を求める式を含むこと。
  `DesignTextPreview.tsx`のソースが`Markdown`で描き、`dangerouslySetInnerHTML`と`rehype-raw`を使わないことも確かめる。

承認画面のファイル(`DesignReview.tsx`)自体も保護パスにある。
全文を描く部分、止める判定への入力の渡し方、プレビュー中の停止の式、行数と終わりの印を、1つのファイルに持つためである。
保護しない祖先の部品、共有のパネル、全体のCSSから一部の行を隠す手は、ファイル単位の保護では閉じられない。
この経路と残るリスクは、[Consoleの安全策の内部仕様の「設計の承認画面の保護」](security.md#設計の承認画面の保護)に書く。

### Issue提案の本文

Issue提案の本文と、ラベルの選択肢の出し分けに使う情報は、`summary`に載せていないので、`console_query`の`inbox`から読む(`useInboxProposals`)。
本文と出どころの期間と担当は`displayableIssueText`を通す。
本文は、既定の原文では解釈せず、プレーンテキストで描く。
切り替えで選んだときだけ、プレビューを参考に描く([承認画面の本文のプレビュー](#承認画面の本文のプレビュー))。
置き換えた文字があれば、警告を出す。
提案が読めないか、一覧に無いときは、本文が分からないまま承認させないので、操作を出さない。
`tests/scripts/console_inbox_contract.test.ts`が、backendの`inbox`の変換結果が型ガードを通ることを確かめる。

### 一覧に出ない項目と空の状態

詳細から行える操作は、承認と却下、失敗の再実行、通知の解決である。
一覧に出ていない件数は、種類ごとのカード(色の点、件数)で知らせる。
対象は、取得の上限を超えた承認、失敗、通知と、再実行できず、後の監査で報告済みにもなっていない監査の失敗である。
監査の失敗のカードだけ、システムの画面へのリンクにして、押せると分かる矢印を添える。
システムの画面が読めるのは監査の失敗だけなので、取得の上限を超えた承認、失敗、通知のカードはリンクにしない。
残る件数は、報告済みになっていない監査の失敗と、取得の上限を超えた分である。
監査の失敗のカードには、再実行できないこととシステムの画面で確認することを添える。

要対応には、人にできる行動があるものだけを出す。
後の監査で報告済みの監査の失敗は、次の監査が失敗した期間を扱っており、人にできる行動が残らない。
そのため、カードの件数から外す。
報告済みかどうかは、後の報告の開始が前の報告の終わり以前かで決める。
切り詰められて報告の開始が遅れた失敗は、作業項目が保持期間で消えるまで要対応に残る。
前の報告が無いとき(初回と、保持期間で前の報告が消えた後)は、後の監査があれば報告済みとして扱う。
カードの件数は、summaryの`counts`の`audit_failures_open`である。
この件数は取得の上限の前の全件から数える。
監査の失敗の判定の規則は[監査の内部仕様](../audit.md#失敗した監査と要対応)にある。
再実行できる失敗の件数を求める引き算は、報告済みを含む監査の全件を引く。
`counts`の失敗には報告済みの監査も含まれるためである。
サイドバーのバッジは、監査を数えない。
古いbackendは`audit_failures_open`を送らないので、そのときは見えている監査の失敗の全件をカードに出す。
取得は新しい順に上限まで読むので、上限を超えた分は古いものから表示されない。
承認、失敗、通知のカードにその旨を添える。
同じ数をサイドバーには出さない。
画面の中で1か所だけに示すためである。

一覧が空のときは、画面を2つに割らず、中央に1枚の面を出す。
面には、承認、失敗、通知が無いことと、ほかの種類に残る件数のカードを載せる。
最終更新と自動更新の間隔は、画面の見出しが示すので、面には載せない。
何も残っていないときだけ緑のチェックを出す。
ほかの種類が残っているときは、中立のアイコンにして、片付いた印象を与えない。
一覧の取り直しが失敗しているときは、緑のチェックを出さず、中立のアイコンにする。
見出しは「最後に取得できた時点では、対応が必要な承認・失敗・通知はありませんでした」に変える。
あわせて、古い値の知らせを添える。
確かめられていない状態で「何もない」と言い切らないためである。
401のときは見出しだけを変え、知らせは上のバナーに任せる。
カードは面の幅を等分して並べる。
401で取得できないときは、バナーと並べて、ログインが必要である旨を中央に出す。

並び、絞り込み、行の表示内容、副題、件数のカードは`src/lib/inboxView.ts`の純関数が決める。
失敗の詳細と再実行の確認の内容は`src/lib/failureView.ts`、再実行のロックのキーと結果の知らせは`src/lib/retryView.ts`が決める。
自動更新の間隔の表示は`src/lib/refreshTiming.ts`が決める。
分で割り切れる間隔は分で、それ以外は秒で書く。
相対時刻の表示は、`src/app/clock.ts`の共有の時計が進める。
進める間隔は、同じファイルの`CLOCK_TICK_MS`が定める。

### 通知

一覧に出す通知は、`summary`の未解決で、重要度が要対応のものである。
重要度が情報の通知は、人の行動が要らないので、一覧に出さない。
情報の通知と、`summary`の上限を超えた通知は、`?notice=<id>`で選ぶと、同じ詳細が開く。
このとき`console_query`の`notices`viewから、未解決の通知を探す。
viewには、backendが受ける最大の2000件を指定する。
`summary`の上限を超えた通知も開くためである。
`notices`viewは自動では取り直さず、詳細を開くたびに取り直す。
タブへ戻っただけでは取り直さない。
解決した通知を未解決のまま出さないためである。
一覧と`notices`viewのどちらにも無いときは、すでに解決されたか、まだ取得できていないと伝える。

一覧の行は、題名に通知の種類の日本語名を出す。
2行目の「通知」の語と副題の組み立ては、[要対応の画面](#要対応の画面)の一覧の行に書いた。
詳細には、重要度、本文、対象、発生した時刻、起きたことと次の操作を出す。
本文は`displayableIssueText`を通し、プレーンテキストで描く。
`summary`は本文を500文字で切る。
一覧から選んだ通知の本文が、ちょうど500文字のときは、本文が途中までであることを添える。
切れ目に接する`owner/repo#番号`は、番号の途中で切れているおそれがあるので、リンクにしない。
`notices`viewは全文を返すので、`?notice=`で開いた詳細には、この扱いをしない。
対象は、本文の`owner/repo#番号`から作ったGitHubへのリンクで、`safeGitHubUrl`を通ったものだけを張る。
本文からはIssueかPRかを区別できない。
GitHubは`/issues/<番号>`をPRなら`/pull/<番号>`へ転送するので、常にIssueの形のURLを作る。
起きたことと次の操作は、`src/lib/noticeGuide.ts`が種類ごとに持つ。
内容は[運用](../../operations.md#通知の種類)の通知の表に合わせる。
表に無い種類は、本文を確かめるよう案内する。
ホスト側の作業が必要な通知(`host_action_required`)には、ホストのcheckoutで順に実行するコマンドを出す。
コマンドは、`git pull`、`mise install`、`mise run up`である。
対応をシステムの画面の区画で行う種類には、次の操作の文の下に、その区画へ移るボタンを出す。
未解決のときだけ出し、解決済みの通知には出さない。
移る先と仕様は[区画への移動](system.md#区画への移動)にある。
次の操作の欄の末尾には、[運用](../../operations.md#通知の種類)の通知の表の、その種類の行へのリンクを出し、設定の`factory_repo`のリポジトリのmainの文書を新しいタブで開く。
URLは、種類ごとのデータを持たず、`docs/operations.md#notice-<種類>`の規則で決める(`src/lib/noticeDocLink.ts`)。
Consoleが説明を持たない種類は、表の節を指す。
設定を読めない間と、`factory_repo`がGitHubのリポジトリのURLの形でないときは、リンクを出さない。

本文が作業項目を名指しする種類(`implement_needs_human`、`implement_launch_failed`)は、次の操作の文の下に、その作業項目の失敗へ移るボタンを出す。
ボタンの名前は「作業項目 #<id>の失敗へ」である。
作業項目は、本文の先頭の`<owner>/<repo>#<番号> (work item <id>):`から読む。
先頭だけを読むのは、後ろの理由の文が外から来た文字を含みうるためである。
移る先は、要対応の画面の`?failure=<id>`で、再実行のボタンがある失敗の詳細が開く。
ボタンは移るだけで、再実行は起こさない。
ボタンは遷移を自分で起こさず、一覧を持つ要対応の画面に開くよう頼む。
履歴は置き換える。
戻る操作で通知の詳細に戻らないためである。
狭い幅で一覧から来た印(`fromList`)は引き継ぐので、「一覧へ戻る」は1回で一覧に戻る。
種類のチップが失敗を隠しているときは、チップを「すべて」に戻す。
隠れた項目の詳細を出したままにしないためである。
押したボタンは詳細の差し替えで消えるので、フォーカスは詳細のペインに移す。
ペインは差し替えの前後で同じ要素のままスクロールの位置を持つので、先頭に戻す。
その作業項目の失敗が一覧にあり、通知が未解決のときだけ出す。
一覧に無いと、移った先が行き止まりになるためである。
どの種類がボタンを持つかは`noticeGuide.ts`が持つ。
システムの入口のバッジ(`systemTargetKinds.ts`)には数えない。
移る先がシステムの画面でないためである。
1つの作業項目を名指ししない種類(`host_action_required`、`check_runtime_unsafe`)は、ボタンを持たず、要対応の失敗で再実行するよう案内する。
この2種類と、上の2種類の計4種類の案内は、作業項目が要対応の失敗に出ていないときの手順を、同じ言い回しで残す。
手順は、Windmillで`f/factory/retry_work_item`を作業項目のIDで実行することである。
失敗の一覧には件数の上限があり、古い作業項目は載らないことがあるためである。

解決のボタンは、未解決で、`summary`の`resolvable`が真のときだけ出す。
Consoleから解決できない種類には、ボタンの代わりに理由を出す。
設定や権限の問題を示す通知を、内容を確かめないまま消せないようにするためである。
ボタンを押すと、確認のダイアログを出さずに`resolveNotice`を呼ぶ。
解決した通知は履歴に残り、状況が続けば新しい通知が出るので、取り返しのつかない操作ではない。
解決済みだった通知は成功として扱い、「すでに解決済み」と知らせる。
成功と、結果が分からない失敗の後は、`summary`と`notices`viewを読み直す。
解決した通知は一覧から消える。

行と詳細に「解決済み」の印を用意している。
両方のviewが未解決の通知だけを返すので、通常は出ない。
解決済みの通知の履歴は、[システムの画面](system.md#システムの画面)に出す。
