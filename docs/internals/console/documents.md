# Consoleの文書の画面の仕様

Consoleの要件定義書、設計書、レポートの画面の仕様を書く。
文書を表示する画面を変更する人が読む。
画面をまたぐ仕様と、ほかの画面の仕様の置き場は、[Consoleの仕様](../console.md)にある。

## 要件定義書の画面

作業項目の入口(`/console/items`)は、進捗と要件定義の2つのタブを持つ([作業項目の画面](work-items.md#作業項目の画面))。
要件定義のタブは、要件定義がある作業項目の一覧を出す。
進捗とは、取得を共有しない。
画面の見出しの更新のボタンが、両方を取り直す。
一覧は更新の新しい順で、直近3650日の500件までである。
取得した行はページに分け、番号で絞り込むと先頭のページへ戻る([ページ送り](../console.md#ページ送り))。
行には、題名、リポジトリとIssueの番号、作業項目の番号、最新の試行、状態のバッジ、更新の時刻を並べる。
作業項目の番号で絞り込める。
先頭に`#`があっても無視する。
行を選ぶと、その作業項目の最新の要件定義書(`/console/items/:id/requirements`)へ移る。

一覧は`console_query`の`requirements_index`、本文は`requirements_doc`で取る。
応答は`src/api/guards/requirements.ts`の型ガードを通す。
形が崩れた応答は、一部だけを使わず、全体を`invalid_response`にする。
backendの型との一致は、`tests/scripts/console_requirements_contract.test.ts`が確かめる。
一覧と本文のキャッシュは決まった時間で古くなり、画面を開いたときに取り直す。
時間は[`src/api/queries.ts`](../../../console/src/api/queries.ts)の`REQUIREMENTS_STALE_MS`が定める。

本文の画面は、左に本文、右に目次を置く。
狭い幅では、目次を本文の前に畳んで置く。
左には、状態、リポジトリ、Issueへのリンク、作業項目、試行の切り替え、要約、表示の形式の切り替え、本文、未確定事項の順に並べる。
状態から試行の切り替えまでは、本文を押し下げないよう、折り返す1〜2行にまとめる。
目次は、スクロールに合わせて読んでいる節を強調する。
底までスクロールしたときは、短い最後の節も選べるよう、最後の見出しを強調する。
底に着いたときだけは、画面に見えている見出しをURLのハッシュが指していれば、最後の見出しではなくその見出しを強調する。
ハッシュは手でスクロールしても消えないので、手で底へ戻したときも、ハッシュの見出しが強調される。
底から1〜2px上へ動くと、基準線の規則に戻り、強調が変わりうる。
スクロールできない短い文書では、目次のリンクを選んでも強調は変わらない。
強調は、色と左の線だけで示す。
太字にすると、折り返しの行数が変わり、本文の位置が動くためである。
表のセルの文字にIDが含まれるときは、ハイフンで折り返すとIDが読めなくなるので、IDの部分を折り返さない。
強調やコード、リンクの中のIDは対象にしない。
表示の判定は`src/lib/requirementsView.ts`の純関数が決める。

### 試行の切り替え

試行は、最新から1までのリンクで切り替える。
表示する試行はURLの`?attempt=<k>`に持ち、番号が無ければ最新を出す。
`?attempt=`があって、先頭が0でない正の整数でないとき(`abc`、`0`、`02`、`1.5`、空)は不正とする。
[`src/lib/requirementsView.ts`](../../../console/src/lib/requirementsView.ts)の`MAX_ATTEMPT`を超える値も不正とする。
不正なときは、取得せずに「試行の番号が正しくありません」と出す。
最新として読むと、別の試行を読んでいると気づけないためである。
最新へのリンクは番号を付けず、最新を指し続ける。
最新の試行を確かめられるのは、最新を指定して本文を取ったときと、一覧にその作業項目の行があるときだけである。
このときの最新の試行の番号は、本文の試行と一覧の行の、大きいほうにする。
古い試行を開いていて、一覧がまだ答えないときと、一覧に行が無いときは、最新を確かめられない。
このあいだは、どの試行にも「(最新)」を付けず、開いている試行までを番号つきのリンクで並べる。
選択肢は、新しいほうから同じファイルの`MAX_ATTEMPT_CHOICES`の件数までに絞る。
却下による作り直しは、試行が増えることで現れる。
却下の理由と承認の履歴は、`work_item_detail`の`approvals`が持つが、この画面は読まない。
`requirements_doc`が持たないためである。

### 本文の描画

本文の描画は`src/components/markdown/Markdown.tsx`にある。
Issueの内容に由来する信頼できない入力なので、次のように扱う。

- 本文、要約、未確定事項、題名は、見えない文字を`displayableIssueText`で置き換えてから描く。
  置き換えたときは、その旨を出す。
- `react-markdown`と`remark-gfm`で描き、`rehype-sanitize`で無害化する。
  生のHTMLは描かず、`dangerouslySetInnerHTML`も使わない。
- リンクにするのは、作業項目と同じリポジトリのIssueとPRのURL、本文内の見出しへのフラグメントだけである(`src/lib/markdownLink.ts`)。
  それ以外は文字で出す。
- リンクの文字とURLが違うときは、URLを括弧で添える。
  添えたURLは`<bdi>`で包む。
- 画像は、図の参照(`![name](name.drawio)`)だけを通す。
  ほかの画像は描かない。
- `> [!NOTE]`、`> [!WARNING]`、`> [!IMPORTANT]`で始まる引用は、ラベル付きの囲みで描く。
- GFMのタスクリスト(`- [x]`)は、箇条書きの点を出さず、読むだけのチェックボックスで描く。
  チェックボックスの名前は、読み上げのために、状態の「完了」と「未完了」にする。
- 表は、標準の余白(`TABLE_CELL_CLASS`)で描き、本体の偶数行に薄い背景の縞を付ける。
- 縞とヘッダーの背景は、文字色の半透明の重ね塗りにする。
  濃さは、縞の3%とヘッダーの8%である。
  ページの背景とCardのどちらの下地でも、縞が下地と、ヘッダーが縞と、輝度比で1.05以上離れるためである。
  不透明な`bg-muted`は、下地によって差が1.02〜1.06に落ちるので使わない。
  縞の見えない下地があるためである。
  輝度比は、`console/e2e/axe.a11y.ts`が描かれた色で測る。
- 横にはみ出す表は、枠をキーボードで操作できるようにする。
  枠には`tabindex="0"`と名前「表」を付ける。
  リンクを含まない表でも、スクロールする領域の規則(`scrollable-region-focusable`)を満たすためである。

理由は[Consoleの安全策の内部仕様の「要件定義書のリンク」](security.md#要件定義書のリンク)にある。

目次は、行頭から始まる`##`と`###`の見出しである。
コードの囲みの中の行は、見出しに数えない。
見出しの走査は正規表現で行う。
そのため、HTMLのコメントの中の行は見出しに数え、`id`のない目次の項目になる。
行頭が空白や`>`で始まる見出しと、下線で書く見出しも数えない。
見出しの`id`は、見出しの文字から作ったスラッグに`h-`を付ける。
ページの他の要素の`id`と名前が重ならないようにするためである。
`id`が使われているときは、使われていない`id`になるまで`-2`、`-3`を付ける。
見出しが`a`、`a`、`a-2`の順に並んでも、`id`は重ならない。
`id`は`src/lib/markdownHeadings.ts`が行ごとに決め、描画は見出しの行から引く。
目次のリンクと見出しの`id`が、必ず一致する。
本文のリンク`[文字](#見出し)`は、同じ規則で`#h-見出し`に読み替える。
本文は脚注の記法を使わない。
`#user-content-fn`で始まるフラグメントは、見出しへのリンクに読み替えず、文字で出す。
行き先のないリンクにしないためである。

題名は、本文の最初のレベル1の見出し(`#`で始まる行)にする。
無ければIssueの題名、それも無ければ「(無題)」にする。
題名の行は、ページの見出しに出すので、本文では描かない。

### 表示の形式

本文は、プレビューとMarkdownの文字の2つの形式で読める。
切り替えは部品`ViewModeSwitch`が出す。
選んだ形式は、画面の部品(`RequirementsDocumentView`と`DesignDocumentView`)が持つ。
目次と注記が本文の外にあり、形式で出し分けるためである。
形式は保存しない。
最初はプレビューである。
要件定義書の画面は試行を替えたとき、設計書の画面は設計書を替えたとき、承認の詳細は承認依頼を替えたときに、画面ごと作り直す。
作り直すと、形式はプレビューに戻る。
切り替えは、要約の後、本文の前に置く。
読み上げの名前は、要件定義書では「要件定義書の表示の形式」、設計書では「設計書の表示の形式」である。
承認画面の要件定義書(`embedded`)にも、同じ切り替えを出す。

承認画面の取り込み時点のIssueと提案の本文は、別の切り替えを持つ。
既定は原文で、プレビューは承認を止める([承認画面の本文のプレビュー](attention.md#承認画面の本文のプレビュー))。
要件定義書の切り替えは、既定がプレビューで、承認を止めない。

Markdownの文字は、題の行を含む本文の全文を、解釈せずに折り返す`pre`で出す(`MarkdownText`)。
文字は、`displayableIssueText`で見えない文字を置き換えた後のものである。
プレビューが描かないHTMLのコメントとリンク参照定義に書かれた内容も、書かれたとおりに見える。
見えない文字は置き換え後の文字で出るので、元の形では確かめられない。
図は描かず、参照(`![name](name.drawio)`)が文字で見える。
目次は出さない。
見出しの`id`が無く、リンクが飛ばないためである。
要約と未確定事項は、どちらの形式でも同じである。
目次の強調に使う見出しの`id`の並びは、`src/lib/requirementsView.ts`の`tocIdsFor`が決める。

限界は、右から左に書く文字が、周りの並びを入れ替えうることである。
Markdownの文字は、承認画面の設計書の全文と違い、行ごとに`bdo`で包まない。
承認画面の要件定義書のプレビューも、同じ限界を持つ。

### 図

本文の図の参照は、`requirements_doc`の`diagrams`から名前で引き、図ごとに`DrawioFrame`で描く。
図は隔離したiframeの中で描く([draw.ioの図](delivery.md#drawioの図))。
図ごとの表示は次のとおりである。

| 図の状態 | 表示 |
| --- | --- |
| `diagrams`にある | `DrawioFrame`で描く |
| 読み戻しの検査を通らず、名前が`rejected_diagrams`にある | 「安全の検査を通らなかったので表示しません」。iframeは作らない |
| どちらにも無い | 「見つかりません」 |

不正な図は、iframeの中に閉じ込めるか、iframeを作らないので、親のページに影響しない。
元のファイルを読めず、データベースの控えを出しているとき(`doc_dir_source`が`db_fallback`)は、図が空になる。
その旨を、本文の前に注記する。

## 設計書の画面

設計書の本文は、承認画面のほかに、設計書の画面(`/console/items/:id/design`)で読み返せる。
承認の判断は承認画面の全文で行い、この画面は承認の操作を持たない。
入口は、作業項目の詳細の設計タブの行のリンクだけである。
承認待ちの設計書の本文の画面からは、承認画面へのリンクを出す。
要件定義の一覧には、設計書のある行に「設計あり」のバッジを出す。
行は全体が1つのリンクなので、バッジはリンクにしない。
リンクを入れ子にすると、キーボードと読み上げの操作が壊れるためである。
一覧に設計のタブは置かない。
設計書は要件定義の下書きに結ばれ、設計のある作業項目は要件定義の一覧にも必ずあるためである。

### 設計書の特定

設計の試行(`design_attempt`)の番号は、作業項目の中で一意でない。
要件定義へ戻ると作業項目の設計の試行は0に戻り、同じ番号の設計書が増えるためである。
画面は、設計書の行の番号(`design_drafts.id`)で設計書を指す。
URLの`?draft=<id>`に持ち、無ければ最新(番号が最大の行)を出す。
最新を指す取得と、番号で指す取得は、別のキャッシュにする。
`?draft=`が正の整数でないとき、設計書が無いとき、別の作業項目の設計書の番号のときは、「この設計書は見つかりません」の1文を出す。
最新と取り違えると、別の設計書を読んでいると気づけないためである。

設計書の名前は、元の要件定義の試行と設計の試行を並べて書く。
2つを並べると、設計の試行の番号が同じでも見分けられる。
同じ名前の行は、作成の時刻で見分ける。

### 取得

設計タブの一覧は、`work_item_detail`の`design_attempts`が持つ。
要約と承認の状態だけを持ち、本文と図は持たない。
承認の履歴の設計の依頼は、同じ応答の承認の行が、設計書の名前の元になる2つの試行を持つ。
要件定義の一覧の`has_design`は、最新の要件定義の下書きに結ばれた設計書があるときだけ真になる。
古い試行の設計書は数えない。
型ガードは、この3つの項目が欠けた応答を、設計書が無いものとして受け入れる。
配信と反映の順序が入れ替わっても、詳細の画面と一覧を壊さないためである。
`design_attempts`の1要素が不正なときは、その要素だけでなく、`work_item_detail`の全体を`invalid_response`にする。

本文は、`console_query`の`design_doc`で、作業項目の番号と、任意の設計書の番号を渡して取る。
型付きの関数は`fetchDesignDoc`と`useDesignDoc`で、型は`DesignDocRow`に合わせてある。
`tests/scripts/console_design_doc_contract.test.ts`が、変換結果が型ガードを通ることを確かめる。
設計書の番号は、渡されて正の整数でないときに空を返し、渡されないとき(`null`を含む)の最新と区別する。
結ぶのは、指した作業項目の設計書だけである。

| 項目 | 出どころ |
| --- | --- |
| 本文 | DBの`markdown`。承認画面と同じ整形(`sanitizeModelTextDetailed`)で、制御文字と書式文字を除き、秘密値をマスクする。長さでは切らない |
| 要約、未確定事項 | DBの値。保存の前に整えてあるので、そのまま返す |
| 図 | ディスクの設計のディレクトリ(`doc_dir`)の`<name>.drawio`だけ。本文は読まない |

図は、`doc_dir`が要件定義の基準のディレクトリの下にあることを確かめてから読む。
基準の外、読めない図、名前の不正な図は、返す図から落とす。
安全の検査(`validateDrawioXml`)を通らない図は、名前を`rejected_diagrams`に入れる。
同じ`doc_dir`を指す新しい設計書があるときは、古い設計書の図を読まず、空にする。
`doc_dir`は`req-<要件定義の試行>/attempt-<設計の試行>`で決まり、生成は同じ`doc_dir`の再利用を止める。
それでも行が重なると、古い行が読んだ図は、新しい行の図を自分の図として返す。
その防御として、最新の行以外は図を読まない。

### 本文の描画(設計書の画面)

本文、目次、図は、要件定義書の画面と同じ部品(`Markdown`、`RequirementsToc`、`useActiveHeading`、`DrawioFrame`)で描く。
表示の形式の切り替えも同じ部品(`ViewModeSwitch`、`MarkdownText`)で、[表示の形式](#表示の形式)に従う。
本文、要約、未確定事項は、`displayableIssueText`で見えない文字を置き換えてから描く。
図の状態ごとの表示は、[要件定義書の図](#図)と同じである。
要件定義書の部品(`RequirementsDocumentView`)は、承認画面の中に置く形を持つので、変えずに、設計書の部品(`DesignDocumentView`)を別に持つ。

本文の画面は、次の順に並べる。

1. 固定の注記。
   承認待ちの設計書には、承認画面へのリンクを添える
2. 作成の時刻
3. 見えない文字を置き換えた旨。
   置き換えたときだけ
4. 要約、表示の形式の切り替え、本文、未確定事項(狭い幅では、本文の前に畳んだ目次)。
   Markdownの文字では、目次を出さない

見出しの題は、本文の最初のレベル1の見出し(`#`で始まる行)にする。
副題は、作業項目と設計書の名前にする。
承認の状態の表示と、設計書の切り替えは置かない。
設計タブが持つので、同じ情報を重ねない。

### 固定の注記

本文の先頭に、表示の形式ごとの注記を常に出す。
プレビューの注記は、次のとおりである。

```text
承認と実装が受け取る文字は、承認画面の全文です。この画面は読みやすく描いたもので、生のHTML(コメントを含む)、リンク参照定義、見えない文字、長さの扱いが違います。
```

Markdownの文字の注記は、次のとおりである。

```text
承認と実装が受け取る文字は、承認画面の全文です。この画面の文字は、見えない文字の表し方、改行と空白の扱い、長さが違います。
```

プレビューは、生のHTMLとリンク参照定義を描かず、見えない文字を置き換え、長さでも切らない。
Markdownの文字は、HTMLのコメントとリンク参照定義も文字で見せるが、見えない文字は置き換えて出し、改行と空白の扱いと長さも承認画面の全文と違う。
承認と実装が受け取る文字は、どちらの形式でも、承認画面の全文である。
画面を読んだ人が、この画面の文字で承認を判断しないよう、注記で伝える。
承認画面へのリンクは、承認依頼の状態が承認待ちのときだけ出し、`/?approval=<依頼の番号>`を指す。
決着した設計書では、実装が受け取った文字を事後に確かめる入口を、Consoleに置いていない。
この限界は[Consoleの安全策の内部仕様](security.md#設計書の読み返しの画面)の残るリスクに書く。

## レポートの画面

レポートの画面は、監査レポートと分析の2つのタブを持つ。
タブに分けるのは、利用者の指示による。
システムの画面と同じ共通の仕組み(`tabSet`)で、縦並びの長さを抑える。
開くタブと本体の見せ方は、[タブ](../console.md#タブ)の規則に従う。
監査レポートのタブの名前には、取得した件数を添える。
更新のボタンは、監査レポートと分析の4つの取得を取り直す。
分析の期間の選択は、タブを往復しても保つ。
監査レポートの本文の画面のパンくずは、戻り先をレポートの画面にする。

監査レポートのタブは、監査レポートの一覧を出す。
一覧は`console_query`の`audit_index`viewから、直近3650日を新しい順に100件まで取る。
型ガードは`src/api/guards/audit.ts`、取得は`src/api/auditQueries.ts`にある。
画面の部品は`AuditReports`で、一覧の取得は部品に渡す。
取得と更新はレポートの画面が持つ。
`tests/scripts/console_audit_contract.test.ts`が、backendの変換結果が型ガードを通ることを確かめる。

一覧の1行は、対象期間、要約、提案の判断の内訳、作業項目の状態、作業項目の番号、作成の時刻である。

### 手動の起動

「今すぐ監査」を押すと、確認のダイアログを出す。
ダイアログは、ブラウザ標準の`dialog`要素をモーダルで開く。
確認すると、`kickoffAudit`で`audit_kickoff`を起動する。
起動の前にダイアログを閉じるので、確認のボタンを二重に押しても、起動は1回になる。

起動の設定は`src/api/auditKickoffConfig.ts`にあり、書き込みの共通の流れに載せる。

- ロックのキーは1つに固定する(`AUDIT_WRITE_KEY`)。
  起動が実行中のあいだ、ボタンは押せない
- 同じ瞬間に2回呼ばれても、実行は1回になる
- 結果が分かったら、監査レポートの一覧を読み直す
- 読み直せなかったときは、一覧が古いことを知らせ、一覧が更新されるまでボタンを押せないままにする

`force`は渡さない。
`force`を付けると、対象の記録が無くても起動するので、画面からは出さない。

結果は、一覧の上に画面を離れるまで残す(`src/lib/auditKickoff.ts`)。
トーストは操作した場所から離れて出るので、対象期間と見送りの理由を、レポートの一覧の隣で読めるようにするためである。

| 結果 | 表示 |
| --- | --- |
| 起動した | 成功の色で、対象期間を添える |
| 見送った | 通常の色で、理由を日本語で出す。理由は`writeNotices.ts`の対応表にある |
| 失敗した | 失敗の色で、書き込みの失敗の文を出す |
| 一覧を読み直せなかった | 警告の色で、一覧が古いことを出す |

見送りは失敗ではなく、何も変えなかった正常な結果である。
