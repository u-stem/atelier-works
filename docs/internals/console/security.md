# Consoleの安全策の内部仕様

Console用workerの操作ごとの守りと、画面での描画の安全策を説明する。
ジョブのログと結果の読み取り、設定の変更、draw.ioの図の描画、要件定義書のリンク、更新履歴のPRを扱う。
Console用workerの境界の全体は、[セキュリティ](../../security.md#console用workerの境界)にある。

## ジョブのログと結果の読み取り

ジョブの一覧と詳細、scheduleの状態、設定を読む3つのscript(`console_jobs`、`console_schedules`、`console_config`)は、tag`console`で動かす。
どれも読むだけで、何も書かない。
ジョブのログと結果は、defaultのworkerで動いたscriptの出力である。
そのため、Console用のworkerは、この3つを通して、ファイルシステムの境界を越えてdefaultのworkerの出力に届く。
届く範囲を、次のとおりに絞る。

| 絞る対象 | 内容 |
| --- | --- |
| 対象のジョブ | パスが`f/factory/`で始まるscriptとフローのジョブだけを返す。プレビューや依存の解決のジョブは返さない。idはUUIDの形だけを受け付ける。対象外は、存在しないジョブと同じ応答にする。存在を返さないためである |
| 呼び出しの順序 | ジョブの取得、パスと種類の確認、ログと結果の取得の順に固定する。確認を通らないジョブのログは取らない |
| 返す項目 | 許可した項目だけを選ぶ。ソースコード、フローの定義、フローの状態の中の引数と結果、メールアドレス、実行の権限は返さない |
| 親のジョブ | 親を持つジョブと、フローのステップは、ルートまでの親がすべて許可した種類のときだけ、詳細に返す。親のidも、その確認を通ったときだけ返す。一覧は、親のidを返さない。確認に使う印は、ステップの印ではなく、親の有無である。印が欠けたり名前が変わったりしても、確認が外れないようにするためである |
| フローのステップ | プレビューのフローでは、ステップのジョブの種類がscript、パスが`f/factory/`になる。そのため、親をたどらないと、実行したフローの一部と見分けられない。プレビューのステップは、存在しないジョブと同じ応答になるが、親をたどる分だけ応答が遅れる。応答時間でプレビューのステップの存在が分かるが、Consoleを呼べるのは管理者だけなので、受け入れる |
| 履歴の件数 | 1回の要求は50件までに限る。カーソルは、返した累積の件数と、境界の時刻のジョブのidを持つ。累積が200件に達したら、次のページを返さない |
| 引数 | 値を出すキーを列挙する(作業項目のid、リポジトリ、取り込みの種類、日数など)。ほかのキーは、名前と型だけを返す |
| scheduleの項目 | 引数、メールアドレス、追加の権限、失敗時と成功時の呼び出し、実行の権限を返さない。リポジトリの定義との差異は、生成した定数のファイルと照らして返す |
| 設定 | 補間しない生の値を読む。`$var:`か`$res:`を含む値は、中身を返さず、参照の印だけを返す。補間する取得は使わない。読むパスはリテラルの1つに固定する |
| SDKの呼び出し | 3つのscriptごとに、呼んでよい`<X>Service.<method>`と`wmill.<member>`を許可表で決める。表の外の呼び出し、別名、名前付きimport、`fetch`、トークンの環境変数、`windmill-client`の深いパスのimportは、契約テストが落とす |

許可表は、importでたどれるファイルの和に当てる。
3つのscriptがimportでたどれるファイルは、すべて保護パスの中にある。
外部のimportは`windmill-client`だけで、共通の部品(`lib/log.ts`、`lib/types.ts`)には頼らない。
型ガードと既知の形の規則は、保護した`lib/console_redact.ts`が持つ。
保護パスの外のファイルをたどれるようにすると、そのファイルの変更が人のレビューを経ずに、走査をすり抜けるためである。
契約テストは、たどれるファイルの集合が保護パスに収まることを確かめる。

3つのscriptの`.script.lock`は、保護パスの外にある。
`windmill-client`の版を上げる変更が、全scriptのlockと一緒に書き換わるので、守るとその変更を止めてしまうためである。
残るリスクは[R-CON-01](../../security-risks.md#r-con-01)である。

走査は、許可表のほかに、次の形を禁じる。

- `windmill-client`の再エクスポート。
- `global`、`self`、`window`、`globalThis`の経由。
- リソースの引数の上書き。
  読み取り(`getResourceValue`)の引数は`{ workspace, path: <定数> }`の形に固定し、`requestBody`を認めない。
  更新(`updateResourceValue`)は、`requestBody`の外側にほかのキー、`path`の重複、スプレッドを置かない。
  `requestBody`の本文の中身は見ない。
- `process.env.NAME`の形以外の環境変数の使い方。
  許可表に載せるのは名前で読むものだけで、現在、3つのscriptとたどれるファイルが読む環境変数は無い。
  環境全体の列挙と、`process`の別名は禁じる。
- 文字列で渡すSQL。
  datatableの`query`と`raw`、`RawSql`は、文字列がそのままSQLになるので禁じる。
  タグ付きテンプレートの`${}`は引数として渡る。
- 字句の迂回。
  `constructor`の言及(文字列の中も数える)、`eval`、`Function`、`Bun`の添字アクセスを禁じる。
  `require`(変数に入れる形も)、`import.meta`のすべて、`Worker`も禁じる。
  `import.meta`は`env`と`require`を持つためである。
- ファイルとサブプロセスへの依存。

読み取り専用であることは、たどれるファイルのテンプレートリテラルに、書き込みやスキーマ変更のSQLの語が無いことで確かめる。
この検査が見るのはテンプレートリテラルだけである。
文字列で渡すSQLは、上の禁止で見つける。

走査には、見ないものもある。
保護した部品の変更は人がレビューするので、次の点は差分を読んで確かめる。

- 文字列の連結で組み立てた名前の参照。
  `Bun`の添字は禁じるが、ほかの対象に連結した名前で触れる書き方は見つけられない。
- 割り算を正規表現リテラルと読み違えた範囲。
  走査は、読み違えた間のコードを落とす。
- 識別子を組み立てて呼ぶ`eval`や`Function`の別名。
- `require`や`Worker`を、識別子を組み立てて呼ぶ書き方。
- 第三者パッケージの中身。

契約テストは`tests/scripts/console_worker_boundary.test.ts`にあり、走査は`tests/scripts/worker_boundary_scan.ts`にある。
3つのscriptと、許可表、返す項目、境界の検査は、保護パスである。
書き換えるPRは、人がレビューしてマージする。

## ログと結果の伏せ字

伏せ字の目的は、画面の共有、スクリーンショット、貼り付けで漏れる量を減らすことである。
ConsoleのXSSで漏れる量は減らない。
XSSは、管理者のCookieでAPIを直接呼べるためである。
secret変数の値との完全一致は使わない。
Console用のworkerにsecret変数を読ませない境界を保つためである。
値の形とキー名だけで判定する。

処理は次の順に行う。

1. ログは行ごとにJSONとして読む。
   読めない行(Windmill自身の行、子プロセスの出力)は、文字列の規則だけをかけ、その行数を返す。
2. JSONは値をたどる。
   キー名が秘密を指す項目の値は、型を問わず丸ごと置き換える。
   名前に`TOKEN`、`SECRET`、`KEY`、`PASSWORD`、`WEBHOOK`、`CREDENTIAL`、`AUTHORIZATION`のどれかを含む項目が当たる。
3. 文字列の値に、次の表の規則をかける。
4. 結果は、直列化の前にも、葉の文字列に値の規則をかける。
   直列化すると引用符が変わり、`password="x"`のような対が当たらなくなるためである。
   直列化した後の文字列にも、もう一度かける。
   葉の合計が上限の2倍を超えたら、以降の葉は捨てる。
5. ANSIと双方向の制御文字を含む制御文字を、解いた後の値と最終の出力の両方で落とす。
6. 切る。
   ログは末尾の256KBを残し、切った先頭の途中の行は捨てる。
   結果は先頭の64KBを残す。

伏せてから切る。
切り口で鍵の途中が残るのを防ぐためである。
入力が上限の2倍を超えるときだけ、計算量を抑えるために、伏せる前に粗く切る。
粗い切り口でPEMの`BEGIN`の行が落ちたときは、先頭から対応する`END`までを伏せる。
BEGINを欠くENDを探すのは、粗い切り口の近く(先頭の窓)に限る。
遠いENDまで伏せると、間の普通の行を失うためである。
切り口に残る末尾の語は落とす。
秘密の断片を残さないためである。
正規表現の計算量が入力長の二乗に膨らまないよう、URLのschemeとJWTの区間の長さに上限を置く。
PEMは、入力を前から1度だけ走査し、`-----BEGIN NAME-----`の形ごとに、16384字の窓の中のENDまでを伏せる。
ENDが窓に無いときは、BEGINと、その後ろの鍵の本文らしい並びだけを伏せる。
伏せた範囲の終わりから走査を続けるので、証明書が何枚並んでも、後ろの失敗の行は読める。

| 規則 | 当たるもの |
| --- | --- |
| 既知の形 | GitHubのPAT、Claude Codeのトークン、AnthropicのAPI鍵、DiscordのWebhook URL、`Bearer`、`Authorization:`、URLのuserinfo、JWT、PEMのブロック、AWSのアクセスキーID |
| PEMの書き方 | 改行がJSONの`\n`のまま残った形と、二重にエスケープされた形も当たる |
| キー=値 | 名前に上のキー名を含む`token=`、`password:`、`API_KEY=`の形。値が短くても伏せる |
| 一般形 | 英数字と`_`と`-`だけからなる32字以上の連続。40桁と64桁の16進(commit shaとダイジェスト)とUUIDは除く |

過剰に伏せることは許容する。
伏せた箇所があるときは、戻りの`masked`で画面に示す。
既知の形の規則は、`lib/log.ts`の`maskSecrets`の形の複製で、`lib/console_redact.ts`が持つ。
`lib/log.ts`と`lib/types.ts`は多くのscriptが使うので保護パスに入れられず、3つのscriptがたどれるファイルを保護パスに閉じるには、複製が要る。
複製が元の形とずれたときは、32字に満たない形の秘密が伏せられなくなる。
`tests/lib/console_redact.test.ts`は、`lib/log.ts`の`SECRET_PATTERNS`を読んで、次の2つを確かめる。
パターンの数と見本の数が合うこと。
パターンごとの見本が伏せられること。
`log.ts`に形が足されて複製が追従しなければ、このテストが落ちる。
`isRecord`も、`lib/types.ts`と同じ判定を返すことを、同じテストで確かめる。
切ったときは`truncated`で示す。
Windmillのジョブトークンは、一般形の規則に当たる。

## PRレビューの投入

PRのレビューを投入する入口は、2つに分かれる。
Console用workerで動く`pr_review_submit`は、入力の形、リポジトリの許可、操作者、稼働中のレビューの有無を確かめて、フロー`pr_review_intake`を起動する。
GitHubを読む確認と、作業項目の登録は、通常のworkerで動く登録のステップ(`pr_review_intake_register`)が行う。
`pr_review_submit`はsecret変数を読まないので、GitHubのトークンを要る確認を持てないためである。
`pr_review_submit`が読むDBは、`factory.work_items`の1回の`SELECT`だけで、書くのは操作の記録の部品だけである。
SDKの呼び出しは、境界テストの許可表には載せない。
`manual_intake_submit`と同じく、secret変数を読まないことだけを境界テストが確かめる。

ラベルの経路と、確かめる関門が違う。
投入は`factory:review`ラベルを使わないので、ラベルの付与者の確認(`isAllowedLabeler`)を通らない。
代わりに、操作者をジョブの実行文脈から導いて操作の記録に残す。
投入できる主体は、フォルダ`f/factory`を実行できる主体で、ラベルを付けられる人とは別の許可である。
リポジトリの許可(`isRepoAllowed`)、オーナーのIDの照合、fork headの断りは、ラベルの経路と同じ判定を通す。
登録のステップは、入口の検査に頼らない。
フローを直接実行された場合に備えて、GitHubを読む前に、PR番号の形、名前の形、リポジトリの許可を確かめ直す。
PRが開いていることも確かめ、GitHubが返す正規のリポジトリ名で、許可とオーナーのIDを確かめる。
入力のリポジトリ名が正規の名前と一致しないとき(改名で転送された場合)は、投入しない。

投入は、Consoleの「PRレビューの投入」の画面から行える。
画面は、送る前に形の誤りを知らせるだけで、入口と登録のステップの検査を置き換えない。
画面の1回の送信で、取り消せないPRへの投稿が始まる。
確認のダイアログは置かず、送信ボタンの文言で、外部への投稿を始める操作と分かるようにする。
画面は、断りの文を符号だけから引いて出す。
入力の文字列は文に含めない。
隠れた文字を画面に出さないためである。
フローの結果は、ジョブの結果から読む。
切り詰められたか伏せられた結果と、形の違う結果は、読み取れないものとして扱い、ジョブを開くよう伝える。

同じPRの稼働中の`pr_review`は、3つの層で1件に保つ。

1. `pr_review_submit`が、DBを読んで断る。
2. 登録のステップの挿入が、`WHERE NOT EXISTS`で稼働中の行を除く。
3. 部分一意インデックス`work_items_active_pr_review_key`が、並行する挿入を拒む。

画面の二重の投入は、この3つの層が止めるので、冪等キーを使わない。

`pr_review`の行の綴りは、書き手によって違いうる。
登録のステップとdependabotは、PRのbaseのリポジトリが返す正規の綴りで書く。
表と明示の一覧から来る候補は、`confirmPrCandidate`が`getIssue`の応答の綴りで作る。
綴りの違う行ができるのは、GitHub側の改名で大文字小文字が変わった場合と、追跡中のPRの経路が前の行の綴りを引き継ぐ場合などである。
そのため、同じPRを指す`pr_review`の検索は、ownerとrepoを小文字にして比べる。
小文字で比べても、綴りの同じ行の判定は変わらないので、害は無い。
対象は、このインデックスと、1と2の比較、最新の行の取得、過去のレビューの有無、再開の巡回が見る新しい行の確かめである。
行そのものの綴りは、書き手ごとにそのまま残す。
`pr_fix`のインデックスの綴りの扱いは、この変更の対象外で、変えていない。

次のファイルを、保護パスに入れる。
書き換えられると、許可されていないリポジトリや閉じたPRのレビューが投入で通ったり、同じPRのレビューが重なったりするためである。

- 入口の`pr_review_submit.ts`
- 登録のステップ`steps/pr_review_intake_register.ts`
- 投入のフロー`pr_review_intake__flow/`(前方一致)
- 作業項目の作り方を`poll_prs`と共有する`lib/pr_review_start.ts`
- 上の3つのファイルの`.script.yaml`
- 一意インデックスを作るmigration2本

3つの`.script.lock`は守らない。
`windmill-client`を含み、その版を上げる変更で全scriptのlockと一緒に書き換わるためである。

投入を止める停止スイッチは無い。
`poll_prs`のスケジュールを止めても、投入は止まらない。

残るリスクがある。

- [R-CON-02](../../security-risks.md#r-con-02)
- [R-CON-03](../../security-risks.md#r-con-03)
- [R-CON-04](../../security-risks.md#r-con-04)
- [R-CON-05](../../security-risks.md#r-con-05)
- [R-CON-06](../../security-risks.md#r-con-06)

## ジョブの取消

ジョブを取り消す`console_job_cancel`は、tag`console`で動かす書き込みのscriptである。
運用者がConsoleの確認のダイアログを通した後にだけ呼ぶ。
ローカルのClaudeのセッションが、このscriptを名前で呼ぶ経路は、拒否フックが止める([Claude Codeのフック](../../security.md#claude-codeのフック))。
フックが止めるのはその経路だけで、汎用の取り消しの経路は止めない。
後述の残るリスクに書く。
取り消せる対象を、次のとおりに絞る。

| 絞る対象 | 内容 |
| --- | --- |
| 対象のジョブ | パスが`f/factory/`で始まるジョブだけを扱う。外のジョブと、UUIDの形でないidは、存在しないジョブと同じ応答にする。存在を返さないためである |
| 取り消せるフロー | `job_kind`が`flow`で、親のジョブが無く、フローのステップでなく、パスが許可した7つのフロー(audit、dependabot、design、implement、pipeline、pr_fix、pr_review)のどれかと完全に一致するものだけ。前方一致にしない |
| 取り消さないもの | `self_update`、migrationを走らせるscript、`cleanup_*`などのscriptのジョブ、tag`console`のジョブ、予定の時刻が先のジョブ、終わったジョブ、取り消しの依頼が済んで止まる途中のジョブ、子のステップ、作業項目を持たない手動投入のフローとPRレビューの投入のフロー。許可したフローの外は、すべて取り消さない。予定の時刻は、10秒の猶予を超えて先のときだけ「先」とみなす。Windmillとworkerの時計のずれで、もうすぐ始まる待ちのジョブを誤って断らないためである |
| 許可表の保守 | 許可表はフローの名前で列挙し、生成した既知のpathの定数とは別に持つ。リポジトリのフローが、許可したか、理由つきで除いたかのどちらかであることを、契約テストが固定する。新しいフローは、決めるまで取り消せない。許可したフローは、作業項目のidを入力に取ることも、契約テストが確かめる |
| 呼び出しの順序 | ジョブの取得、対象の判定、操作者の導出、記録(`attempted`)、取り消し、記録(結果)、ジョブと作業項目の読み直しの順に固定する。操作者を導けないときと、記録を書けないときは、取り消さずに断る |
| SDKの呼び出し | `JobService.getJob`、`JobService.cancelQueuedJob`、`wmill.getWorkspace`、`wmill.datatable`だけ。境界テストの許可表に載せ、importでたどれるファイルの和に当てる |
| SQL | 読むのは作業項目の1行(`id`、`status`、`flow_job_id`)だけ。書くのは記録の部品だけで、書く表は`factory.console_actions`に限る。境界テストが、書く文の表の名前まで確かめる |
| 環境変数 | 操作者を導くための`WM_USERNAME`と`WM_EMAIL`だけ |

取り消しは、Windmillにジョブを止めさせるだけである。
作業項目の行は書き換えない。
リースがそのジョブを指したまま残り、次の照合(`poll_issues`、5分ごと)が、終わった取り消し済みのジョブを見つけて失敗にする。
ただし、承認待ち(`awaiting_approval`、`awaiting_design_approval`)の作業項目は、人の判断を待つ状態なので、照合は失敗にしない。
取り消した後に、ジョブの状態と作業項目の行を読み直して返す。
読めなければ`null`にして、取り消しの結果は隠さない。

実機のWindmillで、tag`console`のscriptのジョブトークンが、待ちのジョブと、実行中のフローを取り消せることを確かめた。
取り消した主体(`canceled_by`)は、Consoleを呼んだユーザーになる。

次のことは、この操作では守れない。

- 子プロセス(Claudeと検査コマンド)は、取り消しで止まらない。
  Claudeは別のセッションとプロセスグループで起動するので、Windmillがジョブのプロセスにだけ送る取り消しは届かない。
  Claudeは、ターン数と費用の上限まで動き続けることがあり、その費用は日次予算に数えられないことがある。
  毎日03:00の作業領域の掃除が止めるのは、実行の上限時間に5分を足した時間を過ぎたClaudeのプロセスだけである。
  確認のダイアログが、この旨を伝える。
- 承認待ちへ移した後、通知の前に取り消すと、作業項目は承認待ちのまま残り、承認依頼の通知は届かないことがある。
  照合は承認待ちを失敗にしないので、運用者がConsoleの要対応で承認依頼を確かめる。
  要件定義のpipelineと設計のdesignは、どちらも承認依頼の記録、状態の移行、通知の順に動く。
  確認のダイアログと結果の知らせが、この旨を伝える。
- pr_fixを取り消すと、作業項目が失敗になった後で、新しい修正が起動し直される。
  起動し直すのは、保留中のラベルと、CIの自動修正が有効なときのCIの監視(`watch_pr_ci`)である。
  残ったプロセスがworktreeを使っていると、その準備はブロックで止まる。
  確認のダイアログが、この旨を伝える。
- 対象の判定と取り消しの間にジョブが終わると、取り消しのAPIは404を返すので、終わったジョブとして断る。
- 管理者は、Windmillの画面か`wmill job cancel`で、許可表の外のジョブも取り消せる。
  その取り消しは操作の記録に残らない。
- ローカルのClaudeのセッションが運用者のwmillの資格で取り消す経路は、[R-CON-39](../../security-risks.md#r-con-39)にあたる。
- 作業項目の行を書き換えないので、照合が失敗にするまでの間は、作業項目が進行中に見える。

取消の画面の部品(`console/src/lib/jobActions.ts`、`console/src/screens/jobs/JobActions.tsx`)とそのテストは、保護パスに入れない。
後続のPRで同じ部品を変えるので、保護すると毎回人のレビューが要るためである。
取り消せる対象の絞り込みと、操作の記録は、保護したscript側にある。
そのため、部品が書き換えられたときの被害は、確認のダイアログを飛ばして呼ぶことに限られる。

## 定期ジョブの再実行

失敗した定期ジョブを再実行する`console_job_rerun`は、tag`console`で動かす書き込みのscriptである。
運用者がConsoleの確認のダイアログを通した後にだけ呼ぶ。
ローカルのClaudeのセッションが、このscriptを名前で呼ぶ経路は、拒否フックが止める([Claude Codeのフック](../../security.md#claude-codeのフック))。
再実行できる対象を、次のとおりに絞る。

| 絞る対象 | 内容 |
| --- | --- |
| 対象のジョブ | パスが`f/factory/`で始まる、終わったscriptのジョブだけを扱う。外のジョブと、UUIDの形でないidは、存在しないジョブと同じ応答にする。存在を返さないためである |
| 再実行できる定期処理 | `collect_github`と`auto_retry_pr_review`の2つだけ。scheduleに由来するジョブで、scriptがそのscheduleのscriptと一致し、失敗したものに限る。取り消されたジョブと、飛ばされたジョブは、失敗とみなさない |
| 列挙の根拠 | 繰り返しても二重の副作用が出ないと、scriptの中身で確かめたものだけを入れる。収集は、GitHubを読んでDBの状態を置き換えるだけで、通知は種類と本文で重複を除く。自動の再開は、理由と回数を条件にした比較交換で、同じ作業項目を二度起動しない |
| 再実行しないschedule | 上の2つ以外のすべて。`watch_*`は、タイムアウト(600秒)が間隔(5分)より長く、再実行が次の回を待つだけになる。`self_update`、`poll_*`、`cleanup_*`、`notify_daily_summary`は、反映、GitHubへの書き込み、削除、通知の二重送信のおそれがある。見張りは、次の回が取り直す。除いた理由は、許可表に注記する。リポジトリのscheduleが、許可したか、理由つきで除いたかのどちらかであることを、契約テストが固定する。新しいscheduleは、決めるまで再実行できない |
| 引数 | scheduleの定義の`args`だけを使う。呼び出し側の引数は受けない。`$var:`か`$res:`を含む引数は、参照の先をscriptが解決しないよう、再実行しない |
| 断る条件 | 終わっていない、失敗していない、scheduleに由来しない、許可表の外にある。同じscriptが実行中か待ちにある。次の回の予定が、scriptのタイムアウト(120秒)より近い。scheduleが無効、定義が変わった |
| 呼び出しの順序 | ジョブの取得、対象の判定、キューの読み取り、scheduleの読み取り、操作者の導出、記録(`attempted`)、起動、記録(結果)の順に固定する。操作者を導けないときと、記録を書けないときは、起動せずに断る |
| 起動 | `runScriptByPathAsync`だけ。フローは起動しない。起動したジョブは親のジョブを持ち、scheduleに由来する印を持たない。この呼び出しはHTTPの失敗の本文もそのまま返すので、戻りの前後の空白を除いた文字列がジョブのIDの形でなければ、起動していないとみなして投げる。記録は`failed`になり、本文はエラーの文に入れない |
| SDKの呼び出し | `JobService.getJob`、`JobService.listQueue`、`ScheduleService.getSchedule`、`wmill.getWorkspace`、`wmill.datatable`、`wmill.runScriptByPathAsync`だけ。境界テストの許可表に載せ、importでたどれるファイルの和に当てる |
| SQL | 自分のSQLは持たない。書くのは記録の部品だけで、書く表は`factory.console_actions`に限る |
| 環境変数 | 操作者を導くための`WM_USERNAME`と`WM_EMAIL`だけ |

次の隙があるので、次の回が近いときは、再実行せずに次の回を待たせる。
scriptのscheduleは、次の回を前の回の終了時に積む。
そのため、定期の回同士は重ならない。
手動で起動したジョブは、この連鎖に入らない。
フローのscheduleの重なりを防ぐ`no_flow_overlap`は、`trigger_kind`が`schedule`のジョブだけを数える。
手動のジョブは数えられないので、定期の回が始まると、手動の再実行と重なりうる。
定期の回が実行中のときは、キューの実行中のジョブとして見えるので、再実行を断る。
定期の回が待っているときは、始まる時刻がタイムアウトより遠いときだけ、再実行を始める。

実機のWindmill(1.817.0)で、次のことを確かめた。

- 使い捨てのpreview(defaultのworker)のジョブのトークンで、`getJob`、`listQueue`、`getSchedule`、`runScriptByPathAsync`が通る。
  tag`console`のworkerでの実行は、反映の後の実ジョブで確かめる。
- scheduleの`args`は、`getSchedule`が返す。
  `collect_github`と`auto_retry_pr_review`は、どちらも空のオブジェクトである。
- `runScriptByPathAsync`で起動したジョブは、`trigger_kind`が`webhook`で、`schedule_path`を持たず、`parent_job`が起動元になる。
  そのため、失敗の検知(`detect_schedule_failures`)は、`schedule_path`の無いジョブを拾わない。
- 起動元のジョブが先に終わっても、起動したジョブは最後まで動く。
- `no_flow_overlap`と次の回の積み方は、Windmillのソース(1.817.0)で読んだ。
  実機では、定期の回と重なる場面を作っていない。

次のことは、この操作では守れない。

- 再実行の失敗は、失敗の検知に載らない。
  通知も出ない。
  画面は新しいジョブの詳細へ移るので、結果はそこで確かめる。
- 押すたびに1回起動する。
  複数のタブから押すと、2つ起動しうる。
  ロックは画面を開いたタブの中だけで効く。
  どちらの処理も冪等なので、二重の副作用は出ない。
- 重なりを避ける判定は、Console用workerと定期ジョブ用workerが、それぞれ1枠であることを前提にする。
  Console用workerが1枠なので、この操作の呼び出し同士は重ならない。
  定期ジョブ用workerが1枠なので、起動した再実行と定期の回は、同時には動かず、どちらかが待つ。
  同じ処理が2つ起動しても、直列に動く。
  `auto_retry_pr_review`の見送りの通知は、先の実行が記録するので、後の実行は二重に送らない。
  `replicas`が1であることは、`tests/scripts/console_script_tags.test.ts`が固定する。
  枠を増やすと、この前提が崩れる。
- 許可の根拠は、`collect_github`と`auto_retry_pr_review`が冪等であることである。
  この2つの中身は保護パスではないので、変更で前提が崩れうる。
  5分ごとの定期の回が同じ副作用をすでに起こすので、再実行で増えるのは、押した回数分だけである。
  許可表の見直しは、この2つを変えるPRのレビューで行う。
- ローカルのClaudeのセッションが`wmill`の汎用の呼び出しから許可表の外のscriptを動かす経路は、[R-CON-40](../../security-risks.md#r-con-40)にあたる。

## 設定の変更

設定を変更する`console_config_update`は、tag`console`で動かす書き込みのscriptである。
運用者がConsoleの確認のダイアログを通した後にだけ呼ぶ。
ローカルのClaudeのセッションが、このscriptを名前で呼ぶ経路は、拒否フックが止める([Claude Codeのフック](../../security.md#claude-codeのフック))。
変更できる項目と向きを、次のとおりに絞る。

| 絞る対象 | 内容 |
| --- | --- |
| 変更できる真偽の項目 | `implement_enabled`、`dependabot_enabled`、`dependabot_merge_enabled`、`pr_ci_fix_enabled`、`pr_conflict_fix_enabled`、`design_enabled`の6つ。`true`から`false`へだけ変えられる。自動でGitHubに書くか、実装か設計を起動する機能を止める向きである。`design_enabled`を止めた後の動きは、[設計工程を有効にする操作](../design.md#設計工程を有効にする操作)にある |
| 変更できる数値の項目 | `daily_budget_usd`、`max_budget_usd_per_run`、`max_fix_rounds`、`implement_max_changed_files`、`max_fix_diff_lines`の5つ。いまの値より小さい値へだけ変えられる。予算の2つは0より大きい値、ほかの3つは1以上の整数に限る。0にすると、設定の検証が拒否するか、Claudeの利用が止まる。止めるのは真偽の項目の役割である |
| 変更できる一覧の項目 | `repo_allowlist`、`dependabot_other_repos`、`default_reviewers`の3つ。1回の呼び出しで、1要素の追加か1要素の削除だけをする。呼び出し側は、読んだ配列と、末尾に1要素を足したか、ちょうど1要素を除いた配列を渡す。scriptは、その差分から操作と動いた要素を導く。並べ替え、要素の書き換え、複数要素の増減、同じ長さの配列は、`invalid_value`で断る。書く値は、書く直前に読み直した配列に、その1要素を足すか除くかしたものである。読んだ配列は比較交換にだけ使い、書かない |
| 一覧に足せる要素の形 | 読み込み側と同じ規則にそろえて、scriptに写す。長さは100字までで、操作の記録が文字列の値を100字までに限るためである。形に合わなければ`invalid_element`で断る。`repo_allowlist`は`https://github.com/<owner>/<repo>`の形だけで、userinfo、クエリ、フラグメント、`github.com`以外のホスト、`http://`、sshは拒否する。`dependabot_other_repos`は`owner/repo`で、`.`と`..`の部分と末尾の`.git`は拒否する。`default_reviewers`はGitHubのログイン名の形で、`[bot]`で終わるものは拒否する。重複は、大文字小文字を区別せずに照合し、`repo_allowlist`は末尾の`.git`とスラッシュも除いて照合する。重複は`already_present`で断る。`repo_allowlist`は、`.git`と末尾のスラッシュを除いた形で書く。読み込み側の照合も、取得の列挙も、この形で通る |
| 一覧で断る変更 | `repo_allowlist`を空にする削除は、`would_empty`で断る。空の一覧は、`owners`配下のすべてのリポジトリを対象にするためである。空にする作業は人がCLIで行う。`repo_allowlist`への追加で、URLのownerが、読み直した生の`owners`の`name`のどれにも無いものは、`owner_not_listed`で断る(大文字小文字は区別しない)。足しても効かないのに、成功に見えるのを防ぐためである。ほかの2項目は、最後の1件の削除も許す |
| 変更できない項目 | 上の14個以外のすべて。`owners`、`factory_repo`、`allowed_*`、`check_commands_by_repo`、モデル名のような権限や宛先に関わる設定、`*_since`、`retention_*`、`dependabot_min_published_days`、`worker_alert_memory_ratio`、`*_timeout_sec`、`pr_conflict_watch_enabled`を含む。新しい項目も、決めるまで変更できない。真偽を有効にする向きと数値を上げる向きは、手順(有効にする前の確認、`*_since`の書き直し)があるので、人がCLIで行う |
| 読み取り | 補間しない生の値(`ResourceService.getResourceValue`)。パスはリテラルの`f/factory/factory_config`に固定し、境界テストが確かめる。補間する取得(`getResourceValueInterpolated`と`getResource`)は使わない |
| 参照 | 設定のどこかに`$var:`か`$res:`があれば、変更しない。読み取りが参照を展開すると、書き戻しで秘密の値が設定に入るおそれがあるためである |
| 比較交換 | 呼び出し側が「読んだ時の値」を渡す。書く直前に読み直した値と違えば、変更しない。項目が設定に無いときも変更しない。一覧は、要素を順序つきで比べる。読み直しも、同じく内容で比べる |
| 書き戻し | 対象の項目だけを置き換えた全体を書く。他のキーは同じ順の同じ文字列のまま残す。書いた後に読み直し、対象の項目が新しい値で、他のキーが書いた内容と同じかを返す。違えば、記録の結果を`partial`にする。読み直しが検出するのは、書き込みの後に起きた変更だけである。書く直前の読み取りから書き込みまでの間の変更は、検出できない |
| 記録 | 項目名と、前後の値(数値か真偽)だけを入れる。一覧は、項目名、操作(`add`か`remove`)、動かした要素、前後の件数を入れる。設定の全体と、配列の中身は入れない。userinfoを拒否するので、要素に資格情報は入らない |
| 呼び出しの順序 | 許可表の判定、操作者の導出、記録(`attempted`)、読み取り、比較と参照の検査、書き込み、読み直し、記録(結果)の順に固定する。項目が文字列でないときは、許可表の外として断る。比較と参照の検査で断ったときも、記録は`failed`で残す |
| SDKの呼び出し | `ResourceService.getResourceValue`、`ResourceService.updateResourceValue`、`wmill.getWorkspace`、`wmill.datatable`だけ。境界テストの許可表に載せ、書き込みのパスもリテラルに固定する |
| SQL | 自分のSQLは持たない。書くのは記録の部品だけで、書く表は`factory.console_actions`に限る |
| 環境変数 | 操作者を導くための`WM_USERNAME`と`WM_EMAIL`だけ |

実機のWindmill(1.817.0)で、使い捨てのpreview(defaultのworker)のジョブのトークンが、`factory_config`の生の値を読めることを確かめた。
現在の設定は参照を含まないので、生の値と補間した値は同じである。
この読み取りだけでは、補間しないことは示せない。
補間しないことは、取得の呼び出しが別のエンドポイントであることと、境界テストが補間する呼び出しを禁じることで守る。
書き込み(`updateResourceValue`)は、実際の設定を書き換えるため、実機では確かめていない。
反映の後に、実ジョブで確かめる。

次のことは、この操作では守れない。

- 書く直前の読み取りから書き込みまでは原子的でない。
  Windmillのresourceの更新は、条件付きの書き込みを持たない。
  その間に、Windmillの画面や`wmill resource push`が設定を書くと、書き戻しがその変更を失わせる。
  項目を問わない。
  対象の項目以外の変更も失われ、検出できない。
  書いた後の読み直しが検出するのは、書き込みの後に起きた変更だけである。
  読み直しは、対象の項目が新しい値で、他のキーが書いた内容と同じかを確かめ、違えば`verified`を偽にして知らせる。
  この間が問題になるのは、別の経路が同時に書く場合に限る。
  Console用workerが1枠なので、この操作の呼び出し同士は重ならない。
- 置き換えた設定の全体は、書く前に設定の読み込みの検証にかけない。
  別の項目がすでに壊れていても、許可した1項目の変更は書かれる。
  全体を検証するには、その本体(`lib/config.ts`)とその型(`lib/types.ts`)をscriptがたどり、境界の走査が要求する保護パスに入れる必要がある。
  この2つは設定の項目を足す変更が日常的に触れるので、守ると、その変更で自動の実装と修正が止まる。
  守っているのは、項目ごとの検査と、契約テストである。
  項目ごとの検査は、許可表の項目と向きと下限、一覧の要素の形、参照、比較交換である。
  契約テストは、許可したすべての項目の変更が、実際の読み込みの検証を通る設定を書くことを確かめる。
  数値は、下限の値まで下げた設定で確かめる。
  一覧の要素の形は、読み込み側の規則を写したものなので、両方向で固定する。
  scriptが受けた値を入れた設定は、読み込みの検証と、リポジトリの照合を通る。
  読み込み側が拒否する値は、scriptも断る。
  この守りで足りる根拠は、2つである。
  1つ目は、一覧の3項目に、他の項目との組み合わせの検査が無いことである。
  2つ目は、要素の形の検査を読み込み側と同じ規則にそろえ、両方向の契約テストで固定することである。
  真偽と数値の変更は、向きを下げるだけなので、組み合わせの検査に触れない。
  一覧は広げる向きを含むので、向きではなく、この2つで守る。
  組み合わせの検査が3項目に加わると、1つ目の根拠が崩れる。
  そのときは、この検査を見直す。
- 一覧の追加は、対象を広げる向きに働く。
  Consoleの管理者は、`owners`配下の別のリポジトリを、`repo_allowlist`に加えて対象にできる。
  対象に加わったリポジトリにも、`allowed_check_commands`の検査コマンドが及ぶ。
  `check_commands_by_repo`に同じ名前のエントリがあれば、実装の検証でその検査コマンドも、隔離なしで実行される。
  確認のダイアログは、この2つを警告する。
  `check_commands_by_repo`は、追加した要素との一致を判定せず、エントリがあれば一般の警告にする。
  `repo_allowlist`が空のときに追加すると、追加した1件と`factory_repo`以外のリポジトリが対象から外れる。
  `owners`に無いownerの追加と、空にする削除は、断る。
  管理者は、`f/factory`フォルダの権限を持つので、Windmillで直接設定を書ける。
  この操作は、その権限を増やさない。
  比較交換、形式の検査、操作の記録は、直接書く経路にない守りである。
- 一覧の要素が記録の形に合わないとき(100字を超える、記録に使えない文字を含む)は、Consoleから削除できない。
  記録を入れられず、`audit_unavailable`で断るためである。
  人がCLIで直す。
  断りの文は、この原因と、CLIで直すことを伝える。
- 元に戻す機能は無い。
  元に戻すには、運用者がWindmillでリソースを編集するか、`wmill resource push`で戻す。
- 実装を止めている間に承認すると、要件定義は承認済みで終わり、要対応に載らず、再開の口が無い。
  有効に戻した後、人が`retry_work_item`(Consoleの再実行)で再開する。
  確認のダイアログが、この旨を伝える。
- 数値の項目は、動いているフローの以後の手順にも効く。
  日次の予算を今日の使用額より小さくすると、今日のClaudeを使うフローがすべて失敗し、Consoleからは引き上げられない。
  確認のダイアログが、この旨を伝える。
  今日の使用額は、ダイアログでは調べない。
- ローカルのClaudeのセッションが設定を直接書く経路は、[R-CON-41](../../security-risks.md#r-con-41)にあたる。

## 保留と凍結を置く

保留と凍結を置く`console_hold_place`は、tag`console`で動かす書き込みのscriptである。
運用者がConsoleの確認のダイアログを通した後にだけ呼ぶ。
ローカルのClaudeのセッションが、このscriptを名前で呼ぶ経路は、拒否フックが止める([Claude Codeのフック](../../security.md#claude-codeのフック))。
置けるものと値を、次のとおりに絞る。

| 絞る対象 | 内容 |
| --- | --- |
| 種類 | マージの保留、deployの保留、スケジュールの凍結の3つ。取り込みの保留は置けない |
| 置く主体 | 引数に取らず、人に固定する。`holder`は`human`に限るので、行に操作者の名前は書けない |
| 期限の上限 | マージの保留と凍結は1440分、deployの保留は120分。置く部品が持つ上限と同じ値で、契約テストが画面の定数と突き合わせる |
| 理由 | 必須で、200字までである。制御文字と書式文字を含めない。記録には長さだけを入れ、理由は入れない |
| 対象 | マージの保留は`owner/repo`の形、凍結は`f/factory/`配下のスケジュールのパスの形、deployの保留は無し。凍結は、リポジトリの定義にあるスケジュールに限る(`console_known_paths.ts`と照合する) |
| 重ね置き | 同じ対象に有効な行があれば、置かずに断る。人以外が置いた行があるときも断る |
| 行数の上限 | 変数の行数が上限(50)に達していれば、置かずに断る。競合で置けなかったときも、例外にせず断りにする |
| 記録 | 置く前に`attempted`の行を入れ、入れられなければ置かずに断る。置いた後に読み直し、置いた行が見えないか、書く前に有効だった他の行が欠けていれば`partial`にする |
| 読み書きするもの | 保留の表は、`placeHold`と`listActiveHolds`だけを通す。凍結の変数は、`f/factory/freezes`のリテラルのパスで読み、書く。書くときは、secretとして作らない。パスと3番目の引数は、境界の走査が固定する |
| 変数が無いとき | 初回には変数が無い。読めなかったときは、`VariableService.existsVariable`を、リテラルのパス`f/factory/freezes`で呼び、`false`のときだけ空の状態として扱う。有無を確かめられないときは、読み取りの失敗をそのまま投げる |
| `placeHold`への到達 | `placeHold`を読み込んでよい`f/`のファイルは、このscriptだけである。配線テストが固定する |
| SDKの呼び出し | `datatable`、`getWorkspace`、`getVariable`、`setVariable`と、`VariableService.existsVariable`だけ |
| 環境変数 | 操作者を導くための`WM_USERNAME`と`WM_EMAIL`だけ |

マージの保留は止めるためだけに使い、許可には使わない。
そのため、対象が`repo_allowlist`の外でも置ける。
偽の保留で起きるのは、マージの遅れだけである。

次のことは、この操作では守れない。

- 凍結の変数の読み書きは排他しない。
  Console用workerは1枠なので、この操作の呼び出し同士は重ならない。
  CLIや`self_update`と重なると、他の行を黙って消すか、置いた行を巻き戻すことがある。
  置いた後の読み直しで、置いた行が見えないか、書く前に有効だった他の行が欠けていれば、`verified`を偽にして知らせる。
  欠けた行の判定は、`freeze_release`の`unconfirmed`と同じ部品を使う。
  窓は秒単位で、`freeze_release`と同じ受け入れである([凍結とdeployの保留](../freezes.md#凍結とdeployの保留))。
- ログインした管理者は、変数と保留の表に直接書ける権限をすでに持つので、権限は増えない。
  置く向きは、止める側に働き、期限で必ず終わり、解除できる。
- ローカルのClaudeのセッションも、運用者のwmillの資格で、汎用の経路から変数を直接書ける。
  この経路は、期限の上限も、操作の記録も通らない。
  フックが止めるのは、置くscriptを名前で呼ぶ経路だけである。

## スケジュールを止める

スケジュールを止める`console_schedule_stop`は、tag`console`で動かす書き込みのscriptである。
凍結を置いたスケジュールを1本だけ無効にする。
運用者がConsoleの確認のダイアログを通した後にだけ呼ぶ。
ローカルのClaudeのセッションが、このscriptを名前で呼ぶ経路は、拒否フックが止める([Claude Codeのフック](../../security.md#claude-codeのフック))。
止める条件を、次のとおりに絞る。
すべてを満たさなければ、止めずに断る。

| 絞る対象 | 内容 |
| --- | --- |
| 止められるスケジュール | 名前で列挙した7本。止められるのは、止めて黙るのがそのスケジュール自身の仕事だけで、ほかのスケジュールの入力や検知を止めず、再開を自己更新の追従へ任せられるものだけである。`self_update`、`poll_issues`、`poll_dependabot`、失敗の検出、見張りは、止めると他の仕組みが黙るので入れない。`collect_github`は、止めると`poll_issues`の取り込みと`poll_dependabot`が黙るので入れない。入れない理由は、同じファイルの表に書く。新しいスケジュールは、決めるまで止められない |
| 凍結 | そのスケジュールに有効な凍結があり、置いたのが人であること。ローカルのセッションが置いた凍結の下では止めない |
| 待ち | 凍結を置いてから7分が過ぎていること。置く前に始まった`self_update`のpushが、定義を上書きしうる間である。値は`scripts/freeze.ts`の待ちと同じで、契約テストが突き合わせる。人の端末のpushには時間の上限が無く、この待ちの対象外である |
| 凍結の残り | 凍結の期限まで5分以上残っていること。止めた直後に凍結が終わると、追従が戻す前に行が片付けられ、スケジュールが無効のまま残りうるためである。画面の定数と、契約テストが突き合わせる |
| 実行中の自己更新 | 凍結を置く前から実行中の`self_update`が無いこと。7分を超えて続く反映が、まだ上書きしうるためである |
| スケジュールの状態 | 今もそのscriptの定期処理で、有効であること。すでに無効なら断る |
| 有効に戻す操作 | 持たない。境界テストが、有効にする呼び出しの無いことを確かめる。画面の「凍結を解除して戻す」は、既存の凍結の解除(`freeze_release`)を呼び、新しい書き込み口は足さない |
| 記録 | 無効にする前に`attempted`の行を入れ、入れられなければ止めずに断る。無効にした後にスケジュールと凍結を読み直し、無効になっていないか、止めたときの凍結が有効でなければ`partial`にする |
| 凍結の変数 | 読むだけで、書かない。パスはリテラルで、走査が固定する。変数が無いときの有無の確認は、置くscriptと同じである |
| SDKの呼び出し | `ScheduleService.getSchedule`、`ScheduleService.setScheduleEnabled`、`JobService.listQueue`、`VariableService.existsVariable`、`getWorkspace`、`datatable`、`getVariable`だけ |
| 環境変数 | 操作者を導くための`WM_USERNAME`と`WM_EMAIL`だけ |

実機のWindmill(1.817.0)で、tag`console`の使い捨てのジョブのトークンが、スケジュールの読み取りと無効化、キューの読み取りを呼べることを確かめた。
無効なスケジュールを無効にする呼び出しは、何も変えない。
有効にすると次回のジョブがキューに積まれ、無効にするとキューが空になることも確かめた。

次のことは、この操作では守れない。

- 「止める準備」から「止める」までの間と、止めてから読み直すまでの間に、別の経路が凍結を解除することがある。
  scriptは、止める時点で凍結を読み直して確かめ、期限まで5分以上残っていなければ断る。
  止めた後にも凍結を読み直し、止めたときの凍結が有効でなければ、結果を`partial`にして、Windmillでスケジュールを有効に戻すよう知らせる。
  追従が動くのは、終わった凍結の行が残っているあいだだけで、行が片付けられた後は、スケジュールが無効のまま残りうるためである。
  読み直しの後に起きる解除は、止めた結果を変えず、追従が次の回でスケジュールを戻す。
- 7分は目安である。
  自己更新のpushが7分を超えて続くと、止めた後に定義で上書きされうる。
  scriptは、凍結を置く前から実行中の`self_update`があれば断る。
  止めた直後の読み直しで見つけられない上書きは、残る。
  人の端末のpushには時間の上限が無く、この待ちの対象外である。
- 止めたスケジュールは、凍結の解除だけで戻る。
  凍結が終わるか解除された後の、次の自己更新の追従で、リポジトリの定義(有効)に戻る。
  有効なdeployの保留があるあいだは、追従も待つので、凍結が終わっても、解除しても戻らない。
  `freeze:reset`で変数を空にすると、追従が動かず、次の反映まで戻らない。
  そのときはWindmillで有効に戻す。
  確認のダイアログが、deployの保留があるときの旨を伝える。
- 追従(`self_update`)が24時間以上動かないと、終わった凍結の行は、次に保留か凍結を置く操作の掃除で片付けられる。
  すると、Consoleで止めたスケジュールは、追従で戻らなくなる。
  通知は出ない。
  そのときはWindmillで有効に戻す。
  24時間は、置く部品が終わった行を残す時間(`STALE_ENDED_MS`)で、凍結の期限の上限と同じである。
- 止めるスケジュールごとに、止めると黙る処理がある。
  通知が出るものと出ないものがあり、確認のダイアログが、対象ごとの影響を伝える。
- Console用workerが1枠なので、この操作の呼び出し同士は重ならない。
  別の経路が同じスケジュールを同時に書く場合は、守れない。
- ローカルのClaudeのセッションも、運用者のwmillの資格で、汎用の経路からスケジュールを無効にできる。
  この経路は、許可表も、待ちも、操作の記録も通らない。

## 操作の記録

Consoleから行う書き込みの操作は、表`factory.console_actions`に記録する。
列は、操作者、操作の名前、対象、変えたキーと値、結果、時刻である。
表を書く部品は`lib/console_actions.ts`にあり、書き込みの操作の前後の順序を決める。

1. 操作の前に、結果が`attempted`の行を入れる。
2. 行を入れられなければ、新しい書き込みの操作は拒否する。
   記録の無い操作を通さないためである。
3. 操作の後に、結果を`succeeded`か`failed`に更新する。
   複数の段の操作で途中まで進んだときは`partial`にし、段ごとの結果を`changes`に入れる。
4. 更新に失敗しても、操作は取り消さない。
   戻りに記録の失敗(`action_audit`が`failed`)を載せる。

既存の操作に記録を足すときは、1の失敗で拒否せず、操作を通して記録の失敗を戻す。
データベースの障害が、記録と無関係な変数だけを書く操作まで止めないためである。
操作者を導けないときも、記録を書かずに操作を通し、記録の失敗を戻す。
更新されないまま残った`attempted`の行は、不明として扱う。

記録を書く操作は、次のとおりである。

| 操作 | 記録の名前 | 記録を書けないとき |
| --- | --- | --- |
| ジョブの取消 | `job_cancel` | 取り消さずに断る |
| 定期ジョブの再実行 | `job_rerun` | 起動せずに断る |
| 設定の変更 | `config_update` | 変更せずに断る |
| マージの保留を置く | `hold_place` | 置かずに断る |
| deployの保留を置く | `deploy_hold_place` | 置かずに断る |
| スケジュールの凍結を置く | `freeze_place` | 置かずに断る |
| スケジュールを止める | `schedule_stop` | 止めずに断る |
| 作業項目の再実行 | `retry_work_item` | 通す |
| 保留の解除 | `hold_release` | 通す |
| 凍結とdeployの保留の解除 | `freeze_release` | 通す |
| 手動投入 | `manual_intake_submit` | 通す |
| PRレビューの投入 | `pr_review_submit` | 通す |

解除の戻りにある`audit`は、解除の通知(`hold_released`)を書けたかを示す。
`action_audit`は、この表への記録を書けたかを示し、別である。
通知は人への知らせで、記録は監査のためなので、両方を残す。
手動投入の記録に入れるのは、リポジトリ(`owner/repo`)と検証後の進め方だけである。
題名、本文、不具合の欄は入れない。
PRレビューの投入の記録に入れるのは、`owner`、`repo`、`pr_number`だけである。
検証で断った投入は、何も起動しないので記録しない。

`changes`には、変えたキーと値だけを入れる。
値は、数値、真偽値、`null`、空白を含まない識別子の形の文字列に限る。
設定の全体や、`reason`などの自由な文字列は入れない。
記録に秘密値や長い文章が混ざるのを、入力の段で防ぐためである。

保持は、固定の90日である。
設定の項目にしない。
定義は`lib/console_actions.ts`にあり、保護パスで守る。
保護パスの目的は、PRの自動修正と実装が、人のレビューを経ずに書き換えるのを止めることである。
この表に記録する書き込みのscriptは、記録の順序を持つので保護パスに入れる。
書き換えられると、記録なしで同じ操作ができ、記録が誰の操作も表さなくなるためである。
対象は、次の11本である。

- 取消の`console_job_cancel`
- 定期ジョブの再実行の`console_job_rerun`
- 設定変更の`console_config_update`
- 保留と凍結を置く`console_hold_place`
- スケジュールを止める`console_schedule_stop`
- `retry_work_item`
- `manual_intake_submit`
- PRレビューの投入の`pr_review_submit`
- 保留の解除の`hold_release`
- 凍結とdeployの保留の解除の`freeze_release`
- 保護パスの変更の反映の承認と却下の`console_deploy_decide`

`approval_decide`、`notice_resolve`、`audit_kickoff`は、この表に記録しない。
記録の順序を持たないので、この理由では保護パスに入れていない。
`approval_decide`が決めた人を残す先は、承認依頼の表の`decided_by`である。
`cleanup_db`が毎日、90日を過ぎた行を消す。
消せなかったときは、`cleanup_db_failed`の通知を残す。
件数はログに残す。

この表は、defaultのworkerと管理者が書けるので、改ざんに耐えない。
誤操作を後から追うための記録であり、不正の証拠には使えない。

## ジョブの画面の描画

ジョブの画面と設定のタブは、サーバー由来の文字列を、テキストのノードとしてだけ描く。
見えない文字と、並びを入れ替える文字は、無害化の入口(`console/src/lib/safeText.ts`)で代替文字にする。
入口は、置き換える文字の範囲を自分で持つ。
保護パスの外のファイルには頼らない。
範囲を狭める変更が、人のレビューを経ずに入るのを防ぐためである。

保護パスに入れるのは、次の4つである。

- 無害化の入口(`safeText.ts`)
- 入口のテスト。
  分類ごとの代表の文字が置き換わることを確かめる
- 網羅テスト(`console/src/screens/jobs/safeTextCoverage.test.tsx`)。
  全項目に見えない文字を入れて描き、残らないことを確かめる
- ソースの契約テスト(`tests/scripts/console_jobs_render_contract.test.ts`)

描画の部品は、保護パスに入れない。
対象は`JobDetailParts.tsx`、`FlowDiagram.tsx`、`FlowScreen.tsx`、`ConfigSection.tsx`である。
契約テストが`screens/jobs/`の全体と設定の節を走査するので、部品を保護しても、上乗せの保証が小さい。
後続のPRで必ず直す部品なので、保護すると、毎回人の確認が要るためである。

残るリスクは[R-CON-07](../../security-risks.md#r-con-07)である。

## 設計書の読み返しの画面

設計書の本文の画面(`/console/items/:id/design`)は、承認の操作を持たない読み返しの画面である。
backendの`design_doc`ビューが、本文と図を返す。

- 本文は、承認画面と同じ整形(`sanitizeModelTextDetailed`)を通す。
  制御文字と書式文字を除き、秘密値をマスクする。
  長さでは切らない。
- 要約と未確定事項は、保存の前に整えてあるので、そのまま返す。
- 図のXMLは、マスクを通さない。
  残るリスクは[draw.ioの図の描画](#drawioの図の描画)に書く。
- `design_doc`は、作業項目の番号と設計書の番号で本文を返し、持ち主を確かめない。

この画面の描画は、承認と実装が受け取る文字と違う。
プレビューは、生のHTML(コメントを含む)とリンク参照定義を描かず、見えない文字を置き換え、長さでも切らない。
Markdownの文字は、HTMLのコメントとリンク参照定義も文字で見せるが、見えない文字の表し方、改行と空白の扱い、長さが承認画面と違う。
承認の判断を、この画面でさせないため、本文の先頭に固定の注記を出す。
注記は、どちらの形式でも、承認と実装が受け取る文字は承認画面の全文であることを伝える。
加えて、プレビューは、生のHTML(コメントを含む)とリンク参照定義と見えない文字と長さの扱いが承認画面と違うことを伝える。
Markdownの文字は、見えない文字の表し方、改行と空白の扱い、長さが承認画面と違うことを伝える。
承認待ちの設計書には、承認画面へのリンクを添える。
承認画面は、実装に渡る全文を、原文では文字として描く。
プレビューは参考表示で、表示している間は承認を止める。
その描き方は、保護パスの次の2つのテストが固定する。

- `console/src/designApprovalWiring.test.ts`
- `tests/scripts/console_design_visible_text_contract.test.ts`

残るリスクは次のとおりである。

- [R-CON-08](../../security-risks.md#r-con-08)
- [R-CON-09](../../security-risks.md#r-con-09)

## 取り込み時点のIssueと提案の描画

要件定義の承認画面の取り込み時点のIssueと、Issue提案の本文は、信頼できない入力を承認者に見せる面である。
承認の対象は、実装や起票に渡る原文である。
表を含むMarkdownは原文では読みにくいので、読みやすいプレビューを参考表示として足す。
プレビューは、生のHTML(コメントを含む)、閉じない`<!--`より後ろの本文、リンク参照定義、画像を描かない。
承認者がこれらを見ないまま承認しうるので、次のとおり、プレビューを承認の根拠にさせない。

- 既定は原文である。
  原文は、解釈せずに文字列として`<pre>`へ描く。
  承認画面を開いた最初の表示は、原文である。
- プレビューを表示している間は、承認を止める。
  既存の止める理由があれば、それを優先する。
- プレビューを一度でも選んだ承認は、原文を表示している間、原文を確かめたかのチェックを求める。
  プレビューを表示している間は、承認を止めているので、チェックを出さない。
  切り詰めの確認とは別のチェックで、別の状態で持つ。
  確認ダイアログで「承認する」を押した時点にも、同じ判定をやり直す。
- 却下は、プレビューで止めず、チェックも求めない。
- プレビューの本文は、見えない文字を置き換えた文字を、保護の対象でない共有の部品(`Markdown`)に渡す。
  `Markdown`は、生のHTMLを描かない(`rehype-raw`を使わず、`rehype-sanitize`のスキーマを通す)。
  リンクは、作業項目のリポジトリのIssueとPRと、同じページの見出しに絞る。
  `.drawio`でない画像は、代わりの文字だけを出す。
- プレビューの本文の上に、承認の対象は原文であることを示す固定の注記を出す。
- 提案のリンク先のリポジトリは、承認依頼の作業項目のリポジトリである。
  提案のIssueは、承認依頼と同じ作業項目のリポジトリに作られる。
  分からないときは、リンクを作らない。

## 設計の承認画面の保護

設計の承認画面は、実装に渡る正規化後の全文を、見えない文字を表記に置き換えて描く。
置き換える文字の範囲と、承認を止める判定は、`console/src/lib/visibleText.ts`が自分で持つ。
`safeText`は通さない。
通すと、U+2028や異体字セレクタがU+FFFDに、`\r\n`が`\n`に変わり、画面の文字が実装に渡る文字と一致しなくなるためである。
範囲を狭める変更や判定を緩める変更が、人のレビューを経ずに入ると、承認する人に見えない文字が、実装に渡ったまま承認される。

保護パスに入れるのは、次の5つである。

- 承認画面(`console/src/screens/inbox/DesignReview.tsx`)。
  取得した全文を描く部分、止める判定への入力の渡し方、プレビュー中の停止の式、全文の外の行数と終わりの印を、1つのファイルに持つ。
  保護しないと、渡す全文を作り替える変更や、判定に別の値を渡す変更、プレビュー中の停止を外す変更が、人のレビューを経ずに入る
- 区切りと判定の部品(`visibleText.ts`)
- 部品のテスト(`console/src/lib/visibleText.test.ts`)
- 全走査の契約テスト(`tests/scripts/console_design_visible_text_contract.test.ts`)。
  承認画面のソースが`safeText`を通さず、`visibleText`だけから描くことも、ここで固定する
- 配線の契約テスト(`console/src/designApprovalWiring.test.ts`)。
  承認画面から承認のボタンまでを描き、異常のある設計書で承認が止まり、画面が判定を通すことを固定する。
  プレビュー中に承認が止まる配線と、プレビューを選んだ承認に確認のチェックを求める配線も、同じファイルで固定する。
  判定の本体を守っても、画面がそれを呼ばなくなれば、承認は止まらないためである

`visibleText.ts`は、設計書の異常と取得の状態から承認を止める判定の全体を持つ。
範囲と件数に加えて、作業項目の状態などを見る判定(`designApprovalBlock`)と、人に見せる止める理由の文も、同じファイルにある。
判定の一部だけを保護すると、緩める変更が保護の外の部品へ移るためである。
止める理由の文言の手直しも、人のレビューを経る。

プレビュー中の停止は、`visibleText.ts`にない。
次のものは、保護している`DesignReview.tsx`の中にある。
表示の形式の判定(`designPreviewGate`)と、表示の状態の遷移(`nextDesignView`)である。
プレビュー中の止める理由の文と、確認のチェックの文も同じ場所に置く。
保護の外の`approvalDecision.ts`の`previewBlockedReason`、`previewCheckMessage`、`previewCheckFor`は、この画面で使わない。
判定が保護の外にあると、承認を通す変更が保護の外へ移るためである。

設計書のプレビューの保護と残るリスクは、「設計書のプレビュー」の節に書く。

契約テストは、0からU+10FFFFまでのすべてのコードポイントを調べる。
期待する集合は、`f/factory/lib/model_text.ts`の`INVISIBLE_PATTERN`と`isAllowedCharacter`から作る。
これに、`\p{Zs}`(U+0020を除く)、`\p{Zl}`、`\p{Zp}`、`\r`、私用領域、未割当、孤立サロゲートを足す。
見えない文字の素通りと、見える文字の置き換えを、両方向で確かめる。
件数も全走査で確かめる。
期待は`\p{Zs}`とカテゴリの集合だけで作り、`visibleText.ts`の述語を呼ばない。
`normalizeDesignForImplement`の出力に残る文字が、1文字ずつ表記と対応することも確かめる。

強い右から左の文字は、UAX#9の既定の範囲の固定の表の中の文字を数える。
`\p{Bidi_Class}`はJavaScriptの正規表現で使えないので、表を自分で持つ。
範囲の中の文字、数字、句読点、記号は、すべて数える。
範囲の中の数字や句読点には、強い右から左でないものもある。
見分ける表を持たず、広めに数える。
結合文字、書式文字、制御文字、私用領域、未割当、空白は、表記の分類が数えるので、重ねて数えない。
契約テストは、表の写しを期待に使わない。
ヘブライ、アラビア、シリア、ターナ、ンコ、サマリア、マンダ、アドラム、ハニフィ・ロヒンギャの文字体系の文字、数字、句読点、記号が、すべて数える側に入ることを、全走査で確かめる。
ラテン、ギリシャ、キリル、漢字、ひらがな、カタカナ、ハングルの文字、数字、句読点、記号を数えないことも確かめる。

表記にする集合と、承認を止める件数の集合は分ける。
表記は、人が見て判断する材料なので、広く残す。
件数は、日本語の設計書が普通に含む文字で承認が詰まらないように、絞る。
表記にしても、単独では件数に数えないものは、次の2つである。

- U+3000やU+00A0など、U+0020以外の空白(`\p{Zs}`)
- ひらがなかカタカナの直後にある、濁点(U+3099)か半濁点(U+309A)の1個

漢字の直後の結合文字と、かなの直後の濁点と半濁点以外の結合文字は、数える。
先頭、改行の直後、2個以上の連続、基底がかな以外の濁点と半濁点も数える。
異体字セレクタなど、既定で無視される文字も数える。
U+2028、U+2029、私用領域、未割当、孤立サロゲートも数える。
`\r`も見えない文字に数えるので、CRLFの設計書は止まる。

承認を止める判定(`designApprovalBlock`)は、次のいずれかのときに承認を止める。
却下は止めない。

- 取り込み時点のIssueか設計書を、見られない
- 表示している設計書が、承認する依頼のものではない
- 作業項目の状態が、設計の承認待ちではない。
  状態が分からないときも止める
- 承認依頼が、承認待ちではない
- 設計書が、長さの上限で切られている
- 全文に、見えない文字、強い右から左の文字、3行以上の空行の連続、空白の長い連続、画面が出す印のまねがある

空行には、空白(U+0020以外を含む)とタブだけの行を含める。
空白の長い連続は、行の途中では8桁以上、行頭では32桁以上である。
タブは4桁に数え、U+3000を含むそれ以外の空白は1個を1桁に数える。
タブやU+3000とスペースが混ざるときは、桁の合計で数える。
行の途中では、タブが1個なら数えず、2個続くと数える。
U+3000は、2個や7個の連続では数えず、8個の連続で数える。
行頭では、タブが8個で数え、7個なら数えない。
行の途中では、U+3000とU+0020を除く空白が2個以上続いても数える。
U+3000は字下げや全角の区切りに普通に使うので、続けても桁の合計だけで数える。
行頭の字下げは普通に使うので、行頭の閾値は大きくする。
長い空行や空白で下の本文を視野から外す手口を、承認を止める件数に数えるためである。

画面が出す空行と空白の印は、`[空行 N 行]`と`[空白 N 個]`の形である。
本文が同じ形を書くと、画面の印と見分けがつかない。
そのため、NFKCにした文字列で、この形を数える。
数字は、十進数字(`\p{Nd}`)と漢数字(〇、一から九、十、百、千)を含む。
括弧は、角括弧(全角を含む)、隅付き括弧(【】)、亀甲括弧(〔〕)を含む。
印の直前と直後が、どちらもバッククォートのときは、コードとして引用した文言なので数えない。
画面の印はバッククォートを伴わないので、引用と見分けがつく。
全文の終わりの印は`<pre>`の外に出すので、本文に同じ文言があっても件数には数えない。
本文に書かれた偽の終わりの印と見分けるには、画面での描き方と、パネルの先頭に出す行数との突き合わせに頼る。

保護しないものがある。
次の部品は、日常的に直すので保護しない。
判定を呼ぶ`designBlockedReason`(`console/src/lib/approvalDecision.ts`)、確認文、トースト、`approval_design_doc`の型ガードである。
承認の詳細(`ApprovalOverview.tsx`)、共有のパネル(`ReviewPanel.tsx`)、承認バー(`ApprovalBar.tsx`)も保護しない。
承認画面(`DesignReview.tsx`)の中の描き方と配線は、上の2つの契約テストが固定する。
固定するのは、画面が固定した入力の全文を描き切ること(描いた`<pre>`の文字と、印が持つ元の文字列から全文を組み直せること)と、ソースの形である。
印の見える文字が空でないことは、組み直しの検査では確かめない。
部品のテストと人のレビューで確かめる。
全文を切る、隠すスタイルの書き方は、代表的なものを拒否の一覧で捕まえる。
一覧は網羅しないので、漏れはレビューで確かめる。
承認画面のファイルを変える変更は、保護パスなので、人のレビューを経る。

## 設計書のプレビュー

設計の承認画面は、設計書を原文で既定に出し、読みやすいプレビューを参考表示で足している。
承認の対象は原文(実装が受け取る正規化後の全文)である。
プレビューは、生のHTML(コメントを含む)、リンク参照定義、画像、閉じない`<!--`より後ろの本文を描かない。
文字参照で書いた見えない文字と向きの制御文字は、置き換えずに描くことがある。
承認者がこれらを見ないまま承認しうるので、次のとおり、プレビューを承認の根拠にさせない。

- 承認画面を開いた最初の表示は、原文である。
  承認の詳細(`ApprovalOverview.tsx`)は、最初の表示の状態を決める`initialView`を渡さない。
- 設計書の表示の形式が`text`(原文)でないときは、承認を止める。
  プレビューのほか、知らない値でも止める。
  知らない値のときは、原文を描いたまま止めるので、止める理由の文は実際の画面と合わない。
  止める理由は、`designBlockedReason`の理由があればそれを優先し、なければ`designPreviewGate`の理由にする。
  設計書が長さの上限で切られているときは、プレビューでも、切られている理由が先に出る。
- プレビューを一度でも選んだ承認は、原文を表示しているとき、原文で確かめたことを申告するチェックを求める。
  `nextDesignView`は、今の形式か次の形式がプレビューのとき、`previewed`を立てる。
  `previewed`は、原文に戻しても下りない。
  知らない形式への切り替えは、プレビューとして扱い、`previewed`を立てる。
  `designPreviewGate`は、`text`で`previewed`のときだけ、チェックの文を返す。
  プレビューの表示中は、承認そのものを止めるので、チェックを出さない。
  チェックは自己申告で、読んだことを保証しない。
- 切り替えは、設計書のパネルの中の1か所にあり、設計書の本文だけに効く。
  取り込み時点のIssueのパネルには`mode`を渡さないので、常に原文である。
- 承認バーは、承認依頼ごとに`key`で作り直す。
  この`key`の効き目は、承認バーの状態に限る。
  `DesignReview`の表示の状態は、祖先の部品(`InboxDetail.tsx`)が`key`を外すと、別の依頼へ持ち越されうる。
  持ち越されたプレビューは承認を止め、持ち越された`previewed`は確認のチェックを増やすだけなので、どちらも止める側に倒れる。
  最初の表示が原文であることは、祖先の`key`に頼る。
- プレビューは、見えない文字を置き換えた本文を、保護の対象でない共有の部品(`Markdown`)に渡して描く。
  `DesignTextPreview.tsx`は、`Markdown`だけで描く。
  注入の境界は、`Markdown`の`rehype-sanitize`のスキーマとCSPである。
- 承認画面の注記が、プレビューが描かないものを挙げ、原文で確かめるよう伝える。
- 確認のチェックを付けた後に原文とプレビューを行き来したときのチェックの扱いは、[R-CON-42](../../security-risks.md#r-con-42)にあたる。

保護テスト(`console/src/designApprovalWiring.test.ts`)は、次のことを固定する。

- 最初の描画が原文で、設計書のパネルに行ごとの`<bdo dir="ltr">`があり、プレビューの印と確認のチェックが無い。
- `initialView`が、プレビューで、まだ選んでいない状態のとき、承認ボタンが無効になる。
  止める理由の文の全体とプレビューの印が出て、`<bdo dir="ltr">`は無い。
  理由の文は、テストが文字列で直接書いて照合する。
  保護の外から期待値を取らない。
- `initialView`が、プレビューで、まだ選んでいない状態のとき、設計書のパネルより前にプレビューの印が無い(取り込み時点のIssueは原文のまま)。
- 切り詰めた設計書と、プレビューの状態の組み合わせで、止める理由が切り詰めの理由である。
- `initialView`が、原文で、プレビューを選んだ状態のとき、確認のチェックの文が出る。
  承認ボタンは無効で、止める理由は確認の理由の文である。
  この2つの文も、テストが文字列で直接書いて照合する。
- `nextDesignView`は、保護テストが直接呼び、戻り値の全体を照合する。
  確かめる遷移は、次の6つである。
  原文で未選択からプレビューへ。
  プレビューで未選択から原文へ。
  原文で選択済みから原文へ。
  原文で未選択から原文へ。
  プレビューで選択済みから原文へ(選択済みのまま残る)。
  知らない値へ。
- `designPreviewGate`は、保護テストが直接呼び、戻り値の全体を文字列で照合する。
  原文で未選択は理由も確認の文も無く、原文で選択済みは確認の文だけ、プレビュー(未選択と選択済みの両方)と知らない形式(選択済み)は理由だけを返す。
- `DesignReview.tsx`のソースで、判定の関数の呼び出しが1つで、`const gate = designPreviewGate({ mode, previewed });`の形であること。
  承認バーに渡す止める理由が`blocked ?? gate.reason`の1か所であること。
  `previewCheckMessage={`(属性名と`=`と`{`の間に空白を挟まない形)の出現が1つで、`previewCheckMessage={gate.check}`の文字列を含むこと。
  空白を挟んだ書き方は、検査の外にある。
  `const { mode, previewed } = view;`を含むこと(数えない)。
  名前の後ろに`(`か`<`を書いた`useState`の呼び出し(`useState(`と`useState<`の形。名前と記号の間の空白は許す)が1つであること。
  `import`から`from "react";`までの間に`;`を含まない形のimportで持ち込む名前は、現在使う`Fragment`、`ReactNode`、`useMemo`、`useState`だけであること。
  その形のimportの別名、`useReducer`、既定とnamespaceのimportは、ここで止まる。
  呼ぶフックが、現在使っているものだけの許可リストに収まること。
  `use`の直後が大文字の名前を、名前の後ろの`(`か`<`で呼ぶ形のフックを足す変更は、ここで止まる。
  名前やフックを足すときは、許可リストと、走査の結果の照合の期待値を直す。
  走査の結果が、今のソースの名前とフックの全体と一致することも固定する。
  走査が空振りして、許可リストの検査が何も見ないまま通る事態を防ぐ。
  `useState`の宣言が`const [view, setView] = useState<DesignView>(initialView);`の文字列を含むこと。

## draw.ioの図の描画

要件定義の図(`<name>.drawio`)は、生のXMLとして、要件定義のファイルと同じworker専用のディレクトリ(`requirement_drafts.doc_dir`の下)に書く。
DBの`requirement_drafts.diagrams`列には、`{name, file}`の参照だけを入れる。
図の内容とURLは、GitHubのIssueとPRのコメントにも、Discordの通知にも投稿しない。

Consoleは、`f/factory/steps/console_query.ts`の`requirements_doc`ビューで、`requirements.md`と各図のファイルを読み戻す。
読む前に、`doc_dir`が`REQUIREMENTS_BASE_DIR`の下にあることを確かめる。
図のXMLはWindmillのジョブ結果としてConsoleのフロントエンドに渡るだけで、GitHubとDiscordには送らない。

設計の図も、`design_doc`ビューが同じ基準のディレクトリの下から読み戻す。
設計のディレクトリに置くのは`design.md`と`<name>.drawio`だけである。
`design_doc`は、本文をDBから返すので、`design.md`を読まず、`<name>.drawio`だけを読む。
同じ`doc_dir`を指す新しい設計書があるときは、古い設計書の図を読まない。
`doc_dir`は`req-<要件定義の試行>/attempt-<設計の試行>`で決まり、生成は同じ`doc_dir`の再利用を止める。
それでも行が重なると、古い行が読んだ図は、新しい行の図を自分の図として返す。
その防御として、最新の行以外は図を読まない。

図のXMLは、`f/factory/lib/drawio.ts`の`validateDrawioXml`で検査する。
検査は2か所でかける。
生成の時点と、`requirements_doc`と`design_doc`のビューがディスクから読み戻す時点である。
ディスクのファイルは生成の後に書き換わりうるので、読み戻す時点でも同じ検査をかける。
読み戻しで通らない図は、ファイル名が不正な図と同じように、警告のログを残して一覧から落とす。
検査が例外で終わった図も、通らない図として扱い、警告のログを残す。
安全と確かめられない図は、表示しないほうを選ぶためである。
文書の本文と、ほかの図は返す。

検査は、大きさ、ルート要素に加えて、次のものを加工せずに拒否する。
拒否したときは`valid: false`と理由を返す。

- 圧縮した図。
  すべての`<diagram>`について、空白以外のテキストとCDATAを拒否する。
  `<mxfile>`の`compressed`属性の値が`true`のときも、引用符の種類を問わず拒否する。
  圧縮した図は中身が見えず、以降の検査を素通りするためである
- `link`属性と`usemap`属性
- `placeholders`属性と、`<mxfile>`の`vars`属性。
  理由は下にある
- 図の構造としての`<a>`、`<area>`、`<map>`、`<meta>`、`<iframe>`要素
- ラベルのHTMLの、パーサーによって読み方が分かれる構文。
  大文字小文字を区別しない。
  - `<!`で始まる構文(コメント、DOCTYPE、CDATA、偽のコメント)、`<?`、`</`の後ろが英字でない形
  - 中身をタグとして読まない要素。
    属性の有無を問わない。
    対象は`<textarea>`、`<title>`、`<xmp>`、`<noscript>`、`<noembed>`、`<noframes>`、`<plaintext>`、`<iframe>`、`<style>`、`<script>`である
  - 外来要素の`<svg>`と`<math>`
  - SVGのアニメーション要素: `<set>`、`<animate>`、`<animateMotion>`、`<animateTransform>`

  理由は、下の「ラベルのHTMLの読み方」にある。
- ラベルのHTMLの、属性付きの次の要素。
  属性付きとは、`名前=`の形の属性を持つことである。
  - リンク: `<a>`、`<area>`、`<map>`
  - ページ遷移: `<meta>`、`<base>`、`<link>`
  - 埋め込み: `<object>`、`<embed>`、`<frame>`、`<img>`、`<image>`、`<video>`、`<audio>`、`<source>`、`<use>`
  - 送信: `<form>`、`<input>`、`<button>`

  `<image>`は、HTMLのパーサーが`<img>`に置き換えるので、`<img>`と同じに扱う。
  `<iframe>`と`<svg>`は、上の読み方が分かれる構文として、属性の有無を問わず拒否する。
- ラベルのHTMLのタグの中のイベントハンドラ属性。
  `onclick=`のように、`on`と英字の名前に`=`が続く形である
- ラベルのHTMLの`usemap=`、`formaction=`、`srcdoc=`
- 構文が不正なXML。
  閉じていないコメント、CDATA、処理命令、タグ、引用符と、タグの引用符の外の`<`である。
  XML全体を前から1回だけ読み、読めない箇所があれば拒否する。
  正規表現の打ち切りで、手前までしか検査されずに通ることを防ぐためである

`Promise<Object>`、`List<Map>`、`Result<A, E>`のように、属性を持たない要素名だけの表記は通す。
型の書き方としてラベルに現れ、属性の無い要素は行き先も資源のURLも持てないためである。
`<A extends B = C>`のような表記は拒否することがある。
要素名と同じ型引数の名前に`名前=`が続くと、属性付きの要素と見分けられないためである。

図のXMLを加工して取り除くと、図の見た目が変わり、ビューアの解釈との差が新しい抜け道にもなる。
そのため、取り除かずに拒否し、理由を生成のやり直しでClaudeに伝える。

属性の値とテキストは、XMLの実体参照(`&lt;a`、数値文字参照の`&#60;`と`&#x3c;`)を復号してから調べる。
ビューアは`html=1`のラベルをHTMLとして解釈するためである。
二重にエスケープした`&amp;lt;a`も、安全側に倒して復号し、拒否する。
実際に何として読まれるかは追わない。
復号は5段までで、それでも変わり続ける値は調べきれないので拒否する。
`placeholders`属性は、どの要素にあっても値を問わず拒否する。
`<mxfile>`の`vars`属性も拒否する。
`placeholders`を持つセルでは、draw.ioがラベルの`%名前%`を別の値に置き換える。
置き換える値は、祖先のセルの属性、ページの名前、`vars`に書いた値などである。
タグを置き換え元の値とラベルに分けて書けるので、置き換えた後のラベルを検査では確かめきれない。
要件定義の図には置き換えが要らないので、使うこと自体を拒否する。
要素と属性の名前は、大文字小文字を区別せずに比べる。
`link`と`usemap`は名前の完全一致だけを見るので、`linkTarget`のような別の属性や、ラベルの文章にあるだけの単語は拒否しない。
`<object>`は、draw.ioがセルを包む要素として正しい。
構造としては許し、ラベルのHTMLの中の、属性付きのものだけを拒否する。

### ラベルのHTMLの読み方

検査は、ラベルのHTMLのタグを、引用符を読む走査で読む。
`<`に英字が続く開始タグと、`</`に英字が続く終了タグを、HTMLのパーサーと同じ規則で、引用符の外の`>`まで読む。
終了タグも読むのは、HTMLのパーサーが終了タグの属性の引用符も読むためである。
この走査で、イベントハンドラ属性と、属性付きの拒否する要素を探す。
タグの外の文章にある`one = 1`、`online = true`、`https://x/?online=1`は拒否しない。

パーサーによって読み方が分かれる構文を拒否するのは、検査とブラウザがタグを同じ位置で区切る入力だけを通すためである。
HTMLのパーサーは、コメントや`<textarea>`の内側をタグとして読まない。
検査がその内側の引用符を読むと、タグの終わりが検査とブラウザでずれ、本物のタグのハンドラを見逃す。
`<svg>`と`<math>`の内側は、CDATAを読むなど、別の規則で読まれる。
これらの構文が無いラベルでは、ブラウザはタグの外を常に同じ規則で読み、引用符を読む走査と同じ位置でタグを区切る。
SVGのアニメーション要素は、`href`などの属性を後から書き換えてリンクを作れるので、`<svg>`の外にあっても拒否する。

要素名は、後ろに空白、`/`、`>`、文字列の終わりが続くときだけ当てる。
HTMLのパーサーは、それ以外の文字を要素名の続きとして読むので、`Map<Settings>`や`List<Titles>`は通す。
`<title>`は、属性が無くても拒否する。
属性の無い`<title>`でも、閉じるまでの内側をタグとして読まない状態に入るためである。
`Map<title>`のような型の表記は拒否されるので、型の名前を変えるか、文章で書く。
`a < b`のように`<`の後ろが英字でない形は通す。
`x </ y`のように`</`の後ろが英字でない形は、HTMLのパーサーが偽のコメントとして読むので拒否する。

補助として、引用符を読まない走査も行う。
`<`に英字が続く箇所から次の`>`までの区間を、引用符を無視してタグとして調べ、イベントハンドラ属性があれば拒否する。
属性付きの要素も、要素名の後ろから最初の`>`までに`名前=`があれば拒否する。
引用符を読む走査とブラウザで読み方の分かれる入力が、まだ残っていたときに備えるためである。
引用符の中の`>`で区間が切れるので、補助の走査だけでは足りない。

どの走査も、調べ終えた位置の後ろから次を探すので、検査の時間は入力の長さに比例する。
この検査は1層目である。
2層目は、iframeのCSPである。
`script-src`に`'unsafe-inline'`が無いので、検査をすり抜けたハンドラも実行されない。

### 隔離したiframeで描く

ConsoleのSPAは、図を最上位のページでは描かず、隔離したiframeの中で描く。
図のXMLはIssue本文に由来する信用できない入力で、ビューアは第三者の大きなコードだからである。
最上位のページで描くと、ビューアの欠陥が、Windmillを管理者として操作できるXSSになる。
実装は`console/src/components/drawio/DrawioFrame.tsx`と、`console/public/drawio.html`である。
要件定義書の画面(`/console/items/:id/requirements`)が、図ごとに`DrawioFrame`で描く。
安全の検査を通らなかった図(`rejected_diagrams`)は、iframeを作らず、表示しない旨だけを出す。
仕組みは[Consoleの配信の仕様](../console.md)の「draw.ioの図」にある。

ジョブの画面と作業項目の詳細のflowの図(`console/src/screens/jobs/FlowDiagram.tsx`)と、スケジュールの説明は、iframeを使わない。
自前のSVGと文字で描く。
図のSVGは、`dangerouslySetInnerHTML`を使わず、サーバー由来の文字列を、子のジョブへのリンクのidを除いて属性に入れない。
図のデータ(`console/src/generated/flows.json`)はリポジトリのコードから作ったバンドルの静的なJSONで、信用できない入力を含まない。
重ねるジョブのステップのidと状態はサーバー由来なので、見えない文字を代替文字にしてから描く。
子のジョブへのリンクに入れるidは、UUIDの形のときだけhrefに入れる。

固定するsha256は、commit固定のURLから取得したバイト列の値である。
版の更新は、[ビューアの更新](#ビューアの更新)で自動のPRにする。
手で上げる手順は[Consoleの配信の仕様](../console.md)の「draw.ioの図」にある。

XMLをiframeへ送るときの`targetOrigin`は`"*"`にする。
不透明なオリジンには、送り先のオリジンを指定する方法が他に無いためである。
宛先を絞れない残るリスクは、[R-DIO-17](../../security-risks.md#r-dio-17)である。
設計の図のXMLには、秘密値のマスクをかけない。
残るリスクは[R-DIO-02](../../security-risks.md#r-dio-02)である。
XMLをpostMessageで送る先は、このsandboxのiframeだけである。
XMLそのものは、`console_query`のジョブ結果としてWindmillに残り、Consoleの最上位のページにも渡る。

サーバー側で図の`link`属性と`html=1`を落とす処理は入れない。
`validateDrawioXml`は1層目として、リンクを含む図のうち既知の形を拒否する。
網羅はしない。
すり抜けた図は、2層目のCSP、sandbox、受け口のscriptとビューアの設定が受け止める。
iframeの中で動くscriptが取れるのは、そのiframeが受け取った図のXMLだけで、リンクを押せず、外への取得はCSPが止める。
`html=1`を落とすと、`<br>`による改行のような正しい図が壊れる。

残るリスクは次のとおりである。

- [R-DIO-03](../../security-risks.md#r-dio-03)
- `'unsafe-eval'`は許さない。
  残るリスクの表の[R-DIO-04](../../security-risks.md#r-dio-04)にあたる。
  根拠は、32.4.1のビューアのコードの読解と、ヘッドレスのChromeでの確認である。
  自動で上げた版は、この調査を経ていない。
  - ビューアが`eval`を呼ぶ箇所は2つある。
    図のスタイルや定義に書かれた式を評価する経路は、評価を許すフラグがどれも既定で無効である。
    外部の図形ライブラリのscriptを取得して評価する経路は、取得をCSPの`connect-src 'none'`が止める。
    `new Function`は無い。
  - `'unsafe-eval'`を付けずに、普通の図と、リンク、外部の画像、フォント、図形ライブラリ、評価を許す式を含む図を描いた。
    `eval`の違反は出なかった。
- [R-DIO-05](../../security-risks.md#r-dio-05)

### 親の部品が守ること

`DrawioFrame`が、iframeを作る。
iframeとのメッセージは、`console/src/lib/drawioMessages.ts`と`console/src/lib/drawioFrameState.ts`の純関数が扱う。

| 守ること | 内容 |
| --- | --- |
| 不透明なオリジンで動かす | `<iframe src="/console/drawio.html" sandbox="allow-scripts" referrerPolicy="no-referrer">`にする。`srcDoc`は使わない。`allow-same-origin`、`allow-popups`、`allow-forms`、`allow-top-navigation`は付けない。iframeは、WindmillのCookie、親のDOM、最上位のページの遷移、ポップアップ、フォームの送信から切り離される。外への取得は、CSPの`connect-src 'none'`が止める |
| 受け口と値を合わせる | メッセージの種別と失敗の種類は、`console/public/drawio/drawio-frame-*.js`と同じにする。`tests/lib/drawio_frame_isolation.test.ts`が、ソースを文字列として読んで確かめる |
| XMLは1回だけ渡す | 最初のloadの後にpostMessageで1回だけ送る。親は、送り元がそのiframeの`contentWindow`のものだけを受け取り、高さを80〜1600の範囲に収め、失敗は固定の3つの種類だけを受ける。iframeが2回目のloadを起こしたら、遷移とみなして表示を止める |
| 図を拒否する | 上の`validateDrawioXml`が、生成の時点と読み戻しの時点で、リンク、危険な要素、圧縮した図を拒否する |

読み戻しで拒否した図は、`requirements_doc`と`design_doc`のビューが名前を`rejected_diagrams`で返す。
本文は、その名前の図を「安全の検査を通らなかったので表示しません」と表示し、図が見つからない場合と区別する。

読み戻しの検査は、すでにディスクにある図にもかかる。
検査を通らない図は表示しない。
`link`属性や`<a>`を含む既存の図は、「表示しません」になる。
承認する人は、図を見ないまま判断することになる。
図が判断に要るときは、要件定義の作り直しを求める。

#### sandboxが止められない経路

`sandbox`は、iframeの`window.top.postMessage`と`window.parent.postMessage`を止められない。
ConsoleのSPAの親のページは、iframeから高さと失敗の種類だけを受け、ほかのメッセージの通り道を持たない。
図のscriptが親へ送れるものは、範囲に収めた数値の高さと、固定の失敗の種類に限られる。

#### 保護パス

次のファイルは、保護パスである。

- `tests/lib/drawio_frame_isolation.test.ts`

`DrawioFrame.tsx`は保護しない。
画面の普段の変更を、保護パスで止めないためである。
`sandbox`の値は上のテストが固定し、HTTPのCSP(`infra/Caddyfile`の`drawio_headers`)も後ろ盾になる。
別の部品が`/console/drawio.html`をsandboxなしのiframeで読む迂回は、CSPの`sandbox allow-scripts`が、ページを不透明なオリジンに固定して止める。
`frame-ancestors`は、埋め込める親を、このサイトと同じオリジンのページに限る。

制約は次のとおりである。

  親は、応答がないものとして固定の文を出す。
- 外部の図形ライブラリ(AWSなどのアイコン集)と、ビューアのtoolbar、ズーム、レイヤは使えない。

### ビューアの更新

固定は、Windmillの`f/factory/drawio_viewer_bump`が週に1回確かめ、新しい版があればPRにして上げる。
GitHub Actionsではなく、Windmillで動かす。
ActionsでPRを作るには、PRに書ける長期のトークンをActionsのsecretに足す必要があるためである。
Actionsの既定のトークンで作ったPRは、CIを起動しない。
このリポジトリは、`ci.yml`の権限を読み取りだけに保つ。
Windmillは、実装とPR修正が使う`f/factory/github_token`で足りる。
このトークンはWorkflowsの権限が無いので、`.github/workflows/`には書けない。

| 守ること | 内容 |
| --- | --- |
| 取得元を絞る | 公式のjgraph/drawioのGitHubのリリースだけを読む。下書きとプレリリースは読まない。タグが指すcommitは、GitHubのAPIでたどって決める。ビューアのURLはcommit固定で、リダイレクトは許さない |
| 2つの時計で待つ | 公開日(`published_at`)から14日以上たち、かつ、同じcommitを14日以上前から見ている版だけを上げる。公開日はリリースを作る側が書き換えられるので、それだけを根拠にしない。見始めた時刻は、タグごとにDBの`factory.drawio_viewer_observations`へ記録する。記録は、Factoryの通常の経路からは書き換えない。DBを直接触る変更(migration、WindmillのSQL)は、この保護の外にある |
| 付け替えで待ちを数え直す | タグが別のcommitに付け替えられたら、記録の時刻を今に取り直す。付け替えた版は、取り直した時刻から14日待つ |
| 正式版から数える | プレリリースは読まず、記録もしない。プレリリースから正式版に切り替わった版は、正式版として初めて見た時刻から14日を数える |
| メジャー版に目印を付ける | メジャー版が変わる版も、他の確認を通ればPRにする。固定のファイルは保護パスで、マージは人が行うため、メジャー版で止めても安全は増えない。題名を`[major]`で始め、本文の先頭に、リリースノートとCSP、sandbox、図の隔離のテスト(`drawio_frame_isolation`)の確認を人が行うと書く |
| 大きさの急変を上げない | 今のビューアの大きさから2割を超えて増減した版は上げない。noticeに残し、人が版を指名したときだけ上げる。空のファイルと、CIの取得の上限(10MB)を超えるファイルは、指名しても上げない |
| 2つの経路で照合する | 取得したバイト列の大きさとgit blobのIDを、GitHubのAPIが返す同じcommitのファイルの値と照合する。違えばPRを作らず、noticeに残す。sha256はこのバイト列から計算して固定ファイルに書く。CIは別の経路(`raw.githubusercontent.com`)で取得し直して照合する |
| 書き込みを絞る | PRのブランチを1つ作るだけで、`main`には書かない。変えるのは固定のファイルと、ビューアを読むページ(`console/public/drawio.html`)の2つだけである。commitの名義はGitHubのnoreplyにする |
| 重複を作らない | 同じ版のブランチをheadにしたPRが、閉じたものを含めて1件でもあれば、ブランチが消えていても作らない。未完了の更新のPRがあるあいだも、新しいPRを作らない。数えるのは、このリポジトリのブランチをheadにしたPRだけで、forkに同じ名前のブランチを作られても更新は止まらない |
| 既存のブランチを確かめる | PRの無いブランチが既にあれば、先頭のcommitを1回だけ取り、そのcommitに対して確かめる。各ファイルのgit blobのIDが作るはずの内容と一致し、`main`との差分がその2ファイルだけで、名前の変更を含まないことを確かめる。合わなければPRを作らず、noticeに残す。PRを作った後に、PRのheadのcommitが確かめたcommitと同じかを確かめ、違えば自動レビューのラベルを付けずに止めて、noticeに残す |
| 自動でマージしない | PRはDraftにせず、自動レビューのラベルを付ける。マージは人が行う |
| 修正を人に限る | ブランチ名が`factory/drawio-viewer-`で始まるPRには、PR修正を始めない。修正の準備のステップも止める。修正を許すと、固定のファイル以外も書き換えたcommitを、人が気づかずにマージするおそれがある。自動レビューは動く。`factory:fix`ラベルは消費されず残る。修正は人が行う。判定はブランチ名だけで行うので、`factory_repo`に限らず、担当するすべてのリポジトリのPRに効く |
| 部品を保護パスにする | 更新のscript、判断、GitHubの読み取り、観測の記録、scriptとスケジュールの定義を保護パスにする。書き換えられると、別の版や取得元の更新を人の確認なしに提案できるためである。一覧は[保護パスの変更を止める](../pr-workflow.md#保護パスの変更を止める)にある |

## 要件定義書のリンク

要件定義書のMarkdownは、Issueの内容に由来する。
Consoleは、これをWindmillと同じオリジンで描く。
`rehype-sanitize`の既定のスキーマは`javascript:`などを除くが、任意の`http(s)`のURLの`a[href]`は通す。
そのため、読み手がリンクの文字を信じて、外のページを開くおそれがある。

`src/components/markdown/Markdown.tsx`は`a`を差し替える。
リンクにするものは、`src/lib/markdownLink.ts`の`resolveMarkdownLink`で絞る。

- 作業項目と同じリポジトリのIssueとPRのURL。
  `src/lib/safeUrl.ts`の`safeGitHubUrl`を通り、ownerとrepoが作業項目のものと一致するものに限る。
  ownerとrepoは、大文字小文字を区別せずに比べる。
  信頼できない本文が、読み手を別のリポジトリへ誘導できないようにするためである。
- 同じページの見出しへのフラグメント。
  `#`で始まり、`slugify`が作るslugと同じ形に限る。

それ以外は、リンクにせず文字で出す。
リンクの文字とURLが違うときは、URLも括弧で添える。
読み手が行き先を判断できるようにするためである。
添えたURLは`<bdi>`で包む。
文字の向きを変える制御文字が、周りの表示を崩さないようにするためである。
同じページの見出しへのリンクは、行き先を取り違えようがないので、URLを添えない。
GitHubへのリンクは、`rel="noopener noreferrer"`を付けて新しいタブで開く。

`Markdown`が`repo`を必須の引数で受けるので、リポジトリを渡さずにGitHubのURLをリンクにする経路は無い。
見出しへのフラグメントは、接頭辞`h-`を付けた見出しの`id`を指すように読み替える。
見出しの`id`が、ページの他の要素の`id`や`name`と重ならないようにするためである。
脚注の記法は使わない。
脚注への参照(`#user-content-fn`で始まるフラグメント)は、リンクにせず文字で出す。
本文、要約、未確定事項、題名は、描く前に`displayableIssueText`で見えない文字を置き換える。
画像は図の参照`<name>.drawio`だけを無害化のスキーマで通し、それ以外の画像のURLは描かない。
`src/components/markdown/Markdown.test.tsx`が、次のものを描かないことを固定している。
生のHTML、外のリンク、別のリポジトリのリンク、`javascript:`のリンク、外の画像である。

### 監査レポートの本文

新しいConsoleの監査レポートの本文(`console/src/screens/reports/AuditMarkdown.tsx`)は、リンクを張らない。
本文は、監査のClaudeが信頼できない運用記録から書くためである。
監査レポートの本文にはURLを書かない決まりで、リポジトリの情報も渡されないので、張ってよいリンクが無い。
同じページの見出しへのリンクも張らない。
見出しに`id`を付けないので、行き先が無い。

リンクの文字はそのまま文字で出し、URLが文字と違うときは括弧で添える。
添えたURLは`<bdi>`で包む。
画像は読み込まず、「画像は表示しません」と出す。
外のURLを読み込むと、レポートを開いただけで外へ通信が出るためである。
本文の生のHTMLは、`rehype-raw`を使わないので要素にならず、描かずに捨てる。
`rehype-sanitize`の既定のスキーマは、変換後の要素と属性を絞る二重の防御である。
描く前に`displayableIssueText`で見えない文字を置き換える。

## 更新履歴のPR

Consoleの更新履歴は、反映に含まれるPRの題名と番号を出す。
FactoryのPRの題名は、信頼できないIssueに由来する。
題名は、マージのコミットの本文として`self_update`が読み、`deployments.pull_requests`に記録する。
そのため、記録から画面までの各段で、値の形を確かめ直す。

| 段 | 守ること |
| --- | --- |
| 取り出し | self cloneの`git log --first-parent`だけを読む。PRのブランチの中のコミットが、件名でマージのコミットを装えないようにするためである。件名`Merge pull request #<N> from <owner>/<branch>`は、親が2つ以上のコミットだけを読む |
| 取り出し | 題名は本文の1行目だけを取る。制御文字、書字方向の制御文字、幅の無い空白などの見えない書式文字、タグ文字を空白にし、200字で切る。ZWJとZWNJは、絵文字の列や一部の文字の題名が崩れるので残す。題名は表示だけに使い、承認の判断には使わない。この処理は`sanitizePullRequestTitle`で、読み出しでも同じものを通す |
| 取り出し | リンクは、Factoryのリポジトリから`https://github.com/<owner>/<repo>/pull/<N>`の形に組み立てる。GitHubのAPIは呼ばない。呼ぶと、Console用のworkerのネットワークとトークンの権限が広がる |
| 読み出し | `console_query`が、番号が正の整数であること、URLがPRのURLの形であること、題名を`sanitizePullRequestTitle`でもう一度通す(取り出しと同じ文字を空白にし、200字で切る)。形が違う要素は捨てる |
| 画面 | 題名は文字としてだけ描く。リンクにするのは、GitHubのPRのURLの形で、末尾の番号がPRの番号と一致するものだけである。それ以外は番号を文字で出す |

作り手のバッジは、確かな証明ではなく、ブランチの名前から決めた印である。
ownerがFactoryのリポジトリと同じで、ブランチが実装ブランチ(`factory/issue-<N>-wi-<id>`)のときだけ「Software Factory」にする。
同じ名前のブランチを作れるのは、リポジトリに書ける人だけである。
forkのブランチは「人」になる。
マージの方式がsquashのPRと、Factoryのリポジトリを読めないときは、ブランチが確かめられないので「不明」にする。

mainに直接pushされたコミットも、件名の末尾が`(#<N>)`で親が1つなら、PRとして記録される。
記録は表示のための印で、PRの実在は確かめない。
mainのrulesetが直接pushを止めていることを前提にする。
