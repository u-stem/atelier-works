# Consoleの作業項目と投入の画面の仕様

Consoleの分析、作業項目、作業項目の詳細、新規投入、PRレビューの投入の画面の仕様を書く。
作業項目と投入の画面を変更する人が読む。
画面をまたぐ仕様と、ほかの画面の仕様の置き場は、[Consoleの仕様](../console.md)にある。

## 分析の画面

レポートの画面の分析のタブに、分析の区画を置く。
区画は部品`AnalyticsReports`で、画面の見出しと余白は持たない。
部品は、期間、期間を変える関数、3つの取得の結果を受け取り、描画だけを受け持つ。
Claudeの実行のコスト、承認の統計、リードタイムを、グラフと表で出す。
監査レポートと同じ画面のタブなので、期間と3つの取得はレポートの画面が持つ。

3つの数値は、`console_query`の`agent_cost_daily`、`approval_stats`、`lead_time`viewから、別々に取る。
集計の期間は直近7日、30日、90日から選び、初期値は30日である。
期間はキャッシュのキーに含めるので、切り替えている間に別の期間の値は出ない。
定期には取り直さない。
取得から60秒を過ぎた値は、タブに戻ったときと画面を開き直したときに取り直す。
分析の取得と期間は、レポートの画面が持つ。
見出しの更新のボタンは、監査の一覧と合わせた4つを取り直す。
行数の上限は2000件で、backendが受け付ける最大にしてある。
行数が上限に届いたときは、古い日が含まれていない可能性を区画に添える。

区画は、次の数値を出す。

- 日別コスト(USD)と日別の実行件数。
  段階とモデルをまとめた日ごとの合計で、費用が記録されていない行は0として足す
- 一発承認率。
  1回目の判断のうち承認の割合で、承認か却下の判断が1件も無いときは「データなし」にする
- 差し戻し分布。
  試行ごとの却下件数
- 状態別の平均リードタイムと件数。
  平均の長い順に並べ、状態は日本語にする

日別のグラフは、横軸に期間の全日を等間隔に並べる。
間隔を日数に比例させ、空いた日があることを読めるようにするためである。
実行の無い日は値0で、棒を描かない。
0より大きい日は、最大との差が大きくても最小の高さを確保する。
表は、実行のあった日だけを出す。
行数が上限に届いたときは、古い日が切れている。
取れた最古の日より前は0で補わず、最古の日そのものもグラフから外す。
最古の日は、段階とモデルの行が途中で切れて、合計が実際より小さい可能性があるためである。

日は、viewが日本時間の0時で丸めた時刻を、日本時間の日付として読む。
丸めはviewが時刻帯を指定して行うので、DBの接続の時刻帯の設定に左右されない。
画面のほかの時刻と、日次の予算の集計と同じ日本時間の日である。
日本時間は夏時間を持たないので、受け取った時刻に9時間を足してUTCの日付として読む。
端末のタイムゾーンで読み替えると、日がずれるためである。
表の日付は`2026-10-08`の形、グラフの横軸は`10/8`の形で出す。

グラフは自前のSVGで描き、グラフのライブラリを使わない。
色は固定のクラスで決め、棒の座標だけを計算する。
実行時の入力から色やstyleを作らないためである。
グラフは題だけを読み上げの対象にし、数値は必ず添える表で読ませる。
日のような連続する並びのグラフは、置かれた領域の幅を測って合わせる。
文字の大きさは変えず、棒の間隔だけが広がる。
状態のような別々の項目のグラフは、項目が少なく、広げると棒が離れすぎるので、幅の上限を置く。
棒の上の値と横軸のラベルは、文字の幅の見積もりが1本分の幅に収まるときだけ出す。
幅は、半角を文字の大きさの0.6倍、それ以外を1倍として数える。
収まらないとき、日のような連続する並びは、横軸のラベルを間引く。
間引くときは最後の棒を基準にして、いちばん読みたい最新の日にラベルを残す。
ラベルが描画領域の端を越えるときは、その端に寄せて置き、はみ出して切れないようにする。
状態のような別々の項目は、間引くと棒が何か分からなくなるので、横軸のラベルを出さず、表で読ませる。
最大の棒の上には、値のラベルの置き場を残す。
座標、幅、ラベルの収まりは`src/lib/barChart.ts`、集計、日の補完、整形は`src/lib/analytics.ts`の純関数が決める。
期間の終わりは、端末の時計の日本時間の日にする。
期間の前後3日以内の日に行があるときは、その日まで範囲を広げて含める。
端末の時計がbackendと少しずれても、行を捨てないためである。
それより遠い日は並べない。
遠い日付の行が1件あるだけで、並べる日数が際限なく増えるのを防ぐためである。
グラフに渡す系列は、純関数`chartSeries`が表と別に作る。
数値の表は、スクロールする領域に名前を付けて、キーボードで焦点を当てられるようにする。

3つの区画は、取得中、失敗、空、値ありを区別して出す。
取得中は値がまだ無いので、空の表示を出さず、読み込み中の枠を出す。
失敗は、401を除いて区画の中に原因と再取得のボタンを出す。
401は画面上部のバナーが知らせる。
再取得に失敗しても前回の値があるときは、空であっても、値を出したまま、古いことと「もう一度取得する」を添える。

3つのviewの型は、backendの同名の行に合わせてある。
`tests/scripts/console_analytics_contract.test.ts`が、backendの変換結果が型ガードを通ることを確かめる。
あわせて、日が日本時間の日付として読めることと、migrationの反映前のviewの値(UTCの0時)も同じ日付として読めることを確かめる。

## 作業項目の画面

この画面は、進捗と要件定義の2つのタブを持つ。
最終更新と更新のボタンは、画面の見出しの右側に置く。
更新のボタンは、進捗と要件定義の取得を取り直す。
新規投入のボタンとPRレビューの投入のボタンは、同じ見出しの右端に並べる。
新規投入のボタンは、[新規投入の画面](#新規投入の画面)を開く。
PRレビューの投入のボタンは、[PRレビューの投入の画面](#prレビューの投入の画面)を開く。

### タブ

開くタブと本体の見せ方は、[タブ](../console.md#タブ)の規則に従う。
要件定義のタブの名前には、取得した件数を添える。
絞り込み、並び替え、ページ、要件定義の番号の絞り込みを、タブを往復しても保つ。
作業項目の詳細のタブは、本体が1つで、中身を切り替える。

### 進捗

進捗は、`console_query`の`pipeline`viewから、直近90日に更新された作業項目を新しい順に500件まで取る。
自動では取り直さず、見出しの更新で取り直す。
取得が500件に達したときは、古い行を取得できていない場合があると本体の先頭に添える。
取得の失敗は、表の位置に再試行のボタン付きで出す。
ログイン切れ(401)は、上のバナーが知らせる。

要対応の画面への案内は、本体に置かない。
サイドバーの要対応のバッジが、同じ件数を出すためである。
失敗や人の対応待ちの作業項目は、進行中に含めず、要対応の画面で扱う。

### 表示する範囲

表に出す範囲は、状態の絞り込みとは別の欄で持ち、切り替えで選ぶ。
既定は進行中である。
範囲はURLの`?scope=`に持つ。
値は`pr_open`(PR待ち)と`all`(すべて)で、既定の進行中は付けない。
不正な値は進行中にする。
`?tab=`と同じく、選び直しても履歴を積まず、他のクエリを残す。
パンくずや戻る操作で作業項目の画面へ戻ったときに、選んだ範囲が保たれるためである。

| 範囲 | 出す行 |
| --- | --- |
| 進行中 | 終端でない状態の行と、`blocked`と`approved`の行 |
| PR待ち | 状態が`pr_open`の行 |
| すべて | 取得したすべての行 |

終端の状態は、backendの`TERMINAL_WORK_ITEM_STATUSES`と同じ一覧を`src/lib/pipelineView.ts`に持つ。
一致は`tests/scripts/console_pipeline_contract.test.ts`が確かめる。
終端のうち、失敗、人の対応待ち、期限切れは要対応に載るので、進行中に含めない。
`blocked`は要対応に載らず、ここでしか見えないので、進行中に含める。
`approved`は、実装を有効にしていない間、承認された要件定義が次の工程へ進まずに残る状態である。
要対応とPR待ちのどちらにも出ないので、進行中に含める。
backendが先に足した知らない状態は、終端でないものとして進行中に含める。
PR待ちは、PRを作った後の状態を指す。
一覧の行にマージ済みかどうかの情報が無いので、マージ待ちの目安であると画面に断る。

状態の選択肢は、範囲で絞った後の行から作る。
選んだ状態が範囲の外になる選び方をしたときは、範囲を「すべて」に替える。
範囲の外の状態で絞ると、行が出ないためである。
再読み込みで範囲の中の行から状態が消えたときは、状態の選択を「すべて」に戻す。
範囲は照合せず、そのまま引き継ぐ。
サイドバーやパンくずからの遷移で、URLの範囲が替わったときも、新しい範囲の外になった状態の選択を外し、先頭のページへ戻る。
「条件を消す」は、状態、リポジトリ、検索を消し、範囲は変えない。
範囲は条件でなく表の見方だからである。
範囲だけが既定と違うときは、絞り込みが効いているものとして数えない。

進行中の行が0件で、取得した行があるときは、「進行中の作業項目はありません」と「すべて(N件)を表示」のボタンを出す。
空の画面だけを見せると、行があるのに無いと読めるためである。
PR待ちが0件のときも、同じ形で出す。
取得が上限に達しているときは、古い進行中の作業項目が表に出ていない場合があると、空の文に添える。
取得は新しい順に上限まで読み、範囲で絞るのはその後なので、取得できなかった古い行に進行中のものが含まれうるためである。

範囲の中に行があり、絞り込みの結果が0件のときは、「条件に合う作業項目はありません」を出す。
範囲の外に条件へ当たる行があるときは、「すべてで探す(N件)」のボタンを添える。
進行中の範囲で探した語が、終わった作業項目にだけ当たることがあるためである。
Nは、範囲の外にある、状態、リポジトリ、検索の条件に当たる行の数である。

リポジトリが1つだけのときは、表とカードのリポジトリ名と、リポジトリの絞り込みを出さない。
全行で同じ名前が並ぶだけだからである。
2つ以上あるときに出す。
リポジトリの選択肢は、範囲に関わらず取得した全行から作る。
リポジトリの列が無いときは、リポジトリで並べた状態を既定の並び(更新が新しい順)に戻す。
列が無いと見出しを押せず、並びを戻す手段が見えないためである。

表は1行が1つの作業項目で、次の列を持つ。

| 列 | 内容 |
| --- | --- |
| 作業項目 | 番号。作業項目の詳細へのリンク |
| 題名 | Issueの題名。無ければ「-」 |
| 種別 | Issue、PRレビュー、PRの修正、監査、dependabotの更新、調査 |
| 状態 | 日本語の名前のバッジ。知らない状態は「不明な状態(生の値)」と書く。色は承認待ちが警告、完了に近いものが成功、失敗と人の対応待ちが失敗、それ以外は枠の無い灰色 |
| リポジトリ | owner/repo。リポジトリが2つ以上のときだけ出す |
| Issue/PR | IssueとPRへのGitHubのリンク。両方あるときは縦に並べる |
| ブランチ | 実装用のブランチ |
| 試行 | 要件定義の試行の番号。却下や再実行による作り直しで増える |
| 修正回数 | PRの修正のラウンド数 |
| 更新 | 相対時刻。日本時間の絶対時刻をツールチップに添える |
| 書類 | 要件定義書へのリンク。Issueの作業項目だけに出す |

色だけに頼らず、状態の名前を隣に出す。

題名の列には最小幅を与え、1行に数文字で折り返して行が縦に伸びるのを防ぐ。
最小幅は、表のセルでなくセルの中身に与える。
表のセルへの最小幅は、効き方が仕様で定まっていないためである。
ブランチの列にも最小幅を与え、列が戻った直後に文字が何行にも折り返すのを防ぐ。
表を包む領域が88rem(1408px)に満たないときは、ブランチ、試行、修正回数の列を隠し、題名、状態、更新を先に確保する。
全列を出したときの表の最小幅は、実測で約87.5remだった。
測った条件は、実データでリポジトリ名が約20文字である。
88remは、これに余裕を足した値である。
閾値が実測より低いと、列が戻った直後に横スクロールが出る。
リポジトリ名がさらに長いと、88remでも横スクロールになることがある。
幅は画面でなく領域で測る。
サイドバーを開閉すると表の使える幅が変わるためである。
本文の幅は、画面が1920pxでサイドバーが開いているとき約1598px(約99.9rem)で、全列を出す。
画面が1440pxのときは、サイドバーが開いていても畳んでいても本文が88remに満たず、3列を隠す。
隠した列も検索の対象に残る。
ブランチの語で絞り込むと、列が見えなくても当たる行が残る。
隠れた列の見出しは押せないが、その列で並べた順は残る。
灰色のバッジは、枠を持たず、主の文字色を薄く重ねた地に主の文字色を載せる。

絞り込みは、状態、リポジトリ、検索の3つで、範囲の中の行から、すべてに当たる行を残す。
状態とリポジトリの選択肢は、取得した行にあるものだけを並べる。
状態は作業の進む順、リポジトリは名前順である。
状態の選択肢も、バッジと同じ表記にする。
検索は、空白で区切った語がすべて当たる行を残し、大文字小文字を区別しない。
対象は、番号、題名、ブランチ、リポジトリ、IssueとPRの番号、状態と種別の日本語名である。
件数は、範囲に入る絞り込み後の行の数で、取得した件数と違うときは全体の件数を添える。
絞り込みが1つでも効いているときは、「条件を消す」ボタンを出す。

並び替えは、番号、状態、リポジトリ、試行、修正回数、更新の見出しを押して行う。
既定は、更新が新しい順である。
同じ列をもう一度押すと向きを反転し、別の列を押すと、数と時刻は大きい方から、状態とリポジトリは先頭から始める。
状態は作業の進む順に並べる。
知らない状態は、向きを変えても最後に置く。
並びが同じ行は、番号が大きい方を先にする。
向きを反転しても、同点の順は変わらない。
選んだ状態やリポジトリが再読み込みで表から消えたときは、その条件だけを「すべて」に戻す。
範囲だけをURLに持つ。
状態、リポジトリ、検索、並び替えは画面の中だけに持ち、URLには持たない。

題名とブランチは信頼できない文字列なので、見えない文字と書字方向の制御文字を落としてから、文字として描く。
リンクは、GitHubのIssueかPRのURLの形のときだけ張る。
IssueのURLが壊れているときは、Issueのリンクだけを出さず、PRのリンクは残す。
絞り込み、並び替え、リンクの規則は`src/lib/pipelineView.ts`の純関数にある。

行の番号は`/console/items/:id`へ、「要件定義」は`/console/items/:id/requirements`へ移る。

進捗の節の幅が狭いとき(56rem未満)は、横にスクロールする表の代わりに、1件を1枚のカードで出す。
画面の幅ではなく節の幅で切り替えるのは、サイドバーが幅を取る分を数えるためである。
カードに出すのは、番号、題名、状態、種別、リポジトリ(2つ以上あるとき)、Issue/PR、PR、更新、要件定義へのリンクである。
ブランチと回数は、詳細の画面で読めるので出さない。
絞り込みは表と同じ操作で行う。
並びは表の並び替えによらず、常に更新が新しい順にする。
カードには並び替えの操作を置かない。

絞り込んだ行は25件ずつのページに分け、表とカードは同じページ番号を共有する([ページ送り](../console.md#ページ送り))。
表のページは選んだ並びで区切る。
カードのページは、表の並びによらず、更新が新しい順に並べた行を同じページ番号で区切る。
表を状態の順に並べ替えても、カードの1ページ目は更新が新しい順の先頭の25件である。
範囲、状態、リポジトリ、検索の文字、並び替えのどれを変えても、先頭のページへ戻る。
ページ送りは表とカードの外側に1つ置く。
「N件(全M件)」は、ページに分ける前の絞り込み後の件数と、取得した件数を指す。
取得は500件までで、ページ送りはこの500件を分けるだけである。

## 作業項目の詳細の画面

作業項目1件の概要と履歴を、読み取り専用で出す。
再実行や承認などの書き込みは置かない。
止まった作業項目の再実行は、要対応の画面で行う。
要対応の失敗の詳細と、進捗の表の行の番号から、この画面へ移る。

取得は`console_query`の`work_item_detail`で、作業項目の番号を渡す。
応答は`src/api/guards/workItemDetail.ts`の型ガードを通す。
形が崩れた応答は、一部だけを使わず、全体を`invalid_response`にする。
backendの型との一致は、`tests/scripts/console_item_detail_contract.test.ts`が確かめる。
周期では取り直さず、キャッシュは30秒で古くなる。
進めているflowのジョブが終わったときに1回、見出しの更新のボタンでも取り直す。
取り直しの条件は[進行](#進行)にある。

存在しない作業項目の番号は、backendが「作業項目が無い」という文のジョブの失敗で返す。
Consoleは、接頭辞(`console_query:`)と要求した番号まで合わせてその文を見分け、取得の失敗ではなく「見つかりませんでした」を出す。
実機のWindmillが返す失敗の本文がこの文のままかは、確かめていない。
違えば、汎用の取得失敗の表示になる。
番号が正の整数でないときは、取得せずにその旨を出す。

### タブ(作業項目の詳細の画面)

開くタブはURLの`?tab=<名前>`に持つ。
名前が無いか知らない名前なら、概要を開く。
名前は、概要が`overview`、要件定義が`requirements`、設計が`design`、ラウンドが`rounds`、承認の履歴が`approvals`である。
タブは矢印キーとHome、Endで移れる。
Alt、Ctrl、Metaを押している間は、ブラウザの操作を奪わないよう移らない。

| タブ | 内容 |
| --- | --- |
| 概要 | 状態と注記、リポジトリ、IssueとPRへのリンク、ブランチ、試行、修正回数、実行の費用、作成と更新の時刻。続けて進行、失敗の記録、状態の遷移。種別は見出しの副題が示すので、行には置かない。タブの名前と重なる見出しは置かない |
| 要件定義 | 試行ごとの要約、承認の状態、要件定義書の画面へのリンク。Issue以外の作業項目には要件定義が無いと伝える |
| 設計 | 設計書ごとの名前、要約、承認の状態、設計書の画面へのリンク。設計書が無いときと、Issue以外の作業項目では、その旨の文だけを出す |
| ラウンド | 実装のラウンドを試行ごとに古い順で、PRのレビューとPRの修正を新しい順で並べる。レビューと修正が無いときは、見出しと一文の1行にする |
| 承認の履歴 | 承認依頼を新しい順に並べ、状態、依頼と決定の時刻、決定者、理由を出す |

承認の履歴は、却下の理由と決定者を読む場所である。
要件定義の承認依頼は対象の試行を、設計の承認依頼は設計書の名前を、Issue提案は提案の題名を添える。
理由や決定者が記録されていないときは、そう書く。

失敗の記録は、フローとステップ、時刻、失敗の文を新しい順に出す。
失敗の文はbackendが4000文字で切るので、その長さに達したときは切っていると添える。
状態の遷移は、遷移前後の状態、注記、時刻を新しい順に出す。
概要に出す状態の注記は、今の状態へ移った最新の記録の注記である。
ただし、状態を変えない次の3つの記録は読み飛ばす。
取り込み内容の更新、自動の再開の停滞、承認の判断を反映する処理の起動し直し(`approval handler restarted for request N`)である。
読み飛ばさないと、状態の理由が、状態が変わらない記録の注記に置き換わるためである。
要件定義書へのリンクは、同じ書類を指すものが重ならないよう、試行ごとに1つだけ置く。
最新の試行のリンクは試行の番号を付けず、常に最新の書類を指す。
実装のラウンドは、差分の規模をファイル数、追加の行数、削除の行数の言葉で出す。
ラウンドのタブは、PRのレビューと修正の本文を持たず、件数と結果だけを出す。
PR修正の結果は、表示名で出す。
完了、要件の不足、設計の不足、ブロックの4つである。
設計の不足は、実装のラウンドと同じ文言と、警告の色で出す。
人の対応を促す点が、要件の不足と同じためである。
知らない結果は「不明(生の値)」と出し、色は付けない。
実装のラウンドは、検査コマンドの出力を持たない。

backendは、履歴を新しい順に切って返す。
上限は、失敗が20件、状態の遷移が100件、PRのレビューと修正がそれぞれ50件である。
件数が上限に届いた履歴には、新しい順に何件まで表示していて、それより古い記録は表示していないと添える。
上限の値は`src/lib/itemDetailView.ts`の`DETAIL_LIMITS`にあり、`console_query`の上限に合わせる。

### 進行

概要のタブに、いま進めているflowの図を出し、ジョブのステップの状態を重ねる。
図は[flowの図の画面](graphs.md#flowの図の画面)と同じ部品(`src/screens/jobs/FlowDiagram.tsx`の`FlowDiagramFrame`)で描く。
実行中のステップの強調と、状態の語は、[実行の状態](graphs.md#実行の状態)にある。
作業項目が通るflowの全体の経路は、図にしない。
次のflowへは、図の出口(狭い幅の一覧では入口も)にあるflowの図へのリンクで移る。
図は、入口の列と、設定や試行の上限による注記、まだ起動されない入口の注記を出さない。
作業項目の詳細は、いま動いている流れを読む場所で、入口と起動の条件は、そのflowの図の画面で読むためである。

見出しには、flow名(「<flow名>のステップ」)、ジョブの状態、ジョブの詳細へのリンク、前の値の印を置く。
図のノードは、子のジョブの詳細と、次のflowの図へ移る。
動いていないflowの履歴は他の作業項目も含むので、1件の作業項目の図からは履歴へ移らせない。

読むジョブは、概要の`flow_job_id`が指す1件である。
`flow_job_id`は、作業項目の行が持つ、いま進めているflowのジョブのidで、無ければ`null`にする。
`null`のときは、進行の節ごと出さない。

進行を出すのは、ジョブが実行中、待ち、失敗、取消のときに限る。
成功かスキップで終わったジョブは、ステップがすべて成功か飛ばしたものなので、何も出さない。
承認待ちのようにflowが終わった作業項目の判断は、受信箱で行う。
失敗と取消は、止まったステップを示すので出す。

見出しのジョブの状態は、図に実行中のステップがあるときは置かない。
図のノードが同じことを言うためである。
図が出ないときと、失敗か取消のとき、ステップがまだ無いとき、待ちのステップだけのときは置く。

同梱のflowのデータに、そのflowが無いときと、データを読めなかったときは、図を描けない。
ジョブの詳細と同じステップの一覧(`StepList`)に替える。
ステップが無ければ「ステップはまだありません。」を出す。
ステップの語は、どちらも同じ関数(`stepStateInfo`)で決める。

図の見せ方は、図を包む要素の実際の幅から、[flowの図の画面の幅](graphs.md#幅)と同じ規則で選ぶ。
入口の列が無いので、図の幅はその分狭い。
本文の幅が760pxのとき、図をそのまま出すflowは、audit、dependabot、manual_intake、pr_reviewである。
pipeline、pr_fix、design、implementは、横にスクロールする枠で出す。
`src/lib/flowDiagram.test.ts`が、実際のflowごとの見せ方を固定する。
スクロールする枠は、開いたとき、実行中か失敗したステップが見える位置へ寄せる。
そのステップが動かない間は、利用者が動かしたスクロールを戻さない。
幅を測る前は、図と一覧のどちらも描かず、見出しだけを出す。

作業項目の状態では止めない。
承認待ちのようにflowが終わった状態でも、ジョブが実行中か待ちなら、ジョブの状態で追う。
取得は、`console_jobs`の`detail`を、`include_output`を偽にして読む。
ジョブの詳細の画面が状態だけを読む取得と、キャッシュを分け合う。
次の3つがそろうあいだ、ジョブが実行中か待ちなら15秒ごとに取り直す。

- 選んでいるタブが概要である
- 文書が見えている
- 画面が15分以内に操作された

終了したジョブの詳細は変わらないので、古くならない。
概要を開き直しても取り直さない。
開き直すたびに読むと、見ていない進行のために、Windmillのジョブが増えるためである。
実行中の強調は実行中のジョブのflowだけにして、終わったジョブのflowは強調しない。

ジョブが実行中か待ちから終了へ変わったら、`work_item_detail`を1回だけ取り直す。
flowが次のflowへ作業項目を引き継ぐと、`flow_job_id`が変わるので、取り直すと新しいジョブに追従できる。
画面を開いた時点で終わっていたジョブは、作業項目の詳細と同じ時点の値なので、取り直しの合図にしない。
画面に出していない詳細は、取り直さない。

追従するのは、画面が実行中か待ちのジョブを見ている間に、そのジョブが終わった場合だけである。
承認と再実行は、画面の外で別のflowを起動する。
開いたままの画面は、この2つの後に新しいflowへ追従しない。
承認や再実行の後は、見出しの更新のボタンで取り直す。

見出しの更新のボタンは、作業項目の詳細を取ってから、ジョブの詳細を取る。
Console用workerの枠が1つなので、2つを重ねない。
ジョブは、取り直した作業項目の`flow_job_id`で読む。
引き継ぎの後に、古いジョブを読まないためである。
最終更新には、2つの取得の古い方の時刻を出す。
概要以外のタブでは、ジョブの詳細を読まず、最終更新にも数えない。
画面に出さない進行のために、Windmillのジョブを増やさないためである。

ジョブの詳細が見つからないときは、進行を出さない。
概要は別の取得なので残る。
見つからないとは、応答の`found`が偽のことである。
ジョブの詳細の取得が失敗したときは、読めている前の値があれば「前の値(取得に失敗)」を添える。
印は、見出しの横に1か所置く。
図のステップの状態も前の値のまま出るためである。
前の値が無いか、前回が見つからなかったときは、「進行を読めませんでした」を出す。
この失敗は進行の節が伝えるので、見出しの失敗には数えない。
ログイン切れ(401)は、上のバナーが知らせる。

flowの名前、ステップのid、図のノードの名前、定義に無いステップは、サーバー由来の文字列と同じく`safeText`を通して描く。
`tests/scripts/console_jobs_render_contract.test.ts`が、進行の部品(`ItemFlowProgress.tsx`)のソースを走査する。

### ジョブのリンク

失敗と遷移のジョブは、`JobLink`でConsoleのジョブの詳細へ移る。
意味が違うので、文言を分ける。

| 行 | `job_id`のリンク | `root_job_id`のリンク |
| --- | --- | --- |
| 状態の遷移 | ステップのジョブ(遷移を起こしたステップ) | フローのジョブ(そのステップを含むフローのルート) |
| 失敗の記録 | 失敗したジョブ(記録に渡されたジョブ。フローの失敗ではフローのルート) | 記録したジョブのフロー(記録したジョブのルート) |

2つが同じジョブなら、リンクは1つにする。
Windmillの画面への副次のリンクは、ジョブの詳細の画面が持つ。

### 表示の規則

題名、ブランチ、状態の注記、要約、却下の理由、決定者、失敗の文は、起票者や実行ログに由来する。
見えない文字と書字方向の制御文字を置き換えてから、プレーンテキストとして描く。
状態の注記が、その作業項目のIssueかPRのURLだけのときは出さない。
同じリンクが「Issue」「PR」の行にあるためである。
別のURLだけの注記は、どの行にも出ていないので残す。
状態の遷移の注記は、URLだけでも出す。
PRを作り直したとき、古いPRを示す唯一の記録になるためである。
実装のラウンドの要約と、要件の不足の報告は、バッククォートで囲んだ範囲をコードの書式で描く。
Markdownは解析せず、囲み以外の文字は記号も含めてそのまま出す。
HTMLとして読む経路が無いためである。
二重のバッククォートの囲みは扱わず、記号の位置がずれることはあっても文字は失われない。
GitHubのリンクは、IssueかPRのURLの形のときだけ張る。
形が違えば、番号だけを文字で出す。
PRのURLが使えないときは、リポジトリとPRの番号から組み立てた同じ形のURLを使う。
作業項目の状態、ラウンドの種類と結果、レビューの判定、修正の結果が表に無いときは、「不明」に生の値を添える。
承認依頼の状態など、ほかの値は「不明な状態」などの決まった文言にする。
知らない値でも詳細の全体が消えないようにして、backendが先に新しい値を反映した間も読めるようにするためである。
表示の規則は`src/lib/itemDetailView.ts`の純関数にある。

## 新規投入の画面

作業項目の一覧の見出しの右端にある「新規投入」のボタンから、`/items/new`を開く。
画面は、Issueを手動で作って工程に乗せる入力欄を持つ。
入力欄は、リポジトリ、進め方、題名、目的、受入基準(任意)である。
リポジトリは、候補から選ぶか、`オーナー名/リポジトリ名`の形で直接入力する。

候補は、`console_query`の`intake_targets`viewから、画面を開いたときに取る。
viewは、設定の`configuredRepos`(`factory_repo`と`repo_allowlist`)を`isRepoAllowed`で絞り、`{owner, repo}`の配列だけを返す。
`configuredRepos`は`owners`で絞らないので、選ぶと必ず断られる候補を出さないよう、ここで絞る。
設定の他の値は返さない。
DBは読まない。
候補を取得できなかったときも、リポジトリは直接入力できる。

送る前に分かる誤り(リポジトリの形、題名が空か256字を超える、目的が空、不具合の修正で3欄のどれかが空)は、`src/lib/manualIntake.ts`が入力欄で知らせる。
検証の本体は`manual_intake_submit`にあり、画面の判定はそれを置き換えない。
誤りで送信が止まったときと、送信中の扱いは、[部品の置き場所](../console.md#部品の置き場所)の節に書く。
送った後の断りと失敗、投入されたか分からない状態、一覧が古い警告は、`Alert`が出す。
`Alert`は`role="alert"`を持つので、出た時点で読み上げに通知される。

### 進め方の選択

進め方は、通常(`standard`)、直接(`direct`)、不具合の修正(`bugfix`)、文書の変更(`docs`)の4つから1つ選ぶ。
初期値は通常である。
選択欄は、ネイティブのラジオを`fieldset`と`legend`でまとめた`NewItemScreen`の部品で、矢印キーで選べる。
各項目は、進め方の違いを知らせる1行の説明を持つ。
名前と説明は`src/lib/manualIntake.ts`の`PROFILE_OPTIONS`にある。

通常以外を選ぶと、承認を省く。
画面は、次の2つでそれを示す。

- 送信ボタンの文言が「承認なしで投入する」になる。
  題名などの欄でEnterを押して送るときも、押す場所で承認なしと分かるようにする
- 欄の下に、PRは人がレビューしてからマージする旨の注記が出る。
  強制はされない

ラジオの上のEnterは、フォームの暗黙の送信にしない。
ラジオの`onKeyDown`で、Enterの既定の動作を止める。
矢印キーで承認を省く進め方に切り替えた直後のEnterが、確認なしに投入を送るのを防ぐためである。
矢印キー、スペース、Tabは、ラジオの選択と移動に使うので止めない。

文言、注記、止めるキーの判定は、`manualIntake.ts`の純関数(`submitLabel`、`profileNotice`、`blocksImplicitSubmit`)にある。
確認のダイアログは置かない。
誤選択は、初期値、リセット、ラジオ上のEnterの抑止、ボタンの文言、注記で抑える。

画面は、設定の`implement_enabled`を読まない。
許可、停止スイッチ、キーの判定は、すべてscript側が担う。
実装が止まっていれば、送った後に断りの文が出る。

不具合の修正を選ぶと、再現手順、期待する動作、実際の動作の3欄が出る。
3欄とも必須で、空白だけの欄は空と見なす。
`buildIntakeInput`が、3欄を次の形でscriptの`body`と`acceptance_criteria`に組み込む。
scriptの引数は増やさない。
通常以外の進め方では、3欄に値が残っていても送らず、空でも問題にしない。

- `body`は、目的、空行、`#### 再現手順`と欄の値、空行、`#### 実際の動作`と欄の値の順になる
- `acceptance_criteria`は、`#### 期待する動作`と欄の値で始まる。
  受入基準の欄に値があれば、空行の後に`#### その他の受入基準`と値が続く

Issueの本文は`### 目的`と`### 受入基準`の2節なので、組み込む見出しは4階層にして階層を壊さない。
欄の中の`#`で始まる行は、投入者本人の内容なので、そのまま残す。
欄の値は、見出しとして信頼しない。
組み立てた後の長さは測らず、scriptの`body_too_long`に任せる。

### 書き込み

`manual_intake_submit`は、tag`console`で動き、`timeout`は30秒である。
フローを非同期に起動するだけで、完了は待たない。

| 項目 | 内容 |
| --- | --- |
| 引数 | `owner`、`repo`、`title`、`body`(目的)、`acceptance_criteria`(省略時は空)、`profile`(進め方。省略時は`standard`)、`intake_key`(冪等キー。承認を省く進め方では必須) |
| 戻り値 | 断ったときは`{ refused: true, reason }`、起動したときは`{ refused: false, flow_job_id }` |

画面は、送信ごとに`intake_key`を付ける。
キーは小文字のUUIDで、形が違うと`invalid_intake_key`で断る。
画面が作るキーは常に正しい形なので、この断りの文は画面に出ない。
符号の表を網羅するために置いていて、描画されない。
キーの扱いは、[手動投入の冪等キー](../work-items.md#手動投入の冪等キー)にある。

画面は、選んだ進め方を`profile`に載せて送る。
受け付ける進め方は`standard`、`direct`、`bugfix`、`docs`で、それ以外は`profile_not_allowed`で断る。
承認を省く進め方は、`intake_key`が無いと`intake_key_required`で、実装が止まっていると`implement_disabled`で断る。
断りはフローを起動する前に起き、フローのステップも、Issueの作成と登録の前に同じ一覧で断る([進め方ごとの承認](../implement.md#進め方ごとの承認))。
画面は常にキーを付けるので、`intake_key_required`の断りの文は画面に出ない。
符号の表を網羅するために置いていて、描画されない。
`implement_disabled`と`profile_not_allowed`は、画面に出る。

投入の記録(`factory.console_actions`)とジョブのログには、検証を通った進め方が載る。
題名、本文、不具合の欄は載らない。

断りは、失敗ではなく結果として返す。
その場合、フローは起動せず、Issueと作業項目は作られない。
理由は固定の符号で、入力の文字列を含まない。
符号の一覧は、`f/factory/lib/manual_intake_support.ts`の`MANUAL_INTAKE_REFUSAL_REASONS`にある。
日本語の固定文は、`src/lib/intakeRefusal.ts`の表にある。
文の末尾に、何も投入していないことを添える。

投入した人は引数に取らない。
scriptが、ジョブの実行文脈から導く。
導けなければ`actor_unknown`で断る。
フローは呼び出した主体の権限で起動する。
Issueの作成、オーナーIDの照合、作業項目の登録、要件定義の工程の起動は、フロー`manual_intake`が行う。
作業項目は、登録のあとに一覧へ現れる。
投入の結果には、戻りの投入のフローのジョブのid(`flow_job_id`)から、Consoleのジョブの詳細へのリンク(「投入のジョブを開く」)を添える。
投入が通ったかは、作業項目が一覧に現れるまで分からないので、このリンクでフローが動いたか、失敗したかを読める。
ジョブのidを持たない結果(断り、ジョブが動く前の失敗)には、リンクを出さない。

### 結果が分からないとき

次の失敗は、投入されたか分からないものとして扱う。
`network`、`timeout_or_unknown`、`job_failed`、`invalid_response`と、5xxの`http`である。
フローを起動した後に、応答だけが失われている場合があるためである。
401、403、4xxは、ジョブが動く前に断られたので、投入されていないものとして扱う。

分からないときは、入力を残し、送信を止める。
画面は、確かめる場所を案内する。
確かめる場所は、Windmillのジョブ一覧(`manual_intake_submit`が待ちか実行中でないかも含む)と、対象リポジトリのIssueである。
送った題名も添える。
承認を省く進め方で送ったときは、送った進め方も添える。
進め方を変えた再送は別の投入になり、先に作られたIssueと実装が重なるためである。
操作は2つある。

- 「確かめたので再送する」は、投入されていないことを確かめたあとに押して、送信を開ける
- 「投入されていたので入力を破棄する」は、投入されていたと分かったときに押して、警告と保存した入力を消し、送信を開ける

再送を明示の操作にするのは、確かめずに送ると、Issue、作業項目、pipelineが重複しうるためである。
再送は、前の送信と同じ冪等キーを付ける。
同じタブでリロードをせず、送る値を変えずに再送したときは、最初の投入のIssueが返る。
重複は起きない。
それ以外の再送は、キーが止めないので、利用者が確かめる。
確かめる3つの案内は、残す。
キーが止める範囲は、同じタブの同じ送信だけである。

### タブ全体の状態

送信の結果と入力欄の値は、画面の部品ではなく、タブ全体で持つ状態(`intakeSession`、`src/api/intakeSession.ts`)に書く。
送信中に一覧へ移って戻っても、結果と入力を失わず、戻った画面が警告を出す。

状態は、このタブの中だけで持つ。
`sessionStorage`にも書かないので、リロードや別のタブには広がらない。
別のタブや、リロードの後の二重の送信は止められない。

冪等キーも、この状態が持つ。
送信を始めるとき、投入されたか分からない結果があり、同じ送る値で再送するなら、そのキーを引き継ぐ。
それ以外は、`crypto.randomUUID()`で新しいキーを作る。
次の場合は、キーを持ち越さない。

- 投入できた
- 断られた(scriptの断りと、ジョブが動く前の断り)
- 投入されていたので入力を破棄した
- 投入されたか分からない結果の後に、入力を変えて送った

送る値を変えて送るときは、別の投入として新しいキーを使う。
同じキーのまま内容が違うと、フローが`intake_key_conflict`で失敗し、画面ではなく通知に出るためである。
送る値は、`buildIntakeInput`が組んだ、リポジトリ、題名、本文、受入基準、進め方である。
引き継ぎの判定(`sameSentValues`)は、入力欄の値ではなく、この送る値で比べる。
通常以外の進め方では、3欄の違いは送る値に現れないので、キーを変えない。
組み立てられない入力は、送れないので「違う」とする。
一覧へ移って戻っても、投入されたか分からない結果の間は、キーが残る。

結果を画面が見せたあと、その画面を離れるときに、結果を消す。
消すのは、画面が実際に描画した結果だけである。
対象は、投入できた結果、断られた結果、ジョブが動く前に断られた結果である。
次の結果は消さない。

- 画面がまだ見せていない結果は、戻った画面で見せる
- 投入されたか分からない結果は、利用者が片付けるまで残す
- 書き込みのロックが残っているあいだの結果

投入できたときは、保存した入力を消し、題名、目的、受入基準を空にする。
リポジトリは残す。
続けて同じ宛先に投入することが多いためである。
投入の後は、作業項目の進捗(`pipeline`view)を読み直す。

## PRレビューの投入の画面

作業項目の一覧の見出しの右端にある「PRレビューの投入」のボタンか、コマンドパレットの「作業項目 › PRレビューの投入」から、`/items/new-pr-review`を開く。
画面は、既存のPRのレビューを手動で始める入力欄を持つ。
新規投入とは入力欄が違うので、別の画面にしている。
入力欄は、リポジトリと「PRの番号またはURL」の2つである。
サイドバーとタブには増やさない。

### 入力

リポジトリ欄は、候補があっても空から始める。
投入先を取り違えないためである。
候補は、新規投入と同じ`intake_targets`viewから取る。
候補に無いリポジトリも入力でき、許可の判定はscriptが行う。
候補を取得できなかったときも、リポジトリは直接入力できる。

「PRの番号またはURL」欄は、前後の空白を除いたうえで、次の形を受ける。

- 数字だけ。
  先頭の0を許し、整数として1以上の安全な整数であること
- `(https://)github.com/<オーナー>/<リポジトリ>/pull/<番号>`の形。
  `http`、`www.`、ホストとスキームの大文字小文字の違いを許す。
  番号の後ろに、`/files`などの続き、末尾の`/`、`?`で始まる続き、`#`で始まる続きが付いてよい

次の入力は受けない。
`#12`(リポジトリが分からない)、`/issues/<番号>`、`github.com`以外のホスト、ユーザー情報やポートの付いたURL、番号が0や整数でないもの、`pull`の後に番号が無いものである。

誤りは、次の順で最初の1つを入力欄に知らせる。

1. リポジトリ欄が入力済みで、形が不正
2. PR欄が空
3. PR欄が読めない
4. PR欄が数字だけなのに、リポジトリ欄が空
5. URLのリポジトリが、入力済みのリポジトリ欄と、大文字小文字を無視して食い違う

URLでリポジトリ欄が空なら、URLのリポジトリを使う。
リポジトリ欄と一致するときは、欄の値を送る。
検証は`src/lib/prReviewInput.ts`の`buildPrReviewInput`にあり、画面の判定は投入の入口と登録のステップの断りを置き換えない。
PRの番号の範囲は、登録のステップの判定(正の安全な整数)と同じにしてある。
`tests/scripts/console_pr_review_input_contract.test.ts`が、同じ入力の列で突き合わせる。

### 書き込み(PRレビューの投入の画面)

画面は、送信を`useWriteMutation`と`prReviewConfig`(`src/api/prReviewConfig.ts`)に載せ、`submitPrReview`を呼ぶ。
ロックのキー(`PR_REVIEW_WRITE_KEY`)は1つに固定する。
冪等キーは使わない。
同じPRの二重の投入は、入口の`already_reviewing`と、登録のステップの一意インデックスが断る。

投入の直後に読み直す取得は無い。
作業項目は登録のステップが後で作るので、直後に読み直しても変わらず、Console用workerの枠を結果の取得と取り合うためである。
そのため`invalidates`は空で、一覧が古いままで止める場面は無く、`onStale`は何もしない。

入力と結果は、画面の中の状態に持つ。
タブ全体の状態(`intakeSession`)には載せないので、画面を離れると結果を失う。
失うのは知らせだけで、重複は起きない。
送信中に離れて戻ったときも、結果の表示は無く、送信ボタンは黙って元に戻る。
投入されたかは、作業項目の一覧とジョブの一覧から確かめられる。
送信中は、共有のロックから送信ボタンを無効にし、文言を投入の最中と分かる語に替える。
送信中に画面を離れて戻っても、ロックが残るので、ボタンは理由なく無効にならない。

送信ボタンの文言は「レビューを投入する」である。
PRへのレビューの投稿が始まる操作と分かる文にする。
確認のダイアログは置かない。

### 同期の結果

入口の結果は4つある。
文は`src/lib/prReviewOutcome.ts`にある。

| 結果 | 表示 |
| --- | --- |
| 入口が断った(6符号) | 見出し「投入できませんでした」と固定文。何も投入していないことは、見出しが伝える |
| 結果が分かる失敗(403、4xx) | 「投入できませんでした」と、書き込みの失敗の文 |
| 投入されたか分からない失敗(通信断、5xx、ジョブの失敗、形の違う応答、待ちの上限) | 「投入されたか分かりません」と、確かめる場所。再送は止めない |
| 起動した | 投入したフローのジョブの結果を読む |

再送を止めないのは、同じPRで稼働中のレビューがあれば再送が断られ、その間は二重に始まらないためである。
前のレビューが終わった後の再送は、新しいレビューを始める。
そのため案内は、作業項目の一覧とジョブの一覧で確かめてから再送するよう促す。
起動したときは、結果を受け取った時点から次の投入を止める。
結果の部品が描かれるまでの間にも、送れないようにするためである。
起動した結果に`action_audit`が`failed`とあるときは、他の書き込みと同じ「操作の記録を残せませんでした」の注意を添える。
トーストは出さない。

結果の知らせのうち、待っているときと始まったときは、読み上げの`role="status"`で伝える。
失敗と断りは`role="alert"`のままにする。
入口の結果の知らせ(`PrReviewAttemptNotice`)も`Alert`で、`role="alert"`で通知される。
誤りで送信が止まったときと、送信中の扱いは、[部品の置き場所](../console.md#部品の置き場所)の節に書く。
入力欄の補足と誤りの文は、共有の`Field`([部品の置き場所](../console.md#部品の置き場所)の節)が、入力の`aria-describedby`に結ぶ。

### 結果の読み方

起動に成功したら、`flow_job_id`があるときだけ描く部品が、`useJobDetail`でそのジョブの結果を読む。
フローの結果は、登録のステップの戻りである。
待つのは1件のジョブだけで、ジョブが終われば取り直しを止める。
画面を離れたら待たない。

状態は、上の行から順に評価する(`src/lib/prReviewResult.ts`)。
ジョブの状態は、結果つきの取得と状態の取得のうち新しい方から取る。
終わった状態から実行中へは戻さない。

| 順 | 条件 | 表示 |
| --- | --- | --- |
| 1 | 結果つきの取得が失敗した(最初の取得も、取り直しも) | 見出し「結果を取得できません」とジョブへのリンクと「もう一度取得する」 |
| 2 | 結果の取得にサーバーが失敗を付けた | 行1と同じ |
| 3 | ジョブが見つからない、結果が切り詰められたか伏せられた、JSONでない、登録の結果の形でない、ジョブが失敗か取り消しか飛ばされた、終わっているのに結果が無い | 「結果を読み取れません。ジョブを開いて確認してください」とジョブへのリンク |
| 4 | 結果が出る前で、状態の取得が失敗した、状態の取得でジョブが見つからない、ジョブが予定か知らない状態である | 行1と同じ |
| 5 | 最初の取得が終わっていない、ジョブが実行中か待ちである、状態の取得が終わりを見たが結果つきの取得が古い | 「結果を待っています」とジョブへのリンク |
| 6 | 成功して、レビューが始まった | 「レビューを始めました」と作業項目へのリンク |
| 7 | 成功して、登録のステップが断った | 断りの固定文 |

行4は、待っても終わらない状態である。
状態の取得は、ジョブが実行中か待ちの間だけ繰り返すので、失敗したままのとき、ジョブが見つからないとき、予定か知らない状態のときは、繰り返しが止まる。
このときは待たず、取得できない状態として取り直しの操作を出す。
取り直しの操作は、失敗した取得を、結果つきを先にして1つずつ取り直す。
どちらも失敗していないときは、状態の取得を取り直す。
この操作はConsole用workerの枠を使う。
待ちを抜けられない状態を残さないほうを選ぶ。

取り直しの操作は、行1、行2、行4に出す。
読み取れない結果は、取り直しても変わらないためである。
待ちに上限は置かない。
結果を待つ間は、同じ画面の次の投入を止める。
2本目のフローが1本目の結果を上書きしないためである。
抜ける方法は、画面を離れて状態を捨てることで、これを意図した挙動としている。
レビューが始まったと分かったときは、作業項目の一覧の取得を1回だけ読み直す。
一覧が最大30秒古いままにならないためである。

### 断りの固定文

断りの符号は2か所から出る。
日本語の固定文は`src/lib/prReviewRefusal.ts`にあり、符号だけから引く。
入力の文字列を含めないので、隠れた文字が画面に出ない。

- 入口の6符号の文は、見出し「投入できませんでした」の下に出す。
  何も投入していないことは見出しが伝えるので、文には繰り返さない
- 登録のステップの8符号の文は、`already_reviewing`を除き、末尾に「フローは動きましたが、レビューは始まっていません。」を添える
- `repo_not_allowed`は2か所で意味が違うので、別の文にする。
  入口は入力したリポジトリ、登録のステップはPRの正しい名前(改名の後の名前)が許可されていない
- `invalid_pr_number`は、2か所で同じ文を使う
- `already_reviewing`は、2か所とも進行中のレビューがあることを伝え、作業項目の一覧から確認するよう促す。
  作業項目の番号を持たない断りがあるので、リンクは足さない。
  登録のステップの文は、進行中のレビューが残るので、「新しいレビューは始めていません」とだけ言い、末尾の定型文は使わない
- 登録のステップの断りのうち、`fork_head`と`owner_mismatch`は通知にも残る。
  画面の文は、ほかの断りと同じく符号から引く
