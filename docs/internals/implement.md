# 実装フロー

工程3の実装フロー(`f/factory/implement`)の内部の挙動、設定値、安全策の仕組みをまとめる。実装フローのコードを変更する人が読む。運用の手順は[運用](../operations.md)に、作業項目の状態と実装フローのリースは[作業項目](work-items.md)に書く。

## 全体の流れ

実装フローは、承認済みの要件定義から対象リポジトリに実装を書き、PRを作るところまでを受け持つ。マージは常に人が行い、FactoryはマージのAPIを呼ばない。

実装フローを起動するのは承認の反映で、`factory_config`の`implement_enabled`が有効なときだけ承認の後に起動する。設計が無効のときは要件定義の承認の反映(`requirements_apply`)が起動し、設計が有効なときは設計の承認の反映(`design_apply`)が起動する。既定は無効で、無効の間、作業項目は承認済み(`approved`)で止まる。有効化の前に、sandboxのリポジトリでe2eを確かめる。

実装フローは4つのステップでできている。

| ステップ | 名前 | 役割 |
| --- | --- | --- |
| `implement_prepare` | 準備 | 前提を確かめ、ブランチとworktreeを用意する |
| `implement_generate` | 実装 | Claudeに最初の実装を書かせる |
| `implement_verify` | 検証と修正のループ | 検査し、失敗すればClaudeに直させる |
| `implement_finish` | 完了 | PRの作成、差し戻し、停止を振り分ける |

実装と検証のステップは、準備の結果が続行(`proceed`)でなければ飛ばす。完了のステップは準備の結果を受け取り、どの場合も動く。フローが例外で失敗すると、`on_error_flow`が失敗を記録する。

defaultのworkerは同時に1つのジョブしか動かさないので、実装フロー1回の実行は、数時間worker全体を占有する。その間、ほかのジョブは待つ。実装フローの同時実行数は制限していない。

## 準備

準備のステップは、承認したときの前提がまだ成り立つかを確かめ、実装用のブランチとworktreeを用意する。

1. 作業項目がIssueの作業項目で、実装中(`implementing`)であることを確かめる。違えば何もせずに終わる。
2. 実装フローのリースを取る。取れなければ何もせずに終わる。リースの仕組みは[作業項目](work-items.md)に書く。
3. 日次予算、リポジトリの許可リスト、リポジトリのオーナーの照合、時間設定、Issueがopenかを確かめる。
   続けて、承認済みの要件定義と、そのディレクトリが基準値と合うかを確かめる。
   設計が有効なら、設計の承認が現在の状態に一致するかも確かめる。
4. ブランチのPR(閉じたものを含む)に、終わっていないPR修正かPRレビューがあれば止める。
5. worktreeを使っているプロセスを調べる。調べ方は[同時実行の防止](#同時実行の防止)に書く。
6. 実装ブランチのworktreeを`git gtr`で用意し、空のブランチをpushする。
7. worktreeの`.git`を検証して中身を記録する。
8. ブランチが既定のブランチから分かれた点(`git merge-base`)を、比較の基準(`base_sha`)として記録する。既定のブランチの先頭には、手順6でリモートと照合したshaを使う。

実装ブランチの名前は`factory/issue-<N>-wi-<work_item_id>`である。空のブランチを先にpushするのは、以後のpushをすべて既存の`commitAndPush`で行えるようにするためである。比較の基準は、後のステップで差分を測るときに使う。

空のブランチとしてpushするのは、既定のブランチの先頭のcommitだけである。
送り方は[pushする履歴の制限](#pushする履歴の制限)に書く。
pushの後は、新しく作ったworktreeも再利用の経路を通し、`origin/<branch>`へ`reset --hard`して`clean -fd`をする。

手順3と4の確認に通らないときの結果は次のとおり。どの場合もworktreeに触れない。

| 確かめること | 通らないときの結果 |
| --- | --- |
| 日次予算を超えていない | 人の対応待ち(`needs_human`) |
| リポジトリが許可リストに含まれる | 人の対応待ち |
| リポジトリのオーナーが`owners`にある(`factory_repo`を除く)。`id`があれば、現在のIDと一致する | 人の対応待ち |
| 時間設定がステップのtimeoutに収まる | 人の対応待ち |
| Issueがopenである | 取り消し(`cancelled`) |
| 作業項目の試行(attempt)に一致する承認済みの要件定義がある | 人の対応待ち |
| 承認済みの要件定義のディレクトリが、承認の前に保存した基準値と合う | 人の対応待ち |
| 設計が有効なら、設計の承認が現在の状態に一致する | 人の対応待ち |
| ブランチのPRに、終わっていないPR修正かPRレビューが無い | 人の対応待ち |

時間設定の確認は[タイムアウト](#タイムアウト)に書く。
基準値の照合は`requirementsGateReason`が行い、基準値は[要件定義の生成と承認](requirements.md)の「基準値」に書く。
基準値が無い下書きは、警告を1回ログに残して照合を飛ばす。
準備のステップは、基準値を実装の文脈(`requirements_doc_hash`)に載せ、Claudeの実行ごとの照合に渡す。
設計の承認の照合は`designGate`が行う。位置は、基準値の照合の後で、ブランチ、PR、worktreeに触れる前である。
判定の表と止まるときの理由は[設計書の生成](design.md)の「承認の照合」に書く。

準備のステップは、リポジトリのロックとfactory cloneのロックを待つ。リポジトリのロックの待ちは1回300秒で最大5回あり、ロックの待ちだけで約1800秒かかりうる。

Claudeに渡すIssueの題名、本文、URLは、取り込んだ時点の値(`work_items.title`、`body`、`issue_url`)を使う。工程2の要件定義の生成と同じ入力である。GitHubから取得した今のIssueは、openかどうかの判定と、取り込み時点のURLが空のときのURLにだけ使う。

## 実装

実装のステップ(`implement_generate`)は、`factory-implementation`スキルを使うheadless Claudeを、worktreeの上で1回実行する。

- Claudeに渡すツールは[Claudeに渡すツールの制限](#claudeに渡すツールの制限)のとおりである。
- 承認済みの要件定義のディレクトリは、実行ごとに一時ディレクトリへ複製して読ませる。
  基準値との照合は[承認済み要件定義の複製](#承認済み要件定義の複製)に書く。
- Claudeを実行する前にリースを確かめる。失っていればClaudeを実行せず、検証のループが止まる結果(`lease_lost`)を返す。
- ステップにWindmillの再試行は付けない。

Claudeの1回の実行は、`implement_timeout_sec`と、期限までの残りの短い方で打ち切る。期限は準備の開始から`implement_flow_timeout_sec`後の時刻(`ImplementContext.deadline_at`)である。

プロンプトは`f/factory/lib/prompts.ts`の`implementPrompt`と`implementFixPrompt`が作る。出力の形は`IMPLEMENT_SCHEMA`で決め、`f/factory/lib/implement_support.ts`の型ガードと検証で確かめる。出力の意味の検査は実行が成功した後にだけ行う。件名が長いといった理由だけで実装全体をやり直さないためである。

Claudeは実装中に要件や設計を書き換えてはならない。要件を満たせないときは、要件の不足(`requirements_gap`)と不足の報告(`gap_report`)を返して中断する。この決まりは`factory-implementation`スキル(`.claude/skills/factory-implementation/SKILL.md`)に書く。

設計書が渡された実行は、承認済みの設計書に従えないとき、設計の不足(`design_gap`)を返せる。
設計書が渡されない実行は、この結果を選べない([設計の不足](#設計の不足))。

### 設計書の入力

設計が有効で、設計の承認が照合を通ったときだけ、承認済みの設計書の本文をプロンプトに載せる。
設計が無効なときは、承認の行があっても載せない。
プロンプトは`implementPrompt`と`implementFixPrompt`のどちらにも、要件定義の後ろに設計書の節を足す。

本文は、設計の承認依頼が指す設計書をDBから読む。最新の設計書は読まない。
設計書のディレクトリは読まず、図、概要、未確定事項は渡さない。
プロンプトには、図を渡していないことと、図への参照を無視することを書く。

設計書は、信頼できない入力を読んだClaudeの出力である。
要件定義と同じく`dataFence`に入れ、命令ではなくデータとして扱わせる。
優先順位は、要件定義、設計書、Issueの本文の順である。
設計書と要件定義が食い違うときは、要件定義に従い、食い違いを`notes_for_reviewer`に1件ずつ書かせる。
この決まりは`factory-implementation`スキルにも書く。

渡す前に、`f/factory/lib/model_text.ts`の`normalizeDesignForImplement`が次の順に整える。

1. 制御文字と書式文字を除き、秘密情報をマスクする。結合文字などを挟んだ秘密情報は、影の文字列で判定してマスクする。
2. 整えた本文が8000コードポイントを超えるときだけ、コードポイントの境界で切り、末尾に`[the design was truncated]`の行を足す。

切るかの判定は、整えた後の長さで行う。
元の本文が8000を超えていても、整えた後に8000以下なら、切らず、印も足さない。
結果は、もう一度通しても変わらない。切り詰めの境界も同じである。

HTMLとリンク参照定義は除かず、文字としてそのまま渡す。
プロンプトには、設計書の中のHTMLとリンク参照定義が、マークアップでなく文字であることを書く。
行ごとの規則では、Markdownの定義と構文のすべてを真似きれず、取りこぼした行が人の見ていない形で実装に届くためである。
HTMLの除去は、見えない文字を挟んだコメントの開きを、整形の後に本物のコメントとして復元しうる。
コードの中の`Promise<void>`のような文字列も壊す。
人が見る文字と実装が受け取る文字を一致させる責任は、描く側にある。
承認画面が、このHTMLとリンク参照定義を、要素や定義にせず文字として描くことを前提にしている。
[セキュリティ](../security.md)の「実装に渡す設計書」に、この前提と限界を書く。

整えて本文が変わったときは、警告のログを1件残し、止めない。
変わったときとは、次のいずれかである。

- 本文を切った。
- 秘密をマスクした。
- 結合文字を落とした。
- 制御文字か書式文字を除いた。

警告の項目は、次の8つに限る。

- `work_item_id`
- `design_draft_id`
- `original_chars`
- `kept_chars`
- `masked`
- `dropped_combining`
- `stripped_characters`
- `truncated`

`original_chars`は整えた本文の長さ、`kept_chars`は残した長さである。
`stripped_characters`は、制御文字・書式文字・結合文字などを除いた文字数である。
設計書には秘密情報や隠れた指示が含まれうるので、本文はログに載せない。
設計書は要件定義より下位の入力で、切れても要件定義が優先されるため、止めない。
正しく生成された設計書は、検査で8000以下に収まるので、通常は何も変わらない。

### 設計の不足

設計書が渡された実行だけが、設計の不足(`design_gap`)を返せる。
設計書が要件定義と食い違うか、書かれたとおりには作れないときに返し、不足の報告(`gap_report`)を必ず付ける。
`gap_report`は、設計の段に向けた報告である。
指示や命令は書かせない。

設計書が渡されない実行は、出力の形(`IMPLEMENT_SCHEMA`)、プロンプト、システムプロンプトのどれにも、設計の不足を出さない。
設計書が渡された実行は、結果の選択肢に`design_gap`を足した出力の形(`IMPLEMENT_SCHEMA_WITH_DESIGN_GAP`)と、`design_gap`の説明を足したプロンプトを使う。
設計書が渡されない実行の出力に`design_gap`があれば、不正な出力として扱う。
選択肢にない結果は、指示に従っていないためである。
設計工程の入口が閉じている間、本番の実行には設計書が渡らないので、本番で`design_gap`は返らない。

`design_gap`を返したラウンドは、ループを終えて完了のステップ(`implement_finish`)に渡る。
完了のステップは、要件の不足と同じく、worktreeと、PRが無ければ実装ブランチを先に片付ける。
不足を返した実装の作業は捨てる。
その後、次の表の行き先に移す。

| 行き先 | 条件 | 作業項目の状態 | 理由 |
| --- | --- | --- | --- |
| 設計へ戻す | 設計工程が有効で、上限に達していない | 設計中(`designing`) | なし |
| 上限で止める | 設計工程が有効で、反映できた設計の却下と設計への戻しの数に1を足すと`max_design_attempts`以上 | 人の対応待ち | `design gap after max_design_attempts` |
| 無効で止める | 設計工程が無効(`design_enabled`が偽) | 人の対応待ち | `design gap reported while design_enabled is off` |

設計工程が無効のときに戻さないのは、閉じた入口を迂回しないためである。
行き先の判定は`decideDesignGapAction`が行い、設計工程が有効かは`config.design_enabled`をそのまま渡す。
上限は、人の設計の却下と数を分け合う。数え方は[設計書の生成](design.md)の「却下の数え方」に書く。

設計へ戻す遷移は、次を1つの比較交換で行う(`returnToDesigningFromImplementingIfLeaseHolder`)。
条件は、作業項目が実装中で、`flow_job_id`が自分のジョブIDのままであることである。

- 状態を設計中にする。
- `design_attempt`を1進める。前の設計の承認が、実装の関門、再実行、承認待ちの走査のどこでも照合を通らないようにするためである。
- `flow_job_id`を空にする。`designing`から`designing`への遷移を作らずに、続く設計フローが新しいジョブIDを記録できるようにするためである。
- 遷移の記録を、遷移元を実装中、注記を`implement design gap:`と報告にして書く。

移せなければ、作業項目が先に動いているので、何も起動しない。
移せたら、設計フローを自動の報告の印(`automatedFeedback`)つきの`feedback`で起動し、空のときだけジョブIDを記録する。
報告は、長さの制限と秘密のマスクを通してから渡す。
設計フローの起動か記録に失敗したら、設計の起動の手順が設計中から人の対応待ちへ戻して通知する。
上限で止めたときの注記は`implement design gap exhausted:`と報告である。
再実行は、この2つの接頭辞で報告を読み出す([作業項目の状態とリース](work-items.md)の「設計フローへ渡す理由」)。

要件の不足で要件定義へ戻すときは、同じ文で`design_attempt`を0にし、`flow_job_id`を空にする。
`feedback`は、設計の不足と同じく自動の報告の印を付けて渡す。
古い設計書の承認を、作り直した要件定義の実装に使わせないためである。

## 検証と修正のループ

検証のステップ(`implement_verify`)は、`f/factory/lib/implement_loop.ts`の検証のループを回す。Claudeの1回の実行を1ラウンドとし、ラウンドごとに次の順で処理する。

1. リースを確かめる。実装のステップがリースを失っていたか、今リースを持っていなければ、worktreeに触れず、記録もせずに止める。
2. worktreeの`.git`を確かめる。変わっていれば、worktreeでgitを1つも実行せずに止める。
3. Claudeの実行が失敗したか、要件の不足か設計の不足が報告されたら、記録して止める。
4. 差分をすべてステージし、指紋(`git write-tree`)と、比較の基準からの差分の量を取る。
5. 比較の基準からの変更パス(`git diff -z --name-status`)を調べる。
6. symlinkの変更と差分の超過を確かめ、当たれば止める。保護パスの変更は記録だけする。
7. 比較の基準から何も変わっていなければ、検査せずに「変更なし」として不合格にする。
8. 変更があれば、gitleaksを実行する。検査したツリーと手順4で取ったツリーが違えば、検査コマンドを実行せずに止める。同じなら、続けて検査コマンドを実行する。
9. ループを終えるかを判定する。
10. 修正ラウンドの前にリースと`.git`を確かめ、どちらかに通らなければ止める。

Claudeの実行ごとに`implement_rounds`へ1行記録する。
リースを失って止まったラウンド、承認済みの要件定義の照合で止めたラウンド、workerが検査の前提を満たさず検査できなかったラウンドは記録しない。

### 検査コマンド

検査コマンドは、そのリポジトリについて`check_commands_by_repo`に明示したものだけを実行する。保護パスを変えたラウンドと、エントリが無いリポジトリでは実行しない。gitleaksは設定に関わらず毎ラウンド実行する。

検査コマンドを実行する直前に、毎回`git clean -fdX`で無視ファイル(`node_modules/`やビルドの成果物)を消す。そのため、検査コマンドの先頭で依存関係をインストールする必要がある。worker imageにmiseは無いので、検査コマンドはworkerで直接動くものに限られる。

各検査コマンドは`implement_check_timeout_sec`で打ち切り、期限では打ち切らない。検査に失敗したら、その出力をDATAとして修正のプロンプトに渡し、Claudeに直させる。

### ループの終わり方

ループは次の表の上から順に判定して終える。どれにも当たらなければ、次の修正ラウンドに進む。

| 終了の理由 | 条件 | `implement_rounds.outcome` |
| --- | --- | --- |
| `requirements_gap` | Claudeが要件の不足を返した | `requirements_gap` |
| `design_gap` | Claudeが設計の不足を返した(設計書が渡された実行だけ) | `design_gap` |
| `checks_skipped` | 検査コマンドを実行しなかった | `checks_skipped` |
| `checks_passed` | 検査に通った | `done` |
| `max_rounds` | ラウンドが`implement_max_rounds`に達した | `check_failed` |
| `daily_budget` | 日次予算を超えた | `check_failed` |
| `deadline` | 期限までの残りが修正ラウンドの最悪の所要時間に足りない | `check_failed` |
| `stalled` | 差分か検査の出力が前のラウンドと同じ。ただし、この失敗で`heavy_model`に上がるときは除く | `stalled` |

検査コマンドを動かさなかったラウンドは、GitHub側のCIに検査を任せる。停滞(`stalled`)で止めるのは、同じ状態でもう1回直させても予算を使うだけになるからである。
ただし、そのラウンドの失敗でモデルが`model`から`heavy_model`に変わるときは、停滞で止めず、`heavy_model`で修正ラウンドを1回回す。
同じ失敗でも、上位のモデルなら直せる場合があるためである。
このとき、修正ラウンドのプロンプトで、前のラウンドが進まなかったことを伝え、同じ直し方を繰り返さないようにする。
`model`と`heavy_model`が同じ設定なら変わらないので、停滞で止める。
ラウンドの上限、日次予算、期限の判定は、この場合も停滞の判定より先に行う。
期限の判定は、ラウンドの上限や日次予算と同じく、修正ラウンドの前のリースの確認より先に行う。

ループは、検査の前にも次の理由で止まる。

- symlinkの変更(`symlink`)
- 差分の超過(`diff_too_large`)
- `.git`の書き換え(`git_pointer_modified`)
- 変更の判定とgitleaksの検査の間のworktreeの変化(`worktree_changed`)
- workerが検査の前提を満たさず、検査コマンドを実行できない(`check_image_stale`)。イメージが古いときと、稼働中のworkerの問題のときの両方である
- 検査コマンドの実行ファイルを起動できない(`check_unrunnable`)
- Claudeの実行の失敗、または承認済みの要件定義のディレクトリが基準値と合わず、Claudeを起動しなかったこと(`claude_error`)
- リースの喪失(`lease_lost`)

`worktree_changed`で止めるのは、変更の判定とgitleaksの検査の両方を経たツリーだけを、検証済みとして記録するためである。
理由は`worktree changed before the secret scan in round <N>`になる。

準備のステップ(`implement_prepare`)は、検査コマンドを設定したリポジトリでは、Claudeより前に、イメージと実行時の前提([検査コマンドの権限](../security.md#検査コマンドの権限))を確かめる。
満たさなければ、Claudeを動かさずに人の対応待ちで止まる。
前提を満たさないまま進むと、Claudeの1ラウンド分を使ってから検証で止まるためである。
イメージの前提には、検査コマンドの設定が使う`bunx`(`/usr/bin/bunx`)を含める。
`bunx`を含めるので、検査コマンドの設定は`bunx`を使える前提で書ける。
`bunx`の無い古いイメージは、リポジトリを問わず、`mise run up`までイメージが古いとして止まる。

ループも、検査コマンドの準備が同じ前提を確かめ直し、満たさなければ`check_image_stale`で止まる。
準備から検証までの間に、イメージも稼働中のworkerも変わりうるためである。
検査の準備は所有権にも枠の記録にも触れる前に止まり、ループはそのラウンドを記録しない。
記録すると、Sonnetの失敗として数えられ(`countImplementFailedRounds`)、`heavy_model`への切り替えを早めるためである。
Claudeが直せる検査の失敗ではないので、修正のラウンドに進まず、作業項目は人の対応待ちになる。

検査コマンドの実行ファイルを起動できないときも、同じ扱いにする。
検査コマンドは、非特権のuidへ切り替える`setpriv`を通して動く。
`setpriv`が実行ファイルを見つけられないか実行できないと、終了コードは127か126になり、出力の先頭の行は`setpriv: failed to execute`で始まる。
この2つがそろい、コマンドの先頭の語が相対パスで`/`を含まないときだけ、環境の問題として止める。
先頭の語が`bunx`のように名前だけなら、固定のPATHで探す。絶対パスなら、worktreeの外のイメージの道具を指す。どちらも実行ファイルが無いのはコードの失敗ではない。
`scripts/check.sh`のように相対パスで`/`を含む先頭の語は、worktreeの中を指す。コードが消したか実行権を落とした失敗なので、修正のラウンドに進む。
検査コマンド自身が127を返したときや、出力の2行目以降に同じ語が混じるだけのときも、コードの失敗なので修正のラウンドに進む。
修正のラウンドを回しても、Claudeはworkerの環境を直せず、差分も検査の出力も変わらないまま、停滞で止まるだけだからである。
このときもラウンドは記録しない。
理由は`check command could not run: <コマンド>: <setprivの出力>`になり、要対応の通知で停滞と区別できる。
検査コマンド側のコードが同じ文面を出して、この停止を起こすこともできる。
起こせるのは人の対応待ちで止めることだけで、権限は広がらない。

止まったときの理由と要対応の通知は次のとおりである。

| 原因 | 理由の先頭 | 要対応の通知 |
| --- | --- | --- |
| イメージが古い | `worker image is stale: run mise run up` | `host_action_required`([運用](../operations.md#fとworkerのイメージを両方変えたとき)) |
| 稼働中のworkerの問題 | `worker runtime is unsafe for checks:` | `check_runtime_unsafe`([運用](../operations.md#稼働中のworkerが検査の前提を満たさないとき)) |
| 検査コマンドの実行ファイルを起動できない | `check command could not run:` | `implement_needs_human`([運用](../operations.md#人の対応待ちになったら)) |

イメージが古く、稼働中のworkerの問題も一緒に見つかったときは、両方の通知を残す([Consoleのnotice](notifications.md#consoleのnotice))。
`host_action_required`は`mise run up`の後に自動で解決されるが、ボリュームのマウントポイントは作り直しでは閉じないためである。

### イメージが古くて止まったとき

イメージが古くて止まった実装とPR修正は、`mise run up`の後に自動で再開する。
自己更新は、次の2つの回に`auto_retry_stale_image`を別のジョブで起動する。
通知を解決した回と、再開できる候補が残っている回である。
このscriptが再開の対象を選ぶ。
再開できるかは、再開のscriptと同じ条件で確かめる。
要件が未承認のIssue、設計が有効で設計の承認が照合を通らないIssue、`implement_enabled`が無効のIssueは、候補に残っても再開できないので数えない。
確かめられなかったときは、取り逃さないよう起動する。
対象の選び方は繰り返しても同じ結果になるので、前の回で取り逃した作業項目も、再開できる候補が残っている次の回で拾える。
起動に失敗しても、自己更新の結果は変わらず、警告のログだけを残す。

再開の対象は、次をすべて満たす作業項目である。

- 実装の人の対応待ち(`needs_human`)か、PR修正の`blocked`である。
- 止まった理由が`worker image is stale`で始まる。許可リストはこの1つだけである。
- 止まった後に、イメージが古いことを知らせる通知が、自己更新に自動で解決された。
  人が解決した通知と、版が載らない通知は、自動で解決されないので対象にならない。
- 実装では、同じIssueに新しいサイクルが無い。
  新しいサイクルに置き換えられた作業項目を再開すると、古い要件を実装しかねないためである。
- PR修正では、同じPRにidの大きい行が無い。
  新しい行に置き換えられた作業項目を再開すると、対応済みの指摘に返信とコミットを重ねかねないためである。
- PR修正では、同じPRに終了していない別のPR修正が無い。
  並んで動くPR修正は、部分一意インデックスに阻まれるためである。
- PR修正では、CIの失敗を直す回ではない。
  失敗の行は`fixing`のまま食い違うので、作業項目だけを再開しても直らない。
  回が終わると`watch_pr_ci`が失敗の行を戻す。

再開は`retry_work_item`と同じ遷移で、同じフローを起動する。
実装は実装フロー、PR修正はPR修正のフローで再開する。
要件が承認済みでないIssue、設計が有効で設計の承認が照合を通らないIssue、実装フローが無効のIssueは、再開しない。
要件定義を作り直さないためと、設計の承認を飛ばさないためである。
再開してよいかは、`isReadyForImplement`が決める。自己更新の起動の要否の判定も、同じ関数を呼ぶ。
記録済みのflowジョブが動いているか、状態を読めないときも再開しない。

状態の交換は、現在の状態と止まった理由を条件にした比較と交換である。
実装は新しいサイクルが無いことを、PR修正は同じPRに新しい行と終了していない別のPR修正が無いことを、同じ文で確かめる。
条件を確かめた後に別のPR修正が先に始まって索引に阻まれたときは、失敗とは数えず、見送る。
新しい行は、終端でも稼働中でも、古い行を置き換えたものとして扱う。
止まった後に通知が自動で解決されていることも、同じ文で確かめる。
人が先に再実行した作業項目と、別の理由で止まり直した作業項目は動かさない。
2つのジョブが同時に走っても、新しい解決の無いまま二重に起動することはない。
同時実行の制限(`concurrent_limit`)は、有償版でしか効かないので使わない。

無限に再開しないよう、次の保護を置く。

- 同じ作業項目の自動の再開は3回までである。
  再開の遷移の注記は`auto_retry:`で始まり、その数を数える。
  上限に達した作業項目は、候補と比較交換の両方から外し、人が`retry_work_item`で再実行する。
- 再開の後に同じ理由で止まった作業項目は、次の通知の自動の解決まで対象にならない。
  起動に失敗して人の対応待ちに戻した作業項目も、同じ理由で止まり直さない限り、再開されない。
- 1回の実行で起動を試みるのは5件までである。
  候補は50件まで読み、要件が未承認の項目などを飛ばしても、後ろの項目を締め出さない。
- フローを起動できなかった作業項目は、理由を注記にして人の対応待ちに戻す。
  この理由は許可リストに無いので、再開されない。

既知の限界は次のとおりである。

- 稼働中のworkerの問題(`worker runtime is unsafe for checks:`)は対象にしない。
  直ったことを示す自動の印が無く、人が閉じて通知を解決するまで続くため、再開しても同じ理由で止まる。
  人が`retry_work_item`で再実行する。
- 通知の自動の解決が、作業項目の止まる遷移より前になった場合は、自動で再開しない。
  作業項目ごとの検出時刻を記録していないためである。
  人が`retry_work_item`で再実行する。
- 稼働中のworkerの問題とイメージの古さが同時に起きて止まった作業項目は、イメージを作り直した後に、1回は無駄に再開しうる。
  再開した準備のステップが、稼働中の問題で止め直す。
- 自己更新が失敗した回(取得の失敗など)は、`auto_retry_stale_image`を起動しない。
  次に成功した回に拾う。
- 新しいサイクルの作成と比較交換が重なる、極小の窓がある。
  作成と確認が別の文なので、この窓では古いサイクルを再開しうる。
- 止まってから長く経ったPR修正は、古い前提のまま再開しうる。
  時間の上限を置いていないためである。
- 通知は、解決から保持期間(`deleteResolvedNoticesBefore`)を過ぎると消えるので、再開の契機が消える。
  それまでに再開されなかった作業項目は、人が`retry_work_item`で再実行する。
- 自己更新が初めてこの仕組みを反映した直後は、過去に止まったまま通知が自動で解決された作業項目が、まとめて再開されうる。

### 期限と修正ラウンド

検査に失敗したラウンドの後は、期限までの残りが修正ラウンドの最悪の所要時間(`fixRoundWorstCaseSec`)以上のときだけ、次の修正ラウンドを始める。足りなければ期限(`deadline`)でループを終える。最悪の所要時間は次の式で求める。

```text
implement_timeout_sec + 600 + 検査コマンド数 × (implement_check_timeout_sec + 15)
```

既定値で検査コマンドが4件なら7860秒である。この条件で始めた修正ラウンドは、Claude、gitleaks、検査コマンドがそれぞれのタイムアウトまでかかっても期限までに終わる。検査コマンドが多いほど修正ラウンドを始められる時間が短くなるので、1リポジトリの検査コマンドは4件までを目安にする。

Claudeが不正な出力を返したときは、1回の実行につき1回だけ再試行する。この再試行だけは期限までの残りで打ち切る。そのため、再試行したラウンドではgitleaksと検査コマンドが期限の後に動くことがある。再試行が打ち切られたときは、変更を検査していないのでpushしない。変更はworktreeに残り、作業項目は人の対応待ちになる。

最初の実装のClaudeが期限で打ち切られたか、期限の後で起動しなかったときも、差分は検査を経ていない。そのためpushせずに人の対応待ちにする。検査に通ったラウンドは、期限の後でもPRを作る。

## 完了

完了のステップ(`implement_finish`)は、ループの結果によって作業項目の行き先を振り分ける。状態の遷移の一覧は[作業項目](work-items.md)に書く。

| ループの結果 | 処理 |
| --- | --- |
| 準備で何もせずに終わった、リースを失った | 何もしない |
| Issueがcloseされていた | 取り消し(`cancelled`)にする |
| 検査に通った、検査を実行しなかった | コミットしてPRを作成または更新し、PR作成済み(`pr_open`)にする |
| 要件の不足 | 要件定義を作り直す工程2へ差し戻す |
| ラウンドの上限、日次予算、期限、停滞、差分の超過 | 途中の変更を残して、人の対応待ちにする |
| symlinkの変更、Claudeの実行の失敗、`.git`の書き換え、判定と検査の間のworktreeの変化、検査を実行できない環境の問題(`check_image_stale`、`check_unrunnable`)、準備での停止 | 何もpushせずに、人の対応待ちにする |

完了のステップは、作業項目を読んだ直後にリースを確かめる。外への副作用の直前にも確かめ直す。外への副作用は、commitとpush、worktreeとリモートのブランチの削除、PRの作成と更新、`pr_url`の記録、ラベルの付与である。

途中経過と最終のcommitの前には、次の確認をすべて通す。
1つでも通らなければ、commitとpushのどちらもせずに人の対応待ちにする。

| 確認 | 詳細 |
| --- | --- |
| 生き残りのプロセスがいない | [pushの前の生き残りのプロセスの確認](#pushの前の生き残りのプロセスの確認) |
| HEADとブランチが記録どおり | [pushする履歴の制限](#pushする履歴の制限) |
| ステージした内容が検査したツリーと同じ | [検証したツリーだけのコミット](#検証したツリーだけのコミット) |
| リポジトリのオーナーの数値IDが設定と一致する | pushの直前に照合する。準備の入口から長い実行を挟むので、その間に名前が別の人に渡っていても、ローカルにしか無いオブジェクトを相手に渡さない。リモートブランチの削除の前にも照合する。照合は[運用](../operations.md)の「オーナーの数値IDを固定する」に書く |

### PRの作成

検査に通ったラウンドのツリーをコミットしてpushし、PRを作る。既にPRがあれば本文を更新する。

- PRには`factory:review`ラベル(`review_label`)を付ける。`poll_prs`がこのラベルを見て自動レビューを起動する。
- PR本文の`Closes #N`で元のIssueに紐づける。
- Discordに`pr_opened`を通知する。保護パスの変更は、PR本文の「確認して欲しい点」と`pr_opened`の通知に載せる。
- 検査コマンドを動かさなかったときは、PR本文の「動作確認結果」に「検査未実施」と理由を書く。

コミットする新しい変更が無くても、ブランチに比較の基準より先のコミット(途中経過のコミットなど)があれば、それを使ってPRを作成または更新する。ブランチに比較の基準より先のものが何も無いときだけ、「実装が変更を生みませんでした」として人の対応待ちにする。

Issueがopenかを確かめるために取得したIssueの題名か本文が、取り込み時点と違うことがある。そのときはPR本文の「確認して欲しい点」にその旨を1行書く。通知はしない。

却下や再実行による作り直しで、取り込み内容を現在のIssueで更新したことのある作業項目では、「確認して欲しい点」に別の1行を必ず書く。更新後の値と現在のIssueを比べる上の注記では、更新のときの書き換えを拾えないためである。更新の有無は、`work_item_events`の更新の履歴から読む。

Consoleの**作業項目**の表は、作業項目のブランチとPRを列に表示する。

### 途中の変更の扱い

ラウンドの上限、日次予算、期限、停滞、差分の超過で止まったときは、途中の変更を残す。PRが無ければ、gitleaksをもう一度実行し、通れば途中の変更をコミットして実装ブランチにpushする。gitleaksに通らないときと、検査自体が失敗したときはpushしない。

次のときも、途中経過と最終のどちらもpushしない。

- 前のステップのClaudeや検査コマンドが、worktreeに残っている。理由に残っているプロセスが載る。
- 検査コマンドがローカルでcommitかブランチの切り替えをした。理由には、worktreeのHEADが記録したブランチの先頭と異なる旨が載る。
- commitしたツリーが、検査したツリーと違う。
- 途中経過では秘密情報の検査の後に、最終のcommitでは検証の後に、worktreeが変わった。

PRがあるときは、未検証の変更がPRに入るのでpushしない。理由には「PRがあるため途中の変更はpushせずworktreeに残しました」と載せる。

次の理由で止まったときは、検査を終えていない変更なのでpushせずworktreeに残す。

- symlinkの変更
- Claudeの実行の失敗
- `.git`の書き換え
- 判定と検査の間のworktreeの変化
- 検査を動かせない環境の問題(`check_image_stale`、`check_unrunnable`)

worktreeに残った途中の変更は、次の実行の準備で捨てる。

途中経過のコミットと、再実行で実装が完了したときのコミットは別のコミットになる。1つのコミットにまとめるのは、途中で止まらなかった場合だけである。

### 要件の不足の差し戻し

Claudeが要件の不足を返すと、完了のステップは次の順に処理する。

1. worktreeを削除する。
2. PRが無ければ、実装ブランチをリモートとローカルから削除する。PRのheadのブランチを消すとPRが閉じるので、PRの検索に失敗したときも削除しない。削除の直前にオーナーの数値IDを照合し、照合の取得に失敗したときも、ブランチを残して差し戻しを続ける。照合に落ちたときは、差し戻さずに人の対応待ちにし、不足の報告をnoticeとDiscordに載せる。
3. 不足の報告を却下理由(feedback)として、工程2を試行(attempt)を1つ増やして起動し直す。

試行の回数が`max_attempts`を超えるときは、差し戻さずに人の対応待ちにする。再承認の後は、同じブランチ名で実装をやり直し、既にPRがあればそのPRを更新する。

### 差分の大きさの測り方

差分の上限(`implement_max_changed_files`、`implement_max_diff_lines`)は、既定のブランチとの分岐点からの累積で測る。既存のPRを更新するときも同じなので、既にPRが大きいと上限に達しうる。

## 設定値

実装フローは`f/factory/factory_config`の次の値を読む。

| キー | 既定値 | 意味 |
| --- | --- | --- |
| `implement_enabled` | `false` | 承認の後に実装フローを起動するか |
| `model` | `claude-sonnet-5-5` | 実装のモデル。同じ要件定義の実装が続けて2回失敗した後は`heavy_model`を使う |
| `heavy_model` | `claude-opus-5-5` | 要件定義の生成のモデルと、続けて2回失敗した後の実装のモデル |
| `implement_max_rounds` | `5` | Claudeを実行するラウンドの上限 |
| `implement_max_turns` | `80` | Claude 1回の実行のターン数の上限 |
| `implement_max_budget_usd_per_run` | `10` | Claude 1回の実行の費用の上限(USD) |
| `implement_timeout_sec` | `3600` | Claude 1回の実行を打ち切る秒数 |
| `implement_check_timeout_sec` | `900` | 検査コマンド1件を打ち切る秒数 |
| `implement_flow_timeout_sec` | `14400` | 準備の開始から期限までの秒数 |
| `implement_max_changed_files` | `60` | 分岐点から変えてよいファイル数の上限 |
| `implement_max_diff_lines` | `3000` | 分岐点からの追加と削除の行数の上限 |
| `check_commands_by_repo` | `{}` | リポジトリごとの検査コマンド |
| `daily_budget_usd` | `50` | 全フローで共有する1日の費用の上限(USD) |
| `max_attempts` | `3` | 要件定義の試行回数の上限 |

設計工程の設定(`design_enabled`、`max_design_attempts`)は[設計書の生成](design.md)の「設定値」に書く。

モデルの昇格に使う失敗の数は、同じ作業項目の同じ試行の`implement_rounds`を新しいほうから見て、結果が`check_failed`、`stalled`、`error`の行が続いた数である。
ほかの結果(`done`、`checks_skipped`、`requirements_gap`、`design_gap`)の行に当たったら、そこで数えるのをやめる。成功が入れば`model`に戻るためである。
`error`と`check_failed`には、トークンの失効やAPIの障害、期限切れ、`.git`ポインタの不一致など、モデルの失敗でないものも入るので、基盤の失敗が2回続くと`heavy_model`に上がる。損失の上限は`implement_max_rounds`と予算で決まる。
停滞したラウンドの扱いは「[ループの終わり方](#ループの終わり方)」にある。
数え方の全体は[運用](../operations.md)の「モデルを使い分ける」にある。

`check_commands_by_repo`は、`{"<owner>/<repo>": ["bun install --frozen-lockfile", "bun test"]}`の形で書く。workerで直接動く例は`bunx --no-install --bun tsc --noEmit`や`bunx --no-install --bun biome check .`である。
`--no-install`は、lockfileから入れていない実行ファイルをレジストリから取得しないための指定で、理由は[運用](../operations.md#検査コマンドを設定する)にある。
workerのイメージは、`bunx`をbunへのsymlinkとして`/usr/bin`に置く。
実装フローは`allowed_check_commands`を使わない。

1つのIssueにかかる費用の上限は、`implement_max_rounds × implement_max_budget_usd_per_run`が目安である。Claudeの不正な出力への再試行は、その実行の費用の上限をもう1回使うので、最悪でその2倍になる。

## タイムアウト

`flow.yaml`の各ステップにはWindmillのtimeoutを付ける。アプリ側の期限と各timeoutが効かなかったときに、最後に打ち切るためである。

| ステップ | Windmillのtimeout | 定数 | 理由 |
| --- | --- | --- | --- |
| 準備 | 3600秒 | なし | ロックの待ちだけで約1800秒かかりうるので、完了より長くする |
| 実装 | 21600秒 | `IMPLEMENT_STEP_TIMEOUT_SEC` | Claude 1回と余裕が収まる |
| 検証と修正のループ | 21600秒 | `IMPLEMENT_STEP_TIMEOUT_SEC` | 期限と、期限の直前に始まった1ラウンド分の検査が収まる |
| 完了 | 1800秒 | なし | commitとpushの前にリポジトリのロックを待つ |

`IMPLEMENT_STEP_TIMEOUT_SEC`は`f/factory/lib/implement_support.ts`にある。上限を上げるときは、`flow.yaml`とこの定数を同じ変更で上げる。`tests/scripts/implement_flow.test.ts`が両者の一致を確かめる。

アプリ側では、次の単位で打ち切る。

| 対象 | 打ち切り |
| --- | --- |
| Claude 1回の実行 | `implement_timeout_sec`と期限までの残りの短い方 |
| 検査コマンド1件 | `implement_check_timeout_sec`(期限では打ち切らない) |
| gitleaks | 300秒 |
| フロー全体 | 準備の開始から`implement_flow_timeout_sec` |

期限は、`retry_work_item`で再実行するたびに最初から数え直す。

### 時間設定の確認

準備のステップは、時間設定が実装と検証のステップのtimeoutの範囲内かを確かめる(`implementTimeoutMisfit`)。次のどちらかが21600秒を超えると、worktreeを使わないまま作業項目を人の対応待ちにする。

```text
implement_flow_timeout_sec + 600 + 検査コマンド数 × (implement_check_timeout_sec + 15)
implement_timeout_sec + 600
```

600秒は、gitleaksの最大300秒と、gitとDBの操作の余裕300秒の和である。15秒は、検査コマンド1件が打ち切りの後に停止と出力待ちで上乗せしうる時間である。既定値なら検査コマンドは7件まで収まる。

確かめるのは準備のステップだけである。そのため、実装フローの実行中は時間設定を変えない。

### Windmillのtimeoutで打ち切られたとき

Windmillのtimeoutはジョブのプロセスにしかシグナルを送らない。そのため、打ち切られたステップが起動したClaudeや検査コマンドは残り、作業項目は失敗(`failed`)になる。再実行したときの扱いは[同時実行の防止](#同時実行の防止)に書く。

Windmillのtimeoutで打ち切られたステップのClaudeは、`--max-turns`と`--max-budget-usd`の上限に達するまで動き続けうる(#53)。
アプリ側のタイマーが、ジョブのbunのプロセスと一緒に消えるためである。
その費用は`agent_runs`に記録されず、日次予算(`daily_budget_usd`)の集計から漏れる。
次の実行の準備のステップが残ったプロセスを止めるまでの間の、既知の制約である。

ステップのtimeoutは、インスタンスの上限を超えられない。セルフホストでは環境変数`TIMEOUT`が上限で、未設定なら7日である。インスタンスの`job_default_timeout`を設定するときは、21600秒以上にする。実装と検証のステップ(とPR修正の検証のステップ)を先に打ち切らないためである。

## 再実行と中断

実装フローの再実行には`retry_work_item`を使う。
失敗した作業項目と人の対応待ちの作業項目はConsoleの**要対応**から実行し、ブロックの作業項目はWindmillで`f/factory/retry_work_item`を作業項目のIDで実行する。
ブロックの作業項目は、失敗ではないので**要対応**に出ないためである。
Windmillでフローを直接動かすと、リースの確認で何もせずに終わる。

| 操作 | 挙動 |
| --- | --- |
| Windmillのrerun | 新しいジョブIDで最初から走り、準備の最初のリースの確認で何もせずに終わる |
| 途中のステップからのrestart | 新しいジョブIDで走り、再開したステップの最初のリースの確認で何もせずに終わる |
| 同じ作業項目での二重の起動 | 後の実行は準備で何もせずに終わる |
| Windmillでの取り消し | Claudeや検査コマンドは止まらずに残る |

二重の起動は、起動の応答が失敗したのに実際にはフローが動いていた場合などに起きる。rerunとrestartは、元の実行で進行中のClaudeの実行や検査を中断しない。

### 実行中のリースの喪失

実装フローは、実行中にリースを失うことがある。例えば、Issueのcloseで実行を取り消すときに`cancelJob`が失敗した場合である。実装フローは次のリースの確認で止まり、commit、push、PRの作成をしない。

- 実装のステップの、Claudeを実行する前
- 検証のループの、各ラウンドの冒頭と各修正ラウンドの前
- 完了のステップの、最初と外への副作用の直前

進行中のClaudeの実行や検査は中断しない。worktreeに残った途中の変更は、次の実行の準備で捨てる。

### 新しいバージョンの反映

`self_update`は、実行中の実装フローを待たずに新しいステップを反映する。そのため、準備と完了の間で、別のバージョンのステップが動く場合もある。実装中の作業項目がある間は、mainへのマージとデプロイを避ける。

### 残ったプロセスの掃除

`cleanup_workspaces`は、閾値を超えて動いているheadless Claude(`claude -p`)だけを孤児として止める。閾値は、`claude_timeout_sec`と`implement_timeout_sec`の長い方に5分を足した時間である。検査コマンドの生き残りは、この掃除の対象にならない。

実行中に、同じ実行の検査コマンドなどが残したプロセスがロックを持ち続けて失敗したときは、`retry_work_item`で再実行するだけでよい。
準備のステップがそのプロセスを止めてから続ける。

## 安全策の実装

実装フローはPR修正と同じくClaudeに書き込みのツールを渡す。PR修正と共通の仕組みは[PRワークフロー](pr-workflow.md)にも書く。

### Claudeに渡すツールの制限

Claudeに渡すツールは`Read,Glob,Grep,Edit,Write`だけで、`Bash`は渡さない。起動のオプションは`--permission-mode dontAsk`、`--allowedTools Edit Write`、`--restricted`である。検査はClaudeではなくフローのステップが実行する。

`--allowedTools Edit Write`と`dontAsk`は、PR修正で書き込みができると確かめた組み合わせである。作業ディレクトリはworktreeにし、要件定義の複製は`--add-dir`で渡す。

### 取り込み時点のIssueの使用

Claudeに渡すIssueの題名と本文は、取り込み時点のもの(`work_items.title`、`body`)である。承認の後にIssueを書き換えて、プロンプトに指示を差し込むことはできない。

承認の時点でも、現在のIssueが取り込み時点と違えば、承認を断る。確認の仕組みは[要件定義](requirements.md)の「承認の前のIssueの確認」にある。

GitHubから取得した今のIssueは、次の3つにだけ使う。

- openかどうかの判定
- 取り込み時点のURL(`work_items.issue_url`)が空のときのURL
- 取り込み時点と違う場合の、PR本文への注記

### 承認済み要件定義の複製

Claudeには、実行ごとに一時ディレクトリへ複製した要件定義のディレクトリを`--add-dir`で渡し、実行の後に削除する(`withReadOnlyDocDirCopy`)。元のファイルは渡さないので、Consoleが表示する承認済みの文書をClaudeは書き換えられない。

基準値がある下書きは、複製の直前と直後に、元のディレクトリのハッシュを基準値と比べる。
複製の中では、各ファイルを1回だけ読み、読んだバイト列のハッシュを基準値と比べる。
照合した内容と複製の内容が同じになるので、複製の最中だけ元を書き換えて戻しても、複製には入らない。
複製の後に複製のディレクトリを読み直したハッシュとは比べない。
複製はsymlinkと通常のファイル以外を写さないので、元の内容と一致しないためである。
ハッシュと複製の関係は[要件定義の生成と承認](requirements.md)の「基準値」に書く。
元のディレクトリが基準値と違うか、無いときは、Claudeを起動しない。
そのラウンドは、要件定義の書き換えのラウンド(`requirements_modified`)として返す(`runDocDirGuardedRound`)。
生成の1ラウンド目と修正のラウンドは、どちらもこの位置を通る。
検証のループは、worktreeと検査に触れず、ラウンドの記録と費用も足さずに止まる。
終了の理由は`claude_error`である。
作業項目は人の対応待ちになり、途中経過はpushしない。
理由は書き換えとディレクトリが無い場合で分かれる。
照合の理由は、複製を包む呼び出しが`DocDirGuard`から受け取る。
省略すると要件定義の理由になる。

基準値が無い下書きは、照合を飛ばし、元のディレクトリがディスクに無ければ、複製せずに実行する。
準備のステップが基準値の項目を載せる前に作った実装の文脈は、基準値の項目自体が無い(`undefined`)。
そのときだけ、複製を包む呼び出しごとに警告を1回ログに残して飛ばす。
基準値が空(`null`)の文脈は、準備のステップの警告だけを残す。

複製には、通常のファイルとディレクトリだけを写す。
symlinkは指す先に関わらず写さない。
リンク先を実体として写すと、`/proc/self/environ`のような文書の外のファイルが複製に入りうるためである。

FIFOなどの通常のファイル以外も写さない。そのため、複製の中に、Claudeの`Write`が外へたどれるリンクは残らない。

### 同時実行の防止

同じ作業項目の実装フローは、同時に1つしか作業しない。
作業項目のリースに加えて、前の実行のプロセスが生きていないことも条件にする。

Windmillでジョブを取り消しても、新しいセッションで起動したClaudeや検査コマンドは止まらない。
そのため、Claudeと、PR修正と実装の検査コマンドはロック付きで起動する。

- ロックは、worktreeの隣のロックファイル(`.<worktreeのディレクトリ名>.process.lock`)を`flock`で持つ。
- 持ち主を表す環境変数`FACTORY_LOCK_OWNER`を付ける。
  値は、実装フロー、PR修正、設計フローの区別、作業項目、ジョブIDである。
- ロックファイルを表す環境変数`FACTORY_LOCK_PATH`を付ける。

ロックファイルは、使っている間は消さない。

#### 準備での走査

準備のステップは、worktreeを使う前にこのロックを確かめる。既存のworktreeならブランチの公開、検証、`reset --hard`と`clean`より前、新しく作ったときは作った直後である。ロックの取得の成否に関わらず、`/proc`を走査する。

走査で探すのは次の2種類のプロセスである。

- 保持者: ロックファイルと同じdevとinoのfdにflockを持つプロセス
- このロックファイルのタグ(`FACTORY_LOCK_PATH`)を持つプロセス

#### 止めてよいプロセス

実装フローの準備が止めるのは、持ち主のタグが「同じ作業項目の実装フローで、この実行とは別のジョブ」のプロセスだけである。
設計フローの持ち主のプロセスは、実装フローの準備も設計フローの準備も止めない。
止めるときはSIGTERMを送り、10秒後にSIGKILLを送る。
対象が自身のプロセスグループのリーダーなら、そのグループにも送る。

これらのプロセスは、次の理由で、終わった実行の生き残りと言える。

- この実行は作業項目のリースを持つので、同じ作業項目の別のジョブは今正当に動いていない。
- 止める直前に、リースを持ち続けていることを確かめ直す。ブランチのPR(閉じたものを含む)に、終わっていないPR修正とPRレビューが無いことも確かめ直す。
- シグナルを送る直前に、走査したときと同じプロセス(起動時刻が一致する)であることを確かめる。

止めた後に走査し直し、止めてよい残りがあれば、合わせて3回まで止め直す。止まる前に書き込まれたものは捨てる。既存のworktreeは再利用の経路で`origin/<branch>`へ`reset --hard`し、`clean -fd`をする。新しく作ったworktreeは、`.git`を検証してから、作った時点のコミットへ同じく戻す。

どちらも`reset --hard`の前に、HEADが`refs/heads/<branch>`を指すことを`git symbolic-ref -q HEAD`で確かめる。
`reset --hard`はHEADが指すブランチを動かすので、生き残りが別のブランチをcheckoutしていると、そのブランチを動かしてしまうためである。

- 指していなければ(別のブランチかdetached)、切り替えの前に`git worktree list`で、ほかのworktreeが対象のブランチをcheckoutしていないことを確かめる。
- 対象のブランチをcheckoutしているworktreeがあれば、切り替えずに失敗する。
- ほかのworktreeが使っていなければ、`git checkout -f --no-track -B <branch> <戻す先>`で対象のブランチへ移す。この切り替えは、それまでHEADが指していたブランチを動かさない。
- 次のときは、resetせずに失敗する。
  - HEADを読めない。
  - worktreeの一覧を取れない。
  - ほかのworktreeが対象のブランチを使っている。
  - 切り替えに失敗した。
  - 切り替えた後もHEADが指していない。

一覧の確認では防げない場合が2つある。
`checkout -B`の拒否は、その2つをgit 2.44以降で防ぐ。

- ほかのworktreeが対象のブランチをrebaseかbisectの途中にしている。
  - そのworktreeのHEADはdetachedで、一覧に対象のブランチが載らない。
  - `checkout -B`がこの場合も拒否することは、git 2.54.0で確かめた。
- 確認とcheckoutの間に、ほかのworktreeが対象のブランチをcheckoutする。

2.44より古いgitでは、この2つの場合に`checkout -B`がほかのworktreeのブランチを黙って付け替える。
そのため、workerのgitは2.44以上が要る。
gitは`infra/worker/Dockerfile`で版を指定せず、aptから入るので、版はベースイメージで決まる。
版は次のコマンドで確かめる。

```bash
mise exec -- docker compose -f infra/docker-compose.yml exec windmill_worker git --version
```

#### 止めないプロセス

保持者やタグを持つ残りに次のプロセスがいれば、何も止めずに人の対応待ちにする。

- タグの無いプロセス
- PR修正のプロセス
- ほかの作業項目のプロセス

理由には、保持者のpid、経過秒、持ち主、コマンドを載せる。PR修正の準備の扱いは[PRワークフロー](pr-workflow.md)に書く。

fdを閉じる子孫は珍しくない。例えばPythonの`subprocess`は既定で`close_fds`を有効にする。それらは環境変数のタグで見つけ、ロックが空いていても、止めてよいものは止め、それ以外があればworktreeに触れない。PR修正と`cleanup_workspaces`も同じように扱う。

#### 調べられないプロセス

workerには`CAP_SYS_PTRACE`が無い。そのため、uidを変えたプロセスやダンプ不可にしたプロセスの環境変数とfdは読めない。

生きているのに環境変数とfdを読めないプロセスは、タグもロックとの関係も分からない。止めずに保持者と同じく扱い、worktreeに触れない。理由には「could not be inspected」と載せる。

検査コマンドは枠のuid(`factory-check-N`)で動くので、そのプロセスは読めない。
走査は、枠のuidで動くプロセスを一覧に入れない。どのworktreeの検査かを特定できず、一覧に入れると無関係なworktreeの走査まで塞ぐためである。
枠のuidのプロセスは、検査の実行が終わるときに止める。取り消された実行が残したものは、同じ枠を次に取る実行か、次の項の所有権の復旧が、枠のロックを持って止める。
そのプロセスがworktreeのロックを持っていても、次の項の復旧がロックを空ける。

#### 残った所有権の復旧

取り消しやタイムアウトで検査の後始末が走らないと、worktreeは枠のuidの所有のまま残る。そのままだと、rootのgitが所有者の違いで実行を拒み、次の作業項目が進まなくなる。
検査は、所有権を渡す前に、枠の記録へworktreeと`HOME`のパスを書く。記録は後始末が最後まで終わったときだけ消える。
`ensureWorktreeLockFree`は、走査で関係するプロセスが見えないと分かった後に、記録がそのworktreeを指す枠を探す。
その枠のロックを取れれば、枠のuidのプロセスを止めてから、worktreeの所有権を取り戻す。
続けて、`HOME`と記録を消す。
最上位のディレクトリの所有者では判断しない。取り戻しが途中で止まると、最上位だけがrootで、中に枠のuidのものが残るためである。
ロックを最大5秒待っても取れなければ、記録を読み直す。
記録がもうそのworktreeを指さなければ先へ進み、まだ指していれば`WorktreeBusyError`で引き返す。
その枠を持つのは、そのworktreeで検査している実行か、その枠を取って記録を片付けている実行なので、worktreeに触れないためである。
プロセスを止められないときと、取り戻しが失敗したときも、詳細を載せた`WorktreeBusyError`にする。
読めない記録が残っていて、worktreeにrootでないものがあるときも同じである。
準備は人の対応待ちになり、詳細に枠のユーザーと理由が載る。
取り戻せなかった理由は`check sandbox:`で始まり、通知の次の操作は、プロセスを止める案内ではなく、[枠の記録を片付ける手順](../operations.md#検査の枠の記録を片付ける)になる。
取り戻す前には、イメージと実行時の前提を確かめる。
満たさなければ、所有権と記録のどちらにも触れずに`CheckEnvironmentError`を投げる。
準備のステップは要対応の通知を残して人の対応待ちになり、完了のステップは理由に載せてpushせずに止まる。掃除はそのworktreeを飛ばす。
通知は、イメージが古ければ`host_action_required`、稼働中のworkerの問題なら`check_runtime_unsafe`である。

ロックが塞がっているのに保持者が見えないときも、この復旧を先に行う。
取り消された検査が別のセッションに残したプロセスは、枠のuidで動くので走査に見えず、worktreeのロックを受け継いで持ち続けるためである。
復旧は、記録がそのworktreeを指す枠のuidのプロセスを止めるので、ロックが空く。
その後、200msおきに最大2秒、ロックが空くのを確かめる。空けば先へ進み、空かなければ`WorktreeBusyError`にする。
走査に見える関係するプロセスがいる間は、所有権に触れない。
準備、完了、掃除の4つのステップが、この関数を使う。
取り戻しの手順は[セキュリティ](../security.md#枠の記録と片付け)にある。

この仕組みが見逃すのは次のものである。

- fdを閉じ、かつ環境変数も消すプロセス
- ロックの下で起動しないgit、gitleaks、ghの生き残り
- 要件定義を書くClaude(要件定義のディレクトリへの書き込みは排他しない)

#### 実行中にロックが取れないとき

実行中にロックが取れなかったときは、フローを失敗させる。同じ実行の検査コマンドが常駐のプロセスを残した場合に起きる。

検査コマンドは常駐のデーモン(バックグラウンドで動き続けるサーバーなど)を残してはならない。ロックのfdを持ったまま残ると、以降のラウンドがロックを取れずに失敗する。fdを閉じて残ったものも、次の準備やPR修正を止める。

### ロックファイルの掃除

ロックファイルは確かめるたびにworktreeの隣に作られ、worktreeを消しても残る。`cleanup_workspaces`は、ロックが持たれているか、タグを持つプロセスが残っているworktreeを消さない。
そのworktreeごとに、Consoleの**要対応**へ`cleanup_worktree_busy`のnoticeを残す。
noticeは1回の掃除でパスごとに1件で、Discordには通知しない。

`cleanup_workspaces`がロックファイルを探す場所は次の2つの直下である。

- 掃除したリポジトリのメインのクローンの親
- `git worktree list`に載る各worktreeの親(realpath)

消す対象は、`.<名前>.process.lock`の形の空の通常ファイルで、隣に同じ名前のworktreeが無いものである。symlinkは対象にしない。消すのは次をすべて満たすときだけである。

- `/proc`の走査で、保持者、タグを持つプロセス、調べられないプロセスがいない。
- ロックを待たずに取れる。
- ロックを持ったまま確かめ直して、パスが今もロックしたファイル(同じdevとino)を指し、worktreeが無い。

消すのはロックを持ったまま行い、ロックは消し終わってから放す。削除のシェルは5秒で打ち切る。別の実行の走査は、削除のシェル(とそれが起動したflock、stat、rm)を一瞬の保持者として扱い、走査し直す。

確かめは、消される前の古いファイルを見て空いていると判断することがある。それでも問題が起きないのは次の理由による。

- ロック付きの起動は、そのたびにパスを開き直す。
- 残ったプロセスは、タグ(パス)で見つかる。
- worktreeを作る実行は、作った後にロックを確かめてからロック付きで起動する。

確かめ直した時点でworktreeが無ければ、その実行の起動は消した後の新しいファイルを開く。古いファイルのロックを持つプロセスが残ったまま、別の実行が新しいファイルでロックを取る状態にはならない。

一覧から消えたworktreeの親(gtrのworktreeの置き場所など)は分からない。そこに残ったロックファイルは、同じ親に別のworktreeが一覧に載るまで残る。

### 検査コマンドの実行範囲

検査コマンドは、Claudeが書いたテストやソースを、workerのコンテナ内で非特権のユーザー(`factory-check-N`)として、コンテナの分離なしに実行する。そのため実装フローは、そのリポジトリについて`check_commands_by_repo`に明示したコマンドだけを実行する。`allowed_check_commands`には落とさない。

検査コマンドを実行するときに、作業項目ごとにnoticeの`unsandboxed_check_commands`を記録する。
同じ本文の未解決のnoticeがあれば、新しく作らず、作成から1日を過ぎていれば時刻を更新する。
networkとworkerの資源を共有するので、Issueを信頼できる人だけが起票するリポジトリにだけ、このエントリを設定する。

検査の間、worktreeと`HOME`の所有者は、取った枠のユーザーである。
検査コマンドが書き込めるのは、worktree、その`HOME`、共有の一時ディレクトリ(`/tmp`、`/var/tmp`、`/dev/shm`、`/dev/mqueue`、`/run/lock`)だけである。
`TMPDIR`は`HOME`の下を指すので、一時ファイルは他の枠から読めない。
`HOME`の`.gitconfig`は、worktreeだけを`safe.directory`にする。
検査の中のテストが`GIT_`で始まる環境変数を外してgitを起動しても、枠のユーザーがrootの所有のmain cloneの`.git`を読めるようにするためである。
検査が終わると、worktreeの所有者はrootに戻り、`HOME`は消える。
枠は別のリポジトリの検査に使い回すので、枠を取るたびに、前の実行がそのuidで残したものを消してから使う。
同時に動く検査は1つなので、枠が全部埋まることは通常ない。埋まっていれば、空くのを最大5分待つ。
main cloneの`.git`は書き換えられないので、検査コマンドの中のgitは、indexを書く`git add`と`git commit`が失敗する。
仕組みは[セキュリティ](../security.md#検査コマンドの権限)にある。

lockfileは保護パスなので、Claudeが書き換えたラウンドでは検査コマンドを実行しない。

### 対象リポジトリのCI

実装ブランチのpushとPRの作成で、対象リポジトリ自身の`push`と`pull_request`のCIが動く。
atelier-worksのCIは`main`のpushと`pull_request`でだけ動くので、実装ブランチのpushでは動かず、PRの作成から動く。
CIは、人のレビューより前に、Claudeが書いたコードをそのリポジトリのsecretsを使える状態で実行しうる。対象リポジトリのCIの権限とsecretsの範囲は、この前提で設定する。

### 保護パスの記録

保護パスの変更は、止めずにPR本文とDiscordに列挙する。保護パスを変えたラウンドでは検査コマンドを実行せず、検査はGitHub側のCIに任せる。Claudeが書き換えた`mise.toml`や`package.json`のscriptsをworkerで実行すると、Issue本文を経由してコードを実行させる経路になるためである。

列挙するのは次の3種類である。

- 保護パスに当たる変更
- 新しく追加した`*.sh`
- `package.json`の`scripts`の変更

保護パスは`f/factory/lib/protected_paths.ts`の3つの定数で決める。

- ディレクトリ: `IMPLEMENT_PROTECTED_PATH_PREFIXES`
- 個別のファイル: `IMPLEMENT_PROTECTED_EXACT_PATHS`。PR修正の一覧と同じで、[PRワークフロー](pr-workflow.md)の[禁止パスによる停止](pr-workflow.md#禁止パスによる停止)にある。
- ファイル名: `IMPLEMENT_PROTECTED_BASENAME_PATTERNS`

ディレクトリとファイル名は、PR修正の一覧に次を加えたものである。

| 種類 | 加えるもの |
| --- | --- |
| ディレクトリ | `.github/`全体(PR修正の`.github/workflows/`と`.github/actions/`を広げる)、`infra/`、`.husky/`、`.githooks/`、`.yarn/`、`.devcontainer/` |
| gitleaks | `.gitleaksignore`、`.gitleaks.toml` |
| ランタイムのバージョン | `.python-version`、`.nvmrc`、`rust-toolchain` |
| パッケージマネージャー | `.yarnrc`、`.pnpmfile.cjs`、JavaScriptのlockfile、すべての`package.json` |
| ツールの設定 | `*.config.[cm][jt]s`、`.eslintrc`、`.babelrc`、`.prettierrc` |
| タスクランナーなど | `Makefile`、`Justfile`、`Taskfile.yml`、`turbo.json`、`nx.json`、`deno.json`、`CODEOWNERS`、`.pre-commit-config.yaml` |
| JavaScript以外のlockfileとmanifest | `uv.lock`、`poetry.lock`、`Pipfile`、`pyproject.toml`、`setup.py`、`setup.cfg`、`requirements*.txt`、`Cargo.toml`、`Cargo.lock`、`go.mod`、`go.sum`、`Gemfile`、`composer.json`、`composer.lock` |

PR修正の一覧そのものの中身は、[PRワークフロー](pr-workflow.md)の[禁止パスによる停止](pr-workflow.md#禁止パスによる停止)にある。markdownlint-cli2とtextlintの設定は、PR修正の一覧に含まれる。

`infra/`を加えるのは、workerのイメージとcomposeの定義の変更が、次にホストで`mise run up`するまで反映されないからである。レビューする人がその変更を知る必要がある。

保護パスの一覧は、Factory自身に限らず、実装フローが扱うすべてのリポジトリに効く。
ほかのリポジトリに`infra/`、`console/public/`、`console/index.html`などがあれば、それに触れたラウンドは検査コマンドを実行しない。
そのときは、GitHub側のCIの結果を見る。
Factory自身のリポジトリでは、ホストの実行役が実行するファイルも保護パスである。
対象は、`scripts/doctor.sh`、`scripts/bootstrap.sh`、`scripts/custom-tags.ts`、実行役のテストである。
`scripts/check-idle.ts`と`tests/scripts/check-idle.test.ts`も対象に含む。
これらに触れたラウンドも、検査コマンドを実行せず、PR本文の「確認して欲しい点」に載せる。
理由と限界は、[ホストの実行役の境界](../security.md#ホストの実行役の境界)にある。

判定は、比較の基準からの差分で行う。前のラウンドや前回の実行でコミット済みの変更も、毎回判定する。renameは元のパスの削除と新しいパスの追加として扱うので、保護パスから外への移動も捕まえる。

変更パスは`git diff -z --name-status`で取得する。引用符付きのパス(非ASCII文字や制御文字を含むもの)でも、保護パスの判定を素通りしない。

### symlinkの変更の停止

比較の基準からのステージ済みの差分(`git diff --cached --raw -z`)に、変更前か変更後のモードが`120000`のエントリがあれば、人の対応待ちにする。新規作成、変更、削除、typechange、renameのどれも対象である。ファイルシステムではなくgitのモードで判定するので、worktreeに残っていないsymlinkも捕まえる。

### worktreeの.gitの検証

Claudeは`Edit`と`Write`で、worktree直下の`.git`(gitdirへの参照)も書き換えられる。参照先を別のディレクトリに向けると、そこに置いた`config`のfilterなどを、次の`git add`がrootで実行する。

準備のステップは、worktreeを作った直後に`.git`を1回だけ読み、その中身で検証して記録する(`verifyWorktreeGitdir`)。検証は次の3点である。

- `.git`が、gitの書く正規の形`gitdir: <絶対パス>`そのものである。空白の数やタブが違うと、gitは別のディレクトリを読むため拒否する。
- `realpath`で解決した先が、`<main clone>/.git/worktrees/`の直下にある。
- その`gitdir`の戻り参照が、worktreeを指している。

以降は、worktreeでgitを実行する前に、`.git`が記録と一致する通常のファイルであることを確かめる。確かめるのは、各ラウンドの冒頭、途中経過のpushの前、最終のコミットの前である。違えば何も実行せずに人の対応待ちにし、途中の変更もpushしない。

次の2つの時点でも確かめる。Claudeの不正な出力への再試行の前と、検査コマンドの後で修正ラウンドのClaudeを起動する前である。違えば、再試行と起動をしない。確かめ自体が失敗したときも再試行しない。最初の試行の記録(費用)はそのまま残す。

既存のworktreeを再利用するときは、中でgitを実行する前に同じ検証をする。PR修正も同じである。通らなければ、worktreeの中でgitを使わずにディレクトリを削除する。続けて`git worktree prune`を実行し、worktreeを作り直す。削除の対象は、`git worktree list`が報告したパスのうち、リポジトリの作業ディレクトリの配下にあるものだけである。

worktreeを消すとき(要件定義への差し戻しや掃除)も、検証に通らなければ`git worktree remove`を使わずに同じ方法で消す。

### 差分の大きさの上限

差分の上限は、実装フロー専用の`implement_max_changed_files`と`implement_max_diff_lines`で決める。どちらかを超えたら人の対応待ちにする。

PR修正の、headブランチが保護ブランチかデフォルトブランチなら止める確認は、実装フローには適用しない。実装フローはPRごとに新しいブランチを作ってpushし、保護されたbaseやデフォルトブランチには直接pushしないからである。

### gitleaksによる秘密情報の検査

gitleaksは、検査コマンドの設定に関わらず、毎ラウンド実行する固定の検査である。
毎ラウンド、差分をすべてステージし、そのツリーを`git write-tree`で記録する。
比較の基準からそのツリーまでの差分全体を次のコマンドで取り出し、追加された行を`gitleaks stdin --redact`に標準入力で渡す。

```bash
git diff --text --no-ext-diff --no-textconv -U0 <merge-base> <tree>
```

索引ではなく記録したツリーと比べるので、検査した内容とそのツリーはちょうど一致する。
検査したツリーと、そのラウンドで変更を判定したツリー(指紋)が違えば、検査コマンドを実行せずにそのラウンドで止める(`worktree_changed`)。

gitleaksは私有の一時ディレクトリで実行する。対象リポジトリの内容で検出を無効にさせないため、次のように起動する。

- 既定のルールだけを`--config`で強制する。
- `--gitleaks-ignore-path`をその一時ディレクトリに向ける。
- `--ignore-gitleaks-allow`を付ける。

このため、次のどれでも検出を無効にできない。

- `.gitleaks.toml`(壊れたものを含む)と`.gitleaksignore`
- 行の中の`gitleaks:allow`のコメント
- `.gitattributes`の`binary`と`-diff`の指定、textconv

前のラウンドや前回の実行でコミット済みの変更も、毎ラウンド検査する。検出結果は、ルール名とファイル名だけをClaudeへの修正の依頼とDBに渡し、一致した文字列は渡さない。

次の場合は検査の失敗として扱う。

- 検査する差分(上限32MiB)かレポート(上限8MiB)が出力の上限を超えた
- どちらかの出力の読み取りを打ち切った([子プロセスの停止](#子プロセスの停止)を参照)
- 終了コードが0と1以外だった

### 検証したツリーだけのコミット

検査に通ったラウンドと、検査コマンドを動かさなかったラウンドでは、ステージ済みのツリー(`git write-tree`)を記録する。
完了のステップは、コミットする直前にもう一度ステージして、記録と一致することを確かめる。
検査コマンドが追跡対象のファイルを書き換えた場合など、検証の後にworktreeが変わっていれば、pushせずに人の対応待ちにする。

`commitAndPush`はステージし直すので、commitの直前にも索引の`git write-tree`を同じツリーと比べる(`inspectStaged`)。
比べる先は、途中経過ならgitleaksが検査したツリー、最終のcommitならループで検証したツリーである。
違えば、commitとpushのどちらもしない。
理由は、途中経過では`worktree changed after the secret scan`、最終のcommitでは検証の後にworktreeが変わった旨になる。

commitの後、pushの前には、作ったcommitのツリーが比べたツリーと同じことを確かめる。
違えばcommitを取り消し、`committed tree differs from the inspected tree`を理由にする。

### pushする履歴の制限

途中経過と最終のcommitでは、`git add -A`の前に次を確かめる(`commitAndPush`の`requireLocalHeadAtExpected`と`expectedBranch`)。

- ローカルのHEADが、準備のステップの記録したブランチの先頭(`expected_head_sha`)である。
- HEADが実装ブランチにある。

ループはcommitしないので、HEADが動いていれば、検査コマンドがcommitかブランチの切り替えをしている。
そのcommitは差分の検査に現れない(後のcommitで消した秘密情報など)のに、pushすると履歴ごと送られる。
そのため、pushせずに人の対応待ちにする。

pushは`HEAD`ではなく、作ったcommitのshaを送る。
そのため、送る履歴は記録した先頭と、新しい1つのcommitだけになる。

準備のステップの空のブランチのpush(`pushNewBranch`)も、ローカルのブランチを送らない。
リモートにブランチが無いときは、ローカルのブランチを`update-ref --no-deref`で既定のブランチの先頭へ向け直す。
送るのは、リモートに問い合わせた既定のブランチの先頭のshaである。
リモートのブランチだけが消えた後は、検査コマンドのcommitがローカルのブランチに残りうるためである。
例えば、要件の不足の差し戻しでローカルのブランチの削除だけに失敗したときと、人がGitHubでブランチを消したときである。
削除して作り直さずに向け直すのは、checkout中のブランチも1回の操作で動かせ、worktreeを消さずに済むためである。

向け直すと、ローカルにだけあったcommitはブランチから外れる。
gitのreflogには残る。
人がGitHubで消したブランチは、消す前の状態には戻さず、既定のブランチの先頭から作り直す。

既定のブランチの先頭は、ローカルの`refs/remotes/origin/HEAD`と追跡refを信じず、`git ls-remote --symref`の1回でリモートに問い合わせる。
問い合わせるのは、リモートの`HEAD`、実装ブランチ、既定のブランチである。
検査コマンドはメインのcloneの`.git`を書き換えられ、`--prune`なしのfetchは書き換えられた`refs/remotes/origin/HEAD`を直さないためである。
次のどれかに当たれば例外を投げ、ローカルのブランチを動かさず、何もpushしない。

- リモートの`HEAD`が、ローカルの`refs/remotes/origin/HEAD`から読んだ既定のブランチでない。
- リモートに既定のブランチが無い。
- ローカルの追跡ref(`refs/remotes/origin/<base>`)が、リモートの既定のブランチの先頭と違う。

この照合は、リモートに実装ブランチがあるときもする。
準備のステップは、照合したリモートの既定のブランチの先頭のshaから、比較の基準(`git merge-base -- <sha> HEAD`)を求めるためである。
短い名前の`origin/<base>`は引き直さない。
検査コマンドが作る`refs/heads/origin/<base>`や`refs/tags/origin/<base>`が、追跡refより先に解決されうるためである。
照合で、そのshaがローカルにあり、追跡refと同じことも確かめる。

ローカルの追跡refは、どの箇所も`refs/remotes/origin/<branch>`の完全な名前で読む。
読み取りは`readExactRef`に集めている。
対象は次の箇所である。

- `currentRemoteHeadSha`
- `commitAndPush`の先頭の照合と、pushを拒否されたときの再読み取り
- worktreeを再利用するときの`reset --hard`
- `pushNewBranch`の、ローカルの追跡refとリモートの照合
- `ensureFactoryClone`の、ブランチを切り替える前の追跡refの確認
- 準備のステップの既定のブランチの先頭と名前(`refs/remotes/origin/HEAD`)

`git show-ref --verify`は、名前が完全に一致するrefだけを返す。
`git rev-parse`は完全な名前でも、追跡refが無いと`refs/heads/refs/remotes/origin/<branch>`のようなrefへ解決し直す。
追跡refの代わりに別のcommitを読んでしまうため、`rev-parse`は使わない。
`readExactRef`が`null`を返すのは、gitがrefは有効でないと報告したときだけである。
safe.directoryやロックの失敗は、理由を隠さずstderrつきで例外にする。

`git gtr new`は、ブランチがリモートとローカルのどちらにも無いとき、短い名前の`origin/<既定のブランチ>`から作る(gtr 2.11.1のソースで確かめた)。
`refs/heads/origin/<既定のブランチ>`が置かれていると、別のcommitから作られる。
そのため、作った後にブランチの先頭を、完全な名前で読んだ値と照合する。
照合の相手は、リモートにブランチがあればその追跡ref、無ければ`refs/remotes/origin/HEAD`である。
違えば、検証したshaへ`reset --hard`して`clean -fdx`をする。
誤ったcommitのtreeが置いたファイルのうち、検証したtreeの`.gitignore`が除外するものも消すため、`-x`を付ける。
すでにあったローカルのブランチが追跡ref(無ければ`refs/remotes/origin/HEAD`)と違うときも、使い回しの経路と同じくそろえる。
gtrは既定のブランチを`gtr.defaultBranch`、`GTR_DEFAULT_BRANCH`、`.gtrconfig`から取ることがある。
Factoryはこの設定を意図して無視し、照合は常に`refs/remotes/origin/HEAD`と比べて、違えばそこへ戻す。
`f/factory/`のコードに短い名前の`origin/...`を書くと、`scripts/lint-no-short-remote-ref.ts`が止める。

`git gtr new`には`--no-hooks`を付け、gtrのpostCreateフックを動かさない。
照合で作り直す前の、誤ったcommitのtreeの中で、フックのコマンドを実行させないためである。
gtrのファイルのコピーはメインのcloneから読むので、そのtreeは読まない。
Factoryはこのフックに依存するセットアップを持たない。
依存のインストールなどは、`check_commands_by_repo`の検査コマンドが実行する。

向け直しの後でpushに失敗したときは、ローカルのブランチが既定のブランチの先頭を指し、worktreeには古いファイルが残る。
リモートにはまだブランチが無いので、次の実行がもう一度向け直してpushし、再利用の経路でworktreeを追跡ref(`refs/remotes/origin/<branch>`)の先頭へ戻す。

### pushの前の生き残りのプロセスの確認

完了のステップは、途中経過のpushと最終のcommitの前に、次のプロセスがいないことを確かめる。何も止めない。

- worktreeのロックを持つプロセス
- このロックファイルのタグを持つプロセス

前のステップのClaudeや検査コマンドが残っていれば、検査とcommitの間にworktreeを書き換えうる。
そのため、pushせずに人の対応待ちにし、理由に残っているプロセスを載せる。

### コミットメッセージのIssue参照の無効化

Claudeが書くコミットメッセージの件名と本文では、Issueへの参照を次のように書き換える。既定のブランチへのマージで任意のIssueを閉じたり、無関係なIssueにリンクしたりしないためである。

| 元の表記 | 書き換え後 |
| --- | --- |
| `#12` | `No.12` |
| `owner/repo#12` | `owner/repo No.12` |
| `GH-12` | `GH No.12` |
| IssueやPRのURL | ホストを`github[.]com`にする |

元のIssueとの紐づけは、Factoryが書くPR本文の`Closes #N`だけで行う。件名は72コードポイントを超えると拒否する。

### 子プロセスの停止

git、gh、Claude、検査コマンドは、新しいプロセスグループで起動する。グループで生き残ったプロセス(バックグラウンドに残した子)は、SIGTERMで止め、続けてSIGKILLで止める。止めるのはタイムアウトのときだけでなく、正常に終了した後も同じである。

`setsid`などで別のセッションに抜けたプロセスには、グループへのkillも孤児のClaudeの掃除も届かない。そのため、グループを止めた後、2秒たっても出力のパイプが閉じなければ読み取りを打ち切り、結果に打ち切りの注記を付ける。抜けたプロセス自体はworkerに残る。

打ち切った出力は途中で切れていることがある。そのため、出力を判断に使う実行は、終了コードが0でも失敗として扱う。対象は次のとおりである。

- gitleaksと、それに渡す差分
- 保護パス、symlink、`package.json`のscriptsの判定に使う変更の一覧とファイルの中身
- 差分の大きさ
- 検証したツリーの`git write-tree`
- 検査コマンド

### 検査コマンドの出力の上限

検査コマンドの出力は、ストリームごとに1MiBまでしか保持しない。
超えた分は、先頭と末尾を残して間を捨てる。
DBには、秘密をマスクした出力を16KB以内で保存する。
失敗した検査の出力を先に、通った検査の出力を後に並べる。
16KBに収まらないときは、検査コマンドごとの節で、先頭の約3分の1と末尾の約3分の2を残し、間を省略したバイト数の目印に置き換える。
失敗した検査に厚く割り、通った検査は薄くする。
通った検査には、失敗した検査が使わない余りを回す。
テストの失敗の一覧は出力の末尾に出ることが多く、先頭だけでは先頭の警告やログで上限を使い切る。
連結した全体を一度に切ると、後ろに並ぶ通った検査の出力が末尾の枠を使うので、節ごとに切る。

### pushの拒否

`.github/workflows/`の下を含むpushは、PATに`workflow`の権限が無いとGitHubが拒否する。拒否されたときは、その旨を人の対応待ちの理由に載せる。
