# Consoleの仕様

Consoleのアプリ(`console/`)の構成と、画面をまたぐ仕様を書く。
画面と部品を変更する人が読む。
API層、画面ごとの仕様、成果物を配信する仕組みは、`docs/internals/console/`の各文書にある。
置き場は、末尾の[仕様の置き場](#仕様の置き場)の表から引ける。
何を守るかと残るリスクは、[セキュリティ](../security.md)の「Consoleの配信」にある。
画面に何を表示するかの原則は、[Consoleの画面の表示の原則](../console-display.md)にある。

## アプリの構成

ConsoleはSPAである。
Vite、React、TypeScript、Tailwind CSS、shadcn/uiの部品で作る。
経路はReact Router、データの取得はTanStack Queryで扱う。
画面の判定は純関数に切り出して`bun test`で確かめる。
画面の部品は、`renderToStaticMarkup`で静的に描いたHTMLを`bun test`で確かめる。
`bun test`にDOMの環境が無いため、DOMを動かすテストは書かない。
クリックなどの操作の結果は、判定を純関数に切り出して確かめる。

| ディレクトリ | 役割 |
| --- | --- |
| `src/api/` | scriptの呼び出し、失敗の分類、応答の型ガード、取得 |
| `src/app/` | 外枠、サイドバー、経路の表、ログインの状態、Provider |
| `src/screens/` | 画面。入口ごとのディレクトリに置く |
| `src/components/` | 共通の部品。`ui/`はshadcn/uiの部品を写したもの |
| `src/lib/` | 表示と判定の純関数 |

shadcn/uiの部品は、CLIを使わず、new-yorkのソースを手で`src/components/ui/`に写す。
importは相対パスにし、型アサーションは外す。
`as`を禁じる検査が、`console/src/`にもかかるためである。

## 見た目の体系

色の定義は`src/index.css`の変数だけにする。
値は`light-dark()`で書き、`html`の`data-theme`が配色を決める。
`data-theme`が無いときだけ、OSの設定に従う。
文字と背景の組はWCAG AAの4.5:1以上、入力欄の境界は3.5:1以上、フォーカスの輪と点のような図形は3:1以上を保つ。

| 区分 | 決まり |
| --- | --- |
| 面 | 背景、面(`card`)、浮いた面(`popover`)の3段で重ねる。ダークは明るさの差、ライトは線と影で階層を出す。背景は真っ黒にしない |
| アクセント | 藍(`primary`)の1色。選択中の枠線と帯、主要な操作、フォーカスの輪に使う |
| 選択中 | 期間と種類の切り替えの選択中は、藍の枠線と藍寄りの面(`src/lib/selectedStyle.ts`)で示す。面の明るさの差は両テーマで小さいため、枠線で未選択と分ける。この2つは文字の太さを変えない。文字幅が動くと隣の項目がずれるためである。試行の切り替えとタブは、この表し方の対象外である |
| 意味の色 | 承認は青(`approval`)、失敗は赤(`destructive`)、通知は琥珀(`warning`)、成功は緑(`success`)。点、バッジ、ラベルに使う |
| 文字の濃さ | 主(`foreground`)、副(`muted-foreground`)、補足(`subtle-foreground`)の3段 |
| 文字の大きさ | 6段(`text-caption`、`text-small`、`text-body`、`text-lead`、`text-title`、`text-display`)。大きさと行間の値は[`src/index.css`](../../console/src/index.css)の`--text-*`が定める |
| 角丸と影 | 角丸は5段、影は3段で、値は`index.css`のトークンが決める([角丸と影](#角丸と影)) |
| 書体 | システムの書体を使い、Webフォントを読み込まない([書体](#書体))。ID、SHA、ジョブID、ログは等幅で出す([等幅](#等幅)) |
| 数字 | 件数や時刻は`tabular-nums`で桁をそろえる |
| 動き | 長さとイージングはトークンで決める([動きのトークン](#動きのトークン))。テーマの切り替えの間は、全要素の遷移を止める([テーマの切り替え](#テーマの切り替え)) |

通知の点は、図形用の`notice-mark`で描く。
図形の基準(3:1)で足りるため、文字の`warning`と色を分ける。

文字と背景の組が基準を満たすことは、`src/theme-tokens.test.ts`が`index.css`を読んで確かめる。
対象は、面の上の文字、意味の色の文字、薄く重ねた面(バッジと帯)の上の文字、入力欄の境界・フォーカスの輪・通知の点などの図形である。
入力欄の境界は、背景、面、浮いた面の上で、ライトとダークの両方とも3.5:1以上にする。
3:1の基準に余裕を持たせ、面の明るさが少し変わっても下回らないようにするためである。
入力欄は、ダイアログの中では浮いた面の上に載る。
入力欄の枠の色(`--input`)は、入力欄、選択欄、複数行の入力欄だけが使う。
図の箱の線とスクロールバーは、元の濃さ(3:1以上)を保つ別の色(`--edge`)を使う。
`--input`を図やスクロールバーにも使うと、入力欄の枠の濃さを変えるたびに、図とスクロールバーまで変わるためである。
使う側が増えていないことは、`src/visual-tokens.test.ts`が確かめる。
`-foreground`で終わる色と、その元の色の組も、定義されたすべてをライトとダークの両方で確かめる。
選択中の枠線は、面とトラックの上で3:1以上を保つ。
承認、失敗、通知の違いは、色だけに頼らず、隣の文字でも伝える。

文字の大きさ(`text-*`)を足したら、`src/lib/cn.ts`の`FONT_SIZES`にも足す。
足し忘れると、`cn`が大きさを文字色と見なし、同じ要素のどちらかを落とす。
足し忘れは、`src/lib/cn.test.ts`が検出する。
`FONT_SIZES`と`index.css`の大きさの一覧が違うと、このテストが失敗するためである。

6段の外の大きさ(`text-sm`、`text-xs`、`text-[11px]`など)は書かない。
`src/visual-tokens.test.ts`が、ソースの中の直書きを検出する。
段が揃っていないと、同じ役割の文字が画面ごとに1〜2px違い、読み手が違いを意味と取り違えるためである。
`BarChart`のラベルは`text-caption`で描き、幅の見積もりは[`src/lib/barChart.ts`](../../console/src/lib/barChart.ts)の`LABEL_FONT_SIZE`の固定のpxで行う。
`--text-caption`と見積もりの一致は、[`counts a full-width character as the text-caption size of index.css`](../../console/src/lib/barChart.test.ts)で確かめる。
残る制限がある。
基準の文字サイズを変えた利用者では、ラベルがremで拡縮する一方、見積もりは固定のpxのままである。
そのため、ラベルの間引きと端の寄せがずれる。
flowの図(`FlowDiagram`)と起動の図(`OriginDiagram`)のSVGの`<text>`だけは、文字の大きさの直書きの検出から外す。
この検出は`src/visual-tokens.test.ts`のもので、axe-coreの検査とは別である。
図は、箱の幅や文字の幅の見積もりを、描く文字の大きさの数値から計算する。
大きさをトークンに替えると、見積もりが実物とずれて、文字が箱をはみ出す。
同じファイルのHTMLの部分は、検出の対象に残す。

表示する日本語は`src/lib/labels.ts`に集める。
画面は、状態や種類の生のコードを出さない。
表に無い値は、元の文字列ではなく決まった文言で出す。
backendの値が表から漏れていないことは、`tests/scripts/console_summary_contract.test.ts`が確かめる。

### 部品の置き場所

`src/components/ui/`には、Consoleの語や画面を知らない部品を置く。
shadcn/uiの部品を写したものと、同じ作りの自前の部品(`Card`、`Dialog`、`Field`)が入る。
`src/components/`には、複数の画面が使い、Consoleの語や挙動を知っている部品を置く。
`ToggleChip`、`ConfirmDialog`、`Tabs`がこれにあたる。
1つの画面だけが使う部品は、その画面のディレクトリに置く。
別の画面が使い始めたら、`src/components/`へ移す。

切り替えの組は`ToggleChip`で作る。
種類と範囲の2つが使い、選択は`fieldset`、`button`、`aria-pressed`で示す。
試行の切り替えは`nav`と`Link`と`aria-current`で作るので、`ToggleChip`を使わない。

面、ダイアログ、入力の項目は、部品で作る。

| 部品 | 決めること |
| --- | --- |
| `Card` | 角丸の枠と面。`variant`は、中身のある面(`default`)、行を線で区切る面(`list`)、破線の面(`empty`、使い分けは下に書く)の3つである。余白は`padding`の段で選び、個別の余白は足さない。面の横の余白はどの段でも同じにし、段は縦の余白で分ける。段の値は[`src/components/ui/card.tsx`](../../console/src/components/ui/card.tsx)の`cardVariants`が定め、横の余白がそろうことは[`gives every padded step the same horizontal padding`](../../console/src/components/ui/card.test.tsx)で確かめる。文書を読ませる面(監査レポートの本文)だけは、長い本文を読みやすくするため、画面の幅に応じて横の余白を変える例外である。描く要素は`tag`で選ぶ |
| `Dialog` | ブラウザ標準の`<dialog>`の外枠と、開閉の同期(`useDialogSync`)。位置は、中央(`center`)と上寄せ(`top`)の2つである。`ConfirmDialog`、ショートカットの一覧、コマンドパレットが使う |
| `Field` | ラベル、入力欄、補足、字数、エラーの組。ラベルを入力欄に結び、補足、字数、エラーを`aria-describedby`で入力欄に結ぶ。字数は、補足とエラーと同じ行の右に置く。誤りのときは、字数も誤りの色にする。ラベルの段は、縦に並ぶ入力の`form`(`text-body font-medium`)と、絞り込みの行やダイアログの小さな入力の`filter`(`text-small text-muted-foreground`)の2つである |

結線を入力欄ごとに書くと、補足、字数、エラーが読み上げに結ばれない入力欄が残る。
`Field`は、入力欄を描く関数を子に取り、渡した`id`、`aria-describedby`、`aria-invalid`を入力欄に展開させる。

入力の誤りで送信が止まったときは、フォームの中で`aria-invalid`が付いた最初の入力欄へ、フォーカスを移す(`useFocusFirstInvalid`、`src/lib/`)。
入力欄の下に誤りを出すだけでは、画面の読み上げが、入力欄へフォーカスが移るまで誤りを伝えないためである。
移った入力欄では、読み上げがラベルと、`Field`が結んだ誤りの説明を伝える。
「最初」は文書の順で、画面の並びと同じである。
誤りが無いときと、誤りを出した後の入力の途中の描き直しでは、フォーカスを動かさない。
最初の誤りの入力欄に、すでにフォーカスがあるときは、`focus()`を呼んでもイベントが起きず、読み上げは何も伝えない。
そのときだけ、視覚的に隠した領域(`InvalidStatus`、`role="status"`)に「入力に誤りがあります(n件)」を書く。
件数を書くのは、フォーカスの移動が起きない場面でも、誤りがあることを伝えるためである。
領域は最初の描画から置く。
読み上げは、後から現れた領域の中身を伝えないことがあるためである。
同じ文を続けて書いても読み直されるよう、送信のたびに中の要素を作り直す。
誤りの要約は置かない。
欄は最大8つで、補足と誤りの文は`Field`が各欄に結ぶので、移した欄で足りるためである。
新規投入とPRレビューの投入が使う。

投入の2画面は、送信中と結果を待つ間に、送信のボタンを`disabled`にしない。
`disabled`にすると、押した位置のフォーカスが外れ、結果の通知もその位置で受けられないためである。
ボタンは`aria-disabled`にし、新規投入の入力欄は読み取り専用にする。
押しても何もしないことは、`decideSend`(`src/lib/`)が決める。
画面は、`decideSend`の戻り値を`switch`で分ける。
値は、止める、誤りを出す、送るの3つである。
止めている間は、誤りの表示もフォーカスの移動もしない。
誤りの無い送信に進むときは、読み上げ専用の領域に残った前の誤りの件数を消す。
誤りが直った後も、誤りがあるように聞こえるのを防ぐためである。
結果が出ても、フォーカスは動かさない。
結果の知らせは`role="alert"`で伝わるためである。

読み取り専用の入力欄(`Input`、`Textarea`)は、半透明にしない。
背景を`muted`に変え、枠を破線にして、カーソルを禁止の形にする。
半透明にすると、文字が背景に近づき、ライトのテーマで文字の4.5:1を割るためである。
`disabled`は色の検査の対象外だが、読み取り専用は対象になる。
文字の色は変えず、境界の3.5:1も保つ。
背景の差はダークのテーマで小さいので、破線の枠を、背景以外の手がかりとして足す。
3つの指定は、`read-only:enabled:`に絞る。
`disabled`の入力欄(承認バーの却下理由)にも読み取り専用の疑似クラスが当たるが、`disabled`には、すでに半透明と禁止のカーソルがあるためである。

新規投入の進め方のラジオは、送信中も`disabled`を付けられない。
`disabled`にしないので、矢印キー、スペース、ラベルのクリックが、選択とフォーカスを動かしてしまう。
`blocksRadioInput`(`src/lib/`)が、送信中はこれらの操作を止めると判定し、画面が既定の動作を止める。
Enterは、送信中かどうかによらず止める。

`aria-disabled`のボタンは、hoverの見た目を出さない。
`Button`は、variantごとのhoverの指定をそのまま持ち、`aria-disabled:hover:`で元の面と文字へ戻す。
戻す値は[`src/components/ui/button.tsx`](../../console/src/components/ui/button.tsx)の`buttonVariants`が定め、[`cancels the hover style of %s`](../../console/src/components/ui/button.test.ts)で確かめる。
hoverで変わる性質のすべてを戻すことは、[`pairs every hover property of %s with a cancel`](../../console/src/components/ui/button.test.ts)で確かめる。
`outline`と`ghost`の文字を`text-current`に戻すのは、`outline`と`ghost`が文字の色を持たず、親から継ぐためである。
`not-aria-disabled:`は使わない。
使うと、`aria-disabled`でない通常のhoverの詳細度が上がり、`className`でhoverを上書きする呼び出し(期間切替の`SELECTED_STYLE`)の指定に負けるためである。
`aria-disabled:hover:`は、`[aria-disabled=true]:hover`として出力され、`:where()`で包まれない。
通常のhoverより詳細度が高いので、`aria-disabled`のときだけ、元の色が勝つ。
`pointer-events: none`は使わない。
クリックが下の要素へ抜けて、押した位置のフォーカスが外れるためである。

禁止のカーソル(`aria-disabled:cursor-not-allowed`)は、`Button`の共通のclassに置かない。
`aria-disabled`にするほかのボタンの見た目を変えないためである。
投入の2画面の`aria-disabled`のボタンだけが、`className`で足す。
新規投入の送信、再送、破棄と、PRレビューの投入の送信である。

空であることの標準は、実線の`EmptyNote`(`src/components/`)である。
中身のある面と同じ見た目で、一覧や節が空であることを短い文で伝える。
破線の面(`Card`の`empty`)は、次の2つに使う。

- 一覧が入るはずの高さを保つ広い版(`spacious`)。
  空になっても下の要素が動かない。
- 操作の面の代わりに置く知らせ(標準の版`compact`)。
  期限切れ、待機中、扱えない種類、取得できない場合がこれにあたる。

破線は、あるはずの面が無いことを示す。
空の一覧を示すだけの所に破線を使うと、同じ空が2通りの見た目になる。

部品にせず、共有のしかたを変えているものがある。

| 対象 | 扱い | 理由 |
| --- | --- | --- |
| 行のリンク | `src/lib/controlClasses.ts`のclassの定数(`ROW_LINK_CLASS`、`ROW_TARGET_CLASS`)で共有する | 要素が`Link`と`button`で違い、部品にすると要素を選ぶ引数が増える。要対応の一覧の行は`button`で、同じ`ROW_LINK_CLASS`を使う |
| アイコンボタン | 同じファイルの`SIDEBAR_ICON_BUTTON_CLASS`で共有する | サイドバーだけが使い、hoverの面と輪の色がサイドバー専用である。別の面に置くなら、その面の色で定数を足す |
| 表 | 同じファイルの`TABLE_CELL_CLASS`(標準)と`TABLE_CELL_COMPACT_CLASS`(詰めた)で、セルの余白の段だけを共有する。数値の小さな表は`DataTable`で描く | 表の枠、行、列の揃えは、表ごとに違う。`th`と`td`で要素が違い、行がリンクになる表、右に寄せる数値の列、利用者の文書から描く表があるので、部品にまとめると引数が増える |
| チェックボックスとラジオ | 同じファイルの`CHECKBOX_CLASS`で共有する | 大きさと選択の色だけが共通で、ラベルとの並びは使う側が決める |
| 左から出すドロワー | `NavDrawer`が、開閉の同期(`useDialogSync`)だけを使う | 外枠の形が`Dialog`と違う。`Dialog`の位置は中央と上寄せの2つで、端に寄せる形を持たない |
| 取得の失敗の表示 | `QueryFailure`と`QueryFailureAlert`を一本化しない | `QueryFailure`は`QueryFailureAlert`を包み、ログイン切れの案内と余白を足す。重複ではない |

表の余白の段は、表の置き場で選ぶ。

| 表 | 段 | 理由 |
| --- | --- | --- |
| 作業項目の一覧(`PipelineTable`) | 標準 | 本文の大きさの文字(`text-body`)で、列が多い表を読む |
| 数値の表(`DataTable`。レポートの3か所) | 詰めた | 小さい文字(`text-small`)の数値を縦に並べる。行が多いと高さを抑えてスクロールさせるので、1画面に見える行を増やす |
| 要件定義書と設計書の本文の表(`Markdown`) | 標準 | 本文の文字の大きさで、偶数行の縞と合わせて行を追う。詰めた段では、行の区切りが読みにくい |
| 監査レポートの本文の表(`AuditMarkdown`) | 標準 | 表が本文の段落に近く、段落と同じ読みやすさを保つ |

`Markdown`と`AuditMarkdown`の表は、余白の段が同じである。
違いは、`Markdown`の表だけが、偶数行の縞とヘッダーの背景を持ち、横にはみ出す枠をキーボードで操作できることである。
`AuditMarkdown`の表は、別の画面の本文なので変えない。

確認ダイアログの影は、浮いた面の影(`shadow-raised`)にそろえる。
`Dialog`が外枠、角、影、背面の幕を決めるので、`ConfirmDialog`を使うダイアログは、外枠、余白、影が同じになる。
余白は[`src/components/ConfirmDialog.tsx`](../../console/src/components/ConfirmDialog.tsx)の`ConfirmDialog`が持つ。
`Dialog`の`onClose`は、利用者の操作(Escなど)で閉じたときだけ呼ぶ。
`open`を偽にして閉じたときは、親がすでに知っているので呼ばない。
閉じるたびに要る後始末は、`onClosed`に書く。
開いたときの初期フォーカスは、取り消しのボタンに置く。
Enterの押し間違いで実行させないためである。

### ブランドの印

`BrandMark`は、Factory Consoleの印をSVGで描く。
外部のファイルを読まないので、CSPの制限を受けない。
大きさは`className`で決める。
広い画面のサイドバーとドロワーの上端は既定の大きさ、狭い画面の上端の帯は一段小さい大きさにする。
既定の値は[`src/components/BrandMark.tsx`](../../console/src/components/BrandMark.tsx)の`BrandMark`に、狭い画面の値は[`src/app/Sidebar.tsx`](../../console/src/app/Sidebar.tsx)にある。
色は`primary`と`primary-foreground`を読むので、テーマに追従する。
印は飾りなので読み上げから外し、隣に名前の文字を置く。

読み込み中の表示には使わない。
読み込み中の表示は、実物の形を示して、読み込み中と空を見分けさせるためにある。
印を回したり脈打たせたりしても、運用者の判断の材料にならない。

### 動きのトークン

動きの長さとイージングは、[`src/index.css`](../../console/src/index.css)の`@theme`のトークンが定め、3つのトークンがあることは[`index.css defines %s`](../../console/src/motion.test.ts)で確かめる。

| トークン | 使う所 |
| --- | --- |
| `--duration-fast` | hoverとfocusでの色の変化、矢印の回転、選択の帯の現れ方、確認のダイアログと背面の幕が開くときのフェード |
| `--duration-moderate` | サイドバーの幅の変化 |
| `--ease-standard` | すべての遷移 |

Tailwind v4は、`--duration-*`から長さのユーティリティを作らない。
そのため`duration-(--duration-fast)`の形で読む。
`--ease-*`は、`ease-standard`のユーティリティになる。
色、回転、幅の遷移の組は、`src/lib/motionClasses.ts`の定数にまとめる。
`duration-150`のような数値の直書きは、`src/motion.test.ts`が検出する。

動きを減らす設定は、`index.css`の全要素への1つの規則が受ける。
部品ごとに`motion-reduce:`を付けると、付け忘れた要素だけが動き続けるためである。
規則は、遷移と回転の長さと遅延を実質0にし、滑らかなスクロールを止める。
宣言の値は[`index.css declares %s in the one rule`](../../console/src/motion.test.ts)で確かめる。
部品には`motion-reduce:`と`motion-safe:`を書かない。
書いたものは`src/motion.test.ts`が検出する。
JavaScriptで動かすものは、`matchMedia('(prefers-reduced-motion: reduce)')`で動かすかどうかを分ける。

### 書体

本文は、システムの書体で描く。
`--font-sans`は、Hiragino Sansから始めて、Meiryoまで日本語の書体を並べ、最後にsystem-uiを置く。
並びは`index.css`にある。
等幅が要る所は、システムの等幅(Tailwindの`font-mono`)を使う。
Webフォントは読み込まない。
CSPが自分のオリジン以外からの取得を拒むので、外部のサービスが配るフォントは読めない。
日本語のフォントのファイルは大きく、配信する成果物に同梱すると初回の表示が遅れる。

### 等幅

ID、SHA、ジョブID、flowの名前、scriptのパス、ログと出力は、システムの等幅(Tailwindの`font-mono`)で出す。
1文字ずつ読み比べる文字列は、文字の幅がそろうと、桁の違いと取り違えに気づきやすいためである。
本文の日本語は等幅にしない。
等幅のトークンは足さない。
`font-mono`が既にあり、決めるのは書体の並びだけなので、別の名前を持つ理由が無い。

| 出す文字列 | 場所 |
| --- | --- |
| ジョブのID | ジョブの詳細の見出しの副題(`PageHeader`の`subtitleMono`)、中止と再実行の確認 |
| flowの名前、scriptのパス | 中止と再実行の確認、ジョブの詳細、スケジュールの一覧 |
| SHAと版 | サイドバーの版(`ReleaseNote`。「版」の語は本文の書体で、SHAの部分だけを等幅にする)、システムの反映の状態と更新履歴、通知の本文の短縮したSHA |
| ログ、出力、設定の値、失敗の原因の塊 | ジョブの詳細の出力、システムの設定、要対応の失敗の概要 |
| コード | Markdownのコードと、レポートのコード |

ジョブの画面の文字列は、等幅にしても、無害化の部品(`safeText`)を通す経路を変えない。
変えるのはclassだけで、値の取り出しと描画の部品は同じである。

### ブランドの色

ブランドの色は藍(`primary`)で、変えない。
アクセントを藍の1色に絞ると、承認の青、失敗の赤、通知の琥珀、成功の緑が、意味の色として目立つ。
`BrandMark`も`primary`を読むので、印の色は`primary`の定義に追従する。
ライトとダークでは、明るさと彩度を変え、色相はほぼ保つ。

### 角丸と影

角丸と影は、`src/index.css`の`@theme`が値を決める。
部品は`rounded-md`のようなユーティリティの名前で段を選び、値を直書きしない。
任意の値(`rounded-[10px]`)と、段を持たない`rounded`と`shadow`は、`src/visual-tokens.test.ts`が検出する。
値を1か所で決めると、画面ごとに角の丸さが揺れず、段を替えるときも1つのファイルで済む。

角丸は、小さい印から大きい面へ、5段で上げる。
値は既定のまま(Tailwindの既定と同じ)で、変えるときは`index.css`の1行を直す。
値を大きくするかは、実機で見て決める。
値は[`src/index.css`](../../console/src/index.css)の`--radius-*`が定め、[`index.css defines --radius-%s as %s`](../../console/src/visual-tokens.test.ts)で確かめる。

| 段 | 使う所 |
| --- | --- |
| `rounded-sm` | 文字の中の印(コードの背景、見出しのフォーカスの輪) |
| `rounded-md` | 操作の部品(ボタン、ツールチップ、スケルトン) |
| `rounded-lg` | 入力欄、通知の枠、コードの塊 |
| `rounded-xl` | 面(`Card`、`Dialog`) |
| `rounded-2xl` | 画面の中央に置く案内の面 |

点とバッジの`rounded-full`は、段に含めない。
テーマが定義しない段(`rounded-xs`、`rounded-3xl`、`shadow-xs`、`shadow-lg`など)は使わない。
Tailwindの既定の値が効き、トークンを迂回するためである。

影は、浮き方の小さい順で3段である。
色は`--shadow-color`だけから取り、ダークでは濃い影に替わる。
Tailwindの既定の影は薄い黒を固定で使うので、ダークでは見えない。

| 段 | 使う所 |
| --- | --- |
| `shadow-sm` | 面の上に載る主要な操作(ボタン) |
| `shadow-md` | 一時的に浮く小さな面(ツールチップ、トースト) |
| `shadow-raised` | 背面を覆う面(確認のダイアログ、案内の面) |

### ファビコン

ブラウザのタブのアイコンは、`BrandMark`と同じ形のSVGである。
`src/lib/favicon.ts`の`installFaviconIn`が、`data:`のURLにしたアイコンを`<head>`へ`<link rel="icon">`として足す。
`src/main.tsx`が、起動時に`installFaviconIn(document)`を呼ぶ。
`console/index.html`は保護パスで、静的な`<link>`を置けない。
そのため、スクリプトが動くまでは、Windmillの`/favicon.ico`がタブに出うる。
CSPの`img-src`は自分のオリジンと`data:`だけを許すので、外のファイルを読まない`data:`にする。
色はCSSの変数を読めないので、藍(`primary`)のライトの値と、その上の色(`primary-foreground`)を固定する。
形と2つの色が`BrandMark`と`index.css`に合うことと、`main.tsx`の配線は、`src/lib/favicon.test.tsx`が確かめる。
`primary`か`primary-foreground`を変えたら、`favicon.ts`の色も直す。
タブの外の色はブラウザが決めるので、ライトとダークの別は持たない。

### 出入りと画面遷移

出入りの動きとして足してよいのは、確認のダイアログ(`ConfirmDialog`を使うもの)と背面の幕が開くときの、`--duration-fast`の不透明度のフェードだけである。
閉じるときは即時に消す。
ドロワー、トースト、画面遷移には、動きを足さない。

フェードは、`index.css`の`dialog:not([data-nav-drawer])[open]`と、その背面の幕の規則に書く。
`@starting-style`で透明から始め、不透明度の遷移で不透明にする。
動かすのは不透明度だけで、位置と大きさは変えない。
閉じるときに残す仕組み(`overlay`と`display`の離散の遷移)は使わない。
閉じる途中のダイアログが最前面に残ると、まだ押せてしまい、中身も先に変わるためである。
メニューのドロワーは`data-nav-drawer`で除く。
規則は`@layer components`に置き、画面ごとのユーティリティ(`transition-*`など)を黙らせない。
動きを減らす設定の規則は、背面の幕(`::backdrop`)にも効く。
`*`は疑似要素の幕を選ばないので、規則に`*::backdrop`を足している。
`src/motion.test.ts`が、規則の形を確かめる。
運用ツールは、開いた直後の内容をすぐ読む道具である。
長い出入りの動きは読み始めを遅らせ、繰り返し開く操作では邪魔になる。
画面遷移のちらつきは、動きを足さずに、[ちらつきの抑え方](#ちらつきの抑え方)で抑える。
今ある動きは、hoverとfocusの色の変化、矢印の回転、サイドバーの幅、確認のダイアログが開くときのフェード、読み込み中のスケルトンと更新の回転である。
トーストは、sonnerの既定の動きのままにする。

## テーマの切り替え

テーマの選択は、ライト、ダーク、OSに合わせる(`system`)の3つである。
画面の操作は、`ThemeSwitch`の1つのボタンで、いまの配色の反対(ライトならダーク)へ入れ替える。
押すと明示の選択(ライトかダーク)になり、「OSに合わせる」へ戻すボタンは無い。
初めて開いたときだけ、保存が無いので「OSに合わせる」になる。
ボタンのアイコンと名前は、押したときに付く配色を示す。
いまの配色は`html`の`data-theme`から読み、OSの設定の変更で付け替わったときも表示を合わせる。
たたんだサイドバーでも、同じボタンをアイコンだけで残す。
保存するのは選択だけで、保存先は`localStorage`のキー`factory-console.theme`である。
「OSに合わせる」を選んだときは、保存したキーを消す。
知らない値と読めない値は、「OSに合わせる」として扱う。
`resolveTheme`が、選択とOSの設定から`data-theme`の値を決める。
「OSに合わせる」で解決した配色は保存しない。

### OS設定の解決

`html`の`data-theme`は、「OSに合わせる」のときも、OSの設定を読めるかぎり`light`か`dark`で付ける。
OSの配色の設定が変わると、JavaScriptが`matchMedia`の`change`を受けて、`data-theme`を付け替える。
メディアクエリに色を任せると、`change`が届くより前にスタイルの再計算が始まるためである。
この順では、遷移を止める前に、`transition-colors`を持つ要素が途中の色を経由し始める。

選択は`html`の`data-theme-preference`にも残す。
OSの設定が変わったとき、この属性で「OSに合わせる」かを見分ける。
ライトとダークを明示した選択は、OSの設定が変わっても動かさない。
属性が無いときは、`theme-init`が動かなかった場合なので、「OSに合わせる」として扱う。

OSの設定を読めない環境(`matchMedia`が無い、または例外を投げる)では、「OSに合わせる」の`data-theme`を付けず、購読もしない。
`applyThemePreference`に「OSに合わせる」を渡した場合は、それまでの`data-theme`を外す。
その環境では`index.css`の`color-scheme: light dark`が、OSの設定に従う。
ライトとダークを明示した選択は、OSの設定を読まないので、読めない環境でも切り替わり、保存される。

### 描画前の設定

`data-theme`と`data-theme-preference`は、描画の前に`public/assets/`の`theme-init`のscriptが付ける。
描画の後に付けると、最初の表示で配色が替わるためである。
保存した値は`light`と`dark`に完全一致するときだけ受け入れる。
CSPがインラインのscriptを拒むので、scriptは外部のファイルにして、`index.html`の`head`から古典的なscriptとして読む。

ファイル名には内容のハッシュを含む。
配信は`immutable`なので、中身を変えて名前を変えないと、ブラウザが古い中身を使い続けるためである。
内容を変えたら、名前を`contentHashedName`が返す名前に替え、`index.html`の参照も替える。
`console/scripts/public-assets.test.ts`が、名前と内容の対応と、`index.html`の参照を確かめる。

`console/public/`と`console/index.html`は保護パスである。
どちらもバンドルを通らずにそのまま配信され、書き換えられると、全画面で任意のコードが動くためである。
変更を含むPRは人がレビューし、Factoryは自動でマージしない。
一覧は[PRワークフローの安全策の内部仕様](pr-workflow/security.md#保護パスの変更を止める)にある。

### 切り替えの間の遷移の停止

`transition-colors`を持つ要素は一部だけなので、テーマを替えると、それらだけが遅れて変わり、ちらついて見える。
切り替えの間だけ、`html`に`data-theme-switching`を付け、全要素の遷移を止める(`index.css`)。
印を付ける入口は`beginThemeSwitch`の1つで、次の2つの操作が呼ぶ。

- `ThemeSwitch`でテーマを選ぶ(`applyThemePreference`)。
- 「OSに合わせる」のとき、OSの配色の設定が変わる(`followColorSchemeChange`)。

どちらも、遷移を止めてから`data-theme`を替える。
印は2フレーム後に外す。
印を付けたのと同じフレームで、スタイルの再計算が終わっているようにするためである。
外す予約は番号で管理し、先の予約が、後の切り替えの途中で印を外さない。
背景のタブではフレームが進まず、印は表示に戻るまで残る。
残っても遷移が止まるだけである。

OSの設定の購読(`useColorSchemeSwitchGuard`)は、`AppProviders`に1つだけ置く。
`ThemeSwitch`が、広い画面のサイドバーと狭い画面のドロワーの2か所に描かれ、それぞれに置くと購読が重なるためである。
外枠(`AppShell`)には置かない。
ルートのErrorBoundaryが外枠を置き換えた画面でも、OSの設定の変更に追従するためである。
購読は、Strict Modeの購読、解除、購読の順でも、リスナーが1つだけ残る。

## 経路

経路は`src/app/screens.ts`の1つの表から作る。
サイドバーの入口、件数のバッジ、React Routerの経路は、すべてこの表を読む。
routerの基準は`/console`で、Caddyが`/console/`の下のパスに`index.html`を返す。

| パス | 画面 | 状態 |
| --- | --- | --- |
| `/console/` | 要対応 | 承認、失敗、通知の一覧。承認・却下、再実行、通知の解決ができる |
| `/console/items` | 作業項目 | 進捗と要件定義のタブ。`?tab=requirements`で要件定義を開き、`?scope=`で進捗の範囲を指す |
| `/console/items/new` | 新規投入 | Issueを手動で作り、作業項目として登録する入力欄 |
| `/console/items/new-pr-review` | PRレビューの投入 | 既存のPRのレビューを手動で始める入力欄と、始まったかの結果 |
| `/console/items/:id` | 作業項目の詳細 | 概要、要件定義、設計、ラウンド、承認の履歴のタブ。`?tab=<名前>`で開くタブを指す |
| `/console/items/:id/requirements` | 要件定義書 | 本文、目次、図。`?attempt=<k>`で試行を指す |
| `/console/items/:id/design` | 設計書 | 本文、目次、図。`?draft=<id>`で設計書を指す |
| `/console/reports` | レポート | 監査レポートの一覧と手動起動(監査レポートのタブ)、分析のグラフと表(分析のタブ) |
| `/console/reports/audit/:id` | 監査レポート | 作業項目`:id`の本文 |
| `/console/jobs` | ジョブ | 実行中と待ち、履歴、スケジュールのタブ。`?tab=<名前>`で開くタブを、`?status=`と`?script=`で履歴の絞り込みを指す |
| `/console/jobs/flows/:name` | flowの図 | 入口、ステップ、出口を並べた、flow1つの図。名前を省くと一覧へ戻す |
| `/console/jobs/origins/:name` | 起動の図 | 定期ジョブ1つから、前進の辺でたどれるflowを段に並べた図。flowを開くと中のステップが出る。名前を省くと一覧へ戻す |
| `/console/jobs/:id` | ジョブの詳細 | 状態、引数、結果、ログ、フローのステップ、失敗の保存済みの原因 |
| `/console/system` | システム | 要約の帯と4つのタブ(状態、失敗と通知、履歴、設定)。全停止と保留と凍結(置ける、解除できる)、反映の承認待ち(承認と却下ができる)、反映の状態、workerの負荷、監査の失敗、作業項目に紐づかない失敗、情報の通知、更新履歴、解決済みの通知、設定の閲覧。`?section=`で、全停止、反映の承認待ち、保留の区画へ移る([区画への移動](console/system.md#区画への移動)) |

どの経路にも当たらないパスは、「ページが見つかりません」の画面で受ける。
経路の番号は、正の整数の文字列だけを受け付ける。
経路やURLの引数は選択を表すだけで、承認や再実行などの操作は起こさない。

表の1行は、入口の画面と、その下で受ける経路(`children`)を持つ。
`children`は入れ子にでき、親の画面は`Outlet`を描く。
どの経路にも`ErrorBoundary`が付き、省くと既定の`RouteError`になる。
画面の読み込みや描画が失敗すると、その画面の位置にだけ再読み込みの案内を出し、サイドバーと帯は残す。
表から作る経路の一覧は、`src/app/routeTable.test.ts`が固定する。

### 旧Consoleのリンク

旧Console(Windmillのraw app)は廃止した。
過去のDiscordの通知、Issueのコメント、PRの本文には、旧Consoleのリンクが残る。
旧ConsoleのURLを開くと、Caddyが固定の`/console/`へ302で飛ばす。
規則は[Consoleの配信の仕様の「配信の経路」](console/delivery.md#配信の経路)にある。

`main.tsx`が、routerを作る前に`history.replaceState`で置き換える。
routerが先に`/console/`の画面を描くと、その画面が一瞬動いてしまうためである。
置き換えは履歴を増やさない。
置き換えるのは、要件定義書(試行の指定を含む)と監査レポートのフラグメントである。
作業項目の番号と試行の番号は、先頭が0でない正の整数に限る。

監査レポートは[`maps an audit link`](../../console/src/lib/legacyDeepLink.test.ts)で確かめる。

置き換えの規則に合わない旧ConsoleのフラグメントとフラグメントのないURLは、`/console/`の入口(要対応)に着く。

承認フローが投稿するConsoleのリンクは、新しいConsoleの経路を直接指す。
リンクは[`f/factory/lib/approval_support.ts`](../../f/factory/lib/approval_support.ts)の関数が作る。
要件定義書は`buildConsoleUrl`、承認の詳細は`buildApprovalConsoleUrl`、監査レポートは`buildAuditConsoleUrl`が作る。
各関数が作る経路は、[`tests/lib/approval_support.test.ts`](../../tests/lib/approval_support.test.ts)の関数ごとのテストで確かめる。

## 画面の外枠

左のサイドバーに、印と名前、5つの入口、下部の情報を置く。
件数のバッジは、要対応の入口とシステムの入口に付く。
下部には、版の情報(広げたときだけ)、テーマの入れ替え、ショートカット、WindmillのUIへのリンクを並べる。
Windmillは同じオリジンの`/`で配信されるので、リンクは`/`への別タブのリンクにする。
広げたサイドバーでもたたんだサイドバーでも、テーマ、ショートカット、Windmillの3つの操作は残り、たたむと名前を読み上げ専用にしてアイコンだけを見せる。
たたんだサイドバーの入口は、名前をツールチップで出す。
広げた形では、入口だけを描き、ツールチップを持たない。
中身の無いツールチップがあると、ポインタが外れても閉じる処理が働かず、「開いた」状態が残るためである。
残った状態は、たたんだ瞬間にすべて見える。
開閉は、サイドバーの右の縁にポインタを重ねると出る丸いボタンで行う。
縁の線が色づき、ポインタを当てた高さにボタンが現れる。
ポインタを動かすと、ボタンも縁に沿って追う。
位置は、縁の上下に余白を残して挟む。
縁が縮んだときに画面の外へ残らないよう、CSSの`clamp`でも同じ余白で縁の内側に挟む。
キーボードで出したときの位置は、最後にポインタを当てた高さで、まだ当てていなければ縁の中央である。
タッチは追わない。
指の動きはスクロールであり、位置を決める操作ではないためである。
ボタンの名前は、ツールチップでなくネイティブの`title`で出す。
ツールチップは、名前の上にポインタを置くと開いたままになり、ボタンが先に消えて名前だけが残るためである。
読み上げの名前は、`aria-label`の「メニューの開閉」と、`aria-expanded`で示す。
キーボードでは、ボタンが常に順番に入り、フォーカス中は見える。
ポインタを重ねられない端末(`hover: none`)では、ボタンを常に見せる。
縁の線は、ホバーできる端末では、ボタンと同じ条件(ホバーとキーボードのフォーカス)で出す。
マウスで押した後に、ボタンだけが消えて線が残るのを避けるためである。
選んだ入口は、左端の藍の帯と面の色で示す。
入口の件数のバッジは、その入口の一覧に出る項目の件数にする。
要対応のバッジは、承認と、再実行できる失敗と、通知の件数である。
失敗は、再実行できるもの(監査を除く)だけを数える。
監査の失敗は再実行できず、次の定期の監査が扱うまで残るので、数えると0に戻らない。
通知は、重要度が要対応の未解決のものを数える。
重要度が情報の通知は、一覧に出さないので数えない。
一覧の件数と食い違う数字を、最初に見る場所へ出さないためである。
システムの入口のバッジは、システムの画面でしか解けない操作の件数である。
数え方は[区画への移動](console/system.md#区画への移動)にある。
この件数は、要対応のバッジと同じ通知から来るので、要対応の合計(狭い画面のメニューのボタンの名前と点)には足さない。
足すと二重に数えるためである。

画面の上部には、版の更新、ログイン切れ、Windmillに届かないときの帯を出す。
画面の遷移の扱いは[画面の遷移](#画面の遷移)にある。

下部の版の情報は、配信している版と取り込みの最後の確認で、`/console/status.json`から読む。
取れなければ出さない。
状態が固定中か失敗のときは、その旨の注意を添える。
たたんだサイドバーでは、入口のアイコンに件数の数字を重ねて出す。

幅が狭いとき(md未満)は、サイドバーを出さず、画面の上にメニューのボタンと名前のバーを置く。
ボタンを押すと、左からドロワーが開く。
要対応の件数があるときは、ボタンに点を付け、ボタンの名前に件数を含める。
ドロワーは、サイドバーと同じ入口と下部の操作(版の情報、テーマ、ショートカット、Windmill)を持つが、縁のつまみによる開閉は持たない。
ドロワーは、次の操作のどれかで閉じる。

- 入口を選ぶ。
- 閉じるボタンを押す。
- 背景を押す。
- Escを押す。
- 画面をmd以上に広げる。

各画面の見出しは、題と短い副題を左に、最終更新の時刻と更新のアイコンのボタンを右に置く。
更新のボタンと最終更新は、画面に1組だけ置く。
画面の主要な操作のボタンは、`PageHeader`の`actions`に渡し、見出しの右端の、更新のボタンの右に置く。
`refresh`が無い画面でも、`actions`だけで右側に置ける。
題の下の`children`には渡さない。
`children`は題の列の中に描かれ、主要な操作を右端にそろえられなくなるためである。
狭い幅では右側が折り返し、更新の組と主要な操作が別の行に分かれる。
どちらの行も右寄せなので、主要な操作は見出しの右端に残る。
更新のボタンは、見出しに渡した取得を取り直す。
要対応の画面は、一覧の取得(`summary`)だけを取り直す。
詳細ペインの取得(提案、要件定義、取り込み時点のIssue、通知)は含まない。
そのため、要対応の画面の更新のボタンの名前は「一覧を更新」にし、ほかの画面は「この画面を更新」にする。
複数の取得を持つ画面の最終更新は、取得できた中で最も古い時刻にする。
新しい取得の時刻を出すと、古いままの節が新しく見えるためである。
見出しに渡した取得のすべてが自動で取り直されるときだけ、最終更新の脇に「（2分ごとに自動更新）」の形で全角の括弧に入れて示す。
一部の取得だけが自動で取り直される画面は、注記を出さない。
ジョブの画面の実行中と待ちのタブは、一覧と今のステップの両方が自動で取り直されるので、「（1分ごとに自動更新）」を出す。
操作が15分途切れて取り直しが止まった間は出さない。
システムの画面は、`summary`と保留と凍結の取得だけが自動で取り直され、反映の状態と更新履歴は取り直さないので、注記を出さない。
取得が失敗している間も、自動の取り直しは続く。
そのため注記は消さず、「（2分ごとに自動で再試行）」に言い換える。
401は失敗に数えないので、401だけのときは通常の注記を出す。
画面全体の更新の失敗は、最終更新の脇の「更新に失敗しました」が示す。
本体は、同じ失敗を別の語で言い換えない。

節には更新のボタンと最終更新を置かない。
節ごとの「もう一度取得する」は、その節だけが独立して失敗したときの再取得に限る。
前回の値を出している節で取り直しが失敗したときは、値が空であっても、値を出したまま、古い値であることと「もう一度取得する」を節に添える。
この知らせは`StaleDataNotice`が出す。
401は上のバナーが知らせるので、知らせは出さない。
取得中は「もう一度取得する」を押せなくする。
押すと進行中の取得を打ち切るためである。

### パンくず

一覧から開く画面は、見出しの題の下に`Breadcrumb`を置く(`src/components/Breadcrumb.tsx`)。
対象は、作業項目の詳細、要件定義書、設計書、監査レポート、ジョブの詳細である。
戻り先をリンクで並べ、最後の1つを今の画面として文字で出す。
最後の1つは、戻り先の経路を持っていてもリンクにしない。
今の画面へのリンクは何も起こさないためである。

| 画面 | 並び |
| --- | --- |
| 作業項目の詳細 | 作業項目 › 作業項目の番号 |
| 要件定義書 | 作業項目 › 要件定義 › 作業項目の番号の要件定義 |
| 設計書 | 作業項目 › 作業項目の番号 › 設計書 |
| 監査レポート | レポート › 作業項目の番号の監査レポート |
| ジョブの詳細 | ジョブ › ジョブの詳細 |

要件定義書の「要件定義」は、作業項目の画面の要件定義のタブ(`/console/items?tab=requirements`)へ戻る。
一覧から要件定義書を開いたときに、一覧のタブへ戻れるようにするためである。
設計書の「作業項目の番号」は、作業項目の詳細の設計タブ(`/console/items/<番号>?tab=design`)へ戻る。
設計書の切り替えと承認の状態は設計タブが持つので、本文の画面に戻るリンクは重ねて置かない。
作業項目の番号が正しくない設計書の画面は、「作業項目 › 設計書」だけを出す。
ほかの画面は、番号が正しくなくても、戻り先は同じ並びで出す。
並びは`src/lib/breadcrumbs.ts`の純関数が決める。

作業項目の詳細の「作業項目」は、一覧の行から開いたときに、その一覧の範囲(`/console/items?scope=...`)へ戻る。
行のリンクが、戻り先を履歴の`state`に持たせる。
戻り先は、`/items`か、`/items?`に安全な文字だけが続く内部のパスだけを受け入れ、それ以外は既定の`/console/items`に落とす。
履歴の`state`は外から書き換えられうるためである。
履歴の`state`は再読み込みで失われることがある。
そのときも既定の`/console/items`へ戻り、範囲は進行中になる。

ジョブの詳細の「ジョブ」は、一覧の行から開いたときに、その一覧のタブと絞り込み(`/console/jobs?tab=history&status=failure`など)へ戻る。
受け入れる戻り先と、`state`が無いときの扱いは、作業項目の詳細と同じである。
受け入れるのは`/jobs`か、`/jobs?`に安全な文字だけが続く内部のパスで、既定は`/console/jobs`である。
親のジョブやステップのジョブへ移るときも、戻り先を引き継ぐ。

## キーボード操作

キーボードだけで画面を移れるようにする。
ショートカットを使っても、入力中の内容を失わないようにする。
外枠(`AppShell`)が、コマンドパレットとショートカットの一覧(ヘルプ)の開閉を持つ。
キーの規則は`lib/shortcutKeys.ts`の純関数が決め、`app/useKeyboardShortcuts.ts`がブラウザのキー入力につなぐ。

### コマンドパレット

Command+K(macだけ)かCtrl+K(mac以外だけ)で開く。
macの入力欄ではCtrl+Kが行末までの削除なので、macではCtrlを奪わない。
修飾キーを伴うので、入力欄の中でも、1文字のショートカットが無効でも開ける。
パレットが開いている間は、同じキーで閉じる。
押しっぱなしの繰り返しでは、開閉を繰り返さない。

検索の対象は、次の2つのグループだけである。

| グループ | 項目 | 行き先 |
| --- | --- | --- |
| 画面 | 画面の表(`app/screens.ts`)の5画面と、各画面の固定の行き先 | 画面の経路 |
| ヘルプ | ショートカットの一覧を開く | ヘルプのダイアログ |

固定の行き先は、サイドバーの1回の押下では届かないものである。
作業項目の新規投入と要件定義のタブ、ジョブの履歴とスケジュールのタブが該当する。
経路と名前は画面の表の`destinations`に持つ。
キーボードだけの運用者が、一覧から開いてタブを探す手間を省くためである。

作業項目の個別の行、ジョブ、テーマは検索しない。
サイドバーとそれぞれの一覧で足りるためである。
ジョブの文字はサーバー由来で、保護された描画の経路の外に出さない。
パレットに出す文字は、画面の表と固定の文言だけから作り、サーバー由来の文字を含めない。

作りは`<dialog>`の中の入力欄(`role="combobox"`)と、候補の一覧(`role="listbox"`)である。
フォーカスは入力欄に残し、選んでいる候補は`aria-activedescendant`で示す。
候補が無いときは、`aria-expanded`を偽にする。
結果の件数は、読み上げ専用の`role="status"`で伝える。
矢印の上下で候補を選び、Enterで開く。
HomeとEndは、入力欄のカーソルの移動に残す。
候補の横にショートカットのキーは出さない。
キーは既定で無効なので、押しても働かない表示になるためである。

IMEの変換中は、Enterと矢印を処理しない。
変換を確定するEnterで候補を選ぶと、入力が途中で確定されるためである。
変換中かは、`isComposing`か`keyCode`の229で見分ける(`isComposingKey`)。
Escの扱いは、ダイアログの標準の動作に任せている。

閉じるときに、入力した文字と選んでいる候補を捨てる。
次に開いたとき、前の検索を見せないためである。

### ショートカット

Command+KかCtrl+Kでコマンドパレットを、`?`でショートカットの一覧を開く。
`g`の次に数字を押すと、その番号の画面へ移る。

画面の移動のキーは、画面の表の`shortcut`に持つ。
サイドバーの並びの番号で、順序を覚えやすくするためである。
番号がサイドバーの並びの順であることは、[`numbers the go-to keys in the order of the side bar`](../../console/src/app/screens.test.ts)で確かめる。
ヘルプの一覧はこの値から作るので、正本は1つである。
`g`の後は[`src/lib/shortcutKeys.ts`](../../console/src/lib/shortcutKeys.ts)の`GO_WAIT_MS`の間だけ次のキーを待ち、別のキーが来たら取り消す。
`?`はShiftを伴うので、Shiftは見ない。
Ctrl、Alt、Metaを伴うキーは、ブラウザや他の部品のものなので使わない。
通知のAlt+Tとは重ならない。

次のときは、1文字のショートカットを受けない。

- 文字を打ち込む場所にフォーカスがあるとき。
  入力を奪わないためである。
  対象は、`textarea`、`select`、`contenteditable`と、文字を打ち込む種類の`input`である。
  `input`の種類は、`src/lib/shortcutKeys.ts`の`TYPING_INPUT_TYPES`が定める。
- 変換中のとき。
- パレットを含む、開いているダイアログがあるとき。
  背面の操作を止めている間に、画面を移さないためである。

チェックボックス、ラジオボタン、ボタンにフォーカスがあるときは、1文字のキーが働く。
文字を打ち込まない場所なので、入力を奪わない。

他のダイアログが開いている間は、パレットも開かない。
パレットだけが開いているときは、パレットのキーだけを受け、`g`の待ちは捨てる。
他の処理がすでに扱ったキーは、何もしない。
この振り分けは、純関数`routeKeydown`が決める。

### ショートカットを有効にする

1文字のショートカットは、既定で無効である。
`g`の次の数字は、画面を移す。
入力は画面の中に持つので、画面を移ると、送っていない内容を失うことがある。
見ずに押した1文字で入力を失わないよう、使う人が有効にするまで働かせない。
新規投入の入力は、移っても残す(次の節)。
承認の却下の理由は、移ると消える。

有効にするのは、ヘルプのダイアログの「ショートカットを有効にする」である。
設定はブラウザの`localStorage`(`factory-console.shortcuts`)に残す。
有効のときだけ値を持ち、無効に戻すと消す。
保存領域を読めないときと、値が読めないときは、無効にする。
別のタブでの切り替えは、`storage`イベントで反映する(`shortcutsEnabledFromStorageEvent`)。

対象は、`g`の次の数字と`?`である。
修飾キーを伴うCommand+KとCtrl+Kは、既定で働く。

ヘルプのダイアログは、キーに頼らない入口を2つ持つ。
無効のままでも、有効にする切り替えへ届くためである。

- パレットの「ショートカットの一覧を開く」
- サイドバーの「ショートカット」ボタン(たたんだときは、アイコンだけを見せる)

### 新規投入の入力の保存

新規投入の入力は、変更のたびに、タブ全体の状態(`api/intakeSession.ts`)へ残す。
サイドバー、パレット、ブラウザの戻る操作で別の画面へ移って戻っても、題名と目的などを復元するためである。
残す値は、リポジトリ、進め方、題名、目的、受入基準、不具合の3欄である。
入力中の保存は、これらの欄の値をすべて比べて、変わったときに書き換える。

投入できたときと、投入されたかが分からない結果を破棄したときは、残した入力を消す。
画面が表示中にこれを知ると、題名、目的、受入基準、3欄を空にし、進め方を通常に戻す(`fieldsAfterCount`)。
リポジトリは残す。
承認を省く選択を、次の投入に持ち越さないためである。
投入されたかが分からない結果があるときは、送った入力を見せ続けるので、入力の変更では書き換えない。
タブを閉じるか再読み込みすると、残した入力は消える。

### フォーカスの規則

パレットとヘルプは、`showModal`で開く。
背面の操作を止め、フォーカスを中に留める。
Escで閉じると、ブラウザが開く前の要素へフォーカスを戻す。

パレットで画面を選んだときは、先にパレットを閉じてから移る(`chooseItem`)。
閉じるとブラウザが元の要素へフォーカスを戻すので、移る前に閉じれば、遷移後のフォーカスの移動(見出しへ)を奪わない。
そのため、画面の遷移の後にフォーカスを移す処理は、メニューのドロワーだけを待ち、パレットは待たない。

ヘルプをパレットから開くときも、先にパレットを閉じる。
ヘルプを閉じると、パレットを開く前にフォーカスがあった要素へ戻る。

### 自動のa11y検査

`lib/a11yRules.ts`が、描画したHTMLの文字列を検査する。
依存を足さず、HTMLを読む手段は小さな字句解析にした。
Biomeが見るもの(画像の`alt`、正の`tabindex`)は入れず、静的に拾えるものに絞る。

| 規則 | 見るもの |
| --- | --- |
| 参照先の存在 | `aria-labelledby`、`aria-describedby`、`aria-controls`、`aria-activedescendant`の参照先のid |
| idの重複 | 同じidを持つ要素 |
| 見出しの段 | 見出しが直前の段より2段以上深くならないこと |
| 入力欄のラベル | 入力欄、`textarea`、`select`の名前。入力欄を包む`label`は、入力欄自身の中身を除いた文字で数える |
| ボタンとリンクの名前 | `button`と、`href`を持つ`a`の名前 |

見出しの開始の段は、検査の引数で渡す。
画面を単体で描くと、h1は`PageHeader`にある。
断片を検査するときは、断片の外にあるh1の分として1を渡す。
閉じた`aria-expanded`の`aria-controls`は、参照先をまだ描かないことがあるので見ない。
閉じた`<dialog>`の中は描かれないので、隠れたものとして扱う。

全画面の代表の状態(取得前、通常、空、失敗)を、`a11yScreens.test.tsx`が描いて検査する。
通常と空の固定データを持つのは、5画面と、作業項目の詳細(設計タブを含む)、設計書、ジョブの詳細、新規投入、PRレビューの投入である。
新規投入とPRレビューの投入のデータは投入先の候補で、候補がリポジトリ欄の選択肢に出ることも確かめる。
そのほかの詳細(要件定義書、監査レポート)は、取得前と失敗を検査する。
新規投入は、書き込みの結果で変わる状態も、描いて検査する。
書き込みの結果とは、断り、ジョブが動く前の拒否、投入されたか分からない状態(再送を確かめる前と後)、投入できた結果、送信中、一覧が古い状態である。
保存した入力の進め方(承認を省く、不具合の修正)も描く。
これらは、タブ全体で持つ状態を直接書いて作り、検査のたびに空へ戻す。
書き込みの結果の知らせは、`role="alert"`で出ることも確かめる。
送信中と保存した入力だけの状態は、`role="alert"`を出さない。
送信中は、送信のボタンが`aria-disabled`で`disabled`が無いことと、新規投入の入力欄が読み取り専用であることも確かめる。
読み取り専用は、リポジトリと題名の1行の入力欄と、すべての複数行の入力欄で別々に確かめる。
進め方のラジオが`aria-disabled`であることも確かめる。
誤りの件数を読み上げる領域が、最初の描画から空で置かれることも、投入の2画面で確かめる。
PRレビューの投入は、結果の部品が状態ごとに検査を通ることと、入口の結果の知らせが`role="alert"`で出ることも確かめる。
状態は、[結果の読み方](console/work-items.md#結果の読み方)の表の行に対応する。
要対応の画面は、承認、失敗、通知を選んだ状態も、確認ダイアログを開いた形にして検査する。
読み込み中の表示は、`LoadingStateView`を表示した形で直接検査する。

取り消せない操作の確認ダイアログは、`a11yDialogs.test.tsx`が、開いた形で個別に検査する。
対象は、次の操作の確認である。

- 保留と凍結を置く、解除する
- 全停止する、全停止を解除する
- 設定を変える
- 監査を起動する
- ジョブを中止する、定期ジョブを再実行する
- スケジュールを止める、戻す
- 作業項目を再実行する、中止する

パレットとヘルプとドロワーは、開いた形にして別に検査する。

### ブラウザでのa11y検査

静的な描画の検査は、描いた時点のHTMLしか見ない。
色のコントラスト、フォーカスの移動、キーを押したときの動きは、ブラウザで確かめる。
ビルドしたConsoleをChromiumで開き、Playwrightとaxe-coreで検査する。
起動は`mise run console:a11y`で、CIでは`console-a11y`ジョブが動かす。
ブラウザの取得が要るので、`mise run check`には含めない。
初回は`bun run --cwd console playwright install chromium`でブラウザを入れる。

検査の構成は、次のとおりである。

- 配信は`scripts/console-branch-server.ts`で行う。
  本番のCaddyと同じCSPを付けるので、CSPの下でも検査が動くことを確かめられる。
- APIは`page.route`で固定の値を返す(`console/e2e/responses.ts`)。
- 書き込みのscriptは、検査が結果を選んだものだけに固定の値で応える(`writes`)。
  結果は、成功、scriptの断り、5xxの3つである。
  既定は空で、書き込みには応えない。
- 次の要求は、中断して記録し、検査を失敗にする(`console/e2e/mockApi.ts`)。
  結果を選んでいない書き込みのscriptも、呼ばれると失敗する。
  - 表に無いscriptの呼び出し
  - 別のオリジンへの通信
  - 同じオリジンで、`/console/`と`/api/`の外を指す通信。
    配信のサーバーは、この通信を実際のWindmillへ中継しうる。
- この3つを止めるので、検査の要求は、Windmillと外部のどちらへも届かない。
  `mockApi.a11y.ts`が、中断と記録を確かめる。
  書き込みを1つ選んだ受け口が、選んだ書き込みに応え、選んでいない書き込みを記録することも確かめる。
- 固定のデータは、静的な描画の検査と共有する(`console/e2e/fixtures.ts`)。
  返す値がConsoleの型ガードを通ることは、単体テストが確かめる。
- ファイル名は`*.a11y.ts`か`*.e2e.ts`にする。
  `bun test`は拾わず、`playwright.config.ts`だけが拾う。
- `console/tsconfig.json`の`include`に`e2e`と`playwright.config.ts`を入れる。
  検査のコードは、Consoleの型検査(`bun run --cwd console typecheck`)に掛かる。
- レポートと一時の出力(`console/playwright-report/`、`console/test-results/`)は、gitに入れない。

axe-coreの検査(`axe.a11y.ts`)は、次の組み合わせを開く。

- テーマはライトとダーク。
  保存領域の値を、ページを開く前に書く。
- 画面は、要対応(承認、失敗、通知を選んだ状態を含む)、作業項目の一覧(進捗と要件定義)と詳細、新規投入、PRレビューの投入、システム(状態と設定のタブ)、ジョブ(進行中、履歴、スケジュール)である。
  このほかに、flowの図と起動の図も開く。
- 設定のタブは、axe-coreの検査に加えて、表の構造も確かめる。
  幅1280pxと320pxで、名前のある表が1つ以上あることと、名前のある表がどれも列見出しと行見出しを持つことを、ブラウザが算出した役割で確かめる。
  axe-coreの規則は、表に名前があることも、見出しが揃うことも求めないためである。
- 起動の図は、`poll_prs`、`poll_issues`、`poll_dependabot`、`self_update`を開く。
  `poll_issues`は、起動するflowが1つなので、初めから開いた状態になる。
- flowの図は、`implement`、`pr_review`、`pr_fix`を開く。
- 起動の図は、見出しを1つずつ開いて検査する。
  開いたときだけ描かれる要素(ステップの行、リンク)を、検査の対象に入れるためである。
  図が一覧に替わる幅([Consoleの図の画面の仕様の「幅」](console/graphs.md#幅))の一覧でも、1つずつ開いて検査する。
- データは、有る状態と無い状態の両方。
- ダイアログは、パレット、ヘルプ、再実行の確認、作業項目の中止の確認を開いた状態。
  作業項目の中止の確認は、開いたときの最初のフォーカスが「閉じる」にあることも確かめる。
- 投入の2画面は、入力の操作で出せる状態も開く(`intakeStates.ts`)。
  初期、入力の誤り(空、題名の超過、リポジトリの形)、進め方の選択(承認を省く、不具合の修正)、入力済みの状態である。
  誤りは、送信のボタンを押して出す。
  誤りの無い入力は送らない。
  送ると書き込みのscriptが呼ばれて、検査が失敗するためである。
  送信中の入力欄の見た目は、不具合の修正の入力済みの状態で、文字を入れる入力欄と複数行の入力欄に読み取り専用を直接付けて模す。
  この状態の文字の色を、ライトとダークで測る。
  本文は画面の中でスクロールし、画面の外の文字は、axe-coreが背景を決められず、色が測られない。
  そのため、フォームの全体が収まる高さで開く。

規則は、WCAG 2.0と2.1のAとAAだけを見る。
規則の無効化、対象の除外、既知の違反の許容リストは持たない。
違反が出たら、規則を緩めずConsoleを直す。

検査が何も測らずに通る事態を、次の確認で防ぐ。

- 違反を埋めた固定のページ(代替テキストの無い画像、コントラストの低い文字)で、画面の検査と同じ設定のaxe-coreが違反を返す。
- 画面とダイアログごとに、axe-coreを通った規則が1件以上ある。
- 画面とダイアログごとに、文字のコントラストが測られている。
  通った要素か違反の要素が1つ以上あれば、測られたと見なす。
  どちらも無いときは、「要確認」が1件以上4件以内であることを求める。
  実画面にはサイドバーと見出しの文字があるのに、通った要素も違反の要素も無ければ、画面全体が測れていない。
  この上限が捕まえるのは、その場合である。
  4件は、検査自身の確認と対にした許容の件数である。
  検査自身の確認は、`axe.a11y.ts`の固定のページで、4件は通し、5件は落とす。
  実画面の「要確認」の最大は、4件の根拠にしない。
- 停止先が0件の画面と、本文に止まらない画面を、キーボードの検査が失敗にする。
- 画面とダイアログごとに、htmlの`data-theme`と`data-theme-preference`が、開いたテーマと一致する。
  ダークの検査がライトの配色で通る事態を防ぐ。
- 「要確認」になった文字のコントラストの件数は、検査の出力とPlaywrightのレポートの注記に残す。
  件数を残すこと自体では失敗にしない。
  測られたかの判定は上の項目による。

キーボードの検査(`keyboard.a11y.ts`)は、実際のTabとEscapeを押して、次を確かめる。
Tabの順序のスナップショットは取らない。

- スキップのリンクが、最初のTabで見え、Enterで本文へフォーカスを移し、アドレスに`#`を足さない。
- 各画面で、Tabの停止先がすべて、正の`tabindex`を持たず、見えて、名前を持つ。
- 各画面で、停止先が1件以上あり、本文に1つ以上止まる。
  最初のTabでページの外へ出る画面を、問題なしとしないためである。
- Tabが同じ要素に留まらず、途中の要素へ戻らず、スキップのリンク、サイドバー、本文の順に進む。
- ダイアログは、開いた直後にフォーカスが内側へ移り、Tabで背面へ出ない。
- ダイアログは、Escで閉じ、開いたボタンへフォーカスが戻る。
- サイドバーからの遷移の後に、フォーカスが見出しへ移り、`document.title`が変わる。
- 起動の図は、Tabで見出しのボタンへ届き、Enterで`aria-expanded`が変わってステップの行が見え、フォーカスが見出しに残る。
  もう一度Enterで閉じる。
- 起動の図のSpaceは、keydownでは切り替えず、keyupで切り替える。
  ページはスクロールしない。
- 起動の図で開いた見出しの次のTabは、同じflowの「flowの図」のリンクへ移る。
  リンクをEnterで開くと、flowの図へ移る。
- 起動の図は、図が一覧に替わる幅([Consoleの図の画面の仕様の「幅」](console/graphs.md#幅))をまたいで図と一覧が入れ替わっても、開いたflowが開いたまま残る。
- 投入の2画面は、一覧へ戻るリンクの次から、入力欄とボタンに、画面の順でTabが止まる。
  止まった要素の名前は、ラベルと一致する。
  進め方のラジオは、選んでいる1つにだけ止まる。
  不具合の修正では、3つの欄が、目的と受入基準の間に入る。
- 投入の2画面は、誤りを出す前、入力欄に`aria-invalid`が無い。
  誤りを出した後は、入力欄が`aria-invalid`になり、誤りの文が説明に含まれる。
  補足と字数も、説明に残る。
- 投入の2画面の1行の入力欄でEnterを押すと、送信として扱われ、誤りが表示される。
  複数行の入力欄のEnterは改行で、送信しない。
- 投入の2画面は、誤りで送信が止まると、最初の誤りの入力欄へフォーカスが移る。
  送信のボタンのクリックでも、ボタンでのEnterでも同じである。
  最初は画面の並びの順で、リポジトリが不正なら題名より先、不具合の修正なら3欄が目的の次である。
  誤りを出した後に入力欄を直しても、誤りが残っていても、フォーカスは動かない。
- 投入の2画面は、最初の誤りの入力欄でEnterを押すと、読み上げ専用の領域に、「入力に誤りがあります(n件)」の文を書く。
  フォーカスが別の欄から移ったときは、領域は空のままである。
- 新規投入の進め方のラジオは、矢印キーで切り替わり、送信ボタンの文言が変わる。
  誤りの無い入力でも、ラジオのEnterは送信しない。
  送信したかは、フォームのsubmitイベントの数で確かめる。

書き込みの検査(`writes.e2e.ts`)は、6つの操作を押し、確認を通して送り、結果の表示を確かめる。
操作は、承認、却下、ジョブの中止、作業項目の中止、保留を置く、全停止である。
結果は、成功、scriptの断り、5xxの3つである。
検査は、操作ごとの表(経路、script、操作の関数、期待する文)から作る。
成功は、トーストと読み直しを別の検査にするので、24本になる。

- 成功は、成功のトーストが出る。
  関連する取得を読み直す。
- 断りと5xxは、成功以外のトーストが出て、閉じるボタンを持つ。
- 失敗のトーストは、成功のトーストの寿命(4秒)より長く残る。
  実時間で待つのは、この1本だけである。
- 失敗のトーストは、閉じるボタンで消える。
- 閉じるボタンに、キーボード(Alt+TとTab)で届き、Enterで閉じる。
- キーボードでフォーカスしたトーストは、輪郭の計算値(`outline`と`box-shadow`)が、フォーカスの前から変わる。
  影はフォーカスが無くても付くので、`none`でないことだけでは確かめられない。
- 成功のトーストも、閉じるボタンを持つ。
- 残るトーストが2件あるとき、どちらも画面の中にあり、透明でなく、重ならない。
- 残るトーストが出た状態のページが、ライトとダークでaxe-coreを通る。
  トーストだけを測った結果で、文字のコントラストが測られたことも確かめる。

axe-coreの規則のタグと、検査するテーマは、`axeScope.ts`が持ち、画面の検査と書き込みの検査が共有する。

ダイアログの開閉の検査(`dialog.a11y.ts`)は、コマンドパレットを実際に開閉して、`Dialog`の通知を確かめる。

- Escで閉じると、親へ閉じたことが伝わり(`onClose`)、同じショートカットでもう一度開ける。
- Escで閉じると、閉じるたびの後始末(`onClosed`)が走り、パレットの入力が消える。
- 親が`open`を偽にして閉じたときも、後始末が走る。

`open`を偽にした場合の`onClose`の不呼び出しは、画面に出ないので、この検査では見えない。
この分岐は、`notifyDialogClosed`の単体のテストが固定する。

この検査が見ないものは、次のとおりである。

- Chromium以外のブラウザの動き
- 画面の読み上げの聞こえ方
- axe-coreが「要確認」とする項目。
  文字のコントラストの件数だけは出力に残す。
- 投入の2画面の、書き込みの結果で出る表示(送信中、断りの理由、投入できた結果、結果の部品)。
  受け口が投入の書き込みのscriptに応えないので、ブラウザでは出せない。
  新規投入の分は静的な描画の検査が、PRレビューの投入の分は結果の部品の単体のテストが見る。
  これらの色のコントラストは測らない。
  送信中の入力欄の文字の色だけは、読み取り専用を直接付けて測る。
- 投入の2画面の、送信中の状態のブラウザでの動き。
  ブラウザで出せないので、静的な描画が`aria-disabled`と読み取り専用の属性だけを見る。
  Chromiumで送信中にフォーカスが残ることと、押しても何も起きないことは、確かめていない。
  ラジオが送信中に矢印キー、スペース、ラベルのクリックを受け付けないことは、判定の単体のテストだけが見る。
  判定を`preventDefault`に結ぶ配線は、ブラウザで確かめていない。
- `aria-disabled`のボタンでhoverの見た目が出ないこと。
  `Button`のclassの規則と、合成後のclassを、単体のテストが見る。
  ビルドしたCSSでは、打ち消しが通常のhoverより高い詳細度で出ることを確かめた。
  ブラウザでの勝ち負けは、自動では確かめていない。
- 読み取り専用の破線の枠が、強制色モードで残るか。
- WCAG 1.4.11(非テキストのコントラスト)。
  axe-coreは測らない。
- WCAG 2.4.7(フォーカスの表示)。
  axe-coreは測らない。
- 6つの操作のほかの書き込みと、一覧が古いことの知らせの、ブラウザでの表示。
  ほかの書き込みは、解除、再実行、通知の解決、スケジュールを止める・戻す、反映の判断である。
  これらも`announce`を通ることは、sonnerを直に読み込むファイルを限る`announce.test.ts`の許可リストが見る。
- 残るトーストが画面の高さを超えて並んだときの見え方
- 開いていないときに描かない内容(Tooltip)
- 狭い幅のメニューのドロワー
- draw.ioのビューアを含む配信物。
  検査するdistにビューアは無く、draw.ioの図を埋め込む画面は実物の形で見ない。
- 見た目と文言の良し悪し(原則は[Consoleの画面の表示の原則](../console-display.md)にある)

### キーボード操作の残る制限

ブラウザでの検査が見ない範囲は、実機で確かめる。

- 開閉で変わる属性の意味(`aria-expanded`、`aria-selected`)
- 検査していないダイアログと遷移のフォーカスの移動
- Radixのポータルに描く内容(Tooltip)
- IMEの変換中の動き
- たたんだサイドバーの「ショートカット」ボタン。
  検査は広げた状態だけを開く。

そのほかの制限は、次のとおりである。

- Firefoxでは、Ctrl+Kが検索欄を開く。
  ページから`preventDefault`で奪えるかは確かめていない。
  奪えない場合は、サイドバーの「ショートカット」ボタンと、画面の入口を使う。
- CapsLockが有効だと、`g`が働かない。
  `key`が大文字になるためである。
- IMEの変換中のEscで、パレットが閉じるかは確かめていない。
  実装は、変換中のEnterと矢印だけを無視する。
- 承認の却下の理由は、別の画面へ移ると消える。
  サイドバー、パレット、`g`の次の数字のどれで移っても同じである。
- Issue作成のやり直しの確認ダイアログは、承認の種類が合うときだけ描かれるので、画面の検査に含めない。
- 要件定義書、監査レポート、新規投入の通常の状態は、固定データを持たないので、静的な検査に含めない。

実機では、ブランチ版を開き(手順は[ブランチ版のConsoleを確かめる](../setup.md#ブランチ版のconsoleを確かめる))、次を確かめる。

1. Command+KかCtrl+Kでパレットが開き、入力欄にフォーカスがある。
2. 矢印とEnterで画面を移り、フォーカスが見出しに移る。
3. 既定で`g`の次の数字と`?`が働かない。
   ヘルプで有効にすると働く。
   入力欄の中では移らない。
4. 新規投入で題名を入力し、サイドバーで別の画面へ移って戻ると、入力が残っている。
5. 別のタブで有効にすると、開いているタブにも反映される。
6. サイドバーをたたんだ状態で、「ショートカット」ボタンからヘルプが開く。
7. ライト、ダーク、幅400pxで、パレットとヘルプが読める。

## 画面の遷移

画面の遷移は、`pathname`が変わったときだけ扱う。
`search`だけの変更(タブ、選択、絞り込み)と、最初の表示では扱わない。
画面の中の操作と、ブラウザが決めた位置を妨げないためである。
判定は純関数`shouldMoveFocus`が行う。

遷移のたびに、外枠(`AppShell`)が次の3つを行う。

- タブの題を「<画面名> - Factory Console」にする。
- `main`の名前を付ける。
  見出し(`PageHeader`のh1)があれば見出しから取り、無い画面では画面名(`aria-label`)を使う。
- フォーカスを、見出しへ移す。
  見出しが無い画面では`main`へ移す。

`main`の名前は`aria-labelledby`で見出しを指し、`aria-label`に画面名を添える。
参照先の見出しが無いと、`aria-labelledby`は使われず、`aria-label`が名前になる。
画面名を別の名前として重ねると、「メイン、作業項目」と「見出し1、作業項目」のように、同じ内容が二度読まれるためである。

画面名は、画面の表(`screens.ts`)が経路の`handle`に載せる。
下の経路が名前を持たないときは、入口の名前を使う。
作業項目の番号を含む名前(「作業項目 #12」「作業項目 #12の要件定義」「作業項目 #12の監査レポート」)は、経路の引数から決める。
取得を待たないので、題は取得の前から変わらない。
番号が読めないときは、番号の無い画面名にする。

メニューのドロワーが開いているときは、閉じ終わってからフォーカスを移す。
`<dialog>`を閉じると、ブラウザが開く前の要素へフォーカスを戻し、先に移すと奪われるためである。
ドロワーは`data-nav-drawer`で見分ける。
フォーカスを移すとき、スクロールはさせない。
`main`は`overflow-clip`で、フォーカスによるスクロールで外側が動くと、見出しの帯が外れるためである。
見出しには、キーボードで移ったときだけ細い輪を描く(`focus-visible`)。
マウスの操作の後には描かない。
キーボードの利用者が、移った先を見失わないためである。
`main`には輪を描かない。
領域全体を囲む輪は、画面の中の操作の輪と紛れる。

要対応の画面が自分で行うフォーカスの移動(一覧と詳細の切り替え)は、`search`の変更で起きる。
そのため、遷移のフォーカスの移動と重ならない。

ページの先頭に「本文へスキップ」のリンクを置く。
フォーカスが当たったときだけ見える。
押すと`main`へフォーカスを移し、アドレスに`#`を足さない。

## ちらつきの抑え方

### 画面の切り替え

画面を替えると、新しい画面の取得が終わるまで、節が空になる。
これを、データの保持、先読み、スケルトンの遅延表示の3つで抑える。

取得したデータは、使われなくなってから5分(`gcTime`の既定)保持する。
5分以内に戻ると、保持中のデータを即座に出し、古ければ裏で取り直す。
`gcTime`を延ばしても、古いデータを出す危険が増えるだけなので、変えない。

サイドバーの入口を押すと、その画面の初回の取得を`prefetchQuery`で先読みする。
押した直後に走らせ、押してから離すまでの時間を、取得に使う。

- 先読みは、pointerdownだけで走らせる。
- 主ボタンで修飾キーが無い押下に限る。
  中クリックとCtrl+クリックは、この画面に移らず、新しいタブで開く操作だからである。
- タッチの押下では先読みしない。
  スクロールの始まりでも起きて、移る操作かが分からないためである。
  タッチでも、移った後の取得は画面が自分で行う。
- focusとhoverでは先読みしない。
  矢印やTabで入口をたどるだけで、Windmillのジョブが溜まるためである。

同じ入口は、先読みが走ってから5秒の間、次の依頼を受けない。
連続した押下で、同じ取得を続けて呼ばないためである。
押下の判定は、純関数`isPrimaryPress`にある。
先読みは、画面の取得と同じ設定(キー、関数、`staleTime`)を使う。
設定は取得ごとの`...QueryOptions`関数にあり、画面のフックと先読みが同じ関数を呼ぶ。
新しいデータは取り直さず、走っている取得には重ねない。
先読みする取得は、作業項目の入口では進捗の一覧と要件定義の一覧、ジョブの入口では実行中と待ちの一覧、システムの入口では状態、更新履歴、保留と凍結である。
`summary`は、サイドバーが常に持つので先読みしない。
要対応とレポートは、先読みの対象に含めない。
workerは1台で直列に処理するので、入口1つの先読みは、その画面の取得数(システムは3つ、ジョブは1つ)に限る。
ジョブの履歴とスケジュール、システムの設定は、タブを開くまで取得しないので、先読みしない。

システムの状態は、画面を開くときの取り直しを`staleTime`(30秒)に任せる。
通知の解決は、一覧、未解決の通知、システムの状態を読み直す(`NOTICE_RESOLVE_INVALIDATES`)。
保留と凍結の解除も、システムの状態を読み直す。
反映の承認と却下は、保留と凍結の取得を読み直す。
システムの状態を変える書き込みはこの3つで、いずれも読み直すので、開くたびの取り直しは要らない。
開くたびに取り直すと、先読みの直後に取り直して、先読みが無駄になる。
システムの状態は、Factory側の変化(新しい通知や反映)を、`staleTime`の間は画面に反映しない。
更新のボタンで取り直せる。

節のスケルトンは、取得が300ms続くときだけ出し、出したら200ms以上残す(`useDelayedVisible`)。
ただし、承認が載る2つの面は、出す前の300msの待ちだけを持ち、出した後に残す時間を持たない。
画面の切り替えの取得は約200msで終わる。
終わる時刻の付近で出し入れすると、かえってちらつくためである。
出すまでの間は、見出しと、節と同じ高さの空の領域を出す。
スケルトンが出るときも、内容に置き換わるときも、下の要素は動かない。
「読み込み中」の通知(`role="status"`)も、スケルトンと同じ時点で出す。
状態の遷移は純関数`reduceDelayed`で、時刻を引数に受ける。
タイマーの結びつきは`scheduleDelayedWake`にあり、時刻とタイマーを引数に受ける。
共通部品`LoadingGate`と`useLoadingDisplay`が、空の領域、スケルトン、内容を出し分ける。

この遅延表示は、取得を待つ画面と節のすべてに使う。
要対応、作業項目の詳細、要件定義書、監査レポート、レポートの各区画、システム、作業項目の一覧、承認と通知の各ペインである。
最初の画面を読み込む`RouteFallback`だけは対象外にする。
最初の読み込みには、節の枠が無く、空の領域を出す先が無いためである。
`RouteFallback`は、外枠でなく、画面の経路の`HydrateFallback`に置く(`buildScreenRoutes`の第3引数)。
外枠に置くと、外枠ごと置き換わり、サイドバーが読み込みの終わりまで消える。
画面の経路に置くと、実物のサイドバーが先に描かれ、本文の位置だけに骨組みが出る。
骨組みの見出しの帯と本文の枠は、実物と同じclass(`PAGE_HEADER_CLASS`、`SCROLL_BODY_CLASS`)で描く。
実物と入れ替わる瞬間に、帯の線と本文の位置が動かないためである。
帯の高さは、副題の行と、題の下の戻り先の行があるかで変わる。
画面の表(`screens.ts`)の経路に、戻り先の印(`trail`)を持たせ、`routeFallbackFor`が骨組みを選ぶ。
副題と戻り先の行は一緒に持つので、印は1つである。
副題だけを持つ印は作れない。
印を持つのは、新規投入、PRレビューの投入、作業項目の詳細、要件定義書、設計書、監査レポート、ジョブの詳細である。
戻り先の行は、新規投入とPRレビューの投入が一覧への戻りのリンク(`back`)、ほかの5つの画面がパンくず(`breadcrumb`)である。
要対応の副題は、すべて片付いたときだけ出るので、印を付けない。
右端には更新の操作の枠を置く。
枠の寸法は、[`src/app/RouteFallback.tsx`](../../console/src/app/RouteFallback.tsx)の`Fallback`が定める。
更新の操作を持たない画面は、経路の印(`refresh: false`)で枠を省く。
省くのは、取得するものを持たない新規投入とPRレビューの投入と、見つからない画面である。
幅が狭いと、実物の更新の操作は題の下へ折り返し、帯が約44px高くなる。
骨組みの枠も同じ幅で折り返す。
幅1280pxと400pxで測ると、帯の高さは実物と一致した。
行の高さと本文の枠は、`layoutClasses.ts`の定数を実物と骨組みが共有する。
行の高さは、`index.css`の文字の大きさと行の高さの積と一致することを、テストが確かめる。
入れ子の経路には骨組みを付けない。
親と子の両方に付けると、帯と本文の枠が二重に出るためである。
画面の表に入れ子の経路を足すときは、親の骨組みが子の位置まで描く。
入れ子が無いことは、`src/app/screens.test.ts`が確かめる。
画面が早期に別の表示へ切り替える場合は、フックを画面の先頭で呼び、値が揃った後もスケルトンを残す時間の間は、読み込み中の表示を続ける。

スケルトンの高さは、内容に置き換わるときのずれを減らすため、実物と並べて測った寸法にそろえる。
値は各節と各画面の定数(`..._LOADING_SHAPE`)にある。
節の内容の形を変えたら、実機で高さを測り直して合わせる。

測り方は、画面ごとに読み取りの応答を固定の値に差し替え、取得を止めたまま骨組みを描き、止めを解いて実物を描く。
どちらも`getBoundingClientRect`で、見出しの帯、節の上端と高さ、行の間隔を比べる。
幅1280pxのライトとダーク、幅400pxで確かめた。

実物と並べて測った画面は、次のとおりである(幅1280px)。

| 画面と部分 | 実物 | 骨組み |
| --- | --- | --- |
| 要対応の一覧の行 | 81px | 81px |
| 作業項目の進捗(絞り込みの帯、件数、表の上端) | 171px、243px、277px | 171px、243px、276px |
| 要件定義の一覧の行 | 81px | 81px |
| 監査レポートの一覧の行 | 99px | 99px |
| レポートの分析(コスト、承認、リードタイム) | 748px、413px、313px | 748px、413px、313px |
| ジョブの実行中と待ちの行、履歴の行 | 74px | 74px |
| スケジュールの行 | 130px | 130px |
| 作業項目の詳細(タブの帯、概要の表) | 42px、489px | 42px、488px |
| システムの保留の節、リリースの節 | 107px、145px | 108px、144px |
| システムの設定の行 | 42px | 42px |

ジョブの詳細、作業項目の詳細、要件定義書、監査レポートは、読み込み中の見出しも実物と同じ高さ(106.6px)にした。
題の下の副題が取得後に決まる画面は、副題の行を見出しに空ける(`PageHeader`の`subtitlePending`)。
取得が短い間は、本文と同じく空の枠にし、高さだけを確保する(`reserve`)。
骨組みを出すときに、行にも骨組みを描く(`skeleton`)。
出し分けは、本文と同じ読み込みの段階から`subtitlePendingOf`が決める。
ジョブの詳細の副題はジョブのIDで、経路から分かるので、取得を待たずに出す。
行を枠で囲んだ一覧は`SkeletonListCard`、見出しと本文の塊は`SkeletonSection`で描く。
作業項目の詳細の骨組みは、概要の表と進行の節の間隔(32px)も実物と同じにした。
進行の節の高さは、進行の図の大きさで変わる。

内容の量で高さが変わる部分は、実物と一致しない。
システムのworkerの負荷、監査の失敗、更新履歴は、並べる行の数で実物の高さが変わる。
設定の行数は、設定の数で変わるので、行の高さだけを合わせた。
実行中のジョブの行は、ステップを持つと101pxになり、骨組みの74pxと違う。
監査レポートは、幅400pxで題が折り返すと、実物の帯が骨組みより高くなる。

## ページ送り

長い一覧は、取得済みの配列を画面の中でページに区切って出す。
取得とbackendの上限は変えない。
ページ送りは、上限まで取った行の表示を分けるだけである。
区切る規則は`src/lib/pagination.ts`の純関数、ページの状態とスクロールは`src/lib/usePagination.ts`にある。
スクロールの目標位置は`src/lib/scrollTarget.ts`の純関数が求める。
スクロールする枠は、`src/lib/scrollRoot.ts`の`findScrollRoot`が、一覧を包む要素から親をたどって探す。
枠は、枠の目印を付けた要素か、縦にスクロールするoverflowを持つ最も近い祖先である。
枠が見つからないときは、何も動かさない。
操作は`src/components/Pagination.tsx`にある。

ページ送りを持つ一覧は、作業項目の進捗、要件定義の一覧、更新履歴、情報の通知、解決済みの通知、監査の失敗、作業項目に紐づかない失敗である。
1ページの件数は、各一覧の部品の`PAGE_SIZE`が定める。
作業項目の画面の部品は、[`PipelineTable.tsx`](../../console/src/screens/items/PipelineTable.tsx)と[`RequirementsIndexList.tsx`](../../console/src/screens/items/RequirementsIndexList.tsx)である。
システムの画面の部品は、[`UpdateHistory.tsx`](../../console/src/screens/system/UpdateHistory.tsx)、[`NoticeLists.tsx`](../../console/src/screens/system/NoticeLists.tsx)、[`FailureLists.tsx`](../../console/src/screens/system/FailureLists.tsx)である。

操作と表示の規則は次のとおりである。

- 項目が1ページに収まる一覧には、ページ送りを描かない。
- 一覧の下に「前へ」「次へ」、「n / mページ」、表示している範囲を並べる。
  範囲は「26–50件目 / 130件」の形で、変わったときは読み上げを遮らずに知らせる。
- ページ送りは、スクロール枠の下端に貼り付く。
  1ページが画面より長くても、一覧の先頭から「次へ」を押せるようにするためである。
  背景と上の境界線を持ち、下をくぐる一覧と重ならない。
  貼り付く範囲は親の要素の中なので、親は一覧とページ送りだけを含み、`overflow`を持たない包みにする。
  帯は、枠が下に持つ余白の分だけ下げて置く。
  余白の上で止めると、帯の下に次の項目が見えるためである。
  帯と枠のclassは互いの値に依存する。
  そのため`src/lib/layoutClasses.ts`で対にして置き、テストで対応を確かめる。
- 枠には、帯の高さを超える`scroll-padding-bottom`を付ける。
  貼り付いた帯が、キーボードで移したフォーカスを覆わないためである。
  帯の高さと余白の値は、`src/lib/layoutClasses.ts`のコメントにある。
- 帯の中のボタンには、枠の`scroll-padding-bottom`を打ち消す負の`scroll-margin-bottom`を付ける。
  帯は枠の下端から`scroll-padding-bottom`の内側にある。
  打ち消さないと、ボタンへのフォーカスのたびに枠が動くためである。
  負の`scroll-margin`の挙動は、Chromeでだけ確かめている。
  ほかのブラウザでは、ボタンにフォーカスすると枠は動き得る。
- 枠は`position:relative`にする。
  枠の中の`position:absolute`の要素(読み上げ専用の文字)は、枠と一緒にスクロールして、本来の位置に置かれる。
  基準が枠の外にあると、要素が枠の外に置かれ、外側が余分な高さを持つ。
  その要素へフォーカスや検索で移ると、外側がスクロールして見出しの帯が外れる。
- `SCROLL_BODY_CLASS`を使わない画面の枠は、`position:relative`を持たない。
  枠の中の読み上げ専用の文字は、基準が`main`になり、枠と一緒にスクロールしない。
  `main`は`overflow-clip`でスクロールしないので、windowも`main`も動かない。
- 全画面に共通の`main`は、`position:relative`と`overflow-clip`にする。
  `relative`は、枠の外へ出た`position:absolute`の要素の基準を`main`にし、windowが伸びないようにする。
  `overflow-clip`は、`main`をスクロール枠にしない。
  `overflow-hidden`だと、プログラムからのスクロールで`main`が動き、操作では戻せない。
  `overflow-clip`はスクロール枠ではないので、縦に並べる幅では中身の高さが最小の高さになる。
  そのため`min-h-0`を付けて、本文の枠を画面の高さに収める。
- 範囲の注記に「全」を使わない。
  進捗の「N件(全M件)」は絞り込み前の件数を指すので、同じ語を別の件数に使うと食い違うためである。
- 端のボタンは`aria-disabled`で使えないことを示し、押しても何もしない。
  `disabled`は使わない。
  押した直後にフォーカスが失われ、キーボードの操作が途切れるためである。
- 「前へ」「次へ」でページを移すと、一覧の先頭が枠の上端に来るまで、画面の本文を包む枠だけをスクロールする。
  windowは動かさない。
  動かすと、上の見出しの帯が外れて下に空白が出るためである。
  枠の上端に貼り付く部分(システムの帯とタブ)があるときは、その高さと16pxの余白の下に合わせる。
  作業項目の進捗は、絞り込み欄と件数も見えるように、それらを含む位置に合わせる。
- 絞り込みや並び替えで先頭へ戻るときは、スクロールしない。
  入力の途中で位置が動かないようにするためである。
- 絞り込みや並び替えを変えると、先頭のページへ戻る。
  再読み込みで選んだ条件が消えて絞り込みが戻ったときも、先頭へ戻る。
- 再読み込みで件数が減り、今のページが範囲の外に出たときは、最後のページを出し、持っているページも最後に揃える。
  揃えないと、件数が戻ったときに、操作なしで元のページへ跳ぶ。
- ページの番号はURLに持たない。
  画面を開き直すと先頭に戻る。

## タブ

作業項目、レポート、ジョブ、システムの画面は、本体をタブで分ける。
共通の仕組みを、この節にまとめる。

開くタブはURLの`?tab=`に持つ。
既定のタブは名前を持たず、名前が無いか知らない名前なら既定のタブを開く。
作業項目の詳細の`?tab=`と名前をそろえてある。
他のクエリは残す。
タブを選び直しても、履歴は積まず、現在の履歴を置き換える。
タブの切り替えで戻る操作を増やさないためである。

| 画面 | タブ | 既定 |
| --- | --- | --- |
| 作業項目 | 進捗、要件定義(`?tab=requirements`) | 進捗 |
| レポート | 監査レポート、分析(`?tab=analytics`) | 監査レポート |
| ジョブ | 実行中と待ち、履歴(`?tab=history`)、スケジュール(`?tab=schedules`) | 実行中と待ち |
| システム | 状態、失敗と通知(`?tab=failures`)、履歴(`?tab=history`)、設定(`?tab=config`) | 状態 |

共通の`Tabs`(`src/components/Tabs.tsx`)が描き、矢印キーとHome、Endで移る。
Alt、Ctrl、Metaを押している間は移らない。
タブの名前に添えた件数も、本体の見出しや副題に繰り返さない(作業項目の要件定義、レポートの監査レポート)。
件数が重なると、読み手は同じ数字を2か所で確かめることになるためである。
タブの名前と重なる見出しは、本体に置かない。
ただし、節が見出しを名前の元(`aria-labelledby`)にし、読み上げの見出しの階層も保つ本体は、見出しを視覚的にだけ隠して残す(レポートの本体)。
タブの名前には、件数を添えられる。
件数の意味は、読み上げにだけ数字の前に添える。
見える数字は件数だけである。
帯は横にだけスクロールし、縦にはスクロールしない。
選んでいるタブの下線を罫線に重ねるため、帯の外側に罫線を引き、帯ごと1px下げる。
タブに1pxの負の余白を付けると、はみ出した1pxで帯が縦に動く。

選んでいないタブの本体は、描いたまま隠す。
絞り込み、並び替え、ページ、入力、分析の期間を、タブを往復しても保つためである。
隠した本体は`hidden`で読み上げからも外れ、タブの`aria-controls`は、それぞれの本体を指す。
本体は共通の`TabPanel`(`src/components/TabPanel.tsx`)が描く。
システムとジョブの画面は、初めて開くまで本体の中身を描かない(`useVisitedTabs`)。
開いた後は、ほかの画面と同じく隠して残す。
本体の枠は常に描くので、タブの`aria-controls`は、中身が無い間も有効である。

開閉できる部分は、共通の`Disclosure`(`src/components/Disclosure.tsx`)が描く。
`<details>`と`<summary>`なので、キーボードの操作と開閉の読み上げは要素が持つ。
見出し行には、開閉を示す矢印を添え、フォーカスの輪を描く。
開閉の状態は、URLと履歴のどちらにも残さない。

本体は1つのスクロール枠を共有する。
そのため、タブごとにスクロール位置を覚え、移った先の位置へ戻す。
まだ離れたことのないタブは先頭から始める。
記憶は画面を開いている間だけ持つ。

取得は画面が持ち、タブの切り替えでは取得しない。
ただし、ジョブの画面と、システムの画面の設定のタブは、タブを初めて開くまで取得を始めない。
Console用workerの枠が1つで、開いていないタブの取得を載せないためである。
選んでいない側の取得が失敗したときは、タブの名前に「取得に失敗」の文言と記号を添える。
色だけに頼らないためである。
選んでいるタブは、本体が失敗を伝えるので印を付けない。
ログイン切れ(401)は上のバナーが知らせるので、印にしない。
段の印(システムの「注意」「要対応」)があるタブは、選んでいるかにかかわらず、取得の失敗の印を並べる。
「注意・取得に失敗」のように書く。
値が前の取得のものだと、読み手に伝えるためである。
段の印は、注意が三角、要対応が八角で、色だけに頼らない。

タブの組、本体の`id`と`hidden`、失敗の印、URLの読み書きは、`src/lib/tabSet.ts`の純関数が決める。
画面ごとの定義は`src/lib/itemsTabs.ts`、`src/lib/reportsTabs.ts`、`src/lib/jobsTabs.ts`、`src/lib/systemTabs.ts`にある。
スクロール位置を戻す処理(`src/lib/useTabScroll.ts`)と、`hidden`が画面に効くことは、画面を描いて確かめる。

## ジョブへのリンク

作業項目の遷移と失敗は、動いたジョブのIDを持つ([作業項目の状態とリース](work-items.md)の「ジョブの記録」)。
`src/lib/jobLink.ts`の`jobDetailPath`が、IDからConsoleのジョブの詳細のパス(`/jobs/<id>`)を作る。
`src/components/JobLink.tsx`の`JobLink`が、そのパスへのリンクを描く。
リンクは同じタブで開く。
`work_item_detail`の遷移と失敗の行の型ガードは、`src/api/guards/workItemTransitions.ts`と`workItemFailures.ts`にある。
`tests/scripts/console_work_item_jobs_contract.test.ts`が、backendの変換結果がこれらの型ガードを通ることを確かめる。

IDはDBに記録された値で、信頼できない入力として扱う。
UUIDの形のものだけを、固定の形のパスに入れる。
形が違えばリンクを出さない。
URLの組み立てに、IDから先の文字列を使わない。

Windmillの画面へのリンクは、`jobRunUrl`と`WindmillJobLink`が作る。
パスは固定の形`/run/<job_id>`で、別のタブで開く。
リンクは、同じオリジンの相対パスにする。
ConsoleはWindmillと同じオリジンで配信するためである。
URLにワークスペースの指定(`?workspace=`)を付けない。
指定の無いURLをWindmillがどのワークスペースで開くかは、確かめていない。
別のワークスペースを選択中だと、ジョブを開けないことがある。
単一のワークスペース(`factory`)の運用を前提にする。

`JobLink`は、次の場所に組み込んである。

- 要対応の失敗の詳細
- システムの画面の、監査の失敗と、作業項目に紐づかない失敗
- 作業項目の詳細の、失敗の記録と状態の遷移
- 新規投入の結果
- PRレビューの投入の結果のうち、待っているとき、取得できないとき、読み取れないとき
- スケジュールの直近の実行

要対応の失敗の詳細は、作業項目の詳細(`/items/<id>`)へのリンクも持つ。

## 画面を足す手順

1. 画面を`src/screens/<入口>/`に置く。
2. `src/app/screens.ts`の表に、入口か詳細の経路を1行足す。
   入れ子の経路は`children`に書く。
   経路の一覧を固定する`src/app/routeTable.test.ts`にも1行足す。
3. 表示する語を`src/lib/labels.ts`に足す。
4. 判定は純関数にして、`src/lib/`に置き、テストを書く。
5. 見出し(`PageHeader`)に、画面が自分のクエリから作った`refreshStatusOf`の結果を渡す。
   取得を複数持つ画面は、`refreshStatusOfAll`で1つにまとめて渡す。
   取得するデータを持たない画面は渡さない。
6. 足した表示を、[Consoleの画面の表示の原則](../console-display.md)に照らして確かめる。
   確認の方法は、同じ文書の[毎日見る目での確認](../console-display.md#毎日見る目での確認)にある。

### ブランチ版の確認

検証用サーバー(`scripts/console-branch-server.ts`)は、ブランチ版のConsoleを、ローカルのWindmillに繋いで開かせる。
操作の手順は、[ブランチ版のConsoleを確かめる](../setup.md#ブランチ版のconsoleを確かめる)にある。
ブラウザから見るとConsoleとWindmillが同じオリジンになるので、ブランチ版のConsoleが、運用者のCookieのまま本物のWindmillのAPIを呼ぶ。
既定は読み取りだけで、要求を次のように振り分ける。

| 要求 | 扱い |
| --- | --- |
| `/console/*` | `console/dist`を返し、無いパスはSPAの`index.html`に落とし、assets、draw.ioのファイル、`status.json`は無ければ404にし、Caddyと同じCSPなどのヘッダーを付ける |
| `/console` | `/console/`へ308で飛ばす |
| 符号化した区切りと`..`を含む`/console/`のパス | 400にする |
| `/api/`の外のGET、HEAD、OPTIONS | `--upstream`(既定は`http://127.0.0.1:8080`)へ中継する(ログインの画面と静的な資源が当たる) |
| `/api/`の下の読み取りのGET、HEAD、OPTIONS | 許可リストにある経路だけ中継する(`/api/version`、`/api/users/whoami`、ジョブ1件を読む`jobs_u`の経路) |
| 読み取りの5つのscriptを実行するPOST | 中継する |
| ほかの要求 | 403にし、人が`--allow-writes`を付けたときだけ中継する |

Windmillは、GETでもscriptを同期で実行できる(`GET /api/w/{workspace}/jobs/run_wait_result/p/{path}`)。
`windmill-client` 1.817.0のOpenAPIに、この経路がGETとPOSTの両方で載っている。
そのため、GETとHEADも許可リストで絞る。
実行、再開、取り消し、再実行、ストリーム、エンドポイントの経路(`/api/r/`)、webhookを含むパスは、メソッドを問わず403にする。
ConsoleがWindmillを呼ぶのは、読み取りのscriptを実行するPOSTと、`/console/status.json`のGETだけである。
`/api/`のGETは使わない。

読み取りの5つは、`console_query`、`console_holds`、`console_jobs`、`console_schedules`、`console_config`である。
`tests/scripts/console-branch-server-readonly.test.ts`が、次を固定する。

- 5つが相対importで辿るファイルに、SQLの書き込みとWindmillの書き込みや実行のAPIが無い。
- 書き込みと読み取りが同居する共有の部品(`lib/db.ts`、`lib/holds.ts`、`lib/freeze_apply.ts`)から取り込む名前が、読み取りの関数に限られる。
- 呼ぶ関数(`fetchDeploymentRows`、`sumAgentCostSince`、`listActiveHolds`、`readFreezeState`)の本文に、書き込みが無い。
- `console_holds`は、凍結の変数の書き込みの口(`writeVariable`)を組み立てるが、読む経路は`readVariable`だけを呼ぶ。

`console_holds`は、保留、凍結、全停止の状態、反映の承認待ちを読むだけである。
解除、承認、却下、全停止は別のscriptが行う。

要求は、次の検査も通る。

- Hostは、`127.0.0.1:<port>`か`localhost:<port>`だけを通す。
  DNSリバインディングで別の名前から届いた要求を断るためである。
- Originは、このサーバー自身のオリジンのときだけ、中継先のオリジンに置き換えて中継する。
  ほかは403にする。
- 中継の要求の`Sec-Fetch-Site`が`cross-site`か`same-site`なら403にする。
- 転送元を名乗るヘッダー(`Forwarded`、`X-Forwarded-*`、`X-Real-IP`)とhop-by-hopのヘッダー(`Connection`が名指しするものを含む)は、中継先へ渡さない。
- 中継先の`Location`は、このサーバーのパスに直す。
  `//host`のようなプロトコル相対の形にならないよう、先頭の`/`を1つにそろえる。
- Bunのfetchは、渡した`Sec-Fetch-*`を落とさずに中継先へ送る(模擬の中継先で実測した)。
  ブラウザが付けた値のまま、中継先のCaddyの規則に届く。

`--allow-writes`は、端末で人が「yes」と入力したときだけ有効になる。
標準入力が端末でないとき(agentの起動やパイプ)は、起動に失敗する。
有効な間は、起動時に目立つ警告を標準出力に出し、全応答に`x-branch-server-writes: on`を付ける。

反映後の実機と違う点は、`status.json`を配信しないことである。
そのため、サイドバーの版の情報は出ない。
CSPなどのヘッダーは、`infra/Caddyfile`の`console_headers`と`drawio_headers`と同じ値を付け、テストが一致を確かめる。

### 描画の確認

アクセシビリティの機械で確かめられる範囲は、[ブラウザでのa11y検査](#ブラウザでのa11y検査)が毎回確かめる。
ここは、その検査が見ない見た目と文言を、目で確かめる手順である。

画面の描画は、Playwrightで確かめる。
Consoleの開発サーバー(`bun run --cwd console dev`、`http://localhost:5173/console/system`)は`/api`を中継しない。
そのため、`/api/w/factory/jobs/run_wait_result/p/**`をすべて`page.route`で差し替える。
`console_holds`だけでなく、システムの画面が呼ぶ`console_query`の`system_status`、`deployments`、`summary`も差し替える。
実際のWindmillには何も届かないので、解除のボタンを押しても、本物の保留は解除されない。

状態ごとに応答を変えて、次を確かめる。

- 保留、取り込みの保留、deployの保留、スケジュールの凍結が並ぶ表示と、何も無い表示
- 保留の表が無い、保留を読めない、保留の表が壊れている、凍結の変数を読めない表示
- `<a href>`を含む理由と、書字方向を変える制御文字を含む置いた主体が、文字のまま出ること
- 長い理由と長い対象の折り返し
- 期限が数十秒後の行が、画面の時計の更新(間隔は[`src/app/clock.ts`](../../console/src/app/clock.ts)の`CLOCK_TICK_MS`)で「期限切れ」に変わること
- 401のときの、ログインを促す文
- ライト、ダーク、狭い幅
- 確認のダイアログと、開いた直後のフォーカスが「取り消す」にあること
- 実行中のロックと、解除の結果のトースト

撮影した画像はリポジトリに置かない。
