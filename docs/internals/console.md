# Consoleの仕様

Consoleのアプリ(`console/`)の構成と、成果物を配信する仕組みを書く。
アプリの構成は、画面とAPI層を変更する人が読む。
配信の仕組みは、`console_fetcher`とCaddyを変更する人が読む。
何を守るかと残るリスクは、[セキュリティ](../security.md)の「Consoleの配信」にある。
画面に何を表示するかの原則は、[Consoleの画面の表示の原則](../console-display.md)にある。

## アプリの構成

ConsoleはSPAである。
Vite、React、TypeScript、Tailwind CSS、shadcn/uiの部品で作る。
経路はReact Router、データの取得はTanStack Queryで扱う。
画面の判定は純関数に切り出して`bun test`で確かめる。
画面の部品は、`renderToStaticMarkup`で静的に描いたHTMLを`bun test`で確かめる。
`bun test`にDOMの環境が無いため、DOMを動かすテストは書かない。
クリックなどの操作の結果は、判定を純関数に切り出して確かめる。

| ディレクトリ | 役割 |
| --- | --- |
| `src/api/` | scriptの呼び出し、失敗の分類、応答の型ガード、取得 |
| `src/app/` | 外枠、サイドバー、経路の表、ログインの状態、Provider |
| `src/screens/` | 画面。入口ごとのディレクトリに置く |
| `src/components/` | 共通の部品。`ui/`はshadcn/uiの部品を写したもの |
| `src/lib/` | 表示と判定の純関数 |

shadcn/uiの部品は、CLIを使わず、new-yorkのソースを手で`src/components/ui/`に写す。
importは相対パスにし、型アサーションは外す。
`as`を禁じる検査が、`console/src/`にもかかるためである。

## 見た目の体系

色の定義は`src/index.css`の変数だけにする。
値は`light-dark()`で書き、`html`の`data-theme`が配色を決める。
`data-theme`が無いときだけ、OSの設定に従う。
文字と背景の組はWCAG AAの4.5:1以上、入力欄の境界と点のような図形は3:1以上を保つ。

| 区分 | 決まり |
| --- | --- |
| 面 | 背景、面(`card`)、浮いた面(`popover`)の3段で重ねる。ダークは明るさの差、ライトは線と影で階層を出す。背景は真っ黒にしない |
| アクセント | 藍(`primary`)の1色。選択中の枠線と帯、主要な操作、フォーカスの輪に使う |
| 選択中 | 期間、種類、テーマの切り替えの選択中は、藍の枠線と藍寄りの面(`src/lib/selectedStyle.ts`)で示す。面の明るさの差は両テーマで小さいため、枠線で未選択と分ける。この3つは文字の太さを変えない。文字幅が動くと隣の項目がずれるためである。試行の切り替えとタブは、この表し方の対象外である |
| 意味の色 | 承認は青(`approval`)、失敗は赤(`destructive`)、通知は琥珀(`warning`)、成功は緑(`success`)。点、バッジ、ラベルに使う |
| 文字の濃さ | 主(`foreground`)、副(`muted-foreground`)、補足(`subtle-foreground`)の3段 |
| 文字の大きさ | 12、13、14、16、20、24pxの6段(`text-caption`、`text-small`、`text-body`、`text-lead`、`text-title`、`text-display`)。本文の行間は1.7 |
| 書体 | Hiragino Sans、Noto Sans JP、system-uiの順。Webフォントを読み込まない。CSPが外部のファイルを拒むためである |
| 数字 | 件数や時刻は`tabular-nums`で桁をそろえる |
| 動き | 選択とhoverの遷移は150ms。テーマの切り替えの間は、全要素の遷移を止める([テーマの切り替え](#テーマの切り替え))。動きを減らす設定の利用者には、アニメーションと遷移をほぼ止める |

通知の点は、図形用の`notice-mark`で描く。
図形の基準(3:1)で足りるため、文字の`warning`と色を分ける。

文字と背景の組が基準を満たすことは、`src/theme-tokens.test.ts`が`index.css`を読んで確かめる。
対象は、面の上の文字、意味の色の文字、薄く重ねた面(バッジと帯)の上の文字、入力欄の境界・フォーカスの輪・通知の点などの図形である。
`-foreground`で終わる色と、その元の色の組も、定義されたすべてをライトとダークの両方で確かめる。
選択中の枠線は、面とトラックの上で3:1以上を保つ。
承認、失敗、通知の違いは、色だけに頼らず、隣の文字でも伝える。

文字の大きさ(`text-*`)を足したら、`src/lib/cn.ts`の`FONT_SIZES`にも足す。
足し忘れると、`cn`が大きさを文字色と見なし、同じ要素のどちらかを落とす。
足し忘れは、`src/lib/cn.test.ts`が検出する。
`FONT_SIZES`と`index.css`の大きさの一覧が違うと、このテストが失敗するためである。

表示する日本語は`src/lib/labels.ts`に集める。
画面は、状態や種類の生のコードを出さない。
表に無い値は、元の文字列ではなく決まった文言で出す。
backendの値が表から漏れていないことは、`tests/scripts/console_summary_contract.test.ts`が確かめる。

## テーマの切り替え

テーマの選択は、ライト、ダーク、OSに合わせる(`system`)の3つである。
保存するのは選択だけで、保存先は`localStorage`のキー`factory-console.theme`である。
「OSに合わせる」を選んだときは、保存したキーを消す。
知らない値と読めない値は、「OSに合わせる」として扱う。
`resolveTheme`が、選択とOSの設定から`data-theme`の値を決める。
「OSに合わせる」で解決した配色は保存しない。

### OS設定の解決

`html`の`data-theme`は、「OSに合わせる」のときも、OSの設定を読めるかぎり`light`か`dark`で付ける。
OSの配色の設定が変わると、JavaScriptが`matchMedia`の`change`を受けて、`data-theme`を付け替える。
メディアクエリに色を任せると、`change`が届くより前にスタイルの再計算が始まるためである。
この順では、遷移を止める前に、`transition-colors`を持つ要素が途中の色を経由し始める。

選択は`html`の`data-theme-preference`にも残す。
OSの設定が変わったとき、この属性で「OSに合わせる」かを見分ける。
ライトとダークを明示した選択は、OSの設定が変わっても動かさない。
属性が無いときは、`theme-init`が動かなかった場合なので、「OSに合わせる」として扱う。

OSの設定を読めない環境(`matchMedia`が無い、または例外を投げる)では、「OSに合わせる」の`data-theme`を付けず、購読もしない。
`ThemeSwitch`で「OSに合わせる」を選んだ場合は、それまでの`data-theme`を外す。
その環境では`index.css`の`color-scheme: light dark`が、OSの設定に従う。
ライトとダークを明示した選択は、OSの設定を読まないので、読めない環境でも切り替わり、保存される。

### 描画前の設定

`data-theme`と`data-theme-preference`は、描画の前に`public/assets/`の`theme-init`のscriptが付ける。
描画の後に付けると、最初の表示で配色が替わるためである。
保存した値は`light`と`dark`に完全一致するときだけ受け入れる。
CSPがインラインのscriptを拒むので、scriptは外部のファイルにして、`index.html`の`head`から古典的なscriptとして読む。

ファイル名には内容のハッシュを含む。
配信は`immutable`なので、中身を変えて名前を変えないと、ブラウザが古い中身を使い続けるためである。
内容を変えたら、名前を`contentHashedName`が返す名前に替え、`index.html`の参照も替える。
`console/scripts/public-assets.test.ts`が、名前と内容の対応と、`index.html`の参照を確かめる。

`console/public/`と`console/index.html`は保護パスである。
どちらもバンドルを通らずにそのまま配信され、書き換えられると、全画面で任意のコードが動くためである。
変更を含むPRは人がレビューし、Factoryは自動でマージしない。
一覧は[セキュリティ](../security.md#保護パスの変更を止める)にある。

### 切り替えの間の遷移の停止

`transition-colors`を持つ要素は一部だけなので、テーマを替えると、それらだけが遅れて変わり、ちらついて見える。
切り替えの間だけ、`html`に`data-theme-switching`を付け、全要素の遷移を止める(`index.css`)。
印を付ける入口は`beginThemeSwitch`の1つで、次の2つの操作が呼ぶ。

- `ThemeSwitch`でテーマを選ぶ(`applyThemePreference`)。
- 「OSに合わせる」のとき、OSの配色の設定が変わる(`followColorSchemeChange`)。

どちらも、遷移を止めてから`data-theme`を替える。
印は2フレーム後に外す。印を付けたのと同じフレームで、スタイルの再計算が終わっているようにするためである。
外す予約は番号で管理し、先の予約が、後の切り替えの途中で印を外さない。
背景のタブではフレームが進まず、印は表示に戻るまで残る。残っても遷移が止まるだけである。

OSの設定の購読(`useColorSchemeSwitchGuard`)は、`AppProviders`に1つだけ置く。
`ThemeSwitch`が、広い画面のサイドバーと狭い画面のドロワーの2か所に描かれ、それぞれに置くと購読が重なるためである。
外枠(`AppShell`)には置かない。
ルートのErrorBoundaryが外枠を置き換えた画面でも、OSの設定の変更に追従するためである。
購読は、Strict Modeの購読、解除、購読の順でも、リスナーが1つだけ残る。

## 経路

経路は`src/app/screens.ts`の1つの表から作る。
サイドバーの入口、件数のバッジ、React Routerの経路は、すべてこの表を読む。
routerの基準は`/console`で、Caddyが`/console/`の下のパスに`index.html`を返す。

| パス | 画面 | 状態 |
| --- | --- | --- |
| `/console/` | 要対応 | 承認、失敗、通知の一覧。承認・却下、再実行、通知の解決ができる |
| `/console/items` | 作業項目 | 進捗と要件定義のタブ。`?tab=requirements`で要件定義を開き、`?scope=`で進捗の範囲を指す |
| `/console/items/new` | 新規投入 | Issueを手動で作り、作業項目として登録する入力欄 |
| `/console/items/:id` | 作業項目の詳細 | 概要、要件定義、ラウンド、承認の履歴のタブ。`?tab=<名前>`で開くタブを指す |
| `/console/items/:id/requirements` | 要件定義書 | 本文、目次、図。`?attempt=<k>`で試行を指す |
| `/console/reports` | レポート | 監査レポートの一覧と手動起動(監査レポートのタブ)、分析のグラフと表(分析のタブ) |
| `/console/reports/audit/:id` | 監査レポート | 作業項目`:id`の本文 |
| `/console/jobs` | ジョブ | 実行中と待ち、履歴、スケジュールのタブ。`?tab=<名前>`で開くタブを、`?status=`と`?script=`で履歴の絞り込みを指す |
| `/console/jobs/:id` | ジョブの詳細 | 状態、引数、結果、ログ、フローのステップ、失敗の保存済みの原因 |
| `/console/system` | システム | 要約の帯と4つのタブ(状態、失敗と通知、履歴と構成、設定)。保留と凍結(解除できる)、反映の状態、workerの負荷、監査の失敗、作業項目に紐づかない失敗、情報の通知、更新履歴、解決済みの通知、起動の関係、設定の閲覧 |

どの経路にも当たらないパスは、「ページが見つかりません」の画面で受ける。
経路の番号は、正の整数の文字列だけを受け付ける。
経路やURLの引数は選択を表すだけで、承認や再実行などの操作は起こさない。

表の1行は、入口の画面と、その下で受ける経路(`children`)を持つ。
`children`は入れ子にでき、親の画面は`Outlet`を描く。
どの経路にも`ErrorBoundary`が付き、省くと既定の`RouteError`になる。
画面の読み込みや描画が失敗すると、その画面の位置にだけ再読み込みの案内を出し、サイドバーと帯は残す。
表から作る経路の一覧は、`src/app/routeTable.test.ts`が固定する。

### 旧Consoleのリンク

旧Console(Windmillのraw app)は廃止した。
過去のDiscordの通知、Issueのコメント、PRの本文には、旧Consoleのリンクが残る。
旧ConsoleのURLを開くと、Caddyが固定の`/console/`へ302で飛ばす。規則は「配信の経路」にある。
URLのフラグメントはブラウザが保つので、新しいConsoleが読み替える。
`main.tsx`が、routerを作る前に`history.replaceState`で置き換える。
routerが先に`/console/`の画面を描くと、その画面が一瞬動いてしまうためである。
置き換えは履歴を増やさない。
`<id>`と`<k>`は、先頭が0でない正の整数に限る。

| 旧Consoleのフラグメント | 置き換え先 |
| --- | --- |
| `#requirements/<id>` | `/console/items/<id>/requirements` |
| `#requirements/<id>/attempt-<k>` | `/console/items/<id>/requirements?attempt=<k>` |
| `#audit/<id>` | `/console/reports/audit/<id>` |

上の表に合わない旧ConsoleのフラグメントとフラグメントのないURLは、`/console/`の入口(要対応)に着く。

承認フローが投稿するConsoleのリンクは、新しいConsoleの経路を直接指す。
`f/factory/lib/approval_support.ts`が、次の3つを作る。

| リンク | 作る関数 | 経路 |
| --- | --- | --- |
| 要件定義書 | `buildConsoleUrl` | `/console/items/<id>/requirements`。試行が分かるときは`?attempt=<k>`を付ける |
| 承認の詳細 | `buildApprovalConsoleUrl` | `/console/?approval=<id>` |
| 監査レポート | `buildAuditConsoleUrl` | `/console/reports/audit/<id>` |

## API層

Consoleは、`src/api/windmill.ts`の`runScript`だけを通してWindmillのscriptを呼ぶ。
`POST /api/w/factory/jobs/run_wait_result/p/<path>`を、`credentials: "same-origin"`と`cache: "no-store"`で呼ぶ。
ログインのCookieだけで動くので、トークンは持たない。

`runScript`は`src/api/`の中にとどめる。
画面は、取得の`queries.ts`と書き込みの`writes.ts`にある型付きの関数だけを使う。
`src/api/`の外が`windmill.ts`をimportしないことは、契約テストが確かめる。

呼べるscriptは、`SCRIPT_PATHS`の許可リストにある次の17個だけである。
どれもtag`console`を持ち、Console用のworkerで動く。

| 名前 | 用途 | 型付きの関数 |
| --- | --- | --- |
| `console_query` | 読み取り | `fetchSummary`など(`queries.ts`) |
| `console_holds` | 有効な保留と凍結の読み取り | `fetchHolds`(`holdsQueries.ts`) |
| `console_jobs` | ジョブの一覧と詳細の読み取り | `fetchActiveJobs`、`fetchJobHistory`、`fetchJobDetail`(`jobsQueries.ts`) |
| `console_schedules` | scheduleの状態の読み取り | `fetchSchedules`(`jobsQueries.ts`) |
| `console_config` | 設定の全項目の読み取り | `fetchConfig`(`jobsQueries.ts`) |
| `approval_decide` | 承認依頼への承認か却下の記録 | `decideApproval` |
| `retry_work_item` | 止まった作業項目の再開 | `retryWorkItem` |
| `audit_kickoff` | 監査の手動起動 | `kickoffAudit` |
| `notice_resolve` | 通知1件の解決 | `resolveNotice` |
| `manual_intake_submit` | 手動投入の受付 | `submitManualIntake` |
| `hold_release` | 保留1件の解除 | `releaseHold` |
| `freeze_release` | 凍結かdeployの保留1件の解除 | `releaseFreeze` |
| `console_job_cancel` | 実行中か待ちのジョブ1件の中止 | `cancelJob` |
| `console_job_rerun` | 失敗した定期ジョブ1件の再実行 | `rerunJob` |
| `console_config_update` | 設定の1項目を、無効にする向きか下げる向きに変更 | `updateConfig` |
| `console_hold_place` | 保留か凍結の設置 | `placeHold` |
| `console_schedule_stop` | scheduleの無効化 | `stopSchedule` |

保留や凍結を置くscriptは`console_hold_place`の1本で、置ける種類と期限の上限を固定する。
スケジュールを止める`console_schedule_stop`は、止めてよいスケジュールの表を持つ。
有効に戻すscriptは許可リストに無い。

パスは呼び出し側の名前から引き、外から受け取った文字列では呼ばない。
Consoleは管理者のCookieで動くので、呼べる範囲を固定する。
許可リストに足すscriptは、tag`console`を付け、秘密値を読む範囲を[Console用workerの境界](../security.md#console用workerの境界)に合わせる。

`runScript`は例外を投げず、応答を`classifyRunResponse`で分類して返す。
中断(`AbortSignal`)だけは、取り消しとして扱えるよう例外を再び投げる。

| 応答 | 分類 |
| --- | --- |
| 2xxで本文がJSON | 成功 |
| 2xxで本文がJSONでない | `invalid_response` |
| 401 | `unauthorized` |
| 403 | `forbidden` |
| 408、504 | `timeout_or_unknown` |
| 500 | `job_failed`。本文から取り出した文(`message`)を500字まで持つ。スタックは持たない |
| 500で、本文の文が待ちの上限の定型文(文頭の`timeout after <数>`)に合う | `timeout_or_unknown` |
| その他の状態 | `http`。状態の番号と、4xxなら本文から取り出した文を500字まで持つ |
| 通信の失敗 | `network` |

本文はContent-Typeを見ずに読む。
失敗の本文は、JSONの`error.message`、`message`、文字列の`error`の順に探し、JSONでなければ本文のテキストを使う。
`timeout_or_unknown`は、ジョブが終わったか分からない状態を表す。
書き込みでは、ジョブの失敗、待ちの上限、形が違う応答、通信の失敗、5xxで、処理が途中まで進んでいる可能性がある。
そのため`describeWriteFailure`は、書き込みのこれらの失敗を「結果が分かりません。一覧を読み直して確かめてください」と案内する。
scriptの例外が届く状態は、経路で変わりうる。
500以外の状態で届いた例外は、`job_failed`に分類されないので、種類で決める書き込みの判定から外れる。
読み取りの失敗は、共通の部品`QueryFailureAlert`が出す。
文は`describeQueryFailure`が、何が起きたかの主文、次の操作、サーバーの文に分けて作る。
サーバーの文は内部の名前を含みうるので、主文に混ぜず、折りたたむ「詳細」だけに出す。
詳細は、書き込みの失敗と同じく、見えない文字と書字方向の制御文字を代替文字に置き換えてから描く。
`view`の不一致を受けたときは、Consoleとバックエンドの版がずれている可能性を主文で伝える。
Consoleが新しい場合も、バンドルが古い場合も起こる。
次の操作は、待つこと、版を見比べること、ログを確かめることの順に案内する。
反映は2分ごとなので、まず待つ。
直らなければ、システムの画面で「反映した版」と「Consoleの取り込み」を見比べる。
反映が失敗していれば、`self_update`のジョブのログを確かめる。
`system_status`が断られたときは、システムの画面も開けないので、画面を案内先にしない。
不一致は状態や分類で決めず、本文の`"view" must be one of`で判定する。
この文は`console_query`が投げるもので、`tests/scripts/`の契約テストが、実際の文でこの判定を確かめ、文が変わったことを検出する。
4xxの案内は、ジョブが作られる前に断られた場合を含むので、workerのtagと権限、またはジョブのログを挙げる。
500を除く5xxの本文はHTMLなどになりうるので、画面に出さない。
ジョブの失敗の結果は`{"error":{"name","message","stack"}}`の形で、`stack`には内部のパスが入る。
画面には`message`だけを出す。

### 実測した応答

| 状況 | 応答 | 確認 |
| --- | --- | --- |
| Cookieなしで`run_wait_result`を呼ぶ | 401、`text/plain; charset=utf-8`、本文`Unauthorized` | 実測 |
| `Sec-Fetch-Site: cross-site`で`/api/*`を呼ぶ | Caddyが403を返す | 実測 |

### 応答の型ガード

応答は、`src/api/guards/`の型ガードを通してから使う。
形が崩れた応答(必須の項目の欠落、型の違い、idの不正)は、一部だけを使わず、全体を`invalid_response`にする。
表示にしか使わない列挙(承認の種類と状態、Issue提案の発生元、通知の重要度と種類、失敗の種類と状態)は、文字列として受ける。
知らない値は`labels.ts`の決まった文言に落とす。
承認・却下などの操作の分岐は、種類や状態を見て決める。その操作の側で、受け付ける値を列挙して絞る。
backendが先に新しい値を反映した間や、配信を前の版に固定している間に、要対応の一覧が丸ごと消えないためである。
時刻の文字列は、`Z`か`+09:00`のオフセットが付いた形だけを通す。
オフセットが無いと、ブラウザがローカル時刻として読み、閲覧する場所で絶対時刻がずれるためである。

### 取得の方針

自動で取り直すのは、`summary`と、ジョブの画面が読む実行中の状態だけである。
`summary`は120秒ごとに、タブが見えている間だけ取る。
ジョブの詳細の状態は15秒ごと、実行中と待ちのタブの今のステップは30秒ごとに取る。どちらも、止める条件は[ジョブの画面](#ジョブの画面)にある。
更新履歴と作業項目の進捗は自動で取り直さない。
サイドバーの件数と、要対応の一覧は、`summary`の1つの取得を共有する。
再試行するのは、通信の失敗、待ちの上限(`timeout_or_unknown`)、500を除く5xxだけで、2回までにする。
500はジョブの失敗として分類される。
401、403、4xx、形が違う応答、ジョブの失敗は再試行しない。再び取っても同じ結果になり、120秒ごとの取得に失敗が積み増されるためである。
書き込みは再試行しない。結果が分からないまま2回実行しないためである。

1つのタブが`summary`を取り直すと、1日に720件のジョブができる(120秒ごと)。
システムの画面を開いたタブは、`console_holds`の取得でも1日に720件を足す。
ジョブの詳細で実行中のジョブを開いたタブは、15秒ごとの状態の取得で1日に最大5,760件を足す。
実行中と待ちのタブで、実行中のflowが2件あるときは、30秒ごとに2件ずつ読むので、同じく1日に最大5,760件を足す。
タブを複数開くと、タブごとに取得する。取得はタブのキャッシュを分け合わないので、件数はタブの数に比例する。
画面が15分操作されないあいだは、今のステップの取得を止める。
ジョブの保持期間は、#138で扱う。

### 書き込み

書き込みのscriptは、`src/api/writes.ts`の型付きの関数だけから呼ぶ。
関数は失敗を`ApiFailure`で投げ、戻りを`src/api/guards/writeResults.ts`の型ガードに通してから返す。
形が違う戻りは`invalid_response`にする。

| 決まり | 理由 |
| --- | --- |
| 認可はWindmillのログインに任せる | Consoleは独自の認可を持たない。ログインしていない呼び出しは、Windmillが401にする |
| 承認者と解決者は引数に取らない | 画面から渡した名前は信用できない。scriptがジョブの実行文脈(`WM_USERNAME`、無ければ`WM_EMAIL`)から導き、導けなければ拒否する |
| 同一オリジンの`fetch`でPOSTし、本文はJSONにする | 他のサイトや注入されたリンクから、運用者のCookieで操作させないため。副作用のあるGETと、ページの移動による書き込みは、Caddyが403にする([セキュリティ](../security.md)の「Consoleの配信」)。Consoleの呼び出しはPOSTの`fetch`なので、この規則に当たらない |
| 操作の値をConsole側で固定する | 監査は`force: false`、`source: "manual"`、`days: 7`で起動する。承認の補足(`note`)は固定の文にする。画面から変えさせない |
| 再試行しない | 結果が分からないまま2回実行しないため |

承認は、同じ決定が記録済みの行にもう一度呼ぶと、ハンドラの起動をやり直す。
二重の送信は、画面側で止める。

却下の理由は、4000文字までにする(`MAX_REASON_LENGTH`)。文字はコードポイントで数える。
`decideApproval`は、上限を超える理由を送らず、`RangeError`で断る。
画面は、送る前に長さを確かめて入力欄で知らせる。
理由はDBに記録され、Issueやレポートに出るためである。
script側には上限が無く、Windmillのapiを直に呼ぶ者には効かない。script側の上限は、別のIssueで扱う。

#### 共通のフック

`useWriteMutation`(`src/api/mutations.ts`)が、ロック、実行、読み直しをつなぐ。
結線は、Reactから切り離した`createWriteRunner`(`src/api/writeRunner.ts`)に置く。
`bun test`が、実際のQueryClientで確かめる。
実行の流れは`executeWrite`、ロックは`runLocked`と`writeLocks`、読み直せなかったときの待ちは`holdUntilFresh`に切り出してある。

- 対象のキー単位でボタンをロックする。キーは`writeTargetKey`が作り、承認の承認と却下のように、同じ対象への操作は同じキーで止める。ロックは画面全体で共有するので、同じ対象のボタンが複数の場所にあっても、同時には動かない
- ロックはmutationの実行の中で取る。同じ瞬間に2回押されても、実行は1回になる
- 成功と、結果が分からない失敗の後に、関連する取得(既定はsummary)を読み直す。読み直しが終わるまでロックを残す
- 画面の知らせの関数は、結果用も一覧が古いこと用も、例外を投げても読み直しとロックの扱いを変えない
- 401は取得と同じ経路でログインの帯に流す
- 成功の知らせの文は、`src/lib/writeNotices.ts`の純関数が作る。解決済みだった通知の解決は成功として扱う

結果が分からない失敗は、ジョブの失敗、待ちの上限、形が違う応答、通信の失敗、5xxである。
401、403、4xxは、ジョブが動く前に断られたので、読み直さない。
ジョブの失敗(`job_failed`)は、結果が分からないものとして扱う。
scriptの断り(理由なしの却下、記録済みの別の決定など)と、副作用の後の失敗が、同じ形で返り、本文から区別できないためである。
区別するには、scriptが断りを固定の接頭辞で投げる必要がある。

読み直しが失敗したか、30秒以内に終わらなかったときは、一覧が古いことを知らせる(`STALE_LIST_NOTICE`)。
その対象は、読み直せなかった取得のすべてが次に成功するまで、押せないままにする。読み直せた取得は待たない。
古い一覧のままだと、済んだ操作をもう一度押せるためである。
summaryは120秒ごとに取り直すので、通信が戻れば解ける。

ロックを持つのは、このタブの中だけである。
複数のタブや、リロードの後の二重の送信は止められない。
サーバー側の冪等性の課題で、Consoleの外で扱う。

Issueに由来する文字は、`displayableIssueText`(`src/lib/intakeText.ts`)を通してプレーンテキストで描く。
書き込みの失敗の文に入るジョブの失敗の文と4xxの詳細も、同じ関数を通す。
見えない文字や並びの見た目を入れ替える文字を、代替文字に置き換えるためである。
置き換える分類は、backendの`countHiddenCharacters`と同じである。
全コードポイントで同じことを、`tests/scripts/console_hidden_characters_contract.test.ts`が確かめる。
リンクは`safeGitHubUrl`を通したものだけにする。

### ジョブ、schedule、設定の読み取り

ジョブの画面とシステムの画面が読む3つのscriptは、読み取り専用である。
型と型ガード、取得、クエリのキーと設定は`src/api/jobsQueries.ts`にある。
backendの型との一致は、`tests/scripts/console_jobs_contract.test.ts`が確かめる。
返す項目の絞り方と、ログと結果の伏せ字は、[セキュリティ](../security.md)の「ジョブのログと結果の読み取り」に書く。

| script | 入力 | 戻り |
| --- | --- | --- |
| `console_jobs`の`active` | なし | 実行中、待ち、予定のジョブ。フローのステップは含めず、この順に並べる。画面は予定を除いて出す。キューの1ページ(100件)に達したときは、`truncated`を真にする |
| `console_jobs`の`history` | `status`、`script_path`、`before`、`include_console`、`limit` | 完了したジョブを、新しい順に1ページ(50件まで)。フローのステップは含めない。次のページのカーソルを`next_before`で返す。累積が200件に達したら、カーソルは`null`になる |
| `console_jobs`の`detail` | `job_id`、`include_output` | ジョブ1件。許可した項目、引数、フローのステップの一覧(条件で飛ばしたステップは`skipped`が真)、ログ、結果、結果を読めなかった理由、失敗の保存済みの原因 |
| `console_schedules` | なし | `f/factory/`のscheduleの状態。有効/無効、一時停止の期限、cron、次回の予定、直近5件の実行(新しい順)、リポジトリの定義との差異。全ページを読む(最大10ページ)。ページの上限かキューの1ページに達したときは、`truncated`を真にする |
| `console_config` | なし | `factory_config`の全項目。参照を含む値は、値の代わりに参照の印 |

一覧は、既定でtag`console`のジョブ(Consoleの呼び出し自身)を除く。
Windmillの一覧のAPIが、tagの否定(`!console`)を受けるためである。
Consoleの画面は、`include_console`を送らない。
`status`は、`success`、`failure`、`canceled`を受ける。
時間切れで止められたジョブは、実機で`failure`でなく`canceled`に入ることを確かめた。
`script_path`は、リポジトリの定義から生成した定数(`lib/console_known_paths.ts`)にあるscriptかフローに限る。
外れた値は、取得せずに`filter_rejected`で返す。
定数は`scripts/gen-console-known-paths.ts`で作り直す。
リポジトリの定義との一致は、`tests/scripts/console_known_paths.test.ts`が確かめる。
履歴のカーソルは、`<時刻>|<これまでに返した件数>|<境界の時刻で返したジョブのid>`の形である。
idは、同じ時刻のジョブが続くときだけ複数になり、20件までである。
形の違うカーソルは、先頭のページとして扱う。
履歴のAPIは、`created_before`を含む境界で返すので、前のページの最後のジョブが再び返る。
scriptは、カーソルのidのジョブだけを落とす。同じ時刻の別のジョブは残す。
取る件数は、ページの件数に、落とす分と、次のページがあるかを見る1件を足した数である。
そのため、ページの件数が1件でも、累積は進み、200件に届く。
件数が200に達したら、scriptは取得せずに空の一覧を返す。最後のページは、残りの件数に絞って取る。
200件は、画面が読み進める上限である。
カーソルを偽造すれば数え直せるので、悪意のある呼び出しには効かない。
1回の要求は50件までに限る。
この契約は、`tests/scripts/console_jobs.test.ts`が、境界のジョブを再び返す偽のAPIで確かめる。

詳細は、ジョブの取得、パスと種類の確認、ログと結果の取得の順に呼ぶ。
確認を通らないジョブは`{ found: false }`で返す。
存在しないid、UUIDの形でないid、`f/factory/`の外のジョブ、プレビューなど許可していない種類のジョブが当たる。
フローのルートのログは短く、ステップの出力は子のジョブにある。
そのため、ステップの一覧に子のジョブのidを添え、画面は子の詳細へ移る。
詳細の親のジョブは、`f/factory/`の許可した種類のジョブと確かめられたものだけを返す。
親を持つジョブと、フローのステップは、ルートまでの親(8段まで)がすべて許可した種類のときだけ返す。
確認に使う印は、ステップの印ではなく、親の有無である。
一覧は、親のidを返さない。
プレビューのフローは、ステップの種類がscriptでパスが`f/factory/`になるので、親をたどって見分ける。
次のときも、存在しないジョブと同じ応答にする。ステップの親が存在しない、許可した種類でない、8段より深い、親が無いのいずれかである。
親の取得の失敗は、404以外なら投げ直す。
結果の取得が404のときは結果なしとし、ほかの失敗は読めなかった理由(`result_error`)で返す。ログと失敗の原因は、結果の失敗に関わらず返す。
読めなかった理由は、伏せた後の先頭の300字までである。
失敗したジョブと取り消したジョブには、失敗の検知が保存した原因(`job_failures`)も添える。
保存済みの原因は伏せてあるが、返すときにもう一度伏せ、伏せた後の先頭の2000字までを返す。
表の`error`列は、実機の44行で最長が661字だった。
読めなかったときは、原因の欄だけが失敗を示し、詳細の全体は返る。

`include_output`を偽にすると、ログと結果とDBの読み取りを省く。
実行中のジョブの状態の取り直しに使い、ログを取り直さないためである。
一覧は、開いたときと更新の操作のときだけ取り、自動では取り直さない。
詳細は、ログと結果を含む取得を1回だけ行う。
実行中か待ちのジョブの状態だけを、タブが見えている間、15秒ごとに取り直す。

### 取得の負荷

Console用のworkerの枠は1つなので、読み取りの重さは承認などの呼び出しの待ちに表れる。
実機(ローカルのWindmill)で測った値は次のとおりである。

| 項目 | 値 |
| --- | --- |
| 履歴の最大の実ログ | 8KB(直近の8000件のジョブ。`self_update`) |
| その取得と伏せ字 | 取得が約3ミリ秒、伏せ字が約2ミリ秒 |
| 256KBに切る入力(600KBの合成ログ)の伏せ字 | 約15ミリ秒 |
| 敵対的な入力(1KBの行を並べた256KB、512KB、1MB)の伏せ字 | 最大で約14、27、27ミリ秒(ローカルのbunで、JWTの先頭を繰り返す入力)。入力を倍にしても、所要時間は倍に近い。テストは、3秒未満と、256KBから512KBで3倍未満を固定する |
| 改行の無い1行の長い入力(`eyJ-`の繰り返し)の伏せ字 | 256KBで約63ミリ秒、512KBで約130ミリ秒(JSON行に包んだ512KBは、上限で切るので1ミリ秒未満)。テストは1秒未満を固定する |
| 3000件の配列を持つ結果の伏せ字 | 約13ミリ秒 |
| 約100KBの葉3000枚を持つ結果の伏せ字 | 約18ミリ秒(葉の合計が上限の2倍を超えたら捨てる) |
| Console用workerの常駐メモリ | 60MB(上限は1024M) |
| 新しいscriptを流している間の`summary`と`console_holds`の待ち | 単独より約140〜180ミリ秒長い(最大で約265ミリ秒) |
| 今のステップの取得(`console_jobs`の`detail`、`include_output`は偽)1件の実行 | 中央値31ミリ秒、最大46ミリ秒(5組の10回) |
| 詳細を読んでいる間の`summary`の待ち | 単独で中央値77ミリ秒(67〜94)。詳細2件と重ねて、中央値74ミリ秒(35〜94)で、増分は見えない |
| 詳細を読んでいる間の`console_holds`の待ち | 単独で中央値52ミリ秒(43〜58)。詳細2件と重ねて、中央値68ミリ秒(34〜78)で、増分は約16ミリ秒 |

待ちの増分は、デプロイ前のscriptをプレビューした値である。毎回のコンパイルを含む。
デプロイ後は、これより短い。
詳細の取得は、配備済みのscriptを`wmill script run`で実行し、Windmillが記録した作成、開始、完了の時刻から求めた。
コマンドの起動に揺れがあり、重なりの度合いは制御していない。
今のステップの取得は、詳細を直列に読むので、ほかの呼び出しが待つのは、最大で詳細1件の実行時間である。
`approval_decide`は書き込むので、測っていない。`summary`と同じworkerの枠を使うので、待ちの型は同じと考える。
いずれも、設計の上限の1秒を下回る。

実ログのAPIは、末尾だけを取る形を持たない。
scriptは全文を受け取ってから、末尾を切って伏せる。
このため、取得の大きさはログの全文で決まる。
実ログの最大が小さい間は問題にならない。
大きなログを持つジョブが増えたら、取得と伏せ字の時間を測り直す。

### workerの生死の取得

workerの一覧(`WorkerService`)は、ワークスペースの管理者のジョブトークンで呼ぶと403になる。
そのため、Consoleは、workerの生死とグループを読まない。
停止は、既存の通知で知る。
Console用workerの停止は`console_worker_missing`、defaultのworkerの停止は`default_worker_watch`、負荷は`worker_load`が知らせる。

## ログイン切れの扱い

取得か書き込みが401を返すと、画面の上部にバナーを出す。
一覧の側は、同じ内容の警告を重ねない。
すぐにはログインの画面へ移さない。入力の途中の内容を失わないためである。
操作者が「ログイン」を押すと、Windmillのログイン画面`/user/login`へ移る。

戻り先は、引数`rd`に`pathname + search + hash`を入れて渡す。
`rd`は`URLSearchParams`で組み立てる。
現在のパスが`/console/`で始まらないとき、または`//`、`..`、`\`を含むときは、`/console/`に戻す。
別のオリジンや別のパスへ飛ばされないようにするためである。

その後の取得が成功すると、バナーは消える。書き込みの成功では消えない。
401以外の失敗では消えない。通信が戻ったとは限らないためである。

## 画面の外枠

左のサイドバーに、印と名前、5つの入口、下部の情報を置く。件数のバッジは要対応の入口だけに付く。
選んだ入口は、左端の藍の帯と面の色で示す。
入口の件数のバッジは、その入口の一覧に出る項目の件数にする。
要対応のバッジは、承認と、再実行できる失敗と、通知の件数である。
失敗は、再実行できるもの(監査を除く)だけを数える。監査の失敗は再実行できず、次の定期の監査が扱うまで残るので、数えると0に戻らない。
通知は、重要度が要対応の未解決のものを数える。重要度が情報の通知は、一覧に出さないので数えない。
一覧の件数と食い違う数字を、最初に見る場所へ出さないためである。

画面の上部には、版の更新、ログイン切れ、Windmillに届かないときの帯を出す。
画面の遷移の扱いは[画面の遷移](#画面の遷移)にある。

下部には、配信している版と取り込みの最後の確認、テーマの切り替え、たたむ操作を置く。
版の情報は`/console/status.json`から読む。取れなければ出さない。
状態が固定中か失敗のときは、その旨の注意を添える。
テーマはライト、ダーク、OSに合わせるの3つをアイコンで切り替える。
たたんだサイドバーでは、入口のアイコンに件数の数字を重ねて出す。

幅が狭いとき(md未満)は、サイドバーを出さず、画面の上にメニューのボタンと名前のバーを置く。
ボタンを押すと、左からドロワーが開く。
要対応の件数があるときは、ボタンに点を付け、ボタンの名前に件数を含める。
ドロワーは、サイドバーと同じ入口と下部の情報を持つが、たたむ操作は持たない。
ドロワーは、次の操作のどれかで閉じる。

- 入口を選ぶ。
- 閉じるボタンを押す。
- 背景を押す。
- Escを押す。
- 画面をmd以上に広げる。

各画面の見出しは、題と短い副題を左に、最終更新の時刻と更新のアイコンのボタンを右に置く。
更新のボタンと最終更新は、画面に1組だけ置く。
画面の主要な操作のボタンは、`PageHeader`の`actions`に渡し、見出しの右端の、更新のボタンの右に置く。
`refresh`が無い画面でも、`actions`だけで右側に置ける。
題の下の`children`には渡さない。
`children`は題の列の中に描かれ、主要な操作を右端にそろえられなくなるためである。
狭い幅では右側が折り返し、更新の組と主要な操作が別の行に分かれる。
どちらの行も右寄せなので、主要な操作は見出しの右端に残る。
更新のボタンは、見出しに渡した取得を取り直す。
要対応の画面は、一覧の取得(`summary`)だけを取り直す。
詳細ペインの取得(提案、要件定義、取り込み時点のIssue、通知)は含まない。
そのため、要対応の画面の更新のボタンの名前は「一覧を更新」にし、ほかの画面は「この画面を更新」にする。
複数の取得を持つ画面の最終更新は、取得できた中で最も古い時刻にする。
新しい取得の時刻を出すと、古いままの節が新しく見えるためである。
見出しに渡した取得のすべてが自動で取り直されるときだけ、最終更新の脇に「（2分ごとに自動更新）」の形で全角の括弧に入れて示す。
一部の取得だけが自動で取り直される画面は、注記を出さない。
システムの画面は、`summary`と保留と凍結の取得だけが自動で取り直され、反映の状態と更新履歴は取り直さないので、注記を出さない。
取得が失敗している間も、自動の取り直しは続く。
そのため注記は消さず、「（2分ごとに自動で再試行）」に言い換える。
401は失敗に数えないので、401だけのときは通常の注記を出す。
画面全体の更新の失敗は、最終更新の脇の「更新に失敗しました」が示す。
本体は、同じ失敗を別の語で言い換えない。

節には更新のボタンと最終更新を置かない。
節ごとの「もう一度取得する」は、その節だけが独立して失敗したときの再取得に限る。
前回の値を出している節で取り直しが失敗したときは、値が空であっても、値を出したまま、古い値であることと「もう一度取得する」を節に添える。
この知らせは`StaleDataNotice`が出す。
401は上のバナーが知らせるので、知らせは出さない。
取得中は「もう一度取得する」を押せなくする。
押すと進行中の取得を打ち切るためである。

### パンくず

一覧から開く画面は、見出しの題の下に`Breadcrumb`を置く(`src/components/Breadcrumb.tsx`)。
対象は、作業項目の詳細、要件定義書、監査レポート、ジョブの詳細である。
戻り先をリンクで並べ、最後の1つを今の画面として文字で出す。
最後の1つは、戻り先の経路を持っていてもリンクにしない。今の画面へのリンクは何も起こさないためである。

| 画面 | 並び |
| --- | --- |
| 作業項目の詳細 | 作業項目 › 作業項目の番号 |
| 要件定義書 | 作業項目 › 要件定義 › 作業項目の番号の要件定義 |
| 監査レポート | レポート › 作業項目の番号の監査レポート |
| ジョブの詳細 | ジョブ › ジョブの詳細 |

要件定義書の「要件定義」は、作業項目の画面の要件定義のタブ(`/console/items?tab=requirements`)へ戻る。
一覧から要件定義書を開いたときに、一覧のタブへ戻れるようにするためである。
番号が正しくない画面でも、戻り先は同じ並びで出す。
並びは`src/lib/breadcrumbs.ts`の純関数が決める。

作業項目の詳細の「作業項目」は、一覧の行から開いたときに、その一覧の範囲(`/console/items?scope=...`)へ戻る。
行のリンクが、戻り先を履歴の`state`に持たせる。
戻り先は、`/items`か、`/items?`に安全な文字だけが続く内部のパスだけを受け入れ、それ以外は既定の`/console/items`に落とす。履歴の`state`は外から書き換えられうるためである。
履歴の`state`は再読み込みで失われることがある。そのときも既定の`/console/items`へ戻り、範囲は進行中になる。

ジョブの詳細の「ジョブ」は、一覧の行から開いたときに、その一覧のタブと絞り込み(`/console/jobs?tab=history&status=failure`など)へ戻る。
受け入れる戻り先と、`state`が無いときの扱いは、作業項目の詳細と同じである。
受け入れるのは`/jobs`か、`/jobs?`に安全な文字だけが続く内部のパスで、既定は`/console/jobs`である。
親のジョブやステップのジョブへ移るときも、戻り先を引き継ぐ。

## 画面の遷移

画面の遷移は、`pathname`が変わったときだけ扱う。
`search`だけの変更(タブ、選択、絞り込み)と、最初の表示では扱わない。
画面の中の操作と、ブラウザが決めた位置を妨げないためである。
判定は純関数`shouldMoveFocus`が行う。

遷移のたびに、外枠(`AppShell`)が次の3つを行う。

- タブの題を「<画面名> - Factory Console」にする。
- `main`の名前を付ける。見出し(`PageHeader`のh1)があれば見出しから取り、無い画面では画面名(`aria-label`)を使う。
- フォーカスを、見出しへ移す。見出しが無い画面では`main`へ移す。

`main`の名前は`aria-labelledby`で見出しを指し、`aria-label`に画面名を添える。
参照先の見出しが無いと、`aria-labelledby`は使われず、`aria-label`が名前になる。
画面名を別の名前として重ねると、「メイン、作業項目」と「見出し1、作業項目」のように、同じ内容が二度読まれるためである。

画面名は、画面の表(`screens.ts`)が経路の`handle`に載せる。
下の経路が名前を持たないときは、入口の名前を使う。
作業項目の番号を含む名前(「作業項目 #12」「作業項目 #12の要件定義」「作業項目 #12の監査レポート」)は、経路の引数から決める。
取得を待たないので、題は取得の前から変わらない。
番号が読めないときは、番号の無い画面名にする。

メニューのドロワーが開いているときは、閉じ終わってからフォーカスを移す。
`<dialog>`を閉じると、ブラウザが開く前の要素へフォーカスを戻し、先に移すと奪われるためである。
ドロワーは`data-nav-drawer`で見分ける。
フォーカスを移すとき、スクロールはさせない。
`main`は`overflow-clip`で、フォーカスによるスクロールで外側が動くと、見出しの帯が外れるためである。
見出しには、キーボードで移ったときだけ細い輪を描く(`focus-visible`)。
マウスの操作の後には描かない。
キーボードの利用者が、移った先を見失わないためである。
`main`には輪を描かない。領域全体を囲む輪は、画面の中の操作の輪と紛れる。

要対応の画面が自分で行うフォーカスの移動(一覧と詳細の切り替え)は、`search`の変更で起きる。
そのため、遷移のフォーカスの移動と重ならない。

ページの先頭に「本文へスキップ」のリンクを置く。
フォーカスが当たったときだけ見える。
押すと`main`へフォーカスを移し、アドレスに`#`を足さない。

## Windmillに届かないとき

Windmillを呼ぶ`runScript`が、Windmillに届かなかった失敗で終わると、画面の上部に帯を出す。
次に応答を得ると、帯を消す。
帯の元は、`runScript`の結果だけである(`connectionState.ts`)。
`runScript`が終わるたびに、結果を報告先(`setConnectionReporter`)へ渡す。
読み取りと書き込みは、どちらも`runScript`を通る。
中断(abort)は報告しない。
`status.json`のように`runScript`を通らない取得は、帯に影響しない。
`status.json`の取得は、失敗しても`null`を返して終わるので、成功と区別できず、Windmillに届かない間も成功になるためである。

届かなかった失敗は、ネットワークの失敗と、転送が返す502と503である。
ConsoleのAPIはCaddyがWindmillへ転送するので、Windmillだけが止まると、Caddyが502か503を返す。
504は届かなかった失敗に含めない。
転送先の待ちの上限でも、Windmillの待ちの上限でも出て、見分けられないためである。
401、4xx、500、ジョブの失敗、待ちの上限は、Windmillが答えたものなので、届いているとして帯を消す。

ブラウザの接続状態(`navigator.onLine`とTanStack Queryの`onlineManager`)は見ない。
ConsoleはWindmillを同じ端末(127.0.0.1)で配信するので、他のネットワークが切れていても、Windmillには届く。
ブラウザの接続状態で取得を止めると、Wi-Fiを切った端末で、届く取得まで止まってしまう。
そのため、取得は`networkMode`を`always`にし、ブラウザの接続状態で止めない。
書き込みは、もとから`always`である。

帯が出ている状態から消える状態に変わったとき、失敗した取得(状態がエラーの取得)だけを読み直す(`watchConnectionRecovery`)。
帯が消えた後も、節が失敗の表示のまま残らないようにするためである。
成功した取得は、既定の`staleTime`と、ウィンドウに戻ったときの取り直し(`refetchOnWindowFocus`)に任せる。
取得の失敗は、通信の失敗として2回まで再試行する。

## ちらつきの抑え方

### 画面の切り替え

画面を替えると、新しい画面の取得が終わるまで、節が空になる。
これを、データの保持、先読み、スケルトンの遅延表示の3つで抑える。

取得したデータは、使われなくなってから5分(`gcTime`の既定)保持する。
5分以内に戻ると、保持中のデータを即座に出し、古ければ裏で取り直す。
`gcTime`を延ばしても、古いデータを出す危険が増えるだけなので、変えない。

サイドバーの入口を押すと、その画面の初回の取得を`prefetchQuery`で先読みする。
押した直後に走らせ、押してから離すまでの時間を、取得に使う。

- 先読みは、pointerdownだけで走らせる。
- 主ボタンで修飾キーが無い押下に限る。
  中クリックとCtrl+クリックは、この画面に移らず、新しいタブで開く操作だからである。
- タッチの押下では先読みしない。
  スクロールの始まりでも起きて、移る操作かが分からないためである。
  タッチでも、移った後の取得は画面が自分で行う。
- focusとhoverでは先読みしない。矢印やTabで入口をたどるだけで、Windmillのジョブが溜まるためである。

同じ入口は、先読みが走ってから5秒の間、次の依頼を受けない。
連続した押下で、同じ取得を続けて呼ばないためである。
押下の判定は、純関数`isPrimaryPress`にある。
先読みは、画面の取得と同じ設定(キー、関数、`staleTime`)を使う。
設定は取得ごとの`...QueryOptions`関数にあり、画面のフックと先読みが同じ関数を呼ぶ。
新しいデータは取り直さず、走っている取得には重ねない。
先読みする取得は、作業項目の入口では進捗の一覧と要件定義の一覧、ジョブの入口では実行中と待ちの一覧、システムの入口では状態、更新履歴、保留と凍結である。
`summary`は、サイドバーが常に持つので先読みしない。
要対応とレポートは、先読みの対象に含めない。
workerは1台で直列に処理するので、入口1つの先読みは、その画面の取得数(システムは3つ、ジョブは1つ)に限る。
ジョブの履歴とスケジュール、システムの設定は、タブを開くまで取得しないので、先読みしない。

システムの状態は、画面を開くときの取り直しを`staleTime`(30秒)に任せる。
通知の解決は、一覧、未解決の通知、システムの状態を読み直す(`NOTICE_RESOLVE_INVALIDATES`)。
保留と凍結の解除も、システムの状態を読み直す。
システムの状態を変える書き込みはこの2つで、どちらも読み直すので、開くたびの取り直しは要らない。
開くたびに取り直すと、先読みの直後に取り直して、先読みが無駄になる。
システムの状態は、Factory側の変化(新しい通知や反映)を、`staleTime`の間は画面に反映しない。
更新のボタンで取り直せる。

節のスケルトンは、取得が300ms続くときだけ出し、出したら200ms以上残す(`useDelayedVisible`)。
ただし、承認が載る2つの面は、出す前の300msの待ちだけを持ち、出した後に残す時間を持たない。
画面の切り替えの取得は約200msで終わる。
終わる時刻の付近で出し入れすると、かえってちらつくためである。
出すまでの間は、見出しと、節と同じ高さの空の領域を出す。
スケルトンが出るときも、内容に置き換わるときも、下の要素は動かない。
「読み込み中」の通知(`role="status"`)も、スケルトンと同じ時点で出す。
状態の遷移は純関数`reduceDelayed`で、時刻を引数に受ける。
タイマーの結びつきは`scheduleDelayedWake`にあり、時刻とタイマーを引数に受ける。
共通部品`LoadingGate`と`useLoadingDisplay`が、空の領域、スケルトン、内容を出し分ける。

この遅延表示は、取得を待つ画面と節のすべてに使う。
要対応、作業項目の詳細、要件定義書、監査レポート、レポートの各区画、システム、作業項目の一覧、承認と通知の各ペインである。
最初の画面を読み込む`RouteFallback`だけは対象外にする。
最初の読み込みには、見出しも節の枠も無く、空の領域を出す先が無いためである。
画面が早期に別の表示へ切り替える場合は、フックを画面の先頭で呼び、値が揃った後もスケルトンを残す時間の間は、読み込み中の表示を続ける。

スケルトンの高さは、内容に置き換わるときのずれを減らすため、内容の目安にそろえる。
対象は、システムの各節、進捗、要件定義と、画面ごとの読み込み中の形である。
値は各節の定数にある。
システムの各節は、実機で測った本文の高さにそろえ、一覧はよくある件数の高さにする。進捗と要件定義は、行の余白と文字の高さから見積もった。
節の内容の形を変えたら、実機で高さを測り直して合わせる。

## ページ送り

長い一覧は、取得済みの配列を画面の中でページに区切って出す。
取得とbackendの上限は変えない。
ページ送りは、上限まで取った行の表示を分けるだけである。
区切る規則は`src/lib/pagination.ts`の純関数、ページの状態とスクロールは`src/lib/usePagination.ts`にある。
スクロールの目標位置は`src/lib/scrollTarget.ts`の純関数が求める。
スクロールする枠は、`src/lib/scrollRoot.ts`の`findScrollRoot`が、一覧を包む要素から親をたどって探す。
枠は、枠の目印を付けた要素か、縦にスクロールするoverflowを持つ最も近い祖先である。
枠が見つからないときは、何も動かさない。
操作は`src/components/Pagination.tsx`にある。

| 一覧 | 1ページの件数 |
| --- | --- |
| 作業項目の進捗 | 25 |
| 要件定義の一覧 | 10 |
| 更新履歴 | 10 |
| 情報の通知 | 10 |
| 解決済みの通知 | 10 |
| 監査の失敗 | 10 |
| 作業項目に紐づかない失敗 | 10 |

操作と表示の規則は次のとおりである。

- 項目が1ページに収まる一覧には、ページ送りを描かない。
- 一覧の下に「前へ」「次へ」、「n / mページ」、表示している範囲を並べる。
  範囲は「26–50件目 / 130件」の形で、変わったときは読み上げを遮らずに知らせる。
- ページ送りは、スクロール枠の下端に貼り付く。
  1ページが画面より長くても、一覧の先頭から「次へ」を押せるようにするためである。
  背景と上の境界線を持ち、下をくぐる一覧と重ならない。
  貼り付く範囲は親の要素の中なので、親は一覧とページ送りだけを含み、`overflow`を持たない包みにする。
  帯は、枠が下に持つ余白の分だけ下げて置く。
  余白の上で止めると、帯の下に次の項目が見えるためである。
  帯と枠のclassは互いの値に依存する。
  そのため`src/lib/layoutClasses.ts`で対にして置き、テストで対応を確かめる。
- 枠には、帯の高さを超える`scroll-padding-bottom`を付ける。
  貼り付いた帯が、キーボードで移したフォーカスを覆わないためである。
  帯の高さと余白の値は、`src/lib/layoutClasses.ts`のコメントにある。
- 帯の中のボタンには、枠の`scroll-padding-bottom`を打ち消す負の`scroll-margin-bottom`を付ける。
  帯は枠の下端から`scroll-padding-bottom`の内側にある。
  打ち消さないと、ボタンへのフォーカスのたびに枠が動くためである。
  負の`scroll-margin`の挙動は、Chromeでだけ確かめている。
  ほかのブラウザでは、ボタンにフォーカスすると枠は動き得る。
- 枠は`position:relative`にする。
  枠の中の`position:absolute`の要素(読み上げ専用の文字)は、枠と一緒にスクロールして、本来の位置に置かれる。
  基準が枠の外にあると、要素が枠の外に置かれ、外側が余分な高さを持つ。
  その要素へフォーカスや検索で移ると、外側がスクロールして見出しの帯が外れる。
- `SCROLL_BODY_CLASS`を使わない画面の枠は、`position:relative`を持たない。
  枠の中の読み上げ専用の文字は、基準が`main`になり、枠と一緒にスクロールしない。
  `main`は`overflow-clip`でスクロールしないので、windowも`main`も動かない。
- 全画面に共通の`main`は、`position:relative`と`overflow-clip`にする。
  `relative`は、枠の外へ出た`position:absolute`の要素の基準を`main`にし、windowが伸びないようにする。
  `overflow-clip`は、`main`をスクロール枠にしない。
  `overflow-hidden`だと、プログラムからのスクロールで`main`が動き、操作では戻せない。
  `overflow-clip`はスクロール枠ではないので、縦に並べる幅では中身の高さが最小の高さになる。
  そのため`min-h-0`を付けて、本文の枠を画面の高さに収める。
- 範囲の注記に「全」を使わない。
  進捗の「N件(全M件)」は絞り込み前の件数を指すので、同じ語を別の件数に使うと食い違うためである。
- 端のボタンは`aria-disabled`で使えないことを示し、押しても何もしない。
  `disabled`は使わない。
  押した直後にフォーカスが失われ、キーボードの操作が途切れるためである。
- 「前へ」「次へ」でページを移すと、一覧の先頭が枠の上端に来るまで、画面の本文を包む枠だけをスクロールする。
  windowは動かさない。
  動かすと、上の見出しの帯が外れて下に空白が出るためである。
  枠の上端に貼り付く部分(システムの帯とタブ)があるときは、その高さと16pxの余白の下に合わせる。
  作業項目の進捗は、絞り込み欄と件数も見えるように、それらを含む位置に合わせる。
- 絞り込みや並び替えで先頭へ戻るときは、スクロールしない。入力の途中で位置が動かないようにするためである。
- 絞り込みや並び替えを変えると、先頭のページへ戻る。再読み込みで選んだ条件が消えて絞り込みが戻ったときも、先頭へ戻る。
- 再読み込みで件数が減り、今のページが範囲の外に出たときは、最後のページを出し、持っているページも最後に揃える。
  揃えないと、件数が戻ったときに、操作なしで元のページへ跳ぶ。
- ページの番号はURLに持たない。画面を開き直すと先頭に戻る。

## タブ

作業項目、レポート、ジョブ、システムの画面は、本体をタブで分ける。
共通の仕組みを、この節にまとめる。

開くタブはURLの`?tab=`に持つ。既定のタブは名前を持たず、名前が無いか知らない名前なら既定のタブを開く。
作業項目の詳細の`?tab=`と名前をそろえてある。
他のクエリは残す。
タブを選び直しても、履歴は積まず、現在の履歴を置き換える。タブの切り替えで戻る操作を増やさないためである。

| 画面 | タブ | 既定 |
| --- | --- | --- |
| 作業項目 | 進捗、要件定義(`?tab=requirements`) | 進捗 |
| レポート | 監査レポート、分析(`?tab=analytics`) | 監査レポート |
| ジョブ | 実行中と待ち、履歴(`?tab=history`)、スケジュール(`?tab=schedules`) | 実行中と待ち |
| システム | 状態、失敗と通知(`?tab=failures`)、履歴と構成(`?tab=history`)、設定(`?tab=config`) | 状態 |

共通の`Tabs`(`src/components/Tabs.tsx`)が描き、矢印キーとHome、Endで移る。Alt、Ctrl、Metaを押している間は移らない。
タブの名前に添えた件数も、本体の見出しや副題に繰り返さない(作業項目の要件定義、レポートの監査レポート)。
件数が重なると、読み手は同じ数字を2か所で確かめることになるためである。
タブの名前と重なる見出しは、本体に置かない。ただし、節が見出しを名前の元(`aria-labelledby`)にし、読み上げの見出しの階層も保つ本体は、見出しを視覚的にだけ隠して残す(レポートの本体)。
タブの名前には、件数を添えられる。件数の意味は、読み上げにだけ数字の前に添える。見える数字は件数だけである。
帯は横にだけスクロールし、縦にはスクロールしない。
選んでいるタブの下線を罫線に重ねるため、帯の外側に罫線を引き、帯ごと1px下げる。
タブに1pxの負の余白を付けると、はみ出した1pxで帯が縦に動く。

選んでいないタブの本体は、描いたまま隠す。
絞り込み、並び替え、ページ、入力、分析の期間を、タブを往復しても保つためである。
隠した本体は`hidden`で読み上げからも外れ、タブの`aria-controls`は、それぞれの本体を指す。
本体は共通の`TabPanel`(`src/components/TabPanel.tsx`)が描く。
システムとジョブの画面は、初めて開くまで本体の中身を描かない(`useVisitedTabs`)。開いた後は、ほかの画面と同じく隠して残す。
本体の枠は常に描くので、タブの`aria-controls`は、中身が無い間も有効である。

開閉できる部分は、共通の`Disclosure`(`src/components/Disclosure.tsx`)が描く。
`<details>`と`<summary>`なので、キーボードの操作と開閉の読み上げは要素が持つ。
見出し行には、開閉を示す矢印を添え、フォーカスの輪を描く。
開閉の状態は、URLと履歴のどちらにも残さない。

本体は1つのスクロール枠を共有する。
そのため、タブごとにスクロール位置を覚え、移った先の位置へ戻す。まだ離れたことのないタブは先頭から始める。
記憶は画面を開いている間だけ持つ。

取得は画面が持ち、タブの切り替えでは取得しない。
ただし、ジョブの画面と、システムの画面の設定のタブは、タブを初めて開くまで取得を始めない。
Console用workerの枠が1つで、開いていないタブの取得を載せないためである。
選んでいない側の取得が失敗したときは、タブの名前に「取得に失敗」の文言と記号を添える。色だけに頼らないためである。
選んでいるタブは、本体が失敗を伝えるので印を付けない。ログイン切れ(401)は上のバナーが知らせるので、印にしない。
段の印(システムの「注意」「要対応」)があるタブは、選んでいるかにかかわらず、取得の失敗の印を並べる。「注意・取得に失敗」のように書く。値が前の取得のものだと、読み手に伝えるためである。
段の印は、注意が三角、要対応が八角で、色だけに頼らない。

タブの組、本体の`id`と`hidden`、失敗の印、URLの読み書きは、`src/lib/tabSet.ts`の純関数が決める。
画面ごとの定義は`src/lib/itemsTabs.ts`、`src/lib/reportsTabs.ts`、`src/lib/jobsTabs.ts`、`src/lib/systemTabs.ts`にある。
スクロール位置を戻す処理(`src/lib/useTabScroll.ts`)と、`hidden`が画面に効くことは、画面を描いて確かめる。

## 要対応の画面

一覧に出すのは承認、失敗、通知である。
項目は、時刻が新しい順に並べる。
同時刻なら種類の順(承認、失敗、通知)、次にidが大きい順にする。
種類の切り替え(すべて、承認、失敗、通知)は、一覧に2種類以上の項目があるときだけ出す。
切り替えには、項目が1件以上ある種類だけを並べる。
選んだ種類の項目がなくなったら、切り替えの状態も「すべて」に戻す。
承認の下位の種類(要件定義、Issue化提案、改善提案)は、行のラベルで示す。
改善提案は、監査から出たIssue提案である。

`summary`の承認には、承認待ちのほかに、承認済みでIssueをまだ作っていないIssue提案も入る。
承認を記録した後にIssueの作成が失敗した提案を、見えなくしないためである。
その行には「承認済み(Issue作成待ち)」のラベルを付ける。

承認として取るのは、画面が扱える種類(`requirements`と`issue_proposal`)だけである。
`summary`と`inbox`の両方がこの種類で絞る。
除外する書き方では、種類を足すと、画面の未対応の種類の行が届く。
届いた行のために、一覧全体を表示できなくなる。
設計の承認依頼(`design`)は、一覧の行と件数のどちらにも数えない。

選んだ項目は、URLの`?approval=<id>`、`?failure=<id>`、`?notice=<id>`のどれか1つに持つ。
2つ以上あるときは、どれも選んでいないものとして扱う。
値が正の整数でなければ、選んでいないものとして扱う。
選択の変更は履歴を積まない。ただし幅が狭いとき(lg未満)に項目を選ぶ操作は、履歴を積む。
面が一覧から詳細へ切り替わるので、ブラウザやスマートフォンの戻る操作で一覧へ戻れるようにするためである。
積んだ履歴には、一覧から選んだ印を付ける。
広い幅で選び直して履歴を置き換えるときは、置き換わる履歴の印を引き継ぐ。
種類の切り替えが選んだ項目の種類を隠すときは、選択を外す。
一覧と詳細は別々にスクロールする。
幅が狭いとき(lg未満)は、一覧と詳細を1画面ずつ出す。
項目を選んでいなければ一覧、選んでいれば詳細を出す。
詳細の上の「一覧へ戻る」と、種類の切り替えによる選択の解除は、印のある履歴を戻って取り除く。
置き換えると、画面の変わらない履歴が残り、戻る操作を余分に求めるためである。
選択つきのURLを直接開いたときは印が無いので、選択を外して履歴を置き換える。
面が切り替わったら、新しく出た面にフォーカスを移す。
一覧へ戻るときは、離れる前のスクロール位置と、直前に選んでいた行に戻す。
どちらを出すかは`src/lib/inboxPane.ts`が決める。

一覧は`InboxList`、詳細は`InboxDetail`の別の部品が描く。
再実行、解決、承認などの行の操作は、一覧の行ではなく詳細のペインに置く。
一覧の行は1つのbuttonなので、操作のbuttonを入れ子にしないためである。
詳細は、種類ごとの描き分けを`InboxDetail`の1か所に集める。
詳細のペインは左寄せで、本文の幅は760pxまでにする。サイドバーを畳んでも位置が動かない。
一覧の行は、1行目に題名と相対時刻、2行目に種類、副題、期限、状態のバッジを並べる。
一覧の項目がすべて通知、またはすべて失敗のときは、全行に同じ語が付いて情報にならないので、「通知」と「失敗」の語を省く。
この判定は、種類の切り替えで絞り込む前の一覧全体で行い、切り替えても行の書式が変わらないようにする。
承認の語(要件定義、Issue化提案、改善提案、承認依頼)は区別を担うので、承認だけの一覧でも省かない。
通知の副題は、同じ題名の通知を見分けるために、本文の最初の対象(`owner/repo#番号`)、最初の版(先頭7桁)、本文の抜粋を「・」でつないで1行にする。
見分ける相手は、種類の切り替えで絞り込む前の一覧全体にある、同じ種類の通知である。
同じ種類の通知が並ぶときは、全員が同じ値の対象と版だけを省く。
一部だけ同じなら、全員に出す。
全員が同じ値なら見分ける役に立たず、幅が狭い一覧では抜粋の食い違いを押し出すためである。
同じ種類の通知が1件だけのときは、本文にあれば出す。
抜粋は、副題に出した対象と最初の版を除いた本文から36文字を取り、省いた側へ省略記号を付ける。
対象と版は現れた位置で切り出す。
先頭の対象と同じ文字列で始まる別の対象(`o/r#1`を切っても`o/r#12`)や、2番目以降の対象と版は残る。
同じ種類の通知が並ぶときは、本文の先頭が最も長く重なる通知と食い違う位置の直前の語の区切りから抜粋する。
書き出しがそろう通知を見分けるためである。
副題にマウスを重ねると、本文の全体を表示する。
通知の詳細の先頭には、種類と重要度を1つにしたタグ(「要対応の通知」と「情報の通知」)を出す。
通知の本文に含まれる40桁の版は、先頭7桁で示す。全体は、マウスを重ねたときの表示と、複製のボタンで取り出せる。
本文が取得の上限で切れているとき、末尾に接する40桁は、別の値の途中である可能性があるので版にしない。
状態のバッジは2行目の末尾で、狭いときは省略記号で縮める。
2行目の高さは24pxに固定し、バッジの有無によらず、どの行も同じ高さにする。
行の頭に種類の点は付けない。
期限が24時間を切った行(期限を過ぎた行を含む)だけ、期限に警告色の印を付ける。
期限を過ぎた行は、失敗の色にする。
選んだ行は、藍を帯びた面(ライトでは淡く、ダークでは暗い)と左の帯で示す。

同じ種類の未解決の通知が2件以上あるときは、件数つきの1行にまとめる。
まとめる単位は通知の種別だけで、対象や版は見ない。
重要度は種別だけで決まるので、同じグループに要対応と情報の通知は混ざらない。
承認と失敗は、1件ずつ判断して操作するので、まとめない。
解決済みの通知は、対応が済んでいるので、まとめずに1件ずつ出す。
まとめた行は、最初の通知があった位置に置き、時刻には中で最も新しい通知の時刻を出す。
副題には、閉じている間、中の通知の本文が最初に挙げる対象を、重複なしで最大2つ並べ、残りを「ほか対象N件」と数える。
「対象」の語は、通知の件数と紛れないよう添える。
対象を挙げない通知は数えない。別の対象の通知が紛れ込んだことに、開かなくても気づけるようにするためである。

まとめた行を押すと、個々の通知が字下げされて開く。
開閉のbuttonは`aria-expanded`を持ち、矢印キーで通常の行と同じように移れる。
グループは、閉じた状態で始める。ただし、選んだ通知を含むグループは開く。
URLで通知を直接開いたときも、選択が別の通知やグループに移ったときも同じである。
選んだ通知を折りたたみの中に隠さないためである。
開いた後に自分でグループを閉じても、選択は外れず、同じ選択のままでは開き直さない。
閉じたグループが選んだ通知を含むときは、行の背景で示し、読み上げにも「選択中の通知を含む」と添える。
取り直しや種類のチップでの絞り込みで、まとめられなくなった(行から消えた)種別は、開閉の状態から外れる。
チップを切り替えて戻すと、そのグループは閉じた状態に戻る。
URLの選択は個々の通知のidなので、グループの開閉に左右されない。
グループが後から成り立つ(同じ種別の通知が増える)と、行の並びが変わる。
そのとき、押していた行はグループの中に移って消えるので、フォーカスを失うことがある。

サイドバーのバッジと種類の切り替えのチップは、まとめる前の個々の項目の数で数える。
見出しの副題は、何も残っていないときの「すべて片付いています」だけで、種類ごとの件数は出さない。
件数はチップの横が示すので、同じ数字を2か所で確かめさせないためである。
一覧では、まとめた行の件数と、まとめない行(1行で1件)の合計が、通知の数と一致する。
開閉の判定とこの対応は`src/lib/inboxGroups.ts`が決め、テストで固定する。

承認の詳細と行には、期限があれば残り時間を出し、過ぎていれば「期限切れ」と出す。
承認の詳細には、題名、種類、作業項目(要件定義なら試行)、Issueへのリンク、期限、依頼した時刻を出す。
要件定義の承認には、要件定義書(`/console/items/<id>/requirements`)へのリンクを添える。
監査から出た提案には、元の監査レポート(`/console/reports/audit/<id>`)へのリンクを添える。
題名は`displayableIssueText`を通してプレーンテキストで描く。
期限と依頼した時刻は、日本時間の絶対時刻と相対時刻を並べる(例: 10/15 18:48まで(残り6日)、10/09 18:48(1時間前))。
IssueのリンクはGitHubのIssueのURLの形のときだけ張る。

### 失敗と再実行

一覧には、`summary`の失敗の行を、作業項目ごとに1行で出す。
対象は、状態が失敗、人の対応待ち、期限切れの作業項目である。
監査の失敗は、再実行できないので行にしない。件数のカードで知らせる。
同じIssueに新しいサイクルがある古い作業項目は含まない。

詳細のペインには、次を出す。

- 題名、種類、状態
- 作業項目への経路(`/items/<id>`)とリポジトリ
- IssueかPRへのリンク
- 失敗した時刻と、最終更新の時刻。一覧は最終更新の新しい順に並ぶので、並びの根拠を示す
- フローとステップ、ジョブへのリンク
- 失敗の内容と、状態が変わったときの注記

失敗の記録が無い作業項目では、その旨を出し、時刻は状態が変わった時刻で代える。
失敗の記録が、今の状態へ遷移した時刻より5分以上前のものは、前の失敗の記録とみなす。
再実行の起動に失敗して人の対応待ちに戻った作業項目で、前の失敗の内容を今の失敗として見せないためである。
この記録の内容、フロー、ジョブは出さず、「この状態になってからの失敗の記録はありません」と出す。時刻は状態が変わった時刻にする。
失敗の処理は、記録を書いてから状態を更新するので、正常な記録も状態の時刻より数秒前になる。5分は、その差を許す幅である。
失敗の内容と注記は、実行の出力であり、Issueの文字を含みうる。
そのため`displayableIssueText`を通し、プレーンテキストで描く。
`summary`は失敗の文を500文字で切る。500文字に達した文には、先頭だけを表示している旨と、ジョブのログへの案内を添える。
IssueかPRへのリンクは、GitHubのURLの形のときだけ張る。PRのURLは、リポジトリと番号から組み立てて、同じ検査を通す。
ジョブへのリンクは、ジョブIDの形のものだけ張る。

再実行は、詳細のペインのボタンから、確認を経て`retryWorkItem`を呼ぶ。
確認は、ブラウザ標準のdialog要素をモーダルで開く。最初のフォーカスは「取り消す」に置く。
確定すると、フォーカスを詳細のペインの処理中の行へ移す。ボタンが無効になっても、フォーカスが文書の先頭へ落ちないためである。
確認には、再実行する作業項目を特定する情報(題名、リポジトリ、対象のIssueかPR、失敗した時刻)と、状態の遷移(今の状態 → 再開先)を出す。
似た題名や古い表示の作業項目を取り違えないためである。
開いた直後のフォーカスは、明示的に「取り消す」へ置く。確定では取り消しの処理を呼ばない。
確認を開いている間に、その作業項目が一覧から外れたときは、確認を閉じ、その旨をトーストで知らせる。
再開先は、scriptが作業項目の種類で決める。

- PRのレビューは、レビュー中へ戻す
- PRの修正は、修正中へ戻す
- Issueは、要件定義の生成、設計、実装のどれかへ戻す。画面はこの3つを並べて示す。再開先の決まりは[作業項目の状態とリース](work-items.md)の「再実行」に書く
- Issueの再開先が要件定義の生成のときは、GitHubの現在のIssueの題名と本文を取り込み直す。確認の注記で伝える
- 知らない種類は、再開先を決めつけない。ボタンは押せるままにして、断るかどうかはscriptに任せる
- 監査は、scriptが再実行を認めない。ボタンの代わりに理由を出す
- dependabotの更新も、scriptが再実行を認めない。ボタンの代わりに、PRを確かめて手でマージするか閉じるよう案内する

ロックのキーは作業項目ごとである(`retryTargetKey`)。
失敗の行の1つを再実行している間も、ほかの行は押せる。
再実行のボタンは詳細のペインだけにある。ロックは画面全体で共有するので、同じ作業項目は二重に実行できない。

scriptは、次のときに再実行を断る。確認の文で、事前に挙げて伝える。

- 記録されたフローが動いている、または動いているか読めないとき
- 同じIssueに、より新しいサイクルがあるとき
- 要件定義が承認済みで、要件定義の改ざんや差し戻しの停止ではなく、設計が無効か承認済みで、実装が無効のとき
- 確認から更新までの間に、作業項目の状態が変わったとき

断りはジョブの失敗として返り、結果が分からない失敗と区別できない。
そのため、断られたときの知らせにも「処理に失敗した可能性があります」と「一覧を読み直して確かめてください」の案内が入る。括弧の中に、scriptの断りの理由が入る。
断りを区別して返すには、scriptの戻りの契約を変える必要がある。この課題はConsoleの外で扱う。

成功と、結果が分からない失敗の後は、`summary`を読み直す。
結果は、どの作業項目のものかを添えて、トーストで伝える。
トーンは次のとおりである。

- 成功は、成功として伝える
- 別の実行が先に作業項目を押さえていたときと、結果が分からない失敗は、警告にする
- ジョブが動く前に断られた失敗は、エラーにする

読み直せなかったときは、一覧が更新されるまで、その作業項目を押せないままにする。

### 取り込み時点のIssue

要件定義の承認の詳細には、取り込み時点のIssueの題名と本文を出す。
実装のClaudeが受け取るのはこの内容で、GitHub上の現在のIssueではない。
承認者が現在のIssueだけを読んで承認すると、取り込み後に書き換えられた内容を見落とすためである。

内容は選んだ承認の作業項目ごとに、`console_query`の`intake_snapshot`で取る。
`summary`には載せない。本文が長く、120秒ごとの取得に含めると応答が膨らむためである。
却下や再実行による作り直しは、同じ作業項目の取り込み内容を書き換える。
そのため、承認依頼ごとに別のキャッシュにし、画面を開くたびに取り直す。更新前の内容を新しい承認の画面に出さないためである。

題名と本文は起票者が書いた信頼できない入力である。次のように扱う。

- MarkdownやHTMLとして解釈せず、文字列としてReactが描く。タグやリンクは文字のまま見える。
- 本文は20,000文字、題名は300文字で`console_query`が切る。切ったときは、先頭だけを表示している旨を出す。
- 切った後ろの部分は、承認者がConsoleでも、HTMLのコメントや不可視の文字を描かないGitHubの画面でも確かめられない。後ろの部分にあるHTMLのコメントの開始(`<!--`)と不可視の文字の数を`console_query`が数え、あれば警告する。
- 取り込み内容を更新したことがあれば(`refreshed`。更新の履歴から導く)、目立つ警告を出す。
- 見えない文字と、並びの見た目を入れ替える文字は、代替文字(U+FFFD)に置き換え、置き換えたことを警告で示す(`src/lib/intakeText.ts`)。対象は、Unicodeの分類がCf(双方向の制御文字、ゼロ幅の文字、tag文字を含む)、Cc(改行とタブを除く)、Zl、Zpの文字と、異体字セレクタである。
- 題名と本文の要素は、`dir="ltr"`と`unicode-bidi: isolate`で、周りの文字の並びに影響しないようにする。

### 承認バー

承認と却下の操作は、詳細のペインの承認バー(`ApprovalBar`)に置く。
要件定義では、取り込み時点のIssueのパネルと、承認する試行の要件定義書を並べ、その直下に置く。
Issue提案では、提案の本文の直下に置く。
承認者が見た内容の隣で押せるようにするためである。

詳細に出す操作は、依頼の状態で決まる(`decisionSurface`)。

| 依頼の状態 | 出すもの |
| --- | --- |
| 承認待ちで期限内 | 承認と却下 |
| 承認待ちで期限切れ | 操作を出さず、その旨の文を出す |
| 承認済みでIssueを未作成のIssue提案 | 「Issueの作成をやり直す」だけを出す |
| その他の承認済み | 操作を出さず、「起票を待っています」などの文を出す |
| 却下済みなど | 何も出さない |

知らない種類の承認は、操作を出さない。

| 操作 | 決まり |
| --- | --- |
| 承認 | 確認ダイアログを経る。承認は取り消せず、要件定義ではClaudeの実装が始まるためである。ダイアログには件名、承認依頼のid、起こることを出し、開いたら取り消しにフォーカスを置く。ダイアログは新しい依存を足さず、ブラウザ標準の`<dialog>`で作る(`components/ConfirmDialog.tsx`)。再実行の確認も同じ部品を使う |
| 却下 | 理由が必須で、空白だけでは押せない。理由は4000文字まで(`MAX_REASON_LENGTH`)で、入力欄の横に「文字数 / 上限」を出す。要件定義の却下だけ、確認ダイアログを経る。却下は要件定義の作り直しになり、その時点の現在のIssueで取り込み内容が更新されるためである |
| 補足 | 承認の記録には、Consoleから決めたことを示す固定の文を添える。画面から補足は入力しない |

確認ダイアログで「承認する」を押した時点で、期限と、承認を止める理由をもう一度確かめる。
満たさなければ送らず、ダイアログを閉じて理由を出す。ダイアログを開いている間に期限を過ぎることがあるためである。

### 承認と却下の呼び出し

承認と却下は`decideApproval`で呼び、`useWriteMutation`のロックと読み直しに載せる。
ロックのキーは依頼のidで、承認と却下は同じキーで止まる。二重に押しても、呼び出しは1回になる。
成功したら`summary`を読み直し、処理した依頼が一覧から消える。
ただしIssue提案は、承認の後にIssueを作り終えるまで、承認済みの状態で一覧に残る。
結果は`sonner`のトーストで知らせる。結果が分からない失敗の文は`describeWriteFailure`が作る。
読み直せなかったときは、一覧が更新されるまで、その依頼のボタンを押せないままにする。

送る`options`の形は、依頼の種類で決め、他のキーは送らない。
Issue提案は`{ with_factory_label: boolean }`、それ以外は`{}`である。
作るIssueにfactoryラベルを付けるかは、チェックボックスで選ぶ。
監査から出た提案は初期値をオンにし、PRのレビューから出た提案はオフにする。
ラベルを付けられない監査の提案(`factory_label_available`が偽)は、選択肢を出さず、`false`を送る。

### Issue作成のやり直し

承認を記録した後でIssueの作成が止まった提案は、承認済みのまま残る。
「Issueの作成をやり直す」は、同じ承認を`decideApproval`でもう一度送る。
サーバーは、同じ決定が記録済みなら、記録せずに起票だけをやり直し、記録済みのラベルの選択を使う。
そのため、ラベルの選択肢は出さない。押しても結果が変わらないためである。
作成済みのIssueは、マーカーで見つけて再利用する。
確認ダイアログに、この2点を書く。

承認の直後は、起票の処理が走っている間でも押せてしまう。
決定の時刻は`summary`と`inbox`のどちらにも無いので、押せる条件に経過時間を入れられない。
代わりに、次の2層で重なりを防ぐ。

- 画面: やり直しに成功したら、このタブでは15分間、同じ依頼のボタンを止めて「起票に数分かかります」と出す(`redoCooldowns`)。時刻はタブのメモリにだけ持つ。画面とダイアログにも、承認の直後は押さないよう書く
- サーバー: `issue_proposal_apply`が、Issueを作る前に`claimIssueCreation`の条件付きUPDATEで印を取る。取れなかった呼び出しは、何もせずに終える。
  印は15分で切れるので、止まった処理のやり直しは塞がれない。
  失敗して提案を保留に戻した後も印は残り、期限が切れるまで、次の承認は何もせずに終わる。期限を過ぎて走り続けた呼び出しが失敗して戻すとき、印を取り直した別の呼び出しがIssueを作っている最中のことがあり、その処理と重ならないようにするためである。
  同時の呼び出しは、どちらもマーカーの走査の時点でIssueが無いと見て、Issueを2件作りうる。
  Windmillの同時実行の制限は設定しない。有償版でしか効かないので、印だけで直列化する

別のタブや別の端末からは、画面の側では止められない。サーバーの印が、この重なりを止める。

### 断りの表示

`approval_decide`は、承認の記録の前に、次の理由で断ることがある。
断りはジョブの失敗として返り、文は英語である。
既知の断りの文を含む失敗だけを、日本語の固定文と取れる手にして、承認バーの中に出す(`classifyDecisionRefusal`)。
トーストは消えるので、バーの中に残す。
Windmillは失敗の文に「Error:」などを前置きすることがあるので、文頭は見ない。
他のscriptの失敗とは、断りの文に固有の部分で区別する。

| 断りの理由 | 取れる手 |
| --- | --- |
| Issueが取り込みの後に書き換えられた | Issueを取り込み時点の内容に戻して承認し直す。現在のIssueを使うなら却下する |
| 現在のIssueを比べられなかった | 少し待って承認し直す。Issueを移したか削除したなら却下する |
| 別の決定が記録済みか、期限切れ | 一覧を読み直して状態を確かめる |
| 却下の理由が空 | 理由を入力して却下し直す |
| 承認依頼が見つからない | 一覧を読み直して状態を確かめる |

文は、`approval_decide.ts`と`approval_support.ts`が関数で作る。
`tests/scripts/console_approval_refusal_contract.test.ts`が、その関数の出力を画面の分類に通す。
Windmillの失敗の包み方を通した場合も、同じテストが確かめる。
既知でない文言は、結果が分からない失敗の案内に落とす。

### 要件定義の承認の前提

要件定義の承認は、承認者が次の2つを見られるときだけ押せる。
実装のClaudeが受け取る取り込み時点のIssueと、承認の対象である要件定義書である。
どちらかが読み込み中か、取得に失敗しているあいだは、承認を止めて理由を添える。
承認の可否は、取得の状態だけで決まる。
そのため、承認が載る2つの面(要件定義の承認と、Issue提案の承認)は、取得が済んだらすぐ内容を出す。
読み込み中の骨組みは残さない([画面の切り替え](#画面の切り替え))。
承認を押せるのに内容が見えない時間を作らないためである。
作業項目に取り込み内容が無いときも止める。確かめる内容が無いまま承認させないためである。
却下は止めない。内容を見られないことが、却下を妨げる理由にならないためである。
本文が長く切られているとき(`body_truncated`)は、GitHubで全文を確かめた旨のチェックを求め、チェックするまで承認を止める。
取り込み後に書き換えられていた場合の警告(`refreshed`)は、パネルの先頭に加えて、承認バーの中にも出す。
承認を押す位置で、確かめるよう促すためである。

要件定義書は、承認依頼の試行(`draft_attempt`)を指定して取り、要件定義書の画面と同じ部品で描く。
本文の描画、図の拒否、見えない文字の置き換えは、その部品に任せる。
承認の画面では、メタ情報、試行の切り替え、目次を省く。承認する試行を切り替えさせないためである。
長い本文は、枠の中でスクロールさせ、承認バーを遠ざけない。
「別の画面で開く」のリンクから、要件定義書の画面で読める。
`draft_attempt`が`null`で承認の試行が分からないときは、最新の試行で代えず、「承認する試行が特定できない」として承認を止める。
最新の試行は、承認する試行と違うことがあるためである。
取得した書の試行が承認の試行と違うときも、承認を止める。

承認の前の確認は、承認の操作を受ける側で働く([要件定義](requirements.md)の「承認の前のIssueの確認」)。

### Issue提案の本文

Issue提案の本文と、ラベルの選択肢の出し分けに使う情報は、`summary`に載せていないので、`console_query`の`inbox`から読む(`useInboxProposals`)。
本文と出どころの期間と担当は`displayableIssueText`を通す。
解釈はせず、プレーンテキストで描く。
置き換えた文字があれば、警告を出す。
提案が読めないか、一覧に無いときは、本文が分からないまま承認させないので、操作を出さない。
`tests/scripts/console_inbox_contract.test.ts`が、backendの`inbox`の変換結果が型ガードを通ることを確かめる。

### 一覧に出ない項目と空の状態

詳細から行える操作は、承認と却下、失敗の再実行、通知の解決である。
一覧に出ていない件数は、種類ごとのカード(色の点、件数)で知らせる。
対象は、取得の上限を超えた承認、失敗、通知と、再実行できず、後の監査で報告済みにもなっていない監査の失敗である。
監査の失敗のカードだけ、システムの画面へのリンクにして、押せると分かる矢印を添える。
システムの画面が読めるのは監査の失敗だけなので、取得の上限を超えた承認、失敗、通知のカードはリンクにしない。
残る件数は、報告済みになっていない監査の失敗と、取得の上限を超えた分である。
監査の失敗のカードには、再実行できないこととシステムの画面で確認することを添える。

要対応には、人にできる行動があるものだけを出す。
後の監査で報告済みの監査の失敗は、次の監査が失敗した期間を扱っており、人にできる行動が残らない。
そのため、カードの件数から外す。
報告済みかどうかは、後の報告の開始が前の報告の終わり以前かで決める。
切り詰められて報告の開始が遅れた失敗は、作業項目が保持期間で消えるまで要対応に残る。
前の報告が無いとき(初回と、保持期間で前の報告が消えた後)は、後の監査があれば報告済みとして扱う。
カードの件数は、summaryの`counts`の`audit_failures_open`である。この件数は取得の上限の前の全件から数える。
監査の失敗の判定の規則は[監査の内部仕様](audit.md#失敗した監査と要対応)にある。
再実行できる失敗の件数を求める引き算は、報告済みを含む監査の全件を引く。`counts`の失敗には報告済みの監査も含まれるためである。
サイドバーのバッジは、監査を数えない。
古いbackendは`audit_failures_open`を送らないので、そのときは見えている監査の失敗の全件をカードに出す。
取得は新しい順に上限まで読むので、上限を超えた分は古いものから表示されない。承認、失敗、通知のカードにその旨を添える。
同じ数をサイドバーには出さない。画面の中で1か所だけに示すためである。

一覧が空のときは、画面を2つに割らず、中央に1枚の面を出す。
面には、承認、失敗、通知が無いことと、ほかの種類に残る件数のカードを載せる。
最終更新と自動更新の間隔は、画面の見出しが示すので、面には載せない。
何も残っていないときだけ緑のチェックを出す。ほかの種類が残っているときは、中立のアイコンにして、片付いた印象を与えない。
一覧の取り直しが失敗しているときは、緑のチェックを出さず、中立のアイコンにする。
見出しは「最後に取得できた時点では、対応が必要な承認・失敗・通知はありませんでした」に変える。
あわせて、古い値の知らせを添える。
確かめられていない状態で「何もない」と言い切らないためである。
401のときは見出しだけを変え、知らせは上のバナーに任せる。
カードは面の幅を等分して並べる。
401で取得できないときは、バナーと並べて、ログインが必要である旨を中央に出す。

並び、絞り込み、行の表示内容、副題、件数のカードは`src/lib/inboxView.ts`の純関数が決める。
失敗の詳細と再実行の確認の内容は`src/lib/failureView.ts`、再実行のロックのキーと結果の知らせは`src/lib/retryView.ts`が決める。
自動更新の間隔の表示は`src/lib/refreshTiming.ts`が決める。
分で割り切れる間隔は分で、それ以外は秒で書く。
相対時刻の表示は、`src/app/clock.ts`の共有の時計が30秒ごとに進める。

### 通知

一覧に出す通知は、`summary`の未解決で、重要度が要対応のものである。
重要度が情報の通知は、人の行動が要らないので、一覧に出さない。
情報の通知と、`summary`の上限を超えた通知は、`?notice=<id>`で選ぶと、同じ詳細が開く。
このとき`console_query`の`notices`viewから、未解決の通知を探す。
viewには、backendが受ける最大の2000件を指定する。`summary`の上限を超えた通知も開くためである。
`notices`viewは自動では取り直さず、詳細を開くたびに取り直す。タブへ戻っただけでは取り直さない。解決した通知を未解決のまま出さないためである。
一覧と`notices`viewのどちらにも無いときは、すでに解決されたか、まだ取得できていないと伝える。

一覧の行は、題名に通知の種類の日本語名を出す。
2行目の「通知」の語と副題の組み立ては、[要対応の画面](#要対応の画面)の一覧の行に書いた。
詳細には、重要度、本文、対象、発生した時刻、起きたことと次の操作を出す。
本文は`displayableIssueText`を通し、プレーンテキストで描く。
`summary`は本文を500文字で切る。
一覧から選んだ通知の本文が、ちょうど500文字のときは、本文が途中までであることを添える。
切れ目に接する`owner/repo#番号`は、番号の途中で切れているおそれがあるので、リンクにしない。
`notices`viewは全文を返すので、`?notice=`で開いた詳細には、この扱いをしない。
対象は、本文の`owner/repo#番号`から作ったGitHubへのリンクで、`safeGitHubUrl`を通ったものだけを張る。
本文からはIssueかPRかを区別できない。GitHubは`/issues/<番号>`をPRなら`/pull/<番号>`へ転送するので、常にIssueの形のURLを作る。
起きたことと次の操作は、`src/lib/noticeGuide.ts`が種類ごとに持つ。内容は[運用](../operations.md)の通知の表に合わせる。
表に無い種類は、本文を確かめるよう案内する。
ホスト側の作業が必要な通知(`host_action_required`)には、ホストのcheckoutで順に実行するコマンドを出す。
コマンドは、`git pull`、`mise install`、`mise run up`である。

解決のボタンは、未解決で、`summary`の`resolvable`が真のときだけ出す。
Consoleから解決できない種類には、ボタンの代わりに理由を出す。設定や権限の問題を示す通知を、内容を確かめないまま消せないようにするためである。
ボタンを押すと、確認のダイアログを出さずに`resolveNotice`を呼ぶ。解決した通知は履歴に残り、状況が続けば新しい通知が出るので、取り返しのつかない操作ではない。
解決済みだった通知は成功として扱い、「すでに解決済み」と知らせる。
成功と、結果が分からない失敗の後は、`summary`と`notices`viewを読み直す。解決した通知は一覧から消える。

行と詳細に「解決済み」の印を用意している。両方のviewが未解決の通知だけを返すので、通常は出ない。
解決済みの通知の履歴は、[システムの画面](#システムの画面)に出す。

表のセルの文字にIDが含まれるときは、ハイフンで折り返すとIDが読めなくなるので、IDの部分を折り返さない。
強調やコード、リンクの中のIDは対象にしない。
表示の判定は`src/lib/requirementsView.ts`の純関数が決める。

### 試行の切り替え

試行は、最新から1までのリンクで切り替える。
表示する試行はURLの`?attempt=<k>`に持ち、番号が無ければ最新を出す。
`?attempt=`があって、先頭が0でない正の整数でないとき(`abc`、`0`、`02`、`1.5`、空)は不正とする。
2147483647を超える値も不正とする。
不正なときは、取得せずに「試行の番号が正しくありません」と出す。最新として読むと、別の試行を読んでいると気づけないためである。
最新へのリンクは番号を付けず、最新を指し続ける。
最新の試行を確かめられるのは、最新を指定して本文を取ったときと、一覧にその作業項目の行があるときだけである。
このときの最新の試行の番号は、本文の試行と一覧の行の、大きいほうにする。
古い試行を開いていて、一覧がまだ答えないときと、一覧に行が無いときは、最新を確かめられない。
このあいだは、どの試行にも「(最新)」を付けず、開いている試行までを番号つきのリンクで並べる。
選択肢は新しいほうから50件までに絞る。
却下による作り直しは、試行が増えることで現れる。
却下の理由と承認の履歴は、`work_item_detail`の`approvals`が持つが、この画面は読まない。
`requirements_doc`が持たないためである。

### 本文の描画

本文の描画は`src/components/markdown/Markdown.tsx`にある。
Issueの内容に由来する信頼できない入力なので、次のように扱う。

- 本文、要約、未確定事項、題名は、見えない文字を`displayableIssueText`で置き換えてから描く。置き換えたときは、その旨を出す。
- `react-markdown`と`remark-gfm`で描き、`rehype-sanitize`で無害化する。生のHTMLは描かず、`dangerouslySetInnerHTML`も使わない。
- リンクにするのは、作業項目と同じリポジトリのIssueとPRのURL、本文内の見出しへのフラグメントだけである(`src/lib/markdownLink.ts`)。それ以外は文字で出す。
- リンクの文字とURLが違うときは、URLを括弧で添える。添えたURLは`<bdi>`で包む。
- 画像は、図の参照(`![name](name.drawio)`)だけを通す。ほかの画像は描かない。
- `> [!NOTE]`、`> [!WARNING]`、`> [!IMPORTANT]`で始まる引用は、ラベル付きの囲みで描く。

理由は[セキュリティ](../security.md)の「要件定義書のリンク」にある。

目次は、行頭から始まる`##`と`###`の見出しである。
コードの囲みの中の行は、見出しに数えない。
見出しの走査は正規表現で行う。そのため、HTMLのコメントの中の行は見出しに数え、`id`のない目次の項目になる。
行頭が空白や`>`で始まる見出しと、下線で書く見出しも数えない。
見出しの`id`は、見出しの文字から作ったスラッグに`h-`を付ける。
ページの他の要素の`id`と名前が重ならないようにするためである。
`id`が使われているときは、使われていない`id`になるまで`-2`、`-3`を付ける。
見出しが`a`、`a`、`a-2`の順に並んでも、`id`は重ならない。
`id`は`src/lib/markdownHeadings.ts`が行ごとに決め、描画は見出しの行から引く。
目次のリンクと見出しの`id`が、必ず一致する。
本文のリンク`[文字](#見出し)`は、同じ規則で`#h-見出し`に読み替える。
本文は脚注の記法を使わない。
`#user-content-fn`で始まるフラグメントは、見出しへのリンクに読み替えず、文字で出す。行き先のないリンクにしないためである。

題名は、本文の最初のレベル1の見出し(`#`で始まる行)にする。
無ければIssueの題名、それも無ければ「(無題)」にする。
題名の行は、ページの見出しに出すので、本文では描かない。

### 手動の起動

「今すぐ監査」を押すと、確認のダイアログを出す。
ダイアログは、ブラウザ標準の`dialog`要素をモーダルで開く。
確認すると、`kickoffAudit`で`audit_kickoff`を起動する。
起動の前にダイアログを閉じるので、確認のボタンを二重に押しても、起動は1回になる。

起動の設定は`src/api/auditKickoffConfig.ts`にあり、書き込みの共通の流れに載せる。

- ロックのキーは1つに固定する(`AUDIT_WRITE_KEY`)。起動が実行中のあいだ、ボタンは押せない
- 同じ瞬間に2回呼ばれても、実行は1回になる
- 結果が分かったら、監査レポートの一覧を読み直す
- 読み直せなかったときは、一覧が古いことを知らせ、一覧が更新されるまでボタンを押せないままにする

`force`は渡さない。
`force`を付けると、対象の記録が無くても起動するので、画面からは出さない。

結果は、一覧の上に画面を離れるまで残す(`src/lib/auditKickoff.ts`)。
トーストは数秒で消え、見送りの理由を読み落とすおそれがあるためである。

| 結果 | 表示 |
| --- | --- |
| 起動した | 成功の色で、対象期間を添える |
| 見送った | 通常の色で、理由を日本語で出す。理由は`writeNotices.ts`の対応表にある |
| 失敗した | 失敗の色で、書き込みの失敗の文を出す |
| 一覧を読み直せなかった | 警告の色で、一覧が古いことを出す |

見送りは失敗ではなく、何も変えなかった正常な結果である。

## システムの画面

この画面は、Software Factory自身の状態を、先頭の要約の帯と、4つのタブに分けた節で出す。
結論は帯で読み、根拠はタブの節で読む。
書き込みは保留と凍結の設置と解除だけで、ほかの節は読むだけである。
通知の解決は、要対応の画面の詳細で行う。
起動の関係の節は、バンドルに取り込んだ静的なデータを図にし、実行中のflowを重ねる。
重ねる実行の状態は、この節だけが読む2つの取得で、「図を表示」を開いた後にだけ始める。

更新のボタンと最終更新は、画面の見出しに1組だけ置く。
ボタンは、下の4つの取得(`console_holds`、`system_status`、`deployments`、`summary`)を取り直す。
設定のタブを開いた後は、設定の取得(`console_config`)も取り直す。
「図を表示」を開いた後は、実行中と待ちの一覧とscheduleの取得も取り直す。
最終更新は、定期に取り直す4つの取得に、図の2つの取得を加えたうち、取得できたものの最も古い時刻である。
図の取得は自動で取り直さないが、最終更新に数える。
実行の状態は短い間に変わるので、古い状態を新しい時刻で見せないためである。
設定は自動で取り直さないので、最終更新には数えない。
数えると、タブを開いた後は、見出しの時刻が設定を取った時刻で止まるためである。
取得中と失敗には、設定も含める。
保留と凍結と要約は定期に取り直し、`system_status`は取り直さない。
そのため、最も古い時刻は、たいてい`system_status`の取得を指す。
節と帯は、取得の時刻を出さない。画面の見出しの「最終更新」と重なるためである。
4つの取得は、保留と凍結、状態、要約、更新履歴の順に始める。
workerは1台で直列に処理する。帯とタブの判定に使う3つを先に済ませ、帯が読まない更新履歴を最後にするためである。
節は、読み込みが続く間は骨組み([画面の切り替え](#画面の切り替え))、取得に失敗したときは節の中に失敗の表示と「もう一度取得する」を出す。
401のときは、上のバナーが知らせるので、節にはログインを促す文だけを出す。
1つの節が失敗しても、ほかの節は表示する。

反映の状態、workerの負荷、情報の通知、解決済みの通知、作業項目に紐づかない失敗は、`console_query`の`system_status`viewを1回取って揃える。
この5つの節は、取得の結果を分け合う。
画面が取得を1つだけ持ち、見出しの更新で一緒に取り直す。
同じ取得を重ねて取り直すと、互いを打ち切るためである。
定期には取り直さない。通知の解決が、この取得を読み直すので、要対応の画面で解決した通知を、未解決のまま出さない。
各一覧は200件までで、200件に達した節には、これより古いものは表示していない場合がある旨を添える。
情報の通知、解決済みの通知、更新履歴(すべて表示したとき)、監査の失敗の一覧と、作業項目に紐づかない失敗のflowごとの失敗は、取得した件数を10件ずつのページに分ける([ページ送り](#ページ送り))。
ページに分けても取得の上限は変わらない。上限の注記は、全ページを通した一覧にかかる。
型は`src/api/guards/systemStatus.ts`の型ガードで確かめる。形がずれると、画面は`invalid_response`の失敗を出す。
backendの型との一致は、`tests/scripts/console_system_contract.test.ts`が確かめる。

### 要約の帯

帯は、タブの上に置き、タブと一緒に本文のスクロール枠の先頭に置く。
幅が768px(md)以上で、高さが640px(40rem)以上のときだけ、枠の上端に貼り付ける。
貼り付くと、タブを替えても、本文をスクロールしても、帯とタブが見える。
条件の片方でも満たさない画面では、貼り付けず、本文と一緒にスクロールさせる。
帯とタブが画面の大半を占め、本文が読めなくなるためである。
条件はCSSの媒体条件で書く(`STICKY_HEADER_CLASS`)。
画面の大きさで親を入れ替えない。入れ替えると、切り替えのたびに本文を描き直し、スクロール位置を失うためである。
貼り付いた部分は、背景を持ち、下をくぐる本文が透けない。
貼り付いた部分の高さと16pxの余白は、節への移動とページ送りのスクロールが差し引く。見出しや一覧の先頭が、帯とタブの下に止まる。
帯はチップの並びで、折り返す。チップは、段の記号、短い名前、件数か一言を並べる。
チップは、節が使う既存の判定を段と文に写したもので、新しいしきい値は作らない。
段は正常、注意、要対応の3つで、読めないチップは「判定なし」にする。
段は、色だけに頼らず、記号と文字でも示す。記号は、正常が丸のチェック、注意が三角の警告、要対応が八角の警告、判定なしが横線である。段の語は、読み上げにだけ出す。読み上げは名前、文、段の語の順で、「要対応 3件 注意」のように結論を先に伝える。
チップの文と段は、`src/lib/summaryBand.ts`の純関数が決める。

| チップ | 文と段の決め方 |
| --- | --- |
| 要対応 | 要対応の画面のバッジと同じ件数。1件以上は注意、0件は正常。押すと要対応の画面へ移る |
| 保留と凍結 | 有効な行があれば注意(意図した停止の周知)、無ければ正常。期限切れの行は何も止めないので、有効な件数から外し、段に影響させない。保留か凍結を読めない場合と、取得が丸ごと失敗した場合は要対応。読めないときは、何が止まっているかを判断できないためである |
| 直近の反映 | 反映が失敗なら要対応。ホストの作業が残っているかは、未解決の通知の件数で決める。1件以上なら注意で、押すと要対応の画面のその通知へ移る。無ければ、成功は正常、記録が無ければ判定なし |
| Consoleの取り込み | 版の固定だけが注意(意図した状態)。失敗、更新の停止、状態を読めない場合、知らない状態は要対応。取り込みが止まっている可能性があるためである。取り込み済みは正常 |
| 失敗 | 監査の失敗(後の監査で報告済みでないもの)が1件以上あれば注意。監査が0件で、作業項目に紐づかない失敗が無ければ正常。紐づかない失敗だけが残るときは、正常にせず、判定なしにして件数を添える |

ホストの作業は、反映の記録の印(`needs_host_action`)では判定しない。作業が済んでも、記録の印は残るためである。
数えるのは、`summary`の未解決の通知のうち、種類が`host_action_required`のものである(`src/lib/hostActionNotices.ts`)。
通知は、ホストでの反映が済むと自動で解決される。
件数は、残っている作業の数と一致するとは限らない。通知は版を持たず、反映の回数分だけ溜まることがある。
`summary`の一覧は上限までしか取らない。全件の数が一覧より多いときは、件数を「N件以上」と書く。
一覧にホストの作業の通知が1件も無いときは、残っているかを言い切れないので、反映の記録の印で代え、「通知を確認できません」と添える。
通知の取得に失敗して値が無いときも、記録の印で代え、「通知の取得に失敗」と添える。
通知を取得中のあいだは、記録の印で代えず、取得中にする。作業が済んでいても、残っているように見えるためである。

作業項目に紐づかない失敗を判定しないのは、直近7日の窓に残る過去の記録で、今対応が要るかを決められないためである。
同じ失敗が繰り返されるflowは、対応が済んだ後も、窓から外れるまで件数に残る。判定すると、対応しても注意が消えない。
一方、監査の失敗は、後の監査で報告済みのものを件数から外す。そのため、対応の後は0件になる。

要対応と失敗の件数は、帯に必ず出る。情報の通知とworkerの負荷は、判定が無く、行動につながらないので、帯に置かない。内容は各タブの節にある。
取得中のチップは「取得中です」、取得に失敗したチップは「取得できませんでした」と出し、判定しない。
ただし、保留と凍結は、取得が丸ごと失敗したときも要対応にする。一部を読めないときと同じ扱いである。
待ちの間は、段を決めない。
取得中の文は、待ちが300msを超えるまで出さず、チップの名前だけを出し、記号と文を隠す。
短い取得で文が一瞬だけ出るのを避け、値が届いたときにチップの大きさを動かさないためである。
規則は[画面の切り替え](#画面の切り替え)のスケルトンと同じである(`useDelayedVisible`)。取得に失敗したチップは、待たずに出す。
取り直しに失敗しても前の値が残っているときは、前の値で判定して出し、「前の値(取得に失敗)」と添える。
失敗の件数は、片方の取得が読めなくても、もう片方の件数を出す。読めない側は「取得中」か「取得できません」と書く。

帯は、取得の時刻を出さない。画面の見出しの「最終更新」が、画面の全取得のうち最も古い時刻を示すためである。
取得の失敗は、時刻を消しても残る。
取得に失敗したチップは「取得できませんでした」、前の値を出すチップは「前の値(取得に失敗)」と書く。
取得に失敗した節は、失敗の表示と「もう一度取得する」を出す。
定期のジョブが動いているかは、この帯では判定しない。ジョブの画面のスケジュールのタブで、有効かどうかと次回の予定、直近の実行を読める。
workerが動いているかも、この帯では判定しない。止まったときは通知で知らせる([workerの負荷](#workerの負荷))。

チップは関係する節へのリンクである。押すと、その節があるタブを開き、節の見出しへ移る。失敗のチップは、監査の失敗が無く、作業項目に紐づかない失敗だけがあるときは、その節へ移る。
直近の反映のチップは、未解決のホストの作業の通知があるときは、要対応の画面のその通知へ移る。
移動は、本文のスクロール枠だけを動かし、見出しへフォーカスを移す。URLの`?tab=`は替えるが、履歴は積まない。
チップの行き先にあるたたんだ部分は、作業項目に紐づかない失敗の最新のflowの組だけである。節へ移るときは、その`<details>`を開く。移った先で本文が見えるようにするためである。
情報の通知、解決済みの通知、起動の関係は、チップの行き先ではないので、移るときも開かない。
修飾キーを押したクリックと中ボタンは、リンクの既定に任せ、新しいタブで開く。

### タブの構成

タブは状態、失敗と通知、履歴と構成、設定の4つで、開くタブは`?tab=failures`、`?tab=history`、`?tab=config`で選ぶ。状態は名前を持たない。
共通の規則は[タブ](#タブ)にある。

| タブ | 節 |
| --- | --- |
| 状態 | 保留と凍結、反映の状態、workerの負荷 |
| 失敗と通知 | 監査の失敗、作業項目に紐づかない失敗、情報の通知(たたむ) |
| 履歴と構成 | 更新履歴、解決済みの通知、起動の関係 |
| 設定 | 設定の全項目 |

タブに分ける理由は、1つの縦並びが長すぎることである。
全部を縦に並べると、実データで約5200px(画面6枚以上)になる。たたむだけでは、短くならない節が残る。
分けた後の長さは、各タブの本体が1〜2画面に収まる目安である。

選んでいないタブは、初めて開くまで描かない。開いた後は隠して残し、スクロール位置と、折りたたみの状態を保つ。
更新履歴と解決済みの通知は描くのが重いので、開かないタブの描画を避ける。
取得は画面が持ち、帯が読む値は常に取得する。節を分けても、取得の数は増えない。
設定の取得だけは、設定のタブを初めて開いた後に始める。
帯とタブは枠の先頭にあり、貼り付くときは本文の上に重なる。本体は、どのタブも帯とタブの下から始まる。

### 失敗が隠れないための条件

タブで分けても、失敗を見落とさないよう、次を守る。

- 帯の失敗のチップに、失敗の件数を必ず出す。監査の失敗の未解決の件数と、作業項目に紐づかない失敗の件数は、開いているタブにかかわらず読める。タブの名前には件数を添えない。同じ数字を2か所で確かめさせないためである
- どちらかの件数が読めないときは、読めない側を「取得中」か「取得できません」と書く。読めた側の件数は出す
- 作業項目に紐づかない失敗が取得の上限(200件)に達したときは、帯の文に「200件以上」と書く。上限で切れた件数を、少なく見せないためである
- 失敗と通知のタブに、失敗のチップが注意のとき、三角と「注意」の印を付ける。紐づかない失敗だけが残るときは、判定しないので印を付けない。選んでいても外さない
- 状態のタブに、そのタブのチップのうち、反映が注意以上のとき(ホストの作業が残っているとき、反映が失敗したとき)、または保留と凍結か取り込みが要対応のとき、最も重い段の印を付ける。注意は三角と「注意」、要対応は八角と「要対応」である。保留の有効な行や、取り込みの版の固定のように意図した状態(注意)は、印を付けない。いつも印が付くと、本物の注意が埋もれるためである
- 印の語と記号は、印を付けるチップの段から決める。帯のチップと同じ形で、色だけに頼らない
- 取得が失敗したタブには、八角と「取得に失敗」の印を付ける。段の印があるタブは、「注意・取得に失敗」のように並べる。段の印があるタブは、選んでいても並べる。値が前の取得のものだと伝えるためである
- 要対応の画面は、この画面のタブとは別で、変えない

次の純関数のテストが、これらの条件を固定する。

- 帯の写像: `src/lib/summaryBand.ts`
- タブの印: `src/lib/systemTabs.ts`
- 取得の失敗とタブの結び付け: `src/screens/system/systemScreenView.ts`

### 保留と凍結

この節は、Factoryのマージと反映を止めている保留、スケジュールの凍結、deployの保留を出し、人が確認して置き、解除できる。
システムの画面で書き込みを持つのは、この節だけである。
置く操作は、節の先頭にある「保留や凍結を置く」のボタンが開くダイアログで行う。
置く操作の仕様は、次の「置く」にある。
ホストの端末のCLIでも置ける([保留の内部仕様](holds.md))。

取得は`console_holds`の1回で、保留の表と凍結の変数を別々に読む。
片方が読めなくても、もう片方は表示する。
取得の結果は`src/api/holdsQueries.ts`の`useHolds`が持つ。
保留は期限で終わるので、画面が見えている間は`summary`と同じ120秒ごとに取り直す。見出しの更新も、この取得を取り直す。
型は`src/api/guards/holds.ts`の型ガードで確かめる。形がずれると、節は`invalid_response`の失敗を出す。
backendの型との一致は、`tests/scripts/console_holds_contract.test.ts`が確かめる。

保留と凍結の両方が読めて、有効な行が1つも無いときは、2つのカードを1行にたたむ。「有効な保留と凍結はありません」と、置き方の案内を出す。
どちらかが読めなかったときと、どちらかに行があるときは、次の2つのカードを出す。
カードは成功と失敗を別々に出す。

| カード | 出す行 | 並び |
| --- | --- | --- |
| 保留 | 有効な保留。マージの保留と、読む処理が無い取り込みの保留 | マージ、取り込みの順に、それぞれ期限が近い順 |
| 凍結とdeployの保留 | 有効なスケジュールの凍結とdeployの保留 | deployの保留、スケジュールの凍結の順に、それぞれ期限が近い順 |

行には、種類、対象、理由、置いた主体、期限と残り時間、「解除」のボタンを出す。
deployの保留の対象は、反映全体(`self_update`、push、migration)と書く。
取り込みの保留は、読む処理が無いので何も止めていないと注記する。
期限を過ぎた行と、有効の条件を満たさない未解除の行は返さない。それらは止める効果が無く、`mise run hold:list`が見せる。
期限は画面の時計で判定する。取得の間に期限が来た行は、解除のボタンを外し、「期限切れ」と出す。
DBの時計と画面の時計のずれで、境界に数秒の誤差が出る。解除はidで行い、idは再利用されないので、別の行を解除することはない。

行の理由、対象、置いた主体は、DBや変数に書ける主体が決める信頼できない文字列である。
backendが制御文字と書式文字を空白にして切り詰め(理由は200字、置いた主体は100字、対象は200字)、画面が`displayableIssueText`で同じ検査をやり直す。
文字としてだけ描き、リンク、画像、Markdownにしない。書字方向は行ごとに隔離する。
通知とログには、理由と置いた主体を載せない。

読めなかったときは、保留なしと取り違えないよう、次の表示にする。

| 状況 | 表示 |
| --- | --- |
| 読めて、行が無い | 「有効な保留はありません」。成功のときだけ出す |
| 保留の表が無い | 警告。migrationが未反映で、dependabotの自動マージとローカルのマージが止まる旨 |
| 保留の表を読めない | 警告と「もう一度取得する」。理由は折りたたむ。止まる旨を添える |
| 保留の表に壊れた行がある | 警告。一覧を出せない旨、止まる旨、理由に含まれる回復の手順をそのまま開いて出す。解除のボタンは出さず、`mise run hold:list`を案内する |
| 凍結の変数を読めない | 警告と「もう一度取得する」。理由に含まれる回復の手順を開いて出す。反映が要る回の`self_update`が止まる旨を添える |
| 取得全体の失敗 | 節の失敗の表示。401はログインを促す文だけ |
| 前回の値があり、取り直しに失敗 | 値を出したまま、古い旨の注意を出す |

失敗の種類と、行の範囲と置いた主体の種類は、文字列で受ける。
知らない値は、決まった文言に落とす。backendが先に新しい値を反映した間も、一覧の全体が消えないためである。
文言は`src/lib/labels.ts`に集め、表示の判断は`src/lib/holdsView.ts`の純関数が持つ。

#### 置く

「保留や凍結を置く」を押すと、確認のダイアログを開く。
入力は、種類、対象、期限(分)、理由の4つである。
種類は、マージの保留、deployの保留、スケジュールの凍結から選ぶ。
deployの保留は対象を持たないので、対象の欄を出さない。

| 種類 | 対象 | 期限の上限 |
| --- | --- | --- |
| マージの保留 | `owner/repo`の形 | 1440分 |
| deployの保留 | 無し | 120分 |
| スケジュールの凍結 | `f/factory/名前`の形のスケジュール | 1440分 |

期限の欄には、入力できる範囲(「1分から120分まで」のような文)を常に添える。
範囲は、置くscriptの上限と同じ値を`src/lib/holdPlace.ts`が持つ。
一致は、`tests/scripts/console_hold_place.test.ts`が固定する。
期限の問題の文(短すぎる、上限を超えている)は、範囲の数字を繰り返さない。
理由は必須で、200字までである。制御文字と書式文字は使えない。
入力が正しくない間は、確認のボタンを押せなくし、問題のある欄の下に文を出す。
空の欄は、まだ入力していないだけなので、問題の文を出さない。

ダイアログは、種類ごとに、置いたときの効果と、終わり方(期限と解除)を並べる。
確認のボタンは破壊的な色にしない。
期限が来れば必ず終わり、解除でき、置き直せるためである。
フォーカスは「取り消す」に置く。
画面の検査は案内で、境界は置くscriptが同じ検査で確かめる。

確認すると`console_hold_place`を呼ぶ。
操作者と置く主体は引数に取らない。
scriptが実行文脈から操作者を導き、置く主体は人に固定する。
二重の送信は、種類と対象ごとのロックで止める。
置く操作は再試行しない。

| 結果 | 知らせ |
| --- | --- |
| 置いた | 成功の色。止められるスケジュールの凍結には、止められるようになる時刻を添える。凍結が、止められる前、または残りの下限(5分)を割る前に終わるときは添えない |
| 置いたが、読み直しで確認できなかった | 警告の色。置いた行が見えない、または書く前に有効だった他の行が欠けているとき。一覧を取り直して確かめる旨 |
| 断った | 情報の色。理由は`writeNotices.ts`の対応表にある |
| 失敗 | 失敗の色 |

置いた後は、保留と凍結の取得と、システムの状態を読み直す。
同じ対象に有効な保留か凍結がすでにあれば、重ねずに断る。
ローカルのセッションの保留や凍結があるときも断る。
保留と凍結の件数が上限に達しているときも断る。
断りの文には、内部の用語(行、主体)を使わない。
二重の送信を止めるロックの鍵は、種類と、小文字にそろえた対象である。
スクリプトが対象を小文字にそろえて置くためである。

確認の流れ(ダイアログを開く、入力を整える、確認を通ったときにだけ書き込みを呼ぶ)は、`src/screens/system/usePlacement.ts`の純関数が持つ。
開いただけでは書き込みを呼ばず、整っていない入力では呼ばない。
フックは、この関数に状態と書き込みを渡すだけにする。

#### 解除

「解除」を押すと、確認のダイアログを開く。
ダイアログは、種類、対象、理由、置いた主体、期限と残り時間、id、解除の効果を出す。
フォーカスは「取り消す」に置く。確認のボタンは破壊的な色にしない。
人以外(セッション、Factory)が置いた行には、置いた理由を確かめてから解除する旨を添える。

| 種類 | 解除の効果 |
| --- | --- |
| マージの保留 | dependabotの自動マージとローカルのセッションのマージが、次の取得から再開する |
| 取り込みの保留 | この範囲を読む処理が無いので、動作は変わらない。表の掃除として解除できる |
| deployの保留 | `self_update`が次の回から反映を再開し、見送っていた変更をまとめて反映する。ほかに有効なdeployの保留が残るときは、その件数を添え、すべて外れるまで再開しない旨を出す |
| スケジュールの凍結 | 次の反映(`self_update`の追従)で、このスケジュールがリポジトリの定義に戻る。有効なdeployの保留があるあいだは、追従も待つので戻らない旨を、その件数とともに添える |

確認の入力(`yes`の打鍵)は求めない。
ログインした管理者が、対象、期限、効果を見て押す操作であり、フォーカスの既定が「取り消す」で、解除は止めが外れる向きだが期限で必ず終わるためである。

確認すると、保留は`hold_release`、凍結とdeployの保留は`freeze_release`を呼ぶ。
操作者は引数に取らない。scriptが実行文脈から導き、解除する主体は人に固定する。
結果は、トーストで知らせる。

| 結果 | 知らせ |
| --- | --- |
| 解除した | 成功の色 |
| 解除した。通知を残せなかった | 警告の色。誰が解除したかはジョブの記録で確かめる旨 |
| 解除したが、解除の前に有効だったかを確認できなかった(`active_unknown`) | 警告の色。通知を残せなかったときは、その旨の文も続く |
| 期限切れの行を片付けた | 成功の色。通知は残さない |
| すでに解除されていた、すでに終わっていた | 情報の色。複数のタブからの再送も成功として返る |
| 解除を確認できなかった | 警告の色。一覧を取り直して確かめる旨 |
| 失敗 | 失敗の色 |

解除の後は、保留と凍結の取得と、解除の通知が出るシステムの状態を読み直す。
読み直せなければ、一覧が更新されるまで、その行を止めたままにする。
二重の送信は、行ごとのロック(`writeTargetKey`の`hold`と`freeze`)で止める。ロックは同じタブの中だけである。
解除は再試行しない。

#### ブランチ版の確認

検証用サーバー(`scripts/console-branch-server.ts`)は、ブランチ版のConsoleを、ローカルのWindmillに繋いで開かせる。
操作の手順は、[ブランチ版のConsoleを確かめる](../setup.md#ブランチ版のconsoleを確かめる)にある。
ブラウザから見るとConsoleとWindmillが同じオリジンになるので、ブランチ版のConsoleが、運用者のCookieのまま本物のWindmillのAPIを呼ぶ。
既定は読み取りだけで、要求を次のように振り分ける。

| 要求 | 扱い |
| --- | --- |
| `/console/*` | `console/dist`を返し、無いパスはSPAの`index.html`に落とし、assets、draw.ioのファイル、`status.json`は無ければ404にし、Caddyと同じCSPなどのヘッダーを付ける |
| `/console` | `/console/`へ308で飛ばす |
| 符号化した区切りと`..`を含む`/console/`のパス | 400にする |
| `/api/`の外のGET、HEAD、OPTIONS | `--upstream`(既定は`http://127.0.0.1:8080`)へ中継する(ログインの画面と静的な資源が当たる) |
| `/api/`の下の読み取りのGET、HEAD、OPTIONS | 許可リストにある経路だけ中継する(`/api/version`、`/api/users/whoami`、ジョブ1件を読む`jobs_u`の経路) |
| 読み取りの5つのscriptを実行するPOST | 中継する |
| ほかの要求 | 403にし、人が`--allow-writes`を付けたときだけ中継する |

Windmillは、GETでもscriptを同期で実行できる(`GET /api/w/{workspace}/jobs/run_wait_result/p/{path}`)。
`windmill-client` 1.817.0のOpenAPIに、この経路がGETとPOSTの両方で載っている。
そのため、GETとHEADも許可リストで絞る。
実行、再開、取り消し、再実行、ストリーム、エンドポイントの経路(`/api/r/`)、webhookを含むパスは、メソッドを問わず403にする。
ConsoleがWindmillを呼ぶのは、読み取りのscriptを実行するPOSTと、`/console/status.json`のGETだけである。
`/api/`のGETは使わない。

読み取りの5つは、`console_query`、`console_holds`、`console_jobs`、`console_schedules`、`console_config`である。
`tests/scripts/console-branch-server-readonly.test.ts`が、次を固定する。

- 5つが相対importで辿るファイルに、SQLの書き込みとWindmillの書き込みや実行のAPIが無い。
- 書き込みと読み取りが同居する共有の部品(`lib/db.ts`、`lib/holds.ts`、`lib/freeze_apply.ts`)から取り込む名前が、読み取りの関数に限られる。
- 呼ぶ関数(`fetchDeploymentRows`、`sumAgentCostSince`、`listActiveHolds`、`readFreezeState`)の本文に、書き込みが無い。
- `console_holds`は、凍結の変数の書き込みの口(`writeVariable`)を組み立てるが、読む経路は`readVariable`だけを呼ぶ。

`console_holds`は、保留と凍結を読むだけで、解除は別のscriptが行う。

要求は、次の検査も通る。

- Hostは、`127.0.0.1:<port>`か`localhost:<port>`だけを通す。
  DNSリバインディングで別の名前から届いた要求を断るためである。
- Originは、このサーバー自身のオリジンのときだけ、中継先のオリジンに置き換えて中継する。
  ほかは403にする。
- 中継の要求の`Sec-Fetch-Site`が`cross-site`か`same-site`なら403にする。
- 転送元を名乗るヘッダー(`Forwarded`、`X-Forwarded-*`、`X-Real-IP`)とhop-by-hopのヘッダー(`Connection`が名指しするものを含む)は、中継先へ渡さない。
- 中継先の`Location`は、このサーバーのパスに直す。
  `//host`のようなプロトコル相対の形にならないよう、先頭の`/`を1つにそろえる。
- Bunのfetchは、渡した`Sec-Fetch-*`を落とさずに中継先へ送る(模擬の中継先で実測した)。
  ブラウザが付けた値のまま、中継先のCaddyの規則に届く。

`--allow-writes`は、端末で人が「yes」と入力したときだけ有効になる。
標準入力が端末でないとき(agentの起動やパイプ)は、起動に失敗する。
有効な間は、起動時に目立つ警告を標準出力に出し、全応答に`x-branch-server-writes: on`を付ける。

反映後の実機と違う点は、`status.json`を配信しないことである。
そのため、サイドバーの版の情報は出ない。
CSPなどのヘッダーは、`infra/Caddyfile`の`console_headers`と`drawio_headers`と同じ値を付け、テストが一致を確かめる。

#### 描画の確認

画面の描画は、Playwrightで確かめる。
Consoleの開発サーバー(`bun run --cwd console dev`、`http://localhost:5173/console/system`)は`/api`を中継しない。
そのため、`/api/w/factory/jobs/run_wait_result/p/**`をすべて`page.route`で差し替える。
`console_holds`だけでなく、システムの画面が呼ぶ`console_query`の`system_status`、`deployments`、`summary`も差し替える。
実際のWindmillには何も届かないので、解除のボタンを押しても、本物の保留は解除されない。

状態ごとに応答を変えて、次を確かめる。

- 保留、取り込みの保留、deployの保留、スケジュールの凍結が並ぶ表示と、何も無い表示
- 保留の表が無い、保留を読めない、保留の表が壊れている、凍結の変数を読めない表示
- `<a href>`を含む理由と、書字方向を変える制御文字を含む置いた主体が、文字のまま出ること
- 長い理由と長い対象の折り返し
- 期限が数十秒後の行が、画面の時計の更新(30秒ごと)で「期限切れ」に変わること
- 401のときの、ログインを促す文
- ライト、ダーク、狭い幅
- 確認のダイアログと、開いた直後のフォーカスが「取り消す」にあること
- 実行中のロックと、解除の結果のトースト

撮影した画像はリポジトリに置かない。

### 反映の状態

次の3行を、1枚のカードに出す。

- 反映した版。`system_status`が読んだ、反映済みの版の記録である。読めなければ「不明」にする
- 直近の反映。日時、前の版から今の版、結果、ホストの作業の残りを出す。ホストの作業は、帯の「直近の反映」と同じく、未解決の通知の件数で出す(`describeHostAction`)
- Consoleの取り込み。状態を出す。取り込んだ版と最後に確かめた時刻は、サイドバーの下部が示すので、このカードでは繰り返さない

取り込みの状態は、`console_fetcher`が書く`status.json`から、backendが判定する。
状態の語は、取り込み済み、取り込みに失敗、版を固定中のどれかで、知らない値は「不明な状態」にする。
判定が更新の停止のときは、語に「(古い記録)」を添える。
色は、判定が失敗なら失敗の色、更新が30分以上無いか版を固定していれば警告の色(30分は`FETCHER_STALE_MINUTES`と同じ値で、契約テストで一致を確かめる)、それ以外は成功の色にする。
状態を読めないときは、警告の色で「状態を読めません」と理由を出す。
失敗の分類と運用者の次の操作があれば、補足の行に出す。
ホストの作業の表示は、通知があれば「ホストの作業N件が残っています」、通知が全件読めて無ければ「ホストの作業は不要」にする。
通知を取得中のあいだは「確認中」と出す。通知を読めないときと、一覧が切れて確かめられないときだけ、反映の記録の印で代える。

### 更新履歴

更新履歴は、Software Factoryが自分を更新した反映の一覧である。
`console_query`の`deployments`viewから、直近90日のものを新しい順に100件まで取る。
自動では取り直さず、見出しの更新で取り直す。
最初は新しい3件だけを出し、「すべて表示」を押すと全件を開く。全件は10件ずつのページに分け、「新しい3件だけ表示」で戻る。
切り替えのボタンは1つで、3件のときも全件のときも、同じ位置の同じ要素である。ラベルと`aria-expanded`だけが替わる。押した後も、フォーカスがボタンに残るためである。ボタンは`aria-controls`で一覧を指す。
ホストの作業が残っているかは、この節では数えない。記録の印は、作業が済んでも残り、残っている作業の数にならないためである。残っている作業は、帯の「直近の反映」と、状態のタブの印が示す。
直近の反映は「反映の状態」の節にもあるので、更新履歴は過去の記録を読む場所である。

反映1回を1枚のカードにする。カードには、次を出す。

- 日時。相対時刻で、日本時間の絶対時刻をツールチップに添える
- 版。前の版と今の版を、7桁の短い形で「前 → 今」と書く。前の版が無い初回は「初回 → 今」にする
- 結果。「反映済み」か「失敗」で、知らない値は「不明な状態」にする
- ホストの作業の要否。要るときは警告の色にする
- 含まれるPR。作り手のバッジ、題名、番号を1行にする
- 失敗の理由。失敗した反映だけに、先頭の120字を「理由:」に続けて出す

失敗の理由は、外部のコマンドの出力を含みうる信頼できない文字列なので、文字としてだけ出し、リンクやマークアップにはしない。
理由を記録する前の失敗の反映には、「理由の記録はありません」と出す。

作り手のバッジは、「Software Factory」か「人」である。
backendが確かな情報(マージしたブランチの名前)を読めたときだけ付ける。読めなければ、バッジを付けない。読み手が判断に使えない印で、行を埋めるだけだからである。
含まれるPRが無い反映には、「含まれるPRの記録はありません」と出す。
PRを記録する前の反映と、PRを取り出せなかった反映も、同じ表示になる。区別できないのは、取り出せなかったときも空で記録するためである。
失敗した反映は、PRを取り出す前に止まるので、PRを持たない。空の配列で記録する。
記録するPRは1回の反映につき100件までなので、100件に達した反映には、これより古いPRは表示していない場合があると添える。件数がちょうど100のときも同じ注記になる。
題名は、GitHubのUIでマージしたコミットの本文の1行目である。別の形でマージしたコミットは、題名が空になるか、PRとして記録されない。

題名はコミットメッセージ由来の信頼できない文字列なので、Reactが文字として描く。マークアップとしては解釈しない。
番号は、GitHubのPRのURLの形で、末尾の番号がPRの番号と一致するときだけリンクにする。それ以外は文字で出す。
リンクは`rel="noopener noreferrer"`を付けて新しいタブで開く。
backendは、URLを`https://github.com/<owner>/<repo>/pull/<N>`の形に限り、題名の制御文字と書字方向の制御文字を空白にし、200字に切って返す。
画面は、同じ検査を`src/lib/updateHistory.ts`の純関数でやり直す。
表示する語は`src/lib/labels.ts`にある。

### workerの負荷

defaultのworkerの直近24時間の負荷を出す。
先頭に結論の1行を置き、内訳は「内訳を表示」で開く。
結論の1行は、枠が塞がっていた記録の件数、開始が遅れた記録の件数、メモリの最大の割合(`anon`の上限に対する割合。読めなければ「不明」)、記録の数を並べる。
どれも内訳にある値で、判定はしない。
値は`system_status`の`worker_load`で、`worker_samples`を1回のクエリで集計した数と時刻だけである。
外部の文字列は含まない。
内訳の行は次のとおりである。

- 枠の使用。最新の記録の実行中のジョブの数と、他のジョブが使える枠の数、窓の中の最大
- 枠が塞がっていた記録。他のジョブが枠をすべて使っていた記録の数と、`running_jobs`が読めた記録に対する割合。
  他のジョブの使える枠が無い記録は数えない
- queueの待ち。待ちの最大の秒数と、待つジョブの最大の数
- 開始が遅れた記録。`lag_seconds`が30秒以上の記録の数と、最大の遅れ
- メモリ。最新と最大の`anon`、working set、上限に対する割合
- `memory.current`と`memory.peak`。キャッシュを含み、`memory.current`は最新の瞬間値、`memory.peak`はコンテナの起動からの最大値で、どちらも逼迫の判断には使わない

「枠の使用」と「メモリ」の最新の行には、最新の記録の時刻をJSTで添える。
上限に対する割合は、窓の中の最大の行にだけある。
割合は、0%に丸まる正の値を小数1桁で出す。

窓に記録が無いときと、集計を読めなかったときは、`worker_load`が`null`になる。
2つを分けないのは、画面が出す次の操作が同じだからである。
画面は、記録がないか集計を読めなかった旨と、`sample_worker_load`のスケジュールと`console_query`のジョブログの警告を確かめる操作を出す。
集計の失敗は、`console_query`のジョブログに警告`could not read the worker load`として残る。

`worker_load`を返す前のbackendの応答では、項目が欠ける。
Consoleが先に配信されても画面が壊れないよう、欠けた値は記録なしと同じに扱う。
形が違う値は、システムの画面の型ガードでは確かめない。
カードが確かめ、形が違えば、カードだけを「表示できません」にする。
画面の他の節は消えない。

節の説明に、workerの一覧をここでは読めないことと、止まったときは通知で知らせることを添える。
workerの一覧が読めない根拠は、[workerの生死の取得](#workerの生死の取得)にある。

画面は閾値を持たない。
通知を出すのはメモリの割合とOOMの増加だけで、割合は`factory_config`の設定にある。
通知は要対応に出る([閾値の通知](../operations.md#閾値の通知))。
待ちと枠の塞がりは通知にせず、この画面と日次のまとめで見る。
「枠の使用」と「枠が塞がっていた記録」を塞がりの判断に使える条件は、[枠の占有](../operations.md#枠の占有)にある。
型は`src/api/guards/workerLoad.ts`で確かめる。

### 情報の通知

重要度が情報の通知は、人の行動が要らないので、要対応の一覧に出ない。
この節は、直近7日の未解決の情報の通知を、新しい順に出す。
行動が要らない通知は、失敗と通知のタブを短くするため、「一覧を表示(N件)」の折りたたみに入れる。件数は、たたんだ行に出す。通知が無いときは、たたまずに空の旨を出す。
監査の失敗は、失敗の本文を先に見せるため、折りたたまない。作業項目に紐づかない失敗は、flowごとの組を折りたたむ。
節へ移るときは、この節の折りたたみを開く。
行には、通知の種類の日本語名、発生の時刻、本文の最初の行を120文字まで出す。
本文は`displayableIssueText`を通し、プレーンテキストで描く。

行の「詳細」は、要対応の画面で同じ通知を選んだ経路(`/console/?notice=<id>`)へのリンクである。
詳細には、本文の全文、対象へのリンク、起きたことと次の操作が出る。
Consoleから解決できる種類の行は、「詳細と解決」と書く。解決は、その詳細で行う。
この節では、解決しない。同じ操作を2か所に置くと、取得の更新が食い違うためである。

### 解決済みの通知

解決した通知の履歴を出す。
履歴は参照用なので、「履歴を表示(N件)」の折りたたみに入れ、開くまで一覧を見せない。件数は、たたんだ行に出す。
人が解決したものを先に、DBの掃除が解決したものを後にし、それぞれ解決の新しい順に並べる。機械が片付けた大量の通知で、人の解決の履歴が押し出されないためである。
並べるのはbackendで、画面は返った順に描く。
行には、通知の種類の日本語名、解決の時刻、解決した主体、本文の最初の行を出す。行を開くと、本文と発生の時刻を読める。
本文は`system_status`が先頭の500文字で切るので、500文字に達した本文には、先頭だけを表示している旨を添える。
解決した主体は、DBの掃除、自己更新、Issueの取得、PRの取得なら処理の名前に「(自動)」を添える。それ以外は、記録された名前を文字のまま出す。記録が無ければ「記録なし」にする。
解決の時刻が記録されていない通知は、「解決の時刻の記録なし」と出す。
解決済みの通知は、解決から既定30日で消えるので、履歴もその間のものである。

### 監査の失敗

失敗した監査の一覧である。
再実行できない失敗なので、要対応の画面では再実行の対象にせず、件数のカードで知らせてこの節へ案内する。
データは、`summary`の失敗のうち、作業項目の種類が監査のものを使う。要対応の画面と同じ取得とキャッシュを共有する。
`summary`の定期の取り直しがあるので、この節も画面を開いている間に更新される。
`summary`の失敗は新しい順に上限まで取る。失敗の件数が取得した件数より多いときは、古い監査の失敗は表示していない場合があると添える。

行には、監査の題名(作業項目の詳細へのリンク)、状態、失敗の時刻、ジョブへのリンク、失敗の内容を出す。
内容は、実行の出力でIssueの文字を含みうるので、プレーンテキストで描く。500文字で切られているときは、切られている旨とジョブのログで全文を読める旨を添える。
再実行のボタンは置かない。次の監査が、失敗した期間を扱う。
内容は`src/lib/failureView.ts`の`describeFailure`を、要対応の失敗の詳細と共有する。

後の監査で報告済みの失敗は、一覧に残し、「後の監査で報告済み」の印を付ける。
印の文言は、期間の終わりまで確かめたとは言わない。比べるのは報告の開始だけだからである。
要対応の画面は、この失敗を件数から外す。履歴として読めるように、この節は全件を出す。
印は文言で示し、色だけに頼らない。
印は`summary`の失敗の`superseded`で決まる。古いbackendが送らないときは、印を付けない。

取得の上限を超えたときは、要対応のカードの件数とこの節の件数が食い違う。
カードは上限の前の全件から数え、この節は取得した新しい順の行だけを出すためである。
そのため、上限を超えた失敗があるときは、節に2つの注記を添える。
1つめは、古い監査の失敗を表示していない場合があること。
2つめは、要対応のカードの件数は表示していない分も数えるので、この節より多いことがあること。

### 作業項目に紐づかない失敗

定期のジョブなど、作業項目を持たないジョブの失敗を、直近7日の分だけ出す。
作業項目が無いので、要対応の画面にも作業項目の画面にも出ない。この節だけが知らせる。
同じflowの失敗が繰り返されるので、flowごとにまとめる。まとめるのはflowのパスで、ステップは分けない。
先頭に失敗の件数とflowの数を出す。
組は、flowのパス、失敗の回数、最新の失敗の時刻を持つ折りたたみで、最新の失敗が新しい順に並べる。
開くと、失敗を新しい順に1件ずつ、ステップ、失敗の時刻、ジョブへのリンク、失敗の内容を出す。
1つの組の失敗は、10件ずつのページに分ける。
ジョブへのリンクは、ジョブのIDがUUIDの形のときだけ張る。
内容の扱いは、監査の失敗と同じである。
再実行の操作は置かない。

表示する内容は、`src/lib/systemView.ts`の純関数が決める。

### 起動の関係

スケジュール、script、flow、人の操作が何を起動するかを、1枚の図に出す。
図は重く、普段は読まないので、「図を表示」の折りたたみに入れる。開いたときに初めて描画し、一度描いた後は閉じても残す。
データは`console/src/generated/flow-graph.json`で、`mise run docs:gen`が次の元から作る。
`scripts/docs-gen.ts --check`が古さを検出するので、CIの`check`が、データを更新し忘れたPRを止める。

- `scripts/launch-graph.ts`の起動辺の表。scriptがflowを起動する関係と、人の操作
- `f/factory/*.schedule.yaml`の実行先とcron。有効で、flowを起動するscriptかflowを実行するスケジュールだけを載せる
- `f/factory/*__flow/flow.yaml`の概要とモジュール。flowが実行するステップのうち、flowを起動するscriptだけを辺にする

ノードはスケジュール、script、flow、人の操作の4種類で、辺はスケジュールからの起動、scriptによるflowの起動、人の操作による起動、flowのステップの4種類である。
人の操作には、フォームからの実行と、新規投入、再実行、今すぐ監査、承認と却下のConsoleの操作がある。
並びは入力の順に依らず、同じ元から同じJSONができる。

JSONはViteがそのままバンドルに取り込む。
`src/lib/flowGraph.ts`の`parseFlowGraph`が形を確かめ、ノードのidの重複や存在しない辺の端があればnullを返す。
nullのときは、節に読み込めなかった旨を出し、図は描かない。
座標は`src/lib/flowGraphLayout.ts`の`layoutFlowGraph`が決める純関数である。
箱は3列に並べる。1列目はscriptを起動するスケジュールとConsoleの操作、2列目はscriptと、flowを直接起動するスケジュールと人の操作、3列目はflowである。
どの辺も隣り合う列を結ぶので、辺が他のノードの箱の上を通らない。
辺は直線で引く。同じ箱の同じ側につく辺は、つなぎ先の高さの順に、箱の高さを等分した位置へ割り当てる。多数の辺が列の間の1本の線に重ならないためである。
flowの箱は、名前に説明が続いて折り返すので、ほかの箱より高く取る。
図全体の大きさは、いちばん外側の箱に余白を足した値で、幅は1080pxになる。
ノードは図の目安の15個を超える。機械生成の全体の見取り図で、分割すると、起動の経路を1枚で追う目的を失うため、1枚にまとめる。

図は自前のSVGで描く(`src/screens/jobs/FlowGraphDiagram.tsx`)。
箱と辺の座標は上の純関数から取り、色はCSSのトークンだけで指定する。そのため、ライトとダークの両方で読める。
辺の線は、scriptがflowを起動する関係を実線、時刻や人の操作による起動を破線、flowのステップを点線にして見分ける。
箱の名前は、12pxで箱に収まらないときだけ11pxにする。文字の幅は、半角を0.55em、それ以外を1emとする見積もりである。
名前と補足は、サーバー由来の文字列と同じく`safeText`を通して描く。描画の経路を1つにそろえるためである。
flowの箱は、実行中のジョブがあればその詳細、無ければそのflowの履歴へのリンクである。
scheduleの箱はスケジュールのタブへのリンクで、scriptと人の操作の箱はリンクを持たない。
リンクはキーボードで届き、焦点は枠の太い線で示す。

図に出ない関係がある。scriptからscriptの起動は含まない。たとえば`self_update`が`auto_retry_stale_image`を起動する関係である。
そのため、入ってくる辺を持たないscriptも図に出る。節の説明にも同じ旨を書く。
無効のスケジュールは、図に載せない。

#### 実行の状態の重ね合わせ

図を表示すると、実行中と待ちの一覧(`console_jobs`の`active`)とscheduleの状態(`console_schedules`)を読み、図に重ねる。
どちらもジョブの画面と同じ取得で、キャッシュを分け合う。この節のために取得を増やさない。
取得は、「図を表示」を開いた後に始める。自動では取り直さず、見出しの更新で取り直す。

flowのジョブのパスは、`src/lib/flowOverlay.ts`の`flowNodeId`が、図のノードのidに直す。
`f/factory/<名前>`を`flow:<名前>`にする純関数で、図に載るflowの集合(`KNOWN_FLOW_PATHS`)の外のパスは無視する。
実行中と待ちの一覧には、ステップのscriptやConsoleの呼び出しも並ぶためである。
予定のジョブとフローのステップは数えない。

| 重ねるもの | 出し方 |
| --- | --- |
| 実行中のflow | 面と枠を強調し、三角の記号と「実行中」を添える。色だけに頼らない |
| 待ちのジョブ | 「待ちN」を添える。キューが1ページ(100件)で切れているときは、件数が下限なので「待ちN以上」にする |
| 定期の入口(動いているschedule) | scheduleの箱に、直近の実行の成否を「直近 成功」か「直近 失敗・取消」で、次回の予定を「次回 HH:MM」(日本時間)で添える。実行の記録や次回の予定が無いものは添えない |
| 定期の入口(止まっているschedule) | 「停止中」だけを添える。直近の実行が成功でも、動いていないので成功とは読ませない |

scheduleは、無効にされているか、一時停止の期限が未来のとき、止まっているとする。
どちらも、`console_schedules`がすでに返す項目(`enabled`、`paused_until`、`next_run_at`)から決める。
定期の入口には、最後に実行した時刻を添えない。scheduleの実行の記録が、成否と所要時間しか持たないためである。
失敗と取消(時間切れを含む)は、スケジュールのタブと同じく区別しない。

図の上には、実行中と待ちの要約を1行置く。
取得中は「取得中」、動いているflowが無ければ「いま動いているflowはありません」、あれば「実行中 N・待ち M」と出す。
強調が無いだけでは、読み込み前と、何も動いていない状態を見分けられないためである。
これは、一覧が空であることを明示する文にあたる。
キューが切れているときは、無いとは言えない。
「読めた範囲では、動いているflowはありません」と出し、待ちの件数に「以上」を付ける。
取得に失敗したときは、要約を出さず、下の注記が伝える。

キューが1ページで切れているときは、強調の無いflowも動いている場合がある。
そのため、「キューが切れているため、強調の無いflowも動いている場合があります」を節に出す。
scheduleの取得が全ページを読み切れていないときも、同じ理由で注記を出す。
文は「scheduleを読み切れていないため、添え書きの無い定期の入口があります」である。

実行中と待ちの取得が失敗したときは、強調と待ちの件数を外し、節の中に「実行の状態を読めませんでした」を出す。
強調が無いことを、動いていないと読ませないためである。前の値が残っていても重ねない。
scheduleの取得が失敗したときは、定期の入口の添え書きを外し、「定期の入口の直近の結果を読めませんでした」を別に出す。
取得中は、強調も失敗の表示も出さない。
一覧(640px未満)は、定期の入口を描かないので、scheduleに関する2つの注記(読めなかった、読み切れていない)は出さない。

scheduleの取得は、実行中と待ちの取得が終わってから始める。
Console用workerの枠が1つなので、2つを重ねない。

#### 図の幅

図の幅と、節の実際の幅(`useElementWidth`が測る)を比べて、見せ方を決める。
決める関数は`src/lib/flowGraphFit.ts`の`graphPresentation`である。
節は最大で1152px(`max-w-6xl`)まで広がる。

| 節の幅 | 見せ方 |
| --- | --- |
| 図の幅(1080px)とカードの分(18px)の合計以上 | 図をそのまま出す |
| 640px以上で、上の幅に満たない | 横にスクロールできる枠に入れる |
| 640px未満 | 図の代わりに、flowごとの一覧を出す |

図は、枠の1pxと余白の8pxを両側に持つカードの中に置く。
そのため、節の幅が図の幅と同じでも、図がカードからはみ出す。収まるのは、節の幅が1098px以上のときである。
枠は`role="region"`で名前を持ち、キーボードで焦点を受ける。隠れた部分を、キーボードだけで読めるようにするためである。
一覧は、flowの名前(リンク)と、実行中と待ちを語で示す。起動の関係の辺は出さない。
幅を測る前(0のとき)は、枠に入れて描く。測れた後に見せ方が変わるだけで、図が隠れない。
幅は、節の全体で測る。一覧のときは、矢印と定期の入口の説明を節の説明から外し、一覧が示す内容だけを書く。図が出ないのに、図の読み方を書かないためである。
サイドバーが幅を取るので、節の幅は画面の幅より狭い。
Chromiumで測ると、画面の幅が1600pxのとき節は1152px、1280pxのとき960px、1100pxのとき780px、950pxのとき630px、400pxのとき368pxだった。

### 設定

設定のタブは、`factory_config`の全項目を、キーと値の一覧で出す。
許可した項目だけ、止める向きか下げる向きに変えられる([設定の変更](#設定の変更))。
取得は`console_config`で、設定のタブを初めて開いたときに始める。
自動では取り直さない。見出しの更新のボタンは、タブを開いた後だけ、この取得も取り直す。
節の見出し「設定」は、タブの名前と重なるので、読み上げにだけ残す。

値は補間しない生の値で読んだものである。
参照(`$var:`か`$res:`を含む値)と、伏せた値は、値を出さず「参照(出さない)」と表示する。
文字列、数、真偽、`null`は、そのままテキストで出す。
配列とオブジェクトは、字下げしたJSONの文字列にして、折り返す`<pre>`に出す。
見えない文字と、並びの見た目を入れ替える文字は、代替文字に置き換える。

キー名の部分一致で絞り込める。大文字と小文字は区別せず、値は探さない。
表示する内容は`src/lib/jobsView.ts`の純関数が決め、部品は`src/screens/system/ConfigSection.tsx`にある。

#### 設定の変更

変更の候補を出すかは、`changeOfferOf`(`src/lib/configChange.ts`)が決める。
候補は、止める操作と、数値を下げる操作の2つである。

- 真偽の5項目は、値が`true`のときだけ、行に**止める**を出す。`false`のときは何も出さない
- 数値の5項目は、値が範囲に合い、下げる余地があるときだけ、**下げる**を出す。予算の2項目は0より大きい小数、ほかの3項目は1以上の整数である。整数の項目は、1つ下の整数が範囲に残るときだけである
- 参照と、伏せた値には出さない。値を読めないためである
- 表の外の項目には出さない

この表は画面が出す操作の絞り込みで、境界ではない。
`console_config_update`が同じ表で確かめ、画面の表との一致を`tests/scripts/console_config_update.test.ts`が固定する。

ボタンは確認のダイアログを開くだけで、scriptは呼ばない。
ダイアログ(`ConfigChangeDialog`)は、項目、現在の値、変更後の値を示し、効く時期と元に戻す方法を並べる。

- 変更は、次に設定を読む処理から効く
- 動いているフローも、以後の手順が設定を読むときから、新しい値で動く
- 元に戻すには、運用者がWindmillでリソースを編集するか、`wmill resource push`で戻す。Consoleからは戻せない
- `implement_enabled`だけ、止めている間に承認した要件定義が承認済みで止まり、要対応に載らないことと、有効に戻した後に人が再実行で再開することを足す
- `daily_budget_usd`だけ、今日の使用額を下回る値にすると、今日のClaudeを使うフローがすべて失敗し、Consoleからは引き上げられないことを足す。今日の使用額は調べない

数値の項目は、変更後の値を入力欄で受ける。
入力は`parseNewNumber`が読む。数字だけを受け、符号、指数、16進、全角の数字は受けない。
範囲に合わない値と、現在の値以上の値は、理由を欄の下に出し、確認のボタンを押せなくする。
欄が空の間は、理由を出さずに、確認のボタンだけを押せなくする。
この押せなさは、確認のダイアログの`confirmDisabled`で表す。実行中を表す`busy`とは別の指定である。
確認のボタンは、**止める**か**下げる**で、破壊的な色にする。
フォーカスは**取り消す**に置く(`ConfirmDialog`)。
**取り消す**ボタンとEscは、ダイアログを閉じるだけで、書き込みを呼ばない。
URLの値や画面の遷移からは、変更を起こさない。

書き込みの入力は`changeInputOf`が作る。
読んだ時の値は、候補を作ったときの値で、scriptが書く直前の値と突き合わせる。
呼び出しは、書き込みの共通のフック(`useWriteMutation`)に載せる。
ロックのキーは項目名で、実行中は同じ項目を操作できなくする。
変更の後は、設定の取得を読み直す。

結果は、画面の知らせ(トースト)に出す。

| 結果 | 知らせ |
| --- | --- |
| 変えた | 成功。止めた項目は「止めました」、下げた項目は前後の値を添えて「下げました」 |
| 書いたが、読み直した値が期待と違う | 警告。書き込みは済んでいることと、Windmillで確かめることを伝える |
| 断られた | 情報。理由を日本語の固定文で伝える。許可表の外の項目、範囲に合わない値、止める向きか下げる向きでない、参照がある、画面を開いた後に値が変わっていた、操作者を確認できない、記録を残せない、の7つである |
| 記録を残せなかった(`action_audit`が`failed`) | 警告。変更は済んでいることと、誰が変えたかはジョブのログで確かめることを伝える |

## 分析の画面

レポートの画面の分析のタブに、分析の区画を置く。
区画は部品`AnalyticsReports`で、画面の見出しと余白は持たない。
部品は、期間、期間を変える関数、3つの取得の結果を受け取り、描画だけを受け持つ。
Claudeの実行のコスト、承認の統計、リードタイムを、グラフと表で出す。
監査レポートと同じ画面のタブなので、期間と3つの取得はレポートの画面が持つ。

3つの数値は、`console_query`の`agent_cost_daily`、`approval_stats`、`lead_time`viewから、別々に取る。
集計の期間は直近7日、30日、90日から選び、初期値は30日である。
期間はキャッシュのキーに含めるので、切り替えている間に別の期間の値は出ない。
定期には取り直さない。
取得から60秒を過ぎた値は、タブに戻ったときと画面を開き直したときに取り直す。
分析の取得と期間は、レポートの画面が持つ。
見出しの更新のボタンは、監査の一覧と合わせた4つを取り直す。
行数の上限は2000件で、backendが受け付ける最大にしてある。
行数が上限に届いたときは、古い日が含まれていない可能性を区画に添える。

区画は、次の数値を出す。

- 日別コスト(USD)と日別の実行件数。段階とモデルをまとめた日ごとの合計で、費用が記録されていない行は0として足す
- 一発承認率。1回目の判断のうち承認の割合で、承認か却下の判断が1件も無いときは「データなし」にする
- 差し戻し分布。試行ごとの却下件数
- 状態別の平均リードタイムと件数。平均の長い順に並べ、状態は日本語にする

日別のグラフは、横軸に期間の全日を等間隔に並べる。
間隔を日数に比例させ、空いた日があることを読めるようにするためである。
実行の無い日は値0で、棒を描かない。0より大きい日は、最大との差が大きくても最小の高さを確保する。
題には「UTC」を添えて、表の見出しと日の基準をそろえる。
表は、実行のあった日だけを出す。
行数が上限に届いたときは、古い日が切れている。
取れた最古の日より前は0で補わず、最古の日そのものもグラフから外す。
最古の日は、段階とモデルの行が途中で切れて、合計が実際より小さい可能性があるためである。

日は、viewが日付で丸めた時刻をUTCのまま読む。
端末のタイムゾーンで読み替えると、日がずれるためである。
viewの日の丸めは、DBの接続のタイムゾーンで決まる。
開発環境のデータベースサーバーの既定のタイムゾーンはUTCである。
接続ごとに別のタイムゾーンを設定した場合は、日の丸めがずれる。
表の日付は`2026-10-08`の形、グラフの横軸は`10/8`の形で出す。

グラフは自前のSVGで描き、グラフのライブラリを使わない。
色は固定のクラスで決め、棒の座標だけを計算する。実行時の入力から色やstyleを作らないためである。
グラフは題だけを読み上げの対象にし、数値は必ず添える表で読ませる。
日のような連続する並びのグラフは、置かれた領域の幅を測って合わせる。文字の大きさは変えず、棒の間隔だけが広がる。
状態のような別々の項目のグラフは、項目が少なく、広げると棒が離れすぎるので、幅の上限を置く。
棒の上の値と横軸のラベルは、文字の幅の見積もりが1本分の幅に収まるときだけ出す。
幅は、半角を文字の大きさの0.6倍、それ以外を1倍として数える。
収まらないとき、日のような連続する並びは、横軸のラベルを間引く。
間引くときは最後の棒を基準にして、いちばん読みたい最新の日にラベルを残す。
ラベルが描画領域の端を越えるときは、その端に寄せて置き、はみ出して切れないようにする。
状態のような別々の項目は、間引くと棒が何か分からなくなるので、横軸のラベルを出さず、表で読ませる。
最大の棒の上には、値のラベルの置き場を残す。
座標、幅、ラベルの収まりは`src/lib/barChart.ts`、集計、日の補完、整形は`src/lib/analytics.ts`の純関数が決める。
期間の終わりは、端末の時計の日(UTC)にする。
期間の前後3日以内の日に行があるときは、その日まで範囲を広げて含める。端末の時計がbackendと少しずれても、行を捨てないためである。
それより遠い日は並べない。遠い日付の行が1件あるだけで、並べる日数が際限なく増えるのを防ぐためである。
グラフに渡す系列は、純関数`chartSeries`が表と別に作る。
数値の表は、スクロールする領域に名前を付けて、キーボードで焦点を当てられるようにする。

3つの区画は、取得中、失敗、空、値ありを区別して出す。
取得中は値がまだ無いので、空の表示を出さず、読み込み中の枠を出す。
失敗は、401を除いて区画の中に原因と再取得のボタンを出す。401は画面上部のバナーが知らせる。
再取得に失敗しても前回の値があるときは、空であっても、値を出したまま、古いことと「もう一度取得する」を添える。

3つのviewの型は、backendの同名の行に合わせてある。
`tests/scripts/console_analytics_contract.test.ts`が、backendの変換結果が型ガードを通ることと、日がUTCの日付として読めることを確かめる。

## 作業項目の画面

この画面は、進捗と要件定義の2つのタブを持つ。
最終更新と更新のボタンは、画面の見出しの右側に置く。
更新のボタンは、進捗と要件定義の取得を取り直す。
新規投入のボタンは、同じ見出しの右端に置く。
新規投入のボタンは、[新規投入の画面](#新規投入の画面)を開く。

### タブ

開くタブと本体の見せ方は、[タブ](#タブ)の規則に従う。
要件定義のタブの名前には、取得した件数を添える。
絞り込み、並び替え、ページ、要件定義の番号の絞り込みを、タブを往復しても保つ。
作業項目の詳細のタブは、本体が1つで、中身を切り替える。

### 進捗

進捗は、`console_query`の`pipeline`viewから、直近90日に更新された作業項目を新しい順に500件まで取る。
自動では取り直さず、見出しの更新で取り直す。
取得が500件に達したときは、古い行を取得できていない場合があると本体の先頭に添える。
取得の失敗は、表の位置に再試行のボタン付きで出す。ログイン切れ(401)は、上のバナーが知らせる。

要対応の画面への案内は、本体に置かない。サイドバーの要対応のバッジが、同じ件数を出すためである。
失敗や人の対応待ちの作業項目は、進行中に含めず、要対応の画面で扱う。

### 表示する範囲

表に出す範囲は、状態の絞り込みとは別の欄で持ち、切り替えで選ぶ。既定は進行中である。
範囲はURLの`?scope=`に持つ。値は`pr_open`(PR待ち)と`all`(すべて)で、既定の進行中は付けない。
不正な値は進行中にする。
`?tab=`と同じく、選び直しても履歴を積まず、他のクエリを残す。
パンくずや戻る操作で作業項目の画面へ戻ったときに、選んだ範囲が保たれるためである。

| 範囲 | 出す行 |
| --- | --- |
| 進行中 | 終端でない状態の行と、`blocked`と`approved`の行 |
| PR待ち | 状態が`pr_open`の行 |
| すべて | 取得したすべての行 |

終端の状態は、backendの`TERMINAL_WORK_ITEM_STATUSES`と同じ一覧を`src/lib/pipelineView.ts`に持つ。
一致は`tests/scripts/console_pipeline_contract.test.ts`が確かめる。
終端のうち、失敗、人の対応待ち、期限切れは要対応に載るので、進行中に含めない。
`blocked`は要対応に載らず、ここでしか見えないので、進行中に含める。
`approved`は、実装を有効にしていない間、承認された要件定義が次の工程へ進まずに残る状態である。要対応とPR待ちのどちらにも出ないので、進行中に含める。
backendが先に足した知らない状態は、終端でないものとして進行中に含める。
PR待ちは、PRを作った後の状態を指す。一覧の行にマージ済みかどうかの情報が無いので、マージ待ちの目安であると画面に断る。

状態の選択肢は、範囲で絞った後の行から作る。
選んだ状態が範囲の外になる選び方をしたときは、範囲を「すべて」に替える。範囲の外の状態で絞ると、行が出ないためである。
再読み込みで範囲の中の行から状態が消えたときは、状態の選択を「すべて」に戻す。範囲は照合せず、そのまま引き継ぐ。
サイドバーやパンくずからの遷移で、URLの範囲が替わったときも、新しい範囲の外になった状態の選択を外し、先頭のページへ戻る。
「条件を消す」は、状態、リポジトリ、検索を消し、範囲は変えない。範囲は条件でなく表の見方だからである。
範囲だけが既定と違うときは、絞り込みが効いているものとして数えない。

進行中の行が0件で、取得した行があるときは、「進行中の作業項目はありません」と「すべて(N件)を表示」のボタンを出す。
空の画面だけを見せると、行があるのに無いと読めるためである。
PR待ちが0件のときも、同じ形で出す。
取得が上限に達しているときは、古い進行中の作業項目が表に出ていない場合があると、空の文に添える。
取得は新しい順に上限まで読み、範囲で絞るのはその後なので、取得できなかった古い行に進行中のものが含まれうるためである。

範囲の中に行があり、絞り込みの結果が0件のときは、「条件に合う作業項目はありません」を出す。
範囲の外に条件へ当たる行があるときは、「すべてで探す(N件)」のボタンを添える。
進行中の範囲で探した語が、終わった作業項目にだけ当たることがあるためである。
Nは、範囲の外にある、状態、リポジトリ、検索の条件に当たる行の数である。

リポジトリが1つだけのときは、表とカードのリポジトリ名と、リポジトリの絞り込みを出さない。全行で同じ名前が並ぶだけだからである。
2つ以上あるときに出す。リポジトリの選択肢は、範囲に関わらず取得した全行から作る。
リポジトリの列が無いときは、リポジトリで並べた状態を既定の並び(更新が新しい順)に戻す。列が無いと見出しを押せず、並びを戻す手段が見えないためである。

表は1行が1つの作業項目で、次の列を持つ。

| 列 | 内容 |
| --- | --- |
| 作業項目 | 番号。作業項目の詳細へのリンク |
| 題名 | Issueの題名。無ければ「-」 |
| 種別 | Issue、PRレビュー、PRの修正、監査、dependabotの更新 |
| 状態 | 日本語の名前のバッジ。知らない状態は「不明な状態(生の値)」と書く。色は承認待ちが警告、完了に近いものが成功、失敗と人の対応待ちが失敗、それ以外は枠の無い灰色 |
| リポジトリ | owner/repo。リポジトリが2つ以上のときだけ出す |
| Issue/PR | IssueとPRへのGitHubのリンク。両方あるときは縦に並べる |
| ブランチ | 実装用のブランチ |
| 試行 | 要件定義の試行の番号。却下や再実行による作り直しで増える |
| 修正回数 | PRの修正のラウンド数 |
| 更新 | 相対時刻。日本時間の絶対時刻をツールチップに添える |
| 書類 | 要件定義書へのリンク。Issueの作業項目だけに出す |

色だけに頼らず、状態の名前を隣に出す。

題名の列には最小幅を与え、1行に数文字で折り返して行が縦に伸びるのを防ぐ。
最小幅は、表のセルでなくセルの中身に与える。表のセルへの最小幅は、効き方が仕様で定まっていないためである。
ブランチの列にも最小幅を与え、列が戻った直後に文字が何行にも折り返すのを防ぐ。
表を包む領域が88rem(1408px)に満たないときは、ブランチ、試行、修正回数の列を隠し、題名、状態、更新を先に確保する。
全列を出したときの表の最小幅は、実測で約87.5remだった。測った条件は、実データでリポジトリ名が約20文字である。88remは、これに余裕を足した値である。
閾値が実測より低いと、列が戻った直後に横スクロールが出る。リポジトリ名がさらに長いと、88remでも横スクロールになることがある。
幅は画面でなく領域で測る。サイドバーを開閉すると表の使える幅が変わるためである。
本文の幅は、画面が1920pxでサイドバーが開いているとき約1598px(約99.9rem)で、全列を出す。
画面が1440pxのときは、サイドバーが開いていても畳んでいても本文が88remに満たず、3列を隠す。
隠した列も検索の対象に残る。ブランチの語で絞り込むと、列が見えなくても当たる行が残る。
隠れた列の見出しは押せないが、その列で並べた順は残る。
灰色のバッジは、枠を持たず、主の文字色を薄く重ねた地に主の文字色を載せる。

絞り込みは、状態、リポジトリ、検索の3つで、範囲の中の行から、すべてに当たる行を残す。
状態とリポジトリの選択肢は、取得した行にあるものだけを並べる。状態は作業の進む順、リポジトリは名前順である。状態の選択肢も、バッジと同じ表記にする。
検索は、空白で区切った語がすべて当たる行を残し、大文字小文字を区別しない。
対象は、番号、題名、ブランチ、リポジトリ、IssueとPRの番号、状態と種別の日本語名である。
件数は、範囲に入る絞り込み後の行の数で、取得した件数と違うときは全体の件数を添える。
絞り込みが1つでも効いているときは、「条件を消す」ボタンを出す。

並び替えは、番号、状態、リポジトリ、試行、修正回数、更新の見出しを押して行う。
既定は、更新が新しい順である。
同じ列をもう一度押すと向きを反転し、別の列を押すと、数と時刻は大きい方から、状態とリポジトリは先頭から始める。
状態は作業の進む順に並べる。知らない状態は、向きを変えても最後に置く。
並びが同じ行は、番号が大きい方を先にする。向きを反転しても、同点の順は変わらない。
選んだ状態やリポジトリが再読み込みで表から消えたときは、その条件だけを「すべて」に戻す。
範囲だけをURLに持つ。状態、リポジトリ、検索、並び替えは画面の中だけに持ち、URLには持たない。

題名とブランチは信頼できない文字列なので、見えない文字と書字方向の制御文字を落としてから、文字として描く。
リンクは、GitHubのIssueかPRのURLの形のときだけ張る。
IssueのURLが壊れているときは、Issueのリンクだけを出さず、PRのリンクは残す。
絞り込み、並び替え、リンクの規則は`src/lib/pipelineView.ts`の純関数にある。

行の番号は`/console/items/:id`へ、「要件定義」は`/console/items/:id/requirements`へ移る。

進捗の節の幅が狭いとき(56rem未満)は、横にスクロールする表の代わりに、1件を1枚のカードで出す。
画面の幅ではなく節の幅で切り替えるのは、サイドバーが幅を取る分を数えるためである。
カードに出すのは、番号、題名、状態、種別、リポジトリ(2つ以上あるとき)、Issue/PR、PR、更新、要件定義へのリンクである。
ブランチと回数は、詳細の画面で読めるので出さない。
絞り込みは表と同じ操作で行う。
並びは表の並び替えによらず、常に更新が新しい順にする。カードには並び替えの操作を置かない。

絞り込んだ行は25件ずつのページに分け、表とカードは同じページ番号を共有する([ページ送り](#ページ送り))。
表のページは選んだ並びで区切る。
カードのページは、表の並びによらず、更新が新しい順に並べた行を同じページ番号で区切る。
表を状態の順に並べ替えても、カードの1ページ目は更新が新しい順の先頭の25件である。
範囲、状態、リポジトリ、検索の文字、並び替えのどれを変えても、先頭のページへ戻る。
ページ送りは表とカードの外側に1つ置く。
「N件(全M件)」は、ページに分ける前の絞り込み後の件数と、取得した件数を指す。
取得は500件までで、ページ送りはこの500件を分けるだけである。

## 作業項目の詳細の画面

作業項目1件の概要と履歴を、読み取り専用で出す。
再実行や承認などの書き込みは置かない。止まった作業項目の再実行は、要対応の画面で行う。
要対応の失敗の詳細と、進捗の表の行の番号から、この画面へ移る。

取得は`console_query`の`work_item_detail`で、作業項目の番号を渡す。
応答は`src/api/guards/workItemDetail.ts`の型ガードを通す。
形が崩れた応答は、一部だけを使わず、全体を`invalid_response`にする。
backendの型との一致は、`tests/scripts/console_item_detail_contract.test.ts`が確かめる。
自動では取り直さず、キャッシュは30秒で古くなる。
見出しの更新で取り直す。

存在しない作業項目の番号は、backendが「作業項目が無い」という文のジョブの失敗で返す。
Consoleは、接頭辞(`console_query:`)と要求した番号まで合わせてその文を見分け、取得の失敗ではなく「見つかりませんでした」を出す。
実機のWindmillが返す失敗の本文がこの文のままかは、確かめていない。違えば、汎用の取得失敗の表示になる。
番号が正の整数でないときは、取得せずにその旨を出す。

### タブ

開くタブはURLの`?tab=<名前>`に持つ。名前が無いか知らない名前なら、概要を開く。
名前は、概要が`overview`、要件定義が`requirements`、ラウンドが`rounds`、承認の履歴が`approvals`である。
タブは矢印キーとHome、Endで移れる。Alt、Ctrl、Metaを押している間は、ブラウザの操作を奪わないよう移らない。

| タブ | 内容 |
| --- | --- |
| 概要 | 状態と注記、リポジトリ、IssueとPRへのリンク、ブランチ、試行、修正回数、実行の費用、作成と更新の時刻。続けて失敗の記録と状態の遷移。種別は見出しの副題が示すので、行には置かない。タブの名前と重なる見出しは置かない |
| 要件定義 | 試行ごとの要約、承認の状態、要件定義書の画面へのリンク。Issue以外の作業項目には要件定義が無いと伝える |
| ラウンド | 実装のラウンドを試行ごとに古い順で、PRのレビューとPRの修正を新しい順で並べる。レビューと修正が無いときは、見出しと一文の1行にする |
| 承認の履歴 | 承認依頼を新しい順に並べ、状態、依頼と決定の時刻、決定者、理由を出す |

承認の履歴は、却下の理由と決定者を読む場所である。
要件定義の承認依頼は対象の試行を、Issue提案は提案の題名を添える。
理由や決定者が記録されていないときは、そう書く。

失敗の記録は、フローとステップ、時刻、失敗の文を新しい順に出す。
失敗の文はbackendが4000文字で切るので、その長さに達したときは切っていると添える。
状態の遷移は、遷移前後の状態、注記、時刻を新しい順に出す。
要件定義書へのリンクは、同じ書類を指すものが重ならないよう、試行ごとに1つだけ置く。
最新の試行のリンクは試行の番号を付けず、常に最新の書類を指す。
実装のラウンドは、差分の規模をファイル数、追加の行数、削除の行数の言葉で出す。
ラウンドのタブは、PRのレビューと修正の本文を持たず、件数と結果だけを出す。
実装のラウンドは、検査コマンドの出力を持たない。

backendは、履歴を新しい順に切って返す。上限は、失敗が20件、状態の遷移が100件、PRのレビューと修正がそれぞれ50件である。
件数が上限に届いた履歴には、新しい順に何件まで表示していて、それより古い記録は表示していないと添える。
上限の値は`src/lib/itemDetailView.ts`の`DETAIL_LIMITS`にあり、`console_query`の上限に合わせる。

### ジョブのリンク

失敗と遷移のジョブは、`JobLink`でConsoleのジョブの詳細へ移る。意味が違うので、文言を分ける。

| 行 | `job_id`のリンク | `root_job_id`のリンク |
| --- | --- | --- |
| 状態の遷移 | ステップのジョブ(遷移を起こしたステップ) | フローのジョブ(そのステップを含むフローのルート) |
| 失敗の記録 | 失敗したジョブ(記録に渡されたジョブ。フローの失敗ではフローのルート) | 記録したジョブのフロー(記録したジョブのルート) |

2つが同じジョブなら、リンクは1つにする。
Windmillの画面への副次のリンクは、ジョブの詳細の画面が持つ。

### 表示の規則

題名、ブランチ、状態の注記、要約、却下の理由、決定者、失敗の文は、起票者や実行ログに由来する。
見えない文字と書字方向の制御文字を置き換えてから、プレーンテキストとして描く。
状態の注記が、その作業項目のIssueかPRのURLだけのときは出さない。同じリンクが「Issue」「PR」の行にあるためである。
別のURLだけの注記は、どの行にも出ていないので残す。
状態の遷移の注記は、URLだけでも出す。PRを作り直したとき、古いPRを示す唯一の記録になるためである。
実装のラウンドの要約と、要件の不足の報告は、バッククォートで囲んだ範囲をコードの書式で描く。
Markdownは解析せず、囲み以外の文字は記号も含めてそのまま出す。HTMLとして読む経路が無いためである。
二重のバッククォートの囲みは扱わず、記号の位置がずれることはあっても文字は失われない。
GitHubのリンクは、IssueかPRのURLの形のときだけ張る。形が違えば、番号だけを文字で出す。
PRのURLが使えないときは、リポジトリとPRの番号から組み立てた同じ形のURLを使う。
作業項目の状態、ラウンドの種類と結果、レビューの判定、修正の結果が表に無いときは、「不明」に生の値を添える。
承認依頼の状態など、ほかの値は「不明な状態」などの決まった文言にする。
知らない値でも詳細の全体が消えないようにして、backendが先に新しい値を反映した間も読めるようにするためである。
表示の規則は`src/lib/itemDetailView.ts`の純関数にある。

## 新規投入の画面

作業項目の一覧の見出しの右端にある「新規投入」のボタンから、`/items/new`を開く。
画面は、Issueを手動で作って工程に乗せる入力欄を持つ。
入力欄は、リポジトリ、題名、目的、受入基準(任意)である。
リポジトリは、候補から選ぶか、`オーナー名/リポジトリ名`の形で直接入力する。

候補は、`console_query`の`intake_targets`viewから、画面を開いたときに取る。
viewは、設定の`configuredRepos`(`factory_repo`と`repo_allowlist`)を`isRepoAllowed`で絞り、`{owner, repo}`の配列だけを返す。
`configuredRepos`は`owners`で絞らないので、選ぶと必ず断られる候補を出さないよう、ここで絞る。
設定の他の値は返さない。
DBは読まない。
候補を取得できなかったときも、リポジトリは直接入力できる。

送る前に分かる誤り(リポジトリの形、題名が空か256字を超える、目的が空)は、`src/lib/manualIntake.ts`が入力欄で知らせる。
検証の本体は`manual_intake_submit`にあり、画面の判定はそれを置き換えない。

### 書き込み

`manual_intake_submit`は、tag`console`で動き、`timeout`は30秒である。
フローを非同期に起動するだけで、完了は待たない。

| 項目 | 内容 |
| --- | --- |
| 引数 | `owner`、`repo`、`title`、`body`(目的)、`acceptance_criteria`(省略時は空) |
| 戻り値 | 断ったときは`{ refused: true, reason }`、起動したときは`{ refused: false, flow_job_id }` |

断りは、失敗ではなく結果として返す。
その場合、フローは起動せず、Issueと作業項目は作られない。
理由は固定の符号で、入力の文字列を含まない。
符号の一覧は、`f/factory/lib/manual_intake_support.ts`の`MANUAL_INTAKE_REFUSAL_REASONS`にある。
日本語の固定文は、`src/lib/intakeRefusal.ts`の表にある。
文の末尾に、何も投入していないことを添える。

投入した人は引数に取らない。
scriptが、ジョブの実行文脈から導く。
導けなければ`actor_unknown`で断る。
フローは呼び出した主体の権限で起動する。
Issueの作成、オーナーIDの照合、作業項目の登録、要件定義の工程の起動は、フロー`manual_intake`が行う。
作業項目は、登録のあとに一覧へ現れる。
投入の結果には、戻りの投入のフローのジョブのid(`flow_job_id`)から、Consoleのジョブの詳細へのリンク(「投入のジョブを開く」)を添える。
投入が通ったかは、作業項目が一覧に現れるまで分からないので、このリンクでフローが動いたか、失敗したかを読める。
ジョブのidを持たない結果(断り、ジョブが動く前の失敗)には、リンクを出さない。

### 結果が分からないとき

次の失敗は、投入されたか分からないものとして扱う。
`network`、`timeout_or_unknown`、`job_failed`、`invalid_response`と、5xxの`http`である。
フローを起動した後に、応答だけが失われている場合があるためである。
401、403、4xxは、ジョブが動く前に断られたので、投入されていないものとして扱う。

分からないときは、入力を残し、送信を止める。
画面は、確かめる場所を案内する。
確かめる場所は、Windmillのジョブ一覧(`manual_intake_submit`が待ちか実行中でないかも含む)と、対象リポジトリのIssueである。
送った題名も添える。
操作は2つある。

- 「確かめたので再送する」は、投入されていないことを確かめたあとに押して、送信を開ける
- 「投入されていたので入力を破棄する」は、投入されていたと分かったときに押して、警告と保存した入力を消し、送信を開ける

再送を明示の操作にするのは、確かめずに送ると、Issue、作業項目、pipelineが重複するためである。

### タブ全体の状態

送信の結果と入力欄の値は、画面の部品ではなく、タブ全体で持つ状態(`intakeSession`、`src/api/intakeSession.ts`)に書く。
送信中に一覧へ移って戻っても、結果と入力を失わず、戻った画面が警告を出す。

状態は、このタブの中だけで持つ。
`sessionStorage`にも書かないので、リロードや別のタブには広がらない。
別のタブや、リロードの後の二重の送信は止められない。

結果を画面が見せたあと、その画面を離れるときに、結果を消す。
消すのは、画面が実際に描画した結果だけである。
対象は、投入できた結果、断られた結果、ジョブが動く前に断られた結果である。
次の結果は消さない。

- 画面がまだ見せていない結果は、戻った画面で見せる
- 投入されたか分からない結果は、利用者が片付けるまで残す
- 書き込みのロックが残っているあいだの結果

投入できたときは、保存した入力を消し、題名、目的、受入基準を空にする。
リポジトリは残す。
続けて同じ宛先に投入することが多いためである。
投入の後は、作業項目の進捗(`pipeline`view)を読み直す。

## ジョブの画面

この画面は、Factoryのジョブを読む。
実行中と待ち、履歴、スケジュールの3つのタブを持つ。
タブは読み取りだけで、操作は置かない。操作は、ジョブの詳細に置く([ジョブの中止](#ジョブの中止)、[失敗した定期ジョブの再実行](#失敗した定期ジョブの再実行))。
取得するscriptは、「ジョブ、schedule、設定の読み取り」の節にある3つである。
開くタブと本体の見せ方は、[タブ](#タブ)の規則に従う。

### 取得の方針

どの一覧も自動で取り直さない。
Console用workerの枠が1つで、一覧の取得が承認などの呼び出しを待たせるためである。
例外は、実行中と待ちのタブの行に添える今のステップで、[今のステップ](#今のステップ)にある。
取得は、タブを初めて開いたときに始める。開いていないタブの取得は走らせない。
見出しの更新のボタンは、今開いているタブの取得だけを取り直す。
サイドバーの入口の先読みは、実行中と待ちの一覧だけで、押した瞬間にだけ走る。
スケジュールの凍結の突き合わせに使う保留と凍結(`console_holds`)も、定期の取り直しと、フォーカスと再接続での取り直しをしない。
一覧の取得も、フォーカスと再接続では取り直さない。
各タブの先頭には、「自動では更新しません」の案内を置かない。
自動で更新しないことは、見出しの最終更新と、自動更新の間隔の有無が示す。

### 実行中と待ち

いま動いているジョブと、workerを待っているジョブを、状態、scriptの名前(詳細へのリンク)、時刻、所要時間の行で並べる。
これから始まる予定のジョブは並べない。
予定かどうかは、`console_jobs`が返す状態の値をそのまま使う。
予定の次回は、スケジュールのタブにも出る。ここに並べると、同じ情報が2か所になるためである。
予定を並べる切り替えも置かない。切り替えると、次回が両方のタブに出て、重複が戻るためである。
タブの名前の件数も、予定を除いた数である。
tag`console`のジョブ(Consoleの呼び出し自身)も出ない。
除外の注記は、どのタブの先頭にも置かない。
スケジュールのタブは隣にあり、tag`console`の除外は[運用の手引き](../operations.md)に書いてあるためである。
一覧が空のときは、「いま実行中・待ちのジョブはありません」と明示する。予定のジョブだけのときも同じである。
キューの1ページ(100件)に達したときは、全件を読めていないと伝え、タブの名前の件数に「以上」の印を付ける。
このとき一覧が空なら、「読めた範囲では、実行中・待ちのジョブはありません」と書く。ページの外に、動いているジョブがありうるためである。

状態は、記号と語を並べて示し、色だけに頼らない。
記号は、成功が丸のチェック、失敗が丸のバツ、実行中が回る円、待ちが時計、予定がカレンダー、取消が禁止の印である。
Windmillは、時間切れで止めたジョブを失敗でなく取消にするので、取消は「取消・時間切れ」と書く。
実行中の記号は、動きを減らす設定のときは回さない。
知らない状態は、生の値を添えて「不明」にする。

#### 残る制限

予定のジョブは、scheduleに由来するかどうかを見ずに、すべて実行中と待ちのタブから外す。
scheduleに由来しない予定は、どのタブにも出なくなる。
Windmillの画面で「あとで実行」にしたジョブと、再試行の待ちが当たる。
スケジュールのタブは、scheduleの次回だけを出すためである。
該当のジョブは、Windmillのジョブ一覧で確かめる。

### 今のステップ

実行中のflowの行に、今のステップを1行で添える。
詰まりを見分けるためで、全ステップは、ジョブの詳細のステップの一覧で読む。
今のステップは、実行中のステップ、無ければ最初に待っているステップ、すべて終わっていれば最後のステップである。
状態の語は、ジョブの詳細のステップの一覧と同じ関数(`stepStateInfo`)で決め、条件で飛ばしたステップは「スキップ」と示す。
取得に失敗した行には、「今のステップを読めませんでした」を出す。

対象は、実行中のflowのルートを開始の古い順に並べた先頭の2件である。
待ちのflowはまだステップを持たないので、対象にしない。3件目以降の行には、ステップを出さない。
取得は、`console_jobs`の`detail`を、`include_output`を偽にして1件ずつ直列に読む。
Console用workerの枠が1つなので、2件を重ねない。

次の3つがそろうあいだだけ、30秒ごとに取り直す。

- 選んでいるタブが実行中と待ちである
- 文書が見えている
- 画面が15分以内に操作された(ポインタ、キー、ホイール、タッチ)

操作が15分途切れたら止め、次の操作で再開する。
取得のたびにWindmillのジョブができるので、開いたままの画面が取得を続けないためである。
フォーカスと再接続では取り直さない。

状態は、詳細の値を、一覧の値より優先する。
一覧は自動で取り直さないので、終わったジョブを実行中のまま見せないためである。
詳細が終了を返したジョブがあれば、購読のある取得だけを1回取り直す。
実行中と待ち、履歴、scheduleの一覧が当たる。開いていないタブの取得は、古いと印を付けるだけで走らせない。
取り直しは、実行中と待ち、scheduleの直近の実行、履歴の順に、1つずつ行う。Console用workerの枠が1つなので、重ねない。
詳細が見つからなくなったジョブも、一覧を取り直す契機に数える。一覧から消えているはずなので、一覧を合わせる必要があるためである。
同じ周期に複数のジョブが終わっても、取り直しは1回にまとめる。
見出しの更新のボタンは、一覧を取ってから、今のステップを取る。2つの取得を重ねないためである。
一覧を取り直すと読むジョブが変わりうるので、ステップの取得には、取り直した一覧のジョブを渡す。古いジョブを読み直さない。
詳細の取得が失敗したジョブは、その行にだけ「今のステップを読めませんでした」を出し、次のジョブを読む。時間切れ(`timeout_or_unknown`)でも、残りのジョブを読む。

### 履歴

完了したジョブを新しい順に、1回50件ずつ読む。
状態(すべて、成功、失敗、取消・時間切れ)とscriptで絞り込む。絞り込みはURLの`?status=`と`?script=`に持つ。
時間切れで止められたジョブは、失敗でなく取消に入る。選択肢の名前は、このためである。

scriptの値は、履歴の絞り込みの集合(`HISTORY_FILTER_PATHS`)と照合し、知らない値は無視する。
URLから来る値なので、サーバーへ渡す前に画面でも確かめる。サーバーは、既知のscriptとフローの全体で照合する。
画面の集合は、選んでも常に0件になるものを除く。
除くのは、フローのステップ(`f/factory/steps/`)、失敗ハンドラ(`on_error_flow`)、tag`console`のscriptである。
承認のハンドラ(`steps/requirements_apply`、`steps/issue_proposal_apply`)は、ステップの置き場にあるが、履歴に出るので集合に入れる。
集合は`f/factory/lib/console_known_paths.ts`の定数で、Consoleはこのファイルを直接importする。
開発サーバー(`bun run --cwd console dev`)でも、このimportは配信される。
定数は定義から生成するので、画面とサーバーで食い違わない。
tagは、各scriptの`.script.yaml`から導く。

「さらに読み込む」で続きを足し、累積200件で止まる。止まったときは、絞り込みを変えて探すよう伝える。
カーソルは画面が組み立てず、サーバーが返す`next_before`をそのまま使う。
絞り込みを変えると、先頭のページから読み直す。
更新のボタンは、先頭のページから読み直し、2ページ目以降のキャッシュを捨てる。
先頭が新しくなった後に、古いカーソルの続きを混ぜないためである。
2ページ目以降の取得に失敗しても、読み込み済みの行は残し、続きの取得の失敗だけを伝える。

### スケジュール

Windmillのscheduleを、名前、有効かどうか、cron、次回の予定、直近の実行の順に並べる。
直近の実行は、新しい順に最大3件で、成功か「失敗・取消」、所要時間、ジョブの詳細へのリンクを出す。
scheduleの実行の記録は、成功かどうかしか持たないので、失敗と取消(時間切れを含む)を区別できない。
`paused_until`が未来のときは、「一時停止中(期限まで)」の印を付ける。期限を過ぎたものと、無いものには付けない。
リポジトリの定義と違う項目があれば、項目の名前を添える。
リポジトリにあってWindmillに無いscheduleは、一覧の上に挙げる。
ページの上限に達したときは、全件を読めていないと伝える。

凍結は、保留と凍結の取得(`console_holds`)の結果と突き合わせる。
期限内の凍結がかかっているscheduleへ、「凍結中」の印を付ける。
凍結を読めなかったときは、凍結が無いとは言わず、読めなかったと伝える。
`console_holds`は、この画面では定期に取り直さず、スケジュールのタブの更新で取り直す。

#### スケジュールを止める

止められるスケジュールの行には、段階に応じたボタンを出す。
止められるスケジュールは、`console_schedule_stop`の許可表にある7本である。
止められるのは、止めて黙るのがそのスケジュール自身の仕事だけで、ほかのスケジュールの入力や検知を止めず、再開を自己更新の追従へ任せられるものだけである。
基準の詳細は、[凍結とdeployの保留の内部仕様](freezes.md)の「Consoleからの止める操作」にある。
それ以外の行には、何も出さない。

| 段階 | 出すもの |
| --- | --- |
| 凍結が無い | 「止める準備」 |
| 凍結を置いて7分が過ぎていない | 押せない「止める」と、押せるようになる時刻 |
| 凍結を置いて7分が過ぎた | 押せる「止める」 |
| 止めた(無効で、人の凍結の下にある) | 「凍結を解除して戻す」 |
| 凍結を読めない、ローカルのセッションが置いた凍結、無効で凍結が無い | 何も出さない |
| 凍結が、止められる前に、または止める時点で残りが5分を割るほど早く終わる | 何も出さない |

「止める準備」は、そのスケジュールの凍結を置く。
凍結の期限と理由は、置くダイアログと同じ入力欄で決める。
対象は固定し、期限の初期値は60分、上限は1440分、下限は12分である。
下限は、止められるまでの待ち(7分)と、止める時点で残っていなければならない分(5分)の和である。
下限より短い凍結は、止められる前に終わってしまうため、確認のボタンを押せなくする。
凍結の目的は、自己更新の追従がスケジュールを有効に戻さないようにすることである。
置く前に始まった自己更新の反映は、最大で約7分続くので、7分待ってから止められる。
人の端末のpushには時間の上限が無く、この待ちの対象外である。

「止める」を押すと、確認のダイアログを開く。
ダイアログは、止めたときの影響と、有効に戻る時期を出す。
有効なdeployの保留があれば(取得済みの保留の一覧から判断する)、追従も待つので、凍結が終わっても、解除しても戻らない旨も出す。
確認のボタンは破壊的な色にする。
Consoleは有効に戻せず、凍結が終わった後の自己更新の追従で、スケジュールがリポジトリの定義へ戻るためである。
影響の文は、止められるスケジュールごとに`src/lib/holdPlace.ts`が持つ。

確認すると`console_schedule_stop`を呼ぶ。
scriptは、画面の段階を信用せず、同じ条件を確かめ直してから止める。
条件を満たさなければ、理由を付けて断る。
断りの理由は`writeNotices.ts`の対応表にある。
早すぎる断りは、止められるようになる時刻を添える。
凍結の期限まで残りが5分を割っていれば、断る。
止めた後は、スケジュールと凍結を読み直す。
スケジュールが無効になっていなければ、止めたと言い切らず、Windmillで確かめるよう伝える。
止めたときの凍結が先に終わった可能性があれば(凍結を読み直せなかったときを含む)、警告の色で、追従では戻らないことがあるので、Windmillでスケジュールを有効に戻すよう伝える。

止めた行の「凍結を解除して戻す」は、確認のダイアログを通して、既存の凍結の解除(`f/factory/freeze_release`)を呼ぶ。
新しい書き込み口は足さない。
確認のボタンは破壊的な色にしない。
解除は止めが外れる向きで、期限でも必ず終わるためである。
ダイアログは、次の自己更新の追従で戻る旨と、有効なdeployの保留があれば、戻らない旨を出す。
結果の知らせは、システムの画面の解除と同じである。

## ジョブの詳細の画面

`/console/jobs/:id`は、ジョブ1件を出す。
IDがUUIDの形でないときと、サーバーが見つからないと返したときは、同じ「ジョブが見つかりません」を出す。
文は「保持期間(30日)を過ぎたか、IDが違います」と、考えられる理由を2つ挙げる。
存在を区別しないためである。入力された文字列は画面に出さない。

| 節 | 内容 |
| --- | --- |
| 概要 | 状態、script、種類、登録、予定、開始、完了、所要時間、スケジュール、親のジョブ、関連する作業項目、Windmillで開くリンク |
| 失敗の原因 | 失敗の検知が保存した原因。ジョブが失敗か取消のとき、保存した原因があるとき、読めなかったときに出す。長い文は枠で切る |
| ステップ | フローのときだけ。モジュールのid、状態、繰り返しの回数、子のジョブの詳細へのリンク。新しい方の取得から描く。条件で飛ばしたステップは「スキップ」と示す |
| 引数 | 値を出してよい引数は値を、それ以外はキーと型を出す |
| 結果 | 結果。読めなかったときは、理由を警告に出す |
| ログ | ログ。「ログと原因を更新」のボタンを持つ |

概要の予定の時刻は、時刻と残り時間で出す。
共通の相対時刻は未来の時刻を「たった今」と書くので、予定には使わない。
関連する作業項目へのリンクは、引数`work_item_id`が正の整数のときだけ、その整数から作る。
親のジョブへのリンクは、サーバーが許可した親のidだけで張る。
ステップの一覧は、所要時間を持たない。サーバーが返さないためである。
ステップの出力は子のジョブにあるので、子のジョブの詳細へ移って読む。

条件で飛ばしたステップは、Windmillが状態を`Success`のまま、`skipped`を真にして返す。
状態だけで語を決めると、動いていないステップに「成功」と出る。
そのため、`skipped`が真で状態が成功のステップは「スキップ」と示す。失敗には`skipped`が付いても、失敗と示す。
語は`stepStateInfo`が決める。この一覧と、実行中と待ちの行の今のステップが、同じ関数を使う。
実機の完了したフロー(`implement`と`pr_fix`)の記録で、`Success`に`skipped: true`が付くことを確かめた。
Consoleは、ステップに`skipped`が無い応答を、飛ばしていないものとして読む。Consoleの配信とscriptの反映の順序に依らず、詳細を読めるようにするためである。真偽値でない`skipped`は拒否する。

### 出力の描画

ログ、結果、引数、失敗の原因、読めなかった理由は、テキストのノードとしてだけ描く。
Markdown、HTML、`innerHTML`、ANSIの解釈、自動のリンクを使わない。
出力にはdefaultのworkerで動いたscriptの出力が含まれ、Issueに由来する値も混じるためである。
`tests/scripts/console_jobs_render_contract.test.ts`が、部品のソースにこれらの経路が無いことを確かめる。
見えない文字と、並びの見た目を入れ替える文字は、`src/lib/safeText.ts`の`safeText`で代替文字に置き換える。
置き換える文字の範囲は`displayableIssueText`と同じで、この入口が自分で持つ。保護パスの外のファイルに頼らないためである。
描画の部品は、`displayableIssueText`を直接呼ばず、この入口を通す。
置き換えは、ログと結果のほかにもかける。
対象は、引数のキー、値、型、ステップのid、保存された原因のステップ、文、読めなかった理由である。
見出しの題と副題、scriptとscheduleのパス、設定のキーと値、scheduleのcronとタイムゾーンとエラー、知らない状態の生の値も対象にする。
起動の関係の図のノードの名前と補足、実行中と待ちの行の今のステップのidも対象にする。
`tests/scripts/console_jobs_render_contract.test.ts`が、次を確かめる。

- 出力の節にリンクを置かない。属性が複数行に折れたタグも捕まえる。ただし、保存された原因の`JobLink`は、UUIDの形のidだけをリンクにするので許す
- URLの形、`www.`、正規表現の中のURL、`new RegExp`で組んだURLを、ソースに書かない
- サーバー由来の項目を、`safeText`を通さずにJSXの子や、`title`などの属性へ埋め込まない
- 描画の部品が、`safeText`を取り込む

`console/src/screens/jobs/safeTextCoverage.test.tsx`は、すべての項目に見えない文字を入れて描き、画面に残らないことを確かめる。
項目を足したときに通し忘れると、ここで落ちる。
ソースの検査は、項目名と埋め込みの形を見る規則である。
式を組み立てて渡す経路は捕まえられないので、その経路は上の描画の確認が受け持つ。

ログと結果には、注記を添える。

- 伏せ字の限界(完全ではないこと)を、常に添える
- 伏せた箇所があるときは、そのことを添える
- 長くて切ったときは、残した側を伝える。ログは末尾、結果は先頭を残す
- ログにJSONでない行があるときは、その行数を伝える。この行には文字列の規則だけで伏せ字をかけている

### 取得と更新

ログと結果を含む取得は、1回行う。
古くならず、フォーカス、再接続、画面を開き直したときにも取り直さない。
取り直すのは、「ログと原因を更新」の操作と、ジョブが終わったと分かったときの1回だけである。
ログと原因を更新すると、保存された失敗の原因も取り直す。

状態だけの取得は、最新の状態が実行中か待ちのときだけ、15秒ごとに取り直す。
予定のジョブは自動では取り直さない。実行が数時間先のことがあり、15秒ごとの取得が無駄になるためである。
見出しの更新で実行中になったときは、その後は取り直しの対象になる。
状態を15秒ごとに更新する旨の案内も、同じ条件で出す。予定のジョブには出さない。
状態だけの取得は、ログと結果の値で初期化する。取った直後に、同じ内容を取り直さないためである。
15秒は新しいとみなし、フォーカスと再接続では取り直さない。タブが見えない間は取り直さない。
状態だけの取得は、ログと結果の取得の間は有効にしない。Console用workerの枠が1つで、2つの詳細の取得を重ねないためである。
ログと原因の更新のボタンは、どちらかの取得が走っている間は押せない。
状態の取得が最初に失敗しても、実行中のジョブは15秒ごとの取り直しを続ける。
状態だけの取得は、Windmillにジョブを読むとき、ログを含めない。ログは、ログと結果を含む取得だけが別に読む。

見出しの更新のボタンは、状態を取り直す。ログと結果は取り直さない。
最終更新は、状態を読んだ時刻を示す。
状態の取り直しに失敗したときは、他の画面と同じ「最新の取得に失敗したため、前回取得した値を表示しています」と「もう一度取得する」を出す。
「もう一度取得する」は、失敗した取得だけを、ログと結果、状態の順に1つずつ取り直す。

表示するジョブとステップは、2つの取得のうち新しい方から取る。
状態だけの取得もステップを持つので、実行中のフローの進み具合を、15秒ごとに更新できる。
終了した状態からは、実行中や待ちの状態へ戻さない。
接続の復帰で2つを同時に読み直すと、先に出した状態の応答が後から届くことがあるためである。
引数、ログ、結果、保存された原因は、ログと結果を含む取得から描く。

ジョブが終わったと分かったときは、ログと結果を1回だけ自動で取り直す。
同じジョブでは1回に限り、取り直しに失敗しても繰り返さない。
予定のジョブが、見出しの更新で実行中になり、終わったときも同じである。
取り直すまでの間は、保存された失敗の原因と結果を「まだ読んでいません」と伝え、無いとは言わない。
ログは、読んだ分を残す。

保存された失敗の原因は、scheduleのジョブでは、検知が5分ごとに書く。
終了から5分より前の失敗で、原因がまだ無いときは、「保存された失敗の原因はありません」と言わない。
「まだ保存されていない場合があります(検知は5分ごとです)」と伝える。

ログは末尾が残り、原因は最後にあることが多い。
ログの枠は、表示するときと内容が変わったときに、末尾までスクロールする。

### ジョブの中止

実行中か待ちの作業項目のフローは、概要の見出しの**ジョブを中止**で止められる。
画面の操作名は「中止」で、Windmillの状態は「取消」である。
確認のダイアログの「取り消す」は操作をやめる意味なので、操作の名前に「取消」を使うと取り違える。

ボタンは、`canCancelJob`(`src/lib/jobActions.ts`)が真のジョブにだけ出る。
条件は、実行中か待ちであること、親を持たないフローであること、フローのパスが許可した7つのどれかと完全に一致すること、tag`console`でないことである。
7つは、audit、dependabot、design、implement、pipeline、pr_fix、pr_reviewである。
予定のジョブ、終わったジョブ、子のステップ、scriptのジョブには出さない。
この条件は画面が出す操作の絞り込みで、境界ではない。
`console_job_cancel`が同じ表で確かめ、画面の表との一致を`tests/scripts/console_cancel.test.ts`が固定する。

ボタンは確認のダイアログを開くだけで、scriptは呼ばない。
ダイアログは、フロー、ジョブのID、作業項目の番号を示し、効果と残るものを並べる。
並べる文は、ジョブの状態とフローで変わる(`cancelDialogLines`)。状態は、実行中と待ちの2つである。

- 実行中のフローは「実行中のフローを止める」、待ちのフローは「待ちのフローを止める」と書く。どちらも元に戻せない
- 実行中のフローだけに、子プロセスの文を並べる。待ちのフローは、まだ何も起動していない
- 子プロセス(Claudeと検査)は止まらない。Claudeは上限まで動き続けることがあり、その費用は日次予算に数えられないことがある
- 残ったプロセスは、毎日03:00の掃除が止める。止めるのは、実行の上限時間に5分を足した時間を過ぎたものだけである
- 作業項目は、リースがこのジョブを指したまま残り、次の照合で失敗になる。承認待ちの作業項目は、照合が失敗にしないので、承認待ちのまま残る。承認依頼の通知は届かないことがある
- implementだけ、再実行の準備のステップが残ったプロセスを止めることを足す
- pr_fixだけ、保留中のラベルとCIの監視が、失敗の後で新しい修正を起動し直すことを足す
- 実行中のpr_fixだけ、残ったプロセスがworktreeを使うと、新しい修正の準備が止まることを足す
- dependabotだけ、中止した後に再実行できないことと、PRを人の手で確かめることを足す

作業項目の状態はジョブの詳細に無いので、ダイアログは承認待ちかどうかで文を分けず、両方の場合を文で伝える。
中止した後の知らせは、読み直した作業項目の状態で分ける。

確認のボタンは「中止する」で、破壊的な色にする。
フォーカスは「取り消す」に置く(`ConfirmDialog`)。
「取り消す」ボタンとEscは、どちらもダイアログを閉じるだけで、書き込みを呼ばない。
URLの値や画面の遷移からは、中止を起こさない。

呼び出しは、書き込みの共通のフック(`useWriteMutation`)に載せる。
ロックのキーはジョブのidで、実行中は同じジョブのボタンを押せなくする。
中止の後は、そのジョブの詳細(ログと結果を含む取得)と、実行中の一覧を読み直す。
状態だけの取得は、ログと結果の取得の値で初期化されるので、読み直さない。2つの詳細の取得を重ねないためである。
結果が分からない失敗は、既存の書き込みと同じに、読み直して確かめる。再試行しない。

結果は、画面の知らせ(トースト)に出す。

| 結果 | 知らせ |
| --- | --- |
| 中止した | 成功。「ジョブを中止しました」で始め、読み直した作業項目の状態を添える。リースがそのジョブを指したままなら、次の照合で失敗になることも伝える。承認待ちの作業項目には、失敗にならず承認待ちのまま残ることと、承認依頼の通知が届かないことがあることを伝える。作業項目を読めなかったときは、読めなかったと伝える |
| 中止を依頼したが、ジョブがまだ実行中か待ちに見える | 警告。「中止を依頼しました。ジョブはまだ止まっていません」で始め、少し待って状態を更新するよう伝える。止まったとは言わない |
| 断られた | 情報。理由を日本語の固定文で伝える。対象外のフロー、子のステップ、すでに終わっている、すでに中止済みで止まる途中、予定が先、操作者を確認できない、記録を残せない、の7つである |
| 見つからない | 情報 |
| 記録を残せなかった(`action_audit`が`failed`) | 警告。中止は済んでいることと、誰が中止したかはジョブのログで確かめることを伝える |

操作の記録を足した他の書き込み(再実行、保留と凍結の解除、手動投入)も、戻りに`action_audit`を持つ。
再実行と解除の知らせは、`failed`のときに同じ警告を添える。
解除の戻りにある`audit`は、解除の通知を書けたかで、`action_audit`とは別である。
手動投入の画面は、`action_audit`を表示しない。記録の失敗はジョブの結果に残る。

### 失敗した定期ジョブの再実行

失敗した定期ジョブは、概要の見出しの**ジョブを再実行**で再実行できる。
押すたびに、scheduleの引数で1回起動する。
中止の**ジョブを中止**とは、対象が重ならない。中止は実行中か待ちのフローに、再実行は終わった失敗に出る。

ボタンは、`canRerunJob`(`src/lib/jobActions.ts`)が真のジョブにだけ出る。
条件は次のとおりである。

- 失敗したscriptのジョブであること
- 親を持たないこと
- tag`console`でないこと
- `schedule_path`が、許可した2つのどちらかであること
- scriptが、そのscheduleのscriptと一致すること

2つは、`collect_github`と`auto_retry_pr_review`である。
実行中、成功、取消、飛ばされたジョブと、フローには出さない。
この条件は画面が出す操作の絞り込みで、境界ではない。
`console_job_rerun`が同じ表で確かめ、画面の表との一致を`tests/scripts/console_rerun.test.ts`が固定する。

ボタンは確認のダイアログを開くだけで、scriptは呼ばない。
ダイアログは、処理と失敗したジョブのIDを示し、効果を並べる(`rerunDialogLines`)。

- scheduleに定義された引数で、1回実行する。画面から引数は渡せない
- 処理ごとの効果。収集はGitHub APIの使用量を使うこと、自動の再開は再開の回数を数えること
- 失敗したジョブは残ること。再実行の失敗は、定期の失敗の通知に載らないこと

結果を読む場所と、再実行しない場合は、押した後の知らせが伝える。
ダイアログには重ねて書かない。

確認のボタンは「再実行する」で、破壊的な色にしない。
再実行は新しいジョブを始めるだけで、失敗したジョブを書き換えないためである。
フォーカスは「取り消す」に置く(`ConfirmDialog`)。
「取り消す」ボタンとEscは、ダイアログを閉じるだけで、書き込みを呼ばない。
URLの値や画面の遷移からは、再実行を起こさない。

呼び出しは、書き込みの共通のフック(`useWriteMutation`)に載せる。
ロックのキーは`job-rerun:`と失敗したジョブのidで、実行中は同じジョブのボタンを押せなくする。
再実行の後は、実行中の一覧とscheduleの取得を読み直す。
起動できたときは、新しいジョブの詳細へ移る。結果をそこで確かめるためである。

| 結果 | 知らせ |
| --- | --- |
| 起動した | 成功。「再実行を始めました」で始め、結果を新しいジョブで確かめるよう伝える。新しいジョブの詳細へ移る |
| 断られた | 情報。理由を日本語の固定文で伝える。定期の実行でない、再実行できない対象、失敗していない、まだ終わっていない、同じ処理が実行中か待ち、次の定期実行が近い、scheduleが無効、scheduleの定義が変わった、引数に参照がある、操作者を確認できない、記録を残せない、の11である |
| 見つからない | 情報 |
| 記録を残せなかった(`action_audit`が`failed`) | 警告。再実行は済んでいることと、誰が再実行したかはジョブのログで確かめることを伝える |

### 画面に出ないジョブ

次のジョブは、ジョブの画面の履歴に出ない。

- フローのステップ。履歴の取得が、APIの`isFlowStep`の絞り込みで除く。ステップの出力は、フローの詳細のステップの一覧から、子のジョブの詳細へ移って読む
- tag`console`のジョブ。Consoleの呼び出し自身で、一覧の取得が除く

履歴は、親を持つかどうかでは絞らない。
承認のハンドラ(`steps/requirements_apply`、`steps/issue_proposal_apply`)には、`runScriptByPathAsync`が親のジョブを付ける。
ただしフローのステップではないので、履歴に出る。
同じ理由で、scriptが起動した別のscriptのジョブも履歴に出る。
詳細は、ルートまでの親がすべて許可した種類のときだけ、親を持つジョブを返す。
そのため、親を持つジョブを履歴に含めても、返す範囲は広がらない。

### 戻り先とWindmillへのリンク

パンくずは共通の`Breadcrumb`で、戻り先は一覧(`/jobs`)である。
一覧の行から開いたときは、一覧のタブと絞り込みを履歴の`state`で受け取り、同じ範囲へ戻る。

概要に、Windmillのジョブの画面(`/run/<id>`)への副次のリンクを小さく添える。
ステップのログが取れないときなど、Consoleの詳細で足りない場合の逃げ道である。
別のタブで開く。

## ジョブへのリンク

作業項目の遷移と失敗は、動いたジョブのIDを持つ([作業項目の状態とリース](work-items.md)の「ジョブの記録」)。
`src/lib/jobLink.ts`の`jobDetailPath`が、IDからConsoleのジョブの詳細のパス(`/jobs/<id>`)を作る。
`src/components/JobLink.tsx`の`JobLink`が、そのパスへのリンクを描く。リンクは同じタブで開く。
`work_item_detail`の遷移と失敗の行の型ガードは、`src/api/guards/workItemTransitions.ts`と`workItemFailures.ts`にある。
`tests/scripts/console_work_item_jobs_contract.test.ts`が、backendの変換結果がこれらの型ガードを通ることを確かめる。

IDはDBに記録された値で、信頼できない入力として扱う。
UUIDの形のものだけを、固定の形のパスに入れる。形が違えばリンクを出さない。
URLの組み立てに、IDから先の文字列を使わない。

Windmillの画面へのリンクは、`jobRunUrl`と`WindmillJobLink`が作る。
パスは固定の形`/run/<job_id>`で、別のタブで開く。
リンクは、同じオリジンの相対パスにする。ConsoleはWindmillと同じオリジンで配信するためである。
URLにワークスペースの指定(`?workspace=`)を付けない。
指定の無いURLをWindmillがどのワークスペースで開くかは、確かめていない。
別のワークスペースを選択中だと、ジョブを開けないことがある。
単一のワークスペース(`factory`)の運用を前提にする。

`JobLink`は、次の場所に組み込んである。

- 要対応の失敗の詳細
- システムの画面の、監査の失敗と、作業項目に紐づかない失敗
- 作業項目の詳細の、失敗の記録と状態の遷移
- 新規投入の結果
- スケジュールの直近の実行

要対応の失敗の詳細は、作業項目の詳細(`/items/<id>`)へのリンクも持つ。

## 画面を足す手順

1. 画面を`src/screens/<入口>/`に置く。
2. `src/app/screens.ts`の表に、入口か詳細の経路を1行足す。入れ子の経路は`children`に書く。
   経路の一覧を固定する`src/app/routeTable.test.ts`にも1行足す。
3. 表示する語を`src/lib/labels.ts`に足す。
4. 判定は純関数にして、`src/lib/`に置き、テストを書く。
5. 見出し(`PageHeader`)に、画面が自分のクエリから作った`refreshStatusOf`の結果を渡す。
   取得を複数持つ画面は、`refreshStatusOfAll`で1つにまとめて渡す。
   取得するデータを持たない画面は渡さない。
6. 足した表示を、[Consoleの画面の表示の原則](../console-display.md)に照らして確かめる。
   確認の方法は、同じ文書の[毎日見る目での確認](../console-display.md#毎日見る目での確認)にある。

## 配信の構成

| 要素 | 役割 |
| --- | --- |
| `console/` | Consoleのソースコード(Vite + React) |
| `.github/workflows/console-dist.yml` | `main`へのpushで、`console/`を組み立てて成果物`console-dist`として上げる。成果物を上げるのはこのワークフローだけである |
| `ci.yml`の`console`ジョブ | PRで、`console-dist.yml`と同じ手順で組み立てられることを確かめる。成果物は上げない。型検査、lint、テストは`check`ジョブが担う |
| `infra/console_fetcher/` | 成果物を検証して、名前付きボリューム`factory_console`に書く |
| Caddy | `factory_console`を読み取り専用でマウントし、`/console/`で配信する |

`factory_console`は、どのworkerにも書き込みでマウントしない。
読む必要があるConsole用のworker(`windmill_worker_console`)にだけ、読み取り専用で渡す。
配信中のファイルを書き換えられると、運用者のブラウザに改ざんが居座るので、書けるのは取り込み専用の`console_fetcher`だけにする。

## console_fetcherのコンテナ

- uid 1000(rootでない)、`read_only`、`cap_drop: [ALL]`、`no-new-privileges`で動く。
- 専用のnetwork`console_egress`につなぐ。このnetworkからは、DBとWindmillに届かない。
- 第三者のパッケージを入れない。
- dockerには外への行き先をドメインで絞る仕組みが無い。そのため、コードが接続する先を`api.github.com`と、そこからリダイレクトされたAzureのblob storage(`*.blob.core.windows.net`、`https:`のみ)に限る。
- 成果物の取得先へはトークンを送らない。

## 取り込みの検証

`console_fetcher`は、`console-dist.yml`の実行の成果物`console-dist`だけを取り込む。
`ci.yml`のジョブは、同名の成果物を上げても取り込まれない。
権限の違うジョブが成果物を上げ直して、配信物をすり替えるのを防ぐためである。

実行の一覧は、ワークフローのファイル`console-dist.yml`で絞って取得する。
取得した実行は、次をすべて満たすものだけを候補にする。
APIの絞り込みに頼らず、取り込み側でも確かめる。

1. ワークフローのパスが`.github/workflows/console-dist.yml`で、名前が`Console dist`である。
2. ブランチが`main`で、イベントが`push`である。
3. 状態が完了で、結論が成功である。
4. commitが40桁の16進数である。

候補を新しく作られた順に見て、同じcommitの`ci.yml`も成功している最初の実行を選ぶ。
`ci.yml`の確認は、`ci.yml`の実行の一覧にcommitを指定して取得し、次をすべて満たす実行があるかで決める。
こちらも、APIの絞り込みに頼らず取り込み側で確かめる。

1. ワークフローのパスが`.github/workflows/ci.yml`で、名前が`CI`である。
2. ブランチが`main`で、イベントが`push`である。
3. 状態が完了で、結論が成功である。
4. commitが、候補のcommitと一致する。

`console-dist.yml`は組み立てしか確かめないので、型検査、lint、テスト、秘密情報の走査を担う`ci.yml`の成功も条件にする。
`ci.yml`が実行中か失敗しているcommitは飛ばして、その前の候補を選ぶ。
確かめる候補は、新しい順に5つを上限にする。
候補を見ている途中で配信中の版に当たったら、その版を選んで探索を止める。
配信中の版より古いcommitに、版が戻らないためである。
戻して取り消した版(`revoked.json`のsha)は、候補から外す。
どの候補も満たさなければ、取り込まず今の版を配信し続ける。

`main`という名前のタグの実行は、`main`のブランチの実行と見分けがつかない。
そのため、両方のワークフローが同じcommitで成功していることを求める。
ただしこの照合だけでは、タグを作れる人は防げない。残るリスクは[セキュリティ](../security.md)にある。

選んだ実行の成果物を、書く前に次をすべて確かめる。

1. 成果物の元のcommitが、その実行のcommitと一致する。
2. zip全体のsha256が、GitHubの`digest`と一致する。
3. 展開した全ファイルのsha256が、`manifest.json`と一致する。
4. マニフェストが、その実行のcommitのものである。

zipは自前のreaderでメモリ上に展開する。
`..`、絶対パス、symlink、通常のファイル以外、暗号化、zip64は拒む。

## CIの組み立て

`console-dist.yml`が、`main`へのpushのたびに組み立てて、成果物を上げる。
変更したパスによらず毎回動かす。
`console_fetcher`が、そのcommitの成果物を取り込むためである。
PRとタグのpushでは動かさず、`ci.yml`のジョブを足さない。
組み立ての手順は、このファイルに直接書き、別のファイルに分けない。
Factoryのトークンは`.github/workflows/`を書けない。
composite action(`.github/actions/`)は書けるので、分けると配布物がその変更に左右されるためである。

- ワークフローの権限は、リポジトリの読み取り(`contents: read`)だけにする。成果物の書き込みには、`GITHUB_TOKEN`の書き込み権限を使わない。
- ジョブは1つで、`console-dist.yml`にほかのジョブやトリガーを足さない。
- 実行を取り消さない。取り消した実行は成功しないので、そのcommitの成果物が欠けるためである。
- 同じ実行を「Re-run all jobs」で上げ直しても失敗しないように、成果物は上書きで上げる。

`ci.yml`の`console`ジョブは、PRで同じ手順を書き写して動かし、組み立てとビューアの取得を確かめる。
2つの手順が食い違わないことは、テストが確かめる。
成果物は上げない。
`scope`ジョブの`console`のフラグが偽のとき、このジョブを飛ばす。
型検査、lint、テストは`check`ジョブの`mise run check`(`console:check`)が担い、どちらのワークフローも重ねて実行しない。
判定の詳細は[セットアップ](../setup.md)の「CIの実行の範囲」にある。

- miseで入れるツールは、bunと、viteとtscを動かすnodeだけにする。ほかの`[tools]`とそのinstall scriptを動かさない。
- miseのキャッシュを読み書きしない。
- ルートと`console/`の依存は`bun install --frozen-lockfile --ignore-scripts`で入れ、依存のinstall scriptを実行しない。
- `console/bun.lock`は`scripts/check-console-lockfile.ts`で検査する。registry由来でsha512のintegrityが付いた依存だけを許す。git、GitHub、tarballのURL、`console/`の外を指す`file:`と`link:`、`trustedDependencies`は拒む。
- 組み立ての後、マニフェストを書く前に、draw.ioのビューアを取得して`dist/drawio/`に置く。詳細は「draw.ioの図」にある。

## 配信の経路

Caddyは、`/console/`の下を次の経路で返す。
`factory_console`の他のファイル(`pin`、`revoked.json`、`history.json`など)は配信しない。

| パス | 返すもの | キャッシュ |
| --- | --- | --- |
| `/apps/get/f/factory/factory_console`と`/apps_raw/get/f/factory/factory_console`(配下を含む) | 固定の`/console/`への302のリダイレクト。パスとクエリは行き先に写さない | `no-store` |
| `/console` | `/console/`への308のリダイレクト。クエリ(`?approval=<id>`など)は保つ | - |
| `/console/status.json` | ボリューム直下の`status.json`。無ければ404 | `no-store` |
| `/console/assets/*` | 共有の`assets/`。無ければ404 | 長期(immutable) |
| `/console/drawio/*` | `current/`の`drawio/`。ビューアと受け口。無ければ404 | 長期(immutable) |
| `/console/drawio.html` | `current/`の`drawio.html`。無ければ404 | `no-cache` |
| `/console/*` | `current/`のファイル。無いパスは`index.html` | `no-cache` |

旧Consoleへの規則は、`/console/`の経路より先に評価する。
旧Consoleの編集画面(`/apps/edit/...`)とAPIは飛ばさない。
この規則は、過去のリンクが残り続けるため、旧Consoleのappを消した後も残す。
302にするのは、ブラウザに転送を覚えさせないためである。転送を覚えると、規則を変えたときに古い行き先へ飛び続ける。

`/console/manifest.json`は、`current/`の`manifest.json`である。
`status.json`は`state`、`sha`、`checked_at`、`error`の4項目だけを持つ。

## 開いたままのタブの版の確認

開いたままのタブは、`manifest.json`と`status.json`を読んで、自分の版が配信中かを確かめる。
実装は`console/src/lib/`と`console/src/`にある。

- `lib/referencedUrls.ts`: 画面が参照するscriptとstylesheetのURLの収集
- `lib/release.ts`: 判定
- `lib/releaseCheck.ts`: 取得と判定の1回分
- `lib/releaseSchedule.ts`: 確認の間隔、タブの可視状態、動的importの失敗での即時の確認、打ち切り、失敗時の間隔の延長
- `useReleaseWatch.ts`: 上の部品をDOMにつなぐ

### 確認の時機

確かめるのは、表示した直後と、その後60秒ごと、タブが見える状態に戻ったとき、動的importが失敗したときである。
動的importが失敗すると、Viteが`window`に`vite:preloadError`を出す。
版の入れ替わりで古いchunkが消えると、このimportは失敗する。
そのイベントを受けると、次の周期を待たずに確かめる。
タブが見えているかは見ない。
失敗は版が外れたことの手掛かりで、見えないタブでも確かめる意味があるためである。
前の確認の開始から2秒は空ける。空いていなければ、空くまで待ってから確かめる。
失敗が続けざまに起きても、確認が続けて走らないためである。
待っている間に何度来ても、確認は1回にまとめる。
確認の実行中に来た要求は、何度来ても、実行が終わった後に1回だけやり直す。
実行中の確認が、失敗より前に始まっていて、版の入れ替わりを見落とす場合があるためである。
やり直しも、前の確認の開始から2秒を空ける。
イベントの既定の動作は変えない。失敗したimportは、そのまま例外になる。
unmount後は確かめず、やり直さない。
Consoleの画面は、経路ごとに動的importで読み込む。
版が入れ替わった後に、古いchunkを読み込む画面へ移ると、このimportが失敗して`vite:preloadError`が出る。
すると確認が走り、版が外れていれば帯が出る。
失敗した画面の位置には、`RouteError`が再読み込みを案内する。
フックがマウントされる前に起きた失敗は拾わない。

### 自分の版の見分け方

自分の版は、画面が参照するscriptとstylesheetのうち、`/console/assets/`の下にあるファイル名の集合で見分ける。
確かめるたびに、DOMから集合を取り直す。
後から読み込んだchunkの参照も拾うためである。
基準のオリジンと違うURLと、`%`を含む名前は集合に入れない。
集合が空の回は、何も取りに行かず、前回の判定を保つ。
開発サーバーは`index.html`の`/console/assets/`の参照にbaseを前置するので、集合が空になる。

`index.html`に直書きした`/console/assets/`の参照は、すべて`console/public/assets/`に置く。
Viteが`dist/assets/`に写し、`manifest.json`に載せるためである。
載らない参照があると、再読み込みしても消えない帯が出る。

ビルドに版のshaは埋め込まない。
版ごとに中身が変わると、`console_fetcher`の中身による同一判定と`revoked.json`の照合が働かなくなるためである。

### 判定

| 状況 | 表示 |
| --- | --- |
| 集合のファイルがすべて`manifest.json`にある | 出さない |
| 1つでも無く、`state`が`pinned`でなく、無かったファイルのどれも404でない | 再読み込みを促す控えめな帯 |
| 1つでも無く、`state`が`pinned`か、無かったファイルのどれかを取ると404 | 再読み込みを求める目立つ色の帯 |

`manifest.json`を取れないときは、前回の判定を保つ。
`status.json`を取れなくても、帯は出す。
一度目立つ色の帯を出したタブは、帯を下げない。

## ブラウザ側のヘッダー

`/console/*`の応答(404とfallbackを含む)だけに、次のヘッダーを付ける。
Windmill(`/`と`/api/*`)には付けない。

- `script-src`を`/console/assets/`に絞ったCSP。`'unsafe-inline'`と`'unsafe-eval'`は許さない。
- `frame-ancestors 'none'`と`X-Frame-Options: DENY`
- `X-Content-Type-Options: nosniff`
- `Referrer-Policy: same-origin`
- `Cross-Origin-Opener-Policy: same-origin`

Trusted Typesは`Content-Security-Policy-Report-Only`で様子を見る。

`/console/drawio.html`と`/console/drawio/`の下だけは、別のヘッダーを付ける。
内容は「draw.ioの図」にある。

## CSPとCaddyのパスの解釈の違い

ブラウザは、パスの`%2f`を区切りとみなさない。
そのため、`/console/assets/..%2f..%2fapi/...`は`script-src`の`/console/assets/`に合う。
一方Caddyは、区切りに戻して正規化する。
そのままでは`/api/...`や`/ws/...`としてWindmillや`windmill_extra`へ転送され、その応答をscriptとして読ませる経路になる。
CSPはパーセント符号を戻してから比べるので、`/%63onsole/assets/...`のように文字を符号化したURLも`/console/assets/`に合う。

そこでCaddyは次のように扱う。

- パーセント符号を戻しただけで正規化していない元のパスが`/console/`で始まる要求は、どの転送先(`windmill_server`、`windmill_extra`)にも渡さない。Consoleの経路で返すか、404にする。`/console`そのものを含み、大文字小文字と先頭の`/`の重複は区別しない。
- Caddyは`handle`をmatcherの種類で並べ替える。そのためCaddyfileでは`route`で順序を固定し、Consoleの経路とこの404を、どの`reverse_proxy`よりも先に評価させる。
- Consoleの経路では、生のパスに`%2f`か`%5c`(大文字小文字を問わない)があれば400にする。

Consoleの画面のURLに、符号化した区切りを使ってはいけない。

### 開くときのホスト名

`script-src`は、ブラウザが使ったスキーム、ホスト、ポートを含む`/console/assets/`のURLで絞る。
CSPのパスには、オリジンが要るためである。
IPv6のリテラル(`http://[::1]:8080/console/`など)で開くと、このURLの形が崩れてscriptが拒否される。
IPv4のアドレス(`127.0.0.1`など)かホスト名で開く。

### ビューアの取得

ビューアはリポジトリに入れない。
`console-dist.yml`の手順は、組み立ての後に`fetch-drawio-viewer.ts`を動かす。
ビューアは`dist/drawio/drawio-viewer-<sha256の先頭8桁>.js`に書く。
取得したバイト列のsha256が固定の値と違えば、何も書かずに失敗する。
URLはリダイレクトを許さず、パスはcommit配下のビューア1ファイルに限る。
応答は10MBまでで、一時的な失敗(ネットワーク、429、5xx)は、待ちを倍にしながら3回まで再試行する。
取得物は、固定のsha256をキーにして`actions/cache`に保持する。
キーとして使う前に、sha256が64桁の小文字の16進数かを検査し、形が違えば失敗させる。
保存先は`console/.cache/drawio-viewer`で、Gitには入れない。
キャッシュに一致するファイルがあれば取得しない。
キャッシュの中身は信用せず、使う前に固定のsha256と照合する。照合に通らなければ、取得し直す。
キャッシュは`dist/`の外に置く。`dist/drawio/`には受け口のscriptもあり、キャッシュから戻すと、組み立てた受け口を上書きしてしまうためである。
raw.githubusercontent.comの障害で取得に失敗したら、失敗したワークフローの実行を再実行する。キャッシュに当たれば取得せず、外れれば取得し直す。
ビューアはApache-2.0のライセンスである。
`console_fetcher`は、他の配信物と同じように、マニフェストの照合を経て`releases/<sha>/drawio/`に置く。
共有の`assets/`には入れない。`current`から`/console/drawio/`として配信する。
そのため、版を入れ替えたとき、古い版の`drawio/`は`releases/`の掃除に従って消える。
`console_fetcher`のコードは、このディレクトリのために変える必要が無い。マニフェストの検査は、`assets/`の入れ子だけを拒む。

ローカルの`mise run console:check`は、ビューアを取得しない。
ネットワークが無くても通る。

`console/scripts/public-assets.test.ts`が、`drawio.html`の参照と固定の値の一致を確かめる。
受け口のscriptを直したときは、ファイル名のハッシュを中身に合わせて付け直す。
同じテストが、合っていないファイル名を検出する。

### ビューアの更新

固定の更新は、Windmillの`f/factory/drawio_viewer_bump`が毎週月曜の10:00(Asia/Tokyo)に行う。
新しい版があれば、固定を書き換えるPRを作る。
人が固定のファイルを手で直す必要はない。
どこで動かすかと、何を守るかは、[セキュリティ](../security.md)の「ビューアの更新」にある。

| ファイル | 役割 |
| --- | --- |
| `f/factory/drawio_viewer_bump.ts` | スケジュールが呼ぶ。取得、観測の記録、重複の確認、PRの作成。判断は純粋関数に任せる |
| `f/factory/lib/drawio_viewer_bump.ts` | 版の比較、14日の待ち、大きさの確認、既存のブランチの確認、sha256の計算、固定のファイルとページの書き換え。純粋関数 |
| `f/factory/lib/drawio_viewer_bump_github.ts` | 更新だけが使うGitHubの操作。リリースの一覧、タグの解決、ファイルの読み取り、PRの一覧、差分の比較、1つのcommitでのブランチの作成 |
| `f/factory/lib/drawio_viewer_observations.ts` | タグごとに、最初に見たcommitと時刻を記録する |
| `migrations/datatable/main/20261011153000_drawio_viewer_observations.up.sql` | 記録の表`factory.drawio_viewer_observations` |

保護パスの一覧は、[セキュリティ](../security.md)の「保護パスの変更を止める」にある。

処理は次の順に進む。

1. `main`の`console/drawio-viewer.json`を読み、今の版を知る。
2. jgraph/drawioのリリースの一覧から、今の版より新しい版を、新しい順に最大20件選ぶ。
3. 選んだタグごとに、指すcommitをGitHubのAPIでたどり、タグとcommitの組を記録する。同じcommitなら記録済みの時刻を保つ。タグが別のcommitに付け替えられていたら、時刻を今に取り直す。解決できないタグは、警告を出して飛ばす。
4. 公開から14日以上たち、かつ、同じcommitを14日以上前から見ている最新の版を選ぶ。メジャー版は問わない。無ければ、何もせず終わる。
5. 未完了の更新のPR(ブランチ名が`factory/drawio-viewer-`で始まり、headがこのリポジトリのもの)があれば、何もせず終わる。選んだ版のブランチをheadにしたPRが、閉じたものを含めて1件でもあれば、作らない。
6. 選んだ版のcommitのビューアを、固定と同じ形のURLから取得する。取得物の大きさとgit blobのIDを、GitHubのAPIの値と照合する。
7. 大きさが今から2割を超えて増減していないかを確かめる。
8. 取得物のsha256を計算し、`console/drawio-viewer.json`と、`console/public/drawio.html`が読むビューアの名前の新しい内容を作る。
9. 選んだ版のブランチが、PRは無いのに既にあれば、先頭のcommitを1回だけ取る。そのcommitで、各ファイルのgit blobのIDが手順8の内容と一致し、`main`との差分がその2ファイルだけで名前の変更を含まないことを確かめる。合わなければPRを作らない。
10. `factory_repo_id`があれば、書き込みの前に、`factory_repo`の現在のリポジトリIDと照合する。食い違うときと見つからないときは、ブランチとPRを作らずに終わり、`factory_repo_id_mismatch`のnoticeが残る。
11. ブランチが無ければ1つのcommitで作る。PRを開き、PRのheadのcommitが、作った(または確かめた)commitと同じかを確かめる。違えばラベルを付けずに止める。同じなら自動レビューのラベルを付ける。

最初に動かした週は、すべての版の観測が始まったばかりなので、14日間は何も上げない。
観測の記録が消えたときも、同じように待ちを数え直す。

PRの本文は、PRテンプレートの章立てで、版、commit、sha256、大きさを書く。
メジャー版が変わる更新は、題名を`[major]`で始める。
本文の先頭には、メジャー版の更新であることと、旧と新の版を書く。
続けて、破壊的変更の可能性があるため、リリースノートとCSP、sandbox、`drawio_frame_isolation`の確認を人が行うと書く。
人は、マージの前にリリースノートを読み、CSPと図の隔離のテストが通っていることを確かめる。
PRは通常のCIを通る。
`console`ジョブが、書き換えた固定のURLからビューアを取得し、sha256を照合する。
`public-assets.test.ts`が、ページの参照と固定の一致を確かめる。
自動レビューが指摘を付けても、このPRにはPR修正を始めない(ブランチ名で判定する)。`factory:fix`ラベルを付けても動かず、ラベルは消費されずに残る。修正は人が行う。ブランチ名だけで判定するので、担当するすべてのリポジトリに効く。
マージの後は、他のConsoleの変更と同じく、CIが通れば数分で`console_fetcher`が反映する。
図が描かれることは自動では確かめないので、マージの後にConsoleの要件定義書の図を開いて確かめる。

自動では上げない版は、noticeの`drawio_viewer_bump_held`に残る。

| 原因 | 本文に載ること |
| --- | --- |
| 大きさが今から2割を超えて増減した | 版と、今と新しい大きさ |
| 大きさとgit blobのIDが、GitHubのAPIの値と違う | 版 |
| PRの無い既存のブランチの中身が、作るはずの内容と違う | 版とブランチ名。次の操作は、ブランチを確かめ、不要なら削除する |
| PRを作る間にブランチの先頭が変わった | 版、PRの番号、ブランチ名。次の操作は、PRとブランチを確かめ、不要ならPRを閉じてブランチを削除する |

上げる版に選んだ最新の版を保留している間は、それより古い版も上げない。保留の理由が、noticeに出続ける。

メジャー版の更新は、この通知には残らない。PRの題名と本文で知らせる。
大きさの変化が正当なら、Windmillで`f/factory/drawio_viewer_bump`を、`approved_version`にその版(例: `v33.0.0`)を指定して実行する。
指名した版は、2割の制限を免れる。
公開から14日の待ちと、GitHubのAPIの値との照合は、指名しても免れない。
空のファイルと10MBを超えるファイルは、指名しても上げない。
上げないと決めたときは、noticeを解決する。原因が続くと、次の週に出直す。

失敗(GitHubのAPIの障害、ネットワーク、トークンの失効)はジョブの失敗になり、スケジュールの失敗の通知に流れる。
次の週に再び試すので、人が再実行する必要はない。

更新のPRが閉じられたときは、その版を再び提案しない。
次の版が出れば、また提案する。
更新のPRが開いたまま残ると、次の更新は止まる。マージするか閉じる。

自動の更新が使えないときだけ、固定を手で上げる。
手順は次のとおりである。

1. jgraph/drawioのリポジトリを、blobを取らない部分cloneで取る。
2. 新しいcommitがリリースのタグ(`v<版>`)にあることを、`git tag --contains <commit>`で確かめる。
3. `git show <commit>:src/main/webapp/js/viewer-static.min.js | shasum -a 256`で、sha256を計算する。配信用のURL(raw.githubusercontent.com)から取ったバイト列を使わず、gitのオブジェクトから取る。
4. `console/drawio-viewer.json`の4項目を書き換える。URLはそのcommitを指し、sha256は3.の値である。
5. `console/public/drawio.html`が読むビューアの名前を、新しいsha256の先頭8桁に合わせる。

### iframeとメッセージ

親の部品は、`sandbox="allow-scripts"`と`referrerPolicy="no-referrer"`を付けたiframeで`/console/drawio.html`を読み込む。
XMLが変わるたびに、iframeを作り直す(keyを変える)。
1つのiframeの一生で送るのは、最初の`load`の後の1回だけである。
受け口は、`load`の前にscriptの実行を終えているためである。
状態の遷移は`console/src/lib/drawioFrameState.ts`の`reduceFrame`にある。`shouldSendXml`が、このloadでXMLを送ってよいかを返す。

2回目の`load`は、iframeが別の文書へ遷移したことを表す。
親は、iframeを`about:blank`にして表示を止め、固定の文を出す。
以後、そのiframeのメッセージは受けない。
この停止は最善の努力である。loadが起きない遷移は検知できず、止まらない。
そのときも、親が受ける値は、数値(高さ)と固定の失敗の種類だけである。

最初の`load`の後、10秒たっても、高さと`drawio:error`のどちらも届かなければ、親は、図のページが応答しないとみなして固定の文を出す。
`drawio.html`が404になったときや、ヘッダーに遮られて、scriptが動かないときである。

| 向き | メッセージ | 検査 |
| --- | --- | --- |
| 親からiframe | 種別`drawio:render`と`xml`(文字列) | 親は、空のXMLと、UTF-8で256KBを超えるXMLを送らない |
| iframeから親 | 種別`drawio:height`と`height`(数値) | 親は、送り元がiframeのwindowでないものと、`height`が有限の数値でないものを捨て、80〜1600pxに収める |
| iframeから親 | 種別`drawio:error`と`reason` | 親は、送り元がiframeのwindowでないものと、`reason`が固定の3つ(`viewer_missing`、`render_failed`、`too_large`)でないものを捨てる。画面に出す文は、親が`reason`から決める |

iframe側の受け口(`console/public/drawio/drawio-frame-*.js`)は、次のものを捨てる。

- 送り元が親のwindowでないメッセージ
- 種別が`drawio:render`でないメッセージ
- `xml`が文字列でないメッセージ
- 2回目以降の`drawio:render`

256KBの上限は、親と受け口の両方に置く。
親は送る前にバイト数で、受け口は受けた後に文字数で確かめる。
片方を変えるときは、もう片方も同じ値に変える。
上限を超えたXMLを受けた受け口は、`too_large`を返す。

受け口は、失敗を黙らせない。
ビューアが読み込まれていない場合、ビューアが例外を投げた場合、描いても図が入らなかった場合は、固定の文をiframeの中に出し、`drawio:error`を親へ返す。
例外の文面は、ページに出さず、親にも渡さない。

iframeは、図の領域の大きさが変わるたびに高さを送る。
図が上限より高いときは、親のiframeが1600pxで止まり、iframeの中で縦にスクロールする。横には隠す。
縦のスクロールバーが出入りして幅が変わると、ビューアが図を合わせ直して高さが変わり、高さの通知が往復するため、幅は固定する(`scrollbar-gutter: stable`)。
枠線は、iframeの外側の要素に付ける。iframeに付けると、枠線の分だけ高さが足りなくなる。

### CSPとヘッダー

`/console/drawio.html`と`/console/drawio/`の下は、Consoleの他のページと別のヘッダーで返す。
Caddyfileでは、次の2つを、Consoleの本体の`handle_path /console/*`より前に置く。

- `handle /console/drawio.html`
- `handle_path /console/drawio/*`

どちらも後ろに置くと、Consoleのヘッダー(`frame-ancestors 'none'`)が付いて、iframeに読み込めなくなるためである。

Consoleの本体のfallback(`handle_path /console/*`)は、`drawio.html`と`drawio/`の下を404にする。
区切りを重ねた要求などでfallbackに落ちても、sandboxの無いConsoleのヘッダーで返さないためである。
ビューアと受け口は、`/console/assets/`ではなく`/console/drawio/`に置く。
Consoleの本体のCSPは`/console/assets/`だけを許すので、本体のページは、`/console/drawio/`のscriptを読めない。
本体にHTMLが注入されても、信頼されたオリジンでビューアを動かす足場にならない。
`tests/infra/caddyfile.test.ts`が、この許可の違いを固定している。

| ヘッダー | 値 | 理由 |
| --- | --- | --- |
| `Content-Security-Policy` | `default-src 'none'`、`script-src`は`/console/drawio/`、`style-src 'unsafe-inline'`、`img-src data:`、`font-src data:`、`connect-src 'none'`、`base-uri 'none'`、`form-action 'none'`、`frame-ancestors`はブラウザが使ったオリジン、`sandbox allow-scripts` | 外への取得をすべて止める。不透明なオリジンでは`'self'`が使えないので、`script-src`と`frame-ancestors`にはブラウザが使ったオリジンを入れる。`style-src`は、ビューアが付けるインラインのstyleのために許す。`sandbox`は、ページを直接開いても不透明なオリジンで動かす |
| `X-Frame-Options` | `SAMEORIGIN` | `frame-ancestors`を解釈するブラウザでは、そちらが優先される。これは、解釈しない古いブラウザ向けの備えで、Console自身のページだけに埋め込ませる |
| `Referrer-Policy` | `no-referrer` | 参照元を送らない |
| `X-Content-Type-Options` | `nosniff` | scriptの種別を推測させない |

`'unsafe-eval'`は付けない。

## 他のサイトからのAPIの呼び出し

`/api/*`への要求は、次のどれかに当てはまるとCaddyが403にする。
ほかのポートのlocalhostや外部のリンクから、運用者のCookieでAPIを実行させないためである。

- `Sec-Fetch-Site`が`cross-site`か`same-site`である。
- `Origin`ヘッダーがあり、ブラウザが開いたホスト名とポートのオリジンと一致しない。
- 副作用のあるGETのAPIを、fetchとXHR以外の読み込み(`<img>`、リンク、iframeなど)から呼んでいる。
- GETとHEAD以外の要求が、ページの移動(`Sec-Fetch-Mode: navigate`)で送られている。

### Sec-Fetch-Siteの規則

- Windmillのフロントエンドからの要求には、ブラウザが`Sec-Fetch-Site: same-origin`を付ける。
- CLI(`wmill`)は、`Sec-Fetch-*`、`Origin`、`Cookie`のどれも送らない。

### Originの検査

`Sec-Fetch-Site`を送らない古いブラウザは、1つ目の規則を素通りする。
ブラウザは、GETとHEAD以外の要求には`Origin`を付けるので、2つ目の規則がそれを止める。
ナビゲーションや`<img>`のGETには`Origin`が付かない。
Firefox 70未満は、フォームのPOSTにも付けない。
そのため、この検査が補えるのは、GETとHEAD以外のブラウザの要求だけである。

ブラウザが開いたオリジンは、`Host`ヘッダーのホスト名とポートに、`http://`か`https://`を付けたものである。
許すのはこの2つだけで、`WM_HTTP_PORT`やホスト名を変えても規則はそのまま合う。
前段でTLSを終端するときは、プロキシがブラウザの使った`Host`を、ポートを含めて保つ必要がある(nginxなら`proxy_set_header Host $http_host`)。
nginxの既定は`Host`を転送先の名前に書き換え、`$host`はポートを落とす。
どちらも`Origin`と合わなくなり、ログインを含む書き込みがすべて403になる。
`Host`が内部の名前に変わると、ブラウザの`Origin`と合わず、書き込みがすべて403になる。
`http://localhost:8080`で開いたなら、`http://localhost:8080`と`https://localhost:8080`が通る。
同じポートでも、`http://127.0.0.1:8080`は通らない。
ポートが違うもの、末尾に`/`が付いたもの、`Origin: null`も止める。

### 副作用のあるGET

Windmillには、GETでジョブを起動するAPIがある。
例は`GET /api/w/<workspace>/jobs/run_wait_result/p/<path>?payload=<base64>`である。
同じオリジンの`<img>`やリンクから呼ぶと、`Sec-Fetch-Site: same-origin`で`Origin`も付かず、上の2つの規則を通る。
Cookieの持ち主の権限でジョブが動き、承認のscriptなら、Cookieの持ち主が承認者として記録される。
そのため、次のGETとHEADは、`Sec-Fetch-Dest`が`empty`(fetchとXHR)で、かつ`Sec-Fetch-Mode`が`navigate`でないときだけ通し、それ以外は403にする。
`<a download>`は`Sec-Fetch-Dest`が`empty`でも`navigate`になるので、`Sec-Fetch-Mode`でも止める。
この規則の対象は、下の表のGETだけである。読み取りのナビゲーションには影響しない。
Consoleの呼び出しはPOSTの`fetch`なので、影響しない。

| 経路(`/api/w/<workspace>/`の下) | 理由 |
| --- | --- |
| `jobs/run_wait_result/p/<path>`と`jobs/run_wait_result/fv/<version>` | scriptとflowを起動し、結果を待つ |
| `jobs/run_and_stream/f/<path>`、`fv/<version>`、`p/<path>`、`h/<hash>` | scriptとflowを起動し、結果を流す |
| `jobs/slack_approval/<id>`と`jobs/teams_approval/<id>` | SlackとTeamsへ承認のメッセージを送る |
| `job_helpers/move_s3_file` | オブジェクトストレージのファイルを動かす |

`Sec-Fetch-Dest`を送らないブラウザは、`Cookie`を持つときだけ止める。
対象は、古いブラウザと、HTTPで公開したブラウザである。
`Sec-Fetch-*`は、信頼できるオリジン(localhostかHTTPS)でだけ付く。
そのため、WindmillのフロントエンドがこれらのGETを使うと、その環境では403になる。
CLIとscriptは、`Sec-Fetch-*`と`Cookie`を送らず、`Authorization`で認証するので、そのまま通る。

パスの照合は、大文字小文字を区別せず、`//`の重なりも許す。
作業スペースの部分は`/`をまたいで一致させるので、`%2f`で`/`を隠しても逃げられない。
`%72un_wait_result`のようにパーセント符号で綴りを変えても、Caddyが戻してから照合するので止まる。

洗い出しは、`windmill-client`の`services.gen.d.ts`にある453個のGETのAPIを、名前と説明で分類して行った。
サーバーの全経路を網羅した確認ではなく、`/api/r/*`のカスタムHTTPルート(HTTPトリガー)は含まない。
このリポジトリはHTTPトリガーを持たない。
足すときは、GETでjobを起動する経路にならないか、認証の方式とあわせて確かめる。

次のGETは、副作用があるか、起動する可能性があっても、対象にしない。

| 経路 | 対象にしない理由 |
| --- | --- |
| `jobs_u/resume/<id>/<resume_id>/<signature>`と`jobs_u/cancel/...` | 署名が資格情報で、Cookieに頼らない。メールの承認リンクとして、ナビゲーションで開くため |
| `auth/login_link/<token>`、`mcp/oauth/start`、`mcp/oauth/callback` | ログインとOAuthの導線で、ナビゲーションで開くため |
| `users/refresh_token` | 新しいトークンを返すだけで、攻撃者に得がない |
| `jobs/resume_urls/...`と`jobs/job_signature/...` | 署名付きURLを返すだけで、応答は別のオリジンから読めない |
| `job_helpers/test_connection`と`workspaces/test_datatable_connection/...` | 設定済みの接続を試すだけで、状態を変えない |
| 上以外の`list`、`get`、`count`、`exists`、`history`、`download`など | 読み取りだけである |

Windmillのフロントエンドの実装は読んでいない。
対象のGETを`fetch`以外で開く導線があれば、そのリンクは403になる。
ジョブ結果の表示は`jobs_u/get`などの読み取り系のGETを使い、対象に入れていない。

### ページの移動で送られる書き込み

同じオリジンに注入された`<form method="post" action="/api/w/<workspace>/jobs/run/p/...">`は、クリック1回で送られる。
このPOSTは、`Sec-Fetch-Site: same-origin`で、`Origin`も一致し、`Sec-Fetch-Dest`は`document`になる。
上の3つの規則は、どれも止められない。
そのため、GETとHEAD以外の要求で`Sec-Fetch-Mode`が`navigate`か`nested-navigate`のものは、メソッドを問わず403にする。
ConsoleとWindmillのフロントエンドのAPI呼び出しは`fetch`なので、`Sec-Fetch-Mode`は`cors`か`same-origin`になり、影響しない。

GETとHEADは、この規則では止めない。
APIをナビゲーションで開く正当な導線があるためである。
副作用のあるGETは、前の節の規則が止める。
ナビゲーションで開く導線は、次のとおりである。

| 経路(`/api/`の下) | 導線 |
| --- | --- |
| `w/<workspace>/jobs_u/resume/...`と`jobs_u/cancel/...` | メールとSlackの署名付きの承認リンク |
| `auth/login_link/<token>` | ログインのリンク |
| `oauth/login_callback/...`、`oauth/connect_callback/...`、`mcp/oauth/start`、`mcp/oauth/callback` | OAuthの認可とコールバック(IdPからのリダイレクト) |
| `w/<workspace>/job_helpers/download_s3_file`、`jobs_u/get_log_file/...`、`jobs/completed/export`、`users/export`、`groups/export`など | ファイルのダウンロードとエクスポート |
| `openapi.yaml`、`version` | 利用者が直接開くページ |

この一覧は、型定義の名前と説明から選んだもので、UIの実装を読んで確かめたものではない。
GETとHEAD以外をナビゲーションで送る導線は、型定義から見つけていない。
`Sec-Fetch-Mode`が無い古いブラウザと、HTTPで公開したブラウザは、止めない。
`Cookie`だけで止めると、`fetch`の書き込みまで巻き込み、UIが動かなくなるためである。

### 実機での確認

規則は、Caddyを起動して`bash scripts/check-caddy-origin.sh`で確かめる。
composeと同じイメージで`infra/Caddyfile`を動かし、止めるべき要求が403に、通すべき要求が(転送先のWindmillを起動しないので)502になることを、`curl`で比べる。
旧ConsoleのURLの転送も、同じスクリプトで確かめる。
旧Consoleのパスと配下、重なった`/`、クエリ付きの要求が、どれも`Location`が`/console/`だけの302になること、名前の続く別のアプリと編集画面は飛ばさないことを比べる。
Caddyが起動しないときは、コンテナのログを出して失敗する。
CIの`caddyfile`ジョブも、同じスクリプトを動かす。
Dockerが要る。
`CHECK_PORT`で、待ち受けるポートを変えられる(既定は18080)。
