# Consoleの仕様

Consoleのアプリ(`console/`)の構成と、成果物を配信する仕組みを書く。
アプリの構成は、画面とAPI層を変更する人が読む。
配信の仕組みは、`console_fetcher`とCaddyを変更する人が読む。
何を守るかと残るリスクは、[セキュリティ](../security.md)の「Consoleの配信」にある。

## アプリの構成

ConsoleはSPAである。
Vite、React、TypeScript、Tailwind CSS、shadcn/uiの部品で作る。
経路はReact Router、データの取得はTanStack Queryで扱う。
画面の判定は純関数に切り出して`bun test`で確かめる。
画面の部品のテストは書かない。

| ディレクトリ | 役割 |
| --- | --- |
| `src/api/` | scriptの呼び出し、失敗の分類、応答の型ガード、取得 |
| `src/app/` | 外枠、サイドバー、経路の表、ログインの状態、Provider |
| `src/screens/` | 画面。入口ごとのディレクトリに置く |
| `src/components/` | 共通の部品。`ui/`はshadcn/uiの部品を写したもの |
| `src/lib/` | 表示と判定の純関数 |

shadcn/uiの部品は、CLIを使わず、new-yorkのソースを手で`src/components/ui/`に写す。
importは相対パスにし、型アサーションは外す。
`as`を禁じる検査が、`console/src/`にもかかるためである。

## 見た目の体系

色の定義は`src/index.css`の変数だけにする。
値は`light-dark()`で書き、OSの設定と`data-theme`の両方に従う。
文字と背景の組はWCAG AAの4.5:1以上、入力欄の境界と点のような図形は3:1以上を保つ。

| 区分 | 決まり |
| --- | --- |
| 面 | 背景、面(`card`)、浮いた面(`popover`)の3段で重ねる。ダークは明るさの差、ライトは線と影で階層を出す。背景は真っ黒にしない |
| アクセント | 藍(`primary`)の1色。選択中の枠線と帯、主要な操作、フォーカスの輪に使う |
| 選択中 | 期間、種類、テーマの切り替えの選択中は、藍の枠線と藍寄りの面(`src/lib/selectedStyle.ts`)で示す。面の明るさの差は両テーマで小さいため、枠線で未選択と分ける。この3つは文字の太さを変えない。文字幅が動くと隣の項目がずれるためである。試行の切り替えとタブは、この表し方の対象外である |
| 意味の色 | 承認は青(`approval`)、失敗は赤(`destructive`)、通知は琥珀(`warning`)、成功は緑(`success`)。点、バッジ、ラベルに使う |
| 文字の濃さ | 主(`foreground`)、副(`muted-foreground`)、補足(`subtle-foreground`)の3段 |
| 文字の大きさ | 12、13、14、16、20、24pxの6段(`text-caption`、`text-small`、`text-body`、`text-lead`、`text-title`、`text-display`)。本文の行間は1.7 |
| 書体 | Hiragino Sans、Noto Sans JP、system-uiの順。Webフォントを読み込まない。CSPが外部のファイルを拒むためである |
| 数字 | 件数や時刻は`tabular-nums`で桁をそろえる |
| 動き | 選択とhoverの遷移は150ms。動きを減らす設定の利用者には、アニメーションと遷移をほぼ止める |

通知の点は、図形用の`notice-mark`で描く。
図形の基準(3:1)で足りるため、文字の`warning`と色を分ける。

文字と背景の組が基準を満たすことは、`src/theme-tokens.test.ts`が`index.css`を読んで確かめる。
対象は、面の上の文字、意味の色の文字、薄く重ねた面(バッジと帯)の上の文字、入力欄の境界・フォーカスの輪・通知の点などの図形である。
`-foreground`で終わる色と、その元の色の組も、定義されたすべてをライトとダークの両方で確かめる。
選択中の枠線は、面とトラックの上で3:1以上を保つ。
承認、失敗、通知の違いは、色だけに頼らず、隣の文字でも伝える。

文字の大きさ(`text-*`)を足したら、`src/lib/cn.ts`の`FONT_SIZES`にも足す。
足し忘れると、`cn`が大きさを文字色と見なし、同じ要素のどちらかを落とす。
足し忘れは、`src/lib/cn.test.ts`が検出する。
`FONT_SIZES`と`index.css`の大きさの一覧が違うと、このテストが失敗するためである。

表示する日本語は`src/lib/labels.ts`に集める。
画面は、状態や種類の生のコードを出さない。
表に無い値は、元の文字列ではなく決まった文言で出す。
backendの値が表から漏れていないことは、`tests/scripts/console_summary_contract.test.ts`が確かめる。

## 経路

経路は`src/app/screens.ts`の1つの表から作る。
サイドバーの入口、件数のバッジ、React Routerの経路は、すべてこの表を読む。
routerの基準は`/console`で、Caddyが`/console/`の下のパスに`index.html`を返す。

| パス | 画面 | 状態 |
| --- | --- | --- |
| `/console/` | 要対応 | 承認、失敗、通知の一覧。承認・却下、再実行、通知の解決ができる |
| `/console/items` | 作業項目 | 進捗の表と、要件定義がある作業項目の一覧 |
| `/console/items/:id` | 作業項目の詳細 | 概要、要件定義、ラウンド、承認の履歴のタブ。`?tab=<名前>`で開くタブを指す |
| `/console/items/:id/requirements` | 要件定義書 | 本文、目次、図。`?attempt=<k>`で試行を指す |
| `/console/reports` | レポート | 監査レポートの一覧と手動起動、分析のグラフと表 |
| `/console/reports/audit/:id` | 監査レポート | 作業項目`:id`の本文 |
| `/console/system` | システム | 反映の状態、更新履歴、workerの負荷、情報の通知、解決済みの通知、監査の失敗、作業項目に紐づかない失敗、起動の関係 |

どの経路にも当たらないパスは、「ページが見つかりません」の画面で受ける。
経路の番号は、正の整数の文字列だけを受け付ける。
経路やURLの引数は選択を表すだけで、承認や再実行などの操作は起こさない。

表の1行は、入口の画面と、その下で受ける経路(`children`)を持つ。
`children`は入れ子にでき、親の画面は`Outlet`を描く。
どの経路にも`ErrorBoundary`が付き、省くと既定の`RouteError`になる。
画面の読み込みや描画が失敗すると、その画面の位置にだけ再読み込みの案内を出し、サイドバーと帯は残す。
表から作る経路の一覧は、`src/app/routeTable.test.ts`が固定する。

### 旧Consoleのリンク

旧Console(Windmillのraw app)は廃止した。
過去のDiscordの通知、Issueのコメント、PRの本文には、旧Consoleのリンクが残る。
旧ConsoleのURLを開くと、Caddyが固定の`/console/`へ302で飛ばす。規則は「配信の経路」にある。
URLのフラグメントはブラウザが保つので、新しいConsoleが読み替える。
`main.tsx`が、routerを作る前に`history.replaceState`で置き換える。
routerが先に`/console/`の画面を描くと、その画面が一瞬動いてしまうためである。
置き換えは履歴を増やさない。
`<id>`と`<k>`は、先頭が0でない正の整数に限る。

| 旧Consoleのフラグメント | 置き換え先 |
| --- | --- |
| `#requirements/<id>` | `/console/items/<id>/requirements` |
| `#requirements/<id>/attempt-<k>` | `/console/items/<id>/requirements?attempt=<k>` |
| `#audit/<id>` | `/console/reports/audit/<id>` |

上の表に合わない旧ConsoleのフラグメントとフラグメントのないURLは、`/console/`の入口(要対応)に着く。

承認フローが投稿するConsoleのリンクは、新しいConsoleの経路を直接指す。
`f/factory/lib/approval_support.ts`が、次の3つを作る。

| リンク | 作る関数 | 経路 |
| --- | --- | --- |
| 要件定義書 | `buildConsoleUrl` | `/console/items/<id>/requirements`。試行が分かるときは`?attempt=<k>`を付ける |
| 承認の詳細 | `buildApprovalConsoleUrl` | `/console/?approval=<id>` |
| 監査レポート | `buildAuditConsoleUrl` | `/console/reports/audit/<id>` |

## API層

Consoleは、`src/api/windmill.ts`の`runScript`だけを通してWindmillのscriptを呼ぶ。
`POST /api/w/factory/jobs/run_wait_result/p/<path>`を、`credentials: "same-origin"`と`cache: "no-store"`で呼ぶ。
ログインのCookieだけで動くので、トークンは持たない。

`runScript`は`src/api/`の中にとどめる。
画面は、取得の`queries.ts`と書き込みの`writes.ts`にある型付きの関数だけを使う。
`src/api/`の外が`windmill.ts`をimportしないことは、契約テストが確かめる。

呼べるscriptは、`SCRIPT_PATHS`の許可リストにある次の5つだけである。
どれもtag`console`を持ち、Console用のworkerで動く。

| 名前 | 用途 | 型付きの関数 |
| --- | --- | --- |
| `console_query` | 読み取り | `fetchSummary`など(`queries.ts`) |
| `approval_decide` | 承認依頼への承認か却下の記録 | `decideApproval` |
| `retry_work_item` | 止まった作業項目の再開 | `retryWorkItem` |
| `audit_kickoff` | 監査の手動起動 | `kickoffAudit` |
| `notice_resolve` | 通知1件の解決 | `resolveNotice` |

パスは呼び出し側の名前から引き、外から受け取った文字列では呼ばない。
Consoleは管理者のCookieで動くので、呼べる範囲を固定する。
許可リストに足すscriptは、tag`console`を付け、秘密値を読む範囲を[Console用workerの境界](../security.md#console用workerの境界)に合わせる。

`runScript`は例外を投げず、応答を`classifyRunResponse`で分類して返す。
中断(`AbortSignal`)だけは、取り消しとして扱えるよう例外を再び投げる。

| 応答 | 分類 |
| --- | --- |
| 2xxで本文がJSON | 成功 |
| 2xxで本文がJSONでない | `invalid_response` |
| 401 | `unauthorized` |
| 403 | `forbidden` |
| 408、504 | `timeout_or_unknown` |
| 500 | `job_failed`。本文から取り出した文(`message`)を500字まで持つ。スタックは持たない |
| 500で、本文の文が待ちの上限の定型文(文頭の`timeout after <数>`)に合う | `timeout_or_unknown` |
| その他の状態 | `http`。状態の番号と、4xxなら本文から取り出した文を500字まで持つ |
| 通信の失敗 | `network` |

本文はContent-Typeを見ずに読む。
失敗の本文は、JSONの`error.message`、`message`、文字列の`error`の順に探し、JSONでなければ本文のテキストを使う。
`timeout_or_unknown`は、ジョブが終わったか分からない状態を表す。
書き込みでは、ジョブの失敗、待ちの上限、形が違う応答、通信の失敗、5xxで、処理が途中まで進んでいる可能性がある。
そのため`describeWriteFailure`は、書き込みのこれらの失敗を「結果が分かりません。一覧を読み直して確かめてください」と案内する。
scriptの例外が届く状態は、経路で変わりうる。
500以外の状態で届いた例外は、`job_failed`に分類されないので、種類で決める書き込みの判定から外れる。
読み取りの失敗は、共通の部品`QueryFailureAlert`が出す。
文は`describeQueryFailure`が、何が起きたかの主文、次の操作、サーバーの文に分けて作る。
サーバーの文は内部の名前を含みうるので、主文に混ぜず、折りたたむ「詳細」だけに出す。
詳細は、書き込みの失敗と同じく、見えない文字と書字方向の制御文字を代替文字に置き換えてから描く。
`view`の不一致を受けたときは、Consoleとバックエンドの版がずれている可能性を主文で伝える。
Consoleが新しい場合も、バンドルが古い場合も起こる。
次の操作は、待つこと、版を見比べること、ログを確かめることの順に案内する。
反映は2分ごとなので、まず待つ。
直らなければ、システムの画面で「反映した版」と「Consoleの取り込み」を見比べる。
反映が失敗していれば、`self_update`のジョブのログを確かめる。
`system_status`が断られたときは、システムの画面も開けないので、画面を案内先にしない。
不一致は状態や分類で決めず、本文の`"view" must be one of`で判定する。
この文は`console_query`が投げるもので、`tests/scripts/`の契約テストが、実際の文でこの判定を確かめ、文が変わったことを検出する。
4xxの案内は、ジョブが作られる前に断られた場合を含むので、workerのtagと権限、またはジョブのログを挙げる。
500を除く5xxの本文はHTMLなどになりうるので、画面に出さない。
ジョブの失敗の結果は`{"error":{"name","message","stack"}}`の形で、`stack`には内部のパスが入る。
画面には`message`だけを出す。

| `Sec-Fetch-Site: cross-site`で`/api/*`を呼ぶ | Caddyが403を返す | 実測 |
| 別のサイトの`Origin`で`/api/*`を呼ぶ | Caddyが403を返す | `scripts/check-caddy-origin.sh`で実測 |

運用者のアカウントはsuperadminなので、tag付きのscriptも呼べる。
ジョブのトークンなど、superadminでない主体から呼ぶと、400の本文が画面の`http`の文言に添えて出る。

### 応答の型ガード

応答は、`src/api/guards/`の型ガードを通してから使う。
形が崩れた応答(必須の項目の欠落、型の違い、idの不正)は、一部だけを使わず、全体を`invalid_response`にする。
表示にしか使わない列挙(承認の種類と状態、Issue提案の発生元、通知の重要度と種類、失敗の種類と状態)は、文字列として受ける。
知らない値は`labels.ts`の決まった文言に落とす。
承認・却下などの操作の分岐は、種類や状態を見て決める。その操作の側で、受け付ける値を列挙して絞る。
backendが先に新しい値を反映した間や、配信を前の版に固定している間に、要対応の一覧が丸ごと消えないためである。
時刻の文字列は、`Z`か`+09:00`のオフセットが付いた形だけを通す。
オフセットが無いと、ブラウザがローカル時刻として読み、閲覧する場所で絶対時刻がずれるためである。
`summary`の型は、`f/factory/steps/console_query.ts`の`ConsoleSummary`に合わせてある。
`tests/scripts/console_summary_contract.test.ts`が、次の5点を確かめる。

- backendの変換結果が型ガードを通ること
- backendの列挙の値が`labels.ts`の表に漏れていないこと
- backendの時刻にオフセットが付くこと
- 承認フローの投稿するConsoleのリンクが、画面が読む引数(`approval`、`attempt`)を持つこと
- 承認フローの投稿するConsoleのリンクの経路が、旧Consoleのフラグメントの読み替え先と同じになること

リンクが経路の表(`screens.ts`)の経路に解決できることは、`console/src/app/consoleLinks.test.ts`が確かめる。
ルートのテストは`.tsx`の画面を読み込めないので、経路の表を引くこのテストはConsoleの側に置く。

新しい値に気づくのは、この契約テストの役目である。
`deployments`viewの型は`DeploymentHistoryRow`に合わせてある。
`tests/scripts/console_deployments_contract.test.ts`が、次の3点を確かめる。

- 変換結果が型ガードを通ること
- 作り手と結果の値が`labels.ts`の表に漏れていないこと
- PRのリンクを画面が受け取れること

`pipeline`viewの型は、`PipelineRow`のうち画面が読む列に合わせてある。
`tests/scripts/console_pipeline_contract.test.ts`が、次の3点を確かめる。

- 変換結果が型ガードを通ること
- 状態と種別の値が`labels.ts`の表と、並び替えの順に漏れていないこと
- IssueとPRのリンクを画面が受け取れること

### 取得の方針

自動で取り直すのは`summary`だけで、120秒ごとに、タブが見えている間だけ取る。
更新履歴と作業項目の進捗は自動で取り直さない。
サイドバーの件数と、要対応の一覧は、この1つの取得を共有する。
再試行するのは、通信の失敗、待ちの上限(`timeout_or_unknown`)、500を除く5xxだけで、2回までにする。
500はジョブの失敗として分類される。
401、403、4xx、形が違う応答、ジョブの失敗は再試行しない。再び取っても同じ結果になり、120秒ごとの取得に失敗が積み増されるためである。
書き込みは再試行しない。結果が分からないまま2回実行しないためである。

1つのタブが`summary`を取り直すと、1日に720件のジョブができる(120秒ごと)。
ジョブの保持期間は、#138で扱う。

### 書き込み

書き込みのscriptは、`src/api/writes.ts`の型付きの関数だけから呼ぶ。
関数は失敗を`ApiFailure`で投げ、戻りを`src/api/guards/writeResults.ts`の型ガードに通してから返す。
形が違う戻りは`invalid_response`にする。

| 決まり | 理由 |
| --- | --- |
| 認可はWindmillのログインに任せる | Consoleは独自の認可を持たない。ログインしていない呼び出しは、Windmillが401にする |
| 承認者と解決者は引数に取らない | 画面から渡した名前は信用できない。scriptがジョブの実行文脈(`WM_USERNAME`、無ければ`WM_EMAIL`)から導き、導けなければ拒否する |
| 同一オリジンの`fetch`でPOSTし、本文はJSONにする | 他のサイトや注入されたリンクから、運用者のCookieで操作させないため。副作用のあるGETと、ページの移動による書き込みは、Caddyが403にする([セキュリティ](../security.md)の「Consoleの配信」)。Consoleの呼び出しはPOSTの`fetch`なので、この規則に当たらない |
| 操作の値をConsole側で固定する | 監査は`force: false`、`source: "manual"`、`days: 7`で起動する。承認の補足(`note`)は固定の文にする。画面から変えさせない |
| 再試行しない | 結果が分からないまま2回実行しないため |

承認は、同じ決定が記録済みの行にもう一度呼ぶと、ハンドラの起動をやり直す。
二重の送信は、画面側で止める。

却下の理由は、4000文字までにする(`MAX_REASON_LENGTH`)。文字はコードポイントで数える。
`decideApproval`は、上限を超える理由を送らず、`RangeError`で断る。
画面は、送る前に長さを確かめて入力欄で知らせる。
理由はDBに記録され、Issueやレポートに出るためである。
script側には上限が無く、Windmillのapiを直に呼ぶ者には効かない。script側の上限は、別のIssueで扱う。

#### 共通のフック

`useWriteMutation`(`src/api/mutations.ts`)が、ロック、実行、読み直しをつなぐ。
結線は、Reactから切り離した`createWriteRunner`(`src/api/writeRunner.ts`)に置く。
`bun test`が、実際のQueryClientで確かめる。
実行の流れは`executeWrite`、ロックは`runLocked`と`writeLocks`、読み直せなかったときの待ちは`holdUntilFresh`に切り出してある。

- 対象のキー単位でボタンをロックする。キーは`writeTargetKey`が作り、承認の承認と却下のように、同じ対象への操作は同じキーで止める。ロックは画面全体で共有するので、同じ対象のボタンが複数の場所にあっても、同時には動かない
- ロックはmutationの実行の中で取る。同じ瞬間に2回押されても、実行は1回になる
- 成功と、結果が分からない失敗の後に、関連する取得(既定はsummary)を読み直す。読み直しが終わるまでロックを残す
- 画面の知らせの関数は、結果用も一覧が古いこと用も、例外を投げても読み直しとロックの扱いを変えない
- 401は取得と同じ経路でログインの帯に流す
- 成功の知らせの文は、`src/lib/writeNotices.ts`の純関数が作る。解決済みだった通知の解決は成功として扱う

結果が分からない失敗は、ジョブの失敗、待ちの上限、形が違う応答、通信の失敗、5xxである。
401、403、4xxは、ジョブが動く前に断られたので、読み直さない。
ジョブの失敗(`job_failed`)は、結果が分からないものとして扱う。
scriptの断り(理由なしの却下、記録済みの別の決定など)と、副作用の後の失敗が、同じ形で返り、本文から区別できないためである。
区別するには、scriptが断りを固定の接頭辞で投げる必要がある。

読み直しが失敗したか、30秒以内に終わらなかったときは、一覧が古いことを知らせる(`STALE_LIST_NOTICE`)。
その対象は、読み直せなかった取得のすべてが次に成功するまで、押せないままにする。読み直せた取得は待たない。
古い一覧のままだと、済んだ操作をもう一度押せるためである。
summaryは120秒ごとに取り直すので、通信が戻れば解ける。

ロックを持つのは、このタブの中だけである。
複数のタブや、リロードの後の二重の送信は止められない。
サーバー側の冪等性の課題で、Consoleの外で扱う。

Issueに由来する文字は、`displayableIssueText`(`src/lib/intakeText.ts`)を通してプレーンテキストで描く。
書き込みの失敗の文に入るジョブの失敗の文と4xxの詳細も、同じ関数を通す。
見えない文字や並びの見た目を入れ替える文字を、代替文字に置き換えるためである。
置き換える分類は、backendの`countHiddenCharacters`と同じである。
全コードポイントで同じことを、`tests/scripts/console_hidden_characters_contract.test.ts`が確かめる。
リンクは`safeGitHubUrl`を通したものだけにする。

#### 契約テスト

`tests/scripts/console_write_contract.test.ts`は、次を確かめる。

- 許可リストの行き先が、tag`console`を持つ実在のscriptであること
- 型付きの関数の引数は、scriptの入力の項目と必須の項目に合うこと
- 各scriptの戻りが、型ガードを通ること

## ログイン切れの扱い

取得か書き込みが401を返すと、画面の上部にバナーを出す。
一覧の側は、同じ内容の警告を重ねない。
すぐにはログインの画面へ移さない。入力の途中の内容を失わないためである。
操作者が「ログイン」を押すと、Windmillのログイン画面`/user/login`へ移る。

戻り先は、引数`rd`に`pathname + search + hash`を入れて渡す。
`rd`は`URLSearchParams`で組み立てる。
現在のパスが`/console/`で始まらないとき、または`//`、`..`、`\`を含むときは、`/console/`に戻す。
別のオリジンや別のパスへ飛ばされないようにするためである。

その後の取得が成功すると、バナーは消える。書き込みの成功では消えない。
401以外の失敗では消えない。通信が戻ったとは限らないためである。

## 画面の外枠

左のサイドバーに、印と名前、4つの入口、下部の情報を置く。件数のバッジは要対応の入口だけに付く。
選んだ入口は、左端の藍の帯と面の色で示す。
入口の件数のバッジは、その入口の一覧に出る項目の件数にする。
要対応のバッジは、承認と、再実行できる失敗と、通知の件数である。
失敗は、再実行できるもの(監査を除く)だけを数える。監査の失敗は再実行できず、次の定期の監査が扱うまで残るので、数えると0に戻らない。
通知は、重要度が要対応の未解決のものを数える。重要度が情報の通知は、一覧に出さないので数えない。
一覧の件数と食い違う数字を、最初に見る場所へ出さないためである。

下部には、配信している版と取り込みの最後の確認、テーマの切り替え、たたむ操作を置く。
版の情報は`/console/status.json`から読む。取れなければ出さない。
状態が固定中か失敗のときは、その旨の注意を添える。
テーマはライト、ダーク、OSに合わせるの3つをアイコンで切り替える。
たたんだサイドバーでは、入口のアイコンに件数の数字を重ねて出す。

幅が狭いとき(md未満)は、サイドバーを出さず、画面の上にメニューのボタンと名前のバーを置く。
ボタンを押すと、左からドロワーが開く。
要対応の件数があるときは、ボタンに点を付け、ボタンの名前に件数を含める。
ドロワーは、サイドバーと同じ入口と下部の情報を持つが、たたむ操作は持たない。
ドロワーは、次の操作のどれかで閉じる。

- 入口を選ぶ。
- 閉じるボタンを押す。
- 背景を押す。
- Escを押す。
- 画面をmd以上に広げる。

各画面の見出しは、題と短い副題を左に、最終更新の時刻と更新のアイコンのボタンを右に置く。
更新のボタンと最終更新は、画面に1組だけ置く。
ボタンは、見出しに渡した取得を取り直す。
要対応の画面は、一覧の取得(`summary`)だけを取り直す。
詳細ペインの取得(提案、要件定義、取り込み時点のIssue、通知)は含まない。
そのため、要対応の画面のボタンの名前は「一覧を更新」にし、ほかの画面は「この画面を更新」にする。
複数の取得を持つ画面の最終更新は、取得できた中で最も古い時刻にする。
新しい取得の時刻を出すと、古いままの節が新しく見えるためである。
見出しに渡した取得のすべてが自動で取り直されるときだけ、最終更新の脇に「（2分ごとに自動更新）」の形で全角の括弧に入れて示す。
一部の取得だけが自動で取り直される画面は、注記を出さない。
システムの画面は`summary`だけが自動で取り直されるので、注記を出さない。
取得が失敗している間も、自動の取り直しは続く。
そのため注記は消さず、「（2分ごとに自動で再試行）」に言い換える。
401は失敗に数えないので、401だけのときは通常の注記を出す。

節には更新のボタンと最終更新を置かない。
節ごとの「もう一度取得する」は、その節だけが独立して失敗したときの再取得に限る。
前回の値を出している節で取り直しが失敗したときは、値が空であっても、値を出したまま、古い値であることと「もう一度取得する」を節に添える。
この知らせは`StaleDataNotice`が出す。
401は上のバナーが知らせるので、知らせは出さない。
取得中は「もう一度取得する」を押せなくする。
押すと進行中の取得を打ち切るためである。

## 要対応の画面

一覧に出すのは承認、失敗、通知である。
項目は、時刻が新しい順に並べる。
同時刻なら種類の順(承認、失敗、通知)、次にidが大きい順にする。
種類の切り替え(すべて、承認、失敗、通知)は、一覧に2種類以上の項目があるときだけ出す。
切り替えには、項目が1件以上ある種類だけを並べる。
選んだ種類の項目がなくなったら、切り替えの状態も「すべて」に戻す。
承認の下位の種類(要件定義、Issue化提案、改善提案)は、行のラベルで示す。
改善提案は、監査から出たIssue提案である。

`summary`の承認には、承認待ちのほかに、承認済みでIssueをまだ作っていないIssue提案も入る。
承認を記録した後にIssueの作成が失敗した提案を、見えなくしないためである。
その行には「承認済み(Issue作成待ち)」のラベルを付ける。

選んだ項目は、URLの`?approval=<id>`、`?failure=<id>`、`?notice=<id>`のどれか1つに持つ。
2つ以上あるときは、どれも選んでいないものとして扱う。
値が正の整数でなければ、選んでいないものとして扱う。
選択の変更は履歴を積まない。ただし幅が狭いとき(lg未満)に項目を選ぶ操作は、履歴を積む。
面が一覧から詳細へ切り替わるので、ブラウザやスマートフォンの戻る操作で一覧へ戻れるようにするためである。
積んだ履歴には、一覧から選んだ印を付ける。
広い幅で選び直して履歴を置き換えるときは、置き換わる履歴の印を引き継ぐ。
種類の切り替えが選んだ項目の種類を隠すときは、選択を外す。
一覧と詳細は別々にスクロールする。
幅が狭いとき(lg未満)は、一覧と詳細を1画面ずつ出す。
項目を選んでいなければ一覧、選んでいれば詳細を出す。
詳細の上の「一覧へ戻る」と、種類の切り替えによる選択の解除は、印のある履歴を戻って取り除く。
置き換えると、画面の変わらない履歴が残り、戻る操作を余分に求めるためである。
選択つきのURLを直接開いたときは印が無いので、選択を外して履歴を置き換える。
面が切り替わったら、新しく出た面にフォーカスを移す。
一覧へ戻るときは、離れる前のスクロール位置と、直前に選んでいた行に戻す。
どちらを出すかは`src/lib/inboxPane.ts`が決める。

一覧は`InboxList`、詳細は`InboxDetail`の別の部品が描く。
再実行、解決、承認などの行の操作は、一覧の行ではなく詳細のペインに置く。
一覧の行は1つのbuttonなので、操作のbuttonを入れ子にしないためである。
詳細は、種類ごとの描き分けを`InboxDetail`の1か所に集める。
詳細のペインは左寄せで、本文の幅は760pxまでにする。サイドバーを畳んでも位置が動かない。
一覧の行は、1行目に題名と相対時刻、2行目に種類、副題、期限、状態のバッジを並べる。
一覧の項目がすべて通知、またはすべて失敗のときは、全行に同じ語が付いて情報にならないので、「通知」と「失敗」の語を省く。
この判定は、種類の切り替えで絞り込む前の一覧全体で行い、切り替えても行の書式が変わらないようにする。
承認の語(要件定義、Issue化提案、改善提案、承認依頼)は区別を担うので、承認だけの一覧でも省かない。
通知の副題は、同じ題名の通知を見分けるために、本文の最初の対象(`owner/repo#番号`)、最初の版(先頭7桁)、本文の抜粋を「・」でつないで1行にする。
見分ける相手は、種類の切り替えで絞り込む前の一覧全体にある、同じ種類の通知である。
同じ種類の通知が並ぶときは、全員が同じ値の対象と版だけを省く。
一部だけ同じなら、全員に出す。
全員が同じ値なら見分ける役に立たず、幅が狭い一覧では抜粋の食い違いを押し出すためである。
同じ種類の通知が1件だけのときは、本文にあれば出す。
抜粋は、副題に出した対象と最初の版を除いた本文から36文字を取り、省いた側へ省略記号を付ける。
対象と版は現れた位置で切り出す。
先頭の対象と同じ文字列で始まる別の対象(`o/r#1`を切っても`o/r#12`)や、2番目以降の対象と版は残る。
同じ種類の通知が並ぶときは、本文の先頭が最も長く重なる通知と食い違う位置の直前の語の区切りから抜粋する。
書き出しがそろう通知を見分けるためである。
副題にマウスを重ねると、本文の全体を表示する。
通知の詳細の先頭には、種類と重要度を1つにしたタグ(「要対応の通知」と「情報の通知」)を出す。
通知の本文に含まれる40桁の版は、先頭7桁で示す。全体は、マウスを重ねたときの表示と、複製のボタンで取り出せる。
本文が取得の上限で切れているとき、末尾に接する40桁は、別の値の途中である可能性があるので版にしない。
状態のバッジは2行目の末尾で、狭いときは省略記号で縮める。
2行目の高さは24pxに固定し、バッジの有無によらず、どの行も同じ高さにする。
行の頭に種類の点は付けない。
期限が24時間を切った行(期限を過ぎた行を含む)だけ、期限に警告色の印を付ける。
期限を過ぎた行は、失敗の色にする。
選んだ行は、藍を帯びた面(ライトでは淡く、ダークでは暗い)と左の帯で示す。

同じ種類の未解決の通知が2件以上あるときは、件数つきの1行にまとめる。
まとめる単位は通知の種別だけで、対象や版は見ない。
重要度は種別だけで決まるので、同じグループに要対応と情報の通知は混ざらない。
承認と失敗は、1件ずつ判断して操作するので、まとめない。
解決済みの通知は、対応が済んでいるので、まとめずに1件ずつ出す。
まとめた行は、最初の通知があった位置に置き、時刻には中で最も新しい通知の時刻を出す。
副題には、閉じている間、中の通知の本文が最初に挙げる対象を、重複なしで最大2つ並べ、残りを「ほか対象N件」と数える。
「対象」の語は、通知の件数と紛れないよう添える。
対象を挙げない通知は数えない。別の対象の通知が紛れ込んだことに、開かなくても気づけるようにするためである。

まとめた行を押すと、個々の通知が字下げされて開く。
開閉のbuttonは`aria-expanded`を持ち、矢印キーで通常の行と同じように移れる。
グループは、閉じた状態で始める。ただし、選んだ通知を含むグループは開く。
URLで通知を直接開いたときも、選択が別の通知やグループに移ったときも同じである。
選んだ通知を折りたたみの中に隠さないためである。
開いた後に自分でグループを閉じても、選択は外れず、同じ選択のままでは開き直さない。
閉じたグループが選んだ通知を含むときは、行の背景で示し、読み上げにも「選択中の通知を含む」と添える。
取り直しや種類のチップでの絞り込みで、まとめられなくなった(行から消えた)種別は、開閉の状態から外れる。
チップを切り替えて戻すと、そのグループは閉じた状態に戻る。
URLの選択は個々の通知のidなので、グループの開閉に左右されない。
グループが後から成り立つ(同じ種別の通知が増える)と、行の並びが変わる。
そのとき、押していた行はグループの中に移って消えるので、フォーカスを失うことがある。

サイドバーのバッジ、種類の切り替えのチップ、見出しの副題は、まとめる前の個々の項目の数で数える。
一覧では、まとめた行の件数と、まとめない行(1行で1件)の合計が、通知の数と一致する。
開閉の判定とこの対応は`src/lib/inboxGroups.ts`が決め、テストで固定する。

承認の詳細と行には、期限があれば残り時間を出し、過ぎていれば「期限切れ」と出す。
承認の詳細には、題名、種類、作業項目(要件定義なら試行)、Issueへのリンク、期限、依頼した時刻を出す。
要件定義の承認には、要件定義書(`/console/items/<id>/requirements`)へのリンクを添える。
監査から出た提案には、元の監査レポート(`/console/reports/audit/<id>`)へのリンクを添える。
題名は`displayableIssueText`を通してプレーンテキストで描く。
期限と依頼した時刻は、日本時間の絶対時刻と相対時刻を並べる(例: 10/15 18:48まで(残り6日)、10/09 18:48(1時間前))。
IssueのリンクはGitHubのIssueのURLの形のときだけ張る。

### 失敗と再実行

一覧には、`summary`の失敗の行を、作業項目ごとに1行で出す。
対象は、状態が失敗、人の対応待ち、期限切れの作業項目である。
監査の失敗は、再実行できないので行にしない。件数のカードで知らせる。
同じIssueに新しいサイクルがある古い作業項目は含まない。

詳細のペインには、次を出す。

- 題名、種類、状態
- 作業項目への経路(`/items/<id>`)とリポジトリ
- IssueかPRへのリンク
- 失敗した時刻と、最終更新の時刻。一覧は最終更新の新しい順に並ぶので、並びの根拠を示す
- フローとステップ、ジョブへのリンク
- 失敗の内容と、状態が変わったときの注記

失敗の記録が無い作業項目では、その旨を出し、時刻は状態が変わった時刻で代える。
失敗の記録が、今の状態へ遷移した時刻より5分以上前のものは、前の失敗の記録とみなす。
再実行の起動に失敗して人の対応待ちに戻った作業項目で、前の失敗の内容を今の失敗として見せないためである。
この記録の内容、フロー、ジョブは出さず、「この状態になってからの失敗の記録はありません」と出す。時刻は状態が変わった時刻にする。
失敗の処理は、記録を書いてから状態を更新するので、正常な記録も状態の時刻より数秒前になる。5分は、その差を許す幅である。
失敗の内容と注記は、実行の出力であり、Issueの文字を含みうる。
そのため`displayableIssueText`を通し、プレーンテキストで描く。
`summary`は失敗の文を500文字で切る。500文字に達した文には、先頭だけを表示している旨と、ジョブのログへの案内を添える。
IssueかPRへのリンクは、GitHubのURLの形のときだけ張る。PRのURLは、リポジトリと番号から組み立てて、同じ検査を通す。
ジョブへのリンクは、ジョブIDの形のものだけ張る。

再実行は、詳細のペインのボタンから、確認を経て`retryWorkItem`を呼ぶ。
確認は、ブラウザ標準のdialog要素をモーダルで開く。最初のフォーカスは「取り消す」に置く。
確定すると、フォーカスを詳細のペインの処理中の行へ移す。ボタンが無効になっても、フォーカスが文書の先頭へ落ちないためである。
確認には、再実行する作業項目を特定する情報(題名、リポジトリ、対象のIssueかPR、失敗した時刻)と、状態の遷移(今の状態 → 再開先)を出す。
似た題名や古い表示の作業項目を取り違えないためである。
開いた直後のフォーカスは、明示的に「取り消す」へ置く。確定では取り消しの処理を呼ばない。
確認を開いている間に、その作業項目が一覧から外れたときは、確認を閉じ、その旨をトーストで知らせる。
再開先は、scriptが作業項目の種類で決める。

- PRのレビューは、レビュー中へ戻す
- PRの修正は、修正中へ戻す
- Issueは、承認済みの要件定義があって実装が有効なら実装へ、そうでなければ要件定義の生成へ戻す。画面はこの2つを並べて示す
- Issueの再開先が要件定義の生成のときは、GitHubの現在のIssueの題名と本文を取り込み直す。確認の注記で伝える
- 知らない種類は、再開先を決めつけない。ボタンは押せるままにして、断るかどうかはscriptに任せる
- 監査は、scriptが再実行を認めない。ボタンの代わりに理由を出す
- dependabotの更新も、scriptが再実行を認めない。ボタンの代わりに、PRを確かめて手でマージするか閉じるよう案内する

ロックのキーは作業項目ごとである(`retryTargetKey`)。
失敗の行の1つを再実行している間も、ほかの行は押せる。
再実行のボタンは詳細のペインだけにある。ロックは画面全体で共有するので、同じ作業項目は二重に実行できない。

scriptは、次のときに再実行を断る。確認の文で、事前に挙げて伝える。

- 記録されたフローが動いている、または動いているか読めないとき
- 同じIssueに、より新しいサイクルがあるとき
- 要件定義が承認済みで、実装が無効のとき
- 確認から更新までの間に、作業項目の状態が変わったとき

断りはジョブの失敗として返り、結果が分からない失敗と区別できない。
そのため、断られたときの知らせにも「処理に失敗した可能性があります」と「一覧を読み直して確かめてください」の案内が入る。括弧の中に、scriptの断りの理由が入る。
断りを区別して返すには、scriptの戻りの契約を変える必要がある。この課題はConsoleの外で扱う。

成功と、結果が分からない失敗の後は、`summary`を読み直す。
結果は、どの作業項目のものかを添えて、トーストで伝える。
トーンは次のとおりである。

- 成功は、成功として伝える
- 別の実行が先に作業項目を押さえていたときと、結果が分からない失敗は、警告にする
- ジョブが動く前に断られた失敗は、エラーにする

読み直せなかったときは、一覧が更新されるまで、その作業項目を押せないままにする。

### 取り込み時点のIssue

要件定義の承認の詳細には、取り込み時点のIssueの題名と本文を出す。
実装のClaudeが受け取るのはこの内容で、GitHub上の現在のIssueではない。
承認者が現在のIssueだけを読んで承認すると、取り込み後に書き換えられた内容を見落とすためである。

内容は選んだ承認の作業項目ごとに、`console_query`の`intake_snapshot`で取る。
`summary`には載せない。本文が長く、120秒ごとの取得に含めると応答が膨らむためである。
却下や再実行による作り直しは、同じ作業項目の取り込み内容を書き換える。
そのため、承認依頼ごとに別のキャッシュにし、画面を開くたびに取り直す。更新前の内容を新しい承認の画面に出さないためである。

題名と本文は起票者が書いた信頼できない入力である。次のように扱う。

- MarkdownやHTMLとして解釈せず、文字列としてReactが描く。タグやリンクは文字のまま見える。
- 本文は20,000文字、題名は300文字で`console_query`が切る。切ったときは、先頭だけを表示している旨を出す。
- 切った後ろの部分は、承認者がConsoleでも、HTMLのコメントや不可視の文字を描かないGitHubの画面でも確かめられない。後ろの部分にあるHTMLのコメントの開始(`<!--`)と不可視の文字の数を`console_query`が数え、あれば警告する。
- 取り込み内容を更新したことがあれば(`refreshed`。更新の履歴から導く)、目立つ警告を出す。
- 見えない文字と、並びの見た目を入れ替える文字は、代替文字(U+FFFD)に置き換え、置き換えたことを警告で示す(`src/lib/intakeText.ts`)。対象は、Unicodeの分類がCf(双方向の制御文字、ゼロ幅の文字、tag文字を含む)、Cc(改行とタブを除く)、Zl、Zpの文字と、異体字セレクタである。
- 題名と本文の要素は、`dir="ltr"`と`unicode-bidi: isolate`で、周りの文字の並びに影響しないようにする。

### 承認バー

承認と却下の操作は、詳細のペインの承認バー(`ApprovalBar`)に置く。
要件定義では、取り込み時点のIssueのパネルと、承認する試行の要件定義書を並べ、その直下に置く。
Issue提案では、提案の本文の直下に置く。
承認者が見た内容の隣で押せるようにするためである。

詳細に出す操作は、依頼の状態で決まる(`decisionSurface`)。

| 依頼の状態 | 出すもの |
| --- | --- |
| 承認待ちで期限内 | 承認と却下 |
| 承認待ちで期限切れ | 操作を出さず、その旨の文を出す |
| 承認済みでIssueを未作成のIssue提案 | 「Issueの作成をやり直す」だけを出す |
| その他の承認済み | 操作を出さず、「起票を待っています」などの文を出す |
| 却下済みなど | 何も出さない |

知らない種類の承認は、操作を出さない。

| 操作 | 決まり |
| --- | --- |
| 承認 | 確認ダイアログを経る。承認は取り消せず、要件定義ではClaudeの実装が始まるためである。ダイアログには件名、承認依頼のid、起こることを出し、開いたら取り消しにフォーカスを置く。ダイアログは新しい依存を足さず、ブラウザ標準の`<dialog>`で作る(`components/ConfirmDialog.tsx`)。再実行の確認も同じ部品を使う |
| 却下 | 理由が必須で、空白だけでは押せない。理由は4000文字まで(`MAX_REASON_LENGTH`)で、入力欄の横に「文字数 / 上限」を出す。要件定義の却下だけ、確認ダイアログを経る。却下は要件定義の作り直しになり、その時点の現在のIssueで取り込み内容が更新されるためである |
| 補足 | 承認の記録には、Consoleから決めたことを示す固定の文を添える。画面から補足は入力しない |

確認ダイアログで「承認する」を押した時点で、期限と、承認を止める理由をもう一度確かめる。
満たさなければ送らず、ダイアログを閉じて理由を出す。ダイアログを開いている間に期限を過ぎることがあるためである。

### 承認と却下の呼び出し

承認と却下は`decideApproval`で呼び、`useWriteMutation`のロックと読み直しに載せる。
ロックのキーは依頼のidで、承認と却下は同じキーで止まる。二重に押しても、呼び出しは1回になる。
成功したら`summary`を読み直し、処理した依頼が一覧から消える。
ただしIssue提案は、承認の後にIssueを作り終えるまで、承認済みの状態で一覧に残る。
結果は`sonner`のトーストで知らせる。結果が分からない失敗の文は`describeWriteFailure`が作る。
読み直せなかったときは、一覧が更新されるまで、その依頼のボタンを押せないままにする。

送る`options`の形は、依頼の種類で決め、他のキーは送らない。
Issue提案は`{ with_factory_label: boolean }`、それ以外は`{}`である。
作るIssueにfactoryラベルを付けるかは、チェックボックスで選ぶ。
監査から出た提案は初期値をオンにし、PRのレビューから出た提案はオフにする。
ラベルを付けられない監査の提案(`factory_label_available`が偽)は、選択肢を出さず、`false`を送る。

### Issue作成のやり直し

承認を記録した後でIssueの作成が止まった提案は、承認済みのまま残る。
「Issueの作成をやり直す」は、同じ承認を`decideApproval`でもう一度送る。
サーバーは、同じ決定が記録済みなら、記録せずに起票だけをやり直し、記録済みのラベルの選択を使う。
そのため、ラベルの選択肢は出さない。押しても結果が変わらないためである。
作成済みのIssueは、マーカーで見つけて再利用する。
確認ダイアログに、この2点を書く。

承認の直後は、起票の処理が走っている間でも押せてしまう。
決定の時刻は`summary`と`inbox`のどちらにも無いので、押せる条件に経過時間を入れられない。
代わりに、次の2層で重なりを防ぐ。

- 画面: やり直しに成功したら、このタブでは15分間、同じ依頼のボタンを止めて「起票に数分かかります」と出す(`redoCooldowns`)。時刻はタブのメモリにだけ持つ。画面とダイアログにも、承認の直後は押さないよう書く
- サーバー: `issue_proposal_apply`が、Issueを作る前に`claimIssueCreation`の条件付きUPDATEで印を取る。取れなかった呼び出しは、何もせずに終える。
  印は15分で切れるので、止まった処理のやり直しは塞がれない。
  失敗して提案を保留に戻した後も印は残り、期限が切れるまで、次の承認は何もせずに終わる。期限を過ぎて走り続けた呼び出しが失敗して戻すとき、印を取り直した別の呼び出しがIssueを作っている最中のことがあり、その処理と重ならないようにするためである。
  同時の呼び出しは、どちらもマーカーの走査の時点でIssueが無いと見て、Issueを2件作りうる。
  Windmillの同時実行の制限は設定しない。有償版でしか効かないので、印だけで直列化する

別のタブや別の端末からは、画面の側では止められない。サーバーの印が、この重なりを止める。

### 断りの表示

`approval_decide`は、承認の記録の前に、次の理由で断ることがある。
断りはジョブの失敗として返り、文は英語である。
既知の断りの文を含む失敗だけを、日本語の固定文と取れる手にして、承認バーの中に出す(`classifyDecisionRefusal`)。
トーストは消えるので、バーの中に残す。
Windmillは失敗の文に「Error:」などを前置きすることがあるので、文頭は見ない。
他のscriptの失敗とは、断りの文に固有の部分で区別する。

| 断りの理由 | 取れる手 |
| --- | --- |
| Issueが取り込みの後に書き換えられた | Issueを取り込み時点の内容に戻して承認し直す。現在のIssueを使うなら却下する |
| 現在のIssueを比べられなかった | 少し待って承認し直す。Issueを移したか削除したなら却下する |
| 別の決定が記録済みか、期限切れ | 一覧を読み直して状態を確かめる |
| 却下の理由が空 | 理由を入力して却下し直す |
| 承認依頼が見つからない | 一覧を読み直して状態を確かめる |

文は、`approval_decide.ts`と`approval_support.ts`が関数で作る。
`tests/scripts/console_approval_refusal_contract.test.ts`が、その関数の出力を画面の分類に通す。
Windmillの失敗の包み方を通した場合も、同じテストが確かめる。
既知でない文言は、結果が分からない失敗の案内に落とす。

### 要件定義の承認の前提

要件定義の承認は、承認者が次の2つを見られるときだけ押せる。
実装のClaudeが受け取る取り込み時点のIssueと、承認の対象である要件定義書である。
どちらかが読み込み中か、取得に失敗しているあいだは、承認を止めて理由を添える。
作業項目に取り込み内容が無いときも止める。確かめる内容が無いまま承認させないためである。
却下は止めない。内容を見られないことが、却下を妨げる理由にならないためである。
本文が長く切られているとき(`body_truncated`)は、GitHubで全文を確かめた旨のチェックを求め、チェックするまで承認を止める。
取り込み後に書き換えられていた場合の警告(`refreshed`)は、パネルの先頭に加えて、承認バーの中にも出す。
承認を押す位置で、確かめるよう促すためである。

要件定義書は、承認依頼の試行(`draft_attempt`)を指定して取り、要件定義書の画面と同じ部品で描く。
本文の描画、図の拒否、見えない文字の置き換えは、その部品に任せる。
承認の画面では、メタ情報、試行の切り替え、目次を省く。承認する試行を切り替えさせないためである。
長い本文は、枠の中でスクロールさせ、承認バーを遠ざけない。
「別の画面で開く」のリンクから、要件定義書の画面で読める。
`draft_attempt`が`null`で承認の試行が分からないときは、最新の試行で代えず、「承認する試行が特定できない」として承認を止める。
最新の試行は、承認する試行と違うことがあるためである。
取得した書の試行が承認の試行と違うときも、承認を止める。

承認の前の確認は、承認の操作を受ける側で働く([要件定義](requirements.md)の「承認の前のIssueの確認」)。

### Issue提案の本文

Issue提案の本文と、ラベルの選択肢の出し分けに使う情報は、`summary`に載せていないので、`console_query`の`inbox`から読む(`useInboxProposals`)。
本文と出どころの期間と担当は`displayableIssueText`を通す。
解釈はせず、プレーンテキストで描く。
置き換えた文字があれば、警告を出す。
提案が読めないか、一覧に無いときは、本文が分からないまま承認させないので、操作を出さない。
`tests/scripts/console_inbox_contract.test.ts`が、backendの`inbox`の変換結果が型ガードを通ることを確かめる。

### 一覧に出ない項目と空の状態

詳細から行える操作は、承認と却下、失敗の再実行、通知の解決である。
一覧に出ていない件数は、種類ごとのカード(色の点、件数)で知らせる。
対象は、取得の上限を超えた承認、失敗、通知と、再実行できない監査の失敗である。
監査の失敗のカードだけ、システムの画面へのリンクにして、押せると分かる矢印を添える。
システムの画面が読めるのは監査の失敗だけなので、取得の上限を超えた承認、失敗、通知のカードはリンクにしない。
残る件数は、再実行できない監査の失敗と、取得の上限を超えた分である。
監査の失敗のカードには、再実行できないこととシステムの画面で確認することを添える。
取得は新しい順に上限まで読むので、上限を超えた分は古いものから表示されない。承認、失敗、通知のカードにその旨を添える。
同じ数をサイドバーには出さない。画面の中で1か所だけに示すためである。

一覧が空のときは、画面を2つに割らず、中央に1枚の面を出す。
面には、承認、失敗、通知が無いことと、ほかの種類に残る件数のカードを載せる。
最終更新と自動更新の間隔は、画面の見出しが示すので、面には載せない。
何も残っていないときだけ緑のチェックを出す。ほかの種類が残っているときは、中立のアイコンにして、片付いた印象を与えない。
一覧の取り直しが失敗しているときは、緑のチェックを出さず、中立のアイコンにする。
見出しは「最後に取得できた時点では、対応が必要な承認・失敗・通知はありませんでした」に変える。
あわせて、古い値の知らせを添える。
確かめられていない状態で「何もない」と言い切らないためである。
401のときは見出しだけを変え、知らせは上のバナーに任せる。
カードは面の幅を等分して並べる。
401で取得できないときは、バナーと並べて、ログインが必要である旨を中央に出す。

並び、絞り込み、行の表示内容、副題、件数のカードは`src/lib/inboxView.ts`の純関数が決める。
失敗の詳細と再実行の確認の内容は`src/lib/failureView.ts`、再実行のロックのキーと結果の知らせは`src/lib/retryView.ts`が決める。
自動更新の間隔の表示は`src/lib/refreshTiming.ts`が決める。
分で割り切れる間隔は分で、それ以外は秒で書く。
相対時刻の表示は、`src/app/clock.ts`の共有の時計が30秒ごとに進める。

### 通知

一覧に出す通知は、`summary`の未解決で、重要度が要対応のものである。
重要度が情報の通知は、人の行動が要らないので、一覧に出さない。
情報の通知と、`summary`の上限を超えた通知は、`?notice=<id>`で選ぶと、同じ詳細が開く。
このとき`console_query`の`notices`viewから、未解決の通知を探す。
viewには、backendが受ける最大の2000件を指定する。`summary`の上限を超えた通知も開くためである。
`notices`viewは自動では取り直さず、詳細を開くたびに取り直す。タブへ戻っただけでは取り直さない。解決した通知を未解決のまま出さないためである。
一覧と`notices`viewのどちらにも無いときは、すでに解決されたか、まだ取得できていないと伝える。

一覧の行は、題名に通知の種類の日本語名を出す。
2行目の「通知」の語と副題の組み立ては、[要対応の画面](#要対応の画面)の一覧の行に書いた。
詳細には、重要度、本文、対象、発生した時刻、起きたことと次の操作を出す。
本文は`displayableIssueText`を通し、プレーンテキストで描く。
`summary`は本文を500文字で切る。
一覧から選んだ通知の本文が、ちょうど500文字のときは、本文が途中までであることを添える。
切れ目に接する`owner/repo#番号`は、番号の途中で切れているおそれがあるので、リンクにしない。
`notices`viewは全文を返すので、`?notice=`で開いた詳細には、この扱いをしない。
対象は、本文の`owner/repo#番号`から作ったGitHubへのリンクで、`safeGitHubUrl`を通ったものだけを張る。
本文からはIssueかPRかを区別できない。GitHubは`/issues/<番号>`をPRなら`/pull/<番号>`へ転送するので、常にIssueの形のURLを作る。
起きたことと次の操作は、`src/lib/noticeGuide.ts`が種類ごとに持つ。内容は[運用](../operations.md)の通知の表に合わせる。
表に無い種類は、本文を確かめるよう案内する。
ホスト側の作業が必要な通知(`host_action_required`)には、ホストのcheckoutで順に実行するコマンドを出す。
コマンドは、`git pull`、`mise install`、`mise run up`である。

解決のボタンは、未解決で、`summary`の`resolvable`が真のときだけ出す。
Consoleから解決できない種類には、ボタンの代わりに理由を出す。設定や権限の問題を示す通知を、内容を確かめないまま消せないようにするためである。
ボタンを押すと、確認のダイアログを出さずに`resolveNotice`を呼ぶ。解決した通知は履歴に残り、状況が続けば新しい通知が出るので、取り返しのつかない操作ではない。
解決済みだった通知は成功として扱い、「すでに解決済み」と知らせる。
成功と、結果が分からない失敗の後は、`summary`と`notices`viewを読み直す。解決した通知は一覧から消える。

行と詳細に「解決済み」の印を用意している。両方のviewが未解決の通知だけを返すので、通常は出ない。
解決済みの通知の履歴は、[システムの画面](#システムの画面)に出す。

## 要件定義書の画面

作業項目の入口(`/console/items`)は、進捗の節の下に、要件定義の節を持つ。
要件定義の節は、要件定義がある作業項目の一覧を出す。
進捗の節とは、取得を共有しない。
画面の見出しの更新のボタンが、両方を取り直す。
一覧は更新の新しい順で、直近3650日の500件までである。
行には、題名、リポジトリとIssueの番号、作業項目の番号、最新の試行、状態のバッジ、更新の時刻を並べる。
作業項目の番号で絞り込める。先頭に`#`があっても無視する。
行を選ぶと、その作業項目の最新の要件定義書(`/console/items/:id/requirements`)へ移る。

一覧は`console_query`の`requirements_index`、本文は`requirements_doc`で取る。
応答は`src/api/guards/requirements.ts`の型ガードを通す。
形が崩れた応答は、一部だけを使わず、全体を`invalid_response`にする。
backendの型との一致は、`tests/scripts/console_requirements_contract.test.ts`が確かめる。
一覧と本文のキャッシュは30秒で古くなり、画面を開いたときに取り直す。

本文の画面は、左に本文、右に目次を置く。
狭い幅では、目次を本文の前に畳んで置く。
左には、状態、リポジトリ、Issueへのリンク、作業項目、試行の切り替え、要約、本文、未確定事項の順に並べる。
状態から試行の切り替えまでは、本文を押し下げないよう、折り返す1〜2行にまとめる。
目次は、スクロールに合わせて読んでいる節を強調する。
底までスクロールしたときは、短い最後の節も選べるよう、最後の見出しを強調する。
底に着いたときだけは、画面に見えている見出しをURLのハッシュが指していれば、最後の見出しではなくその見出しを強調する。
ハッシュは手でスクロールしても消えないので、手で底へ戻したときも、ハッシュの見出しが強調される。
底から1〜2px上へ動くと、基準線の規則に戻り、強調が変わりうる。
スクロールできない短い文書では、目次のリンクを選んでも強調は変わらない。
強調は、色と左の線だけで示す。太字にすると、折り返しの行数が変わり、本文の位置が動くためである。
表のセルの文字にIDが含まれるときは、ハイフンで折り返すとIDが読めなくなるので、IDの部分を折り返さない。
強調やコード、リンクの中のIDは対象にしない。
表示の判定は`src/lib/requirementsView.ts`の純関数が決める。

### 試行の切り替え

試行は、最新から1までのリンクで切り替える。
表示する試行はURLの`?attempt=<k>`に持ち、番号が無ければ最新を出す。
`?attempt=`があって、先頭が0でない正の整数でないとき(`abc`、`0`、`02`、`1.5`、空)は不正とする。
2147483647を超える値も不正とする。
不正なときは、取得せずに「試行の番号が正しくありません」と出す。最新として読むと、別の試行を読んでいると気づけないためである。
最新へのリンクは番号を付けず、最新を指し続ける。
最新の試行を確かめられるのは、最新を指定して本文を取ったときと、一覧にその作業項目の行があるときだけである。
このときの最新の試行の番号は、本文の試行と一覧の行の、大きいほうにする。
古い試行を開いていて、一覧がまだ答えないときと、一覧に行が無いときは、最新を確かめられない。
このあいだは、どの試行にも「(最新)」を付けず、開いている試行までを番号つきのリンクで並べる。
選択肢は新しいほうから50件までに絞る。
却下による作り直しは、試行が増えることで現れる。
却下の理由と承認の履歴は、`work_item_detail`の`approvals`が持つが、この画面は読まない。
`requirements_doc`が持たないためである。

### 本文の描画

本文の描画は`src/components/markdown/Markdown.tsx`にある。
Issueの内容に由来する信頼できない入力なので、次のように扱う。

- 本文、要約、未確定事項、題名は、見えない文字を`displayableIssueText`で置き換えてから描く。置き換えたときは、その旨を出す。
- `react-markdown`と`remark-gfm`で描き、`rehype-sanitize`で無害化する。生のHTMLは描かず、`dangerouslySetInnerHTML`も使わない。
- リンクにするのは、作業項目と同じリポジトリのIssueとPRのURL、本文内の見出しへのフラグメントだけである(`src/lib/markdownLink.ts`)。それ以外は文字で出す。
- リンクの文字とURLが違うときは、URLを括弧で添える。添えたURLは`<bdi>`で包む。
- 画像は、図の参照(`![name](name.drawio)`)だけを通す。ほかの画像は描かない。
- `> [!NOTE]`、`> [!WARNING]`、`> [!IMPORTANT]`で始まる引用は、ラベル付きの囲みで描く。

理由は[セキュリティ](../security.md)の「要件定義書のリンク」にある。

目次は、行頭から始まる`##`と`###`の見出しである。
コードの囲みの中の行は、見出しに数えない。
見出しの走査は正規表現で行う。そのため、HTMLのコメントの中の行は見出しに数え、`id`のない目次の項目になる。
行頭が空白や`>`で始まる見出しと、下線で書く見出しも数えない。
見出しの`id`は、見出しの文字から作ったスラッグに`h-`を付ける。
ページの他の要素の`id`と名前が重ならないようにするためである。
`id`が使われているときは、使われていない`id`になるまで`-2`、`-3`を付ける。
見出しが`a`、`a`、`a-2`の順に並んでも、`id`は重ならない。
`id`は`src/lib/markdownHeadings.ts`が行ごとに決め、描画は見出しの行から引く。
目次のリンクと見出しの`id`が、必ず一致する。
本文のリンク`[文字](#見出し)`は、同じ規則で`#h-見出し`に読み替える。
本文は脚注の記法を使わない。
`#user-content-fn`で始まるフラグメントは、見出しへのリンクに読み替えず、文字で出す。行き先のないリンクにしないためである。

題名は、本文の最初のレベル1の見出し(`#`で始まる行)にする。
無ければIssueの題名、それも無ければ「(無題)」にする。
題名の行は、ページの見出しに出すので、本文では描かない。

### 手動の起動

「今すぐ監査」を押すと、確認のダイアログを出す。
ダイアログは、ブラウザ標準の`dialog`要素をモーダルで開く。
確認すると、`kickoffAudit`で`audit_kickoff`を起動する。
起動の前にダイアログを閉じるので、確認のボタンを二重に押しても、起動は1回になる。

起動の設定は`src/api/auditKickoffConfig.ts`にあり、書き込みの共通の流れに載せる。

- ロックのキーは1つに固定する(`AUDIT_WRITE_KEY`)。起動が実行中のあいだ、ボタンは押せない
- 同じ瞬間に2回呼ばれても、実行は1回になる
- 結果が分かったら、監査レポートの一覧を読み直す
- 読み直せなかったときは、一覧が古いことを知らせ、一覧が更新されるまでボタンを押せないままにする

`force`は渡さない。
`force`を付けると、対象の記録が無くても起動するので、画面からは出さない。

結果は、一覧の上に画面を離れるまで残す(`src/lib/auditKickoff.ts`)。
トーストは数秒で消え、見送りの理由を読み落とすおそれがあるためである。

| 結果 | 表示 |
| --- | --- |
| 起動した | 成功の色で、対象期間を添える |
| 見送った | 通常の色で、理由を日本語で出す。理由は`writeNotices.ts`の対応表にある |
| 失敗した | 失敗の色で、書き込みの失敗の文を出す |
| 一覧を読み直せなかった | 警告の色で、一覧が古いことを出す |

見送りは失敗ではなく、何も変えなかった正常な結果である。

## システムの画面

この画面は、Software Factory自身の状態を、読むだけの節に分けて出す。
節は上から、反映の状態、更新履歴、workerの負荷、情報の通知、解決済みの通知、監査の失敗、作業項目に紐づかない失敗、起動の関係である。
画面に書き込みの操作は無い。通知の解決は、要対応の画面の詳細で行う。
起動の関係の節だけは、取得を持たず、バンドルに取り込んだ静的なデータを図にする。

更新のボタンと最終更新は、画面の見出しに1組だけ置く。
ボタンは、下の3つの取得(`system_status`、`deployments`、`summary`)を取り直す。
節は、読み込み中は骨組み、取得に失敗したときは節の中に失敗の表示と「もう一度取得する」を出す。
401のときは、上のバナーが知らせるので、節にはログインを促す文だけを出す。
1つの節が失敗しても、ほかの節は表示する。

反映の状態、workerの負荷、情報の通知、解決済みの通知、作業項目に紐づかない失敗は、`console_query`の`system_status`viewを1回取って揃える。
この5つの節は、取得の結果を分け合う。
画面が取得を1つだけ持ち、見出しの更新で一緒に取り直す。
同じ取得を重ねて取り直すと、互いを打ち切るためである。
定期には取り直さない。画面を開くたびに取り直すので、要対応の画面で解決した通知を、未解決のまま出さない。
各一覧は200件までで、200件に達した節には、これより古いものは表示していない場合がある旨を添える。
型は`src/api/guards/systemStatus.ts`の型ガードで確かめる。形がずれると、画面は`invalid_response`の失敗を出す。
backendの型との一致は、`tests/scripts/console_system_contract.test.ts`が確かめる。

### 反映の状態

次の3行を、1枚のカードに出す。

- 反映した版。`system_status`が読んだ、反映済みの版の記録である。読めなければ「不明」にする
- 直近の反映。日時、前の版から今の版、結果、ホストの作業の要否を、更新履歴のカードと同じ語で出す
- Consoleの取り込み。状態、取り込んだ版、最後に確かめた時刻を出す

取り込みの状態は、`console_fetcher`が書く`status.json`から、backendが判定する。
状態の語は、取り込み済み、取り込みに失敗、版を固定中のどれかで、知らない値は「不明な状態」にする。
判定が更新の停止のときは、語に「(古い記録)」を添える。
色は、判定が失敗なら失敗の色、更新が30分以上無いか版を固定していれば警告の色(30分は`FETCHER_STALE_MINUTES`と同じ値で、契約テストで一致を確かめる)、それ以外は成功の色にする。
状態を読めないときは、警告の色で「状態を読めません」と理由を出す。
失敗の分類と運用者の次の操作があれば、補足の行に出す。

### 更新履歴

更新履歴は、Software Factoryが自分を更新した反映の一覧である。
`console_query`の`deployments`viewから、直近90日のものを新しい順に100件まで取る。
自動では取り直さず、見出しの更新で取り直す。

反映1回を1枚のカードにする。カードには、次を出す。

- 日時。相対時刻で、日本時間の絶対時刻をツールチップに添える
- 版。前の版と今の版を、7桁の短い形で「前 → 今」と書く。前の版が無い初回は「初回 → 今」にする
- 結果。「反映済み」か「失敗」で、知らない値は「不明な状態」にする
- ホストの作業の要否。要るときは警告の色にする
- 含まれるPR。作り手のバッジ、題名、番号を1行にする
- 失敗の理由。失敗した反映だけに、先頭の120字を「理由:」に続けて出す

失敗の理由は、外部のコマンドの出力を含みうる信頼できない文字列なので、文字としてだけ出し、リンクやマークアップにはしない。
理由を記録する前の失敗の反映には、「理由の記録はありません」と出す。

作り手のバッジは、「Software Factory」、「人」、「不明」のどれかである。
backendが確かな情報(マージしたブランチの名前)を読めたときだけ、前の2つにする。読めなければ「不明」にする。
含まれるPRが無い反映には、「含まれるPRの記録はありません」と出す。
PRを記録する前の反映と、PRを取り出せなかった反映も、同じ表示になる。区別できないのは、取り出せなかったときも空で記録するためである。
失敗した反映は、PRを取り出す前に止まるので、PRを持たない。空の配列で記録する。
記録するPRは1回の反映につき100件までなので、100件に達した反映には、これより古いPRは表示していない場合があると添える。件数がちょうど100のときも同じ注記になる。
題名は、GitHubのUIでマージしたコミットの本文の1行目である。別の形でマージしたコミットは、題名が空になるか、PRとして記録されない。

題名はコミットメッセージ由来の信頼できない文字列なので、Reactが文字として描く。マークアップとしては解釈しない。
番号は、GitHubのPRのURLの形で、末尾の番号がPRの番号と一致するときだけリンクにする。それ以外は文字で出す。
リンクは`rel="noopener noreferrer"`を付けて新しいタブで開く。
backendは、URLを`https://github.com/<owner>/<repo>/pull/<N>`の形に限り、題名の制御文字と書字方向の制御文字を空白にし、200字に切って返す。
画面は、同じ検査を`src/lib/updateHistory.ts`の純関数でやり直す。
表示する語は`src/lib/labels.ts`にある。

### workerの負荷

defaultのworkerの直近24時間の負荷を、1枚のカードに出す。
値は`system_status`の`worker_load`で、`worker_samples`を1回のクエリで集計した数と時刻だけである。
外部の文字列は含まない。
行は次のとおりである。

- 枠の使用。最新の記録の実行中のジョブの数と、他のジョブが使える枠の数、窓の中の最大
- 枠が塞がっていた記録。他のジョブが枠をすべて使っていた記録の数と、`running_jobs`が読めた記録に対する割合。
  他のジョブの使える枠が無い記録は数えない
- queueの待ち。待ちの最大の秒数と、待つジョブの最大の数
- 開始が遅れた記録。`lag_seconds`が30秒以上の記録の数と、最大の遅れ
- メモリ。最新と最大の`anon`、working set、上限に対する割合
- `memory.current`と`memory.peak`。キャッシュを含み、`memory.current`は最新の瞬間値、`memory.peak`はコンテナの起動からの最大値で、どちらも逼迫の判断には使わない

「枠の使用」と「メモリ」の最新の行には、最新の記録の時刻をJSTで添える。
上限に対する割合は、窓の中の最大の行にだけある。
割合は、0%に丸まる正の値を小数1桁で出す。

窓に記録が無いときと、集計を読めなかったときは、`worker_load`が`null`になる。
2つを分けないのは、画面が出す次の操作が同じだからである。
画面は、記録がないか集計を読めなかった旨と、`sample_worker_load`のスケジュールと`console_query`のジョブログの警告を確かめる操作を出す。
集計の失敗は、`console_query`のジョブログに警告`could not read the worker load`として残る。

`worker_load`を返す前のbackendの応答では、項目が欠ける。
Consoleが先に配信されても画面が壊れないよう、欠けた値は記録なしと同じに扱う。
形が違う値は、システムの画面の型ガードでは確かめない。
カードが確かめ、形が違えば、カードだけを「表示できません」にする。
画面の他の節は消えない。

画面は閾値を持たない。
通知を出すのはメモリの割合とOOMの増加だけで、割合は`factory_config`の設定にある。
通知は要対応に出る([閾値の通知](../operations.md#閾値の通知))。
待ちと枠の塞がりは通知にせず、この画面と日次のまとめで見る。
「枠の使用」と「枠が塞がっていた記録」を塞がりの判断に使える条件は、[枠の占有](../operations.md#枠の占有)にある。
型は`src/api/guards/workerLoad.ts`で確かめる。

### 情報の通知

重要度が情報の通知は、人の行動が要らないので、要対応の一覧に出ない。
この節は、直近7日の未解決の情報の通知を、新しい順に出す。
行には、通知の種類の日本語名、発生の時刻、本文の最初の行を120文字まで出す。
本文は`displayableIssueText`を通し、プレーンテキストで描く。

行の「詳細」は、要対応の画面で同じ通知を選んだ経路(`/console/?notice=<id>`)へのリンクである。
詳細には、本文の全文、対象へのリンク、起きたことと次の操作が出る。
Consoleから解決できる種類の行は、「詳細と解決」と書く。解決は、その詳細で行う。
この節では、解決しない。同じ操作を2か所に置くと、取得の更新が食い違うためである。

### 解決済みの通知

解決した通知の履歴を出す。
人が解決したものを先に、DBの掃除が解決したものを後にし、それぞれ解決の新しい順に並べる。機械が片付けた大量の通知で、人の解決の履歴が押し出されないためである。
並べるのはbackendで、画面は返った順に描く。
行には、通知の種類の日本語名、解決の時刻、解決した主体、本文の最初の行を出す。行を開くと、本文と発生の時刻を読める。
本文は`system_status`が先頭の500文字で切るので、500文字に達した本文には、先頭だけを表示している旨を添える。
解決した主体は、DBの掃除、自己更新、Issueの取得、PRの取得なら処理の名前に「(自動)」を添える。それ以外は、記録された名前を文字のまま出す。記録が無ければ「記録なし」にする。
解決の時刻が記録されていない通知は、「解決の時刻の記録なし」と出す。
解決済みの通知は、解決から既定30日で消えるので、履歴もその間のものである。

### 監査の失敗

失敗した監査の一覧である。
再実行できない失敗なので、要対応の画面では再実行の対象にせず、件数のカードで知らせてこの節へ案内する。
データは、`summary`の失敗のうち、作業項目の種類が監査のものを使う。要対応の画面と同じ取得とキャッシュを共有する。
`summary`の定期の取り直しがあるので、この節も画面を開いている間に更新される。
`summary`の失敗は新しい順に上限まで取る。失敗の件数が取得した件数より多いときは、古い監査の失敗は表示していない場合があると添える。

行には、監査の題名(作業項目の詳細へのリンク)、状態、失敗の時刻、ジョブへのリンク、失敗の内容を出す。
内容は、実行の出力でIssueの文字を含みうるので、プレーンテキストで描く。500文字で切られているときは、切られている旨とジョブのログで全文を読める旨を添える。
再実行のボタンは置かない。次の定期の監査が、失敗した期間を扱う。
内容は`src/lib/failureView.ts`の`describeFailure`を、要対応の失敗の詳細と共有する。

### 作業項目に紐づかない失敗

定期のジョブなど、作業項目を持たないジョブの失敗を、直近7日の分だけ新しい順に出す。
作業項目が無いので、要対応の画面にも作業項目の画面にも出ない。この節だけが知らせる。
行には、フローとステップ、失敗の時刻、ジョブへのリンク、失敗の内容を出す。
ジョブへのリンクは、ジョブのIDがUUIDの形のときだけ張る。
内容の扱いは、監査の失敗と同じである。
再実行の操作は置かない。

表示する内容は、`src/lib/systemView.ts`の純関数が決める。

### 起動の関係

スケジュール、script、flow、人の操作が何を起動するかを、1枚の図に出す。
データは`console/src/generated/flow-graph.json`で、`mise run docs:gen`が次の元から作る。
`scripts/docs-gen.ts --check`が古さを検出するので、CIの`check`が、データを更新し忘れたPRを止める。

- `scripts/launch-graph.ts`の起動辺の表。scriptがflowを起動する関係と、人の操作
- `f/factory/*.schedule.yaml`の実行先とcron。有効で、flowを起動するscriptかflowを実行するスケジュールだけを載せる
- `f/factory/*__flow/flow.yaml`の概要とモジュール。flowが実行するステップのうち、flowを起動するscriptだけを辺にする

ノードはスケジュール、script、flow、人の操作の4種類で、辺はスケジュールからの起動、scriptによるflowの起動、人の操作による起動、flowのステップの4種類である。
人の操作には、フォームからの実行と、再実行、今すぐ監査、承認と却下のConsoleの操作がある。
並びは入力の順に依らず、同じ元から同じJSONができる。

JSONはViteがそのままバンドルに取り込む。
`src/lib/flowGraph.ts`の`parseFlowGraph`が形を確かめ、ノードのidの重複や存在しない辺の端があればnullを返す。
nullのときは、節に読み込めなかった旨を出し、図は描かない。
座標は`src/lib/flowGraphLayout.ts`の`layoutFlowGraph`が決める。
`src/lib/flowGraphXml.ts`の`flowGraphToDrawioXml`が、その座標からdraw.ioのXMLを作る。
どちらも純関数で、XMLは`DrawioFrame`に渡す。
箱は3列に並べる。1列目はscriptを起動するスケジュールとConsoleの操作、2列目はscriptと、flowを直接起動するスケジュールと人の操作、3列目はflowである。
どの辺も隣り合う列を結ぶので、辺が他のノードの箱の上を通らない。
辺は直線で引く。同じ箱の同じ側につく辺は、つなぎ先の高さの順に、箱の高さを等分した位置へ割り当てる。多数の辺が列の間の1本の線に重ならないためである。
辺の線は、scriptがflowを起動する関係を実線、時刻や人の操作による起動を破線、flowのステップを色の違う点線にして見分ける。
ノードは31個あり、図の目安の15個を超える。機械生成の全体の見取り図で、分割すると、起動の経路を1枚で追う目的を失うため、1枚にまとめる。
ラベルはHTMLとして、続いてXMLの属性値としてエスケープする。リンク、`placeholders`、HTMLの属性は出さない。
XMLの大きさが`DrawioFrame`の上限を超えると、図は描かず、大きすぎる旨を出す。

図に出ない関係がある。scriptからscriptの起動は含まない。たとえば`self_update`が`auto_retry_stale_image`を起動する関係である。
そのため、入ってくる辺を持たないscriptも図に出る。節の説明にも同じ旨を書く。
無効のスケジュールは、図に載せない。

図は取得も実行の状態の重ね合わせも持たない。コードから読み取った構造だけを示す。

## 分析の画面

レポートの画面に、分析の区画を置く。
区画は部品`AnalyticsReports`で、画面の見出しと余白は持たない。
部品は、期間、期間を変える関数、3つの取得の結果を受け取り、描画だけを受け持つ。
Claudeの実行のコスト、承認の統計、リードタイムを、グラフと表で出す。
監査の区画と同じ画面に並ぶので、期間と3つの取得はレポートの画面が持つ。

3つの数値は、`console_query`の`agent_cost_daily`、`approval_stats`、`lead_time`viewから、別々に取る。
集計の期間は直近7日、30日、90日から選び、初期値は30日である。
期間はキャッシュのキーに含めるので、切り替えている間に別の期間の値は出ない。
定期には取り直さない。
取得から60秒を過ぎた値は、タブに戻ったときと画面を開き直したときに取り直す。
分析の取得と期間は、レポートの画面が持つ。
見出しの更新のボタンは、監査の一覧と合わせた4つを取り直す。
行数の上限は2000件で、backendが受け付ける最大にしてある。
行数が上限に届いたときは、古い日が含まれていない可能性を区画に添える。

区画は、次の数値を出す。

- 日別コスト(USD)と日別の実行件数。段階とモデルをまとめた日ごとの合計で、費用が記録されていない行は0として足す
- 一発承認率。1回目の判断のうち承認の割合で、承認か却下の判断が1件も無いときは「データなし」にする
- 差し戻し分布。試行ごとの却下件数
- 状態別の平均リードタイムと件数。平均の長い順に並べ、状態は日本語にする

日別のグラフは、横軸に期間の全日を等間隔に並べる。
間隔を日数に比例させ、空いた日があることを読めるようにするためである。
実行の無い日は値0で、棒を描かない。0より大きい日は、最大との差が大きくても最小の高さを確保する。
題には「UTC」を添えて、表の見出しと日の基準をそろえる。
表は、実行のあった日だけを出す。
行数が上限に届いたときは、古い日が切れている。
取れた最古の日より前は0で補わず、最古の日そのものもグラフから外す。
最古の日は、段階とモデルの行が途中で切れて、合計が実際より小さい可能性があるためである。

日は、viewが日付で丸めた時刻をUTCのまま読む。
端末のタイムゾーンで読み替えると、日がずれるためである。
viewの日の丸めは、DBの接続のタイムゾーンで決まる。
開発環境のデータベースサーバーの既定のタイムゾーンはUTCである。
接続ごとに別のタイムゾーンを設定した場合は、日の丸めがずれる。
表の日付は`2026-10-08`の形、グラフの横軸は`10/8`の形で出す。

グラフは自前のSVGで描き、グラフのライブラリを使わない。
色は固定のクラスで決め、棒の座標だけを計算する。実行時の入力から色やstyleを作らないためである。
グラフは題だけを読み上げの対象にし、数値は必ず添える表で読ませる。
日のような連続する並びのグラフは、置かれた領域の幅を測って合わせる。文字の大きさは変えず、棒の間隔だけが広がる。
状態のような別々の項目のグラフは、項目が少なく、広げると棒が離れすぎるので、幅の上限を置く。
棒の上の値と横軸のラベルは、文字の幅の見積もりが1本分の幅に収まるときだけ出す。
幅は、半角を文字の大きさの0.6倍、それ以外を1倍として数える。
収まらないとき、日のような連続する並びは、横軸のラベルを間引く。
間引くときは最後の棒を基準にして、いちばん読みたい最新の日にラベルを残す。
ラベルが描画領域の端を越えるときは、その端に寄せて置き、はみ出して切れないようにする。
状態のような別々の項目は、間引くと棒が何か分からなくなるので、横軸のラベルを出さず、表で読ませる。
最大の棒の上には、値のラベルの置き場を残す。
座標、幅、ラベルの収まりは`src/lib/barChart.ts`、集計、日の補完、整形は`src/lib/analytics.ts`の純関数が決める。
期間の終わりは、端末の時計の日(UTC)にする。
期間の前後3日以内の日に行があるときは、その日まで範囲を広げて含める。端末の時計がbackendと少しずれても、行を捨てないためである。
それより遠い日は並べない。遠い日付の行が1件あるだけで、並べる日数が際限なく増えるのを防ぐためである。
グラフに渡す系列は、純関数`chartSeries`が表と別に作る。
数値の表は、スクロールする領域に名前を付けて、キーボードで焦点を当てられるようにする。

3つの区画は、取得中、失敗、空、値ありを区別して出す。
取得中は値がまだ無いので、空の表示を出さず、読み込み中の枠を出す。
失敗は、401を除いて区画の中に原因と再取得のボタンを出す。401は画面上部のバナーが知らせる。
再取得に失敗しても前回の値があるときは、空であっても、値を出したまま、古いことと「もう一度取得する」を添える。

3つのviewの型は、backendの同名の行に合わせてある。
`tests/scripts/console_analytics_contract.test.ts`が、backendの変換結果が型ガードを通ることと、日がUTCの日付として読めることを確かめる。

## 作業項目の画面

この画面は、進捗の節を持つ。
最終更新と更新のボタンは、画面の見出しに置く。
ボタンは、進捗と要件定義の取得を取り直す。

進捗は、`console_query`の`pipeline`viewから、直近90日に更新された作業項目を新しい順に500件まで取る。
自動では取り直さず、見出しの更新で取り直す。
取得が500件に達したときは、古い行を取得できていない場合があると節の見出しに添える。
取得の失敗は、表の位置に再試行のボタン付きで出す。ログイン切れ(401)は、上のバナーが知らせる。

表は1行が1つの作業項目で、次の列を持つ。

| 列 | 内容 |
| --- | --- |
| 作業項目 | 番号。作業項目の詳細へのリンク |
| 題名 | Issueの題名。無ければ「-」 |
| 種別 | Issue、PRレビュー、PRの修正、監査、dependabotの更新 |
| 状態 | 日本語の名前のバッジ。知らない状態は「不明な状態(生の値)」と書く。色は承認待ちが警告、完了に近いものが成功、失敗と人の対応待ちが失敗、それ以外は枠の無い灰色 |
| リポジトリ | owner/repo |
| Issue/PR | IssueとPRへのGitHubのリンク。両方あるときは縦に並べる |
| ブランチ | 実装用のブランチ |
| 試行 | 要件定義の試行の番号。却下や再実行による作り直しで増える |
| 修正回数 | PRの修正のラウンド数 |
| 更新 | 相対時刻。日本時間の絶対時刻をツールチップに添える |
| 書類 | 要件定義書へのリンク。Issueの作業項目だけに出す |

色だけに頼らず、状態の名前を隣に出す。

題名の列には最小幅を与え、1行に数文字で折り返して行が縦に伸びるのを防ぐ。
最小幅は、表のセルでなくセルの中身に与える。表のセルへの最小幅は、効き方が仕様で定まっていないためである。
ブランチの列にも最小幅を与え、列が戻った直後に文字が何行にも折り返すのを防ぐ。
表を包む領域が88rem(1408px)に満たないときは、ブランチ、試行、修正回数の列を隠し、題名、状態、更新を先に確保する。
全列を出したときの表の最小幅は、実測で約87.5remだった。測った条件は、実データでリポジトリ名が約20文字である。88remは、これに余裕を足した値である。
閾値が実測より低いと、列が戻った直後に横スクロールが出る。リポジトリ名がさらに長いと、88remでも横スクロールになることがある。
幅は画面でなく領域で測る。サイドバーを開閉すると表の使える幅が変わるためである。
本文の幅は、画面が1920pxでサイドバーが開いているとき約1598px(約99.9rem)で、全列を出す。
画面が1440pxのときは、サイドバーが開いていても畳んでいても本文が88remに満たず、3列を隠す。
隠した列も検索の対象に残る。ブランチの語で絞り込むと、列が見えなくても当たる行が残る。
隠れた列の見出しは押せないが、その列で並べた順は残る。
灰色のバッジは、枠を持たず、主の文字色を薄く重ねた地に主の文字色を載せる。

絞り込みは、状態、リポジトリ、検索の3つで、すべてに当たる行を残す。
状態とリポジトリの選択肢は、取得した行にあるものだけを並べる。状態は作業の進む順、リポジトリは名前順である。状態の選択肢も、バッジと同じ表記にする。
検索は、空白で区切った語がすべて当たる行を残し、大文字小文字を区別しない。
対象は、番号、題名、ブランチ、リポジトリ、IssueとPRの番号、状態と種別の日本語名である。
絞り込みが1つでも効いているときは、件数に全体の件数を添え、「条件を消す」ボタンを出す。

並び替えは、番号、状態、リポジトリ、試行、修正回数、更新の見出しを押して行う。
既定は、更新が新しい順である。
同じ列をもう一度押すと向きを反転し、別の列を押すと、数と時刻は大きい方から、状態とリポジトリは先頭から始める。
状態は作業の進む順に並べる。知らない状態は、向きを変えても最後に置く。
並びが同じ行は、番号が大きい方を先にする。向きを反転しても、同点の順は変わらない。
選んだ状態やリポジトリが再読み込みで表から消えたときは、その条件だけを「すべて」に戻す。
絞り込みと並び替えの状態は画面の中だけに持ち、URLには持たない。

題名とブランチは信頼できない文字列なので、見えない文字と書字方向の制御文字を落としてから、文字として描く。
リンクは、GitHubのIssueかPRのURLの形のときだけ張る。
IssueのURLが壊れているときは、Issueのリンクだけを出さず、PRのリンクは残す。
絞り込み、並び替え、リンクの規則は`src/lib/pipelineView.ts`の純関数にある。

行の番号は`/console/items/:id`へ、「要件定義」は`/console/items/:id/requirements`へ移る。

進捗の節の幅が狭いとき(56rem未満)は、横にスクロールする表の代わりに、1件を1枚のカードで出す。
画面の幅ではなく節の幅で切り替えるのは、サイドバーが幅を取る分を数えるためである。
カードに出すのは、番号、題名、状態、種別、リポジトリ、Issue/PR、PR、更新、要件定義へのリンクである。
ブランチと回数は、詳細の画面で読めるので出さない。
絞り込みは表と同じ操作で行う。
並びは表の並び替えによらず、常に更新が新しい順にする。カードには並び替えの操作を置かない。

## 作業項目の詳細の画面

作業項目1件の概要と履歴を、読み取り専用で出す。
再実行や承認などの書き込みは置かない。止まった作業項目の再実行は、要対応の画面で行う。
要対応の失敗の詳細と、進捗の表の行の番号から、この画面へ移る。

取得は`console_query`の`work_item_detail`で、作業項目の番号を渡す。
応答は`src/api/guards/workItemDetail.ts`の型ガードを通す。
形が崩れた応答は、一部だけを使わず、全体を`invalid_response`にする。
backendの型との一致は、`tests/scripts/console_item_detail_contract.test.ts`が確かめる。
自動では取り直さず、キャッシュは30秒で古くなる。
見出しの更新で取り直す。

存在しない作業項目の番号は、backendが「作業項目が無い」という文のジョブの失敗で返す。
Consoleは、接頭辞(`console_query:`)と要求した番号まで合わせてその文を見分け、取得の失敗ではなく「見つかりませんでした」を出す。
実機のWindmillが返す失敗の本文がこの文のままかは、確かめていない。違えば、汎用の取得失敗の表示になる。
番号が正の整数でないときは、取得せずにその旨を出す。

### タブ

開くタブはURLの`?tab=<名前>`に持つ。名前が無いか知らない名前なら、概要を開く。
名前は、概要が`overview`、要件定義が`requirements`、ラウンドが`rounds`、承認の履歴が`approvals`である。
タブは矢印キーとHome、Endで移れる。Alt、Ctrl、Metaを押している間は、ブラウザの操作を奪わないよう移らない。

| タブ | 内容 |
| --- | --- |
| 概要 | 状態と注記、種別、リポジトリ、IssueとPRへのリンク、ブランチ、試行、修正回数、実行の費用、作成と更新の時刻。続けて失敗の記録と状態の遷移。タブの名前と重なる見出しは置かない |
| 要件定義 | 試行ごとの要約、承認の状態、要件定義書の画面へのリンク。Issue以外の作業項目には要件定義が無いと伝える |
| ラウンド | 実装のラウンドを試行ごとに古い順で、PRのレビューとPRの修正を新しい順で並べる。レビューと修正が無いときは、見出しと一文の1行にする |
| 承認の履歴 | 承認依頼を新しい順に並べ、状態、依頼と決定の時刻、決定者、理由を出す |

承認の履歴は、却下の理由と決定者を読む場所である。
要件定義の承認依頼は対象の試行を、Issue提案は提案の題名を添える。
理由や決定者が記録されていないときは、そう書く。

失敗の記録は、フローとステップ、時刻、失敗の文を新しい順に出す。
失敗の文はbackendが4000文字で切るので、その長さに達したときは切っていると添える。
状態の遷移は、遷移前後の状態、注記、時刻を新しい順に出す。
要件定義書へのリンクは、同じ書類を指すものが重ならないよう、試行ごとに1つだけ置く。
最新の試行のリンクは試行の番号を付けず、常に最新の書類を指す。
実装のラウンドは、差分の規模をファイル数、追加の行数、削除の行数の言葉で出す。
ラウンドのタブは、PRのレビューと修正の本文を持たず、件数と結果だけを出す。
実装のラウンドは、検査コマンドの出力を持たない。

backendは、履歴を新しい順に切って返す。上限は、失敗が20件、状態の遷移が100件、PRのレビューと修正がそれぞれ50件である。
件数が上限に届いた履歴には、新しい順に何件まで表示していて、それより古い記録は表示していないと添える。
上限の値は`src/lib/itemDetailView.ts`の`DETAIL_LIMITS`にあり、`console_query`の上限に合わせる。

### ジョブのリンク

失敗と遷移のジョブは、`JobLink`でWindmillのジョブの画面へ移る。意味が違うので、文言を分ける。

| 行 | `job_id`のリンク | `root_job_id`のリンク |
| --- | --- | --- |
| 状態の遷移 | ステップのジョブ(遷移を起こしたステップ) | フローのジョブ(そのステップを含むフローのルート) |
| 失敗の記録 | 失敗したジョブ(記録に渡されたジョブ。フローの失敗ではフローのルート) | 記録したジョブのフロー(記録したジョブのルート) |

2つが同じジョブなら、リンクは1つにする。
リンク先のジョブの画面が実機で開けるかは、確かめていない。

### 表示の規則

題名、ブランチ、状態の注記、要約、却下の理由、決定者、失敗の文は、起票者や実行ログに由来する。
見えない文字と書字方向の制御文字を置き換えてから、プレーンテキストとして描く。
状態の注記が、その作業項目のIssueかPRのURLだけのときは出さない。同じリンクが「Issue」「PR」の行にあるためである。
別のURLだけの注記は、どの行にも出ていないので残す。
状態の遷移の注記は、URLだけでも出す。PRを作り直したとき、古いPRを示す唯一の記録になるためである。
実装のラウンドの要約と、要件の不足の報告は、バッククォートで囲んだ範囲をコードの書式で描く。
Markdownは解析せず、囲み以外の文字は記号も含めてそのまま出す。HTMLとして読む経路が無いためである。
二重のバッククォートの囲みは扱わず、記号の位置がずれることはあっても文字は失われない。
GitHubのリンクは、IssueかPRのURLの形のときだけ張る。形が違えば、番号だけを文字で出す。
PRのURLが使えないときは、リポジトリとPRの番号から組み立てた同じ形のURLを使う。
作業項目の状態、ラウンドの種類と結果、レビューの判定、修正の結果が表に無いときは、「不明」に生の値を添える。
承認依頼の状態など、ほかの値は「不明な状態」などの決まった文言にする。
知らない値でも詳細の全体が消えないようにして、backendが先に新しい値を反映した間も読めるようにするためである。
表示の規則は`src/lib/itemDetailView.ts`の純関数にある。

## ジョブの画面へのリンク

作業項目の遷移と失敗は、動いたジョブのIDを持つ([作業項目の状態とリース](work-items.md)の「ジョブの記録」)。
`src/lib/jobLink.ts`の`jobRunUrl`が、IDからWindmillのジョブの画面のURLを作る。
`src/components/JobLink.tsx`の`JobLink`が、そのURLへのリンクを描く。リンクは別のタブで開く。
`work_item_detail`の遷移と失敗の行の型ガードは、`src/api/guards/workItemTransitions.ts`と`workItemFailures.ts`にある。
`tests/scripts/console_work_item_jobs_contract.test.ts`が、backendの変換結果がこれらの型ガードを通ることを確かめる。

IDはDBに記録された値で、信頼できない入力として扱う。
UUIDの形のものだけを、固定の形のパス`/run/<job_id>`に入れる。形が違えばリンクを出さない。
URLの組み立てに、IDから先の文字列を使わない。

リンクは、同じオリジンの相対パスにする。
ConsoleはWindmillと同じオリジンで配信するためである。

URLにワークスペースの指定(`?workspace=`)を付けない。
指定の無いURLをWindmillがどのワークスペースで開くかは、確かめていない。
別のワークスペースを選択中だと、ジョブを開けないことがある。
単一のワークスペース(`factory`)の運用を前提にする。

`JobLink`は、要対応の失敗の詳細と、作業項目の詳細の失敗の記録と状態の遷移に組み込んである。
要対応の失敗の詳細は、作業項目の詳細(`/items/<id>`)へのリンクを持つ。

## 画面を足す手順

1. 画面を`src/screens/<入口>/`に置く。
2. `src/app/screens.ts`の表に、入口か詳細の経路を1行足す。入れ子の経路は`children`に書く。
3. 表示する語を`src/lib/labels.ts`に足す。
4. 判定は純関数にして、`src/lib/`に置き、テストを書く。
5. 見出し(`PageHeader`)に、画面が自分のクエリから作った`refreshStatusOf`の結果を渡す。
   取得を複数持つ画面は、`refreshStatusOfAll`で1つにまとめて渡す。
   取得するデータを持たない画面は渡さない。

## 配信の構成

| 要素 | 役割 |
| --- | --- |
| `console/` | Consoleのソースコード(Vite + React) |
| `.github/workflows/console-dist.yml` | `main`へのpushで、`console/`を組み立てて成果物`console-dist`として上げる。成果物を上げるのはこのワークフローだけである |
| `ci.yml`の`console`ジョブ | PRで、`console-dist.yml`と同じ手順で組み立てられることを確かめる。成果物は上げない。型検査、lint、テストは`check`ジョブが担う |
| `infra/console_fetcher/` | 成果物を検証して、名前付きボリューム`factory_console`に書く |
| Caddy | `factory_console`を読み取り専用でマウントし、`/console/`で配信する |

`factory_console`は、どのworkerにも書き込みでマウントしない。
読む必要があるConsole用のworker(`windmill_worker_console`)にだけ、読み取り専用で渡す。
配信中のファイルを書き換えられると、運用者のブラウザに改ざんが居座るので、書けるのは取り込み専用の`console_fetcher`だけにする。

## console_fetcherのコンテナ

- uid 1000(rootでない)、`read_only`、`cap_drop: [ALL]`、`no-new-privileges`で動く。
- 専用のnetwork`console_egress`につなぐ。このnetworkからは、DBとWindmillに届かない。
- 第三者のパッケージを入れない。
- dockerには外への行き先をドメインで絞る仕組みが無い。そのため、コードが接続する先を`api.github.com`と、そこからリダイレクトされたAzureのblob storage(`*.blob.core.windows.net`、`https:`のみ)に限る。
- 成果物の取得先へはトークンを送らない。

## 取り込みの検証

`console_fetcher`は、`console-dist.yml`の実行の成果物`console-dist`だけを取り込む。
`ci.yml`のジョブは、同名の成果物を上げても取り込まれない。
権限の違うジョブが成果物を上げ直して、配信物をすり替えるのを防ぐためである。

実行の一覧は、ワークフローのファイル`console-dist.yml`で絞って取得する。
取得した実行は、次をすべて満たすものだけを候補にする。
APIの絞り込みに頼らず、取り込み側でも確かめる。

1. ワークフローのパスが`.github/workflows/console-dist.yml`で、名前が`Console dist`である。
2. ブランチが`main`で、イベントが`push`である。
3. 状態が完了で、結論が成功である。
4. commitが40桁の16進数である。

候補を新しく作られた順に見て、同じcommitの`ci.yml`も成功している最初の実行を選ぶ。
`ci.yml`の確認は、`ci.yml`の実行の一覧にcommitを指定して取得し、次をすべて満たす実行があるかで決める。
こちらも、APIの絞り込みに頼らず取り込み側で確かめる。

1. ワークフローのパスが`.github/workflows/ci.yml`で、名前が`CI`である。
2. ブランチが`main`で、イベントが`push`である。
3. 状態が完了で、結論が成功である。
4. commitが、候補のcommitと一致する。

`console-dist.yml`は組み立てしか確かめないので、型検査、lint、テスト、秘密情報の走査を担う`ci.yml`の成功も条件にする。
`ci.yml`が実行中か失敗しているcommitは飛ばして、その前の候補を選ぶ。
確かめる候補は、新しい順に5つを上限にする。
候補を見ている途中で配信中の版に当たったら、その版を選んで探索を止める。
配信中の版より古いcommitに、版が戻らないためである。
戻して取り消した版(`revoked.json`のsha)は、候補から外す。
どの候補も満たさなければ、取り込まず今の版を配信し続ける。

`main`という名前のタグの実行は、`main`のブランチの実行と見分けがつかない。
そのため、両方のワークフローが同じcommitで成功していることを求める。
ただしこの照合だけでは、タグを作れる人は防げない。残るリスクは[セキュリティ](../security.md)にある。

選んだ実行の成果物を、書く前に次をすべて確かめる。

1. 成果物の元のcommitが、その実行のcommitと一致する。
2. zip全体のsha256が、GitHubの`digest`と一致する。
3. 展開した全ファイルのsha256が、`manifest.json`と一致する。
4. マニフェストが、その実行のcommitのものである。

zipは自前のreaderでメモリ上に展開する。
`..`、絶対パス、symlink、通常のファイル以外、暗号化、zip64は拒む。

## CIの組み立て

`console-dist.yml`が、`main`へのpushのたびに組み立てて、成果物を上げる。
変更したパスによらず毎回動かす。
`console_fetcher`が、そのcommitの成果物を取り込むためである。
PRとタグのpushでは動かさず、`ci.yml`のジョブを足さない。
組み立ての手順は、このファイルに直接書き、別のファイルに分けない。
Factoryのトークンは`.github/workflows/`を書けない。
composite action(`.github/actions/`)は書けるので、分けると配布物がその変更に左右されるためである。

- ワークフローの権限は、リポジトリの読み取り(`contents: read`)だけにする。成果物の書き込みには、`GITHUB_TOKEN`の書き込み権限を使わない。
- ジョブは1つで、`console-dist.yml`にほかのジョブやトリガーを足さない。
- 実行を取り消さない。取り消した実行は成功しないので、そのcommitの成果物が欠けるためである。
- 同じ実行を「Re-run all jobs」で上げ直しても失敗しないように、成果物は上書きで上げる。

`ci.yml`の`console`ジョブは、PRで同じ手順を書き写して動かし、組み立てとビューアの取得を確かめる。
2つの手順が食い違わないことは、テストが確かめる。
成果物は上げない。
`scope`ジョブの`console`のフラグが偽のとき、このジョブを飛ばす。
型検査、lint、テストは`check`ジョブの`mise run check`(`console:check`)が担い、どちらのワークフローも重ねて実行しない。
判定の詳細は[セットアップ](../setup.md)の「CIの実行の範囲」にある。

- miseで入れるツールは、bunと、viteとtscを動かすnodeだけにする。ほかの`[tools]`とそのinstall scriptを動かさない。
- miseのキャッシュを読み書きしない。
- ルートと`console/`の依存は`bun install --frozen-lockfile --ignore-scripts`で入れ、依存のinstall scriptを実行しない。
- `console/bun.lock`は`scripts/check-console-lockfile.ts`で検査する。registry由来でsha512のintegrityが付いた依存だけを許す。git、GitHub、tarballのURL、`console/`の外を指す`file:`と`link:`、`trustedDependencies`は拒む。
- 組み立ての後、マニフェストを書く前に、draw.ioのビューアを取得して`dist/drawio/`に置く。詳細は「draw.ioの図」にある。

## 配信の経路

Caddyは、`/console/`の下を次の経路で返す。
`factory_console`の他のファイル(`pin`、`revoked.json`、`history.json`など)は配信しない。

| パス | 返すもの | キャッシュ |
| --- | --- | --- |
| `/apps/get/f/factory/factory_console`と`/apps_raw/get/f/factory/factory_console`(配下を含む) | 固定の`/console/`への302のリダイレクト。パスとクエリは行き先に写さない | `no-store` |
| `/console` | `/console/`への308のリダイレクト。クエリ(`?approval=<id>`など)は保つ | - |
| `/console/status.json` | ボリューム直下の`status.json`。無ければ404 | `no-store` |
| `/console/assets/*` | 共有の`assets/`。無ければ404 | 長期(immutable) |
| `/console/drawio/*` | `current/`の`drawio/`。ビューアと受け口。無ければ404 | 長期(immutable) |
| `/console/drawio.html` | `current/`の`drawio.html`。無ければ404 | `no-cache` |
| `/console/*` | `current/`のファイル。無いパスは`index.html` | `no-cache` |

旧Consoleへの規則は、`/console/`の経路より先に評価する。
旧Consoleの編集画面(`/apps/edit/...`)とAPIは飛ばさない。
この規則は、過去のリンクが残り続けるため、旧Consoleのappを消した後も残す。
302にするのは、ブラウザに転送を覚えさせないためである。転送を覚えると、規則を変えたときに古い行き先へ飛び続ける。

`/console/manifest.json`は、`current/`の`manifest.json`である。
`status.json`は`state`、`sha`、`checked_at`、`error`の4項目だけを持つ。

## 開いたままのタブの版の確認

開いたままのタブは、`manifest.json`と`status.json`を読んで、自分の版が配信中かを確かめる。
実装は`console/src/lib/`と`console/src/`にある。

- `lib/referencedUrls.ts`: 画面が参照するscriptとstylesheetのURLの収集
- `lib/release.ts`: 判定
- `lib/releaseCheck.ts`: 取得と判定の1回分
- `lib/releaseSchedule.ts`: 確認の間隔、タブの可視状態、動的importの失敗での即時の確認、打ち切り、失敗時の間隔の延長
- `useReleaseWatch.ts`: 上の部品をDOMにつなぐ

### 確認の時機

確かめるのは、表示した直後と、その後60秒ごと、タブが見える状態に戻ったとき、動的importが失敗したときである。
動的importが失敗すると、Viteが`window`に`vite:preloadError`を出す。
版の入れ替わりで古いchunkが消えると、このimportは失敗する。
そのイベントを受けると、次の周期を待たずに確かめる。
タブが見えているかは見ない。
失敗は版が外れたことの手掛かりで、見えないタブでも確かめる意味があるためである。
前の確認の開始から2秒は空ける。空いていなければ、空くまで待ってから確かめる。
失敗が続けざまに起きても、確認が続けて走らないためである。
待っている間に何度来ても、確認は1回にまとめる。
確認の実行中に来た要求は、何度来ても、実行が終わった後に1回だけやり直す。
実行中の確認が、失敗より前に始まっていて、版の入れ替わりを見落とす場合があるためである。
やり直しも、前の確認の開始から2秒を空ける。
イベントの既定の動作は変えない。失敗したimportは、そのまま例外になる。
unmount後は確かめず、やり直さない。
Consoleの画面は、経路ごとに動的importで読み込む。
版が入れ替わった後に、古いchunkを読み込む画面へ移ると、このimportが失敗して`vite:preloadError`が出る。
すると確認が走り、版が外れていれば帯が出る。
失敗した画面の位置には、`RouteError`が再読み込みを案内する。
フックがマウントされる前に起きた失敗は拾わない。

### 自分の版の見分け方

自分の版は、画面が参照するscriptとstylesheetのうち、`/console/assets/`の下にあるファイル名の集合で見分ける。
確かめるたびに、DOMから集合を取り直す。
後から読み込んだchunkの参照も拾うためである。
基準のオリジンと違うURLと、`%`を含む名前は集合に入れない。
集合が空の回は、何も取りに行かず、前回の判定を保つ。
開発サーバーは`index.html`の`/console/assets/`の参照にbaseを前置するので、集合が空になる。

`index.html`に直書きした`/console/assets/`の参照は、すべて`console/public/assets/`に置く。
Viteが`dist/assets/`に写し、`manifest.json`に載せるためである。
載らない参照があると、再読み込みしても消えない帯が出る。

ビルドに版のshaは埋め込まない。
版ごとに中身が変わると、`console_fetcher`の中身による同一判定と`revoked.json`の照合が働かなくなるためである。

### 判定

| 状況 | 表示 |
| --- | --- |
| 集合のファイルがすべて`manifest.json`にある | 出さない |
| 1つでも無く、`state`が`pinned`でなく、無かったファイルのどれも404でない | 再読み込みを促す控えめな帯 |
| 1つでも無く、`state`が`pinned`か、無かったファイルのどれかを取ると404 | 再読み込みを求める目立つ色の帯 |

`manifest.json`を取れないときは、前回の判定を保つ。
`status.json`を取れなくても、帯は出す。
一度目立つ色の帯を出したタブは、帯を下げない。

## ブラウザ側のヘッダー

`/console/*`の応答(404とfallbackを含む)だけに、次のヘッダーを付ける。
Windmill(`/`と`/api/*`)には付けない。

- `script-src`を`/console/assets/`に絞ったCSP。`'unsafe-inline'`と`'unsafe-eval'`は許さない。
- `frame-ancestors 'none'`と`X-Frame-Options: DENY`
- `X-Content-Type-Options: nosniff`
- `Referrer-Policy: same-origin`
- `Cross-Origin-Opener-Policy: same-origin`

Trusted Typesは`Content-Security-Policy-Report-Only`で様子を見る。

`/console/drawio.html`と`/console/drawio/`の下だけは、別のヘッダーを付ける。
内容は「draw.ioの図」にある。

## CSPとCaddyのパスの解釈の違い

ブラウザは、パスの`%2f`を区切りとみなさない。
そのため、`/console/assets/..%2f..%2fapi/...`は`script-src`の`/console/assets/`に合う。
一方Caddyは、区切りに戻して正規化する。
そのままでは`/api/...`や`/ws/...`としてWindmillや`windmill_extra`へ転送され、その応答をscriptとして読ませる経路になる。
CSPはパーセント符号を戻してから比べるので、`/%63onsole/assets/...`のように文字を符号化したURLも`/console/assets/`に合う。

そこでCaddyは次のように扱う。

- パーセント符号を戻しただけで正規化していない元のパスが`/console/`で始まる要求は、どの転送先(`windmill_server`、`windmill_extra`)にも渡さない。Consoleの経路で返すか、404にする。`/console`そのものを含み、大文字小文字と先頭の`/`の重複は区別しない。
- Caddyは`handle`をmatcherの種類で並べ替える。そのためCaddyfileでは`route`で順序を固定し、Consoleの経路とこの404を、どの`reverse_proxy`よりも先に評価させる。
- Consoleの経路では、生のパスに`%2f`か`%5c`(大文字小文字を問わない)があれば400にする。

Consoleの画面のURLに、符号化した区切りを使ってはいけない。

### 開くときのホスト名

`script-src`は、ブラウザが使ったスキーム、ホスト、ポートを含む`/console/assets/`のURLで絞る。
CSPのパスには、オリジンが要るためである。
IPv6のリテラル(`http://[::1]:8080/console/`など)で開くと、このURLの形が崩れてscriptが拒否される。
IPv4のアドレス(`127.0.0.1`など)かホスト名で開く。

## draw.ioの図

要件定義書の図は、最上位のページではなく、隔離したiframeの中で描く。
何を守るかは、[セキュリティ](../security.md)の「draw.ioの図の描画」にある。
要件定義書の画面が、本文の図ごとに`DrawioFrame`で描く。
システムの画面の起動の関係の節も、組み立てたXMLを`DrawioFrame`で描く。XMLはリポジトリ由来で、同じ隔離したiframeを通す。

| ファイル | 役割 |
| --- | --- |
| `console/drawio-viewer.json` | ビューアの版、commit、取得元のURL、sha256の固定。保護パス |
| `console/scripts/drawio-viewer.ts` | 固定の値の検査と、取得したビューアの照合(`verifyViewer`)。純粋関数 |
| `console/scripts/fetch-drawio-viewer.ts` | CIが呼ぶ。取得して照合し、`dist/drawio/`に書く |
| `console/public/drawio.html` | 図を描くページ。scriptはすべて外部のファイルで、通常のscriptとして読む |
| `console/public/drawio/drawio-frame-*.js` | ページの中の受け口。素のJavaScriptで、ビルドを通らない |
| `console/src/lib/drawioMessages.ts` | 親が送るメッセージの組み立てと、iframeから届いたメッセージ(高さ、失敗の種類)の検査。純粋関数 |
| `console/src/lib/drawioFrameState.ts` | iframeの状態の遷移(load、メッセージ、応答なし、XMLの差し替え)を`(state, event) => state`で表す。純粋関数 |
| `console/src/components/drawio/DrawioFrame.tsx` | 親の部品。どの画面からも使える |

### ビューアの取得

ビューアはリポジトリに入れない。
`console-dist.yml`の手順は、組み立ての後に`fetch-drawio-viewer.ts`を動かす。
ビューアは`dist/drawio/drawio-viewer-<sha256の先頭8桁>.js`に書く。
取得したバイト列のsha256が固定の値と違えば、何も書かずに失敗する。
URLはリダイレクトを許さず、パスはcommit配下のビューア1ファイルに限る。
応答は10MBまでで、一時的な失敗(ネットワーク、429、5xx)は、待ちを倍にしながら3回まで再試行する。
取得物は、固定のsha256をキーにして`actions/cache`に保持する。
キーとして使う前に、sha256が64桁の小文字の16進数かを検査し、形が違えば失敗させる。
保存先は`console/.cache/drawio-viewer`で、Gitには入れない。
キャッシュに一致するファイルがあれば取得しない。
キャッシュの中身は信用せず、使う前に固定のsha256と照合する。照合に通らなければ、取得し直す。
キャッシュは`dist/`の外に置く。`dist/drawio/`には受け口のscriptもあり、キャッシュから戻すと、組み立てた受け口を上書きしてしまうためである。
raw.githubusercontent.comの障害で取得に失敗したら、失敗したワークフローの実行を再実行する。キャッシュに当たれば取得せず、外れれば取得し直す。
ビューアはApache-2.0のライセンスである。
`console_fetcher`は、他の配信物と同じように、マニフェストの照合を経て`releases/<sha>/drawio/`に置く。
共有の`assets/`には入れない。`current`から`/console/drawio/`として配信する。
そのため、版を入れ替えたとき、古い版の`drawio/`は`releases/`の掃除に従って消える。
`console_fetcher`のコードは、このディレクトリのために変える必要が無い。マニフェストの検査は、`assets/`の入れ子だけを拒む。

ローカルの`mise run console:check`は、ビューアを取得しない。
ネットワークが無くても通る。

`console/scripts/public-assets.test.ts`が、`drawio.html`の参照と固定の値の一致を確かめる。
受け口のscriptを直したときは、ファイル名のハッシュを中身に合わせて付け直す。
同じテストが、合っていないファイル名を検出する。

### ビューアの更新

固定の更新は、Windmillの`f/factory/drawio_viewer_bump`が毎週月曜の10:00(Asia/Tokyo)に行う。
新しい版があれば、固定を書き換えるPRを作る。
人が固定のファイルを手で直す必要はない。
どこで動かすかと、何を守るかは、[セキュリティ](../security.md)の「ビューアの更新」にある。

| ファイル | 役割 |
| --- | --- |
| `f/factory/drawio_viewer_bump.ts` | スケジュールが呼ぶ。取得、観測の記録、重複の確認、PRの作成。判断は純粋関数に任せる |
| `f/factory/lib/drawio_viewer_bump.ts` | 版の比較、14日の待ち、大きさの確認、既存のブランチの確認、sha256の計算、固定のファイルとページの書き換え。純粋関数 |
| `f/factory/lib/drawio_viewer_bump_github.ts` | 更新だけが使うGitHubの操作。リリースの一覧、タグの解決、ファイルの読み取り、PRの一覧、差分の比較、1つのcommitでのブランチの作成 |
| `f/factory/lib/drawio_viewer_observations.ts` | タグごとに、最初に見たcommitと時刻を記録する |
| `migrations/datatable/main/20261011153000_drawio_viewer_observations.up.sql` | 記録の表`factory.drawio_viewer_observations` |

保護パスの一覧は、[セキュリティ](../security.md)の「保護パスの変更を止める」にある。

処理は次の順に進む。

1. `main`の`console/drawio-viewer.json`を読み、今の版を知る。
2. jgraph/drawioのリリースの一覧から、今の版より新しい版を、新しい順に最大20件選ぶ。
3. 選んだタグごとに、指すcommitをGitHubのAPIでたどり、タグとcommitの組を記録する。同じcommitなら記録済みの時刻を保つ。タグが別のcommitに付け替えられていたら、時刻を今に取り直す。解決できないタグは、警告を出して飛ばす。
4. 公開から14日以上たち、かつ、同じcommitを14日以上前から見ている最新の版を選ぶ。メジャー版は問わない。無ければ、何もせず終わる。
5. 未完了の更新のPR(ブランチ名が`factory/drawio-viewer-`で始まり、headがこのリポジトリのもの)があれば、何もせず終わる。選んだ版のブランチをheadにしたPRが、閉じたものを含めて1件でもあれば、作らない。
6. 選んだ版のcommitのビューアを、固定と同じ形のURLから取得する。取得物の大きさとgit blobのIDを、GitHubのAPIの値と照合する。
7. 大きさが今から2割を超えて増減していないかを確かめる。
8. 取得物のsha256を計算し、`console/drawio-viewer.json`と、`console/public/drawio.html`が読むビューアの名前の新しい内容を作る。
9. 選んだ版のブランチが、PRは無いのに既にあれば、先頭のcommitを1回だけ取る。そのcommitで、各ファイルのgit blobのIDが手順8の内容と一致し、`main`との差分がその2ファイルだけで名前の変更を含まないことを確かめる。合わなければPRを作らない。
10. `factory_repo_id`があれば、書き込みの前に、`factory_repo`の現在のリポジトリIDと照合する。食い違うときと見つからないときは、ブランチとPRを作らずに終わり、`factory_repo_id_mismatch`のnoticeが残る。
11. ブランチが無ければ1つのcommitで作る。PRを開き、PRのheadのcommitが、作った(または確かめた)commitと同じかを確かめる。違えばラベルを付けずに止める。同じなら自動レビューのラベルを付ける。

最初に動かした週は、すべての版の観測が始まったばかりなので、14日間は何も上げない。
観測の記録が消えたときも、同じように待ちを数え直す。

PRの本文は、PRテンプレートの章立てで、版、commit、sha256、大きさを書く。
メジャー版が変わる更新は、題名を`[major]`で始める。
本文の先頭には、メジャー版の更新であることと、旧と新の版を書く。
続けて、破壊的変更の可能性があるため、リリースノートとCSP、sandbox、`drawio_frame_isolation`の確認を人が行うと書く。
人は、マージの前にリリースノートを読み、CSPと図の隔離のテストが通っていることを確かめる。
PRは通常のCIを通る。
`console`ジョブが、書き換えた固定のURLからビューアを取得し、sha256を照合する。
`public-assets.test.ts`が、ページの参照と固定の一致を確かめる。
自動レビューが指摘を付けても、このPRにはPR修正を始めない(ブランチ名で判定する)。`factory:fix`ラベルを付けても動かず、ラベルは消費されずに残る。修正は人が行う。ブランチ名だけで判定するので、担当するすべてのリポジトリに効く。
マージの後は、他のConsoleの変更と同じく、CIが通れば数分で`console_fetcher`が反映する。
図が描かれることは自動では確かめないので、マージの後にConsoleの要件定義書の図を開いて確かめる。

自動では上げない版は、noticeの`drawio_viewer_bump_held`に残る。

| 原因 | 本文に載ること |
| --- | --- |
| 大きさが今から2割を超えて増減した | 版と、今と新しい大きさ |
| 大きさとgit blobのIDが、GitHubのAPIの値と違う | 版 |
| PRの無い既存のブランチの中身が、作るはずの内容と違う | 版とブランチ名。次の操作は、ブランチを確かめ、不要なら削除する |
| PRを作る間にブランチの先頭が変わった | 版、PRの番号、ブランチ名。次の操作は、PRとブランチを確かめ、不要ならPRを閉じてブランチを削除する |

上げる版に選んだ最新の版を保留している間は、それより古い版も上げない。保留の理由が、noticeに出続ける。

メジャー版の更新は、この通知には残らない。PRの題名と本文で知らせる。
大きさの変化が正当なら、Windmillで`f/factory/drawio_viewer_bump`を、`approved_version`にその版(例: `v33.0.0`)を指定して実行する。
指名した版は、2割の制限を免れる。
公開から14日の待ちと、GitHubのAPIの値との照合は、指名しても免れない。
空のファイルと10MBを超えるファイルは、指名しても上げない。
上げないと決めたときは、noticeを解決する。原因が続くと、次の週に出直す。

失敗(GitHubのAPIの障害、ネットワーク、トークンの失効)はジョブの失敗になり、スケジュールの失敗の通知に流れる。
次の週に再び試すので、人が再実行する必要はない。

更新のPRが閉じられたときは、その版を再び提案しない。
次の版が出れば、また提案する。
更新のPRが開いたまま残ると、次の更新は止まる。マージするか閉じる。

自動の更新が使えないときだけ、固定を手で上げる。
手順は次のとおりである。

1. jgraph/drawioのリポジトリを、blobを取らない部分cloneで取る。
2. 新しいcommitがリリースのタグ(`v<版>`)にあることを、`git tag --contains <commit>`で確かめる。
3. `git show <commit>:src/main/webapp/js/viewer-static.min.js | shasum -a 256`で、sha256を計算する。配信用のURL(raw.githubusercontent.com)から取ったバイト列を使わず、gitのオブジェクトから取る。
4. `console/drawio-viewer.json`の4項目を書き換える。URLはそのcommitを指し、sha256は3.の値である。
5. `console/public/drawio.html`が読むビューアの名前を、新しいsha256の先頭8桁に合わせる。

### iframeとメッセージ

親の部品は、`sandbox="allow-scripts"`と`referrerPolicy="no-referrer"`を付けたiframeで`/console/drawio.html`を読み込む。
XMLが変わるたびに、iframeを作り直す(keyを変える)。
1つのiframeの一生で送るのは、最初の`load`の後の1回だけである。
受け口は、`load`の前にscriptの実行を終えているためである。
状態の遷移は`console/src/lib/drawioFrameState.ts`の`reduceFrame`にある。`shouldSendXml`が、このloadでXMLを送ってよいかを返す。

2回目の`load`は、iframeが別の文書へ遷移したことを表す。
親は、iframeを`about:blank`にして表示を止め、固定の文を出す。
以後、そのiframeのメッセージは受けない。
この停止は最善の努力である。loadが起きない遷移は検知できず、止まらない。
そのときも、親が受ける値は、数値(高さ)と固定の失敗の種類だけである。

最初の`load`の後、10秒たっても、高さと`drawio:error`のどちらも届かなければ、親は、図のページが応答しないとみなして固定の文を出す。
`drawio.html`が404になったときや、ヘッダーに遮られて、scriptが動かないときである。

| 向き | メッセージ | 検査 |
| --- | --- | --- |
| 親からiframe | 種別`drawio:render`と`xml`(文字列) | 親は、空のXMLと、UTF-8で256KBを超えるXMLを送らない |
| iframeから親 | 種別`drawio:height`と`height`(数値) | 親は、送り元がiframeのwindowでないものと、`height`が有限の数値でないものを捨て、80〜1600pxに収める |
| iframeから親 | 種別`drawio:error`と`reason` | 親は、送り元がiframeのwindowでないものと、`reason`が固定の3つ(`viewer_missing`、`render_failed`、`too_large`)でないものを捨てる。画面に出す文は、親が`reason`から決める |

iframe側の受け口(`console/public/drawio/drawio-frame-*.js`)は、次のものを捨てる。

- 送り元が親のwindowでないメッセージ
- 種別が`drawio:render`でないメッセージ
- `xml`が文字列でないメッセージ
- 2回目以降の`drawio:render`

256KBの上限は、親と受け口の両方に置く。
親は送る前にバイト数で、受け口は受けた後に文字数で確かめる。
片方を変えるときは、もう片方も同じ値に変える。
上限を超えたXMLを受けた受け口は、`too_large`を返す。

受け口は、失敗を黙らせない。
ビューアが読み込まれていない場合、ビューアが例外を投げた場合、描いても図が入らなかった場合は、固定の文をiframeの中に出し、`drawio:error`を親へ返す。
例外の文面は、ページに出さず、親にも渡さない。

iframeは、図の領域の大きさが変わるたびに高さを送る。
図が上限より高いときは、親のiframeが1600pxで止まり、iframeの中で縦にスクロールする。横には隠す。
縦のスクロールバーが出入りして幅が変わると、ビューアが図を合わせ直して高さが変わり、高さの通知が往復するため、幅は固定する(`scrollbar-gutter: stable`)。
枠線は、iframeの外側の要素に付ける。iframeに付けると、枠線の分だけ高さが足りなくなる。

### CSPとヘッダー

`/console/drawio.html`と`/console/drawio/`の下は、Consoleの他のページと別のヘッダーで返す。
Caddyfileでは、次の2つを、Consoleの本体の`handle_path /console/*`より前に置く。

- `handle /console/drawio.html`
- `handle_path /console/drawio/*`

どちらも後ろに置くと、Consoleのヘッダー(`frame-ancestors 'none'`)が付いて、iframeに読み込めなくなるためである。

Consoleの本体のfallback(`handle_path /console/*`)は、`drawio.html`と`drawio/`の下を404にする。
区切りを重ねた要求などでfallbackに落ちても、sandboxの無いConsoleのヘッダーで返さないためである。
ビューアと受け口は、`/console/assets/`ではなく`/console/drawio/`に置く。
Consoleの本体のCSPは`/console/assets/`だけを許すので、本体のページは、`/console/drawio/`のscriptを読めない。
本体にHTMLが注入されても、信頼されたオリジンでビューアを動かす足場にならない。
`tests/infra/caddyfile.test.ts`が、この許可の違いを固定している。

| ヘッダー | 値 | 理由 |
| --- | --- | --- |
| `Content-Security-Policy` | `default-src 'none'`、`script-src`は`/console/drawio/`、`style-src 'unsafe-inline'`、`img-src data:`、`font-src data:`、`connect-src 'none'`、`base-uri 'none'`、`form-action 'none'`、`frame-ancestors`はブラウザが使ったオリジン、`sandbox allow-scripts` | 外への取得をすべて止める。不透明なオリジンでは`'self'`が使えないので、`script-src`と`frame-ancestors`にはブラウザが使ったオリジンを入れる。`style-src`は、ビューアが付けるインラインのstyleのために許す。`sandbox`は、ページを直接開いても不透明なオリジンで動かす |
| `X-Frame-Options` | `SAMEORIGIN` | `frame-ancestors`を解釈するブラウザでは、そちらが優先される。これは、解釈しない古いブラウザ向けの備えで、Console自身のページだけに埋め込ませる |
| `Referrer-Policy` | `no-referrer` | 参照元を送らない |
| `X-Content-Type-Options` | `nosniff` | scriptの種別を推測させない |

`'unsafe-eval'`は付けない。

## 他のサイトからのAPIの呼び出し

`/api/*`への要求は、次のどれかに当てはまるとCaddyが403にする。
ほかのポートのlocalhostや外部のリンクから、運用者のCookieでAPIを実行させないためである。

- `Sec-Fetch-Site`が`cross-site`か`same-site`である。
- `Origin`ヘッダーがあり、ブラウザが開いたホスト名とポートのオリジンと一致しない。
- 副作用のあるGETのAPIを、fetchとXHR以外の読み込み(`<img>`、リンク、iframeなど)から呼んでいる。
- GETとHEAD以外の要求が、ページの移動(`Sec-Fetch-Mode: navigate`)で送られている。

### Sec-Fetch-Siteの規則

- Windmillのフロントエンドからの要求には、ブラウザが`Sec-Fetch-Site: same-origin`を付ける。
- CLI(`wmill`)は、`Sec-Fetch-*`、`Origin`、`Cookie`のどれも送らない。

### Originの検査

`Sec-Fetch-Site`を送らない古いブラウザは、1つ目の規則を素通りする。
ブラウザは、GETとHEAD以外の要求には`Origin`を付けるので、2つ目の規則がそれを止める。
ナビゲーションや`<img>`のGETには`Origin`が付かない。
Firefox 70未満は、フォームのPOSTにも付けない。
そのため、この検査が補えるのは、GETとHEAD以外のブラウザの要求だけである。

ブラウザが開いたオリジンは、`Host`ヘッダーのホスト名とポートに、`http://`か`https://`を付けたものである。
許すのはこの2つだけで、`WM_HTTP_PORT`やホスト名を変えても規則はそのまま合う。
前段でTLSを終端するときは、プロキシがブラウザの使った`Host`を、ポートを含めて保つ必要がある(nginxなら`proxy_set_header Host $http_host`)。
nginxの既定は`Host`を転送先の名前に書き換え、`$host`はポートを落とす。
どちらも`Origin`と合わなくなり、ログインを含む書き込みがすべて403になる。
`Host`が内部の名前に変わると、ブラウザの`Origin`と合わず、書き込みがすべて403になる。
`http://localhost:8080`で開いたなら、`http://localhost:8080`と`https://localhost:8080`が通る。
同じポートでも、`http://127.0.0.1:8080`は通らない。
ポートが違うもの、末尾に`/`が付いたもの、`Origin: null`も止める。

### 副作用のあるGET

Windmillには、GETでジョブを起動するAPIがある。
例は`GET /api/w/<workspace>/jobs/run_wait_result/p/<path>?payload=<base64>`である。
同じオリジンの`<img>`やリンクから呼ぶと、`Sec-Fetch-Site: same-origin`で`Origin`も付かず、上の2つの規則を通る。
Cookieの持ち主の権限でジョブが動き、承認のscriptなら、Cookieの持ち主が承認者として記録される。
そのため、次のGETとHEADは、`Sec-Fetch-Dest`が`empty`(fetchとXHR)で、かつ`Sec-Fetch-Mode`が`navigate`でないときだけ通し、それ以外は403にする。
`<a download>`は`Sec-Fetch-Dest`が`empty`でも`navigate`になるので、`Sec-Fetch-Mode`でも止める。
この規則の対象は、下の表のGETだけである。読み取りのナビゲーションには影響しない。
Consoleの呼び出しはPOSTの`fetch`なので、影響しない。

| 経路(`/api/w/<workspace>/`の下) | 理由 |
| --- | --- |
| `jobs/run_wait_result/p/<path>`と`jobs/run_wait_result/fv/<version>` | scriptとflowを起動し、結果を待つ |
| `jobs/run_and_stream/f/<path>`、`fv/<version>`、`p/<path>`、`h/<hash>` | scriptとflowを起動し、結果を流す |
| `jobs/slack_approval/<id>`と`jobs/teams_approval/<id>` | SlackとTeamsへ承認のメッセージを送る |
| `job_helpers/move_s3_file` | オブジェクトストレージのファイルを動かす |

`Sec-Fetch-Dest`を送らないブラウザは、`Cookie`を持つときだけ止める。
対象は、古いブラウザと、HTTPで公開したブラウザである。
`Sec-Fetch-*`は、信頼できるオリジン(localhostかHTTPS)でだけ付く。
そのため、WindmillのフロントエンドがこれらのGETを使うと、その環境では403になる。
CLIとscriptは、`Sec-Fetch-*`と`Cookie`を送らず、`Authorization`で認証するので、そのまま通る。

パスの照合は、大文字小文字を区別せず、`//`の重なりも許す。
作業スペースの部分は`/`をまたいで一致させるので、`%2f`で`/`を隠しても逃げられない。
`%72un_wait_result`のようにパーセント符号で綴りを変えても、Caddyが戻してから照合するので止まる。

洗い出しは、`windmill-client`の`services.gen.d.ts`にある453個のGETのAPIを、名前と説明で分類して行った。
サーバーの全経路を網羅した確認ではなく、`/api/r/*`のカスタムHTTPルート(HTTPトリガー)は含まない。
このリポジトリはHTTPトリガーを持たない。
足すときは、GETでjobを起動する経路にならないか、認証の方式とあわせて確かめる。

次のGETは、副作用があるか、起動する可能性があっても、対象にしない。

| 経路 | 対象にしない理由 |
| --- | --- |
| `jobs_u/resume/<id>/<resume_id>/<signature>`と`jobs_u/cancel/...` | 署名が資格情報で、Cookieに頼らない。メールの承認リンクとして、ナビゲーションで開くため |
| `auth/login_link/<token>`、`mcp/oauth/start`、`mcp/oauth/callback` | ログインとOAuthの導線で、ナビゲーションで開くため |
| `users/refresh_token` | 新しいトークンを返すだけで、攻撃者に得がない |
| `jobs/resume_urls/...`と`jobs/job_signature/...` | 署名付きURLを返すだけで、応答は別のオリジンから読めない |
| `job_helpers/test_connection`と`workspaces/test_datatable_connection/...` | 設定済みの接続を試すだけで、状態を変えない |
| 上以外の`list`、`get`、`count`、`exists`、`history`、`download`など | 読み取りだけである |

Windmillのフロントエンドの実装は読んでいない。
対象のGETを`fetch`以外で開く導線があれば、そのリンクは403になる。
ジョブ結果の表示は`jobs_u/get`などの読み取り系のGETを使い、対象に入れていない。

### ページの移動で送られる書き込み

同じオリジンに注入された`<form method="post" action="/api/w/<workspace>/jobs/run/p/...">`は、クリック1回で送られる。
このPOSTは、`Sec-Fetch-Site: same-origin`で、`Origin`も一致し、`Sec-Fetch-Dest`は`document`になる。
上の3つの規則は、どれも止められない。
そのため、GETとHEAD以外の要求で`Sec-Fetch-Mode`が`navigate`か`nested-navigate`のものは、メソッドを問わず403にする。
ConsoleとWindmillのフロントエンドのAPI呼び出しは`fetch`なので、`Sec-Fetch-Mode`は`cors`か`same-origin`になり、影響しない。

GETとHEADは、この規則では止めない。
APIをナビゲーションで開く正当な導線があるためである。
副作用のあるGETは、前の節の規則が止める。
ナビゲーションで開く導線は、次のとおりである。

| 経路(`/api/`の下) | 導線 |
| --- | --- |
| `w/<workspace>/jobs_u/resume/...`と`jobs_u/cancel/...` | メールとSlackの署名付きの承認リンク |
| `auth/login_link/<token>` | ログインのリンク |
| `oauth/login_callback/...`、`oauth/connect_callback/...`、`mcp/oauth/start`、`mcp/oauth/callback` | OAuthの認可とコールバック(IdPからのリダイレクト) |
| `w/<workspace>/job_helpers/download_s3_file`、`jobs_u/get_log_file/...`、`jobs/completed/export`、`users/export`、`groups/export`など | ファイルのダウンロードとエクスポート |
| `openapi.yaml`、`version` | 利用者が直接開くページ |

この一覧は、型定義の名前と説明から選んだもので、UIの実装を読んで確かめたものではない。
GETとHEAD以外をナビゲーションで送る導線は、型定義から見つけていない。
`Sec-Fetch-Mode`が無い古いブラウザと、HTTPで公開したブラウザは、止めない。
`Cookie`だけで止めると、`fetch`の書き込みまで巻き込み、UIが動かなくなるためである。

### 実機での確認

規則は、Caddyを起動して`bash scripts/check-caddy-origin.sh`で確かめる。
composeと同じイメージで`infra/Caddyfile`を動かし、止めるべき要求が403に、通すべき要求が(転送先のWindmillを起動しないので)502になることを、`curl`で比べる。
旧ConsoleのURLの転送も、同じスクリプトで確かめる。
旧Consoleのパスと配下、重なった`/`、クエリ付きの要求が、どれも`Location`が`/console/`だけの302になること、名前の続く別のアプリと編集画面は飛ばさないことを比べる。
Caddyが起動しないときは、コンテナのログを出して失敗する。
CIの`caddyfile`ジョブも、同じスクリプトを動かす。
Dockerが要る。
`CHECK_PORT`で、待ち受けるポートを変えられる(既定は18080)。
