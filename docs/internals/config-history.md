# 設定の変更の履歴の内部仕様

設定の変更の履歴は、設定`factory_config`の変更を、追記専用で、ハッシュでつないで残す記録である。
状態は表`factory.config_history`に置く。
次のファイルの履歴に関わる部分を変更する人が読む。

- `migrations/datatable/main/20261121100000_config_history.up.sql`と、対のdown
- `f/factory/lib/config_history.ts`(値の射影、追記、検証の呼び出し、証跡パックの集計)
- `f/factory/console_config_update.ts`と`f/factory/console_stop_all.ts`(成功の後に履歴を書く呼び出し)
- `f/factory/lib/audit_evidence.ts`(証跡パックの節「設定の変更」)
- `scripts/test-db-queries.ts`(実DBの検査)

## 目的

設定の変更は、Consoleの操作の記録(`console_actions`)にも残る。
その記録は90日で消え、更新もでき、全停止が止めた旗の名前を持たない。
設定の変更の履歴は、次の3つを満たすために置く。

- 誰がどの項目を何から何へ変えたかを、決まった一覧の理由コードで数えられる。
- 行を書き換えても、消しても、検証で見つかる。
- 保持の期限で消えない。

## 記録するもの

履歴の行は、変更1つにつき1行である。
連鎖は全体で1本にする。
変更の量は少ないので、追記を1か所に並べても詰まらない。

| 列 | 内容 |
| --- | --- |
| `seq` | 連鎖の連番。1から始まり、欠けずに続く |
| `item_key` | 変更した設定の項目名。小文字、数字、下線の識別子に限る |
| `reason_code` | 変更の理由コード([理由コード](#理由コード)) |
| `before`、`after` | 変更の前後の値を射影したもの([値の射影](#値の射影))。値が無かった側は`null` |
| `actor` | 変更した人。Consoleの操作の記録と同じく、ジョブの実行文脈から導いた値である |
| `source` | 書いた経路。`console`(設定の更新)、`stop_all`(全停止)、`out_of_band`(Consoleの外の変更を見つける照合のために予約した値で、今は書き手が無い) |
| `occurred_at` | 書いた時刻 |
| `prev_hash`、`row_hash` | 連鎖のハッシュ([ハッシュの連鎖](#ハッシュの連鎖)) |

記録しないものは次のとおりである。

- コマンド、URL、リポジトリ、所有者、ラベルを付けてよい人の生の値
  - 変更の有無だけが分かるハッシュにする。
  - このハッシュで分かるのは変更の有無だけで、値の秘匿にならない。
  - 限界を[値を隠さないハッシュ](#ハッシュは値を隠さない)に書く。
- 秘密値
  - 設定に秘密値のキーは無く、秘密値は変数に置く。
  - 値の側に参照や秘密らしい語があれば、値を伏せた印にする。
- 射影の表に無い項目の値
  - 値は入れず、項目が未知であることだけを残す。

## 値の射影

履歴に入れる値は、`lib/config_history.ts`の`projectConfigValue`が、許可リストで射影する。
生の値をそのまま通すのは、真偽、有限の数、時刻、短い列挙の文字列に限る。

| 項目の種類 | 履歴に入れる値 |
| --- | --- |
| 真偽の旗(名前が`_enabled`で終わる項目と、表にある項目) | 真偽 |
| 数の項目(予算、回数、日数、行数など。表にある項目) | 有限の数 |
| 時刻の項目(`*_enabled_since`) | ISO 8601の時刻。形に合わなければ伏せた印 |
| 列挙の項目(モデル名、ラベル名、ブランチ名、投稿の形式など。表にある項目) | 60字までの英数字と`.`、`_`、`:`、`/`、`-`の文字列。形に合わない、参照を含む、秘密らしい語か秘密の形を含む文字列は、伏せた印(`{redacted: true}`) |
| 要素が名前かURLの一覧(`repo_allowlist`、`dependabot_other_repos`、`default_reviewers`) | 件数だけ(`{count}`) |
| コマンド、URL、リポジトリ、身元に関わる項目(`check_commands_by_repo`、`allowed_check_commands`、`factory_repo`、`factory_repo_id`、`windmill_public_url`、`owners`、`allowed_labeler_`で始まる項目) | 正規化したJSONのsha256の先頭16桁(`{hash}`)。変更後の側には、前後のハッシュが違うかを示す`changed`を付ける |
| 表に無い項目 | 値を入れず、`{kind: "unknown"}`だけにする |

項目の種類に合わない型の値(旗に文字列など)も、値を入れず`{kind: "unknown"}`にする。
射影は、迷ったときに値を出力に写さない側へ倒してある。
未知の項目の変更は、履歴に項目名と「未知の値」だけが残り、値は読めない。

ハッシュの正規化は、オブジェクトのキーを辞書順に並べ、配列の順は保つ。
同じ値は、キーの並びによらず、同じハッシュになる。
検出に使う秘密の語は、`lib/console_redact.ts`の一覧と同じである。

### ハッシュは値を隠さない

射影のハッシュは、塩を付けないsha256の先頭16桁である。
値が変わったかを検知するための印であり、値を隠すものではない。
`owners`や`allowed_labeler_`で始まる項目のように、候補が少ない識別子は、辞書や総当たりでハッシュから元の値を当てられる。
履歴を読める人に見せてよい値だけを、ハッシュの項目にする。
本当に隠したい値は、ハッシュの項目にせず、`{kind: "unknown"}`のままにする。
この限界は[R-CFGH-04](../security-risks.md#r-cfgh-04)に書く。

射影の表は、`config_history.ts`の中にあり、設定の項目を足しても自動では広がらない。
足した項目は、表に加えるまで`{kind: "unknown"}`になる。

## 書き込み

Consoleの設定の更新と全停止のscriptは、設定の書き込みが成功した後で、履歴を書く。
書き込みはSQL関数`factory.config_history_append`を呼ぶ1文で、値はすべてパラメータで渡す。

| script | 書くタイミング | 行 |
| --- | --- | --- |
| 設定の更新 | 書き込みが成功したとき。読み直しの結果は問わない | 項目1つにつき1行。読み直しが期待と一致したときの理由は`console_update`で、後の値は書いた値の射影。一致しなかったときの理由は`console_update_unverified` |
| 全停止 | 設定の書き込みが成功し、scheduleの無効化まで済んだ後 | 止めた旗1つにつき1行。前は`true`、後は`false`。理由は`stop_all_flag_off` |

全停止は、止める働きがすべて済んでから、履歴を書く。
履歴の追記がロックを待っても、scheduleを止めるのが遅れないためである。

読み直しで期待した値を確かめられなかった変更も、書き込みが成功していれば、履歴に書く。
設定が変わったのに履歴に残らないと、変更を追えなくなるためである。
その行の理由は`console_update_unverified`で、操作の記録には`partial`が残る。
`after`は、読み直せたときは、読み直した値の射影である。
読み直せなかったとき(読み取りの失敗、設定が連想配列でない)は、書こうとした値の射影である。
読み直しが一致しなかった行の`after`は、書いた値と違うことがある。
書き込みが失敗した変更は、設定が変わっていないので、履歴に書かない。

履歴の書き込みが失敗しても、設定の書き込みは戻さず、scriptも失敗させない。
人の操作を止めないためである。
`lib/config_history.ts`の`appendConfigChange`は、失敗を投げずに結果で返す。
scriptは、操作の記録の結果(`changes`)に`history_recorded: false`を残し、続ける。
書けなかった行は、履歴に穴として残る([R-CFGH-02](../security-risks.md#r-cfgh-02))。
穴は、証跡パックが、期間内の操作の記録で`history_recorded: false`を持つ行の数として示す。
数えられるのは、操作の記録が残る90日の範囲に限る。

失敗の原因は、次の4つである。

1. 入力が表の形に合わない。
   項目名が識別子でないか、操作者が1〜100字でないときで、文は送らない。
2. 表か関数が無い。
   migrationより先にコードが反映された間に起きる。
3. DBに届かないか、追記のadvisory lockが取れない。
   lockを持つのは別の追記のトランザクションだけで、追記は1行の挿入なので、待ちは短い。
   lockの待ちは、接続の`lock_timeout`に従う。
4. 追記の関数が返したidを整数として読めない。
   行が書けたかを確かめられないので、書けなかったものとして扱う。

## 理由コード

理由コードは、呼び出し側が明示する。
一覧はSQL関数`factory.config_history_reason_codes()`が返し、TypeScriptの`CONFIG_HISTORY_REASON_CODES`と同じ並びにする。
実DBの検査が、一覧の一致と、TypeScriptの一覧のすべての値を表が受けることを確かめる。
表の`CHECK`が、一覧の外の値を拒む。

| 理由コード | 条件 |
| --- | --- |
| `console_update` | Consoleの設定の更新で、真偽、数値、一覧の項目が変わり、書いた後の読み直しが期待と一致した |
| `console_update_unverified` | Consoleの設定の更新で書き込みは成功したが、読み直しが期待と一致しなかった |
| `stop_all_flag_off` | Consoleの全停止が、`*_enabled`を`false`にした |
| `unspecified` | 呼び出し側が理由を決められなかった |

コードを足すときは、新しいmigrationで`config_history_reason_codes`を置き換え、同じ変更で`CONFIG_HISTORY_REASON_CODES`に足す。
すでに書いた行の理由コードは、`row_hash`に含まれるので書き換えない。

## ハッシュの連鎖

`row_hash`は、行の次の項目を、この順に並べた文字列のsha256(16進)である。

1. `prev_hash`
2. `seq`
3. `item_key`
4. `reason_code`
5. `before`(jsonbの文字列表現)
6. `after`(jsonbの文字列表現)
7. `actor`
8. `source`
9. `occurred_at`

各項目は`<バイト長>:<値>`の形にし、値が`NULL`のときは`~`にして、`|`でつなぐ。
バイト長を付けるのは、値に区切りの文字が含まれても、項目の境界が曖昧にならないためである。
`occurred_at`は、接続の時刻帯に左右されないよう、UTCで`YYYY-MM-DD"T"HH24:MI:SS.US"Z"`の形(マイクロ秒まで)にする。
算出はSQL関数`factory.config_history_row_hash`が行い、追記と検証が同じ関数を使う。
遷移の履歴の関数とは別に持ち、片方のmigrationを戻しても、もう片方は動く。

連鎖の最初の行の`prev_hash`は、0を64個並べた文字列である。
2行目からは、1つ前の行の`row_hash`を`prev_hash`にする。
追記は、固定のadvisory lockを取って直列にし、`seq`を最後の行の次の値にする。
ロックはトランザクションの終わりまで持つ。
既定の分離水準(READ COMMITTED)では、ロックを取った後の文が、先の追記の結果を読む。

## 検証

`factory.config_history_verify()`が連鎖を検証する。
行のハッシュを再計算し、`prev_hash`のつながりと、`seq`が1から欠けずに続くことを確かめる。
壊れた位置を、`seq`の昇順に、理由つきですべて返す。

| 理由 | 意味 |
| --- | --- |
| `gap` | `seq`が欠けている。最初の行が1でないときを含む。欠けた次の行の`seq`を返す |
| `prev_hash_mismatch` | `prev_hash`が、1つ前の行の`row_hash`と合わない |
| `row_hash_mismatch` | 行の内容から求めたハッシュが、`row_hash`と合わない |

検証をSQLで行うので、言語をまたぐ正規化は要らない。
TypeScriptの呼び出しは`verifyConfigHistory`である。

連鎖の末尾の行を消した場合は、検証では見つからない([R-CFGH-03](../security-risks.md#r-cfgh-03))。
連鎖の長さと最後の連番は、証跡パックに載るので、前回の監査より短くなっていれば、人が気づける。

## 追記専用

行のトリガー`config_history_guard_row`が、UPDATEとDELETEを例外で拒む。
文のトリガー`config_history_guard_truncate`が、TRUNCATEを例外で拒む。
遷移の履歴と違い、通す例外は無い。
掃除の関数を持たないためである。

この歯止めは安全柵である。
表の所有者はトリガーを外せるので、歯止めは改ざんを防がない。
改ざんを見つけるのは、ハッシュの連鎖である。
所有者が連鎖の途中の行を書き換えれば、検証が、その行を指す。
所有者がその行から先の連鎖をすべて計算し直せば、検証は通る([R-CFGH-03](../security-risks.md#r-cfgh-03))。

## 保持

保持は無期限である。
行は、設定の変更の数だけ増え、増え方は少ない。
掃除の関数も、保持日数の設定も持たない。

## 記録しない変更

履歴に残るのは、Consoleの設定の更新と、全停止による停止だけである。
次の経路の変更は、記録しない([R-CFGH-01](../security-risks.md#r-cfgh-01))。

- 旗を`true`に戻す復元
  - 全停止の解除、ホストの`mise run stop`の解除と復元、CLIによる復元が当たる。
- ホストのCLI(`mise run stop`と`mise run stop:restore`)
- `wmill resource push`
- Windmillの画面での、resourceの編集
- Consoleの外の、そのほかの書き込み

履歴に記録が無いことは、設定が変わらなかったことを示さない。
復元を記録しないので、ある旗の履歴が`false`で終わっていても、今の設定は`true`のことがある。
履歴の最後の値を、今の設定として読まない。
復元と、Consoleの外の変更を記録する仕組みは、まだ無い。
`source`の`out_of_band`は、Consoleの外の変更を、resourceの値と最後の履歴の差から見つけて書くために予約した値である。
その照合は、まだ無い。

## 証跡パックの節

証跡パックの節「設定の変更」は、連鎖の検証の結果と、期間内の変更の項目別と理由コード別の件数を載せる。
固定の行「記録の範囲」は、記録するのがConsoleの設定の更新と全停止による停止だけで、復元とConsoleの外の変更は記録しないことを示す。
履歴を書けなかった操作が期間内に1件以上あるときは、固定の行「記録できなかった操作」を足す。
この件数は、操作の記録の範囲(90日)に限る。
内容は[監査の仕様の「設定の変更」](audit.md#設定の変更)に書く。
