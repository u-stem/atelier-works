# 設定の変更の履歴の内部仕様

設定の変更の履歴は、設定`factory_config`の変更を、追記専用で、ハッシュでつないで残す記録である。
状態は表`factory.config_history`に置く。
次のファイルの履歴に関わる部分を変更する人が読む。

- `migrations/datatable/main/20261121100000_config_history.up.sql`と、対のdown
- `migrations/datatable/main/20261122100000_config_snapshot.up.sql`と、対のdown(照合の理由コード)
- `f/factory/lib/config_history.ts`(値の射影、追記、検証の呼び出し、証跡パックの集計)
- `f/factory/console_config_update.ts`と`f/factory/console_stop_all.ts`(成功の後に履歴を書く呼び出し)
- `f/factory/config_snapshot.ts`と`f/factory/lib/config_snapshot.ts`(Consoleの外の変更の照合)
- `f/factory/lib/audit_evidence.ts`(証跡パックの節「設定の変更」)
- `scripts/test-db-queries.ts`(実DBの検査)

## 目的

設定の変更は、Consoleの操作の記録(`console_actions`)にも残る。
その記録は90日で消え、更新もでき、全停止が止めた旗の名前を持たない。
設定の変更の履歴は、次の3つを満たすために置く。

- 誰がどの項目を何から何へ変えたかを、決まった一覧の理由コードで数えられる。
- 行を書き換えても、消しても、検証で見つかる。
- 保持の期限で消えない。

## 記録するもの

履歴の行は、変更1つにつき1行である。
連鎖は全体で1本にする。
変更の量は少ないので、追記を1か所に並べても詰まらない。

| 列 | 内容 |
| --- | --- |
| `seq` | 連鎖の連番。1から始まり、欠けずに続く |
| `item_key` | 変更した設定の項目名。小文字、数字、下線の識別子に限る |
| `reason_code` | 変更の理由コード([理由コード](#理由コード)) |
| `before`、`after` | 変更の前後の値を射影したもの([値の射影](#値の射影))。値が無かった側は`null` |
| `actor` | 変更した人。Consoleの操作の記録と同じく、ジョブの実行文脈から導いた値である。照合が書く行は、人ではなく、固定の`config_snapshot`になる |
| `source` | 書いた経路。`console`(設定の更新)、`stop_all`(全停止)、`out_of_band`(Consoleの外の変更。照合が書く) |
| `occurred_at` | 書いた時刻 |
| `prev_hash`、`row_hash` | 連鎖のハッシュ([ハッシュの連鎖](#ハッシュの連鎖)) |

記録しないものは次のとおりである。

- コマンド、URL、リポジトリ、所有者、ラベルを付けてよい人の生の値
  - 変更の有無だけが分かるハッシュにする。
  - このハッシュで分かるのは変更の有無だけで、値の秘匿にならない。
  - 限界を[値を隠さないハッシュ](#ハッシュは値を隠さない)に書く。
- 秘密値
  - 設定に秘密値のキーは無く、秘密値は変数に置く。
  - 値の側に参照や秘密らしい語があれば、値を伏せた印にする。
- 射影の表に無い項目の値
  - 値は入れず、項目が未知であることだけを残す。
  - 値の変更は、意図して追わない([照合が見つけない変更](#照合が見つけない変更))。
- 型が項目の種類に合わない値
  - 値は入れず、値のハッシュだけを残す。

## 値の射影

履歴に入れる値は、`lib/config_history.ts`の`projectConfigValue`が、許可リストで射影する。
生の値をそのまま通すのは、真偽、有限の数、時刻、短い列挙の文字列に限る。

| 項目の種類 | 履歴に入れる値 |
| --- | --- |
| 真偽の旗(名前が`_enabled`で終わる項目と、表にある項目) | 真偽 |
| 数の項目(予算、回数、日数、行数など。表にある項目) | 有限の数 |
| 時刻の項目(`*_enabled_since`) | ISO 8601の時刻。形に合わなければ伏せた印 |
| 列挙の項目(モデル名、ラベル名、ブランチ名、投稿の形式など。表にある項目) | 60字までの英数字と`.`、`_`、`:`、`/`、`-`の文字列。形に合わない、秘密らしい語か秘密の形を含む文字列は、伏せた印(`{redacted: true, hash}`) |
| 要素が名前かURLの一覧(`repo_allowlist`、`dependabot_other_repos`、`default_reviewers`) | 件数と、要素のハッシュ(`{count, hash}`)。要素の順は比べない |
| コマンド、URL、リポジトリ、身元に関わる項目(`check_commands_by_repo`、`allowed_check_commands`、`factory_repo`、`factory_repo_id`、`windmill_public_url`、`owners`、`allowed_labeler_`で始まる項目) | 正規化したJSONのsha256の先頭16桁(`{hash}`)。変更後の側には、前後のハッシュが違うかを示す`changed`を付ける |
| 値が参照(`$var:`、`$res:`、`$jsonvar:`)を含む項目(項目の種類を問わない) | 参照の先を調べず、伏せた印(`{redacted: true, hash}`) |
| 表にある項目で、値の型が項目の種類に合わない | 値を入れず、値のハッシュだけを添えた`{kind: "unknown", hash}` |
| 表に無い項目 | 値を入れず、ハッシュも添えず、`{kind: "unknown"}`だけにする |
| 項目が設定から無くなった(照合だけが書く) | 変更後の側に`{removed: true}`。値が`null`の項目とは区別する |
| 基準の段階が終わった印の行(照合だけが書く) | `{kind: "marker"}`([基準の段階](#基準の段階)) |
| resource全体がオブジェクトでない間(予約の項目`config_snapshot_resource`。照合だけが書く) | 値のハッシュ(`{redacted: true, hash}`)。オブジェクトに戻ったら`{kind: "object"}`([resource全体がオブジェクトでないとき](#resource全体がオブジェクトでないとき)) |

項目の種類に合わない型の値(旗に文字列など)は、値を入れず、値のハッシュだけを添える(`{kind: "unknown", hash}`)。
ハッシュがあるので、型に合わない値を別の型に合わない値へ差し替えた変更は、変更として書かれる。
ハッシュが無いと、どの値も同じ`{kind: "unknown"}`になり、差し替えが見えなくなる。
ハッシュを足す前の行(`{kind: "unknown"}`だけ)は、今の射影と違う値として比べるので、その項目は1回だけ変更の行が書かれる。
表に無い項目は、ハッシュも添えない。
表に無い項目の値は、意図して追わない。
追わない値にハッシュを添えると、履歴を読む人に、値の変化を見せることになるためである。
足した項目は、名前を表へ加えるまで、種類別の射影にならない。
射影は、迷ったときに値を出力に写さない側へ倒してある。
未知の項目の変更は、履歴に項目名と「未知の値」だけが残り、値は読めない。

ハッシュの正規化は、オブジェクトのキーを辞書順に並べ、配列の順は保つ。
同じ値は、キーの並びによらず、同じハッシュになる。
一覧の項目(`{count, hash}`)だけは、要素を正規化してから並べ替えて、ハッシュにする。
一覧の要素の順に意味は無く、並べ替えを変更に数えると、意味の無い行が増えるためである。
同じ要素を重ねた変更は、件数が変わるので、見つかる。
検出に使う秘密の語は、`lib/console_redact.ts`の一覧と同じである。

伏せた印のハッシュは、生の値の正規化したJSONから、メモリの中で計算する。
生の値は、履歴にも、ログにも、結果にも残さない。
このハッシュがあるので、参照を含む項目の値が後で別の値に変わると、変更として書かれる。
ハッシュが無いと、伏せた印はどの値でも同じになり、後の変更がすべて見えなくなる。
参照の名前は、秘密の値ではない。
秘密らしい文字列は、塩を付けないハッシュなので、候補が少なければ当てられる(次の節)。

履歴に`{count}`だけ、または`{redacted: true}`だけで書かれた行(ハッシュを足す前の形)は、今の射影と違う値として比べる。
その項目は、1回だけ変更の行が書かれ、次の実行からは、ハッシュを持つ行どうしで比べる。

### ハッシュは値を隠さない

射影のハッシュは、塩を付けないsha256の先頭16桁である。
値が変わったかを検知するための印であり、値を隠すものではない。
`owners`や`allowed_labeler_`で始まる項目のように、候補が少ない識別子は、辞書や総当たりでハッシュから元の値を当てられる。
一覧の項目(`repo_allowlist`、`dependabot_other_repos`、`default_reviewers`)は、候補が少ない名前の一覧なので、同じである。
秘密らしい文字列の伏せた印のハッシュも、同じである。
履歴を読める人に見せてよい値だけを、ハッシュの項目にする。
本当に隠したい値は、ハッシュの項目にせず、`{kind: "unknown"}`のままにする。
この限界は[R-CFGH-04](../security-risks.md#r-cfgh-04)に書く。
型に合わない値のハッシュも、同じ限界を持つ。

射影の表は、`config_history.ts`の中にあり、設定の項目を足しても自動では広がらない。
足した項目は、表に加えるまで`{kind: "unknown"}`になる。
`{kind: "unknown"}`の項目は、値が変わっても射影が同じなので、照合は変更を見つけられない。
このため、`tests/lib/config_snapshot.test.ts`が、設定の解析が返す項目のすべてに、表の種類があることと、表の名前が知っている項目の一覧に入っていることを確かめる。

表の名前の一覧は、このコードが知っている項目の一覧でもある(`isKnownConfigKey`)。
名前の規則(`*_enabled`、`*_enabled_since`、`allowed_labeler_`で始まる名前)に合うだけの項目は、射影の種類は規則で決まるが、知っている項目には入らない。
照合が書く順と、調べる項目の数の上限([書き込みの順と上限](#書き込みの順と上限))が、この一覧を使うためである。
設定に旗や時刻の項目を足したときは、表にも足す。

## 書き込み

Consoleの設定の更新と全停止のscriptは、設定の書き込みが成功した後で、履歴を書く。
書き込みはSQL関数`factory.config_history_append`を呼ぶ1文で、値はすべてパラメータで渡す。

| script | 書くタイミング | 行 |
| --- | --- | --- |
| 設定の更新 | 書き込みが成功したとき。読み直しの結果は問わない | 項目1つにつき1行。読み直しが期待と一致したときの理由は`console_update`で、後の値は書いた値の射影。一致しなかったときの理由は`console_update_unverified` |
| 全停止 | 設定の書き込みが成功し、scheduleの無効化まで済んだ後 | 止めた旗1つにつき1行。前は`true`、後は`false`。理由は`stop_all_flag_off` |

全停止は、止める働きがすべて済んでから、履歴を書く。
履歴の追記がロックを待っても、scheduleを止めるのが遅れないためである。

読み直しで期待した値を確かめられなかった変更も、書き込みが成功していれば、履歴に書く。
設定が変わったのに履歴に残らないと、変更を追えなくなるためである。
その行の理由は`console_update_unverified`で、操作の記録には`partial`が残る。
`after`は、読み直せたときは、読み直した値の射影である。
読み直せなかったとき(読み取りの失敗、設定が連想配列でない)は、書こうとした値の射影である。
読み直しが一致しなかった行の`after`は、書いた値と違うことがある。
書き込みが失敗した変更は、設定が変わっていないので、履歴に書かない。

履歴の書き込みが失敗しても、設定の書き込みは戻さず、scriptも失敗させない。
人の操作を止めないためである。
`lib/config_history.ts`の`appendConfigChange`は、失敗を投げずに結果で返す。
scriptは、操作の記録の結果(`changes`)に`history_recorded: false`を残し、続ける。
書けなかった行は、履歴に穴として残る([R-CFGH-02](../security-risks.md#r-cfgh-02))。
穴は、証跡パックが、期間内の操作の記録で`history_recorded: false`を持つ行の数として示す。
数えられるのは、操作の記録が残る90日の範囲に限る。
穴の変更は、resourceに残っているので、照合が最大5分後に、`out_of_band`の行として書く([Consoleの外の変更の照合](#consoleの外の変更の照合))。
その行には、Consoleの操作者と理由コードは残らない。

失敗の原因は、次の4つである。

1. 入力が表の形に合わない。
   項目名が識別子でないか、操作者が1〜100字でないときで、文は送らない。
2. 表か関数が無い。
   migrationより先にコードが反映された間に起きる。
3. DBに届かないか、追記のadvisory lockが取れない。
   lockを持つのは別の追記のトランザクションだけで、追記は1行の挿入なので、待ちは短い。
   lockの待ちは、接続の`lock_timeout`に従う。
4. 追記の関数が返したidを整数として読めない。
   行が書けたかを確かめられないので、書けなかったものとして扱う。

## 理由コード

理由コードは、呼び出し側が明示する。
一覧はSQL関数`factory.config_history_reason_codes()`が返し、TypeScriptの`CONFIG_HISTORY_REASON_CODES`と同じ並びにする。
実DBの検査が、一覧の一致と、TypeScriptの一覧のすべての値を表が受けることを確かめる。
表の`CHECK`が、一覧の外の値を拒む。

| 理由コード | 条件 |
| --- | --- |
| `console_update` | Consoleの設定の更新で、真偽、数値、一覧の項目が変わり、書いた後の読み直しが期待と一致した |
| `console_update_unverified` | Consoleの設定の更新で書き込みは成功したが、読み直しが期待と一致しなかった |
| `stop_all_flag_off` | Consoleの全停止が、`*_enabled`を`false`にした |
| `unspecified` | 呼び出し側が理由を決められなかった |
| `out_of_band_change` | 照合が、履歴の最後の値と今の値が違う項目を見つけた |
| `out_of_band_removed` | 照合が、履歴にある項目が設定から無くなったのを見つけた |
| `snapshot_baseline` | 照合が、基準の段階に、履歴にまだ無い項目の最初の値を、比べる基準として残した。基準の段階が終わった印の行にも使う。変更ではない |
| `out_of_band_added` | 照合が、基準の印の後に、履歴にまだ無い項目がresourceに現れたのを見つけた。変更に数える |

コードを足すときは、新しいmigrationで`config_history_reason_codes`を置き換え、同じ変更で`CONFIG_HISTORY_REASON_CODES`に足す。
すでに書いた行の理由コードは、`row_hash`に含まれるので書き換えない。

## ハッシュの連鎖

`row_hash`は、行の次の項目を、この順に並べた文字列のsha256(16進)である。

1. `prev_hash`
2. `seq`
3. `item_key`
4. `reason_code`
5. `before`(jsonbの文字列表現)
6. `after`(jsonbの文字列表現)
7. `actor`
8. `source`
9. `occurred_at`

各項目は`<バイト長>:<値>`の形にし、値が`NULL`のときは`~`にして、`|`でつなぐ。
バイト長を付けるのは、値に区切りの文字が含まれても、項目の境界が曖昧にならないためである。
`occurred_at`は、接続の時刻帯に左右されないよう、UTCで`YYYY-MM-DD"T"HH24:MI:SS.US"Z"`の形(マイクロ秒まで)にする。
算出はSQL関数`factory.config_history_row_hash`が行い、追記と検証が同じ関数を使う。
遷移の履歴の関数とは別に持ち、片方のmigrationを戻しても、もう片方は動く。

連鎖の最初の行の`prev_hash`は、0を64個並べた文字列である。
2行目からは、1つ前の行の`row_hash`を`prev_hash`にする。
追記は、固定のadvisory lockを取って直列にし、`seq`を最後の行の次の値にする。
ロックはトランザクションの終わりまで持つ。
既定の分離水準(READ COMMITTED)では、ロックを取った後の文が、先の追記の結果を読む。

## 検証

`factory.config_history_verify()`が連鎖を検証する。
行のハッシュを再計算し、`prev_hash`のつながりと、`seq`が1から欠けずに続くことを確かめる。
壊れた位置を、`seq`の昇順に、理由つきですべて返す。

| 理由 | 意味 |
| --- | --- |
| `gap` | `seq`が欠けている。最初の行が1でないときを含む。欠けた次の行の`seq`を返す |
| `prev_hash_mismatch` | `prev_hash`が、1つ前の行の`row_hash`と合わない |
| `row_hash_mismatch` | 行の内容から求めたハッシュが、`row_hash`と合わない |

検証をSQLで行うので、言語をまたぐ正規化は要らない。
TypeScriptの呼び出しは`verifyConfigHistory`である。

連鎖の末尾の行を消した場合は、検証では見つからない([R-CFGH-03](../security-risks.md#r-cfgh-03))。
連鎖の長さと最後の連番は、証跡パックに載るので、前回の監査より短くなっていれば、人が気づける。

## 追記専用

行のトリガー`config_history_guard_row`が、UPDATEとDELETEを例外で拒む。
文のトリガー`config_history_guard_truncate`が、TRUNCATEを例外で拒む。
遷移の履歴と違い、通す例外は無い。
掃除の関数を持たないためである。

この歯止めは安全柵である。
表の所有者はトリガーを外せるので、歯止めは改ざんを防がない。
改ざんを見つけるのは、ハッシュの連鎖である。
所有者が連鎖の途中の行を書き換えれば、検証が、その行を指す。
所有者がその行から先の連鎖をすべて計算し直せば、検証は通る([R-CFGH-03](../security-risks.md#r-cfgh-03))。

## 保持

保持は無期限である。
行は、設定の変更の数だけ増え、増え方は少ない。
掃除の関数も、保持日数の設定も持たない。

## Consoleの外の変更の照合

Consoleの外の経路で変わった設定は、`config_snapshot`が5分ごとに見つけて、履歴に書く。
経路は、ホストのCLI(`mise run stop`、`mise run stop:restore`)、`wmill resource push`、Windmillの画面でのresourceの編集である。
旗を`true`に戻す復元も、この経路で見つかる。

### 手順

1. 項目ごとの、履歴の最後の`after`を読む(`DISTINCT ON (item_key)`を`seq`の降順で選ぶ1文)。
   読む順は、履歴が先で、resourceが後である([Consoleの経路との重なり](#consoleの経路との重なり))。
   読み取りには時間の上限を付け、読めなければ、その回は何も書かずに終える。
2. `f/factory/factory_config`のresourceを、補間しない生の値で読む(`ResourceService.getResourceValue`)。
   補間する読み取りは、`$var:`を秘密の値に解決するので使わない。
   読み取りには時間の上限を付け、読めなければ、その回は何も書かずに終える。
   値がオブジェクトでなければ、項目は読まず、resource全体の行を書いて、ジョブを失敗させる([resource全体がオブジェクトでないとき](#resource全体がオブジェクトでないとき))。
3. 最上位のすべての項目を、[値の射影](#値の射影)の規則で射影する。
   値が参照(`$var:`、`$res:`、`$jsonvar:`)を含む項目は、値を調べず、`{redacted: true, hash}`にする。
   項目名が履歴の項目名の形(小文字、数字、下線の識別子)に合わない項目は、書けないので、飛ばして数える。
   照合が自分の行に使う名前の項目も、飛ばして数える。
   名前は`config_snapshot_baseline`、`config_snapshot_unknown_keys`、`config_snapshot_resource`である。
   知らない項目は、名前の昇順に50項目まで射影し、超えた項目は調べない([書き込みの順と上限](#書き込みの順と上限))。
4. 今の射影と、最後の`after`を比べる。
   ハッシュの項目は、変更の経路が付ける`changed`を外して比べる。
   一覧の項目と伏せた印は、ハッシュも比べる。
   基準の印の行は、設定の項目ではないので、比べない。
5. 差があった項目を、書く順に、1項目1行で追記する。
   `source`は`out_of_band`、`actor`は`config_snapshot`である。
   `before`は履歴の最後の`after`、`after`は今の射影である。
6. 基準の段階で、基準の行をすべて書き終えたら、最後に基準の印の行を書く([基準の段階](#基準の段階))。

履歴の表か関数が無い間(migrationより先にコードが反映された間)は、何も書かずに終える。
resourceへは書かない。

### 見つける差と理由コード

| 差 | 理由コード | `before`と`after` |
| --- | --- | --- |
| 基準の段階(印が無い間)に、履歴にまだ無い項目が、resourceにある | `snapshot_baseline` | `before`は`null`、`after`は今の射影 |
| 基準の印の後に、履歴にまだ無い項目が、resourceにある | `out_of_band_added` | `before`は`null`、`after`は今の射影 |
| 履歴にある項目の射影が、今の射影と違う | `out_of_band_change` | 履歴の最後の`after`と、今の射影 |
| 履歴にある項目が、resourceに無い | `out_of_band_removed` | 履歴の最後の`after`と、`{removed: true}` |
| 知らない項目の数が、上限を超えた | `out_of_band_added`か`out_of_band_change` | 項目名は`config_snapshot_unknown_keys`、値は知らない項目の総数(`{count}`)。ほかの項目と同じ規則で比べる |
| resource全体が、オブジェクトでない値に変わった。またはオブジェクトに戻った | `out_of_band_change` | 項目名は`config_snapshot_resource`。`before`は、この項目の履歴の最後の値(無ければ`null`)。`after`は、値のハッシュ(`{redacted: true, hash}`)か`{kind: "object"}` |

項目が無くなった後で、同じ項目がまた現れたときは、`{removed: true}`との差として、`out_of_band_change`を書く。
無くなった項目が、無いままのときは、書かない。

履歴の最後の`after`が`null`で、項目がresourceに無いときも、書かない。
Consoleの経路は、読み直しで値が見つからなかった項目の`after`を`null`で書くためである。
値が`null`の項目を消したときの`out_of_band_removed`は、この規則のために書かれない。
履歴の最後の`after`が`null`で、項目がresourceにあるときは、値との差として、`out_of_band_change`を書く。

参照(`$var:`、`$res:`、`$jsonvar:`)を含む項目は、照合とConsoleが、同じ`projectConfigValue`で`{redacted: true, hash}`にする。
ハッシュは生の値から計算するので、参照を別の参照に変えた変更は、変更として書かれる。
参照される先の値の変更は、書かれない([参照の先の変更](#参照の先の変更))。

### resource全体がオブジェクトでないとき

Windmillは、resource全体の値を、別のresourceへの参照だけの文字列(`"$res:<path>"`)にすることを受け付ける。
補間して読むほかの読み取りは、この文字列を参照先のオブジェクトに解決するので、ほかのflowは動き続ける。
補間しない照合だけは、文字列を見る。
照合が何も書かずに終えると、resourceを書ける人は、履歴に行を残さず、参照先のオブジェクトを変え続けられる。
このため、resourceがオブジェクトでない間は、次のとおりにする。

- 予約の項目`config_snapshot_resource`に、1行だけ書く。
  - 理由コードは`out_of_band_change`、`source`は`out_of_band`、`actor`は`config_snapshot`である。
  - `before`は、この項目の履歴の最後の値で、行が無ければ`null`である。
  - `after`は、生の値の正規化したJSONのハッシュ(`{redacted: true, hash}`)である。
    ハッシュはメモリの中で計算する。
    生の値(参照の名前)は、履歴、ログ、結果のどこにも残さない。
- 同じ値の間は、書かない。
  履歴の最後の値が、今の値の射影と同じなら、何も書かない。
  別の値(別の参照や、数)に変わったときは、もう1行書く。
- オブジェクトに戻ったときは、この項目の履歴の最後の値が`{kind: "object"}`以外なら、`after`が`{kind: "object"}`の行を1行書く。
  履歴にこの項目の行が無いとき(一度もオブジェクトでなくなっていないとき)は、書かない。
  この行は、ほかの行より先に書き、行の上限に数えない。
- オブジェクトでない間は、項目を1つも比べない。
  基準の行も、基準の印の行も、書かない。
- 結果の`skipped_reason`は`resource_not_object`で、`changed`と`failed`に、resource全体の行を書けた数と書けなかった数が入る。
  scriptは、行を書いた後で、ジョブを失敗させる。
  失敗の文は固定で、値と項目名を入れない。
  失敗が続くと、scheduleの連続した失敗の検知が、3回目に要対応の通知にする。

resourceと履歴を読めなかった実行(`resource_unreadable`、`history_unreadable`)は、ジョブを失敗させない。
読み取りの一時的な失敗で、要対応の通知を出さないためである。
読めない状態が続くことは、結果の`skipped_reason`には出るが、通知にはならない。

予約の項目の行は、証跡パックで、基準の印の行と違い、変更として数える。
項目ごとの件数にも載る。

resource全体が参照になった後の、参照される先のオブジェクトの変更は、履歴に残らない([参照の先の変更](#参照の先の変更))。

### 参照の先の変更

項目の値を参照(`$var:`、`$res:`、`$jsonvar:`)に書き換えると、履歴には、切り替えが1回の変更として残る。
その後の、参照される先の値の変更は、履歴に残らない。
照合は参照を解決しないためである。
解決すると、変数や別のresourceの秘密の値を読むことになる。
この選択を、設計として受け入れる([R-CFGH-07](../security-risks.md#r-cfgh-07))。

- 基準の段階で、すでに参照として書かれていた項目は、基準の行が参照の印で始まるので、参照への切り替えの行を持たない。
- resource全体が参照になった場合は、予約の項目の1行が残るだけで、参照先のオブジェクトの、その後の変更は残らない。

### 基準の段階

履歴にまだ無い項目を、基準にするか、足された項目にするかは、基準の印の行の有無で決める。
項目ごとに「履歴に行が無い」ことで決めると、最初の実行の後に足された項目が、基準の行になり、変更の件数から外れてしまう。

- 印が無い間(基準の段階)は、履歴にまだ無い項目のすべてに、基準(`snapshot_baseline`)を書く。
  基準は変更ではなく、以後の変更を比べるための値である。
  基準の行は、行の上限に数えない。
  実行全体の時間の区切りには従う。
- 基準の行をすべて書き終えた最後に、印の行を1行書く。
  項目名は`config_snapshot_baseline`、理由コードは`snapshot_baseline`である。
  `source`は`out_of_band`、`before`は`null`、`after`は`{kind: "marker"}`である。
  基準の行を1つでも書けなかった実行と、時間の区切りで書き残した実行は、印を書かない。
  次の実行が、基準の続きを書く。
  基準の行をすべて書いた後で、時間が尽きた実行も、印を書かない。
  次の実行が、印だけを書く。
- 印が書かれた後は、履歴にまだ無い項目を、足された項目(`out_of_band_added`)として書く。
  `before`は`null`、`after`は今の射影で、変更に数える。
  証跡パックの期間内の変更と項目別の件数に入る。
- 印の行は、設定の項目ではない。
  比べるときに除き、証跡パックのどの件数にも数えない(連鎖の行の数には入る)。

基準より前に、Consoleの外で起きた変更は、履歴に残らない。
履歴の行は追記専用なので、印の行は、表の書き込みの権限では消せない。
連鎖の途中の行を消した改ざんは、欠番として検証が見つける。
末尾の行を消した改ざんは、見つからない([R-CFGH-03](../security-risks.md#r-cfgh-03))。

### Consoleの経路との重なり

Consoleの経路は、変更の成功の後に、変更後の値の射影を自分で書く。
照合は、その行の`after`を、今の射影と比べるので、値が同じなら何も書かない。
同じ変更が二重に残らないのは、この比較による。

Consoleの設定の更新で、読み直しが期待と一致しなかった行(`console_update_unverified`)は、`after`が読み直した値の射影である。
今のresourceの値と違えば、差になり、照合が`out_of_band_change`を書く。

Consoleが設定を書いてから、自分の行を書くまでの間に、照合が走ると、同じ変更の行が2つ残りうる。
照合の行が先に付き、Consoleの行がその後に付く。
2行は、`source`と`reason_code`で見分けられる。

照合は、履歴を先に読み、resourceを後で読む。
Consoleは、resourceを書いた後に、自分の行を書く。
この2つの書き込みの間に、照合の2つの読み取りが入っても、組は、古い履歴と新しいresourceになる。
この組で書かれるのは、正しい値で、経路の記録だけが違う重複の行である。
順が逆だと、組は、新しい履歴と古いresourceになり、古い値へ戻した偽の行が増える。

### 書き込みの順と上限

差は、次の順に書く。
同じ群の中は、項目名の昇順である。

1. 知っている項目(`isKnownConfigKey`)の、変更、無くなった項目、足された項目
   - 知らない項目の総数の項目(`config_snapshot_unknown_keys`)も、この群に入れる。
2. 知らない項目の、変更、無くなった項目、足された項目
3. 基準の行

1回の実行で書く行は、1と2の合計で100行までにする。
基準の行(3)は、この上限に数えない。
超えた差は、次の実行に回し、ログに件数だけを出す。
差は、書くまで残るので、変更が無いまま2回続けて実行しても、2回目は何も書かない。
1行の書き込みが失敗しても、残りを続け、失敗した項目は、次の実行でもう一度差として見つかる。

項目名の昇順だけで100行を切ると、狙った項目の変更が、後ろへ押しやられる。
設定に知らない項目を多数足されると、狙った変更は、何回もの実行の間、書かれない。
知っている項目は、表に数十あるだけなので、100行の上限を使い切らない。
狙った変更が知っている項目なら、知らない項目がいくつあっても、次の実行で書かれる。
知っている項目は、表の名前だけである。
名前の規則に合うだけの項目は、知らない項目に入れる。

知らない項目の数にも上限を置く。
知らない項目は、名前の昇順に50項目まで調べる。
超えた項目は、値と履歴を調べず、`deferred`に数える。
超えた項目に履歴の行があっても、無くなった項目とは見なさない。
知らない項目が50項目を超える間は、知らない項目の総数を、`config_snapshot_unknown_keys`の項目(`{count}`)として、ほかの項目と同じ規則で比べて書く。
総数が変わらなければ、書かない。
総数が上限以下に戻ったときは、その項目が無くなった行(`out_of_band_removed`)を書く。
上限の中の知らない項目の値は、射影が`{kind: "unknown"}`なので、値の変更は見えない。
調べない項目は、その有無の変更も見えない。

`deferred`が1以上の実行は、書ける行を書いた後で、ジョブを失敗させる。
失敗の文は件数だけで、項目名と値を含まない。
書き残しが続くと、scheduleの連続した失敗の検知(`detect_schedule_failures`)が、3回目に`schedule_failing`の要対応の通知にする。
新しい通知の種類は足さない。
書き残しが1回だけで消えた実行は、1回の失敗にとどまり、通知にならない([R-CFGH-06](../security-risks.md#r-cfgh-06))。

実行全体にも時間の区切りがある。
実行の開始から40秒を過ぎたら、残りの行は書かずに、`deferred`に数え、そのまま終える。
ジョブのtimeoutは60秒で、1回の読み書きの上限は15秒である。
区切りを過ぎた分は、次の実行が、差としてもう一度見つける。

追記は1行ずつ、別々のトランザクションで行う。
追記の関数が連鎖の固定のadvisory lockで直列にするので、並行するConsoleの追記と、連鎖が崩れることはない。

### 読み取りの索引

項目ごとの最後の行を読む1文は、`(item_key, seq DESC)`の索引`config_history_item_key_seq_idx`を使う。
履歴は追記専用で縮まないので、索引が無いと、5分ごとに表全体を並べ替える。
索引は、照合のmigrationが作り、downが消す。

### 結果とログ

scriptは、件数だけの結果を返す。
項目名と値は、結果にも、ログにも出さない。

| 項目 | 内容 |
| --- | --- |
| `keys_checked` | 射影した項目の数 |
| `baseline`、`added`、`changed`、`removed` | 書いた行の数。`baseline`は印の行を含まない |
| `marker_written` | 基準の印の行を書いたら1、書かなかったら0 |
| `failed` | 書けなかった行の数。印の行を含む |
| `deferred` | 行の上限、実行全体の時間の区切り、知らない項目の数の上限で、書かずに次に回した差と項目の数。0でないと、ジョブは失敗する |
| `reference_keys` | 参照を含み、値を見ずに伏せた項目の数 |
| `unnamed_keys` | 項目名の形に合わない、または照合の予約の名前で、飛ばした項目の数 |
| `unknown_keys` | 知らない項目の総数 |
| `skipped_reason` | 終えられなかった理由。`resource_unreadable`、`resource_not_object`、`history_missing`、`history_unreadable`のどれか。終えたときは`null`。`resource_not_object`のときだけ、ジョブを失敗させる |

scriptは、読み取りの失敗では投げない。
読み取りの失敗(`resource_unreadable`、`history_unreadable`)は、`skipped_reason`に出し、次の実行を待つ。
resourceがオブジェクトでないとき(`resource_not_object`)と、書き残しが出たときは、行を書いた後でジョブを失敗させる。

### 照合が見つけない変更

次の変更は、履歴に残らない([R-CFGH-01](../security-risks.md#r-cfgh-01))。

- 照合の間隔(5分)の中で、元の値へ戻された変更
  - 照合は、各回の値だけを比べるので、間の値は見えない。
- 基準を書く前の変更
- 射影が`{kind: "unknown"}`の項目(表に無い項目)の値の変更
  - 項目の有無だけが分かる。
  - 表にある項目の、型に合わない値は、ハッシュを持つので、差し替えが分かる。
- 参照される先の値の変更
  - 項目の値が参照(`$var:`、`$res:`、`$jsonvar:`)のとき、参照を別の参照に変えた変更は分かるが、参照の先は解決しないので、先の値の変更は分からない([参照の先の変更](#参照の先の変更))。
- 知らない項目が50項目を超える間、超えた項目の変更
  - 総数の変化(`config_snapshot_unknown_keys`)だけが分かる。
- 照合が動いていない間の変更
  - 全停止はscheduleを止めるので、全停止の間は照合も動かない。
  - 再開した後の最初の実行が、差をまとめて書く。

次のことも、履歴からは分からない。

- 変更した人
  - `actor`は常に`config_snapshot`である。
- 変更した時刻
  - 行の`occurred_at`は、照合が見つけた時刻である。
  - 変更の時刻より最大5分遅い。

履歴に記録が無いことは、照合が動いていなければ、設定が変わらなかったことを示さない。
復元は、照合が最大5分遅れて記録する。
履歴の最後の値は、照合が動いている間は今の設定とみなせるが、最大5分の遅れがある。

履歴と照合が信頼する前提は、履歴と設定のresourceに書けるのが、レビューを経てマージされたscriptだけであることである。
侵害されたworkerは、resourceを書き換え、同じ射影の行を自分で追記して、照合を欺ける([R-CFGH-05](../security-risks.md#r-cfgh-05))。

## 証跡パックの節

証跡パックの節「設定の変更」は、連鎖の検証の結果と、期間内の変更の項目別と理由コード別の件数を載せる。
期間内の変更の件数と項目別の件数は、基準(`snapshot_baseline`)の行を数えない。
基準は変更ではないためである。
基準の印の後に足された項目(`out_of_band_added`)の行は、変更として数える。
resource全体の行(`config_snapshot_resource`)も、変更として数え、項目ごとの件数に載せる。
基準の印の行は、どの件数にも数えない。
理由コード別の件数には、基準の行も入る。
基準の行が期間内に1件以上あるときは、削れる行「基準の記録」に、その件数を載せる。
固定の行「記録の範囲」は、記録するものを示す。
記録するのは、Consoleの設定の更新、全停止による停止、5分ごとの照合が見つけたConsoleの外の変更である。
見えない変更として、間隔の中で戻された変更と、基準より前の変更も示す。
履歴を書けなかった操作が期間内に1件以上あるときは、固定の行「記録できなかった操作」を足す。
この件数は、操作の記録の範囲(90日)に限る。
内容は[監査の仕様の「設定の変更」](audit.md#設定の変更)に書く。
