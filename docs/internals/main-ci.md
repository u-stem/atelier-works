# mainのCI監視の内部仕様

工程4の`watch_main_ci`が、何を読み、どう判定し、何を通知するかを定める仕様である。`watch_main_ci`、`lib/main_ci_watch.ts`、`lib/main_ci_support.ts`を変更する人が読む。必要な権限は[セキュリティ](../security.md)に、通知を受けた人がすることは[運用](../operations.md)に書く。

## 方針

作業項目の状態、終端、リードタイムには触れない。記録は`factory.main_ci_runs`だけに残す。
監視の単位はコミットである。コミットの作り手(Factory、人)は区別せず、原因のPRも特定しない。通知には、リポジトリ、コミットの先頭7文字、実行のURLだけを載せる。

## 対象のリポジトリ

`factory_repo`と`repo_allowlist`のうち、`isRepoAllowed`が許すものを対象にする(`listMainCiTargets`)。
`owners`は、`id`の照合を通ったオーナーだけを渡す。名前が付け替えられたアカウントのリポジトリを読まないためである。
`factory_repo`は`isRepoAllowed`が常に許すので、照合の対象外で、必ず対象になる。
`repo_allowlist`が空のときは`factory_repo`だけになる。`poll_prs`と違い、`owners`の全リポジトリを列挙するAPIは使わない。
リポジトリは、設定の綴りで`main_ci_runs`の行と対応する。オーナーやリポジトリの綴りを変えると、新しい綴りは初めての観測として扱い、既存のコミットを`baseline`で記録する。
GitHubのリポジトリのURLとして読めない項目は読み飛ばし、件数だけをログに残す。URLに認証情報が埋め込まれていることがあるためである。

## 発見

リポジトリごとに、既定のブランチへのpushの実行を新しい順に1ページ(20件)読み、`head_sha`ごとにまとめる。
ブランチの一覧では、ブランチやeventが合わない実行を捨てて続ける。ブランチと同じ名前のタグのpushで動いた実行が混ざりうるためである。

まだ記録していないコミットは、`planNewShas`の順に記録する。

- 記録の無いリポジトリの初回の観測では、既存のコミットを`baseline`で記録し、判定と通知は行わない。
- 記録済みの最新の実行より古いコミットも`baseline`にする。掃除で消えた行のコミットが一覧に残っていても、古い失敗を新しく通知しないためである。
- それ以外は`pending`で記録する。

1件の記録に失敗したら、そのリポジトリの残りは記録せず、次の回に回す。続けると、最新の`baseline`が抜けて既存の失敗が`pending`になったり、古い`pending`が黙って`baseline`になったりするためである。

1ページが満杯(20件)で、最古の実行が記録済みの最新の実行より新しいときは、間のコミットを見逃した可能性がある。ログに`main ci discovery page is full; older commits may be missed`を残す。

## 判定

判定待ち(`pending`)のコミットは、最初に見たものから最大200件取り出す。
コミットごとに、`head_sha`を指定して実行を取り直す(1ページ100件、3ページまで)。
ページが上限まで埋まった場合と、別のコミット、ブランチ、eventの実行が混ざった場合は、そのコミットの実行を読み切れないものとして扱う。

判定は2段で行う。先に全行の結果を決め、次に`passed`、`failed`、`expired`と`no_ci`の順に適用する。
同じ回で古いコミットが失敗し、新しいコミットが通ったときに、古い失敗を通知しないためである。

`decideState`が状態を決める。

| 状態 | 条件 |
| --- | --- |
| `passed` | 最古の実行から2分以上たち、すべての実行が完了していて、結論がsuccess、skipped、neutralだけ |
| `failed` | 同じく確定していて、それ以外の結論(failure、timed_out、cancelled、action_required、stale、未知の値)がある |
| `no_ci` | 照会して実行が0件のまま、最初に見てから15分たった。通知しない |
| `expired` | 未完了のまま、最古の実行から2時間たった。通知しない。ただし、完了した失敗が1件でもあれば`failed`にする |
| `pending` | 上のどれでもない。次の回に取り直す |

期限が来ても、完了した失敗の実行があれば、通知せずに捨てず、`failed`として確定する。未完了の実行が残っていても、失敗は確かなためである。
`cancelled`は失敗に数える。mainの実行を取り消す設定のリポジトリでは、取り消しが失敗として通知される。

実行を取り直せなかったコミットは、読めない理由で扱いが分かれる。

- 次のどちらかの永続的な条件で読めないときは、最初に見てから24時間たったら`expired`にする(通知しない、ログのみ)。人に知らせる手段が無いまま、行が残り続けるのを防ぐためである。
  - `head_sha`を指定した読み取りが、実行の多さ(`WorkflowRunsIncompleteError`)か403・404で、読み切れない。
  - リポジトリが対象から外れた。
- それ以外では、何も決めずに次の回に回し、期限を進めない。rate limit、サーバーの一時的な失敗、発見の失敗(発見の403・404を含む)、経過時間の予算切れが当たる。発見の403・404は、権限が戻れば読めるようになる一時的な条件として扱う。読めていない実行の結果を捨てないためである。

## 失敗の通知

`failed`のコミットは、次の順に処理する。

1. 1つ前のコミット(`getPreviousMainCiRun`)が`failed`だったかを決める。`pending`や`baseline`は失敗として数えない。
2. 要約(`summary`列)を作る。失敗したworkflowの名前(整形して60文字まで)と結論を並べ、全体を400文字までにする。1つ前も失敗なら、前のコミットから失敗が続いている旨を添える。
3. 次のどちらかなら、通知を出さずに手順5へ進む。知らせても人の行動につながらないためである。
   - このコミットより新しい`passed`のコミットが、同じリポジトリにある。直った後で分かった失敗である。
   - 最初に見てから24時間以上たち、同じリポジトリに、このコミットより新しい行が状態を問わず記録済みである(実行の時刻と`id`の組で比べる)。権限が長く戻らなかった後に判定が再開したときに、止まっていた間の古い失敗を一度に通知しない。

そのリポジトリで最新の行の失敗は、24時間以上たっていても通知する。止まっていた間にpushが無く、今も壊れているmainの先頭の失敗を捨てないためである。
権限を戻すと、最新の失敗が通知され、より新しい行がある古い失敗は通知されない。

続きの手順は次のとおりである。
4. 要対応のnotice`main_ci_failed`を登録する。noticeを新しく登録できたときだけ、Discordに`main_ci_failed`を送る。1つ前も失敗のときは、noticeの本文に前のコミットから失敗が続いている旨を添える。
5. 状態を`failed`に更新する(`WHERE state = 'pending'`)。要約は、手順3で通知を出さなかったときも残す。

noticeを先に登録し、状態の更新を後にする。更新が先に成功して登録が失敗すると、通知が永久に出ないためである。更新に失敗した回は、次の回に同じ手順をやり直す。noticeは重複が索引で防がれるので、Discordは重ねて送らない。

noticeの本文は、`<owner>/<repo>:`で始まる固定文に、コミットの先頭7文字と実行のURLだけを入れる。workflowの名前と結論は、リポジトリへ書ける人が決める文字列なので、本文には載せない。
実行のURLは、失敗した実行のうち、`parseRunUrl`を通ったものを使う。通るものが無ければ、検証済みの名前とshaから作ったコミットのページにする。

## 自動解決

あるコミットが`passed`になったとき、同じリポジトリに、そのコミットより新しい判定待ち(`pending`)か失敗(`failed`)の行が無ければ、未解決の`main_ci_failed`を解決する。
新しい行が`passed`、`expired`、`no_ci`、`baseline`なら、解決を妨げない。
解決の対象は、種類が`main_ci_failed`で、本文が`<owner>/<repo>:`で始まるものである。種類を固定するので、`main_ci_check_denied`などほかの種類は解決しない。
解決者は`watch_main_ci`で、Consoleは「mainのCIの監視(自動)」と表示する。
より新しいコミットが判定待ちか失敗なら、その結果を待つ。古いコミットが遅れて通っても、新しい失敗を解決しないためである。
新しさは、実行の時刻と`id`の組で比べる。時刻が同じなら、`id`の大きい行を新しいとする。同じ時刻のBとCがあるとき、BはCの失敗を解決しない。
解決は冪等なので、状態の更新より先に行う。更新に失敗した回は、次の回にやり直せる。

新しいコミットが判定待ちの間に古いコミットが通り、その新しいコミットが`expired`か`no_ci`で終わることがある。このとき、失敗の通知は、次に通るコミットまで残る。人が解決してよい。

古いコミットBの実行が長引き、新しいコミットCが先に`passed`となる場合がある。Bの失敗が確定しても、通知は出さない(失敗の通知の手順3)。Bの`failed`は記録に残る。
この扱いは、新しいコミットが通ったことを、古い失敗が直ったとみなす前提に立つ。
mainのpushで動くworkflowをパスで絞っていると、この前提が成り立たない。新しいコミットでは、古いコミットで失敗したworkflowが動かないまま、CIが通るためである。古い失敗の通知は、出ないことがある。
この条件は、`repo_allowlist`に入れるリポジトリの要件に含める。

mainへのpushで承認待ちになるworkflowなどのために、どのコミットも`passed`にならないリポジトリでは、自動解決されない。失敗の通知は、人が解決する。

同じコミットの実行をやり直して通っても、`failed`は終端のまま戻らない。失敗の通知を解決するのは、後続のコミットが`passed`になった回である。

## 権限エラー

発見の読み取りが403か404で失敗したリポジトリは、`main_ci_check_denied`を1リポジトリにつき1件登録する。本文はリポジトリごとに同じ文なので、未解決の通知がある間は重ねて登録されない。毎回の実行で読み直し、読めたら未解決の`main_ci_check_denied`を種類と接頭辞で解決する。Discordには送らない。
rate limitの403は権限エラーとして扱わない。一度待って再試行しても解けなければ、その回はGitHubを読むのをやめ、判定待ちのコミットはそのまま残す。

## APIの呼び出し数

1回の実行で呼ぶGitHubのAPIは、次のとおりである。

- オーナーの照合。`owners`の数だけ呼ぶ。
- 対象のリポジトリごとに、既定のブランチの取得と実行の一覧の取得。
- 判定待ちのコミットごとに、実行の取得。1〜3ページで、判定待ちは最大200件である。

## 経過時間の予算

1回の実行は、開始から180秒を超えたら、次の3つを始めない。残りは次の回に回す。

- 新しいリポジトリの発見
- 新しいコミットの読み取り
- 失敗の確定

失敗の確定は、通知の登録とDiscordの前に予算を見る。超えていれば、通知も状態の更新もせず、行は判定待ちのままになる。
ただし、1回の実行で最初の1件は予算を見ずに確定する。予算切れが続いても、失敗の通知が飢えないためである。
通ったコミットなど軽い適用は、予算の対象にしない。
時計は注入でき、テストでは進め方を変えて確かめる。

scriptのtimeoutは600秒である。見積もりは次のとおりである。

- 1回の要求の上限は、ghの実行60秒、5xxの再送(待ち2秒と実行60秒)、rate limitの待ち120秒を足した約240秒である。rate limitの待ちの後に再び拒まれたら、読み取りをやめる。
- 予算の直前に始めた発見は、既定ブランチの取得と実行一覧の2要求なので、最悪で約480秒かかる。
- 予算の直前に始めた判定の読み取りは、1ページなら約240秒かかる。実行が100件を超えるコミットは最大3ページで、その3倍になる。
- 適用の段では、最初の失敗の確定だけが予算を見ない。Discordの待ちは最大30秒である。

通常は、rate limitの待ちと再送が起きず、数秒から数十秒で終わるので、timeoutに収まる。
rate limitの待ちが重なると、timeoutを超えうる。そのときはjobが打ち切られるが、行ごとの更新は冪等なので、確定しなかった行は次の回に残る。

## 例外の扱い

例外は、リポジトリごと、コミットごとに捕まえて、ほかの処理を止めない。
捕まえた例外は、`factory.job_failures`に記録する。rate limitと、権限エラー、実行を読み切れないエラーは、記録せずログだけに残す。

## 時計

時刻は実行の最初にworkerの`now`を1回だけ読む。GitHubの時計とずれても、確定を待つ2分と、期限の15分、2時間、24時間に余裕があるので、判定の結果は変わらない。
