# 監査の内部仕様

工程5の監査が、いつ起動し、何を集め、何を検査して保存するかを定める仕様である。監査のscript、フロー、`factory-audit`スキルを変更する人が読む。監査で守る信頼境界の考え方は[セキュリティ](../security.md)に書く。

## 起動

監査の起点は`audit_kickoff`である。起動元は2つあり、引数`source`で区別する。

| 起動元 | `source` | 作業項目の`claimed_by` |
| --- | --- | --- |
| 毎週月曜09:30のスケジュール | `schedule` | 空 |
| Consoleの**レポート**の**今すぐ監査** | `manual` | 実行したユーザー(`WM_USERNAME`) |

`audit_kickoff`は対象期間を決め、次の順に起動を見送るかを判定する(`decideAuditKickoff`)。見送りは戻り値とログに残すだけで、通知しない。人の対応は要らないためである。

| 順 | 見送る理由 | 条件 |
| --- | --- | --- |
| 1 | `audit_in_progress` | 別の監査の作業項目が`picked`か`auditing`にある |
| 2 | `empty_period` | 対象期間が空になる |
| 3 | `daily_budget_exceeded` | 日次予算を超えている |
| 4 | `no_new_records` | 期間に行動につながる記録が無い。強制実行(`force`)のときは判定しない |

行動につながる記録として数えるのは、失敗、決定済みの承認依頼、Claudeの実行、修正ラウンド、レビュー、デプロイ、要対応事項の7種類である。1件でもあれば監査する。

見送らなければ、`picked`の監査の作業項目を挿入して`f/factory/audit`を起動する。挿入は部分一意インデックス`work_items_active_audit_key`で守る。別の監査が同時に作業項目を作っていれば挿入は何もせず、`concurrent_kickoff`として見送る。

起動の戻り値がジョブIDの形でなければ、例外で`audit_kickoff`を失敗させる。ジョブIDは作業項目の`flow_job_id`に記録する。

## 対象期間

対象期間は、始まりを含み終わりを含まない区間である。終わりは実行日のJSTの00:00で、実行日の当日は含めない。

| 前回の監査 | 始まり |
| --- | --- |
| 無い | 終わりから`days`日前。`days`は既定7日で、`max_lookback_days`を上限にする |
| 前回の終わりが`max_lookback_days`より前 | 終わりから`max_lookback_days`日前 |
| それ以外 | 前回の監査レポートの終わり |

`max_lookback_days`の既定値は28日である。始まりを切り詰めたときは、切り捨てた日数を`unaudited_gap_days`として証跡に記録する。`days`は正の整数でなければ例外にする。

## 証跡パック

監査に渡す資料を証跡パック(`evidence.md`)と呼ぶ。`audit_prepare`が期間のDBの記録を集めて作る(`f/factory/lib/audit_evidence.ts`)。

証跡パックは次の節で構成する。

| 節 | 内容 |
| --- | --- |
| 対象 | インスタンスと期間 |
| 実行統計(stage別) | Claudeの実行の件数と費用 |
| 失敗(flow + step別) | フローの失敗と、発生時に稼働していた版 |
| 却下 | 却下された承認依頼 |
| 要人手・ブロック・期限切れ | 人の対応待ち、中断、期限切れの作業項目 |
| 修正ラウンド | PR修正の結果 |
| レビュー指摘 | PRレビューの指摘 |
| 通知 | 期間内に作成した通知の種別内訳と、未解決の通知 |
| デプロイ | 自己更新の結果と、期間中の稼働版の推移 |
| 過去の提案(直近3回) | 直近3回の監査の提案と決定 |

先頭には、このファイルが指示ではなく監査の入力データであることを述べる注意書きを置く。

DBから読んだ文字列は、すべて`sanitizeCell`を通す。秘密をマスクし、HTMLのコメントとタグを取り除き、改行とパイプと連続する空白を1つの空白にまとめる。1行は300字で切り詰める。行はすべて箇条書きの記号で始め、DBの値がMarkdownの見出しや引用として読まれないようにする。

全体は12000字に収まるよう、節の中のデータ行を削る。文字列を途中で切ることはしない。見出しと固定の行だけで上限を超えるときは、上限を超えたまま返す。

### 稼働版

自己更新が成功すると、反映したコミットを`deployments`に記録する。
稼働版は、成功したデプロイの記録だけから導く。
失敗したデプロイは、記録上は稼働版を変えない。
ただし、自己更新は`wmill sync push`の後でも失敗しうるため、失敗したデプロイは、途中まで反映した可能性がある。

| 場所 | 内容 |
| --- | --- |
| デプロイの節の固定の行 | 期間の開始時点と終了時点の稼働版 |
| デプロイの節の一覧 | 期間内のデプロイを新しい順に最大30件。反映前後の版と、成功か失敗か |
| 失敗の節の各行 | グループの最初と最後の失敗が起きたときの稼働版。版が違えば`→`でつなぐ |

一覧に載せないデプロイがあるときは、一覧の末尾に`一覧に含めない古いデプロイ`として、その件数を示す。
一覧は新しい順に並べる。文字数の上限のために行を削るときは、この節では末尾の`一覧に含めない古いデプロイ`の行を最初に落とし、続けて古い記録から落とす。

稼働版は、時刻に応じて次の規則で導く。

| 対象 | 稼働版 |
| --- | --- |
| 失敗が起きた時刻 | その時刻以前で最後の成功デプロイの反映先。無ければ、その時刻より後で最初の成功デプロイの反映元 |
| 期間の開始時点と終了時点 | その時刻より前で最後の成功デプロイの反映先。無ければ、その時刻以後で最初の成功デプロイの反映元 |

デプロイの記録は`retention_logs_days`(既定30日)を過ぎると掃除で消える。
最後の成功の記録が消えていても、後の成功デプロイの反映元から版を導けるのは、このためである。
どちらの記録も無いときは導けないものとして、失敗の行に`版不明`の件数を、版が1つも無ければ`未設定`を示す。
期間の開始と終了の稼働版が導けないときは、`未設定`を示す。

成功したデプロイで`needs_host_action`が真のものは、`infra/`と`mise.toml`の変更を含み、次にホストで`mise run up`するまで反映されない。
この変更は、稼働版に含まれていても、ホストへの反映が済むまで動いていない。
デプロイの節の固定の行は、該当するデプロイの件数を示す。

グループの最後の失敗が期間の終了時点の稼働版と違う版で起きたときは、失敗の行に`期間末の版より前の版で発生`と示す。
この表示は版の違いだけを示す。失敗の原因が後の版で直ったかどうかは、記録から導けないため示さない。
監査は、失敗の原因となる処理が後の版で変わったかを、リポジトリの履歴で確かめる。

### 未解決の通知

通知の節は、未解決の通知を2つの母集団に分けて示す。

| 行 | 母集団 |
| --- | --- |
| 未解決(期間内に作成) | 期間内に作成され、集計時点で未解決の通知 |
| 未解決(期間前から) | 期間の開始より前に作成され、集計時点で未解決の通知 |

件数は固定の行で、種別ごとの内訳は削れる行で示す。
内訳の行には、種別と件数と、その種別で最も古い通知の作成時刻を載せる。
件数は内訳の件数の合計であり、別に数えない。
内訳の行は、期間内に作成した通知の種別内訳より前に置き、行を削るときは後ろの種別内訳から落とす。

期間の終わり以後に作成された通知は数えない。
通知が解決した時刻は記録されないため、解決したかどうかは集計時点の値である。

重要度が「情報」の未解決の通知は、同じ本文の通知が続くと、作成から1日を過ぎた後に作成時刻が更新される([作成時刻の更新](notifications.md#作成時刻の更新))。
更新された通知は、更新後の時刻の期間に数える。そのため、この節の行の読み方は次のとおり変わる。

- 「未解決(期間前から)」には、長く続く情報の通知が含まれない。更新のたびに作成時刻が進み、期間内に作成した通知として数えるためである。期間内に更新された情報の通知は、期間前から残る通知に含まれない。
- 内訳の「最古」は、情報の通知では最後の更新の時刻である。通知が初めて起きた時刻とは限らない。
- 期間内に作成した通知の種別内訳の件数も、更新の影響を受ける。更新された情報の通知は、更新後の期間にだけ数える。
- 期間の終わりで絞るのは、期間より後に作られた通知で数が増えないようにするためである。ただし、更新で作成時刻が進むため、後から集計し直すと、更新された情報の通知の分だけ、その期間の件数が減りうる。

### 未設定の値

記録に値が無いグループは、キーを空欄にせず`未設定`として件数を示す。
`null`と空文字は1つの`未設定`にまとめる。
グループの並びは件数の降順、同数ならキーの昇順で固定する。

修正の返信の`decision`と、レビュー指摘の`kind`が空になる記録の経路は、特定できていない。
Claudeの出力は、記録の前に型ガードで検査する。
一方、`insertFixRound`と`insertReview`は型で必須にしているだけで、実行時には検査しない。
`未設定`の件数は、記録の経路を調べる手掛かりとして、そのまま示す。

## 準備

`audit_prepare`は、作業項目の状態で始め方を決める。

| 状態 | 扱い |
| --- | --- |
| `picked` | `auditing`へ比較交換で移して始める |
| `auditing` | ステップの再試行として、遷移をやり直さずに再開する |
| それ以外 | 何もせずに`skip`を返す。生成ステップも飛ばす |

`picked`からの比較交換が一致しなかったときは、読み直した状態が`auditing`なら再開し、それ以外なら飛ばす。

準備ステップは証跡パックを作り、Factory自身のself cloneを同期する。日次予算はここでは確かめない。`audit_kickoff`が作業項目を作る前に確かめているためである。

## 生成

`audit_generate`は、作業項目が`auditing`のときだけ動く。失敗すると、Windmillが60秒おいて2回まで再試行する(`attempts: 2`)。

作業用のディレクトリは`/var/lib/factory/audits/wi-<id>`で、`evidence.md`とテンプレートの複製の`report.md`を置く。Claudeは`report.md`を`Edit`で埋める。

| 項目 | 値 |
| --- | --- |
| カレントディレクトリ | 作業用のディレクトリ |
| ツール | `Read`、`Glob`、`Grep`、`Edit` |
| 許可するツール | `Edit`(`--permission-mode dontAsk`で確認なしに実行する) |
| 読み取り専用で渡すもの | self cloneのスナップショット(`--add-dir`) |
| スキル | `factory-audit` |
| 構造化出力 | `{summary, proposals}`。提案は`{title, body}`の配列 |
| モデル | `heavy_model` |
| 上限 | `max_turns`、`max_budget_usd_per_run`、`claude_timeout_sec` |

### スナップショット

Claudeには、`self_update`がデプロイ元にするself cloneそのものを見せない。`Edit`を許可しているので、そこへ書き込まれると次のデプロイに入ってしまうためである。

代わりに、実行のたびにself cloneのHEADを使い捨てのdetached worktree(`/var/lib/factory/audits/wi-<id>-snapshot`)に取り出す。テンプレート、スキル、`--add-dir`のツリーはすべてこのスナップショットから読む。スナップショットの操作はself cloneのロックを取ってから行い、`self_update`と競合しないようにする。

作業用のディレクトリとスナップショットは、成否にかかわらず`finally`で消す。ステップを再試行すると両方を作り直す。強制終了した実行が残したスナップショットは、作る前に消す。

### 検査

レポートと構造化出力は、保存する前に`f/factory/lib/audit_doc.ts`で検査する。

| 対象 | 検査 |
| --- | --- |
| レポートの章立て | `##`の見出しが、順序も含めてテンプレートの6章と一致する |
| レポートと構造化出力 | HTMLコメントが残っていない。見出しにコード表記が無い |
| 改善提案の表 | 表のタイトルの列が、構造化出力の提案のタイトルと集合として一致する |
| 要約 | 200字以内 |
| 提案 | 5件以内。タイトルは空でなく80字以内で、重複しない。本文は3000字以内 |
| 要約と提案の文字列 | 禁止の記法を使っていない。URLが許可リストに当てはまる |

文体も調べるが、ログに残すだけで失敗にしない。レポートと要約は常体、改善提案はIssueとして人が読むので敬体で調べる。
理由は[要件定義の生成と承認](requirements.md)の検査と同じである。

URLの許可リストは、Factory自身のリポジトリのGitHubのURL(`factory_repo`)と、Windmillの公開URL(`windmill_public_url`)の2つである。`http(s)://`のURLに加え、スキームの無い`//host`と`www.host`も検査する。

当てはまるとみなすのは、接頭辞と完全に一致するか、接頭辞の直後が`/`、`?`、`#`のどれかのときである。単純な前方一致では、名前の先頭が同じ別のリポジトリも通してしまう。

レポート本文はURLの許可リストの対象外にする。証跡にある対象リポジトリのURLを正当に引用するためである。

出力が検査を通らないときは、問題点を付け足して1回だけ再試行する。
再試行は新しいセッションで動くので、前回書いたレポートを編集して直し、改善提案は中身を保ったまま出し直すよう、プロンプトで伝える。
再試行がタイムアウトなどの別の理由で失敗したときは、再試行に至った問題も失敗の詳細に残す。再試行の後も通らなければ例外で失敗し、何も保存しない。想定外のファイルが作業用のディレクトリにあれば、警告を残して消す。

### 保存と再開

検査に通ったら、レポートを`audit_reports`に保存する。要約と本文は秘密をマスクしてから保存する。続けて提案を`issue_proposals`に、出どころ`audit`と順番(`position`)を付けて保存する。

この作業項目のレポートが既に保存されていれば、Claudeを再実行しない。前回の再試行が保存した後に失敗した場合である。保存済みの提案の行数がレポートの改善提案の表と一致するかを確かめ、一致しなければ例外にする。一致すれば、提案の登録と承認依頼の作成をやり直す。

失敗は例外を投げるだけで、終端の遷移はしない。フローの失敗時のステップ(`on_error_flow`)が作業項目を失敗にする。

## 提案と承認

提案ごとに、期限の無い承認依頼(`kind = 'issue_proposal'`)を作る。承認依頼の仕組みは[要件定義の生成と承認](requirements.md)に書く。

| 提案の数 | 作業項目の遷移 |
| --- | --- |
| 0件 | `auditing`から`audited` |
| 1件以上 | `auditing`から`awaiting_approval` |

提案を登録してから遷移するまでの間で、人がすべての提案を決定し終えていることがある。そのため`awaiting_approval`へ移した直後、未決の提案を数え直す。未決が無ければ、すぐ`audited`へ進める。

すべての提案が決定すると、`issue_proposal_apply`が作業項目を`awaiting_approval`から`audited`へ進める。

Discordの`audit_completed`の通知は、提案が1件以上あるときだけ送る。通知のリンクは、Consoleの監査レポートのページ(`/console/reports/audit/<work_item_id>`)を指す。通知の失敗はジョブを失敗させない。

### 起票

承認された提案は、`issue_proposal_apply`がFactory自身のリポジトリ(`factory_repo`)にIssueとして作る。Issueの本文には、提案元の監査レポートの期間を入れる。PR修正の提案と違い、返信とスレッドの解決はしない。

決定のオプション`with_factory_label`が真なら、作ったIssueに`factory_config.trigger_label`を付ける。ただし`factory_repo`が`owners`か`repo_allowlist`で許可されていなければ、ラベルを付けずに理由をログに残す。`factory_repo`は常に許可されるので、これが起きるのは作業項目のリポジトリと`factory_repo`が食い違ったときだけである。

## 再実行

監査は`retry_work_item`による再実行の対象外である。失敗した期間は、次の週次監査か**今すぐ監査**で扱う。次の監査の期間は前回のレポートの終わりから始まるので、失敗した期間も含まれる。ただし`max_lookback_days`より前の分は切り詰める。
