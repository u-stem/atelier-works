# 設計書の生成

承認済みの要件定義から設計書を作る処理を定める仕様である。
設計フロー、設計書の保存、設計のClaudeの書き込み範囲を変更する人が読む。

設計工程の生成側と承認の反映は入っている。
既定は無効で、設定で有効にする([設定値](#設定値))。
無効の間は、作業項目が設計中(`designing`)にならず、設計の承認依頼も作られない。

## 設計フローを起動する元

設計フローを起動できる元は5つである。
どの元も、設定の`design_enabled`が真のときだけ起動する。
設定を読む処理は、`design_enabled_since`が日時として読めるときだけ、`true`を`true`として読む([設定値](#設定値))。
既定では、5つとも起動しない。

| 起動元 | 起動する場面 | 無効のときに起動しない理由 |
| --- | --- | --- |
| `retry_work_item` | 設計が有効で未承認の止まった作業項目の再実行 | 設計フローの入力を作るのは、設計が有効なときのブロックの中だけである。偽なら実装か要件定義から再開する |
| `requirements_apply` | 要件定義の承認の反映 | `buildApprovedBranchDeps`が、`design_enabled`が真のときだけ設計フローを起動する依存`startDesign`を渡す。偽なら空で、承認済み(`approved`)へ移して実装へ進む |
| `design_apply` | 設計の却下の反映([承認の反映](#承認の反映)) | 設計の承認待ち(`awaiting_design_approval`)の作業項目からだけ動く。設計の承認依頼は設計フローが作るので、設計フローが動かない間は起動する対象が無い |
| `implement_finish` | 実装が設計の不足を返したときの、設計への戻し([実装フローの内部仕様](implement.md)の「設計の不足」) | 設計の不足を返せるのは、設計書が渡された実行だけである。設計書は設計の承認が照合を通ったときだけ渡るので、設計フローが動かない間は渡らない。判定の入力には`config.design_enabled`をそのまま渡し、偽なら戻さずに人の対応待ちにする |
| `pr_fix_finish` | PRの修正が設計の不足を返したときの、設計への戻し([PRワークフロー](pr-workflow.md)の「設計の不足の差し戻し」) | 設計書は、設計が有効なときだけ、レビュー回のPRの修正に渡る。判定の入力には`config.design_enabled`をそのまま渡し、偽なら戻さずに人の対応待ちにする。判定と起動は`main`の中に置き、人の対応待ちで止める分岐を、起動の手順を作る呼び出しより前に置く |

`requirements_apply`は、承認の分岐を、依存を注入できる関数`applyApprovedBranch`に切り出している。
`startDesign`が空でなければ、作業項目を承認待ち(`awaiting_approval`)から設計中へ移し、設計フローを起動する。
設計中を経由すると`approved`を通らない。
要件定義が承認されたことの根拠は、承認依頼(`approval_requests`)の承認の行だけになる。

設計フローを手で起動しても、起動側がジョブIDを記録しないので、準備ステップがリースを確かめられずに何もせず終わる。
準備ステップは、起動側が記録したジョブIDとの一致を、最大60秒待って確かめる。

### 配線の門

門は、`f/factory/lib/design_gate.ts`の関数`resolveDesignGate`の1か所である。
設定の`design_enabled`が真で、`design_enabled_since`が日時として読めるときだけ、設計工程が開く。
設定を読む処理(`lib/config.ts`)と、Consoleの設定の取得(`console_config.ts`)が、同じ関数を呼ぶ。
門は、環境変数と現在時刻を読まない。
`design_gate.ts`はimportを持たず、保護パスに入れる。
門の条件を書き換えると、人の確認なしに設計工程が開くためである。

`config.ts`は、設定の項目を足すたびに直すファイルで、保護パスに入れると正当な設定の追加がすべて止まる。
そのため保護せず、門の呼び出しの形を、保護パスのテスト2つで固定する。

| テスト | 固定すること |
| --- | --- |
| `tests/scripts/design_entry_origins.test.ts` | `f/factory`のテスト以外の`.ts`とフローの定義を、コメントを落として読み、設計フローを指す識別子を参照するファイルの集合と出現の数を、テスト内の許可表と完全に一致させる。設計中への遷移を書くファイルとその数も同じである。起動元ごとの条件(`requirements_apply`は`config.design_enabled`の条件の内側、`retry_work_item`は設計が有効なときのブロックの内側、`design_apply`は設計中へ移した後、`implement_finish`と`pr_fix_finish`は`config.design_enabled`を渡した判定が戻す結果になる分岐の内側で、設計中へ移した後)も固定する。起動の台帳(`LAUNCH_EDGES`)の辺の起点は、追加の検査である。台帳は保護していないので、固定の根拠にしない |
| `tests/scripts/design_stage_closed.test.ts` | 設定を本番の読み込みに通した結果で、全入口(`requirements_apply`、`design_apply`、`implement_prepare`、`implement_finish`、`pr_fix_apply`、`pr_fix_verify`、`pr_fix_finish`、`retry_work_item`、`auto_retry_stale_image`)の開閉を確かめる。`design_enabled`が真でも`design_enabled_since`が無いか日時として読めなければ閉じていて、日時として読めれば開く。`DESIGN_STAGE_OPENABLE`が本番のコードのどこにも無いこと。`config.ts`が`design_enabled`の要求を1回宣言し、`design_enabled_since`を生の値から1回だけ読み、`design_enabled`と`design_enabled_ignored`を`resolveDesignGate`の結果だけから導き、環境変数を読まないこと。`DEFAULTS.design_enabled`が`false`で、`DEFAULTS.design_enabled_since`が`null`の字面であること。本番のコードに`null`以外の`design_enabled_since`の字面が無いこと。`design_enabled`と`design_enabled_since`を参照するファイルの集合と数が、許可表と一致すること |

2つのテストは、実装フローの保護パスの一覧(`protected_paths.ts`)に入っている。
門を緩める変更が、テストの書き換えを必ず伴うようにするためである。
文字列の照合なので、識別子を連結や別名で組み立てる起動は追えない。
そのため、設定を通した戻り値の検査と組み合わせる。

## 設定値

設計工程は`f/factory/factory_config`の次の値を読む。

| キー | 既定値 | 意味 |
| --- | --- | --- |
| `design_enabled` | `false` | 設計工程を有効にするか。`true`を書いても、`design_enabled_since`が日時として読めるまでは`false`として読む |
| `design_enabled_since` | 無し | 有効にする意思の表明と、有効にした時刻の記録。秒まで書いたタイムゾーン付きの日時 |
| `max_design_attempts` | `3` | 現在の要件定義の試行で、設計の却下と、実装とPRの修正から設計への戻しを合わせて受けられる回数の上限。1以上10以下の整数 |

`design_enabled_since`は、他の`*_since`と違い、作業を除く境の時刻ではない。
未来の日時でも、書いた時点で開く。
日時として読めない値は、例外にせず、無いものとして扱う。例は、日付だけの文字列、数値、`null`である。

`design_enabled`が`true`でも、`design_enabled_since`が日時として読めないとき、設定を読む処理は`false`として読む。
このとき警告のログと通知`design_enabled_ignored`(要対応)を残す。
例外にすると、設定を読むすべてのscriptが止まる。
自己更新と、止まったことを知らせる通知も動かなくなり、知らせる手段が無くなるためである。
自己更新が設定を読むたびに、通知を1件にまとめて残す。
`design_enabled_since`を書くか、`design_enabled`を`false`に戻すと、自己更新が通知を解決する。
解決は1回に3件までで、残りは次の回に解決する。
通知の処理は、全体を5秒の上限で包んで更新の前に行う。失敗しても時間切れでも、更新と検知は止めない。

Consoleの設定タブは、`console_config`の返り値の`design_stage`で、効いている値(`enabled`)と、書かれた値が無視されているか(`ignored`)を出す。
門の関数を、設定を読む処理と同じ入力で呼んで決める。
ただし、`design_enabled`か`design_enabled_since`が参照を含むときは、設定を読む処理が解決した値を、設定タブは知らない。
そのときは効いている値を断定せず、`indeterminate`を立てて、設定タブは「判定できない」と出す。
`design_enabled`の参照が、文字列やオブジェクトなど真偽値でない値に解決されると、設定を読む処理は例外で止まる。
`design_enabled_since`の参照が、日時として読めない値に解決されても、例外にならない。
その場合は、設計工程が閉じたまま、`design_enabled_ignored`の通知が出る。
運用の手順は[運用](../operations.md)の「設計工程を有効にする」にある。

`design_enabled`が真偽値でないときと、`max_design_attempts`が範囲外のときは、例外にする。
`max_design_attempts`の範囲は、`design_enabled`が`false`でも検査する。
`max_design_attempts`を読むのは、設計の却下の反映と、実装とPRの修正の設計の不足の判定である([承認の反映](#承認の反映)の「却下の数え方」)。

## 設計フローの流れ

設計フロー(`f/factory/design`)は、pipelineフローと同じ形の3つのステップで動く。
入力は`work_item_id`、`design_attempt`、`feedback`である。
`design_attempt`は1から数える。
0は設計していない作業項目の既定値にだけ使う。
`design_generate`にフローの再試行(`retry`)は付けない。
再試行はステップ全体を呼び直すので、要件定義へ戻す遷移と、起動したpipelineのジョブIDの記録が、再試行と競合するためである。
どのステップも、設計フローのリースを持つときだけ作業項目を書き換える。
リースは[作業項目の状態とリース](work-items.md)に書く。

| ステップ | 処理 |
| --- | --- |
| `design_prepare` | リースを確かめ、現在のattemptに一致する承認済みの要件定義があるかと、オーナーの数値IDを確かめる。Issueが閉じていれば取り消す。設計の試行を保存し、設計用のworktreeを作り直す |
| `design_generate` | 日次予算を確かめ、headless Claudeに設計書と図を書かせ、検査して下書きとして保存する |
| `design_request_approval` | 設計の承認依頼を記録して通知し、作業項目を設計の承認待ち(`awaiting_design_approval`)へ移す |

承認済みの要件定義が無いとき、オーナーの照合に通らないとき、日次予算を超えているときは、作業項目を人の対応待ち(`needs_human`)にしてDiscordに通知する。
後続のステップは飛ばす。

## 設計書の置き場所

設計書と図は、要件定義書と同じく、DBではなくworkerのファイルに置く。
試行ごとのディレクトリの形式は次のとおり。

```text
/var/lib/factory/requirements/<owner>/<repo>/issue-<N>/wi-<work_item_id>/design/req-<attempt>/attempt-<design_attempt>/
```

パスに要件定義のattemptと設計の試行の両方を入れる。
要件定義のattemptを進める更新(`setAttemptIfLeaseHolder`)は、同じ文で設計の試行を0に戻す。
パスに要件定義のattemptが無いと、戻った後の設計が、承認済みの設計の図を上書きしうるためである。

ディレクトリには、設計書の`design.md`と、図の`<name>.drawio`だけを置く。
Console用workerのマウントと、作業項目の掃除(`wi-<work_item_id>`ごとの削除)は、要件定義と共通である。

DBの設計の下書き(`design_drafts`)は、本文(`markdown`)、概要、図の参照、未確定事項、ファイルの置き場所(`doc_dir`)、読んだ既定ブランチの先頭(`head_sha`)を持つ。
図のXMLはDBに保存しない。

| 制約 | 内容 |
| --- | --- |
| 複合外部キー | `(requirement_draft_id, work_item_id)`が`requirement_drafts`の`(id, work_item_id)`を指す。別の作業項目の要件定義を指せない |
| 試行 | `design_attempt`は1以上である |
| 一意性 | 一意制約は無い。同じ組を複数保存でき、最新の行を採る |
| 削除 | 作業項目の削除は、`requirement_drafts`を経由して`design_drafts`に届く |

`requirement_drafts`の`UNIQUE (id, work_item_id)`は、複合外部キーのために足している。
`work_items`への直接の外部キーは作らない。
作ると`work_items`に暗黙のロックがかかり、`cleanup_db`の削除とロックを取る順が逆になるためである。

## Claudeの実行

`design_generate`は、試行ごとのディレクトリを空にしてからテンプレートを`design.md`として複製し、そこをClaudeのカレントディレクトリにする。
空にするのは、再試行した試行に前の試行の書きかけを見せないためである。

| 項目 | 値 |
| --- | --- |
| カレントディレクトリ | 試行ごとのディレクトリ |
| ツール | `Read`、`Glob`、`Grep`、`Write`、`Edit` |
| 書き込みの範囲 | `--restricted`で、作業ディレクトリと`--add-dir`の下に限る |
| 対象リポジトリ | 設計用のworktreeを`--add-dir`で読み取り専用として渡す |
| 要件定義の本文 | DBの`requirement_drafts.markdown`を、`dataFence`に入れてプロンプトに渡す |
| 要件定義の図 | 一時ディレクトリに複製した図だけを`--add-dir`で渡す |
| スキル | `factory-design`と`drawio-diagram` |
| 構造化出力 | `{outcome, summary, open_questions, gap_report}` |
| モデル | `heavy_model` |
| 上限 | `max_turns`、`max_budget_usd_per_run`、`claude_timeout_sec` |

`outcome`は、設計書を書けたときの`designed`と、要件の不足を返すときの`requirements_gap`のどちらかである。
`requirements_gap`では`gap_report`が空であってはならず、`designed`では`gap_report`が空でなければならない。

実行の後、`design.md`と`*.drawio`以外の項目は、警告を残して消す。
各図は`validateDrawioXml`で検査し、通らなければステップは例外で失敗する。
失敗は`on_error_flow`が扱う。

### 出力の守り

設計のClaudeの出力のうちDBに保存する文字列は、信頼できない入力を読んだClaudeの出力として扱う。
`summary`は1000字、`open_questions`は30件までで各要素は1000字までに収める。
`open_questions`の空の要素は捨てる。
処理の順は、制御文字と書式文字の除去、`maskSecrets`、切り詰めである。
この整形は`f/factory/lib/model_text.ts`にあり、設計のClaudeの出力の保存と、実装に渡す設計書、再実行が渡す差し戻しの理由が共有する。
除くのは、C0制御文字、DEL、C1制御文字(U+0080〜U+009F)、書式文字(Unicodeの分類`Cf`)である。
書式文字にはゼロ幅スペース、双方向の制御、バイトオーダーマークに加えて、絵文字をつなぐゼロ幅接合子(ZWJ)も入る。
そのため、ZWJでつないだ絵文字の列は、つながりが崩れる。
制御文字と書式文字を先に除くと、秘密情報の途中に挟まれた見えない文字でマスクをすり抜けられない。
結合文字(`Mn`、`Me`)、既定で無視されるコードポイント(`Default_Ignorable_Code_Point`)、ハングルのフィラー、U+2800は、保存する文字列からは除かない。
日本語の濁点の結合と異体字列に使うためである。
代わりに、それらを除いた影の文字列でマスクを判定する。
影に秘密情報があれば、影をマスクした結果を保存するので、それらの文字は落ちる。
影に秘密情報が無ければ、元の文字列をマスクして保存するので、濁点の結合と異体字列は崩れない。
見える区切り文字(空白、ハイフン、記号)を秘密情報の途中に挟む難読化は、マスクでは止められない。
マスクを切り詰めより先に行うと、切った末尾に秘密情報の一部が残らない。
改行とタブは本文に使うので残す。
`gap_report`は[要件の不足](#要件の不足)の上限を使う。

### 試行ディレクトリの再利用の防止

試行ディレクトリを空にする前、保存済みの設計の下書きの置き場所と重ならないか確かめる(`hasDesignDraftForDocDir`)。
持つ下書きがあれば、ディレクトリを触らず、作業項目を人の対応待ちにする。
空にして書き直すと、その下書きの図が消えるためである。

### 書き込み境界

設計のClaudeは、承認済みの要件定義を書き換えられない。
元の要件定義のディレクトリは、`--add-dir`の対象と、カレントディレクトリのどちらにも使わない。
Claudeが読む図は、行に宣言された図で、ファイル名の規則(`[a-z0-9-]{1,64}.drawio`)に合う通常のファイルだけを複製する。
リンクの図は、警告を残して複製に入れない。
複製を作る前に、`doc_dir`が`/var/lib/factory/requirements/`の下にあることを、Consoleの読み戻しと同じ方法で確かめる。

元のディレクトリの内容のハッシュは、承認の前に保存した基準値(`requirement_drafts.doc_hash`)と比べる。
基準値の取り方、図の複製との関係、照合の結果は[要件定義の生成と承認](requirements.md)の「基準値」に書く。
照合は次の位置で行い、合わなければ保存せずに作業項目を人の対応待ちにする。

| 位置 | 合わないときの理由 |
| --- | --- |
| Claudeの起動前、図の複製の前 | 設計を始める前に書き換わっていた |
| 図の複製の中。複製が読んだバイト列のハッシュを比べる。図が無く複製しないときは行わない | 設計を始める前に書き換わっていた |
| 図の複製の後 | 設計を始める前に書き換わっていた |
| Claudeの実行の後。実行が失敗したときと要件の不足を返したときも、結果を採る前に行う | 設計の実行中に書き換わった |

どの位置でも、基準値があるのにディレクトリが無ければ、書き換えとは別の理由(ディレクトリが無い)で止める。

基準値が無い下書きは、警告を1回ログに残す。
ルートがシンボリックリンクなら、基準値の有無に関わらず、書き換えとして止める。
実行の前の内容として、図の複製が読んだバイト列のハッシュ(複製しなかったときは複製の後の内容のハッシュ)を取り、実行の後のハッシュと比べるだけにする。

元のディレクトリは、作業ディレクトリと`--add-dir`のどちらの外にもある。
`--restricted`が、その外への書き込みを拒むかは確かめていない。
そのため、元のディレクトリが書き換わりうるかも確かめられていない。
ハッシュの比較は、書き換えを防ぐものではなく、検出して止める補強である。
複製とworktreeへの書き込みは使い捨てなので、検出の対象にしない。
セキュリティ上の限界は[セキュリティ](../security.md)の「設計書の生成の安全策」に書く。

## 検査

テンプレートは`.claude/skills/factory-design/template.md`にある。
生成した文書は、`f/factory/lib/design_doc.ts`の`validateDesignDoc`が機械的に検査する。
章立てなどの決まりは`f/factory/lib/design_template.ts`の定数に持つ。

| 検査 | 内容 |
| --- | --- |
| 章立て | `##`の見出しが、順序も含めて決まった9章と一致する |
| 要件のID | 要件との対応表のIDが`DS-001`の形である |
| 禁止の記法、引用、長さ、図、文章 | 要件定義書と同じ規則である([要件定義の生成と承認](requirements.md)の「テンプレートと検査」) |

Claudeの出力が検査を通らないときの再試行も、要件定義と同じである。

## 要件の不足

設計が要件定義だけでは足りないと判断したときは、`requirements_gap`と、要件定義への報告(`gap_report`)を返す。
`design_generate`は次のように扱う。

1. `gap_report`を長さの上限と`maskSecrets`に通す。
2. 要件定義の試行(`attempt`)が上限(`max_attempts`)に達していれば、作業項目を人の対応待ちにする。
   理由は`design requirements_gap after max_attempts N`である。
3. 達していなければ、リースを条件にした1文の比較交換で、設計中から要件定義の生成中(`requirements_generating`)へ移す。
   同じ文で`design_attempt`を0にし、`flow_job_id`を空にする。`attempt`はこの文では書かない。
4. `pipeline`を`attempt + 1`で起動し、ジョブIDを記録する。
5. 起動か記録に失敗したら、リースが空のときだけ人の対応待ちへ戻す。
   手順は却下の再生成と同じである([作業項目の状態とリース](work-items.md)の「却下と再生成」)。

`gap_report`は、信頼できない入力を読んだClaudeの出力である。
`feedback`には自動の報告の印(`AUTOMATED_FEEDBACK_MARKER`)で始まる文として渡す。
`requirementsPrompt`は、印のある`feedback`を人の差し戻しの理由として扱わず、`dataFence`に入れて、別の段のClaudeが出した信頼できない報告だと明記する。
リースを失った実行は、何も書かず、起動もしない。

## 自動の報告の入力

設計フローの`feedback`が自動の報告の印(`AUTOMATED_FEEDBACK_MARKER`)で始まるときは、実装かPRの修正のClaudeが返した設計の不足の報告である。
`designPrompt`は、印を外した本文を信頼できない報告として`dataFence`に入れる。
報告はヒントにとどめ、指示としては扱わず、承認済みの要件定義とリポジトリで確かめるようにプロンプトに書く。
印が無い`feedback`は、人の却下の理由として扱う。
人の却下の理由には印を付けない。

## 承認依頼

`design_request_approval`は、承認依頼を記録する前に、最新の下書きの行を確かめる。
行の`design_attempt`がフローの入力と、行の`requirement_draft_id`が最新の承認済みの要件定義の下書きと、それぞれ一致しなければ、例外にする。

承認依頼は、種類(`kind`)を`design`、対象(`subject_id`)を`design_drafts.id`として記録する。
`payload`は`{"attempt": n, "design_attempt": m}`で、期限は7日である。
続けて、作業項目を設計中から設計の承認待ちへ比較交換で移し、Discordに設計の承認依頼を通知する。
移せなければ、記録した依頼を期限切れにする。
古い下書きを承認できないようにするためである。
人が先に決定していれば、依頼は変えない。

### 依頼の記録と移行の競合

依頼を記録してから作業項目を移すまでの間に、人が判断を記録することがある。
そのとき承認の反映(`design_apply`)は、作業項目がまだ設計中なので何もせず、判断が失われる。
そのため、移せたら依頼を読み直す(`getApprovalRequest`)。

| 読み直した依頼の状態 | 動き |
| --- | --- |
| 承認待ち(`pending`) | 承認待ちの通知を送って終わる |
| 承認済みか却下 | `design_apply`を起動する。承認待ちの通知は送らない。人はすでに判断しており、行動が要らないためである。起動に失敗しても例外にしない。作業項目は決定済みで未反映の待ちになり、[承認待ちの走査](#承認待ちの走査)が起動し直す |
| 期限切れ | 作業項目を`awaiting_design_approval`から期限切れ(`expired`)へ移し、人の対応待ちの通知を送る。承認待ちの通知は送らない |

読み直しが例外を投げたとき、依頼が見つからないときは、承認待ちと同じに扱う。取りこぼした判断は走査が拾う。
`design_apply`を起動した後は、状態やworktreeを書く処理を呼ばない。反映と競合するためである。

## 承認の照合

設計の承認が作業項目の現在の状態に一致するかは、`f/factory/lib/approval_gate.ts`が判定する。
実装の関門、再実行、自動再開、自己更新の起動の要否が、同じ判定を使う。
判定の実体を日常的に直される共有モジュールから離して小さくしたのは、CI回の自動修正が書き換えられない拒否の一覧に入れるためである。
拒否の一覧は[CIの失敗を直す部品の内部仕様](ci-fix.md)に書く。
このモジュールはDBを読まない。判定に要る値は呼び出し側が渡す。

### 承認の読み方

`latestDesignApproval`は、作業項目の種類が`design`の承認依頼のうち、依頼の新しい順(`requested_at`、`id`の降順)で最新の1件を返す。
最新の1件を先に決めてから、依頼の`subject_id`で設計の下書きを結ぶ。
下書きは、同じ作業項目の行だけを結ぶ。最新の下書きは読まない。
後から保存された別の下書きが、承認済みの下書きに取って代わらないようにするためである。
下書きが引けない最新の依頼は、読み飛ばさずに返す。このとき下書きの項目(`draft`)は空にする。
読み飛ばすと、書き換えられた最新の依頼の代わりに、古い承認が効いてしまうためである。
依頼を作った時点の写し(`payload`)から、`attempt`と`design_attempt`を整数として読む。無い値、整数でない値、負の値は空にする。

### 判定

`designApprovalVerdict`は、承認と作業項目の現在の値を上から順に照合し、最初に当たった結果を返す。
現在の値は、`work_items.attempt`、`work_items.design_attempt`、現在の`attempt`で承認済みの最新の要件定義の承認の下書きIDである。

| 順 | 条件 | 判定 |
| --- | --- | --- |
| 1 | 承認が無い、または承認済みでない(承認待ち、却下、期限切れ) | 承認されていない(`not_approved`) |
| 2 | 依頼が指す下書きが無い、または別の作業項目のものである | 記録の食い違い(`inconsistent`) |
| 3 | `payload`の`attempt`か`design_attempt`が空、または`payload`の`design_attempt`が下書きと違う | 記録の食い違い |
| 4 | 現在の`design_attempt`が1未満、または下書きの`design_attempt`と違う | 承認されていない |
| 5 | 下書きが元にした要件定義の下書きIDか、`payload`の`attempt`が、現在と違う | 要件定義と食い違う(`stale_requirements`) |
| 6 | それ以外 | 通る(`ok`) |

行2と行3は、承認済みの行に対してだけ働く。
承認済みの行の写しが欠けているか、下書きとずれているなら、行が書き換えられたか、別の依頼を指している。
承認として扱わず、古い承認にも落とさない。
行4は、要件定義へ戻って`design_attempt`が0に戻った後や、却下の後で次の試行が始まった後に、古い承認を効かせない。
行5は、要件定義を作り直して`design_attempt`がたまたま同じ値になっても、古い要件定義に基づく承認を効かせない。

`isDesignApprovedForAttempt`は、判定が`ok`のときだけ真を返す。

### 実装へ進んでよいか

`isReadyForImplement`は、次の2つがそろったときだけ真を返す。

- 要件定義が現在の`attempt`で承認済みである。
- 設計が無効であるか、設計の承認の判定が`ok`である。

設計が無効のときは、設計の承認を読まない。
再実行、自動再開、自己更新の起動の要否が、実装フローで再開してよいかをこの関数で決める。
自己更新の起動の要否は、自動再開の候補が実際に再開できるかを数えるために、同じ判定を使う。

### 実装の関門

実装の準備のステップ(`implement_prepare`)は、`designGate`で設計の承認を確かめる。
位置は、リースを取り、要件定義の承認と基準値を確かめた後で、ブランチ、PR、worktreeに触れる前である。
基準値の照合を先に行うのは、要件定義の改ざんと設計の承認の欠落が重なったとき、再実行の行き先が要件定義の生成になるのは改ざんだけだからである。

| 結果 | 条件 | 実装の準備 |
| --- | --- | --- |
| 飛ばす(`skip`) | 設計が無効 | 承認の行があっても読まない。設計書を渡さない |
| 止める(`stop`) | 判定が`ok`でない、または読み直した下書きが照合した値と食い違う | 人の対応待ちにする |
| 通す(`pass`) | 判定が`ok` | 整えた設計書を実装の入力に載せる |

承認の照合の後に、承認依頼が指す下書きを読み直す(`getDesignDraft`)。
下書きを2回読むのは、読み間違いと削除に備えるためである。
読み直した下書きが無いとき、別の作業項目のものであるとき、`design_attempt`か要件定義の下書きIDが1回目の値と違うときは、記録の食い違いとして止める。

止めるときの理由は、人の対応待ちの注記になる。

| 判定 | 理由 |
| --- | --- |
| 承認されていない | `no approved design for design attempt N`(Nは`design_attempt`) |
| 要件定義と食い違う | `approved design does not match the approved requirements` |
| 記録の食い違い | `design approval record is inconsistent` |

関門は、止めるときに要件定義や設計へ自動で戻さない。
正常な経路(承認の反映、再実行、自動再開)は、設計が承認されていない作業項目を実装中にしない。
関門に届くのは、次のいずれかの異常である。

- 設計の設定を後から有効にした。
- 承認の行が書き換わった。
- 処理が競合した。

原因が分からないまま自動で戻すと、承認済みの要件定義を捨てるか、設計を作り直し続ける。
人が確かめて、`retry_work_item`で再実行する。
設計が有効で未承認なら、再実行は設計から始まる。
実装に渡す設計書の整え方は[実装フロー](implement.md)の「設計書の入力」に書く。

## 承認の反映

人が設計の承認依頼を承認または却下すると、`approval_decide`が判断を記録し、承認の反映のscript(`f/factory/steps/design_apply`)を起動する。
入力は承認依頼のIDである。`design_apply`は、フローから独立したジョブとして動く。
承認待ちの走査と設計の承認依頼のステップも、反映されなかった判断に同じ起動をする。

### 状態遷移

`design_apply`は、`flow_job_id`のリースを取らない。
反映は比較交換で行い、作業項目の状態(`awaiting_design_approval`)と、待ちの間に残る`flow_job_id`が調停になる。
設計の承認依頼のステップは、移行で`flow_job_id`を空にしないので、待ちの間は前の設計フローのジョブIDが残る。
読み直した後に別の経路が作業項目を動かし、同じ状態へ戻していても、古い判断では動かない。
副作用はすべて比較交換より後に行う。比較交換が失敗したら何もしない。

次の表を、上から順に評価する。

| 条件 | 結果 |
| --- | --- |
| 承認依頼か作業項目が無い、依頼の種類が`design`でない | 例外にする。失敗を`job_failures`に記録して通知する |
| 作業項目が設計の承認待ちでない(二重実行、期限切れの後、再実行の後、取り消し、終端) | 何もしない |
| 作業項目に`issue_number`が無い | 例外にする |
| 依頼が承認でも却下でもない(承認待ち、期限切れ) | 何もしない |
| 最新の設計の依頼が、この依頼と違う(古い依頼) | 何もしない |
| 最新の依頼と同じで、`payload`の`design_attempt`が無い、整数でない、作業項目と違う | 人の対応待ち(`needs_human`)にして通知する。理由は`design approval record is inconsistent`である |
| 承認で、要件定義が現在の`attempt`で承認済みでない | 人の対応待ちにして通知する。理由は`design requires approved requirements for attempt N` |
| 承認で、[承認の照合](#承認の照合)の判定が`ok`でない | 人の対応待ちにして通知する。理由は[実装の関門](#実装の関門)の表と同じである |
| 承認で、判定が`ok`で、比較交換が失敗する | 何もしない |
| 承認で、判定が`ok`で、比較交換が成功する | 承認済み(`approved`)へ移す。実装が有効(`implement_enabled`)なら実装フローを起動し、実装中へ移す |
| 却下で、Issueが取り込み時点から変わっている | 要件定義の生成中(`requirements_generating`)へ戻す([要件定義へ戻す経路](#要件定義へ戻す経路)) |
| 却下で、Issueは変わっていない(または確かめられなかった)。反映できた却下の数に1を足すと`max_design_attempts`以上 | 人の対応待ちにして通知する。理由は`design rejected after max_design_attempts N`である |
| 却下で、上の2つに当たらず、設計工程が無効(`design_enabled`が偽) | 人の対応待ちにして通知する。理由は`design stage is closed, so the rejected design was not regenerated`である |
| 却下で、それ以外 | 設計中(`designing`)へ移し、設計フローを起動して設計を作り直す |

承認で`approved`を経由するのは、要件定義の承認の反映と同じである。
`implement_enabled`が偽なら`approved`で止まり、[`retry_work_item`](work-items.md)が、設計の承認が`ok`の承認済みを実装フローで再開する。
承認の受理と却下の受理は、通知もIssueへのコメントもしない。判断した本人に知らせる情報で、行動が要らないためである。
GitHubには成果物だけを載せる。

照合が通らない異常は、自動で戻さず人の対応待ちで止める。
自動で戻すと、承認済みの要件定義を捨てるか、設計を作り直し続けるためである。
依頼のIDが違う場合と、IDが同じで`payload`だけが違う場合は、扱いを分ける。
前者は古い依頼なので、今の依頼の判断を待つ作業項目を動かさない。
後者は承認の行が書き換えられたか壊れた状態で、誰にも知らせず捨てると、判断が失われたまま残る。

設計工程が無効なときに設計を作り直さないのは、無効の設定を`design_apply`が迂回しないためである。
承認の反映は、この確認をしない。承認は実装へ進むだけで、設計フローを起動しない。

設計の再生成では、遷移の注記を固定文(`design rejected; regenerating`)にする。
人の理由には長さの上限が無い。
そのため、Consoleの履歴と通知に流れる遷移の記録には入れない。
理由は承認依頼に残り、設計フローの`feedback`へ整形と切り詰めをせずに渡す。
Issueが変わった却下の注記も固定文(`design rejected; the issue changed since intake`)である。

読み取りの順序は次のとおりである。

1. 依頼と作業項目を読む。
2. 却下のときだけ、現在のIssueを読む。遅い読み取りを状態の読み取りの前に置き、状態を読んでから比較交換までの間を縮める。
3. 作業項目と最新の設計の承認を読み直す。承認なら最新の要件定義の承認を、却下なら反映できた却下の数を読む。
4. 比較交換で状態を動かす。

### 却下の数え方

上限`max_design_attempts`は、現在の要件定義の試行で反映できた却下の数と、実装から設計へ戻した数と、PRの修正から設計へ戻した数の合計で判定する。
人の却下、実装からの戻し、PRの修正からの戻しが、同じ上限を分け合う。
どれも設計を作り直す回数であり、別々に数えると設計の作り直しが上限の倍以上まで続くためである。
`design_attempt`は設計を始めた数(起動の番号)で、失敗や期限切れの後の再実行でも進む。
そのため、却下の数と合わず、判定には使わない。

数えるのは、作業項目の遷移の記録(`work_item_events`)のうち、次の4つである。
遷移元の条件は、分岐ごとに持つ。

- 遷移元が`awaiting_design_approval`、遷移先が`designing`で、注記が設計の再生成の固定文と等しい
- 遷移元が`awaiting_design_approval`、遷移先が`needs_human`で、注記が上限の理由の接頭辞で始まる
- 遷移元が`implementing`、遷移先が`designing`。注記では照合しない。この遷移は、リースを持つ実装だけが、設計の試行を進める1つの文でしか作れないためである
- 遷移元が`pr_open`、遷移先が`designing`で、注記がPRの修正の戻しの接頭辞(`PR_FIX_DESIGN_GAP_NOTE_PREFIX`)で始まる。書く側(`pr_fix_finish`)と数える側(`countAppliedDesignRejections`)が同じ定数を使う

承認依頼の却下の行を数えると、反映されずに終わった却下まで数えてしまう。
遷移の記録は、比較交換が成功したときだけ残るので、反映できた却下と戻しだけを数えられる。
数える関数は`countAppliedDesignRejections`である。

範囲は現在の要件定義の試行に絞る。
遷移の記録に試行の番号は無いので、作業項目の「要件定義の生成中への遷移(遷移元と遷移先が違うもの)」の最新の記録より後の記録だけを数える。
取り込み内容の更新のように、同じ状態どうしの記録は範囲を区切らない。
範囲の前後は、時刻でなく記録の`id`の大小で決める。同じ時刻の記録の順序を`id`が決めるためである。

判定は「数に1を足した値が、`max_design_attempts`以上」である。
実装とPRの修正の設計の不足の判定(`decideDesignGapAction`)も、同じ比較(`isDesignRejectionExhausted`)を使う。
今回の却下または戻しは、比較交換が成功するまで記録に無いので、1を足す。
`max_design_attempts`が3なら、1回目と2回目の却下は設計を作り直し、3回目の却下で人の対応待ちになる。
実装からの戻しとPRの修正からの戻しも同じ数に入る。却下1回と戻し1回の後の3回目は、却下でも戻しでも上限になる。
同じ依頼を処理し直しても、比較交換の前は記録が増えないので、判定は変わらない。

失敗や期限切れの後の再実行は記録を増やさないので、数えない。再実行が書く`needs_human`から`designing`への遷移は、どの分岐にも当たらない。
上限で人の対応待ちになった後の再実行は設計を始め、次の却下か戻しで数が`max_design_attempts`(上限の記録を含む)になり、また人の対応待ちになる。
再実行ごとに、設計を1回試せる。
実装が設計の不足を返して上限で止まった作業項目の再実行は、その報告を設計に渡す([作業項目の状態とリース](work-items.md)の「設計フローへ渡す理由」)。
PRの修正からの戻しは、上限か設計工程の無効で止まったとき、親がPR作成済みのまま残る。
親は再実行の対象でないので、再実行で設計を作り直せない。
次の操作は、Issueにトリガーのラベルを付け直して新しいサイクルを始めるか、PRを人が直すことである。
設計の起動に失敗して親が人の対応待ちになったときは、再実行が報告を設計に渡す。
要件定義の生成中へ戻ると、範囲の起点の記録が新しくなり、数え直しになる。

### Issueの確認

承認の前の確認は、`approval_decide`が行う。確認の仕組みは[要件定義の生成と承認](requirements.md)の「承認の前のIssueの確認」に書く。
却下の反映での確認は、`design_apply`が行う。

- 設計の承認でIssueが変わっていたら、承認を記録せずに断る。案内は、現在のIssueを使うには却下する、である。却下による作り直しは、要件定義へ戻って現在のIssueを取り込み直す。
- 設計の承認で比べられなかったときも断る。承認者が見た内容と、実装に渡る内容を一致させるためである。案内は、Issueが移されたか消されたなら却下する、である。ただし、Issueが読めないと設計の却下も要件定義へ戻れず、設計の再生成が上限まで繰り返される。案内にはそのことを書く。
- 設計の却下では、`design_apply`が現在のIssueを読んで取り込み時点と比べる。読めなかったときは、変わっていないものとして進める。却下は人の意思で、読めないことを理由に止めても、`approval_decide`の再実行は同じ読めない状態に戻るだけで、出口にならないためである。進めた先の設計の再生成は、上限が数える。Issueが実は変わっていたときは、再生成した設計の承認の前の確認が断り、人は却下して要件定義へ戻せる。

設計の承認では、`approval_decide`の確認から記録までの間の書き換えは防げない。
要件定義の承認と同じ前提で、実装を終えたときの比較(PR本文の注記)が拾う。
`design_apply`の承認の分岐は、Issueを読み直さない。

### 要件定義へ戻す経路

Issueが変わった却下は、要件定義の却下の作り直しと同じ手順で、要件定義の生成へ戻す。

1. 作業項目を`awaiting_design_approval`から`requirements_generating`へ、比較交換で移す。同じ文で`design_attempt`を0にし、`flow_job_id`を空にする。待ちの間の`flow_job_id`を条件にする。
2. 取り込み内容を現在のIssueで更新する。承認者へ、取り込み内容を更新した通知(`intake_refreshed`)が出る。更新に失敗しても作り直しは止めない。
3. `pipeline`フローを`attempt + 1`で起動する。`feedback`は人の却下の理由で、空なら含めない。
4. ジョブIDを、空のときだけ記録する。

起動か記録に失敗したら、作業項目を`requirements_generating`から人の対応待ちへ戻す。理由は`requirements regeneration could not be started`である。
戻せたときは人の対応待ちを通知し、例外を投げる。戻せなかったとき(別の実行がリースを持つ)は通知しない。
戻した後の再実行は、要件定義の生成へ戻り、人の却下の理由を渡す([作業項目の状態とリース](work-items.md)の「再実行」)。

この経路には`max_attempts`の判定を足さない。
起きるのは、人がIssueを書き換え、続けて設計を却下したときだけで、モデルのループではなく人の操作が数を決めるためである。
上限に達していても人の対応待ちで止めず、要件定義へ戻して`design_attempt`を0に戻すほうが出口になる。

この経路を通ると`attempt`が1進むので、`attempt`が`max_attempts`以上になりうる。
そのとき、新しい要件定義の最初の却下と、設計の最初の要件の不足は、すぐ人の対応待ちになる。
人がIssueを書き換えた後の操作で、人の対応待ちの通知を受けて動ける。
人の対応待ちからの再実行(`retry_work_item`)で、要件定義の作り直しに進める。

設計のworktreeは、反映では消さない。設計フローの後始末が、リースを持つときだけ消す。
要件定義のworktreeは、要件定義の承認で消えている。

## 承認待ちの走査

`poll_issues`は、毎回の実行で作業項目の照合(reconcile)の後に、承認待ちの走査(`lib/approval_sweep.ts`の`sweepApprovals`)を呼ぶ。
走査は、承認待ちの作業項目を最新の承認依頼と照合し、期限切れを片付け、決定済みなのに反映されなかった依頼の処理先を起動し直す。
`poll_issues`は5分ごとに動く。

種類ごとの期限切れの行き先は、`approval_sweep.ts`の表(`expiryPlanFor`)が持つ。

| 種類 | 作業項目の移る元 | 期限切れの注記 |
| --- | --- | --- |
| 要件定義 | 承認待ち(`awaiting_approval`) | `approval timed out` |
| 設計 | 設計の承認待ち | `design approval timed out` |
| Issue化の提案 | 期限を持たない | 走査の対象外 |

表を`approval_support.ts`に置かないのは、このファイルをConsole用workerの`approval_decide`が読み込むためである。
設計の定数への依存を足すと、Console用workerが読むコードの範囲が広がる。

### 作業項目の側の走査

承認待ちの作業項目ごとに、最新の依頼を`latestApprovalRequest`で読む。
この問い合わせは、要件定義や設計の下書きと結合しない。
下書きと結合すると、結合できない最新の依頼を読み飛ばし、古い承認を最新として返すためである。

| 最新の依頼 | 動き |
| --- | --- |
| 無い | 何もしない |
| 承認待ちで期限を過ぎている。設計で、`payload`の`design_attempt`が無い、整数でない、作業項目と違う | 作業項目を人の対応待ちへ移し(理由は設計の承認の記録の食い違い)、依頼を期限切れにしてから通知する |
| 承認待ちで期限を過ぎている | 作業項目を期限切れへ移し、移せたときだけ、依頼を期限切れにしてから人の対応待ちを通知する |
| 期限切れで、作業項目が承認待ちのまま残っている | 作業項目を期限切れへ移し、移せたときだけ通知する |
| 承認済みか却下で、決定から5分以上、直前の起動し直しから15分以上たち、作業項目が承認待ちのまま | 処理先(`requirements_apply`か`design_apply`)を起動し直す。状態は書かない |
| それ以外(期限前の承認待ち、決定から5分未満、直前の起動し直しから15分未満) | 何もしない |

作業項目を動かす比較交換(`updateStatusIfLatestApproval`)は、1つの文で更新と遷移の記録をする。
更新するのは、作業項目の状態、最新の依頼のID、その依頼の状態がすべて一致するときだけである。
読み取りと更新の間に新しい依頼ができても、古い依頼を根拠に作業項目を動かさないためである。

作業項目を先に動かし、次に依頼を期限切れにして、最後に通知する。
依頼の期限切れの前に落ちても、依頼は承認待ちのまま残り、依頼の側の走査が片付ける。
通知の前に依頼を期限切れとするのは、通知を待つ間に依頼が承認待ちのまま残り、人が判断を記録できてしまうのを避けるためである。
依頼を期限切れにできなかったときも、通知は送る。
通知が失敗しても、依頼はすでに期限切れである。
順序を逆にすると、依頼だけが期限切れになり、作業項目が承認待ちのまま残る。

処理先を起動し直すのは、判断の記録の後に処理先が反映の前に失敗した場合と、設計の承認依頼のステップが`design_apply`の起動に失敗した場合の出口である。
起動し直した処理先は、比較交換で冪等に動く。
決定から5分の猶予を置くのは、判断の記録の直後の通常の起動と、二重に走らせないためである。二重に走っても比較交換が調停する。
直前の起動し直しの記録からも15分の猶予を置く。
既定のworkerが長いジョブで詰まっていると、起動し直したジョブが動き出す前に、回数だけが上限に達して作業項目が誤って人の対応待ちになるためである。
3回目の起動し直しの後も、15分たつまでは人の対応待ちにしない。

起動し直しの回数には上限がある。

| 上限 | 値 | 目的 |
| --- | --- | --- |
| 1回の走査 | 5件まで | 走査の実行時間を一定に保つ |
| 1つの依頼 | 3回まで | 恒久的に失敗する依頼を、走査のたびに起動し続けない |
| 同じ依頼の連続する起動し直し | 15分あける | 起動し直したジョブが動く前に、回数だけが上限に達しない |

起動し直すたびに、作業項目の遷移の記録へ、状態を変えない行を書く。
注記は`approval handler restarted for request N`で、Nは依頼のIDである。この行の数が回数になる。
3回起動し直しても作業項目が承認待ちのままなら、人の対応待ちへ移して通知する。理由は`approval decision could not be applied after 3 restarts of the handler`である。
起動し直しの行は、状態が同じ遷移の記録なので、Consoleの「今の状態へ遷移したときの注記」からは除く([Console](console.md))。

### 依頼の側の走査

作業項目の側の走査の後に、期限切れの承認待ちの依頼を読み、作業項目の側が扱わないものを、依頼だけ期限切れにする。
作業項目は動かさず、通知しない。
対象は、新しい依頼を作り直した後に残った古い依頼、作業項目が先に進んだ依頼、作業項目だけが期限切れになって落ちた後の依頼である。
「作業項目が承認待ちにあり、最新の依頼がこの依頼」のものは、作業項目の側の担当なので、触らない。
比較交換が負けたときに、依頼だけが期限切れになって作業項目が残る状態を作らないためである。

1件の例外は`job_failures`に記録して、次へ進む。
期限切れの通知の対象リンクはIssueのURLで、次の操作は理由の表が決める。

期限切れの後の人の操作は`retry_work_item`である。
設計が有効で未承認なら、設計フローで設計を作り直す。`design_attempt + 1`で始まり、`feedback`は空である。最新の依頼が却下でないためである。

走査が作業項目を期限切れへ移した後も、依頼が承認待ちの間は、人が承認を記録しうる。
そのとき判断は反映されず、依頼は承認済みのまま残る。
作業項目は期限切れで、再実行できる。再実行は、最新の依頼が承認済みなら承認の後の工程から始める。窓は走査の1件の処理の間に限られ、実装が人の承認なしに進むことはない。

## worktreeと掃除

設計は、対象リポジトリの設計専用のworktree(`/workspaces/<owner>/<repo>/design-<N>`)を読む。
要件定義用の`req-<N>`とは別にする。
要件定義の承認の反映が`req-<N>`を消すので、共有すると設計の途中で消えるためである。

`design_prepare`は、リースと設計中の状態を確かめた後でだけ、`design-<N>`を毎回作り直す。
前の実行のプロセスが使用中なら、消さずに例外とする。
リースを失った実行は、worktreeを触らずに終える。
既定ブランチの先頭は、メインのcloneで求めて`head_sha`として次のステップへ渡す。
Claudeの実行の後に、`design-<N>`の中でgitを実行しない。
書き換えられた`.git`の設定を、gitが読みうるためである。

`design_generate`は、Claudeの実行をworktreeのプロセスロックで包む。
準備が使用中のworktreeを消さないためである。
ロックの持ち主の種別は`design`で、値はリースのルートジョブIDである。
設計の準備は、プロセスを止めない。
実装の準備も、持ち主が`design`のプロセスは止めない。
残ったプロセスが使用中なら、`WorktreeBusyError`で引き返す。
後始末は`finally`で行う。

| 後始末の対象 | 削除の条件 |
| --- | --- |
| `design-<N>`のworktree | リースを持つときだけ。リースを失った実行が消すと、同じパスを使う新しい実行のものを消しうる |
| 要件定義の図の複製 | リースに関係なく消す。ジョブごとの一時ディレクトリで、新しい実行と共有しない |

実行が強制終了されて`finally`が走らなかったときの`design-<N>`は、日次の掃除(`f/factory/cleanup_workspaces`)が消す。
消す対象の判定は`f/factory/lib/cleanup_support.ts`にある。
対象は、終端の作業項目の`design-<N>`である。
稼働中の作業項目のものは除く。

## 人の対応待ちの通知

設計フローの人の対応待ちの通知は、理由の訳と次の操作を`designNeedsHumanFields`で作る。
設計フローの失敗でも、`on_error_flow`の`failureNextAction`が、設計フローの失敗に設計向けの次の操作を返す。
worktreeのロックが残っているときの案内が、実装と設計で変わるためである。
設計のClaudeが残したプロセスを確かめて止める操作を示し、設計の準備が何も止めないことを添える。

設計が使う理由の文字列は、理由の定数と関数が作る。
理由と次の操作の対応は、`pr_workflow_support.ts`の表(`DESIGN_REASON_RULES`)が持つ。
表は定数をimportせず、文字列を直接書く。
`tests/scripts/pr_workflow_support_design.test.ts`が、定数と関数の出力を表と突き合わせる。

| 理由 | 定数または関数 |
| --- | --- |
| 設計フローを起動できなかった | `DESIGN_START_FAILED_REASON` |
| 承認済みの要件定義が無い | `designNoApprovalReason` |
| 要件の不足を返したが試行が上限に達した | `designGapExhaustedReason` |
| 設計の却下が上限に達した | `designRejectedExhaustedReason` |
| 設計の承認が期限切れになった | `DESIGN_APPROVAL_TIMED_OUT_REASON` |
| 設計を始める前に書き換わっていた | `REQUIREMENTS_MODIFIED_BEFORE_DESIGN_REASON` |
| 設計の実行中に書き換わった | `REQUIREMENTS_MODIFIED_REASON` |
| 実装の関門で書き換わっていた | `REQUIREMENTS_MODIFIED_BEFORE_IMPLEMENT_REASON` |
| 要件定義のディレクトリが無い | `REQUIREMENTS_DIR_MISSING_REASON` |
| 保存済みの下書きと同じディレクトリである | `DESIGN_DOC_DIR_IN_USE_REASON` |
| 設計の承認が無い | `noApprovedDesignReason` |
| 承認済みの設計書が要件定義と食い違う | `DESIGN_STALE_REQUIREMENTS_REASON` |
| 設計の承認の記録が食い違う | `DESIGN_APPROVAL_INCONSISTENT_REASON` |

下の3つの理由は[承認の照合](#承認の照合)の定数と関数で、実装の関門と設計の承認の反映が出す。

承認の判断の反映を3回起動し直しても作業項目に反映されなかったときの理由(`approvalApplyStalledReason`)は、承認待ちの走査が出す。
この理由は設計と要件定義で共通である。次の操作は、`pr_workflow_support.ts`の共通の規則が持つ。

設計の却下の反映で要件定義へ戻せなかったときの理由は、要件定義の生成を起動できなかったとき(`requirements regeneration could not be started`)である。
次の操作は、再実行すると要件定義を作り直し、承認し直しが要ること、取り込み内容は現在のIssueで更新されること、却下の理由は再実行で渡ることを案内する。

書き換えとディレクトリが無い場合の次の操作は、承認済みのディレクトリを確かめてから、`retry_work_item`で再実行することである。
再実行は、設計が有効かに関わらず、要件定義を作り直す。人の承認し直しが要る。
基準値が残るので、実装や設計に戻しても同じ理由で止まるためである。

## リースと失敗

設計フローのリースは、pipelineフローと同じ規則で、`flow_job_id`が自分のルートジョブIDと一致することを求める。
`on_error_flow`は、設計フローの失敗でも、`flow_job_id`がルートジョブIDと一致するときに限って作業項目を失敗(`failed`)にする。
要件へ戻す比較交換は`flow_job_id`を空にする。
空の間は、残った古い実行の失敗が、新しい作業項目を失敗扱いにできない。

`retry_work_item`は、止まった作業項目だけを設計中へ移す。
設計中と設計の承認待ちの作業項目は、再実行できない。
人の判断を待つ間に、別の実行が並ばないようにするためである。
設計の却下の再生成は、設計の承認待ちから設計中へ移す。
設計中から設計中への遷移は作らない。
遷移で`flow_job_id`を空にしても安全な根拠は、次の3つである。

- 前の設計フローは、最後のステップ(`design_request_approval`)の中にあり、その後に動くステップが無い。
- 設計の後始末は、生成のステップの`finally`で済んでいる。承認依頼のステップはworktreeに触れない。
- 前のフローが移行の後で失敗しても、失敗ハンドラ(`failure_module`が呼ぶ`on_error_flow`)は、`flow_job_id`がルートジョブと一致するときだけ作業項目を失敗にする。再生成の遷移の後は`flow_job_id`が空で一致しないので、古いフローは新しい実行の作業項目を動かせない。

設計の実行の後始末は、リースを確かめてからworktreeを削除する。
設計中のまま別の実行にリースを渡す経路があると、確認と削除の間に、古い実行が新しい実行のworktreeを消すためである。
停止した状態を経由すれば、古い実行は、停止の遷移より前に必ず終わっている。
設計フローへの再実行も、pipelineと同じく、遷移で`flow_job_id`を空にし、ジョブIDは空のときだけ記録する。

設計中と設計の承認待ちは、承認済み以降の状態の集合(`APPROVED_OR_LATER_STATUSES`)に入れる。
設計中の親の作業項目を、PR修正の差し戻しが見つけられるようにするためである。
