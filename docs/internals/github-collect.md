# GitHubの収集の内部仕様

`collect_github`がGitHubから何を読み、どう判定し、何をDBに書くかを定める仕様である。
収集の本体と判定、問い合わせを変更する人が読む。
対象は`collect_github`と、`lib/gh_collect*.ts`、`lib/gh_graphql.ts`である。
トークンの作り方と扱いは[セキュリティ](../security.md)に書く。
有効にする手順と失敗への対処は[運用](../operations.md#収集の運用)に書く。

## 方針

収集は、読み取り専用のトークンで、所有者ごとのリポジトリの状態と、開いているPRとトリガーラベル付きIssueの詳細をDBに集める。
収集は二段で進む。
段1はリポジトリの一覧と件数を取り、段2はPRとIssueの詳細を取る。
収集は作業項目の状態には触れない。
記録を読むのは、次の6つの処理だけである。

- `self_update`は、実行の記録を読み、収集の鮮度を監視する([鮮度の監視](#鮮度の監視))。
- `poll_dependabot`は、設定`gh_source_dependabot`が`db`のとき、候補のPRを表から読む([読む側の判定](#読む側の判定))。
- `watch_pr_conflicts`は、設定`gh_source_pr_conflict_watch`が`db`のとき、リポジトリの発見とPRの列挙を表から読む([読む側の判定](#読む側の判定))。
- `poll_issues`は、設定`gh_source_poll_issues`が`db`のとき、トリガーラベル付きのIssueを表から見つける([所有者の単位の読み取り](#所有者の単位の読み取り))。
- `poll_prs`は、設定`gh_source_poll_prs`が`db`のとき、ラベル、レビューの依頼、assigneeのPRを表から見つける([所有者の単位の読み取り](#所有者の単位の読み取り))。
- `watch_pr_ci`は、設定`gh_source_pr_ci_watch`が`db`のとき、許可された人のPRの候補を表から見つける([所有者の単位の読み取り](#所有者の単位の読み取り))。

記録は`gh_repos`、`gh_collect_runs`、`gh_pull_requests`、`gh_issues`の4つの表に残す。

`collect_github`は、tag `periodic`のworkerで5分ごとに動く。
読むsecret変数は`github_read_tokens`だけで、書き込みのできる`github_token`は読まない。
通信先は`https://api.github.com/graphql`に固定し、トークンは`Authorization`ヘッダだけに載せる。
応答の本文とGraphQLのエラーの文は、残さない。
ジョブの結果には、所有者、件数、失敗の種類だけを載せる。
ログには、これに加えて、拒否された項目の許可表の`type`と問い合わせの項目名だけを、1回10件まで載せる([拒否された項目のログ](#拒否された項目のログ))。
リポジトリの名前は、ログの警告にだけ載せる。

設定`gh_collect_enabled`が`false`(既定)の間は、トークンを読まず、行も書かずに終わる。
設定`gh_collect_detail_enabled`が`false`(既定)の間は、段2の要求と、件数が0のリポジトリを閉じる処理を行わず、段1の下限も変えない。
段2だけを止めるためのキーで、`gh_collect_enabled`が`false`なら、このキーによらず何もしない。
使えない行の無効化([使えない行の無効化](#使えない行の無効化))は段1の一部なので、このキーによらず行う。
ただし、レート制限で`next_allowed_at`を書いた所有者は、次の周回で段1を通信しないので、無効化も最大1時間遅れる。

## 収集の対象

設定の`owners`に書いた所有者のリポジトリのうち、`isRepoAllowed`が真のものを集める。
所有者ごとに、`ownerAffiliations`が`OWNER`で、forkでないリポジトリを一覧する。
archive済みのリポジトリも一覧に載るので、`archived`を立てて記録する。

一覧にあって`isRepoAllowed`が偽のリポジトリは、`allowed`を偽にして記録し、件数の列は書かない(`NULL`)。
`owners`に無い所有者の`factory_repo`は、集めない。
一覧は所有者ごとに取るので、`isRepoAllowed`が`factory_repo`を無条件に許しても、一覧に現れないためである。

loginに`_`を含む所有者(EMUのアカウント)は、扱わない。
`bootstrap.sh`が環境変数の名前の`_`を`-`に直すので、対応表のキーに合わず、その所有者は`no_token`になる。
`mise run doctor`が、`owners`にある該当の所有者の名前を警告する。

## トークンの対応表

変数`github_read_tokens`の値は、所有者のlogin(小文字)をキーにしたJSONの対応表である。
`mise run bootstrap`が、環境変数`GITHUB_READ_TOKEN_<OWNER>`から組む。
人がJSONを手で組むことは無い。

変数は、次の順に読む。

1. 変数が空、未投入、または読む呼び出しが例外を投げた。全員分が`no_token`になる。例外の文は捨てる。
2. 対応表の形が誤り。全員分が`token_config_invalid`になる。
3. `owners`にあって対応表に無い所有者。その所有者だけ`no_token`になり、通信しない。

形の誤りは、次のいずれかである。

- JSONでない。
- オブジェクトでない。
- キーがGitHubの名前の形でない。
- 小文字にして重なるキーがある。
- 値が、許す文字だけの文字列でない。

読み取りは、例外を投げない述語で行う。
キーと値は、戻り値、ログ、DB、例外のどこにも出さない。
所有者の引き当ては`Map`で行うので、`constructor`などのプロトタイプの名前とは混ざらない。

## 1回の実行

1回の実行は次の順に進む。

1. `gh_collect_enabled`が偽なら、何もせずに終わる。
2. `owners`の全員分の実行の行(`gh_collect_runs`)を、1つの文で先に書く。書けなければ、トークンを読む前に例外を投げて、`on_failure`に任せる。
3. 変数を読み、所有者ごとの最新の実行を読む。
4. 所有者を、先頭を担当してから長い順に回す。並びの規則は[所有者の順](#所有者の順)に書く。
5. 段1: 所有者ごとに、一覧を読み、照合し、記録を置き換える。置き換えの文は、使えない行の無効化も行う。
6. 段1が失敗した所有者は、その場で行を更新して`finished_at`を書く。段2の要求は送らない。
7. `gh_collect_detail_enabled`が偽なら、段1が成功した所有者も、その場で行を終える。
8. 真なら、段1が成功した所有者は行を保留にし、全員分の段1が終わった後に、段1と同じ順で段2を回す。段2を終えた所有者から、行を終える。

所有者のループ全体は、段2が有効なとき1つの`try`/`finally`で包む。
`finally`は、保留のまま行を終えていない所有者をすべて終える。
例外で抜けた保留の所有者は、`ok`が偽、`error_code`が`parse_error`、`stage`が`detail`になり、段1の照合の結果と`led`は保つ。
例外は`finally`の後に投げ直すので、ジョブは失敗になる。
段1の途中で例外を投げた所有者と、まだ回していない所有者の行は、`finished_at`が空のまま残る。
段2で想定外の例外が出た所有者は、同じ`parse_error`の行で終え、次の所有者の段2は続ける。

終わりの更新に失敗した行は、`ok`が偽、`finished_at`が空のまま残る。
最新の実行は、所有者ごとに`finished_at`のある最新の行である。実行中の行は数えない。

### 通信を控える

前回の`next_allowed_at`が未来の所有者には、通信しない。
行は`ok`を偽にし、前回の`error_code`と`next_allowed_at`を引き継いで、`finished_at`を書く。
`gh_repos`は前回のままにする。

レート制限を受けた所有者は、`next_allowed_at`を書く。
一次の制限は`x-ratelimit-reset`、二次の制限は`Retry-After`まで通信を控える。
GitHubが時刻を示さないときは1分とする。
どの場合も、1時間以内に切り詰める。

### 締め切り

実行全体の締め切りは100秒で、scriptのtimeout(120秒)の内側にある。
残りが10秒(1要求の打ち切り)未満なら、新しい要求を始めない。
段2が有効なときは、段1に限り、残りが40秒未満なら新しい要求を始めない。
段2に30秒の取り分を残すためである。
下限を切った所有者は、`error_code`が`deadline`、`stage`が`list`になる。
段1で1人が確実に取り切れる大きさは、要求ごとに10秒かかる最悪で6要求、約600リポジトリである。

締め切りで未着手の所有者と、一覧の途中で打ち切った所有者は、`error_code`が`deadline`になる。
照合と`gh_repos`は前回のままにする。

### 所有者の順

所有者は、先頭を担当してから長い順に回す。
先頭を担当するとは、その周回で最初に段1の要求を送ることである。
先頭を担当した所有者の行だけ、`led`を真にする。
結果(成功、失敗、`deadline`)は問わない。
`led`は1周回に高々1人で、要求を1回も送れずに終えた所有者には付かない。
段2の要求は、`led`に数えない。

`led`は、段1の最初の要求を送る直前に決める。
行を終える順は、要求の順と一致しない(失敗した所有者が先に終わる)ためである。

並びのキーは、`led`が真の実行のうち、`finished_at`のある最新のものの`started_at`である。
終わりの更新に失敗した行は数えない。
先頭を担当したことの無い所有者は先に回す。
同じキーの所有者は、設定の順を保つ。

先頭を担当した所有者は、結果を問わず後ろへ回る。
所有者がn人なら、各所有者は、n周回に1回は予算のすべてを持つ。
段2が有効なときは、締め切りの40秒前までに段1の最後の要求を始められる所有者が、n周回に1回は成功する。
予算の半分を超える所有者が何人いても同じである。
前の所有者に時間を使い切られる所有者も、いつかは先頭になるので、取り残されない。
時間を使ってから502や`timeout`で終える所有者も、同じ回り方になる。

段1で先頭を担当した所有者は、段2でも先頭になる。
段2の残りの時間は、先頭の所有者がすべて持ち、ほかの所有者は先頭の使い残しを、順番制の順で使う。
所有者ごとの予算の数は持たない。
所有者の番の中で、残りが10秒を切ったら新しい束を送らない。

1人で締め切りに収まらない所有者がいても、ほかの所有者は取り残されない。
その所有者自身は、先頭を担当しても取り終えられないので、記録は前回のまま凍る。
速い所有者が先頭を担当したときは、その分が短時間で終わり、後ろの所有者が残りの時間をほぼすべて持つ。

### 一覧の問い合わせ

所有者ごとに、`repositoryOwner(login)`の`repositories`を100件ずつ、カーソルで全ページ読む。
所有者、ラベル、カーソルはGraphQLの変数で渡し、文字列に埋め込まない。
並びは名前の昇順で固定する。
各リポジトリについて、数値ID、名前、archive済みか、開いているPRの件数、トリガーラベル付きの開いているIssueの件数を読む。
既定のブランチの名前(`default_branch`)は取らない。ブランチの参照の読み取りにContentsの権限が要るためである。
列は残し、値は空のままにする。
所有者の数値IDは、照合に使う。

要求数は、所有者ごとに、リポジトリの数を100で割って切り上げた値になる。
`cost`と`remaining`は、応答の`rateLimit`から読む。
`rateLimit.resetAt`も読む。読めなければ空として扱う。

## 詳細の取得

段2は、段1が成功した所有者の、開いているPRとトリガーラベル付きの開いているIssueの詳細を取る。
`gh_collect_detail_enabled`が真のときだけ行う。
`lib/gh_collect_detail.ts`は、対象の選別、応答の解析、書き込みの計画、結果の分類を持つ。
`lib/gh_collect_detail_round.ts`は、待ち行列と束、分割、ページ送りを持つ。
どちらも通信とDBを持たない。

### 詳細の対象

段1の一覧と、置き換えの前の`gh_repos`の全行から、リポジトリを次の3つに分ける。
前回すでに`gone`だったリポジトリを見落とさないよう、差分の`gone`だけには頼らない。

| 分類 | 条件 | 扱い |
| --- | --- | --- |
| 対象 | 一覧に載り、許可され、archiveされておらず、開いているPRの件数かトリガーラベル付きIssueの件数が1以上 | 段2の要求を送る。件数が0の側は取らず、空の一覧を取り終えたものとして閉じる |
| 件数0 | 一覧に載り、許可され、archiveされておらず、2つの件数がどちらも0 | 要求を送らない。開いている行を閉じ、`last_collected_at`と`last_attempted_at`を進め、2つの印を偽に戻す。所有者ごとに1つの文で行う |
| 使用不可 | 許可の外、archive済み、または`gh_repos`にあって今回の一覧に載らない | 段2では何もしない。開いている行は段1の置き換えの文が使用不可にしている |

件数0のリポジトリを要求なしで閉じてよいのは、一覧の件数が、段2が数えるのと同じ集合の件数だからである。
一覧は取り終えて照合を通した応答なので、0件の一覧を取り直しても空の一覧が返るだけである。

段1が成功しなかった所有者の行は、`owner_mismatch`を除き、何も変えない。
段1が`owner_mismatch`の所有者は、設定にIDがあるかによらず、その所有者の開いている行をすべて使用不可にする。
名前が別のアカウントに付け替わった疑いがあるので、閉じる側に寄せるためである。
置き換えを呼ばないため、段1の失敗の場で1つの文で行い、失敗しても結果は変えず、警告だけを残す。

### 詳細の問い合わせ

1回の要求に、最大20リポジトリを別名`r0`〜`r19`で束ねる。
所有者、名前、ラベル、カーソル、取る側の真偽は、GraphQLの変数で渡す。
問い合わせの文は、固定の雛形と別名の数だけから`buildRepoDetailQuery`が組み立て、外から来た文字列は入れない。
別名の数は1以上20以下の整数に限る。

- PRは開いているものを、Issueはトリガーラベル付きで開いているものを、それぞれ1ページ30件で取る。ページの上限は3で、リポジトリごとに最大90件である。
- 並びは作成の新しい順にする。ページの間にPRが更新されても、カーソルより前へ動いて取りこぼされないためである。
- 取る側は`@include`で切り替える。件数が0の側と、取り終えた側は取り直さない。
- ブランチの参照(`headRef`、`baseRef`、`defaultBranchRef`)は辿らない。参照を辿るとContentsの権限が要りうるので、名前とコミットのSHAはPRのスカラー項目で読む。
- `baseRefOid`と`mergeStateStatus`は問い合わせない。この2つはスキーマで`null`にならない項目で、権限で拒否されるとPRのノードごと`null`になる。

### 必須と任意の項目

応答は、例外を投げない述語で検査する。
値は例外の文とログに出さない。
項目は必須と任意に分ける。

任意の項目は、スキーマで`null`を許す`labels`、`reviewRequests`、`author`、`autoMergeRequest`の4つと、Issueの`author`である。
任意の項目のエラーは、その項目の列だけを`NULL`にし、リポジトリの取得は失敗にしない。
その項目だけが`null`になり、ノードは残るためである。
組織のリポジトリでチームの依頼の読み取りが拒否されても、そのPRの依頼の列が`NULL`になるだけである。
任意の項目のエラーは、固定の項目名と丸めた種類の組ごとに数え、実行の結果とログに件数で載せる。

必須の項目は、検査に通らなければリポジトリの取得を失敗にする。

| 項目 | 列 | 検査に通らないとき |
| --- | --- | --- |
| 番号、SHA、ドラフトか、forkか、作成と更新の時刻 | `number`、`head_sha`、`is_draft`、`is_cross_repository`、`created_at`、`updated_at` | 失敗(`parse_error`) |
| `assignees` | `assignee_ids` | 失敗(`parse_error`)。件数が取れた数より多いときは`NULL` |
| ブランチ名 | `head_ref`、`base_ref` | `NULL`。forkのブランチ名は任意で、通らない名前で行ごと捨てると誤って閉じるため |
| `mergeable` | `mergeable` | `MERGEABLE`と`CONFLICTING`だけを書く。それ以外は`NULL` |
| 作者 | `author_login`、`author_type`、`author_id` | 3つとも`NULL`。作者の削除でも同じ。数値IDが無い種別は`author_id`だけ`NULL` |
| `autoMergeRequest` | `auto_merge_enabled` | `null`なら偽、オブジェクトなら真。エラーなら`NULL` |
| `labels` | `has_review_label`、`has_fix_label` | 名前を小文字にして、設定の`review_label`と`fix_label`と比べた真偽。100件を超えるときとエラーのときは2つとも`NULL`。ラベル名は保存しない |
| `reviewRequests` | `review_requested_user_ids`、`team_review_requested` | 利用者の数値IDを集める。チームの依頼か依頼先が読めない依頼が1件でもあれば、チームの依頼を真にする。20件を超えるときとエラーのときは2つとも`NULL` |

別名ごとの扱いは次のとおりで、上から当てる。

1. 別名の水準のエラーがあれば、その別名は失敗(`graphql_error`)にする。値の検査より先に当てる。
2. `repository`が`null`、または`databaseId`が段1の数値IDと違えば、その別名は失敗(`parse_error`)にする。名前が付け替わったか、別のリポジトリに置き換わったおそれがあるためである。
3. `nodes`に`null`の要素があれば、その要素を読まずに数え、別名を失敗(`parse_error`)にする。番号の分からない行があると、一覧を取り終えられないためである。

`mergeable`は、前回の値を保たず、今回の値をそのまま書く。
GitHubが計算していない間は`NULL`になる。
下流が最初に`mergeable`を読む変更で、保つ規則を決める。

### 保存する値の検査

書くときと読むときの両方で、次の述語を通す。
通らない値は、書くときは`NULL`(必須の項目は失敗)にし、読むときは例外にして値を含めない。

| 述語 | 規則 |
| --- | --- |
| ブランチ名 | ブランチ名の規則を通り、UTF-8で255バイト以下で、制御文字、書式文字、行と段落の区切りを含まない |
| ログイン名 | GitHubの名前の形で、39文字以下 |
| 数値ID | 正の安全な整数 |
| SHA | 40桁の小文字16進 |
| 列挙 | 決められた値のどれか。`mergeable`は`MERGEABLE`と`CONFLICTING`、作者の種別は5つ、PRの状態は`open`と`closed`、Issueの状態は`open`と`unlisted` |

書き込みの全体は`checkGhRepoDetailWrite`で検査する。
各行の列、行の番号の重なり、行の番号が残す番号に含まれること、残す番号が正の整数で重ならないことを確かめる。
通らなければ、そのリポジトリを失敗(`parse_error`)にし、書かない。
`writeGhRepoDetail`は、書く前に同じ検査をやり直す。
通らないときは、DBに触れず`rejected`を返す。
DBの失敗だけを例外にするので、検査の失敗とDBの失敗は、戻り値と例外で分かれる。

### 詳細の予算と順

段2は、全員分の段1の後に、段1と同じ順で回す。
先頭を担当した所有者が段2の残りの時間をすべて持ち、ほかの所有者は先頭の使い残しを順に使う。
段2の取り分は30秒で、段1は、段2が有効なとき40秒を残して要求を止める。
段2に残るのは、置き換えの文などの時間を引いた30秒弱で、最悪(どの要求も10秒かかる)では、全員で2束を送れる。
段1が速く終われば、段2は残りのすべてを使う。

要求は、全体の残りが10秒以上のときだけ始める。
1要求の打ち切りは、10秒と全体の残りの短い方である。

その周回の最後の応答(段1か段2)の`rateLimit.remaining`が500未満なら、その所有者の段2を始めない、または続けない。
このとき行は`rate_limited`になり、`next_allowed_at`を`rateLimit.resetAt`(読めなければ1分後)に、1時間以内に切り詰めて書く。
次の周回は、その所有者の段1も通信しない。
対象が無い所有者と、段2が無効のときは、`remaining`が500未満でも成功の行にする。

### 待ち行列と分割

所有者の中のリポジトリは、2本の待ち行列で送る。

- 疑いの無いリポジトリを、結果を最後に書いた時刻(`last_attempted_at`)の古い順に、20件ずつの束にした健全な列。一度も着手していないものを先にし、同じ時刻は名前の順にする。
- 疑いの列。前回失敗したリポジトリ(`detail_failed`が真)を、同じ順に1件ずつの束にしたもの。

健全な列から束を1つ送るごとに、疑いの列が空でなければ、疑いの束を1つ送る。
健全な列が空になったら、疑いの束を続けて送る。
疑いのあるリポジトリは、時間の短い周回でも、永久に後ろへ回らない。
数値IDが入れ替わったリポジトリは、一度も着手していない疑いの無いものとして扱う。

ページが続くリポジトリは、その応答の分をまとめて1つの束にし、健全な列の先頭に置く。
取りかけのリポジトリを先に取り終え、締め切りで中途のリポジトリを減らすためである。

束の中の1件が原因でありうる失敗は、束を半分に分けて送り直す。
次の4つがその失敗である。

- 時間切れ
- 5xx、通信断、要求が投げた例外
- 要求全体のGraphQLのエラー(`path`が無いか、別名で始まらないもの)
- 応答全体の形の誤り

分けた2つの束は、健全な列の末尾に戻す。
分けた束のリポジトリは、通るまで分割の疑いを持つ。
分けた束が通ると、その分割の疑いは晴れる。
単独の束が失敗したら、そのリポジトリを失敗にする。

分割は、1周回に所有者あたり8回までにする。
すぐ返る5xxが続くと、20件の束を分け切るまでに多くの要求を使うためである。
上限に達した後で、分けて送り直す失敗をした束は、分けずにリポジトリをすべて失敗にする。
既に列にある束は、そのまま送る。

周回の終わり(列が空になったか、締め切りか停止で止まった)に、次のリポジトリの結果を確定する。

- 分割の疑いが晴れていないもの。失敗にする。
- 1ページ以上を取り、分割の疑いが無いもの。打ち切りにする。
- 一度も送らなかったもの。何も書かない。疑いの列で送らなかったものも同じ。

何も書かないリポジトリは`last_attempted_at`が進まないので、次の周回で先頭に来る。
常に失敗するリポジトリは、次の周回から疑いとして1件ずつ送られ、同じ束のほかのリポジトリを巻き込まない。

### 失敗の扱い

段2の要求は、別名の水準のエラーだけを成功として返す。
次をすべて満たすときである。

- `data`がオブジェクトである。
- すべてのエラーの`path`が、送った別名で始まる。
- `RATE_LIMITED`のエラーが無い。

返すのは、別名、固定の語に丸めた種類(`FORBIDDEN`、`NOT_FOUND`、`OTHER`)、位置の3つと、位置が別名全体になったエラーの拒否された項目である。
位置は、PRの任意の項目の添字と項目名、Issueの作者の添字、別名全体のどれかに丸める。
`message`と`path`の残りは捨てる。
満たさなければ、段1と同じく要求全体の失敗(`graphql_errors`)にする。

次は、その所有者の段2を止める失敗で、ほかの所有者の段2は続ける。
所有者ごとにトークンの持ち主が違いうるためである。

- 401
- レート制限でない403
- 429、二次の制限、`RATE_LIMITED`
- `remaining`の下限
- 段2の初めの行の読み取りの失敗と、`writeGhRepoDetail`のDBの失敗(例外)

リポジトリの結果は、次の5つである。

| 結果 | 条件 | 書くもの |
| --- | --- | --- |
| 取り終えた | 取ると決めた側を最後のページまで取り、件数の照合が通り、書く前の検査が通り、書き込みが成功した | 行の差分、閉じる行、`last_collected_at`(観測を始めた時刻)、`last_attempted_at`(`now()`)、2つの印を偽に戻す。1つの文 |
| 打ち切り | ページの上限に達した。件数の照合が合わない。1ページ以上を取った後に締め切りか停止で止まった | `truncated`を真、`detail_failed`を偽、`last_attempted_at`を進める。行は書かない。`last_collected_at`は進めない |
| 失敗 | 別名の水準のエラー、値の検査の失敗、書く前の検査の失敗、書き込みの拒否、単独の束の失敗、分割の疑いが晴れないまま終えた | `detail_failed`を真、`truncated`を偽、`last_attempted_at`を進める。行と`last_collected_at`は前回のまま |
| 未着手 | 一度も送らないうちに止まった。疑いで送らなかった。書き込みが`no_repo_row`を返した | 何も書かない |

打ち切りと失敗が重なるときは、失敗を優先する。
続く失敗を打ち切りに紛れさせないためである。
打ち切りのリポジトリの行を書かない理由は、見えた行だけを書いても`last_collected_at`を進めない以上、下流は使えないためである。
書き込みの経路を「取り終えたときに丸ごと」だけにし、部分の書き込みで閉じる判定を誤る道を作らない。

失敗と打ち切りの印の書き込みの失敗、件数0の閉じる処理の失敗、`owner_mismatch`の無効化の失敗は、警告だけにし、段2を止めない。
印や閉じる処理が書けなくても、下流は`last_collected_at`からの閾値までは前回の値に頼り、閾値を過ぎれば閉じる側に止まるためである。

### 拒否された項目のログ

権限で項目が拒否されたとき、どの項目かをログだけで分かるようにする。
エラーの文は読まず、`type`と`path`だけを次の規則で絞る。
外から来た文字列を、形の検査では通さない。
トークンの形をした文字列を通してしまうためである。

- `type`は、次のどれかと完全に一致するときだけ残す。
  欠けているときと、ほかの値のときは`OTHER`にする。
  - `FORBIDDEN`
  - `NOT_FOUND`
  - `INSUFFICIENT_SCOPES`
  - `MAX_NODE_LIMIT_EXCEEDED`
  - `SERVICE_UNAVAILABLE`
- 項目名は、`path`から数値の添字を除き、先頭の別名(`r<数>`)を除いた各要素を、問い合わせの文に現れる語の表と照らす。
  表は、一覧と詳細の問い合わせの文から、変数(`$`付き)と別名を除いた語を、読み込み時に作る。
  項目名、引数名、型名が入るが、すべて自前の固定の文の語である。
  問い合わせを変えると表も変わるので、手で保つ必要は無い。
- すべての要素が表に含まれ、要素が6個までのときだけ、`.`でつないだ項目名にする(例: `pullRequests.nodes.autoMergeRequest`)。
  次のときは、項目名を空にする。
  - ひとつでも表に無い要素があるとき。
  - 数値と文字列以外の要素があるとき。
  - 要素が0個のとき(`path`が別名と添字だけのとき)。
- レート制限(`RATE_LIMITED`)は項目の拒否ではないので除く。`type`が`OTHER`で項目名も空のエラーは、特定に使えないので除く。
- 同じ`type`と項目名の組は1件にまとめ、先頭から10件までにする。

詳細の問い合わせの成功の応答では、位置が別名全体になった(項目が固定の語に落ちなかった)エラーだけを、同じ規則で読む。
任意の項目のエラーは、既存の件数の集計で足りるため、読まない。

収集は、1件以上あるときだけ、警告のログ`graphql query items refused`を1行出す。
載せるのは、所有者、段(`list`か`detail`)、項目の配列(`type`と項目名)だけである。
段2では、束を分けて再送した応答ごとに出るので、同じ項目が繰り返し出る。
段2の行にはリポジトリ名が載らない。
同じ周回の`a repository detail failed`と突き合わせて、対象を絞る。

### 閉じる判定

PRの行を閉じる(`closed`にする)のは、そのリポジトリを取り終えたときだけで、前回`open`の行のうち今回の一覧に無いものである。
取り終えたとみなすのは、集めた番号(重なりを除く)の数が、最後のページの`totalCount`と等しいときだけである。
違えば打ち切りとして扱う。
この照合が防ぐのは、ページの間にPRが開閉されたときに、取りこぼした行を誤って閉じることに限る。

Issueも同じで、一覧から消えた行を`unlisted`にする。
Issueの一覧はトリガーラベルで絞るので、閉じたのかラベルが外れたのかは区別できない。
閉じた行が再び一覧に載ったら、`open`に戻して書き直す。
使用不可のリポジトリの行は閉じない。

### 書き込み

差分は、前回の行と今回の値を比べ、列と`repo_id`、`state`、`usable`のどれかが違う行だけを書く。
前回の行は、所有者ごとに1回、開いている行を読む。
`written_at`は値を書いた時刻で、鮮度には使わない。

取り終えたリポジトリは、リポジトリごとに1つの文で書く。
`gh_repos`の更新を最初の共通表式にし、PRとIssueの書き込みと閉じる処理は、その更新が行を変えたときだけ行う。
更新の条件に`repo_id`、`allowed`、`NOT gone`を含めるので、段1の後に行が変わっていれば、文全体が何も書かない。
書いた行数が0なら`no_repo_row`を返し、未着手として数える。

`last_collected_at`は、`now()`でなく、その所有者のその周回の観測を始めた時刻で書く。
一覧が1ページなら応答を受けた時刻、複数ページなら最初のページを送った時刻である。
段2で取った値は段1の後に観測したものなので、段1の時刻で書けば、鮮度を実際より古く見せる側(閉じる側)に倒れる。
workerとDBは同じホストのコンテナで時計を共有するので、下流はDBの`now()`と比べてよい。
`last_attempted_at`は並びのキーなので、DBの`now()`で書く。

## 照合と記録の置き換え

一覧を取り終え、照合が通ったときだけ、その所有者の記録を、1つの文(1つのトランザクション)で置き換える。
一覧を取り終えられなかったとき(2ページ目の失敗、締め切りなど)は、置き換えず、載らなかったリポジトリを`gone`にしない。

照合は、1ページ目の応答で行う。
2ページ目以降は、所有者があり、数値IDが1ページ目と同じことだけを確かめる。
違えば`parse_error`にして、記録を置き換えない。
一覧の途中で所有者が消えた応答を、完了として扱わないためである。
収集は、REST用の`gateOwnerId`を呼ばない。
`/graphql`のHTTP 404は、オーナー不在として扱わず、`http_5xx`と同じ失敗にする。

| 場合 | `verified` | `id_checked` | `gh_repos` |
| --- | --- | --- | --- |
| IDが一致 | 真 | 真 | 置き換える |
| 設定にIDが無い | 真 | 偽 | 置き換える |
| 不一致 | 偽 | `NULL` | 置き換えない。`owner_id_mismatch`の通知を残す |
| 所有者が見つからず、設定にIDがある | 偽 | `NULL` | 置き換えない。見つからない旨の通知を残す |
| 所有者が見つからず、設定にIDが無い | 偽 | `NULL` | 置き換えず、通知も出さない |
| 照合に至らなかった失敗 | 偽 | `NULL` | 前回のまま |

`verified`の意味は「照合の失敗が無い」であって、「IDが一致した」ではない。
IDが一致したことを確かめたい処理は、`id_checked`を見る。
設定にIDが無い所有者は、`verified`が真でも、`id_checked`は偽である。
段2の失敗の行も、段1の照合の結果(`verified`、`id_checked`、`owner_id`)を保つ。

### 使えない行の無効化

置き換えの文は、同じ文の中で、詳細の行(PRとIssue)の無効化も行う。
`gh_collect_detail_enabled`によらず行う。
レート制限で`next_allowed_at`を書いた所有者は、次の周回で段1を通信しないので、無効化も最大1時間遅れる。
そのため、詳細の表のmigrationを、コードより先に反映する。

使える行は、所有者の開いている行のうち、次のすべてを満たすリポジトリのものである。

- 今回の一覧に載っている。
- 許可され、archiveされていない。
- 行の`repo_id`が、今回の数値IDと等しい。
それ以外の開いている行は、許可の外、archive済み、一覧から消えた(前回からのものを含む)、数値IDの入れ替わりのどれかなので、`usable`を偽にする。
差分の`gone`や、段2の書き込みの成否には頼らない。
一覧が空の所有者でも文を送り、開いている行を残さない。

リポジトリの数値IDが変わった(同じ名前で削除して作り直した、改名して同じ名前を作った)ときは、`gh_repos`の詳細の4列を初めに戻し、そのリポジトリの名前を返す。
戻すのは、数値IDが空でなく、別の値に変わったときだけである。
一度も見えていない`not_visible`の行が初めて見えたときは、入れ替わりにしない。
収集は、返った名前をowner、repoの警告に残す。

無効にした行は、次に段2がそのリポジトリを取り終えたときに、差分で使用可に書き直されるか、一覧に無ければ閉じられる。
使用不可のリポジトリのあいだは、段2が取らないので、使用不可のまま残る。

### gone

`gone`の行は消さない。一覧に載り直すと、`gone`が偽、`gone_reason`が空に戻る。

| --- | --- |

人が対象にすると決めたリポジトリが見えなくなったことを、ほかの理由と区別して残すためである。

### 許可リストが空のとき

`repo_allowlist`が空の所有者は、見えないリポジトリを判別できない。
手がかりが無いので、`not_visible`は付かない。
反映の後に、記録の件数をGitHubの一覧の件数と、目で比べる([運用](../operations.md#許可リストが空のときの件数の確かめ方))。

### 保存する文字列の検証

書くときと読むときに、次を通す。
どれも例外を投げない述語で判定し、例外の文に値を入れない。

- `owner`と`repo`は、GitHubの名前の形。
- `gone_reason`と`error_code`は、決められた値。
- `default_branch`は、解析で見ない。
  書き込みと読み出しで、`null`以外をブランチ名の規則で検査する。
  収集が取らないので、値は常に空である。
- 詳細の行の文字列は、[保存する値の検査](#保存する値の検査)を通す。

検査を通らないリポジトリは、そのページから外す。
外したリポジトリは、一覧に載らなかったものとして扱うので、閉じる側に倒れる。
捨てた行の記録は、所有者、リポジトリの名前(検査を通ったものだけ)、番号、列の名前に限る。

### 詳細の表

`gh_pull_requests`は開いているPRの行、`gh_issues`はトリガーラベル付きの開いているIssueの行を持つ。
段2が書き、`cleanup_db`が消す。
2つの表の行は、`(owner, repo, number)`で一意である。
外部キーは持たない。作業項目とは独立した記録である。

| 列 | 意味 |
| --- | --- |
| `repo_id` | 行を書いたときのリポジトリの数値ID。`gh_repos.repo_id`と違う行は、別のリポジトリに置き換わった後の行なので使わない |
| `state` | PRは`open`か`closed`、Issueは`open`か`unlisted`。Issueの一覧はトリガーラベルで絞るので、閉じたのかラベルが外れたのかを区別できず、1つの値にまとめる |
| `usable` | 偽の行は使わない。許可の外、archive済み、一覧から消えた、所有者の不一致、`repo_id`の入れ替わりのどれかを表す |
| `written_at` | 値を書いた時刻。鮮度ではない。鮮度は`gh_repos.last_collected_at`で表す |

`gh_repos`に足した列は、詳細の取得の状態を表す。

| 列 | 意味 |
| --- | --- |
| `last_collected_at` | 詳細を最後に取り終えた周回の、観測を始めた時刻。書いた時刻ではない。`NULL`は一度も取り終えていない |
| `last_attempted_at` | 詳細の結果を最後に書いた時刻。取る順の並びのキー。`NULL`は一度も着手していない |
| `truncated` | 前回の着手が、ページの上限か件数の照合の不一致で打ち切られた印。既定は偽 |
| `detail_failed` | 前回の着手が失敗した印。真のリポジトリは、次の周回で1件ずつ取る。既定は偽 |

### 詳細のデータの意味

- `gh_repos.last_collected_at`は、そのリポジトリの行を段2で最後に取り終えた周回の、観測を始めた時刻である。
- `open`は、`last_collected_at`の時点以降の観測で開いていたことを表す。`closed`と`unlisted`も同じ観測の事実である。
- 行が無いことは、閉じたことを意味しない。`last_collected_at`の後に開いたPR、打ち切りや失敗で取れていないリポジトリのPR、保持期間の掃除で消えた閉じた行は、どれも行が無い。
- `usable`が偽の行は、許可の外、archive済み、一覧から消えた、所有者の不一致、`repo_id`の入れ替わりのどれかで、使えない。
- `NULL`の列は不明で、偽や空を意味しない。
- 1つのリポジトリの行と`gh_repos`の列は、1つの文で書く。下流は1つのリポジトリの行を1つの文で読む。
- 題と本文は保存しない。ラベルは名前でなく、`has_review_label`と`has_fix_label`の真偽だけを持つ。
- 作者は生の`login`と種別を保存する。dependabotはGraphQLで`dependabot`と`Bot`になる。`dependabot[bot]`への正規化は、読む側で行う。

### 下流が守る不変条件

詳細の行を読む処理は、次を守る。
ブランチ名と作者は信頼できない入力で、DBの値だけでGitHubへの操作に進むと、誤った操作につながるためである。

- DBの値は、候補を絞ることと、閉じる側に止めることにだけ使う。GitHubへ作用する操作(マージ、push、修正の起動、ラベルやコメント)は、判断に使った行のSHAに固定するか、操作の直前にRESTで読み直して一致を確かめる。
- Factoryのブランチとみなすのは、forkでなく、`head_ref`が合うときだけである。`head_ref`が`NULL`の行は、Factoryのブランチではない。
- 人の確認(ラベルを付けた人、権限に関わる作者)は、RESTのまま行う。
- 行の`repo_id`が`gh_repos.repo_id`と等しく、`usable`が真の行だけを使う。
- `head_ref`、`base_ref`、`author_login`は、切り詰めてから通知やプロンプトに載せる。
- `head_ref`と`base_ref`は、シェルへ文字列で結合せず、引数の配列で渡す。
  ブランチ名は外の人が決められ、結合するとシェルが名前の一部を命令として読むためである。
- GitHubへ投稿する本文に`head_ref`、`base_ref`、`author_login`を載せるときは、コード表記で囲む。
  囲まないと、`@`を含む名前で意図しない通知が飛ぶためである。
- `NULL`の列は、候補を広げる側(RESTで確かめる)に扱い、DBの値だけで起動の判断に進まない。

### 読む側の判定

詳細の行を読む処理は、閾値で判断を止める判定を備えなければならない。
打ち切りや失敗のリポジトリの古い行は、`usable`が真のまま残るためである。
判定は`lib/gh_collect_read.ts`が持つ。
通信とDBを持たない純粋関数で、`poll_dependabot`、`watch_pr_conflicts`、`poll_issues`、`poll_prs`、`watch_pr_ci`が使う。

| 関数 | 役割 |
| --- | --- |
| `ghDetailStaleAfterMs` | 記録を使わずに止める閾値を返す |
| `judgeGhRepoFreshness` | リポジトリの記録を使ってよい鮮度かを判定する。PRの行とIssueの行のどちらにも当てる |
| `usableGhDetailRows` | PRの行とIssueの行から、使ってよい行だけを残す。`usableGhPullRequests`はPRの行に当てる名前である |
| `judgeGhOwnerRepos` | 所有者のPRの読み取りを、リポジトリごとの判定に分ける |
| `judgeGhOwnerIssueRepos` | 所有者のIssueの読み取りを、リポジトリごとの判定に分ける |
| `judgeGhOwnerCoverage` | 所有者の全体を表で探してよいかを判定する |
| `requiredRepos` | 設定で明示したリポジトリのうち、その所有者のものの名前を返す |
| `usableTableRows` | 所有者の判定から、表の候補にしてよい行を(リポジトリ、番号)の順に集める |
| `effectiveGhSource` | 設定と収集の設定から、実際に使う読み取り元を決める |

読む処理は、1つのリポジトリの`gh_repos`の行、開いているPRの行、DBの`now()`を、1つの文で読む(`readGhRepoOpenPullRequests`)。
収集がリポジトリの行と`last_collected_at`を1つの文で書くので、別々の文で読むと、新しい時刻と古い行の組を読み、古い行を新しいと誤りうるためである。
照会の名前と行の名前は、どちらも小文字にして比べる。

閾値は、所有者がn人のとき`max(15分, (n+1)×5分)`である。
nは、トークンの無い所有者も数える。
順番制では、健全な所有者の段2の成功の間隔が最悪n×5分になる。
`last_collected_at`は観測を始めた時刻なので、読む時点の経過は、その間隔に書き込みの遅れが加わる。
そこで1周回の余裕を足す。
どの所有者の数でも、鮮度の監視の通知の閾値より短い。
閾値を超えたリポジトリは、その周回だけ記録を使わない。

閾値は、所有者の段2の対象が、その所有者の1周回で取り終えられる規模であることを前提にする。
対象がこれを超える所有者は、`last_attempted_at`の古い順に回るので、一部のリポジトリの間隔が閾値を超える。

鮮度は、次の表を上から当てて、最初に当たった行を採る。
比べる相手は、行を読んだ同じ文のDBの`now()`で、workerの時計とは比べない。
どの行にも当たらなければ、記録を使ってよい。

| 順 | 理由 | 条件 |
| --- | --- | --- |
| 1 | `no_record` | `gh_repos`に行が無い |
| 2 | `unusable` | 数値IDが無い、許可の外、一覧から消えた、またはarchive済み |
| 3 | `unusable` | 開いた行が1件以上あり、すべて使えない(`usable`が偽か、数値IDが違う) |
| 4 | `not_collected` | `last_collected_at`が空 |
| 5 | `in_future` | `last_collected_at`がDBの時刻より後 |
| 6 | `too_old` | DBの時刻との差が閾値を超える。ちょうどは使ってよい |

順3は、無効にされたまま書き直されていない行だけが残る状態を、PRが無いことと取り違えないための条件である。
一部の行だけが使えないときは、使える行だけを候補にする。
順5は、`last_collected_at`が書く前の時刻なので、正しく書かれていれば起きない。

`gh_collect_runs`の最新の実行(`verified`、`id_checked`)は読まない。
照合の不一致では、収集が配下の行を使用不可にする。
照合の一時的な失敗では、`last_collected_at`が進まず、閾値を過ぎて使わなくなる。

`poll_dependabot`は、記録を使わないリポジトリを、判断を止めて黙らせずに、その周回だけ検索で列挙する。
手順は[dependabotの更新の内部仕様](dependabot.md#表から読むとき)にある。

### 所有者の単位の読み取り

`watch_pr_conflicts`、`poll_issues`、`poll_prs`、`watch_pr_ci`は、探す範囲が所有者の全体なので、所有者の単位で読む。
所有者の`gh_repos`の全行、開いている行の全行、DBの`now()`を、1つの文で読む。
`watch_pr_conflicts`と`poll_prs`と`watch_pr_ci`はPRの行(`readGhOwnerOpenPullRequests`)を読む。
`poll_issues`はIssueの行(`readGhOwnerOpenIssues`)を読む。
所有者の全リポジトリを同じ文で読むので、リポジトリの間でも同じ時点の値になる。
行が保存する値の述語を通らなければ、その所有者の読み取りの失敗として扱い、通る行だけを残すことはしない。
通らない行は収集の書き込みの不具合を示し、同じ文で読んだほかの行も信用できないためである。

所有者の読み取りは、`gh_repos`の行ごとに`judgeGhRepoFreshness`を当て、鮮度が足りるリポジトリだけ使ってよい行を残す。
PRの行には`judgeGhOwnerRepos`、Issueの行には`judgeGhOwnerIssueRepos`を使う。
`gh_repos`に行が無いリポジトリの開いた行は、数値IDを確かめられないので使わない。

`judgeGhOwnerCoverage`は、次の表を上から当てて、所有者の全体を表で探してよいかを決める。
引数`required`は、設定で明示したリポジトリ(`factory_repo`と`repo_allowlist`の各項目)のうち、その所有者のものの名前である。
省くと、順2と順5の`required`の扱いは働かない。

| 順 | 条件 | 結果 |
| --- | --- | --- |
| 1 | `gh_repos`にその所有者の行が無い | `stale`(`no_record`) |
| 2 | `required`の名前のうち、`gh_repos`に行の無いものがある | `stale`(`no_record`) |
| 3 | 読む時点の`isRepoAllowed`が偽のリポジトリ | 判定から外す |
| 4 | archive済みのリポジトリ | 判定から外す |
| 5 | 一覧から消えた(`gone`が真でarchive済みでない)リポジトリ | `required`に入っていれば`stale`(`unusable`)、入っていなければ判定から外す |
| 6 | 残りに鮮度が`stale`のリポジトリがある | `stale`(名前の順で最初のものの理由) |
| 7 | 上のどれでもない | `fresh` |

- 順3は、記録の`allowed`でなく読む時点の設定で当てる。記録の`allowed`が偽でも、読む時点で許されるリポジトリは外さず、`unusable`で`stale`にする。設定を広げた直後に、収集が`allowed`を書き直すまで、行の無いリポジトリを見落とさないためである。
- 順4で外さないと、archive済みのリポジトリを1つ持つ所有者が毎周回検索に戻り、表を読む意味が無くなる。archive済みのリポジトリは読み取り専用で、`required`に入っていても外す。
- 順5で外さないと、消したリポジトリを1つ持つ所有者が毎周回検索に戻る。`required`に入っているリポジトリが`stale`になるのは、表で使えないまま所有者を`fresh`にすると、検索なら見つけるものを黙って取りこぼすためである。
- `required`を渡すのは、リポジトリ単位の戻し先を持たない`poll_issues`と`poll_prs`と`watch_pr_ci`である。`watch_pr_conflicts`は、明示されたリポジトリをREST一覧で列挙できるので渡さない。
- 明示したリポジトリの名前(`requiredRepos`)と、表の候補にしてよい行の絞り込み(`usableTableRows`)は、`gh_collect_read.ts`に置き、この3つの処理が共有する。
- 所有者の最新の実行の`verified`は、ここでも読まない。

`watch_pr_conflicts`は、`stale`の所有者を検索に戻す。
PRの列挙は別の判定で、鮮度が足りるリポジトリは、所有者が検索に戻った周回でも表から列挙する。
鮮度の足りないリポジトリと、表に行の無いリポジトリは、REST一覧で列挙する。
リポジトリの引き当ては、所有者とリポジトリの名前を小文字にして行う。
設定や検索から来る綴りは大文字を含みうるが、表の名前は小文字だけである。

表の行は候補を絞るだけに使う。
Factoryのブランチかと作者は、PRごとに読み直す`getPr`の応答で確かめ直す。
表の`mergeable`は読まない。競合の判定に要る`mergeable_state`を集めていないためである。

`poll_issues`は、`stale`の所有者を検索に戻し、`fresh`の所有者は、判定から外さなかったリポジトリの使ってよい行を候補にする。
外さないのは、読む時点で許され、archive済みでなく、一覧から消えていないリポジトリである。
リポジトリ単位の戻し先は無いので、戻し先は所有者の単位の検索だけである。
候補は、`getIssue`で読み直し、次の条件を満たすものだけを使う。

- 応答の`repository_url`のリポジトリと番号が、表の行と一致する。一致しなければ失敗として記録し、その候補を外す。
- Issueが開いている。
- トリガーラベルが付いている。外れていれば、付与者の確認に進まず外す。外れたラベルの付与者を読むと、許可されない人が外した後に偽の拒否を残すためである。

外した候補は失敗にせず、件数だけを結果に載せる。
作業項目のownerとrepoは、`getIssue`の応答の綴りで作る。検索が返す綴りと同じにするためである。
稼働中の作業項目を引く鍵は、大文字小文字を区別しない。

`poll_prs`も、`stale`の所有者を検索に戻す。
`fresh`の所有者は、`poll_issues`と同じ条件で絞ったリポジトリの使ってよい行を分類する(`classifyPollPrRow`)。
分類は、検索の4本のどれかに当たるかで決める。
4本は、PATのアカウントへの依頼、assignee、レビューのラベル、修正のラベルである。
依頼とassigneeは、`getViewer`が返すPATのアカウントの数値IDで比べる。

| 分類 | 条件 | 扱い |
| --- | --- | --- |
| 対象 | ラベルが真、またはPATのアカウントへの依頼かassigneeがある | 候補にする |
| チーム | チームへの依頼が真か不明、または直接の依頼先が不明 | 所有者を検索に戻す |
| 不明 | ラベルかassigneeが不明 | 候補にしてRESTで確かめる |
| 対象外 | 上のどれでもない | 読まない |

チームへの依頼は、表ではPATのアカウントが属するチームかを決められない。
検索の依頼の条件は、PATのアカウントが属するチームへの依頼も返す。
そこで、分類が「チーム」の行を1件でも持つ所有者は、候補を表から取らず、発見を検索に戻して4本をすべて送る。
その所有者の表の候補は、`getPr`と`getIssue`を呼ばずに捨てる。
検索と表の候補を同じ所有者で混ぜないためである。
下書きとforkのPRは絞らない。検索も絞らず、判定が`getPr`の値で扱う。

表の候補は、`getPr`と`getIssue`で読み直し、次の条件を上から当てる。
読み直しはPRを1件ずつ順に行い、1件の中の2本だけを並列にする。GitHubへの同時の要求を増やさないためである。

- 応答のリポジトリと番号が、表の行と一致する。一致しなければ失敗として記録し、その候補を外す。
- PRが開いている。閉じていれば失敗にせず外す。
- レビューか修正のラベル、またはPATのアカウントのassigneeがあれば、候補にする。
- `requested_reviewers`を読めなければ、外さずに失敗として記録する。外すと、依頼で起きるはずのレビューが黙って止まるためである。
- PATのアカウントへの依頼があれば、候補にする。ほかは失敗にせず外す。

候補の項目はRESTの綴りと題で作る。
候補にした後は、検索の経路と同じく`buildPrCandidate`が`getPr`と`getIssue`を読み直す。表の候補ごとにRESTの読み取りが2回増える。
追跡中のPRの経路は変えない。表で外した候補が追跡中なら、その経路が候補にする。

`watch_pr_ci`は、許可された人のPRの候補を、範囲ごとに表で探す。
範囲は、照合を通った所有者と、その中に所有者が無い`factory_repo`のリポジトリである。
FactoryのPRは作業項目から引くので、表は人のPRの発見にだけ使う。
所有者の範囲は`poll_prs`と同じ`required`つきの判定で、`stale`なら範囲の全体を検索に戻す。
リポジトリ単位の戻し先は無いので、戻し先は範囲の単位の検索だけである。
`fresh`の所有者は、判定から外さなかったリポジトリの使ってよい行から、`humanPrCandidatesFromRows`が候補を作る。
候補は、開いていて下書きでない行のうち、次のどちらかである。

- 作者の種別が`User`で、ログイン名が許可された作者に入る行。
- 作者が不明の行。候補を広げる側に扱い、候補の並びの末尾に回す。

forkとFactoryの形のブランチでは絞らない。検索も絞らず、読み直した値で除くためである。
照合を通った所有者に無い`factory_repo`は、リポジトリの範囲にする。
この範囲は、1つのリポジトリの読み取り(`readGhRepoOpenPullRequests`)と`judgeGhRepoFreshness`で判定する。
`owners`に無い所有者の`factory_repo`は収集が集めないので、毎周回`no_record`で検索に戻る。

表の候補は、検索の候補と同じく`getPrWithoutWait`で読み直す。
作者、fork、ブランチは読み直した値で確かめ、記録するheadも読み直したheadである。
表の候補にだけ、次の2つを足す。

- 応答のリポジトリが候補と違えば、記録せず、警告のログに残す。名前の付け替えや移管の途中で、別のリポジトリのPRを記録しないためである。
- 404か403なら、権限の不足の通知を作らず、警告のログに残す。読み取りトークンに見えて書き込みのPATに見えないリポジトリは、検索の経路では候補に出ず、通知も作らないためである。

## 掃除

`cleanup_db`が、`gh_collect_runs`のうち、`started_at`が保持期間(`retention_logs_days`)以前の行を消す。
所有者ごとに、直近の成功(`ok`が真で`finished_at`のある最新の行)と、直近の実行(`finished_at`のある最新の行)は、古くても残す。
`finished_at`が空の新しい行があっても、`finished_at`のある最新の行を残す。
件数はログだけに載せる。

詳細の表からは、閉じたPRと一覧から外れたIssueのうち、`written_at`が同じ保持期間以前の行を消す。
開いている行は、古くても、使用不可の行を含めて消さない。
件数はログだけに載せる。

`gh_repos`は消さない。`gone`の行も残る。

## 鮮度の監視

`self_update`(2分ごと)が、`finally`の最後の文で`checkGhCollectFreshness`(`lib/gh_collect_freshness.ts`)を呼ぶ。
確認は、所有者ごとに収集が続けて成功しているかを判定する。
defaultのworkerで動かす。収集は定期ジョブ用のworkerで動くので、同じworkerで確かめると、そのworkerが止まったときに収集の停止にも気づけないためである。
確認は全体を30秒で区切り、例外を投げない。
記録を読めないとき、時間内に終わらないときは`unknown`を返し、noticeを足さず、解決もしない。
ログと戻り値には、固定の語と件数だけを載せる。

段2の所有者単位の失敗(行15から19)は`ok`が偽なので、最後の成功を進めない。
所有者単位の段2の失敗は、その所有者のPRとIssueを下流が使えないことで、段1の失敗と同じ結果になるためである。
リポジトリ単位の失敗と打ち切りは`ok`を変えないので、この監視には届かない。

### 基準と閾値

最後の成功は、`ok`と`verified`が真で、`finished_at`のある行の、最大の`finished_at`である。
基準の時刻は、最後の成功と、監視の開始時刻の遅い方である。
監視の開始時刻は、監視がその所有者を有効の状態で初めて見た時刻である。
`self_update`のstateのキー`gh_collect_watch_since_ms`に、所有者(小文字)ごとのエポックミリ秒で持つ。
長く無効にした後と、`owners`に足し直した後は、古い成功から閾値を超えたと誤って判定しないためである。

stateの読み書きは次のとおりにする。

- 読むときは、キーが`isGitHubName`を通る小文字の名前で、値が有限で0以上の数のものだけを`Map`に移す。`GITHUB_NAME_PATTERN`は`constructor`などの名前を通すので、素のオブジェクトの添字では引かない。
- 保存した値が今より後(時計が戻った)なら、今に直す。
- 有効の間は、`owners`の所有者の値だけを残し、変わったときだけ書く。無効の間は、キーを消す。
- stateは全体を置き換えるので、読んだ値のほかのキー(`console_worker_unknown_since_ms`)を残す。
- 読めなかった回は書かない。今の時刻で書くと、監視の開始時刻が今に戻るためである。
  所有者の最古の`started_at`(`first_started_at`)を代わりに使う。それも無い所有者は、基準を決められないので、足さず、解決もしない。
- 新しい値を書けなかった回は、その回に今を入れた所有者に`first_started_at`を使う。今のままにすると、書けない間は基準が毎回今になり、通知が出なくなるためである。

通知の閾値は`max(25分, (2n + 1) × 5分)`である(`staleNotifyThresholdMs`)。nは`owners`の所有者の数で、トークンの無い所有者も数える。
自分の番の周回で1回失敗したときの成功の間隔が`2n × 5分`になるので、その間隔に1周回を足す。
順番制を変えるときは、この式を見直す。
下限の25分は、一時的な失敗と定期ジョブ用のworkerの待ちを、所有者の数によらず黙らせる。

### 判定の順

先に原因を求める。
最新の実行が無い、実行の終わりが16分(`GH_COLLECT_NOT_RUNNING_AFTER_MS`)より前、または`error_code`が空のときは、収集が動いていない(`not_running`)。
それ以外は、最新の実行の`error_code`である。
16分は、定期ジョブ用のworkerの待ちの上限11分に、収集の1周回の5分を足した値である。
`periodic_worker.ts`をimportせずに写し、テストが`PERIODIC_JOB_WAIT_SECONDS`との関係を固定する。

所有者ごとに、次の表を上から当てて、最初に当たった行を採る。`T`は通知の閾値である。

| 順 | 条件 | 結果 | noticeの操作 |
| --- | --- | --- | --- |
| 1 | 原因が`not_running`でなく、最新の実行が`no_token`で、最後の成功が無い | `skip` | 解決する |
| 2 | 最後の成功があり、経過が`T`未満 | `recovered` | 解決する |
| 3 | 基準の時刻を決められない | `unknown` | 何もしない |
| 4 | 基準の時刻からの経過が`T`未満 | `grace` | 何もしない |
| 5 | 最新の行が実行中で、`started_at`が150秒以内 | `running` | 何もしない |
| 6 | 原因が`not_running`でなく、`next_allowed_at`に10分を足した時刻より前で、基準の時刻から60分未満 | `waiting` | 何もしない |
| 7 | 原因が`http_5xx`か`timeout`で、基準の時刻から60分未満 | `waiting` | 何もしない |
| 8 | 上のどれでもない | `stale` | 足す |

- 解決は行1と行2だけで行う。基準の時刻が新しいだけの`grace`は、回復の証拠が無いので解決しない。解決すると、閾値の後に出し直してDiscordに二度送る。
- 原因を先に求めるのは、収集が止まると最新の実行が古いまま残り、行1と行6が永久に黙るためである。行7は原因そのものが条件なので、`not_running`のときは当たらない。
- 行5は記録の新しさに頼らないので、原因が`not_running`でも当てる。150秒は、`collect_github`の`timeout`120秒に30秒を足した値である。
- 行6は`error_code`でなく`next_allowed_at`の有無で判定する。引き継ぎの行(「実行の行の結果」の行4)にだけ値が入るためである。
- `owner_mismatch`は、設定にIDがあるかによらず`stale`として知らせる。
  設定にIDがあるときは、収集の`owner_id_mismatch`と二重になるが、受け入れる。

### 通知と抑止

noticeの種類は`github_collect_stale`で、本文は`<所有者>:`と空白と固定の文である。
原因や時刻を含めないので、原因が変わっても重ねて記録しない。
Discordには、noticeを新しく挿入できたときだけ送る。
Discordの説明には、閾値、最後の成功(JST)、最新の実行の原因が載る。

足さない条件は、その回に定期ジョブ用のworkerの停止(`stalled`)を検知したときだけである。
停止は`periodic_worker_missing`が知らせる。
次の2つは、二重を受け入れて抑止しない。
`schedule_failing`による抑止は、noticeの作成時刻と基準の時刻の関係を保ち続ける必要があり、崩れると黙るためである。
`owner_id_mismatch`による抑止は、人が通知を解決した後に、最新の実行が`owner_mismatch`のまま永久に黙るためである。

解決は、種類を`github_collect_stale`に固定して行う。
所有者ごとの解決は、本文の先頭の`<所有者>:`と空白で行う。末尾の区切りまで含めるので、`foo`が`foobar`を解決しない。
無効のときは、種類のnoticeをすべて解決する。
`owners`から外れた所有者は、未解決の本文の先頭から所有者を取り出し、`isGitHubName`を通り、`owners`に無ければ解決する。
形の合わない本文は解決せず、件数だけを警告に残す。

## 既知の限界

- `repo_allowlist`が空のとき、見えないリポジトリを検出できない。
- 締め切りやGitHubの失敗が続くと、リポジトリの記録が前回のまま凍る。
- 「All repositories」のトークンは、集める範囲より広く読める。
- loginに`_`を含む所有者は集めない。
- 先頭が`.`のリポジトリ名(`.github`など)は集めない。共通の名前の述語を緩めると、シェルとパスの守りに及ぶためである。
- 監視が無効の間を観測しないと、古いstateのキーと古い成功が残る。有効に戻した直後に`self_update`が収集より先に走ると、誤報が1回出うる。収集が次に成功すると、自動で解決される。
- 所有者を足して閾値が延びると、noticeのある所有者の最後の成功が新しい閾値の内に入り、解決される。止まったままなら、新しい閾値を過ぎると足し直され、Discordが1回余分に届く。
- 一時的でない失敗が続いた後に定期ジョブ用のworkerが止まると、`periodic_worker_missing`より先に`github_collect_stale`が立ち、1回だけ重なる。
- 収集が止まると、所有者の数だけnoticeとDiscordが届く。
- しきい値を変えた反映の時点で待ちが続いていると、`periodic_worker_missing`のnoticeと通知が1回だけ二重になる。回復すれば、先頭一致で両方が解決される。
- `repo_allowlist`にあるforkは、一覧から除くので`not_visible`になる。
- 権限名とGraphQLの項目の対応は、反映後の実ジョブで確かめる。
- 所有者がn人のとき、取り終えられない所有者が先頭でない位置に来る周回では、その所有者が後ろの所有者の時間を使う。
  そのため、後ろの所有者の成功の間隔が、最悪でn×5分まで伸びる。
  鮮度の判断は、最悪の間隔をn×5分として扱う。
- リポジトリ単位の停止は通知しない。
  特定のリポジトリが続けて失敗するか、打ち切られるか、回り切らないと、そのリポジトリの`last_collected_at`が古くなる。
  下流は閾値で判断を止める。
  `poll_dependabot`は、そのリポジトリを検索に戻して処理を続ける。
  `watch_pr_conflicts`は、所有者の全体を検索に戻し、そのリポジトリのPRをREST一覧で列挙する。
  `poll_issues`と`poll_prs`と`watch_pr_ci`は、所有者の全体を検索に戻す。
  所有者の`ok`は真のままなので、鮮度の監視の通知は出ない。
  確かめるには、`gh_repos`の`detail_failed`と`truncated`と`last_attempted_at`、実行の行の`detail_incomplete`を見る。
- 収集が集めないリポジトリは、`gh_repos`に使える行が無いので、`poll_dependabot`が毎周回検索に戻す。
  `watch_pr_conflicts`は、設定か作業項目か競合の行で明示されたリポジトリをREST一覧で列挙する。
  どれにも入らず検索だけが見つけていたリポジトリは、表では見つからない。
  `owners`に無い所有者の`factory_repo`、`repo_allowlist`にあるfork、先頭が`.`のリポジトリ名、loginに`_`を含む所有者のリポジトリ、archive済みのリポジトリ、改名か移管をした古い名前が当たる。
  改名か移管をした新しい名前は、人が設定を直すまで対象に入らない。
  `owners`に無い所有者の`factory_repo`は、`watch_pr_ci`が毎周回その範囲を検索に戻す。結果の`human_fallback_reasons`の`no_record`で見える。
- `watch_pr_conflicts`が表から列挙するとき、表に載る前のPRと、表の`is_draft`が古いPRは、次にそのリポジトリを取り終えるまで候補にならない。
  遅れは、普段は監視の1周回、最大で閾値と監視の周期(5分)の和である。
  取り直しが止まれば、閾値を過ぎた時点でそのリポジトリはREST一覧に戻る。
  競合の通知と、直す作業項目の起動の判断も同じだけ遅れる。競合が解けたことと、PRが閉じたことの検知は遅れない。
- `repo_allowlist`が空の構成では、`watch_pr_conflicts`は`gh_repos`に行の無いリポジトリのPRを、表では見つけない。
  所有者のfork、直近の一覧より後に作られたリポジトリ、読み取りトークンに見えないリポジトリが当たる。
  `repo_allowlist`が空でないとき、対象のリポジトリはすべて設定で明示されるので、REST一覧で列挙される。
- `poll_issues`が表から見つけるとき、表に載る前のIssueと、トリガーラベルを付けた直後のIssueは、次にそのリポジトリを取り終えるまで候補にならない。
  ラベルを付けてから着手までの遅れは、普段は収集の周期とポーリングの周期の和に近く、数分から10分ほどになる。
  取り直しが止まれば、閾値を過ぎた時点で所有者は検索に戻る。
- `repo_allowlist`が空の構成では、`poll_issues`は`gh_repos`に行の無いリポジトリのIssueを、表では見つけない。
  `repo_allowlist`が空でないときは、明示したリポジトリが`gh_repos`に無いか、表で使えない場合に所有者の全体が検索に戻るので、見落とさない。
- archive済みのリポジトリのIssueは、`poll_issues`が表では見つけない。
  archive済みのリポジトリは読み取り専用で、ラベルを外せず、作業項目も起動できない。
- `poll_prs`が表から見つけるとき、表に載る前のPRと、ラベル、レビューの依頼、assigneeを付けた直後のPRは、次にそのリポジトリを取り終えるまで候補にならない。
  遅れは、普段は収集の周期とポーリングの周期の和に近く、数分から10分ほどになる。
  取り直しが止まれば、閾値を過ぎた時点で所有者は検索に戻る。
- `watch_pr_ci`が表から見つけるとき、表に載る前のPRと、下書きから戻したPRは、次にそのリポジトリを取り終えるまで候補にならない。
  遅れは、普段は4分から9分ほど、最大で閾値と監視の周期(5分)の和である。
  取り直しが止まれば、閾値を過ぎた時点で範囲は検索に戻る。
  記録済みのPRに新しいheadをpushしたときは、表の行が開いたまま残るので、候補が60件以下なら遅れない。
  候補が60件を超えると、読む順は表の収集の時点の更新の時刻で決まり、pushした直後のPRが上位に上がらない。
  新しいheadの記録と、その失敗の通知は、次の収集まで遅れうる。
  記録済みの人の行の判定と、PRが閉じたことの検知は遅れない。
- `watch_pr_ci`が表から見つけるとき、表には検索の「範囲と作者ごとに100件」の上限が無い。
  読む数と記録する数の上限(1回に60件と20件)は、検索の経路と同じく効く。
- 開いたPRにチームへのレビューの依頼が1件でも付いていると、`poll_prs`はその所有者を毎周回検索に戻す。
  CODEOWNERSでチームへの依頼が自動で付く組織では、ほぼ常に戻る。
  戻した回数は、結果の`fallback_reasons`の`team_review`で見える。
- `repo_allowlist`が空の構成では、`poll_prs`は`gh_repos`に行の無いリポジトリのPRを、表では見つけない。
  archive済みのリポジトリのPRも、表では見つけない。
- `repo_allowlist`が空の構成では、`watch_pr_ci`も`gh_repos`に行の無いリポジトリの人のPRを、表では見つけない。
  `repo_allowlist`が空でないときは、明示したリポジトリを表で使えない場合に所有者の範囲が検索に戻るので、見落とさない。
  archive済みのリポジトリの人のPRも、表では見つけない。archive済みのリポジトリではActionsが動かず、新しい失敗は出ない。
- `review_label`と`fix_label`を変えた直後は、収集が各リポジトリを取り直すまで、表のラベルの真偽は古い名前で答える。
  古い名前で真の行は、`poll_prs`のRESTの確かめ直しで外れる。新しい名前のラベルのPRは、取り直しの後に載る。
- `trigger_label`を変えた直後は、収集が各リポジトリを取り直すまで、表は古い名前で答える。
  古い名前で載っている行は、`poll_issues`のRESTの確かめ直しで外れる。新しい名前のIssueは、取り直しの後に載る。
- 収集は、トリガーラベルでIssueを絞るとき、ラベル名の大小文字を区別しないGitHubの挙動に頼る。
  この挙動が変わると、`trigger_label`の綴りと違うラベルのIssueが表に載らず、`poll_issues`が`fresh`のまま見落とす。
  実行中には検知できないので、切り替えの前に[運用](../operations.md#issueの発見の元を表に切り替える)の手順で確かめる。
- 読み取りトークンに見えるが、書き込みのPATに見えないリポジトリのIssueは、`poll_issues`の`getIssue`が404になる。
  `confirm_table_issue:`の失敗が毎周回残る。
- 読み取りトークンに見えるが、書き込みのPATに見えないリポジトリの対象のPRも、同じ失敗を残す。
  `poll_prs`の`getPr`が404になり、`confirm_table_pr:`の失敗が毎周回残る。
  検索の経路では、書き込みのPATがそのリポジトリを返さないので、何も残らない。
- 読み取りトークンに見えるが、書き込みのPATに見えないリポジトリの人のPRは、`watch_pr_ci`の`getPrWithoutWait`が404か403になる。
  表の候補の404と403は通知を作らず、警告のログだけが毎周回残る。検索の経路では候補に出ないので、何も残らない。
- 表の古い対象の行が、チームへの依頼の戻しを覆い隠すことがある。
  assigneeを外された後の行は、次の収集まで対象のままなので、`poll_prs`はその所有者を検索に戻さない。
  検索なら、チーム経由の依頼で拾っていたPRは、次の収集までは見つからない。
  遅れの上限は、鮮度の閾値である。
- 開いたPRが90件を超えるリポジトリは、打ち切りが続いて`last_collected_at`が進まない。公開リポジトリでは、forkからPRを91件開けば、誰でもそのリポジトリを打ち切りに留められる。下流は閾値で判断を止める側に倒れ、誤った操作には進まないので、安全は損なわれない。
- 段1が60秒で取り切れない所有者(約600リポジトリ以上)は、段2が有効な間、先頭を担当しても段1が`deadline`(`stage=list`)になり続ける。リポジトリを減らすか、段2を止めて下限を10秒に戻す。
- 段1の重い所有者がいる周回では、先頭でない所有者は段1が`deadline`で終わり、段2に入れない。
  先頭を担当する周回(n周回に1回)は、段1と段2の両方を回せる。
- 段2の時間が短い周回では、全員で2束しか送れず、先頭の所有者が使い切れば、2人目からは行19になる。順番制で順が回るので、鮮度の判断の最悪の間隔の内に収まる。
- 分割の上限に達した周回の束は、リポジトリがすべて失敗になり、次の周回から疑いとして1件ずつ送られる。回復が遅い代わりに、常に失敗するリポジトリで健全なリポジトリが凍ることを防ぐ。
- ページの間に取得済みのPRが1件閉じ、新しいPRが1件開くと、件数が合って取り終えたとみなされる。新しいPRの行が無いことと、閉じたPRの行が`open`で残ることが、次の周回まで続く。

- `last_collected_at`は、workerの時計で書く。workerとDBを別のホストに分けるときは、時計の前提を見直す。
