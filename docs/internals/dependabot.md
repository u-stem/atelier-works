# dependabotの更新の内部仕様

dependabotが開いた依存の更新PRを、Factoryがどう選び、どう評価し、どの作業項目の状態で終えるかを定める仕様である。
`poll_dependabot`、フロー`f/factory/dependabot`とそのステップ、`lib/dependabot_*.ts`を変更する人が読む。
自動でマージする条件、安全策、残るリスクは[この文書の「dependabotの更新の自動マージ」](#dependabotの更新の自動マージ)に、有効にする手順は[運用](../operations/features.md#dependabotの更新を設定する)に書く。

## 全体の流れ

処理は、PRを選ぶスケジュールと、1件のPRを処理するフローに分かれる。

| 部品 | 役割 |
| --- | --- |
| `poll_dependabot` | 10分ごとにPRを探し、フローと同じ収集とゲートで評価する。通ったPRだけ作業項目を作り、フローを起動する |
| `dependabot_prepare` | 事実を集め直してゲートを評価し、headのshaの作業ツリーに依存を隔離してインストールする |
| `dependabot_assess` | Claudeに影響を調べさせる。ツールは読み取りだけで、コマンドは実行させない。対象が複数でも1回の実行で、全パッケージを調べる |
| `dependabot_finish` | 結論を出し、マージ、所見の投稿、人に回すのどれかを行って作業項目を終える。対象が2つ以上なら、マージの直前に`dependabot_group_enabled`を読み直し、偽か読めなければ、マージせずに人に回す |

`dependabot_enabled`が偽の間は、スケジュールはGitHubとDBのどちらにも触れずに終わる。
起動の後で無効になったときは、フローの各ステップが作業項目を取り消し、GitHubへは書かない。
`dependabot_merge_enabled`が偽の間は試運転で、終了のステップはマージの結論でもマージせず、人に回す。
`dependabot_group_enabled`が偽の間は、変わったパッケージが2つ以上のPRを人に回す。
マージの保留があるか、保留を読めないリポジトリは、取得がPRを待たせる。
終了のステップは、同じ場合に自動マージをやめて人に渡す。
仕様は[保留の内部仕様](holds.md#dependabotの自動マージ)にある。

## PRの選び方

対象のリポジトリは、`watch_main_ci`と同じ規則(`listMainCiTargets`)で決める。

- `factory_repo`は、常に対象にする。
- `dependabot_other_repos`に挙げたリポジトリを足せる。
  `repo_allowlist`の照合を通ったオーナーのリポジトリだけを通す。
- `dependabot_other_repos`が空なら、`factory_repo`だけを見る。
  オーナーの全リポジトリは見ない。
  `repo_allowlist`にだけ載せたリポジトリは見ない。

自動でマージする対象を、明示したリポジトリに限るためである。
`poll_dependabot`は、対象のリポジトリごとに、次の条件をすべて満たすPRを候補にする。

- dependabotのアプリが開いた。
- 開いていて、draftでない。
- baseが`main`である。

候補の列挙は候補を絞るだけなので、PRを読み直して、リポジトリの名前、開いていること、draftでないこと、baseが`main`であること、作者が`dependabot[bot]`であることを確かめる。

### 候補の列挙の元

候補は、収集の表か、RESTの開いているPRの一覧から列挙する。
元は、収集の設定と、リポジトリごとの記録で決まる。

| 条件 | 実効の元 |
| --- | --- |
| `gh_collect_enabled`と`gh_collect_detail_enabled`がどちらも真で、リポジトリの記録を使える | 収集の表 |
| 収集の2つの設定が真で、リポジトリの記録を使えない | その周回だけ、RESTの一覧 |
| 収集の2つの設定のどちらかが偽 | 周回全体がRESTの一覧 |

収集のどちらかを止めると、記録の時刻が進まず、表を使えないためである。
元を選ぶ設定は無い。
一覧は検索の枠でなく、REST全体の枠を使う。
収集が動いていても、収集が集めないリポジトリ(`owners`に無い所有者の`factory_repo`、fork、先頭が`.`のリポジトリ名など)は、毎周回一覧で読む。

### 表から読むとき

対象のリポジトリごとに、`gh_repos`の行、開いているPRの行、DBの時刻を1つの文で読み、記録を使ってよい鮮度かを判定する(判定の規則は[GitHubの収集の内部仕様](github-collect.md#読む側の判定))。
鮮度が足りれば、使ってよい行から次の条件で候補を選ぶ。

- draftでない。
- baseが`main`である。
  baseが不明の行も候補にする。
- 作者がdependabotのアプリである。
  収集は種別が`Bot`の`login`に`[bot]`を付けずに保存するので、種別が`Bot`のときに付けて比べる。
  作者が不明の行も候補にする。

不明の行を候補にするのは、候補を広げる側に倒し、PRごとの読み直しで確かめるためである。
forkのPRは絞らない。
ゲートが人に回すためである。
作者の項目が組織の権限で拒否され続けると、リポジトリの開いたPRがすべて候補になり、読み直しが増える。
1リポジトリで最大90件に収まる。

表でarchive済みと分かり、記録が鮮度の閾値の内にあるリポジトリは、マージできない。
このリポジトリは、表と一覧のどちらも読まず、戻しに数えない。
古い記録のarchiveの印は、解除された後も残りうるので信用しない。
次の場合は、archive済みでも一覧で読む。
収集の無効(`collection_disabled`)と、表の読み取りの失敗(`read_failed`)と、古い記録である。
次のリポジトリは、その周回だけRESTの一覧で候補を列挙する。
一覧に戻す理由は、結果の`fallback_reasons`のキーに出る。

| 理由 | 意味 |
| --- | --- |
| `collection_disabled` | 収集の2つの設定のどちらかが偽で、表を読まない |
| `no_record` | `gh_repos`に行が無い |
| `unusable` | 数値IDが無い、許可の外、一覧から消えた、または開いた行がすべて使えない |
| `not_collected` | 一度も詳細を取り終えていない |
| `in_future` | 最後に取り終えた時刻がDBの時刻より後 |
| `too_old` | 最後に取り終えた時刻から閾値を超えた |
| `read_failed` | 表の読み取りが失敗した。失敗は記録する |

一覧に戻すのは、リポジトリごとに1周回で1回までである。
記録を使えないことは失敗に数えない。
一覧から消えたリポジトリも一覧で読む。
削除されたリポジトリは、404が一覧の失敗として記録される。
改名か移管をしたリポジトリは、`gh`が301を辿り、新しい名前のPRが返る。
候補の名前は要求した名前なので、PRの読み直しで名前の照合に当たり、`repoMismatch`で飛ばす。
マージを誤る方向には進まない。
既知の限界として、この場合は失敗の記録を残さず、人にも回らない。
収集が集めないリポジトリは、毎周回一覧に戻る。
一覧の読み取りが失敗したリポジトリのPRの待ちの記録は、次の周回へ引き継ぐ。
鮮度が足りるリポジトリで、表に行が無いPRの待ちの記録は捨てる。
閉じたと判断するのではなく、記録を保つ根拠が無いためである。

### 一覧から読むとき

一覧は、`GET /repos/{owner}/{repo}/pulls?state=open`を、全ページ読む。
ページの上限は10(1000件)で、超えたときは一部だけを使わず、そのリポジトリの失敗として記録する。
一部だけでは、読まなかったPRを開いていないと取り違えうるためである。
一覧の1件は、表の行と同じ形にそろえ、表と同じ規則で候補にする。

- 作者の`login`は、アプリなら末尾に`[bot]`が付いて返る。
  付いていれば外して種別を`Bot`にし、表の形に合わせる。
  付いていなければ種別を`User`にする。
- 作者が無い件と、baseが応答に無い件は、不明として候補に残す。
  作成の時刻が無い件は、並びの最後に置く。
- headの処理済みと待ちでは、一覧の段階で除かない。
  待ちの記録を保つためで、処理済みの判定は読み直しの後に行う。

候補の名前は、一覧の値でなく、対象に挙げた名前から作る。

### PRの読み直し

候補のPRは、RESTで読み直す。
判断に使う値は、操作の直前にRESTで読んだ値にする。
表の値は、候補の列挙と並びにだけ使う。

- リポジトリの名前は、GitHubが返したbaseのリポジトリの名前を使う。
  表の名前は小文字で、作業項目の照合は大小文字を区別するので、小文字のままだと処理済みの判定が外れ、同じheadを二度処理しうる。
  返った名前が候補と大小文字を除いて違うPRは、改名か移管の疑いがあるので飛ばす。
- 保持期間の判定と、待ちの上限の起点には、RESTで読んだ作成の時刻を使う。
  表の値が偽られても、保持期間の安全策を外せないようにするためである。
  候補の作成の時刻は並びにだけ使う。
  作成の時刻が読めないPRは、そのPRの失敗として記録する。

### 選ばないPR

次のPRは選ばず、何もしない。

| 条件 | 理由 |
| --- | --- |
| baseのリポジトリの名前が候補と違う | 改名か移管の疑いがある。許可していない名前のまま自動でマージしない |
| 同じPRに、終端でない`pr_review`か`pr_fix`がある | 人が頼んだレビューと修正を先にする |
| 同じPRに、終端でない`dependabot`の作業項目がある | フローが動いている |
| 同じheadを処理済みである(`hasDependabotItemForHead`) | マージした後と人に回した後に、同じheadを処理し直さない |
| 待っていて、次に確かめる時刻の前である | 待つ間に、毎回registryの大きな応答やGitHubを読み直さない |
| 同じheadで、フローが待ちで止まってから1時間たっていない | レート制限などの間に、周回ごとにフローを起動しない |

フロー自身が取り消した行は、処理済みに数えない。
対象の4つの注記は「作業項目の状態」の表にある。
それ以外の終端の行と、失敗した行は処理済みに数える。
取り消した理由が分からないheadと、マージや投稿の後に失敗しうるheadを、自動で処理し直さないためである。

## 対象の導出

収集は、ロックファイルの差分から更新の対象(パッケージの名前、前後の版、更新の幅)を導く。
導出は次の順に行い、先の段で止まれば後の段は見ない。

1. 変わったエントリの名前の集合を数える。
   0個は`no package changed in the lockfiles`で人に回す。
2. 2個以上で`dependabot_group_enabled`が偽なら、`more than one package changed`で人に回す。
3. 2個以上でフラグが真かつ3個(`MAX_GROUP_TARGETS`)を超えれば、`too many packages changed`で人に回す。
4. 更新の前後で名前が変わるエントリは、人に回す。
5. パッケージごとに、トップレベルのエントリ、版の一致、更新の幅を導く。

対象は名前の辞書順に並べる。
フラグの値は、導出、ゲート、終了のステップのマージの直前の3か所で確かめる。
registryの事実は、対象ごとに順に読む。
全体の更新の幅は、最も重い種別にする。

## 更新を許すファイル

更新を許すファイルは、`dependabot_support.ts`の`MANIFEST_LOCKFILES`が出典である。
マニフェストと、同じディレクトリのロックファイルを組にした表で、今はルートと`console/`の2組になる。
ロックファイルとして読むパス(`LOCKFILE_PATHS`)は、この表から作る。

許可するパス(`ALLOWED_PATHS`)は、表から作らず、リテラルで持つ。
表だけ、許可だけを変えると、テストが落ちる。
許可の拡大が、表への行の追加だけでは通らないようにするためである。

表はbunの解析器に渡す前提で、テストが、すべてのロックファイルの名前が`bun.lock`であることを固定する。
別の言語の行を足すときは、表と許可に加えて、次のbun専用の箇所を見直す。

- `dependabot_support.ts`の`fileProblem`と`integrityProblem`
- `dependabot_collect.ts`の`deriveTargets`
- `dependabot_flow_support.ts`の`isFileNamed`
- `dependabot_prepare.ts`の`installedPackageDirsFor`と`LOCKFILE_NAME`

これらは保護パスのファイルなので、行の追加は人のレビューを通る。

## リポジトリの扱い

リポジトリの扱いは、`resolveRepoPolicy`が3つに分ける。

| 扱い | 条件 | 必須チェック | 準備と終了 |
| --- | --- | --- | --- |
| `primary` | `factory_repo`。`dependabot_other_repos`に載せても変わらない | 固定の`REQUIRED_CHECKS`(10件)。GitHubを読まない | 今までどおり |
| `other` | `dependabot_other_repos`の項目と、大文字小文字を除いて完全に一致する | baseのブランチに効くルールセットの必須チェック | cloneもインストールもせずに人に回す |
| `off` | 上のどれでもない | なし | 収集が人に回す。pollは対象に入れない |

他のリポジトリの必須チェックは、設定に持たせない。
設定を書き換えて、必須チェックを空や短い一覧にしても、リポジトリ自身のルールより弱くならないようにするためである。
収集は、`GET repos/{owner}/{repo}/rules/branches/{branch}`の応答を、解釈せずに読む(`listBranchRules`)。
`requiredChecksFromRules`が、そこから必須チェックの名前を取り出す。
次の場合は、固定の文言で人に回す。
この理由にGitHub由来の値を載せない。
導出に成功した名前は、ゲートの理由に、切り詰めと区切りの除去を通して載る。

- 応答や規則の形が想定と違う。
- 名前が1〜100文字でない、前後に空白がある、制御文字を含む。
- GitHub Actions以外のAppに結んだ規則がある。
  ゲートは、GitHub Actionsから来たチェックだけを出揃ったと見なすため。
- 必須チェックが0件、または40件を超える。
- 読み取りが4xxで拒まれた。
  レート制限と5xxは待つ。
- PRのbaseのリポジトリの名前が、要求した名前と違う(移管)。

古典的なブランチ保護の必須チェックは読まない。
読むには管理の権限が要り、404が「保護なし」と「権限なし」を区別しないためである。
併用するリポジトリは、古典的な分が見えず、一覧がGitHubの規則より短くなりうる。
他のリポジトリは準備で人に回るので、マージには届かない。
準備と終了のステップが他のリポジトリを止める条件を外す前に、この点を決める(セキュリティの残るリスクを参照)。

許可するパス(`ALLOWED_PATHS`)は、リポジトリごとの設定にしない。
他のリポジトリがマージの経路に入らないので、設定しても効果が無く、許可はリテラルのまま表と一致させる。

## 評価と分岐

選んだPRは、フローの準備と同じ収集(`collectGateInput`)とゲート(`evaluateGateGroup`)で評価する。
ゲートは、対象ごとに単独の更新と同じ評価(`evaluateGate`)で判定し、結果を合成する。
共通の事実は1つの組み立てから作り、他の対象の名前と版を、変わってよいエントリとして評価に渡す。
対象が1つのときは、単独の更新と同じ結果と理由になる。

- 人に回す結果が1つでもあれば、人に回す。
  対象が2つ以上なら、理由の先頭にパッケージ名を付ける(`package`、名前、コロンの順)。
- 人に回す結果はなく、待つ結果のみなら、待つ。
  公開の日数を満たさない対象が複数なら、最も遅い公開日から次に確かめる時刻を決める。
- すべて通れば、通る。

結果ごとの扱いは次のとおりである。

| 結果 | 扱い |
| --- | --- |
| 通った | 作業項目を`picked`で作り、フローを起動する |
| 人に回す | 作業項目を`picked`で作り、すぐ人の対応待ちにして、1回だけ通知する |
| 待つ | 作業項目を作らない。次に確かめる時刻を決め、その時刻の後の周回で評価し直す |
| マージの保留がある、または保留を読めない | 作業項目を作らず、収集も影響調査もしない。待ちの記録は変えない。保留が解けるか読めるようになった後の周回で評価し直す |
| PRが閉じた | 何もしない |

評価の途中でheadが動いたときは、待ちとして扱う。
GitHubがマージできないと判定したPR(競合)も、待ちとして扱う。
dependabotがrebaseで直しうるので、同じリポジトリのほかの更新のたびに人へ知らせないためである。
ゲートはこの場合を種別で返し(`notMergeable`)、取得は理由の文字列で見分けない。
フローの準備は、同じ判定を人に回す。

### 影響調査の入力の切り詰め

準備のステップは、切り詰められた入力を確かめた入力に数えず、未確認にする。
単独の更新にも同じ規則を適用する。
切り詰めた部分に破壊的変更が残りうるためである。

- 変更履歴は、対象ごとのバイト数の上限で抜粋する。
  抜粋や無害化で切り詰めが起きたときは、`changelog`を未確認にする。
- マニフェストの差分とロックファイルの要約は、切り詰めの印が付いたとき、それぞれ未確認にする。
- 全パッケージの入力の合計が`MAX_PROMPT_CHARS`を超えたときは、影響調査を起動せず人に回す。

影響調査の結論は、出力に全対象の名前が揃わなければ、未確認として人に回す。
名前は、`evidence`、`supplyChainConcerns`、`unverified`の全体を対象に、名前に使える文字が前後に続かない形だけを数える。
`react`と`react-dom`のような、名前が重なる組を区別するためである。
この検査は網羅の補助で、防御には数えない。

### 待ちの記録と間引き

待ちになったheadは、スケジュールのstateに記録する。
記録は、初めて待ちを見た時刻、続けて待った回数、次に確かめる時刻である。
次に確かめる時刻までは、そのheadを評価しない。
headごとに記録するので、新しいheadは前のheadの待ちを引き継がない。

| 待ち | 次に確かめる時刻 |
| --- | --- |
| 公開の日数が足りない | 公開から日数がたつ時刻 |
| そのほか(チェックの未完了、マージできるかの計算中、競合など) | 1回目は次の周回、2回目は約30分後、3回目からは約60分後 |

処理を終えたPRと、候補から外れたPRの記録は消す。
失敗したPRと、レート制限で調べなかったPRの記録は、次の周回へ引き継ぐ。

### レート制限

PRの読み取りや、一覧で候補を列挙するリポジトリの一覧の読み取りが、GitHubのレート制限に当たったら、その周回の残りを調べない。
制限が解ける時刻をstateに残し、その時刻まで周回を飛ばす。
時刻が分からないときは、15分飛ばす。

### 待ちの上限

待ちの起点から、公開の日数(`dependabot_min_published_days`)に7日を足した時間を超えて待ちが続けば、人に回す。
必須のチェックの失敗の放置やレート制限の連続で、いつまでも黙って待たないためである。
起点は、PRを作った時刻と、そのheadで初めて待ちを見た時刻の遅いほうである。
古いPRにdependabotが新しいheadを積んでも、すぐには人に回らない。

### フローの待ちの抑止

スケジュールの評価が通っても、フローの準備やマージの直前の確認が待ちを返すことがある。
このとき、フローは作業項目を取り消して終える(注記`gate_waiting`)。
同じheadの取り消しから1時間たつまでは、フローを起動し直さない。
同じheadで取り消しが3回に達したら、人に回す。

### 処理済みの記録が消えたPR

`cleanup_db`は、保持期間(`retention_work_items_days`)を過ぎた終端の作業項目を消す。
作業項目の行はPRより後に作られるので、行が消えうるのは、作ってから保持期間を過ぎたPRだけである。
そのため、PRを作ってから「保持期間から1日を引いた日数」がたっていれば、評価せず人へ回す。
処理済みの記録が消えた後に、同じheadを自動で処理し直さないためである。
PR側に印を残す方法は採らない。
ラベルは人からFactoryへのトリガーに限り、PRに運用のコメントを書かない決まりがあるためである。

### リポジトリの照合

作業項目を作る前に、リポジトリのオーナーの数値IDと`factory_repo_id`を照合する(`verifyRepoOwnerId`)。
PRレビューの準備と同じ関門である。
落ちたときは、関門がnoticeを残し、その理由で人に回す。

準備のステップ(`dependabot_prepare`)も、リポジトリをcloneする直前に1回照合する。
取得時の照合から、事実の再収集を挟むためである。
落ちたときは、cloneも作業ツリーの作成もせずに、作業項目を人に回す。
注記は、`dependabot prepare:`の接頭辞に関門の理由を付けたものになる。
通知の次の操作は、終了のステップと同じく、`owners`と`factory_repo_id`を見直す案内になる。
オーナーの取得が404以外で失敗したときは、ステップが失敗する。

終了のステップ(`dependabot_finish`)も、書き込みの直前に1回照合する。
PRを読み直して書いてよいと確かめた後、マージ、所見の投稿、ラベルの付与のどれの前でも、同じ1回の照合を通る。
取得時の照合から、準備と影響調査を挟むので、その間に名前が別の人に渡っていても、相手のPRに書かないためである。
落ちたときは、書かずに作業項目を人に回す(注記は`dependabot finish:`の接頭辞に、関門の理由を付けたもの)。
通知の次の操作は、手でマージする案内でなく、`owners`と`factory_repo_id`を見直す案内になる。
試運転でも照合は走り、落ちれば試運転の理由でなく関門の理由で人に回す。
`id`の無いオーナーは、取得せずに通す。
オーナーの取得が404以外で失敗したときは、ステップが失敗し、フローの失敗の扱いが作業項目を終端にする。

### 二重に起動しない

作業項目は、同じPRに終端でない`dependabot`の行があると作れない(部分一意インデックス`work_items_active_dependabot_key`)。
作れなかったときは、ほかの取得が先に始めたものとして何もしない。
スケジュールは`no_flow_overlap`で、前回の実行中は次の実行を飛ばす。
フローの起動に失敗したら、作業項目を失敗にして通知する。
失敗した行は処理済みに数えるので、同じheadは自動では起動し直さない。

### 周回の結果

周回の結果には、一覧に戻した数が出る。

| 項目 | 意味 |
| --- | --- |
| `fallback_lists` | 表の代わりにRESTの一覧で列挙したリポジトリの数 |
| `fallback_reasons` | 一覧に戻した理由ごとの、リポジトリの数 |
| `failed` | 失敗の数。表の読み取りが失敗して一覧に戻し、その一覧も失敗すれば、1つのリポジトリで2増える |
| `held` | マージの保留のために待ったPRの数。保留を読めずに待ったPRを含む |

dependabotが無効な周回と、レート制限の解除まで飛ばす周回は、表と一覧のどちらも使わない。
この2つの周回では、`fallback_lists`は0になる。
一覧に戻したリポジトリは、リポジトリと理由をログの警告にも出す。

失敗の記録の段の名前は、次のとおりで、リポジトリの部分は小文字にそろえる。
経路によって大小文字が違っても、同じリポジトリの記録を同じ名前にするためである。

| 段 | 名前 |
| --- | --- |
| 表の読み取り | `read_gh_pull_requests:<owner>/<repo>` |
| 一覧の読み取り | `list_open_pull_requests:<owner>/<repo>` |
| 1件のPR | `dependabot_pr:<owner>/<repo>#<番号>` |
| フローの起動 | `start_flow:<owner>/<repo>#<番号>` |

## 作業項目の状態

状態の値と意味は[アーキテクチャ](../architecture.md#状態の一覧)の表にある。
dependabotの作業項目は、`picked`で始まり、次の終端のどれかで終わる。

| 状態 | 注記(`status_reason`) | 意味 |
| --- | --- | --- |
| `reviewed` | `merged` | フローがマージした |
| `reviewed` | `reconcile: merged` | 照合が、マージ済みのPRを見つけた。Factory以外がマージしたか、フローの記録が間に合わなかった |
| `reviewed` | `impact_found` | 影響の所見を投稿した。修正のラベルは人が付ける |
| `cancelled` | `dependabot_disabled` | 処理の途中で無効になった |
| `cancelled` | `pr_closed` | 処理の途中でPRが閉じた |
| `cancelled` | `head_moved` | 処理の途中でheadが動いた |
| `cancelled` | `gate_waiting` | フローの収集かゲートが待ちを返した |
| `needs_human` | `dependabot <段階>: <詳細>`などの理由 | 自動では処理できず、人に回した |
| `needs_human` | `dependabot dry run: merge allowed` | 試運転で、マージしてよいと判断したがマージしなかった |
| `needs_human` | `dependabot merge held by a hold` | 終了のステップがマージの直前に、リポジトリのマージの保留を見つけた |
| `needs_human` | `dependabot merge hold unreadable: <種類>` | 終了のステップがマージの直前に、保留を読めなかった。種類は`missing_table`、`read_failed`、`corrupt`、`error` |
| `failed` | フローの例外の理由など | 実行時エラーで止まった |

`cancelled`の4つの注記は、フローがそのheadを判断せずに止めたことを表す。
そのheadは、スケジュールが改めて評価する。

人に回す理由は、どの段階で止めたかを表す接頭辞で始まる。
接頭辞は、次の表の文字列に半角スペースを1つ続けた形である。
訳と次の操作は`pr_workflow_support.ts`の規則が決め、どの理由でも再実行を案内しない。

| 接頭辞 | 段階 |
| --- | --- |
| `dependabot poll:` | スケジュール(待ちの上限、保持期間、フローの待ちの回数、リポジトリの照合、起動の失敗) |
| `dependabot collect:` | 事実の収集と対象の導出(`more than one package changed`、`too many packages changed`など) |
| `dependabot prepare:` | リポジトリの取得と作業ツリーの作成(オーナーの照合) |
| `dependabot gate:` | ゲート |
| `dependabot install failed:` | 隔離したインストール |
| `dependabot local check:` | インストールの後の確認と、プロンプトの入力が合計の上限(`MAX_PROMPT_CHARS`)を超えたとき |
| `dependabot assess:` | 影響調査の実行 |
| `dependabot impact:` | 影響調査の結論 |
| `dependabot finish:` | マージや投稿の処理 |

## 照合と再実行

`poll_issues`の照合は、ほかの種別と同じく、dependabotの作業項目も扱う。
PRがマージされていれば、取り消しでなくマージ済み(`reviewed`、注記`reconcile: merged`)として記録する(`reconcileTransition`)。
フロー自身のマージ(注記`merged`)とは、注記で見分けられる。
マージされずに閉じていれば、取り消す。
どちらも、Discordに知らせない(`reconcileNotifies`)。
マージされずに閉じるのは、dependabotが置き換えたPRを自分で閉じたときである。
どちらも人の行動を求めない。
孤児として失敗にしたときは、ほかの種別と同じく知らせる。

`retry_work_item`は、dependabotの作業項目を再実行しない。
Consoleも再実行のボタンを出さず、PRを確かめて手でマージするか閉じるよう案内する。
新しいcommitが積まれると、スケジュールが新しいheadを別の作業項目で拾う。

## 定数

| 値 | 定義 | 意味 |
| --- | --- | --- |
| 10分 | `poll_dependabot.schedule.yaml` | スケジュールの周期 |
| 7日 | `WAIT_LIMIT_EXTRA_DAYS` | 待ちの上限で、公開の日数に足す日数 |
| 9分、29分、59分 | `WAIT_BACKOFF_MS` | 公開の日数のほかの待ちで、次に確かめるまでの間。周期のずれで1周多く飛ばさないよう、1分短い |
| 15分 | `RATE_LIMIT_DEFAULT_PAUSE_MS` | レート制限が解ける時刻が分からないときに、周回を飛ばす時間 |
| 1時間 | `FLOW_WAIT_COOLDOWN_MS` | フローが待ちで止まった後に、起動を見送る時間 |
| 3回 | `MAX_FLOW_GATE_WAITS` | フローの待ちの取り消しが、この回数に達したら人に回す |
| 1日 | `RETENTION_MARGIN_DAYS` | 保持期間から差し引く余裕 |

## dependabotの更新の自動マージ

Factoryは、原則としてPRをマージしない。
例外は、dependabotが開いた依存の更新PRのうち、機械の関門と影響調査をすべて通ったものだけである。
依存の更新は件数が多く、差分の形が決まっていて、機械で確かめられる範囲が広いためである。
既定では無効で、`f/factory/factory_config`の`dependabot_enabled`を真にしたときだけ動く。
マージは、`dependabot_merge_enabled`も真にしたときだけ行う。
`dependabot_merge_enabled`が偽の間は試運転で、マージしてよいと判断したPRもマージせず人に回す。
有効にする手順は[運用](../operations/features.md#dependabotの更新を設定する)に、状態と分岐は[この文書の「評価と分岐」](#評価と分岐)と[この文書の「作業項目の状態」](#作業項目の状態)にある。

候補のPRの列挙は、収集が有効なときは収集の表から読み、表を使えないリポジトリはRESTの開いているPRの一覧から読む。
表と一覧の値は、候補を絞ることにだけ使う。
マージの判断と保持期間の判定は、PRごとにRESTで読み直した値と集めた事実で行う。
そのため、表の値が書き換えられても、候補が増えれば読み直して飛ばし、減れば一覧に戻るか処理が遅れるだけである。
記録が新しいリポジトリで、表に行の無いPRは、待ちの記録を捨てるので、人に回すのが遅れる。
保持期間とゲートの判定は変わらない。

### マージする条件

マージするのは、次の条件をすべて満たすPRだけである。
1つでも満たさなければ、待つか人に回す。

| 関門 | 内容 |
| --- | --- |
| 対象のリポジトリ | `factory_repo`と、`dependabot_other_repos`に挙げたリポジトリだけである(後者は`repo_allowlist`の照合も通す)。オーナーの全リポジトリは対象にしない。`factory_repo`以外は、今は準備のステップで人に回し、マージしない([他のリポジトリ](#他のリポジトリ)) |
| リポジトリの照合 | オーナーの数値IDと`factory_repo_id`が、設定と一致する。PRレビューの準備と同じ関門で、作業項目を作る前に確かめる |
| 作者 | PRの作者が`dependabot[bot]`で、種別がBotである。headが同じリポジトリにある |
| commit | 通常のcommitは、作者が`dependabot[bot]`、コミッターが`dependabot[bot]`か`web-flow`で、署名が検証済みである。mergeのcommitは、コミッターが`web-flow`で、署名が検証済みである |
| 更新の幅 | patchかminorである。majorの版と、更新の幅を判別できない版は人に回す |
| 変わるファイル | `package.json`、`bun.lock`、`console/package.json`、`console/bun.lock`だけである。保護パスに触れない |
| 対象 | ロックファイルの差分から導いた、1つのパッケージの更新である。グループ更新は、`dependabot_group_enabled`が真のときだけ、2〜3つのパッケージまで対象にする([グループの更新](#グループの更新)) |
| ロックファイル | 対象以外のエントリが変わらない。グループでは、全対象のエントリを除く([グループの更新](#グループの更新))。整合性ハッシュがnpm registryの`dist.integrity`と一致する |
| マニフェスト | 対象の依存の版指定のほかは変わらない。scriptsなどの変更は止める |
| install時のスクリプト | 更新先の版が、前の版に無いスクリプトか、中身の違うスクリプトを持たない。`binding.gyp`による暗黙のinstallも含む |
| 必須チェック | `main`の必須チェック10件が、そのheadで成功かスキップである。同じ名前の実行はすべて合格を求め、GitHub Actionsから来た実行が1件以上要る |
| マージできる | GitHubがマージできると判定している。判定の途中と競合のときは待ち、待ちの上限を超えたら人に回す |
| 公開の日数 | 更新先の版の公開から`dependabot_min_published_days`日(既定7日)以上たっている |
| マージの設定 | `dependabot_merge_enabled`が真である。偽なら、マージの直前の確認までを行い、マージせずに人に回す |

`factory_repo`の必須チェックの名前は、`main`のrulesetの10件に固定している。
設定では変えられない。
他のリポジトリの必須チェックは、設定に持たず、そのリポジトリのrulesetから読む([他のリポジトリ](#他のリポジトリ))。

事実はすべて、最初に読んだheadとbaseのshaに固定して集める。
集めている間にheadかbaseが動いたら、古い事実で判断せず待つ。

### 他のリポジトリ

`factory_repo`以外のリポジトリは、`dependabot_other_repos`に挙げたものだけが候補になる。
既定は空で、挙げない。

必須チェックの名前を設定に持たせると、設定を書き換えられる者が、空や短い一覧にして関門を外せる。
そのため、名前は設定に持たず、次の層で閉じる。

| 層 | 内容 |
| --- | --- |
| 既定で無効 | 一覧は空。`repo_allowlist`にだけ載せたリポジトリは対象にならない |
| 名前の出典 | 必須チェックは、リポジトリのrulesetだけから導く。設定を書き換えても、リポジトリ自身のルールより弱くならない。0件、形の違い、GitHub Actions以外のAppは人に回す |
| `factory_repo`は設定を読まない | このリポジトリの必須チェックは固定の10件で、一覧に載せても変わらない |
| マージの経路が無い | 他のリポジトリは、準備のステップがcloneとインストールの前に、終了のステップが書き込みの前に人に回す。上の層がすべて破られても、マージには至らない |

他のリポジトリでは、そのリポジトリのコマンドをworkerで動かさない。
影響調査の入力の変更履歴は、インストールした依存から読むので、インストールを避けると確かめられない。
そのため、自動の経路は作らず、ゲートを通ったことを人に回した理由で確かめる試運転にとどめる。
`repo_allowlist`にだけ載せたリポジトリでは、インストールも走らない。

### グループの更新

dependabotが1つのPRで複数のパッケージを上げるグループ更新は、既定では人に回す。
`dependabot_group_enabled`を真にすると、変わったパッケージが2〜3つのPRを対象にする。
4つ以上は人に回す。
プロンプトとregistryの取得が対象数で増えるため、上限を3に抑えている。
このフラグの既定は偽である。

グループの更新は、各パッケージを単独の更新と同じ関門で個別に評価する。
公開から日の浅い版を含むパッケージは、待つ。
次のいずれかに当たると、人に回す。

- 変わったロックファイルのエントリに、更新前後で名前が変わるもの、追加、削除がある。
  依存を差し替える変更を通さないためである。
- 1つのパッケージでも、関門かインストールの後の確認に通らない。
  理由にはパッケージ名を付ける。
- ルートと`console/`で別々のパッケージが上がっている。
  ロックファイルごとに、対象の更新を求めるためである。

影響調査のClaudeは、全パッケージを1回の実行で調べる。
各パッケージを個別に調べ、`evidence`に全パッケージの名前を挙げさせる。
出力に全パッケージの名前が揃わなければ、コードが未確認として人に回す。
この検査は網羅の補助で、防御には数えない。
名前を挙げるだけで通りうるためである。

マージの直前にも`dependabot_group_enabled`を読み直す。
偽なら、マージを見送り、人に回す。

### インストールの後の確認

関門を通ったPRは、headのshaの作業ツリーに依存をインストールしてから、影響を調べる。
インストールは`bun install --frozen-lockfile --ignore-scripts`で、検査コマンドと同じ隔離(非特権のuid、許可した環境変数、新しいHOME)で行う。
インストールの後に、次を確かめる。

- 作業ツリーに、インストール先(`node_modules`と`vendor`)のほかの変更が無い。
- インストールしたパッケージの名前と版が、対象と一致する。
- インストールしたパッケージのinstall時のスクリプトと`binding.gyp`の有無が、registryの値と一致する。
  registryの記述とtarballの中身の食い違い(manifest confusion)を止めるためである。
- 更新の前後で、registryが示すリポジトリのURLが同じ場所を指す。
  同じと確かめられなければ、サプライチェーンの懸念として人に回す。

### Claudeは関門を緩めない

影響調査のClaudeは、関門を通った後にだけ起動する。
ツールは`Read`、`Glob`、`Grep`だけで、`Bash`とネットワークは渡さない。
作業ディレクトリは、関門を通したheadのきれいな作業ツリーである。
変更履歴、PR本文、差分、registryの情報は、データとして区切って渡す。
`node_modules`の下のファイルに書かれた指示めいた文は、それ自体をサプライチェーンの懸念として報告させる。

Claudeの結論は、マージを止める方向にしか働かない。
懸念か未確認の項目が1件でもあれば、影響なしと答えても人に回す。
取得できなかった入力があれば、Claudeの答えに関わらず、コードが人に回す。

### 影響があるとき

影響があると判断したPRには、所見をPRのレビューとして投稿し、作業項目を終える。
修正のラベル(`factory:fix`)は自動で付けない。
所見は外部の入力から作られうるので、人が確かめてから修正に回すためである。
人がラベルを付けると、PR修正が動く想定である。
動くかは、有効化の前の確認で確かめる。
修正をpushしたPRは、commitの作者が`dependabot[bot]`でなくなるので、関門を通らない。
そのPRは、レビューの指摘が0件でも自動ではマージせず、人がマージする。

### マージの仕方

マージは、終了のステップだけが行う。
マージの直前に、PRとbaseのshaを読み直し、影響を調べたheadとbaseのままであることを確かめる。
headが動いていればマージせずに取り消し、新しいheadは改めて評価する。
baseが動いていれば、評価していない`main`にマージしないよう、取り消して評価し直す。
マージはsquashで、headのshaを固定して1回だけ要求し、題名を固定にする。
上流の文字列(release notesの`[skip ci]`など)が`main`のcommitに入らないためである。
結果が分からないときは再送せず、人に回す。

### PATのマージ権限

マージは、ほかのフローと同じPAT(`f/factory/github_token`)で行う。
PATの持ち主がrulesetを迂回できる管理者だと、マージのAPIが必須チェックの未達を止めない可能性がある。
その場合は、関門の必須チェックの確認が唯一の防御になる。
有効化の前に、PATで`main`へマージできるかと、迂回が働くかを確かめる。
マージが403で拒まれたときは、人に回し、権限とrulesetの確認を案内する。

### 守る部品と守らない部品

関門、収集、registryの取得、プロンプト、フローの支援関数、取得のscript、3つのステップ、フローの定義は保護パスにする。
一覧は[保護パスの変更を止める](pr-workflow.md#保護パスの変更を止める)にある。
共有のモジュールは守らない。
対象は、`lib/`の`dependabot_*`以外のモジュールと`steps/pr_workflow_support.ts`である。
たとえば`lib/github.ts`、`lib/db.ts`、`lib/workspace.ts`が含まれる。
`lib/check_sandbox.ts`は、安全策を担うコードとして保護パスに入れている。
ほかのフローも使い、守るとそれらの変更をすべて止めてしまうためである。
これらを書き換えてdependabotの判断を変える変更は、PRのレビューで差分を確かめて止める。

### 有効化の前の確認

次の点は、実機でしか確かめられない。
確かめる順は3段階である。
最初に、フローを使わない単独の実験で、Claudeが`node_modules`の下の指示のファイルを読み込まないことを確かめる。
次に試運転(`dependabot_enabled`を真、`dependabot_merge_enabled`を偽)で、フローを実際のPRに通して確かめる。
試運転ではマージしないので、フローの不具合や想定外の入力があっても`main`は変わらない。
結果を確かめてから、`dependabot_merge_enabled`を真にする。
確かめた結果は、この節の残るリスクに反映する。

試運転の前に、単独の実験で確かめることは次のとおりである。

| 確かめること | 確かめ方 | 満たさないとき |
| --- | --- | --- |
| `node_modules`の下の`CLAUDE.md`と`AGENTS.md`を、Claudeが読み込まないこと | 置いたファイルを含む作業ツリーで、`--setting-sources user`のClaudeに読ませ、記憶として載らないかを見る | 試運転を始めない。影響調査の前に、そのようなファイルがあれば人に回す検査を足す |

単独の実験の結果は、`node_modules`の下の`CLAUDE.md`と`AGENTS.md`が読み込まれなかった。
起動時の記憶にも、そのディレクトリのファイルを読んだ直後の追加の文にも、置いた合図の語は現れなかった。
実験の設定は、本番と同じ`--tools Read,Glob,Grep`、`--setting-sources user`、`--strict-mcp-config`、`--restricted`である。
Claudeのバージョンが変わったときは、同じ実験をやり直す。

試運転で確かめることは次のとおりである。

| 確かめること | 確かめ方 | 満たさないとき |
| --- | --- | --- |
| 隔離したユーザーで、npm registryに届き、`--frozen-lockfile`のインストールが時間内に終わること | 試運転で起動したフローの、準備のステップの結果を見る | インストールの設定とステップのtimeoutを見直す |
| フローの式がWindmillで評価され、3つのステップが順に動くこと | 試運転で起動したフローの、各ステップの結果を見る | フローの定義を直す |
| `auto-merge`やdependabot用のrulesetの有無 | rulesetの一覧を読む | 修正のフローは、auto-mergeが有効なPRで止まる |
| dependabotが`bun.lock`を更新するか | 実際のPRの差分を見る | 更新しないなら、ロックファイルの無いPRは常に人に回る。運用で受け入れるか決める |
| Claudeの構造化出力の上限の指定が受け付けられること | 影響調査のステップの結果を見る | 出力の形を直す |
| 修正のラベルを付けたdependabotのPRを、PR修正が受けること | 所見の出たPRに人がラベルを付ける | 修正は人が行う。ラベルを自動で付ける判断は、確かめた後で行う |

マージの前に確かめることは次のとおりである。

| 確かめること | 確かめ方 | 満たさないとき |
| --- | --- | --- |
| 試運転で、マージ可と判定したPRの判断が妥当であること | 試運転で人に回ったPRの理由と所見を読む | マージを有効にしない |
| PATのマージ権限と、rulesetの迂回の有無 | PATの権限とrulesetの迂回の設定を読む | マージを有効にしない。迂回が働くなら、必須チェックの防御が関門だけになることを受け入れるか決める |
| 他のリポジトリのrulesetに必須チェックがあること | `gh api repos/<owner>/<repo>/rules/branches/main`を読み、`required_status_checks`の規則と`context`を確かめる | 必須チェックが無いリポジトリは人に回る。ruleset、またはGitHub Actionsの名前を直す |
| squashの空のcommit本文の扱い | 最初のマージのcommitを見る | commitの本文を直す |

- 他のリポジトリを処理する条件を外す前に、次を決める。
  これを決めるまで、他のリポジトリはマージの経路に入れない。
  - 古典的なブランチ保護の必須チェックの読み方(権限と、404の曖昧さ)と、併用するリポジトリの扱い。
  - ルールの`bypass_actors`、`strict`、古典的な保護の`enforce_admins`、commit statusで満たす必須チェック。
  - `required_status_checks`以外の規則。
    `workflows`、`code_scanning`、`required_deployments`、`merge_queue`、承認数1以上の`pull_request`がある。
  - `dependabot_other_repos`の既定値の置き場。
    今は保護パスの外の`config.ts`にある。
    保護パスの定数にするか、リソースに明示されたときだけ有効にする。
  - インストールを使わない変更履歴と同一性の確認(5b)。
