# 作業項目の状態とリース

作業項目(`work_items`)の状態が、どの処理でどう変わるかを定める仕様である。状態を書き換えるコードを変える人が、遷移の条件、リース、孤児の判定を確かめるために読む。状態の一覧と遷移の図は[アーキテクチャ](../architecture.md)にある。

## 状態とラベル

作業項目の状態は`work_items.status`だけが持つ。GitHubのラベルは、人がFactoryに作業を始めさせるトリガーとしてだけ使う。

| 対象 | トリガーラベル | 消費する時点 |
| --- | --- | --- |
| Issue | `factory` | claimでトリガーラベルを外した直後 |
| PR | `factory:review`、`factory:fix` | claimでトリガーラベルを外した直後 |

トリガーラベルはclaimのときに一度だけ消費する。その後の状態遷移では、終端への遷移を含めてIssueとPRのラベルを変えない。再実行(`retry_work_item`)も、フローを起動するだけでラベルを付け直さない。

最初からやり直すには、人がトリガーラベルを付け直す。Factoryはこれを新しいサイクル(`cycle`)として扱う。

### PRの再発見

PRは終端になってもラベルが変わらないので、収集の表でもRESTの一覧でも、追跡中のPRを見つけられない。そのため`poll_prs`は、DBの作業項目から追跡中のPRを見つけ直す(`listTrackedPrs`)。

対象は次の条件をすべて満たす作業項目のPRである。見つけたPRは、`owners`(`id`の照合を通ったオーナー)と`repo_allowlist`で絞り、まだopenであることを`getPr`で確かめてから候補にする。

- 種別が`pr_review`か`pr_fix`である。
- 状態が取り消し(`cancelled`)でない。
- `factory_config`の`tracked_pr_days`(既定30日)以内に更新されている。

この経路があるので、人が新しいcommitをpushするとPRレビューが次のサイクルを始める。トリガーラベルを付け直したときも、同じ経路で次のサイクルが始まる。

## 遷移の詳細

### 要件定義の承認から実装へ

要件定義の承認を反映する`requirements_apply`は、まず承認の副作用を実行する。副作用はIssueへのコメント、Discordへの通知、要件定義用のworktree(`req-<N>`)の削除の3つである。どれかが失敗しても次へ進む。コメントの失敗は、Consoleの要対応事項(`approval_comment_failed`)に残す。

設計が有効で、設計フローを起動する依存が空でないときは、承認済みを経ずに設計中へ移し、設計フローを起動する。
設定が無効の間(既定)は空なので、この経路は動かない([設計書の生成](design.md)の「設計フローを起動する元」)。
設計が有効なときの実装フローは、設計の承認を反映する`design_apply`が起動する。
`design_apply`は、照合が通った承認を、設計の承認待ち(`awaiting_design_approval`)から承認済みへ比較交換で移す。
続けて`implement_enabled`が真なら、次の手順と同じ`startImplement`で実装フローを起動する。
遷移の条件は[設計書の生成](design.md)の「承認の反映」に書く。

続けて、`implement_enabled`が真なら実装フローを起動する(`startImplement`)。手順は次のとおり。

1. 作業項目を承認済み(`approved`)から実装中(`implementing`)へ比較交換で移す。同じ文で`flow_job_id`を空にする。
2. `f/factory/implement`を起動する。
3. 起動したジョブIDを、`flow_job_id`が空か同じ値のときだけ記録する。

状態を先に移すのは、承認済みが終端だからである。承認済みのままフローが準備より前に落ちると、失敗ハンドラ(`on_error_flow`)は作業項目を失敗にできない。

`runFlowAsync`はHTTPエラーでも例外を投げず、応答本文を返す。そのため戻り値がジョブID(UUID)の形でなければ、起動の失敗として扱う。この検証は、フローを起動するすべての箇所で行う。

各段階が失敗したときの扱いは次のとおり。

| 失敗 | 扱い |
| --- | --- |
| 比較交換が一致しない | 別の処理(再実行など)が作業項目を動かしたので、何もしない |
| 比較交換が例外を投げた | `job_failures`(stepは`cas`)と要対応事項(`implement_launch_failed`)に残す。作業項目は承認済みのまま残り、reconcileの対象にならないので、人が再実行する |
| 起動が失敗した | リースが空のときだけ人の対応待ちにし、`job_failures`の行(stepは`launch`)、要対応事項、Discordに残す。作業項目がConsoleの**要対応**の失敗に出るので、そこから再実行できる |
| 起動が失敗したが、フローが既にリースを取っている | フローは動いているので何もしない |
| ジョブIDの記録が2回とも例外を投げた | 実装中のままにし、`job_failures`と要対応事項だけを残す |

比較交換が例外を投げても、その前に実装中へ移っていることがまれにある。この作業項目はフローの無い実装中として残り、猶予の後にreconcileが失敗とする。その後は同じく再実行できる。

### 実装フローの結果

実装フローの完了ステップ(`implement_finish`)は、結果に応じて作業項目を次のように移す。どの遷移も、`flow_job_id`が自分のジョブIDであることを条件にする。

| 遷移先 | 条件 |
| --- | --- |
| PR作成済み(`pr_open`) | 検査に通った実装をコミットしてpushし、PRを作成か更新して`factory:review`ラベルを付けた。保護パスの変更や検査コマンドの未設定で検査を実行しなかった場合も含む |
| 要件定義の生成中(`requirements_generating`) | 実装が要件の不足(`requirements_gap`)を返した。試行回数を1つ増やして工程2を起動する |
| 設計中(`designing`) | 設計書が渡された実行が、設計の不足(`design_gap`)を返した。設計工程が有効で、上限に達していない。`design_attempt`を1つ増やして設計フローを起動する |
| 人の対応待ち(`needs_human`) | ラウンドの上限、日次予算、期限、停滞、symlinkの変更、差分の上限超過、Claudeの実行の失敗、変更なし、pushかPR作成の失敗、時間設定がステップのtimeoutに収まらない、前の実行のプロセスがworktreeを使用中、PRの修正やレビューが実行中、設計の不足で設計へ戻せない(設計工程が無効か、上限に達した)のいずれか |
| 取り消し(`cancelled`) | Issueが閉じられた。準備と完了のときに確かめ、実行中は`poll_issues`のreconcileが確かめる |

要件の不足で戻すときは、worktreeを消し、PRが無ければ実装ブランチもリモートとローカルの両方で消す。不足の報告(`gap_report`)は、自動の報告の印を付けて、工程2のフィードバックとして渡す。試行回数が`max_attempts`に達していれば、差し戻さずに人の対応待ちにする。
要件定義の生成中へ移す文は、同じ文で`design_attempt`を0にし、`flow_job_id`を空にする。古い設計書の承認を、作り直した要件定義の実装に使わせないためである。
PR修正が親のIssueを要件定義へ戻す遷移も同じである。

設計の不足で戻すときも、worktreeとブランチを同じように消す。行き先の判定、設計中へ移す比較交換、人の対応待ちの理由は[実装フローの内部仕様](implement.md)の「設計の不足」に書く。
設計中へ移す文は、同じ文で`design_attempt`を1つ増やし、`flow_job_id`を空にし、遷移の記録を遷移元を実装中として書く。

PR修正が設計の不足を返したときも、親を設計中へ戻す。
遷移元はPR作成済みで、比較交換は、親がPR作成済みで`flow_job_id`が読んだ値のままのときだけ書く。
同じ文で、`design_attempt`を1つ増やし、`flow_job_id`を空にし、遷移の記録を書く。
遷移の注記は、固定の接頭辞`pr_fix design gap:`と、整えた報告である。
この接頭辞が、再実行の報告の受け渡しと、設計の上限の数え方の根拠になる。
戻す先の設計中は稼働中の状態なので、読んだ後に同じIssueの新しいサイクルが稼働中で挿入されると、部分一意インデックス(`work_items_active_issue_key`)が更新を拒む。
確認と比較交換は1つの文でないので、確認の後に割り込んだ新しいサイクルを捕まえるのは、この一意制約である。
比較交換は、この違反を競合に負けたものとして扱い、何も書かずに断る。
確認の内容と失敗時の扱いは、[PRワークフロー](pr-workflow.md)の「設計の不足の差し戻し」に書く。

人の対応待ちで止めたときに途中の変更をどう扱うかは、[実装フローの内部仕様](implement.md)に書く。

### 却下と再生成

要件定義の却下を反映する`requirements_apply`は、作業項目を却下(`rejected`)にしない。試行回数で次のどちらかに移す。

| 条件 | 遷移 |
| --- | --- |
| attemptが`max_attempts`(既定3)未満 | 承認待ちから要件定義の生成中へ移し、attempt+1でpipelineを起動する。却下の理由をフィードバックとして渡す |
| attemptが`max_attempts`に達した | 承認待ちから人の対応待ちへ移し、Discordに通知する |

再生成への移行は、状態の遷移と同じ文で`flow_job_id`を空にする。起動したジョブIDは、空のままのときだけ記録する。
起動に失敗するか記録が例外を投げたときは、リースが空のままなら人の対応待ちへ戻す。理由は`requirements regeneration could not be started`である。
この作業項目の再実行は、要件定義の生成へ戻り、却下の理由を渡す([再実行](#再実行)の行1)。

#### 設計の却下

設計の却下を反映する`design_apply`は、Issueと反映できた却下の数で、次の3つに分ける。
どの遷移も、設計の承認待ちの間に残る`flow_job_id`を条件にした比較交換で行う。

| 条件 | 遷移 |
| --- | --- |
| Issueが取り込み時点から変わっている | 設計の承認待ちから要件定義の生成中へ移す。同じ文で`design_attempt`を0にし、`flow_job_id`を空にする。取り込み内容を現在のIssueで更新し、attempt+1でpipelineを起動する。却下の理由をフィードバックとして渡す |
| 変わっていない(または確かめられなかった)。反映できた却下の数に1を足すと`max_design_attempts`未満 | 設計の承認待ちから設計中へ移し、`flow_job_id`を空にする。設計フローを`design_attempt`+1で起動し、却下の理由を`feedback`として渡す |
| 変わっていない(または確かめられなかった)。反映できた却下の数に1を足すと`max_design_attempts`以上 | 設計の承認待ちから人の対応待ちへ移し、Discordに通知する |

数え方と注記は[設計書の生成](design.md)の「承認の反映」に書く。
再実行は数えない。
設計中の再生成の起動に失敗するか記録が例外を投げたときは、リースが空のままなら人の対応待ちへ戻す。理由は`design flow could not be started`である。
要件定義へ戻す経路の起動に失敗したときの理由は、要件定義の却下と同じ`requirements regeneration could not be started`である。この作業項目の再実行は、要件定義の生成へ戻り、設計の却下の理由を渡す([再実行](#再実行)の行3)。

#### 取り込み内容の更新

移行の後、pipelineを起動する前に、作業項目の題名と本文(`title`、`body`)を現在のIssueの内容に更新する(`refreshIntakeFromIssue`)。
却下の理由が「Issueを書き換えた」ことのとき、作り直した要件定義が書き換え後の内容に基づき、次の承認の前の確認([要件定義](requirements.md)の「承認の前のIssueの確認」)が通るようにするためである。
Consoleに出る取り込み時点の内容は更新後の値で、実装に渡る内容と一致したままになる。
更新の決まりは次のとおりである。

- 更新は、移行の直後で`flow_job_id`が空の`requirements_generating`の作業項目に限る(`updateIntakeIfRegenerating`)。pipelineは起動の後に作業項目を読むので、新しい内容で作り直される。
- GitHubから取れなかったとき、書き込みに失敗したとき、作業項目が先に動いたときは、更新せずに元の内容で作り直す。例外は投げない。Issueが違えば次の承認が断られるので、もう一度却下すれば更新を再試行できる。
- 更新中にIssueがまた書き換わっても、更新は読んだ時点の内容で済む。書き換えが続けば、次の承認が断られ、却下のたびに取り込み直す。書き換えが止まれば収束する。
- 更新は`max_attempts`未満の却下の作り直しと、設計の却下でIssueが変わっていたときの要件定義への戻しと、`retry_work_item`による要件定義の作り直しに限る。上限に達した却下は人の対応待ちへ移るので、その場では更新しない。人の対応待ちからの再実行が、現在のIssueで作り直す出口になる。
- Issueの書き換えを理由にした却下も、試行を1回使う。

更新は、書き換え後の内容を承認者が見ないまま実装に渡さないよう、次の4つで記録し、知らせる。

- 更新と同じ文で、`work_item_events`に状態の変わらない行を残す。`note`は`intake refreshed from the current issue;`で始まり、更新の前後の題名と本文を文字数とSHA-256の先頭16桁で書く。Issueの内容は信頼できない入力なので、そのまま入れない。
- noticeの`intake_refreshed`(重要度は`action`)を残す。
- 却下による作り直しでは、Discordにも通知する。`retry_work_item`はConsole用のworkerで動くので、Discordのwebhookを読まず、noticeだけを残す。
- Consoleの`intake_snapshot`が、履歴から導いた`refreshed`を返し、承認画面が警告を出す。実装を終えたときのPR本文は、同じ履歴を読んで注記を必ず出す。

### 再実行

`retry_work_item`は、止まった作業項目のフローを直接起動し直す。再実行できる状態は、失敗、人の対応待ち、期限切れ、ブロック(`blocked`)、承認済みの5つである。
承認済みからの再実行は、承認の後に実装フローが起動する前に止まった作業項目のためにある。戻す状態と起動するフローは種別で決まる。
要対応の照合が、閉じた対象を理由に取り消した作業項目も、取り消す前の状態の作業項目として再実行できる。詳しくは「要対応の終端の取り消し」に書く。
要件定義を作り直す再実行(Issueの作業項目を`requirements_generating`へ戻す経路)も、起動の前に取り込み内容を現在のIssueで更新する。更新の決まりと記録は「却下と再生成」の「取り込み内容の更新」と同じである。
同じIssueに、より新しいサイクルの`issue`の作業項目がある作業項目は、状態を問わず再実行しない。新しいサイクルに置き換えられた要件定義を実装しないためである。
断る理由には、最新のサイクルの作業項目のIDと状態を含める。
進行中ならそのまま待つよう案内する。
再実行できる状態ならその作業項目の再実行を案内する。
それ以外の終端なら、トリガーラベルの付け直しを案内する。

Issueの作業項目は、次の表を上から順に評価し、最初に当たった行で再開先を決める。
設計の分岐(行4)は、実装フローが無効かの拒否(行6)より前にある。実装フローが無効でも、設計は進められるためである。

| 順 | 条件 | 戻す状態 | 起動するフロー |
| --- | --- | --- | --- |
| 1 | 最新の要件定義の承認がattemptに一致しない | 要件定義の生成中。ただし承認済みの作業項目は拒否する | `f/factory/pipeline`(attempt+1) |
| 2 | 要件定義の改ざんか欠落で止まった | 要件定義の生成中 | `f/factory/pipeline`(attempt+1) |
| 3 | 要件定義の生成へ戻った後に止まった | 要件定義の生成中 | `f/factory/pipeline`(attempt+1) |
| 4 | 設計が有効で、設計の承認が照合を通らない。または、実装かPR修正が返した設計の不足を設計がまだ受けていない | 設計中 | `f/factory/design`(`design_attempt`+1) |
| 5 | `implement_enabled`が真 | 実装中 | `f/factory/implement` |
| 6 | 上記以外 | 拒否する | なし |

行2は、改ざんと欠落の理由で止まった作業項目である。
理由は、完全に一致するか、理由の後ろにセミコロンと空白を挟んで別の注記が続くものに限る。
設計の有効と無効、実装の有効と無効に関わらず、要件定義の生成へ戻る。
基準値が残るので、実装や設計に戻しても同じ検出で止まり、要件定義を作り直せば新しい基準値が生まれるためである。
作り直した要件定義は、人が承認し直す。

行3は、設計か実装が要件の不足を返して、または設計の却下でIssueが変わっていて、要件定義の生成へ戻った後、次のpipelineが`attempt`を進める前に止まった作業項目である。
起動に失敗して人の対応待ちに戻った作業項目も当たる。
この間、要件定義の承認は古い`attempt`に一致したままなので、行3が無いと実装を再開してしまう。
不足を報告した要件定義のままの実装は、また不足を報告する。
設計の有効と無効、実装の有効と無効に関わらず、要件定義の生成へ戻り、人が承認し直す。

行2と行3は、止まったときの遷移の記録で判定する。
読むのは、止まった状態への最新の遷移の遷移元と注記である。
取り消された作業項目は、取り消す前の状態の遷移を読む。
注記の文面を判定に使うので、理由の定数を変えるときは、読む側と同時に変える。
定数を変える前に止まった作業項目の注記は分類できず、行2と行3に当たらない。

行4の設計フローへの再開は、`design_attempt`に1を足した試行で始める。
設計が有効でも、設計の承認が照合を通り、設計の不足を受け終えていれば行5に進む。
期限切れの後の再実行も、この表で決まる。
最新の設計の承認が期限切れなら照合を通らないので、行4で設計を作り直す。
期限切れの直後に人の承認が記録されて、承認が照合を通るなら、行5で実装から始まる。
設計の承認の照合は[設計書の生成](design.md)の「承認の照合」に書く。

要件定義の生成へ戻す3つの遷移(行1、行2、行3)は、同じ文で`design_attempt`を0にし、`flow_job_id`を空にする。
次のpipelineの準備が`attempt`を進める前に止まっても、要件定義の生成中の`design_attempt`を0に保つためである。
この間に`design_attempt`が古い値で残ると、古い設計の承認と古い要件定義の承認が、一致して見える。

#### 要件定義の生成へ渡す理由

要件定義の生成へ戻す再実行は、理由を渡すことがある。
理由は、要件定義の生成の`feedback`に載る。

| 場面 | 渡す理由 | 印 |
| --- | --- | --- |
| 行1で、最新の承認が現在の`attempt`の却下 | 承認依頼の`reason`。整形も切り詰めもしない | 付けない |
| 行3 | 要件定義の生成への最新の遷移の注記から取った差し戻しの理由 | 付ける |
| 行2 | 渡さない | なし |

却下の理由は人が書いた指示なので、通常の却下と同じく、そのまま渡す。
空白だけの理由は渡さない。

差し戻しの理由は、信頼できない入力を読んだClaudeの出力なので、`automatedFeedback`の印を付けて渡す。
要件定義の生成は、印のある理由を人の指示でなく、信頼できない報告として`dataFence`に入れて扱う。
理由を取るのは、要件定義の生成中への最新の遷移の注記が、`gap:`か`design gap:`と空白1つで始まるときだけである。
状態の変わらない行(取り込み内容の更新の記録)は、遷移として数えない。
接頭辞の後ろに、制御文字と書式文字の除去、秘密のマスク、2000文字への切り詰めをかける。
結果が空なら渡さない。

差し戻しの理由を渡した再実行の遷移の注記は、`retry_work_item: restarted (carrying gap) from <状態>`の形にする。
取り消した対象を再実行したときは、`from <状態> (was <取り消す前の状態> before the closed target was cancelled)`と続く。
次に読むときは、注記が先頭の接頭辞`retry_work_item: restarted (carrying gap)`で始まる遷移だけを飛ばして、その前の差し戻しの理由を読む。
差し戻しの本文が`(carrying gap)`で終わっていても、その遷移は飛ばさない。
理由を渡した再実行が、起動に失敗して止まっても、次の再実行が同じ理由を渡せるようにするためである。
印の無い再実行の遷移は飛ばさない。その前の古い差し戻しの理由を渡さないためである。

行2が理由を渡さないのは、現在の`attempt`の要件定義の承認が、前の差し戻しの理由を消費済みであることを示すからである。
その承認を作ったpipelineが、理由を読んで要件定義を作り直している。
残っている差し戻しの注記は、改ざんと関係が無い。

pipelineが`attempt`を進めた後、下書きを作れずに止まった作業項目(日次予算の超過など)は、理由を消費していない。
最新の承認の`attempt`より後の下書きが無いことで、これを見分ける。
承認が却下なら承認依頼の理由を、承認済みで行3の止まり方なら差し戻しの理由を、もう一度渡す。
下書きができた後に止まった場合は、理由が消費済みなので渡さない。

理由が無い場合は、起動の引数に`feedback`を含めない。

#### 設計フローへ渡す理由

行4で設計フローを起動する再実行は、設計フローの`feedback`に、次のどちらかを載せることがある。
どちらも、設計が有効で、要件定義が承認済みで、設計が未承認(または設計の不足を受けていない)のときに限る。

| 場面 | 渡す理由 | 印 |
| --- | --- | --- |
| 直前の設計の却下 | 承認依頼の`reason`。整形も切り詰めもしない | 付けない |
| 実装かPR修正が返した設計の不足 | 遷移の注記から取った報告 | 付ける |

実装かPR修正が返した設計の不足を渡すのは、現在の要件定義の試行について、次をすべて満たすときである。
試行の範囲は、要件定義の生成中への最新の遷移(遷移元と遷移先が違うもの)より後である。

- 設計中への最新の遷移と、実装中から人の対応待ちへの最新の停止のうち、新しいほうが次のどれかである。
  設計中への遷移で、遷移元が実装中で、注記が`implement design gap:`で始まる。
  設計中への遷移で、遷移元がPR作成済みで、注記が`pr_fix design gap:`で始まる。
  人の対応待ちへの停止で、注記が`implement design gap exhausted:`で始まる。
- その遷移より後に作られた設計の承認依頼が無い。
  依頼の`requested_at`が遷移の`occurred_at`より後でなければ、依頼が無いものとして扱う。同時刻の依頼は、遷移より後とは見なさない。
- 接頭辞の後ろの報告が、整えた後に空でない。

設計中への遷移を探すとき、報告を渡した再実行の遷移(注記が`retry_work_item: restarted (carrying gap)`で始まる)は飛ばす。
設計の起動に失敗しても、保存の前後で失敗しても、依頼の記録の前に止まっても、2回目以降の再実行が同じ報告を渡せるようにするためである。
設計の承認依頼が先に作られていれば、設計は報告を読んで作り直し済みなので、渡さない。
別の要件定義の試行の戻しも、範囲の外なので渡さない。

報告は、要件定義へ渡す差し戻しの理由と同じ整え方をして、印を付ける。
接頭辞の後ろに、制御文字と書式文字の除去、秘密のマスク、2000文字への切り詰めをかけ、結果が空なら渡さない。
渡した再実行の遷移の注記には、要件定義の場合と同じ印を付ける。

上限で止めた後の再実行は、`design_attempt`が進んでいないので、古い設計の承認が照合を通る。
設計の不足を受けていなければ、承認が通ってもこの承認を通らないものとして扱い、設計を作り直す。
数え方は再実行を数えないので、設計へ戻した数が再び上限に達するまで、人の操作ごとに設計を1回試せる。

PR修正から戻して、設計の起動に失敗した親は、人の対応待ちになる。
この親の再実行は、設計中への遷移の注記から報告を取って、設計へ渡す。
PR修正の作業項目の注記は固定文で、報告を持たない。
この固定文は、自動で再開する理由の接頭辞に当たらないので、PR修正が自動で再開されることは無い。
設計の最中は、PR修正を再実行しても、準備の確認が止める。

PR修正の戻しが、設計工程の無効か上限で止まったときは、親がPR作成済みのまま残る。
PR作成済みは再実行できる状態でないので、再実行で設計を作り直せない。
次の操作は、Issueにトリガーのラベルを付け直して新しいサイクルを始めるか、PRを人が直すことである。

設計の不足を返した実装が、設計工程の無効と所有者の照合のどちらかで止まったときは、注記に接頭辞が付かず、`design_attempt`も進まない。
接頭辞を付けて報告を残すのは、設計へ戻した場合と上限で止めた場合だけだからである。
後で再実行しても、設計の不足を受けていないので設計へは回らず、承認済みの設計で実装を1周やり直す。
人が承認した設計書なので、承認なしの起動にはならない。

却下の理由を渡す条件は、次のとおりである。

- 設計が有効で、要件定義が承認済みで、設計が未承認である。
- 最新の設計の承認依頼が却下である。
- その依頼を作ったときの`attempt`が、作業項目の現在の`attempt`と一致する。

理由は承認依頼の`reason`である。人が書いた指示なので、整形せず、切り詰めず、印も付けない。
設計の試行の番号(`design_attempt`)は問わない。失敗や期限切れの後の再実行で番号が進んでも、その後に新しい依頼が無ければ、直前の却下の理由は有効だからである。
`attempt`を問うのは、要件定義を作り直した後の古い却下の理由を、新しい要件定義の設計に渡さないためである。
承認済み、期限切れ、承認待ち、別の`attempt`、依頼が無い、理由が空のときは、空文字列を渡す。
上限で人の対応待ちになった作業項目の再実行も、直前の却下の理由を渡して設計を始める。

設計の却下でIssueが変わって要件定義へ戻した後に、起動に失敗して止まった作業項目は、行3に当たる。
遷移の注記が固定文なので、注記でなく設計の承認依頼の却下の理由を、印を付けずに要件定義の生成へ渡す。
設計が無効でも渡す。根拠は設定でなく、止まる前の状態が設計の承認待ちだったという事実である。
却下の理由を渡す条件は、要件定義の却下と同じである。
依頼を作ったときの`attempt`が現在の`attempt`と一致するか、`attempt`が進んでそれより後の下書きが無いときに渡す。
この再実行の遷移の注記にも、理由を渡した印を付ける。印が無いと、次の再実行が止まる前の状態を見失うためである。

他の種別の再開先は次のとおりである。

| 種別 | 条件 | 戻す状態 | 起動するフロー |
| --- | --- | --- | --- |
| pr_review | なし | レビュー中 | `f/factory/pr_review` |
| pr_fix | CIの失敗を直す回でも競合を直す回でもない(`ci_check_id`と`conflict_check_id`がNULL) | 修正中 | `f/factory/pr_fix` |
| pr_fix | CIの失敗を直す回(`ci_check_id`が非NULL) | 拒否する | なし |
| pr_fix | 競合を直す回(`conflict_check_id`が非NULL) | 拒否する | なし |
| audit | なし | 拒否する | なし |
| dependabot | なし | 拒否する | なし |

CIの失敗を直す回の再実行は、作業項目だけを再開すると失敗の行と食い違うため、拒否する。
回が終わると、`watch_pr_ci`が失敗の行を戻す([PRワークフロー](pr-workflow.md)の「CIの失敗を直す回」)。
競合を直す回の再実行も拒否する。競合の行が、直している作業項目を結んだままになるためである。

競合を直す回は、止まっていても、自動の再開の候補に入れず、比較交換でも再開しない。
指摘への対応の失敗の数(モデルを`heavy_model`に上げる判定)にも数えない。
CIの失敗を直す回と同じ扱いである。

行6の拒否は、要件定義が承認済みで、設計が無効か承認済みで、実装フローが無効なときである。
この場合にpipelineで再開すると、人が承認した要件定義を作り直してしまう。そのため状態を問わず拒否する。

状態の遷移は、読み取った状態からの比較交換で行う。途中で別の処理が状態を変えていれば、再実行しない。

記録されたジョブがまだ動いている(キュー待ちを含む)か、ジョブの状態を読めないときは、再実行を拒否する。実装フロー、設計フロー、pipelineへの再実行では、比較交換で`flow_job_id`を空にしてから起動し、ジョブIDは空のままのときだけ記録する。

起動の戻り値がジョブIDでなければ、作業項目を人の対応待ちに戻してエラーにする。別の実行が既にリースを持っていて戻せないときは、その旨のエラーにする。

起動したジョブIDを、別の実行が先にリースを取っていたために記録しなかったときは、Consoleから再実行した場合、その旨が警告として出る。
Windmillで`retry_work_item`を直接実行したときは、実行結果(`ok: false`、`flow_job_id: null`)にだけ現れる。

### 修正の回を結ぶ列

`pr_fix`の作業項目は、直している対象の行を、次の列で指す。
`ci_check_id`と`conflict_check_id`は、どちらも外部キーを持たない。対象の行は作業項目の削除に連なって消えず、作業項目も行の掃除に連なって消えない。

| 列 | 意味 |
| --- | --- |
| `ci_check_id` | CIの失敗を直す回が直している`pr_ci_checks`の行のID。それ以外はNULL |
| `conflict_check_id` | マージの競合を直す回が直している`pr_conflict_checks`の行のID。それ以外はNULL。値は正の整数 |
| `conflict_episode` | 直している競合の回(`episode`)。`conflict_check_id`と同時に値を持ち、同時にNULLになる。値は1以上 |

1つの作業項目が直す対象は1つだけなので、`ci_check_id`と`conflict_check_id`は同時に値を持たない。
`ci_check_id`と`conflict_check_id`の索引には、値のある作業項目だけを入れる。
競合の1回は、行のIDと回の組で指す。行は競合が解けて再び競合しても同じ行のままで、回だけが進むためである。
`pr_conflict_checks`の列の意味は、[PRのCI監視の内部仕様](pr-ci.md)の「記録」にある。

### 進め方の列

作業項目は、進め方を`profile`列で持つ。
値は`standard`、`direct`、`bugfix`、`docs`のどれかで、既定は`standard`である。
種別がIssue以外の作業項目も既定値で埋まるが、意味を持たない。

値の一覧は、列のCHECK制約と`f/factory/lib/types.ts`の`WORK_ITEM_PROFILES`にある。
2つが食い違わないことは、`tests/scripts/profile_migration.test.ts`が確かめる。

行の読みは、`profile`を文字列のまま持つ。
一覧にない値の行も、読みを止めずに通すためである。
列が無い行は`standard`として読む。`f/`の反映がmigrationより先に走るので、その間も読みが失敗しないためである。

`profile`を書く処理は、要件定義の生成へ移す更新だけである。
この更新は、同じ文で`profile`を`standard`にする。
承認を省く進め方の実装が、要件の不足か保護パスの変更を報告したとき、作業項目は要件定義の生成へ移り、通常の進め方になるためである。
要件定義の生成へ移すUPDATEがすべて進め方を戻すことは、保護されたテスト`tests/scripts/profile_gate.test.ts`が固定する。
登録の`INSERT`は`profile`を名指しせず、新しい行は、すべて既定の`standard`になる。
受け付ける進め方は`standard`だけで、入口は他の値を断る([進め方ごとの承認](../security.md#進め方ごとの承認))。

値で挙動を変えるのは、承認の要否を引く関門だけである([実装フロー](implement.md)の「進め方と承認の要否」)。
`profile`を名指しして読む問い合わせは、再開の候補の問い合わせ(`listAutoRetryCandidates`)だけである。
関門に渡すためである。列を足すmigrationの反映より前に、この問い合わせが動くと失敗する。
`v_*`のviewには出さない。

要件定義の承認が要らない進め方を表に足すときは、`isReadyForImplement`、`implement_prepare`、`buildRestartContext`の3つの判定を揃える。
承認の行が無いときの扱いと、要件定義の下書きを実装に渡すかが、3つで同じになる必要がある。

### 手動投入の冪等キー

表`manual_intake_keys`は、手動投入の1回を表すキー、投入の内容のハッシュ、作ったIssueの所有者とリポジトリと番号、キーを予約したジョブのID、予約した時刻を持つ。
キーは小文字のUUIDだけを受け、作業項目とは外部キーを持たない。
表に触れるのは、Issueを作るステップ(`steps/manual_intake_create_issue.ts`)と、`cleanup_db`の削除である。
表を落とすdown migrationを当てる前に、この2つの読み書きも外す。表が無いと、Issueの作成と`cleanup_db`が毎回失敗するためである。

#### 予約の手順

キーを付けない投入は、表に触れず、Issueを作る。
キーを付けた投入は、許可の照合とリポジトリのオーナーIDの照合を済ませた後、Issueを作る直前に次の順で進む。

1. キーを予約する。`INSERT … ON CONFLICT DO NOTHING`で、予約したジョブのIDを持ち主に書く。
2. 衝突したときは、行を読む。
   - 内容のハッシュが違えば、`intake_key_conflict`で失敗する。
   - 番号があれば、Issueを作らず、行のリポジトリと番号を再利用として返す。
     フローは、再利用のとき登録のステップを飛ばす。
   - 番号が無く、予約から10分以内なら、`intake_key_in_flight`で失敗する。
   - 番号が無く、10分を過ぎていれば、1つの`UPDATE`で持ち主を自分に替えて予約を取り直す。
     取れなければ、`intake_key_in_flight`で失敗する。
3. 予約の後、Issueを作る前に、本文の末尾が目印の行である既存のIssueを探す。
   見つかれば、その番号を使い、作らない。
   目印は`<!-- factory:intake:<キー> -->`で、作るIssueの本文の末尾に付ける。
4. 作れたら、持ち主が自分である行に番号を書く。
   書けなくても、作ったIssueは返す。取り直したジョブが、目印で見つける。
5. 作るのに失敗しても、予約は消さない。

内容のハッシュは、リポジトリ、題名、本文、受入基準、進め方を正規化した文字列のsha256である。
正規化は、前後の空白を除き、改行をLFにそろえる。
例外のメッセージは固定文で、入力を含まない。
SQLは、パラメータを束縛するタグ付きテンプレートだけで書く。
時刻の比較は、DBの`now()`だけで行う。

#### 保持

保持期間は、予約した時刻から`retention_work_items_days`である。
`cleanup_db`が期限を過ぎた行を、状態にかかわらず消し、件数をログだけに残す。
消したキーの再送は、重複として止まらず、新しい投入として扱われる。

### 新しいサイクルによる取り消し

Issueの新しいサイクルの作業項目を挿入すると、同じIssueの古いサイクルの`approved`の作業項目を取り消す。
`approved`は終端で、稼働中のIssueの部分一意インデックスの対象外なので、承認済みの作業項目が新しいサイクルと並んで残るためである。
取り消すのは`cycle`が新しいサイクルより小さい項目だけで、イベントに行を残す。

挿入と取り消しは、別々に自動コミットされる2つの文である。
1つの文にまとめると、取り消しは文の開始時点のスナップショットを見るので、実行中にコミットされた承認を取り逃す。
取引で囲むと、承認から実装への移行の更新と、行のロックを逆の順に取り合ってデッドロックしうる。
挿入の後に取り消しが失敗しても、挿入は戻さない。警告を残し、取り消せなかった承認は次の新しいサイクルで取り消す。
それまでは、`retry_work_item`が新しいサイクルのある作業項目の再開を断る。

### 終端の一覧の同期

終端の状態の一覧は次の2か所にある。

- `f/factory/lib/types.ts`の`TERMINAL_WORK_ITEM_STATUSES`
- Data Tableのview`factory.v_lead_time`の`WHERE status IN (...)`

終端の状態を増やすときは、migrationで`v_lead_time`を`CREATE OR REPLACE`し、同じPRで`TERMINAL_WORK_ITEM_STATUSES`を更新する。
`poll_issues`のreconcileは終端の作業項目を照合の対象から外す(`listActive`)。片方だけを更新すると、完了した作業項目が孤児と判定されて失敗にされる。
例外は、要対応の終端の作業項目を取り消す専用の照合だけである。詳しくは「要対応の終端の取り消し」に書く。

## ジョブの記録

状態の遷移と失敗は、動いたWindmillのジョブに結び付ける。
Consoleは、このIDからジョブの画面(`/run/<job_id>`)へのリンクを作る。

| 記録先 | 列 | 値 |
| --- | --- | --- |
| `work_item_events` | `job_id` | 遷移を起こしたステップ(またはscript)のジョブID。環境変数`WM_JOB_ID` |
| `work_item_events` | `root_job_id` | そのステップを含むフローのルートジョブID。環境変数`WM_ROOT_FLOW_JOB_ID` |
| `job_failures` | `root_job_id` | 失敗を記録したジョブのルートジョブID。環境変数`WM_ROOT_FLOW_JOB_ID` |

`job_failures.job_id`は既存の列で、呼び出し側が渡す値を持つ。出どころによって指す先が違う。

- フローの失敗(`on_error_flow`)の行は、ルートのフローを指す。どのフローも`failure_module`から`job_id`を渡さないので、`root_job_id`と同じ値になり、失敗したステップのジョブIDは取れない。
- ステップやscriptの中で記録した行は、そのジョブのID(`WM_JOB_ID`)を持つ。該当のジョブの画面へ辿れる。
  記録するのは`poll_issues`、`poll_prs`、`requirements_apply`、`pr_fix_finish`、`issue_proposal_apply`などである。
- スケジュールの失敗(`detect_schedule_failures`)の行は、失敗したジョブのIDを`job_id`とルートのジョブIDに持つ。検出器自身のジョブIDではない。発生時刻は、失敗したジョブの完了時刻である。

取れなかったときは`unknown`が入り、Consoleには`null`で返す。

遷移を記録する`lib/db.ts`の関数が、入口で環境変数から読んで同じ文に書く。
呼び出し側は何も渡さない。
対象は、`updateStatus`と、`updateStatusIf`で始まる4つの比較交換と、新しいサイクルによる取り消し(`supersedeApprovedIssueWorkItems`)である。
失敗の記録(`recordFailure`)も同じ仕組みでルートジョブIDを書く。

読んだ値がUUIDの形でなければ、記録せずNULLにする。
フローの外のジョブでの`WM_ROOT_FLOW_JOB_ID`の値は、確かめていない。
未設定、空、UUIDの形でない値のどれでもNULLになるので、記録は壊れない。
migrationが書く行も、NULLになる。
`console_query`の`work_item_detail`は、DBから読んだ値がUUIDの形でなければNULLにして返す。
失敗の`job_id`の`unknown`も、NULLで返す。
値がリンクの一部になるため、書くときと読むときの両方で形を確かめる。

`work_item_detail`は、遷移を`transitions`に新しい順で最大100件返す。
要件定義の試行や実装のラウンドの行は、ジョブIDを持たない。
試行やラウンドの境は、遷移の時刻と、各行の`created_at`を突き合わせて読む。

### 反映の順序とリスク

`self_update`は、`f/`を反映した後にmigrationを流す。
列を足すmigrationが遅れるか失敗すると、新しいコードは存在しない列を指名してしまう。
失敗の記録(`recordFailure`)は、列が無いエラー(PostgreSQLのundefined_column)のときだけ、新しい列を含まない文で記録し直す。
失敗の記録が消えると、反映の遅れに気づけないためである。ほかのエラーは握らない。
状態の遷移の関数は、同じ回避を持たない。
その間は、遷移が列の欠落で失敗し、migrationが流れるまで作業項目の状態が進まない。
関数ごとに新旧2つの文を持つと、状態を移す文が重複して保守しにくくなるためである。
`console_query`の`work_item_detail`も新しい列を読むので、migrationが遅れる間は失敗する。作業項目の詳細の画面は、その間は取得の失敗を出す。
`reviews.result`も同じである。
`f/`の反映からmigrationまでの数秒の間は、`insertReview`が列の欠落で失敗する。
この窓は受け入れる。
失敗した作業項目は`retry_work_item`で再実行でき、再実行は投稿済みのレビューを再利用して記録し直すので、レビューが二重に投稿されることも、記録が失われることもないためである。

記録したジョブは、Windmillの保持期間を過ぎると画面が開けなくなる。
DBの記録の保持期間は[運用](../operations.md)の「保持期間」にある。
Windmillの保持期間のほうが短いと、古い行のリンクは開けない。

残る作業として、フローの失敗の行から該当のステップのジョブへ辿る仕組みがある。
失敗したステップのジョブIDを`failure_module`から渡す設計が要る。

## リース

作業項目の`flow_job_id`は、その作業項目を書き換えてよいフローの実行を表すリースである。
値はフローのルートジョブID(`WM_ROOT_FLOW_JOB_ID`)で、起動側が記録する`runFlowAsync`の戻り値と一致する。
リースは要件定義のフロー(pipeline)、設計フロー、実装フローが使う。

起動側は、記録済みの値がジョブIDの形でなければ、ジョブの状態を問い合わせずに記録が無いときと同じに扱う。HTTPエラーの応答本文をジョブIDとして記録しないためである。

### 要件定義フローのリース

pipelineの起動側は、`runFlowAsync`の戻り値を作業項目の`flow_job_id`に記録する。起動側は次の6つである。

- `poll_issues`
- `manual_intake_register`
- `retry_work_item`
- `requirements_apply`の却下
- `implement_finish`の要件不足による差し戻し
- `pr_fix_finish`の要件不足による差し戻し

pipelineの各ステップは、`flow_job_id`が自分のルートジョブIDで、作業項目が終端でないときだけ作業項目を書き換える(`f/factory/lib/pipeline_lease.ts`)。

準備ステップ(`pipeline_prepare`)は、作業項目と`req-<N>`のworktreeを触る前、起動側が記録するまで最大60秒待つ。2秒ごとに読み直す。起動から記録までの間、`flow_job_id`は空か前の実行のIDのままだからである。

空の`flow_job_id`を自分で取ることはしない。差し戻しの起動側は`flow_job_id`を空にしてから起動する。取り消しに失敗して残った古い実行が空のリースを取ると、起動側が記録する新しい実行を締め出してしまう。

待っても確かめられないとき、作業項目が終端になったときは、何も書かずに`skip`で終わる。失敗にはしない。

各ステップの書き換えは、`flow_job_id`が自分のIDのままであることを条件にした比較交換で行う。

| ステップ | 比較交換で行う書き換え |
| --- | --- |
| `pipeline_prepare` | attemptの保存(`setAttemptIfLeaseHolder`)、取り消し、要件定義の生成中への遷移 |
| `pipeline_generate` | 日次予算の超過による人の対応待ちへの遷移 |
| `pipeline_request_approval` | 承認待ちへの遷移 |

`pipeline_generate`は、試行ごとのディレクトリを空にする前と、ドラフトを保存する前にリースを確かめる。`pipeline_request_approval`は、承認依頼を記録する前に確かめる。どちらも、持っていなければ何もせずに終わる。

承認依頼を記録した後、承認待ちへの比較交換が一致しなければ、記録した依頼を期限切れにする。古いattemptのドラフトを承認できないようにするためである。人が先に承認か却下をしていれば、依頼は変えず、警告をログへ残す。

起動側が記録に失敗したまま残った作業項目は、reconcileが孤児として扱う。

### 設計フローのリース

設計フロー(`f/factory/design`)のリースは、pipelineと同じ規則である。
起動側は`requirements_apply`の承認の分岐で、入口が開いているときだけ設計フローを起動し、ジョブIDを`flow_job_id`に記録する。
実装の完了とPR修正の完了も、設計の不足を返した作業項目を設計中へ戻した直後に、設計フローを起動して記録する。
本番では開いていない。
再実行(`retry_work_item`)も、設計の承認が照合を通らない作業項目に限り、設計フローを起動する。
再実行できるのは止まった状態の作業項目だけで、設計中と設計の承認待ちは再実行できない。
設計中のまま別の実行にリースを渡さないためである。
設計の各ステップは、状態が設計中(`designing`)で、`flow_job_id`が自分のルートジョブIDのときだけ作業項目を書き換える。

| ステップ | 比較交換で行う書き換え |
| --- | --- |
| `design_prepare` | `design_attempt`の保存(`setDesignAttemptIfLeaseHolder`)、取り消し、人の対応待ちへの遷移 |
| `design_generate` | 下書きの保存(`saveDesignDraftIfLeaseHolder`)、人の対応待ちへの遷移、要件定義の生成中への戻し |
| `design_request_approval` | 設計の承認待ちへの遷移 |

設計が要件の不足を返したときの戻しは、リースを条件にした1文で、設計中から要件定義の生成中へ移す。
同じ文で`design_attempt`を0に、`flow_job_id`を空にする。`attempt`は、続けて起動するpipelineが進める。
手順と失敗時の扱いは[設計書の生成](design.md)の「要件の不足」に書く。

`attempt`を進める更新(`setAttemptIfLeaseHolder`)も、同じ文で`design_attempt`を0に戻す。
設計の試行は、要件定義の`attempt`ごとに数え直すためである。
`attempt`を進める経路は、設計と実装の要件の不足、PR修正の差し戻し、要件定義の却下、再実行のどれもこの更新を通る。
`design_attempt`は必須の列として読み、列が無い行を0とは扱わない。

設計フローも、リースを持たない実行はClaudeの実行、保存、worktreeの削除をしない。
`design_request_approval`は、承認依頼を記録する前に、リースと最新の下書きを確かめる。
承認待ちへの比較交換が一致しなければ、記録した依頼を期限切れにする。

### 実装フローのリース

実装フローでは、準備ステップ(`implement_prepare`)が自分でリースを取る。worktreeを触る前、次の条件を満たすときだけ、`flow_job_id`へ自分のIDを書き込む。

- 状態が実装中である。
- `flow_job_id`が空か、自分のルートジョブIDである。

書き込めなければ何もせずに終わる。そのとき、読み直した`flow_job_id`と自分のIDをログに残す。

Issueのcloseによる取り消しなどで、実行中にリースが別の実行に移ることがある。取り消し(`cancelJob`)の失敗は無視されるためである。そのため各ステップは、次の時点でリースを確かめ、失っていれば何もせずに終わる。

| ステップ | リースを確かめる時点 |
| --- | --- |
| `implement_generate` | Claudeを実行する前 |
| `implement_verify` | 各ラウンドの冒頭(worktreeに触れる前)と、各修正ラウンドの前 |
| `implement_finish` | 作業項目を読んだ直後と、外への副作用の直前 |

外への副作用は、commitとpush、worktreeとリモートブランチの削除、PRの作成と更新、`pr_url`の記録、ラベルの付与である。

### リースとほかの処理

| 処理 | リースの扱い |
| --- | --- |
| `retry_work_item` | 記録されたジョブがまだ動いているか、状態を読めなければ再実行を拒否する |
| `poll_issues`のreconcile | 読み取った時点の`flow_job_id`が変わっていないときだけ、失敗か取り消しにする |
| `poll_issues`の要対応の取り消し | 読み取った時点の状態と`flow_job_id`が変わっていないときだけ、取り消しにする。`retry_work_item`との競合では、先に書いた方だけが成功する |
| `on_error_flow` | 読み取った時点の`flow_job_id`が変わっていないときだけ失敗にする。pipelineと設計フローでは、`flow_job_id`が自分のルートジョブIDと一致するときに限る。空のときも書き換えない |
| Windmillのrerun | 新しいジョブIDで最初から走る。実装フローでは、準備ステップがリースを取れずに何もせず終わる |
| Windmillのrerunか画面からの直接の実行(pipelineと設計フロー) | ジョブIDが`flow_job_id`に記録されないので、準備ステップが何もせずに終わる。作業項目が終端ならすぐ終わり、そうでなければ記録を最大60秒待ってから終わる |
| Windmillのrestart | 途中のステップから新しいジョブIDで走るので、再開したステップの最初のリースの確認で何もせずに終わる |

rerunとrestartのどちらも、元の実行で進行中のClaudeの実行や検査を中断しない。再実行には`retry_work_item`を使う。

## reconcileと孤児の検出

`poll_issues`は5分ごとに、終端でないすべての作業項目を照合する(reconcile)。対象の種別は、issue、pr_review、pr_fix、audit、dependabotのすべてである。

ジョブの状態は`JobService.getJob`で読む。読んだ結果と、それに応じた判定は次のとおり。

| ジョブの状態 | 判定 |
| --- | --- |
| 実行中、またはキュー待ち | 何もしない |
| 完了し、取り消されたか失敗していた | 猶予を待たずに失敗にする |
| 完了し、成功していた | 猶予を過ぎたら孤児として失敗にする |
| `flow_job_id`が未記録か、取得が404 | 見つからないものとして、猶予を過ぎたら孤児として失敗にする |
| 404以外の取得の失敗 | 状態不明として、IssueとPRのcloseの検知を除いて何もしない |

猶予は、10分と`claude_timeout_sec`の2倍の大きい方である。経過時間は作業項目の更新時刻から数える。

取り消されたか失敗したジョブは、自分で終端の状態を書かない。そのため猶予を待たずに失敗とする。成功したジョブは、最後のステップがまもなく追いつくはずなので猶予を待つ。

IssueかPRが閉じられていれば、ジョブの状態にかかわらず作業項目を取り消しにする。PRのcloseにはマージを含む。監査の作業項目にはGitHubの対象が無いので、ジョブの状態だけを見る。

### 承認待ちの作業項目

承認待ち(`awaiting_approval`)と設計の承認待ち(`awaiting_design_approval`)の作業項目は、フローのジョブが完了したまま人の決定を待つ。
そのためreconcileは、この2状態にはジョブの生死と猶予による孤児の判定をしない。
IssueとPRのcloseだけを確かめる。

### 要対応の終端の取り消し

reconcileが照合するのは、終端でない作業項目だけである。
失敗(`failed`)、人の対応待ち(`needs_human`)、期限切れ(`expired`)になった後でIssueやPRが閉じられても、reconcileはその作業項目を取り消さない。
そのままだと、Consoleの要対応の一覧に保持期間のあいだ残る。
人が対応しないと決めた作業項目を一覧に残さないため、`poll_issues`は別の照合で、この3つの状態の作業項目を取り消しにする。

- 対象は、Consoleの要対応の一覧に出る作業項目である。
  監査の作業項目は、GitHubの対象が無いので含めない。
  次の作業項目は、一覧に出ないので含めない。
  - 同じIssueに新しいサイクルがある作業項目
  - 同じ種類で、同じPRに新しい行がある作業項目
- IssueかPRが閉じられていて、閉じた人が許されるときだけ取り消しにする。
  PRのcloseにはマージを含む。
  閉じた人は、IssueまたはPRの取得の応答だけで、次の順に確かめる。
  1. PRで`pull_request.merged_at`があれば許す。マージにもmerge queueへの投入にも、write権限が要る。
  2. `closed_by`が無いときは許さない。
  3. `closed_by`がBotのときは許さない。
  4. 作者が分からないときは許さない。
  5. 作者以外の人が閉じたときは許す。
  6. 作者が閉じたときは、作者の`author_association`が`allowed_labeler_associations`に含まれるときだけ許す。

  許されないときは、取り消さず要対応に残す。
  理由(`no_closer`、`bot_closer`、`author_unknown`、`author_not_allowed`など)と対象は、infoのログに出す。
  理由は[セキュリティ](../security.md)に書く。
- 状態の注記は`reconcile: closed (actionable)`か`reconcile: pr_closed (actionable)`にする。
- 状態の遷移は、読み取った状態と`flow_job_id`のままのときだけ行う。
  `retry_work_item`が先に再開していれば、何も書かない。
- ジョブを止める操作はしない。
  終端の状態は、フローの最後のステップかエラー処理が書くので、止めるべき動いているジョブが無いためである。
- PRが閉じられたときは、レビューのworktreeを消す。
  消すのは、リポジトリの親の直下にあるdetachedの`review-<PR番号>-<sha7>`だけである。
  パスは文字列の前方一致で比べる。workerの`/workspaces`はボリュームのマウント先そのものなので、cloneのパスと一覧のパスは同じ綴りになる。違う綴りで返されたときは、警告のログを出し、何も消さない。
  同じPRに終端でない`pr_review`か`pr_fix`の作業項目があるときは消さない。
  取り消さなかったPRのworktreeは、この照合では消えない。
  `cleanup_workspaces`が、終端の作業項目が`worktree_ttl_days`(既定7日)更新されなければ、PRが閉じたかどうかによらず消す。
  この確認とworktreeの削除の間は、ロックで守らない。
  その間に閉じたPRで手動の再開をすると、作られたworktreeが消えうる。
  時間幅が狭く、閉じたPRでの手動の再開に限る。
- Discordには通知しない。
  人が対応しないと決めた後の片付けで、通知は雑音になるためである。
  ログと状態の注記だけを残す。
- GitHubへの問い合わせに失敗したときは、作業項目のIDを付けずに`job_failures`へ記録する。
  IDを付けると、要対応の一覧が最新の失敗としてその記録を表示し、元の失敗の理由を隠すためである。
  対象は記録のstepに入る`owner/repo#番号`で追える。
  対象の削除やアクセスの喪失(404と410)は、失敗として記録せず、警告のログだけを残す。
- stale Botが閉じた対象や、依存更新のBotが自分のPRを閉じた対象は、取り消されずに毎回調べ直される。

Issue化の提案を待つ`pr_fix`の`needs_human`も、PRが閉じられれば取り消す。
提案の承認依頼は取り消さず、人が決められる状態のまま残す。
決定後の状態の更新は`needs_human`からの比較交換なので、取り消された作業項目は取り消されたままで、壊れない。

取り消した作業項目は、`retry_work_item`で取り消す前の状態として再開できる。
対象は、最新の遷移の注記が上の2つのどちらかで、取り消す前の状態が要対応の3つのどれかのものだけである。
ほかの理由の取り消しは、再開できない。
`pr_review`と`pr_fix`の行は、同じ種類・同じPRで`id`の大きい行があるときも再開できない。
取り消した後にラベルが付け直されて、新しい行が追跡しているためである。
基準は、要対応の一覧が引き継ぎ済みとする行の条件である。
再開するフローと遷移先は、取り消す前の状態の作業項目を再開するときと同じである。
状態の更新は`cancelled`からの比較交換なので、同時に実行されても片方だけが成功する。
この再開に限り、`retry_work_item`は対象のIssueやPRが開いているかをGitHubで確かめる。
閉じたままで再開すると、作業項目は終端でない状態に戻り、reconcileが再開できない注記で取り消す。
取り消す前の状態からの再開が二度とできなくなるので、閉じているときと、開いているか確かめられないときは、再開を断る。
断る場合は、状態を書き換えない。
確かめるときは、Console用のworkerに`gh`が無いため、`github_token`を読み、`fetch`で状態を取る。
リダイレクトは辿らず、Issueの移動やリポジトリの改名で返る3xxは、移転の理由を示して断る。
ほかの再開は、GitHubに依存しない。
開いていることの確認と状態の更新の間に対象が閉じられると、通常のreconcileが取り消し、取り消す前の状態からは再開できなくなる。
この窓は数秒で、新しいサイクルにしたいときは、ラベルを付け直す。
要対応のまま(取り消されていない)の作業項目を、対象が閉じたまま`retry_work_item`で再開した場合も、通常のreconcileが取り消すので、先に対象を開き直す。

取り消した作業項目は`cancelled`として集計される。
`updated_at`も取り消した時刻に更新される。
そのため、保持期間とリードタイム(`v_lead_time`)は、閉じた時刻ではなく取り消した時刻から数える。
照合は5分ごとに動くので、差は通常、数分である。問い合わせの上限で次の実行に回ると、その分だけ延びる。

PRを開き直しても、取り消した作業項目の追跡は自動では戻らない。
`poll_prs`は`cancelled`のPRを追わないためである。
PRは、開き直してから`retry_work_item`で再開する方法を勧める。
トリガーラベルの付け直しと再開の両方を行うと、同じPRに作業項目が並んで動くので避ける。
ラベルの付け直しは、取り消す前の状態からの再開ができないとき(ほかの理由で取り消した作業項目など)に使う。

問い合わせの上限と順番は次のとおり。

- GitHubへの問い合わせは1回の実行で30件の対象までにする。
  対象ごとにIssueかPRの取得を1回行い、閉じた人もこの応答で確かめる。
  同じPRのレビューと修正の行は、1つの対象として問い合わせる。
- 上限に達したら、次の対象から次の実行に回し、警告のログを出す。
- 取りこぼしが続かないよう、最後に調べた対象のIDを`poll_issues`のstateに保存し、次の実行はその続きから始める。
  末尾まで進んだら先頭に戻るので、対象が開いたまま残っても全件を一巡する。
- stateを読めないときは先頭から始める。
- GitHubのrate limitを受けたら、その回の問い合わせを打ち切り、カーソルをその対象の直前に置く。制限の間の問い合わせと、後ろの承認依頼の期限切れの遅れを避けるためである。
- 失敗は、1回の実行につき1行だけ`job_failures`に記録する。最初に失敗した対象のキーで記録し、ほかにも失敗した対象があれば、件数を理由に含める。GitHubの障害の間に、同じ原因の行が対象の数だけ増えないようにするためである。

reconcileの後、`poll_issues`は承認依頼の期限切れを判定する。仕組みは[要件定義の生成と承認](requirements.md)に書く。
