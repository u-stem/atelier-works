# PRのCI監視の内部仕様

`watch_pr_ci`が、Factoryが作ったPRと許可された人が作ったPRのCIを何で読み、どう判定し、何を通知するかを定める仕様である。
失敗を直す作業項目を、いつ起動するかも定める。
Factoryが作ったPRのマージの競合を検知する`watch_pr_conflicts`も、[競合の検知](#競合の検知)に定める。
`watch_pr_ci`、`lib/pr_ci_watch.ts`、`lib/pr_ci_support.ts`、`lib/pr_ci_fix_claim.ts`を変更する人が読む。
人のPRの判定は`lib/pr_ci_human_support.ts`にある。
必要な権限は[セキュリティ](../security.md)に、通知を受けた人がすることは[運用](../operations.md)に書く。mainのCIは[mainのCI監視の仕様](main-ci.md)に分けて書く。失敗のログを整形してClaudeに渡す部品は、[CIの失敗を直す部品の仕様](ci-fix.md)に分けて書く。

## 方針

失敗を通知し、設定で有効にしたときは、失敗を直す作業項目も起動する。
自動で直す対象の失敗は、確定した時点では通知せず、直せるかが決まってから通知する。
設定で有効にしたときは、許可された人が作ったPRの失敗も通知する。人のPRの失敗は、確定した時点で通知し、直す作業項目は起動しない([人が作ったPR](#人が作ったpr))。
`watch_pr_ci`は、PRとリポジトリへは書き込まず、ワークフローのログも読まない。ログを読んで直すのは、起動した作業項目(PRワークフローのCI回)である。
記録は`factory.pr_ci_checks`に残す。作業項目へ触れるのは、起動で作業項目を挿入するときと、フローの起動に失敗した作業項目を`failed`にするときだけである。リードタイムには触れない。
失敗を直す作業項目が終わった行を戻す回復は、`pr_ci_checks`の行だけを書き換える。
1回の実行は、発見、回復、判定、起動、人のPRの発見、保留した失敗の通知の順に進む。
`pr_ci_watch_enabled`が`false`のときは、回復、保留した失敗の通知の順に進む。
監視の単位は、PRの今のheadのコミットである。行は`(owner, repo, pr_number, head_sha)`で一意になる。
通知には、PR、コミットの先頭7文字、理由コード、次の操作、実行のURLだけを載せる。
自動修正を保留した理由があれば、その理由コードも載せる。

## 対象

次の条件をすべて満たすPRだけを見る。

1. 作業項目が、種別`issue`で、状態が`pr_open`で、`pr_url`を持つ。更新が`tracked_pr_days`以内のものを、新しい順に最大50件取る。
2. PRのリポジトリが、許可リスト(`isRepoAllowed`)に合う。`owners`は、`id`の照合を通ったものだけを渡す。名前が付け替えられたアカウントのリポジトリを読まないためである。
3. PRが開いていて、下書きでなく、headのリポジトリがベースと同じである。forkと、削除されたforkのPRには、行を作らない。
4. headのブランチ名から引いた作業項目が、このPRを指している(`isFactoryPrBranch`)。同じ形の名前のブランチを作った人のPRを、Factoryのものとして扱わないためである。

ここまでの条件は、Factoryが作ったPRの条件である。人が作ったPRは[人が作ったPR](#人が作ったpr)で別に扱う。
`pr_open`は終端で、PRが閉じても作業項目は変わらない。更新の期間で絞らないと、閉じたPRを毎回読み続けるためである。
更新が期間より古い作業項目のPRは、新しいheadを追わない。ただし、記録済みの行は、後で述べる読み直しで引き続き扱う。

## 人が作ったPR

設定`pr_ci_watch_human_prs`が`true`のときだけ、許可された人が作ったPRも見る。
既定は`false`である。`pr_ci_watch_enabled`が`false`のときは、`true`でも見ない。
人のPRの行は、`pr_ci_checks.work_item_id`が空である。出所を表す列は足さない。
行を記録するのは、FactoryのPRの発見(常に作業項目のIDを入れる)と、人のPRの発見の2か所だけである。

人のPRには、直す作業項目を起動せず、PRへ書き込まない。
人が直しているPRにFactoryが同時にpushすると、2者が同じ失敗を直すためである。
失敗の通知は、自動修正の設定に関わらず、確定した時点で出す。

### 対象

次の条件をすべて満たすPRだけを記録する。

1. 作者が許可された人である(`isAllowedPrAuthor`)。
   PATのアカウントか、`allowed_labeler_logins`に載るアカウントで、種別が`User`であること。
   `allowed_labeler_ids`に載る名前は、数値のIDも一致すること。
   載っていない名前は、名前だけで通す。通知だけに使うためである。
2. 開いていて、下書きでなく、headのリポジトリがベースと同じである。
3. headのブランチ名が`factory/issue-<N>-wi-<id>`の形でない。
   PATのアカウントはFactoryのPRの作者でもあるので、作者では除けない。
4. 追跡対象の作業項目が指すPRでない。
5. リポジトリが、許可リストに合う。

draw.ioのビューアの固定を上げるPRのブランチは、Factoryの実装ブランチの形ではないので除かない。
通知してよいPRだからである。

### 発見

人のPRの発見は、起動の後、保留した失敗の通知の前に行う(`discoverHuman`)。
FactoryのPRの判定と起動が、人のPRの発見に時間を使われたり止められたりしないためである。
そのため、新しく記録した人の行の判定は、次の回になる。
全体の経過時間の予算の残りと、人のPRの発見だけの予算(30秒)のうち、先に尽きた方で止める。

1. 検索する範囲を決める。照合を通ったオーナーごとに1つ、`factory_repo`のオーナーがその中に無ければ`factory_repo`のリポジトリを足す。
2. 範囲と作者(PATのアカウントと`allowed_labeler_logins`)の組ごとに、1回検索する。
   条件は、作者が合い、開いていて、下書きでないPRである。
   更新が新しい順に、1ページ(100件)だけ読む。
   作者とオーナーの名前は、検索の修飾子が紛れ込まないよう、名前の形を検査する。
3. 全部の検索結果を、範囲と作者をまたいで、更新の新しい順に並べ直す。
   範囲ごとに処理すると、先の範囲にある更新の止まったPRが枠を埋め、後の範囲の新しいPRを見落とすためである。
4. 見つかったPRを順に読む。rate limitの解除を待たない読み取りを使う。
   この回の判定は終わっているので、読んだPRは再利用しない。
   許可リストに合わないリポジトリは、読まずに捨てる。
5. 対象の条件に合わないPRを捨て、合ったPRのheadの行を記録する。古いheadの行の整理は、FactoryのPRと同じである。
6. 新しく行を記録したPRと、`superseded`の行を`pending`に戻したPRが、合わせて20件に達したら、残りは読まない。
   記録済みでheadが動いていないPRは数えない。数えると、赤い人のPRが20件を超えたときに、同じ上位20件が毎回枠を埋め、残りが通知されないためである。
7. 読む数は、1回の実行で60件までである。数えない記録済みのPRを読み続けて、時間を使い切らないためである。

検索は、rate limitの解除を待たない。
検索がrate limitで拒まれたら、残りの検索を止める。
PRの読み取りがrate limitで拒まれたときも、残りのPRの読み取りを止める。
どちらも全体のrate limitにはしない。
範囲がオーナーで、一部の作者だけが検索で422になったときは、作者の改名や削除とみなす。
その作者の検索を飛ばし、範囲と作者を警告のログに1行残す。毎回の失敗としては記録しない。
範囲がリポジトリのときと、範囲の全員が422になったときは、原因が範囲にあるおそれがあるので、失敗として記録する。
ほかの検索の失敗は、手順名`search_human_prs`で記録し、次の検索へ進む。

### 判定と通知

判定は、FactoryのPRの行と同じ手順で行う。
通知の方針だけが違い、人の行は自動修正が無効のものとして扱う(`notifyPolicyFor`)。
そのため、失敗は確定した時点で、保留なしで通知する。通知の文面はFactoryのPRと同じである。
人の行に限り、新しいheadの失敗を通知する前に、同じPRの古いheadの失敗のnoticeを解決する。
人のPRでは、直した後も新しいheadの失敗が続きうる。古いnoticeを残すと、1つのPRに未解決のnoticeが重なるためである。
今のheadのnoticeは解決しない。通知をやり直した回に、同じ本文が重複と見なされ、Discordが重ならないためである。
先頭7文字が今のheadと同じheadも解決しない。本文はコミットを先頭7文字で表すので、今のheadのnoticeに当たるためである。
解決に失敗しても、失敗を手順名`resolve_older_notices`で記録して、通知へ進む。
FactoryのPRの行は、この解決をしない。

判定する行の並びは、FactoryのPRの行を先、人の行を後にする。
人の行は、1回の実行で40件(`HUMAN_RECHECK_LIMIT`)までを、読み直していない順に判定する。判定待ち、失敗、実行なしの合計である。
超えた分は書き換えず、次の回に回す。
人の行が、FactoryのPRの行の判定の時間と、PATのcoreの枠を際限なく分け合わないためである。
FactoryのPRの行の順序と件数は変えない。

起動の候補は、`work_item_id`が空でない行に限る(`listClaimablePrCiChecks`)。
人の行が、起動の候補の枠を食わないためである。
人のPRは、起動の判断が読むPRの集合(その回の発見でFactoryのブランチと確かめたPR)に入らないので、構造上も起動しない。

閉じたPRと、headが進んだ行の整理は、FactoryのPRと同じである。
設定`pr_ci_watch_human_prs`を`false`に戻しても、記録した行は読み直す。
PRが閉じる、headが進む、通るのどれかになるまで続ける。上限は`HUMAN_RECHECK_LIMIT`のままである。
失敗の行は期限切れにしない。

## 状態

`pr_ci_checks.state`の値は次のとおりである。

| 状態 | 意味 | 通知 |
| --- | --- | --- |
| `pending` | 実行を読み直して判定を待っている | しない |
| `passed` | 全実行が完了し、結論がsuccess、skipped、neutralだけ。終端 | しない |
| `failed` | 完了した実行に失敗がある。再実行で通れば`passed`に戻る | する。自動で直す対象は、直せるかが決まってから |
| `superseded` | headが進んだか、PRが閉じた | しない |
| `expired` | 未完了のまま最古の実行から2時間たったか、読めないまま24時間たった。終端 | しない |
| `no_ci` | 実行が現れないまま15分たった。実行が現れれば読み直す | しない |
| `observed` | 遷移表にはあるが、この監視は使わない | しない |
| `fixing` | 失敗を直す作業項目の結果待ち。`claimPrCiCheckForFix`だけが`failed`から移す。判定で実行を読み直さず、回復が行き先を決める | しない |

遷移は`canTransitionPrCi`が定める。更新は`WHERE state = <移る前の状態>`の条件付きで、別の実行が先に移した行は書き換えない。
`transitionPrCiCheck`は`fixing`への移行を拒否し、`claimPrCiCheckForFix`だけが行う。
作業項目の挿入と同じ1つのSQL文で行う必要があるためである。
`fixing`からは、`failed`、`superseded`、`passed`へ移れる。
`fixing`から出る移行は、`fix_work_item_id`を空にする。

## 失敗を直すための状態と関数

失敗を直す作業項目のために、`pr_ci_checks`は次の3列を持つ。
外部キーは無い。作業項目は行の削除に連なって消えず、行も作業項目の削除に連なって消えない。

| 列 | 意味 |
| --- | --- |
| `fix_work_item_id` | いま直している作業項目のID。`fixing`の間だけ値を持つ |
| `fix_attempts` | 同じheadで、直す作業項目を起動した回数。既定は0 |
| `fix_hold_reason` | 起動を保留している理由コード。保留していなければNULL。空でなく、64字まで |

`work_items`は、列`ci_check_id`(bigint、NULL可)と、値のある行だけの部分索引を持つ。
直す作業項目だけが、直す行のIDを入れる。それ以外の作業項目はNULLである。

`lib/db.ts`の関数の責務は次のとおりである。

| 関数 | 責務 |
| --- | --- |
| `claimPrCiCheckForFix` | `failed`の行を`fixing`にし、直す`pr_fix`の作業項目を挿入して、そのIDを返す。起動できなければNULLを返す |
| `countPrCiFixRounds` | そのPRで、直近の`passed`の行より後に起動した、直す作業項目の数を返す |
| `listFixingPrCiChecks` | `fixing`の行を、リポジトリの発見に頼らず、読み直していない順に返す |
| `findOrphanFixingPrCiChecks` | 直す作業項目に結ばれていない`fixing`の行を返す |
| `releaseFixingPrCiCheck` | `fixing`の行を`failed`に戻す。保留の理由も書ける |
| `setPrCiFixHold` | `failed`の行の保留の理由を設定する。NULLで解除する |
| `isLatestMainCiRunFailed` | そのリポジトリのmainのCIの最新の記録が、失敗かを返す |

`claimPrCiCheckForFix`は、行の更新と作業項目の挿入を1つの文で行う。
同じ行を1つの文で2回更新できないので、作業項目のIDを先にシーケンスから取り、行の`fix_work_item_id`と作業項目の主キーの両方に使う。
次のどれかなら、何も書かずにNULLを返す。

- 行が`failed`でない。
- 行の`head_sha`が、呼び出し側が読んだPRのheadと違う。
- 行が保留されている。
- 同じPRに、終端でない`pr_fix`の作業項目がある。同じブランチへ別々にpushして競合するのを防ぐためである。

確認をすり抜けた並行する起動は、部分一意索引`work_items_active_pr_fix_key`が拒む。
違反は文全体を取り消すので、行は変わらずNULLを返す。
作業項目は、種別`pr_fix`、状態`fixing`、サイクルと試行は1で挿入する。
ラウンドの番号(`fix_round`)と処理済みの位置は、同じPRの直近の`pr_fix`から写す。
処理済みの位置は、`last_review_id`、`last_comment_id`、`last_review_comment_id`の3列である。
直近の`pr_fix`が無ければ、すべて0にする。直す作業項目は、ラウンドの番号も処理済みの位置も進めない。
完了のステップでも、作業項目の`head_sha`を更新しない([PRワークフロー](pr-workflow.md)の「CIの失敗を直す回」)。
ownerとrepoは、行との照合では小文字で比べる。
作業項目には、`poll_prs`が`startFix`に渡すownerとrepo(検索結果の`repository_url`由来)と同じ綴りを渡す。
一意索引と既存の照合が大文字小文字を区別するためである。

`countPrFixFailures`は、`ci_check_id`を持つ作業項目を数えない。
指摘への対応の失敗から、モデルを`heavy_model`に上げるかを決める。この判定に、CIの失敗を直す作業項目の失敗を混ぜないためである。

`fixing`の行は、掃除(`deletePrCiChecksBefore`)が削除しない。
`touchPrCiCheck`は`fixing`の行も読み直した時刻を進める。

## 保留の理由の語彙

`fix_hold_reason`に書く値は、`lib/pr_ci_support.ts`の`PR_CI_FIX_HOLD_REASONS`の13個に限る。
DBの検査は長さだけなので、書く側をこの型で縛る。
値ごとの性質と、人が次にすることの固定文は`prCiFixHoldInfo`が返す。
固定文は2種類ある。
常体の`nextAction`は、理由コードごとの案内と同じ文体である。
敬体の`stopAction`は、直す作業が止まった通知に載せる。
どちらも、1つの文字列の中で文体を混ぜない。
決定的な理由は、同じheadでは起動し直さない。headが進んで新しい行になるまで残る。
一時的な理由は、解ければ外してよい理由である。起動の判断が毎回見直し、解ければ外す([起動](#起動))。

| 理由 | 種類 | 意味 |
| --- | --- | --- |
| `unfixable_job` | 決定的 | 失敗したジョブに名前が無く、直せる種類を決められない |
| `metadata_manual` | 決定的 | `metadata`ジョブの失敗を、再計算では直せない。原因は、事前検査が通らない(依存や入力の`schema`が変わる、mainの先端を含まないなど)、再計算しても本文が変わらない、lockを書き込めない、再計算の途中でbaseが動いた、のどれかである。種別は作業項目の理由に残る |
| `other_conclusion` | 決定的 | 失敗ではなく、取り消しや期限切れなどで終わった |
| `log_unavailable` | 決定的 | 失敗のログを読めない |
| `fix_stopped` | 決定的 | 直す作業項目が、pushしないまま人の判断待ちで止まった |
| `rounds_exhausted` | 決定的 | 直す回数の上限に達した |
| `not_factory_head` | 決定的 | 最後のpushがFactoryのものでない |
| `marker_missing` | 一時的 | Factoryのクローンのスキルが、CIの失敗を直す節を持たない。スキルが入れば外れる |
| `main_ci_failed` | 一時的 | mainのCIが赤い |
| `budget_exceeded` | 一時的 | 日次の予算を使い切った |
| `not_reviewed` | 一時的 | 今のheadの自動レビューがまだ無い |
| `last_fix_unsettled` | 一時的 | 直近の直す作業項目が、まだ終わっていない(動いている) |
| `pr_draft_or_auto_merge` | 一時的 | PRがドラフトか、auto-mergeが有効である |

noticeを出す時機は、決定的な理由なら保留した時点、一時的な理由なら保留が続いたときである。
一時的な保留は、解ければ何も知らせずに済むためである。
保留が続いたと見なす時間は、`not_reviewed`と`last_fix_unsettled`では`claude_timeout_sec`の2倍、ほかの一時的な理由では30分になる。
自動レビューや直す作業項目が走っている間は、この2つが長く続いても異常でないためである。
Discordも送るかは理由ごとに決める。`fix_stopped`は、止めた`pr_fix_finish`がすでに送っているので、noticeだけにする。
通知の手順は[保留した失敗の通知](#保留した失敗の通知)に書く。

## 回復

回復は、直す作業項目が終わったのに`fixing`のまま残る行を、`failed`か`superseded`に戻す。
作業項目は行を戻さないので、監視が戻す。戻さないと、行が`fixing`のまま残る。残った行は、判定されず、通知されない。`claimPrCiCheckForFix`の対象にもならない。
回復は発見の後、判定の前に行い、設定`pr_ci_watch_enabled`が`false`でも動く。
作業項目の起動はしない。
`false`のときは、発見と判定と失敗の通知をしない。オーナーの照合はせず、設定の`owners`と`repo_allowlist`に合うリポジトリのPRを読む(`buildRecoveryRepoGates`)。
照合はGitHubの呼び出しとnoticeの追加を伴うためである。
照合に伴うnoticeは足さないが、回復がPRを読めず403か404になると、権限の不足のnotice(`pr_ci_check_denied`)は足しうる。
このnoticeを解決するのは判定なので、`false`の間は解決されない。
行を戻すPRが閉じていたら、`false`のときでも閉じたPRを整理する。失敗のnoticeを解決し、そのPRの未完了の行を`superseded`にする。
対象は、`listFixingPrCiChecks`が返す行と、`findOrphanFixingPrCiChecks`が返す行を合わせたものである。
前者は最大100件、後者は最大50件を、読み直していない順に取る。
作業項目に結ばれていない行(`fix_work_item_id`が空)は、`updated_at`から10分以上たったものだけを扱う。起動の直後の行を戻さないためである。

行ごとに、作業項目の状態を先に読み、PRのheadを後で読む(`decideFixingRecovery`)。
先にPRのheadを読むと、読んでいる間に作業項目がpushした場合に、古いheadの行を`failed`に戻してしまうためである。

| 作業項目 | 行の行き先 |
| --- | --- |
| 動いている(終端でない) | そのままにする。読み直した時刻だけを進める |
| pushした(`rereview_requested`か、直す回がpushしたcommitを記録している) | `superseded`にする。PRのheadは読まない。headの読み遅れで、古いheadの行を起動し直さないためである |
| イメージが古い理由(自動の再開の対象の理由)で`blocked`になった | 止まってから24時間は戻さない。24時間後に保留なしで戻す。保留の理由ではなく、人がイメージを作り直す猶予である |
| それ以外の`blocked` | 止めた理由を保留の理由に写して`failed`に戻す。写せなければ、保留なしで`failed`に戻す。起動し直す回数は、直す回数の上限が止める |
| `needs_human` | 止めた理由を保留の理由に写して`failed`に戻す。写せなければ`fix_stopped`にする |
| 存在しない、または上の行に当たらない終端の状態(`failed`、`cancelled`、`expired`、`reviewed`、`approved`、`rejected`など) | 保留なしで`failed`に戻す |

24時間待つのは、待たずに戻すと、同じ理由で止まる回を重ねて、直す回数の上限を使い切るためである。
CIの回は自動の再開の対象外なので、この間に作業項目が再開されることはない。
`pr_fix`が`cancelled`になるのはPRが閉じたときだけである。
設定から外れたリポジトリを除き、閉じたPRは、戻す前のheadの読み取りが拾う。
そのため`cancelled`は保留しない。

既知の競合がある。
`poll_issues`は、PRが閉じた`pr_fix`を`cancelled`にする。
この後、回復が走る前にPRを開き直すと、`needs_human`から取り消された回の`fix_stopped`は消えて、保留なしで`failed`に戻る。
同じheadでCIの直しが再び起動しうる。起動し直す回数は、直す回数の上限が止める。
CIの回は`retry_work_item`が再開を断るので、作業項目が二重に起動することはない。

`failed`などに戻す前に、PRのheadを読む。
headが行のheadと違えば、戻さず`superseded`にする。PRが閉じていれば、閉じたPRの整理に任せる。
rate limitと権限の不足で読めない回は、行を動かさず、読み直した時刻だけを進める。
許可リストに合わないリポジトリは読まない。
設定から外れたリポジトリ(`isRepoConfigured`が偽)は、そのまま戻す。
監視が有効なら、戻した`failed`の行を続く判定が扱う。判定は、最初に見てから24時間たった行を`superseded`にし、そうでなければ読み直した時刻だけを進める。
監視が無効のときは判定が動かないので、戻した行は`failed`のまま残る。
設定には合うが照合を通っていないリポジトリは、照合が一時的に失敗しているだけの場合がある。
headが動いたか分からないまま戻すと古いheadの行を再び直しうるので、行を動かさず、読み直した時刻だけを進めて次の回に回す。
監視が無効のときは照合をしないので、設定に合うリポジトリはすべて読む。

止めた理由を保留の理由に写すのは、固定文への先頭一致か完全一致だけである(`holdReasonForStoppedItem`)。
部分一致は使わない。Claudeの出力は、止めた理由の中で`ci round: claude blocked:`の接頭辞の後ろに置かれ、固定文と一致しない。
固定文の前後に別の文字列が付いた理由も、一致しない。
そのため、Claudeやログに由来する文字列では、保留の理由を選べない。
写す固定文は、`lib/ci_fix_round.ts`の`CI_ROUND_DETAILS`が止める側と共有する。

| 止めた理由 | 保留の理由 |
| --- | --- |
| スキルにCI回のマーカーが無い | `marker_missing` |
| ジョブの名前が無く、直せる種類を決められない | `unfixable_job` |
| `metadata`ジョブの失敗を、再計算では直せない | `metadata_manual` |
| 完了のステップが、pushの直前に、baseの先端が動き、再計算の結果が確認済みの本文と合わなくなったと判断した(`CI_ROUND_REHASH_STALE_REASON`) | `metadata_manual` |
| ジョブが失敗でなく、ほかの結論で終わった | `other_conclusion` |
| トークンがログを読めない、ログが取得できない | `log_unavailable` |
| 日次予算の超過 | `budget_exceeded` |
| PRがドラフトか、auto-mergeが有効 | `pr_draft_or_auto_merge` |

保留なしで戻した行は、直す作業を起動し直せる。
直す回数の上限(`pr_ci_fix_max_rounds`)が、起動し直しの歯止めになる。

## 起動

起動は、失敗した行を直す作業項目(`pr_fix`のCI回)を起動する。
判定の後に行い、`PrCiWatchDeps.claim`を渡したときだけ動く。
`watch_pr_ci`は、設定`pr_ci_watch_enabled`と`pr_ci_fix_enabled`がどちらも`true`のときに渡す。
回復だけを行う実行(`pr_ci_watch_enabled`が`false`)は、起動しない。
自動で直す対象の失敗の通知は、起動の判断の結果が出てから出す([保留した失敗の通知](#保留した失敗の通知))。

### 候補

候補は`listClaimablePrCiChecks`が、読み直していない順に最大50件返す。次をすべて満たす行である。

- `failed`である。
- 最初に見た時刻(`first_seen_at`)が、`pr_ci_fix_enabled_since`以後である。
- 保留が無いか、保留の理由が一時的である。決定的な理由の行は返さない。

候補のうち、次の行は扱わない。

- その回の発見で読んでいないPRの行。発見は、同じリポジトリのheadで、ブランチが作業項目のものであることを確かめる。
- その回の回復が`failed`に戻した行。戻した直後の状態で、すぐ起動し直さないためである。

扱わなかった行も含めて、見た行は、結果にかかわらず読み直した時刻を進める。進めないと、同じ行が先頭に残り続け、後ろの行が判断されないためである。

### 判断

判断は`decideFixClaim`が行う。次の順に確かめ、最初に当たったもので止める。
作業項目の状態を先に読み、PRを後で読む。読んでいる間に作業項目がpushすると、先に読んだPRのheadは古くなるためである。

1. 通知した理由が`ci_other_conclusion`なら、`other_conclusion`で保留する。
2. そのPRに、終端でない直す作業項目があれば、`last_fix_unsettled`で保留する。
3. 行のheadのレビューの行(`factory.reviews`の`head_sha`)が無ければ、`not_reviewed`で保留する。
4. PRを読み直す。閉じていれば、行のheadから進んでいれば、何もしない。ドラフトか、auto-mergeが有効なら、`pr_draft_or_auto_merge`で保留する。
5. PRのすべてのcommit(250件まで)の本文の最後の段落に、次の行が無ければ、`not_factory_head`で保留する。
   `Generated-By: Software Factory (<instance_name>)`
   250件に達したときも保留する。
   トレーラーの無いcommitを含むPRは、自動で直さない。commitのauthorは、人が同じアカウントでpushしても同じになるので使わない。
6. 失敗したジョブを分類する。
7. `metadata`だけの失敗でなく、factory-fixスキルがCI回のマーカーを持たなければ、`marker_missing`で保留する。
   `metadata`だけの失敗は、Claudeを使わないので、マーカーを確かめない。
   マーカーは、Factoryのリポジトリの`factory_branch`にあるファイルをGitHubのAPIで読んで確かめる。`pr_fix`の準備は、毎回`factory_branch`をfetchしてhard resetするので、cloneのスキルは準備の時点の`factory_branch`と同じになる。
   APIで読んだ値とcloneの値がずれるのは、起動から準備までの数秒の間にスキルが変わったときだけである。
   その間に`pr_fix`が止まると、回復が`marker_missing`を書く。次の巡回で保留が外れて起動し直し、`pr_ci_fix_max_rounds`に達すると`rounds_exhausted`で保留する。損失は最大でも1ラウンド分である。
   ファイルが無いときも、マーカーが無いものとして扱う。スキルが入れば、毎巡回の見直しで外れて起動できる。
8. 分類の結果で止める。名前が無く種類を決められないなら`unfixable_job`、失敗でない結論なら`other_conclusion`で保留する。失敗したジョブが無ければ、何もしない。
9. 日次の予算を使い切っていれば`budget_exceeded`で保留する。
   `metadata`だけが失敗しているときは、Claudeを起動せずhashの再計算で直すので、予算では保留しない。
   `check`などが同時に落ちているときは、予算で保留する。保留した行は、巡回のたびに読み直すだけで、ラウンドを消費しない。
   mainのCIが赤ければ`main_ci_failed`で保留する。
   直近の`passed`より後に起動した数が`pr_ci_fix_max_rounds`に達していれば、`rounds_exhausted`で保留する。
   数えるのは、ジョブIDが記録された作業項目である。`failed`で`flow_job_id`が空の作業項目は数えない。
   これには、フローの起動に失敗した回のほかに、ジョブIDが記録されないまま回復や失敗の処理が`failed`にした回も含む。
   Claudeを走らせていない回で、直す機会を使い切らないためである。
   ただし、行の起動の回数(`fix_attempts`)が`pr_ci_fix_max_rounds`に3を足した数に達したときも、`rounds_exhausted`で保留する。数えない回が続いても、起動し直し続けないための歯止めである。
10. どれにも当たらなければ起動する。

ジョブの分類は、workflowごとの最新の実行のうち、失敗した実行を古い順に最大5件まで読む。CI回の収集と同じ関数(`classifyFailedRuns`)で、同じ範囲を読む。
ログは読まない。ログを読めないときは、CI回が止まり、回復が`log_unavailable`で保留する。

### 保留の見直し

保留は判断のたびに見直す。
同じ理由なら書き換えない。別の理由に変わったら書き換える。
一時的な保留が解けた行は、保留を外し、その回のうちに判断を続けて起動する。
外すのは、いまの理由が読んだ理由と同じ行だけである。読んだ後に別の実行が理由を書き換えていたら、外せない。外せなかった行は起動せず、読み直した時刻だけを進めて次の回に判断し直す。
決定的な保留は外さない。実行が変わっても外さないので、取り消された実行を再実行して失敗した行は、`other_conclusion`のまま残る。再実行が通れば、行は`passed`になる。
何もしない行は、保留を変えない。

### 起動と失敗

起動してよいと決まった行は、`claimPrCiCheckForFix`で`fixing`に移し、`launchPrFixFlow`でフローを起動する。
`claimPrCiCheckForFix`に渡すownerとrepoは、PRが示す綴り(`baseRepoFullName`)である。headは判断の途中で読み直したPRのものを渡す。作業項目の起動者は、人でないので空にする。
`claimPrCiCheckForFix`がNULLを返したら、何もしない。
フローの起動が例外になったら、作業項目を`failed`にして、行を`failed`に戻す。戻すのは、`fix_work_item_id`が起動した作業項目の行だけである。
作業項目を`failed`にできなくても、行は戻す。作業項目が動いている間は、次の判断が`last_fix_unsettled`で保留する。
戻した行は`fix_attempts`を減らさない。起動の失敗はラウンドの数に入らないので、起動し直し続けるのは`fix_attempts`の上限が止める([判断](#判断))。
フローは起動したが、ジョブIDを作業項目に記録できなかったときは、起動したジョブを取り消す。動いているフローが次の起動と二重にならないためである。
取り消せたら、フローの起動が例外になったときと同じに、作業項目を`failed`にして行を戻す。
取り消せなかったときは、動いているフローを残すために、作業項目を`failed`にせず、行も戻さない。警告のログを残し、`job_failures`に`record_fix_job_id`で記録する。

1回の実行で作業項目を挿入するのは、2件までである。フローの起動に失敗した分も数える。起動の失敗が続いても、1回の実行で作業項目を作り続けないためである。
新しい行は、実行の開始から120秒を超えたら始めない。
予算の使用、スキルのマーカー、リポジトリごとのmainのCIは、1回の実行で1回だけ読む。
スキルのマーカーを読めなかったら、その回の以後の行も同じ失敗として扱い、読み直さない。失敗は、手順名`skill_marker`で1回だけ記録する。対象のPRのリポジトリの権限の不足としては扱わない。`factory_repo`の解釈も、この最初の読み取りの中で行う。
ほかの値は、読みに失敗したら覚えない。

## 失敗を直す設定

次の3項目は`factory_config`で決める。既存のリソースにこれらの項目が無くても、既定値で動く。

| 項目 | 既定値 | 意味 |
| --- | --- | --- |
| `pr_ci_fix_enabled` | `false` | 直す作業項目を起動してよいか。偽の間は何も起動せず、失敗は確定した時点で通知する |
| `pr_ci_fix_max_rounds` | `2` | 1つのPRで起動できる、直す作業項目の数の上限。1以上10以下の整数。直近の`passed`の行より後を数え、通ると数え直す。数えるのは`countPrCiFixRounds` |
| `pr_ci_fix_enabled_since` | 無し | 最初に見た時刻(`first_seen_at`)がこの時刻より前の失敗を、直す対象にしない。この失敗は、確定した時点で通知する。`pr_ci_fix_enabled`が`true`なら必須 |

`pr_ci_fix_enabled_since`は、秒まで書いたタイムゾーン付きのRFC 3339の日時にする(例: `2026-10-13T03:00:00Z`)。
読み込みの後は`Date`になる。
比較は`Date`かSQLのtimestamptzで行い、文字列では比べない。
有効にした時点で判定待ちだった失敗も、最初に見た時刻が前なら対象外になる。
直す対象を絞る側に倒すためである。
`pr_ci_fix_enabled`が`true`で`pr_ci_fix_enabled_since`が無い設定は拒否する。
時刻が無いと、有効にする前から残る失敗を、すべて直しにいくためである。
日時の形が違う値や、`pr_ci_fix_max_rounds`が範囲を外れた値も、既定値に倒さず設定の読み込みで拒否する。
設定を書き損じると、設定の読み込み全体が設定エラーで止まり、Factoryのほかの処理も動かなくなる。

## 発見

対象のPRごとに、PRを読み、今のheadの行を整える(`planPrHead`)。
人のPRも、同じ関数で行を整える。

- 今のheadの行が無ければ、`pending`で記録する。
- 古いheadの`pending`、`failed`、`no_ci`、`fixing`の行は、`superseded`にする。通知しない。headが進んだなら、その行のheadのCIを直す意味が無くなるためである。
- 今のheadの`fixing`の行は触らない。
- 今のheadの行が`superseded`なら、`pending`に戻す。headが以前の値に戻ったときである。
- `passed`などの終わった行は、記録として残す。

新しいheadの行を先に記録し、旧行の整理を後にする。整理が途中で止まっても、次の回に同じ計画で整理し直せる。
記録に失敗したら、そのPRの残りは行わない。例外はPRごとに捕まえ、他のPRを止めない。

## 閉じたPR

PRが閉じていたら(マージを含む)、次の順に整理する。

1. そのPRの失敗のnoticeを、種類`pr_ci_failed`と、本文の接頭辞`<owner>/<repo>#<PR番号>:`で選んで解決する。
2. `pending`、`failed`、`no_ci`、`fixing`の行を`superseded`にする。

接頭辞は、コロンの後の空白まで含めて照合する。`acme/app#1:`で始まる通知は、`acme/app#12:`で始まる通知と取り違えない。解決は冪等なので、行の更新より先に行う。
行が1件も無いPRには何もしない。解決者は`watch_pr_ci`で、Consoleは「PRのCIの監視(自動)」と表示する。

## 判定の順序

判定待ち、失敗、実行なしの行を、読み直していない順(`checked_at`の古い順)に読み直す。
取る件数は、判定待ち200件、失敗100件、実行なし50件である。実行なしの行は、最後に読み直してから1時間以上たったものだけを、PRで最新の行に限って取る。

1つの行の判定は、次の順に行う。

1. PRを読む。ブランチ名とベースのリポジトリのIDを知るためで、この回の発見で読んだPRがあれば、それを使う。PRが閉じていれば、閉じたPRの整理へ移る。行のheadが今のheadでない場合は、実行を読まずに`superseded`へ移す。
2. 行のheadの実行を、head側のブランチ名で読む(`listPrHeadWorkflowRuns`)。ベースのリポジトリのIDとPR番号を渡す。
3. PRのheadを読み直し、行のheadが今のheadかを決める。
4. 判定する(`decidePrCiPending`、`decidePrCiFailed`)。

実行を読んだ後にPRのheadを読む。先にheadを読むと、読んでいる間に進んだheadの実行を、今のheadの失敗として扱ってしまうためである。
行のheadが今のheadでない場合は、実行の中身を問わず`superseded`へ移す。PRのCIは新しいpushで古い実行を取り消す。古いheadの`cancelled`を失敗にすると、直した後で失敗を通知してしまうためである。今のheadの`cancelled`は失敗に数える。

実行は、workflowごとの最新の1件に絞ってから判定する(`latestRunPerWorkflow`)。同じheadでも、取り消してやり直した実行や、手で再実行した実行があるためである。

| 結果 | 条件 |
| --- | --- |
| `passed` | 最古の実行から2分以上たち、すべての実行が完了していて、結論がsuccess、skipped、neutralだけ |
| `failed` | 同じく確定していて、それ以外の結論(failure、timed_out、cancelled、action_required、stale、未知の値)がある |
| `no_ci` | 実行が0件のまま、最初に見てから15分たった |
| `expired` | 未完了のまま、最古の実行から2時間たった。ただし、完了した失敗が1件でもあれば`failed`にする |
| `pending` | 上のどれでもない |

`failed`の行は、巡回のたびに読み直す。同じheadの再実行が通れば`passed`に戻し、そのPRの失敗のnoticeを解決する。再実行が終わっていなければ、`failed`のままにする。
`no_ci`の行は、実行が現れれば`pending`に戻す。`no_ci`の行は期限切れにしない。
状態を変えずに読み直した行は、`checked_at`を進める。例外の経路でも進める。進めないと、同じ行が先頭に残り続け、後ろの行が読み直されないためである。

## 読めない行

実行かPRを読めなかった行は、理由で扱いが分かれる。最初に見た時刻から24時間たつまでは、どの行も`checked_at`だけを進める。

| 理由 | 24時間たった判定待ちの行 | 24時間たった失敗と実行なしの行 |
| --- | --- | --- |
| rate limit | 変えない。以降のGitHubの読み取りを止め、`checked_at`も進めない | 同じ |
| 権限の不足(403、404) | 通知せず`expired`にする。リポジトリごとに1回、`pr_ci_check_denied`を登録する | 変えない |
| 実行を読み切れない(`WorkflowRunsIncompleteError`) | 通知せず`expired`にする | 変えない |
| 読み取りの段階の例外(サーバーの5xxを含む) | 通知せず`expired`にする。`job_failures`に記録する | 変えない。`job_failures`に記録する |
| リポジトリが設定から外れた | 通知せず`expired`にする | `superseded`にして、そのPRの失敗のnoticeを解決する |
| オーナーの照合に失敗して対象に入らない | 通知せず`expired`にする | 変えない |
| 読んだ後の段階の例外(通知の登録など) | 変えない。`job_failures`に記録する | 同じ |

`expired`にするときはログへ残す。人へ知らせる手段が無いのに、判定待ちの行が残り続けるのを防ぐためである。
`expired`にする判定待ちの行は、旧headの失敗のnoticeを解決しない。読めない間は、旧い通知を残すほうが安全なためである。
失敗と実行なしの行を`superseded`にするのは、リポジトリが設定から外れたときだけである。外れたリポジトリの失敗を、人は確かめられないためである。
外れたかどうかは、許可の判定と同じ規則を、照合前の`owners`に当てて決める。照合に失敗したオーナーの、許可リストに合うリポジトリは、設定に残っているものとして扱う。`repo_allowlist`が空でないときは、許可リストの項目まで外れて初めて外れたと数える。
照合に失敗しているだけの回は含めない。照合は次の回に戻りうるため、失敗の行は変えない。
権限の不足や実行の多さで読めない回は、失敗の行を`superseded`にせず、noticeも解決しない。一時的な不通で、今も続く失敗の通知を消さないためである。
読めた回に今も失敗していても、通知は重ねない。
サーバーの一時的な失敗は、rate limitと違って、読み取りの例外として数える。

読み取りで捨てた実行(forkの実行、別のPRの実行)は、件数をログに残す。読んだ実行がすべて別のリポジトリのものなら、`no_ci`に倒さず、読み切れないものとして扱う。

## 失敗の通知

失敗の通知は、確定した時点で出す場合と、直せるかが決まってから出す場合がある。
次のどれかの失敗は、確定した時点で出す。

- 自動修正が無効である。
- 最初に見た時刻が、`pr_ci_fix_enabled_since`より前である。
- 理由コードが`ci_other_conclusion`である。取り消しなどで終わった失敗は、直す作業項目を起動しないためである。

それ以外の失敗は、自動で直す対象である。
自動で直す対象の失敗は、状態を`failed`に移すだけにする。
noticeとDiscordは出さず、通知した理由コードも記録しない。
直せるかが決まる前に通知すると、直って消える通知で人を呼ぶためである。
通知は[保留した失敗の通知](#保留した失敗の通知)が出す。

確定した時点で出す失敗は、次の順に処理する。

1. 理由コードを決める。完了した最新の実行にfailureがあれば`ci_failure`、なければ(取り消し、期限切れ、承認待ちなど)`ci_other_conclusion`。
2. 要対応のnotice`pr_ci_failed`を登録する(`addNoticeUnlessUnresolved`)。
3. noticeを新しく登録できたときだけ、Discordに`needs_human`を送る。送れなくても処理を続ける。
4. 状態を`failed`に更新し、要約(`summary`列)と、最古の実行の時刻を残す。
5. 通知した理由コードを記録する(`markPrCiNotified`)。

noticeを先に登録し、状態の更新を後にする。更新が先に成功して登録が失敗すると、通知が永久に出ないためである。更新に失敗した回は、次の回に同じ手順をやり直す。noticeは重複が索引で防がれるので、Discordは重ねて送らない。

noticeの本文は、`<owner>/<repo>#<PR番号>:`で始まる固定文に、コミットの先頭7文字、理由コード、次の操作、実行のURLだけを入れる。
次の操作は理由コードごとの固定文である。
`ci_failure`の固定文には、metadataジョブの失敗なら`mise run metadata`を実行して差分をコミットする案内が入る。
ジョブの名前は本文に載せないため、どのジョブが落ちたかに関わらず、同じ案内を載せる。
metadataジョブの失敗では、artifactが出ていても案内は変えず、人の操作を案内する([CIのメタデータの検査](../setup.md#ciのメタデータの検査))。
workflowの名前、結論、ログは、リポジトリへ書ける人が決める文字列である。そのためnoticeとDiscordには載せず、検証と整形をした上で`summary`列にだけ残す。
実行のURLは、失敗した実行のうち、`parseRunUrl`を通ったものを使う。通るものが無ければ、PRのページにする。

Discordの`needs_human`は、リンクをPRのページにし、理由に理由コード、次の操作を固定文で載せる。
同じheadの失敗は、再実行が失敗し続けても、通知を重ねない。

### 保留した失敗の通知

保留した失敗は、`notifyDeferred`が通知する。
失敗で、通知した理由コードが空の行(`listUnnotifiedFailedPrCiChecks`)を、更新の古い順に最大200件読む。
行の今の状態だけで、通知するかを決める(`decideDeferredNotice`)。
失敗に移った時点で通知を決めないのは、設定やGitHubの読み取りの結果が変わっても、通知を取りこぼさないためである。
DBだけを読み、GitHubを読まない。
1回の実行の最後に、発見、回復、判定、起動の後で動く。
起動が書いた保留の理由を、同じ回の通知が見られるためである。
設定`pr_ci_watch_enabled`が`false`でも動き、そのときは回復の後に動く。
`false`のときは起動もしないので、保留していた通知はすぐ出す。

次のどれかなら通知する。当たらない行は、次の回に判断し直す。

| 条件 | 通知に載せる理由 |
| --- | --- |
| 保留の理由が決定的である(`rounds_exhausted`を含む) | 保留の理由 |
| 保留の理由が一時的で、しきい値を超えて続いた | 保留の理由 |
| 保留の理由が一時的で、自動修正が無効か、最初に見た時刻が`pr_ci_fix_enabled_since`より前である | 失敗の理由コード |
| 保留の理由が無く、自動修正が無効か、最初に見た時刻が`pr_ci_fix_enabled_since`より前である | 失敗の理由コード |
| 保留の理由が無く、起動もされないまま、`failed`になってから2時間たった | 失敗の理由コード |

決定的な保留の理由が付いた行は、方針に関わらず、その理由と語彙のDiscordの要否で通知する。
同じheadでは起動し直さないので、自動修正が無効でも、人が直すことに変わりはないためである。
一時的な保留の理由は、自動修正が有効で、`pr_ci_fix_enabled_since`以後に見つけた失敗にだけ載せる。
無効のときや有効にした時刻より前の失敗は起動されないので、待たずに通知する。
一時的な保留の案内は解けるまで待つ内容だが、起動されない行は待っても解けない。
そのため、保留の理由は載せない。
Discordは、保留の理由が無い行と同じく送る。
しきい値は、`not_reviewed`と`last_fix_unsettled`が`claude_timeout_sec`の2倍、ほかの一時的な理由が30分である。
最後の条件は、発見の対象から外れたPRや、起動の候補に入らない行の通知を、取りこぼさないための保険である。
語彙に無い保留の理由は、保留が無いものとして扱う。
リポジトリが設定から外れた行は、通知しない。
通知した理由コードが空でない行も、通知しない。
確定した時点で`ci_other_conclusion`を通知した行を、`ci_failure`として通知し直さないためである。
保留した失敗の通知は、理由コードを`ci_failure`に固定する。
通知を遅らせるのは`ci_failure`の行だけで、`ci_other_conclusion`の行はすぐ通知するためである。

保留が続いた時間は、行の更新時刻(`updated_at`)から測る。
更新時刻は、保留の理由を書き換えたとき、`failed`に確定したとき、起動した行が戻ったときに進み、状態を変えずに読み直したときは進まない。
そのため、保留を付けた時刻の専用の列は持たない。
一時的な理由が別の一時的な理由に変わると、測り直す。

通知は、noticeの登録、Discord、通知した理由コード`ci_failure`の記録の順に行う。
登録が先なのは、記録が先に成功して登録が失敗すると、通知が永久に出ないためである。
記録に失敗した回は、次の回に同じ手順をやり直し、noticeの重複は索引が防ぐ。
本文は、保留の理由があれば、失敗の理由コードの後に`自動修正の保留: <理由コード>`を足し、次の操作を保留の理由の固定文(`nextAction`)にする。
保留の理由が無ければ、確定した時点で出す失敗と同じ本文になる。
リンクはPRのページである。実行を読まないので、失敗した実行のリンクは載せない。
noticeを新しく登録できたときだけ、保留の理由の`discord`が真ならDiscordにも送る。
1回の実行で最初の1件は予算を見ずに通知し、2件目以後は予算を見る。

通知した理由コードは、次の3つの書き込みが空に戻す。
いずれも、先に知らせた後の行を、改めて通知するためである。

- 起動(`claimPrCiCheckForFix`)。保留が続いたと知らせた後に起動した行でも、直す作業が止まったときに通知できる。
- 決定的な保留の理由を書く更新(`setPrCiFixHold`の`resetNotified`)。「待つ」と知らせた後に、人が直す保留へ変わった行に通知できる。
  確定時に`ci_other_conclusion`で「人が直す」と知らせた行は、同じ保留に着くだけなので空に戻さない。
- 回復が決定的な保留の理由を書いて`failed`に戻す更新(`releaseFixingPrCiCheck`の`resetNotified`)。

一時的な保留の理由を書く更新と、保留を外す更新は、空に戻さない。
先に出たnoticeは、行が`passed`になるまで残る。

## 自動解決

行が`passed`になったとき、そのPRの未解決の`pr_ci_failed`を、種類と本文の接頭辞で解決する。
種類を固定するので、`pr_ci_check_denied`などほかの種類は解決しない。
新しいheadが通ったときは、旧headの失敗のnoticeも解決される。旧headの行は`superseded`にして、noticeはそのまま残しているためである。
新しいheadが`no_ci`か`expired`で終わったときも、そのPRの失敗のnoticeを解決する。新しいheadに失敗は無く、旧い失敗の通知は古くなっているためである。
解決は冪等なので、状態の更新より先に行う。更新に失敗した回は、次の回にやり直せる。

## 権限の不足

PRか実行を読めなかったリポジトリは、`pr_ci_check_denied`を1リポジトリにつき1件登録する。本文はリポジトリごとに同じ文なので、未解決の通知がある間は重ねて登録されない。
Discordには送らない。
実行を読めたら、そのリポジトリの未解決の`pr_ci_check_denied`を、種類と`<owner>/<repo>:`の接頭辞で解決する。
rate limitの403は、権限の不足として扱わない。

## 時間の見積もり

1回の実行で呼ぶGitHubのAPIは、次のとおりである。

- オーナーの照合。`owners`の数だけ呼ぶ。
- 対象のPRごとに、PRの取得を1回(最大50件)。
- 読み直す行ごとに、PRの取得(この回の発見で読んだPRがあれば省く)、実行の取得(1〜3ページ)、PRの取得。
- 起動の候補ごとに、判断が進んだ分だけ、PRの取得、commitの一覧(1〜3ページ)、実行の取得、失敗した実行ごとのジョブの取得(最大5件)。スキルのファイルの取得は、1回の実行で1回である。
- 人のPRの発見が有効なら、検索を範囲の数と作者の数の積だけ(1ページずつ)、PRの取得を最大60回(`HUMAN_PR_READ_LIMIT`)。
- 記録済みの人の行の判定は、1件あたりPRの取得2回と実行の取得1〜3ページで、3〜5回である。上限の40件で、1回の実行の最大は200回である。
  5分ごとの実行は1時間に12回なので、判定は最大2400回、発見のPRの取得を足すと最大3120回である。
  認証したトークンのRESTの上限(1時間に5000回)の約6割になる。

1回の実行は、開始から120秒を超えると、新しい読み取りを始めず、残りを次の回に回す。読み残した行は`checked_at`を進めないので、次の回の先頭になる。
予算を見るのは、PRの発見、行の判定の開始、失敗の確定、起動の行の開始、人のPRの検索とPRの読み取りの前である。実行の読み取りのページごとには見ない。`watch_main_ci`も同じで、読み始めた行は読み切るほうが、判定の途中で止まるより単純なためである。
失敗の確定は、通知の登録とDiscordの前に予算を見る。超えていれば、通知も状態の更新もせず、行はそのままになる。
ただし、1回の実行で最初の1件は予算を見ずに確定する。予算切れが続いても、失敗の通知が飢えないためである。
保留した失敗の通知も、同じ理由で、1回の実行で最初の1件は予算を見ずに通知する。
時計は注入でき、テストでは進め方を変えて確かめる。

scriptのtimeoutは600秒である。見積もりは次のとおりである。

- 1回の要求の上限は、ghの実行60秒、5xxの再送(待ち2秒と実行60秒)、rate limitの待ち120秒を足した約240秒である。rate limitの待ちの後に再び拒まれたら、読み取りをやめる。
- 予算の直前に始めた行の判定は、PRの取得2回と実行の取得で、最悪で約4要求かかる。実行が100件を超えるheadは、最大3ページでさらに増える。
- 最初の失敗の確定だけが予算を見ない。Discordの待ちは最大30秒である。

予算は120秒にしてある。予算の直前に始めた行が数十秒で終われば、timeoutに十分収まるためである。
通常は、rate limitの待ちと再送が起きず、数秒から数十秒で終わるので、timeoutに収まる。
rate limitの待ちが重なると、timeoutを超えうる。そのときはjobが打ち切られるが、行ごとの更新は冪等なので、確定しなかった行は次の回に残る。
実行が長引いた回は、`no_flow_overlap`により次の回が飛ばされる。

## 既知の限界

次の限界は、通知の見落としにつながる。対象のリポジトリの運用で補う。

- 通ったheadの実行を後から再実行して失敗しても、通知されない。`passed`は終端で、読み直さないためである。
- 条件付きで動くworkflow(ラベルが付いたときだけ動く型など)の実行は、条件に合わず`skipped`となっても、成功に数える。動くはずの検査が動かなかったことは見逃す。
- 戻ったheadの行が`passed`か`expired`のとき、その後の新しい実行は評価されない。`superseded`の行だけが`pending`に戻るためである。
- 手動や定期など、`pull_request`と`push`以外のeventの実行は、PRのCIとして数えない。全workflowがこれに当たると、`no_ci`になる。
- 新しいpushで古い実行を取り消す設定(`cancel-in-progress`)が無いリポジトリでは、古いheadの実行が長く残りうる。古いheadの行は、実行の中身を問わず`superseded`にするため、今のheadの判定は変わらない。
- 実行が100件を超えるheadと、権限の問題で読めないheadは、24時間たつと`expired`になる。それまでは失敗に気づけない。
- 更新が`tracked_pr_days`(既定30日)より古い作業項目のPRは、新しいheadの失敗に気づけない。起点は作業項目の更新時刻である。headが進むと失敗の行は`superseded`になるが、新しいheadの行は作られず、旧headの失敗のnoticeが解決されずに残りうる。
- 権限を直した直後に、読めた最初のPRが閉じていた回は、権限の不足の通知を解決しない。次に実行を読めた回で解決する。
- 新しいheadでも失敗が続くと、旧headのnoticeは解決されない。headごとにnoticeとDiscordが1件ずつ出る。
- 失敗の確定中に行の更新が例外を投げ、次の回までに実行が増えてnoticeの本文が変わると、まれにDiscordが2回送られる。本文が同じなら、noticeの重複が索引で防がれる。
- 巡回する50件の枠には、閉じたPRも入る。`tracked_pr_days`以内にFactoryのPRが50件を超えて作られると、古い開いたPRは監視から外れる。
- 先頭が英数字でない名前(`.github`など)のリポジトリは、監視しない。DBへの記録がその名前を受け付けないため、ログに残して読み飛ばす。
- 経過時間の予算の保証は、判定を始めた行にだけ効く。発見で予算を使い切ると、その回は判定が走らない。
- Discordは、noticeを新しく登録したときに最大1回だけ送る。noticeの登録の後に実行が打ち切られた場合と、送信が失敗した場合は、再送しない。受け皿は、要対応に残るnoticeである。
- 監視を有効にした直後の最初の巡回で、そのとき赤い開いたFactoryのPRは、すべて通知する。
- 一時的な保留の理由が、しきい値より短い間隔で別の一時的な理由に入れ替わり続ける行は、通知されない。保留が続いた時間を、理由を書き換えるたびに測り直すためである。2時間の保険は、保留の理由が無い行にしか効かず、この行を救わない。
- 保留した失敗の通知はGitHubを読まないので、PRが閉じたことを知らない。閉じたPRの行は、閉じたPRの整理が`superseded`にするまで、通知しうる。
- 保留が続いたと知らせた後に直す作業が起動するか、決定的な保留へ変わって改めて通知すると、先に出た「待つ」のnoticeは、行が`passed`になるまで残る。本文が違うので重複と見なされず、`passed`のときの接頭辞による自動解決まで消えない。
- 確定した時点で通知した失敗の、通知した理由コードの記録だけが失敗すると、保留した失敗の通知が同じ失敗をもう一度通知する。本文が違うので、noticeの重複を索引が防がない。二度目の通知は、リンクが実行のURLでなくPRのページになる。
  `ci_other_conclusion`の行は、理由コード`ci_failure`として通知される。
- 自動修正や監視を止める前に「待つ」と知らせた行は、止めた後も「待つ」の案内のまま残る。
  止めても、先に出たnoticeは書き換わらない。
  noticeは行が`passed`になるかPRが閉じるまで残るので、人が確かめる。
- 監視を止めて戻したとき、無効の間に通知した行は、起動の候補に戻る。
  決定的な保留に変わると、本文が違う2件目の通知が出うる。
  戻すときに`pr_ci_fix_enabled_since`を書き直すと、止めている間に見つけた行は候補から外れる。
- 回復が止めた理由を保留の理由に写した行は、止めたフローのDiscordと、保留した失敗の通知のDiscordが二重に出うる。受け入れた挙動である。`fix_stopped`は後者のDiscordを送らない。
- 保留した失敗の通知は、`failed`の行にだけ出る。行が`fixing`の間は、作業項目側のフローの停止通知が先に出る前提である。イメージが古い理由で`blocked`になった作業項目は、行が24時間`fixing`に残るので、この間は停止通知だけが届く。
- 監視を無効にした直後は、保留中の行がまとめて通知される。1回の実行で読むのは200件までで、残りは次の回に回る。閉じたPRの行と、再実行で通った行のnoticeは、判定が動くまで解決されない。
- 設定から外れたリポジトリの行は、監視が有効な間だけ`superseded`になる。無効の間は一覧に残って先頭を占める。この行が200件以上あると、後ろの行は監視を有効に戻すまで通知されない。
- 通知の保険(2時間)で、保留の理由が無いまま「人が直す」と通知した行も、その後に発見が戻れば起動の候補になりうる。人とFactoryが同じPRを直しうる。受け入れた挙動である。
- トレーラーの無いcommitを含むPRは、自動で直さない。人がPRを直し終えた後も、同じPRのCIの失敗は人が直す。
- 人がFactoryのcommitをamend、rebase、cherry-pickすると、トレーラーが残り、Factoryのcommitとして扱う。人が書き換えたPRを、自動で直しうる。
- `last_fix_unsettled`で保留するのは、終端でない`pr_fix`がある場合だけである。直近の`pr_fix`が失敗や`needs_human`で終わっていても起動する。意図した縮小である。
- 準備の段階で止まる`guard_blocked`の連続は、直す回数を使う。上限に達すると止まる。受け入れた挙動である。
- 取り消された実行を再実行して失敗した行の`other_conclusion`と`unfixable_job`の保留は、外れない。意図した挙動である。
- 予算(`daily_budget_usd`)は、走行中の分を数えない。1日の上限を、走行中のClaudeの費用の分だけ超えうる。
- ジョブIDの記録と取り消しの両方が失敗した回は、Claudeが走ってもラウンドに数えないことがある。歯止めは、`fix_attempts`の上限と日次の予算である。
- 取り消せなかったフローを残すのは、`poll_issues`の照合の猶予の間だけである。猶予は、10分と`claude_timeout_sec`の2倍の大きい方である。猶予が過ぎると、照合が作業項目を`failed`にし、回復が行を戻して、2本目のフローが起動しうる。2本目は、準備のworktreeの保持者の検査で止まる見込みなので、損失は有界である。
- 取り消したフローで、`pr_fix`の`failure_module`(`on_error_flow`のDiscordの`job_failed`)が走るかは確かめていない。有効にした最初の1件で、取り消しの経路を踏んだときにDiscordの通知が増えるかを見る。
- 人のPRの検索は、作者ごとに更新が新しい100件までを読み、1回の実行で新しく記録するのは20件、読むのは60件までである。開いているPRがそれを超えると、古いPRは、pushで更新が進むまで見つからない。記録済みの行は、件数に関わらず判定される。
- 人のPRの検索がrate limitで拒まれた回は、新しいPRと新しいheadを見つけない。次の回に見つける。
- 人のPRは、PATのアカウントが作ったものも対象である。運用者が同じアカウントで作ったPRのCIの失敗も通知される。FactoryのPRは、ブランチ名と作業項目で除く。
- 記録した後に下書きへ戻した人のPRは、記録済みの行が判定され、失敗すれば通知しうる。下書きの間に新しいheadの行は作らない。下書きから戻すと、次の回の検索で見つけて記録する。
- 人のPRの監視を有効にした直後の最初の巡回で、そのとき赤い開いた人のPRは、すべて通知する。
  1回の実行で新しく記録するのは20件までなので、残りは次の回以降に記録して通知する。新しく記録した行の判定も次の回になる。
- 人のPRの行は、作業項目に結ばれていない。起動の候補にも、回復の対象にもならず、`fix_hold_reason`は付かない。

## 競合の検知

`watch_pr_conflicts`が、Factoryが作ったPRのマージの競合を検知して通知する。
`lib/pr_conflict_support.ts`に判断を、`lib/pr_conflict_watch.ts`に流れを置く。
`watch_pr_ci`とは別のscriptで、設定`pr_conflict_watch_enabled`(既定は`false`)だけで有効にする。
偽の間は、設定を読むだけで終わる。GitHubとDBを読まず、何も書かない。
PRとリポジトリへは書き込まず、競合を解く作業も起動しない。
対象は、Factoryがブランチ`factory/issue-<N>-wi-<id>`に作ったPRだけである。draw.ioのビューアを上げるPRなど、別の形のブランチのPRは見ない。

### 対象の見つけ方

作業項目の存在や更新時刻には頼らず、開いているPRの一覧から見つける。
状態が`pr_open`の作業項目は、PRがマージされた後も変わらないうえに、`cleanup_db`が一定の期間で消す。
作業項目から引くと、閉じたPRを読み続けるか、消えた作業項目のPRを見失う。

1. 次の4つの和集合から、列挙するリポジトリを作る。大文字小文字は区別せず、重ならない。次の順に並べるので、予算が尽きたときは、後ろのものが次の回に回る。
   - 状態が`pr_open`で`pr_url`を持つ`issue`の作業項目のリポジトリ(`listPrOpenRepos`)。
   - 競合の記録(`pr_conflict_checks`)の行を持つリポジトリ。状態は問わない(`listPrConflictRepos`)。
   - 設定で明示されたリポジトリ。`factory_repo`と、`repo_allowlist`の各項目である(`configuredRepos`)。`owners`はオーナーの全体を指すので、展開しない。
   - 照合を通ったオーナーごとに、PATのアカウントが作った開いているPRを検索して見つけたリポジトリ(`searchOpenAuthoredPrs`)。検索はリポジトリを見つけるためだけに使い、判定は一覧と`getPr`で行う。
2. 許可リスト(`isRepoAllowed`)に合うリポジトリの、開いているPRを一覧する(`listOpenPullRequests`)。`owners`は、`id`の照合を通ったものだけを渡す。
3. 一覧のうち、次をすべて満たすPRを、Factoryが作ったPRとして読む(`getPr`)。マージ可否は一覧に載らないためである。
   - 下書きでない。
   - headのリポジトリがベースと同じである。
   - headのブランチが`factory/issue-<N>-wi-<id>`の形である。
   - 作者が、PATのアカウント(`getViewer`)である。ログイン名を大文字小文字を区別せずに比べ、PRの応答に数値IDがあれば、IDも比べる。

元ごとの件数は、ログ`pr conflict repositories collected`で読める。リポジトリ名は出さない。
`work_items`、`conflict_rows`、`explicit`はリポジトリの数である。`searched`は検索が返したPRの件数で、リポジトリの数ではない。同じリポジトリが重なり、Factory以外のPRも含む。`total`は重複を除いたリポジトリの数である。

人が作ったPRは、作者で除く。同じ形のブランチを作った他の人のPRも、作者で除く。
PATのアカウントを読めない回は、一覧からの発見を飛ばし、競合の行の整理だけを行う。
検索が失敗した回は、失敗を記録し、ほかの元で発見を続ける。検索のrate limitは別の枠で全オーナーが共有するので、記録せず、残りのオーナーの検索だけを飛ばし、ほかの読み取りは止めない。

一覧は1リポジトリにつき10ページ(1000件)までを読む。超えたときは、一部だけを使わず、そのリポジトリを飛ばして、失敗として記録する。
ただし、検索だけが見つけたリポジトリは、失敗として記録せず、ログに警告だけを残す。一部だけでは、一覧に無いPRを「開いていない」と取り違えうるためである。
1回の実行の経過時間の予算は、CIの監視と同じ`RUN_BUDGET_MS`(120秒)である。超えたら、残りは次の回に回す。

### 判定

PRの今の状態から、次の順に扱いを決める(`decidePrConflict`)。

| 条件 | 扱い |
| --- | --- |
| PRが閉じている、またはマージされた | 閉じる |
| マージ可否が真 | 競合なし。下書きでも判定する |
| 下書き | 何もしない |
| マージ可否が`null` | 何もしない。GitHubが計算していないので、真偽に丸めず、次の回に判定し直す |
| マージ可否が偽で、状態が`dirty` | 競合 |
| マージ可否が偽で、状態が`dirty`でない | 何もしない。異常なのでログに警告を残す |

競合でも、headが完全なコミットshaでなければ、何もしない。記録できないためで、ログに警告を残す。
何もしなかったPRは、結果の`skipped`に数える。
下書きは新しい競合の対象にしない。下書きに戻したPRでも、競合の行を持つものは、マージ可否が真になれば通知を解決する。

### 記録

記録は`factory.pr_conflict_checks`に、PRごとに1行で持つ。行は`(owner, repo, pr_number)`で一意になる。

| 状態 | 意味 |
| --- | --- |
| `conflicted` | 競合している。`head_sha`は、競合を最後に見た時点のheadである |
| `resolved` | 競合が解けた。再び競合したら、同じ行を`conflicted`に戻して新しい競合を始める |
| `closed` | PRが閉じたか、マージされたか、設定が対象から外した |

競合を見るたびに、行を挿入するか書き換える(`recordPrConflict`)。
競合は、行が無い状態か、`resolved`か`closed`の状態から`conflicted`に移った時点で始まる。
始まったときだけ、通知した時刻を空にして、競合の回(`episode`)を1つ増やす。回は、競合の行のidと組にして、競合の1回を指す。競合のままheadが進んだときは、`head_sha`だけを書き換える。通知した時刻と回は変えない。
`recordPrConflict`は、新しい競合が始まったかを返す。読んで書く間に値が変わらないよう、1つの文で行う。
`episode`は、PRの何回目の競合かを区別する。1から始める。

競合を自動で直すために、行は次の4列を持つ。
外部キーは無い。作業項目は行の削除に連なって消えず、行も作業項目の削除に連なって消えない。

| 列 | 意味 |
| --- | --- |
| `fix_work_item_id` | いま競合を直している作業項目のID。直していなければNULL |
| `fix_attempts` | 直す作業項目を起動した回数。既定は0で、負にならない |
| `fix_hold_reason` | 起動を保留している理由コード。保留していなければNULL。空でなく、64字まで |
| `episode_started_at` | 行を挿入した時刻 |

`checked_at`は読み直すたびに、`updated_at`は書くたびに進む。
行を挿入した時刻は、これらとは別に`episode_started_at`へ持つ。
競合の1回は、行のidと`episode`の組で指す。作業項目の`conflict_check_id`と`conflict_episode`が、直している競合をこの組で結ぶ([作業項目の状態とリース](work-items.md)の「修正の回を結ぶ列」)。

既存の行の`episode_started_at`は、列を足した時刻になる。競合の本来の開始時刻は記録していないためである。

### 競合を直す設定

次の5項目は`factory_config`で決める。既存のリソースにこれらの項目が無くても、既定値で動く。

| 項目 | 既定値 | 意味 |
| --- | --- | --- |
| `pr_conflict_fix_enabled` | `false` | 競合を直す作業項目を起動してよいか。偽の間は何も起動せず、通知の挙動も変わらない |
| `pr_conflict_fix_max_rounds` | `2` | 競合の1回(`episode`)で起動できる数の上限。1以上5以下の整数 |
| `pr_conflict_fix_max_rounds_per_pr` | `5` | 1つのPRで起動できる数の上限。2以上10以下の整数で、`pr_conflict_fix_max_rounds`より大きい |
| `pr_conflict_fix_enabled_since` | 無し | 今の競合の回が始まった時刻(`episode_started_at`)がこの時刻より前の競合を、直す対象にしない。`pr_conflict_fix_enabled`が`true`なら必須 |
| `pr_conflict_fix_notify_grace_min` | `60` | 解ければ外れる理由で保留している競合を、通知するまで待つ分数。0以上1440以下の整数 |

`pr_conflict_fix_enabled`が`true`なら、`pr_conflict_watch_enabled`も`true`でなければならない。
直す対象は検知が記録した行なので、検知が止まっていれば何も起動できず、設定の食い違いに気づけないためである。
`pr_conflict_fix_enabled_since`は、`pr_ci_fix_enabled_since`と同じ形の日時にする。
時刻が無いと、有効にする前から残る競合を、すべて直しにいくためである。
PR全体の上限が競合1回の上限以下の設定は、拒否する。
競合1回の上限へ達する前に、PR全体の上限が起動を止めるためである。
範囲を外れた値も既定値に倒さず拒否する。
設定を書き損じると、設定の読み込み全体が設定エラーで止まり、Factoryのほかの処理も動かなくなる。

### 保留の理由の語彙

`fix_hold_reason`に書く値は、`lib/pr_conflict_fix_holds.ts`の`PR_CONFLICT_FIX_HOLD_REASONS`の14個に限る。
`lib/pr_conflict_support.ts`が同じ名前で再エクスポートする。
DBの関数が一時の理由の一覧を読むので、依存を持たない小さなモジュールに置く。
DBの検査は長さだけなので、書く側をこの型で縛る。
種別は`PR_CONFLICT_FIX_HOLD_INFO`が持つ。
一時の理由は、解ければ外れる。最終の理由は、人が直すまで起動し直さない。

| 理由 | 種別 | 意味 |
| --- | --- | --- |
| `last_fix_unsettled` | 一時 | 直近の直す作業項目が、まだ終わっていない |
| `budget_exceeded` | 一時 | 日次の予算を使い切った |
| `recently_fixed` | 一時 | 直近の直す作業項目が終わってから5分に満たない。GitHubが競合の有無を更新するまで待つ |
| `marker_missing` | 一時 | Factoryのクローンのスキルが、競合を直す節を持たない |
| `main_ci_failed` | 一時 | 既定のブランチの先頭のmainのCIが失敗している |
| `pr_draft_or_auto_merge` | 最終 | PRがドラフトか、auto-mergeが有効である |
| `not_factory_head` | 最終 | PRのコミットに、Factoryのものでないものがある |
| `rounds_exhausted` | 最終 | 直す回数の上限に達した |
| `base_not_default` | 最終 | PRのbaseが、リポジトリの既定のブランチでない |
| `base_changes_workflows` | 最終 | 既定のブランチの更新が、`.github/workflows/`を変える |
| `protected_path` | 最終 | 競合したパスが保護パスである |
| `unresolvable` | 最終 | 競合が自動で解ける形でない |
| `check_failed` | 最終 | 解消した後の検査コマンドが失敗した |
| `fix_stopped` | 最終 | 直す作業項目が、上のどれにも当たらない理由で止まった |

語彙に無い値は、最終として扱う。人に知らせず放置するより、通知に倒すためである。

### 競合を直す判断

判断は`lib/pr_conflict_fix_claim.ts`と`lib/pr_conflict_fix_recovery.ts`の関数が行う。
どちらも事実を引数で受け取り、DBとGitHubには書かない。

`decideConflictFixClaim`は、競合の行について、直す作業項目を起動してよいかを決める。
次の順に確かめ、最初に当たったもので止める。
安く確かめられるものが先で、事実は必要になるまで読まない。

1. 直す作業項目が動いていれば、`last_fix_unsettled`で保留する。
2. PRを読み直す。閉じていれば、行のheadから進んでいれば、何もしない。baseが既定のブランチでなければ`base_not_default`、ドラフトかauto-mergeが有効なら`pr_draft_or_auto_merge`で保留する。
3. コミットがすべてFactoryのものでなければ、`not_factory_head`で保留する。
4. スキルのマーカーが無ければ`marker_missing`、予算を使い切っていれば`budget_exceeded`で保留する。
5. 既定のブランチの先頭のmainのCIが失敗していれば、`main_ci_failed`で保留する。記録が無い、判定待ち、期限切れ、CIなし、基準の行のときは止めない。
6. 競合の1回の起動数、PR全体の起動数、行の起動の回数のどれかが上限に達していれば、`rounds_exhausted`で保留する。
7. 直近の直す作業項目が終わってから5分に満たなければ、`recently_fixed`で保留する。

作業項目の状態をPRより先に読むのは、読んでいる間に直す作業項目がpushしたとき、古いheadの行を起動しないためである。
Factoryのレビューの記録は要求しない。
行の起動の回数の上限は、競合の1回の上限に`LAUNCH_FAILURE_ALLOWANCE`を足した数である。
フローが起動しないまま起動し直し続けるのを止める。

`decideConflictNotify`は、通知していない競合の行の扱いを決める。
扱いは、通知、待機、起動の判断のどれかである。

- 起動が無効なら、常に通知する。
- 起動を有効にした時刻より前に始まった競合の回は、起動の対象外なので通知する。
- 最終の保留は、猶予を待たずに通知する。
- 直す作業項目が動いていれば、待つ。
- 一時の保留は、競合の回の開始(`episode_started_at`)から猶予が過ぎたら通知する。それまでは、解ければ外れるので、起動の判断に回して見直す。
- 保留と作業項目がどちらも無ければ、起動の判断に回す。

猶予を保留を書いた時刻から数えないのは、保留が付け外しされても通知が遅れ続けないためである。

`decideConflictFixRecovery`は、直す作業項目が結ばれた行について、行き先を決める。

- 作業項目が存在しないとき(掃除で消えた)は、終端として扱い、保留なしで結びを外す。
- 動いていれば、そのままにする。
- pushしていれば、結びを外す。pushした回と、何も変えずに終えた回(`reviewed`で注記が`conflict round: up_to_date`)は区別する。
- `needs_human`と`blocked`は、止めた理由を保留の理由に写せればその理由で、写せなければ`fix_stopped`で保留する。
- フローの起動より前に失敗した`failed`は、保留なしで結びを外す。

止めた理由の注記は、固定文への完全一致だけで保留の理由に写す。

| 注記 | 保留の理由 |
| --- | --- |
| `conflict round: base is not the default branch` | `base_not_default` |
| `conflict round: base changes workflows` | `base_changes_workflows` |
| `conflict round: a conflicted path is protected` | `protected_path` |
| `conflict round: unresolvable conflict` | `unresolvable` |
| `conflict round: check failed` | `check_failed` |
| `conflict round: the factory-fix skill lacks the conflict-fix-skill:v1 marker` | `marker_missing` |
| 予算を使い切った、ドラフトかauto-mergeが有効、の固定文 | `budget_exceeded`、`pr_draft_or_auto_merge` |

Claudeの出力には、固定文の前に接頭辞が付く。接頭辞は「conflict round: claude blocked: 」である。
そのため、出力の中の文字列で、保留の理由を選ばれない。

### 競合を直す作業項目と行の結び

`lib/db.ts`の関数が、行と直す作業項目の結びを書く。
行の状態(`state`)は、直している間も`conflicted`のままである。直している作業項目は`fix_work_item_id`が示す。

`claimPrConflictForFix`は、行に作業項目を結び、`pr_fix`の作業項目を挿入して、そのIDを返す。
行の更新と挿入は1つの文で行うので、片方だけが書かれることはない。
次のどれかなら、何も書かず`null`を返す。

- 行が競合でない、または`head_sha`が渡したheadと違う。
- 行が通知済みである。
- 行にすでに作業項目が結ばれている。
- 行が最終の保留である。一時の保留は、起動と同じ文で外す。
- 同じPRに、終端でない`pr_fix`がある。綴りの大文字小文字は区別しない。

一意索引`work_items_active_pr_fix_key`に違反したときも、文全体が取り消されるので`null`を返す。
作業項目は状態`fixing`で挿入し、`conflict_check_id`に行のID、`conflict_episode`に行の競合の回を入れる。
ラウンドの番号と処理済みの位置は、同じPRの直近の`pr_fix`から写す。無ければ0にする。

`setPrConflictFixHold`は、結ばれていない競合の行の保留の理由を書く。今の値と違うときだけ書き、`null`で外す。
結ばれた行の保留は、結びを外す`releasePrConflictFix`が同時に書く。
`releasePrConflictFix`は、行の状態を問わず、結びを外す。作業項目が動いている間に競合が解けた行も、結びは外す必要があるためである。
`listPrConflictFixing`は、結ばれた行を、読み直していない順に返す。

`countPrConflictFixRounds`は、競合を直したラウンドを数える。
範囲は、競合の1回(行のIDと回の組)かPR全体である。PR全体は、掃除で行が消えても回数が戻らないよう、行を経由せず作業項目を直接数える。
どちらも同じ条件で数え、次のものは数えない。

- 状態が`failed`で、フローのジョブIDが無い作業項目。Claudeを走らせていない回で、直す機会を使い切らないためである。
- 何も変えずに終えた作業項目。状態が`reviewed`で、その状態へ移った最新の注記が`conflict round: up_to_date`である。

### 通知

通知は、競合の1回につき1回である。通知した時刻が空の競合は、次の順に通知する。

1. 競合を記録する。
2. 通知(notice)を登録する。同じ本文の未解決の通知があれば、重ねて登録しない。
3. 通知を新しく登録したときだけ、Discordに`needs_human`を送る。
4. 通知した時刻を記録する。競合のままで、まだ記録していない行にだけ書く。

通知の登録を、通知した時刻の記録より先にする。記録が先に成功して登録が失敗すると、通知が永久に出ないためである。
通知した時刻が空のまま残った行は、次の回に同じ手順をやり直す。
通知の本文は、固定文、PRのリンク、次の操作だけを載せる。コミットのshaも、PRの題名やブランチ名も載せない。
本文と解決の接頭辞は、小文字にそろえたオーナーとリポジトリから作る。PRのリンクも同じ綴りにする。場面によってGitHubの返す綴りが違っても、接頭辞を一致させるためである。
同じPRの本文は常に同じなので、未解決の通知がある間は重ならない。

通知を解決するのは、競合が終わったときだけである。新しい競合が始まったときには解決しない。
手動の実行と定期の実行が重なったとき、一方が出したばかりの通知を、他方が解決してしまうのを避けるためである。

通知した時刻を記録する文は、書けなかった理由を区別して返す。
書けなかったときだけ、別の文で行の状態を読む。書く文と同じ文の中で読むと、待っている間に別の実行が`resolved`にした行を、競合のままと取り違えるためである。

- 他の実行がすでに記録していたとき。競合は続くので、通知を解決しない。
- 行が競合でなくなっていたとき。通知の登録の後に、競合が解けたか、PRが閉じた。

行が競合でなくなっていたときは、この実行が新しく登録した通知だけを、idで解決する。競合を終わらせた側が動いた時点では、その通知がまだ無く、解決できなかったためである。
同じ本文の通知がすでにあって、この実行が登録しなかったときは、解決しない。

### 自動解決

マージ可否が真になったときと、PRを閉じたときは、通知を解決してから、行を`resolved`か`closed`に移す。
解決の対象は、種類`pr_conflict`と、本文の接頭辞`<owner>/<repo>#<PR番号>:`で選ぶ。
解決は冪等なので、行の更新より先に行う。解決に失敗した回は、行を`conflicted`のまま残し、次の回にやり直す。
行を移した後に、もう一度解決する。最初の解決と行の移動の間に、別の実行が通知を登録することがあるためである。
解決者は`watch_pr_conflicts`で、Consoleは「PRの競合の監視(自動)」と表示する。
マージ可否が`null`の回は、通知と行を変えない。

### 開いているPRの一覧で読めなかった行

開いているPRの一覧で読めなかった`conflicted`の行は、別に整理する。
マージされたPR、閉じたPR、一覧を読めなかったリポジトリ、下書きに戻したPR、読めなかったPRの行が当たる。
1回の実行で、競合している行を200件まで、読み直していない順に読む。

| 行の状況 | 扱い |
| --- | --- |
| リポジトリを設定が対象から外した | PRを読まずに、通知を解決して`closed`にする |
| オーナーの照合が、この回は失敗した | 設定は変わっていないので、PRを読まず、行を変えずに時刻だけを進める |
| PRが閉じた、またはマージされた | 通知を解決して`closed`にする |
| マージ可否が真 | 通知を解決して`resolved`にする |
| まだ競合している、または見送り | 読み直した時刻だけを進める。通知は出さない |
| PRまたは一覧を読めない(403、404) | 行を変えず、通知も解決せず、ログと時刻だけにする |

設定が対象から外したかは、照合の結果ではなく、設定だけで決める(`isRepoConfigured`)。照合の一時的な失敗で、通知を解決して行を閉じ、次の回に通知し直す揺れを避けるためである。
404は、PATがリポジトリを読む権限を失った場合にも返る。PRが無くなったとは扱わない。PRが閉じたと応答から読めたときだけ、行を閉じる。
一覧の読み取りで`getPr`が403か404になったPRは、読めたものに数えず、この整理で読み直す。

### 例外とrate limit

rate limitは、以降の読み取りを止める。残りは次の回に回す。
PATが拒まれた(401)ときも、以降の読み取りを止め、失敗を1件だけ記録する。結果の`unauthorized`が真になる。
403と404の一覧の読み取りは、ログだけに残して飛ばす。
それ以外の例外は、PRごと、リポジトリごとに捕まえて`factory.job_failures`に記録し、他を止めない。
予算かrate limitで読み残したリポジトリ、PR、競合の行の数は、結果の`deferred`に合計し、ログに警告で残す。
rate limitに当たったリポジトリ、PR、行そのものも、読み残しに数える。

### 掃除

`cleanup_db`が、`conflicted`以外の行を、最後の更新から保持期間(`retention_logs_days`)を過ぎたら削除する。
`conflicted`の行は、古くても削除しない。通知が未解決のままの行を消さないためである。
削除した件数は`cleanup_runs`に記録せず、ログに残す。

### 限界

- 列挙するリポジトリは、作業項目、競合の行、検索、設定の明示の4つのどれかに入るものに限る。
  次の条件をすべて満たすリポジトリの古いPRは、見つけられない。
  作業項目が`cleanup_db`に消された。競合の行が無い。検索に現れない。`factory_repo`でも`repo_allowlist`の項目でもない。
  このとき`repo_allowlist`にリポジトリを足してはならない。1件でも入れると、`repo_allowlist`が対象のリポジトリを絞り、書かなかったリポジトリがFactory全体で対象から外れ、この監視もその行を閉じる。
- 検索の索引は数分遅れる。検索は1つのオーナーにつき、更新が新しい100件までを読む。PATのアカウントの開いているPRが100件を超えると、古いPRのリポジトリは、検索には現れない。
- 作者の確認にPATのアカウントを使う。PATのアカウントが変わると、変わる前のアカウントが作ったPRは見つけられない。
- 計算前のPRが続くと、競合に気づくのが遅れる。GitHubはPRを読まれたときに計算するので、次の回に判定し直す。
- 競合が解けた後に、再び競合したときは、行を`conflicted`に戻して新しく通知する。
- 無効にしても、残っている通知は解決されない。残した通知は、再開した後に、競合が続く間は残り、競合が解けると自動で解決される。
  手で解決した通知は、その競合が解けるかPRが閉じるまで、再び出ない。同じ競合では、通知を重ねないためである。
- 2回目の解決は、接頭辞で通知を選ぶ。手動の実行と定期の実行が重なり、マージ可否が短時間に解けて再び競合する場合は、新しい競合の通知を解決することがある。Discordには届き、通知は競合が解けるまで再び出ない。
- 2回目の解決が例外を投げると、行は移った後なので、次の回の整理の対象にならない。その間に登録された通知が残りうる。残った通知は、人がConsoleから解決する。
- PATがリポジトリを読めなくなったときの専用の通知は無い(`pr_ci_check_denied`に当たるもの)。この監視だけを有効にしているときは、ログの警告だけが残る。
- PRが404になった行は、閉じずに残り続ける。PATの権限を失った場合と区別できないためである。
- 競合している行は、1回の実行で200件まで読む。超えた分は、読み直していない順に次の回へ回る。
- 開いているFactoryのPRが多く、予算を使い切る回が続くと、リポジトリの並びで後ろのものの読み取りが遅れる。順番の入れ替えはしない。読み残した数は`deferred`に出る。
- 一覧が1000件を超えるリポジトリは、読み切れないので飛ばす。検索だけが見つけたリポジトリはログの警告だけで、それ以外は失敗として記録する。
  検索だけが見つけたリポジトリは、設定でも作業項目でも選んでいない。対応できない失敗を、毎回記録しないためである。
- 検索だけが見つけたリポジトリを第三者が1000件超のPRで埋めると、毎回10ページを読み、PATのrate limitの枠を1リポジトリにつき1時間で約120リクエスト使う。1回の実行の上限(10ページ、予算120秒、rate limitでの停止)があるので、受け入れる。

## 例外の扱い

例外は、PRごと、行ごとに捕まえて、他の処理を止めない。
捕まえた例外は、`factory.job_failures`に記録する。rate limitと、権限の不足、実行を読み切れないエラーは、記録せずログだけに残す。

## 時計

時刻は実行の最初にworkerの`now`を1回だけ読む。GitHubの時計とずれても、確定を待つ2分と、期限の15分、2時間、24時間に余裕があるので、判定の結果は変わらない。
