# PRワークフロー

PRのレビュー(`f/factory/pr_review`)とPRの修正(`f/factory/pr_fix`)のフローの全体、起動条件、修正の回、差し戻し、設定値をまとめる。
これらのフローのコードを変更する人が読む。
レビューの投稿、タイムアウトと再実行、安全策は、`docs/internals/pr-workflow/`の各文書にある。
置き場は、末尾の[仕様の置き場](#仕様の置き場)の表から引ける。
PRのレビューと修正を使う手順は[PRのレビューとCIの運用](../operations/pr.md#prでレビューと修正を使う)に書く。
トリガーラベルが外れたままのPRと、検査の枠の記録の片付けの手順は[運用](../operations.md)に書く。
作業項目の状態の一覧は[作業項目](work-items.md)に書く。
安全策と残るリスクは、[PRワークフローの安全策の内部仕様の「PR修正の安全策」](pr-workflow/security.md#pr修正の安全策)に書く。

## 全体の流れ

PRワークフローは、Issueから要件定義を作る工程1と2とは別に、既存のPRをレビューし、修正する。
対象は人が作ったPRと、実装フローが作ったPRである。

PRレビューは3つのステップでできている。

| ステップ | 役割 |
| --- | --- |
| `pr_review_prepare` | PRを取得して確かめ、レビュー用のworktreeを用意する |
| `pr_review_generate` | Claudeにレビューを書かせる |
| `pr_review_post` | レビューを投稿して記録し、worktreeを消す |

PR修正は5つのステップでできている。

| ステップ | 役割 |
| --- | --- |
| `pr_fix_prepare` | 安全のための確認をして、PRのブランチのworktreeを用意する |
| `pr_fix_collect` | 修正の対象にするフィードバックを集める |
| `pr_fix_apply` | Claudeに修正させる |
| `pr_fix_verify` | 変更を確かめ、検査コマンドを実行する |
| `pr_fix_finish` | commitしてpushし、返信して再レビューを依頼する |

PRに投稿するのは、PRレビューの指摘と総評、PR修正の返信だけである。
失敗、人の対応待ち、ブロック、要件の不足、設計の不足といった運用上の知らせは、PRに書かずDiscordで知らせる。
Issue化の提案の承認と却下の結果は、PRのスレッドに返信する。

実装フローが作ったPRのCIの失敗も、PRには書かずDiscordとnoticeで知らせる。
この監視はレビューと修正のフローとは独立している。
設定`pr_ci_fix_enabled`が`true`のときは、失敗したPRを直す修正(CI回)を起動し、自動で直す対象の失敗は、直せるかが決まってから知らせる。
内容は[PRのCI監視の仕様](pr-ci.md)に書く。

## 起動条件

`poll_prs`がPRを見つけて作業項目を作り、フローを起動する。

| フロー | 起動条件 |
| --- | --- |
| PRレビュー | PRに`factory:review`ラベルが付いた |
| PRレビュー | PRのレビューの依頼先かassigneeがこのインスタンスのGitHubアカウントで、未処理のhead(`head_sha`)がある |
| PR修正 | PRに`factory:fix`ラベルが付いた |
| PR修正のCI回 | `watch_pr_ci`が、失敗したheadの行を直すと判断した。条件は[PRのCI監視の仕様](pr-ci.md)の「起動」に書く |

### PRの発見

`poll_prs`は、ラベル、レビューの依頼、assigneeのPRを、検索でなく収集が書いた表から見つける。
表の行をPATのアカウントへの依頼、assignee、レビューのラベル、修正のラベルの4つで絞り、`getPr`と`getIssue`で開いていることと今も対象であることを確かめてから候補にする。
表が新しくない明示リポジトリは、RESTの開いているPRの一覧を、同じ4つで絞って読み、同じ確かめを通す。
明示でないリポジトリは見送る。
確かめた後の判定は、`decidePrActions`が行う。

チーム宛てのレビューの依頼は、`GET /user/teams`のチームの数値IDと、PRの`requested_teams`の数値IDで照合する。
チームへの依頼は、作者が許可された人のPRだけ候補にする。
チームを使えない組織では、チーム宛てだけの依頼を見送り、直接の依頼だけを拾う。
個人の所有者のリポジトリには、チーム宛ての依頼が付かない。
表の読み方と見送る条件は[GitHubの収集の仕様](github-collect.md#所有者の単位の読み取り)に書く。

トリガーのラベルは、着手(claim)したときに消費して外す。
レビューの依頼とassigneeの経路には、消費するラベルが無い。
ラベル名は`factory_config`の`review_label`と`fix_label`で決める。

ブランチ名が`factory/drawio-viewer-`で始まるPR(draw.ioのビューアの固定を上げるPR)には、`factory:fix`ラベルが付いていてもPR修正を始めない。
`decidePrActions`が`headRef`で判定し、ラベルは消費せずに残す。
ラベルは外れず、修正は人が行う。
判定はブランチ名だけで行うので、`factory_repo`に限らず、担当するすべてのリポジトリに効く。
`pr_fix_prepare`も同じ判定(`evaluateHumanOnlyBranchGuard`)で止め、作業項目をblockedにする。
修正を許すと、固定のファイル以外も書き換えたcommitを、人が気づかずにマージするおそれがある。
このPRは人が直す。
レビューは動く。

PR修正の通常の回は、ラベルからしか起動しない。
コメントやcommitのpushだけでは起動しない。
CI回だけは、`watch_pr_ci`が起動する。
次のラウンドを始めるには、PRに`factory:fix`ラベルを付け直す。
PRレビューが終わった(`reviewed`)PRにも付けられる。

同じPRに終了していないPR修正があるとき、許可された人が付けた`factory:fix`ラベルは、PR修正を始めない。
`decidePrActions`が、候補の`activeFixItemId`で判定し、ラベルは消費せずに残す。
保留の理由は、PRと進行中の作業項目のidを`poll_prs`のinfoログに残す。
noticeは出さない。
修正中に付けたラベルは保留され、その修正が終わった後に1回だけ新しいラウンドが始まる。
同じPRのPR修正が並んで動くと、同じブランチへ別々にpushして競合する。
部分一意インデックス`work_items_active_pr_fix_key`が、終了していないPR修正を、PRごとの1件までに制限する。

判定は、ポーリングの先頭で読んだ作業項目の状態に基づく。
読んだ後に別のPR修正が始まると、ラベルの消費の後にある挿入が、このインデックスに阻まれる。
このとき、消費したラベルを付け直し、失敗ではなく見送りとして数える。
人の依頼は失われず、その修正が終わった後のポーリングが拾う。
ラベルの付け直しも失敗したときは、ラベルが外れたままになる。
取得の確認に失敗したときの付け直しと同じく、失敗に記録して人へ知らせる。

同じPRに終了していない`pr_review`があるときも、許可された人が付けた`factory:review`ラベルは、レビューを始めない。
`decidePrActions`が、候補の`hasActiveReviewingItem`で判定し、ラベルは消費せずに残す。
保留の理由は、PRを`poll_prs`のinfoログに残す。
noticeは出さない。
レビュー中に付けたラベルは保留され、そのレビューが終わった後の巡回で、新しいレビューが始まる。
ラベルを消費してから挿入が阻まれると、人の依頼が失われるためである。
`pr_review`の行の綴りは、書き手によって違いうる。
登録のステップとdependabotは、PRのbaseのリポジトリが返す正規の綴りで書く。
表と明示の一覧から来る候補は、`confirmPrCandidate`が`getIssue`の応答の綴りで作る。
綴りの違う行ができるのは、GitHub側の改名で大文字小文字が変わった場合と、追跡中のPRの経路が前の行の綴りを引き継ぐ場合などである。
同じPRを指す`pr_review`の検索は、ownerとrepoを小文字にして比べる。
稼働中の行の確かめに加えて、最新の行の取得、過去のレビューの有無、再開の巡回が見る新しい行の確かめが対象である。
行そのものの綴りは、書き手ごとにそのまま残す。
`pr_fix`の稼働中の判定は綴りを区別したままで、変えない。
最新の行の取得(`latestPrWorkItem`)と新しい行の確かめ(`newestNewerPrWorkItem`)は`pr_fix`と共有なので、その挙動も変わる。
`previousFixRound`と`prevFixSeed`は、綴りの違う`pr_fix`の行も引く。
取り消した`pr_fix`の手動の再開は、綴りの違う新しい行があれば断られる。
どちらも、見落とす向きでなく、安全な向きの変化である。

部分一意インデックス`work_items_active_pr_review_key`が、終了していない`pr_review`を、PRごとの1件までに制限する。
ownerとrepoは小文字にして比べる。
判定の後に別のレビューが始まる競合で、挿入が何も作らなかったときは、レビューの起動の共有の手順(`startPrReview`)が`already_active`を返す。
ラベルの経路は、消費したラベルを付け直して見送りに数える。
割り当ての経路は見送りに数える。
どちらも失敗に数えない。
同じ巡回で`factory:fix`も付いているPRは、レビューの見送りの後に、修正の判定へ進む。

インデックスを足すmigrationは、重なった古い行を`cancelled`にする。
`pr_review`はリースを使わないので、取り消された行のフローは自分では止まらない。
止めるのは、投稿の直前に作業項目が`reviewing`かを確かめる処理で、そうでなければ投稿しない。
残るリスクは[R-CON-04](../security-risks.md#r-con-04)である。

修正への指示は、ラベルを付ける前に、PRへ通常のコメントとして書く。
`pr_fix_collect`が、ほかの人のコメントと同じくフィードバックとして集める。

### 投稿者の関係の確認

レビューとコメントの投稿者の`author_association`が`allowed_labeler_associations`に含まれないとき、その投稿は起動の対象から外す。
既定値は`OWNER`、`MEMBER`、`COLLABORATOR`である。

### ラベルの付与者の確認

`poll_prs`は、`factory:review`と`factory:fix`のそれぞれについて、そのラベルを最後に付けた人を、ラベルの`labeled`イベントの`actor`で確かめる。
許可されるのは、FactoryのPATのアカウントと、`allowed_labeler_logins`に挙げたアカウントである。
`allowed_labeler_ids`にIDを入れたアカウントは、`actor`の数値IDも一致するときだけ許可する。
許可されない人が付けたラベルと、付与者を特定できないラベルは、外さずに残し、起動しない。
取得の直前にも、同じ確認をもう一度行う。
イベントを取得できなかったPRは、そのポーリングでは対象にしない。
付与者を判定できないPR(直近100件のラベルのイベントにトリガーラベルのイベントが無い)は、`labeler_check_limit`のnoticeを残し、ラベルを外して付け直すまで対象にしない。
仕組みの全体は[ラベル付与の制限](../security.md#ラベル付与の制限)にある。

レビュー依頼かassigneeによる起動と、追跡中のPRの新しいcommitによる再レビューは、ラベルを介さない。
この2つは、PRの作成者が許可されたアカウントのときに限る。
トリガーラベルが拒否された状態で付いているPRでも、始めない。
同じリポジトリのブランチから出した第三者のPRは、許可されたアカウントがラベルを付けたときだけレビューされ、新しいcommitのたびにラベルの付け直しが要る。

PRのheadが対象のリポジトリにないとき(forkのPRと、headのリポジトリを取得できないPR)は、ラベルの経路もラベルを介さない経路も、レビューを始めない。
`decidePrActions`が、始めるはずだったレビューを見送りとして返し、`poll_prs`が`fork_head_denied`のnoticeを残す。
ラベルは外さない。
`pr_review_prepare`も、作業項目を手で作るなどの経路に備えて、clone、fetch、worktreeの前に同じ確認をする。
通らなければ、作業項目を終端の`blocked`にして理由を残し、Discordで人に知らせてから、処理を飛ばす。
同じ判定は、PR修正の準備のステップの「forkからでない」確認と共有する。

`pr_review_prepare`は、forkの確認より先に、リポジトリのオーナーを`owners`と照合する。
通らなければ、PRを読む前に、処理を飛ばす。
そのとき、作業項目を終端の`blocked`にして理由を残し、Discordで人に知らせる。
forkのPRを見送るときと同じ終わり方である。
照合は[運用](../operations.md)の「オーナーの数値IDを固定する」に書く。

`pr_review_prepare`は、forkの確認の後に、PRのheadのブランチが指す作業項目を引く(`matchBranchWorkItem`)。
作業項目が設計の段階(`designing`、`awaiting_design_approval`)にあれば、`pr_review`の作業項目を終端の`blocked`にして、処理を飛ばす。
clone、fetch、worktreeの作成より前に飛ばす。
注記は固定文である。
検出が始めたレビューは、Discordに通知しない。
人の操作が要らないためである。
人が`review_label`で頼んだレビューと、Consoleの投入で頼んだレビューは、同じ注記で終端にして、Discordに通知する。
ラベルは取得時に消費済みで、投入は頼んだ人が結果を待っているので、黙って落とすと頼んだ人が気づけないためである。
どちらのレビューかは、`pr_review`の行の`body`に書いた印で見分ける(`reviewRowBody`)。
再実行がフローの入力を引き継がないためである。
ラベルの印と投入の印は別の文字列である。
準備は、どちらも人が頼んだレビューとして読む(`isReviewRequestedByLabel`)。
設計の承認の後の実装が同じブランチへpushして完了すると、新しいheadのレビューが自動で付く。
実装のpushなしに設計と実装が止まったとき(上限での人の対応待ち、期限切れ、取り消し)は、次の`poll_prs`の巡回が同じheadのレビューを検出し直す。
保留した行のheadは、作業項目が設計の段階か実装が動く間だけ、処理済みとみなすためである(`resolveLastKnownHeadSha`)。
作業項目が引けないときと、ほかの状態(実装中と承認直後を含む)では止めない。
実装の完了で付くレビューを止めないためである。

### Consoleからの投入

PRのレビューは、`factory:review`ラベルのほかに、投入からも始められる。
入口は2つある。
1つは、Console用workerの`pr_review_submit`である。
もう1つは、通常のworkerで動くフロー`pr_review_intake`の登録のステップ(`pr_review_intake_register`)である。
Consoleの「PRレビューの投入」の画面が、この入口を呼ぶ([PRレビューの投入の画面](console/work-items.md#prレビューの投入の画面))。
Windmillから`pr_review_submit`かフローを実行しても投入できる。

`pr_review_submit`は、引数が`owner`、`repo`、`pr_number`だけである。
操作者は引数に取らず、ジョブの実行文脈から導く。
次の順に検査し、通らなければフローを起動せず、理由の符号だけを返す。

1. `owner`と`repo`がGitHubの名前の形であること(`invalid_owner`、`invalid_repo`)。
2. PR番号が正の安全な整数であること(`invalid_pr_number`)。
3. `factory_config`が許可したリポジトリであること(`repo_not_allowed`)。
4. 操作者を導けること(`actor_unknown`)。
5. 同じPRの稼働中の`pr_review`が無いこと(`already_reviewing`)。
   ownerとrepoは小文字で比べる。

このscriptはsecret変数を読まないので、GitHubは読まない。
操作者がその場で受け取る断りは、5のDBの読み取りが返すものだけである。
断りは記録せず、起動した投入だけを操作の記録(`pr_review_submit`)に残す。
記録には、`owner`、`repo`、`pr_number`だけを入れる。

登録のステップは、GitHubを読んで、次の順に確かめる。
入力の形と許可はGitHubを読む前に確かめるので、フローを直接実行して不正なPR番号を渡しても、GitHubは読まない。

| 断りの符号 | 内容 |
| --- | --- |
| `invalid_pr_number` | PR番号が正の安全な整数でない |
| `repo_not_allowed` | 名前の形が不正、または設定が許可していない。GitHubが返す正規のリポジトリ名で確かめ直す |
| `pr_not_found` | PRが見つからない(404)。番号がIssueのとき、権限が無いときも含む |
| `repo_mismatch` | 入力のリポジトリ名が、GitHubが返す正規の名前と大文字小文字を除いて一致しない(改名で転送された場合) |
| `pr_closed` | PRが閉じている、またはマージ済み |
| `fork_head` | headが別のリポジトリにある。ラベルの経路と同じ判定で、`fork_head_denied`のnoticeを残す |
| `owner_mismatch` | リポジトリのオーナーのIDが、設定の`owners`と食い違う。オーナーの照合がnoticeを残す |
| `already_reviewing` | 挿入が、同じPRの稼働中の行に阻まれた |

GitHubの読み取りの失敗(404以外)は、断りでなく例外にして、フローを失敗させる。
断りは、ステップのジョブの結果として読む。
noticeに残すのは、上のforkとオーナーのIDの2つだけである。

作業項目の行は、GitHubが返す正規の綴りのownerとrepoで書く。
作業項目の作り方と起動は、ラベルの経路と同じ共有の手順(`startPrReview`)である。
`body`には投入の印を書く(`reviewRowBody("request")`)。
`claimed_by`は操作者でなくFactoryのログイン名で、親の作業項目の導き方と、観測したレビューのidの記録も、ラベルの経路と同じである。
ラベルを介さないので、ラベルの付与者の確認(`isAllowedLabeler`)は通らない。
代わりに、操作者を導いて操作の記録に残す。
dependabotのPRも、ラベルの経路と同じく特別に扱わない。

同じPRの二重の投入は、3つの層で防ぐ。

1. `pr_review_submit`の同期の確認。
2. 登録のステップの挿入が持つ`WHERE NOT EXISTS`。
   インデックスの有無に頼らず、順次の二重の投入を防ぐ。
3. 部分一意インデックス`work_items_active_pr_review_key`。
   並行する挿入に対する最後の防壁である。

ラベルの経路と投入が重なっても、稼働中の行は2件にならない。
投入を止める停止スイッチは無い。
`poll_prs`のスケジュールを止めても、投入は止まらない。

### 対象のリポジトリ

対象は、`factory_config`の`repo_allowlist`に含まれるリポジトリだけである。
`repo_allowlist`が空なら、`owners`に含まれるリポジトリのすべてが対象になる。
`factory_repo`は`repo_allowlist`に関わらず常に対象である。

`poll_prs`は作業項目を作る前に許可リストで候補を絞る。
作業項目を作った後で`factory_config`を変えることもあるので、両方のフローの準備のステップも許可リストを確かめ直す。

### ラベルを外した後の追跡

Factoryが扱ったPRには、トリガーのラベルのほかにラベルを付けない。
状態は作業項目の状態(`work_items.status`)だけで表し、Consoleの**作業項目**に表示する。

ラベルが外れた後も追跡を続けるため、`poll_prs`はDBからPRを見つけ直す。
`f/factory/lib/db.ts`の`listTrackedPrs`が、次の条件をすべて満たす作業項目を返す。

- 種類(`kind`)が`pr_review`か`pr_fix`である。
- 状態が取り消し(`cancelled`)でない。
- `tracked_pr_days`以内に更新された。
- PRごとの最新の行で、閉じた印が有効でない。

`(owner, repo, pr_number)`ごとに最新の行だけを見て、新しく更新された順に最大200件を読む。
200件を超えて古い側を読み残した回は、警告のログと結果の`trackedOverLimit`に残る。
許可リストに合わないリポジトリの行も、この200件の枠を使う。

`poll_prs`は、そのPRが`owners`(`id`の照合を通ったオーナー)と`repo_allowlist`に合い、まだopenであることを`getPr`で確かめてから候補にする。
人が新しいcommitをpushすると、この経路でPRレビューが自動で起動する。
1回のpushにつき、Claudeの実行は1回である。

`getPr`でマージ済みと分かったPRは、そのPRの`pr_review`と`pr_fix`の行に、閉じた印(`work_items.pr_closed_at`)を付ける。
結果の`trackedClosedMarked`は、印を付けたPRの数である。
印が有効なPRは、以後の回で一覧に出ないので、`getPr`も起きない。
印の時刻は、一覧を読む前にDBの時計から取る。
その時刻より前から更新されていない行にだけ付くので、一覧を読んでから動いた行に、有効な印は付かない。
印が有効なのは、行がその後に更新されていない間だけである。
状態の遷移と`retry_work_item`による再開は更新時刻を進めるので、印を外す処理なしに、そのPRは追跡へ戻る。
マージせずに閉じたPRには印を付けない。
開き直されたPRを取りこぼさないためである。
列を足すmigrationより先にコードが反映された間は、印の列が無い。
一覧は印の無い行として今までどおり返し、印の書き込みは警告のログを残して続ける。

`review_post_mode`が`gated`のときは、レビューを投稿しない。
`gated`は検証用に予約した値で、承認を経て投稿する画面はまだ無い。
このモードでは、PRはレビューの依頼かassigneeの経路でだけ見つけ直す。
PRレビュー完了の通知は送らない([通知](notifications.md#通知を送らない場合))。
投稿しない状態が続くことは、日次のまとめと要対応のnoticeで知らせる([継続の通知](notifications.md#レビューを投稿しない状態の継続))。

## 自己再発火の防止

Factoryが投稿するIssueのコメント、PRのレビュー、レビューへの返信には、必ず目印(`<!-- factory:<kind>:<work_item_id> -->`)を入れる。
目印は本文の最後の行に置き、判定では最後の行の目印だけを読む。

Factory自身の投稿かどうかは、`f/factory/lib/github.ts`の`isFactoryPost`で次の両方を満たすかで判定する。

- 投稿者のログインが、viewer(PATの持ち主のGitHubアカウント)と一致する。
  大文字と小文字は区別しない。
- 本文が、最後の行にFactoryの目印を持つ。

Factoryは人と同じGitHubアカウント(共有のPAT)で動く。
そのため、ログインの一致だけでは人の投稿と区別できない。
目印は誰でも本文に貼れるので、目印だけでも区別できない。

フィードバックとして扱わないのは、次の返信だけである。

- Factory自身のPR修正の返信(`pr_fix`の目印を持つもの)
- 再レビューの了承と解消の返信(`pr_review_ack`の目印を持つもの)
- 質問への回答の返信(`pr_review_answer`の目印を持つもの)

人が同じアカウントで書いたコメントは、目印が無いのでフィードバックになる。
Factory自身のPRレビューと、その未解決のインラインの指摘もフィードバックになる。

## 作業ディレクトリ

対象リポジトリのメインのクローン(`/workspaces/<owner>/<repo>/main`)はfetchだけに使い、working treeをcheckoutしない。

PRレビューは、PRごと・実行ごとにdetachedのworktreeを作り、投稿のステップで消す。

```bash
git worktree add --detach /workspaces/<owner>/<repo>/review-<pr>-<sha7>-<run> <sha>
```

`<sha7>`はレビューするコミットのshaの先頭7文字である。
`<run>`は、準備のステップが実行のたびに乱数から作る8桁の小文字の16進数である。
flowのジョブIDは、先頭の桁が長く変わらず、同じジョブの再実行では値も同じになるので使わない。
実行ごとに名前が変わるので、残りがあっても作成は衝突せず、準備のステップは残りを消さない。
準備のステップは、worktreeを作る間にheadのshaが動いていないかを最後にもう一度確かめる。
作った後の確認が失敗したときは、そのステップが作ったworktreeだけを消して、元の例外を投げる。
生成のステップが早く抜けて投稿しなかったときも、投稿のステップがworktreeを消す。
生成のステップが失敗して残ったworktreeは、やり直しを妨げず、失敗した実行の数だけ残る。
残りは、PR番号で選んで消す(shaは問わず、`<run>`の無い名前も含む)。
PRが閉じたとき(`poll_issues`)は、期限を待たずに消す。
`cleanup_workspaces`は、作業ツリーの一覧からPRごとに扱う。
そのPRに終端でない`pr_review`があれば、見直している最中なので、何も消さない。
無ければ、ディレクトリの更新が`worktree_ttl_days`より古いものだけを消す(作業項目の行が消えたPRも同じ)。
gitが`initializing`でロックした残りは`--force`を2回で消し、ほかの理由のロックは消さずに警告を残す。

PR修正は、`git gtr new`で作るPRのブランチのworktreeを使う。
PR修正の完了のステップはworktreeを消さず、後で`cleanup_workspaces`が片付ける。

## 修正

### 止めたときの作業項目の状態

PR修正のステップの結果の`blocked`と、作業項目の状態のブロック(`blocked`)は別のものである。
修正と検証のステップは、続けられないときに止める結果(`blocked`)を返す。
完了のステップ(`decideFixFinishAction`)は、この結果の作業項目を人の対応待ち(`needs_human`)にする。

作業項目がブロックになるのは、次の4つのときだけである。

| 止めたところ | 例 |
| --- | --- |
| 準備のステップの確認([準備での確認](#準備での確認)) | PRがdraft、forkのPR、親のIssueの実装フローが実行中、親のIssueかブランチの作業項目が設計の段階にある、ブランチの実装が動く直前、worktreeの使用中、時間設定 |
| 完了のステップの、pushの直前の確認 | 修正の実行中にPRのheadが動いた |
| 要件の不足の差し戻しに成功した | [requirements_gapの差し戻し](#requirements_gapの差し戻し) |
| 設計の不足の差し戻しに成功した | [設計の不足の差し戻し](#設計の不足の差し戻し) |

それ以外で止めたとき(Claudeが止めた、日次予算、禁止された変更、検査の失敗、`.git`の書き換えなど)は、作業項目は人の対応待ちになる。

### フィードバックの収集

収集のステップ(`pr_fix_collect`)は、作業項目の処理済みの位置より新しいフィードバックを集める。
処理済みの位置は[watermark](#watermark)に書く。
集めるのは、PRのレビュー、インラインのレビューコメント、Issueコメントである。

Factory自身のPRレビューと、目印の無いインラインの指摘も集める。
Factoryのレビューの後に`factory:fix`ラベルを付けるのは、その指摘を直させる操作だからである。
集めるものが無ければ、「no actionable feedback」として人の対応待ちにする。

承認済みの要件定義は、このステップの結果で受け渡さない。
修正と検証のステップが、親の作業項目(`parent_work_item_id`)から直接取得する。

### 修正の適用

修正のステップ(`pr_fix_apply`)は、`factory-fix`スキルでheadless Claudeを実行する。
入力は、集めたレビューとコメント、未解決のコメント、承認済みの要件定義である。
レビュー回で親の承認済みの設計書があるときは、設計書も入力に加える([設計書の受け渡し](#設計書の受け渡し))。

Claudeは修正の結果(`outcome`)、理由、要約、各コメントへの返信、コミットの件名と本文を返す。
日次予算を超えていれば、Claudeを起動せずに止める結果(`blocked`)を返す。
Claudeの実行が失敗したときは例外を投げる。

### 設計書の受け渡し

レビュー回の修正と、検査に失敗した後のClaudeの再実行(検証のステップ)だけが、親の承認済みの設計書を受け取る。
CI回と競合回は受け取らない。
この2つはClaudeの出力が完了かブロックに絞られていて、設計へ戻す道が無いためである。

渡すかは`loadParentDesignForFix`が、次の順に判定する。
どれかに当たれば設計書なしで動く。

1. 設定`design_enabled`が偽で、設計工程が無効。
   何も読まない。
2. レビュー回でない。
3. 親の作業項目が無い。
4. PRのheadが、親のFactoryのブランチでない。
   作業項目のID、owner、repoのどれかが親と違うときも含む。
   人が書いたPR(`Closes #N`で親に結んだもの)は、設計書を渡す相手ではないためである。
5. 親がPR作成済み(`pr_open`)でない。
   設計の最中や実装中の親の設計書は、今のPRと食い違いうるためである。
6. 親のIssueに、より新しいサイクルの作業項目がある。
   置き換わった親の設計書は、今のサイクルの設計と無関係なためである。
7. 親の最新の要件定義の承認が、親の今の試行(`attempt`)の承認でない。
8. 実装の関門(`designGate`)が止める。
   止めた理由は、本文を含まない警告に残す。

修正のステップと検証のステップは、同じ判定を使う。
再実行だけ設計書の有無が変わると、設計の不足を返せる実行と返せない実行が、同じ修正の中で入れ替わるためである。

設計書なしの実行は、`FIX_SCHEMA`の出力の形、プロンプト、出力の検査で動く。
設計書がある実行は、結果に`design_gap`を足した出力の形(`FIX_SCHEMA_WITH_DESIGN_GAP`)と、設計書の囲みと`design_gap`の説明を足したプロンプトを使う。
`factory-fix`スキルは変えない。
プロンプトが、スキルの「要件や設計の変更は`requirements_gap`」より、`design_gap`の説明を優先すると明示する。
設計書は信頼できない入力を含みうるので、囲みに入れて、データとして読ませる。

`design_gap`を返してよいのは、承認済みの設計書どおりに直すと、要件定義の要件か受入条件を満たせないときだけである。
レビューの指摘が設計と食い違うだけで、要件を満たせるときは、返信の判断を`skipped`にして、理由を返信させる。
報告には、設計のどこが足りないかと、元のレビュー指摘の要約を書かせる。

出力の検査(`isFixClaudeOutput`)は、次を不正な出力にする。

- 設計書の無い実行の`design_gap`
- 報告(`blocked_reason`)が空の`design_gap`
- 返信(`replies`)が空でない`design_gap`。
  返信を投稿しないので、提案が黙って消えるのを防ぐためである。

CI回の出力の検査は`design_gap`を拒む。
設計工程が無効の間は設計書が渡らないので、`design_gap`は返らない。

### 検証

検証のステップ(`pr_fix_verify`)は、修正をpushしてよいかを確かめる。
Claudeが要件の不足、設計の不足、ブロックのどれかを返したときは、検証するものが無いのでそのまま返す。

検証は次の順に進む。

1. 変更を調べ、禁止された変更があれば止める結果を返す。
2. 検査コマンドを全件実行する。
3. 検査に失敗したら、日次予算の範囲で、失敗の出力を添えてClaudeの修正を1回だけ追加で実行する。
4. 変更をもう一度調べ、検査コマンドの全件をもう一度実行する。
5. それでも失敗するときは止める結果を返す。

変更を調べる時点と内容は[安全策の実装](pr-workflow/security.md#安全策の実装)に書く。

### commitとpush

完了のステップ(`pr_fix_finish`)は、commitの前に[コミットの前の再確認](pr-workflow/security.md#コミットの前の再確認)をする。
commitとpushの直前には、リポジトリのオーナーの数値IDを照合する。
準備の入口から長い実行を挟み、その間に名前が別の人に渡りうるためである。
通らなければ、pushと返信をせずに、作業項目を`blocked`にしてDiscordで人に知らせる。
通ったら、commitしてpushし、各コメントに返信して、再レビューを依頼する。
作業項目は再レビューの依頼済み(`rereview_requested`)になる。

コミットメッセージは、Claudeが提案する件名(`commit_subject`)と、任意の本文(`commit_body`)をフローがつないで作る。

- 件名はConventional Commitsの形で、50文字以内を目安にする。
  72コードポイントを超えると拒否する。
- 本文は箇条書きにする。
- `Co-Authored-By`と`Generated-By`のトレーラーは、`commitAndPush`の`withCommitTrailers`が付ける。
- 英数字と日本語の間のスペースを取り除く。
  コードスパンの中は除く。

pushするcommitが無くても、溜めた返信は投稿する。
Claudeがすべての指摘を見送った場合も、返信をGitHubに届けるためである。
すべての返信が`skipped`で、Factoryの指摘のスレッドに付くものがあれば、再レビューの依頼済みで終える。
それ以外は人の対応待ちになる([再レビューの依頼](#再レビューの依頼))。

### 再レビューの依頼

再レビューは`factory_config`の`default_reviewers`に依頼する。
空なら、そのラウンドを起こしたレビューとコメントの投稿者に依頼する。
PRの作者とFactoryのアカウントは依頼先から除く。

修正はpushまで済んでいるので、依頼の結果に関わらず作業項目は再レビューの依頼済みに進める。
依頼できなかったときの記録は、結果によって次のように分ける。

| 依頼の結果 | 作業項目の理由(`status_reason`) | notice | Discordの通知 |
| --- | --- | --- | --- |
| 依頼先の候補がいない | 残す | 残さない | 別に通知しない |
| 候補が全員除外された | 残す | 残さない | 別に通知しない |
| 依頼のAPIが失敗した | 残す | `pr_fix_reviewer_request_failed` | `pr_fixed`の通知の補足欄に載せる |

候補がいない場合と全員除外された場合は想定内で、人がすることは無い。
`pr_fixed`の通知そのものが、再レビューの依頼という結果を伝える。

依頼のAPIが失敗したときは、人がGitHubのPRでレビュアーを依頼する必要がある。
依頼の前のPRの取得(`getPr`)の失敗と、Botや削除済みの作成者の名前で依頼を組み立てられない場合も、APIの失敗として扱う。

返信に`skipped`があるラウンドは、`factory:review`を付けて再レビューに回す(CI回を除く)。
見送りの理由を読んで答えるのは再レビューだからである。
再レビューが答えられるのはFactoryの指摘のスレッドだけなので、そこに付く見送りが無ければ付けない(`hasSkipOnFactoryThread`)。
スレッドを読めないときは、付くものとして扱う。
Issue化の提案があるラウンドは、提案が決まるまで付けない。

すべての返信が`skipped`でcommitが無いラウンドは、人の対応待ちにせず、再レビューの依頼済みで終える。
watermarkはすべての返信を投稿した後に進める。
レビュアーへの依頼と`pr_fixed`の通知はしない。
結果は再レビューの通知で届くためである。
次のどれかに当たるラウンドは、人の対応待ちにする。

- `fixed`の返信が混ざるのにcommitが無い。
- Factoryの指摘のスレッドに付く見送りが無い。
- 見送りの返信を1件でも投稿できなかった。
  watermarkを進めず、ラベルも付けない。
  復旧は再実行に絞り、`fix_reply_post_failed`を残さない。
  人が返信すると、再実行の返信と二重になるためである。
  再実行は同じ指摘を集め直すので、投稿できていた返信はもう一度投稿されることがある。

ラベルを付けられないときは人の対応待ちにし、次の操作に`factory:review`を付けることを書く。
オーナーの照合が止めたときは、その理由で人の対応待ちにし、ラベルを付けるよう案内しない。
反論の後に`pr_fix`を自動で起動しない。
人が`factory:fix`を付ける。

返信は`matchReviewThreadForComment`と同じ照合で見つけたスレッドの最初のコメントに宛てる(`replyTargetCommentId`)。
GitHubは返信への返信を受けないので、反論の返信にそのまま宛てられないためである。
スレッドが見つからないときは、元のコメントに宛てる。

## CIの失敗を直す回

CIの失敗を直す回(CI回)は、PRのCIが失敗したとき、失敗したジョブのログから修正するための回である。
`pr_fix`のフローを、作業項目の`ci_check_id`が非NULLのときだけ、次のように変えて動かす。
`ci_check_id`は、直す失敗の行(`pr_ci_checks`)のIDである。
失敗の行の状態は[PRのCI監視の仕様](pr-ci.md)に、ログとプロンプトの部品は[CIの失敗を直す部品の仕様](ci-fix.md)に書く。

### 通常の回との違い

| ステップ | CI回 |
| --- | --- |
| 準備 | 修正ラウンドの上限を確かめない。失敗の行が、いまのheadについて、この作業項目で修正中であることを確かめる。worktreeを用意した後、無視されたファイルを消す |
| 収集 | レビューもコメントも集めない |
| 修正 | 失敗した実行のログの抜粋をClaudeに渡す。`Bash`は渡さない。`metadata`ジョブだけが落ちていれば、Claudeを起動せず、`wmill-lock.yaml`のhashを再計算する |
| 検証 | 変更を許可リスト方式でも検査する。返信を持つ結果は受け付けない。変更が再計算と一致する`wmill-lock.yaml`だけのときは、検査コマンドを実行しない |
| 完了 | 返信を投稿せず、作業項目のheadと処理済みの位置を更新しない。pushの直前にPRの状態を確かめる。再計算の出力は、baseの先端も確かめ直す |

`metadata`ジョブの失敗を再計算で直す流れは、[CIの失敗を直す部品の仕様](ci-fix.md#metadataジョブの失敗を直す経路)に書く。
再計算で直せないPRは、固定の理由で人の対応待ちになり、`mise run metadata`を案内する通知が出る。

修正ラウンドの上限を確かめないのは、CI回が`fix_round`を前の値のまま写すためである。
指摘の修正が上限に達したPRでも、CI回を止めない。
CI回の回数の上限は、`pr_ci_fix_max_rounds`が決める。

失敗の行が合わないときは、準備のステップの結果を`skip`ではなく`guard_blocked`にする。
`skip`にすると、完了のステップが何もせず、作業項目が修正中のまま残るためである。

CI回の作業項目は、`parent_work_item_id`を持たない。
要件の不足は差し戻さず、人の対応待ちにする。

### 作業項目のheadを更新しない理由

通常の回は、pushしたshaを作業項目の`head_sha`に記録する。
CI回は記録しない。
`poll_prs`の自動のレビューは、PRの最新の作業項目の`head_sha`とPRのheadが違うときに起動する。
CI回が記録すると、pushしたheadが「処理済み」になり、再レビューは起動しない。
通常の回と逆なので、完了のステップの配線を調べるテストで固定している。

### 再レビューへの入力

CI回か競合回がpushしたheadのレビューには、どちらの回の差分かを、プロンプトの固定文で伝える。
そのPRの`pr_fix`のうちCI回か競合回のどれかが、pushしたcommitにレビューするshaを含むときに限る。
最新かどうかと状態は問わない。
pushしたcommitは、依頼の前後で変わらないためである。
人が後からpushしたheadのレビューには伝えない。
この問い合わせが失敗したときは、固定文を足さず警告を残し、通常のレビューを続ける。
値はDBから決める回の種類(CI回、競合回、どちらでもない)だけで、PRの内容からは決めない。
CI回の固定文は、次の点を重点的に見るよう頼む。

- テストの弱体化。
- 抑制のコメントの追加。
- 原因を隠すだけの修正。
- 失敗の原因と無関係な振る舞いの追加(外への通信、環境変数の読み取り)。
- 無視ファイルとツールの設定の変更。

CI回のClaudeは、通るように直す立場なので、検査を弱めて通す誘惑があるためである。
競合回の固定文は、[競合回の再レビューへの入力](#競合回の再レビューへの入力)に書く。

再レビューの依頼(`requestRereview`)は通常の回と同じである。
CI回は集めたレビューとコメントが無いので、`default_reviewers`が空なら、依頼先が無く、依頼しない。

### 再開

CI回の`pr_fix`は、手動の再開(`retry_work_item`)でも、イメージが古いときの自動の再開でも再開しない。
作業項目だけを再開すると、失敗の行が`fixing`のまま食い違うためである。
回が終わると、`watch_pr_ci`が失敗の行を`failed`か`superseded`に戻す([PRのCI監視の仕様](pr-ci.md)の「回復」)。
PRにpushしてheadが変わると、新しい失敗として判定される。

競合を直す回(`conflict_check_id`が非NULL)の`pr_fix`も、手動の再開でも、イメージが古いときの自動の再開でも再開しない。
競合の行が、直している作業項目を結んだままになり、行と作業項目が食い違うためである。

## マージの競合を解く回

マージの競合を解く回(競合回)は、PRのブランチが既定のブランチ(base)と競合したとき、baseをmergeして競合を解き、mergeコミットをpushするための回である。
`pr_fix`のフローを、作業項目の`conflict_check_id`が非NULLのときだけ、次のように変えて動かす。
`conflict_check_id`は、直す競合の行(`pr_conflict_checks`)のIDである。
作業項目は、競合の回(`conflict_episode`)も持つ。
git操作と検査の部品は[CIの失敗を直す部品の仕様](ci-fix.md#競合回のgit操作と検査)に、安全策の理由は[PRワークフローの安全策の内部仕様の「マージの競合を解く回(PR修正の安全策)」](pr-workflow/security.md#マージの競合を解く回pr修正の安全策)に書く。

### 通常の回との違い

| ステップ | 競合回 |
| --- | --- |
| 準備 | 修正ラウンドの上限を確かめない。競合の行が、いまのheadについて、この作業項目で競合のままであることと、PRのbaseが既定のブランチであることを確かめる。worktreeを用意した後、baseをmergeして、ローカルだけの基準コミットを作る |
| 収集 | GitHubを読まず、固定の結果を返す。処理済みの位置は進めない |
| 修正 | 競合ファイルだけをClaudeに解かせる。`Bash`は渡さない。競合ファイルが無いときは、Claudeを起動せず、日次予算も見ない。コミットメッセージは固定文で、返信は空である |
| 検証 | HEADが基準コミットであることを確かめ、変更と解消を検査する。検査コマンドは1回だけ実行し、失敗してもClaudeを再実行しない。検査コマンドの前後で同じだったツリーのshaを`verified_tree_sha`として返す |
| 完了 | pushの直前に、検証と同じ検査をもう一度行い、ツリーが`verified_tree_sha`と同じであることを確かめ、PRを読み直す。mergeコミットをpushし、通知を出さない |

修正ラウンドの上限を確かめないのは、競合回が`fix_round`を前の値のまま写すためである。
競合回の回数の上限は、`pr_conflict_fix_max_rounds`が決める。

### 準備の結果

準備のステップの結果(`outcome`)は、次のとおり振り分ける。
競合回で直せない場合とbaseがすでにPRにある場合は、後続のステップを実行せず、完了のステップへ進む。

| 事象 | 結果 | 作業項目の遷移 |
| --- | --- | --- |
| mergeできて、検査に通った | `proceed` | 修正中のまま |
| baseがすでにPRの履歴にある | `conflict_up_to_date` | `reviewed`。注記は`conflict round: up_to_date` |
| 競合ファイルが10を超える、通常のファイルでない、バイナリ、衝突ブロックが無い、属性がある | `conflict_blocked` | `needs_human`。注記は`conflict round: unresolvable conflict` |
| 保護パスが競合しているか、両側が変えた | `conflict_blocked` | `needs_human`。注記は`conflict round: a conflicted path is protected` |
| baseが`.github/workflows/`を変えている | `conflict_blocked` | `needs_human`。注記は`conflict round: base changes workflows` |
| PRのbaseが既定のブランチでない | `conflict_blocked` | `needs_human`。注記は`conflict round: base is not the default branch` |
| 競合の行が無い、競合でない、別の作業項目に結ばれた、競合の回が終わった | `guard_blocked` | `blocked`。注記は固定文で、一時の停止 |
| PRのheadが動いた(準備の時点、baseのmerge中) | `guard_blocked` | `blocked`。注記は固定文で、一時の停止 |
| worktreeを別の処理が使っている、ブランチの作業項目で実装のフローが動いているか動く直前、ブランチの作業項目が設計の段階にある | `guard_blocked` | `blocked`。注記は固定文で、一時の停止 |
| worktreeの状態が前提と違う | `guard_blocked` | `blocked`。注記は理由そのまま |

一時の停止は、待てば解ける事情で止めた回である。
回復は、一時の停止の注記を保留の理由に写さず、行に最終の保留を書かない。
次の巡回で判定し直す。
起動し直しを止めるのは、準備の停止なら行の起動の回数の上限、完了の停止なら競合を直した回数の上限(`pr_conflict_fix_max_rounds`)である。
Claudeを動かす前の停止は、競合を直した回数に数えないためである。
一時の停止の注記の一覧は、[PRのCI監視の仕様](pr-ci.md#競合を直す判断)にある。

競合ファイルが無いのに`proceed`になる場合がある。
GitHubが競合と判定したのに、ローカルではきれいにmergeできたときである。
この場合は、Claudeを起動せず、検査コマンドを実行して、そのままpushへ進む。
きれいにmergeできたときも、両側が変えた保護パスは止める。

### 完了の結果

完了のステップの遷移は、次のとおりである。
どれも、再レビューの依頼、返信、`pr_fixed`の通知を出さない。
失敗のDiscordの通知とnoticeも出さない。
ただし、次の2つは運用者の対応が要るので、通常の回と同じnoticeを残す。

- リポジトリのオーナーの数値IDの照合に落ちたとき。
  準備と完了のステップが残す。
- workerのイメージが古いとき。
  準備と検証のステップが残す。

完了のステップがイメージの古さを検出したときは、noticeを残さない。
その場合は、`blocked`で止まった回が回数に数えられず、行の起動の回数の上限に達して`rounds_exhausted`で通知されるまで、通知が無い。
上限に達するまでの時間は、上限の回数に巡回間隔の5分を掛けた程度である。

| 事象 | 作業項目の遷移 |
| --- | --- |
| mergeコミットをpushできた | `rereview_requested`。ラウンドを記録する |
| pushの前の確認に通らない | `needs_human`。注記は止めた理由。workerが検査の前提を満たさないときは、ラウンドを記録せず`blocked` |
| 検査したツリーが、検証のステップが通したツリーと違う、または検証が通したツリーを記録していない | `needs_human`。注記は`conflict round: the tree changed after the verification`。ラウンドを記録する |
| PRのheadが動いた | `blocked`。ラウンドを記録する。注記は`conflict round: the PR head moved before the push`で、一時の停止 |
| worktreeを別の処理が使っている | `needs_human`。ラウンドを記録する。注記は準備のステップと同じ固定文で、一時の停止。保持者はログに残す |
| baseがpushの直前に動いた | `reviewed`。注記は`conflict round: the base branch moved`。ラウンドを記録する |
| GitHubがworkflowの権限不足でpushを拒否した | `needs_human`。注記は`conflict round: base changes workflows`。ラウンドを記録する |
| Claudeや検査が止めた | `needs_human`。検査コマンドの失敗の注記は`conflict round: check failed` |

検証のステップの検査コマンドは、対象リポジトリのコードで、worktreeを書き換えられる。
そのため、検証は検査コマンドの後にもう一度解消を検査する。
検査コマンドの前後のツリーが違えば、注記`conflict round: the tree changed during the checks`で止める。
この注記は一時の停止に数えず、`fix_stopped`で最終の保留になる。
同じなら、そのツリーのshaを完了のステップへ渡す。
完了のステップは、pushの直前の検査で得たツリーが、そのshaと同じであることを確かめる。
検査コマンドが通ったツリーとpushするツリーを結びつけるためである。

baseがpushの直前に動いたときは、`reviewed`にして、注記で`up_to_date`と区別する。
baseは動き続けるので、次の判定で読み直す。
行には最終の保留が付かない。

作業項目のheadは、CI回と同じく更新しない。
その差が、`poll_prs`の自動のレビューを起動するためである。

### 注記の固定文

注記は、固定文の完全一致で、競合の行の保留の理由へ写せる形にしている(`holdReasonForConflictStoppedItem`)。
一時の停止の注記は、保留の理由に写さず、行に最終の保留を書かない。
どちらにも当たらない注記は、保留の理由が`fix_stopped`になる。
注記にshaや保持者のような変わる値を含めると、完全一致が外れて`fix_stopped`になるので、固定文だけにして、変わる値はログに残す。
Claudeの理由の先頭には固定の接頭辞`conflict round: claude blocked:`が付くので、Claudeの出力の文字列が保留の理由を決めることは無い。

止めた理由の注記には、イメージが古い理由(`worker image is stale: run mise run up:`で始まる文)の接頭辞を壊す語句を付けない。
回復は`startsWith`でこの理由を見分け、自動の再開と回数の除外に使う。
検証と完了のステップが検査の前提を満たさないときの注記は、例外の文のまま残す。

### 競合回の再レビューへの入力

競合回がpushしたheadのレビューには、競合回用の固定文を足す。
回の種類の決め方は[再レビューへの入力](#再レビューへの入力)と同じで、CI回の固定文は足さない。
固定文は、次の点を重点的に見るよう頼む。

- mergeコミットであること。
- 衝突を解いた箇所が、PRの変更とbaseの変更が重なる範囲にあり、その外のファイルを編集していないこと。
- 両側の変更の意図が、解消後のコードに残っていること。
- 片側を丸ごと捨てていないこと。
- テストの弱体化と抑制のコメントの追加が無いこと。
- 解消に無関係な振る舞いの追加(外への通信、環境変数の読み取り)が無いこと。

競合回のClaudeは、衝突を消すことを求められる立場なので、片側を捨てたり検査を弱めたりして済ませる誘惑があるためである。

## 返信の形式

返信は運用者自身のアカウントで投稿する。
そのため、フローが固定の構造で組み立てる(`renderFixReply`)。
1行目がロールタグ、続いて本文、末尾が対応の行である。
形式は`.claude/skills/factory-fix/SKILL.md`の「返信形式」に書く。

各コメントへの返信は、次の3つの判断(`decision`)のどれかになる。

| `decision` | 意味 | 返信の末尾 |
| --- | --- | --- |
| `fixed` | このPRの範囲で修正した | `対応: <commit sha7>` |
| `skipped` | 対応しないと判断した。理由は`body`に書く | `対応: 見送り` |
| `propose_issue` | 指摘は妥当だが、このPRの範囲外なのでIssue化を提案する | `対応: Issue化を提案(承認待ち)` |

返信は、実際に集めたコメントの`review_comment_id`を指すものだけを扱う。
Claudeの出力の全体は、監査のために`insertFixRound`がそのまま記録する。

## Issue化の提案

Claudeは`propose_issue`を選んだとき、修正を強行せず、Issueの`title`と`body`を返す。
`pr_fix_finish`は、返信を投稿する前に提案を`factory.issue_proposals`に記録する。

- レビューコメントのスレッドのidは、`listReviewThreads`を使ってベストエフォートで解決する。
- コメントがPRのレビューコメントか、通常のIssueコメントかは、`is_inline`列に記録する。
- `matchReviewThreadForComment`は、コメントの`databaseId`でスレッドを照合し、`(path, line)`には頼らない。

提案が1件でもあるラウンドは、再レビューの依頼済みではなく人の対応待ちで終わり、レビュアーへの依頼もしない。
Discordには「Consoleの要対応で提案を承認または却下してください」と通知する。
commitするものが無いラウンドでも、提案は記録する。

### 承認と却下の反映

人がConsoleの**要対応**で決定すると、`f/factory/approval_decide`が決定を記録し、`f/factory/steps/issue_proposal_apply`を起動する。
承認依頼の種類(`kind`)は`issue_proposal`である。
要件定義の承認と同じく、人が判断してから進む仕組みである。

| 決定 | 処理 |
| --- | --- |
| 承認 | 提案の`title`と`body`でIssueを対象リポジトリに作り、スレッドに「Issue #Nを起票しました。」と返信して解決する |
| 却下 | スレッドに「見送りとします。」と入力した理由を返信し、スレッドは開いたままにする |

承認で作るIssueの本文では、`{{pr_url}}`を元のPRのURLに置き換え、末尾に起票元を示す一文を付ける。
`with_factory_label`が真なら、作ったIssueに`factory_config.trigger_label`(既定値は`factory`)を付け、そのまま要件定義の工程に乗せる。
偽なら起票だけをする。

返信の宛先は、`is_inline`列をもとに決まった方法で選ぶ。

### 状態の切り替え

対象の作業項目の提案がすべて決まると、作業項目の状態を人の対応待ちから切り替える(`decidePostProposalStatus`)。
そのラウンドでcommitをpushしていれば再レビューの依頼済みに、していなければレビュー済みにする。
未決定の提案が残る間は、人の対応待ちのままである。

### 再実行の安全性

同じ決定での再実行は安全である。
途中でジョブが失敗しても、Issueを二重に作ったり、決定を上書きしたりしない。

- 承認者(`decided_by`)は、要件定義の承認と同じくfail-closedで導出する。
- 決定は、状態が`pending`であることを条件にしたUPDATEで1回だけ記録する(楽観ロック)。
- 作ったIssueの本文の最後に`<!-- factory:issue_proposal:<id> -->`の目印を入れる。
  再実行では`findIssueByMarker`でこのIssueを探して再利用する。
- `findIssueByMarker`は、リポジトリのIssueの一覧(REST)を、PATのアカウントが作ったものに絞り、作成の新しい順に読む。
  本文の最後の行が目印だけのIssueを、PRを除いて探す。
  提案の作成の1時間前より古いIssueに当たったら読み終える。
  10ページを読んでも終わらなければ失敗にして、提案を`pending`に戻す。
  1000件は、PATのアカウントが作ったIssueとPRの合計である。
  除いたPRもページを消費する。
  長く保留した提案では、上限に当たりうる。
  当たった提案は、再度承認しても通らないので、却下して起票し直す。
- Issueを作る前に、`claimIssueCreation`が提案の行の印を条件付きのUPDATEで取る。
  取れた呼び出しだけがIssueを作り、取れなかった呼び出しは何もせずに終える。
  同時の呼び出しは、どちらも作成済みのIssueが無いと見て、Issueを2件作りうるためである。
  印は15分で切れる。
  例外で終わった呼び出しの印も、期限まで残す。
  期限を過ぎて走り続けた呼び出しが失敗して戻すとき、印を取り直した別の呼び出しがIssueを作っている最中のことがあり、その処理と重ならないようにするためである。
  Windmillの同時実行の制限(`concurrent_limit`)は設定しない。
  有償版でしか効かず、印だけで直列化する。
- 決定済みの提案に違う決定を送ると、上書きせずにエラーで拒否する。

起票に失敗した提案は**要対応**に残る。
Issueの作成自体が失敗したときは、決定の前の`pending`に戻す。
Issueの作成の後の返信、スレッドの解決、状態の遷移が失敗したときは、「承認済み・起票未完了」として残す。
どちらも、もう一度承認すれば続きから起票する。

## watermark

処理済みの位置(watermark)は、`last_review_id`、`last_comment_id`、`last_review_comment_id`の3つである。
収集のステップは、これより新しいフィードバックだけを集める。

watermarkを進めるのは、そのラウンドのフィードバックを実際に消化したときだけである(`shouldAdvanceWatermarks`)。

| 終わり方 | watermark |
| --- | --- |
| pushに成功した | 進める |
| pushに成功し、Issue化の提案があって人の対応待ちで終わった | 進める |
| 要件の不足を親のIssueに差し戻した | 進める |
| 設計の不足を親のIssueに戻した(設計の起動に失敗したときを含む) | 進める |
| 失敗、人の対応待ち、ブロック | 進めない |
| CI回がpushに成功した | 進めない |
| 差し戻しか戻しに失敗した | 進めない |
| すべての返信が`skipped`でcommitが無く、返信をすべて投稿した | 進める |
| pushが反映されなかった(コミットメッセージが無い、headが動いた、commitするものが無く見送りだけでもない) | 進めない |

Issue化の提案があっても、元のコメントには提案で返信しているので、フィードバックは消化済みである。

結果が分かる前に進めてはならない。
先に進めると、後のステップが例外で失敗したときに、watermarkがそのラウンドのフィードバックを越えてしまう。
すると`retry_work_item`で再実行しても集めるものが無く、「no actionable feedback」の人の対応待ちになる。
進めないことで、再実行が同じフィードバックを集め直せる。

## requirements_gapの差し戻し

修正中に要件の変更が必要になったとき、Claudeは要件や設計を自分で書き換えない。
要件の不足(`requirements_gap`)を返して中断する。

完了のステップは、親の作業項目(`parent_work_item_id`)で元のIssueの作業項目を探し、工程2へ差し戻す。
差し戻すのは、親が承認済み(`approved`)かPR作成済み(`pr_open`)のとき、つまり親のフローが動いていないときだけである。

1. 親の状態を、読み取った時点の`status`と`flow_job_id`のままであることを条件にした比較交換で、要件定義の生成中(`requirements_generating`)にする。
   同じ文で試行(attempt)を1つ増やし、設計の試行(`design_attempt`)を0にし、`flow_job_id`を空にする。
   古い設計書の承認を、作り直した要件定義の実装に使わせないためである。
2. 要件定義のフロー(pipeline)を、不足の報告を自動の報告の印つきの`feedback`にして起動する。
3. `flow_job_id`が空のままのときだけ、起動したジョブIDを記録する。
4. PR修正の作業項目をブロックで終える。

記録できなかったときは、比較交換の後に別の実行が親に書いている。
そのときは、起動したジョブの取り消しを試み、`job_failures`に記録する。
取り消しに失敗しても、起動したpipelineはリースを持たないので、作業項目を書き換えずに終わる。
pipelineのリースは[作業項目](work-items.md)に書く。

次の場合は差し戻さず、PR修正の作業項目を人の対応待ちにする。
PRへのリンクと次の操作をDiscordで知らせ、要件の不足の報告は通知の理由に載せる。

- 元のIssueの作業項目が見つからない。
  例えば、Factory製でないPRを手動で投入した場合である。
- 親にIssue番号が無い。
- 親が承認済みとPR作成済み以外の状態である(実装中、要件定義の生成中、承認待ちなど)。
- 親の試行回数が`max_attempts`に達している。
- 読み取った後に親の`status`か`flow_job_id`が変わり、比較交換に失敗した。

親が実装中になるのは、準備のステップが確かめた後に実装フローが動き出した場合である。
差し戻さないのは、動いているフローや人の判断を上書きしないためである。

## 設計の不足の差し戻し

レビュー回のClaudeが設計の不足(`design_gap`)を返したとき、完了のステップは、親の作業項目をPR作成済みから設計中(`designing`)へ戻し、設計フローを起動する。
設計書が渡る実行だけが返せるので([設計書の受け渡し](#設計書の受け渡し))、設計工程が有効な間だけ起きる。
設計工程が無効の間は起きない。

完了のステップの`main`は、次の順に進む。

1. 修正のラウンドを`design_gap`として記録する。
   親を読む前に書く。
   人の対応待ちで止めるときも書く。
2. 親を読む。
   無ければ、PR修正を人の対応待ちにする。
3. 戻す上限を判定する(`decideDesignGapAction`)。
   設計工程が無効か上限に達していれば、親に触れず設計も起動せず、PR修正を人の対応待ちにする。
4. 親が戻せる状態かを確かめる(`reroutePrFixToDesign`)。
5. 比較交換で、親をPR作成済みから設計中へ移す。
6. 直後に設計フローを起動する。
7. 処理済みの位置を進め、PR修正をブロックにする。

手順4で確かめるのは、次の4つである。

- 親にIssue番号がある。
- 親がPR作成済みである。
  設計の段階と実装中は、専用の理由で断る。
  動いているフローや人の判断を上書きしないためである。
- 同じIssueに、より新しいサイクルの作業項目が無い。
  新しいサイクルに置き換わった親を生き返らせないためである。
- このPR修正が始まった後に、親の状態を変えた遷移の記録が無い。
  修正が読んだ設計と、親の今の状態が食い違わないためである。
  基準の時点は、この修正が修正中(`fixing`)へ入った最新の遷移の時刻で、無ければ修正の作成時刻である。
  修正の行は修正中で挿入され、遷移の記録を持たないためである。

手順5の比較交換(`returnToDesigningFromPrFixIfLeaseHolder`)は、親がPR作成済みで、`flow_job_id`が読んだ時点のままのときだけ書く。
同じ文で、設計の試行(`design_attempt`)を1つ増やし、`flow_job_id`を空にし、遷移の記録を書く。
設計の試行を増やすので、前の設計の承認は、どの照合も通らなくなる。
遷移の注記は、固定の接頭辞(`PR_FIX_DESIGN_GAP_NOTE_PREFIX`)と、整えた報告である。

手順6の`feedback`は、報告を自動の報告の印つきで渡す。
設計フローが、報告を人の却下の理由として扱わないためである。
起動は取り消せず外から見える操作なので、比較交換の直後に行う。
起動か記録に失敗したら、起動の手順が親を設計中から人の対応待ちへ戻し、Issueへ通知する。

手順7は、比較交換が通った時点を「戻しに成功した」として、起動の結果に関わらず行う。
戻しに成功したときの、PR修正の作業項目の注記は固定文で、報告は親の遷移の注記から設計に届く。
止めたときは、整えた報告を、固定の理由の後ろに別の区間としてつなぐ。
整えるとは、秘密値のマスク、制御文字の除去、長さの制限、区切りのエスケープである。
手順6か7の書き込みが失敗したときは、設計が起動済みか、親が人の対応待ちのままである。
PR修正は`on_error_flow`が失敗(`failed`)にし、処理済みの位置は進まない。
再実行は、設計の段階の間は準備の確認が止める。
設計の承認の後の実装は、PRのレビューも処理済みの位置も読まないので、元の指摘を集めない。
処理済みの位置が進んでいると、次のPR修正の行は位置を引き継ぐので、元の指摘は二度と集まらない。
指摘は、絞った要約として設計に届くだけで、PRには返信しない。
位置が進んでいないときに限り、人がPR修正を再実行するかラベルを付け直すと、元の指摘が集め直される。

### 一意制約が割り込みを捕まえる前提

手順4の確認と手順5の比較交換は、1つの文ではない。
その間に、同じIssueの新しいサイクルが稼働中の状態で挿入されることがある。
設計中は稼働中の状態なので、部分一意インデックス(`work_items_active_issue_key`)が、親の更新を拒む。
比較交換は、この違反だけを捕まえて「競合に負けた」として扱い、何も書かずに断る。
違反以外の失敗は投げる。
この経路は、新しいサイクルの割り込みを一意制約が捕まえることに頼る。
この制約を外す変更は、割り込みを素通りさせる。

### 戻さずに止めるとき

次のときは、親を戻さず、PR修正を人の対応待ちにする。
PRへのリンクと次の操作をDiscordで知らせ、報告は通知の理由に載せる。
修正のラウンドは記録済みである。

- 元のIssueの作業項目が見つからない。
- 親にIssue番号が無い。
- 親がPR作成済みでない。
- 同じIssueに、より新しいサイクルの作業項目がある。
- このPR修正の開始後に、親が動いた。
- 比較交換に負けた。
  親の状態か`flow_job_id`が変わったとき、一意制約の違反も含む。
- 設計工程が無効である。
- 設計の却下と戻しの数が上限(`max_design_attempts`)に達した。

数える対象は、人の却下、実装からの戻し、PR修正からの戻しの合計である([設計書の生成](design.md)の「却下の数え方」)。

上限と設計工程の無効で止めたときは、親がPR作成済みのまま残る。
親は再実行の対象でないので、再実行しても設計を作り直せない。
次の操作は、Issueにトリガーのラベルを付け直して新しいサイクルを始めるか、PRを人が直すことである。

上限と設計工程の無効の判定は、親の状態の確認より前にある。
親が別の経路ですでに設計の段階にあり、数が上限に達しているときの理由の食い違いは、[R-DES-09](../security-risks.md#r-des-09)にあたる。

### 設計の最中のPR

PRのブランチの作業項目が設計の段階にある間は、設計の承認の後の実装がそのPRを引き継ぐ。
この間に別の回がブランチへpushすると、実装の引き継ぎと食い違うので、回ごとに止める。

| 回 | 止め方 |
| --- | --- |
| 親の行を持つPR修正 | 準備の親の状態の確認が`guard_blocked`で止める |
| 親の行を持たないPR修正 | 準備のブランチの確認が`guard_blocked`で止める。対象は、競合回と、本文から閉じるIssueが消えたレビュー回である |
| CI回と競合回の起動 | 起動の判断が、作業項目の状態を見て起動しない([ブランチを引き継ぐ間](pr-ci.md#ブランチを引き継ぐ間)) |
| 自動のレビュー | 準備が終端にする。検出が始めたレビューは通知せず、ラベルで頼んだレビューは通知する([ラベルの付与者の確認](#ラベルの付与者の確認)) |

競合回は、作業項目の状態に頼らずPRを列挙し、行を親の行を持たずに挿入する。
レビュー回は、`poll_prs`がPR本文の`Closes #N`から親を結ぶ。
人が本文から閉じるIssueを消すと、`parent_work_item_id`が`null`になる。
レビュー回には設計書が渡らないので、設計の不足は返らない。

#### ブランチのガード

準備のステップのブランチのガード(`evaluateBranchImplementingGuard`)は、PRのブランチ名から引いた作業項目が次の4状態にあるとき、`guard_blocked`で止める。
要件定義の段階の2状態では止めない。
既存のレビュー回の挙動を変えないためである。
ガードは、止めた種別と、種別ごとの固定の理由を返す。

| 種別 | 状態 | 理由 |
| --- | --- | --- |
| 実装 | 実装中(`implementing`)、承認済み(`approved`) | `implementation of the branch's work item is running or about to run` |
| 設計の段階 | 設計の生成中(`designing`)、設計の承認待ち(`awaiting_design_approval`) | `the branch's work item is in the design stage` |

承認済みの状態を含めるのは、実装が動き出す直前だからである。
本番では、親が承認済みのレビュー回の`pr_fix`が、このガードで`blocked`になる。
競合回の注記は種別で選ぶ。
どちらも、数えない一時の停止である([注記の固定文](#注記の固定文))。
ブランチ名から引けないとき(形が違う、削除済み、別のリポジトリ)は止めない。

#### 動いている回との行き違い

設計の承認は、起動の判断が状態を読んだ後から準備が動くまでの間に、入ることがある。
この窓で起動した回が終わらないうちに実装の準備が動くと、準備はPRに終端でない回があることを見つけて、人の対応待ちで止まる。
理由は`pull request has an active fix run`である。
この理由で止まった実装は、PRの回が終わった後に自動で再開する([実装フロー](implement.md#回が終わるのを待って止まったとき))。

設計工程が無効の間は、設計の段階の作業項目は存在しない。

## 設定値

PRワークフローは`f/factory/factory_config`の次の値を読む。

| キー | 既定値 | 意味 |
| --- | --- | --- |
| `review_label` | `factory:review` | PRレビューを起動するラベル |
| `fix_label` | `factory:fix` | PR修正を起動するラベル |
| `allowed_labeler_logins` | `[]` | ラベルを付けてよいアカウント。FactoryのPATのアカウントに加えて許可する |
| `allowed_labeler_ids` | `{}` | `allowed_labeler_logins`のアカウントの数値ID。名前をキーにする。入れたアカウントは、IDも一致するときだけ許可する |
| `allowed_labeler_associations` | `["OWNER", "MEMBER", "COLLABORATOR"]` | 修正の材料にする投稿者の関係 |
| `repo_allowlist` | `[]` | 対象のリポジトリ。空なら`owners`のすべて |
| `tracked_pr_days` | `30` | ラベルが外れた後もPRを追跡する日数 |
| `review_post_mode` | `comment_only` | `gated`ならレビューを投稿しない |
| `diff_max_lines` | `3000` | レビューに渡す差分の行数の上限 |
| `claude_timeout_sec` | `1800` | Claude 1回の実行と、PR修正の検査コマンド1件を打ち切る秒数 |
| `max_fix_rounds` | `3` | PR修正のラウンドの上限。上げると、失敗の下限により3ラウンド目以降は`heavy_model`で動く |
| `allowed_check_commands` | `[]` | PR修正の検査コマンド |
| `max_fix_changed_files` | `30` | PR修正で変えてよいファイル数の上限 |
| `max_fix_diff_lines` | `1500` | PR修正の追加と削除の行数の上限 |
| `default_reviewers` | `[]` | 再レビューを依頼する人 |
| `daily_budget_usd` | `50` | 全フローで共有する1日の費用の上限(USD) |
| `max_attempts` | `3` | 要件定義の試行回数の上限 |
| `design_enabled` | `false` | 設計工程を有効にするか。偽なら、設計書を渡さず、設計の不足の差し戻しもしない([設計書の生成](design.md)) |
| `max_design_attempts` | `3` | 人の却下、実装からの戻し、PR修正からの戻しを合わせた上限 |
| `model` | `claude-sonnet-5-5` | PR修正のモデル。同じPRの修正が続けて2回失敗した後は`heavy_model`を使う |
| `heavy_model` | `claude-opus-5-5` | PRレビューのモデルと、続けて2回失敗した後のPR修正のモデル |

モデルの昇格に使う失敗の数は、同じPRの`pr_fix`の作業項目から数え、次の2つの大きいほうにする。
CIの失敗を直す作業項目(`ci_check_id`を持つもの)と、競合を直す作業項目(`conflict_check_id`を持つもの)は、どちらにも数えない。

- 直近に連続した失敗。
  `blocked`でないラウンド(`done`か`requirements_gap`)で最後に終えた時刻より後の、次の3つの合計である。
  - Claudeが動いて`blocked`で終えた`fix_rounds`の行
  - 検査の再実行(`pr_fix_verify_retry`)をした作業項目
  - `agent_runs.error`がある失敗した実行の行
  - どれも、使用上限か全停止で終わった実行(`agent_runs.failure_reason`が`usage_limit`か`stopped`)を数えない。
    `blocked`の行はその行の実行(間に再実行の無い直前の実行)の種類で、検査の再実行は最後の試行の種類で判定する
- 作業項目の`fix_round`から1を引いた値。
  毎回`done`で終えても再レビューが続くと、失敗の記録が残らないためである。

除く条件と数の理由は、[機能ごとの運用の「モデルを使い分ける」](../operations/features.md#モデルを使い分ける)にある。

PR修正のラウンドが`max_fix_rounds`を超えると、準備のステップが止め、作業項目は人の対応待ちになる。
ラウンドの番号(`fix_round`)は、`poll_prs`が作業項目を作るときに入れる。
PR修正の各ラウンドは別の作業項目になり、完了のステップは番号を増やさない。

## 検査コマンドの実行

対象リポジトリの検査(lint、typecheck、testに当たるもの)は、Claudeではなく検証のステップが実行する。
実行するのは`factory_config.allowed_check_commands`に書いたコマンドで、例えば`["mise run check"]`である。
結果は、Claudeの2回目の実行(修正)への入力にする。

検査コマンドは、対象リポジトリのコードをworkerのコンテナ内で、非特権のユーザー(`factory-check-N`)として実行する。
コンテナとnetworkは分けない。
別のコンテナでnetworkなしに動かせるまで、既定値の`[]`を保つ。
空でなければ、実行する作業項目ごとにnoticeの`unsandboxed_check_commands`を記録する。
同じ本文の未解決のnoticeがあれば新しく作らない。
作成から1日を過ぎていれば、時刻を更新する。

検査コマンドには、許可リストの環境変数だけを渡し、workerの環境変数は引き継がない。
許可するのは、固定の`PATH`、実行ごとに作る非公開の`HOME`とその下の`TMPDIR`、`LANG`、worktreeだけを`safe.directory`にするgitの設定である。
gitの設定は環境変数と`HOME`の`.gitconfig`の両方に書く。
実行の前に、空いている枠を取って前の実行の残りを片付け、枠の記録を書いてから、worktreeと`HOME`の所有者をその枠のユーザーにする。
実行の後は、所有者をrootに戻してから`HOME`のディレクトリを消し、共有の一時ディレクトリから枠のユーザーのものを消して、枠の記録を消す。
コマンドごとに、枠のユーザーの残りのプロセスを止める。
止まらなければ、所有権を戻さずにステップを失敗させる。
戻せなかった所有権と`HOME`は、枠の記録を通して、次にその枠を取る検査が片付ける。

準備のステップは、`allowed_check_commands`を設定していれば、Claudeより前に、イメージと実行時の前提([検査コマンドの権限](check-sandbox.md#検査コマンドの権限))を確かめる。
満たさなければ、関門と同じ`guard_blocked`で止め、作業項目は`blocked`になる。
前提を満たさないまま進むと、Claudeの修正を1回使ってから検証で止まるためである。
検証のステップも検査の前に確かめ直し、満たさなければClaudeの修正を再実行せずに`guard_blocked`を返す。
準備から検証までの間に、イメージも稼働中のworkerも変わりうるためである。
完了のステップが、commitの前に残った所有権を同じ理由で取り戻せずに止まったときも、`blocked`にする。
どれも修正のラウンド(`fix_rounds`)を記録しない。
Claudeが直せる検査の失敗ではないので、Sonnetの失敗として数え(`countPrFixFailures`)、`heavy_model`への切り替えを早めないためである。
理由と要対応の通知は、原因によって次のとおりである。

| 原因 | 理由の先頭 | 要対応の通知 |
| --- | --- | --- |
| イメージが古い | `worker image is stale: run mise run up` | `host_action_required`([更新の反映の運用](../operations/deploy.md#fとworkerのイメージを両方変えたとき)) |
| 稼働中のworkerの問題 | `worker runtime is unsafe for checks:` | `check_runtime_unsafe`([更新の反映の運用](../operations/deploy.md#稼働中のworkerが検査の前提を満たさないとき)) |

イメージが古く、稼働中のworkerの問題も一緒に見つかったときは、両方の通知を残す([Consoleのnotice](notifications.md#consoleのnotice))。
`host_action_required`は`mise run up`の後に自動で解決されるが、ボリュームのマウントポイントは作り直しでは閉じないためである。
イメージが古くて止まった`blocked`は、通知の自動の解決の後に、自動で`fixing`へ戻って再開する([実装フロー](implement.md#イメージが古くて止まったとき))。
CIの失敗を直す回は除く([CIの失敗を直す回](#ciの失敗を直す回))。

`PATH`の値と、workerの値を使わない理由、uidの切り替えと所有権の受け渡しは、[検査コマンドはフローが実行する](check-sandbox.md#検査コマンドはフローが実行する)と[検査コマンドの権限](check-sandbox.md#検査コマンドの権限)にある。

検査コマンドが指す先(対象リポジトリの`mise.toml`や`package.json`のscriptsなど)は、信頼できない内容として扱う。
workerのmiseは対象リポジトリの`mise.toml`をtrustしない(`mise --yes trust`をしない)。
`mise.toml`に頼るコマンドと、`MISE_TRUSTED_CONFIG_PATHS`を使わずには実行できないコマンドは、実行せずにブロックとして報告する。

検査コマンドは1件ずつ`claude_timeout_sec`で打ち切る。
出力の扱いは[実装フロー](implement.md)の[検査コマンドの出力の上限](implement.md#検査コマンドの出力の上限)と同じである。

### 検査コマンドの実行ファイルを起動できないとき

検査コマンドの実行ファイルを起動できなかったときも、環境の問題なので、Claudeの修正を再実行せずに`guard_blocked`を返し、作業項目は`blocked`になる。
修正のラウンドは記録しない。
競合を直す回も同じである。
判定は[実装フロー](implement.md#ループの終わり方)と共有する。
環境の問題として扱うのは、次の3つがそろうときだけである。

- 終了コードが127か126である。
- 出力の先頭が`setpriv: failed to execute`である。
- コマンドの先頭の語が、相対パスで`/`を含むものではない。

理由は`check command could not run: <コマンド>: <setprivの出力>`になる。

この理由で止まった`blocked`は、自動では再開しない。
PR修正の自動の再開はイメージが古い理由だけである。
実行ファイルをイメージに足すか検査コマンドを直した後に、人が再実行する。

CIの失敗を直す回では、監視がこの理由を保留`fix_stopped`に写す。
同じheadで起動し直しても、同じ理由で止まるためである。
競合を直す回の理由は固定文ではないが、固定文に写せない`blocked`は`fix_stopped`で保留するので、同じ結果になる。
固定文に寄せていないので、競合を直す回の保留の理由は、検査が実行できなかったことを区別しない。

## 準備での確認

PR修正の準備のステップは、worktreeを作る前に次を確かめる(`evaluatePrFixSafetyGuards`など)。

| 確かめること | 通らないとき |
| --- | --- |
| リポジトリが許可リストに含まれる | ブロック |
| リポジトリのオーナーが`owners`にある(`factory_repo`を除く)。`id`があれば、現在のIDと一致する | ブロック |
| `fix_round`が`max_fix_rounds`以下である | 人の対応待ち |
| 時間設定がステップのtimeoutに収まる | ブロック |
| 親のIssueの作業項目が実装中でも設計の段階でもない | ブロック |
| PRのブランチ名から引いた作業項目が、設計の段階でも、実装中でも、承認直後でもない | ブロック |
| PRがopenである | ブロック |
| `head.repo`が`base.repo`と同じである(forkのPRにはpushしない) | ブロック |
| PRがdraftでない | ブロック |
| PRのauto-mergeが有効でない | ブロック |
| headのブランチの状態を読める | 失敗(`failed`)。`job_failed`で通知する |
| headのブランチがデフォルトブランチでない | ブロック |
| headのブランチが保護ブランチでない | ブロック |
| headのブランチにrulesetのruleが適用されていない | ブロック |

PR修正がpushするのはheadのブランチなので、headの保護を確かめる。
baseが保護されていても、headが普通のブランチなら止めない。
保護の有無は、branches APIの`protected`で読む。
`main`を保護するruleset(対象は既定のブランチ)は、`protected: true`として返ることを確かめた。
globで対象を指定するrulesetなどが`protected`に反映されるかは確かめていない。
そのため、headのブランチに効くrulesetの規則も、`GET repos/{owner}/{repo}/rules/branches/{branch}`で読む。
1件でもあれば、理由`head branch has rules`でブロックにする。
ruleの種類は問わずに止める。
止めすぎは安全側で、`protected`に反映されないrulesetを見落とさないためである。
auto-mergeが有効なPRを止めるのは、Factoryの修正pushがレビューを経ずにマージされうるからである。
headの状態は、GitHubのAPIで読む。
読めなかったときは例外になり、flowの失敗ハンドラが作業項目を失敗(`failed`)にして、`job_failed`で通知する。
ブロックにはならない。
デフォルトブランチは保護されていることが多いので、デフォルトブランチを先に判定し、理由を区別する。

親のIssueの作業項目とブランチの作業項目を確かめるのは、設計、実装、PR修正がPRのブランチのworktreeを共有するからである。
ブランチ名から引くのは、ブランチ名が`factory/issue-<N>-wi-<id>`の形のときで、親の行が無いPRでも止まる。
理由を分けているので、どちらで止まったかを見分けられる。

親が設計の段階(`designing`、`awaiting_design_approval`)にある間は、親の状態の確認が`guard_blocked`で止める。
設計の最中に別のPR修正が同じブランチへpushすると、設計の承認の後に実装が引き継ぐPRと食い違うためである。
設計への戻しの書き込みが失敗した後の再実行も、この確認で止まるので、同じ指摘を設計なしで直してpushすることは無い。
ブランチから引いた作業項目の確認は、設計の段階、実装中、承認直後の4状態で止める。
親の行を持たない修正(競合回と、本文から閉じるIssueが消えたレビュー回)も、この確認で止まる([設計の最中のPR](#設計の最中のpr))。

worktreeを使っているプロセスがいるときもブロックにする([再実行と中断](pr-workflow/retries.md#再実行と中断))。
