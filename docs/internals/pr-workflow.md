# PRワークフロー

PRのレビュー(`f/factory/pr_review`)とPRの修正(`f/factory/pr_fix`)のフローの内部の挙動、設定値、安全策の仕組みをまとめる。これらのフローのコードを変更する人が読む。運用の手順は[運用](../operations.md)に、作業項目の状態の一覧は[作業項目](work-items.md)に書く。

## 全体の流れ

PRワークフローは、Issueから要件定義を作る工程1と2とは別に、既存のPRをレビューし、修正する。対象は人が作ったPRと、実装フローが作ったPRである。

PRレビューは3つのステップでできている。

| ステップ | 役割 |
| --- | --- |
| `pr_review_prepare` | PRを取得して確かめ、レビュー用のworktreeを用意する |
| `pr_review_generate` | Claudeにレビューを書かせる |
| `pr_review_post` | レビューを投稿して記録し、worktreeを消す |

PR修正は5つのステップでできている。

| ステップ | 役割 |
| --- | --- |
| `pr_fix_prepare` | 安全のための確認をして、PRのブランチのworktreeを用意する |
| `pr_fix_collect` | 修正の対象にするフィードバックを集める |
| `pr_fix_apply` | Claudeに修正させる |
| `pr_fix_verify` | 変更を確かめ、検査コマンドを実行する |
| `pr_fix_finish` | commitしてpushし、返信して再レビューを依頼する |

PRに投稿するのは、PRレビューの指摘と総評、PR修正の返信だけである。失敗、人の対応待ち、ブロック、要件の不足といった運用上の知らせは、PRに書かずDiscordで知らせる。Issue化の提案の承認と却下の結果は、PRのスレッドに返信する。

実装フローが作ったPRのCIの失敗も、PRには書かずDiscordとnoticeで知らせる。この監視はレビューと修正のフローとは独立している。設定`pr_ci_fix_enabled`が`true`のときは、失敗したPRを直す修正(CI回)を起動し、自動で直す対象の失敗は、直せるかが決まってから知らせる。内容は[PRのCI監視の仕様](pr-ci.md)に書く。

## 起動条件

`poll_prs`がPRを見つけて作業項目を作り、フローを起動する。

| フロー | 起動条件 |
| --- | --- |
| PRレビュー | PRに`factory:review`ラベルが付いた |
| PRレビュー | PRのレビューの依頼先かassigneeがこのインスタンスのGitHubアカウントで、未処理のhead(`head_sha`)がある |
| PR修正 | PRに`factory:fix`ラベルが付いた |
| PR修正のCI回 | `watch_pr_ci`が、失敗したheadの行を直すと判断した。条件は[PRのCI監視の仕様](pr-ci.md)の「起動」に書く |

トリガーのラベルは、着手(claim)したときに消費して外す。レビューの依頼とassigneeの経路には、消費するラベルが無い。ラベル名は`factory_config`の`review_label`と`fix_label`で決める。

ブランチ名が`factory/drawio-viewer-`で始まるPR(draw.ioのビューアの固定を上げるPR)には、`factory:fix`ラベルが付いていてもPR修正を始めない。
`decidePrActions`が`headRef`で判定し、ラベルは消費せずに残す。ラベルは外れず、修正は人が行う。
判定はブランチ名だけで行うので、`factory_repo`に限らず、担当するすべてのリポジトリに効く。
`pr_fix_prepare`も同じ判定(`evaluateHumanOnlyBranchGuard`)で止め、作業項目をblockedにする。
修正を許すと、固定のファイル以外も書き換えたcommitを、人が気づかずにマージするおそれがある。このPRは人が直す。レビューは動く。

PR修正の通常の回は、ラベルからしか起動しない。コメントやcommitのpushだけでは起動しない。CI回だけは、`watch_pr_ci`が起動する。次のラウンドを始めるには、PRに`factory:fix`ラベルを付け直す。PRレビューが終わった(`reviewed`)PRにも付けられる。

同じPRに終了していないPR修正があるとき、許可された人が付けた`factory:fix`ラベルは、PR修正を始めない。
`decidePrActions`が、候補の`activeFixItemId`で判定し、ラベルは消費せずに残す。
保留の理由は、PRと進行中の作業項目のidを`poll_prs`のinfoログに残す。noticeは出さない。
修正中に付けたラベルは保留され、その修正が終わった後に1回だけ新しいラウンドが始まる。
同じPRのPR修正が並んで動くと、同じブランチへ別々にpushして競合する。
部分一意インデックス`work_items_active_pr_fix_key`が、終了していないPR修正を、PRごとの1件までに制限する。

判定は、ポーリングの先頭で読んだ作業項目の状態に基づく。
読んだ後に別のPR修正が始まると、ラベルの消費の後にある挿入が、このインデックスに阻まれる。
このとき、消費したラベルを付け直し、失敗ではなく見送りとして数える。
人の依頼は失われず、その修正が終わった後のポーリングが拾う。
ラベルの付け直しも失敗したときは、ラベルが外れたままになる。
取得の確認に失敗したときの付け直しと同じく、失敗に記録して人へ知らせる。

修正への指示は、ラベルを付ける前に、PRへ通常のコメントとして書く。`pr_fix_collect`が、ほかの人のコメントと同じくフィードバックとして集める。

### 投稿者の関係の確認

レビューとコメントの投稿者の`author_association`が`allowed_labeler_associations`に含まれないとき、その投稿は起動の対象から外す。既定値は`OWNER`、`MEMBER`、`COLLABORATOR`である。

### ラベルの付与者の確認

`poll_prs`は、`factory:review`と`factory:fix`のそれぞれについて、そのラベルを最後に付けた人を、ラベルの`labeled`イベントの`actor`で確かめる。
許可されるのは、FactoryのPATのアカウントと、`allowed_labeler_logins`に挙げたアカウントである。
`allowed_labeler_ids`にIDを入れたアカウントは、`actor`の数値IDも一致するときだけ許可する。
許可されない人が付けたラベルと、付与者を特定できないラベルは、外さずに残し、起動しない。
取得の直前にも、同じ確認をもう一度行う。
イベントを取得できなかったPRは、そのポーリングでは対象にしない。
付与者を判定できないPR(直近100件のラベルのイベントにトリガーラベルのイベントが無い)は、`labeler_check_limit`のnoticeを残し、ラベルを外して付け直すまで対象にしない。
仕組みの全体は[ラベル付与の制限](../security.md#ラベル付与の制限)にある。

レビュー依頼かassigneeによる起動と、追跡中のPRの新しいcommitによる再レビューは、ラベルを介さない。
この2つは、PRの作成者が許可されたアカウントのときに限る。
トリガーラベルが拒否された状態で付いているPRでも、始めない。
同じリポジトリのブランチから出した第三者のPRは、許可されたアカウントがラベルを付けたときだけレビューされ、新しいcommitのたびにラベルの付け直しが要る。

PRのheadが対象のリポジトリにないとき(forkのPRと、headのリポジトリを取得できないPR)は、ラベルの経路もラベルを介さない経路も、レビューを始めない。
`decidePrActions`が、始めるはずだったレビューを見送りとして返し、`poll_prs`が`fork_head_denied`のnoticeを残す。
ラベルは外さない。
`pr_review_prepare`も、作業項目を手で作るなどの経路に備えて、clone、fetch、worktreeの前に同じ確認をする。
通らなければ、作業項目を終端の`blocked`にして理由を残し、Discordで人に知らせてから、処理を飛ばす。
同じ判定は、PR修正の準備のステップの「forkからでない」確認と共有する。

`pr_review_prepare`は、forkの確認より先に、リポジトリのオーナーを`owners`と照合する。
通らなければ、PRを読む前に、処理を飛ばす。
そのとき、作業項目を終端の`blocked`にして理由を残し、Discordで人に知らせる。
forkのPRを見送るときと同じ終わり方である。
照合は[運用](../operations.md)の「オーナーの数値IDを固定する」に書く。

### 対象のリポジトリ

対象は、`factory_config`の`repo_allowlist`に含まれるリポジトリだけである。`repo_allowlist`が空なら、`owners`に含まれるリポジトリのすべてが対象になる。`factory_repo`は`repo_allowlist`に関わらず常に対象である。

`poll_prs`は作業項目を作る前に許可リストで候補を絞る。作業項目を作った後で`factory_config`を変えることもあるので、両方のフローの準備のステップも許可リストを確かめ直す。

### ラベルを外した後の追跡

Factoryが扱ったPRには、トリガーのラベルのほかにラベルを付けない。状態は作業項目の状態(`work_items.status`)だけで表し、Consoleの**作業項目**に表示する。

ラベルが外れた後も追跡を続けるため、`poll_prs`はDBからPRを見つけ直す。`f/factory/lib/db.ts`の`listTrackedPrs`が、次の条件をすべて満たす作業項目を返す。

- 種類(`kind`)が`pr_review`か`pr_fix`である。
- 状態が取り消し(`cancelled`)でない。
- `tracked_pr_days`以内に更新された。

`poll_prs`は、そのPRが`owners`(`id`の照合を通ったオーナー)と`repo_allowlist`に合い、まだopenであることを`getPr`で確かめてから候補にする。人が新しいcommitをpushすると、この経路でPRレビューが自動で起動する。1回のpushにつき、Claudeの実行は1回である。

`review_post_mode`が`gated`のときは、レビューを投稿しない。`gated`は検証用に予約した値で、承認を経て投稿する画面はまだ無い。このモードでは、PRはレビューの依頼かassigneeの経路でだけ見つけ直す。PRレビュー完了の通知は送らない([通知](notifications.md#通知を送らない場合))。投稿しない状態が続くことは、日次のまとめと要対応のnoticeで知らせる([継続の通知](notifications.md#レビューを投稿しない状態の継続))。

## 自己再発火の防止

Factoryが投稿するIssueのコメント、PRのレビュー、レビューへの返信には、必ず目印(`<!-- factory:<kind>:<work_item_id> -->`)を入れる。目印は本文の最後の行に置き、判定では最後の行の目印だけを読む。

Factory自身の投稿かどうかは、`f/factory/lib/github.ts`の`isFactoryPost`で次の両方を満たすかで判定する。

- 投稿者のログインが、viewer(PATの持ち主のGitHubアカウント)と一致する。大文字と小文字は区別しない。
- 本文が、最後の行にFactoryの目印を持つ。

Factoryは人と同じGitHubアカウント(共有のPAT)で動く。そのため、ログインの一致だけでは人の投稿と区別できない。目印は誰でも本文に貼れるので、目印だけでも区別できない。

フィードバックとして扱わないのは、Factory自身のPR修正の返信(`pr_fix`の目印を持つもの)だけである。人が同じアカウントで書いたコメントは、目印が無いのでフィードバックになる。Factory自身のPRレビューと、その未解決のインラインの指摘もフィードバックになる。

## 作業ディレクトリ

対象リポジトリのメインのクローン(`/workspaces/<owner>/<repo>/main`)はfetchだけに使い、working treeをcheckoutしない。

PRレビューは、PRごとにdetachedのworktreeを作り、投稿のステップで消す。

```bash
git worktree add --detach /workspaces/<owner>/<repo>/review-<pr>-<sha7> <sha>
```

`<sha7>`はレビューするコミットのshaの先頭7文字である。準備のステップは、worktreeを作る間にheadのshaが動いていないかを最後にもう一度確かめる。生成のステップが早く抜けて投稿しなかったときも、投稿のステップがworktreeを消す。worktreeが残ると、同じshaを再実行したときに`git worktree add`が既存のパスで失敗するためである。

PR修正は、`git gtr new`で作るPRのブランチのworktreeを使う。PR修正の完了のステップはworktreeを消さず、後で`cleanup_workspaces`が片付ける。

## レビュー

生成のステップ(`pr_review_generate`)は、`factory-review`スキルと読み取り専用のツールで、headless Claudeを実行する。作業ディレクトリはレビュー用のworktreeである。

レビューの観点は、`factory-review`スキルの「レビューの観点」にある。
依存の宣言か取得を変えるPRには、サプライチェーン攻撃の観点も当てる([依存の変更のレビュー](../security.md#依存の変更のレビュー))。

Claudeへの入力は次のとおりである。

- PRの本文
- PRの差分(`diff_max_lines`行で切り詰める)
- 変更されたファイルの一覧
- 承認済みの要件定義(PRが要件定義に紐づくとき)
- このPRへのFactory自身の未解決の指摘の一覧(再レビューのとき)

PRが要件定義に紐づくのは、Factoryの実装フローが作ったPRか、本文に`Closes #123`と書いたPRである。`Fixes`と`Resolves`も使える。`poll_prs`はそのIssueの承認済みの要件定義を探し、PRレビューとPR修正のClaudeに渡す。

日次予算を超えているか、時間設定がステップのtimeoutに収まらないときは、Claudeを起動せずに人の対応待ちにする。

再レビューでは、実質的に同じ内容の指摘を新しい指摘として投稿しない。新しい指摘と、変化があった指摘だけを報告する。差分で解消済みと判断できる指摘は何も報告しない。スレッドの解決は別の処理が行う。

レビューは常にGitHubのCOMMENTレビューとして投稿する。承認(approve)と変更の要求(request changes)は使わない。スキルが返す判定(`verdict`)は`factory.reviews`に残すだけで、投稿の種類にも、通知とConsoleの状態にも使わない。
通知とConsoleのレビュー行は、flowが決めた結果(`factory.reviews`の`result`)を使う。結果は、修正必須の指摘の有無で決まる(通知の規則は[通知](notifications.md)にある)。

### 差分の取得

PRの差分は、`application/vnd.github.v3.diff`で取るJSONでない本文である。
PRの作者がESCなどの制御文字を含むファイルを足すと、`gh`は本文を出さず、ステータスが200のまま終了コード1で終わる。
本文が空に見えると、差分が空のままレビューが進み、作者が差分を隠せてしまう。
この挙動は、gh 2.101.0で確認した。

`getPrDiff`は次のように扱う。

- `--allow-escape-sequences`を付けて、本文を受け取る。
- 制御文字と見えない文字を、1文字ずつ`<U+001B>`の形の見える表記に置き換える。
- 置き換えの後に、改行の`\r\n`を`\n`にそろえる。
  改行の種類で、行数、切り詰め、レビューの結果が変わらないようにするためである。
  直後が改行でない復帰は、置き換えで見える表記になっている。
- そろえた後に、行数の上限(`diff_max_lines`)、文字数の上限(40万字)の順で切り詰める。
  どちらで切っても、切り詰めたことを注記する。
- ステータスが2xxなのに`gh`の終了コードが0以外のときは、1回だけ取り直す。
  取り直しても欠けたときは、`GitHubRawBodyIncompleteError`を投げ、Claudeを起動しない。
- 例外は固定の文だけを持ち、本文とstderrを載せない。
- gitが内容を出さない`Binary files ... differ`のファイルは、切り詰める前の全体からパスを集める。
  引用符で囲まれたパスは、引用符の中の接頭辞を外し、引用符は残す。
  パスがandを含むときは、新しい側の接頭辞`b/`の直前にあるandのうち、左の`a/`を外したパスと右の`b/`を外したパスが一致する位置で区切る。
  一致する位置が無いとき(renameなど)は、最後のandで区切る。
- バイナリのファイルについての指示は、プロンプトの囲みの外に固定の文で置き、パスの一覧だけを別の囲みに入れる。
  囲みの中の文は、指示として読まれないためである。
  内容は差分に無いので、Readで読めるテキストなら読んで判断し、読めないものは判断せず、未レビューだと指摘に書くよう求める。
  `.gitattributes`で読めるコードがバイナリ扱いになることがあるので、読むことは禁じない。
  一覧に挙げるのは20件までで、残りは件数で書く。
- プロンプトの指示は、Claudeが従うとは限らない。
  そのため、変更ファイルと照合したパス(`binary_files`)と落とした件数は、生成ステップの戻り値で投稿のステップまで運び、投稿の本文に決定的な一文を足す。
  プロンプトに載せるのも、照合したパスだけである。
  詳細は「総評のパターン」にある。
- 取り直しと例外は、CIのログとファイルの内容の取得と同じである。実装は`callGhApiRawBody`にある。
  冪等でない要求は取り直さず、欠けたときにすぐ例外を投げる。取り直すと副作用が重なるためである。

CIの失敗を直す回は、`git diff`を自分で読み、`Binary files`の行を削除1件として数える。
そのため、ここで集めたパスは、CIの回の判断に使わない。

端末の制御列を取り除かず、置き換えにするのは、取り除くと列の中に書いたコードを読み手から隠せるためである。
置き換えなら、制御文字があること自体をレビューが指摘できる。
文字を1つずつ照合するので、列の終端を探す処理は無く、処理の時間は入力の長さに比例する。

置き換える文字は次のとおりである。

- 制御文字(C0、DEL、C1)。タブと改行は残す。
- 直後が改行でない復帰。行の途中で表示を戻し、前の文字を上書きして見せられるため。
- 書式文字(書字方向の制御、ゼロ幅、タグ文字、BOM、ソフトハイフンなど)。
- 行区切り(U+2028)と段落区切り(U+2029)。行の途中で行が変わったように見せて、`+`の無い行を偽装できるため。
- 表示されない文字(Unicodeの`Default_Ignorable_Code_Point`)。異体字選択子、字を結合する記号、ハングルの詰め文字、タグ文字のほか、未割り当てなのに表示されないU+2065などを含む。
- 点字の空白、私用領域、対のないサロゲート。
- 元の本文にある`<U+`の`<`。`<U+003C>U+`にして、作者が書いた`<U+001B>`と本物の置き換えを区別する。

正当な文字も置き換わる。
絵文字を結合するZWJ、絵文字の異体字選択子(U+FE0F)、ペルシャ語のZWNJ、ソフトハイフン、先頭のBOMがその例である。
`❤<U+FE0F>`のように見えるが、読めるので許容する。
U+FE0Fだけを除くと、異体字選択子を使って見えない情報を埋める余地が残るため、除かない。
レビューのプロンプトは、次の4点を伝える。

- `<U+XXXX>`は、元の本文にあった文字の置き換えである。
- 正当な使い方があるので、前後の文脈で判断する。
- 疑わしいものは指摘する。
- `suggested_code`には写さない。

置き換えで本文は、1文字につき最大10文字に増える。
文字数の上限(40万字)は、増えた本文がプロンプトを膨らませないための歯止めである。
値は、行数の上限(3000行)に1行133字の差分が収まる大きさである。
置き換えの前ではなく後の長さに上限をかけるのは、増えた分を含めて、プロンプトに載る長さを抑えるためである。
上限は行の末尾で切り、1行が上限を超えるときだけ行の途中で切る。
行の途中で切るときは、末尾の閉じていない`<U+00`のような断片と、サロゲートペアの前半を落とす。
1行の平均が133字を超える差分は、ロックファイルや生成物を含むPRなどで、行数の上限より先に切れる。
切れたときは、切り詰めの注記を付け、残りを変更ファイルの一覧からReadで見るよう促して、レビューを進める。
Readで読むファイルは、置き換えを通らない。
注記は、見えない文字と制御文字を自分で探して指摘するよう、固定の英文で促す。

例外は`pr_review_generate`を失敗で止め、失敗の記録と通知に流れる。
終了コードが0で本文が空のときは、差分の無いPRなので、そのままレビューする。

ファイルの生の内容を取る`getRepoFileText`(draw.ioのビューアの固定を上げる処理が使う)も、終了コードが0以外なら同じ例外を投げる。
内容を書き換えてコミットするので、制御文字は置き換えない。

### 投稿の形

Factoryはレビューの開始のコメントを投稿しない。投稿するのは、インラインの指摘(コードの提案を含む)と総評だけである。指摘の形は`.claude/skills/factory-review/SKILL.md`の「投稿形式」に書く。

Factoryは運用者自身のアカウントで投稿する。そのため、総評とインラインのコメントは、1行目に`[pr_review 自動レビュー] @<author>`というロールタグとメンションを付ける。

ClaudeがGitHubに投稿する文章は、共通の文体の規則に従う。半角英数字と日本語の間に半角スペースを入れない(インラインコードとコードブロックの中は除く)。文体はです・ます調で、1文を1行に書き、要点が複数あれば箇条書きにする。規則の詳細は`factory-writing`スキルに書く。

### 通知の判定

投稿の後、Discordの通知の種類を決める。今回の指摘に`[MUST]`があるか、前回までの`[MUST]`の指摘が今回の解決の後も残っていれば、`changes_requested`にする。それ以外は`reviewed`にする。変更が要るのか、承認だけでよいのかを通知で見分けられるようにするためである。

再レビューで未解決のスレッドの一覧を読めなかったときは、残りの有無が分からない。0件として数えず、`unverified`にする。`reviewed`にすると、未解決の`[MUST]`が残るPRを、人のApproveを待てる状態と示してしまうためである。
今回の指摘に`[MUST]`があれば、一覧を読めなくても`changes_requested`にする。
`unverified`のとき、総評はパターン5(指摘を投稿するときはパターン1)になり、`factory.reviews`の`result`は記録しない。作業項目は`reviewed`に進み、状態遷移の記録に補足を残す。
一覧を読めなかったPRは、人がPRのスレッドを確かめてから承認を判断する。

スレッドの一覧は、100件ずつページを辿って全件を読む。
次のいずれかのときは、一部だけの一覧を返さず、読めなかったものとして扱う。
一部だけを返すと、読めなかった分の未解決の`[MUST]`を数えずに0件と判断し、LGTMにしてしまうためである。

- 1000件(10ページ)を読んでも続きがある。
- 続きがあるのに、次のページを指すカーソルが無い。
- 形の合わないスレッドがある。コメントが1つも無いスレッドを含む。

PRレビューが終わると、作業項目はレビュー済み(`reviewed`)になる。

## 総評のパターン

総評はClaudeの自由記述ではなく、次の5つの定型からフローが組み立てる(`renderReviewSummary`)。Claudeの要約(`summary`)は`factory.reviews`に記録するだけで、GitHubには投稿しない。

| パターン | 条件 | 総評 |
| --- | --- | --- |
| 1 | 指摘を投稿した | 件数と「確認お願いします。」 |
| 2 | 再レビューで指摘が0件 | 「修正を確認しました。LGTMです。」と最終判断の一文 |
| 3 | 初回のレビューで指摘が0件 | 「指摘はありません。LGTMです。」と最終判断の一文 |
| 4 | 再レビューで指摘が0件だが、未解決の`[MUST]`が残る | 「新しい指摘はありません。未対応の指摘がN件残っています。確認お願いします。」 |
| 5 | 再レビューで指摘が0件だが、未解決のスレッドの一覧を読めなかった | 「新しい指摘はありません。未解決の指摘を読み取れなかったため、残りがあるかは確認できていません。確認お願いします。」 |

最終判断の一文は「最終的なApprove判断は人が行ってください。」である。パターン1、4、5には付けない。

差分に内容が出ないバイナリのファイルがあるときは、パターンによらず、総評に固定の一文とパスの一覧を足す。
一文は、バイナリのファイルの件数を伝え、人が内容を確認するよう求める(`renderBinaryFilesLines`)。
Claudeが指摘を出さなくても、バイナリのファイルが隠れたまま通らないようにするためである。
パターン2と3は、読めていないファイルが残るので、LGTMと書かない。
パターン2は「修正を確認しました」、パターン3は「差分に指摘はありません」で止める。
行コメントを解決できず投稿し直した総評にも、同じ一文と一覧を足す。

一覧の並べ方は、次のとおりである。

- 空行を挟んで、最終判断の一文の後(パターン1と4は確認を求める文の後)に置く。
- 一覧は20件までで、残りは「(ほかN件)」と書く。
- 並べるパスは、改行を空白にまとめ、200文字で切る。切ったときは末尾に「…」を付ける。
- `<!--`は`&lt;!--`に置き換える。
- パスはコードスパンで囲む。`@`のメンションやリンクとして描画させないためである。
- パスがバッククォートを含むときは、含まれる連なりより長いフェンスで囲む。
- 先頭か末尾がバッククォートなら、フェンスと混ざらないよう空白を挟む。

照合で落とす分は、次のとおりである。

- 差分の行から取り出したパスは、PRの作者が書ける行なので、APIの変更ファイルに載るものだけを一覧に並べる(`selectListedBinaryFiles`)。
- 載らないものは、Claudeに読ませない。件数(`binary_unlisted_count`)だけを一文の件数に加えて、「(パスを確認できなかったものがN件あります)」と書く。
- パスの区切りの細工で、変更に無いパスが読む対象になることを防ぐためである。

投稿のステップは、`binary_files`と件数の入力がundefinedかnullでも、バイナリが無いものとして扱う(`normalizeBinaryInput`)。
このときの総評は、バイナリの一文と一覧を持たない形になる。
古いflow定義が新しいscriptを呼んでも、投稿が落ちないようにするためである。

パターン1は、初回と再レビューで共通である。行と紐づけられずに投稿できなかった指摘があるだけの場合も、パターン1である。再レビューとは、このPRへのFactoryのレビューが過去にある場合をいう。

行に紐づけられなかった指摘は、総評に並べる。
並べる`path`と`message`は、`<!--`を`&lt;!--`に置き換える。
`path`は、改行を空白にまとめ、200文字で切り、コードスパンで囲む。バイナリのパスの一覧と同じ扱いである。

GitHubが行コメントの行を解決できず、レビュー全体を422で拒否したときは、行コメントを付けずに一度だけ投稿し直す(`postMarkedReview`)。
対象は行の解決に限らない、すべての422である。422の文言はGitHub側で変わりうるので、文言で絞ると復旧できなくなるためである。
行コメントと無関係な422でも、投稿し直しは1回だけで、失敗すればそのまま失敗になる。
受けた422のメッセージはマスクしてログに残すので、原因を切り分けられる。
このとき、行コメントにするはずだった指摘もすべて、行に紐づけられなかった指摘として総評に並べる。
総評の2行目は「GitHubが行を解決できなかったため、行コメントにする指摘を総評に移しました。」の1行にする。
確認を求める文は、次の3行目に分ける。1文を1行に保つためである。
「N件コメントしました」は書かない(`renderUnresolvedLineSummary`)。
行コメントにするはずだった指摘には、位置(`path:line`、範囲の指摘は`path:line-end_line`)を添える。行に紐づけられなかった指摘の形は変えない。
同じ入力では何度投稿しても同じ行で拒否されるため、失敗にせず、指摘を総評で届ける。
拒否された投稿はGitHubに残らないので、レビューが二重になることは無い。
行コメントが無いときと、投稿し直しも拒否されたときは、そのまま失敗にする。

## スレッドの解決

再レビューのたびに、PR修正が対応済みとみなせるFactory自身のスレッドを、ベストエフォートで解決(resolve)する(`selectThreadsToResolve`)。初回のレビューでは何も解決しない。

解決の対象にするのは、Factory自身のインラインの指摘のスレッドのうち、最後のコメントもFactoryが書いたものだけである。スレッドに人が返信していれば、対象から外して開いたまま残す。

| スレッドの状態 | 解決するか |
| --- | --- |
| PR修正がcommitのsha付きで「対応: `<sha>`」と返信した | 再レビューのたびに解決する |
| PR修正が「対応: 見送り」か「対応: 変更なし」と返信した | 人の判断が要るので解決しない |
| Factoryの指摘のまま、何も返信されていない | 指摘が0件の再レビュー(パターン2と4)で解決する |

何も返信されていないスレッドは、人が手で直した場合などに残る。解決の処理の後も開いたままの`[MUST]`のスレッドが1件以上あれば、パターン4になる。

## 投稿の冪等性

投稿のステップ(`pr_review_post`)は、投稿の前に、同じ作業項目が同じ`review_sha`に対して投稿済みのレビューを探す(`findPostedReview`)。見つかれば投稿せずに、そのレビューのidで`factory.reviews`に記録する。投稿と記録の間でステップが落ちても、再実行でレビューを二重に投稿しないためである。

投稿の直前には、リポジトリのオーナーの数値IDも照合する。
準備の入口の照合から、Claudeの実行を挟むので、その間に名前が別の人に渡っても、レビューの文面を相手に渡さないためである。
通らなければ、投稿もスレッドの解決もせずに、作業項目を終端の`blocked`にして、Discordで人に知らせる。
投稿済みのレビューを再利用するときは書き込まないので、照合しない。
照合は[運用](../operations.md)の「オーナーの数値IDを固定する」に書く。

総評には、レビューしたcommitのshaを表す目印(`<!-- factory-review-sha:<sha> -->`)を入れる。shaの目印は、PRレビューの目印(`<!-- factory:pr_review:<work_item_id> -->`)の前の行に置く(`withReviewMarkers`)。PRレビューの目印が最後の行に残るので、自己再発火の判定とPR修正の指摘の収集の読み方は変わらない。

投稿済みとみなすのは、次をすべて満たすレビューである(`findPostedReviewId`)。

- 投稿者がviewerである。目印は誰でも本文に貼れるので、投稿者も確かめる。
- 本文が、shaの目印とこの作業項目のPRレビューの目印でこの順に終わる。末尾の空白は無視し、CRLFはLFとして比べる。

本文の途中に貼られたshaの目印には一致させない。shaの目印の無いレビューは、どのshaに対するものか分からないので一致させない。

### 投稿済みのレビューを再利用するとき

再利用するときは、スレッドを1つも解決しない。再実行ではClaudeがレビューを作り直すので、新しい指摘が0件になりやすい。それを根拠に、投稿済みのレビューの指摘を閉じないためである。

代わりに、未解決の`[MUST]`のスレッドをすべて数える。再利用したレビュー自身の指摘も含める。1件以上あれば、Discordの通知を`changes_requested`にする。

前の実行がスレッドの解決の前に落ちていた場合、そのラウンドで解決するはずだったスレッドは開いたまま残る。これは人が確かめて解決する。

再利用には、既知の制約が2つある。

- 再利用したレビューの`[MUST]`のうち、行と紐づけられず総評に並べたものはスレッドにならない。そのため、残っている`[MUST]`の数に入らない。
- `factory.reviews`には、再実行で作り直した`verdict`と`findings`が、再利用したレビューのidと組で記録される。そのため、実際に投稿した内容と食い違うことがある。監査の証跡(`audit_evidence`)のレビューの数と指摘の集計は、この記録をそのまま数える。

### 投稿のステップの失敗

投稿済みのレビューを探すのに要るviewerとレビューの一覧を取得できないときは、投稿せずに失敗する。投稿済みかが分からないまま投稿しないためである。

再利用するときにスレッドの一覧を取得できなければ、記録する前に失敗する。このときも投稿は起きない。

投稿した後のGitHub APIの呼び出し(スレッドの解決)は、失敗しても警告を残して続ける。そのため、投稿済みなのに記録と状態の遷移が無い、という状態は残らない。

準備と投稿のステップは、GitHubの5xxや応答の無い失敗(認証失敗を除く)で落ちると、例外の文の先頭に`github_transient:`を付ける。
付けるのは`markTransientGitHubFailure`で、付けた例外はそのまま失敗になる。
4xxや応答の形の不一致のように、待っても結果が変わらない失敗には付けない。
印の付いた失敗は自動で再開する([一時的な失敗の自動の再開](#一時的な失敗の自動の再開))。

## 修正

### 止めたときの作業項目の状態

PR修正のステップの結果の`blocked`と、作業項目の状態のブロック(`blocked`)は別のものである。
修正と検証のステップは、続けられないときに止める結果(`blocked`)を返す。
完了のステップ(`decideFixFinishAction`)は、この結果の作業項目を人の対応待ち(`needs_human`)にする。

作業項目がブロックになるのは、次の3つのときだけである。

| 止めたところ | 例 |
| --- | --- |
| 準備のステップの確認([準備での確認](#準備での確認)) | PRがdraft、forkのPR、親のIssueの実装フローが実行中、worktreeの使用中、時間設定 |
| 完了のステップの、pushの直前の確認 | 修正の実行中にPRのheadが動いた |
| 要件の不足の差し戻しに成功した | [requirements_gapの差し戻し](#requirements_gapの差し戻し) |

それ以外で止めたとき(Claudeが止めた、日次予算、禁止された変更、検査の失敗、`.git`の書き換えなど)は、作業項目は人の対応待ちになる。

### フィードバックの収集

収集のステップ(`pr_fix_collect`)は、作業項目の処理済みの位置より新しいフィードバックを集める。処理済みの位置は[watermark](#watermark)に書く。集めるのは、PRのレビュー、インラインのレビューコメント、Issueコメントである。

Factory自身のPRレビューと、目印の無いインラインの指摘も集める。Factoryのレビューの後に`factory:fix`ラベルを付けるのは、その指摘を直させる操作だからである。集めるものが無ければ、「no actionable feedback」として人の対応待ちにする。

承認済みの要件定義は、このステップの結果で受け渡さない。修正と検証のステップが、親の作業項目(`parent_work_item_id`)から直接取得する。

### 修正の適用

修正のステップ(`pr_fix_apply`)は、`factory-fix`スキルでheadless Claudeを実行する。入力は、集めたレビューとコメント、未解決のコメント、承認済みの要件定義である。

Claudeは修正の結果(`outcome`)、理由、要約、各コメントへの返信、コミットの件名と本文を返す。日次予算を超えていれば、Claudeを起動せずに止める結果(`blocked`)を返す。Claudeの実行が失敗したときは例外を投げる。

### 検証

検証のステップ(`pr_fix_verify`)は、修正をpushしてよいかを確かめる。Claudeが要件の不足かブロックを返したときは、検証するものが無いのでそのまま返す。

検証は次の順に進む。

1. 変更を調べ、禁止された変更があれば止める結果を返す。
2. 検査コマンドを全件実行する。
3. 検査に失敗したら、日次予算の範囲で、失敗の出力を添えてClaudeの修正を1回だけ追加で実行する。
4. 変更をもう一度調べ、検査コマンドの全件をもう一度実行する。
5. それでも失敗するときは止める結果を返す。

変更を調べる時点と内容は[安全策の実装](#安全策の実装)に書く。

### commitとpush

完了のステップ(`pr_fix_finish`)は、commitの前に[コミットの前の再確認](#コミットの前の再確認)をする。commitとpushの直前には、リポジトリのオーナーの数値IDを照合する。準備の入口から長い実行を挟み、その間に名前が別の人に渡りうるためである。通らなければ、pushと返信をせずに、作業項目を`blocked`にしてDiscordで人に知らせる。通ったら、commitしてpushし、各コメントに返信して、再レビューを依頼する。作業項目は再レビューの依頼済み(`rereview_requested`)になる。

コミットメッセージは、Claudeが提案する件名(`commit_subject`)と、任意の本文(`commit_body`)をフローがつないで作る。

- 件名はConventional Commitsの形で、50文字以内を目安にする。72コードポイントを超えると拒否する。
- 本文は箇条書きにする。
- `Co-Authored-By`と`Generated-By`のトレーラーは、`commitAndPush`の`withCommitTrailers`が付ける。
- 英数字と日本語の間のスペースを取り除く。コードスパンの中は除く。

pushするcommitが無くても、溜めた返信は投稿する。Claudeがすべての指摘を見送った場合も、返信をGitHubに届けるためである。この場合、作業項目は人の対応待ちになる。

### 再レビューの依頼

再レビューは`factory_config`の`default_reviewers`に依頼する。空なら、そのラウンドを起こしたレビューとコメントの投稿者に依頼する。PRの作者とFactoryのアカウントは依頼先から除く。

修正はpushまで済んでいるので、依頼の結果に関わらず作業項目は再レビューの依頼済みに進める。
依頼できなかったときの記録は、結果によって次のように分ける。

| 依頼の結果 | 作業項目の理由(`status_reason`) | notice | Discordの通知 |
| --- | --- | --- | --- |
| 依頼先の候補がいない | 残す | 残さない | 別に通知しない |
| 候補が全員除外された | 残す | 残さない | 別に通知しない |
| 依頼のAPIが失敗した | 残す | `pr_fix_reviewer_request_failed` | `pr_fixed`の通知の補足欄に載せる |

候補がいない場合と全員除外された場合は想定内で、人がすることは無い。
`pr_fixed`の通知そのものが、再レビューの依頼という結果を伝える。

依頼のAPIが失敗したときは、人がGitHubのPRでレビュアーを依頼する必要がある。
依頼の前のPRの取得(`getPr`)の失敗と、Botや削除済みの作成者の名前で依頼を組み立てられない場合も、APIの失敗として扱う。

## CIの失敗を直す回

CIの失敗を直す回(CI回)は、PRのCIが失敗したとき、失敗したジョブのログから修正するための回である。
`pr_fix`のフローを、作業項目の`ci_check_id`が非NULLのときだけ、次のように変えて動かす。
`ci_check_id`は、直す失敗の行(`pr_ci_checks`)のIDである。
失敗の行の状態は[PRのCI監視の仕様](pr-ci.md)に、ログとプロンプトの部品は[CIの失敗を直す部品の仕様](ci-fix.md)に書く。

### 通常の回との違い

| ステップ | CI回 |
| --- | --- |
| 準備 | 修正ラウンドの上限を確かめない。失敗の行が、いまのheadについて、この作業項目で修正中であることを確かめる。worktreeを用意した後、無視されたファイルを消す |
| 収集 | レビューもコメントも集めない |
| 修正 | 失敗した実行のログの抜粋をClaudeに渡す。`Bash`は渡さない。`metadata`ジョブだけが落ちていれば、Claudeを起動せず、`wmill-lock.yaml`のhashを再計算する |
| 検証 | 変更を許可リスト方式でも検査する。返信を持つ結果は受け付けない。変更が再計算と一致する`wmill-lock.yaml`だけのときは、検査コマンドを実行しない |
| 完了 | 返信を投稿せず、作業項目のheadと処理済みの位置を更新しない。pushの直前にPRの状態を確かめる。再計算の出力は、baseの先端も確かめ直す |

`metadata`ジョブの失敗を再計算で直す流れは、[CIの失敗を直す部品の仕様](ci-fix.md#metadataジョブの失敗を直す経路)に書く。
再計算で直せないPRは、固定の理由で人の対応待ちになり、`mise run metadata`を案内する通知が出る。

修正ラウンドの上限を確かめないのは、CI回が`fix_round`を前の値のまま写すためである。
指摘の修正が上限に達したPRでも、CI回を止めない。
CI回の回数の上限は、`pr_ci_fix_max_rounds`が決める。

失敗の行が合わないときは、準備のステップの結果を`skip`ではなく`guard_blocked`にする。
`skip`にすると、完了のステップが何もせず、作業項目が修正中のまま残るためである。

CI回の作業項目は、`parent_work_item_id`を持たない。
要件の不足は差し戻さず、人の対応待ちにする。

### 作業項目のheadを更新しない理由

通常の回は、pushしたshaを作業項目の`head_sha`に記録する。
CI回は記録しない。
`poll_prs`の自動のレビューは、PRの最新の作業項目の`head_sha`とPRのheadが違うときに起動する。
CI回が記録すると、pushしたheadが「処理済み」になり、再レビューは起動しない。
通常の回と逆なので、完了のステップの配線を調べるテストで固定している。

### 再レビューへの入力

CI回か競合回がpushしたheadのレビューには、どちらの回の差分かを、プロンプトの固定文で伝える。
そのPRの`pr_fix`のうちCI回か競合回のどれかが、pushしたcommitにレビューするshaを含むときに限る。
最新かどうかと状態は問わない。
pushしたcommitは、依頼の前後で変わらないためである。
人が後からpushしたheadのレビューには伝えない。
この問い合わせが失敗したときは、固定文を足さず警告を残し、通常のレビューを続ける。
値はDBから決める回の種類(CI回、競合回、どちらでもない)だけで、PRの内容からは決めない。
CI回の固定文は、次の点を重点的に見るよう頼む。

- テストの弱体化。
- 抑制のコメントの追加。
- 原因を隠すだけの修正。
- 失敗の原因と無関係な振る舞いの追加(外への通信、環境変数の読み取り)。
- 無視ファイルとツールの設定の変更。

CI回のClaudeは、通るように直す立場なので、検査を弱めて通す誘惑があるためである。
競合回の固定文は、[競合回の再レビューへの入力](#競合回の再レビューへの入力)に書く。

再レビューの依頼(`requestRereview`)は通常の回と同じである。
CI回は集めたレビューとコメントが無いので、`default_reviewers`が空なら、依頼先が無く、依頼しない。

### 再開

CI回の`pr_fix`は、手動の再開(`retry_work_item`)でも、イメージが古いときの自動の再開でも再開しない。
作業項目だけを再開すると、失敗の行が`fixing`のまま食い違うためである。
回が終わると、`watch_pr_ci`が失敗の行を`failed`か`superseded`に戻す([PRのCI監視の仕様](pr-ci.md)の「回復」)。
PRにpushしてheadが変わると、新しい失敗として判定される。

競合を直す回(`conflict_check_id`が非NULL)の`pr_fix`も、手動の再開でも、イメージが古いときの自動の再開でも再開しない。
競合の行が、直している作業項目を結んだままになり、行と作業項目が食い違うためである。

## マージの競合を解く回

マージの競合を解く回(競合回)は、PRのブランチが既定のブランチ(base)と競合したとき、baseをmergeして競合を解き、mergeコミットをpushするための回である。
`pr_fix`のフローを、作業項目の`conflict_check_id`が非NULLのときだけ、次のように変えて動かす。
`conflict_check_id`は、直す競合の行(`pr_conflict_checks`)のIDである。
作業項目は、競合の回(`conflict_episode`)も持つ。
git操作と検査の部品は[CIの失敗を直す部品の仕様](ci-fix.md#競合回のgit操作と検査)に、安全策の理由は[セキュリティ](../security.md#マージの競合を解く回)に書く。

### 通常の回との違い

| ステップ | 競合回 |
| --- | --- |
| 準備 | 修正ラウンドの上限を確かめない。競合の行が、いまのheadについて、この作業項目で競合のままであることと、PRのbaseが既定のブランチであることを確かめる。worktreeを用意した後、baseをmergeして、ローカルだけの基準コミットを作る |
| 収集 | GitHubを読まず、固定の結果を返す。処理済みの位置は進めない |
| 修正 | 競合ファイルだけをClaudeに解かせる。`Bash`は渡さない。競合ファイルが無いときは、Claudeを起動せず、日次予算も見ない。コミットメッセージは固定文で、返信は空である |
| 検証 | HEADが基準コミットであることを確かめ、変更と解消を検査する。検査コマンドは1回だけ実行し、失敗してもClaudeを再実行しない。検査コマンドの前後で同じだったツリーのshaを`verified_tree_sha`として返す |
| 完了 | pushの直前に、検証と同じ検査をもう一度行い、ツリーが`verified_tree_sha`と同じであることを確かめ、PRを読み直す。mergeコミットをpushし、通知を出さない |

修正ラウンドの上限を確かめないのは、競合回が`fix_round`を前の値のまま写すためである。
競合回の回数の上限は、`pr_conflict_fix_max_rounds`が決める。

### 準備の結果

準備のステップの結果(`outcome`)は、次のとおり振り分ける。
競合回で直せない場合とbaseがすでにPRにある場合は、後続のステップを実行せず、完了のステップへ進む。

| 事象 | 結果 | 作業項目の遷移 |
| --- | --- | --- |
| mergeできて、検査に通った | `proceed` | 修正中のまま |
| baseがすでにPRの履歴にある | `conflict_up_to_date` | `reviewed`。注記は`conflict round: up_to_date` |
| 競合ファイルが10を超える、通常のファイルでない、バイナリ、衝突ブロックが無い、属性がある | `conflict_blocked` | `needs_human`。注記は`conflict round: unresolvable conflict` |
| 保護パスが競合しているか、両側が変えた | `conflict_blocked` | `needs_human`。注記は`conflict round: a conflicted path is protected` |
| baseが`.github/workflows/`を変えている | `conflict_blocked` | `needs_human`。注記は`conflict round: base changes workflows` |
| PRのbaseが既定のブランチでない | `conflict_blocked` | `needs_human`。注記は`conflict round: base is not the default branch` |
| 競合の行が無い、競合でない、別の作業項目に結ばれた、競合の回が終わった | `guard_blocked` | `blocked`。注記は固定文で、一時の停止 |
| PRのheadが動いた(準備の時点、baseのmerge中) | `guard_blocked` | `blocked`。注記は固定文で、一時の停止 |
| worktreeを別の処理が使っている、同じブランチで実装のフローが動いている | `guard_blocked` | `blocked`。注記は固定文で、一時の停止 |
| worktreeの状態が前提と違う | `guard_blocked` | `blocked`。注記は理由そのまま |

一時の停止は、待てば解ける事情で止めた回である。
回復は、一時の停止の注記を保留の理由に写さず、行に最終の保留を書かない。
次の巡回で判定し直す。
起動し直しを止めるのは、準備の停止なら行の起動の回数の上限、完了の停止なら競合を直した回数の上限(`pr_conflict_fix_max_rounds`)である。
Claudeを動かす前の停止は、競合を直した回数に数えないためである。
一時の停止の注記の一覧は、[PRのCI監視の仕様](pr-ci.md#競合を直す判断)にある。

競合ファイルが無いのに`proceed`になる場合がある。
GitHubが競合と判定したのに、ローカルではきれいにmergeできたときである。
この場合は、Claudeを起動せず、検査コマンドを実行して、そのままpushへ進む。
きれいにmergeできたときも、両側が変えた保護パスは止める。

### 完了の結果

完了のステップの遷移は、次のとおりである。
どれも、再レビューの依頼、返信、`pr_fixed`の通知を出さない。
失敗のDiscordの通知とnoticeも出さない。
ただし、次の2つは運用者の対応が要るので、通常の回と同じnoticeを残す。

- リポジトリのオーナーの数値IDの照合に落ちたとき。準備と完了のステップが残す。
- workerのイメージが古いとき。準備と検証のステップが残す。

完了のステップがイメージの古さを検出したときは、noticeを残さない。
その場合は、`blocked`で止まった回が回数に数えられず、行の起動の回数の上限に達して`rounds_exhausted`で通知されるまで、通知が無い。
上限に達するまでの時間は、上限の回数に巡回間隔の5分を掛けた程度である。

| 事象 | 作業項目の遷移 |
| --- | --- |
| mergeコミットをpushできた | `rereview_requested`。ラウンドを記録する |
| pushの前の確認に通らない | `needs_human`。注記は止めた理由。workerが検査の前提を満たさないときは、ラウンドを記録せず`blocked` |
| 検査したツリーが、検証のステップが通したツリーと違う、または検証が通したツリーを記録していない | `needs_human`。注記は`conflict round: the tree changed after the verification`。ラウンドを記録する |
| PRのheadが動いた | `blocked`。ラウンドを記録する。注記は`conflict round: the PR head moved before the push`で、一時の停止 |
| worktreeを別の処理が使っている | `needs_human`。ラウンドを記録する。注記は準備のステップと同じ固定文で、一時の停止。保持者はログに残す |
| baseがpushの直前に動いた | `reviewed`。注記は`conflict round: the base branch moved`。ラウンドを記録する |
| GitHubがworkflowの権限不足でpushを拒否した | `needs_human`。注記は`conflict round: base changes workflows`。ラウンドを記録する |
| Claudeや検査が止めた | `needs_human`。検査コマンドの失敗の注記は`conflict round: check failed` |

検証のステップの検査コマンドは、対象リポジトリのコードで、worktreeを書き換えられる。
そのため、検証は検査コマンドの後にもう一度解消を検査する。
検査コマンドの前後のツリーが違えば、注記`conflict round: the tree changed during the checks`で止める。
この注記は一時の停止に数えず、`fix_stopped`で最終の保留になる。
同じなら、そのツリーのshaを完了のステップへ渡す。
完了のステップは、pushの直前の検査で得たツリーが、そのshaと同じであることを確かめる。
検査コマンドが通ったツリーとpushするツリーを結びつけるためである。

baseがpushの直前に動いたときは、`reviewed`にして、注記で`up_to_date`と区別する。
baseは動き続けるので、次の判定で読み直す。
行には最終の保留が付かない。

作業項目のheadは、CI回と同じく更新しない。
その差が、`poll_prs`の自動のレビューを起動するためである。

### 注記の固定文

注記は、固定文の完全一致で、競合の行の保留の理由へ写せる形にしている(`holdReasonForConflictStoppedItem`)。
一時の停止の注記は、保留の理由に写さず、行に最終の保留を書かない。
どちらにも当たらない注記は、保留の理由が`fix_stopped`になる。
注記にshaや保持者のような変わる値を含めると、完全一致が外れて`fix_stopped`になるので、固定文だけにして、変わる値はログに残す。
Claudeの理由の先頭には固定の接頭辞`conflict round: claude blocked:`が付くので、Claudeの出力の文字列が保留の理由を決めることは無い。

止めた理由の注記には、イメージが古い理由(`worker image is stale: run mise run up:`で始まる文)の接頭辞を壊す語句を付けない。
回復は`startsWith`でこの理由を見分け、自動の再開と回数の除外に使う。
検証と完了のステップが検査の前提を満たさないときの注記は、例外の文のまま残す。

### 競合回の再レビューへの入力

競合回がpushしたheadのレビューには、競合回用の固定文を足す。
回の種類の決め方は[再レビューへの入力](#再レビューへの入力)と同じで、CI回の固定文は足さない。
固定文は、次の点を重点的に見るよう頼む。

- mergeコミットであること。
- 衝突を解いた箇所が、PRの変更とbaseの変更が重なる範囲にあり、その外のファイルを編集していないこと。
- 両側の変更の意図が、解消後のコードに残っていること。
- 片側を丸ごと捨てていないこと。
- テストの弱体化と抑制のコメントの追加が無いこと。
- 解消に無関係な振る舞いの追加(外への通信、環境変数の読み取り)が無いこと。

競合回のClaudeは、衝突を消すことを求められる立場なので、片側を捨てたり検査を弱めたりして済ませる誘惑があるためである。

## 返信の形式

返信は運用者自身のアカウントで投稿する。そのため、フローが固定の構造で組み立てる(`renderFixReply`)。1行目がロールタグ、続いて本文、末尾が対応の行である。形式は`.claude/skills/factory-fix/SKILL.md`の「返信形式」に書く。

各コメントへの返信は、次の3つの判断(`decision`)のどれかになる。

| `decision` | 意味 | 返信の末尾 |
| --- | --- | --- |
| `fixed` | このPRの範囲で修正した | `対応: <commit sha7>` |
| `skipped` | 対応しないと判断した。理由は`body`に書く | `対応: 見送り` |
| `propose_issue` | 指摘は妥当だが、このPRの範囲外なのでIssue化を提案する | `対応: Issue化を提案(承認待ち)` |

返信は、実際に集めたコメントの`review_comment_id`を指すものだけを扱う。Claudeの出力の全体は、監査のために`insertFixRound`がそのまま記録する。

## Issue化の提案

Claudeは`propose_issue`を選んだとき、修正を強行せず、Issueの`title`と`body`を返す。`pr_fix_finish`は、返信を投稿する前に提案を`factory.issue_proposals`に記録する。

- レビューコメントのスレッドのidは、`listReviewThreads`を使ってベストエフォートで解決する。
- コメントがPRのレビューコメントか、通常のIssueコメントかは、`is_inline`列に記録する。
- `matchReviewThreadForComment`は、コメントの`databaseId`でスレッドを照合し、`(path, line)`には頼らない。

提案が1件でもあるラウンドは、再レビューの依頼済みではなく人の対応待ちで終わり、レビュアーへの依頼もしない。Discordには「Consoleの要対応で提案を承認または却下してください」と通知する。commitするものが無いラウンドでも、提案は記録する。

### 承認と却下の反映

人がConsoleの**要対応**で決定すると、`f/factory/approval_decide`が決定を記録し、`f/factory/steps/issue_proposal_apply`を起動する。承認依頼の種類(`kind`)は`issue_proposal`である。要件定義の承認と同じく、人が判断してから進む仕組みである。

| 決定 | 処理 |
| --- | --- |
| 承認 | 提案の`title`と`body`でIssueを対象リポジトリに作り、スレッドに「Issue #Nを起票しました。」と返信して解決する |
| 却下 | スレッドに「見送りとします。」と入力した理由を返信し、スレッドは開いたままにする |

承認で作るIssueの本文では、`{{pr_url}}`を元のPRのURLに置き換え、末尾に起票元を示す一文を付ける。`with_factory_label`が真なら、作ったIssueに`factory_config.trigger_label`(既定値は`factory`)を付け、そのまま要件定義の工程に乗せる。偽なら起票だけをする。

返信の宛先は、`is_inline`列をもとに決まった方法で選ぶ。

### 状態の切り替え

対象の作業項目の提案がすべて決まると、作業項目の状態を人の対応待ちから切り替える(`decidePostProposalStatus`)。そのラウンドでcommitをpushしていれば再レビューの依頼済みに、していなければレビュー済みにする。未決定の提案が残る間は、人の対応待ちのままである。

### 再実行の安全性

同じ決定での再実行は安全である。途中でジョブが失敗しても、Issueを二重に作ったり、決定を上書きしたりしない。

- 承認者(`decided_by`)は、要件定義の承認と同じくfail-closedで導出する。
- 決定は、状態が`pending`であることを条件にしたUPDATEで1回だけ記録する(楽観ロック)。
- 作ったIssueの本文に`<!-- factory:issue_proposal:<id> -->`の目印を入れる。再実行では`findIssueByMarker`でこのIssueを探して再利用する。
- Issueを作る前に、`claimIssueCreation`が提案の行の印を条件付きのUPDATEで取る。取れた呼び出しだけがIssueを作り、取れなかった呼び出しは何もせずに終える。GitHubの検索は索引の反映が遅れ、同時の呼び出しがどちらも目印の検索を空振りしうるためである。印は15分で切れる。例外で終わった呼び出しの印も、期限まで残す。Windmillの同時実行の制限(`concurrent_limit`)は設定しない。有償版でしか効かず、印だけで直列化する。
- 決定済みの提案に違う決定を送ると、上書きせずにエラーで拒否する。

起票に失敗した提案は**要対応**に残る。Issueの作成自体が失敗したときは、決定の前の`pending`に戻す。Issueの作成の後の返信、スレッドの解決、状態の遷移が失敗したときは、「承認済み・起票未完了」として残す。どちらも、もう一度承認すれば続きから起票する。

## watermark

処理済みの位置(watermark)は、`last_review_id`、`last_comment_id`、`last_review_comment_id`の3つである。収集のステップは、これより新しいフィードバックだけを集める。

watermarkを進めるのは、そのラウンドのフィードバックを実際に消化したときだけである(`shouldAdvanceWatermarks`)。

| 終わり方 | watermark |
| --- | --- |
| pushに成功した | 進める |
| pushに成功し、Issue化の提案があって人の対応待ちで終わった | 進める |
| 要件の不足を親のIssueに差し戻した | 進める |
| 失敗、人の対応待ち、ブロック | 進めない |
| CI回がpushに成功した | 進めない |
| 差し戻しに失敗した | 進めない |
| pushが反映されなかった(コミットメッセージが無い、headが動いた、commitするものが無い) | 進めない |

Issue化の提案があっても、元のコメントには提案で返信しているので、フィードバックは消化済みである。

結果が分かる前に進めてはならない。先に進めると、後のステップが例外で失敗したときに、watermarkがそのラウンドのフィードバックを越えてしまう。すると`retry_work_item`で再実行しても集めるものが無く、「no actionable feedback」の人の対応待ちになる。進めないことで、再実行が同じフィードバックを集め直せる。

## requirements_gapの差し戻し

修正中に要件の変更が必要になったとき、Claudeは要件や設計を自分で書き換えない。要件の不足(`requirements_gap`)を返して中断する。

完了のステップは、親の作業項目(`parent_work_item_id`)で元のIssueの作業項目を探し、工程2へ差し戻す。差し戻すのは、親が承認済み(`approved`)かPR作成済み(`pr_open`)のとき、つまり親のフローが動いていないときだけである。

1. 親の状態を、読み取った時点の`status`と`flow_job_id`のままであることを条件にした比較交換で、要件定義の生成中(`requirements_generating`)にする。同じ文で試行(attempt)を1つ増やし、`flow_job_id`を空にする。
2. 要件定義のフロー(pipeline)を起動する。
3. `flow_job_id`が空のままのときだけ、起動したジョブIDを記録する。
4. PR修正の作業項目をブロックで終える。

記録できなかったときは、比較交換の後に別の実行が親に書いている。そのときは、起動したジョブの取り消しを試み、`job_failures`に記録する。取り消しに失敗しても、起動したpipelineはリースを持たないので、作業項目を書き換えずに終わる。pipelineのリースは[作業項目](work-items.md)に書く。

次の場合は差し戻さず、PR修正の作業項目を人の対応待ちにする。PRへのリンクと次の操作をDiscordで知らせ、要件の不足の報告は通知の理由に載せる。

- 元のIssueの作業項目が見つからない。例えば、Factory製でないPRを手動で投入した場合である。
- 親にIssue番号が無い。
- 親が承認済みとPR作成済み以外の状態である(実装中、要件定義の生成中、承認待ちなど)。
- 親の試行回数が`max_attempts`に達している。
- 読み取った後に親の`status`か`flow_job_id`が変わり、比較交換に失敗した。

親が実装中になるのは、準備のステップが確かめた後に実装フローが動き出した場合である。差し戻さないのは、動いているフローや人の判断を上書きしないためである。

## 設定値

PRワークフローは`f/factory/factory_config`の次の値を読む。

| キー | 既定値 | 意味 |
| --- | --- | --- |
| `review_label` | `factory:review` | PRレビューを起動するラベル |
| `fix_label` | `factory:fix` | PR修正を起動するラベル |
| `allowed_labeler_logins` | `[]` | ラベルを付けてよいアカウント。FactoryのPATのアカウントに加えて許可する |
| `allowed_labeler_ids` | `{}` | `allowed_labeler_logins`のアカウントの数値ID。名前をキーにする。入れたアカウントは、IDも一致するときだけ許可する |
| `allowed_labeler_associations` | `["OWNER", "MEMBER", "COLLABORATOR"]` | 修正の材料にする投稿者の関係 |
| `repo_allowlist` | `[]` | 対象のリポジトリ。空なら`owners`のすべて |
| `tracked_pr_days` | `30` | ラベルが外れた後もPRを追跡する日数 |
| `review_post_mode` | `comment_only` | `gated`ならレビューを投稿しない |
| `diff_max_lines` | `3000` | レビューに渡す差分の行数の上限 |
| `claude_timeout_sec` | `1800` | Claude 1回の実行と、PR修正の検査コマンド1件を打ち切る秒数 |
| `max_fix_rounds` | `3` | PR修正のラウンドの上限。上げると、失敗の下限により3ラウンド目以降は`heavy_model`で動く |
| `allowed_check_commands` | `[]` | PR修正の検査コマンド |
| `max_fix_changed_files` | `30` | PR修正で変えてよいファイル数の上限 |
| `max_fix_diff_lines` | `1500` | PR修正の追加と削除の行数の上限 |
| `default_reviewers` | `[]` | 再レビューを依頼する人 |
| `daily_budget_usd` | `50` | 全フローで共有する1日の費用の上限(USD) |
| `max_attempts` | `3` | 要件定義の試行回数の上限 |
| `model` | `claude-sonnet-5-5` | PR修正のモデル。同じPRの修正が続けて2回失敗した後は`heavy_model`を使う |
| `heavy_model` | `claude-opus-5-5` | PRレビューのモデルと、続けて2回失敗した後のPR修正のモデル |

モデルの昇格に使う失敗の数は、同じPRの`pr_fix`の作業項目から数え、次の2つの大きいほうにする。
CIの失敗を直す作業項目(`ci_check_id`を持つもの)と、競合を直す作業項目(`conflict_check_id`を持つもの)は、どちらにも数えない。

- 直近に連続した失敗。`blocked`でないラウンド(`done`か`requirements_gap`)で最後に終えた時刻より後の、次の3つの合計である。
  - Claudeが動いて`blocked`で終えた`fix_rounds`の行
  - 検査の再実行(`pr_fix_verify_retry`)をした作業項目
  - `agent_runs.error`がある失敗した実行の行
- 作業項目の`fix_round`から1を引いた値。毎回`done`で終えても再レビューが続くと、失敗の記録が残らないためである。

除く条件と数の理由は、[運用](../operations.md)の「モデルを使い分ける」にある。

PR修正のラウンドが`max_fix_rounds`を超えると、準備のステップが止め、作業項目は人の対応待ちになる。ラウンドの番号(`fix_round`)は、`poll_prs`が作業項目を作るときに入れる。PR修正の各ラウンドは別の作業項目になり、完了のステップは番号を増やさない。

## タイムアウト

`flow.yaml`の各ステップにはWindmillのtimeoutを付ける。アプリ側のtimeoutが効かなかったときに、最後に打ち切るためである。

| フロー | ステップ | Windmillのtimeout | 定数 | 理由 |
| --- | --- | --- | --- | --- |
| PRレビュー | 準備 | 1800秒 | なし | ロックの待ちだけで900秒かかりうる |
| PRレビュー | 生成 | 7200秒 | `PR_REVIEW_GENERATE_STEP_TIMEOUT_SEC` | Claude 2回分と余裕が収まる |
| PRレビュー | 投稿 | 5400秒 | なし | 個別の見積もりは無い |
| PR修正 | 準備 | 1800秒 | なし | ロックの待ちだけで900秒かかりうる |
| PR修正 | 収集 | 600秒 | なし | 個別の見積もりは無い |
| PR修正 | 修正 | 7200秒 | `PR_FIX_APPLY_STEP_TIMEOUT_SEC` | Claude 2回分と余裕が収まる |
| PR修正 | 検証 | 21600秒 | `PR_FIX_VERIFY_STEP_TIMEOUT_SEC` | 検査コマンドの2周とClaude 2回分が収まる |
| PR修正 | 完了 | 5400秒 | なし | 個別の見積もりは無い |

準備のロックの待ちは、factory cloneとリポジトリのロックの待ち(1回300秒、最大3回)である。定数は`f/factory/steps/pr_workflow_support.ts`にある。上限を上げるときは、`flow.yaml`と定数を同じ変更で上げる。`tests/scripts/pr_flows.test.ts`が両者の一致を確かめる。

### 時間設定の確認

Claudeは`claude_timeout_sec`で打ち切り、不正な出力の後に1回だけ再試行する。そのため、Claudeは1つのステップで`claude_timeout_sec`まで2回走りうる。各式の15秒は、Claude 1回か検査コマンド1件が打ち切りの後に上乗せしうる停止と出力待ちの時間である。600秒は、GitHub API、git、DBの操作の余裕である。

| ステップ | 見積もり | 収まらないとき |
| --- | --- | --- |
| PRレビューの生成 | 2 × (`claude_timeout_sec` + 15) + 600 | Claudeを起動せず、人の対応待ちにする |
| PR修正の修正 | 2 × (`claude_timeout_sec` + 15) + 600 | 準備でworktreeに触れずにブロックにする |
| PR修正の検証 | (2 + 2 × 検査コマンド数) × (`claude_timeout_sec` + 15) + 600 | 準備でworktreeに触れずにブロックにする |
| CI回の修正 | 2 × (`claude_timeout_sec` + 15) + 5 × 135 + 600 | 準備でworktreeに触れずにブロックにする |
| CI回の検証 | (2 + 2 × 検査コマンド数) × (`claude_timeout_sec` + 15) + 6 × 135 + 2 × 75 + 4 × 345 + 600 | 準備でworktreeに触れずにブロックにする |

検証の見積もりは、検査コマンドがあるときだけ確かめる。検査コマンドが無ければ、検証のステップは検査とClaudeを実行しない。

既定値では、生成と修正の見積もりは4230秒である。`claude_timeout_sec`は3285秒まで収まる。PR修正の検証は、既定値なら検査コマンド4件まで収まる。

CI回の式の135秒は、gitleaks 1回のタイムアウト120秒と停止の15秒である。
修正の5回は、抜粋の4回と出力の1回である。
検証の6回は、再実行の5回と、止める理由の検査の1回である。
75秒は、gitの1回のタイムアウト60秒と停止の15秒で、検査コマンドの後の`git clean`が2回ある。
345秒は、変更を読む1回の上限で、読む時間の上限120秒と、上限を超えた時点で実行中のgit 3回分の225秒である。
変更を読むのは4回ある。
ファイルごとにgitを実行するので、時間の上限が無いと、1回の読み取りがステップのtimeoutを超えうる。
CI回は、通常の回の確認に加えて、この2つも確かめる。
既定値では、CI回の修正は4905秒で、`claude_timeout_sec`は2947秒まで収まる。
CI回の検証は、既定値なら検査コマンド4件まで収まる。

PR修正で時間設定を確かめるのは準備のステップだけである。そのため、PR修正の実行中は時間設定を変えない。

### Windmillの再試行

PRレビューの生成とPR修正の修正のステップには、Windmillの再試行(`attempts: 2`)がある。

- PRレビューの生成は、timeoutで打ち切られた後に再試行されうる。読み取り専用のClaudeが2回目も起動し、費用がかかる。
- PR修正の修正も、timeoutで打ち切られた後に再試行されうる。打ち切られたClaudeがworktreeのロックを持ったままなら、再試行はロックを取れずにすぐ失敗する。

### Windmillのtimeoutで打ち切られたとき

打ち切られたステップが起動したClaudeや検査コマンドは残り、作業項目は失敗(`failed`)になる。残ったプロセスがworktreeを使っている間は、再実行しても準備のステップがブロックにする。

### rate limitを待てないとき

GitHub APIのrate limitの扱いは[通知](notifications.md)に書く。PRワークフローのステップで解除を待てないときの挙動は次のとおりである。

| ステップ | 挙動 |
| --- | --- |
| PRレビューの準備 | `GitHubRateLimitError`で失敗し、作業項目は失敗になる |
| PRレビューの投稿 | レビューを投稿する前なら、投稿せずに失敗する |
| PR修正の準備と収集 | `GitHubRateLimitError`で失敗し、作業項目は失敗になる |
| PR修正の完了 | pushの前なら、pushせずに失敗する |

PR修正の完了のステップで、pushの後のGitHub APIの呼び出しは、失敗しても続けるものと、ステップを失敗させるものに分かれる。

| 呼び出し | 失敗したとき |
| --- | --- |
| Issue化の提案のスレッドの取得 | 警告を残して続ける |
| 返信の投稿 | 警告を残して続け、noticeの`fix_reply_post_failed`を1件残す |
| 再レビューの依頼 | noteを残して続ける |
| 再レビューの依頼の前のPRの取得(`getPr`) | 再レビューの依頼の失敗として扱い、noteを残して続ける |

`fix_reply_post_failed`には、失敗した件数、`review_comment_id`、最初のエラーを載せる。Discordには通知しない。

### rate limitで止まったPRレビューの扱い

rate limitで止まったPRレビューは、自動の再開の対象にしない。
人が解除を待ってから、`retry_work_item`で再開する。
`failed`になった作業項目は`job_failed`の通知で人に届き、次の操作に解除を待ってから再実行することが載る。
対象にしない理由は次のとおりである。

- 待ちの長さを決められない。
  `GitHubRateLimitError`のメッセージには解除までの待ちの秒数が載り、`on_error_flow`が作業項目の遷移の注記に渡す。
  ただし、待ちは注記の文にしか無く、構造化されていない。
  解除の時刻のヘッダーが無いときは、秒数も載らない。
  自動の再開の待ち(5分、15分、45分)は、解除の時刻と無関係である。
- 解除の前に再開すると、同じ制限に当たって回数を使い切りうる。
  5分、15分、45分の累計は約65分で、一次レート制限の解除は最大で1時間後になる。
  PRワークフローとポーリングが同じ認証で制限を共有するためである。
  5xxは再開のたびに成否が独立するので、回数と待ちの伸長で足りる。
- 届く条件が狭い。
  `callGhApi`は120秒までの待ちを済ませて再試行するので、1回の待ちで解けるrate limitは作業項目まで届かない。
  届くのは、[待てないときの失敗](notifications.md#待てないときは失敗する)の3つの場合だけである。
  必要な待ちが120秒を超えるとき、待って再試行してもまた拒まれたとき、GraphQLの一次レート制限に当たったときである。
- 実機では、rate limitによるPRレビューの失敗を確認できていない。
  確認できた失敗の記録(Windmillに残る最古の失敗から数えた失敗ジョブ102件)に、rate limitの文言は0件である。
  頻度は観測されておらず、解除までの待ちの実測もない。
  人の再実行が定常の作業になっていない、というのは推論である。

次の条件を満たしたときは、対象にすることを再検討する。
`factory.job_failures`の`error`に`GitHub rate limit on`を含むPRレビューの失敗が、1か月に3件を超えたときである。
`on_error_flow`が、失敗のたびにこの表へエラーのメッセージを記録する。
3件は目安であり、再実行の手間が重くなる件数に合わせて見直す。
その場合は、注記の待ちの秒数を構造化して読めるようにし、解除の時刻を過ぎてから、待ちの上限を置いて再開する。

## 再実行と中断

`retry_work_item`は、失敗、人の対応待ち、ブロックのPR修正の作業項目を再実行できる。ただしCIの失敗を直す回は除く([CIの失敗を直す回](#ciの失敗を直す回))。watermarkはpushの成功か差し戻しでしか進まないので、それ以外の終わり方から再実行すると、前回と同じフィードバックを集め直す。
同じPRに終了していない別のPR修正があるとき、止まったPR修正は再実行できない。
`retry_work_item`は、進行中の作業項目のIDを示して断り、進行中のものに従わせる。
再実行は部分一意インデックスに阻まれるためである。
同じPRに終了していない別のPR修正があるPR修正は、自動の再開でも候補と比較交換の両方から外し、見送る。
headがforkのPRのレビューが`blocked`になったときは、再実行すると、準備のステップが同じ理由でまた止め、Discordにも再通知する。PRを同一リポジトリのブランチから出し直す。

人の対応待ちとブロックの通知の次の操作は、修正のどこで止めたかで分ける(`nextAction`に渡すフロー`pr_fix`)。

| 止めたところ | 例 | 次の操作 |
| --- | --- | --- |
| 修正の前(準備のステップ) | PRがドラフト、親のIssueかブランチの実装フローが実行中、worktreeの使用中、時間設定 | `retry_work_item`で同じ作業項目を再実行する |
| 修正の後 | 要件定義への差し戻しの見送り、commitしたツリーが検査したツリーと違う、秘密情報の検査の後にworktreeが変わった、worktreeのHEADが動いた | `factory:fix`を付け直す |
| CI回で止めた、保留の理由に写せる理由(CI回が作る理由は`ci round`で始まる。通常の回と共通の理由はそのまま通る) | ログを読めない、直せない種類のジョブ、スキルにマーカーが無い | 保留の理由ごとの敬体の固定文(`prCiFixHoldInfo`の`stopAction`) |
| CI回で止めた、写せない理由 | 秘密値の検査に当たった、許可されない変更 | 原因を確かめて直し、PRにpushする |
| CI回で止めた、人が取る手順がある理由 | PRがドラフト、PRのauto-mergeが有効 | 手順を残して待つ(ドラフトなら「ドラフトを解除してから、保留が解けるまで待つか、PRにpushしてください」) |

修正の前に止めたときは、修正のラウンドを使っていない。
`factory:fix`を付け直すと新しい作業項目で修正のラウンドを1つ使うので、同じ作業項目のまま再実行させる。
修正の後に止めたときは、修正のClaudeを実行してそのラウンドを使い終わっているので、新しいラウンドとして付け直させる。
CI回では、再実行と付け直しのどちらも案内しない。
作業項目を再実行しても、付け直しても、失敗の行は動かないためである。
人が基盤を直す手順がある理由は、手順を残し、再実行の部分だけを差し替える。
手順がある理由は、worktreeの使用中、検査の枠の記録の片付け、workerのイメージが古い、検査コマンドが残したプロセスなどである。
差し替える案内は、保留の理由が一時的な理由(ドラフト、auto-merge)なら「保留が解けるまで待つか、PRにpushしてください」である。
待った後にFactoryが何かを始めるとは書かない。
イメージが古い理由は、保留の理由ではない。失敗の行が止まってから24時間後に保留なしで戻ることと、待てないときはPRにpushすることを案内する。
時間設定が合わない理由は、設定を減らす案内に、直すと次の巡回でpushなしに自動で起動し直すことを添える。起動の前にwatcherが同じ設定を確かめて保留するためである。
許可リスト外のリポジトリの理由は、設定を見直す案内に、直すと次の巡回で起動し直すことを添える。最初に失敗を見てから24時間たった行は閉じるので、その場合はPRにpushする案内も添える。
それ以外の理由なら「PRにpushしてください。headが変わると、Factoryが新しい失敗として判定し直します」である。
手順が無い理由は、保留の理由に写せればその敬体の固定文を使う。
写せなければ、原因を確かめて直し、PRへpushする案内を使う。

PR修正の準備は、worktreeを使っているプロセスがいても何も止めない。同じPR修正の前の実行のプロセスでも止めない。PR修正は実装フローのリースを持たないので、保持者が終わった実行の生き残りだと言えないためである。保持者を理由に載せてブロックにする。
人は、載ったプロセスが終わるのを待つか、workerのコンテナで止めてから、`retry_work_item`で再実行する。
workerの再起動は同じworkerのすべてのジョブを止めるので、載ったプロセスを止められないときだけにする。

PRレビューとPR修正の作業項目は、`retry_work_item`で再起動した後も`listTrackedPrs`の追跡の対象であり続ける。

### 一時的な失敗の自動の再開

準備か投稿のステップがGitHubの一時的な失敗で落ちると、`pr_review`の作業項目は`failed`になり、遷移の注記に`github_transient:`で始まる失敗の文が残る。
`auto_retry_pr_review`が5分ごとに、次の条件をすべて満たす作業項目を探す。
見つけた作業項目は、`retry_work_item`と同じ遷移で`reviewing`に戻し、`f/factory/pr_review`を起動する。
ラベルは付け直さない。付け直すと新しいサイクルになり、付与者の許可の判定も通り直すためである。

- 種類が`pr_review`で、状態が`failed`である。
- `failed`へ移った最新の遷移の注記が`github_transient:`で始まる。
- その遷移から、これまでの再開の回数に応じた待ちが過ぎている。待ちは1回目が5分、2回目が15分、3回目が45分である。GitHubの障害が続く間に回数を使い切らないためである。
- 注記が`auto_retry:`で始まる遷移(これまでの自動の再開)が3回未満である。上限は`AUTO_RETRY_MAX_RESTARTS`で、イメージが古くて止まった作業項目の自動の再開と共有する。
- 同じPRに、`id`の大きいPRレビューも、終了していない別のPRレビューも無い。
- 記録済みのflowジョブが動いていない。

待ち、回数、理由は、候補の選択、比較交換、再開の見送りの判定が同じ値を使う(`transientReviewQuery`)。
状態の交換は、理由、回数、待ちを条件に含む比較交換である。人が先に`retry_work_item`で再開した作業項目や、別の実行が先に再開した作業項目は、条件に合わず再開しない。
許可リストは注記の先頭の`github_transient:`だけである。ほかの理由で止まったPRレビューは、人が`retry_work_item`で再開する。
再開したレビューは、同じ`review_sha`の投稿済みのレビューを探してから投稿するので、5xxの応答の裏でレビューが投稿されていても二重にならない。
フローを起動できなかったときは、作業項目を一時的な失敗の印を付けた注記で`failed`に戻す。
起動に失敗した再開も、再開の遷移で1回に数える。
戻した作業項目は再開の候補に戻り、回数を使い切れば巡回が`needs_human`で知らせるので、別の通知を送らない。
使い切りの通知は、起動の失敗ではGitHubの障害と書かず、次の操作をWindmillの状態の確認にする。

印を付けるのは、GitHubの5xxと、応答の無い失敗(状態0)である。
状態0のうち、`gh`が認証を求めて終わったもの(終了コード4)は、同じ入力で必ず落ちるので、印を付けない。
timeoutで打ち切られたものは、一時的として印を付ける。
それ以外の状態0は、通信断と`gh`のほかの失敗を見分ける情報が例外に無いので、まとめて一時的として扱う。
落ち続けるものは、回数の上限と待ちの伸長で打ち切り、使い切ったときに人へ知らせる。
4xxや応答の形の不一致には印を付けないので、自動では再開しない。

再開の回数は、作業項目ごとの累計である。人が`retry_work_item`で再開しても戻さない。
自動の再開を使い切った作業項目を、人が再開した後に同じ失敗が続いたとき、自動の再開を繰り返さないためである。

再開の状態交換は`flow_job_id`を空にし、起動したジョブのIDは空のときだけ記録する(`setFlowJobIdIfUnset`)。
記録までの間、reconcileが終わった前のジョブを見て孤児と判定せず、未記録として猶予を待つためである。
フローを起動できずに戻すときの注記は、印の次に`auto_retry_launch_failed:`を置き、`auto_retry:`で始めない。
再開の遷移がすでに1回に数えられており、戻した遷移で二重に数えないためである。

失敗を記録する処理(`on_error_flow`)は、作業項目を`failed`にできたときだけ、印の付いた失敗に`job_failed`を出さない。
`failed`にできなかったときと、同じPRに置き換えた行か並走するPRレビューがあるときは、巡回の一覧に載らず誰にも届かないので、`job_failed`を出す。
失敗の記録(`job_failures`)はどちらも残す。
通知を巡回に任せるのは、再開と、再開できなかったときの通知を、巡回の1か所に集めるためである。
巡回が候補を取得できないときは、握りつぶさず、スケジュールの失敗として`on_error_schedule`から人に届ける。

巡回は、次の作業項目を`needs_human`で知らせる。

- 再開の待ちに猶予の30分を足しても、再開されないまま残っているもの。記録済みのジョブの状態を読めない状態が続く場合などである。
- 自動の再開を使い切ったもの。待ちを置かず、次の巡回で知らせる。対象のPRのリンクと、`retry_work_item`を作業項目のIDで実行する次の操作を載せる。

通知は、送信の結果が`sent`のときだけ、`failed`から`failed`への遷移として注記`auto_retry_stalled:`に記録する。
届かなかった(送れなかった、レート制限の待ちが上限を超えた、例外になった)作業項目は記録が残らないので、次の巡回で送り直す。
記録に失敗したときも送り直すので、重複することはあっても、黙ることは無い。
通知が遅れる最大は巡回の間隔の5分で、届くまで5分ごとに繰り返す。
Discordの送信先が未設定のときは、知らせる先が無いので記録せず、情報のログだけを残す。警告は出さない。

次の限界がある。見送りの検出は同じ巡回の中にあるので、スケジュールが無効になっているときは届かない。
記録済みのジョブが消えている(404)作業項目は、終わったものとして再開する。
状態を読めない(404以外の失敗)作業項目は再開を見送られるが、一覧には残る。
一覧は50件ずつIDの昇順に読む。見送られた行が先頭の50件を占めても、最後のIDより後ろを次のページとして読み、後ろの再開すべき行に届く。
再開の数の上限に達したら、残りのページは読まない。
見送りの通知の一覧も同じように読む。
1回の巡回で読むのは10ページまでである。巡回を有限にするためで、上限で打ち切ったときは警告のログを残す。上限より後ろの行には、前の行が片付くまで届かない。
GitHubのレート制限(`GitHubRateLimitError`)は、5xxと通信断のどちらにも当たらないので、自動の再開の対象にしない。
理由は[rate limitで止まったPRレビューの扱い](#rate-limitで止まったprレビューの扱い)に書く。

総評に移した[MUST]の指摘は、スレッドにならないので、再レビューの未解決の[MUST]の数には入らない。
これは行に紐づけられなかった指摘と同じである。
一方で、結果の判定(`reviewResultFor`)は今回の指摘の種類を直接読むので、通知は要修正になる。
PR修正も、レビューの本文を修正の入力として集めるので、総評の指摘を扱う。

### 再開で生成をやり直す費用

自動の再開は、前の回の生成結果(指摘の下書き)を再利用せず、準備から生成、投稿までをやり直す。
再利用しない理由は、費用の増え方が小さく、再利用の実装が大きいためである。

費用が増えるのは、投稿のステップがGitHubの一時的な失敗で落ちたときだけである。
準備のステップで落ちたときは、Claudeを起動する前なので、生成の費用は増えない。

#### 費用の上限

上限は、Claude 1回の起動と、フロー1回の生成に分ける。

| 単位 | 上限 | 内訳 |
| --- | --- | --- |
| Claude 1回の起動 | 5USD、30分 | `max_budget_usd_per_run`(既定5USD)と`claude_timeout_sec`(既定30分)。モデルは`heavy_model` |
| フロー1回の生成 | 起動4回、最大20USD | 不正な出力の再試行が起動1回を足し、Windmillの再試行(`attempts: 2`)が生成のステップを最初からもう1回走らせる。2 × 2回である |
| 1つの作業項目の自動の再開 | 3回(`AUTO_RETRY_MAX_RESTARTS`) | 追加の費用は最悪で3 × 4 × 5 = 60USD |

不正な出力の再試行は、`runClaude`が出力の形か内容の検査で不正と判定したとき、新しい試行を1回起動する。
`pr_review_generate`は再試行の前の確認(`beforeRetry`)を渡さないので、再試行は無条件である。
`--max-budget-usd`は試行ごとに渡るので、1回の生成の費用は5USDの2倍まで増えうる。
Claudeが1つのステップで最大2回走りうることは、[時間設定の確認](#時間設定の確認)にも書く。
Windmillの再試行は、ステップの`main()`を先頭から走らせるので、日次予算の検査も起動のたびに通る。
再開した生成の費用は`factory.agent_runs`に記録され、日次予算(`daily_budget_usd`、既定50USD)に数えられる。

#### 許容の根拠

最悪の60USDは、既定の日次予算の50USDを超えうる。
それでも許容するのは、次の2点のためである。

- 最悪値はほぼ起きない。
  起きるのは、投稿のステップがGitHubの5xxか通信断で落ちる再開に限られる。
  そのうえで、生成が不正な出力になり、Windmillの再試行でも不正な出力になり、再開が3回とも重なる必要がある。
  通常は、再開1回の追加が起動1回の5USD以下である。
- 日次予算の検査が各起動の前にあるので、日次予算に達した後は、新しい生成を起動しない。
  日次予算を超える幅は、起動済みの1回のフローの分(最大20USD)までである。

実際の再開の頻度は計測していない。
上の判断は、設定値から求めた構造上の上限にもとづく。

#### 頻度の確認

再開が多いかは、`pr_review`の実行を作業項目ごとに数え、各作業項目の2回目以降の起動の費用を日ごとに合計して確かめる。

```sql
SELECT day, sum(cost_usd) AS extra_cost_usd
FROM (
  SELECT
    created_at::date AS day,
    cost_usd,
    row_number() OVER (PARTITION BY work_item_id ORDER BY created_at, id) AS run_no
  FROM factory.agent_runs
  WHERE stage = 'pr_review'
) AS runs
WHERE run_no > 1
GROUP BY day
ORDER BY day DESC;
```

この集計の2回目以降には、自動の再開のほかに、不正な出力の再試行とWindmillの再試行で起動した分も入る。
不正な出力の再試行で捨てた試行(`discardedAgentRun`)の行も記録されるので、集計に入る。
再開の費用だけを見たい場合は、集計より多めの値になる。

#### 再利用を入れない理由

| 理由 | 根拠 |
| --- | --- |
| 生成結果の保存先が無い | 生成のステップの出力はWindmillのジョブの結果にだけ残る。`factory.agent_runs`は費用と回数だけを持ち、`factory.reviews`は投稿の後にしか書かない。再開は`flow_job_id`を空にして新しいジョブを起動するので、前のジョブの結果へ辿る手がかりも残らない。 |
| 保存の実装が大きい | 保存には、新しい表、移行、古い行の削除が要る。 |
| 再利用の条件が多い | プロンプトは、PRの本文、未解決のスレッド、要件定義のドラフト、CI回の印を含み、再開の間に変わりうる。head sha、プロンプト全文、スキルの内容、モデル、出力スキーマのすべてが一致するときだけ使える。見落とすと、古い指摘を新しい差分に投稿する。 |

#### 見直しの基準

上の集計の`extra_cost_usd`が、日次予算の1割(既定で5USD)を超える日が続くときは、再利用を入れる。

## 安全策の実装

PR修正はClaudeに書き込みのツールを渡すので、次の安全策を持つ。実装フローと共通の仕組みは[実装フロー](implement.md)にも書く。安全策を変えたときのE2Eの検証は、本番のIssueやブランチではなく、捨てるブランチとPRで行う。

### Claudeに渡すツールの制限

PR修正のClaudeに渡すツールは`Read,Glob,Grep,Edit,Write`だけで、`Bash`は渡さない。起動のオプションは次のとおりである。

| オプション | 目的 |
| --- | --- |
| `--permission-mode dontAsk` | 確認なしで実行する。`Edit`と`Write`を拒否する既定の動作を上書きするため |
| `--allowedTools Edit Write` | `Read`、`Glob`、`Grep`に加えて、`Edit`と`Write`だけを許可する |
| `--restricted` | `Bash`などのコードを実行するツールと`WebFetch`を外し、ファイルのツールを作業ディレクトリ(`--add-dir`を含む)に閉じる |

`--restricted`はネットワークを遮断しない。PRレビューのClaudeには、読み取り専用のツールだけを渡す。

### 検査コマンドの実行

対象リポジトリの検査(lint、typecheck、testに当たるもの)は、Claudeではなく検証のステップが実行する。実行するのは`factory_config.allowed_check_commands`に書いたコマンドで、例えば`["mise run check"]`である。結果は、Claudeの2回目の実行(修正)への入力にする。

検査コマンドは、対象リポジトリのコードをworkerのコンテナ内で、非特権のユーザー(`factory-check-N`)として実行する。
コンテナとnetworkは分けない。別のコンテナでnetworkなしに動かせるまで、既定値の`[]`を保つ。
空でなければ、実行する作業項目ごとにnoticeの`unsandboxed_check_commands`を記録する。
同じ本文の未解決のnoticeがあれば新しく作らない。作成から1日を過ぎていれば、時刻を更新する。

検査コマンドには、許可リストの環境変数だけを渡し、workerの環境変数は引き継がない。
許可するのは、固定の`PATH`、実行ごとに作る非公開の`HOME`とその下の`TMPDIR`、`LANG`、worktreeだけを`safe.directory`にするgitの設定である。
実行の前に、空いている枠を取って前の実行の残りを片付け、枠の記録を書いてから、worktreeと`HOME`の所有者をその枠のユーザーにする。
実行の後は、所有者をrootに戻してから`HOME`のディレクトリを消し、共有の一時ディレクトリから枠のユーザーのものを消して、枠の記録を消す。
コマンドごとに、枠のユーザーの残りのプロセスを止める。止まらなければ、所有権を戻さずにステップを失敗させる。
戻せなかった所有権と`HOME`は、枠の記録を通して、次にその枠を取る検査が片付ける。

準備のステップは、`allowed_check_commands`を設定していれば、Claudeより前に、イメージと実行時の前提([検査コマンドの権限](../security.md#検査コマンドの権限))を確かめる。
満たさなければ、関門と同じ`guard_blocked`で止め、作業項目は`blocked`になる。
前提を満たさないまま進むと、Claudeの修正を1回使ってから検証で止まるためである。
検証のステップも検査の前に確かめ直し、満たさなければClaudeの修正を再実行せずに`guard_blocked`を返す。
準備から検証までの間に、イメージも稼働中のworkerも変わりうるためである。
完了のステップが、commitの前に残った所有権を同じ理由で取り戻せずに止まったときも、`blocked`にする。
どれも修正のラウンド(`fix_rounds`)を記録しない。
Claudeが直せる検査の失敗ではないので、Sonnetの失敗として数え(`countPrFixFailures`)、`heavy_model`への切り替えを早めないためである。
理由と要対応の通知は、原因によって次のとおりである。

| 原因 | 理由の先頭 | 要対応の通知 |
| --- | --- | --- |
| イメージが古い | `worker image is stale: run mise run up` | `host_action_required`([運用](../operations.md#fとworkerのイメージを両方変えたとき)) |
| 稼働中のworkerの問題 | `worker runtime is unsafe for checks:` | `check_runtime_unsafe`([運用](../operations.md#稼働中のworkerが検査の前提を満たさないとき)) |

イメージが古く、稼働中のworkerの問題も一緒に見つかったときは、両方の通知を残す([Consoleのnotice](notifications.md#consoleのnotice))。
`host_action_required`は`mise run up`の後に自動で解決されるが、ボリュームのマウントポイントは作り直しでは閉じないためである。
イメージが古くて止まった`blocked`は、通知の自動の解決の後に、自動で`fixing`へ戻って再開する([実装フロー](implement.md#イメージが古くて止まったとき))。
CIの失敗を直す回は除く([CIの失敗を直す回](#ciの失敗を直す回))。

`PATH`の値と、workerの値を使わない理由、uidの切り替えと所有権の受け渡しは、[検査コマンドはフローが実行する](../security.md#検査コマンドはフローが実行する)と[検査コマンドの権限](../security.md#検査コマンドの権限)にある。

検査コマンドが指す先(対象リポジトリの`mise.toml`や`package.json`のscriptsなど)は、信頼できない内容として扱う。workerのmiseは対象リポジトリの`mise.toml`をtrustしない(`mise --yes trust`をしない)。`mise.toml`に頼るコマンドと、`MISE_TRUSTED_CONFIG_PATHS`を使わずには実行できないコマンドは、実行せずにブロックとして報告する。

検査コマンドは1件ずつ`claude_timeout_sec`で打ち切る。出力の扱いは[実装フロー](implement.md)の[検査コマンドの出力の上限](implement.md#検査コマンドの出力の上限)と同じである。

### 禁止パスによる停止

修正の差分に次のどれかが含まれると、検証のステップが止める結果を返す。作業項目は人の対応待ちになる。

- `.claude/`、`.agents/`、`.github/workflows/`、`.github/actions/`、`.mise/`、`.config/mise/`、`.lefthook/`の下のファイル
- `console/public/`、`infra/console_fetcher/`の下のファイル
- 個別のファイル(一覧は下の説明を参照)
- `mise.toml`、`mise.*.toml`、`.mise.toml`
- `lefthook.yml`、`lefthook-local.yml`、`lefthook.toml`、`lefthook.json`
- `bunfig.toml`、`.npmrc`、`.gitattributes`、`.gitmodules`
- markdownlintとmarkdownlint-cli2の設定(`.markdownlint.*`と`.markdownlint-cli2.*`。拡張子は`jsonc?`、`ya?ml`、`[cm]?js`)
- textlintの設定(`.textlintrc`と`.textlintrc.*`)
- `package.json`の`scripts`の変更
- 新しく追加した`*.sh`

一覧の本体は、`f/factory/lib/protected_paths.ts`の次の3つの定数である。

- `FORBIDDEN_PATH_PREFIXES`
- `FORBIDDEN_EXACT_PATHS`
- `FORBIDDEN_BASENAME_PATTERNS`

`steps/pr_workflow_support.ts`が判定の関数を再exportして使う。
実装フローが記録だけに使う一覧(`IMPLEMENT_PROTECTED_PATH_PREFIXES`など)は別の定数で、PR修正の判定には使わない。

ディレクトリは、リポジトリのルートからの相対パスの前方一致で判定する。個別のファイルは、ルートからの相対パスの完全一致で判定する。ファイル名の一覧は、ディレクトリを問わずファイル名で判定する。

`console/public/`と`console/index.html`は、Consoleでバンドルを通らずにそのまま配信され、ページの中で動く。
`console/index.html`はファイル名だけではほかの`index.html`と区別できないので、パスで判定する。
個別のファイルの一覧は、`FORBIDDEN_EXACT_PATHS`にある。
一覧には、次の9種類が入る。

- Consoleのページの入口: `console/index.html`
- draw.ioのビューアの固定: `console/drawio-viewer.json`
- 固定を書き換えるPRを作る側: `f/factory/drawio_viewer_bump*`と、それが使う`f/factory/lib/`の3ファイル
- 固定を強制し、配信物を作って検査する側: `console/scripts/`の一部、`console/vite.config.ts`、`scripts/check-console-lockfile.ts`
- 配信の設定: `infra/Caddyfile`
- 図を隔離して描くiframeの検査: `tests/lib/drawio_frame_isolation.test.ts`
- CIの実行の範囲を決める側: `scripts/ci-scope.ts`
- CIが出すメタデータのパッチを取得して検査する側: `f/factory/lib/metadata_patch_*.ts`の6つと、それぞれの`.script.yaml`、`.script.lock`
- hashの再計算の側
  - 部品: `lib/metadata_{hash,precheck,signature,git_ports}`の`.ts`、`.script.yaml`、`.script.lock`
  - 配線: `lib/ci_metadata_rehash`の`.ts`、`.script.yaml`、`.script.lock`

`console/drawio-viewer.json`は、CIが取得して配信するビューアの取得元とsha256を固定する。
書き換えられると、別のスクリプトが固定の値として配信される。
固定を書き換えるPRを作る側は、書き換えられると、人の確認なしに別の版や取得元を固定するPRを作れる。
固定を強制する側のスクリプトは、書き換えられると、検査をすり抜けた内容が配信物に混ざる。
`scripts/ci-scope.ts`は、書き換えられると、検査のジョブを黙って飛ばせる。
`f/factory/lib/metadata_patch_*.ts`は、パッチの取得先とトークンの渡し先、zipの読み方、パッチに載せてよい内容を決める。
書き換えられると、パッチの受け取り側の検査が緩む。
hashを再計算する4つの部品は、hashの算法、再計算してよい条件、`main`の引数の比べ方、検査が読むオブジェクトの取り方を決める。
書き換えられると、依存が変わるPRや、入力のスキーマが変わるPRのlockを、人の確認なしに書き換えさせられる。
`lib/ci_metadata_rehash`は、`wmill-lock.yaml`だけの変更を許す条件と、書き込み先を決める。
書き換えられると、再計算と一致しないlockを、検査を通してpushさせられる。
例外を開くコールバックの本体(`steps/pr_fix_verify.ts`と`steps/pr_fix_finish.ts`)と`lib/ci_fix_round.ts`は、一覧に入れない。
日常的に直すファイルで、入れるとその正当な変更を止めるためである。
これらを書き換えて例外の条件を緩める変更は、マージ前の人のレビューで止める。
`infra/Caddyfile`には、Consoleのscriptの許可と、draw.ioの図を隔離するCSPがある。
`infra/console_fetcher/`は、配信物を検証して配信する。
どちらも書き換えられると、検証や隔離をすり抜けた内容が運用者のブラウザで動く。
図を隔離して描くiframeの検査は、書き換えられると役目を果たさなくなる。
sandboxを外したり、別のページをiframeに読ませたりしても、検査を通るためである。

markdownlint-cli2の設定は、`customRules`、`markdownItPlugins`、`modulePaths`で任意のモジュールを`import()`できる。
textlintの設定は、`rules`の名前からモジュールを解決して読み込む。
どちらもpre-commitの文書の検査と`mise run check`が読むので、書き換えられると、人の手元とCIでコードを実行される。

### 変更パスの取得

変更パスは、次の2つの和集合で取る。

```bash
git status --porcelain -z --untracked-files=all --ignore-submodules=none
git diff --name-only -z
```

symlinkのモード(`git ls-files -s -z`)と差分の行数(`git diff --numstat -z`)も、NUL区切りで読む。引用符付きのパス(非ASCII文字や制御文字を含むもの)でも、禁止パス、symlink、差分の大きさの判定を素通りしない。

未追跡のディレクトリは`dir/`の1件にまとめず、中のファイルを1件ずつ判定する。そのため、まだ無い`.github/`の下に作ったworkflowも止める。renameは新しいパスと元のパスの両方を判定するので、禁止パスへの移動も、禁止パスから外への移動も止める。

symlinkのモードを引くときは`--literal-pathspecs`でパスを文字どおりに渡す。`*`や`[`を含む名前を、別のファイルに一致させないためである。

### symlinkと特殊なファイルの検出

main cloneのconfigには`core.symlinks=false`を書いておく。
このモジュールが実行するgitには、`-c core.symlinks=false`も付ける。
`-c`は`.git/config`や`config.worktree`より優先されるので、検査コマンドがそこで`true`に戻しても、このモジュールのgitには効かない([セキュリティ](../security.md)の「gitが読む設定を限る」)。
configに書いた値は、このモジュールを通さずにClaudeや検査コマンドが実行するgit向けの既定である。
PR修正の検証は、symlinkの新規作成(未追跡のものを含む)、変更、削除、typechangeで止める結果を返す。symlinkは次の3つで探し、どれかで見つかれば止める。

| 探し方 | 見つけるもの |
| --- | --- |
| 索引のモード(`git ls-files -s -z`) | 追跡しているsymlink |
| 削除以外の変更パスの`lstat` | 検査コマンドが作ったものなど、未追跡の新しいsymlink |
| `git diff --raw --no-renames -z --ignore-submodules=none HEAD`のモード | 通常のファイルとして置かれた追跡済みのsymlink |

`core.symlinks=false`のworktreeでは、追跡済みのsymlinkが通常のファイルとして置かれる。その中身を書き換えると指す先が変わるのに、`readlink`と`lstat`はsymlinkと報告しない。そのため、HEADと作業ツリーのモードも比べる。変更、削除、typechangeを含む。

検証のステップは、次の変更パスでも止める結果を返す。

- 末尾が`/`のパス(`git status`が未追跡の入れ子のリポジトリを`dir/`の1件にまとめたもの)
- 要素が`.git`のパス(大文字と小文字を区別しない)
- HEADと作業ツリーの`git diff --raw`で、古いか新しいモードがgitlink(`160000`)のパス。サブモジュールのディレクトリを消したgitlinkの削除も止める。
- 削除以外の変更パスのうち、`lstat`が通常のファイルとsymlinkのどちらでもないもの(ディレクトリ、FIFO、デバイスなど)

パスが無い以外の理由で`lstat`が失敗したときは、検証を失敗させる。これらとsymlinkのどれかで止めるときは、`package.json`の中身と差分の行数を読まない。symlinkの先やFIFOを読まないためである。

### 変更を調べる時点

検証のステップは、変更の一覧と上の判定を次の時点で行う。

- Claudeの実行の後
- Claudeの再実行の後
- 検査コマンドが通った後(1回目の検査が通ったときと、再実行の後の2回目の検査の後)

判定するのは、禁止パス、symlink、入れ子のリポジトリ、通常のファイルでないもの、`package.json`のscripts、差分の大きさである。`allowed_check_commands`は対象リポジトリのコードなので、保護パスのファイルやsymlinkを作りうる。そのため、検査コマンドの後にも調べる。

### HEADとブランチの確認

検証のステップは、変更を調べる前に毎回、次の2点を確かめる(`checkHead`)。違えば止める結果を返す。

- worktreeのHEADが、準備のステップが見たPRのhead(`head_sha`)である。
- `git symbolic-ref HEAD`が`refs/heads/<PRのheadブランチ>`である。

検査コマンドがローカルでcommitやブランチの切り替えをすると、HEADを基準にした変更の一覧から、そのcommitの変更が消えるためである。準備のステップの結果に`head_sha`か`branch`が無いときも止める結果を返す。

### worktreeの.gitの検証

worktreeの`.git`の書き換えを止める。参照先を別のディレクトリに向けると、そこに置いた`config`のfilterやfsmonitorなどを、次のgitがrootで実行するためである。Claudeが起動するときに実行するgitも含む。検証の仕組みは[実装フロー](implement.md)の[worktreeの.gitの検証](implement.md#worktreeのgitの検証)と同じである。

PR修正の各ステップは、次のように確かめる。

| ステップ | 確かめる時点 | 違うとき |
| --- | --- | --- |
| 準備 | worktreeを用意した直後に`.git`を1回だけ読み、検証して記録する | 例外 |
| 修正 | Claudeを起動する前 | Claudeを起動せずに止める結果を返す |
| 修正と検証 | Claudeの不正な出力への再試行の前 | 再試行しない |
| 検証 | 変更を調べる前と、検査コマンドの後にClaudeを再実行する前 | gitとClaudeのどちらも実行せずに止める結果を返す |
| 完了 | commitの前 | commitせずに人の対応待ちにする |

準備のステップは、記録した中身(`worktree_git_pointer`)を修正、検証、完了のステップに渡す。前回の実行が書き換えたまま残した`.git`を信頼しないよう、検証した1回の読み取りをそのまま記録する。

修正のステップが、違うときに例外を投げず止める結果を返す理由は、例外だとフローの再試行がClaudeを起動し直すからである。再試行の前の確かめが失敗したときも、再試行しない。最初の試行の記録(費用)はそのまま残す。確かめが例外を投げたときは、秘密を伏せたメッセージを最初の失敗の詳細に足し、原因を追えるようにする。

Claudeの実行が失敗で終わったときは、修正と検証のステップが`.git`を確かめ直す。書き換えられていれば、Claudeの失敗ではなく`.git`の書き換えを理由として止める結果を返す。

準備のステップの結果に`worktree_git_pointer`が無いときは、どのステップもgitとClaudeを実行せず、止める結果を返す。

### コミットの前の再確認

完了のステップは、検証のステップの最後の検査とは別のジョブである。そのため、commitの前に次を確かめる。どれかに通らなければ、commitとpushをせずに人の対応待ちにし、理由を`status_reason`に記録する。

1. worktreeのロックを持つプロセスがいない。何も止めずに確かめる。前のステップのClaudeや検査コマンドが残っていると、検証の後もworktreeを書き換えうるためである。
2. `.git`が準備のステップの記録と一致し、準備のステップの結果に`branch`がある。
3. `commitAndPush`の前に、実装フローと同じgitleaksの検査をする。
4. fetchの前に、`git symbolic-ref -q HEAD`が`refs/heads/<準備のステップの記録したPRのブランチ>`である。detachedの`HEAD`も止める(`commitAndPush`の`expectedBranch`)。
5. `git add -A`の前に、ローカルのHEADがPRのhead(`head_sha`)である(`commitAndPush`の`requireLocalHeadAtExpected`)。
6. `git add -A`の後、commitの前に、ステージした内容を`head_sha`と比べ、索引のツリーをgitleaksが検査したツリーと比べる。
7. commitの後、pushの前に、作ったcommitのツリーが検査したツリーであることを確かめる。

手順3のgitleaksは、[実装フロー](implement.md)の[gitleaksによる秘密情報の検査](implement.md#gitleaksによる秘密情報の検査)と同じ検査である。

- 比較の基準は`head_sha`で、この修正が足す行だけを検査する。
- 検査は長くかかりうるので、リポジトリのロックの外で行う。
- 秘密情報らしき文字列が見つかれば、`secrets detected, changes not pushed`を理由に止める。検出したルール名とファイル名はジョブのログに残し、一致した文字列は残さない。
- 検査そのものが失敗したときは、commitとpushのどちらもせずに失敗させる。

手順6では、`git diff --cached -z --name-status`と`git diff --cached --raw -z`でステージした内容を読む。次のどれかがあれば止める。

- 禁止パス
- 新しい`*.sh`
- symlinkのモードとgitlink(入れ子のリポジトリ)のモード
- 要素が`.git`のパス
- `package.json`のscriptsの変更(ステージした中身を`git show :0:<path>`で読む)
- commitする索引の`git write-tree`が、gitleaksの検査したツリーと違う。理由は`worktree changed after the secret scan`になる。

どれかに当たれば、`git reset -q`でステージを戻してcommitしない。この検査自体が失敗したときも、ステージを戻してから失敗させる。

手順7で違えば、`git reset -q <head_sha>`でcommitを取り消し、`committed tree differs from the inspected tree`を理由にする。
戻す先は、`HEAD`からたどらずに明示する。

pushは`HEAD`ではなく、作ったcommitのshaを`refs/heads/<ブランチ>`へ送る。

### サブモジュールと置換オブジェクトの扱い

検証と完了のステップが変更の一覧に使う`git status`と`git diff`には、`--ignore-submodules=none`を付ける。対象は`--raw HEAD`、`--cached --raw`、`--cached --name-status`の各呼び出しである。`.gitmodules`や設定の`ignore = all`で、サブモジュール(gitlink)の変更を隠させないためである。

`f/factory/lib/workspace.ts`と`steps/pr_workflow_support.ts`が実行するgitには、環境変数`GIT_NO_REPLACE_OBJECTS=1`を付ける。PR修正と実装フローのworktreeでの操作も含む。`refs/replace/`で差し替えたオブジェクトを読まないためで、差し替えのrefは検査コマンドが作れる。

`commitAndPush`のfetchは、サブモジュールに降りない(`--no-recurse-submodules`)。

### 差分の大きさの上限

差分に含まれるファイル数が`max_fix_changed_files`を超えるか、追加と削除の行数の合計が`max_fix_diff_lines`を超えると、検証のステップが止める結果を返す。マージのコンフリクトやファイルの削除による大きな変更を見つけるためである。

### 準備での確認

PR修正の準備のステップは、worktreeを作る前に次を確かめる(`evaluatePrFixSafetyGuards`など)。

| 確かめること | 通らないとき |
| --- | --- |
| リポジトリが許可リストに含まれる | ブロック |
| リポジトリのオーナーが`owners`にある(`factory_repo`を除く)。`id`があれば、現在のIDと一致する | ブロック |
| `fix_round`が`max_fix_rounds`以下である | 人の対応待ち |
| 時間設定がステップのtimeoutに収まる | ブロック |
| 親のIssueの作業項目が実装中でない | ブロック |
| PRのブランチ名から引いた実装の作業項目が実装中でない | ブロック |
| PRがopenである | ブロック |
| `head.repo`が`base.repo`と同じである(forkのPRにはpushしない) | ブロック |
| PRがdraftでない | ブロック |
| PRのauto-mergeが有効でない | ブロック |
| headのブランチの状態を読める | 失敗(`failed`)。`job_failed`で通知する |
| headのブランチがデフォルトブランチでない | ブロック |
| headのブランチが保護ブランチでない | ブロック |
| headのブランチにrulesetのruleが適用されていない | ブロック |

PR修正がpushするのはheadのブランチなので、headの保護を確かめる。
baseが保護されていても、headが普通のブランチなら止めない。
保護の有無は、branches APIの`protected`で読む。
`main`を保護するruleset(対象は既定のブランチ)は、`protected: true`として返ることを確かめた。
globで対象を指定するrulesetなどが`protected`に反映されるかは確かめていない。
そのため、headのブランチに効くrulesetの規則も、`GET repos/{owner}/{repo}/rules/branches/{branch}`で読む。
1件でもあれば、理由`head branch has rules`でブロックにする。
ruleの種類は問わずに止める。
止めすぎは安全側で、`protected`に反映されないrulesetを見落とさないためである。
auto-mergeが有効なPRを止めるのは、Factoryの修正pushがレビューを経ずにマージされうるからである。
headの状態は、GitHubのAPIで読む。
読めなかったときは例外になり、flowの失敗ハンドラが作業項目を失敗(`failed`)にして、`job_failed`で通知する。ブロックにはならない。
デフォルトブランチは保護されていることが多いので、デフォルトブランチを先に判定し、理由を区別する。

親のIssueの作業項目と実装の作業項目を確かめるのは、実装フローとPR修正がPRのブランチのworktreeを共有するからである。ブランチ名から引くのは、ブランチ名が`factory/issue-<N>-wi-<id>`の形のときで、親の行が無いPRでも止まる。理由を分けているので、どちらで止まったかを見分けられる。

worktreeを使っているプロセスがいるときもブロックにする([再実行と中断](#再実行と中断))。

### pushの直前の確認

pushの直前には、`commitAndPush`がfetchし直した`head_sha`と、準備のステップが確かめた値を比べる。違えば、その間に人がpushしたとみなし、pushを止めてブロックにする。

### コミットの作成者情報

コミットのauthorとcommitterには、PATが解決するGitHubアカウントのログイン名とnoreplyのメールアドレスを使う。メールアドレスの形は`<数値ID>+<ログイン名>@users.noreply.github.com`である。個人のメールアドレスをどこにも書き込まないためである。値は`git commit`の環境変数(`GIT_AUTHOR_*`と`GIT_COMMITTER_*`)としてだけ渡し、git configには書き込まない。
