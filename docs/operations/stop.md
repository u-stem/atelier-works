# 保留と全停止の運用

保留を確かめる手順と、Factoryを全停止する手順と、設定を止める向きに変える手順である。
Factoryを運用する人が読む。
[運用](../operations.md)の手順のうち、Factoryを止めるものをこの文書に置く。

## 保留を確かめる

保留は、対象を進めないことを、期限つきで伝える仕組みである。
保留を読んで止まるのは、Factoryのdependabotの自動マージと、ローカルのClaudeのセッションのマージ(`gh pr merge`など)である。
仕様は[保留の内部仕様](../internals/holds.md)にある。
Claudeが保留を置く・解除する手順は、[保留のスキル](../../.claude/skills/hold/SKILL.md)にある。

保留の一覧は、Consoleのシステムの画面の「保留と凍結」でも見られる。
置く操作と解除は、端末の`mise run`のタスクのほかに、Consoleの画面からもできる。

| 操作 | コマンド |
| --- | --- |
| 一覧 | `mise run hold:list` |
| 置く | `mise run hold:place -- --scope merge --target <owner>/<repo> --minutes <分> --reason <理由>` |
| 解除 | `mise run hold:release -- <id>` |

Consoleでは、行の「解除」を押し、確認のダイアログで種類、対象、理由、置いた主体、期限、効果を読んでから確定する。
Consoleの解除は、`yes`の入力を求めず、誰が置いた保留も解除できる。
解除した操作者は、情報の通知`hold_released`に残る。
凍結とdeployの保留も、同じ画面から解除できる。
Consoleから置く手順は、[Consoleから保留と凍結を置く](#consoleから保留と凍結を置く)にある。

タスクは、チェックアウトを更新した端末で使える。
タスクが見つからないときは、`mise exec -- bun ./scripts/hold.ts <list|place|release>`を直接実行する。
人が端末で実行する置く操作と解除は、`yes`の入力で確かめる。
`CLAUDECODE`があるClaude Codeのセッションは、確認なしで通る。
セッションは、自分の`holder`(`session:<ブランチ>`)の保留だけ解除できる。
期限は最長24時間で、延長は無い。
続けるときは、解除して置き直す。
置き直しの回数に上限は無いので、続けて置くと保留は続く。
`hold:list`で、期限の切れた行と、有効の条件を満たさない行(`invalid`)も確かめられる。

保留が止めるのは、dependabotのPRの評価と自動マージ、ローカルのClaudeのセッションのマージである。
取得は、`dependabot_merge_enabled`が偽の試運転中も、保留のあるリポジトリのPRを待たせる。
マージの直前の最後の確認が働くのは、`dependabot_merge_enabled`が真のときだけである。
ローカルのセッションの`gh pr merge`などは、フックが止める。
人の端末(プロンプトの`!`)、GitHubのWeb UI、クラウドのセッションのGitHubのMCPによるマージは止めない。
範囲`claim`は読む処理が無く、設ける予定もないので、置けない。

保留を置く前に、自動マージが有効なPRを確かめる。
GitHubの自動マージは、保留を置いた後もチェックが通れば実行されるためである。

```bash
gh pr list --repo <owner>/<repo> --json number,autoMergeRequest --jq '.[] | select(.autoMergeRequest != null) | .number'
```

### 保留で止まったdependabotのPRを再開する

1. `mise run hold:list`で、保留の理由と期限を確かめる。
2. 解除してよければ、Consoleのシステムの画面の「保留と凍結」の「解除」か、`mise run hold:release -- <id>`で解除する。
3. 取得が待たせていたPRは、次の取得(10分ごと)に自動で再開する。
4. 終了のステップで止まった作業項目は、再開しない。
   作業項目は人の対応待ちで終わり、理由は`dependabot merge held by a hold`である。
   PRを確認して手でマージする。
   dependabotがrebaseして新しいコミットが積まれると、新しいheadとして自動で評価される。

保留を読めないときは、通知`dependabot_merge_hold_unreadable`の手順に従う。

### 保留でマージや反映が止められたとき

Claudeのセッションのマージ(`gh pr merge`など)と、`wmill sync push`、`wmill datatable migrate`が拒否されたときの手順である。

1. 拒否の文に載るidと期限を、`mise run hold:list`と`mise run freeze:list`で確かめる。
2. 置いた主体が解除するか、期限が切れるのを待つ。
   解除してよければ、人が解除する。
   Consoleのシステムの画面の「保留と凍結」から解除する。
   端末では、`mise run hold:release -- <id>`か`mise run freeze:release -- <id>`を実行する。
3. 保留を読めないという拒否は、保留が無いことを意味しない。
   スタックが止まっていれば`mise run up`で起動して、同じコマンドをやり直す。
   ツールが無いと出たら`mise install`を実行する。
4. それでも読めないときは、人が端末でプロンプトの先頭に`!`を付けて実行する。
   クラウドのセッションは保留を読めないので、マージと反映を人が行う。

スケジュールの凍結だけが有効なときの`wmill sync push`は、除外を付ける`mise run push`を使う。

### 保留を置くときの注意

保留は止めるためだけに使い、許可には使わない。
`reason`には秘密を書かない。
値はプロセスの引数に現れ、一覧に表示される。

subagentは保留を置かず、解除もしない。
deployの保留を置くことと、凍結の解除も同じである。
主セッションか人に頼む。
一覧(`mise run hold:list`、`mise run freeze:list`)と、スケジュールの凍結を置くことは、subagentも使える。
Consoleの書き込みscriptの名前を含むコマンドは、実行系の包み方やglobを問わず、フックが拒否する。
対象は、`scripts/claude-hooks/console-scripts.ts`の`CONSOLE_WRITE_SCRIPTS`が挙げる書き込みの16本である。
ソースを読むときは、Readツールか`git show`を使う。
subagentだけでなく、主セッションを含むすべてのClaudeのセッションが対象である。
解除と、Consoleからの置く操作と止める操作は、人がConsoleの画面で行う。

### Consoleから保留と凍結を置く

Consoleのシステムの画面の「保留と凍結」から、マージの保留、deployの保留、スケジュールの凍結を置ける。
置く主体は人に固定し、誰が置いたかは操作の記録に残る。
Issueの取り込みの保留は、読む処理が無いので置けない。

1. 「保留や凍結を置く」を押す。
2. 種類を選ぶ。
3. 対象を入力する。
   マージの保留は`owner/repo`、スケジュールの凍結は`f/factory/<名前>`である。
   deployの保留は対象を持たない。
4. 期限を分で入力する。
   入力欄に、入力できる範囲が出る。
   上限は、マージの保留とスケジュールの凍結が1440分、deployの保留が120分である。
5. 理由を入力する。
   必須で、200文字までである。
   理由は一覧に表示されるので、秘密を書かない。
6. 確認のダイアログで、効果と終わり方を読んでから、「置く」を押す。
   開いた直後のフォーカスは「取り消す」にあるので、Enterだけでは置かない。

次の場合は、置かずに断る。
断った理由は、画面の知らせに出る。

- 同じ対象に、ローカルのClaudeのセッションなどが置いた有効な保留か凍結がある。
- 同じ対象に、人が置いた有効な保留か凍結がある。
- スケジュールの凍結で、対象が`self_update`か、リポジトリに定義の無いスケジュールである。
- 期限が上限を超えるか、理由が空か長すぎる。
- 保留と凍結の件数が上限に達している。
  不要なものを解除してから、もう一度置く。

置いた後に、一覧を読み直して確かめる。
置いた行が見えないときと、置く前に有効だった他の行が欠けているときは、置いたと言い切らず、警告を出す。
一覧を取り直して確かめる。
他の行が欠けていたときは、別の書き込みと重なって、行を消した可能性がある。
`mise run freeze:list`で、残っている行を確かめる。

解除は、同じ画面の一覧の「解除」で行う。
期限が来ても終わる。
仕様と残るリスクは、[保留の内部仕様](../internals/holds.md)と[凍結とdeployの保留の内部仕様](../internals/freezes.md)、[Consoleの安全策の内部仕様の「保留と凍結を置く」](../internals/console/security.md#保留と凍結を置く)にある。

### Consoleでスケジュールを止める

確認作業のために、定期の処理を止めたいときは、Consoleのジョブの画面のスケジュールのタブから止める。
止められるのは、次の7つのスケジュールだけである。
止めるまでに、凍結を置く段と、止める段の2つがある。

| スケジュール | 止めると起きること |
| --- | --- |
| `poll_prs` | トリガーのラベルを付けたPRを、作業項目に取り込まない。通知は出ない |
| `watch_main_ci` | mainのCIの失敗を通知しない |
| `watch_pr_ci` | FactoryのPRのCIの失敗を通知しない。CIの失敗を直す作業項目も起動しない |
| `watch_pr_conflicts` | PRのコンフリクトの検知と通知が止まる |
| `auto_retry_pr_review` | GitHubの一時的な失敗で止まったPRレビューを、自動では再開しない。通知は出ない |
| `drawio_viewer_bump` | draw.ioのビューアの版を上げるPRを作らない |
| `notify_daily_summary` | 日次サマリが届かない。再開した後、予定が飛んだ日を最大7日分まとめて出す |

止められるのは、止めて黙るのがそのスケジュール自身の仕事だけで、ほかのスケジュールの入力や検知を止めず、再開を自己更新の追従へ任せられるものだけである。
`self_update`、`poll_issues`、`poll_dependabot`、`cleanup_*`、見張りのスケジュールは、止められない。
止めると、反映、作業項目の照合、掃除、異常の通知が止まるためである。
`collect_github`も止められない。
止めると、`poll_issues`の取り込みと`poll_dependabot`が黙り、PRのCIとコンフリクトの判断が古い記録で動くためである。

1. 止めるスケジュールの行の「止める準備」を押す。
   確認のダイアログで、期限と理由を入力する。
   期限は、確認作業が終わるまでの長さにする。
   12分より短い期限は入力できない。
   止められるまでの待ち(7分)と、止める時点で残っていなければならない分(5分)の和にあたる。
2. 「凍結を置く」を押す。
   凍結を置いても、スケジュールはまだ止まらない。
   凍結は、反映(`self_update`と`mise run push`)がスケジュールの定義を上書きしないようにするだけである。
   行には、「止める」を押せる時刻が出る。
   凍結を置いた時刻から7分後で、置く前に始まった反映が終わるまでの時間にあたる。
   人の端末のpushには時間の上限が無く、この待ちの対象外である。
3. 時刻を過ぎたら、行の「止める」を押す。
   確認のダイアログで、止めたときの影響と、有効に戻る時期を読む。
   有効なdeployの保留があるときは、その旨も出る。
4. 止まったら、確認作業をする。
5. 有効に戻す。
   止めた行の「凍結を解除して戻す」を押すと、凍結を解除する。
   解除しなくても、凍結が終われば同じである。
   どちらも、次の自己更新の追従が、スケジュールをリポジトリの定義(有効)に戻す。
   有効なdeployの保留があるあいだは、追従も待つので、解除しても戻らない。
   deployの保留が終わるか解除された後の追従で戻る。
   先に戻したいときは、Windmillの画面でスケジュールを有効化し、その後で凍結を解除する。
   Consoleに、スケジュールを直接有効に戻す操作は無い。

止めずに断られる場合は、次のとおりである。

| 断りの文 | 原因と対処 |
| --- | --- |
| 有効な凍結がありません | 凍結が無い、終わった、解除された。「止める準備」からやり直す |
| ローカルのセッションが置いた凍結 | 人が置いた凍結だけが、止める根拠になる。セッションの凍結を解除し、「止める準備」からやり直す |
| まだ止められません | 凍結を置いて7分が過ぎていない。表示された時刻まで待つ |
| 凍結が終わるまで5分を切っている | 止めた直後に凍結が終わると、スケジュールが無効のまま残りうる。凍結が終わるのを待ち、「止める準備」からやり直す |
| 自己更新が実行中です | 凍結を置く前から実行中の反映がある。終わってから、もう一度止める |
| スケジュールの定義が変わった | Windmillのスケジュールが、別のscriptの定期処理になっている。Windmillの画面で確かめる |
| すでに無効です | 止める必要が無い |

止めた後に読み直したスケジュールが無効になっていないときは、警告が出る。
Windmillの画面で状態を確かめる。

止めたときの凍結が、読み直しで有効でなかったときも、警告が出る。
凍結が先に終わった可能性があり、追従がスケジュールを戻さないことがある。
Windmillの画面で、スケジュールを有効に戻す。

`mise run freeze:reset`で変数を空にした後も、Consoleで止めたスケジュールは、次の反映まで戻らない。
Windmillの画面で、スケジュールを有効に戻す。
`reset`は、この旨を表示する。
仕様と残るリスクは、[凍結とdeployの保留の内部仕様](../internals/freezes.md)と[Consoleの安全策の内部仕様の「スケジュールを止める」](../internals/console/security.md#スケジュールを止める)にある。

### 凍結と合わせて確かめる

対象を止める仕組みは、保留のほかに、スケジュールの凍結がある。
凍結は変数に置くので、保留の表には現れない。
`mise run hold:list`は、有効なスケジュールの凍結とdeployの保留の件数も表示する。
スケジュールを止めている凍結とdeployの保留は、`mise run freeze:list`で確かめる([凍結とdeployの保留の内部仕様](../internals/freezes.md)の「運用手順」)。

## 全停止する

Factoryが暴走したとき、1つの操作でFactory全体を止める。
止めた状態は、Windmillの秘密でない変数`f/factory/stop_all`に置く。
変数は同期の対象外で、置いた時刻、操作者、理由を持つ。
入口は、Consoleと、ホストの`mise run stop`の2つである。
どちらも、Windmillの同じscriptで全停止を置く。
仕組みと残るリスクは、[セキュリティ](../security.md#全停止)にある。

### 全停止の間に起きること

全停止は、次のことを行う。

- `factory_config`の`true`の`*_enabled`を、すべて`false`にする。
  止める直前に、その名前を秘密でない変数`f/factory/stop_all_record`に記録する。
  全停止が置かれていなかったときは記録を置き換え、すでに置かれていたときは前の記録に足す。
  止める名前が無いときは、前の記録をそのまま残す。
  記録は、解除の後に[記録した設定を戻す](#記録した設定を戻す)ときに使う。
- リポジトリのscheduleを無効にする。
  次の見張りと片付けの4本は、動かし続ける。
  - `detect_schedule_failures`(失敗の検出、全停止の通知、外部の死活監視)
  - `default_worker_watch`(defaultのworkerの停止の検知)
  - `notify_daily_summary`(日次のまとめと、資格情報の期限の確認)
  - `cleanup_workspaces`(作業ディレクトリの片付け)
- 実行中のClaudeと検査は、15秒ごとに変数を読み、置かれていればプロセスグループごと止まる。
- 5分以内に、検出器が要対応の通知(`stop_all_active`)を残し、Discordへ1回だけ送る。
  時刻、操作者、理由は、Discordの通知とConsoleのシステムの画面に出る。

実行中のジョブは、Consoleからは中止しない。
中止すると、ジョブのプロセスと一緒に、子プロセスを止める監視が消えるためである。

止めた実装フローの作業項目は、人の対応待ち(`needs_human`)で終わる。
解除の後に、[失敗した作業を再実行する](../operations.md#失敗した作業を再実行する)の手順で再実行する。

自己更新(`self_update`)とIssueの取り込み(`poll_issues`)は、次のように見送る。
手動で動かしても同じである。

- 自己更新は、self cloneの更新も、Windmillへの反映もしない。
  止めた後に入ったマージで、Factoryが動き直さないためである。
  解除の後の最初の回が、見送った範囲をそのまま反映する。
- 取り込みは、新しいIssueを取らない。
  進行中の作業項目の照合と、承認待ちの期限切れの扱いは続ける。
- 承認か却下が決まった依頼の処理先は、起動し直さない。
  起動し直された処理先が、次の工程やIssueの作成を始めるためである。
  起動し直しの記録を書かないので、再起動の回数は使い切らない。
- 版の食い違いの通知(`deployed_sha_mismatch`)は出さない。
  反映の見送り中に食い違いが出ても、異常ではないためである。

変数を読めない回や、読みが5秒の時間切れになった回も、止まっていないと確かめられないので、同じように見送る。

ホストの`mise run push`と`mise run deploy`も、全停止の間は断る。
pushが、止めたscheduleを定義の`enabled: true`で有効に戻すためである。
解除してから実行する。
`mise run up`は、pushもscheduleの復帰もしないので、全停止の間は警告だけで通す。
解除の前でも、コンテナを作り直す復旧ができるようにするためである。
変数を読めないときも、`mise run up`は警告を出して通し、pushは断る。
止まっているスタックを`mise run up`で起こせるようにするためである。

### Consoleから全停止する

1. システムの画面の「保留と凍結」の節の先頭にある**全停止**を押す。
2. 確認のダイアログに理由を書き、**全停止する**を押す。
   理由は200文字までで、改行などの制御文字は使えない。
3. 結果のトーストを読む。
   止められなかったscheduleがあれば、Windmillの画面で無効にする。
   すでに全停止中のときは、設定とscheduleを止め直す。
   名前を記録できなかったときや、記録に載らなかった名前があるときは、トーストが警告で知らせる。
   その名前は`mise run stop:restore`では戻らないので、控えておき、解除の後に手で戻す。
4. 15秒ほど待ち、Consoleのジョブの画面で、実行中のジョブが終わることを確かめる。
   プロセスが残ったときは、ホストで`mise run stop -- --kill-only`を実行する。

### ホストから全停止する

Consoleを開けないときは、ホストの端末で次を実行する。

```bash
mise run stop -- --reason "<理由>"
```

端末で`yes`を入力して確かめると、Consoleと同じscriptで全停止を置く。
そのあと30秒待ち、実行中のジョブを中止し、workerに残ったClaudeと検査のプロセスを止める。
30秒は、実行中のClaudeと検査が、自分で変数を読んで止まるまでの間である。
内訳は、監視の間隔15秒、変数の読み取りの上限5秒、SIGTERMの後の猶予5秒に、余裕を足したものである。
端末(TTY)を持たない実行(subagentや背景のセッション)は断る。
環境変数`CLAUDECODE`があるときも、確認の前に断る。

Windmillが落ちていて変数を置けないときは、残ったプロセスを止めるだけにする。

```bash
mise run stop -- --kill-only
```

この場合、全停止の変数は置かれない。
Windmillが戻ったら、`mise run stop -- --reason "<理由>"`を実行し直す。

### 全停止を解除する

原因を取り除いてから解除する。
Consoleでは、全停止の区画の**解除**を押し、確認のダイアログで**解除する**を押す。
ホストでは、端末で`mise run stop:release`を実行し、`yes`を入力して確かめる。

解除は、変数を空に戻し、リポジトリの定義で有効なscheduleを、凍結のあるものを除いて有効に戻す。
全停止の前に凍結を通さずに止めていたscheduleも、有効に戻る。
凍結を通さない停止は自己更新の反映でも戻るので、残したい停止は凍結で置く。
凍結のあるscheduleは戻さない。
凍結が終わると、自己更新が戻す。
凍結を読めないときは、解除を断る。

解除は`factory_config`の`*_enabled`を戻さないので、機能は動き出さない。
全停止の間は自己更新が反映しないので、解除の直後は、修正のマージがまだWindmillに届いていないことがある。
修正の反映を確かめてから、[記録した設定を戻す](#記録した設定を戻す)の手順で戻す。
5分以内に、検出器が情報の通知(`stop_all_released`)を残してから、`stop_all_active`を解決する。

全停止で止めた実行の作業項目は、失敗のまま残り、自動では再実行されない。
解除の後に、Consoleの**要対応**で失敗の行を選び、**再実行**を押す。
監査は再実行できないので、**レポート**の**今すぐ監査**で起動し直す。
全停止の後は、日次予算に早く達しうる。
達したときの対応は、[Claudeの実行が上限で失敗したとき](../operations.md#claudeの実行が上限で失敗したとき)に書く。

### 記録した設定を戻す

全停止が止めて記録した`*_enabled`は、解除の後に、ホストの端末で次を実行して戻す。
修正の反映(Consoleのシステムの画面の反映の状態)を確かめてから実行する。

```bash
mise run stop:restore
```

原因の機能だけを止めたままにするときは、名前をカンマで区切って除く。

```bash
mise run stop:restore -- --except pr_conflict_fix_enabled
```

コマンドは次の順に進む。

1. 全停止の変数を読む。
   置かれているか、壊れているか、読めないときは、何も変えずに断る。
   先に[全停止を解除する](#全停止を解除する)。
2. 記録を読む。
   記録が空なら、何もせずに終える。
   記録が壊れているか読めないときは断るので、Windmillの画面で`f/factory/factory_config`を開き、手で戻す。
   `--except`に記録に無い名前があるときも、何も変えずに断る。
   綴りを誤った名前で、止めておきたい機能が戻らないためである。
3. `factory_config`を、参照を展開しない生の値で読む。
   値に`$var:`か`$res:`があるとき、`!inline`で始まる文字列があるとき、今の設定が設定の検査(`lib/config.ts`)を通らないとき(`config_invalid`)は断る。
   `!inline`で始まる値は、`wmill resource push`がホストのファイルの中身に置き換えるので、書き戻さない。
4. 記録の名前のうち、設定にあり、今`false`のものを、1つずつ`true`にして検査する。
   `pr_conflict_watch_enabled`は、`pr_conflict_fix_enabled`より先に戻す。
   `<名前>_since`の項目がある名前は、その値を実行した時刻に書き直す。
   止めている間に起きたことまで、戻した機能が拾いに行かないためである。
5. 記録の時刻と、戻す名前と、戻さない名前を理由つきで表示する。
   記録の時刻が古いときは、前の全停止の記録である。
   戻さない理由は次のどれかである。
   - 今`true`である。
   - 設定に無い。
   - 真偽値でない。
   - 有効にすると検査を通らない。
   - `--except`で除いた。
6. `yes`を入力して確かめると、設定と記録を読み直し、どちらも読んだときと同じなら設定を書く。
   違っていれば、何も書かずに断るので、もう一度実行する。
7. 書いた後に、全停止の変数と設定を読み直す。
   書き込みが時間切れなどで失敗したときも、値が書かれていることがあるので、全停止の変数を読む。
   全停止の変数を読めないときは、1回だけ読み直す。
   全停止が置かれていたか読めなかったら、設定を読み直し、`true`の`*_enabled`をすべて`false`に書き直して、記録には触らずに失敗で終える。
   記録に無い名前も止めたときは、その名前を表示するので、全停止を解除した後に、必要なら手で戻す。
   記録が置き換わっていたときは、今回戻した名前のうち今の記録に無いものを表示するので、全停止を解除した後に、必要なら手で戻す。
   全停止の変数を読めなかったときは、解除の代わりに、全停止が置かれていないことをWindmillで確かめてから戻す。
   設定を読み直せないときは、手で`false`にするよう案内して終える。
8. 記録を読み直し、最初に読んだ記録と同じで、全停止が空なら、記録をすべて消す。
   戻す名前が無いときは、設定を書かずに記録を消す。
   記録が変わっていれば、新しい全停止が記録を置き換えたので、消さずに失敗で終える。
   消した後に、全停止の変数をもう一度読む。
   消す書き込みが失敗と返ったときも、値が書かれていることがあるので読む。
   失敗と返ったときは、記録が残っていることもある。
   置かれていたときは、標準エラーに警告を出して失敗で終える。
   戻した名前があるときは、手順7と同じく設定を止め直し、戻した名前を表示する。
   記録はこのコマンドが消したので、もう一度実行せず、全停止を解除した後に表示した名前を手で`true`にする。
   読めなかったときは、標準エラーに警告を出し、設定は止め直さずに失敗で終える。
   記録はもう無いので、止め直すと、戻した設定がすべて手作業に変わるためである。
   変数には条件つきの更新が無いので、確かめてから消すまでの間に置かれた全停止の記録は、消えうる。
   消えた場合も、設定はその全停止が`false`にしている。
   警告が出たら、全停止を解除した後に(読めなかったときは、全停止が置かれていないことを確かめてから)、`factory_config`で`false`の`*_enabled`を確かめ、要るものを手で`true`にする。

戻さなかった名前も記録から消える。
記録に残すと、止めたままにした機能が、次の`mise run stop:restore`や別の全停止の後に、意図せず戻るためである。
必要なら、Windmillの画面で`factory_config`を開いて手で`true`にする。
書き込みに失敗したときと、途中で全停止か記録の変化を見つけたときは、記録を残す。
記録を消せなかったときは、同じ`--except`を付けて実行し直すと、記録だけを消せる。

戻さないまま全停止を置き直すと、前の記録は、新しく止める名前があるときに置き換わる。
置き換わった後は、前の全停止が止めた名前をこのコマンドで戻せないので、全停止を置き直す前に`mise run stop:restore`を実行する。

端末(TTY)を持たない実行と、環境変数`CLAUDECODE`があるときは、何かを読む前に断る。
Claude Codeのフックもこのコマンドと記録の変数への書き込みを止める。
設定を有効にする向きの書き込みを、人の`wmill`のプロファイルだけに限るためである。

### 全停止の変数を読めないとき

変数が壊れているときは、止まっている扱いにする。
システムの画面には「全停止中」と、変数が壊れていることが出る。
解除すると、変数が空に戻る。

変数を読めないときは、実行中のClaudeと検査を止めない。
変数を読むAPIの障害で、動いている実行を壊さないためである。
読み取りが返らないときは、約1分たつと読み取りを見切って読み直す。
その間にConsoleから置いた全停止は、最長で約1分遅れて届く。
自己更新と取り込みは、止まっていないと確かめられないので見送る。
急いで止めるときは、ホストで`mise run stop -- --kill-only`を実行する。

### 全停止の実機の確認の記録

未実施。
反映の後に、次の順で確かめ、日付と結果を書く。

| 確かめること | 期待 | 結果 |
| --- | --- | --- |
| Consoleから全停止する | `*_enabled`が`false`になり、4本を除くscheduleが無効になる | 未実施 |
| 実行中の実装フロー | 15秒以内にClaudeが止まり、作業項目が人の対応待ちになる | 未実施 |
| 通知 | 5分以内に`stop_all_active`が残り、Discordに1回届く | 未実施 |
| `mise run stop -- --kill-only` | workerにClaudeと検査のプロセスが残らない | 未実施 |
| 解除する | scheduleが戻り、5分以内に`stop_all_released`が残る | 未実施 |
| `mise run stop`、`mise run stop:release`、`mise run stop:restore`の往復 | 全停止の前に`true`だった`*_enabled`だけが`true`に戻り、`*_since`が実行の時刻になり、記録が空になる | 未実施 |

## 設定を止める向きに変える

Consoleのシステムの**設定**タブから、factory_configの許可した項目を、止める向きと下げる向きに変えられる。
許可リポジトリなどの3つの一覧は、1要素の追加と削除ができる。
自動で動く機能やClaudeの費用を急いで抑えたいときに、WindmillやCLIを開かずに済ませるための操作である。
対象のリポジトリやレビュアーを入れ替えるときにも使う。

| 項目 | できる変更 | ボタン |
| --- | --- | --- |
| `implement_enabled`、`dependabot_enabled`、`dependabot_merge_enabled`、`pr_ci_fix_enabled`、`pr_conflict_fix_enabled`、`design_enabled` | `true`から`false`へ。`false`の項目にはボタンが出ない | **止める** |
| `daily_budget_usd`、`max_budget_usd_per_run` | いまより小さい、0より大きい値へ | **下げる** |
| `max_fix_rounds`、`implement_max_changed_files`、`max_fix_diff_lines` | いまより小さい、1以上の整数へ | **下げる** |
| `repo_allowlist`、`dependabot_other_repos`、`default_reviewers` | 1要素の追加か、1要素の削除 | 一覧の下の**追加**と、各要素の**削除** |

上の表の外の項目は、Consoleから変えられない。
有効にする向きと、上げる向きの変更も、Consoleからはできない。
人がCLIで行う。
`repo_allowlist`の最後の1件は、削除できない。
空にすると`owners`配下のすべてのリポジトリが対象になるため、人がCLIで行う。

1. Consoleのシステムの**設定**タブで、項目を探す。
   キー名、グループ名、値で絞り込める。
2. その行の**止める**か**下げる**を押す。
   一覧の項目は、要素の**削除**か、一覧の下の**追加**を押す。
   止められる項目は、タブの先頭の機能のスイッチの表にも並ぶ。
3. 確認のダイアログの先頭の結論で、何が起きるかを確かめる。
   止めるときは、結論の下の項目と値の行も確かめる。
   下げるときは、結論の前後の値を確かめ、変更後の値を入力する。
   追加は足す要素を入力する。
   使えない値の間は、確認のボタンを押せない。
4. **止める**、**下げる**、**追加**、**削除**のいずれかを押す。
   ダイアログを開いた直後は**取り消す**にフォーカスがあるので、Enterだけでは変えない。

変更は、次に設定を読む処理から効く。
動いているフローも、以後の手順が設定を読むときから、新しい値で動く。
実行中のジョブを止めるには、[動いているジョブを中止する](../operations.md#動いているジョブを中止する)。

次の3つは、確認のダイアログが先に伝える。

- `implement_enabled`を止めている間に承認した要件定義は、承認済みで止まる。
  要対応には載らず、再開の口が無い。
  有効に戻した後、人が**再実行**で再開する。
- `design_enabled`を止めても、`design_enabled_since`は残る。
  `design_enabled`だけを`true`に戻すと、残った時刻が読めるので、設計工程が、有効にする意思の表明が無いまま、すぐ開く。
  止めている間に承認した要件定義は、設計を経ずに実装へ進む。
  進行中の設計と承認待ちは止まらない。
  承認すると、設計書を実装へ渡さずに進む。
  却下は、Issueが変わっていれば要件定義へ戻り、そうでなければ人の対応待ちで止まる。
  有効に戻すには、人が`design_enabled`を`true`にし、`design_enabled_since`に新しい時刻を書く。
- `daily_budget_usd`を今日の使用額より小さくすると、今日のClaudeを使うフローがすべて失敗する。
  Consoleからは引き上げられない。

結果は、画面に出る知らせで確かめる。
成功の知らせは数秒で消える。
断り、確かめる警告、失敗の知らせは、設定のタブの先頭に、閉じるまで残る。
断りには、次の操作が書かれている。

| 知らせ | 意味と人がすること |
| --- | --- |
| 止めた、下げた、追加した、削除した | 変更が済んだ。タブの値が読み直される |
| 画面を開いた後に、設定の値が変わっていた | 別の経路が同じ項目を先に変えた。変更はしていない。見出しの更新を押して読み直し、もう一度確かめる |
| 設定に変数かresourceへの参照がある | 参照を含む設定は、Consoleからは変えない。CLIで変える |
| 書き込んだが、読み直した値が期待と違う | 書き込みは済んでいる。Windmillで`factory_config`を開いて、値を確かめる |
| 値が範囲に合わない、止める向きか下げる向きではない | 変更していない。値を確かめる |
| 要素がすでにある、要素の形が合わない、`owners`に無いアカウントのリポジトリ、`repo_allowlist`の最後の1件 | 変更していない。要素を直すか、人がCLIで行う |
| 操作者を確認できない、操作の記録を残せない | 変更していない。記録の表が無いか、DBに届かない |

一覧の追加と削除は、同じ値を逆の操作で元に戻せる。
止めた項目と下げた値は、Consoleからは戻せない。
元に戻すには、運用者がWindmillでリソース`factory_config`を編集するか、`wmill resource push`で戻す。
`wmill resource push`で戻す手順は、`wmill resource get`で値を取得して直し、`wmill resource push`で反映する。
詳しくは次の見出しにある。

- [失敗の自動修正を有効にする](pr.md#失敗の自動修正を有効にする)
- [競合の自動修正を有効にする](pr.md#競合の自動修正を有効にする)

`pr_ci_fix_enabled`と`pr_conflict_fix_enabled`を`true`へ戻すときは、`*_enabled_since`も要る。
時刻を書き直さないと、止めていた間の失敗を、まとめて直しに行く。
この2つは、上の手順に従って戻す。

操作の記録は、操作が`config_update`、対象が`f/factory/factory_config`で、`item`に項目名、`before`と`after`に前後の値が残る。
一覧では、`before`と`after`の代わりに、`op`(`add`か`remove`)、`element`、`before_count`、`after_count`が残る。
設定の全体は記録に入れない。
