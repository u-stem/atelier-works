# 運用

Factoryを動かす人が、日々の作業で何をすればよいかと、通知や失敗にどう対応するかをまとめた手順書である。
構成と仕組みは[アーキテクチャ](architecture.md)、内部の挙動は`docs/internals/`の各文書を参照する。
目的ごとの手順の一部は、`docs/operations/`の各文書にある。
置き場は、末尾の[手順の置き場](#手順の置き場)の表から引ける。

画面の操作は、Factory Console(`/console/`)で行う。
左のサイドバーの入口は、**要対応**、**作業項目**、**レポート**、**システム**の4つである。

| 入口 | できること |
| --- | --- |
| **要対応** | 承認と却下、失敗した作業項目の再実行、通知の解決 |
| **作業項目** | 進捗の表、作業項目の詳細、要件定義書の閲覧 |
| **レポート** | 監査レポートの閲覧と**今すぐ監査**、コストと承認の統計の分析 |
| **システム** | 反映の状態、更新履歴、情報の通知、解決済みの通知、監査の失敗、作業項目に紐づかない失敗の閲覧と、設定を止める向きに変える操作 |

## 運用の決まり

1つのIssueは1つのインスタンスだけが処理する。
トリガーラベルを外す取得(claim)に成功したインスタンスが、そのIssueを受け持つ。
Factoryは取得の前に、自分のGitHubユーザーをassigneeに追加する。
後から来たインスタンスは手を引く。

この排他はベストエフォートである。
GitHubは、同時に届いた複数の削除のうち、成功が1つだけになることを保証していない。
すべてのインスタンスが同じPATで動くので、GitHub側ではインスタンスを区別できない。
同じIssueに2つ目の作業項目を作らせない最後の防御は、DBの部分一意インデックスである。
終端でないIssueの作業項目は、`owner`、`repo`、Issueの番号の組ごとに、同時に1つしか持てない。
別の取得が同じIssueを先に取得していたときは、Factoryは取得を失ったものとして引き、`claim_race_lost`のnoticeを残す。
この防御が働くのは、インスタンスが同じDBを共有している場合である。
DBを分けた複数のインスタンスが同じリポジトリを扱う構成は、対象外である。
1つのリポジトリは1つのインスタンスだけで扱う。

終端でない`pr_review`の作業項目も、`owner`と`repo`を小文字にした組と、PRの番号の組ごとに、同時に1つしか持てない。
このインデックスを足すmigrationは、先に重なりを片付ける。
同じPRの終端でない`pr_review`が重なっていれば、`id`が最大の行を残して古い行を取り消し、`work_item_events`に記録する。
そのあとで、インデックスを作る。
重なりは、ラベルの経路で作れる。
人の作業は要らない。
取り消した行は、`work_item_events`の注記`duplicate active pr_review work item cancelled by migration`で探せる。

同じIssueに、より新しいサイクルの作業項目がある古い作業項目は、`retry_work_item`で再実行できない。
新しいサイクルに置き換えられていて、古い要件定義を実装しかねないためである。
再実行は、最新のサイクルの状態に合わせた英語のエラーで止まる。
エラーは、次のどれかを示す。

- 最新のサイクルが進行中のときは、操作は要らない。
- 最新のサイクルが再実行できる状態(失敗、人の対応待ち、期限切れ、ブロック、承認済み)のときは、その最新のサイクルを再実行する。
- 最新のサイクルがPRを作成した(`pr_open`)ときは、そのPRを確かめる。
- 最新のサイクルがそれ以外の終端のときは、Issueにトリガーラベルを付け直して、新しいサイクルを始める。

承認済みの最新のサイクルを実装から再実行するには、`implement_enabled`が有効でなければならない。
無効のままだと、再実行は有効にするよう求めるエラーで止まる。
次の作業項目は、実装を起動しないので、このエラーで止まらない。

- 要件定義が書き換わって止まった作業項目
- 要件定義を作り直そうとして止まった作業項目

再開先の決まりは[作業項目の状態とリース](internals/work-items.md#再実行)に書く。

最新のサイクルの再実行が、同じIssueの稼働中の作業項目に阻まれるのは、まれな競合のときだけである。
再実行の確認と状態の更新の間に、同じIssueで新しいサイクルが始まると、状態を戻す更新が一意インデックスに拒まれる。
そのエラーは、稼働中の作業項目が現在のサイクルであり、再実行しようとした作業項目は再開されないことを示す。
現在のサイクルの作業項目に従う。

要件が承認された作業項目(`approved`)は終端で、一意インデックスの対象外である。
`implement_enabled`が無効の間は、承認済みの作業項目が長く残る。
その間に同じIssueで新しいサイクルが始まると、新しい作業項目が稼働中となる。
古い承認を使うと、置き換えられた要件定義を実装しかねない。
そこでFactoryは、新しい作業項目を挿入した直後に、同じIssueの古いサイクルの`approved`の作業項目を取り消す。
挿入が競合に負けたときは、何も取り消さない。
取り消しは作業項目のイベントに残る。
取り消した作業項目は終端で、新しいサイクルがあるため、`retry_work_item`でも再開できない。
取り消しの前にプロセスが落ちたときは、古い承認が残る。
残った承認は、同じIssueで次の新しいサイクルが始まるときに取り消される。
それまでも、上のとおり再実行は断られる。

取り消しの後に、Issueへ取り消しを伝えるコメントが付く。
コメントは、新しいサイクルの起動を終えてから投稿する。
コメントには、取り消した要件定義と新しいサイクルの作業項目のIDが載る。
新しいサイクルの要件定義には、あらためて承認が必要なことと、前の承認には対応が要らないことも伝える。
新しいサイクルが途中で失敗することもあるので、承認の依頼が届くとは約束しない。
コメントを投稿できなくても、取り消しは戻らない。
取り消しとコメントの間にプロセスが落ちると、コメントは付かない。
その場合も、人の操作は要らない。

このインデックスを足したmigrationは、既にある重複した稼働中の作業項目のうち、サイクルの古い方を取り消し、その承認待ちの依頼を期限切れにする。
残すのはサイクルが最大の作業項目である。
新しいサイクルがある`approved`の作業項目も、同じmigrationが取り消す。
これらの規則は自動で適用され、人が確かめたものではない。

Issueを取得したインスタンスの所有者が、そのIssueの承認をする。

各インスタンスは、稼働前に`f/factory/factory_config`の`instance_name`を設定する。
Discordの通知と承認の画面で、どのインスタンスの担当かを示すのに使うためである。

作業項目の状態は、Consoleの**作業項目**で確かめる。
画面は既定で進行中の作業項目だけを出す。
失敗、人の対応待ち、期限切れ、取り消し、PR作成済み、レビュー済みなどの終わった状態は、範囲を「すべて」にして探す(URLは`/console/items?scope=all`)。
状態の値と意味は[アーキテクチャ](architecture.md)の状態の一覧にある。

### ラベルの扱い

Issue・PRに付けるラベルは、Factoryを起動するトリガーだけである。

| ラベル | 付ける対象 | 起動するもの |
| --- | --- | --- |
| `factory` | Issue | 要件定義 |
| `factory:review` | PR | PRのレビュー |
| `factory:fix` | PR | PRの修正 |

トリガーラベルは、取得のときに外れる。
その後はどの状態になっても、FactoryはIssue・PRのラベルを付け外ししない。
状態はDBの作業項目にだけあるためである。

もう一度処理させたいときは、人がトリガーラベルを付け直す。
付け直すと、新しいサイクルとして別の作業項目ができる。

このリポジトリ自身のPRにも、`factory:review`を付けてよい。
レビューはコメントの投稿だけで、PRのブランチへ書き込まないためである。
`factory:fix`も付けてよい。
保護パスの外の修正はpushし、保護パスを変える修正はpushせずに人の対応待ちにするためである。
保護パスの一覧は[保護パスの変更を止める](internals/pr-workflow/security.md#保護パスの変更を止める)にある。

### 対象のリポジトリ

Factoryが扱うのは、`factory_config`の`repo_allowlist`に含まれるリポジトリだけである。
`repo_allowlist`が空なら、`owners`に含まれるリポジトリ全体が対象になる。

Factory自身のリポジトリ(`factory_repo`)は、`repo_allowlist`の内容に関わらず常に対象である。
対象を試験的に絞りたいときは、`repo_allowlist`に対象のリポジトリを明示する。

### オーナーの数値IDを固定する

`owners`の各要素は、GitHubの数値のIDを`id`に持てる。
`id`を省略するか`null`にすると、`id`が無いものとして扱う。
`id`は、ユーザーと組織のどちらも次のコマンドで調べられる。

```bash
gh api users/<名前> --jq .id
```

オーナーが改名して別の人がその名前を取得すると、名前だけの照合では同じオーナーに見える。
`id`を入れると、名前を取得した第三者のリポジトリのIssueとPRが、発見の候補に入らない。
承認を待つ間に名前が入れ替わっても、保存済みの作業項目は、リポジトリを取得する前に止まる。
`allowed_labeler_logins`に古い名前が残っていても、その名前がオーナーの名前なら、そのオーナーのリポジトリのラベルはラベルの確認まで進まない。
候補に入らないので、拒否のnotice(`labeler_denied`)も積もらない。

`allowed_labeler_logins`に古い名前が残っていなければ、`id`が無くても、名前を取得した人はラベルの確認で拒否される。
ラベルの付与者とPRの作成者は、ログイン名で判定するためである。
`id`を入れたオーナーでは、この拒否を待たずに、候補の段階で外す。

`id`があるオーナーは、`poll_issues`と`poll_prs`が発見の前にGitHubの現在のIDを取得して照合する。
IDが一致すれば、そのオーナーのIssueとPRを発見する。
食い違うか、IDを取得できないオーナーは、その回の発見を飛ばし、失敗として記録する。
`id`の無いオーナーが名前だけで動く残るリスクは、[R-TB-27](security-risks.md#r-tb-27)である。
DBから見つけ直す追跡中のPRも、`owners`にあって照合を通ったオーナーのものだけを候補に残す。
飛ばしたオーナーと、`owners`に無い旧名のオーナーのPRは、候補から外れる。
`factory_repo`のPRは、オーナーによらず残る。

食い違いと、名前のアカウントが見つからない(404)ときは、Consoleの**要対応**に`owner_id_mismatch`が残る。
本文にオーナー名と、設定のIDが載る。
食い違いのときは、GitHubの現在のIDも載る。
GitHubでそのアカウントが意図した持ち主かを確かめ、`factory_config`の`owners`の名前か`id`を見直す。
名前とIDが合うと、次の回から発見が再開する。
見直した後に、noticeを解決する。

正規の改名(AからB)のときは、`owners`の名前をBに直し、B側のIssueとPRにトリガーラベルを付け直す。
数値のIDは改名で変わらないので、`id`はそのまま使える。
旧名Aで記録した作業項目は、`owners`から外れても取り消されない。
そのIssueかPRが閉じられたときに、`poll_issues`の整理が取り消す。
実行中のジョブが孤児になったときは、整理が失敗にする。

404以外のすべて(5xx、レート制限、認証の失敗、通信断を含む)でIDを取得できなかったときは、失敗の記録だけが残る。
一時的な障害でありうるので、次の回に再試行する。

#### 作業項目を進める前の照合

作業項目は、発見の時点の`owner`と`repo`の名前を保存する。
承認を待つ間などに名前が別の人に渡ると、保存した名前のURLは別のリポジトリを指す。
そこで、作業項目を進めるステップが、リポジトリを取得する前か、GitHubへ書き込む前に照合する。
対象は次のとおりである。

- 要件定義(`pipeline_prepare`)、実装(`implement_prepare`)、PR修正(`pr_fix_prepare`)、PRレビュー(`pr_review_prepare`)の準備。
- dependabotのPRの取得(`poll_dependabot`)。
  作業項目を作る前に照合する。
- dependabotの準備(`dependabot_prepare`)。
  事実の再収集の後、cloneの前に1回照合する。
- フォームで投入する`manual_intake_create_issue`。
  Issueを作る前に照合する。
- Issue化の提案を処理する`issue_proposal_apply`。
  承認は判断の記録の前に、却下は返信の前に、1回だけ照合する。
- 長い実行を挟んだ後の書き込みのうち、次の5つの処理。
  Claudeの実行と検査の間に名前が別の人に渡りうるので、準備の入口に加えて、書き込みの直前にも1回照合する。
  実装の終了処理(`implement_finish`)は、pushとリモートブランチの削除の前に照合する。
  PR修正の終了処理(`pr_fix_finish`)は、pushの前に照合する。
  PRレビューの投稿(`pr_review_post`)は、レビューの投稿の前に照合する。
  dependabotの終了処理(`dependabot_finish`)は、PRを読み直した後、マージ、所見の投稿、ラベルの付与の前に照合する。
  draw.ioのビューアを上げる`drawio_viewer_bump`は、`factory_repo_id`をブランチの作成の前に照合する。

書き込みの直前の照合に落ちた処理は、書かずに止める。
dependabotの終了処理では、作業項目を人に回し、関門のnoticeを残す。
dependabotの準備の照合に落ちたときも、作業項目を人に回し、関門のnoticeを残す。
このとき準備は、cloneも作業ツリーの作成もしない。
noticeは、`owner_id_mismatch`である。
`factory_repo`で`factory_repo_id`が設定されているときは、リポジトリIDの食い違いが`factory_repo_id_mismatch`になる。
残る余地は、[セキュリティ](security.md#オーナーの数値idの照合)の残るリスクにある。

照合は、リポジトリのオーナーの名前で`owners`を引いて行う。
大文字と小文字は区別しない。

- 要素が`id`を持つときは、`GET repos/<owner>/<repo>`が返すオーナーのIDと比べる。
- 要素が`id`を持たないときは、照合せず、名前だけで動く。
- 要素が無いときは、リポジトリが`factory_repo`と一致する場合だけ通す。
  それ以外は対象外として止める。

リポジトリが`factory_repo`と一致し、`factory_repo_id`があるときは、これらより先に、リポジトリ自体のIDも比べる([Factory自身のリポジトリの数値IDを固定する](#factory自身のリポジトリの数値idを固定する))。
cloneを開かない処理にも、この照合を効かせるためである。
cloneを開く準備のステップでは、`openFactoryClone`も同じ照合をするので、取得が1回増える。
通ったときだけ、cloneとcheckoutに進む。
`check_commands_by_repo`のキーは名前だが、`id`を入れたオーナーのリポジトリでは、照合を通ったものにしか検査コマンドが走らない。

止めたときは、Consoleの**要対応**にnoticeが残る。
止めるのは、次のいずれかのときである。

- オーナーのIDが食い違う。
- リポジトリが見つからない(404)。
- オーナーが`owners`に無い。
- `factory_repo`のリポジトリIDが食い違うか、見つからない。

オーナーの照合で止めたときの種類は、`owner_id_mismatch`である。
本文にリポジトリ名が載る。
`owners`に無いときは、オーナーを改名したなら名前を直し、対象にするなら足す操作が載る。
それ以外は、設定のIDが載り、食い違いのときはGitHubの現在のIDも載る。
404は、リポジトリの削除や改名のほかに、PATがそのリポジトリを読めなくなったときにも返る。
privateリポジトリでは、PATがアクセスを失うと、401でなく404になりうる。
GitHubでそのオーナーが意図した持ち主かを確かめ、`factory_config`の`owners`の名前か`id`を見直す。
見直した後に、`retry_work_item`で再実行し、noticeを解決する。

`factory_repo`のリポジトリIDで止めたときの種類は、`factory_repo_id_mismatch`である。
本文にリポジトリ名と、設定の`factory_repo_id`が載る。
食い違いのときは、GitHubの現在のIDも載る。
`factory_config`の`factory_repo`と`factory_repo_id`を見直し、見直した後に、noticeを解決する。

照合に落ちたときの終わり方は、処理ごとに次のとおりである。

| 処理 | 終わり方 |
| --- | --- |
| `pipeline_prepare` | 作業項目を人の対応待ち(`needs_human`)にして、Discordに知らせる。後続のステップは飛ばす |
| `implement_prepare` | 作業項目を人の対応待ちにして、Discordに知らせる |
| `pr_fix_prepare` | 作業項目をブロック(`blocked`)にして、Discordに知らせる |
| `pr_review_prepare` | PRを読む前に、作業項目をブロックにして、Discordに知らせる。forkのPRを見送るときと同じ終わり方である |
| `implement_finish` | pushかリモートブランチの削除の前に止める。何も書かずに、作業項目を人の対応待ちにして、Discordに知らせる。途中までの作業のpushでは、理由を人の対応待ちの理由に足す。要件の不足の差し戻しでは、不足の報告も載せる。削除の前の照合で404以外の取得に失敗したときは、止めずにブランチを残して差し戻しを続ける。最終のpushの前の照合で404以外の取得に失敗したときは、照合に落ちたのではなく処理の失敗として、作業項目を人の対応待ちにする |
| `pr_fix_finish` | pushの前に止める。作業項目をブロックにして、修正のラウンドは記録せず、Discordに知らせる。返信も投稿しない |
| `pr_review_post` | レビューの投稿とスレッドの解決の前に止める。作業項目をブロックにして、Discordに知らせる。投稿済みのレビューを再利用するときは、書き込まないので照合しない |
| `drawio_viewer_bump` | ブランチもPRも作らずに終わる。`factory_repo_id_mismatch`のnoticeが残る。`factory_repo_id`が無いときは照合しない |
| `poll_dependabot` | 作業項目を作る前に照合する。落ちたら、作業項目を作ってすぐ人の対応待ちにして、Discordに知らせる。フローは起動しない。作業項目は再実行できないので、設定を見直した後は、PRを人が確かめる |
| `issue_proposal_apply`の承認 | 判断を記録せず、GitHubへ何も書かずに、例外で失敗する。承認依頼は`approved`のまま、Issueが作られるまでConsoleの要対応に残る。例外の文は、`factory_repo_id`の食い違いか見つからないとき(404やURLを読めないとき)なら`factory_repo`と`factory_repo_id`、それ以外なら`owners`を見直すよう案内する |
| `issue_proposal_apply`の却下 | 判断を記録した後、返信だけを止め、作業項目は先へ進める。止めた理由はログに残る。照合そのものが失敗したとき(404以外の取得の失敗を含む)も、例外にしない |

`pr_fix_finish`と`pr_review_post`の書き込み前の照合で、404以外の取得に失敗したときは、止める結果にならず、ステップが失敗する。
一時的な障害でありうるので、ジョブの失敗として扱い、noticeは残さない。

`factory_repo_id`の食い違いで止まるときの終わり方は、作業項目のリポジトリで2通りに分かれる。
作業項目が`factory_repo`自身のリポジトリのときは、関門が止めるので、上の表のとおりに終わる。
それ以外のリポジトリのときは、関門を通り、cloneを開く`openFactoryClone`の照合が例外を投げる。
そのときは、ステップが失敗し、フローが失敗する([Factory自身のリポジトリの数値IDを固定する](#factory自身のリポジトリの数値idを固定する))。

照合に落ちたIssue化の提案の承認は、原因を見直して同じ承認をやり直す。
やり直すと、`approval_decide`が起動し直し、続きから処理する。
`approval_decide`は、記録済みの承認を却下に変える操作を断る。
名前が乗っ取られたままのときは、承認依頼が要対応に残り続ける。

404以外のすべて(認証の失敗、5xx、レート制限、通信断を含む)でIDを取得できなかったときの扱いは、処理ごとに次のとおりである。
どれも、noticeは残さない。
持続する障害を見逃さないためである。

- 準備のステップと`manual_intake_create_issue`は、ステップが失敗する。
  準備のステップは、原因を直した後に、`retry_work_item`で再実行する。
  `manual_intake_create_issue`は、食い違いと404でも同じく、Issueを作らずにフローが失敗する。
- Issue化の提案の承認は、例外で失敗する。
  判断は記録せず、承認依頼は要対応に残るので、原因を直した後に、Consoleの要対応から承認をやり直す。
- Issue化の提案の却下は、例外にしない。
  返信を止め、作業項目は先へ進む。
  照合が止めたときは警告のログに残り、照合そのものが失敗したときはエラーのログに残る。
  エラーのログには、秘密をマスクした文とエラーの名前が載る。

照合は、処理の始めに行う。
Issue化の提案の承認も、判断の記録の前に照合する。
却下だけは、判断を記録した後に照合する。
照合の後に、実行中に名前が入れ替わっても、その実行は検知しない。

照合しない処理も残る。
同じ項目を、[セキュリティ](security.md#オーナーの数値idの照合)の残るリスクにも挙げている。

- Issueの状態の確認と整理、承認後のIssueへのコメント、PRへの返信。
  名前のままで、投稿の内容は、名前を取得した人の目に触れうる。
- 取り消された作業項目の再開の前に行うIssueの状態の確認と、要件定義を作り直す再実行の前に行うIssueの題名と本文の取り込み。
  どちらも、Console用のworkerに`gh`が無いので、名前のまま読む。
  取り込んだ内容は、続く`pipeline_prepare`の照合が止めるので、Claudeには渡らない。
- 準備の照合から長い実行を挟んで、名前へ書き込む処理。
  実装(`implement_finish`)とPR修正(`pr_fix_finish`)のpush、実装のPR作成とラベル付与、レビューの投稿(`pr_review_post`)である。
  実行中に名前が乗っ取られると、pushでは、ローカルにしか無いオブジェクトが相手に送られうる。
  privateリポジトリでは、履歴が渡りうる。
  PR作成とレビューの投稿では、PRの本文とレビューの文面が渡りうる。
  どちらも、コードの抜粋を含みうる。
  どれも、書き込みの直前には照合しない。
- `drawio_viewer_bump`。
  `factory_repo`の名前だけで、ブランチとPRとラベルを作る。
  送る内容は公開物である。

### ラベルの付与者の数値IDを固定する

ラベルの付与者は、名前に加えて数値IDでも照合できる。
名前だけの照合では、アカウントが改名した後に別の人がその名前を取得すると、同じアカウントに見える。
`factory_config`の`allowed_labeler_ids`に、許可するアカウントの名前とIDを対で入れると、そのアカウントはIDでも照合する。
IDはラベルのイベントの応答に含まれるので、照合のためにGitHubへの呼び出しは増えない。
PRの作成者は、PRの応答の`user.id`で照合する。

IDは次のコマンドで調べる。

```bash
gh api users/<名前> --jq .id
```

`allowed_labeler_ids`は、名前をキー、IDを値にして書く。

```yaml
allowed_labeler_logins:
  - alice
allowed_labeler_ids:
  alice: 1001
```

キーには、`allowed_labeler_logins`の要素と同じ名前を書く。
含まれない名前、`[bot]`で終わる名前、大文字小文字だけが違う重複したキー、正の整数でない値は、設定の検証が拒否する。
綴りの誤りで、IDを入れたつもりのアカウントが名前だけの照合に戻るのを防ぐためである。

IDを入れたアカウントでは、名前が同じでもIDの違う人のラベルを許可しない。
改名の後に別の人が古い名前を取得しても、そのラベルは拒否される。
イベントにIDが無いときは、IDを確かめられないので拒否する。
拒否の流れは名前の不一致と同じで、ラベルを外さずに`labeler_denied`を残す。
許可した本人のラベルが拒否されたときは、設定のIDが合っているかを確かめる。

IDを入れないアカウントと、FactoryのPATのアカウントは、名前だけで照合する。
古い名前が`allowed_labeler_logins`に残ると、その名前を取得した人が、許可されたラベル付与者になりうる。
名前を変えたアカウントは、`allowed_labeler_logins`から古い名前を外して新しい名前を足し、`allowed_labeler_ids`のキーも合わせる。
ラベルを付けられる人は、書き込み権限を持つ人に限られない。
公開リポジトリでは、起票者が自分のIssueにラベルを付けられることもある。

### Factory自身のリポジトリの数値IDを固定する

`factory_config`の`factory_repo_id`に、`factory_repo`のGitHubリポジトリの数値IDを入れられる。
省略すると、IDを照合せず、名前だけで取得する。
次のコマンドで調べる。

```bash
gh api repos/<owner>/<repo> --jq .id
```

`self_update`は`factory_repo`のURL(名前)から取得し、リモートの内容を`wmill sync push`で反映する。
ほかの処理も、`factory_repo`のcloneからスキルとテンプレートを読んで、Claudeに渡す。
オーナーが改名して別の人がその名前を取得し、同じ名前のリポジトリを作ると、名前のURLはその人のリポジトリを指す。
その内容は、秘密値を持つworkspaceに反映されたり、Claudeに読まれたりしうる。

`factory_repo_id`を入れると、Factory自身のcloneを用意するすべての処理が、取得の前に、GitHubの現在のIDと照合する。
IDが一致したときだけ、取得に進む。
cloneのoriginは、取得の前に毎回`factory_repo`のURLへ付け替える。
照合したURLと取得するURLは、同じである。

食い違うか、リポジトリが見つからない(404)か、`factory_repo`のURLが`https://github.com/<owner>/<repo>`の形でないときは、取得しない。
Consoleの**要対応**に`factory_repo_id_mismatch`が残る。
本文にリポジトリ名と、設定のIDが載る。
食い違いのときは、GitHubの現在のIDも載る。
GitHubでそのリポジトリが意図した持ち主のものかを確かめ、`factory_config`の`factory_repo`か`factory_repo_id`を見直す。
404は、リポジトリの削除や改名のほかに、PATがそのリポジトリを読めなくなったときにも返る。
privateリポジトリでは、PATがアクセスを失うと、401でなく404になりうる。
そのときは、PATの権限を確かめる。
名前とIDが合うと、次の回から取得が再開する。
見直した後に、noticeを解決する。

照合に落ちたときの振る舞いは、処理ごとに次のとおりである。

| 処理 | 振る舞い |
| --- | --- |
| `self_update` | 取得も反映もせず、成功で終わる。`job_failures`に失敗を記録する。食い違いが続く間は、実行ごとに失敗の行が1行ずつ増える |
| `poll_issues`のデプロイ版の確認 | その回の確認を飛ばし、警告のログを残す。ポーリングは続く |
| 要件定義の準備(`pipeline_prepare`)、実装、PR修正、PRレビューの準備 | 作業項目が`factory_repo`自身のリポジトリのときは、オーナーの照合の関門が先に止める。終わり方は[作業項目を進める前の照合](#作業項目を進める前の照合)の表のとおりである。それ以外のリポジトリでは、取得の前にステップが失敗し、フローが失敗する。作業項目は失敗になり、Discordに`job_failed`が届く。原因を直した後に、`retry_work_item`で再実行する |
| `pipeline_generate` | 関門を呼ばず、`openFactoryClone`の照合だけが行われる。リポジトリIDが食い違うと、取得の前にステップが失敗し、`job_failed`が届く |
| 監査の準備 | 取得の前にステップが失敗し、フローが失敗する。作業項目は失敗になり、Discordに`job_failed`が届く。監査の作業項目は再実行できない。失敗した期間は、次の週次の監査か、**レポート**の**今すぐ監査**で取り込む |
| フォームからのIssueの作成、Issue化の提案の処理 | cloneを開かない。リポジトリが`factory_repo`と一致するときだけ、オーナーの照合の関門が`factory_repo_id`を照合する。食い違いと404では、書き込まずに止める([作業項目を進める前の照合](#作業項目を進める前の照合)) |

404以外のすべて(認証の失敗、5xx、レート制限、通信断を含む)でIDを取得できなかったときは、noticeを残さず、例外としてそのまま失敗にする。
`self_update`のジョブは失敗し、`job_failed`が届く。
持続する障害を見逃さないためである。
`poll_issues`のデプロイ版の確認は、警告のログだけを残す。
次の回に照合が通れば、取得が再開する。

リポジトリ自体の改名や移管では、IDが変わらない。
正規の改名のときは、`factory_repo`のURLを新しい名前に直す。
`factory_repo_id`はそのまま使える。
originは取得の前にそのURLへ付け替わるので、古い名前のcloneが残らない。

照合の限界は次のとおりである。

- 照合は、cloneのロックを取った直後に行う。
  ロックの待ちは、照合から取得までの間に入らない。
- 照合の応答を読んでからfetchするまでの間に、リポジトリが入れ替わる余地は残る。
  この間は、originの付け替えと、fetchの接続である。
- ロックを持つ時間は、照合の1往復の分だけ延びる。
- `isRepoAllowed`は`factory_repo`を名前で常に許す。
  自己改善の起票と、`factory_repo`のPRの候補への採用は、名前のままである。
- [R-TB-26](security-risks.md#r-tb-26)
- [R-TB-25](security-risks.md#r-tb-25)

前回反映したshaが新しいHEADの祖先であることは、force pushで巻き戻す正規の運用が止まるので、反映の条件にしない。

## 作業を投入する

### ラベルで投入する

Issueに`factory`ラベルを付けると、Factoryがそれを拾う。
拾うのは、そのラベルを最後に付けたのが、次のアカウントのときだけである。

- FactoryのPATのアカウント。
- `factory_config`の`allowed_labeler_logins`に挙げたアカウント。
  `allowed_labeler_ids`にIDを入れたアカウントは、IDも一致するときだけである。

通常は、Factoryを動かすアカウントでラベルを付ける。
確認の仕組みは[ラベル付与の制限](security.md#ラベル付与の制限)にある。

許可されていない人がラベルを付けたIssueは拾わない。
Consoleの**システム**の「情報の通知」に、ラベルを付けたのが許可されていないユーザーである旨(`labeler_denied`)が残る。
付与者を確かめられなかったときも、同じく拾わない。
許可された人がラベルを付け直し、FactoryがそのIssueを取得すると、このnoticeは解決済みになる。
フォームで投入したIssueは`manual_intake_register`が登録するので、このnoticeは自動では解決されない。
Consoleからも解決できない種類なので、DBの掃除が保持期間を過ぎてから解決済みにする。
このnoticeの記録に失敗してもジョブは止まらず、**システム**の「作業項目に紐づかない失敗」に`labeler_denied:<owner>/<repo>#<Issue番号>`として残る。

付与者を確かめるイベントを取得できなかったときは、noticeを残さず、**システム**の「作業項目に紐づかない失敗」に`fetch_labeler:<owner>/<repo>#<Issue番号>`として残る。
取得の直前の確認で取得できなかったときは、同じ節に`confirm_labeler:<owner>/<repo>#<Issue番号>`として残る。
どちらもラベルは外れていないので、操作は要らない。
次のポーリングが、自動で拾い直す。
ラベルを付け直すと付与者が変わるので、付け直さない。

付与者を判定できないIssueは、Consoleの**要対応**に`labeler_check_limit`が残る。
判定できないのは、直近100件のラベルのイベントにトリガーラベルのイベントが無く、それより古いイベントが残っているときである。
このIssueは、人が対応するまで、ポーリングのたびに同じ取得を繰り返す。
拾わせたいときは、ラベルを外してから、許可された人が付け直す。
付け直したラベルのイベントが直近に入り、判定できるようになる。
対応した後は、Consoleでこのnoticeを解決する。

GitHubのIssueフォーム(`.github/ISSUE_TEMPLATE/factory-task.yml`)は、ラベルを付けない。
フォームが付けるラベルは起票者の権限によらず付くため、第三者の起票で作業が始まってしまうからである。
フォームで起票した後は、許可された人が手でラベルを付けて、作業を始める。

### フォームで投入する

Consoleの**作業項目**を開き、「新規投入」から入力して投入する。
FactoryがIssueを作成し、選んだ進め方の工程に乗せる。
通常の進め方は、ラベルで投入したときと同じ要件定義の工程に乗る。

| 入力 | 内容 |
| --- | --- |
| リポジトリ | 対象のリポジトリ。候補から選ぶか、`オーナー名/リポジトリ名`の形で入力する |
| 進め方 | 通常、直接、不具合の修正、文書の変更から選ぶ。初期値は通常 |
| 題名 | Issueの題名。256字まで |
| 目的 | このタスクで達成したい目的 |
| 再現手順、期待する動作、実際の動作 | 進め方が不具合の修正のときだけ出る。3つとも必須 |
| 受入基準 | 1行に1項目で書く(任意) |

投入できたときと、入力を破棄したときは、題名、目的、受入基準、不具合の3欄が空になり、進め方は通常に戻る。
リポジトリは残る。

次の入力は、投入せずに断られる。
断られたときは、何も投入されていないので、文の案内に従って直し、もう一度投入する。

- 許可されていないリポジトリ
- 題名か目的が空、または不具合の修正で3欄のどれかが空
- 題名が256字を超える、または目的、受入基準、不具合の欄がIssueの本文にして65,536字を超える
- 改行とタブ以外の制御文字や、文字の向きを変える記号
- 受け付けていない進め方。
  承認を省く進め方は、実装が止められていても断られる

投入できたら、作業項目は登録のあとに一覧へ現れる。
現れないときは、**システム**の「作業項目に紐づかない失敗」を確かめる。

「投入されたか分かりません」と出たときは、入力が残り、送信が止まる。
再送の前に、次の3つを確かめる。
投入されていたのに再送すると、Issue、作業項目、pipelineが重複するためである。

1. Windmillのジョブ一覧で、`manual_intake_submit`のジョブが待ち状態か実行中ではないか。
   待っている間は、`manual_intake`のジョブとIssueが無い。
   `manual_intake_submit`はtag`console`のscriptなので、Consoleのジョブの画面には出ない
2. Consoleのジョブの画面の履歴で、scriptを`manual_intake`に絞り、投入のジョブがあるか。
   投入のジョブの詳細に、フローが動いたか、失敗したかが出る
3. 対象リポジトリのIssueに、送った題名と同じIssueがあるか
   承認を省く進め方で送ったときは、案内に「送った進め方」が出る。
   進め方を変えて再送すると別の投入になり、先に作られたIssueと実装が重なる

投入されていなければ「確かめたので再送する」を押して、もう一度投入する。
投入されていたら「投入されていたので入力を破棄する」を押す。

再送は、前の送信と同じ冪等キーを付ける。
同じタブでリロードをせず、Issueに届く内容を変えずに再送したときは、Issueが増えない。
進め方や、不具合の修正の3欄を変えた再送は、Issueに届く内容が変わるので、新しいキーになる。
不具合の修正以外では、3欄に残った値はIssueに届かないので、変えても同じキーのままである。
リロードの後と別のタブの再送は、キーが止めないので、上の3つの確認が要る。

再送した投入のフローが、通知(`job_failed`)で失敗したときは、メッセージで原因を見分ける。

- `intake_key_in_flight`は、同じキーの投入がIssueを作っている途中か、途中で止まって予約が残っている。
  最初の投入のIssueが作業項目の一覧に出ているかを確かめ、無いときだけ新しく投入する。
  Consoleの再送は新しいキーになるため、10分待っても同じキーでは送れない。
  同時に走った二重の送信では、Issueが1件でも、後のフローが`intake_key_in_flight`で失敗として通知されうる。
  受け入れた挙動なので、Issueが1件なら対応は要らない。
- `intake_key_conflict`は、同じキーで内容が違う投入である。
  画面からは起きない。
  Consoleは、入力を変えた再送に新しいキーを使う。
  同じキーを手で付けた直接のフロー実行で起きる。
  最初の投入のIssueの有無を確かめ、無ければ、キーを空にして投入する。

キーの付いた`manual_intake`が登録のステップで失敗したとき、Windmillの画面からの再実行は、進め方で結果が分かれる。

- 通常の進め方は、再実行では直らない。
  Issueの番号が書かれた同じキーは、`reused`として登録を飛ばすためである。
- 承認を省く進め方は、再実行で直る。
  同じキーで再実行すると、Issueを作り直さず、そのIssueに作業項目が1件も無いときだけ登録する。
  作業項目が既にあるときは、何も始めない。

### 承認を省く進め方の投入

進め方の直接、不具合の修正、文書の変更は、要件定義と設計の承認を省き、Issueの本文を仕様にして実装を直接始める。
フォームで進め方を選ぶと、送信ボタンが「承認なしで投入する」になり、注記が出る。
フォームは、冪等キーを毎回付けて送る。

投入の前に、次を確かめる。
どれかが欠けると、フローは起動せず、フォームに断りの文が出る。

- 実装の停止スイッチ(`implement_enabled`)が真である。
  偽だと、実装が止められている旨の断りが出る。
  フォームは停止スイッチを読まないので、送った後に分かる。
- 対象のリポジトリが許可リストにあり、オーナーのIDの照合を通る。

不具合の修正は、再現手順と実際の動作をIssueの本文に、期待する動作を受入基準の先頭に組み込む。
実装は、この本文を仕様にして、再現するテストを先に書く。

実行すると、トリガーラベルなしのIssueが作られ、作業項目が`picked`で登録され、実装フローが起動する。
Issueのassigneeは設定しない。
Discordの`issue_claimed`の通知は届かない。

投入の結果は、Consoleの作業項目の一覧で確かめる。
実装フローの起動に失敗すると、作業項目は`needs_human`になり、noticeとDiscordに出る。
`implementing`へ移す更新が失敗したときは、作業項目が`picked`のまま残る。
`poll_issues`の照合が、猶予(10分と`claude_timeout_sec`の2倍の大きい方)を過ぎて失敗に移す。
失敗に移るまで待ち、通知に従って対応する。
実装フローの起動が成功して、ジョブIDだけを記録できなかったときは、作業項目が`implementing`のまま進む。
フローが自分でジョブIDを書くので、待つ必要は無い。
noticeが出ていても、実装の進み方で確かめる。

PRのレビューとマージは人が行う。
承認を省いたPRにも、人のレビューは強制されない。
PR本文の先頭に、進め方と、承認なしで実装した旨が載るので、確認してからマージする。

Consoleを使えないときは、Windmillで`manual_intake_submit`を直接実行して投入できる。
引数は`owner`、`repo`、`title`、`body`、`acceptance_criteria`、`profile`、`intake_key`で、`profile`に進め方、`intake_key`に小文字のUUIDを渡す。
承認を省く進め方でキーが無いと、`intake_key_required`で断られる。
同じ投入を再実行するときは、同じキーを使う。
不具合の修正の3欄は、引数に分けず、本文と受入基準に自分で組み込む。

### Consoleを使えない障害のとき

Consoleを使えない障害のときは、Windmillで手動投入のフロー(`f/factory/manual_intake`)を開く。
フォームに`owner`、`repo`、`title`、`body`、`acceptance_criteria`を入力して実行する。
`intake_key`は空にする。
キーを付けた実行は、再送を止めるための値なので、通常の進め方では手で付けない。
承認を省く進め方は、上の節のとおりキーが要る。
フローはリポジトリの名前と許可だけを検査するので、題名と本文の検証は、Consoleの「新規投入」より少ない。

### 取得の後に登録が失敗したとき

ラベルを外した直後にDBへの登録が失敗すると、そのIssueはラベルと作業項目の両方が無い状態になる。
Factoryはこれを自動では拾い直さない。

1. Discordの「人による対応が必要です: Issue #<番号>」の通知を開く。
   リンクはそのIssueである。
2. 失敗の原因を取り除く。
   原因は、Consoleの**システム**の「作業項目に紐づかない失敗」にある`claim_issue:<owner>/<repo>#<Issue番号>`か、`poll_issues`のジョブのログで確かめる。
   DBへの書き込みも失敗しているときは、Consoleに出ず、ジョブのログにだけ残る。
3. そのIssueに`factory`ラベルを付け直す。

作業項目が無いので、**再実行**は使えない。
`poll_issues`のジョブ自体は失敗しない。
Factoryが自分でラベルを付け直さないのは、次の2つの害があるためである。
ラベルの付与者の記録がFactoryに置き換わり、付与者の確認が、人ではなくFactoryに対して行われる。
DBの障害が続く間は、取得と失敗が`poll_issues`のたびに繰り返される。

DBが挿入を確定したのに応答が失われたときは、作業項目が既にある。
付け直したラベルは、作業項目が進行中とみなされて見送られる。
`poll_issues`の点検が作業項目を孤児と判定して失敗にすると、次のポーリングで拾い直される。

### ラベルを外した結果が分からないとき

Factoryは、Issueを取得するときにトリガーラベルを外す。
外す要求が応答なしかサーバーエラーで終わると、外せたのかが分からない。
そこでFactoryは、間隔を空けて最大3回までIssueを読み直す。

- ラベルが残っていれば、外れていないので、次のポーリングが拾い直す。
- ラベルが無ければ、タイムラインでそのラベルを最後に外したユーザーを調べる。
  FactoryのGitHubユーザーなら、取得できたものとして作業を続ける。
  別のユーザーなら、先に外した側が受け持つので引く。

次の場合は、外したのが誰か判断できない。

- 読み直しがすべて失敗した。
- タイムラインを読めなかった。
- タイムラインに、最後にラベルが付けられた後の削除の記録が無い。

読み直しやタイムラインの取得がレート制限に当たったときは、繰り返さずにここへ進む。
Issueにはラベルが無いので、次のポーリングは拾わない。

この場合は、Discordに「人による対応が必要です: Issue #<番号>」の通知が届く。
1回のポーリングで複数のIssueが該当したときは、通知は1件にまとまる。
通知の本文に、該当したIssueが`owner/repo#番号`とリンクの組で並び、タイトルとリンクの先は先頭のIssueになる。
並ぶのは10件までで、残りは件数で示す。

手動投入(`manual_intake`)のフローでは、このまとめた通知は届かない。
フローが失敗し、`on_error_flow`のジョブ失敗(`job_failed`)の通知が届く。
対象のIssueはその通知か、**システム**の「作業項目に紐づかない失敗」で確かめ、次の手順2から4に従う。

1. 通知のリンクからIssueを開く。
2. Consoleの**作業項目**で、そのIssueの作業が始まっているか確かめる。
3. 始まっていれば、何もしない。
4. 始まっていなければ、Issueに`factory`ラベルを付け直す。

原因は、Consoleの**システム**の「作業項目に紐づかない失敗」にある`claim_issue:<owner>/<repo>#<Issue番号>`か、`poll_issues`のジョブのログで確かめる。
`confirm_labeler:`と`fetch_labeler:`の失敗は、ラベルを外す前に起きているので、この手順の対象ではない。
付与者の確認で見送ったIssueのnoticeを記録できなかった失敗は、同じ節に`labeler_denied:<owner>/<repo>#<Issue番号>`で残る。

次の場合は、人の操作は要らない。

- 外す要求が失敗し、読み直してもラベルが残っていた。
  次のポーリングが拾い直す。
- ほかのインスタンスか人が先にラベルを外していた。
  そのIssueはFactoryが処理せず、Consoleの**システム**の「情報の通知」に`claim_race_lost`が残る。
- ラベルを外せた後に、Issueを読み直せなかった。
  作業はそのまま進む。

### PRのトリガーラベルが外れたままになったとき

FactoryはPRを取得するとき、トリガーラベル(`factory:review`か`factory:fix`)を外し、外せたか読み直して確かめる。
読み直しが数回とも失敗したときは、ラベルを付け直して引く。
次のポーリングが拾い直すので、人の操作は要らない。
Consoleの**システム**の「情報の通知」には、`claim_race_lost`として「確認できなかったのでラベルを戻した」旨が残る。
同じPRで作業を始めると、このnoticeは自動で解決済みになる。

外す要求が、応答なし、サーバーエラー、2xxの後で本文が切れた失敗のどれかで終わると、外せたのかが分からない。
このときも、FactoryはPRを読み直す。

- ラベルが残っていれば、外れていないので、次のポーリングが拾い直す。
  「情報の通知」に`claim_race_lost`が残り、同じPRで作業を始めると自動で解決済みになる。
- ラベルが無ければ、タイムラインでそのラベルを最後に外したユーザーを調べる。
  FactoryのGitHubユーザーなら、取得できたものとして作業を始める。
  別のユーザーなら、引く。
- 外したのが誰か判断できなければ、ラベルを付け直して引く。
  外したのが誰か判断できない条件は、[ラベルを外した結果が分からないとき](#ラベルを外した結果が分からないとき)のIssueと同じである。

次の場合は、ラベルが外れたままで、作業項目も無い。
Factoryはそのまま拾い直さない。

- 読み直しがレート制限で失敗した。
  この場合は、同じ制限に当たるので、ラベルも付け直さない。
- ラベルの付け直しも失敗した。

この場合は、Discordに「人による対応が必要です: PR #<番号>」の通知が届く。
1回のポーリングで複数のPRが該当したときは、通知は1件にまとまる。
本文に、該当したPRがリンクと外れたラベルの組で並ぶ。
並ぶのは10件までで、残りは件数で示す。

1. 通知のリンクからPRを開く。
2. PRにラベルが既に付いていないか確かめる。
3. Consoleの**作業項目**で、同じPRの`pr_review`か`pr_fix`が始まっていないか確かめる。
4. どちらも該当しなければ、レート制限の解除を待ってから、外れたラベル(通知の括弧内)をPRに付け直す。

Consoleの**システム**の「作業項目に紐づかない失敗」には、次の行が残る。

- `trigger_review:<owner>/<repo>#<PR番号>`
- `trigger_fix:<owner>/<repo>#<PR番号>`

作業項目が無いので、**再実行**は使えない。
`poll_prs`のジョブ自体は失敗しない。
Consoleの**要対応**には、PRごとに`pr_trigger_label_left_removed`が残る。
Discordの通知を見逃しても、こちらから該当のPRを確かめられる。
そのPRとラベルで次に作業を始めると、このnoticeは自動で解決済みになる。
取得が不要なら、人がConsoleで解決する。
未解決のあいだに同じPRとラベルで再発しても、行は増えず、最初の日時のまま残る。
Discordには毎回届く。
リポジトリの改名や移管でPRの表記が変わると、自動では解決されないので、人がConsoleで解決する。

### assigneeが付かなかったとき

Factoryがラベルを外せていれば、Issueにassigneeが付いていなくても作業は進む。
Consoleの**要対応**に`claim_assignee_missing`が残る。
GitHubは、push権限を持たないユーザーのassigneeへの追加を、成功の応答のまま無視するためである。

FactoryのGitHubユーザーが、そのリポジトリのpush権限を持つcollaboratorか確かめる。
持っていなければ、権限を付ける。

## 要件定義を承認・却下する

要件定義の生成が終わると、Discordに承認待ちの通知が届く。

1. 通知のリンクか、Consoleの**要対応**を開く。
2. 一覧から承認を選ぶ。
3. 詳細に表示される取り込み時点のIssue、要件定義書、未確定事項を読む。
4. 承認するなら**承認**を押し、確認のダイアログで承認する。
5. 却下するなら、却下理由を書いてから**却下**を押す。
   要件定義の却下では、確認のダイアログが出る。

承認した人は、実行したWindmillのユーザー(`WM_USERNAME`、無ければ`WM_EMAIL`)として記録される。
承認すると、FactoryはIssueに要件定義へのConsoleのリンクを1件だけ投稿する。

却下すると、Factoryは却下理由を反映して要件定義を作り直し、もう一度承認待ちにする。
作り直すたびに試行回数(attempt)が1つ増える。
試行回数が上限(`max_attempts`、既定3)に達した後の却下では、作業項目は人の対応待ち(`needs_human`)になる。

承認依頼には7日の期限がある。
期限までに判断しなかった作業項目は期限切れ(`expired`)になり、Discordに人の対応を求める通知が届く。
期限切れの作業項目は、[失敗した作業を再実行する](#失敗した作業を再実行する)の手順で再実行できる。
最新の依頼が承認済みなら承認の後の工程から始まり、そうでなければ要件定義を作り直す。
作り直した要件定義は、取り込み内容を現在のIssueで更新し、あらためて承認が要る。

### Windmillから直接承認する

Consoleを使えないときは、Windmillで`f/factory/approval_decide`を開き、次の値を入力して実行する。

| 入力 | 値 |
| --- | --- |
| `approval_request_id` | 承認依頼のID。Consoleの**要対応**で承認を選んだときのURL(`?approval=<id>`)にある |
| `decision` | `approve`か`reject` |
| `reason` | 却下の理由。却下では必須 |
| `note` | 補足(任意) |
| `options` | 要件定義の承認では空のままにする |

### 要件定義書を読む

Consoleの**作業項目**にある要件定義の一覧から、要件定義書を選んで読める。
一覧には、承認待ちのものに限らず、要件定義のあるすべての作業項目が並ぶ。
書の画面では、試行を切り替えられる。
本文は見出し・表・図を含む文書ページの形で表示され、draw.ioの図もページ内に描かれる。

Issueの承認のコメントと、Discordの承認済みの通知のリンクは、要件定義書のページを開く。
ページは承認した試行のもの(`/console/items/<work_item_id>/requirements?attempt=<k>`)である。
承認待ちのDiscordの通知のリンクは、Consoleの要対応でその承認依頼を選んだ状態(`/console/?approval=<id>`)で開く。

旧Consoleは廃止した。
過去に投稿された旧Consoleのリンクは、Caddyが`/console/`へ飛ばす。
例は`/apps/get/f/factory/factory_console#requirements/<work_item_id>`である。
新しいConsoleは、そのフラグメントを同じ要件定義書のページに読み替える。
フラグメントの形に合わないリンクは、要対応の画面に着く。
その場合は、リンクの文に書かれた`work_item_id`で作業項目を探す。

### 承認の前後でIssueを直したいとき

Factoryは、Issueを取り込んだ時点の題名と本文で要件定義を作り、実装もその内容で行う。
取り込んだ後にIssueを書き換えても、要件定義と実装のどちらにも反映されない。

- 承認の前に直したいとき: Issueは書き換えず、Consoleの**要対応**で却下する。
  直したい内容を却下理由に書くと、Factoryがそれを反映して要件定義を作り直す。
- 承認の後に作り直したいとき: まず既存のPRを閉じてから、`factory`ラベルをIssueに付け直す。
  新しいサイクルは別の作業項目・別のブランチ・別のPRになるので、古いPRを残すと重複する。

承認の時点で、現在のIssueの題名か本文が取り込み時点と違うと、承認は断られ、Issueが変わった旨のエラーが出る。
次のどちらかで進める。

- Issueを取り込み時点の内容に戻してから、もう一度承認する。
  取り込み時点の内容は、Consoleの**要対応**で、承認を選ぶと確かめられる。
- 却下する。
  却下による作り直しは、現在のIssueの題名と本文を取り込み直して要件定義を作る。
  作り直した要件定義には、あらためて承認が要る。

GitHubから取得できずに断られたときは、しばらく待ってもう一度承認する。
Issueが移されたか削除されたときは、待っても通らないので、却下する。
取得の確認は、GitHubが遅いと1回の承認で最長10秒、Console用workerの2つの枠の1つを塞ぐ。

#### 取り込み内容を更新したとき

却下や再実行による作り直しで、取り込んだ題名と本文を現在のIssueの内容へ更新すると、次の知らせが出る。

- Discordの「取り込み内容を更新」と、noticeの`intake_refreshed`(再実行ではnoticeだけ)。
- Consoleの**要対応**で承認を選んだときの、取り込み時点のIssueの警告。
- 実装のPR本文の「確認して欲しい点」の1行。

Issueが取り込み後に書き換えられたということなので、Consoleで更新後の内容を確かめてから承認する。
確かめずに承認すると、書き換え後の内容がそのまま実装に渡る。
更新の前後の題名と本文は、作業項目の履歴(`work_item_events`)に、文字数とハッシュで残る。

#### 残る制限

承認者は、Consoleの**要対応**で、取り込み時点のIssueと更新の警告を確かめて承認する。
Consoleは、内容を表示できないあいだ、承認を押せないようにする。
確かめずに承認しても、承認の前の確認が働くので、承認の時点で書き換わっているIssueは通らない。
ただし、却下を挟むと、書き換え後の内容が取り込み直されて承認画面に出る。
更新を知らせるDiscordとnoticeを見て、Consoleで確かめる。
確認から承認の記録までの間の書き換えは防げない。
実装後のPR本文の注記が残りを拾う。

承認の後にIssueを書き換えると、実装のPR本文の「確認して欲しい点」にその旨が1行出る。

## 失敗した作業を再実行する

止まった作業項目は、`f/factory/retry_work_item`で再開する。
再実行はトリガーラベルを付け直さず、対応するフローを直接起動する。
GitHubには何も書き込まない。

どこから実行するかは、作業項目の止まり方で決まる。

| 止まり方 | 実行のしかた |
| --- | --- |
| ジョブが失敗した、人の対応待ち、期限切れで止まった | Consoleの**要対応**で失敗の行を選び、**再実行**を押す |
| ブロックで止まった | Windmillで`f/factory/retry_work_item`を開き、作業項目のID(`work_item_id`)を入れて実行する |

**要対応**の失敗には、状態が失敗、人の対応待ち、期限切れの作業項目が並ぶ。
ブロックは安全策で止めた状態であり、失敗ではないので、**要対応**に出ない。
作業項目のIDは、Consoleの**作業項目**で、範囲を「すべて」にして確かめる。
失敗、人の対応待ち、期限切れの作業項目は終わった状態で、既定の進行中に出ないためである。

再実行できる状態と、作業項目の種類ごとに起動するフローは、[作業項目の状態とリース](internals/work-items.md)の「再実行」にある。
監査の作業項目は再実行できない。
監査が失敗した期間は、次の週次の監査か、**レポート**の**今すぐ監査**で取り込む。

### 閉じたIssueやPRの失敗

Consoleの要対応の一覧にある失敗、人の対応待ち、期限切れの作業項目は、対象のIssueやPRを閉じると自動で外れる。
`poll_issues`が5分ごとに、閉じたものを取り消し(`cancelled`)にするためである。
PRのcloseにはマージを含む。
Discordには通知しない。

マージ済みのPRは、閉じた人によらず取り消す。
それ以外は、作者以外の人が閉じたときに取り消す。
作者自身が閉じたときは、作者の関係が許可する関係(`allowed_labeler_associations`、既定はOWNER、MEMBER、COLLABORATOR)のときだけ取り消す。
Botが閉じた対象と、GitHubが閉じた人を返さない対象は、取り消さず、一覧に残す。
判定の理由は[セキュリティ](security.md)の「閉じた人の確認」に書く。
一覧に残した理由と対象は、`poll_issues`のジョブのログにinfoで出る。
一覧に残った作業項目は、再実行して扱うか、リポジトリの権限を持つ人が開き直して閉じ直す。

Botが閉じた対象と、作者が許可されない関係で閉じた対象は、要対応に残る。
たとえば、stale Botが閉じた対象や、依存更新のBotが自分のPRを閉じた対象である。
残った対象は毎回調べ直すので、問い合わせの上限を使い続けることがある。
closing keywordを含むPRをmerge queueがマージしたとき、Issueの`closed_by`がBotか空になるかは実機で確かめる。
Botか空になるなら、Issueの作業項目も要対応に残る。
外すには、人が対象を開き直してから閉じ直す。
PRの作業項目は、マージ済みなら`merged_at`で外れるので、この操作は要らない。
削除された対象(404、410)と、移動したIssue(リダイレクト先の状態を読む)も、一覧に残る。
Consoleから外す操作は無い。

再実行しない失敗を一覧から外したいときは、権限を持つ人が対象のIssueかPRを閉じる。
失敗した監査の作業項目は、対象のIssueやPRが無いので外れない。
対象のIssueやリポジトリが削除されたり、アクセスを失ったりした作業項目も外れない。
この場合は`poll_issues`のジョブのログに警告が残る。

取り消した作業項目は、対象を開き直してから再実行できる。
作業項目のIDはConsoleの**作業項目**で、範囲を「すべて」にして確かめ、Windmillの`f/factory/retry_work_item`に渡して実行する。
取り消した作業項目は終わった状態で、既定の進行中に出ないためである。
取り消す前の状態から再実行するのと同じ扱いになる。
対象が閉じたままのときと、開いているかGitHubで確かめられないときは、再実行を断る。
取り消す前の状態からの再実行が二度とできなくなるのを避けるためで、先に開き直してから、もう一度実行する。
この再実行ができるのは、この照合が取り消した作業項目だけである。
Issueの新しいサイクルに置き換えられた作業項目などは、再実行できない。

取り消しは`cancelled`として集計され、`updated_at`も取り消した時刻に更新される。
そのため、**レポート**の分析のリードタイムと、DBの保持期間は、閉じた時刻ではなく取り消した時刻から数える。
PRを開き直しても、追跡は自動では戻らない。
PRは、開き直してから`retry_work_item`で再実行する方法を勧める。
トリガーラベルの付け直しと再実行の両方を行うと、同じPRに作業項目が並んで動くので避ける。
取り消した後にトリガーラベルを付け直したときの断りは、[再実行が拒否される場合](#再実行が拒否される場合)に書く。
トリガーラベルの付け直しは、取り消す前の状態から再実行できないときに使う。

`poll_issues`が1回の実行でGitHubに問い合わせる対象は、30件までである。
対象ごとにIssueかPRの取得を1回行い、閉じた人もこの応答で確かめる。
要対応の一覧が多いときは、前回の続きから調べるので、閉じたものが外れるまでに数回の実行がかかる。
上限に達したことは`poll_issues`のジョブのログに警告で残る。
rate limitを受けたときは、その回の問い合わせを打ち切り、次の実行で続ける。
取得の失敗は、1回の実行につき1行だけ失敗に記録する。

### 再実行が拒否される場合

次のときは、Factoryが理由を示して再実行を拒否する。

| 状況 | 人がすること |
| --- | --- |
| 承認が試行回数に一致しているのに、`implement_enabled`が無効 | 承認済みの要件定義を作り直さないための拒否である。実装させるなら`implement_enabled`を有効にする。要件定義が書き換わって止まったときと、要件定義を作り直そうとして止まったときは、拒否されずに要件定義を作り直す |
| 承認済みの作業項目で、承認が試行回数に一致しない | 表示された理由を確かめる |
| 作業項目のフローのジョブがまだ実行中か、キュー待ち | Consoleのジョブの詳細で**ジョブを中止**を押す([動いているジョブを中止する](#動いているジョブを中止する))か、終わるのを待ってから再実行する |
| ジョブの状態を読めない(Windmill APIの一時的な障害など) | 時間をおいて再実行する |
| 読み取った後に、別の処理が作業項目の状態を変えた | Consoleの**作業項目**で、範囲を「すべて」にして今の状態を確かめる |
| 取り消された作業項目の対象のIssueやPRが閉じたまま、または開いているか確かめられない | 対象を開き直して、もう一度実行する。確かめられないときは、時間をおいて実行する |
| 取り消された作業項目の`pr_review`か`pr_fix`に、同じPRで`id`の大きい作業項目がある(取り消した後にトリガーラベルを付け直した)。エラーは「work item N … now tracks the same pull request … follow work item M」 | 取り消した作業項目は再実行せず、エラーに表示された新しい作業項目(M)に従う |
| 取り消された作業項目の対象が移動した。Issueの移動、リポジトリの改名、所有者の移管でGitHubがリダイレクトを返す。エラーは「was redirected (the issue or repository moved); it cannot be restarted」 | 待っても直らず、再実行は常に断られる。Issueなら、移した先のIssueにトリガーラベルを付けて新しく始める |

別の実行が先に作業項目を取っていたときの表示と、再実行の内部の仕組みは、[作業項目の状態とリース](internals/work-items.md)を参照する。

### Windmillの再実行機能は使わない

フローの再実行には、必ず`retry_work_item`を使う。
Windmillの画面でフローを再実行したり、途中のステップから再開したり、フローを直接実行したりすると、新しいジョブIDで動くため何もせずに終わる。
元の実行で進んでいるClaudeや検査も止まらない。

要件定義のフローをWindmillから直接動かすと、作業項目が終端でなければ最大60秒待ってから何もせずに終わる。
この実行が例外で失敗しても、作業項目は失敗にならない。

### 動いているジョブを中止する

実行中か待ちの作業項目のフローは、Consoleのジョブの詳細から中止できる。
Windmillのジョブには、取り消した人(`canceled_by`)と理由(`canceled_reason`)が残る。
Consoleから中止しても、Windmillの画面や`wmill job cancel`で取り消しても同じである。
Consoleから中止すると、これに加えて、操作の記録(`factory.console_actions`)に、操作の名前と対象のジョブが残る。
違いは範囲と期間である。
操作の記録は90日残る。
Consoleでジョブ履歴を読める期間は30日である。
Windmillの画面からは、許可したフローの外のジョブも取り消せるが、操作の記録には残らない。
そのため、許可したフローはConsoleから中止する。

1. Consoleの**ジョブ**の**実行中と待ち**で、止めるフローを開く。
2. 概要の見出しにある**ジョブを中止**を押す。
3. 確認のダイアログで、対象と、残るものを読み、**中止する**を押す。
   ダイアログを開いた直後は**取り消す**にフォーカスがあるので、Enterだけでは中止しない。

**ジョブを中止**が出るのは、親を持たない、実行中か待ちの、次のフローのジョブだけである。
対象のフローは、audit、dependabot、design、implement、pipeline、pr_fix、pr_reviewである。
次のジョブには出ない。
子のステップ、scriptのジョブ、予定の時刻が先のジョブ、手動投入のフロー(`manual_intake`)、PRレビューの投入のフロー(`pr_review_intake`)である。
scriptのジョブには、`self_update`、migrationを走らせるscript、`cleanup_*`も含む。
作業項目を持たないフローを途中で止めると、次のことが起きうるためである。
手動投入では、Issueだけが作られて工程に乗らない。
PRレビューの投入では、ジョブIDの無い`reviewing`の行が残る。

中止しても、止まらないものがある。

- 子プロセス(Claudeと検査)は止まらない。
  Claudeは、ターン数と費用の上限まで動き続けることがあり、その費用は日次予算に数えられないことがある。
- 毎日03:00の作業領域の掃除が止めるのは、実行の上限時間に5分を足した時間を過ぎたClaudeのプロセスだけである。
  それより前のプロセスは残る。
- implementでは、同じ作業項目の再実行の準備のステップが、前の実行が残したプロセスを止める。
  残ったプロセスの扱いは、[実装フローを再実行するとき](operations/stages.md#実装フローを再実行するとき)にある。
- 作業項目は、リースが中止したジョブを指したまま残る。
  次の照合(5分ごと)が失敗にする。
  失敗になったら、**再実行**で続ける。
- 承認待ちの作業項目は、照合が失敗にしない。
  承認依頼を記録して承認待ちへ移した後、通知の前に中止すると、承認待ちのまま残り、通知は届かないことがある。
  要件定義のpipelineと設計のdesignは、どちらもこの順序で動く。
  Consoleの**要対応**で、承認依頼があるかを確かめる。
- dependabotの作業項目は、中止した後に再実行できない。
  PRを確かめて、マージするか閉じる。
- pr_fixの作業項目が失敗になると、保留中の`factory:fix`ラベルがあれば、次のポーリングが新しい修正を始める。
  残ったプロセスがworktreeのロックを持っていると、その準備はブロックで止まる([修正を再実行する](operations/pr.md#修正を再実行する))。
- CIの失敗を直すpr_fixを中止すると、作業項目が失敗になる。
  その後、CIの自動修正が有効なら、`watch_pr_ci`が同じPRの修正を起動し直す。
  中止した回も、回数の上限(`pr_ci_fix_max_rounds`)に数える。
  起動し直したくないときは、中止の前に、[失敗の自動修正を有効にする](operations/pr.md#失敗の自動修正を有効にする)の設定で自動修正を止める。

結果は、画面に出る知らせで確かめる。
知らせには、中止の後に読み直した作業項目の状態が載る。
知らせが「中止を依頼しました。ジョブはまだ止まっていません」と言うときは、少し待って、見出しの**状態を更新**を押す。
知らせが「すでに中止済みです」と言うときは、ジョブが止まる途中なので、少し待って**状態を更新**を押す。
知らせが「操作の記録を残せませんでした」と言うときは、中止は済んでいる。
誰が中止したかは、ジョブのログで確かめる。
通信が切れたなど、結果が分からない失敗のときは、ジョブの詳細を読み直して、状態が取消になっているかを見る。
もう一度押さない。

操作の記録は、表`factory.console_actions`に90日残る。
中止のほかに、作業項目の再実行、定期ジョブの再実行、設定の変更、保留と凍結の解除、手動投入、PRレビューの投入も残る。
中止の記録は、操作が`job_cancel`、対象がジョブのIDである。
記録を残せない状態では、中止、定期ジョブの再実行、設定の変更は断られる。
作業項目の再実行と解除は通り、知らせが記録の失敗を伝える。
手動投入とPRレビューの投入は通り、記録の失敗はジョブの結果の`action_audit`に出る。

### 作業項目を中止する

続けない作業項目は、Consoleの作業項目の詳細の概要から中止できる。
「作業項目を中止」は、実行中のジョブが無い作業項目(承認待ち、承認済み、止まった状態)にだけ出る。
中止できる種別と状態は、[作業項目の状態とリース](internals/work-items.md#人による中止)の表にある。
実行中の作業項目は、終わるのを待つか、ジョブの詳細からジョブを中止して、止まった後に中止する。

中止すると、次のとおりになる。

- 作業項目は取り消しになり、再開できない。
  Issue、PRのレビュー、PRの修正を続けたくなったときは、トリガーラベルを付け直して、新しいサイクルを始める。
- 承認待ちのIssueの、要件定義と設計の承認依頼は、期限切れになる。
  その依頼は、承認と却下のどちらもできなくなる。
- 監査、PRのレビュー、PRの修正のIssue化の提案の依頼は、状態によらず残る。
- ブランチとPRは残る。
  要らなければ、人が閉じるか消す。
- PRの作業項目を中止すると、CIの失敗は、headが同じ間、Factoryが自動で直さない。
  競合は、次に競合が起きるまで、自動で直さない。
- Issueを中止すると、そのブランチのPRのCIの失敗と競合を、Factoryが自動で直さない。
  この保留は、同じPRでは外れない。
  直すときは、人がPRに修正のラベルを付け直す。
- PRのheadが動くと、ラベルを付け直さなくても、新しいレビューの始まることがある。

確かめている間に状態が変わったときは、中止せずに断る。
状態を更新して、もう一度確かめる。
PRに、より新しい作業項目があるときも断る。
最新でない行は中止できず、要対応の一覧に残ることがある。
その行は再実行で進めるか、そのPRの最新の作業項目を中止する。
中止の記録は、表`factory.console_actions`に、操作が`work_item_cancel`、対象が`work_item:<番号>`で残る。
記録を残せない状態では、中止は断られる。

### 失敗した定期ジョブを再実行する

定期ジョブが失敗したとき、Consoleのジョブの詳細から再実行できる。
押すたびに、scheduleの引数で1回起動する。
再実行できるのは、次の2つの定期処理の、失敗した実行だけである。

| 定期処理 | 再実行すると起こること |
| --- | --- |
| `collect_github` | GitHubの状態を1回集め直す。GitHub APIの使用量を使う |
| `auto_retry_pr_review` | 待ちを過ぎた、一時的な失敗のPRレビューを再開する。再開は同じ作業項目につき3回までで、この再実行も数える |

ほかの定期処理は、再実行できない。
次の回が自動で取り直すものと、繰り返すと二重の副作用が出うるものと、タイムアウトが間隔より長いものがあるためである。
除いた理由は、再実行のscriptの許可表に注記してある。

1. Consoleの**ジョブ**の**履歴**で、失敗した定期ジョブを開く。
2. 概要の見出しにある**ジョブを再実行**を押す。
3. 確認のダイアログで、処理と失敗したジョブを読み、**再実行する**を押す。
   ダイアログを開いた直後は**取り消す**にフォーカスがあるので、Enterだけでは再実行しない。
4. 画面が、新しく始まったジョブの詳細に移る。
   結果は、その詳細で確かめる。

再実行は、scheduleに定義された引数で動く。
画面から引数は渡せない。
失敗したジョブは、そのまま残る。
再実行の失敗は、定期の失敗の通知に載らない。
新しいジョブの状態を、必ず自分で確かめる。
再実行は元に戻せない。
繰り返しても二重の副作用が出ない処理だけを対象にしている。
押すたびに1回起動する。
続けて押すと、起動した回数だけ動く。

次のときは、再実行を断る。
知らせが理由を伝える。

| 知らせの趣旨 | 人がすること |
| --- | --- |
| 同じ処理が実行中か待ち | 終わるのを待つ。定期の回が実行中のときも、これに当たる |
| 次の定期実行がもうすぐ始まる | 次の回を待つ。処理のタイムアウト(120秒)より近いと、再実行と重なるためである |
| scheduleが無効 | 無効にしたのが意図なら、再実行しない。有効に戻すのは人がWindmillで行う |
| scheduleの定義が変わった、または引数に参照がある | scheduleの定義を確かめる |
| 失敗したジョブではない、まだ終わっていない、再実行できない対象 | 対象のジョブを確かめる |
| 操作者を確認できない、操作の記録を残せない | 記録の表が無いか、DBに届かない。[操作の記録](internals/console/security.md#操作の記録)の状態を確かめる |

操作の記録は、操作が`job_rerun`、対象が失敗したジョブのIDで、`script`に再実行した処理、`rerun_job`に新しいジョブのIDが残る。

### 照合が動いていないとき

中止した作業項目は、5分ごとの照合(`poll_issues`)が失敗にする。
中止から10分たっても、承認待ちでない作業項目が進行中のまま変わらないときは、照合が動いていない。
次の順に確かめる。

1. Consoleの**ジョブ**の履歴で、`poll_issues`の直近のジョブを開く。
   5分ごとに並んでいて、成功していれば、照合は動いている。
2. 直近のジョブが失敗しているときは、ログを読む。
   ログの先頭に`health check ok`が無ければ、ヘルスチェック(GitHubのトークンで自分を引く最初の確認)に失敗している。
   ヘルスチェックに失敗すると、ジョブ全体が失敗し、照合まで進まない。
   トークンは[秘密をローテーションする](#秘密をローテーションする)で直す。
3. 直近のジョブが5分ごとに並んでいないときは、スケジュールの凍結が有効でないかを、端末の`mise run freeze:list`で確かめる。
   `poll_issues`の凍結が有効なら、解除か期限切れまで動かない。
   解除はConsoleのシステムの画面の「保留と凍結」から行う([凍結とdeployの保留の内部仕様](internals/freezes.md))。
4. 前の実行が長引いていないかを、実行中のジョブで確かめる。
   前の回が終わらない間は、次の回が飛ばされる(`no_flow_overlap`)。
5. ジョブが成功していても、作業項目1件の読み取りに失敗すると、その作業項目だけ飛ばされる。
   ログから`reconcile:`で始まる失敗を探し、対象の作業項目を確かめる。

照合が動くようになると、次の回で作業項目が失敗になる。

### GitHubのrate limitで失敗したとき

GitHub APIのrate limitの解除を待てないと、作業項目は`GitHubRateLimitError`で失敗になる。
拒まれた要求の副作用は起きていない。
解除を待ってから、Consoleの**要対応**で失敗の行を選んで再実行する。

rate limitが原因で人の対応待ちになったときは、通知の次の操作に、解除を待ってから再実行するよう表示される。
人の対応待ちの作業項目も**要対応**に出るので、解除を待ってから、同じ手順で再実行する。
待つ時間の上限などの仕組みは[通知とrate limit](internals/notifications.md)を参照する。

PRのトリガーラベルを外した直後のrate limitで、ラベルが外れたままになることがある。
作業項目が無く、**システム**の「作業項目に紐づかない失敗」の`trigger_review:`と`trigger_fix:`の行からは再実行できない。
Discordの通知に従い、解除を待ってからラベルを付け直す([PRのトリガーラベルが外れたままになったとき](#prのトリガーラベルが外れたままになったとき))。

### Claudeの実行が上限で失敗したとき

次の4つのステップは、Claudeの実行が上限で失敗すると、flowの再試行をしない。
PRレビューの生成、PR修正の修正、要件定義の生成、監査の生成である。
上限は次の3つである。

- `claude_timeout_sec`での打ち切り(`timeout`)
- `max_budget_usd_per_run`の超過(`run_budget_exceeded`)
- サブスクリプションの使用上限(`usage_limit`)

すぐ再試行しても同じ失敗になり、費用だけがかかるためである。
全停止(`stopped`)で止めた実行も、flowの再試行をしない。
解除の直後に動かさないためである。
flowは失敗のまま終わる。
作業項目は失敗になり、Discordに`job_failed`が届く。
使用上限か全停止で失敗したCIを直す回には、`job_failed`を送らない。
検証のステップで止まった回の`needs_human`も送らない。
監視が同じ行を起動し直すので、使用上限が続く間に同じ通知を重ねないためである。
それ以外のClaudeの失敗では、Windmillが再試行する。

Windmillのジョブの結果とログには、例外の文の先頭の`[no-flow-retry]`が残る。
このタグはflowの再試行を止める印で、失敗の原因ではない。
タグの後ろの文が失敗の内容である。
作業項目の注記と`job_failed`の本文では、`on_error_flow`がタグを外す。

使用上限のときは、要対応の通知`claude_usage_limit`も残る。
使用上限はアカウント全体に効くので、この通知は上の4つに限らず、Claudeを呼ぶどのflowでも残る。
本文は固定の文なので、未解決の間は新しい通知を足さず、1回の上限で通知は1件になる。
例外で終わるflowは**要対応**に失敗の行を残すので、動かし直す実行はその行で分かる。
例外を投げないflow(`dependabot_assess`と`investigate_generate`)は、失敗の行を残さない。
どちらのflowでも、当たった実行は次の手順で調べられる。

1. 次のコマンドで、使用上限で終わった実行のステージと作業項目を読む。

   ```bash
   mise exec -- docker compose -f infra/docker-compose.yml exec db psql -U postgres -d datatable_db -c "SELECT created_at, stage, work_item_id FROM factory.agent_runs WHERE failure_reason = 'usage_limit' ORDER BY created_at DESC LIMIT 20"
   ```

2. ステップのジョブを次のコマンドで探す。
   ステージ`dependabot_assess`のステップは`f/factory/steps/dependabot_assess`である。
   ステージ`investigate`のステップは`f/factory/steps/investigate_generate`である。

   ```bash
   mise exec -- wmill job list --all --script-path <ステップのパス> --limit 10
   ```

3. 次のコマンドでログを読み、`claude usage limit reached`の行を探す。
   行の`path`がflowのパスで、`job_id`がそのflowのジョブのIDである。

   ```bash
   mise exec -- wmill job logs <ジョブのID>
   ```

timeoutで打ち切った実行は、標準出力に費用があればその値を、無ければ上限の値を記録し、日次予算に数える。
上限は`max_budget_usd_per_run`で、実装のフローでは`implement_max_budget_usd_per_run`である。
打ち切った実行の費用は結果に無いことが多いので、上限の値で少なく数えないようにする。
そのため、timeoutが続いた日は、日次予算に早く達する。
起動した後にシグナルで終わった実行(終了コードが129から192)も、同じ順で記録する。
終了コードが0以外でも、結果を読めれば、その実費と使用量を記録する。
結果の形でなくても、標準出力のJSONに費用があれば、その値を記録する。
起動の直後に終わる失敗(認証の失敗など)は、日次予算を使い切らないよう、費用を記録しない。
起動しなかった実行の費用も記録しない。
実装のフローの期限が残っていなくて起動しなかった実行は、失敗の種類を`not_started`で記録する。
起動していないので、モデルの昇格の失敗に数えない。

全停止で止めた実行も、標準出力に費用があればその値を、無ければ上限の値を記録する。
そのため、全停止の後は、日次予算に早く達しうる。
達したときは、JSTの翌0時まで待つか、`daily_budget_usd`を上げる。
`daily_budget_usd`は、Windmillの画面で`f/factory/factory_config`を開いて書く。
Consoleからは上げられない([設定を止める向きに変える](operations/stop.md#設定を止める向きに変える))。

上限が戻ってから、Consoleの**要対応**で失敗の行を選んで再実行する。
再実行の経路が違うものは、次のとおりである。

- 監査は再実行できないので、**レポート**の**今すぐ監査**で起動し直す。
  起動し直さなくても、次の週次の監査が失敗した期間を取り込む。
- 調査は再実行できないので、同じ依頼を投入し直す。
- dependabotの更新は再実行できないので、PRを人が確かめ、手でマージするか閉じる。
  新しいコミットが積まれると、自動で再び対象になる。
- CIを直す回は行を保留する。
  使用上限と全停止の行は、監視が自動で起動し直す([Claudeの失敗で保留したCIの修正を起動し直す](#claudeの失敗で保留したciの修正を起動し直す))。
- 競合を直す回は行を`fix_stopped`で保留する。
  人が競合を解消するか、PRにpushする。

#### 使用上限の判定を確かめる

使用上限の応答の形はClaude Codeの文書に無く、実機でも確かめていない。
判定の文面は、workerのClaude Codeのバイナリの文字列から取った。
結果の本文か`errors`のどれかの行が次の文面で始まれば、使用上限とする。
行頭の`API Error:`の前置きは無視する。
大文字と小文字は区別しない。

- `You've hit your`か`You've reached your`で、同じ行に`limit`か`team's shared budget`があるもの
- `You're out of usage credits`
- `You're out of extra usage`
- `Your org is out of usage`
- `Your seat type doesn't include usage`
- `Your seat type doesn't include extra usage`
- `Your usage allocation has been disabled`
- `Your group's usage limit is set to $0`
- 40字までの主語に続く`requires usage credits`

`api_error_status`の429だけでは使用上限にしない。
一時的なレート制限は、Windmillの再試行で回復するためである。
`claude_usage_limit`が初めて出たときと、使用上限に当たったのに出なかったときは、次の手順で確かめる。

1. 次のコマンドで、上限の文を含む直近の失敗の記録を読む。

   ```bash
   mise exec -- docker compose -f infra/docker-compose.yml exec db psql -U postgres -d datatable_db -c "SELECT created_at, stage, failure_reason, error FROM factory.agent_runs WHERE failure_reason = 'usage_limit' OR error ~* 'limit|usage|hit your|reached your' ORDER BY created_at DESC LIMIT 5"
   ```

2. `failure_reason`と、`error`の`subtype=`、`api_error_status=`、その後の本文を見る。
   `is_error`の結果の`failure_reason`は`usage_limit`、`run_budget_exceeded`、`claude_error`のどれかである。
3. 使用上限の失敗の`failure_reason`が`claude_error`なら、判定が漏れている。
   `failure_reason`が`non_zero_exit`か`invalid_json`の失敗に使用上限の文があるときも、同じである。
   本文と終了の形をIssueに書き、`f/factory/lib/claude.ts`の判定を直す。
4. 判定が正しければ、Consoleで`claude_usage_limit`を解決する。

### 既定のブランチが食い違って実装フローが失敗するとき

実装フローの準備が、次のエラーで失敗することがある。

```text
origin HEAD is refs/heads/<新しい既定のブランチ>, not refs/heads/<古い既定のブランチ>
```

workerにある対象リポジトリのclone(`/workspaces/<owner>/<repo>/main`)の`origin/HEAD`が、GitHubの既定のブランチと違うことが原因である。
対象リポジトリの既定のブランチの名前を変えたときと、検査コマンドがcloneの`origin/HEAD`を書き換えたときに起きる。
fetchでは`origin/HEAD`が直らないので、再実行しても同じエラーで失敗する。

GitHubで既定のブランチの名前を確かめ、次のコマンドでcloneの`origin/HEAD`を合わせる。

```bash
mise exec -- docker compose -f infra/docker-compose.yml exec windmill_worker git -C /workspaces/<owner>/<repo>/main remote set-head origin <新しい既定のブランチ>
```

その後、Consoleの**要対応**で失敗の行を選び、**再実行**を押す。

## 検査の枠の記録を片付ける

検査は、worktreeを枠のユーザーへ渡す前に、worktreeと`HOME`のパスを枠の記録に書く。
記録はworkerの`/var/lib/factory/check-slots/slot-<N>.state`である。
記録は、所有権をrootに戻し終えたときだけ消える。
残った記録は、次にその枠を取る検査か、次にそのworktreeを使うステップが使って片付ける。
仕組みは[検査コマンドの実行と権限の内部仕様](internals/check-sandbox.md#枠の記録と片付け)にある。

人が片付けるのは、次の4つの場合である。

- `check_slot_record_unreadable`が残った。
  読めない記録は`slot-<N>.state.corrupt-<時刻>-<乱数>`へ退避されていて、それが指していたworktreeは自動では戻らない。
- `check_slot_skipped`が、worktreeを取り戻せない理由で続く。
- 実装かPR修正が、検査用のユーザーへ渡したworktreeをrootへ戻せないまま止まった。
  理由の詳細は`check sandbox:`で始まり、通知の次の操作がこの手順を示す。
  記録が指すworktreeを取り戻せなかったか、読めない記録が残っていてworktreeにrootでないものがある。
  詳細に枠のユーザーと記録のパスが載る。
  作業領域の掃除が同じ理由でworktreeを飛ばしたときは、`cleanup_worktree_busy`が残る。
- 枠の数(`FACTORY_CHECK_POOL_SIZE`)を減らすか、先頭のuid(`FACTORY_CHECK_UID`)を変える。
  または、検査を枠のユーザーで動かす前の版へ`f/`を戻す。
  範囲の外になった枠の記録と、前の版が読まない記録は、どの実行も片付けないためである。

片付けは、実装フローとPR修正のフローが動いていないときに、次の順で行う。

1. 記録の一覧を見る。

   ```bash
   mise exec -- docker compose -f infra/docker-compose.yml exec windmill_worker ls -l /var/lib/factory/check-slots
   ```

   枠の数を変える前と`f/`を戻す前は、`slot-<N>.state`が1つも無ければ片付けは要らない。

2. 記録の中身を読み、worktreeと`HOME`のパスを確かめる。

   ```bash
   mise exec -- docker compose -f infra/docker-compose.yml exec windmill_worker cat /var/lib/factory/check-slots/<記録のファイル>
   ```

3. worktreeが残っていれば、rootに戻し、グループとその他の書き込みと、拡張のACLを消す。
   ACLは`chown`と`chmod`では消えず、残ると後でrootが作るファイルに、ほかの枠から書ける権限が付くためである。
   `HOME`が残っていれば消す。

   ```bash
   mise exec -- docker compose -f infra/docker-compose.yml exec windmill_worker chown -R -h 0:0 <worktree>
   mise exec -- docker compose -f infra/docker-compose.yml exec windmill_worker chmod -R go-w,ug-s <worktree>
   mise exec -- docker compose -f infra/docker-compose.yml exec windmill_worker setfacl -R -P -b -k <worktree>
   mise exec -- docker compose -f infra/docker-compose.yml exec windmill_worker rm -rf --one-file-system <HOME>
   ```

4. 記録のファイルを消す。

   ```bash
   mise exec -- docker compose -f infra/docker-compose.yml exec windmill_worker rm /var/lib/factory/check-slots/<記録のファイル>
   ```

`check_slot_skipped`のときは、4を飛ばしてもよい。
記録が残っていれば、次にその枠を取る検査が、同じworktreeを取り戻し直してから記録を消す。
止まらないプロセスが理由なら、片付けの前にworkerを再起動する。
片付けた後は、止まった作業項目をWindmillの`f/factory/retry_work_item`で再実行する。

### 前の版へ戻したときに記録が残っていたら

検査を枠のユーザーで動かす前の版へ`f/`を戻すrevertは、マージすると自己更新が2分以内に反映する。
マージの前に手順1で記録が無いことを確かめても、反映までの間に取り消された検査が記録を残すことがある。
そのため、反映の後にも手順1で記録の一覧を見る。

前の版の`f/`は記録を読まない。
記録が残ったworktreeは枠のユーザーの所有のままで、rootのgitが所有者の違い(`detected dubious ownership`)で実行を拒む。
そのworktreeを使う作業項目だけが失敗(`job_failed`)になり、ほかのworktreeには影響しない。
手順2から4で片付けてから、失敗した作業項目を`retry_work_item`で再実行する。

`f/`はそのままで、workerのイメージだけを前の版へ戻したときは、記録を片付けなくてよい。
記録がworktreeを指していても、そのworktreeを次に使うステップは、取り戻す前にイメージの前提を確かめる。
満たさなければ、所有権と記録のどちらにも触れずに止まり、`host_action_required`を残す。
準備のステップなら、作業項目は[f/とworkerのイメージを両方変えたとき](operations/deploy.md#fとworkerのイメージを両方変えたとき)と同じ状態で止まる。
作業領域の掃除は、そのworktreeを消さずに飛ばす。
イメージを作り直すまで、そのworktreeを使う作業項目は進まない。
作り直した後の準備のステップが記録を使って取り戻す。
止まった作業項目は、通知が自動で解決されると自動で再開する。

## Claudeの失敗で保留したCIの修正を起動し直す

直す作業のClaudeの実行が次の4つで失敗すると、監視は行を保留する。
待てば解ける2つは、監視が自動で起動し直すので、解ける間は人の操作は要らない。

| 種類 | 保留の理由 | 起動し直す時機 | 原因の解き方 |
| --- | --- | --- | --- |
| `usage_limit` | `claude_usage_limit` | 30分ごとに起動し直す。8日たつと`claude_run_failed`に移る | 使用上限が戻るのを待つ |
| `stopped` | `claude_stopped` | 全停止を解除した後の巡回 | 全停止を解除する |
| `timeout` | `claude_run_failed` | 同じheadでは起動し直さない | 直す範囲が大きすぎないかをログで確かめ、必要なら`claude_timeout_sec`を上げる |
| `run_budget_exceeded` | `claude_run_failed` | 同じheadでは起動し直さない | 直す範囲が大きすぎないかをログで確かめ、必要なら`max_budget_usd_per_run`を上げる |

使用上限と全停止で終わった回は、`pr_ci_fix_max_rounds`の回数に数えない。
待つ間に回数を使い切ると、上限が戻っても直せないためである。
起動し直してまた使用上限に当たると、同じ保留に戻り、さらに30分待つ。
そのheadを最初に見てから8日たっても戻らないときは、待っても解けないとみなし、保留を`claude_run_failed`に移して起動し直すのをやめる。
PRのリンクと次の操作がDiscordに届く。
8日は週単位の上限が戻るのを待てる長さで、headが進むと測り直しになる。
全停止には時間の上限が無い。
全停止の間は起動しないためである。
全停止の変数を読めないときは、解除を確かめられないので、起動し直さない。

`timeout`と`run_budget_exceeded`は同じheadで繰り返しても同じ失敗になり、費用と回数を使い切る。
`claude_run_failed`の行の手順は次のとおりである。

1. 行のIDは[失敗の自動修正を有効にする](operations/pr.md#失敗の自動修正を有効にする)の読み取りのコマンドで確かめる。
2. 次のコマンドで、行を直した作業項目と、止めた理由を読む。
   理由の`claude run failed (<種類>)`で、種類を確かめる。

   ```bash
   mise exec -- docker compose -f infra/docker-compose.yml exec db psql -U postgres -d datatable_db -c "SELECT wi.id, wi.status, (SELECT e.note FROM factory.work_item_events e WHERE e.work_item_id = wi.id AND e.to_status = wi.status ORDER BY e.occurred_at DESC, e.id DESC LIMIT 1) AS note FROM factory.work_items wi WHERE wi.ci_check_id = <行のID> ORDER BY wi.created_at DESC LIMIT 1"
   ```

3. 表に従って原因を解く。
   8日で移った行の種類は`usage_limit`である。
   席の種類と、判定が誤っていないかを確かめる([使用上限の判定を確かめる](#使用上限の判定を確かめる))。
4. 人が直してPRにpushすると、新しいheadが新しい行になり、保留は引き継がない。
5. 同じheadで自動の修正を動かし直すときは、次のコマンドで保留を外す。

   ```bash
   mise exec -- docker compose -f infra/docker-compose.yml exec db psql -U postgres -d datatable_db -c "UPDATE factory.pr_ci_checks SET fix_hold_reason = NULL, notified_reason = NULL, updated_at = now() WHERE id = <行のID> AND state = 'failed' AND fix_hold_reason = 'claude_run_failed'"
   ```

   次の巡回が起動するかを判断し直す。
   直す回数の上限に達していれば、`rounds_exhausted`で保留する。

CIの回は`retry_work_item`が再開を断るので、Consoleの**再実行**では動かし直せない。

## 実行の記録の読み方

実行の記録は`factory.gh_collect_runs`に、所有者ごとに1行ずつ残る。
`finished_at`が空の行は実行中か、終わりの更新に失敗した行である。
最新の実行は、`finished_at`のある最新の行である。

| `error_code` | 意味 | 対処 |
| --- | --- | --- |
| 空(`ok`が`true`) | 一覧を取り終え、照合が通り、記録を置き換えた | 要らない |
| `no_token` | 変数が空か読めない。または、対応表にその所有者が無い。成功が一度も無い所有者は、収集が動いている間は通知しない。成功した後にこの状態になった所有者は、閾値の後に通知する | トークンを入れ、`mise run bootstrap`を実行する。集めないなら、`owners`から外す |
| `token_config_invalid` | 変数の形が誤り | `mise run bootstrap`を実行し直す。変数を手で書き換えない |
| `unauthorized` | 401。トークンが失効したか、取り消された | トークンを作り直して入れる |
| `forbidden` | レート制限でない403 | トークンの権限と、組織の承認を確かめる |
| `rate_limited`、`secondary_limit` | レート制限。`next_allowed_at`まで通信しない。待つのは1時間以内に切り詰める | 待つ。続くときは所有者とリポジトリの数を見直す |
| `http_5xx` | GitHubの5xx、通信断、GraphQLの宛先の404 | 続くときはGitHubの状態を確かめる |
| `timeout` | 1要求の10秒の打ち切り | 続くときはGitHubの状態を確かめる |
| `graphql_error` | 応答に`errors`がある(レート制限でない)。トークンに無い権限が要る項目を問い合わせると、その項目が拒否されて起きる。問い合わせは、Metadata、Pull requests、IssuesのRead-onlyで読める項目だけにしてある | 続くときは、`collect_github`のジョブのログで`graphql query items refused`(`stage`が`list`)を探し、`items`の`type`と項目名を見る。項目名は問い合わせ(`f/factory/lib/gh_graphql.ts`の`OWNER_REPOS_QUERY`)の項目で、トークンの権限と突き合わせる。`type`が`SERVICE_UNAVAILABLE`か`NOT_FOUND`のときは、権限の問題とは限らない(一時的な障害や、リポジトリが消えた場合がある)。この行が無いときは、読み取りトークンで同じ問い合わせを流して`errors`の`path`を見る |
| `parse_error` | 応答の形が誤り | 続くときは調べる |
| `deadline` | 100秒の締め切りで、未着手か、一覧の途中で打ち切った。記録は前回のまま | 続くときは、所有者かリポジトリが多すぎる |
| `db_error` | DBの書き込みに失敗した。記録は前回のまま | DBの状態を確かめる |
| `owner_mismatch` | 設定のIDと一致しない、または所有者が見つからない。要対応の通知`owner_id_mismatch`が出る(設定にIDが無く、所有者が見つからないときは出ない) | `owners`の名前とIDを見直す |

失敗した行は、リポジトリの記録(`factory.gh_repos`)を前回のまま残す。
一覧を取り終え、照合が通った周回だけが、その所有者の記録を置き換える。

列`stage`は、`error_code`が生じた段を表す。
`list`は段1、`detail`は段2で、成功の行は空である。
段2の`error_code`は、段1と同じ語で、次のように読む。

| `stage`が`detail`の`error_code` | 意味 | 対処 |
| --- | --- | --- |
| `unauthorized`、`forbidden` | 段2の要求が401か、レート制限でない403 | 段1と同じ。トークンの権限と、組織の承認を確かめる |
| `rate_limited`、`secondary_limit` | 段2の要求が制限を受けたか、`remaining`が500を切った。`next_allowed_at`まで通信しない | 待つ。続くときはリポジトリと所有者の数を見直す |
| `graphql_error`、`parse_error`、`timeout`、`http_5xx` | 対象を1件以上取ろうとして、1件も取り終えられず、失敗が1件以上あった | リポジトリごとの`detail_failed`を見る。`graphql_error`のときは、`collect_github`のジョブのログで`graphql query items refused`(`stage`が`detail`)を探し、`items`の項目名を見る。`type`が`SERVICE_UNAVAILABLE`か`NOT_FOUND`のときは、権限の問題とは限らない(一時的な障害や、リポジトリが消えた場合がある)。この行にリポジトリ名は載らないので、同じ周回の`a repository detail failed`と突き合わせる。続くときは調べる |
| `deadline` | 対象が1件以上あるのに、時間が足りず1件も着手できなかった | 続くときは、所有者かリポジトリが多すぎる |
| `db_error` | DBの書き込みか読み取りに失敗した | DBの状態を確かめる |

リポジトリ単位の失敗と打ち切りは、所有者の`ok`を変えない。
特定のリポジトリが続けて失敗するか打ち切られると、`gh_repos`の`detail_failed`か`truncated`が真のまま残る。
開いたPRが90件を超えるリポジトリは、打ち切りが続く。
この間、`last_collected_at`が進まず、古い行は`usable`が真のまま残る。
最初に詳細の行を読む処理は、閾値で判断を止める判定を備えなければならない([下流が守る不変条件](internals/github-collect.md#下流が守る不変条件))。
明示されていないリポジトリの古さは、所有者の収集が成功していても通知する([収集が止まったときの通知](operations/collect.md#収集が止まったときの通知))。

### 日次のまとめの追い付き

日次のまとめは、最後に出した日(JSTの日付)をWindmillのstateに残す。
ホストのスリープなどで09:00の予定が飛んでも、次の実行が最後に出した日の翌日から前日までを、古い順に1日ずつ出す。
続けて出すときは、同じwebhookの他の通知をrate limitで落とさないよう、日と日の間を1秒あける。
ジョブの上限は120秒にしている。
1日分の集計は通常数秒で終わるが、webhookのrate limitの待ち(1回で最大30秒)が重なって上限を超えた回は、ジョブが打ち切られる。
保存した日までは進んでいるので、次の実行が続きから出す。
送ってから保存するまでの間に打ち切られると、次の実行が同じ日をもう一度送る。
打ち切りはスケジュールの失敗として記録され、Consoleに残る。
stateが無い初回は、前日だけを出す。

stateは、常に次に出す日の前日を指す。
送る前に、出す日の最初の日の前日をstateに保存する。
すでにその日が保存されている通常の日は、書き込まない。
そのため、stateが空でも、読めない値でも、未来の日付でも、止まった日から次の実行が始まる。
この保存に失敗したときは、何も送らずにジョブが失敗し、次の実行が同じ状態から再開する。

出さない日と止まる日は次のとおりである。

- 一度に遡るのは7日までで、それより古い日は出さず、ジョブのログに警告を残す。
  警告には、飛ばした範囲の最初の日と最後の日が載る。
- 集計が例外になった日は、そこで止まり、stateを進めずにジョブを失敗にする。
  次の実行が、その日からやり直す。
- Discordに届かなかった日は、stateを進めずに止まる。
  次の実行は、届かなかった日から始まる。
- 届かなかった日より新しい日は、その回は出さない。
- 届かなかった日が前日のときは、次の実行が自動で出し直すので、警告をジョブのログに残すだけで成功として終える。
  通知が届いても、stateの保存に失敗すると、次の実行が同じ日をもう一度出す。
- 昨日より古い日が届かないときは、届いた日までstateを進めたうえで、ジョブを失敗にする。
  昨日が届かなかった回は警告だけで、翌日も届かなければ、その日が昨日より古い日になり、失敗として記録される。
  失敗は失敗の記録に残るので、Consoleで確かめられる。
- ある日の集計が毎回例外になるか、ある日の通知だけが恒久的に拒まれると、その日より後の日も出ない。
  その日が7日の窓から押し出されると、警告を1行残して飛ばし、stateを窓の前日まで進めて、残りの日をまとめて出す。
- webhookを設定していないときは、送る先が無いので、stateを進める。

stateの異常は次のように扱う。

- 読めない値(実在しない日付など)は、記録なしと同じに扱い、前日だけを出す。
  ジョブのログに警告を残す。
- 前日より後の日(時計のずれなど)は、記録なしと同じに扱い、前日だけを出す。
  送る前にstateを前日の前日に上書きして直す。
  ジョブのログに警告を残す。

### 通知の種類

noticeには、Discordに送らない事項と、Discordに届かなくても残しておく事項が残る。

通知には重要度がある。
「要対応」の通知は、解決するまでConsoleの要対応の一覧に残る。
「情報」の通知は、人の行動が要らないので要対応の一覧に出さず、Consoleのシステムの画面の「情報の通知」に7日だけ出す。
内容を確かめたいときは、行の「詳細」から要対応の画面の詳細を開く。
表に無い種類は「要対応」として扱う。
「情報」の種類は次のとおりである。

- `approval_notify_failed`
- `claim_race_lost`
- `supersede_failed`
- `cleanup_worktrees_skipped`
- `workspace_disk_usage`
- `fix_feedback_association_excluded`
- `labeler_denied`
- `fork_head_denied`
- `unsandboxed_check_commands`
- `implement_needs_human`
- `dependabot_merge_held`
- `hold_released`
- `deploy_approval_decided`
- `stop_all_released`

次の表の各行は、種類の列の先頭に`notice-<種類>`の名前のアンカーを持つ。
種類を足すときは、同じ形のアンカーを行に置く。
Consoleの通知の詳細のリンクが、種類からこの名前を決めて行を開くためである。

### 日次のまとめでの見方

日次のまとめ(`daily_summary`)の「workerの負荷」欄に、集計の対象の日(JSTの0時から24時)の`worker_samples`の集計が載る。
対象の日は、通常は前日である。
追い付きで出す日は、前日より古い。
負荷の記録は日次のまとめの補足なので、別の通知は出さない。
その日に1行も無ければ「その日の記録なし」と出る。
この場合は、`sample_worker_load`のスケジュールが有効かを確かめる。
集計を読めなかったときは「集計を読めませんでした」と出る。
この場合は、`wmill job list --script-path f/factory/notify_daily_summary`で直近のジョブを探し、ログの警告から原因を確かめる。
負荷の集計だけが失敗した場合の代表的な原因は次のとおりである。

- 列の値の形が変わり、読み取りが例外になった。
- 読み取りの権限が足りない。
- DBが一時的に不調で、クエリが失敗した。

いずれの場合も、ほかの項目の通知は止まらない。
`factory.worker_samples`の表が無いときや、migrationが反映されていないときは、集計より先に掃除の集計が例外になり、日次のまとめ全体が投稿されない。
[保持期間](#保持期間)を短くした場合は、対象の日の冒頭の行が先に消え、欠けとして現れうる。

| 項目 | 内容 | 読み方 |
| --- | --- | --- |
| 記録 | 対象の日の行の数と、期待する720行に対する欠けの割合 | 欠けは、枠が塞がって記録のジョブが動けなかった印か、停止の印である。記録を始めた日や、記録の失敗でも欠ける。欠けが1件以上あるのに整数のパーセントでは0%に丸まるときは、小数1桁で出す |
| 遅れ | `lag_seconds`の最大と、30秒以上の行の数とその遅れの合計(秒) | 枠の塞がりか停止のどちらかを表す。合計が大きく、短い空白も多ければ塞がりである。停止や長い塞がりの直後に、1件だけ大きな遅れが出ることもある |
| 空白 | 行の間隔が4分を超えた回数と、最長の間隔(分、切り上げ)と、その開始と終了のJSTの時刻 | 長い空白は、停止(ホストのスリープ、`mise run up`、Windmillの再起動)でも、長いジョブが枠をすべて塞いだ場合でも出る。空白の時刻に`wmill job list`かConsoleの作業項目で動いていたジョブを確かめ、あれば塞がり、無ければ停止と見分ける。短い空白が何度も出て、遅れも多ければ塞がりである |
| 他のジョブの枠の使用 | `running_jobs`の最大(件)と、上限`slots`-1 | 記録のジョブ自身の枠を除く。`slots`が1の日は、他のジョブの枠が無いので出さない。上限に近い値は、記録のジョブが動けた瞬間に、他のジョブがほぼ枠を使っていたことを表す。平均は、位相の偏りで占有率にならないので出さない |
| メモリ | `mem_anon_bytes`の最大(MiB)と、上限に対する比。`mem_working_set_bytes`の最大。OOMの有無 | 逼迫の判断には`anon`の最大と比を使う。上限が無いか読めない日は、比が出ない。OOMは`mem_oom`と`mem_oom_kill`の増分の合計である。再起動で累積が戻ったときは、現在値を増分に数える |
| 待ちの最長 | `max_wait_seconds`の最大 | 記録のジョブ自身の遅れで打ち切られるので、下限である |

空白が1回以上ある日だけ、この見分け方が「読み方」の行として添えられる。
遅れだけの日には添えない。
ポーリングの山で遅れが毎日出て、添えると読まれなくなるためである。
読めなかった値だけの日は「不明」と出る。
OOMの増分は、値の読めた行が2行以上なければ求められないので、1行だけの日や値がすべて空の日は「OOMの増分は不明」と出る。
「0」は、読めて0だったことを表す。
OOMの増分は、`mem_oom`と`mem_oom_kill`を別々に、値の読めた行だけを並べて隣り合う行の差を足す。
値が空の行をまたいでも、その間の増分は数える。

### 閾値の通知

`sample_worker_load`は、行を記録した直後に、直近の記録を読んでメモリの状態を判定する。
超えた原因ごとに、通知`worker_load_high`を残す。
通知はConsoleの要対応に出る。
Discordには届かない。
本文には、原因、閾値、システムの画面のリンク、次の操作が載る。
測定した値は本文に載せない。
載せると本文が毎回変わり、同じ原因の通知が重なるためである。
測定した値は、システムの画面で見る。

原因は2つである。

| 原因 | 判定 |
| --- | --- |
| メモリ | 最新の記録の`mem_anon_bytes`が、`mem_limit_bytes`の設定の割合以上 |
| OOM | 最新の記録の`mem_oom_kill`が、値の読めた直前の記録より増えた |

割合は、設定`worker_alert_memory_ratio`で変える。
既定値は0.8で、0を超え1以下の数でなければ、設定の読み込みが失敗する。
`mem_limit_bytes`が読めない記録や0の記録では、割合を判定しない。

OOMの`mem_oom_kill`は、コンテナの起動からの累積の回数なので、増分で判定する。
比べる相手は、直近の記録30件(途切れが無ければ1時間)のうち、値の読めた最も新しい記録である。
記録が途切れていると、30件は1時間より長い期間にまたがる。
累積が戻ったとき(コンテナの再起動)は、現在値が1以上なら増えたと見なす。
最新の値が読めない記録や、比べる相手が無い記録は、増えたと見なさない。

割合の分子は、回収できないメモリを表す`mem_anon_bytes`にする。
ページキャッシュを含む`mem_current_bytes`や、非アクティブなファイルキャッシュだけを除いた`mem_working_set_bytes`は、上限に近くても回収できる分を含み、逼迫と限らない。
行動不要の通知が出るのを避けるためである。

上限に達した回数(`mem_events_max`)は、通知の条件に使わない。
cgroup v2のこの回数は、確保が上限を超えそうになり直接の回収を始めるたびに、回収が成功しても増える。
defaultのworkerは上限が4096MiBで、`memory.high`が無い。
ページキャッシュが上限まで溜まった後は、平常時のgitやbunの入出力でも増え続けるので、行動不要の通知になる。
回数は記録と、Consoleの画面と、日次のまとめにそのまま残す。

通知は自動では解決されない。
閾値を下回っても取り消さないのは、解決を人の確認に任せ、揺れる値で通知が出入りしないようにするためである。
未解決の通知がある間は、同じ原因の通知を重ねない。

人が解決した後の出方は、原因で違う。

- 割合: 条件が続く限り、次の記録(2分後)で同じ本文の通知がもう一度出る。
  出直しが多いときは、設定の割合を調整する。
- OOM: 増えた記録でしか判定しないので、解決した後は、次に増えるまで出ない。

待ちと枠の塞がりは、通知にしない。
記録のジョブは、枠が空いたときにしか動けない。
最も詰まった間は記録が途切れ、判定が動かないので、鳴るべき状態で鳴らないためである。
暫定値を決める実測も無い。
この2つは、Consoleのシステムの画面と日次のまとめで見る。
塞がりの割合は、`running_jobs`が読めた記録だけを分母にして数える。
数え方を確かめた結果と、画面の「枠の使用」と「枠が塞がっていた記録」を塞がりの判断に使える条件は、[枠の占有](operations/monitoring.md#枠の占有)にある。

閾値の判定が失敗しても、記録の成否には影響しない。
設定が読めない、直近の記録が読めない、通知を残せない場合は、ジョブログに警告を残す。
警告は次の文である。

- `could not check the load alerts`: 設定か直近の記録を読めなかった。
- `could not add the load alert notice`: 通知を残せなかった。
  `cause`に原因が載る。

判定の失敗が続いても、専用の通知は足さない。
失敗の原因は、次の3つが主である。

- 設定の書き損じ。
  設定を読む他のscriptも同じ設定で失敗し、スケジュールの失敗の通知(`schedule_failing`)が出る。
- DBの障害。
  記録の挿入も失敗し、通知`worker_sample_failed`が出る。
- 直近の記録の読み取りだけの失敗。
  挿入が成功すると、`worker_sample_failed`も出ない。

読み取りだけの失敗は、ジョブログの警告で気づく。
メモリの通知が長く出ていないときは、警告が続いていないかを確かめる。

割合の通知、メモリの通知の取りこぼし、再起動をまたぐOOMの増分、OOMの通知の限界は[workerとスケジュールの監視の運用の「限界」](operations/monitoring.md#限界)にある。

### 通知を解決する

内容を確かめて対応を終えた通知は、Consoleの**要対応**で1件ずつ解決する。
一覧から通知を選び、詳細の「解決済みにする」を押す。
確認のダイアログは出ない。
詳細には、起きたことと次の操作が種類ごとに出る。
その操作を済ませてから押す。
解決の操作は`notice_resolve`で、解決した人と時刻が通知に記録される。
何を確かめたか分からないまま消せないよう、まとめて解決する操作は無い。
別の人が先に解決していた通知を押しても、成功として扱う。
解決した通知は一覧から消える。

「情報」の通知は、人の行動が要らないので、要対応の一覧に出ない。
`?notice=<id>`で開いた詳細にだけ出る。
解決しなくてよい。

次の4種類は、設定や権限の問題を示すので、Consoleから解決できない。
詳細には、ボタンの代わりに解決できない旨が出る。
最初の3種類は「情報」として7日で一覧から外れる。
`design_enabled_ignored`は「要対応」で、一覧に残る。
設定を直すと、自己更新が自動で解決する。

- `unsandboxed_check_commands`
- `labeler_denied`
- `fix_feedback_association_excluded`
- `design_enabled_ignored`

解決済みの通知は、Consoleの**システム**の「解決済みの通知」に履歴として残り、既定30日で消える。
並びは、人が解決したものを先にし、DBの掃除で解決したもの(`resolved_by`は`cleanup_db`)を後にする。
どちらも解決の新しい順である。
同じ状況がまた起きれば、新しい通知として記録される。

### 要件定義の作り直しを起動できなかったとき

却下、設計の要件の不足、実装の要件の不足のどれかで要件定義を作り直すときに、フローを起動できないか、起動したジョブのIDを記録できないことがある。
このとき作業項目は人の対応待ちになり、理由は`requirements regeneration could not be started`になる。
Discordにはジョブ失敗が届く。

Consoleの**要対応**の失敗から再実行する。
再実行は、要件定義を作り直す。
人が承認し直す。
理由は、止まり方に応じて、要件定義のフローに渡る。

| 止まり方 | 渡る理由 | 理由が残っている場所 |
| --- | --- | --- |
| 却下による作り直し | 却下の理由 | 承認依頼(`approval_requests.reason`) |
| 設計の要件の不足 | 設計の差し戻しの理由 | 作業項目の履歴の注記(`design gap:`で始まる) |
| 実装の要件の不足 | 実装の差し戻しの理由 | 通知と作業項目の履歴の注記(`gap:`で始まる) |

要件定義のフローが下書きを作る前に、日次予算の超過などで止まったときも、同じ理由が渡る。
下書きができた後に止まったときは、理由が使われ済みなので渡らない。

### 承認済みの要件定義が書き換わって止まったとき

承認済みの要件定義のディレクトリが、書き換わったか、無くなったときは、作業項目が人の対応待ちになる。
ディレクトリを確かめてから、Consoleの**要対応**の失敗で**再実行**を押す。
再実行は、実装や設計に戻さず、要件定義を作り直す。
人が承認し直す。
承認の前に保存した基準値が残るので、実装や設計に戻しても同じ理由で止まるためである。
設計が有効かと、実装フローが有効かには依らない。

### 実装フローの起動前の処理が失敗したとき

承認済みから実装中へ進める処理がDBの失敗で例外になると、Consoleの**要対応**に`implement_launch_failed`が残る。
作業項目はふつう承認済みのまま残り、自動では再開しない。

作業項目の詳細の失敗の記録には`job_failures`の行(stepは`cas`)が出る。
作業項目は承認済みのまま残り、**要対応**の失敗には出ないので、Windmillで`f/factory/retry_work_item`を作業項目のIDで実行して再開する。

まれに、例外の前に実装中へ進んでいることがある。
この作業項目はフローの無いまま残る。
猶予を過ぎると、定期の点検がこれを失敗にする。
失敗になった後は、同じ手順で再開できる。

## 秘密をローテーションする

1. GitHubのPAT(`GITHUB_TOKEN`、`CONSOLE_GITHUB_TOKEN`)かClaude CodeのOAuthトークンを発行し直す。
   手順は[セキュリティ](security.md)にある。
2. 新しい値を`mise.local.toml`に投入する。
   コマンドは[セットアップ](setup.md)にある。
3. `mise run bootstrap`を実行し直す。
   `bootstrap.sh`は冪等で、既存のWindmillの変数を新しい値で上書きする。
4. `CONSOLE_GITHUB_TOKEN`は、`bootstrap`ではなく`mise run up`で反映する。
   `console_fetcher`のコンテナが新しい値で作り直される。

### 資格情報の期限の通知

日次のまとめ(毎日09:00)が、資格情報の期限を確かめる。
期限まで`credential_warn_days`日以内か、期限を過ぎていると、要対応の通知(`credential_expiring`)を残す。
`credential_warn_days`は`factory_config`の設定で、既定は30日、範囲は1〜365日である。
期限は、`mise run bootstrap`がホストで集め、秘密でない変数`f/factory/credential_expiry`に置く。

| 資格情報 | 期限の元 |
| --- | --- |
| Windmillのトークン(`wmill_token`) | `bootstrap`が発行した日から180日 |
| Claude CodeのOAuthトークン | 値が変わった後の最初の`bootstrap`の日から、`CLAUDE_OAUTH_TOKEN_DAYS`日(既定365日) |
| GitHubのPAT(`GITHUB_TOKEN`) | GitHubの応答ヘッダー`github-authentication-token-expiration` |
| 読み取り専用のPAT(`GITHUB_READ_TOKEN_<OWNER>`) | 同じ応答ヘッダー |
| interaction-limits | `INTERACTION_LIMITS_REPO`の設定。読めなければ`INTERACTION_LIMITS_EXPIRES_AT` |

環境変数の意味は[セットアップ](setup.md#資格情報を用意する)にある。
Claude CodeのOAuthトークンは、値の指紋を記録に残し、指紋が変わったときだけ発行日を数え直す。
同じトークンのまま`bootstrap`を実行し直しても、発行日は変わらず、期限は延びない。
`CLAUDE_OAUTH_TOKEN_DAYS`を直したときは、次の`bootstrap`で、前回の発行日にその日数を足して期限を計算し直す。
期限の無いPATは記録しないので、通知も出ない。
通信の失敗や200以外の応答でPATの期限を読めなかったときは、前回の記録の同じ項目を保ち、`bootstrap`の標準エラーに警告を出す。
読めなかっただけの期限を記録から外すと、日次のまとめが期限の通知を解決するためである。
前回の記録の読み取りが、200でも404でもない応答か接続の失敗になったときは、記録を作り直さず、前回の記録を残して警告を出す。
作り直すと、OAuthトークンの発行日が今日に戻り、読み取り専用のPATの項目も消えるためである。

通知は、資格情報ごとに1件で、本文に期限の日付(JST)が載る。
通知を残すと、Discordにも1回届く。

資格情報を更新したら、`mise run bootstrap`を実行する。
期限が先に延びると、次の日次のまとめが通知を解決する。
interaction-limitsは、GitHubの設定画面で延ばす。
期限をAPIで読めずに`INTERACTION_LIMITS_EXPIRES_AT`を使っているときは、延ばした後に、`mise.local.toml`のその値を書き直す。

## バックアップ

夜間のバックアップ(`f/factory/backup`)が、毎日02:30(JST)に、失うと戻せない状態を控える。
控えは、defaultのworkerの名前付きvolume`factory_backups`(`/var/lib/factory-backups`)に置く。
作業領域の掃除(03:00)とDBの掃除(03:30)より前に動くので、掃除の前の状態が残る。

> [!WARNING]
> `mise exec -- docker compose -f infra/docker-compose.yml down -v`は、`db_data`と`factory_backups`を含むすべてのvolumeを消す。
> 消したデータは戻せない。
> 控えを残したいときは、先に[ホストに写す](#ホストに写す)の手順で写す。

### 控えるもの

| ファイル | 中身 | 取り方 |
| --- | --- | --- |
| `cluster.sql` | Postgresの全データベース(`windmill`、`datatable_db`)とロール | `pg_dumpall` |
| `factory_state.tar` | `factory_state`のvolume。要件定義書、設計書、監査の記録、反映済みのshaを含む | `tar`。`claude/`、`gh/`、`check-slots/`は除く |
| `factory_config.json` | `f/factory/factory_config`の値。変数とresourceへの参照は`<redacted>`に置き換える | Windmillの補間しない読み取り |
| `manifest.json` | 取った時刻、各ファイルのバイト数、`f/factory/deployed_sha`の値 | scriptが書く |

`claude/`と`gh/`は、人がworkerに入って使うときのログインの記録である。
ジョブは使わないので、戻した後に要るのは、手で使うときのログインのやり直しだけである。
`check-slots/`は検査の枠の記録で、戻すと存在しない実行の記録が残るため除く。
控えに含まれる秘密と置き場の権限は、[セキュリティ](security.md#バックアップの控え)にある。

### 保存先と世代

世代は`/var/lib/factory-backups/<時刻>/`に置く。
時刻はUTCの`YYYYMMDDTHHMMSSZ`である。
書きかけの世代は`.partial-<時刻>/`に置き、すべて書き終えてから`<時刻>/`に改名する。
途中で止まった世代は`.partial-`のまま残り、次の実行が消す。

新しい世代を書いた後、新しい方から`backup_keep_generations`(既定7)の世代を残し、古い世代を消す。
数は[保持期間](#保持期間)の表にある。
控えの大きさは監視しない。
増え方は、`manifest.json`のバイト数で人が見る。

世代の一覧は次のコマンドで見る。

```bash
mise exec -- docker compose -f infra/docker-compose.yml exec -T windmill_worker ls -l /var/lib/factory-backups
```

### 失敗したとき

失敗すると、scriptは要対応の通知(`backup_failed`)を残し、ジョブを失敗にする。
本文には失敗した段階だけが載り、原因はジョブのログに出る。
本文が段階ごとに同じなので、同じ段階の失敗が続く間、未解決の通知は1件にまとまる。
ジョブの失敗は、scheduleの失敗の検出(`detect_schedule_failures`)がDiscordに知らせる。
成功したときは通知しない。
`tar`が、読んでいる間にファイルが変わったか消えたと報告したとき(終了コード1)は、失敗にしない。
アーカイブは書けているので、ジョブのログに警告を出して先へ進む。

| 段階 | よくある原因 | 確かめること |
| --- | --- | --- |
| `prepare` | `f/factory/db_backup_url`が無いか、URLの形でない。URLに`?sslmode=`などの問い合わせ文字列がある | `mise run bootstrap`を実行したか |
| `pg_dumpall` | workerのイメージに`pg_dumpall`が無い。DBに接続できない | 更新の後に`mise run up`を実行したか。`db`が動いているか |
| `tar` | `factory_state`を読めない。tarが終了コード2以上で終わった | ジョブのログのtarのエラー |
| `config`、`manifest`、`finalize` | 置き場に書けない。ディスクが足りない | ホストのディスクの空き |
| `prune` | 古い世代を消せない。`backup_keep_generations`が正の整数でない | ジョブのログ。新しい世代は書けている |

原因を直したら、Windmillの画面で`f/factory/backup`を実行して取り直す。
取り直しが成功したら、Consoleで通知を解決する。
通知は自動では解決されない。

### ホストに写す

最新の世代を、ホストのディレクトリに写す。
保存先には、既にあるディレクトリを渡す。

```bash
mise run backup:export -- <保存先>
```

世代は`<保存先>/<時刻>/`に写り、写した先のパスが出る。
写した世代は、所有者だけが読める権限になる。
別の媒体やホストに移すのは人が行う。
控えはDBの全体を含むので、移した先もホストの権限で守る。

### 使い捨ての環境に戻す

世代を使い捨てのcomposeのプロジェクト`factory-restore`に戻して、戻せることを確かめる。
本番のプロジェクト`infra`のvolumeには触れない。
プロジェクトの名前が違うので、volumeの名前は`factory-restore_*`になる。

```bash
mise run backup:restore -- <世代のディレクトリ>
```

ディレクトリには`cluster.sql`と`factory_state.tar`が要る。
`backup:restore`は次の順に動く。

1. `db`だけを起動し、TCPで受け付けるまで待つ。
2. イメージが作った空の`windmill`のデータベースを消す。
3. `cluster.sql`を`psql`で流し、最初のエラーで止める。
4. `factory_state.tar`を、同じプロジェクトの`factory_state`に展開する。
5. `factory.work_items`と`factory.notices`の行数と、`requirements/`のファイル数を出す。

手順3では、`CREATE ROLE postgres;`の1行だけを除いて流す。
`pg_dumpall`は接続したsuperuserのロールにも`CREATE ROLE`を出し、戻し先には同じロールが既にあるためである。

終わりに、使い捨てのプロジェクトを消すコマンドが出る。
確かめ終えたら、人が実行する。

```bash
mise exec -- docker compose -p factory-restore -f infra/docker-compose.yml down -v
```

前の実行の`db`が残っているときは、`backup:restore`は何もせずに止まる。
上のコマンドで消してから、実行し直す。

### 本番に戻す

本番のvolumeへ戻す操作は、自動にしていない。
戻すかどうかと、いつ戻すかは人が判断する。

> [!WARNING]
> 次の手順は、本番の`db_data`を消して作り直す。
> 消したデータは戻せない。
> 先に[使い捨ての環境に戻す](#使い捨ての環境に戻す)の手順で、使う世代が戻せることを確かめる。

1. 使う世代をホストに置く。
   volumeが残っているときは、[ホストに写す](#ホストに写す)の手順で写す。
2. スタックを止める。

   ```bash
   mise run down
   ```

3. `cluster.sql`と`factory_state.tar`がホストにあることを確かめてから、次へ進む。
   `db_data`のvolumeを消す。
   `infra`はcomposeのプロジェクト名で、composeのファイルに`name`がないので、ディレクトリの名前になる。

   ```bash
   docker volume rm infra_db_data
   ```

4. `db`だけを起動し、TCPで受け付けるまで待つ。
   次のコマンドが`accepting connections`を出せば受け付けている。

   ```bash
   mise exec -- docker compose -f infra/docker-compose.yml up -d --wait db
   mise exec -- docker compose -f infra/docker-compose.yml exec -T db pg_isready -h 127.0.0.1 -U postgres
   ```

5. 空の`windmill`を消し、`cluster.sql`を流す。
   `<世代のディレクトリ>`は手順1のパスにする。

   ```bash
   mise exec -- docker compose -f infra/docker-compose.yml exec -T db psql -X -v ON_ERROR_STOP=1 -U postgres -d postgres -c 'DROP DATABASE windmill'
   grep -v -x -F 'CREATE ROLE postgres;' <世代のディレクトリ>/cluster.sql | mise exec -- docker compose -f infra/docker-compose.yml exec -T db psql -X -q -v ON_ERROR_STOP=1 -U postgres -d postgres
   ```

6. superuserのパスワードを、今の`DB_PASSWORD`に合わせ直す。
   `cluster.sql`は、控えを取ったときの`postgres`のパスワードを戻すためである。
   その後に`DB_PASSWORD`を変えていると、次の`mise run up`が接続できない。
   `<DB_PASSWORD>`は、`mise.local.toml`の`DB_PASSWORD`と同じ値に置き換える。

   ```bash
   mise exec -- docker compose -f infra/docker-compose.yml exec -T db psql -U postgres -c "ALTER ROLE postgres PASSWORD '<DB_PASSWORD>'"
   ```

   このコマンドはパスワードをシェルの履歴に残す。
   残したくないときは、`-T`を外して`psql -U postgres`を対話で開き、`\password postgres`で入れる。

7. `factory_state`に展開する。
   volumeが残っているときは、同じ名前のファイルを上書きする。
   `--pull missing`は、サービスの`pull_policy: always`を引き継がず、レジストリに問い合わせないために付ける。

   ```bash
   mise exec -- docker compose -f infra/docker-compose.yml run --pull missing --rm --no-deps -T --entrypoint tar factory_state_init --no-same-owner -xf - -C /var/lib/factory < <世代のディレクトリ>/factory_state.tar
   ```

8. スタックを起動する。

   ```bash
   mise run up
   ```

9. `factory_state`のvolumeも失っていたときは、人がworkerに入って使う`claude`と`gh`のログインをやり直す。

### リハーサルの記録

ホストで取った`pg_dumpall`と`factory_state`のtarを、`mise run backup:restore`で使い捨ての環境に戻した結果である。

| 項目 | 結果 |
| --- | --- |
| 戻した控え | 本番のクラスタの`pg_dumpall`(2.1GB)と、`factory_state`のtar(215KB) |
| `cluster.sql`の流し込み | `ON_ERROR_STOP`で止まらずに最後まで流れた |
| `factory.work_items`の行数(本番、戻した先) | 169、168(控えを取った後に本番で1件増えた) |
| `factory.notices`の行数(本番、戻した先) | 141、141 |
| `requirements/`のファイル数(本番、戻した先) | 21、21 |
| かかった時間 | 約1分(`db`の起動から件数の表示まで) |

## 保持期間

DBの掃除のスケジュール(`cleanup_db`、毎日03:30)が、保持期間を過ぎたレコードを消す。
バックアップの世代は、夜間のバックアップ(`backup`、毎日02:30)が、新しい世代を書いた後に数で消す。
日数と世代の数は、どれも`f/factory/factory_config`で変えられる。

| 対象 | 保持期間 | 設定 |
| --- | --- | --- |
| 終端の状態になった作業項目と、それに連なる記録 | 90日 | `retention_work_items_days` |
| 監査の作業項目とレポート・提案 | 監査完了(`audited`)から90日 | `retention_work_items_days` |
| 失敗の記録、デプロイの記録(最後に成功した反映の行は消さない)、解決済みの通知(解決の時刻から数える) | 30日 | `retention_logs_days` |
| 判定済みのmainのCIの記録(最後の更新から数える。判定を待つ記録と、各リポジトリの最新の記録は消さない) | 30日 | `retention_logs_days` |
| 判定済みのPRのCIの記録(最後の更新から数える。判定を待つ記録と失敗を直している記録は消さない。各PRの最新の記録は、保持期間の4倍まで残す) | 30日(各PRの最新の記録は120日) | `retention_logs_days` |
| workerの負荷の記録(測った時刻から数える) | 30日 | `retention_logs_days` |
| 手動投入の冪等キー(予約した時刻から数える) | 90日 | `retention_work_items_days` |
| バックアップの世代(新しい方から数える) | 7世代 | `backup_keep_generations` |

workerの負荷の記録(`worker_samples`)は、測った時刻(`sampled_at`)から30日を過ぎた行をすべて消す。
1日に720行が増えるので、掃除が毎日動いていれば、行数は約2.2万行で頭打ちになる。
次の掃除の直前は、31日分の約2.2万行である。
掃除が失敗した日や、`retention_logs_days`を延ばしたときは、行数が増える。

`retention_logs_days`を1にすると、03:30の掃除が、前日の00:00から03:30(JST)の標本を消す。
たとえば09:00に前日の標本を読む日次のまとめは、前日の冒頭が欠ける。
2以上なら欠けない。
直近の3時間を読む閾値の判定は、1でも欠けない。

「情報」の未解決の通知は、作成から30日たつと削除せず解決済みにする。
Consoleの**システム**の「情報の通知」から7日で外れて誰も解決しないので、溜まり続けないようにするためである。
解決者は`cleanup_db`と記録され、解決済みの履歴に残る。
その後は上の表のとおり、解決の時刻から30日で消える。

終端の状態は、承認済み、人の対応待ち、期限切れ、失敗、レビュー済み、再レビュー依頼、ブロック、キャンセル、PR作成済み、監査完了、調査完了である。
PR作成済みの作業項目は、PRがopenのままでも90日で消える。

作業項目を消すと、外部キーの`ON DELETE CASCADE`で次の記録も消える。

- 要件定義のドラフト
- 承認の履歴と承認依頼
- 状態遷移の履歴(`work_item_events`)
- Claudeの実行の記録(`agent_runs`)

Claudeの実行の記録は、コスト分析(`v_agent_cost_daily`)の元データである。
コスト分析を保持期間より長く見たいときは、`retention_work_items_days`を延ばす。

作業項目を消すときは、その要件定義のディレクトリも消す。
ディレクトリは`requirement_drafts.doc_dir`が指す場所である。
workerの`/var/lib/factory/requirements/<owner>/<repo>/issue-<N>/wi-<id>/`以下にある。

この削除はDBの行の削除とは別の処理である。
失敗しても、ほかの掃除とDBの削除は止まらない。

未解決のお知らせは消さない。
消した件数は`cleanup_runs`テーブルに記録し、翌朝09:00の日次サマリーの「DB掃除」欄に出す。

同じIssueの作業項目がすべて消えた後にそのIssueを拾い直すと、サイクルの番号は1から振り直す。
番号は残っている行の最大値から決めるためである。
過去の通知やDiscordの履歴にあるサイクルの番号と重なることがある。
