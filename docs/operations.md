# 運用

Factoryを動かす人が、日々の作業で何をすればよいかと、通知や失敗にどう対応するかをまとめた手順書である。構成と仕組みは[アーキテクチャ](architecture.md)、内部の挙動は`docs/internals/`の各文書を参照する。

画面の操作は、Factory Console(`/console/`)で行う。
左のサイドバーの入口は、**要対応**、**作業項目**、**レポート**、**システム**の4つである。

| 入口 | できること |
| --- | --- |
| **要対応** | 承認と却下、失敗した作業項目の再実行、通知の解決 |
| **作業項目** | 進捗の表、作業項目の詳細、要件定義書の閲覧 |
| **レポート** | 監査レポートの閲覧と**今すぐ監査**、コストと承認の統計の分析 |
| **システム** | 反映の状態、更新履歴、情報の通知、解決済みの通知、監査の失敗、作業項目に紐づかない失敗の閲覧 |

## 運用の決まり

1つのIssueは1つのインスタンスだけが処理する。
トリガーラベルを外す取得(claim)に成功したインスタンスが、そのIssueを受け持つ。
Factoryは取得の前に、自分のGitHubユーザーをassigneeに追加する。
後から来たインスタンスは手を引く。

この排他はベストエフォートである。
GitHubは、同時に届いた複数の削除のうち、成功が1つだけになることを保証していない。
すべてのインスタンスが同じPATで動くので、GitHub側ではインスタンスを区別できない。
同じIssueに2つ目の作業項目を作らせない最後の防御は、DBの部分一意インデックスである。
終端でないIssueの作業項目は、`owner`、`repo`、Issueの番号の組ごとに、同時に1つしか持てない。
別の取得が同じIssueを先に取得していたときは、Factoryは取得を失ったものとして引き、`claim_race_lost`のnoticeを残す。
この防御が働くのは、インスタンスが同じDBを共有している場合である。
DBを分けた複数のインスタンスが同じリポジトリを扱う構成は、対象外である。
1つのリポジトリは1つのインスタンスだけで扱う。

同じIssueに、より新しいサイクルの作業項目がある古い作業項目は、`retry_work_item`で再実行できない。
新しいサイクルに置き換えられていて、古い要件定義を実装しかねないためである。
再実行は、最新のサイクルの状態に合わせた英語のエラーで止まる。
エラーは、次のどれかを示す。

- 最新のサイクルが進行中のときは、操作は要らない。
- 最新のサイクルが再実行できる状態(失敗、人の対応待ち、期限切れ、ブロック、承認済み)のときは、その最新のサイクルを再実行する。
- 最新のサイクルがPRを作成した(`pr_open`)ときは、そのPRを確かめる。
- 最新のサイクルがそれ以外の終端のときは、Issueにトリガーラベルを付け直して、新しいサイクルを始める。

承認済みの最新のサイクルを再実行するには、`implement_enabled`が有効でなければならない。
無効のままだと、再実行は有効にするよう求めるエラーで止まる。

最新のサイクルの再実行が、同じIssueの稼働中の作業項目に阻まれるのは、まれな競合のときだけである。
再実行の確認と状態の更新の間に、同じIssueで新しいサイクルが始まると、状態を戻す更新が一意インデックスに拒まれる。
そのエラーは、稼働中の作業項目が現在のサイクルであり、再実行しようとした作業項目は再開されないことを示す。
現在のサイクルの作業項目に従う。

要件が承認された作業項目(`approved`)は終端で、一意インデックスの対象外である。
`implement_enabled`が無効の間は、承認済みの作業項目が長く残る。
その間に同じIssueで新しいサイクルが始まると、新しい作業項目が稼働中となる。
古い承認を使うと、置き換えられた要件定義を実装しかねない。
そこでFactoryは、新しい作業項目を挿入した直後に、同じIssueの古いサイクルの`approved`の作業項目を取り消す。
挿入が競合に負けたときは、何も取り消さない。
取り消しは作業項目のイベントに残る。
取り消した作業項目は終端で、新しいサイクルがあるため、`retry_work_item`でも再開できない。
取り消しの前にプロセスが落ちたときは、古い承認が残る。
残った承認は、同じIssueで次の新しいサイクルが始まるときに取り消される。
それまでも、上のとおり再実行は断られる。

取り消しの後に、Issueへ取り消しを伝えるコメントが付く。
コメントは、新しいサイクルの起動を終えてから投稿する。
コメントには、取り消した要件定義と新しいサイクルの作業項目のIDが載る。
新しいサイクルの要件定義には、あらためて承認が必要なことと、前の承認には対応が要らないことも伝える。
新しいサイクルが途中で失敗することもあるので、承認の依頼が届くとは約束しない。
コメントを投稿できなくても、取り消しは戻らない。
取り消しとコメントの間にプロセスが落ちると、コメントは付かない。
その場合も、人の操作は要らない。

このインデックスを足したmigrationは、既にある重複した稼働中の作業項目のうち、サイクルの古い方を取り消し、その承認待ちの依頼を期限切れにする。
残すのはサイクルが最大の作業項目である。
新しいサイクルがある`approved`の作業項目も、同じmigrationが取り消す。
これらの規則は自動で適用され、人が確かめたものではない。

Issueを取得したインスタンスの所有者が、そのIssueの承認をする。

各インスタンスは、稼働前に`f/factory/factory_config`の`instance_name`を設定する。Discordの通知と承認の画面で、どのインスタンスの担当かを示すのに使うためである。

作業項目の状態は、Consoleの**作業項目**で確かめる。状態の値と意味は[アーキテクチャ](architecture.md)の状態の一覧にある。

### ラベルの扱い

Issue・PRに付けるラベルは、Factoryを起動するトリガーだけである。

| ラベル | 付ける対象 | 起動するもの |
| --- | --- | --- |
| `factory` | Issue | 要件定義 |
| `factory:review` | PR | PRのレビュー |
| `factory:fix` | PR | PRの修正 |

トリガーラベルは、取得のときに外れる。その後はどの状態になっても、FactoryはIssue・PRのラベルを付け外ししない。状態はDBの作業項目にだけあるためである。

もう一度処理させたいときは、人がトリガーラベルを付け直す。付け直すと、新しいサイクルとして別の作業項目ができる。

このリポジトリ自身の基盤整備PRには、`factory:review`と`factory:fix`のどちらも付けない。

### 対象のリポジトリ

Factoryが扱うのは、`factory_config`の`repo_allowlist`に含まれるリポジトリだけである。`repo_allowlist`が空なら、`owners`に含まれるリポジトリ全体が対象になる。

Factory自身のリポジトリ(`factory_repo`)は、`repo_allowlist`の内容に関わらず常に対象である。対象を試験的に絞りたいときは、`repo_allowlist`に対象のリポジトリを明示する。

### オーナーの数値IDを固定する

`owners`の各要素は、GitHubの数値のIDを`id`に持てる。
`id`を省略するか`null`にすると、`id`が無いものとして扱う。
`id`は、ユーザーと組織のどちらも次のコマンドで調べられる。

```bash
gh api users/<名前> --jq .id
```

オーナーが改名して別の人がその名前を取得すると、名前だけの照合では同じオーナーに見える。
`id`を入れると、名前を取得した第三者のリポジトリのIssueとPRが、検索の候補に入らない。
承認を待つ間に名前が入れ替わっても、保存済みの作業項目は、リポジトリを取得する前に止まる。
`allowed_labeler_logins`に古い名前が残っていても、その名前がオーナーの名前なら、そのオーナーのリポジトリのラベルはラベルの確認まで進まない。
候補に入らないので、拒否のnotice(`labeler_denied`)も積もらない。

`allowed_labeler_logins`に古い名前が残っていなければ、`id`が無くても、名前を取得した人はラベルの確認で拒否される。
ラベルの付与者とPRの作成者は、ログイン名で判定するためである。
`id`を入れたオーナーでは、この拒否を待たずに、候補の段階で外す。

`id`があるオーナーは、`poll_issues`と`poll_prs`が検索の前にGitHubの現在のIDを取得して照合する。
IDが一致すれば、そのオーナーを検索する。
食い違うか、IDを取得できないオーナーは、その回の検索を飛ばし、失敗として記録する。
`id`の無いオーナーは、名前だけで動く。
DBから見つけ直す追跡中のPRも、`owners`にあって照合を通ったオーナーのものだけを候補に残す。
飛ばしたオーナーと、`owners`に無い旧名のオーナーのPRは、候補から外れる。
`factory_repo`のPRは、オーナーによらず残る。

食い違いと、名前のアカウントが見つからない(404)ときは、Consoleの**要対応**に`owner_id_mismatch`が残る。
本文にオーナー名と、設定のIDが載る。
食い違いのときは、GitHubの現在のIDも載る。
GitHubでそのアカウントが意図した持ち主かを確かめ、`factory_config`の`owners`の名前か`id`を見直す。
名前とIDが合うと、次の回から検索が再開する。
見直した後に、noticeを解決する。

正規の改名(AからB)のときは、`owners`の名前をBに直し、B側のIssueとPRにトリガーラベルを付け直す。
数値のIDは改名で変わらないので、`id`はそのまま使える。
旧名Aで記録した作業項目は、`owners`から外れても取り消されない。
そのIssueかPRが閉じられたときに、`poll_issues`の整理が取り消す。
実行中のジョブが孤児になったときは、整理が失敗にする。

404以外のすべて(5xx、レート制限、認証の失敗、通信断を含む)でIDを取得できなかったときは、失敗の記録だけが残る。
一時的な障害でありうるので、次の回に再試行する。

#### 作業項目を進める前の照合

作業項目は、検索の時点の`owner`と`repo`の名前を保存する。
承認を待つ間などに名前が別の人に渡ると、保存した名前のURLは別のリポジトリを指す。
そこで、作業項目を進めるステップが、リポジトリを取得する前か、GitHubへ書き込む前に照合する。
対象は次のとおりである。

- 要件定義(`pipeline_prepare`)、実装(`implement_prepare`)、PR修正(`pr_fix_prepare`)、PRレビュー(`pr_review_prepare`)の準備。
- dependabotのPRの取得(`poll_dependabot`)。作業項目を作る前に照合する。
- フォームで投入する`manual_intake_create_issue`。Issueを作る前に照合する。
- Issue化の提案を処理する`issue_proposal_apply`。承認は判断の記録の前に、却下は返信の前に、1回だけ照合する。
- 長い実行を挟んだ後の書き込み。Claudeの実行と検査の間に名前が別の人に渡りうるので、準備の入口に加えて、書き込みの直前にも1回照合する。
  実装の終了処理(`implement_finish`)は、pushとリモートブランチの削除の前に照合する。
  PR修正の終了処理(`pr_fix_finish`)は、pushの前に照合する。
  PRレビューの投稿(`pr_review_post`)は、レビューの投稿の前に照合する。
  draw.ioのビューアを上げる`drawio_viewer_bump`は、`factory_repo_id`をブランチの作成の前に照合する。

照合は、リポジトリのオーナーの名前で`owners`を引いて行う。
大文字と小文字は区別しない。

- 要素が`id`を持つときは、`GET repos/<owner>/<repo>`が返すオーナーのIDと比べる。
- 要素が`id`を持たないときは、照合せず、名前だけで動く。
- 要素が無いときは、リポジトリが`factory_repo`と一致する場合だけ通す。それ以外は対象外として止める。

リポジトリが`factory_repo`と一致し、`factory_repo_id`があるときは、これらより先に、リポジトリ自体のIDも比べる([Factory自身のリポジトリの数値IDを固定する](#factory自身のリポジトリの数値idを固定する))。
cloneを開かない処理にも、この照合を効かせるためである。
cloneを開く準備のステップでは、`openFactoryClone`も同じ照合をするので、取得が1回増える。
通ったときだけ、cloneとcheckoutに進む。
`check_commands_by_repo`のキーは名前だが、`id`を入れたオーナーのリポジトリでは、照合を通ったものにしか検査コマンドが走らない。

止めたときは、Consoleの**要対応**にnoticeが残る。
止めるのは、次のいずれかのときである。

- オーナーのIDが食い違う。
- リポジトリが見つからない(404)。
- オーナーが`owners`に無い。
- `factory_repo`のリポジトリIDが食い違うか、見つからない。

オーナーの照合で止めたときの種類は、`owner_id_mismatch`である。
本文にリポジトリ名が載る。
`owners`に無いときは、オーナーを改名したなら名前を直し、対象にするなら足す操作が載る。
それ以外は、設定のIDが載り、食い違いのときはGitHubの現在のIDも載る。
404は、リポジトリの削除や改名のほかに、PATがそのリポジトリを読めなくなったときにも返る。
privateリポジトリでは、PATがアクセスを失うと、401でなく404になりうる。
GitHubでそのオーナーが意図した持ち主かを確かめ、`factory_config`の`owners`の名前か`id`を見直す。
見直した後に、`retry_work_item`で再実行し、noticeを解決する。

`factory_repo`のリポジトリIDで止めたときの種類は、`factory_repo_id_mismatch`である。
本文にリポジトリ名と、設定の`factory_repo_id`が載る。
食い違いのときは、GitHubの現在のIDも載る。
`factory_config`の`factory_repo`と`factory_repo_id`を見直し、見直した後に、noticeを解決する。

照合に落ちたときの終わり方は、処理ごとに次のとおりである。

| 処理 | 終わり方 |
| --- | --- |
| `pipeline_prepare` | 作業項目を人の対応待ち(`needs_human`)にして、Discordに知らせる。後続のステップは飛ばす |
| `implement_prepare` | 作業項目を人の対応待ちにして、Discordに知らせる |
| `pr_fix_prepare` | 作業項目をブロック(`blocked`)にして、Discordに知らせる |
| `pr_review_prepare` | PRを読む前に、作業項目をブロックにして、Discordに知らせる。forkのPRを見送るときと同じ終わり方である |
| `implement_finish` | pushかリモートブランチの削除の前に止める。何も書かずに、作業項目を人の対応待ちにして、Discordに知らせる。途中までの作業のpushでは、理由を人の対応待ちの理由に足す |
| `pr_fix_finish` | pushの前に止める。作業項目をブロックにして、修正のラウンドは記録せず、Discordに知らせる。返信も投稿しない |
| `pr_review_post` | レビューの投稿とスレッドの解決の前に止める。作業項目をブロックにして、Discordに知らせる。投稿済みのレビューを再利用するときは、書き込まないので照合しない |
| `drawio_viewer_bump` | ブランチもPRも作らずに終わる。`factory_repo_id_mismatch`のnoticeが残る。`factory_repo_id`が無いときは照合しない |
| `poll_dependabot` | 作業項目を作る前に照合する。落ちたら、作業項目を作ってすぐ人の対応待ちにして、Discordに知らせる。フローは起動しない。作業項目は再実行できないので、設定を見直した後は、PRを人が確かめる |
| `issue_proposal_apply`の承認 | 判断を記録せず、GitHubへ何も書かずに、例外で失敗する。承認依頼は`approved`のまま、Issueが作られるまでConsoleの要対応に残る。例外の文は、`factory_repo_id`の食い違いか見つからないとき(404やURLを読めないとき)なら`factory_repo`と`factory_repo_id`、それ以外なら`owners`を見直すよう案内する |
| `issue_proposal_apply`の却下 | 判断を記録した後、返信だけを止め、作業項目は先へ進める。止めた理由はログに残る。照合そのものが失敗したとき(404以外の取得の失敗を含む)も、例外にしない |

`factory_repo_id`の食い違いで止まるときの終わり方は、作業項目のリポジトリで2通りに分かれる。
作業項目が`factory_repo`自身のリポジトリのときは、関門が止めるので、上の表のとおりに終わる。
それ以外のリポジトリのときは、関門を通り、cloneを開く`openFactoryClone`の照合が例外を投げる。
そのときは、ステップが失敗し、フローが失敗する([Factory自身のリポジトリの数値IDを固定する](#factory自身のリポジトリの数値idを固定する))。

照合に落ちたIssue化の提案の承認は、原因を見直して同じ承認をやり直す。
やり直すと、`approval_decide`が起動し直し、続きから処理する。
`approval_decide`は、記録済みの承認を却下に変える操作を断る。
名前が乗っ取られたままのときは、承認依頼が要対応に残り続ける。

404以外のすべて(認証の失敗、5xx、レート制限、通信断を含む)でIDを取得できなかったときの扱いは、処理ごとに次のとおりである。
どれも、noticeは残さない。持続する障害を見逃さないためである。

- 準備のステップと`manual_intake_create_issue`は、ステップが失敗する。
  準備のステップは、原因を直した後に、`retry_work_item`で再実行する。
  `manual_intake_create_issue`は、食い違いと404でも同じく、Issueを作らずにフローが失敗する。
- Issue化の提案の承認は、例外で失敗する。
  判断は記録せず、承認依頼は要対応に残るので、原因を直した後に、Consoleの要対応から承認をやり直す。
- Issue化の提案の却下は、例外にしない。
  返信を止め、作業項目は先へ進む。
  照合が止めたときは警告のログに残り、照合そのものが失敗したときはエラーのログに残る。
  エラーのログには、秘密をマスクした文とエラーの名前が載る。

照合は、処理の始めに行う。
Issue化の提案の承認も、判断の記録の前に照合する。
却下だけは、判断を記録した後に照合する。
照合の後に、実行中に名前が入れ替わっても、その実行は検知しない。

照合しない処理も残る。
同じ項目を、[セキュリティ](security.md#オーナーの数値idの照合)の残るリスクにも挙げている。

- Issueの状態の確認と整理、承認後のIssueへのコメント、PRへの返信。
  名前のままで、投稿の内容は、名前を取得した人の目に触れうる。
- 取り消された作業項目の再開の前に行うIssueの状態の確認と、要件定義を作り直す再実行の前に行うIssueの題名と本文の取り込み。
  どちらも、Console用のworkerに`gh`が無いので、名前のまま読む。
  取り込んだ内容は、続く`pipeline_prepare`の照合が止めるので、Claudeには渡らない。
- 準備の照合から長い実行を挟んで、名前へ書き込む処理。
  実装(`implement_finish`)とPR修正(`pr_fix_finish`)のpush、実装のPR作成とラベル付与、レビューの投稿(`pr_review_post`)である。
  実行中に名前が乗っ取られると、pushでは、ローカルにしか無いオブジェクトが相手に送られうる。
  privateリポジトリでは、履歴が渡りうる。
  PR作成とレビューの投稿では、PRの本文とレビューの文面が渡りうる。
  どちらも、コードの抜粋を含みうる。
  どれも、書き込みの直前には照合しない。
- `drawio_viewer_bump`。`factory_repo`の名前だけで、ブランチとPRとラベルを作る。送る内容は公開物である。

#### ラベルの付与者の判定

ラベルの付与者は、名前で判定する。
タイムラインのラベルのイベントは、GraphQLでユーザーの数値IDを返せる。
しかし、`allowed_labeler_logins`は名前だけを持つ。
名前から数値IDを引くと、今その名前を持つ人のIDが返るので、IDで比べても名前を取得した人は通る。
IDで判定するには、許可するアカウントのIDを設定に持たせる必要があり、今はその設定を持たない。

古い名前が`allowed_labeler_logins`に残ると、その名前を取得した人が、許可されたラベル付与者になりうる。
名前を変えたアカウントは、`allowed_labeler_logins`から外す。
ラベルを付けられる人は、書き込み権限を持つ人に限られない。
公開リポジトリでは、起票者が自分のIssueにラベルを付けられることもある。

### Factory自身のリポジトリの数値IDを固定する

`factory_config`の`factory_repo_id`に、`factory_repo`のGitHubリポジトリの数値IDを入れられる。
省略すると、IDを照合せず、名前だけで取得する。
次のコマンドで調べる。

```bash
gh api repos/<owner>/<repo> --jq .id
```

`self_update`は`factory_repo`のURL(名前)から取得し、リモートの内容を`wmill sync push`で反映する。
ほかの処理も、`factory_repo`のcloneからスキルとテンプレートを読んで、Claudeに渡す。
オーナーが改名して別の人がその名前を取得し、同じ名前のリポジトリを作ると、名前のURLはその人のリポジトリを指す。
その内容は、秘密値を持つworkspaceに反映されたり、Claudeに読まれたりしうる。

`factory_repo_id`を入れると、Factory自身のcloneを用意するすべての処理が、取得の前に、GitHubの現在のIDと照合する。
IDが一致したときだけ、取得に進む。
cloneのoriginは、取得の前に毎回`factory_repo`のURLへ付け替える。
照合したURLと取得するURLは、同じである。

食い違うか、リポジトリが見つからない(404)か、`factory_repo`のURLが`https://github.com/<owner>/<repo>`の形でないときは、取得しない。
Consoleの**要対応**に`factory_repo_id_mismatch`が残る。
本文にリポジトリ名と、設定のIDが載る。
食い違いのときは、GitHubの現在のIDも載る。
GitHubでそのリポジトリが意図した持ち主のものかを確かめ、`factory_config`の`factory_repo`か`factory_repo_id`を見直す。
404は、リポジトリの削除や改名のほかに、PATがそのリポジトリを読めなくなったときにも返る。
privateリポジトリでは、PATがアクセスを失うと、401でなく404になりうる。
そのときは、PATの権限を確かめる。
名前とIDが合うと、次の回から取得が再開する。
見直した後に、noticeを解決する。

照合に落ちたときの振る舞いは、処理ごとに次のとおりである。

| 処理 | 振る舞い |
| --- | --- |
| `self_update` | 取得も反映もせず、成功で終わる。`job_failures`に失敗を記録する。食い違いが続く間は、実行ごとに失敗の行が1行ずつ増える |
| `poll_issues`のデプロイ版の確認 | その回の確認を飛ばし、警告のログを残す。ポーリングは続く |
| 要件定義の準備(`pipeline_prepare`)、実装、PR修正、PRレビューの準備 | 作業項目が`factory_repo`自身のリポジトリのときは、オーナーの照合の関門が先に止める。終わり方は[作業項目を進める前の照合](#作業項目を進める前の照合)の表のとおりである。それ以外のリポジトリでは、取得の前にステップが失敗し、フローが失敗する。作業項目は失敗になり、Discordに`job_failed`が届く。原因を直した後に、`retry_work_item`で再実行する |
| `pipeline_generate` | 関門を呼ばず、`openFactoryClone`の照合だけが行われる。リポジトリIDが食い違うと、取得の前にステップが失敗し、`job_failed`が届く |
| 監査の準備 | 取得の前にステップが失敗し、フローが失敗する。作業項目は失敗になり、Discordに`job_failed`が届く。監査の作業項目は再実行できない。失敗した期間は、次の週次の監査か、**レポート**の**今すぐ監査**で取り込む |
| フォームからのIssueの作成、Issue化の提案の処理 | cloneを開かない。リポジトリが`factory_repo`と一致するときだけ、オーナーの照合の関門が`factory_repo_id`を照合する。食い違いと404では、書き込まずに止める([作業項目を進める前の照合](#作業項目を進める前の照合)) |

404以外のすべて(認証の失敗、5xx、レート制限、通信断を含む)でIDを取得できなかったときは、noticeを残さず、例外としてそのまま失敗にする。
`self_update`のジョブは失敗し、`job_failed`が届く。
持続する障害を見逃さないためである。
`poll_issues`のデプロイ版の確認は、警告のログだけを残す。
次の回に照合が通れば、取得が再開する。

リポジトリ自体の改名や移管では、IDが変わらない。
正規の改名のときは、`factory_repo`のURLを新しい名前に直す。
`factory_repo_id`はそのまま使える。
originは取得の前にそのURLへ付け替わるので、古い名前のcloneが残らない。

照合の限界は次のとおりである。

- 照合は、cloneのロックを取った直後に行う。
  ロックの待ちは、照合から取得までの間に入らない。
- 照合の応答を読んでからfetchするまでの間に、リポジトリが入れ替わる余地は残る。
  この間は、originの付け替えと、fetchの接続である。
- ロックを持つ時間は、照合の1往復の分だけ延びる。
- `isRepoAllowed`は`factory_repo`を名前で常に許す。
  自己改善の起票と、`factory_repo`のPRの候補への採用は、名前のままである。
- 監査のスナップショットのworktreeが、self cloneに既にあるshaを取るfetchは、照合しない。
- Consoleの配信物を取り込む処理と、ホストの`git pull`は、`factory_repo_id`を照合しない。

前回反映したshaが新しいHEADの祖先であることは、force pushで巻き戻す正規の運用が止まるので、反映の条件にしない。

## 作業を投入する

### ラベルで投入する

Issueに`factory`ラベルを付けると、Factoryがそれを拾う。
拾うのは、そのラベルを最後に付けたのが、次のアカウントのときだけである。

- FactoryのPATのアカウント。
- `factory_config`の`allowed_labeler_logins`に挙げたアカウント。

通常は、Factoryを動かすアカウントでラベルを付ける。
確認の仕組みは[ラベル付与の制限](security.md#ラベル付与の制限)にある。

許可されていない人がラベルを付けたIssueは拾わない。
Consoleの**システム**の「情報の通知」に、ラベルを付けたのが許可されていないユーザーである旨(`labeler_denied`)が残る。
付与者を確かめられなかったときも、同じく拾わない。
許可された人がラベルを付け直し、FactoryがそのIssueを取得すると、このnoticeは解決済みになる。
フォームで投入したIssueは`manual_intake_register`が登録するので、このnoticeは自動では解決されない。
Consoleからも解決できない種類なので、DBの掃除が保持期間を過ぎてから解決済みにする。
このnoticeの記録に失敗してもジョブは止まらず、**システム**の「作業項目に紐づかない失敗」に`labeler_denied:<owner>/<repo>#<Issue番号>`として残る。

付与者を確かめるイベントを取得できなかったときは、noticeを残さず、**システム**の「作業項目に紐づかない失敗」に`fetch_labeler:<owner>/<repo>#<Issue番号>`として残る。
取得の直前の確認で取得できなかったときは、同じ節に`confirm_labeler:<owner>/<repo>#<Issue番号>`として残る。
どちらもラベルは外れていないので、操作は要らない。
次のポーリングが、自動で拾い直す。
ラベルを付け直すと付与者が変わるので、付け直さない。

付与者を判定できないIssueは、Consoleの**要対応**に`labeler_check_limit`が残る。
判定できないのは、直近100件のラベルのイベントにトリガーラベルのイベントが無く、それより古いイベントが残っているときである。
このIssueは、人が対応するまで、ポーリングのたびに同じ取得を繰り返す。
拾わせたいときは、ラベルを外してから、許可された人が付け直す。
付け直したラベルのイベントが直近に入り、判定できるようになる。
対応した後は、Consoleでこのnoticeを解決する。

GitHubのIssueフォーム(`.github/ISSUE_TEMPLATE/factory-task.yml`)は、ラベルを付けない。
フォームが付けるラベルは起票者の権限によらず付くため、第三者の起票で作業が始まってしまうからである。
フォームで起票した後は、許可された人が手でラベルを付けて、作業を始める。

### フォームで投入する

Windmillで手動投入のフロー(`f/factory/manual_intake`)を開き、フォームに入力して実行する。FactoryがIssueを作成し、ラベルで投入したときと同じ要件定義の工程に乗せる。

| 入力 | 内容 |
| --- | --- |
| `owner` | 対象リポジトリの所有者 |
| `repo` | 対象リポジトリ |
| `title` | Issueの題名 |
| `body` | このタスクで達成したい目的 |
| `acceptance_criteria` | 受入基準。1行に1項目で書く(任意) |

### 取得の後に登録が失敗したとき

ラベルを外した直後にDBへの登録が失敗すると、そのIssueはラベルと作業項目の両方が無い状態になる。Factoryはこれを自動では拾い直さない。

1. Discordの「人による対応が必要です: Issue #<番号>」の通知を開く。リンクはそのIssueである。
2. 失敗の原因を取り除く。原因は、Consoleの**システム**の「作業項目に紐づかない失敗」にある`claim_issue:<owner>/<repo>#<Issue番号>`か、`poll_issues`のジョブのログで確かめる。DBへの書き込みも失敗しているときは、Consoleに出ず、ジョブのログにだけ残る。
3. そのIssueに`factory`ラベルを付け直す。

作業項目が無いので、**再実行**は使えない。
`poll_issues`のジョブ自体は失敗しない。
Factoryが自分でラベルを付け直さないのは、次の2つの害があるためである。
ラベルの付与者の記録がFactoryに置き換わり、付与者の確認が、人ではなくFactoryに対して行われる。
DBの障害が続く間は、取得と失敗が`poll_issues`のたびに繰り返される。

DBが挿入を確定したのに応答が失われたときは、作業項目が既にある。
付け直したラベルは、作業項目が進行中とみなされて見送られる。
`poll_issues`の点検が作業項目を孤児と判定して失敗にすると、次のポーリングで拾い直される。

### ラベルを外した結果が分からないとき

Factoryは、Issueを取得するときにトリガーラベルを外す。
外す要求が応答なしかサーバーエラーで終わると、外せたのかが分からない。
そこでFactoryは、間隔を空けて最大3回までIssueを読み直す。

- ラベルが残っていれば、外れていないので、次のポーリングが拾い直す。
- ラベルが無ければ、タイムラインでそのラベルを最後に外したユーザーを調べる。FactoryのGitHubユーザーなら、取得できたものとして作業を続ける。別のユーザーなら、先に外した側が受け持つので引く。

次の場合は、外したのが誰か判断できない。

- 読み直しがすべて失敗した。
- タイムラインを読めなかった。
- タイムラインに、最後にラベルが付けられた後の削除の記録が無い。

読み直しやタイムラインの取得がレート制限に当たったときは、繰り返さずにここへ進む。
Issueにはラベルが無いので、次のポーリングは拾わない。

この場合は、Discordに「人による対応が必要です: Issue #<番号>」の通知が届く。
1回のポーリングで複数のIssueが該当したときは、通知は1件にまとまる。
通知の本文に、該当したIssueが`owner/repo#番号`とリンクの組で並び、タイトルとリンクの先は先頭のIssueになる。
並ぶのは10件までで、残りは件数で示す。

手動投入(`manual_intake`)のフローでは、このまとめた通知は届かない。
フローが失敗し、`on_error_flow`のジョブ失敗(`job_failed`)の通知が届く。
対象のIssueはその通知か、**システム**の「作業項目に紐づかない失敗」で確かめ、次の手順2から4に従う。

1. 通知のリンクからIssueを開く。
2. Consoleの**作業項目**で、そのIssueの作業が始まっているか確かめる。
3. 始まっていれば、何もしない。
4. 始まっていなければ、Issueに`factory`ラベルを付け直す。

原因は、Consoleの**システム**の「作業項目に紐づかない失敗」にある`claim_issue:<owner>/<repo>#<Issue番号>`か、`poll_issues`のジョブのログで確かめる。
`confirm_labeler:`と`fetch_labeler:`の失敗は、ラベルを外す前に起きているので、この手順の対象ではない。
付与者の確認で見送ったIssueのnoticeを記録できなかった失敗は、同じ節に`labeler_denied:<owner>/<repo>#<Issue番号>`で残る。

次の場合は、人の操作は要らない。

- 外す要求が失敗し、読み直してもラベルが残っていた。次のポーリングが拾い直す。
- ほかのインスタンスか人が先にラベルを外していた。そのIssueはFactoryが処理せず、Consoleの**システム**の「情報の通知」に`claim_race_lost`が残る。
- ラベルを外せた後に、Issueを読み直せなかった。作業はそのまま進む。

### PRのトリガーラベルが外れたままになったとき

FactoryはPRを取得するとき、トリガーラベル(`factory:review`か`factory:fix`)を外し、外せたか読み直して確かめる。
読み直しが数回とも失敗したときは、ラベルを付け直して引く。次のポーリングが拾い直すので、人の操作は要らない。
Consoleの**システム**の「情報の通知」には、`claim_race_lost`として「確認できなかったのでラベルを戻した」旨が残る。同じPRで作業を始めると、このnoticeは自動で解決済みになる。

次の場合は、ラベルが外れたままで、作業項目も無い。Factoryはそのまま拾い直さない。

- 読み直しがレート制限で失敗した。この場合は、同じ制限に当たるので、ラベルも付け直さない。
- ラベルの付け直しも失敗した。

この場合は、Discordに「人による対応が必要です: PR #<番号>」の通知が届く。
1回のポーリングで複数のPRが該当したときは、通知は1件にまとまる。
本文に、該当したPRがリンクと外れたラベルの組で並ぶ。並ぶのは10件までで、残りは件数で示す。

1. 通知のリンクからPRを開く。
2. PRにラベルが既に付いていないか確かめる。
3. Consoleの**作業項目**で、同じPRの`pr_review`か`pr_fix`が始まっていないか確かめる。
4. どちらも該当しなければ、レート制限の解除を待ってから、外れたラベル(通知の括弧内)をPRに付け直す。

Consoleの**システム**の「作業項目に紐づかない失敗」には、次の行が残る。

- `trigger_review:<owner>/<repo>#<PR番号>`
- `trigger_fix:<owner>/<repo>#<PR番号>`

作業項目が無いので、**再実行**は使えない。`poll_prs`のジョブ自体は失敗しない。
Consoleの**要対応**には、PRごとに`pr_trigger_label_left_removed`が残る。Discordの通知を見逃しても、こちらから該当のPRを確かめられる。
そのPRとラベルで次に作業を始めると、このnoticeは自動で解決済みになる。取得が不要なら、人がConsoleで解決する。
未解決のあいだに同じPRとラベルで再発しても、行は増えず、最初の日時のまま残る。Discordには毎回届く。
リポジトリの改名や移管でPRの表記が変わると、自動では解決されないので、人がConsoleで解決する。

### assigneeが付かなかったとき

Factoryがラベルを外せていれば、Issueにassigneeが付いていなくても作業は進む。
Consoleの**要対応**に`claim_assignee_missing`が残る。
GitHubは、push権限を持たないユーザーのassigneeへの追加を、成功の応答のまま無視するためである。

FactoryのGitHubユーザーが、そのリポジトリのpush権限を持つcollaboratorか確かめる。
持っていなければ、権限を付ける。

## 要件定義を承認・却下する

要件定義の生成が終わると、Discordに承認待ちの通知が届く。

1. 通知のリンクか、Consoleの**要対応**を開く。
2. 一覧から承認を選ぶ。
3. 詳細に表示される取り込み時点のIssue、要件定義書、未確定事項を読む。
4. 承認するなら**承認**を押し、確認のダイアログで承認する。
5. 却下するなら、却下理由を書いてから**却下**を押す。要件定義の却下では、確認のダイアログが出る。

承認した人は、実行したWindmillのユーザー(`WM_USERNAME`、無ければ`WM_EMAIL`)として記録される。承認すると、FactoryはIssueに要件定義へのConsoleのリンクを1件だけ投稿する。

却下すると、Factoryは却下理由を反映して要件定義を作り直し、もう一度承認待ちにする。作り直すたびに試行回数(attempt)が1つ増える。試行回数が上限(`max_attempts`、既定3)に達した後の却下では、作業項目は人の対応待ち(`needs_human`)になる。

承認依頼には7日の期限がある。期限までに判断しなかった作業項目は期限切れ(`expired`)になり、Discordに人の対応を求める通知が届く。期限切れの作業項目は、[失敗した作業を再実行する](#失敗した作業を再実行する)の手順で作り直せる。

### Windmillから直接承認する

Consoleを使えないときは、Windmillで`f/factory/approval_decide`を開き、次の値を入力して実行する。

| 入力 | 値 |
| --- | --- |
| `approval_request_id` | 承認依頼のID。Consoleの**要対応**で承認を選んだときのURL(`?approval=<id>`)にある |
| `decision` | `approve`か`reject` |
| `reason` | 却下の理由。却下では必須 |
| `note` | 補足(任意) |
| `options` | 要件定義の承認では空のままにする |

### 要件定義書を読む

Consoleの**作業項目**にある要件定義の一覧から、要件定義書を選んで読める。一覧には、承認待ちのものに限らず、要件定義のあるすべての作業項目が並ぶ。
書の画面では、試行を切り替えられる。本文は見出し・表・図を含む文書ページの形で表示され、draw.ioの図もページ内に描かれる。

Issueの承認のコメントと、Discordの承認済みの通知のリンクは、要件定義書のページを開く。
ページは承認した試行のもの(`/console/items/<work_item_id>/requirements?attempt=<k>`)である。
承認待ちのDiscordの通知のリンクは、Consoleの要対応でその承認依頼を選んだ状態(`/console/?approval=<id>`)で開く。

旧Consoleは廃止した。過去に投稿された旧Consoleのリンクは、Caddyが`/console/`へ飛ばす。
例は`/apps/get/f/factory/factory_console#requirements/<work_item_id>`である。
新しいConsoleは、そのフラグメントを同じ要件定義書のページに読み替える。
フラグメントの形に合わないリンクは、要対応の画面に着く。
その場合は、リンクの文に書かれた`work_item_id`で作業項目を探す。

### 承認の前後でIssueを直したいとき

Factoryは、Issueを取り込んだ時点の題名と本文で要件定義を作り、実装もその内容で行う。取り込んだ後にIssueを書き換えても、要件定義と実装のどちらにも反映されない。

- 承認の前に直したいとき: Issueは書き換えず、Consoleの**要対応**で却下する。直したい内容を却下理由に書くと、Factoryがそれを反映して要件定義を作り直す。
- 承認の後に作り直したいとき: まず既存のPRを閉じてから、`factory`ラベルをIssueに付け直す。新しいサイクルは別の作業項目・別のブランチ・別のPRになるので、古いPRを残すと重複する。

承認の時点で、現在のIssueの題名か本文が取り込み時点と違うと、承認は断られ、Issueが変わった旨のエラーが出る。次のどちらかで進める。

- Issueを取り込み時点の内容に戻してから、もう一度承認する。取り込み時点の内容は、Consoleの**要対応**で、承認を選ぶと確かめられる。
- 却下する。却下による作り直しは、現在のIssueの題名と本文を取り込み直して要件定義を作る。作り直した要件定義には、あらためて承認が要る。

GitHubから取得できずに断られたときは、しばらく待ってもう一度承認する。
Issueが移されたか削除されたときは、待っても通らないので、却下する。
取得の確認は、GitHubが遅いと1回の承認で最長10秒、Console用workerの2つの枠の1つを塞ぐ。

#### 取り込み内容を更新したとき

却下や再実行による作り直しで、取り込んだ題名と本文を現在のIssueの内容へ更新すると、次の知らせが出る。

- Discordの「取り込み内容を更新」と、noticeの`intake_refreshed`(再実行ではnoticeだけ)。
- Consoleの**要対応**で承認を選んだときの、取り込み時点のIssueの警告。
- 実装のPR本文の「確認して欲しい点」の1行。

Issueが取り込み後に書き換えられたということなので、Consoleで更新後の内容を確かめてから承認する。
確かめずに承認すると、書き換え後の内容がそのまま実装に渡る。
更新の前後の題名と本文は、作業項目の履歴(`work_item_events`)に、文字数とハッシュで残る。

#### 残る制限

承認者は、Consoleの**要対応**で、取り込み時点のIssueと更新の警告を確かめて承認する。
Consoleは、内容を表示できないあいだ、承認を押せないようにする。
確かめずに承認しても、承認の前の確認が働くので、承認の時点で書き換わっているIssueは通らない。
ただし、却下を挟むと、書き換え後の内容が取り込み直されて承認画面に出る。更新を知らせるDiscordとnoticeを見て、Consoleで確かめる。
確認から承認の記録までの間の書き換えは防げない。実装後のPR本文の注記が残りを拾う。

承認の後にIssueを書き換えると、実装のPR本文の「確認して欲しい点」にその旨が1行出る。

## 失敗した作業を再実行する

止まった作業項目は、`f/factory/retry_work_item`で再開する。
再実行はトリガーラベルを付け直さず、対応するフローを直接起動する。
GitHubには何も書き込まない。

どこから実行するかは、作業項目の止まり方で決まる。

| 止まり方 | 実行のしかた |
| --- | --- |
| ジョブが失敗した、人の対応待ち、期限切れで止まった | Consoleの**要対応**で失敗の行を選び、**再実行**を押す |
| ブロックで止まった | Windmillで`f/factory/retry_work_item`を開き、作業項目のID(`work_item_id`)を入れて実行する |

**要対応**の失敗には、状態が失敗、人の対応待ち、期限切れの作業項目が並ぶ。
ブロックは安全策で止めた状態であり、失敗ではないので、**要対応**に出ない。
作業項目のIDは、Consoleの**作業項目**で確かめる。

再実行できる状態と、作業項目の種類ごとに起動するフローは、[作業項目の状態とリース](internals/work-items.md)の「再実行」にある。
監査の作業項目は再実行できない。
監査が失敗した期間は、次の週次の監査か、**レポート**の**今すぐ監査**で取り込む。

### 閉じたIssueやPRの失敗

Consoleの要対応の一覧にある失敗、人の対応待ち、期限切れの作業項目は、対象のIssueやPRを閉じると自動で外れる。
`poll_issues`が5分ごとに、閉じたものを取り消し(`cancelled`)にするためである。
PRのcloseにはマージを含む。
Discordには通知しない。

マージ済みのPRは、閉じた人によらず取り消す。
それ以外は、作者以外の人が閉じたときに取り消す。
作者自身が閉じたときは、作者の関係が許可する関係(`allowed_labeler_associations`、既定はOWNER、MEMBER、COLLABORATOR)のときだけ取り消す。
Botが閉じた対象と、GitHubが閉じた人を返さない対象は、取り消さず、一覧に残す。
判定の理由は[セキュリティ](security.md)の「閉じた人の確認」に書く。
一覧に残した理由と対象は、`poll_issues`のジョブのログにinfoで出る。
一覧に残った作業項目は、再実行して扱うか、リポジトリの権限を持つ人が開き直して閉じ直す。

Botが閉じた対象と、作者が許可されない関係で閉じた対象は、要対応に残る。
たとえば、stale Botが閉じた対象や、依存更新のBotが自分のPRを閉じた対象である。
残った対象は毎回調べ直すので、問い合わせの上限を使い続けることがある。
closing keywordを含むPRをmerge queueがマージしたとき、Issueの`closed_by`がBotか空になるかは実機で確かめる。
Botか空になるなら、Issueの作業項目も要対応に残る。
外すには、人が対象を開き直してから閉じ直す。
PRの作業項目は、マージ済みなら`merged_at`で外れるので、この操作は要らない。
削除された対象(404、410)と、移動したIssue(リダイレクト先の状態を読む)も、一覧に残る。
Consoleから外す操作は無い。

再実行しない失敗を一覧から外したいときは、権限を持つ人が対象のIssueかPRを閉じる。
失敗した監査の作業項目は、対象のIssueやPRが無いので外れない。
対象のIssueやリポジトリが削除されたり、アクセスを失ったりした作業項目も外れない。この場合は`poll_issues`のジョブのログに警告が残る。

取り消した作業項目は、対象を開き直してから再実行できる。
作業項目のIDはConsoleの**作業項目**で確かめ、Windmillの`f/factory/retry_work_item`に渡して実行する。
取り消す前の状態から再実行するのと同じ扱いになる。
対象が閉じたままのときと、開いているかGitHubで確かめられないときは、再実行を断る。
取り消す前の状態からの再実行が二度とできなくなるのを避けるためで、先に開き直してから、もう一度実行する。
この再実行ができるのは、この照合が取り消した作業項目だけである。
Issueの新しいサイクルに置き換えられた作業項目などは、再実行できない。

取り消しは`cancelled`として集計され、`updated_at`も取り消した時刻に更新される。
そのため、**レポート**の分析のリードタイムと、DBの保持期間は、閉じた時刻ではなく取り消した時刻から数える。
PRを開き直しても、追跡は自動では戻らない。
PRは、開き直してから`retry_work_item`で再実行する方法を勧める。
トリガーラベルの付け直しと再実行の両方を行うと、同じPRに作業項目が並んで動くので避ける。
取り消した後にトリガーラベルを付け直したときの断りは、[再実行が拒否される場合](#再実行が拒否される場合)に書く。
トリガーラベルの付け直しは、取り消す前の状態から再実行できないときに使う。

`poll_issues`が1回の実行でGitHubに問い合わせる対象は、30件までである。
対象ごとにIssueかPRの取得を1回行い、閉じた人もこの応答で確かめる。
要対応の一覧が多いときは、前回の続きから調べるので、閉じたものが外れるまでに数回の実行がかかる。
上限に達したことは`poll_issues`のジョブのログに警告で残る。
rate limitを受けたときは、その回の問い合わせを打ち切り、次の実行で続ける。
取得の失敗は、1回の実行につき1行だけ失敗に記録する。

### 再実行が拒否される場合

次のときは、Factoryが理由を示して再実行を拒否する。

| 状況 | 人がすること |
| --- | --- |
| 承認が試行回数に一致しているのに、`implement_enabled`が無効 | 承認済みの要件定義を作り直さないための拒否である。実装させるなら`implement_enabled`を有効にする |
| 承認済みの作業項目で、承認が試行回数に一致しない | 表示された理由を確かめる |
| 作業項目のフローのジョブがまだ実行中か、キュー待ち | Windmillでそのジョブを止めるか、終わるのを待ってから再実行する |
| ジョブの状態を読めない(Windmill APIの一時的な障害など) | 時間をおいて再実行する |
| 読み取った後に、別の処理が作業項目の状態を変えた | Consoleの**作業項目**で今の状態を確かめる |
| 取り消された作業項目の対象のIssueやPRが閉じたまま、または開いているか確かめられない | 対象を開き直して、もう一度実行する。確かめられないときは、時間をおいて実行する |
| 取り消された作業項目の`pr_review`か`pr_fix`に、同じPRで`id`の大きい作業項目がある(取り消した後にトリガーラベルを付け直した)。エラーは「work item N … now tracks the same pull request … follow work item M」 | 取り消した作業項目は再実行せず、エラーに表示された新しい作業項目(M)に従う |
| 取り消された作業項目の対象が移動した。Issueの移動、リポジトリの改名、所有者の移管でGitHubがリダイレクトを返す。エラーは「was redirected (the issue or repository moved); it cannot be restarted」 | 待っても直らず、再実行は常に断られる。Issueなら、移した先のIssueにトリガーラベルを付けて新しく始める |

別の実行が先に作業項目を取っていたときの表示と、再実行の内部の仕組みは、[作業項目の状態とリース](internals/work-items.md)を参照する。

### Windmillの再実行機能は使わない

フローの再実行には、必ず`retry_work_item`を使う。
Windmillの画面でフローを再実行したり、途中のステップから再開したり、フローを直接実行したりすると、新しいジョブIDで動くため何もせずに終わる。
元の実行で進んでいるClaudeや検査も止まらない。

要件定義のフローをWindmillから直接動かすと、作業項目が終端でなければ最大60秒待ってから何もせずに終わる。この実行が例外で失敗しても、作業項目は失敗にならない。

### GitHubのrate limitで失敗したとき

GitHub APIのrate limitの解除を待てないと、作業項目は`GitHubRateLimitError`で失敗になる。
拒まれた要求の副作用は起きていない。
解除を待ってから、Consoleの**要対応**で失敗の行を選んで再実行する。

rate limitが原因で人の対応待ちになったときは、通知の次の操作に、解除を待ってから再実行するよう表示される。
人の対応待ちの作業項目も**要対応**に出るので、解除を待ってから、同じ手順で再実行する。
待つ時間の上限などの仕組みは[通知とrate limit](internals/notifications.md)を参照する。

PRのトリガーラベルを外した直後のrate limitで、ラベルが外れたままになることがある。
作業項目が無く、**システム**の「作業項目に紐づかない失敗」の`trigger_review:`と`trigger_fix:`の行からは再実行できない。
Discordの通知に従い、解除を待ってからラベルを付け直す([PRのトリガーラベルが外れたままになったとき](#prのトリガーラベルが外れたままになったとき))。

### 既定のブランチが食い違って実装フローが失敗するとき

実装フローの準備が、次のエラーで失敗することがある。

```text
origin HEAD is refs/heads/<新しい既定のブランチ>, not refs/heads/<古い既定のブランチ>
```

workerにある対象リポジトリのclone(`/workspaces/<owner>/<repo>/main`)の`origin/HEAD`が、GitHubの既定のブランチと違うことが原因である。
対象リポジトリの既定のブランチの名前を変えたときと、検査コマンドがcloneの`origin/HEAD`を書き換えたときに起きる。
fetchでは`origin/HEAD`が直らないので、再実行しても同じエラーで失敗する。

GitHubで既定のブランチの名前を確かめ、次のコマンドでcloneの`origin/HEAD`を合わせる。

```bash
mise exec -- docker compose -f infra/docker-compose.yml exec windmill_worker git -C /workspaces/<owner>/<repo>/main remote set-head origin <新しい既定のブランチ>
```

その後、Consoleの**要対応**で失敗の行を選び、**再実行**を押す。

## 実装フローを有効にして使う

要件定義の承認の後に実装まで進めるには、`factory_config`の`implement_enabled`を`true`にする。既定は`false`で、その間は作業項目が承認済み(`approved`)で止まる。

実装フロー(`f/factory/implement`)は、実装ブランチ`factory/issue-<N>-wi-<work_item_id>`を作ってpushする。検査に通ったらコミットしてPRを作成する。既にPRがあれば、その本文を更新する。

PRには`factory:review`ラベルが付くので、自動レビューが起動する。PR本文の`Closes #N`で元のIssueに紐づく。マージは常に人が行う。

実装フローの設定値と既定値、時間の上限は[実装フローの仕様](internals/implement.md)にある。時間の設定を変えるときは、そこに書かれたステップのtimeoutの範囲で組み合わせる。実装フローの実行中は時間の設定を変えない。設定を確かめるのは準備のステップだけだからである。

### 検査コマンドを設定する

実装の検査コマンドは、リポジトリごとに`check_commands_by_repo`で設定する。

```json
{
  "<owner>/<repo>": ["bun install --frozen-lockfile", "bun test"]
}
```

- エントリが無いリポジトリでは、検査コマンドを実行しない。PRの修正で使う`allowed_check_commands`は、実装では使わない。
- 検査の前に毎回`git clean -fdX`で無視ファイル(`node_modules/`など)を消す。そのため先頭で依存関係をインストールする。
- workerのイメージにmiseは無い。worker内で直接動くコマンドにする。例は`bun install --frozen-lockfile`、`bun test`、`bunx --bun tsc --noEmit`、`bunx --bun biome check .`である。
- 1つのリポジトリの検査コマンドは4件までを目安にする。検査コマンドが多いほど、修正のラウンドを始められる時間が短くなるためである。
- 検査コマンドが書き込めるのは、worktree、その`HOME`、共有の一時ディレクトリ(`/tmp`、`/var/tmp`、`/dev/shm`、`/dev/mqueue`、`/run/lock`)だけである。main cloneの`.git`に書けないので、`git add`、`git commit`、`git stash`、lint-stagedのように`.git`へ書き込む検査コマンドは失敗する。検査コマンドには使わない。
- 検査コマンドの`TMPDIR`は`HOME`の下を指す。共有の一時ディレクトリに置いたものは、並行して動く別の検査から読めることがある。
- 取り消しやworkerの再起動で後始末が走らなかった検査の残りは、次にその枠を取る検査か、次にそのworktreeを使うステップが片付ける。片付けられない枠は手放して次の枠を試し、`check_slot_skipped`を残す。すべての枠で片付けに失敗したときだけ、検査が失敗する([検査の枠の記録を片付ける](#検査の枠の記録を片付ける))。
- 検査コマンドの枠のユーザーが同時に持てるプロセスは、スレッドを含めて256までである。超えるとforkが失敗し、その検査コマンドは失敗する。子を作り続ける検査コマンドが、workerのほかのジョブを止めないためである。値の根拠は[プロセス数の上限の決め方](security.md#プロセス数の上限の決め方)にある。
- 所有権の受け渡しは、ハードリンクのあるファイルがworktreeに無ければ一括で行い、あればディレクトリごとに行う。
  取り戻しは常に一括で行う。
  ディレクトリごとの受け渡しは、50万個を超えると300秒の上限で打ち切られて検査が失敗する。
  目安は、9,000個のディレクトリで約5秒である。
- 検査がworktreeの外を指すsymlinkを置くと、取り戻しの後に消される。
  `python3 -m venv`の`.venv/bin/python3`のような正当な置き物も消えるが、検査は失敗しない。
  「check sandbox: symlink scan」という失敗した検査が足されるのは、検出が不完全だったときと、追跡されているsymlinkが書き換えられたときだけである。
  足されたら、出力に書かれたパスのコマンドを直す。
- 同時に動く検査が枠の数(8)を超えると、検査は空くのを最大5分待つ。待っても取れなければ「no check slot became free」で失敗し、作業項目は失敗になる。`retry_work_item`で再実行する。
- 検査コマンドに常駐のデーモンを残させない。ロックのファイル記述子を持ったまま残ると、以降のラウンドがロックを取れずに失敗する。記述子を閉じて残ったものも、次の準備やPRの修正を止める。

> [!WARNING]
> 検査コマンドは、Claudeが書いたコードをworker内で非特権のユーザーとして、コンテナの分離なしに実行する。networkとworkerの資源を共有するので、Issueを信頼できる人だけが起票するリポジトリにだけ`check_commands_by_repo`を設定する。

実装ブランチのpushとPRの作成で、人のレビューの前に対象リポジトリ自身のCIも動く。atelier-worksのCIはPRの作成から動く。そのCIが使えるsecretsの範囲を確かめておく。

検査コマンドを実行すると、Consoleの**システム**の「情報の通知」にコンテナの分離が無い検査コマンドの実行(`unsandboxed_check_commands`)が記録される。
本文は件数と対象と作業項目で決まるので、記録は作業項目ごとになる。
同じ本文の未解決の通知があれば、新しく作らず、作成から1日を過ぎていれば時刻を更新する。
秘密情報の検査(gitleaks)は、設定に関わらず毎ラウンド実行する。

### 検査の枠の記録を片付ける

検査は、worktreeを枠のユーザーへ渡す前に、worktreeと`HOME`のパスを枠の記録に書く。
記録はworkerの`/var/lib/factory/check-slots/slot-<N>.state`である。
記録は、所有権をrootに戻し終えたときだけ消える。
残った記録は、次にその枠を取る検査か、次にそのworktreeを使うステップが使って片付ける。
仕組みは[セキュリティ](security.md#枠の記録と片付け)にある。

人が片付けるのは、次の4つの場合である。

- `check_slot_record_unreadable`が残った。
  読めない記録は`slot-<N>.state.corrupt-<時刻>-<乱数>`へ退避されていて、それが指していたworktreeは自動では戻らない。
- `check_slot_skipped`が、worktreeを取り戻せない理由で続く。
- 実装かPR修正が、検査用のユーザーへ渡したworktreeをrootへ戻せないまま止まった。
  理由の詳細は`check sandbox:`で始まり、通知の次の操作がこの手順を示す。
  記録が指すworktreeを取り戻せなかったか、読めない記録が残っていてworktreeにrootでないものがある。
  詳細に枠のユーザーと記録のパスが載る。
  作業領域の掃除が同じ理由でworktreeを飛ばしたときは、`cleanup_worktree_busy`が残る。
- 枠の数(`FACTORY_CHECK_POOL_SIZE`)を減らすか、先頭のuid(`FACTORY_CHECK_UID`)を変える。
  または、検査を枠のユーザーで動かす前の版へ`f/`を戻す。
  範囲の外になった枠の記録と、前の版が読まない記録は、どの実行も片付けないためである。

片付けは、実装フローとPR修正のフローが動いていないときに、次の順で行う。

1. 記録の一覧を見る。

   ```bash
   mise exec -- docker compose -f infra/docker-compose.yml exec windmill_worker ls -l /var/lib/factory/check-slots
   ```

   枠の数を変える前と`f/`を戻す前は、`slot-<N>.state`が1つも無ければ片付けは要らない。

2. 記録の中身を読み、worktreeと`HOME`のパスを確かめる。

   ```bash
   mise exec -- docker compose -f infra/docker-compose.yml exec windmill_worker cat /var/lib/factory/check-slots/<記録のファイル>
   ```

3. worktreeが残っていれば、rootに戻し、グループとその他の書き込みと、拡張のACLを消す。
   ACLは`chown`と`chmod`では消えず、残ると後でrootが作るファイルに、ほかの枠から書ける権限が付くためである。
   `HOME`が残っていれば消す。

   ```bash
   mise exec -- docker compose -f infra/docker-compose.yml exec windmill_worker chown -R -h 0:0 <worktree>
   mise exec -- docker compose -f infra/docker-compose.yml exec windmill_worker chmod -R go-w,ug-s <worktree>
   mise exec -- docker compose -f infra/docker-compose.yml exec windmill_worker setfacl -R -P -b -k <worktree>
   mise exec -- docker compose -f infra/docker-compose.yml exec windmill_worker rm -rf --one-file-system <HOME>
   ```

4. 記録のファイルを消す。

   ```bash
   mise exec -- docker compose -f infra/docker-compose.yml exec windmill_worker rm /var/lib/factory/check-slots/<記録のファイル>
   ```

`check_slot_skipped`のときは、4を飛ばしてもよい。
記録が残っていれば、次にその枠を取る検査が、同じworktreeを取り戻し直してから記録を消す。
止まらないプロセスが理由なら、片付けの前にworkerを再起動する。
片付けた後は、止まった作業項目をWindmillの`f/factory/retry_work_item`で再実行する。

#### 前の版へ戻したときに記録が残っていたら

検査を枠のユーザーで動かす前の版へ`f/`を戻すrevertは、マージすると自己更新が2分以内に反映する。
マージの前に手順1で記録が無いことを確かめても、反映までの間に取り消された検査が記録を残すことがある。
そのため、反映の後にも手順1で記録の一覧を見る。

前の版の`f/`は記録を読まない。
記録が残ったworktreeは枠のユーザーの所有のままで、rootのgitが所有者の違い(`detected dubious ownership`)で実行を拒む。
そのworktreeを使う作業項目だけが失敗(`job_failed`)になり、ほかのworktreeには影響しない。
手順2から4で片付けてから、失敗した作業項目を`retry_work_item`で再実行する。

`f/`はそのままで、workerのイメージだけを前の版へ戻したときは、記録を片付けなくてよい。
記録がworktreeを指していても、そのworktreeを次に使うステップは、取り戻す前にイメージの前提を確かめる。
満たさなければ、所有権と記録のどちらにも触れずに止まり、`host_action_required`を残す。
準備のステップなら、作業項目は[f/とworkerのイメージを両方変えたとき](#fとworkerのイメージを両方変えたとき)と同じ状態で止まる。
作業領域の掃除は、そのworktreeを消さずに飛ばす。
イメージを作り直すまで、そのworktreeを使う作業項目は進まない。
作り直した後の準備のステップが記録を使って取り戻す。
止まった作業項目は、通知が自動で解決されると自動で再開する。

### PRができたら

Discordに実装のPRの通知(`pr_opened`)が届く。通知とPR本文で次を確かめる。

- 保護パスの変更は、実装を止めずにPR本文の「確認して欲しい点」と通知に並ぶ。保護パスは`.claude/**`、`.github/**`、`infra/**`、`mise.toml`、`package.json`、lockfileなどである。
- 保護パスを変えたラウンドでは、検査コマンドを実行しない。PR本文の「動作確認結果」に「検査未実施」と理由が出るので、GitHub側のCIの結果を確かめる。

保護パスの一覧と理由は[セキュリティ](security.md)にある。

### 人の対応待ちになったら

Discordの通知の「次の操作」に従う。主な場合は次のとおり。

| 起きたこと | 途中の変更 | 人がすること |
| --- | --- | --- |
| 実装が変更を生まなかった | 無い | 要件定義を見直すか、Issueを閉じる |
| ラウンド・予算の上限、期限、停滞、差分の超過で止まった(PRが無い) | 秘密情報の検査に通れば、実装ブランチにpush済み | ブランチを確かめて人がPRを作る、要件を直す、不要ならブランチを消す |
| 同じ理由で止まった(PRが既にある) | pushせずworktreeに残す | 同上 |
| symlinkの変更、Claudeの実行の失敗、worktreeの`.git`の書き換えで止まった | pushせずworktreeに残す | 同上 |
| 前のステップのClaudeや検査コマンドが、worktreeに残っている。理由に残っているプロセスが載る | pushしない | 載ったプロセスを止めてから再実行する |
| 検査コマンドがローカルでcommitかブランチの切り替えをした(「worktreeのHEAD(…)が記録したブランチの先頭(…)と異なります」など) | pushしない | 検査コマンドを確かめて人が直してから再実行する |
| commitしたツリーが、検査したツリーと違う | pushしない | 検査コマンドなどが残したプロセスがworktreeを書き換えていないか確かめてから再実行する |
| 途中経過では秘密情報の検査の後に、最終のcommitでは検証の後に、worktreeが変わった(「秘密情報の検査の後にworktreeが変更されました」、「検証の後にworktreeが変更されました」) | pushしない | 同上 |
| 検証のラウンドで、変更の判定と秘密情報の検査の間にworktreeが変わった | そのラウンドで止め、pushしない | 同上 |

完了時に新しい変更が無くても、ブランチに分岐点より先のコミット(途中経過のコミットなど)があれば、FactoryはそれでPRを作るか更新する。ブランチに分岐点より先のものが何も無いときだけ、変更を生まなかったとして止まる。

atelier-worksのCIはPRの作成から動くので、PRを作らずに止まったブランチはCIの結果が無い。
PRを作るか、手元で`mise run check`を実行して確かめる。

原因を取り除いたら、Consoleの**要対応**で人の対応待ちの作業項目を選び、**再実行**を押して、実装フローを再実行する。
途中経過のコミットは、再実行で完了したときのコミットとは別のコミットとして残る。

実装が要件の不足(`requirements_gap`)を報告したときは、Factoryが自動で要件定義を作り直す。再承認すると、同じブランチ名で実装をやり直す。既にPRがあれば、そのPRを更新する。

### 実装フローを再実行するとき

`retry_work_item`で再実行すると、準備のステップが、同じ作業項目の前の実装フローが起動して残っているプロセスを止めてから続ける。
そのため、実行中に同じ実行の検査コマンドなどが残したプロセスがロックを持ち続けて失敗したときは、再実行するだけでよい。

PRの修正のプロセスや、持ち主の分からないプロセスがworktreeを使っていると、作業項目は人の対応待ちになる。
理由に、残っているプロセスが載る。
この場合は、載ったプロセスが終わるのを待つか、何のプロセスかを確かめてworkerのコンテナで止めてから再実行する。

```bash
mise exec -- docker compose -f infra/docker-compose.yml exec windmill_worker kill <pid>
```

残ったプロセスが終端の作業項目のworktreeを使っていると、作業領域の掃除はそのworktreeを消さずに飛ばす。
このときConsoleの**要対応**に`cleanup_worktree_busy`が残る。
載ったプロセスを止めれば、次の掃除で消える。

Windmillで取り消した実行のClaudeや検査コマンドは、止まらずに残る。残ったプロセスの扱いと、実行中に作業項目を取られたときの挙動は[実装フローの仕様](internals/implement.md)を参照する。

### 実装フローの実行中に避けること

- mainへのマージとデプロイを避ける。自己更新は実行中の実装フローを待たずに新しいステップを反映するので、1回の実行の中で別の版のステップが動きうる。実装中(`implementing`)の作業項目があれば、実行中である。
- 実装フローは1回の実行で、workerのプロセス(`NUM_WORKERS`の数だけある)の1つを数時間使う。その間、ほかのフローが使えるworkerはその分減る。
- インスタンスの`job_default_timeout`を設定するなら、21600秒以上にする。実装と検証のステップ、PRの修正の検証のステップより先に打ち切らないためである。

## PRでレビューと修正を使う

PRのレビュー(`pr_review`)と修正(`pr_fix`)の内部の挙動は、[PRワークフローの仕様](internals/pr-workflow.md)にある。

失敗、人の対応待ち、ブロックといった運用上の知らせは、PRには書かずDiscordに送る。PRに書くのは、レビューの指摘と総評、修正の返信だけである。

### レビューを起動する

次のどれかでレビューが起動する。

- PRに`factory:review`ラベルを付ける。
- PRのレビュー依頼かassigneeにこのインスタンスのGitHubアカウントを入れる。

レビュー依頼かassigneeによる起動は、まだレビューしていないcommitがあり、PRの作成者が許可されたアカウントのときだけ起こる。

`factory:review`ラベルは、最後に付けたのが許可されたアカウントのときだけ起動する。
許可されるアカウントはIssueの`factory`ラベルと同じである。
許可されていない人が付けたラベルは、外さずに残し、Consoleの**システム**の「情報の通知」に`labeler_denied`を残す。
そのPRは、人がラベルを外すまで、ラベルを介さないレビューの自動検出も止まる。
追跡中のPRの新しいcommitによる再レビューも、PRの作成者が許可されたアカウントのときに限る。
同じリポジトリのブランチから出した第三者のPRは、許可されたアカウントがラベルを付けたときだけレビューされる。
新しいcommitが入るたびに、ラベルを付け直す。

PRのheadのリポジトリが、このリポジトリと同一でないときは、レビューを始めない。
同じ組織の別のリポジトリのfork、許可されたアカウントのfork、headのリポジトリを取得できないPRも対象である。
ラベルを付けても、レビュー依頼やassigneeを入れても同じである。
forkの内容は第三者が書いたもので、信頼してレビューに渡せないためである。
判定できないときも見送る。
ラベルは外さずに残し、Consoleの**システム**の「情報の通知」に`fork_head_denied`を残す。
作業項目をすでに作っていたときは、終端の`blocked`にして、Discordで人に知らせる。

レビューさせたいときは、同じリポジトリにブランチを作ってPRを出し直す。
通知を止めるには、次のどれかを行う。

- `factory:review`ラベルを外す。
- FactoryのGitHubアカウントを、assigneeとレビュー依頼から外す。
- PRを閉じる。

ラベルとassigneeが残る間は、通知を解決しても次のポーリングで同じ通知が出直す。
PRを閉じるかマージすると、新しい通知は出ない。
残った通知は自動では解決されない。情報の通知なので、要対応の一覧には出ず、`?notice=<id>`で開いた詳細にだけ出る。

修正の材料にするコメントやレビューは、投稿者の関係(`author_association`)が`allowed_labeler_associations`に含まれるものだけにする。

レビューは、GitHubのCOMMENTのレビューとして投稿する。総評とインラインコメントの1行目には、`[pr_review 自動レビュー] @<author>`という印とメンションが付く。運用者自身のアカウントで投稿するため、Factoryの投稿だと分かるようにしている。

総評の文面と、指摘のスレッドを自動で解決する条件は[PRワークフローの仕様](internals/pr-workflow.md)にある。指摘が無いときも、最終的なApproveは人が判断する。

レビューの投稿のステップを再実行すると、前の実行で解決する予定のスレッドは開いたまま残ることがある。人が確かめて解決する。

### 修正を起動する

1. 直してほしい内容を、PRに通常のコメントとして書く。
2. PRに`factory:fix`ラベルを付ける。

Factoryは、ほかの人のコメントと同じく、ラベルの前に書かれた指示を修正の材料として集める。Factoryのレビュー済みのPRにも使える。

修正は`factory:fix`ラベルでしか起動しない。コメントやcommitのpushだけでは起動しない。ただしCIの失敗を直す回は、`watch_pr_ci`が起動する([失敗の自動修正を有効にする](#失敗の自動修正を有効にする))。次の修正を始めたいときは、`factory:fix`を付け直す。
同じPRの修正が動いている間は、`factory:fix`を付けても始まらず、ラベルは保留される。
保留中のラベルは消えずに残る。
その修正が終わった後に、1回だけ新しいラウンドが始まる。

修正の作業項目が`fixing`のまま回収されないとき、同じPRのラベルは保留され続ける。
ジョブが動いていない作業項目は、猶予の後にreconcileが孤児として失敗にする。
猶予は、10分と`claude_timeout_sec`の2倍の大きい方である。
失敗になれば、次のポーリングが保留中のラベルから新しい修正を始める。
猶予を大きく過ぎても進行中のまま残るときは、運用者がConsoleの作業項目の詳細で状態とジョブを確認する。
記録されたジョブが実行中かキュー待ちなら、Windmillでそのジョブを止める。
止めたジョブの作業項目は、猶予を待たず、次の照合で失敗になる。
ジョブを止めても、reconcileが失敗にしないまま残るときは、回復の手段が無い。
`retry_work_item`は進行中の作業項目を再実行できず、Consoleにも取り消しの操作が無い。
DBの`work_items`を直接直す前に、運用者は拾われない原因を確かめて判断する。

修正が終わると、Factoryは各コメントに返信してから再レビューを依頼する。返信の形式は`.claude/skills/factory-fix/SKILL.md`にある。

### 修正の返信の判断

各コメントへの返信は、次の3つのどれかになる。

| 判断 | 意味 | 返信の末尾 |
| --- | --- | --- |
| `fixed` | このPRの範囲で修正した | `対応: <commit sha7>` |
| `skipped` | 対応しないと判断した。理由は返信の本文に書く | `対応: 見送り` |
| `propose_issue` | 指摘は妥当だが、このPRの範囲外。Issue化を提案する | `対応: Issue化を提案(承認待ち)` |

Issue化の提案が1件でもあると、その回の修正は人の対応待ちで終わる。提案が1件でも残っている間は、この状態が続く。

### Issue化の提案を承認・却下する

1. Consoleの**要対応**を開く。Issue化の提案は、要件定義の承認待ちと同じ一覧に種別の印付きで並ぶ。
2. 一覧の題名と種別を見て、提案を選ぶ。
3. 詳細に提案の本文と操作欄が表示される。
4. 起票と同時に要件定義へ進めるなら、「起票と同時にfactoryラベルを付けて要件定義に進める」にチェックを入れる。Issue化の提案では既定でオフである。
5. **承認**か**却下**を押す。却下では理由が必須である。

承認すると、Factoryが対象リポジトリにIssueを作り、レビューのスレッドに`Issue #Nを起票しました。`と返信してスレッドを解決する。チェックを入れていれば、Issueに`trigger_label`(既定`factory`)が付いて要件定義に進む。チェックを外したときは起票だけを行い、必要になったら人が後からラベルを付ける。

却下すると、スレッドに`見送りとします。`と理由を返信する。スレッドは開いたまま残し、人が改めて判断する。

作業項目に未決定の提案が残らなくなると、作業項目の状態が自動で切り替わる。その回でコミットをpushしていれば再レビュー依頼(`rereview_requested`)、pushしていなければレビュー済み(`reviewed`)になる。

Consoleを使えないときは、Windmillで`f/factory/approval_decide`を実行する。入力は[Windmillから直接承認する](#windmillから直接承認する)と同じで、承認では`options`に`{"with_factory_label": true}`のように指定する。

同じ判断で承認や却下をやり直しても安全である。Issueは二重に作られない。既に決まった提案に別の判断を送ると、Factoryは上書きせずにエラーを返す。

起票が途中で失敗した提案は、**要対応**に残る。Issueの作成が失敗したときは未決定に戻る。Issueを作った後の返信やスレッドの解決が失敗したときは、「起票未完了」の印付きで残る。どちらも、もう一度承認すれば続きから起票する。

### 修正を再実行する

失敗(`failed`)、人の対応待ち、ブロック(`blocked`)で終わった修正は、`retry_work_item`で再実行できる。
ただしCIの失敗を直す回は除く([PRワークフロー](internals/pr-workflow.md#CIの失敗を直す回))。
実行のしかたは[失敗した作業を再実行する](#失敗した作業を再実行する)にある。

修正がpushに成功するか、要件定義へ差し戻すまでは、処理済みの位置が進まない。そのため、それ以外で終わった修正を再実行すると、前回と同じ指摘を集め直す。

通知の次の操作は、修正のどこで止まったかで変わる。

| 止まったところ | 例 | 人がすること |
| --- | --- | --- |
| 修正の前(準備のステップ) | PRがドラフト、親のIssueかブランチの実装フローが実行中、worktreeの使用中、時間の設定 | 原因を取り除いてから、`retry_work_item`で同じ作業項目を再実行する。修正のラウンドを使わない |
| 修正の後 | 要件定義への差し戻しの見送り、commitしたツリーが検査したツリーと違う、秘密情報の検査の後にworktreeが変わった、worktreeのHEADが動いた | 原因を確かめてから、新しいラウンドとして`factory:fix`を付け直す |

`factory:fix`を付け直すと、新しい作業項目で修正のラウンドを1つ使う。

前の実行の残したプロセスがworktreeを使っていれば、修正の準備のステップはブロックで止まる。
そのプロセスが同じpr_fixのものであっても、準備のステップは止めない。
実行中にロックが取れずに失敗した修正も、再実行するとこの理由でブロックになる。
この場合は、理由に載ったプロセスが終わるのを待つか、何のプロセスかを確かめてworkerのコンテナで止めてから、`retry_work_item`で再実行する。

```bash
mise exec -- docker compose -f infra/docker-compose.yml exec windmill_worker kill <pid>
```

載ったプロセスを止められないときだけ、workerを再起動する。

```bash
mise exec -- docker compose -f infra/docker-compose.yml restart windmill_worker
```

> [!WARNING]
> workerを再起動すると、同じコンテナで動いているすべてのジョブが止まる。

### 修正の差分に秘密情報が見つかったとき

修正は、pushの前に実装フローと同じ秘密情報の検査(gitleaks)をする。
見つかるとpushせず、作業項目は人の対応待ちになる。
理由には`secrets detected, changes not pushed`が載る。
検出したルール名とファイル名はジョブのログに残り、一致した文字列は残らない。

worktreeの差分から秘密情報を取り除いてから、人が修正するか`factory:fix`を付け直す。

次のときもpushしない。

- 検査の後にworktreeが変わった(`worktree changed after the secret scan`)。
- commitしたツリーが、検査したツリーと違う(`committed tree differs from the inspected tree`)。

検査そのものが失敗したときは、pushせずに作業項目が失敗になる。

返信の投稿に失敗した分は、Consoleの**要対応**に返信の投稿の失敗(`fix_reply_post_failed`)が残る。その場合は、PRで人が返信する。

### 修正が要件の不足を報告したとき

修正のClaudeが要件の不足を報告すると、Factoryは修正をやめ、元のIssueの要件定義を作り直す。作り直せるのは、元のIssueの作業項目が承認済みかPR作成済み(`pr_open`)のときだけである。

元のIssueが実装中や承認待ちのとき、試行回数が上限に達しているとき、読み取った後に状態が変わったときは、作り直さない。修正の作業項目を人の対応待ちにして、Discordで知らせる。実装フローの完了や要件定義の承認を待ってから、`factory:fix`を付け直す。

### PRの状態と人がすること

レビューと修正の作業項目は、次の状態で止まる。

| 状態 | 意味 | 人がすること |
| --- | --- | --- |
| レビュー済み(`reviewed`) | レビューが終わり、修正は不要 | 内容を確かめてApproveする |
| 再レビュー依頼(`rereview_requested`) | 修正をpushし、再レビューを依頼した | 再レビューを待つ |
| ブロック(`blocked`) | 準備の確認でレビューか修正の前に止めた(headがforkのPRのレビューなど)、修正の実行中にPRのheadが動いた、要件の不足で元のIssueへ差し戻した | 通知の理由に従う。修正の前に止めたときは、原因を取り除いて再実行する。headがforkのPRは、同一リポジトリのブランチから出し直す |
| 人の対応待ち(`needs_human`) | 修正を安全策や検査の失敗で止めた、レビューが失敗した、Issue化の提案がある | 通知の「次の操作」に従う |

### ラベルを外した後の追跡

トリガーラベルが外れた後も、Factoryは`tracked_pr_days`(既定30日)以内に更新があったPRをDBから見つけ直す。人が新しいcommitをpushすると、そのたびに再レビューが起動する。1回のpushにつきClaudeの実行は1回である。

それ以上追跡させたくないPRは、closeするか、`tracked_pr_days`を過ぎるまで待つ。

`review_post_mode`を`gated`にすると、レビューを投稿しない。検証用の予約のモードで、PRはレビュー依頼かassigneeからだけ見つけ直す。

### 人が作ったPRを要件と紐づける

PR本文に`Closes #123`と書くと、そのIssueの承認済みの要件と照合する。`Fixes`と`Resolves`も使える。照合できれば、レビューと修正のClaudeに要件を渡す。

## mainのCIを監視する

`watch_main_ci`が5分ごとに、対象リポジトリの既定のブランチ(main)のGitHub Actionsの結果を、コミット単位で確かめる。
対象は、`factory_repo`と`repo_allowlist`のリポジトリである。
`repo_allowlist`の項目は、`owners`の照合を通ったオーナーのものだけが対象になる。`factory_repo`は照合の対象外で、常に対象になる。
照合が一時的に失敗している間は、そのオーナーのリポジトリが対象に入らない。
PATの失効や権限の剥奪などで24時間以上止まると、直前にpushされたコミットの失敗は通知されないことがある。復旧した後は、次のコミットから通知される。
`repo_allowlist`が空のときは`factory_repo`だけを見る。`poll_prs`のように、オーナーの全リポジトリは見ない。
`factory_config`のオーナーやリポジトリの綴りを変えると、そのリポジトリは初めての監視からやり直しになる。既存のコミットは基準として記録し直し、通知しない。
Factoryが作ったコミットも人が作ったコミットも区別せず、原因のPRは特定しない。

mainの実行が取り消されると、`cancelled`は失敗に数えられる。
また、新しいコミットが通ると、古い失敗は直ったとみなして通知しない。
そのため、次の条件を満たすリポジトリだけを、`repo_allowlist`に入れる。

- mainの実行を取り消さない設定である。
- mainのpushで動くworkflowを、パスで絞っていない。パスで絞ると、新しいコミットが通っても、古い失敗は直っていないことがある。その場合、古い失敗は通知されない。

事前に、PATに`Actions: Read-only`を付ける([GitHubのPAT](security.md#githubのpat))。
付けていなくても動き、権限が足りないリポジトリごとに、通知`main_ci_check_denied`が1件残る。

CIが失敗したコミットを見つけると、通知`main_ci_failed`を残し、Discordにも届ける。
リンク先の実行のログで原因を確かめ、直す修正を入れるか、原因のコミットを取り消す。
同じリポジトリでより新しいコミットのCIが通ると、通知は自動で解決される。
mainへのpushで承認待ちになるworkflowなどのために、どのコミットも通らないリポジトリでは、自動で解決されない。人が解決する。
同じコミットの実行をやり直して通っても、失敗は取り消されない。次のコミットが通ったときに解決される。
完了した失敗が1件でもあれば、残りの実行が2時間たっても終わらないコミットも、失敗として知らせる。

次の場合は通知しない。

- 初めて監視するリポジトリの既存のコミット。基準として記録するだけにする。
- 実行が15分たっても現れないコミット。
- 実行が2時間たっても終わらず、完了した失敗も無いコミット。
- より新しいコミットが先に通った後で、古いコミットの失敗が確定した場合。
- 古い失敗の確定。最初に見てから24時間以上たち、より新しい行も記録済みの場合に限る。権限が長く戻らなかった間の古い失敗を、一度に通知しないための扱いである。そのリポジトリで最新の失敗は、通知する。

workerの時計とGitHubの時計が数分ずれても、確定を待つ時間と期限に余裕があるので、判定は変わらない。

1回の実行で呼ぶGitHubのAPIは次のとおりである。

- `owners`の数だけ、オーナーの照合。
- 対象のリポジトリごとに、既定のブランチの取得と、実行の一覧の取得を1回ずつ。
- 判定待ちのコミットごとに、実行の取得を1〜3ページ。1回に取り出す判定待ちは、最大200件である。

1回の実行は、開始から180秒を超えると新しい読み取りを始めず、残りを次の回に回す。

内部の挙動は[mainのCI監視の仕様](internals/main-ci.md)にある。

## PRのCIを監視する

`watch_pr_ci`が5分ごとに、Factoryが作ったPRのGitHub Actionsの結果を、headのコミット単位で確かめる。
失敗を通知する。設定で有効にしたときは、失敗を直す作業項目も起動する([失敗の自動修正を有効にする](#失敗の自動修正を有効にする))。
`watch_pr_ci`自身は、PRとリポジトリへは書き込まず、ログも読まない。
設定`pr_ci_watch_enabled`を`false`にすると、発見、判定、失敗の通知、作業項目の起動をしない。失敗を直す作業項目が終わった行を戻す回復だけは、行があれば動く。行が無ければ、何も読まずに終わる。
回復はオーナーの照合をせず、設定に合うリポジトリのPRを読む。行を戻すPRが閉じていたときは、そのPRの失敗の通知を解決し、未完了の行を`superseded`にする。
照合に伴う通知は足さない。ただし、回復がPRを読めず403か404になると、通知`pr_ci_check_denied`は足しうる。判定が動かない間は、この通知は解決されないので、権限を直した後に人が解決する。
既定は`true`である。

次の条件をすべて満たすPRだけを見る。

- 実装フローが作ったPRで、作業項目が`tracked_pr_days`(既定30日)以内に更新されている。
- 開いていて、下書きでなく、headのリポジトリがベースと同じである。
- headのブランチが`factory/issue-<N>-wi-<id>`の形で、その作業項目が同じPRを指している。
- リポジトリが、`factory_repo`か、`repo_allowlist`と照合を通った`owners`に合う。

人が作ったPRとforkのPRは、追跡せず、通知もしない。自動で書き込む対象を、Factoryが作ったPRに限るためである。

事前に、PATに`Actions: Read-only`を付ける([GitHubのPAT](security.md#githubのpat))。
付けていなくても動き、権限が足りないリポジトリごとに、通知`pr_ci_check_denied`が1件残る。

CIが失敗したheadを見つけると、通知`pr_ci_failed`を残し、Discordにも`needs_human`として届ける。
リンク先の実行のログで原因を確かめ、PRに修正を入れる。
metadataジョブの失敗なら、`mise run metadata`を実行して差分をコミットする。
`mise run metadata`はローカルのWindmillに接続するため、先に`mise run up`でスタックを起動しておく([セットアップ](setup.md#gitのフック))。
metadataジョブはWindmillの起動やログインでも落ちるので、`mise run metadata`で差分が出ないときは、実行をやり直す。
取り消しやフレークなら、実行をやり直す。
通知は、次のときに自動で解決される。

- 同じheadの実行をやり直して通った。
- PRに新しいheadをpushして、そのheadが通った。
- PRを閉じたか、マージした。

次の場合は通知しない。

- 新しいheadがpushされて取り消された、古いheadの実行。
- 実行が15分たっても現れないhead。
- 実行が2時間たっても終わらず、完了した失敗も無いhead。
- 実行の多さや権限の問題で24時間読めないままのhead。

PRのCIが新しいpushで古い実行を取り消す設定のリポジトリを前提にする。
取り消された古い実行は、新しいheadがあれば失敗に数えない。今のheadの取り消しは失敗に数える。
通ったheadの実行を後からやり直して失敗しても、通知されない。
監視を有効にした直後の最初の巡回では、そのとき赤い開いたFactoryのPRが、すべて通知される。

見落としうる限界と内部の挙動は[PRのCI監視の仕様](internals/pr-ci.md)にある。

### 失敗の自動修正を有効にする

設定`pr_ci_fix_enabled`を`true`にすると、`watch_pr_ci`が失敗したheadを直す作業項目を起動する。
既定は`false`で、偽の間は何も起動しない。
起動した作業項目は、失敗した実行のログの抜粋をClaudeに渡して直し、PRのブランチにpushする([PRワークフロー](internals/pr-workflow.md#CIの失敗を直す回))。
通知`pr_ci_failed`は、起動の結果を待たず、これまでどおり失敗を見つけたときに届く。直した結果のheadのCIが通ると、通知は自動で解決される。

次の条件をすべて満たす失敗だけを直す。満たさない失敗は、人が直す。

- 失敗を見つけた時刻が、`pr_ci_fix_enabled_since`以後である。
- PRのすべてのcommitが、Factoryのトレーラーを持つ。トレーラーの無いcommitを含むPRは、自動で直さない。
- 今のheadのFactoryのレビューがある。ドラフトでなく、auto-mergeが有効でもない。
- 失敗が`failure`で、ソースの編集で直せる種類である。metadataジョブの失敗や、取り消しなどで終わった実行は、直さない。
- 同じPRで動いている直す作業項目が無い。
- 日次の予算が残っていて、mainのCIが赤くなく、そのPRで起動した数が`pr_ci_fix_max_rounds`に満たない。
- Factoryのリポジトリの`factory_branch`にあるfactory-fixスキルが、CI回の節(マーカー`ci-fix-skill:v1`)を持つ。ファイルはGitHubのAPIで読む。
  `pr_fix`の準備は毎回`factory_branch`をfetchしてhard resetする。
  起動した後にスキルが変わって作業項目が準備で失敗すると、保留`marker_missing`になり、次の巡回で外れて起動し直す。
  仕組みと損失は[PRのCI監視の仕様](internals/pr-ci.md#判断)にある。

条件を満たさない行は、理由が`pr_ci_checks.fix_hold_reason`に残る。理由と意味は[PRのCI監視の仕様](internals/pr-ci.md#保留の理由の語彙)にある。
一時的な理由は、条件が解ければ自動で外れて起動する。決定的な理由は、そのheadでは外れない。

設定は、WindmillのResourcesの`factory_config`で直す。

| 項目 | 既定値 | 内容 |
| --- | --- | --- |
| `pr_ci_fix_enabled` | `false` | 直す作業項目を起動するか |
| `pr_ci_fix_max_rounds` | `2` | 1つのPRで起動できる数。直近に通ったheadより後を数える |
| `pr_ci_fix_enabled_since` | 無し | この時刻より前に見つけた失敗は直さない。`pr_ci_fix_enabled`が`true`なら必須 |

`pr_ci_fix_enabled`が`true`で`pr_ci_fix_enabled_since`が無い設定は、設定の読み込みが拒否する。Factoryのほかの処理も止まるので、2項目は同じ編集で書く。

有効にする手順は次のとおりである。
有効にした最初の1件を、実際の失敗で確かめるためである。検証用のPRを1件だけ選ぶ設定は無いので、次の順に範囲を絞る。

1. Factoryのリポジトリの`factory_branch`のfactory-fixスキルが、マーカー`ci-fix-skill:v1`を持つことを確かめる。
   ファイルをAPIで読み、マーカーを探す。出力に行が出れば持っている。
   `<owner>/<repo>`は、`factory_config`の`factory_repo`である。

   ```bash
   gh api -H "Accept: application/vnd.github.raw" "repos/<owner>/<repo>/contents/.claude/skills/factory-fix/SKILL.md?ref=<factory_branch>" | grep ci-fix-skill:v1
   ```

   何も出ないときは、`grep`を外した`gh api`単体が成功するかを先に確かめる。ファイルを読めていないだけのことがある。

   マーカーは、保護パスのスキルへの人のPRで入れる。PRがマージされるまで、有効にしない。
   持たないと、すべての失敗が保留`marker_missing`になる。スキルが入れば、次の巡回で外れる。
2. 有効にする前から残る失敗(`failed`の行)を片付ける。PRを直すか閉じる。さらに、赤いFactoryのPRが残っていないかを確かめる。
3. `pr_ci_fix_max_rounds`を`1`にし、`daily_budget_usd`を「当日の使用額に1ラウンド分を足した値」にする。
   当日の使用額は、Factoryが予算の判定に使う集計と同じ式で読む。日の区切りはJSTの0時である。

   ```bash
   mise exec -- docker compose -f infra/docker-compose.yml exec db psql -U postgres -d datatable_db -c "SELECT COALESCE(SUM(cost_usd), 0) AS spent_usd FROM factory.agent_runs WHERE created_at >= date_trunc('day', now() AT TIME ZONE 'Asia/Tokyo') AT TIME ZONE 'Asia/Tokyo'"
   ```

   1ラウンド分は、`max_budget_usd_per_run`(Claude 1回の実行の費用の上限)を単位に見積もる。1ラウンドは複数回の実行を含みうるので、その数を見込んで足す。
   決めきれなければ、小さい値から始め、巡回ごとに様子を見て増やす。
   `daily_budget_usd`はFactory全体で共有するので、使い切ると`pr_review`など、ほかのフローも止まる。
   走行中の分は数えないので、予算を使い切るまで、巡回ごとに最大2件を起動しうる。
4. `pr_ci_fix_enabled_since`へ有効にする時刻を書く。同じ編集で`pr_ci_fix_enabled`を`true`にする。
5. 有効にした後の最初の失敗で、起動した作業項目の結果をConsoleで確かめる。
   失敗したのに起動しなかったときは、保留の理由を読む。

   ```bash
   mise exec -- docker compose -f infra/docker-compose.yml exec db psql -U postgres -d datatable_db -c "SELECT id, owner, repo, pr_number, head_sha, state, fix_hold_reason, fix_attempts, fix_work_item_id FROM factory.pr_ci_checks WHERE state IN ('failed','fixing') ORDER BY updated_at DESC LIMIT 20"
   ```

   理由ごとの意味は[保留の理由の語彙](internals/pr-ci.md#保留の理由の語彙)の表にある。
   一時的な理由は条件が解ければ自動で外れる。決定的な理由は人が対処する。
   ジョブIDの未記録でフローを取り消した回が起きたときは、Discordの通知(`job_failed`)が増えるかを見る。取り消したフローで失敗時の通知が動くかは、確かめていない。
6. 結果に問題が無ければ、`pr_ci_fix_max_rounds`と`daily_budget_usd`を戻す。

止め方は次のとおりである。

- すべてを止めるには、`pr_ci_fix_enabled`を`false`に戻す。動いている作業項目は止まらず、終わると回復が行を戻す。有効に戻すときも、`pr_ci_fix_enabled_since`を戻す時刻に書き直す。書き直さないと、止めている間に見つけた失敗まで直しにいく。
- 1つのPRだけを止めるには、PRをドラフトにする。ドラフトのPRは起動せず、動いている作業項目も、準備かpushの直前でドラフトを見て止まる。

直す作業項目が`cancelled`になるのは、PRが閉じたときだけである。閉じたPRの行は、`superseded`になる。

## 監査を使う

Factory自身の運用記録の監査は、毎週月曜09:30に自動で走る(`audit_kickoff`)。Consoleの**レポート**の**今すぐ監査**で前倒しできる。

次のときは監査を始めず、スキップの理由を表示する。

- 実行中の監査がある。
- 対象の期間が空である。
- 新しい記録が無い。
- 日次の予算を超えている。

監査レポートはConsoleの**レポート**で読む。一覧から選ぶと、本文が表示される。

Discordの監査完了の通知(`audit_completed`)のリンクは、監査レポートのページ(`/console/reports/audit/<work_item_id>`)を開く。旧Consoleの`#audit/<work_item_id>`のリンクも、同じページに読み替える。

改善提案は、Consoleの**要対応**に「改善提案」として並ぶ。承認すると、Factory自身のリポジトリにIssueを起票する。「起票と同時にfactoryラベルを付けて要件定義に進める」は、改善提案では既定でオンである。外せば起票だけになる。Factory自身のリポジトリは常に対象なので、ラベルを付けたIssueはそのまま要件定義に進む。

監査の内部の挙動は[監査の仕様](internals/audit.md)にある。

## dependabotの更新を設定する

dependabotが開いた依存の更新PRを、Factoryが評価して自動でマージできる。
`f/factory/factory_config`の次の3つの項目で設定する。
`factory_config`は同期の対象外なので、WindmillのResourcesの編集画面で直す。

| 項目 | 既定値 | 意味 |
| --- | --- | --- |
| `dependabot_enabled` | `false` | dependabotのPRを自動で処理するか |
| `dependabot_merge_enabled` | `false` | マージしてよいと判断したPRを、実際にマージするか。偽の間は試運転で、そのPRを人に回す |
| `dependabot_min_published_days` | `7` | 更新先の版が公開されてから、マージしてよくなるまでの日数 |

`dependabot_min_published_days`は、公開から日が浅い版を自動でマージしないための下限である。
1以上の整数にする。0、負の値、小数は設定の読み込みで拒否する。
既存のリソースにこれらの項目が無くても、既定値で動く。

対象は、`factory_repo`と`repo_allowlist`のリポジトリである。
`repo_allowlist`の項目は、`owners`の照合を通ったオーナーのものだけが対象になる。
`repo_allowlist`が空のときは`factory_repo`だけを見る。`poll_prs`のように、オーナーの全リポジトリは見ない。
対象のリポジトリを足すときは、そのリポジトリの`main`のrulesetと必須チェックの名前が、[マージする条件](security.md#マージする条件)の7件と同じかを確かめる。

マージする条件と残るリスクは[セキュリティ](security.md#dependabotの更新の自動マージ)に、選び方と状態は[dependabotの更新の内部仕様](internals/dependabot.md)にある。

### 有効にする

有効にする順は、単独の実験、試運転、マージの順である。
1つずつ確かめてから進める。
設定を一度に変えると、問題が起きたときに原因を切り分けられないためである。

1. `dependabot_enabled`を`false`のまま、`poll_dependabot`の実行の結果が`enabled: false`で終わることを、WindmillのRunsで確かめる。
2. [有効化の前の確認](security.md#有効化の前の確認)の、試運転の前に単独の実験で確かめる項目を確かめる。
   フローは使わない。
   満たさなければ、試運転を始めない。
3. `dependabot_merge_enabled`が`false`であることを確かめてから、`dependabot_enabled`を`true`にする。
   これで試運転が始まる。
4. 次の`poll_dependabot`の実行の結果を確かめる。
   フローを起動していれば、`dependabot`フローの3つのステップの結果と、作業項目の終わり方を確かめる。
5. 同じ節の、試運転で確かめる項目をすべて確かめる。
6. 同じ節の、マージの前に確かめる項目をすべて確かめる。
   マージにはPATのContentsの書き込みが要る。
   実際にマージできるかは、この確認で確かめる。
   classicのPATはリポジトリ単位で権限を絞れないので、fine-grainedのPATを使う。
7. `dependabot_merge_enabled`を`true`にする。
8. 最初のマージの結果を確かめる。
   問題があれば、すぐに`dependabot_merge_enabled`を`false`に戻す。

### 初回の実機で確かめること

試運転とマージの最初の数件は、次の点を作業項目の結果とWindmillのRunsで確かめる。

- 隔離したインストールが、npm registryに届き、`--frozen-lockfile`で成功する。
- インストールが、準備のステップのtimeout(3600秒)の中で終わる。
- 影響調査のClaudeの出力が、構造化出力の形で受け付けられる。
- 試運転でマージ可と判定したPRが、理由「dry run」で人に回る。
- マージしたPRのsquashのcommitの題名が固定の文で、本文が空である。
- 人に回したPRの通知に、PRのリンクと次の操作が載る。

### 無効にする

マージだけを止めるときは、`dependabot_merge_enabled`を`false`にする。
処理は続き、マージしてよいと判断したPRは人に回る。

すべてを止めるときは、`dependabot_enabled`を`false`にする。
次の実行から、`poll_dependabot`はGitHubとDBのどちらにも触れずに終わる。
動いているフローは、準備と終了のステップで作業項目を取り消し(`dependabot_disabled`)、GitHubに書かない。
影響調査のステップも、無効ならClaudeを起動しない。
スケジュールは、Windmillの画面で無効にして止めない。
`mise run push`がリポジトリの定義で有効に戻すためである。

### 人に回ったとき

dependabotの作業項目は再実行できない。
通知のリンクからPRを開き、理由とPRのコメントの所見を確かめて、手でマージするか閉じる。
理由が「dry run」なら、マージしてよいと判断したPRである。
このPRは、確かめて手でマージする。
`dependabot_merge_enabled`を有効にしても、このPRは再評価されない。
試運転を終えるなら、`dependabot_merge_enabled`を有効にする。
有効にした後の新しいPRとheadから、マージが始まる。
影響の所見が出たPRを修正に回すときは、所見を確かめてから`factory:fix`ラベルを付ける。
修正をpushしたPRは、自動ではマージされないので、レビューを確かめて人がマージする。
新しいcommitが積まれると、Factoryは新しいheadを改めて評価する。

## モデルを使い分ける

Factoryは、工程によってClaudeのモデルを使い分ける。
間違えたときにやり直しが高くつく判断は上位のモデルに任せ、安く直せる作業は既定のモデルで済ませるためである。
モデルは`f/factory/factory_config`の2つの項目で決める。

| 項目 | 既定値 | 使う工程 |
| --- | --- | --- |
| `model` | `claude-sonnet-5-5` | 実装、PR修正 |
| `heavy_model` | `claude-opus-5-5` | 要件定義の生成、PRのレビュー、監査 |

実装とPR修正は、同じ作業で`model`が続けて2回失敗したら`heavy_model`に上げる。
Sonnetで試して届かなかった課題を、上位のモデルでやり直すためである。
数えるのは直近に連続した失敗で、成功が1回入ると数え直して`model`に戻る。
基盤の障害で数えた失敗が、復旧した後も`heavy_model`のまま残らないようにするためである。
`model`が成功と失敗を交互に出す課題は、連続しないので上がらない。
失敗は、工程ごとに次の記録から数える。

- 実装は、同じ作業項目の同じ要件定義(同じ試行)の実装ラウンドを新しいほうから見て、検査が通らなかったもの、変更が進まなかったもの、Claudeの実行が失敗したものを数える。
  検査に通ったラウンド、検査をしなかったラウンド、要件の不足を返したラウンドに当たったら、そこで数えるのをやめる。
  実装フローの中の修正ラウンドも、`retry_work_item`で再開する前の失敗も、続いていれば合わさる。
- PR修正は、次の2つの大きいほうを失敗の数にする。
  - 同じPRの直近に連続した失敗。内訳は「PR修正の連続した失敗」にある。
  - 再レビューで指摘が続いたラウンドの数。作業項目のラウンド番号(`fix_round`)から1を引いた値である。

実装のラウンドが停滞したときの扱いは、[実装](internals/implement.md)の「ループの終わり方」にある。

要件定義の却下や実装中の要件の不足で試行が増えても、それだけでは上げない。
試行が増えると、実装の失敗の数は0から数え直す。
要件定義の生成、PRのレビュー、監査は、失敗の数にかかわらず`heavy_model`を使う。

実際に使ったモデルは、Claudeの実行の記録(`agent_runs`)の`model`列に残る。
`heavy_model`に上がったかどうかは、この列で確かめる。

`heavy_model`が無い既存のリソースでも、既定値の`claude-opus-5-5`で動く。
一方、既存のリソースに`model: claude-opus-5-5`が書かれていると、既定が変わっても書き換わらない。
その間は、実装とPR修正もOpusで動く。
Sonnetを既定にするには、Windmillの画面で`f/factory/factory_config`を開き、`model`を`claude-sonnet-5-5`に書き換える。
リソースはgitで同期しないので、リポジトリの変更だけでは反映されない。

モデル名は、英数字で始まり、英数字と`.`、`_`、`-`、`[`、`]`だけで書く。
`-`で始まる値や空白を含む値は、設定の読み込みで拒否する。`claude --model`の引数にそのまま渡すためである。

このリポジトリでClaudeを使うときのモデルの方針は、[コーディング規約](coding-guidelines.md)の「Claudeのモデルの使い分け」にある。

### PR修正の連続した失敗

同じPRの修正のうち、`blocked`でないラウンド(`done`か要件の不足)で最後に終えた時刻より後の、次の3つを足す。

- Claudeが動いたのに修正をpushせず`blocked`で終えたラウンド
- 検査が通らず再実行したラウンド
- Claudeの実行そのものの失敗(ターン上限、予算上限、タイムアウト、不正な出力)

新しい指摘でラベルを付け直しただけのラウンドは数えない。
Claudeが動かなかったラウンドも数えないが、同じ作業項目で前にClaudeが動いていれば数える。
適用の実行(`pr_fix_apply`)の失敗は例外で終わってラウンドの記録を残さないので、実行の記録(`agent_runs`)の`error`から1回ずつ数える。
検査の再実行の失敗は、`pr_fix_verify`ステップで起きる。
例外にならず、`blocked`のラウンドを残すので、そのラウンドを`blocked`の1回として数える。
flowの再試行や`retry_work_item`で同じ作業項目の実行が何度失敗しても、失敗した回数だけ数える。
ラウンドの記録と重なる失敗は、次のように扱う。

- `blocked`で終えたラウンドの直前の実行の失敗は、`blocked`の1回に含めて重ねない。
  たとえば、検査の再実行が失敗して`blocked`になったときである。
- `blocked`のラウンドより前の失敗と、`blocked`の後に`retry_work_item`で再実行した失敗は、別に数える。
- `done`か要件の不足で終えたラウンドより前の失敗は数えない。成功が入ったので、連続が途切れるためである。
- 不正な出力を返して再試行したときは、捨てた最初の試行を数えず、再試行も失敗したときだけ1回と数える。
  捨てた試行は、同じ作業項目、stage、試行で10秒以内に次の記録がある失敗として見分ける。
  別の実行の記録は、flowの再試行の60秒の待ちを経て書かれるので、10秒以内には来ない。
  この見分けは、捨てた行と最後の行が同じ実行の中で続けて書かれ、両者の書き込みの間が10秒を超えないことを前提にする。
- 検査の再実行は、作業項目ごとに1回と数える。
  同じ作業項目で再実行が続いても増えない。
- 同じラウンドで検査の再実行と`blocked`が重なると、2回と数える。初回と再実行で、Sonnetが2回失敗しているためである。

### ラウンドの数を下限にする理由

Sonnetが毎回修正をpushして`done`で終え、再レビューで同じ指摘が付く経路は、失敗の記録が残らない。
連続した失敗だけでは、`max_fix_rounds`に達するまでSonnetのまま回って昇格しない。
そこで、ラウンド番号から1を引いた値を下限にする。
3ラウンド目に入ると、失敗の記録が無くても失敗の数が2になり、`heavy_model`を使う。

2つの数は、大きいほうを取る。足さない。ラウンドの数は`blocked`で終えたラウンドも含むので、足すと同じラウンドを2回数えるためである。
そのため、2ラウンド目(下限は1)で適用の実行が1回失敗した後のflowの再試行は、`max(1, 1)`で`model`のままになる。
一方、検査の再実行は下限に1回を足すので`heavy_model`になる。この非対称は受け入れる。検査の再実行は検査に落ちた後の2回目の修正で、モデルの失敗が確かである。flowの再試行は基盤の障害でも起きるためである。
合わせると、次のように振る舞う。

- ラウンド番号は戻らないので、3ラウンド目以降は`heavy_model`から`model`に戻らない。
  `model`に戻れるのは、1、2ラウンド目に限る。
- 基盤の障害は、同じ作業項目の再実行で積み重なり、ラウンド番号を進めない。
  障害で下限が上がるのは、障害で作業項目が停止して、人が新しい指摘でラベルを付け直し、新しいラウンドが始まったときだけである。
- 復旧して最初の実行は、直前の失敗が残っているので`heavy_model`で動く。
  それが成功してラウンドが`done`で終わると、連続は途切れる。
- 新しい指摘が付いたラウンドも数える。指摘が続くだけで上がる粗い数え方で、誤差は早く上がる方向に出る。

PR修正の検査の再実行では、このラウンドの最初の修正が検査に通らなかった失敗が、まだ記録に無い。
そこで、検査の再実行のモデルを決める`prFixRetryModel`が、記録から出した失敗の数にその1回を足してモデルを選ぶ。
下限に当たるときも1回足すので、2ラウンド目の検査の再実行は`heavy_model`で動く。

### 数えるものの粗さ

数えるのは記録に残った結果だけなので、モデルの失敗でないものも入る。

- 実装の`error`と`check_failed`には、トークンの失効やAPIの障害、期限切れ、`.git`ポインタの不一致など、基盤の失敗も含まれる。
- PR修正の`blocked`には、返信だけで終えて何もcommitしなかったラウンド、人のpushでheadが動いたラウンド、ロックなど基盤の停止も含まれる。
  実行の失敗には、トークンの失効やAPIの障害も含まれる。
- PR修正は同じPRで数える。要件の不足で要件定義をやり直しても、ラウンド番号は戻らない。
- 返信だけでcommitの無いラウンドは`blocked`で記録される。基盤の障害の後で、Sonnetが正しく見送りを返しても、連続は数え直されない。記録から見送りと失敗を見分けられないので、多めに数える。
- `done`で終えた後に`retry_work_item`で再実行し、検査の再実行が起きても、時刻の比較で成功より前になるため数えない。昇格が1回遅れる側に外れるので受け入れる。

そのため、基盤の失敗が2回続くと`heavy_model`に上がる。
一方、次に成功したラウンドで数え直すので、復旧すれば`model`に戻る。
上がり方が早すぎても、損失の上限は`max_fix_rounds`(PR修正)、`implement_max_rounds`(実装)と、予算の上限で決まる。
ただし、PR修正を`retry_work_item`で再実行してもラウンドの番号は進まない。
人が再実行を繰り返す間は、予算の上限だけが損失を抑える。

## 通知を受けたら

Factoryは、人の行動が要るものだけをDiscordに送る。通知の仕組み、送れなかったときの扱い、rate limitは[通知とrate limit](internals/notifications.md)にある。

> [!NOTE]
> 通知は失敗しても再送しない。通知が来ないときは、ConsoleとGitHubで状態を確かめる。

### Discordの通知

| 通知 | 意味 | 人がすること |
| --- | --- | --- |
| Issue着手(`issue_claimed`) | FactoryがIssueを取得し、要件定義の生成を始めた | なし |
| 承認待ち(`approval_requested`) | 要件定義が承認待ちになった | [要件定義を承認・却下する](#要件定義を承認却下する) |
| 要件定義承認(`requirements_approved`) | 要件定義が承認され、Issueにリンクを投稿した | なし。実装が有効なら実装フローが始まる |
| 人による対応が必要(`needs_human`) | 作業項目が人の対応待ちか期限切れになった。または、Factoryが作ったPRのCIが失敗した。通知を新しく残したときに届く | 通知の「次の操作」に従う。作業項目を再実行するときは、Windmillで`retry_work_item`を実行する。PRのCIの失敗は[PRのCIを監視する](#prのciを監視する)にある |
| ジョブ失敗(`job_failed`) | フローやスケジュールが失敗した。孤児のジョブや閉じたIssue・PRの片付けも含む | Consoleの**要対応**の失敗か、**システム**の「作業項目に紐づかない失敗」で内容を確かめる。作業項目の失敗は再実行する。dependabotの作業項目は再実行できないので、通知の「次の操作」に従ってPRを人が確かめる |
| PR作成・更新(`pr_opened`) | 実装フローがPRを作成か更新した | [PRができたら](#prができたら) |
| PRレビュー完了(`pr_reviewed`) | レビューを投稿した | 指摘を確かめる。指摘が無ければApproveを判断する |
| PR修正適用(`pr_fixed`) | 修正をpushし、再レビューを依頼した | 再レビューを待つ。補足に依頼の失敗が載っていれば、GitHubのPRで人がレビュアーを依頼する |
| Consoleの取り込みの問題(`console_fetch_problem`) | Consoleの取り込みが失敗したか、結果が30分以上更新されていないか、状態を読めない | 通知の「次の操作」に従う。通知を新しく残したときだけ届く |
| ホスト側の作業が必要(`host_action_required`) | 自己更新が反映した版に、ホスト側の作業が要る変更(`infra/`、`mise.toml`の`[tools]`・`[env]`)が含まれる。通知を新しく残したときだけ届く | [ホスト側で反映するもの](#ホスト側で反映するもの)の手順で、`mise run up`を実行する |
| mainのCIの失敗(`main_ci_failed`) | 対象リポジトリのmainのコミットで、CIが失敗した。通知を新しく残したときに届く | [mainのCIを監視する](#mainのciを監視する) |
| 日次サマリー(`daily_summary`) | 前日のコスト、件数、失敗、DBの掃除の件数、workerの負荷 | 異常が無いか見る。負荷の見方は[日次のまとめでの見方](#日次のまとめでの見方)にある |
| 監査レポート(`audit_completed`) | 監査で改善提案が1件以上できた | Consoleの**要対応**で提案を承認か却下する |

GitHubのPATが失効していると、Issueの取得のスケジュール(`poll_issues`)がジョブ失敗として通知される。PATを再発行する手順は[秘密をローテーションする](#秘密をローテーションする)にある。

### 通知の種類

noticeには、Discordに送らない事項と、Discordに届かなくても残しておく事項が残る。

通知には重要度がある。
「要対応」の通知は、解決するまでConsoleの要対応の一覧に残る。
「情報」の通知は、人の行動が要らないので要対応の一覧に出さず、Consoleのシステムの画面の「情報の通知」に7日だけ出す。
内容を確かめたいときは、行の「詳細」から要対応の画面の詳細を開く。
表に無い種類は「要対応」として扱う。
「情報」の種類は次のとおりである。

- `approval_notify_failed`
- `claim_race_lost`
- `supersede_failed`
- `cleanup_worktrees_skipped`
- `workspace_disk_usage`
- `fix_feedback_association_excluded`
- `labeler_denied`
- `fork_head_denied`
- `unsandboxed_check_commands`
- `implement_needs_human`

| 種類 | 意味 | 人がすること |
| --- | --- | --- |
| `approval_notify_failed` | 承認待ちの通知がDiscordに届かなかった | 承認依頼は記録済みなので、Consoleの**要対応**で判断する |
| `intake_refreshed` | 却下や再実行による作り直しで、Issueが取り込み後に書き換えられていたので、取り込み内容を現在のIssueで更新した | Consoleの**要対応**で更新後の内容を確かめてから、承認する。確かめたら解決する |
| `approval_comment_failed` | 承認のコメントをIssueに投稿できなかった | 承認と実装の起動は進んでいる。必要ならnoticeのリンクを載せたコメントを人がIssueに投稿する |
| `implement_launch_failed` | 承認の後、実装フローへ進める処理がDBの失敗で例外になった | Windmillで`f/factory/retry_work_item`を作業項目のIDで実行して再開する |
| `implement_needs_human` | 実装フローが人の対応待ちで止まった。作業項目はConsoleの**要対応**の失敗に出る | [人の対応待ちになったら](#人の対応待ちになったら)で原因を取り除いてから、**要対応**の失敗で**再実行**を押す |
| `unsandboxed_check_commands` | 検査コマンドをコンテナの分離なしで実行した | 設定が意図どおりか確かめる |

### Console用のworkerの検知を確かめる

Console用のworkerがジョブを受けているかどうかは、自己更新(`self_update`)が毎回の最後に確かめる。
workerの一覧を読むAPIは、ジョブのトークンでは読めない(Forbidden)ので、読めるqueueとジョブの履歴を見る。
判定は次の順で決める。

1. tag `console`のジョブのうち、予定時刻を過ぎても実行が始まっていないものを、古い順に100件まで読む。予定時刻から5分以上待っているものが1件でもあれば、workerがジョブを受けていないと判定する。
2. 待っているジョブが残っている(5分未満)か、Console用のworkerが`console_fetch_watch`を30分以内に完了していれば、問題なしと判定する。ジョブが作られていることが、スケジュールが生きている証拠になる。
3. どちらも無ければ、判定できないものとして扱う。

完了の記録は、`console_fetch_watch`の完了した実行を新しい順に10件読み、tagが`console`で、取り消されていないものだけを数える。
手動の実行やpreviewはdefaultのworkerで動き、人が取り消したジョブもworkerの動作の証拠にならないためである。
完了時刻は、`completed_at`があればそれを使い、空なら開始時刻に所要時間を足して出す。Windmillの応答では`completed_at`が空のことがある。
失敗した実行は、workerがジョブを受けて動いた証拠として数える。

`console_fetch_watch`が10分ごとにtag `console`のジョブを作る。
workerがジョブを受けなければそのジョブが待ち続けるので、止まってから約20分かけて検知する。
内訳は、ジョブの作成の間隔10分、待ちの5分、自己更新の間隔2分に、自己更新の実行時間を足した値である。
この確認は自己更新の最後に走るので、同じ回で反映が走ると、その分だけ検知が遅れうる。
反映の`wmill`は2回で最大10分かかり、約20分の余裕の3分を超えうる。

通知`console_worker_missing`が立つのは、workerが居ないときだけではない。
workerが居ても、2枠とも塞がっているときや、tagの設定がずれてジョブを受けないときにも立つ。
通知の次の操作に従い、コンテナの状態、再起動、Windmillの画面での実行中のジョブとワーカーグループのtagの順に確かめる。

次の点に注意する。

- workerが動いていても、ジョブが大量に溜まると5分以上待つことがある。通知が出たら、待っているジョブの数と実行中のジョブを確かめる。
- workerは居るがジョブが毎回すぐ失敗するときは、この検知では拾わない。スケジュールの失敗の検知(`schedule_failing`)が拾う。
- `mise run up`でConsole用のworkerを作り直している間は、`console_worker_missing`が出うる。作り直しが終われば、通知を解決する。
- この検知は、`console_fetch_watch`のスケジュールが有効なことを前提にする。スケジュールを無効にするか削除すると、待つジョブと完了の記録が新しく増えなくなる。判定できない回が続き、1時間で`console_worker_check_failed`になる。

確認できなかった回は、自己更新のジョブログに警告を残し、通知は出さない。
警告は次の4種類である。

- `could not list the waiting console jobs`: 待っているジョブの一覧を読むAPIが失敗した。権限が足りないときもこうなる。
- `could not list the recent console_fetch_watch runs`: 完了した実行の履歴を読むAPIが失敗した。
- `could not confirm the console worker from the job lists`: 応答が一覧の形でない。または、待つジョブも30分以内の完了も無い(完了は、Console用のworkerのものだけを数える)。
- `console worker check timed out`: 10秒以内に終わらなかった。

確認できない回数は自己更新のstateに数える。
stateを読めなかった回は、数えず、stateも書かない。
30回(1時間)続くと、通知`console_worker_check_failed`を残し、Discordにも知らせる。
確認できれば回数は0に戻る。

マージの後は、次の手順で検知が動いていることを確かめる。
Console用のworkerを止めて戻すコマンドは次のとおりである。

```bash
mise exec -- docker compose -f infra/docker-compose.yml stop windmill_worker_console
mise exec -- docker compose -f infra/docker-compose.yml start windmill_worker_console
```

1. 正常な状態で1時間以上、自己更新のジョブログに上の警告が出ず、通知`console_worker_check_failed`も出ないことを見る。
2. `stop`でConsole用のworkerを止める。
3. 約20分以内に、通知`console_worker_missing`ができ、Discordにも届くことを見る。
   反映と重なった回では、最大10分遅れうる。
4. `start`で戻し、通知を解決する。

Consoleが止まっていてもDiscordには届くので、通知の確認先はConsoleに限らない。

### workerの負荷の記録を確かめる

`sample_worker_load`が2分ごとに、defaultのworkerの負荷を1行ずつ`factory.worker_samples`に記録する。
workerの並列数やポーリングの間隔を見直すとき、枠の占有とメモリのどちらが先に効くかを、この記録で判断する。
記録の行を読むコマンドは次のとおりである。

```bash
mise exec -- docker compose -f infra/docker-compose.yml exec db psql -U postgres -d datatable_db -c "SELECT sampled_at, running_jobs, running_by_script, waiting_jobs, max_wait_seconds, lag_seconds, mem_working_set_bytes, mem_anon_bytes, mem_pressure_total_us FROM factory.worker_samples ORDER BY sampled_at DESC LIMIT 10"
```

反映の後は、次の順で動いていることを確かめる。

1. 反映の数分後に、行が2分おきに増えていることを見る。
2. 最新の行で、`mem_pressure_total_us`以外の列が空でないことを見る。
   確かめた環境のworkerには`memory.pressure`が無かった。
   `memory.pressure`が無ければ`mem_pressure_total_us`は空になり、これは異常ではない。
   あれば値が入る。
3. `wmill job list --script-path f/factory/sample_worker_load`で直近のジョブを選ぶ。
   `wmill job result <id>`の`outcome`が`complete`であることを見る。
   `partial`や`failed`なら、`wmill job logs <id>`の警告から原因を探す。
4. Claudeのジョブが走っているときの行で、`running_jobs`が増え、`running_by_script`にそのscriptが載ることを見る。
5. 同じ時刻に、管理者の`wmill job list`で実行中のジョブを数え、`running_jobs`と合うことを見る。
   記録するジョブ自身と、数えない対象は、実行中の件数から除いて比べる。
   数えない対象は、tag `console`、nativeのworkerのtag、フローの親ジョブである。

#### 枠の占有

- `running_jobs`は、実行中のジョブのうち、defaultのworkerが受けるtagのものの数である。
  記録するジョブ自身は数えない。
- 記録のジョブは、枠が1つ空いたときにしか動かない。
  そのため、`slots`の枠がすべて埋まった状態は、行として残らない。
- 占有は、`running_jobs`と`slots`を並べて読む。
  記録のジョブ自身が1つの枠を使うので、`running_jobs`は最大でも`slots`から1を引いた値までしか出ない。
  この値は、記録のジョブが動けるだけ枠が空いていた瞬間の標本である。
- 塞がりの目安は、`lag_seconds`の大きさと、`sampled_at`の間隔の空白である。
  `running_jobs`の大きさでは判定しない。
  空白だけでは停止と区別できないので、見分け方は[予定の欠け](#予定の欠け)と[日次のまとめでの見方](#日次のまとめでの見方)に従う。
- 内訳は`running_by_script`に、件数の多い10件のscriptのパスと、残りをまとめた`other`で載る。
- 数えるtagは、Windmillの既定でdefaultのworkerグループが受けるものである。
  `infra/docker-compose.yml`の`windmill_worker`は`WORKER_TAGS`を設定しないので、既定が使われる。
- tag `console`のジョブはConsole用のworkerが動かす。
  tag `postgresql`などnativeのworkerが受けるtagのジョブは、nativeのworkerが動かす。
  どちらも数えない。
- `wmill.datatable()`のクエリは、tag `postgresql`のプレビューとして投げられ、nativeのworkerが動かす。
  tag `bun`のジョブは、defaultのworkerが動かす。
  どちらも実機で確かめている。
- 動き出したフローの親ジョブは、枠を使い続けない。
  実際の処理は子のscriptが枠を使うので、実行中には数えない。
  まだ始まっていない親は、枠が空くのを待つので、待ちには数える。
- どのworkerが受けるかを知らないtagのジョブは、数えない。
  ジョブログに、件数とtag名の先頭5件が、記録のたびに1回、警告として残る。

#### queueの待ち

- `waiting_jobs`と`max_wait_seconds`は、予定時刻を過ぎても開始していないジョブを、古いものから100件まで読んで数える。
  予定時刻が未来のジョブは数えない。
  待つジョブが無ければ`max_wait_seconds`は0になる。
- 記録するジョブ自身が始まった後の様子なので、`max_wait_seconds`は自分の遅れ(`lag_seconds`)で打ち切られる。
  待ちの深さの下限として読む。
- `lag_seconds`は、記録するジョブ自身の予定時刻(`scheduled_for`)から開始までの秒数である。
- `sampled_at`は、値を読み始めた時刻である。
  挿入のジョブが遅れても、測った時刻が残る。

#### 枠の数

`slots`は、コードの定数`DEFAULT_WORKER_SLOTS`で、行の値は記録時点のコードの値である。
workerから読んだ値ではない。
`NUM_WORKERS`を変えた直後は、`mise run up`でworkerを作り直すまで、実際の枠の数と食い違う。
`DEFAULT_WORKER_SLOTS`と`infra/docker-compose.yml`の`NUM_WORKERS`が食い違うと、テストが落ちる。

#### メモリ

- `mem_current_bytes`は、ページキャッシュを含む。
  上限に近くても、回収できるキャッシュなら逼迫ではない。
- 逼迫の判断には、プロセスが確保した`mem_anon_bytes`と、非アクティブなファイルキャッシュを除いた`mem_working_set_bytes`を使う。
  主に`mem_anon_bytes`を読む。
- `mem_peak_bytes`は、コンテナの起動からの累積の最大値で、キャッシュも含む。
  判断には使わない。
  前の行より増えたかどうかを見る印にだけ使う。
- 上限への到達は、`mem_events_max`、`mem_oom`、`mem_oom_kill`で見る。
  どれもコンテナの起動からの累積の回数なので、前の行との差を取る。
- 読めなかった値は空のまま残る。
  0は、読めて0だったことを表す。
- `mem_limit_bytes`の空は、上限が無いことと、読めなかったことの両方を表し、区別できない。

#### 予定の欠け

予定の欠けは、行の`sampled_at`の間隔で数える。
間隔が2分より開いていれば、その間の予定が実行されていない。
枠が塞がると、予定時刻から開始までが遅れ、さらに塞がると予定そのものが飛ばされる。
ホストのスリープ、`mise run up`によるworkerの作り直し、Windmillの再起動でも、予定が飛ばされ、再開直後の遅れが大きくなる。
塞がりの割合は、行数ではなく、遅れの合計か、欠けた予定の回数を窓の長さで割った値から求める。
欠けや遅れが塞がりによるのか停止によるのかは、空白の時刻にジョブが動いていたかで見分ける。

#### 日次のまとめでの見方

日次のまとめ(`daily_summary`)の「workerの負荷」欄に、前日(JSTの0時から24時)の`worker_samples`の集計が載る。
負荷の記録は日次のまとめの補足なので、別の通知は出さない。
前日に1行も無ければ「前日の記録なし」と出る。
この場合は、`sample_worker_load`のスケジュールが有効かを確かめる。
集計を読めなかったときは「集計を読めませんでした」と出る。
この場合は、`wmill job list --script-path f/factory/notify_daily_summary`で直近のジョブを探し、ログの警告から原因を確かめる。
負荷の集計だけが失敗した場合の代表的な原因は次のとおりである。

- 列の値の形が変わり、読み取りが例外になった。
- 読み取りの権限が足りない。
- DBが一時的に不調で、クエリが失敗した。

いずれの場合も、ほかの項目の通知は止まらない。
`factory.worker_samples`の表が無いときや、migrationが反映されていないときは、集計より先に掃除の集計が例外になり、日次のまとめ全体が投稿されない。
[保持期間](#保持期間)を短くした場合は、前日の冒頭の行が先に消え、欠けとして現れうる。

| 項目 | 内容 | 読み方 |
| --- | --- | --- |
| 記録 | 前日の行の数と、期待する720行に対する欠けの割合 | 欠けは、枠が塞がって記録のジョブが動けなかった印か、停止の印である。記録を始めた日や、記録の失敗でも欠ける。欠けが1件以上あるのに整数のパーセントでは0%に丸まるときは、小数1桁で出す |
| 遅れ | `lag_seconds`の最大と、30秒以上の行の数とその遅れの合計(秒) | 枠の塞がりか停止のどちらかを表す。合計が大きく、短い空白も多ければ塞がりである。停止や長い塞がりの直後に、1件だけ大きな遅れが出ることもある |
| 空白 | 行の間隔が4分を超えた回数と、最長の間隔(分、切り上げ)と、その開始と終了のJSTの時刻 | 長い空白は、停止(ホストのスリープ、`mise run up`、Windmillの再起動)でも、長いジョブが枠をすべて塞いだ場合でも出る。空白の時刻に`wmill job list`かConsoleの作業項目で動いていたジョブを確かめ、あれば塞がり、無ければ停止と見分ける。短い空白が何度も出て、遅れも多ければ塞がりである |
| 他のジョブの枠の使用 | `running_jobs`の最大(件)と、上限`slots`-1 | 記録のジョブ自身の枠を除く。上限に近い値は、記録のジョブが動けた瞬間に、他のジョブがほぼ枠を使っていたことを表す。平均は、位相の偏りで占有率にならないので出さない |
| メモリ | `mem_anon_bytes`の最大(MiB)と、上限に対する比。`mem_working_set_bytes`の最大。OOMの有無 | 逼迫の判断には`anon`の最大と比を使う。上限が無いか読めない日は、比が出ない。OOMは`mem_oom`と`mem_oom_kill`の増分の合計である。再起動で累積が戻ったときは、現在値を増分に数える |
| 待ちの最長 | `max_wait_seconds`の最大 | 記録のジョブ自身の遅れで打ち切られるので、下限である |

空白が1回以上ある日だけ、この見分け方が「読み方」の行として添えられる。
遅れだけの日には添えない。
ポーリングの山で遅れが毎日出て、添えると読まれなくなるためである。
読めなかった値だけの日は「不明」と出る。
OOMの増分は、値の読めた行が2行以上なければ求められないので、1行だけの日や値がすべて空の日は「OOMの増分は不明」と出る。
「0」は、読めて0だったことを表す。
OOMの増分は、`mem_oom`と`mem_oom_kill`を別々に、値の読めた行だけを並べて隣り合う行の差を足す。
値が空の行をまたいでも、その間の増分は数える。

#### 限界

- 2分より短い塞がりは見えない。
  値は、記録した瞬間の様子である。
- 日への振り分けは`sampled_at`で行う。
  日をまたぐ遅れがあると、1日の行数が721行になりうる。
  欠けは0%に丸めて表示する。
- 空白は、`sampled_at`の間隔で数える。
  隣り合う行の間隔に加えて、日の両端も数える。
  範囲の最初の行は、始端の10分前までの直近の行との間隔で、その行が無ければ始端との間隔で数える。
  最後の行は、終端との間隔で数える。
  正常な日の両端の間隔は、記録の周期と遅れの範囲に収まり、4分を超えない。
- 日をまたぐ1回の停止は、前日の終わり側と当日の始まり側の空白に分かれて出る。
  23時から8時までのホストのスリープなら、前日に1時間、当日に8時間の空白が出る。
- OOMの増分は、再起動で累積が戻ると現在値を数える。
  累積が戻った後、前の値を超えるまでに増えた分は、再起動と判別できず、差だけを数えるので、増分を少なく数えうる。
- OOMで落ちて作り直されたworkerでは、新しいcgroupの`memory.events`が0から始まるので、workerを止めたその1回が記録されない。
  `mem_peak_bytes`が前の行より減った回は、再起動の目安になる。
  ただし、集計では使っていない。
- 5分ごとの`poll_*`が作る山は、2分ごとの記録の位相に入らないことがある。
  記録は30秒に始まり、`poll_*`は0秒に始まる。
  山に当たる回の割合は偏るので、行の平均を占有率として使わない。
- `waiting_jobs`は100件で頭打ちになる。
  `max_wait_seconds`は古い順に読むので、頭打ちでも正しい。
- 実行中のジョブの一覧が100件を超えると、全件を読めない。
  100件に達した一覧は打ち切られているので、そこに自分のジョブが無くても、読めた回として扱う。
- 実行中と待ちの一覧は、スケジュールの実行ユーザーの権限で見える範囲に絞られる可能性がある。
  絞られると、`running_jobs`と`waiting_jobs`は実際より少なくなる。
  この前提は確かめていない。
  反映の後の手順5で、管理者の件数と合うかを見る。
- メモリはコンテナ全体の値で、ジョブごとの内訳は取れない。
  内訳は`running_by_script`の件数から推す。
- `memory.pressure`が無い環境では、`mem_pressure_total_us`は空になる。
- tagの割り当てを変えたときは、数えるtagの一覧(`DEFAULT_WORKER_TAGS`)を直す。
  変えるのは、defaultのworkerに`WORKER_TAGS`を設定したときと、nativeのworkerのtagを変えたときである。
- 単一ステップのフロー(`singlestepflow`)の親ジョブは、枠を使うかを確かめていないので、除かずに数える。
  `running_jobs`が多めに出うる。
- 2分ごとの実行は、1回ごとに、記録のジョブ(tag `bun`)と、挿入のジョブ(tag `postgresql`のプレビュー)ができる。
  Windmillのジョブ履歴とログに、1日に1440件以上を足す。
- 失敗が続く間は、noticeを扱うクエリのジョブも加わる。
- ジョブ履歴の保持期間は、公式文書では自前運用の無償版で最大30日である。
  1日1440件の増加と合わせると、記録だけで約4.3万件が履歴に残りうる。
  実機のインスタンス設定に保持期間の行は無い。
- 記録の表は、DBの掃除が、`sampled_at`から30日(`retention_logs_days`)を過ぎた行を消す。
  掃除が毎日動いていれば、行数は約2.2万行で頭打ちになる。
  詳しくは[保持期間](#保持期間)の節に書く。
- 掃除は、保持期間を過ぎた行をすべて消す。
  記録が保持期間より長く止まると、最後の標本も消え、「止まった」と「一度も記録していない」を表から区別できなくなる。
  この表の窓を読んで判定する処理は、窓に標本が無いときを「判定できない」として扱う。

#### 記録できない状態

記録が取れない状態は、ジョブが成功のまま続く。
`sample_worker_load`は例外を投げないので、スケジュールの失敗の通知(`schedule_failing`)は出ない。
代わりに、完全には記録できない回を数え、5回(10分)続くと通知`worker_sample_failed`を残す。
完全に記録できた回は、次をすべて満たす回である。

- queueの2つの応答が一覧で、空でなければ、形を読める要素が1つ以上ある。
  空の一覧も、完全な回になる。
- 実行中の一覧から、記録するジョブ自身を読めた。
  100件未満の一覧に自分が居ない、またはその`tag`と`job_kind`が読めないときは、応答の形が変わったと見なす。
  この場合は`running_jobs`と`running_by_script`を空にして、完全な回に数えない。
- `memory.current`と`memory.stat`の`anon`が読めた。
- 記録するジョブ自身の予定時刻と開始の遅れが取れた。
- 行の挿入が成功した。

`memory.peak`と`memory.pressure`が読めなくても、完全な回として数える。
回数はWindmillのstateに持つ。
stateを読めなかった回は、数えず、stateも書かない。
stateを読めない状態が続くと、失敗が数えられず、通知も出ない。
ジョブログの`could not read the sampling state`が続いていないかを、反映の後に見る。

stateはscriptのパスごとに持つ。
パスを変えたときや、stateを消したときは、回数が0から読み直される。
直前に未解決の`worker_sample_failed`があっても、回数が上限に届かないので、自動では解決されない。
その場合は、人がConsoleから解決する。

完全な回に戻り、直前の連続失敗の回数が上限(5回)以上だったときは、`worker_sample_failed`を自動で解決する。
解決者は`sample_worker_load`である。
解決に失敗した回は、回数を戻さず、次の回でやり直す。

外への呼び出しは、1回5秒、全体で20秒までに区切る。
ジョブの上限(`timeout`は30秒)より前に終えるためである。
全体の20秒を使い切ると、残りの呼び出しは飛ばす。
実行中の一覧の取得が失敗した回は、自分のジョブの情報を直接は読まない。

警告は、ジョブログに次の文で残る。

- `could not read the running jobs`、`could not read the waiting jobs`: queueを読むAPIが失敗した。
- `could not read the sampling job`: 自分のジョブの情報を直接読むAPIが失敗した。
  `lag_seconds`だけが空になる。
- `the running jobs response has elements of an unexpected shape`: 形を読めず、数えなかった要素がある。
  `malformed`に件数が載る。
- `the waiting jobs response has elements of an unexpected shape`: 待ちの一覧で、同じ状態になった。
- `the running jobs response has an unexpected shape`: 応答が一覧でないか、すべての要素の形を読めない。
- `the waiting jobs response has an unexpected shape`: 待ちの一覧で、同じ状態になった。
- `the sampling job is not readable in the running jobs`: 実行中の一覧から、記録するジョブ自身を読めなかった。
- `jobs with a tag no worker is known to listen to are not counted`: どのworkerが受けるかを知らないtagのジョブがある。
  `jobs`に件数、`tags`にtag名の先頭5件が載る。
  そのジョブは数えないので、`running_jobs`と`waiting_jobs`が少なく出うる。
  defaultのworkerが受けるtagなら、`DEFAULT_WORKER_TAGS`に足す。
- `could not read memory.current`: cgroupのファイルを読めなかった。
  `memory.max`、`memory.stat`、`memory.events`も同じ形の文になる。
- `could not record the worker sample`: DBへの挿入が失敗した。
  この回は行が残らない。
- `could not read the sampling state`: stateを読めなかった。
  この回は失敗を数えず、stateも書かない。
- `could not resolve the sampling failure notice`: noticeの解決に失敗した。
  noticeが残り、回数は戻さず、次の回で解決をやり直す。
- `could not write the sampling state`: stateへの書き込みが失敗した。
  この回の回数が残らず、次の回は前の値から数え直す。
- `could not update the sampling failure count`: 回数の更新の途中で例外が出た。
  主な原因はnoticeの記録の失敗で、この回は通知が残らない。
  回数が上限以上の間は、次の回で記録をやり直す。

### 続けて失敗するスケジュールの検知を確かめる

スケジュールの直近3回の実行が続けて失敗したかどうかは、失敗のハンドラ(`on_error_schedule`)がジョブ履歴を読んで判定する。
飛ばされた回(前回の実行中で見送った回)と、人が取り消した回は、失敗として数えず、連続も切らない。
ジョブの上限(`timeout`)で打ち切られた回は、失敗として数える。
時間切れの取り消しは、ジョブ履歴で`canceled_by`が`timeout`になる想定で判定する。
この値は実機で未確認である。
マージの後は、次の手順で検知が動いていることを確かめる。

1. 失敗する状態を作る。たとえば、あるスケジュールのscriptを一時的に失敗させるか、直近3回が失敗の状態を用意する。
2. 失敗が3回続いた後で、通知`schedule_failing`ができていることを見る。
3. `on_error_schedule`のジョブログに、次のエラーが出ていないことを見る。
   履歴を読めなかったときは`failed to read the schedule history`である。
   通知を記録できなかったときは`failed to record the schedule failing notice`である。
   通知`schedule_failing_check_failed`を記録できなかったときは`failed to record the schedule check failure`である。
4. 3回目の失敗の直後に通知ができていなければ、次の失敗で出るかを見る。直後は今回の失敗をジョブ履歴で読めない場合があり、検知が1回遅れることもある。

ジョブ履歴を読めないとき(APIの失敗と、想定外の形の応答)は、通知`schedule_failing_check_failed`が残る。
その場合は、ジョブ履歴を読む権限を確かめる。

### 自己更新の打ち切りを確かめる

`self_update`のジョブには、全体の上限(3000秒)がある。
値の内訳は[アーキテクチャ](architecture.md)の「自己更新」に書く。
通常は、各コマンドの上限と、区切った呼び出し(1回30秒)の上限で先に終わる。
全体の上限は、それでも止まったときの最後の砦である。

上限で打ち切られた回は、最後に行うConsole用のworkerの確認が走らない。
打ち切られるまでの最大約47分は、2分ごとの次の約23回が飛ばされる。
この間は、自己更新の反映とConsole用のworkerの停止の検知が止まる。

気づく経路は2つある。

- `on_error_schedule`が時間切れでも呼ばれるなら、打ち切りのたびにDiscordの`job_failed`が届く。
  これが主な経路になる想定である。
- 打ち切りが3回続くと、通知`schedule_failing`が残る想定である。
  補助の経路になる。

どちらも、次の2点を実機で確かめていない。
確かめるまでは、頼れる経路とみなさない。
確かめていなければ、自己更新が止まっても気づけない。
なお、ユーザー名が`timeout`の人が取り消した回は、時間切れと見分けられず、失敗に数えられる。

- 時間切れの取り消しが、ジョブ履歴で`canceled_by`が`timeout`になること。
  違う値なら、打ち切られた回が失敗として数えられず、`schedule_failing`が出ない。
- `on_error_schedule`が、打ち切られた回でも呼ばれること。
  呼ばれなければ、`job_failed`と`schedule_failing`のどちらも出ない。

あわせて、`self_update`の実行ユーザーに`f/factory/deployed_sha`が見えることも実機で確かめる。
見えないと存在の確認が`false`になり、全体を反映し直す。
このとき、見えない既存の変数に対して、`setVariable`の作成が既存のパスと衝突しうる。

確かめるには、本番の`self_update`やロックには触れず、使い捨てのscriptとスケジュールを使う。
`wmill sync`の対象は`f/**`だけなので、`u/<user>/`のscriptとスケジュールはWindmillの画面で作る。
自己更新の`wmill sync push`で消えたり上書きされたりしない。

次の点に注意する。

- 作る人は、`f/factory`のスケジュールと同じ権限(admin)にする。
  失敗のハンドラはスケジュールの`permissioned_as`で動くので、`f/factory`の資源と変数を読めないと、黙って失敗する。
- 手順の前に、Discordのチャンネルの人へ知らせる。
  使い捨てのスケジュールの失敗が、`job_failed`として届くためである。
- `on_error_schedule`は、`factory.job_failures`に`flow_path`が`u/<user>/timeout_probe`の行を残す。
  この行は週次監査(月曜9時30分)の証跡に入るので、後片付けで消すか、監査の前に手順を終える。

手順は次のとおりである。

1. `self_update`の上限が反映されていることを確かめる。
   `wmill script get f/factory/self_update`の出力で、`timeout`が3000であることを見る。
   3000秒がインスタンスの上限で切り詰められないのは、セルフホストの上限が環境変数`TIMEOUT`で、未設定なら7日だからである。
   `job_default_timeout`は21600秒以上にする決まりなので、3000秒はその範囲に収まる([実装フローの仕様](internals/implement.md)の「Windmillのtimeoutで打ち切られたとき」)。
2. `u/<user>/timeout_probe`というscriptを作る。
   子プロセスを起動せず、60秒待つだけにする。
   設定の`timeout`は10秒にする。

   ```ts
   export async function main() {
     await new Promise((resolve) => setTimeout(resolve, 60_000));
   }
   ```

3. `u/<user>/timeout_probe`のスケジュールを作る。
   cronは`0 */2 * * * *`(2分ごと)にし、`no_flow_overlap`を有効にする。
   失敗時のハンドラは`f/factory/on_error_schedule`にする。
4. スケジュールの実行を待つ。
   手動の実行では`on_error_schedule`が呼ばれないので、手動では確かめられない。
5. `wmill job list --script-path u/<user>/timeout_probe`で打ち切られた回を見つける。
   `wmill job get <id> --json`で`canceled`、`canceled_by`、`canceled_reason`を読む。
   出力に`canceled_by`が無いときは、Windmillの画面のジョブ詳細で読む。
   `canceled_by`が`timeout`であることを見る。
   違う値なら、`f/factory/lib/schedule_failing.ts`の判定を、読んだ値に合わせて直す。
6. 先に`wmill job list --script-path f/factory/on_error_schedule`を見る。
   `on_error_schedule`のジョブが、打ち切られた回の直後にあることを確かめる。
   ジョブが無ければ、`on_error_schedule`は時間切れでは呼ばれない。
   ジョブがあれば、続けてDiscordに`job_failed`が届いたことを見る。
7. 通知`schedule_failing`まで見るなら、打ち切りが3回続くまで(約6分)待つ。
   Consoleの**要対応**に出ることを見る。
8. 終わったら、スケジュールとscriptを消す。
   出た`schedule_failing`は、Consoleで解決する。
9. `factory.job_failures`に残った使い捨ての記録を消す。
   Data Tableのデータベースに接続し、消す前に行を確かめる。
   データベース名は、`main`のData Tableのresource_pathで、既定は`datatable_db`である。
   `<user>`は、作ったscriptのパスに合わせて置き換える。

   ```bash
   mise exec -- docker compose -f infra/docker-compose.yml exec db psql -U postgres -d datatable_db -c "SELECT id, flow_path, occurred_at FROM factory.job_failures WHERE flow_path = 'u/<user>/timeout_probe'"
   ```

   表示された行の件数が使い捨ての実行の回数と合うことを確かめ、行の`id`を控える。
   確かめた`id`だけを、同じ`flow_path`の条件で消す。
   `<確かめたid>`には、控えた`id`をカンマで区切って並べる。

   ```bash
   mise exec -- docker compose -f infra/docker-compose.yml exec db psql -U postgres -d datatable_db -c "DELETE FROM factory.job_failures WHERE flow_path = 'u/<user>/timeout_probe' AND id IN (<確かめたid>)"
   ```

   `u/<user>/timeout_probe_child`と`u/<user>/timeout_probe_tail`は手動で実行するので、`on_error_schedule`が呼ばれず、通常は行が付かない。
   SELECTで行が出た場合だけ、同じ手順で消す。

打ち切りの扱いの確認は、同じ手順の使い捨てのscriptで続ける。

- 打ち切りが子を止めるか。
  `u/<user>/timeout_probe_child`を作り、`timeout`を10秒にする。
  本体で、`Bun.spawn(["sleep", "600"], { detached: true })`で別のセッションの子を起動し、60秒待つ。
  `wmill script run`で実行し、打ち切られた後に、後述の`ps`で`sleep 600`が残っているかを見る。
  残っていれば、Windmillの打ち切りは子を止めない。
  確かめたら、残った`sleep`を`kill`で止め、scriptを消す。
- 取り残した処理が、ジョブの終わりを遅らせるか。
  `withCallTimeout`は呼び出しを中断しないので、時間切れの後も処理が残りうる。
  `u/<user>/timeout_probe_tail`を作り、60秒のタイマーを残したまま、すぐに戻るようにする。
  実行して`wmill job get <id>`の`duration_ms`を見る。
  60秒近くかかるなら、取り残した処理が終わりを遅らせる。
  実際の`self_update`では、区切った呼び出しが時間切れになった回で、ジョブの終了がログの最後の時刻より大きく遅れないかを見る。

### 打ち切りで残ったプロセスを確かめる

Windmillの打ち切りが子プロセスを止めるかは、上の手順で確かめる。
止めなければ、子の実行中に打ち切られたとき、`wmill sync push`などが上限なしで残る。
残った`wmill sync push`は次の回の作業ツリーを読み続け、`wmill datatable migrate up`は次の回と並行しうる。
リスクは[セキュリティ](security.md)の「自己更新の打ち切り」に書く。

打ち切られた回の後は、workerで残ったプロセスを探す。

```bash
mise exec -- docker compose -f infra/docker-compose.yml exec windmill_worker ps -eo pid,pgid,etime,args
```

出力から`wmill`、`npm`、`git`を探し、経過時間(`etime`)が打ち切りより長いものがあれば残っている。
内容を確かめてから、`kill <pid>`で止める。

### 自己更新が繰り返し打ち切られるとき

自己更新が打ち切られ続けると、反映とConsole用のworkerの停止の検知が止まる。
次の順で復旧する。

1. `wmill job list --script-path f/factory/self_update`で、打ち切りが続いているかを見る。
   原因はジョブのログで確かめる。
2. 上の「打ち切りで残ったプロセスを確かめる」で、残った`wmill`、`npm`、`git`を探して止める。
3. ホスト側のcheckoutで`git pull --ff-only`を実行する。
   続けて`mise run push`と`mise run migrate`を実行し、自己更新が済ませるはずだった反映を手で行う。
   `mise run push`は`--keep-deleted`付きなので、削除は反映しない。
4. 次の回で自己更新が成功することを見る。
   次の「打ち切られた回の記録を確かめる」の見比べで、`deployed_sha`がself cloneのHEADと同じになっていることを確かめる。

### 区切った呼び出しが時間切れになったとき

`self_update`の区切った呼び出しが30秒で終わらないと、例外にする。
呼び出し自体は中断しないので、後から完了することがある。

- 更新のうち、`wmill_token`の取得を含め、それ以降の失敗と時間切れは、更新の失敗として`factory.deployments`に記録する。
  記録されない範囲は[アーキテクチャ](architecture.md)の「自己更新」に書く。
  ジョブの失敗は、Discordの`job_failed`と、3回続いたときの`schedule_failing`で知る。
  ただし`deployed_sha`の更新が時間切れのときは、変数を読み直し、書けていれば成功として続ける。
  成功の記録そのものが時間切れのときは、反映が済んでいるので失敗にしない。
  ログに警告を残し、成功として終わる。
  この回の`deployments`の行は欠けることがある。
  後から成功の行が入ることもある。
  監査は、失敗の時刻以前で最後の成功の行から稼働版を導く。
  そのため、成功の行が欠けると、次の成功の行までの間の失敗が1つ前の版に帰属しうる。
- `deployed_sha`の読み取りが時間切れのときは、未デプロイとは扱わず、更新を失敗にする。
  読み取りがそれ以外で失敗したときは、区切った`existsVariable`で変数の有無を確かめる。
  `false`のときだけ未デプロイとして全体を反映し直す。
  `true`のときと、確認できないときも、更新を失敗にする。
  このとき、エラーは`Variable not found at f/factory/deployed_sha or not visible to you`になるが、変数が存在することもある。
  一時的な失敗か、存在の確認(`existsVariable`)の失敗を疑う。
- noticeの挿入が時間切れになり、後から挿入されたときは、その回のDiscordの通知は出ない。
  次の回からは、同じ本文の未解決のnoticeがあるので、通知しない。
  Consoleの要対応には残る。
- stateの読み取りが失敗か時間切れの回は、stateを書かない。
  確認できなかった回数の積み上げを、0に戻さないためである。
  stateを書けなかった回は、警告だけにして、noticeの判定は数えた回数で続ける。
- Console用workerの確認で、stateを書けなかった回の後は、保存された回数が実際と食い違う。
  回数を0に戻す書き込みが失敗すると、古い回数が残る。
  その後は、1回の確認失敗でも通知`console_worker_check_failed`が出うる。
  回数を増やす書き込みが失敗すると、保存された回数は実際より少なくなり、通知が遅れる。

### 打ち切られた回の記録を確かめる

打ち切られた回は`factory.deployments`に記録が残らない。
成功と失敗のどちらの記録も、更新の最後のほうで書くためである。

`wmill sync push`と`wmill datatable migrate up`が済み、`deployed_sha`を更新した後で、記録の前に打ち切られることがある。
このときは、その版の反映が済んでいるのに`deployments`に行が無い。
次の回は、`deployed_sha`がself cloneのHEADと同じなので、何もせずに終わる。
欠けた記録は補われない。

見分けるには、次の3つを見比べる。

- `deployed_sha`の値。
  Windmillの画面で変数`f/factory/deployed_sha`を開いて読む。
- self cloneのHEAD。
- `deployments`の最新の行の`sha_to`。

self cloneのHEADは、次のコマンドで読む。

```bash
mise exec -- docker compose -f infra/docker-compose.yml exec windmill_worker git -C /workspaces/factory/atelier-works rev-parse HEAD
```

`deployed_sha`とHEADが違えば、反映が済んでいないか、打ち切りが`deployed_sha`の更新より前に当たっている。
通知`deployed_sha_mismatch`が残り、次の回が反映をやり直す。
`deployed_sha`とHEADが同じで、`deployments`の最新の`sha_to`だけが違えば、その版の記録が欠けている。
`wmill job list --script-path f/factory/self_update`で、打ち切られた回の時刻が、その版の反映の時刻と合うかを確かめる。

`sha_to`がHEADと同じで、`result`が`failed`の行だけがあることもある。
`deployed_sha`の更新が時間切れになった後で、実は書けていた場合の組である。
更新は読み直しで成功として続けるので、この組は起きにくい。
起きていれば、`deployed_sha`がHEADと同じかを見て、同じなら反映は済んでいる。

欠けた記録は監査の「デプロイ」に出ないので、必要なら人が補う。

### 通知を解決する

内容を確かめて対応を終えた通知は、Consoleの**要対応**で1件ずつ解決する。
一覧から通知を選び、詳細の「解決済みにする」を押す。確認のダイアログは出ない。
詳細には、起きたことと次の操作が種類ごとに出る。その操作を済ませてから押す。
解決の操作は`notice_resolve`で、解決した人と時刻が通知に記録される。
何を確かめたか分からないまま消せないよう、まとめて解決する操作は無い。
別の人が先に解決していた通知を押しても、成功として扱う。
解決した通知は一覧から消える。

「情報」の通知は、人の行動が要らないので、要対応の一覧に出ない。`?notice=<id>`で開いた詳細にだけ出る。解決しなくてよい。

次の3種類は、設定や権限の問題を示すので、Consoleから解決できない。詳細には、ボタンの代わりに解決できない旨が出る。「情報」として7日で一覧から外れる。

- `unsandboxed_check_commands`
- `labeler_denied`
- `fix_feedback_association_excluded`

解決済みの通知は、Consoleの**システム**の「解決済みの通知」に履歴として残り、既定30日で消える。
並びは、人が解決したものを先にし、DBの掃除で解決したもの(`resolved_by`は`cleanup_db`)を後にする。
どちらも解決の新しい順である。
同じ状況がまた起きれば、新しい通知として記録される。

### 要件定義の作り直しを起動できなかったとき

却下で要件定義を作り直すときに、フローを起動できないか、起動したジョブのIDを記録できないことがある。このとき作業項目は人の対応待ちになり、理由は`requirements regeneration could not be started`になる。Discordにはジョブ失敗が届く。

Consoleの**要対応**の失敗から再実行する。この再実行では却下理由が要件定義のフローに渡らない。却下理由は承認依頼(`approval_requests.reason`)に残っている。

### 実装フローの起動前の処理が失敗したとき

承認済みから実装中へ進める処理がDBの失敗で例外になると、Consoleの**要対応**に`implement_launch_failed`が残る。作業項目はふつう承認済みのまま残り、自動では再開しない。

作業項目の詳細の失敗の記録には`job_failures`の行(stepは`cas`)が出る。作業項目は承認済みのまま残り、**要対応**の失敗には出ないので、Windmillで`f/factory/retry_work_item`を作業項目のIDで実行して再開する。

まれに、例外の前に実装中へ進んでいることがある。この作業項目はフローの無いまま残る。猶予を過ぎると、定期の点検がこれを失敗にする。失敗になった後は、同じ手順で再開できる。

## 更新を反映する

### 自動で反映されるもの

`f/`、`migrations/`、`.claude/skills/`の変更は、自己更新のスケジュール(`self_update`、2分ごと)が自動で反映する。ホスト側の操作は要らない。

自己更新は、`infra/`か`mise.toml`の`[tools]`・`[env]`の変更を検知すると、デプロイの記録(`deployments.needs_host_action`)に残す。
続けて、要対応の通知`host_action_required`とDiscordで知らせる。
これらは、ホスト側で`mise run up`するまで反映されない。
人が気づかないと、古い構成で動き続けるためである。

`mise.toml`の`[tasks.*]`だけの変更、`scripts/`の変更、`mise.local.toml.example`の変更は記録しない。workerの動作に影響しないためである。

`f/factory/lib/workspace.ts`のgitの実行(`buildGitArgv`と`localGitEnv`)を変えたときは、反映の後に、sandboxの実装フローで確かめる。
clone、fetch、push、`git gtr new`が1回ずつ成功することを見る。
テストのoriginはローカルのパスで、`GIT_ALLOW_PROTOCOL`を上書きしているので、httpsでの動作はテストでは確かめられない。

### ホスト側で反映するもの

`infra/`と`mise.toml`の`[tools]`・`[env]`の変更は、次の手順で反映する。ビルドはホスト側のcheckoutから行うので、先にmainを取り込む。

1. ホスト側のcheckoutで`git pull`する。
2. `mise install`で、`mise.toml`の`[tools]`のツールを入れる。
3. `mise run up`で起動し直す。workerのイメージの再ビルドとコンテナの再作成、Caddyの再起動まで行う。

`mise install`は、すでに入っているツールには何もしない。
miseの自動インストールが`mise run`の前に不足分を入れるかは、確かめていない。そのため、通知の手順に`mise install`を含める。

workerの並列数(`NUM_WORKERS`)のような`infra/docker-compose.yml`の変更も、`git pull`だけでは反映されず、`mise run up`で反映される。
マウントの変更では、該当するコンテナが作り直される。Console用のworkerが作り直される間は、Consoleの問い合わせが待たされる。

`mise run up`と`mise run deploy`は、`up -d`の前に、一時コンテナで`caddy validate`を実行し、Caddyfileを確かめる。
不正なら、そこで止まり、何も起動し直さない。
不正なCaddyfileのまま、Caddyの作り直しや再起動をすると、Caddyが落ちて再起動を繰り返し、公開の入口が止まるためである。
続けて、`up -d`の後に、Caddyを再起動する。
再起動の後に、動いているCaddyでも`caddy validate`を実行し、失敗したら止まる。
`restart`はコンテナを起動できれば成功を返し、直後に落ちても気づけないためである。
止まったときは、HEADを書かないので、通知は解決されない。
`infra/Caddyfile`は単一ファイルのbind mountで、`up -d`はcomposeの設定が変わらない限りCaddyを作り直さず、再読み込みもしないためである。
再起動しないと、古いCaddyfileのまま、次に書くHEADが反映済みを表してしまう。
`mise run up`を使わずにcomposeを直接実行したときは、Caddyの再起動もHEADの記録も行われない。

続けて、起動の最後に`scripts/record-host-applied.sh`を呼ぶ。
このスクリプトは、ホストのcheckoutのHEADを、workerの共有ボリュームの`/var/lib/factory/host_applied_sha`に書く。
書くのは作業ツリーではなくHEADなので、`infra/`か`mise.toml`に未コミットの変更を残したまま`mise run up`しても、HEADの版を反映済みとして書く。
そのときは、ホストの構成とHEADの食い違いを残したまま通知が解決されうるので、変更をコミットするか戻してから`mise run up`を実行する。
自己更新は2分ごとにこの値を読む。
通知`host_action_required`の版が、この値と同じか祖先であれば、通知を自動で解決する。
ホストのcheckoutがその版を含んで起動し直されたことを、確かめられるためである。
祖先でなくても、`infra/`と`mise.toml`の内容がこの値の版と同じなら、同じく解決する。
PRのブランチで先に`mise run up`した場合、マージの版はPRのブランチのHEADの祖先にならないが、反映した内容は同じだからである。

自己更新が反映した時点で、ホストがその版か、`infra/`と`mise.toml`の内容が同じ版を反映済みなら、通知とDiscordのどちらも出さない。
運用者が先に`mise run deploy`やPRのブランチでの`mise run up`で反映した場合に、操作の要らない通知を送らないためである。
通知を出すときと解決するときの両方で、その回の変更のパスだけでなく、`infra/`と`mise.toml`のすべてを比べる。
並行する2つのPRを両方とも先に`mise run up`してからマージしたとき、もう一方のPRの`infra/`の違いを見落とさないためである。
比べ方の詳細は[通知の仕様](internals/notifications.md)にある。

値を書けなかったときは警告が出るが、起動は成功のまま終わる。
値のファイルが無いとき、通常のファイルでない(symlinkなど)か128バイトを超えるとき、版として読めないとき、self cloneに無い版のときは、通知を解決しない。
1回の実行で調べる未解決の通知は、版を読めたものの古い順に3件までである。残りは次の回に調べる。
自動で解決されない通知は、`mise run up`が済んでいることを確かめたうえで、人がConsoleの**要対応**で解決してよい。
このスクリプトを持たない版から取り込む最初の1回は、先に`git pull`を済ませてから`mise run up`を実行する。
`mise run deploy`はpullの前のタスク定義で動くので、HEADを書かないためである。

まとめて反映したいときは、`mise run deploy`を手で実行する。必須の手順ではない。`mise run deploy`は次を順に行う。

1. ホスト側のcheckoutで`git pull --ff-only`
2. Dockerの版の検査。Engineが26.0以上、Composeが2.26.0以上でなければ止まる
3. イメージの取得と、`windmill_worker`と`console_fetcher`のイメージのビルド
4. 一時コンテナでの`caddy validate`。不正なら止まる
5. `docker compose up -d`
6. Caddyの再起動と、動いているCaddyでの`caddy validate`
7. `wmill sync push`
8. migrationの実行
9. 反映したHEADの記録

版の検査は`git pull --ff-only`の後に行う。取り込んだ新しい版の検査を使うためである。
この検査を持たない版から取り込む最初の1回は、`mise run deploy`を使わない。miseは起動の時点のタスク定義で動くので、取り込んだ検査が走らないためである。
`git pull --ff-only`を実行してから`mise run up`を実行する。`wmill sync push`とmigrationも要るときは、その後に`mise run deploy`を実行する。

`mise run push`と`mise run deploy`は、`wmill sync push`を`NPM_CONFIG_IGNORE_SCRIPTS=true`で動かす。
`wmill`がnpmを走らせることがあっても、依存のinstall scriptを動かさないためである。
理由は[セキュリティ](security.md)の「サブプロセスのnpmのinstall script」にある。

### f/とworkerのイメージを両方変えたとき

`f/`の変更が、新しいworkerのイメージを前提にすることがある。
例えば、検査コマンドを枠のユーザー(`factory-check-N`)で動かす`f/`は、イメージの`acl`、`procps`、`prlimit`と枠のユーザーを前提にする。
ベースのイメージが誰でも書き込めるようにしている`/usr/src/app`と`/tmp/.cache`を、イメージが閉じていることも前提にする。
マージすると、自己更新が2分以内に`f/`を反映するが、イメージは人が`mise run up`するまで古いままである。

この種の変更は、イメージを先に作り直す。

1. PRのブランチに、先にmainを取り込んでおく。
   `mise run up`はcheckoutの`infra/`でイメージを作るので、PRのブランチがmainより遅れていると、mainで入った`infra/`の変更が戻るためである。
2. 稼働中のworkerの状態を確かめる([稼働中のworkerの状態の確かめ方](#稼働中のworkerの状態の確かめ方))。
   1つ目の走査が何も出さず、2つ目の走査が`/usr/src/app`と`/tmp/.cache`のディレクトリそのものだけを出すことを確かめる。
   この2つは、次の`mise run up`で閉じる。
   ほかに出たものは、先に閉じる。
3. マージの前に、ホストのcheckoutでPRのブランチを取り込み、`mise run up`を実行する。
   新しいイメージは前の版の`f/`でも動く。前の版の`f/`は検査コマンドをrootのまま実行し、枠のユーザーとACLを使わないためである。
4. PRをマージする。
5. マージの後に、次のホスト側の反映に備えて、ホストのcheckoutをmainに戻して`git pull`する。
   マージの版の`infra/`と`mise.toml`が3で反映したPRのブランチと同じなら、自己更新は通知`host_action_required`を出さず、出ていても自動で解決する。
   1の後にmainへ`infra/`か`mise.toml`の変更が入っていると、内容が違うので通知が出る。そのときは、mainで`mise run up`を実行する。
6. 稼働中のworkerの状態を、2と同じ走査で確かめる。
   2つの走査が何も出さないことを確かめ、出たものは閉じる。

`f/`だけが先に反映された間は、検査コマンドのある実装とPR修正が、Claudeを動かす前に止まる。
実装とPR修正の準備のステップは、検査コマンドを設定したリポジトリでは、最初にイメージの前提を確かめるためである。
検査の準備も、所有権と枠の記録へ触れる前に同じことを確かめ直す。
準備から検証までの間に、イメージは変わりうるためである。

止まった作業項目の状態は次のとおりである。
理由はどちらも`worker image is stale: run mise run up`で始まる。

| フロー | 作業項目の状態 | 修正のラウンドの記録 |
| --- | --- | --- |
| 実装 | 人の対応待ち(`needs_human`) | 記録しない |
| PR修正 | `blocked` | 記録しない(`fix_rounds`の行を作らない) |

ラウンドを記録しないので、モデルの失敗にも数えず、`heavy_model`への切り替えを早めない。
要対応の通知`host_action_required`が1件残り、本文にイメージの満たさない前提が載る。
稼働中のworkerの問題も一緒に見つかれば、その問題は別の通知`check_runtime_unsafe`に載る([稼働中のworkerが検査の前提を満たさないとき](#稼働中のworkerが検査の前提を満たさないとき))。
`host_action_required`は`mise run up`の後に自動で解決されるが、ボリュームのマウントポイントは作り直しでは閉じないので、人が閉じるまで残すためである。
PR修正の`blocked`はConsoleの**要対応**の失敗に出ないので、この通知とDiscordの通知で気づく。

対処は、ホストのcheckoutで`git pull`し、`mise install`と`mise run up`を実行する。
通知の本文に反映した版が載っていれば、ホストがその版以降で`mise run up`したときに、自己更新が自動で解決する。
通知が自動で解決されると、止まった実装とPR修正を、自己更新が自動で再開する([実装フローの仕様](internals/implement.md#イメージが古くて止まったとき))。
CIの失敗を直す回は除く([PRワークフロー](internals/pr-workflow.md#CIの失敗を直す回))。
人の再実行は要らない。
同じ作業項目の自動の再開は3回までで、上限に達したときは、止まった作業項目をWindmillの`f/factory/retry_work_item`で再実行する。
版が載らない通知は自動では解決されず、自動の再開も起きないので、`mise run up`の後に人が解決し、止まった作業項目を`retry_work_item`で再実行する。

`/usr/src/app`か`/tmp/.cache`の下に誰でも書けるものがあれば、ベースのイメージが置いたものでも`check_runtime_unsafe`に載る。
この通知は`mise run up`の後も自動では解決されない。
[稼働中のworkerの状態の確かめ方](#稼働中のworkerの状態の確かめ方)の2つ目の走査で何も出ないことを確かめてから、通知を人が解決する。

#### 稼働中のworkerの状態の確かめ方

ホストのcheckoutで、次の2つの走査をする。

1つ目の走査は、ボリュームの中から、誰でも書けるもの(symlinkを除く)を探す。
検査の準備の走査は、ボリュームのマウントポイントそのものしか見ないためである。
検査を枠のユーザーで動かす前の版では、rootが検査コマンドを実行するので、誰でも書けるworktreeやファイルが`/workspaces`に残りうる。
残ったままだと、検査用のユーザーがそこへ書き込める。

```bash
mise exec -- docker compose -f infra/docker-compose.yml exec windmill_worker /usr/bin/find /workspaces /var/lib/factory -xdev '!' -type l -perm -0002 -print
```

2つ目の走査は、検査の準備と同じ走査である([セキュリティ](security.md#誰でも書き込めるものの探し方))。
引数は`f/factory/lib/check_sandbox.ts`の`worldWritablePathsArgv`と同じである。
食い違わないことは`tests/lib/check_sandbox.test.ts`が確かめる。

```bash
mise exec -- docker compose -f infra/docker-compose.yml exec windmill_worker \
  /usr/bin/find -P / /dev/shm -xdev -path /tmp/windmill -prune -o '!' -type l -perm -0002 \
  '!' '(' -path /tmp -o -path /var/tmp -o -path /run/lock -o -path /dev/shm ')' \
  '(' -path /usr/src/app -o -path '/usr/src/app/*' -o -path /tmp/.cache -o -path '/tmp/.cache/*' \
  -o '!' '(' -path '/tmp/*' -o -path '/var/tmp/*' -o -path '/run/lock/*' -o -path '/dev/shm/*' ')' \
  -o '(' -uid 0 -type d '!' -perm -1000 ')' ')' -print
```

出たものは、次のコマンドで、中のものも含めて閉じる。
`<パス>`には、走査が出したパスを1つずつ指定する。
ボリュームのマウントポイント(`/workspaces`と`/var/lib/factory`)そのものが出たときは、`-R`を付けずに`chmod o-w`で閉じる。
`-R`を付けると、ボリュームの中のすべてに及ぶためである。
閉じたら、同じ走査をもう一度実行し、何も出ないことを確かめる。

```bash
mise exec -- docker compose -f infra/docker-compose.yml exec windmill_worker chmod -R o-w <パス>
```

### 稼働中のworkerが検査の前提を満たさないとき

検査の準備は、イメージの前提のほかに、稼働中のworkerに誰でも書き込めるパスが無いことを確かめる。
イメージのビルドが同じことを確かめるので、見つかったパスは稼働中にできたものである。
共有の一時ディレクトリの下で数えるのは、rootが所有し、stickyでない、誰でも書き込めるディレクトリだけである。
ただし、`/tmp/.cache`とその下では、ファイルも数える。
探し方は[セキュリティ](security.md#誰でも書き込めるものの探し方)にある。
走査がタイムアウトしたときと、走査が失敗したときも、同じ扱いにする。

止まった作業項目の状態とラウンドの記録は、[f/とworkerのイメージを両方変えたとき](#fとworkerのイメージを両方変えたとき)の表と同じである。
理由は`worker runtime is unsafe for checks:`で始まる。
要対応の通知`check_runtime_unsafe`が1件残り、本文にパスか、確かめられなかった理由が載る。
イメージの問題ではないので、`mise run up`は要らない。

対処は、ホストのcheckoutで次のどちらかを行う。

- 本文のパスを閉じる。

  ```bash
  mise exec -- docker compose -f infra/docker-compose.yml exec windmill_worker chmod o-w <パス>
  ```

- workerのコンテナを作り直す。
  ボリュームの外はイメージの状態に戻るので、稼働中にできたパスも消える。
  ボリュームのマウントポイント(`/workspaces`と`/var/lib/factory`)は直らないので、上のコマンドで閉じる。
  マウントポイントの権限は、コンテナではなくボリュームが持つためである。
  作り直すと、そのとき動いているジョブも止まる。

  ```bash
  mise exec -- docker compose -f infra/docker-compose.yml up -d --force-recreate windmill_worker
  ```

続けて、止まった作業項目をWindmillの`f/factory/retry_work_item`で再実行し、通知を人が解決する。
走査のタイムアウトで止まったときは、workerの負荷を確かめてから再実行する。
同じパスが繰り返しできるときは、そのパスを作るジョブを確かめる。

### mise run upで反映されないもの

| 変更 | 反映のしかた |
| --- | --- |
| `infra/Caddyfile`(composeを直接実行したとき) | bind mountしたファイルなので、`up -d`はコンテナを作り直さない。`mise run up`と`mise run deploy`は起動の後にCaddyを再起動するが、composeを直接実行したときは、`mise exec -- docker compose -f infra/docker-compose.yml restart caddy`で再起動する |
| `mise.toml`の`[tools]`のうちホスト側のCLI | `mise install`か`mise run setup`で反映する |

`mise run up`が反映するのは、`[env]`に書いたworkerのイメージのツールのバージョンである。

### workerのツールのバージョン

workerのイメージに入れるツールのバージョンは、`mise.toml`の`[env]`で固定し、`infra/worker/Dockerfile`のbuild argとして渡す。

| ツール | 変数 |
| --- | --- |
| `claude` | `CLAUDE_VERSION` |
| `gh` | `GH_VERSION` |
| `gitleaks` | `GITLEAKS_VERSION` |
| `gtr` | `GTR_REF` |
| `wmill` | `WMILL_VERSION` |

`WM_VERSION`を上げるときは、新しいベースのイメージのPATHを`docker image inspect`で調べる。
それを`infra/worker/Dockerfile`の`ENV PATH`と突き合わせる。
ベースのPATHに必要なディレクトリが増えていれば、`ENV PATH`に足す。

ツールの追加やバージョンの変更には、workerのイメージの再ビルドが要る。`gitleaks`は、実装フローが毎ラウンドの固定の検査として`--redact`付きで実行するために入れている。版はホスト側のpre-commitのフックと同じである。

### 同期されない変数とリソース

`wmill sync push`に`--include-secrets`を付けてはいけない。付けると、値を空のままコミットしている`f/factory/*.variable.yaml`で、4つの秘密の変数が空に上書きされる。対象は`claude_oauth_token`、`github_token`、`wmill_token`、`discord_webhook_url`である。`mise run push`は`--include-secrets`を付けない設定になっている。

秘密の変数とインスタンス固有の`factory_config`のリソースは、同期の対象外である。説明文(description)を変えても、`mise run push`では既存のインスタンスに反映されない。既存のインスタンスでは、WindmillのVariablesとResourcesの編集画面で説明文だけを直す。新しいインスタンスは、bootstrapがリポジトリの説明文で作る。

`f/factory/deployed_sha`変数も同期の対象外である。自己更新が書き込む実行時の状態だからである。`bootstrap`は初回だけ空の値で作り、既にあれば値を変えない。値を戻したいときは、Windmillの画面で直接編集する。

### リポジトリから消したものをWindmillから消す

リポジトリから消したscriptやappは、`mise run push`ではWindmillに残る。
`mise run push`と自己更新は`--keep-deleted`を付けるので、削除を反映しない。
消すのは、人が`mise run push:prune`で行う。
先に`mise run push:dry`で、消える対象を確かめる。
消したものは、Windmillのゴミ箱に3日残る。

廃止した旧Consoleのapp(`f/factory/factory_console`)が残っているときも、この手順で消す。
マージ後に`mise run push:dry`を実行し、`f/factory/factory_console`が消える対象に出ることを確かめる。
確かめたら、人が`mise run push:prune`を実行する。
消えても、過去のリンクは新しいConsoleに着く。

### Console(console/)を反映する・戻す

`console/`の変更は、`main`にマージされて`console-dist.yml`が成功すれば、数分で`console_fetcher`が取り込んで反映する。
`self_update`は関与しない。
`console-dist.yml`は、draw.ioのビューアを外部から取得する。
取得に失敗したときの対応は、[Consoleの配信の仕様](internals/console.md)の「ビューアの取得」にある。
`infra/console_fetcher/`の変更は、ほかの`infra/`と同じく次の`mise run up`で反映される。
取得元や検証を変える変更は、マージ後に`mise run up`でfetcherのイメージを作り直すまで反映されない。
それまでは、古いイメージが新しい取得元の成果物を見つけられず、`artifact_missing`になる。
配信中の版は変わらない。急ぎではないが、マージしたらすぐ`mise run up`を実行する。
`infra/Caddyfile`は、`mise run up`と`mise run deploy`が起動の後にCaddyを再起動して反映する。
composeを直接実行したときは、次のコマンドでCaddyを再起動する。
Caddyを再起動するまで、`/console/drawio.html`には`frame-ancestors 'none'`のヘッダーが付き、図のページを埋め込めない。

```bash
mise exec -- docker compose -f infra/docker-compose.yml restart caddy
```

`console_fetcher`は5分ごとに、`main`へのpushで成功した`console-dist.yml`の最新の実行を探す。
同じcommitの`ci.yml`も成功していることを確かめ、実行中か失敗していれば、その前の候補を選ぶ。
その成果物`console-dist`を検証して`factory_console`の`releases/<sha>/`に置き、`current`を付け替える。
状態は`status.json`に書き、ログにも出す。
`status.json`には、`state`(`ok`、`failed`、`pinned`)、`sha`、`checked_at`、`error`が入る。

```bash
mise exec -- docker compose -f infra/docker-compose.yml logs --tail 50 console_fetcher
```

版は、配信するファイルの中身(`manifest.json`の`files`)が違うものを3つまで残す。
版は`main`へのpushのたびに作られ、`console/`に触れないpushでできた版は中身が同じなので、1つと数える。
無関係なマージが続いても、戻せる版を押し出さないためである。
数える対象は、直近20回のpushの範囲である(`history.json`が覚えている回数)。
共有の`assets/`は、残した版から参照されず14日を超えたファイルを消す。

新しい版に問題があれば、直前の版に戻す。

1. `mise run console:rollback`を実行する。取り込みの最中なら`console_fetcher is updating the console right now.`と出て止まるので、少し待ってやり直す。
2. 戻すと`pin`が置かれ、自動の付け替えが止まる。もう一度実行すると、さらに1つ前に戻る。
3. `main`に修正を入れてCIが成功したら、`mise run console:unpin`で`pin`を外す。5分以内に最新の版へ戻る。

戻し先は、中身が今の版と違い、マニフェストと`assets/`のファイルが揃っている最も新しい版である。
中身が同じ版へ戻しても、何も変わらないためである。
揃っていない版は、配信するとページが壊れるので選ばない。
そのような版が残っていないと、`No previous release with different content to roll back to.`と出て止まる。
この場合と、残っている版より前に戻したい場合は、`main`で該当のcommitをrevertし、CIを動かす。

戻すと、戻した元の版と、それと中身が同じ版を消す。
その版だけが参照する共有の`assets/`のファイルも、更新日時にかかわらず消す。
`pin`の間も、問題の版のscriptを`/console/assets/`から読めるままにしないためである。
消す版のshaは`pin`の`rolled_back_from`に、戻した元の版の中身(`files`のsha256)は`rolled_back_content`に記録する。
消し終わらなかったときは、`console:rollback`が`The rollback succeeded, but removing ...`で始まる文を出す。
続きは`console_fetcher`が次の取り込みで消す。
戻した元の版のshaと中身は、`pin`とは別に、ボリュームの`revoked.json`にも記録する。
この記録は`pin`を外しても残り、記録にある版は、`console:rollback`の戻し先に選ばれない。
取り込みの整理は、保持の数え方にかかわらず、記録にある版を先に消す(配信中の版は消さない)。
消えた版のshaも記録に残り、その版は取り込みの候補から外れる。
戻した元のcommitは、`pin`を外した後も再び配信されない。
shaと中身の記録は、それぞれ100件まで残し、超えると古いものから捨てる。
`rolled_back_from`を持たない`pin`では、戻した元の版は消えない。
消した版のページを開いたままのブラウザは、assetsを読み込めなくなる。
開いたままのタブは、配信中の版の`/console/manifest.json`と`/console/status.json`を読んで、自分の版を確かめる。
確かめるのは、表示した直後と、その後60秒ごと、タブが見える状態に戻ったとき、画面の部品の読み込みに失敗したときである。
タブが見えないあいだは周期の確認をしない。
見える状態に戻ったときは、前の確認から5秒以上空いていれば確認する。
1回の確認は10秒で打ち切る。
確認が失敗し続けるあいだは、間隔を10分まで倍々に延ばし、成功したら60秒に戻す。
画面が読み込んだファイルのどれかが配信中の版に無ければ、再読み込みを促す帯を画面の上端に出す。
配信中の版に無いファイルを読み込んでいて、版を戻して`pin`で固定している間や、そのファイルがもう取れないときは、目立つ色の帯で再読み込みを求める。
一度目立つ色の帯を出したタブは、帯を下げない。
確かめに失敗したときは、表示を変えない。
Caddyfileを更新してCaddyを再起動するまでは、`/console/status.json`が`index.html`に落ちて状態を読めない。
その間は、`pin`による目立つ色の帯は出ない。
無かったファイルが404のときの目立つ色の帯と、控えめな帯は出る。

`revoked.json`の扱いは次のとおり。

- 中身が壊れているか形が違うときは、`revoked_state_unreadable`をログに出す。
  壊れたファイルは`revoked.json.corrupt-<epochミリ秒>`(同じ時刻なら`-<番号>`付き)へ移し、新しい方から5個まで残す。
  空の記録で続けるので、戻す操作と整理は止まらない。
- 権限やディレクトリになっているなど、読む操作が失敗したときは、`revoked_state_read_failed`をログに出す。
  中身の破損ではないので、ファイルは移さない。
  空の記録で続けるので、戻す操作と整理は止まらない。
  その回は、記録による除外と削除が効かない。
  `console:unpin`は、記録し直す段階で同じ読む失敗に当たり、`--force`を付けても失敗して`pin`を残す。
  先に権限などの原因を直す。
- `console:rollback`が記録を書けなかったときも、戻す操作は成功する。
  `revoked_record_failed`をログに出す。
  同じ内容を`pin`が持ち、`console:unpin`が記録し直すためである。
- `console:unpin`が記録を書けなかったときは、失敗を出して`pin`を外さない。
  原因を直してやり直す。
- 戻した元の版と同じ中身が、別のcommitの最新の成功した実行として配信し直されると、その中身は記録から外れる。
  `console:unpin --force`で外して`console_fetcher`が取り込んだ場合も同じである。
  外れたときは`revoked_digest_cleared`をログに出す。
  ワークフローを通った中身を意図して配信し直したものとして扱うためで、記録を手で編集する必要は無い。
- 外す処理が失敗したときは、`revoked_digest_clear_failed`をログに出す。
  記録は残るので、その中身の版は戻し先に選ばれず、配信中の版でなくなると整理が消す。
  原因を直すと、次にその中身が配信されるときに外れる。

戻した元の版のマニフェストを読めないと、その版の中身を`pin`に記録できない。
このとき`console:rollback`は、`The files of the release rolled back from could not be recorded`で始まる文を出す。
この`pin`は、`console:unpin`がshaだけを照らすので、外す前に最新の`console-dist.yml`の結果を確かめる。

`pin`を外すと、`console_fetcher`は最新の成功した実行を取り込む。
その実行が戻した元の版と同じ中身だと、問題の版が再び配信される。
`console/`に触れないマージでも、同じ中身の版が新しいcommitで作られるので、commitのshaだけでは見分けられない。
`console:unpin`は、最新の成功した実行のshaと、その実行の`files`のsha256を、`pin`の記録と`revoked.json`の記録を合わせたものと照らす。
`console:rollback`を重ねて`pin`が書き直されても、前に戻した版を落とさないためである。
`revoked.json`の記録は、その中身が配信し直されるまで残る。
shaと中身(sha256)の記録は、整理で外れない。
以前に戻した中身を、別のcommitで意図して配信し直すときの出口は、`--force`である。
戻した元のcommit自体は、`--force`で外しても再び配信されない。同じ中身の修正は、新しいcommitで`main`に入れる。
次の場合は`pin`を外さず、理由を出して止まる。

| 状況 | 人がすること |
| --- | --- |
| `pin`を読めない(JSONでない、`rolled_back_from`や`rolled_back_content`の要素がshaやsha256の形でない) | 最新の`console-dist.yml`の結果を確かめ、`--force`で外す |
| 最新の成功した実行のshaが、戻した元の版のshaである | 修正を`main`に入れ、その`console-dist.yml`が成功してからやり直す |
| 最新の成功した実行の`files`が、戻した元の版と同じである | `console/`を変える修正を`main`に入れ、その`console-dist.yml`が成功してからやり直す |
| 最新の実行を調べられない(トークンや`CONSOLE_GITHUB_REPO`の不備、ネットワークの失敗) | 原因を直してやり直す |
| 最新の実行の`files`を調べられない(成果物の取得か検証に失敗) | 原因を直してやり直す |
| 戻した元の版を消せていない | このコマンドの出力か`console_fetcher`のログの`revoked_cleanup_skipped`、`revoked_cleanup_failed`を確かめ、原因を直してやり直す |

`pin`と`revoked.json`のどちらにも中身の記録が無いときは、shaだけを照らす。
戻した元の版の記録がどちらにも無いときは、照らす版が無いので、問い合わせずに外す。
`pin`の`sha`と配信中の版が違うときは、取り込みが`pin_mismatch`をログに出す。
これは検出だけで、状態は変えない。
違いが続く間は、取り込みのたびに出る。
`pin`を読めないときは、`pin_read_failed`をログに出し、状態は`pinned`のままにする。

確認を飛ばすオプションは2つある。
`mise run console:unpin -- --force`は、`pin`と最新の実行についての確認(上の表の前の5行)を飛ばす。
問題の中身が別のcommitで再び配信されるのを承知の上で使う。
`mise run console:unpin -- --ignore-cleanup`は、戻した元の版を消せていない確認を飛ばす。
`--force`だけでは、この確認は飛ばない。
`--ignore-cleanup`で外しても、消せていない版は`revoked.json`に記録が残る。
`console_fetcher`は、次の取り込みの整理でその版を消し、`console:rollback`もその版を戻し先にしない。
手で消す必要は無い。
消せない原因は、上の表の最後の行と同じ見方で確かめる。
ログに`revoked_cleanup_skipped`が続くときは、原因を直す。

主な`error`と対処は次のとおり。

| `error` | 意味 | 人がすること |
| --- | --- | --- |
| `config_missing` | `CONSOLE_GITHUB_TOKEN`が無いか、`mise.toml`の`CONSOLE_GITHUB_REPO`の形が違う | 直して`mise run up`する |
| `auth_failed` | トークンが失効した | 再発行して投入し、`mise run up`する |
| `forbidden`、`not_found` | トークンの対象リポジトリか権限(Actions: Read)が違う | トークンと`mise.toml`の`CONSOLE_GITHUB_REPO`を確かめる |
| `rate_limited` | GitHub APIの呼び出し回数の上限に達した | 何もしなくてよい。5分ごとの次の確認で再試行し、その間も今の版を配信し続ける |
| `no_successful_run`、`artifact_missing`、`artifact_expired` | 取り込める成果物が無い | `console-dist.yml`の実行の結果を確かめ、必要なら`main`にpushして動かす |
| `digest_mismatch`、`manifest_mismatch`、`zip_unsafe_entry`、`unexpected_redirect` | 検証に失敗した | 今の版を配信し続けるので急ぎではないが、原因を調べる |
| `asset_conflict` | 新しい版の`assets/`のファイルが、既にある同じ名前のファイルと中身が違う(`console/public/assets/`の名前の付け替え忘れなど) | 置き換えると配信中の版が壊れるので取り込まない。名前を直したcommitを`main`に入れる |

取り込みの失敗は、10分ごとの見張り(`console_fetch_watch`)が通知とDiscordに知らせる。知らせる原因は、取り込みの失敗、結果が30分以上更新されていないこと、状態を読めないことである。
同じ原因の未解決の通知がある間は、通知を重ねず、Discordにも送らない。
運用者が通知を解決した後に原因が続いていれば、次の確認で通知が1件でき、Discordにも届く。
`rate_limited`と`github_unavailable`は自然に直ることが多いので、どちらかが60分以上続いたときだけ知らせる。
2つの間で入れ替わっても、60分の数え始めは戻さない。
取り込みの側が新しくなって未知の分類が来たときは、通知の本文と原因を`unknown_code`にそろえる。

通知の種類は、失敗が`console_fetch_failed`、停止と読めないことが`console_fetch_stale`である。
どちらも「要対応」で、正常に戻っても自動では解決しない。
原因を確かめて取り除いたら、Consoleで通知を解決する。
固定(`pin`)した状態は、更新が新しければ異常としない。

Discordの通知とConsoleの通知には、上の表の次の操作が載る。詳しい原因は、取り込みのコンテナのログで確かめる。

### タグのrulesetを確かめる

`main`という名前のタグの実行は、`main`のブランチの実行と見分けがつかない。
そのため、rulesetの`protect-tags`で、すべてのタグの作成、更新、削除を禁止している。
迂回できるのは、リポジトリの管理者のロールだけである。

設定は、次のコマンドで確かめる。

```bash
gh api repos/<owner>/<repo>/rulesets
```

一覧に、名前が`protect-tags`で対象が`tag`のrulesetがあり、有効(`enforcement`が`active`)なことを確かめる。
詳しい中身は、一覧の`id`を使って`gh api repos/<owner>/<repo>/rulesets/<id>`で読む。
中身では、作成、更新、削除の規則があり、迂回できる者が管理者のロールだけなことを確かめる。
無いときは、rulesetを作り直すまで`console_fetcher`の取り込みを信頼しない。

### Console用workerを確かめる

Console用のworker(`windmill_worker_console`)は、`mise run up`で作られる。
ワーカーグループ`console`に属し、tag`console`のジョブだけを受ける。
どのscriptをこのworkerで動かすかは、scriptの`tag`で決める。
このworkerには、`factory_state`のボリューム全体をマウントしない。
ボリューム全体とは、`factory_state`の最上位を指す。`claude`、`gh`、`audits`、`requirements`などが並ぶ層である。
まず`mise run doctor`を実行する。
Dockerの版と、起動中のworkerのマウントを判定する。
`sh -c`を渡す`exec`(下のマウントの判定のコマンド)は、フックが拒否する。
そのため、Claudeのセッションでは人が実行するか、`mise run doctor`を使う。
動いていることは、コンテナの状態とログで確かめる。

```bash
mise exec -- docker compose -f infra/docker-compose.yml ps windmill_worker_console
mise exec -- docker compose -f infra/docker-compose.yml logs --tail 20 windmill_worker_console
```

DBにワーカーグループの設定があると、composeの環境変数`WORKER_TAGS`ではなくそちらの値が使われる。
そのため、Windmillの画面の「Workers」で、グループ`console`のworkerのtagが`console`だけであることを確かめる。
詳しくは[セキュリティ](security.md)の「Console用workerの境界」にある。

メモリとプロセス数は、最初のジョブを動かしている間に確かめる。
`docker stats`は`windmill_worker_console`の行を見て、`MEM USAGE / LIMIT`の使用量が上限の1GiBに収まっていることを確かめる。プロセス数の上限は256なので、`pids.current`にも余裕があることを確かめる。

```bash
mise exec -- docker stats --no-stream
mise exec -- docker compose -f infra/docker-compose.yml exec windmill_worker_console cat /sys/fs/cgroup/pids.current
```

このworkerがボリュームに書くのは、ログと専用の依存キャッシュ(`worker_console_dependency_cache`)だけである。
再起動しても、キャッシュのボリュームは残る。
ボリュームを消したときは、次のジョブで依存をレジストリから取り直すので、外向きの通信が要る。

このworkerは、要件定義書のディレクトリ(`factory_state`のサブパス`requirements`)を読み取り専用でマウントする。
サブパスのディレクトリが無いと起動しないので、1回限りのサービス`factory_state_init`が先に作る。
このサービスは、`requirements`がsymlinkなら失敗で終わり、そうでなければ`mkdir -p -m 0755`を実行して正常に終了する。
停止したコンテナが残る。
`mise run up`のたびに実行し直すが、ディレクトリがあれば何も変えない。
既存の環境でも、`mise run up`を1回実行すれば、このworkerが作り直されて新しいマウントになる。
`windmill_worker_console`が起動しないときは、このサービスのログを確かめる。
`requirements is a symlink`と出たときは、`requirements`を通常のディレクトリに直してから、`mise run up`を実行し直す。

```bash
mise exec -- docker compose -f infra/docker-compose.yml ps -a factory_state_init
mise exec -- docker compose -f infra/docker-compose.yml logs factory_state_init
```

symlinkを消す手順は次のとおりである。
defaultのworkerで動いたコードがsymlinkを置いた可能性がある。`ls -la`に出るリンク先を控え、置いた経緯を調べてから消す。

1. `factory_state_init`の一時コンテナで`ls -la`を実行し、`requirements`が`->`でリンク先を示すsymlinkであることを確かめる。ボリューム名は、Composeが解決するので指定しない。
2. 同じ形の一時コンテナで`rm`を実行する。
3. `mise run up`を実行する。`factory_state_init`が成功し、`requirements`が通常のディレクトリとして作られる。
4. Console用のworkerを作り直す。

```bash
mise exec -- docker compose -f infra/docker-compose.yml run --rm --no-deps --pull never --entrypoint ls factory_state_init -la /var/lib/factory
mise exec -- docker compose -f infra/docker-compose.yml run --rm --no-deps --pull never --entrypoint rm factory_state_init /var/lib/factory/requirements
mise run up
mise exec -- docker compose -f infra/docker-compose.yml up -d --force-recreate windmill_worker_console
```

> [!WARNING]
> `rm`の対象は、`ls -la`で確かめたsymlinkだけにする。パスの末尾に`/`を付けない。付けるとリンク先のディレクトリを指す。
> `-r`と`-f`は付けない。`requirements`が通常のディレクトリなら、`rm`は何も消さずに失敗する。

作り直す段が要る理由は、Composeが、設定の変わらない、動いているworkerを作り直さないことである。
作り直さないと、symlinkの先をマウントしたworkerが残る。

> [!NOTE]
> `factory_state_init`は`read_only`で、権限もすべて落としている。
> この条件でも`rm`は通る見込みである。`factory_state_init`が新しいボリュームで`mkdir`できたのと同じ条件(所有者がrootでモードが0755の`_data`)だからである。実機では確かめていない。
> `--pull never`は、外向きの通信が無いときでも使え、余計なpullをしないために付ける。
> `rm`が権限のエラーで失敗したときは、出力を控えて、運用者が対処を決める。

マウントが想定どおりかは、起動中のworkerの中から、`factory_state`のボリューム全体がマウントされている証拠が見えるかで判定する。
正しい設定では、`/var/lib/factory`はコンテナのrootfsにあり、その下にはマウント先の`requirements`しか無い。
証拠は次の2つである。

- `/var/lib/factory`の直下の`claude`、`gh`、`audits`。ボリューム全体を`/var/lib/factory`にマウントする設定で作られたworkerが残っていると見える。直下の名前なので、owner名とはぶつからない。
- `/var/lib/factory/requirements/requirements`。`volume.subpath`が無視されて、ボリューム全体が`/var/lib/factory/requirements`にマウントされると見える。ボリューム全体には`factory_state_init`が必ず`requirements`を作るためである。ただし、対象リポジトリのowner名が`requirements`だと、サブパスだけが正しく付いていても見える。

`docker inspect`のSourceは、サブパスを反映しないので、判定に使わない。

判定は1回の`exec`で行い、`sh -c`の終了コードで結果を返す。
composeの失敗(1、126、127など)とぶつからないよう、専用の値を使う。

- 11なら、ボリューム全体がマウントされている証拠は見えない。
- 10なら、ボリューム全体がマウントされている証拠が見える。
- 3なら、マウント先が見えない。マウントが設定どおりに付いていないので、`mise run up`を実行してから、Console用のworkerを作り直す。
- ほかの終了コードか、コンテナが動いていないときは、確かめられない。

```bash
mise exec -- docker compose -f infra/docker-compose.yml exec -T windmill_worker_console sh -c 'test -e /var/lib/factory/claude || test -e /var/lib/factory/gh || test -e /var/lib/factory/audits && exit 10; test -d /var/lib/factory/requirements || exit 3; test -e /var/lib/factory/requirements/requirements && exit 10; exit 11'; echo "exit=$?"
```

`mise run doctor`は同じ判定をし、画面には終了コードではなく`console worker mount`の行を出す。

- 11は、OKと「`factory_state`のボリューム全体はマウントされていません」を出す。
- 10は、NGを出す。メッセージは「/var/lib/factory/requirements/requirements」か「/var/lib/factoryの直下のclaude、gh、audits」で始まる。
- 3は、NGと終了コードを出す。
- workerが起動していないときは、確かめられない旨をOKで出す。このとき、マウントは判定されていない。

NGの行が10を表すときは、次の2つの`ls`でどちらの証拠が見えたかを確かめる。

```bash
mise exec -- docker compose -f infra/docker-compose.yml exec -T windmill_worker_console ls -la /var/lib/factory
mise exec -- docker compose -f infra/docker-compose.yml exec -T windmill_worker_console ls -la /var/lib/factory/requirements
```

- 1つめの`ls`に`claude`、`gh`、`audits`のどれかが並べば、ボリューム全体が`/var/lib/factory`にマウントされている。Dockerの版を下限以上にし、Console用のworkerを作り直す。
- 2つめの`ls`に`requirements`が並ぶのは、次のどちらかのときである。
  ボリューム全体が`/var/lib/factory/requirements`にマウントされているか、owner名が`requirements`でサブパスだけがマウントされている。
  この判定では見分けられないので、`requirements/requirements`だけが見えても、正常とは断定しない。
  見分けられない分は、Dockerの版の下限と、workerの作り直しで補う。
- `audits`は、監査を1回実行するまで作られない。
  `gh`は、作られないことがある。
  4つの名前が揃わなくても、ボリューム全体がマウントされていることがある。
  名前が揃うことを、ボリューム全体がマウントされている条件にしない。

この判定が見分けるのは、ボリューム全体がマウントされたかどうかだけである。
symlinkの先がマウントされた場合は見分けられないので、その疑いは、上の`ls -la`で確かめる。

Dockerの版は`mise run doctor`で確かめる。
`doctor`はworkerが作り直されたかを確かめないので、作り直しは別に行う。
次のコマンドで作り直す。

```bash
mise exec -- docker compose -f infra/docker-compose.yml up -d --force-recreate windmill_worker_console
```

`mise run up`は、設定の変わらないworkerを作り直さない。
ボリューム全体がマウントされる原因として考えられるのは、次の2つである。

- ボリューム全体をマウントする設定で作られたworkerが残っている。
- DockerのEngineかComposeが下限に届いていない。

### adminsワークスペースの組み込み項目

Windmillは起動時に、`admins`ワークスペースへ組み込みのscriptとscheduleを作る。「Synchronize Hub Resource types with instance」などである。これらはWindmill本体の一部で、このリポジトリの管理対象ではない。`mise run push`と自己更新の同期にも含まれない。summaryが英語のままなのはそのためで、日本語化と削除はしない。

Factoryの資産は、すべて`factory`ワークスペースの`f/factory/**`にある。

### workerがプロセスを作れなくなったとき

workerのコンテナは、`init: true`でdocker-initをPID 1にし、終了した子プロセスを回収する。ジョブが起こすgit、gh、esbuildの子プロセスは、親より長く残ることがある。initが無いと、回収されないプロセスが上限を使い切り、すべてのジョブが`errno=11`(EAGAIN)で失敗する。
上限は、defaultのworker(`windmill_worker`)が`pids: 1024`、nativeのworker(`windmill_worker_native`)が`pids: 512`である。
defaultのworkerは検査コマンドを動かすので、その分を足している([プロセス数の上限の決め方](security.md#プロセス数の上限の決め方))。
Console用のworker(`windmill_worker_console`)は`pids: 256`である。

同じ症状が出たら、使用量を確かめてからworkerを再起動する。

```bash
mise exec -- docker compose -f infra/docker-compose.yml exec windmill_worker cat /sys/fs/cgroup/pids.current
mise exec -- docker compose -f infra/docker-compose.yml restart windmill_worker
```

## 秘密をローテーションする

1. GitHubのPAT(`GITHUB_TOKEN`、`CONSOLE_GITHUB_TOKEN`)かClaude CodeのOAuthトークンを発行し直す。手順は[セキュリティ](security.md)にある。
2. 新しい値を`mise.local.toml`に投入する。コマンドは[セットアップ](setup.md)にある。
3. `mise run bootstrap`を実行し直す。`bootstrap.sh`は冪等で、既存のWindmillの変数を新しい値で上書きする。
4. `CONSOLE_GITHUB_TOKEN`は、`bootstrap`ではなく`mise run up`で反映する。`console_fetcher`のコンテナが新しい値で作り直される。

## バックアップ

Windmillのデータ(ワークスペースの設定、Data Table、ジョブの履歴など)は、すべて`db_data`というDockerのvolume(Postgres)にある。バックアップの対象はこのvolumeである。

> [!WARNING]
> `mise exec -- docker compose -f infra/docker-compose.yml down -v`は、`db_data`を含むすべてのvolumeを消す。消したデータは戻せない。

## 保持期間

DBの掃除のスケジュール(`cleanup_db`、毎日03:30)が、保持期間を過ぎたレコードを消す。日数はどちらも`f/factory/factory_config`で変えられる。

| 対象 | 保持期間 | 設定 |
| --- | --- | --- |
| 終端の状態になった作業項目と、それに連なる記録 | 90日 | `retention_work_items_days` |
| 監査の作業項目とレポート・提案 | 監査完了(`audited`)から90日 | `retention_work_items_days` |
| 失敗の記録、デプロイの記録、解決済みの通知(解決の時刻から数える) | 30日 | `retention_logs_days` |
| 判定済みのmainのCIの記録(最後の更新から数える。判定を待つ記録と、各リポジトリの最新の記録は消さない) | 30日 | `retention_logs_days` |
| 判定済みのPRのCIの記録(最後の更新から数える。判定を待つ記録と失敗を直している記録は消さない。各PRの最新の記録は、保持期間の4倍まで残す) | 30日(各PRの最新の記録は120日) | `retention_logs_days` |
| workerの負荷の記録(測った時刻から数える) | 30日 | `retention_logs_days` |

workerの負荷の記録(`worker_samples`)は、測った時刻(`sampled_at`)から30日を過ぎた行をすべて消す。
1日に720行が増えるので、掃除が毎日動いていれば、行数は約2.2万行で頭打ちになる。
次の掃除の直前は、31日分の約2.2万行である。
掃除が失敗した日や、`retention_logs_days`を延ばしたときは、行数が増える。

`retention_logs_days`を1にすると、03:30の掃除が、前日の00:00から03:30(JST)の標本を消す。
たとえば09:00に前日の標本を読む日次のまとめは、前日の冒頭が欠ける。
2以上なら欠けない。
直近の3時間を読む閾値の判定は、1でも欠けない。

「情報」の未解決の通知は、作成から30日たつと削除せず解決済みにする。
Consoleの**システム**の「情報の通知」から7日で外れて誰も解決しないので、溜まり続けないようにするためである。
解決者は`cleanup_db`と記録され、解決済みの履歴に残る。その後は上の表のとおり、解決の時刻から30日で消える。

終端の状態は、承認済み、人の対応待ち、期限切れ、失敗、レビュー済み、再レビュー依頼、ブロック、キャンセル、PR作成済み、監査完了である。PR作成済みの作業項目は、PRがopenのままでも90日で消える。

作業項目を消すと、外部キーの`ON DELETE CASCADE`で次の記録も消える。

- 要件定義のドラフト
- 承認の履歴と承認依頼
- 状態遷移の履歴(`work_item_events`)
- Claudeの実行の記録(`agent_runs`)

Claudeの実行の記録は、コスト分析(`v_agent_cost_daily`)の元データである。コスト分析を保持期間より長く見たいときは、`retention_work_items_days`を延ばす。

作業項目を消すときは、その要件定義のディレクトリも消す。ディレクトリは`requirement_drafts.doc_dir`が指す場所である。workerの`/var/lib/factory/requirements/<owner>/<repo>/issue-<N>/wi-<id>/`以下にある。

この削除はDBの行の削除とは別の処理である。失敗しても、ほかの掃除とDBの削除は止まらない。

未解決のお知らせは消さない。消した件数は`cleanup_runs`テーブルに記録し、翌朝09:00の日次サマリーの「DB掃除」欄に出す。

同じIssueの作業項目がすべて消えた後にそのIssueを拾い直すと、サイクルの番号は1から振り直す。番号は残っている行の最大値から決めるためである。過去の通知やDiscordの履歴にあるサイクルの番号と重なることがある。
