# PR本文の書き方

PR本文は、レビュアーが差分を開く前に、何が変わり、何を見ればよいかを知るための文書である。
節の並びは`.github/PULL_REQUEST_TEMPLATE.md`に従い、文体は`factory-writing`スキルに従う。

## 読み手が追える形にする

- 結論を先に書く。何を変えたかを最初の1文に置き、理由はその後に書く。
- 要点が複数あるときは、1文に詰め込まず、箇条書きか表に分ける。1項目は2文までにする。
- 数値(ファイル数、行数、回数、時間)は、文の中へ埋めず、表か1行の項目で示す。
- 1文は1行に書き、60字を目安にする。1段落は3文までにする。
- 根拠はIssueの番号か文書の節の名前で示す。本文に経緯を長く写さない。
- 敬体(です・ます)で書き、常体を混ぜない。太字と絵文字は使わない。

## 節ごとに書くこと

| 節 | 書くこと | 書かないこと |
| --- | --- | --- |
| 概要 | 変えたものと、なぜ要るかを3文以内で書く。置き換えや削除では、消したものと残したものを分ける | 作業の経緯、試した案 |
| 受入条件 | Issueの受入条件を写し、満たしたものにチェックを付ける。マージ後に測るものは、未チェックのまま測る時期を書く。Issueが無いPRでは、このPRで満たす条件を3項目以内で書く | Issueにある条件の言い換え |
| 動作確認結果 | 実行した検証にチェックを付け、該当しないものは「該当なし」と書く | 実行していない検証へのチェック |
| 確認して欲しい点 | レビュアーに判断を求める点を、1項目1論点で並べる。規則や既定を変えた箇所、トレードオフ、範囲外にした理由がここに入る | 自明な変更の説明 |
| 関連リンク | `Closes #<番号>`を1行に1つ書く。閉じないIssueは`Refs #<番号>`にする。Issueが無ければ「なし」 | 他の節にある説明の繰り返し |
| 保護パスの変更 | 触れた保護パスと理由を書く。無ければ「なし」 | 保護パスの一覧の写し、触れていないファイルの列挙 |
| 残るリスク | 受け入れたセキュリティの指摘と、その理由を1文で書く。無ければ「なし」と書き、`/security-review`を通したときはその結果を1文で添える | 悪用の手順、秘密値、`file:line` |
| 備考 | 「開発の記録」と「Windmillへの反映」の2つの小節 | その他の雑記 |

## 開発の記録

備考の「開発の記録」には、次の3つを書く。
PRごとの作業量を測り、開発の流れを見直す材料にするためである。

- subagentの起動の回数。計画、実装、レビュー、修正を合わせた合計を書く。
- 通したレビュー。タスクごとのレビュー、`/code-review`、`/security-review`のうち、実行したものと指摘の件数を書く。
- 回数が多かった理由。起動が11回を超えたときだけ、1文で書く。

## 手順

1. テンプレートを読み、節の見出しをそのまま使う。
2. 節ごとに、表の「書くこと」に従って書く。
3. `yomiyasu`スキルで推敲する。意味と条件は変えない。
4. 本名、個人の連絡先、ホームディレクトリの絶対パス、個人の設定ディレクトリのパスが無いことを確かめる。公開リポジトリのため。
5. 本文をファイルに保存し、`gh pr create --body-file <ファイル>`で作る。既存のPRは`gh pr edit --body-file <ファイル>`で直す。
