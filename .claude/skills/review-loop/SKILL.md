# レビューのループ(review-loop)

implementerが実装し、code-reviewerとdevil-advocateが独立にレビューと反証をする。
指摘が無くなり、`mise run check`が通るまで繰り返す。
最後にsecurity-auditorを通す。

## 始める前に決めること

- 完了の条件(計画の受け入れ条件)
- 触ってよいファイルの範囲
- ラウンドの上限。既定は5ラウンドとする

## 手順

1. implementerに実装を任せる。implementerは`mise run check`が通るまで直してから返す。
2. code-reviewerとdevil-advocateを、同じメッセージで並列に起動する。
3. `[MUST]`と`[IMO]`の指摘と、devil-advocateの致命的な反証を、implementerに直させる。
4. 新しく起動したcode-reviewerとdevil-advocateで、もう一度レビューする。
5. 指摘が無くなり、`mise run check`が通るまで、手順3と4を繰り返す。
6. security-auditorを1回起動する。CriticalかHighがあれば、手順3に戻る。
7. 文書を変えたときは、doc-writerに文書の検査を任せる。
8. 完了の報告を返す。

上限のラウンドに達したとき、またはセッションの利用の上限が近いときは、そこで止めて残った指摘を報告する。
1回だけ再試行して止めることはしない。

## subagentの起動の仕方

- 名前(`name`)を付けずに、非同期で起動する。名前を付けると、結果が親に届かないことがある。
- プロンプトに「結果は最終回答として返し、ファイルに書かない」と書く。
- レビューは毎ラウンド新しく起動する。同じレビュアーを続けると、前の判断に引きずられる。
- 前のラウンドで決着した論点を1〜2行にまとめて渡し、蒸し返しを防ぐ。
- implementerを同時に2つ以上動かすときは、2つ目から`isolation: "worktree"`で起動する。同じ作業ツリーで変更がぶつかるため。

## 指摘の扱い

- 指摘は、コードを読んで正しいかを確かめてから直す。
- 誤った指摘は直さず、根拠を「決着した論点」に書いて次のラウンドに渡す。
- `[NITS]`と`[Q]`は、親が直すか答えるかを決める。
- 同じ指摘が2ラウンド続けて直らないときは、直し方ではなく前提を疑い、原因を調べ直す。

## 完了の報告

完了の報告には、作業範囲、検証結果、自己確認に加えて、次を載せる。

- ラウンドの数と、ラウンドごとの指摘の数
- security-auditorの結果
- 残った指摘と、直さなかった理由

PRを作った後は、Factoryの`pr_review`(`factory:review`ラベル)が別のレビューとして加わる。
